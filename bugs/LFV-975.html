Flexible query parser prints small boosts in E-notation: ab^0.0009 comes back as ab^9.0E-4, which it cannot parse

BoostQueryNode.toQueryString() prints every nonzero boost below 0.001 with Float.toString, so ab^0.0009 comes back as ab^9.0E-4, text the same parser rejects. The query that actually runs is correct; only code that prints node trees and reads the text back is hit.

The finding in 30 seconds

#

How Java prints a float, and what the query syntax accepts

#
  1. Float.toString writes plain decimals only from 0.001 up to just below 10,000,000 (0.5, 2.5). Outside that range it uses scientific notation: 0.0009f prints 9.0E-4.
  2. The query syntax after ^ accepts only digits with an optional .digits (2, 0.5, 0.0009). It has no exponent, so 9.0E-4 is not a number to it.

The finding, step by step

#
  1. Parse ab^0.0009 with the flexible StandardSyntaxParser, the syntax parser behind StandardQueryParser. The tree is a BoostQueryNode with boost 0.0009.
  2. Print the tree with toQueryString(new EscapeQuerySyntaxImpl()). You expect text the parser reads back: the method is documented to produce "a query string understood by the query parser".
  3. Instead you get f:ab^9.0E-4. The node prints the boost with Java's Float.toString, which switches to scientific notation below 0.001. Boosts above 2^63 are hit too: 1e19 prints 1.0E19.
  4. Parsing f:ab^9.0E-4 again throws ParseException: after ^ the grammar accepts only digits with an optional .digits. Before 9.0 the same text silently became a different query, f:ab^9 f:E-4.
  5. Search is unaffected: StandardQueryParser.parse builds the right boost. The fuzzy node has the same pattern in a different method, and there it is silent today: ab~0.0001 prints ab~1.0E-4, which re-parses as ab~2 plus an extra term.

Who is affected

#

Applications that print a flexible-parser syntax tree, a hand-built boost node or a tree with a configured field boost via toQueryString, then parse or forward the text, when a boost is below 0.001 (usually a computed one) or above 2^63. Default configuration. Searches built by StandardQueryParser.parse are unaffected.

Mechanism, terms and numbers696 words

The flexible query parser reads a boost ^N into a BoostQueryNode holding a float. To print it, toQueryString() and toString() write a whole-number boost as a long and every other boost with Float.toString, which uses scientific notation below 0.001. So ab^0.0009 prints f:ab^9.0E-4. The grammar's number token has no exponent, so the same parser rejects that text with ParseException; before 9.0.0 it silently read it as a different query (f:ab^9 f:E-4). Above 2^63 the whole-number check overflows and 1e19 prints 1.0E19, with the same result. An exhaustive check ran the real printer on all 2,139,095,040 non-negative finite floats and classified its output with a model of the grammar's number token (validated against the real parser in 761,082 checks): exactly the boosts in (0, 0.001) and above 2^63 print text that does not parse back; every other boost round-trips. That breaks the documented promise that a node tree prints "a query string that can be parsed back by the original text parser". Original parsing and search are unaffected: the Query built from the original text is correct, and the impact appears only when printed node text is reused as query syntax. FuzzyQueryNode has the same pattern in a different method (ab~0.0001 prints ab~1.0E-4), and there the re-parse silently builds a different query. The fix prints a plain decimal (BigDecimal.toPlainString) in both nodes.

The code

#
  • Parse side. The grammar's Boost rule reads '^' <NUMBER> and builds new BoostQueryNode(node, Float.parseFloat(...)) (StandardSyntaxParser.jj:695-702, :115-116). The node stores a float (BoostQueryNode.java:33).
  • Print side (BoostQueryNode.java:80-84):
private CharSequence getValueString() {
  Float f = Float.valueOf(this.value);
  if (f == f.longValue()) return "" + f.longValue();   // whole numbers up to 2^63
  else return "" + f;                                  // Float.toString: 9.0E-4, 1.0E19
}

toQueryString returns the child's text + "^" + getValueString() (:91-95), and toString prints <boost value='...'> with the same helper (:86-89).

  • The grammar. NUMBER is (<_NUM_CHAR>)+ ( "." (<_NUM_CHAR>)+ )? with no exponent (StandardSyntaxParser.jj:160), while TERM (:161) accepts digits, ., E and -. By longest match 9.0E-4 lexes as one term, so Boost ::= '^' <NUMBER> (:688-703) fails.

Why exactly two ranges fail

#

Float.toString is plain only for magnitudes in [10^-3, 10^7). Every non-integral float is below 2^23, and integral floats up to 2^63 take the long branch, so [0.001, 2^63] always prints plainly. Below 0.001 the else branch prints 9.0E-4. Above 2^63 longValue() saturates at Long.MAX_VALUE, the equality fails and 1e19 prints 1.0E19. An exhaustive run printed all 2,139,095,040 non-negative finite floats with the real BoostQueryNode and classified each output with a model of the NUMBER token (the model agreed with the real parser in all 761,082 real-parser checks on a sample around the notation switches and at random). It found 981,668,462 failures in (0, 0.001) and 545,259,519 above 2^63, and none elsewhere. A grid through 15 host constructs (term, phrase, group, ranges, wildcard, regexp, ...) gave 5,700 ParseExceptions in 19,620 checks and no silent difference.

The same pattern in the fuzzy node

#

FuzzyQueryNode.toQueryString appends "~" + this.similarity (FuzzyQueryNode.java:50-57). The grammar's number after ~ is optional (StandardSyntaxParser.jj:712-729), so f:ab~1.0E-4 re-parses without error as ~ with the default 2 edits plus a separate term 1.0E-4. ab~0.0001 builds f:ab~1; its printed text builds f:ab~2 f:1.0e-4, which matched 1 document instead of 0 on a one-document index. That witness is narrow: the edit count changes only for 1-2 character terms (FuzzyQuery.floatToEdits already gives 2, the cap, for 3 or more, so abcd~0.0001 builds f:abcd~2). The extra clause is there for every term: under the default OR operator it widens the query (f:abcd~2 f:1.0E-4), under AND it narrows it (+f:abcd~2 +f:1.0E-4), and what it matches depends on the analyzer.

What is not affected

#

BoostQueryNodeBuilder copies getValue() into the BoostQuery (BoostQueryNodeBuilder.java:48), so StandardQueryParser.parse("ab^0.0009", "f") searches with boost 0.0009. Apart from the node printers themselves (composite nodes print their children; IntervalQueryNode.toString() returns its own toQueryString), Lucene puts toQueryString output only into exception messages (for example QueryTreeBuilder.java:161); it never parses it again.

Exposure and likelihood178 words
  • Who. Code that turns node trees back into text to log, display, cache, forward or rewrite a query and then parses it again. The usual source is the syntax tree from StandardQueryParser.getSyntaxParser().parse(text, field), plus hand-built BoostQueryNode trees and processed trees with a configured field boost (setFieldsBoost(Map.of("title", 0.0005f)) prints title:lucene^5.0E-4). No option is needed.
  • Trigger. A boost below 0.001 or above 2^63. Such boosts mostly come from code that computes them; a 2019 java-user post shows a client generating foo:bar^2.77E-4.
  • Effect. Since 9.0.0 the printed query cannot be parsed again (ParseException), a loud failure. From 2.9.0 to 8.11.4 it silently re-parsed as a different query (f:ab^9 f:E-4). The fuzzy leg is silent on current releases.
  • Not affected. Search results: the query is built from the exact float. Lucene's own code never re-parses the text.
  • Likelihood: rare. It needs both the print-and-reuse pattern and an unusual boost; it is deterministic when both are present, and no matching public report was found in the recorded searches, although the code dates from 2.9.0 (2009).

Why it looks unintended

#
  • The javadoc promises "a query string understood by the query parser"; the package doc, one that "can be parsed back by the original text parser".
  • Upstream fixed the same broken round trip for range nodes as a bug (GITHUB#7865, Lucene 11.0.0).
  • ab^0.0009 is ordinary syntax: the parser accepts it and builds the right boost, then prints text it rejects.
The full argument167 words
  • The contract: QueryNode.java:26 ("convert to a query string understood by the query parser"); core/nodes/package-info.java:42-43 ("A query node tree can also generate a query string that can be parsed back by the original text parser, at this point only the standard lucene syntax is supported."). Both date from 2.9.0.
  • Upstream enforces it: GITHUB#7865, fixed by #14697 (merged 2025-05-29): "AbstractRangeQueryNode#toQueryString(EscapeQuerySyntax) now returns a string which can be parsed back into the original node" (lucene/CHANGES.txt:296-298, 11.0.0 bug fixes), with TestAbstractRangeQueryNode parsing the printed string back.
  • Ordinary input: StandardQueryParser's javadoc documents "a floating-point weight boost" (jones^2 OR smith^0.5) with no lower bound, and 0.0009 is even inside the class javadoc's own (stale) range "0.0 to 1.0".
  • The grammar was never meant to take exponents (a 2006 java-user reply about the classic parser: scientific notation would be a new feature; for the flexible grammar this is an inference), so the printer is the place to fix.
  • Tests: no upstream test references BoostQueryNode or asserts its printed form.
The devil's-advocate check272 words

The strongest case for "intended": in a 2017 java-user thread about range queries parsed twice, a committer replied: "There has never been a guarantee that going back and forth between a parsed query and its string representation is idempotent. so this isn't supported." Add that Float.toString is the normal Java rendering, that the grammar has no exponent on purpose, that Lucene uses toQueryString only for messages, that processor-only nodes print unparseable text ([TP[...]]), that the open #8667 (LUCENE-7616) calls the method "a design error" that "could never work as currently designed" (for custom syntaxes), and that BoostQuery.toString prints E-notation too.

Our answer, and its limits: in the same thread a PMC member replied "Why don't we fix this in Lucene? ... Could you open an issue and add a patch?", and the project later fixed exactly that range case as a bug (#7865 / #14697). The written contract says parse-back; Query.toString makes no such promise. #8667 is about custom syntaxes, while this is standard syntax to standard syntax, and StandardSyntaxParser produces BoostQueryNode from input it accepts. A grammar without exponents points at the printer as the fix site. This is a credible case for a bug, not a proof: #7865 concerned range nodes, so it is a precedent rather than a ruling on every node, and the processor-only nodes show the promise is not kept everywhere. Verifiers, the adjudication and a tie-break rejected the intended-behaviour case and a read-only cross-model review rated it weak; a later cross-model fact check rated the intended-behaviour case moderate for the boost leg, strong for boosts above 2^63 only, and weak for the fuzzy leg.

Suggested fix

#

Recommended Print a plain decimal in both nodes (validated)

Print a plain decimal: in BoostQueryNode.getValueString(), replace the Float.toString fallback with new BigDecimal(f.toString()).toPlainString() (Infinity and NaN unchanged), and do the same in FuzzyQueryNode.toQueryString(). 0.0009 then prints 0.00090, which parses back; boosts that printed correctly before are unchanged. It passes the repro and the whole queryparser module.

private CharSequence getValueString() {
  Float f = Float.valueOf(this.value);
  if (f == f.longValue()) return "" + f.longValue();
  // The grammar's NUMBER token has no exponent: print a plain decimal, never Float.toString's
  // E-notation (9.0E-4, 1.0E19), which does not parse back.
  else if (f.isInfinite() || f.isNaN()) return "" + f;
  else return new BigDecimal(f.toString()).toPlainString();
}

Print a plain decimal in both nodes (validated) (recommended)

#

In BoostQueryNode.getValueString() keep the whole-number branch and Float.toString for Infinity and NaN, and otherwise print new BigDecimal(f.toString()).toPlainString(). In FuzzyQueryNode.toQueryString() print new BigDecimal(Float.toString(similarity)).toPlainString() for finite values in both return lines. +14/-3 in the two files, including the imports. The boost half alone fixes this repro; the fuzzy half fixes the merged fuzzy leg.

private CharSequence getValueString() {
  Float f = Float.valueOf(this.value);
  if (f == f.longValue()) return "" + f.longValue();
  // The grammar's NUMBER token has no exponent: print a plain decimal, never Float.toString's
  // E-notation (9.0E-4, 1.0E19), which does not parse back.
  else if (f.isInfinite() || f.isNaN()) return "" + f;
  else return new BigDecimal(f.toString()).toPlainString();
}

Trade-offs

  • BigDecimal(Float.toString(f)) is the exact decimal Float.toString chose, so its plain form parses back to the identical float. Text that was already plain is unchanged (0.5, 2.0).
  • Cosmetic: 0.0009 prints 0.00090 and the fuzzy ~0.0001 prints ~0.00010 (the trailing zero comes from 9.0E-4); 1e19 prints 10000000000000000000.
  • Printing only; one BigDecimal per printed non-integral value. Parsing does not change.
  • Visible output: toString() shares the helper, so <boost value='9.0E-4'> becomes <boost value='0.00090'>; exact-string tests, snapshots or log parsers that captured the old text see the new one (only for values that printed in E-notation). Very small values become long plain decimals: Float.MIN_VALUE prints as 48 characters (it still parses back).
  • Out of scope: negative, NaN and infinite boosts. The grammar cannot produce them (no sign after ^) and BoostQuery rejects them (BoostQuery.java:40-41); a hand-built node prints f:ab^-0.5, f:ab^NaN or f:ab^Infinity, which does not parse back with or without the fix.

Downstream note

#

The query built from the original text is unchanged; only services that log, cache or forward printed node trees as the canonical query and parse them again are hit: they get text their own parser rejects for such boosts, and for the fuzzy node a silently different query.

How it was found

#

While verifying the sibling slop-node bug, reviewers noticed that the boost node uses the same printing helper on a real float. A parse, print and re-parse probe over the node printers then showed a^0.0009 printing a^9.0E-4, and an exhaustive check of every non-negative float found exactly two failing ranges.

The method in full132 words

Method: non-formal first signal (a differential round-trip probe), then bounded-exhaustive translation validation of the stock printer and a public-API JUnit.

  • Signal. Code reading during the verification of LFV-892 (slop nodes print their int through a float) noted the lead; a planning probe (parse, toQueryString, re-parse, compare) executed it on stock main.
  • Exhaustive check. All 2,139,095,040 non-negative finite floats through the real BoostQueryNode printer against a model of the NUMBER token (the model agreed with the real parser on 761,082 checks): exactly (0, 0.001) and (2^63, max] fail; 3,515 s on 4 threads. A host-construct grid through StandardQueryParser (19,620 checks) found only loud failures.
  • Confirmation. An independent reproducer, a devil's-advocate verifier, read-only cross-model reviews (OpenAI GPT-5.6), an adjudication, the version-history runs, a prior-report search, a current-main reproducer and a tie-break checked it.

History

#

The printer dates from the flexible parser's first release, 2.9.0 (2009), and never changed. Up to 8.11.4 the printed text silently re-parsed as a different query (f:ab^9 f:E-4); since 9.0.0, after a grammar cleanup, it fails with ParseException.

Versions tested5 rows

Introduced by 343992fcbb4 "LUCENE-1567: New flexible QueryParser framework." (2009-08-03, the original contribution, GitHub #2641), which created BoostQueryNode with this printer, the exponent-free NUMBER token and the parse-back contract. Later commits only changed new Float to Float.valueOf (835de0b44d4) and reformatted it (2cbf261032d). Symptom changed by 3a92e1b93eb (LUCENE-9528 grammar cleanup, #10568, first released in 9.0.0), which removed the lexer's Boost state: before it, 9.0 became the boost and E-4 a new term. That commit is neither the cause nor a fix. A bytecode scan of all 148 final release jars from 2.9.0 to 10.6.0 (4.0.0-ALPHA and 4.0.0-BETA not scanned) finds the same printer in every one.

LFV-975, snapshot of 2026-11-08

Registry title
Flexible query parser: BoostQueryNode#toQueryString prints a boost below 0.001 (or above 2^63) in E-notation, e.g. ab^0.0009 prints ab^9.0E-4, which StandardSyntaxParser cannot parse back
Area
queryparser / flexible parser node serialization (BoostQueryNode toQueryString/toString)
Priority
Low, rank 782: The fuzzy-node leg merged into this finding re-parses silently as a different query; the boost leg has a slightly more plausible trigger, but on 9.0 and later its re-parse fails loudly.
Impact class
minor
Impact note
A round-trip (contract) defect in a utility method, with no effect on the Query that StandardQueryParser.parse builds: applications that print flexible-parser node trees with toQueryString (trees from StandardSyntaxParser or StandardQueryParser.getSyntaxParser(), processed trees that carry an application-configured setFieldsBoost value, or hand-built BoostQueryNodes) and re-parse or forward that text get a ParseException for every boost below 0.001 or above 2^63 (9.0.0 and later; on 2.9.0 to 8.11.4 the re-parse silently builds a different query, e.g. boost 9 plus an extra term E-4); inside Lucene the output only feeds exception messages; default parser configuration, any scale.
Summary
You parse ab^0.0009 with the flexible StandardSyntaxParser, print the node tree with toQueryString, and expect text that parses back to the same boost, since QueryNode#toQueryString is documented as 'convert to a query string understood by the query parser' and the package documentation says the string 'can be parsed back by the original text parser'. Instead BoostQueryNode prints f:ab^9.0E-4, because its getValueString falls back to Float.toString, which uses E-notation below 0.001 and above 2^63 (ab^10000000000000000000 prints ab^1.0E19). The grammar's NUMBER token has no exponent, so re-parsing the printed text throws ParseException; the same happens to a per-field boost such as setFieldsBoost(Map.of("title", 0.0005f)) in the processed tree (title:lucene^5.0E-4).
Introduced
343992fcbb4b31249f07354014723f18d0508d8a (LUCENE-1567 'New flexible query parser', the original contribution of the flexible query parser, svn trunk r800191, no PR; issue migrated as apache/lucene#2641), which created BoostQueryNode with this getValueString ('if (f == f.longValue()) return "" + f.longValue(); else return "" + f;'), its toQueryString, and the grammar whose NUMBER token has no exponent; the printer is unchanged since (835de0b44d4, LUCENE-1833, 2009-10-02, new Float -> Float.valueOf, same behaviour; 2cbf261032d, LUCENE-9570, 2021, reformatting) [read: git log -L and git blame -C -C -M on getValueString, git log -G on the NUMBER token; bytecode: all 147 release jars; exec: 2.9.0 fails, 2.4.1 has no flexible parser]. The symptom changed in 9.0.0 with 3a92e1b93eb (LUCENE-9528 grammar cleanup, apache/lucene#10568, PR apache/lucene-solr#1879), which removed the grammar's Boost lexical state: the printed text no longer re-parses silently into a different query but throws ParseException. That commit is neither a fix nor a regression of the printer; its discussion does not mention exponents or boost printing. (2009-08-03 (343992fcbb4, author date = commit date; the printer defect); 2020-09-18 (3a92e1b93eb author date; symptom change from silent misparse to ParseException, first released in 9.0.0))
