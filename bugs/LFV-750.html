SweetSpotSimilarity.hyperbolicTf returns max instead of min for frequencies far below its midpoint

SweetSpotSimilarity.hyperbolicTf, the S-shaped tf curve a subclass can use as its tf(), returns its maximum instead of its minimum for frequencies far below the midpoint. With factors (min 0, max 2, base 10, midpoint 400), tf(1) is 2.0 instead of 0.0, so one mention of a term outranks 400.

The finding in 30 seconds

#

Background

#
  1. tf. In ClassicSimilarity (TF-IDF), a document's score for a term is multiplied by tf(freq), a function of how often the term occurs in the document, at search time. SweetSpotSimilarity extends it.
  2. hyperbolicTf is an optional S-shaped tf curve: about min well below the midpoint xoffset, halfway at it, about max well above. The stock tf() does not use it; a subclass opts in by returning hyperbolicTf(freq) from tf().
  3. Overflow. A double holds at most about 1.8e308, so for base > 1 base^t becomes Infinity once t passes about ln(1.8e308) / ln(base): about 308 at base 10, about 2705 at the default base 1.3.

The finding, step by step

#
  1. You subclass SweetSpotSimilarity so that tf(freq) returns hyperbolicTf(freq), as its javadoc suggests, and call setHyperbolicTfFactors(0, 2, 10, 400): min 0, max 2, base 10, midpoint 400.
  2. You expect the documented S-curve: tf about 0 well below 400, 1.0 at 400, 2.0 well above, never decreasing as the frequency grows.
  3. Instead tf is 2.0, the maximum, for every frequency from 1 to 91, drops to 0.0 at 92, and only then follows the curve: 1.0 at 400, 2.0 at 800.
  4. Why: far below the midpoint Math.pow(10, 400 - freq) overflows to Infinity, the ratio -Infinity / Infinity is NaN, and the guard Float.isNaN(result) ? max : result, right only for the overflow above the midpoint, returns max.
  5. Effect: of two equally long documents (450 terms), the one with the term once scores 0.0953 and the one with it 400 times 0.0477. No error. It needs xoffset - freq above about 308 at base 10, or about 2705 at the default base 1.3.

Who is affected

#

Only applications that opt in: a SweetSpotSimilarity subclass whose tf() returns hyperbolicTf, with the midpoint far above their documents' term frequencies (more than about 2705 occurrences at the default base 1.3, 308 at base 10). The class defaults, the stock tf() and the documented example curves never trigger it.

Mechanism, terms and numbers550 words

SweetSpotSimilarity offers hyperbolicTf, a tanh-shaped tf curve "provided as a convenience for subclasses that want to use a hyperbolic tf function": about min below the midpoint xoffset, about max above it. It computes the tanh as (base^x - base^-x) / (base^x + base^-x) with x = freq - xoffset. Once |x| passes ln(Double.MAX_VALUE) / ln(base) (for base > 1: about 308 at base 10, 2705 at the default base 1.3) one power overflows to Infinity and the ratio is NaN, on either side of the midpoint. The guard return Float.isNaN(result) ? max : result; returns max for both: right above the midpoint, wrong below it, where the formula gives min. A subclass that uses hyperbolicTf as its tf() with a midpoint far above its documents' frequencies then gives the largest tf to the rarest mentions and inverts rankings, silently, in every release since 2.0.0. The class defaults, the stock tf() and the documented example curves are unaffected. A one-branch fix (use Math.tanh when the ratio is NaN) was validated.

The code (main 645d4fe14a20)

#

SweetSpotSimilarity.java:160-179:

final double x = (double) (freq - xoffset);                      // :167
final float result =
    min + (float) ((max - min) / 2.0f
        * (((Math.pow(base, x) - Math.pow(base, -x))
                / (Math.pow(base, x) + Math.pow(base, -x)))          // :174-175
            + 1.0d));
return Float.isNaN(result) ? max : result;                          // :178
  1. The formula (javadoc, :150-152): tf(x)=min+(max-min)/2*(((base**(x-xoffset)-base**-(x-xoffset))/(base**(x-xoffset)+base**-(x-xoffset)))+1). The ratio is tanh((x - xoffset) * ln(base)): -1 far below the midpoint, 0 at it, +1 far above it.
  2. Far above the midpoint (freq 800, xoffset 400, base 10: x = 400): Math.pow(10, 400) is Infinity, Math.pow(10, -400) is 0, the ratio is Infinity / Infinity = NaN, and the guard returns max = 2.0. The formula's limit is max too: this side is right.
  3. Far below the midpoint (freq 1: x = -399): Math.pow(10, 399) is Infinity and Math.pow(10, -399) is 0, so the ratio is (0 - Infinity) / (0 + Infinity) = NaN, and the same guard returns max = 2.0. The formula's limit here is min = 0.
  4. Just inside the range (freq 92: x = -308): 10^308 is still finite, the ratio is exactly -1 and the result is 0.0. So tf falls from 2.0 at freq 91 to 0.0 at freq 92.
  5. Where it reaches scores. The TF-IDF scorer multiplies tf(freq) by the query weight at search time (TFIDFSimilarity.java:469). The stock SweetSpotSimilarity.tf delegates to baselineTf (:122-130), so only a subclass whose tf() returns hyperbolicTf is affected; no non-test code in Lucene calls hyperbolicTf.

Overflow points

#

For base > 1, hyperbolicTf returns max wrongly when xoffset - freq is above about 709.78 / ln(base): about 2705 at base 1.3 (the default), 1024 at base 2, 710 at e, 308 at base 10, 154 at base 100. A verifier measured the first failing xoffset at freq 1 for 14 bases (2707 at base 1.3, 1025 at 2, 711 at e, 310 at 10, 156 at 100); each matched this threshold.

The numbers

#

Factors (0, 2, 10, 400): tf = 2.0 for freq 1 to 91, 0.0 at 92, 1.0 at 400, 2.0 at 800. The exhaustive check over 720,000 inputs found 37,209 mismatches with the formula, every one of them this fallback, and no other kind.

Exposure and likelihood262 words
  • Who. Opt-in only. The class javadoc says "baselineTf and hyperbolicTf functions are provided, which subclasses can choose between" (SweetSpotSimilarity.java:28-29), and the upstream test builds exactly such a subclass (TestSweetSpotSimilarity.java:207-213). Downstream, Solr's SweetSpotSimilarityFactory builds one from the hyperbolicTfMin/Max/Base/Offset schema settings, without a range check (read in Solr's source, not run).
  • When. xoffset - freq above about 2705 at the default base 1.3 (a midpoint of thousands of occurrences), or above 308 at base 10 (a steep, near step-like curve with a midpoint of hundreds). The class author's advice is to pick "the value that makes sense for your data", and that for books or encyclopedia articles "the sweetspots are going to be much larger" (java-user@, 2012), so very long documents are where such a setting is plausible.
  • Not affected (executed): the class defaults (0, 2, 1.3, 10), the four curves in the shipped doc-files/ss.gnuplot and the upstream test factors (3.3, 7.7, e, 5): 0 mismatches over freq 1..100000.
  • Effect. Once configured it is deterministic: every document whose frequency is below the overflow point gets the largest possible tf, documents just above it get about the smallest, and rankings invert. No exception, assertions on and off. Values stay inside [min, max], so range checks do not notice.
  • Nothing is written to the index. tf is applied at search time, so a fixed jar corrects existing indexes without reindexing.
  • Not claimed: an effect on impact-based top-k pruning (WAND/MaxScore). It is plausible, since scores must not decrease with freq, but it was not executed.
  • How likely: rare. No report in 20 years.

Why it looks unintended

#
  • The javadoc writes the formula out, min+(max-min)/2*(tanh((x-xoffset)*ln(base))+1); below the midpoint it tends to min.
  • SimScorer#score: "Score must not decrease when freq increases"; this tf falls from 2.0 at freq 91 to 0.0 at 92.
  • The NaN guard is right only above the midpoint, the only side the upstream test reaches (xoffset 5, freq up to 1000).
The full argument226 words
  • The formula is the spec. The method javadoc gives it exactly (SweetSpotSimilarity.java:150-152); setHyperbolicTfFactors calls xoffset "the midpoint of the hyperbolic function" (:75); the shipped doc-files/ss.gnuplot:47 plots the same formula. The class author: "The functions are pretty clearly spelled out in the javadocs" (java-user@, 2012), and of the default curve on dev@ (2006): "~2 for all values greater then 15, and ~0 for all values less then 5".
  • Monotonicity is a contract. Similarity.java:207-209: "Score must not decrease when freq increases, ie. if freq1 > freq2, then score(freq1, norm) >= score(freq2, norm)". The TF-IDF scorer multiplies tf by a fixed positive query weight and norm (TFIDFSimilarity.java:469-471), so a tf that falls from 2.0 at freq 91 to 0.0 at 92 makes the score fall too. TFIDFSimilarity.java:342-344: tf implementations "usually return larger values when freq is large".
  • The guard was only exercised on the correct side. TestSweetSpotSimilarity.java:205-226 uses factors (3.3, 7.7, e, 5) and freq 1..1000; with base e the power overflows only for freq >= 715, above the midpoint. It checks 3.3 <= tf <= 7.7, tf(5) = 5.5 and tf(0) = 0, nothing below the midpoint.
  • History. The guard is in the first check-in (2006, LUCENE-577 / #1655), which describes hyperbolicTf as "available for subclasses to call from their own tf functions" and never discusses overflow.
The devil's-advocate check113 words

The strongest case for "intended": the NaN-to-max guard is deliberate code, it keeps the value inside the documented bounds (:71-72: min and max are "the minimum/maximum tf value to ever be returned"), and the trigger factors are unusual.

Why it fails: staying inside [min, max] is necessary, not sufficient. The documented formula, the plotted curve and the author's own description all put the value near min there; returning max makes tf decrease with freq, which SimScorer#score forbids; and the only evidence of the guard's purpose, the upstream test, reaches only the upper overflow. Rarity lowers the impact; it does not make the behaviour intended. All verifiers rated the intended-behaviour argument weak.

Suggested fix

#

Recommended Fall back to Math.tanh when the ratio is NaN (validated)

When the Math.pow ratio is NaN (a power overflowed on either side of the midpoint), use Math.tanh(x * Math.log(base)), the same quantity computed without overflow. Values that are finite today do not change; the repro, TestSweetSpotSimilarity and the whole misc module (317 tests) pass.

double ratio =
    (Math.pow(base, x) - Math.pow(base, -x)) / (Math.pow(base, x) + Math.pow(base, -x));
if (Double.isNaN(ratio)) {
  // base^x or base^-x overflowed to Infinity, far above or far below xoffset; the ratio is
  // tanh(x * ln(base)), which goes to +1 above the midpoint and to -1 below it (for base > 1)
  ratio = Math.tanh(x * Math.log(base));
}
final float result = min + (float) ((max - min) / 2.0f * (ratio + 1.0d));

Fall back to Math.tanh when the ratio is NaN (validated) (recommended)

#

In hyperbolicTf (SweetSpotSimilarity.java:169-176), compute the ratio first and, when it is NaN, replace it with Math.tanh(x * Math.log(base)) (+8/-8 lines).

double ratio =
    (Math.pow(base, x) - Math.pow(base, -x)) / (Math.pow(base, x) + Math.pow(base, -x));
if (Double.isNaN(ratio)) {
  // base^x or base^-x overflowed to Infinity, far above or far below xoffset; the ratio is
  // tanh(x * ln(base)), which goes to +1 above the midpoint and to -1 below it (for base > 1)
  ratio = Math.tanh(x * Math.log(base));
}
final float result = min + (float) ((max - min) / 2.0f * (ratio + 1.0d));

Trade-offs

  • No change where the code works today. Only the NaN branch changes, so every finite value stays bit-identical: over freq 1..100000 the stock and fixed values differ only at the overflow points (91, 294 and 76 of them in three trigger configurations) and nowhere for the defaults, the gnuplot curves and the upstream test factors.
  • Upper side unchanged in effect. Above the midpoint tanh gives +1, so the result is min + (max - min) in float, the value the finite path already returns just below the overflow point; no tf above max and no decreasing step in the eight probed configurations.
  • Also covers the base < 1 side case (a decreasing curve), where the stock guard returns max far above the midpoint. The final isNaN guard stays for NaN factors.
  • Cost. The extra log and tanh run only on overflow; no benchmark was run.

Always compute Math.tanh(x * Math.log(base)) (validated on the repro and the closest suite)

#

Replace the Math.pow ratio everywhere with Math.tanh(x * Math.log(base)), which cannot overflow (+2/-7 lines).

// (base^x - base^-x) / (base^x + base^-x) is tanh(x * ln(base)); Math.tanh does not overflow

    min + (float) ((max - min) / 2.0f * (Math.tanh(x * Math.log(base)) + 1.0d));

Trade-offs

Simpler, and no Math.pow at all, but a few finite values change: by up to 4.4e-16 absolute, at values near min (the largest: 4.3785993E-9 becomes 4.3785997E-9), at 3, 28 and 1 points of the three trigger configurations; none for the defaults, gnuplot curves and upstream test factors over freq 1..100000. Return min or max by the sign of x (not recommended, not run)

#

return Float.isNaN(result) ? (x > 0 ? max : min) : result;

Trade-offs

The smallest diff, but right only for base > 1: for base < 1 the limits swap, so it would need (x > 0) == (base > 1). It keeps two hand-coded limits next to a formula that already has them; A and B follow the formula for every finite base > 0. A javadoc-only limit (xoffset below ln(Double.MAX_VALUE) / ln(base), about 308 at base 10) would avoid the overflow, since freq is always positive, but it would forbid long-document midpoints and still return max silently above the limit; the code fix is one branch.

How it was found

#

A bounded-exhaustive check compared hyperbolicTf on the stock jar with its javadoc formula over 720,000 inputs (freq 1..5000, 6 bases, 8 midpoints, 3 min/max pairs): 37,209 mismatches, every one this NaN fallback returning max where the formula gives min, and no other kind. A public-API JUnit then confirmed it, including the ranking inversion.

Hits only applications that score with a SweetSpotSimilarity subclass whose tf() returns hyperbolicTf (the use its javadoc names; in Solr, SweetSpotSimilarityFactory with the hyperbolicTf* settings builds exactly such a subclass [read]) and that set the midpoint far above the term frequencies their documents have (xoffset - freq above about 2705 at the default base 1.3, 1024 at base 2, 710 at base e, 308 at base 10): every such low frequency then gets the maximum tf, tf falls to about min just above the overflow point, and rankings invert, with no error, with -ea and -da, in every release since 2.0.0; the stock SweetSpotSimilarity.tf (baselineTf), the class defaults, the shipped gnuplot curves and the upstream test factors are unaffected, nothing is written to the index, and any effect on impact-based top-k pruning was not executed.
Summary
You subclass SweetSpotSimilarity so that tf() returns hyperbolicTf(freq), as its javadoc suggests, call setHyperbolicTfFactors(0, 2, 10, 400) and search, expecting the documented curve min+(max-min)/2*(tanh((freq-xoffset)*ln(base))+1): a tf near min (0) for frequencies far below the midpoint 400, rising to max (2) above it. Instead hyperbolicTf returns the maximum 2.0 for every frequency from 1 to 91 and drops to 0.0 at 92, so a document that contains the term once outranks an equally long one that contains it 400 times. Far below the midpoint Math.pow(base, xoffset - freq) overflows to Infinity (once xoffset - freq exceeds about 308 at base 10, about 2705 at the default base 1.3), the ratio becomes NaN, and the guard 'return Float.isNaN(result) ? max : result', which is right only for the overflow above the midpoint, returns max.
