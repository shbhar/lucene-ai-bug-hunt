SortedSetDocValuesWriter counts each growth of its per-document value buffer twice in IndexWriter's RAM usage

Since 8.11.0, SortedSetDocValuesWriter adds each growth of its per-document value buffer to IndexWriter's RAM estimate twice: a document with 9 values in one field adds 32 bytes instead of 16, one with 100,000 values 0.8 MB instead of 0.4 MB. Flush-by-RAM fires early; no data or result is wrong.

The finding in 30 seconds

#

One buffer growth reaches IndexWriter's RAM counter twice: directly after the grow, and again through sizeOf(currentValues).

Background: how IndexWriter counts buffered RAM

#
  1. IndexWriter adds up the heap its buffered documents use (ramBytesUsed()) and flushes a segment when the sum reaches the RAM buffer, 16 MB by default.
  2. Each doc-values field has a writer that reports what it allocates to that sum.
  3. A SORTED_SET field's writer keeps the current document's term ids in an int buffer of 8 slots and grows it with ArrayUtil.grow when a document has more values. The buffer never shrinks.

The finding, step by step

#
  1. You index one document with 8 values of a SortedSetDocValuesField named f, then one with 9 values (all the term a). The writer keeps the current document's values in an int[8] buffer; the 9th value grows it to int[12], 16 bytes more.
  2. You expect IndexWriter.ramBytesUsed() to rise by those 16 bytes.
  3. Instead it rises by 32. The writer adds the growth right after ArrayUtil.grow, then adds it again when it recomputes its own size, which since 8.11.0 includes sizeOf(currentValues). Nothing takes the first charge back; it leaves only with the whole per-thread writer, when that writer flushes or is aborted.
  4. It scales with the value count: a document with 100,000 values grows the buffer by 406,016 bytes and adds 812,032. Flush-by-RAM fires that much earlier; no data, exception or search result changes.

Who is affected

#

Writers indexing documents with more than 8 values in one SORTED_SET doc-values field, default settings included. The extra is about 4 bytes per buffer slot of the field's largest per-document value count, per field and indexing thread: a few hundred bytes at 100 values, 0.4 MB at 100,000. The estimate reads high: earlier, smaller flushes; no wrong data.

Mechanism, terms and numbers496 words

While a document is indexed, SortedSetDocValuesWriter keeps that document's term ids in int[] currentValues (8 slots at first) and grows it with ArrayUtil.grow when the document has more values. Each growth is added to the indexing RAM counter twice: once directly after the grow (SortedSetDocValuesWriter.java:209, and :153 on the addBatch path), and once more by updateBytesUsed(), which since LUCENE-10116 (8.11.0) also counts RamUsageEstimator.sizeOf(currentValues) (:221). Nothing takes the direct charge back: it leaves the counter only with the whole per-thread writer, when that writer flushes (or is discarded on abort). So a document with 9 values of one field raises IndexWriter.ramBytesUsed() by 32 bytes instead of 16, and one with 100,000 values by 812,032 bytes instead of 406,016. The extra is bounded by the largest per-document value count of the field, per field and per indexing thread; only the RAM estimate is wrong: it reads high, so flush-by-RAM fires earlier and writes smaller segments. The sibling SortedNumericDocValuesWriter counts its analogous 8-slot buffer (a long[8] there) once. The fix deletes the two direct charges.

The code (SortedSetDocValuesWriter.java at 5adff78bb168)

#
  1. :55: private int[] currentValues = new int[8];. The constructor (:77-81) puts RamUsageEstimator.sizeOf(currentValues) into the tracked bytesUsed and charges it once.
  2. addValue (:84-105) calls addOneValue (:103), then updateBytesUsed() (:104).
  3. addOneValue (:195-214): when the buffer is full, currentValues = ArrayUtil.grow(currentValues, currentValues.length + 1); and then iwBytesUsed.addAndGet((currentValues.length - currentUpto) * (long) Integer.BYTES); (:207-210): charge 1, the growth.
  4. updateBytesUsed (:216-224) recomputes newBytesUsed, which includes RamUsageEstimator.sizeOf(currentValues) (:221), and adds newBytesUsed - bytesUsed (:222): the same growth again, charge 2. bytesUsed tracks only this sum (:223), so charge 1 is never subtracted.
  5. finishCurrentDoc only resets currentUpto (:191): later documents that fit add nothing, and the extra stays in the per-thread writer's counter until that writer flushes or is aborted.
  6. The addBatch path has the same pair: addOrdinalTuples grows at :152, charges at :153 and calls updateBytesUsed() at :158 (used by the @lucene.experimental IndexWriter.addBatch with a SORTED_SET DictionaryColumn, since 10.5.0).

The sibling SortedNumericDocValuesWriter grows the same kind of buffer with no direct charge (SortedNumericDocValuesWriter.java:133-140) and counts it only through sizeOf (:142-150).

Exposure and likelihood285 words
  • Who is hit: any IndexWriter that indexes a document with more than 8 values in one SORTED_SET doc-values field, with the default configuration and codec: several SortedSetDocValuesField or KeywordField values of one name, or more than 8 SortedSetDocValuesFacetField labels, which FacetsConfig.build writes into one SORTED_SET field ($facets by default), through addDocument, updateDocument, softUpdateDocument and their batch forms; or addBatch with a SORTED_SET DictionaryColumn.
  • Size: about 4 bytes per buffer slot beyond the first 8, per SORTED_SET field and per indexing thread, bounded by the largest value count one document had in that field: a few hundred bytes at about 100 values, about 0.4 MB at 100,000, about 4 MB at 1,000,000. Against the default 16 MB RAM buffer it is small unless documents carry tens of thousands of values in one field (0.4 MB at 100,000 values is 2.5% of 16 MB); no flush-timing or segment-size experiment was run.
  • Effect: every check that reads the estimate sees the extra: IndexWriter.ramBytesUsed() itself, flush-by-RAM (which fires that much earlier and writes smaller segments), and the per-thread hard limit and stall check (DocumentsWriterFlushControl.java:246-256). No wrong data, no exception, no query effect; the double charge is an over-estimate and allocates nothing. Assertions on and off behave the same.
  • With default settings per-thread deltas under 16 KB are published later, not lost (DocumentsWriterFlushControl.java:202-223); the repro sets maxBufferedDocs only to see a 16-byte delta at once.
  • JVM: all figures are for a 64-bit JVM, as in every recorded run. On a 32-bit JVM ArrayUtil.oversize(9, 4) is 13 (ArrayUtil.java:188-198), so the direct charge is 20 bytes and the total is not exactly 2x; the growth is still charged twice (read, not run).

Why it looks unintended

#
  • The sibling SortedNumericDocValuesWriter keeps an analogous 8-slot buffer (a long[8]) and counts each growth once, through sizeOf only.
  • The direct charge was the buffer's only accounting from 2013; LUCENE-10116 (2021) added sizeOf(currentValues) as missing accounting and left the old charge in place.
  • No comment, refund, javadoc or test accepts the double charge; the RAM-buffer javadoc calls only pending deletions approximate.
The full argument182 words
  • Contract: setRAMBufferSizeMB: "the writer will flush whenever buffered documents and deletions use this much RAM" (LiveIndexWriterConfig.java:162-163); the only accounting it calls approximate is pending deletions (:174-177).
  • Sibling: SortedNumericDocValuesWriter keeps an analogous long[8] buffer (:44); :133-150 grow it with no direct charge and count it through sizeOf(currentValues) only.
  • History: the direct charge came with the original writer (2dcf80718c2, 2013), when it was the buffer's only accounting; the field comment still says bytesUsed "only tracks differences in 'pending' and 'pendingCounts'" (:52). LUCENE-10116 (#11153, #316) compared the writer with SortedNumericDocValuesWriter, found "it seems to lack of bytes used of DocsWithFieldSet and currentValues", added sizeOf(currentValues) (:80, :221) and kept the direct charge; neither the issue nor the PR (one approval, no review comments) mentions it. #16101 (2026) copied the direct charge into addOrdinalTuples.
  • Tests: no upstream test asserts this writer's buffer accounting.
  • Precedent: upstream fixed similar RAM miscounts as bugs: GITHUB#15901 ("overcounting byte vectors by 4x" in buffered vectors, 10.5.0), GITHUB#16046 and GITHUB#16389 (double-counting in ramBytesUsed, 10.5.0 and 10.6.0).
The devil's-advocate check139 words

The case for intended: Accountable.ramBytesUsed() promises only "an estimate" (Accountable.java:35), the RAM buffer is "just an indicator when to flush" (LiveIndexWriterConfig.java:169), over-counting is the safe direction (an earlier flush, never an OOM), and this writer already over-reserves on purpose (2 ints per unique term, :200-204). The extra could be read as a reserve for the moment during ArrayUtil.grow when the old and new arrays are both alive.

Why it fails: the deliberate reservation is commented and per term; this charge has no comment, no refund and no counterpart in the sibling writer, and it predates the second charge by eight years. It is an exact duplicate of one array's growth, created by a change that set out to add missing accounting. The argument is about size, not intent, which is why this is Low.

Suggested fix

#

Recommended Delete the two direct charges after ArrayUtil.grow (validated)

Delete the two iwBytesUsed.addAndGet((currentValues.length - currentUpto) * (long) Integer.BYTES) calls after ArrayUtil.grow (:153, :209); updateBytesUsed() already counts the buffer, as in SortedNumericDocValuesWriter. With it the repro and 600 tests of the closest suites pass, as do the core format, ECJ and forbidden-apis checks.

 // addOrdinalTuples (:151-154); addOneValue (:207-210) has the same line, deleted the same way
 if (currentUpto == currentValues.length) {
   currentValues = ArrayUtil.grow(currentValues, currentValues.length + 1);
-  iwBytesUsed.addAndGet((currentValues.length - currentUpto) * (long) Integer.BYTES);
 }

Delete the two direct charges after ArrayUtil.grow (validated) (recommended)

#

updateBytesUsed() runs after both call sites when they return normally (:104, :158) and counts the buffer through sizeOf(currentValues), exactly as SortedNumericDocValuesWriter does. Keep the commented 2-ints-per-unique-term reservation (:147, :200-204); optionally update the stale field comment at :52.

 // addOrdinalTuples (:151-154); addOneValue (:207-210) has the same line, deleted the same way
 if (currentUpto == currentValues.length) {
   currentValues = ArrayUtil.grow(currentValues, currentValues.length + 1);
-  iwBytesUsed.addAndGet((currentValues.length - currentUpto) * (long) Integer.BYTES);
 }

Trade-offs

  • Two deleted lines; one addAndGet per grow fewer, no other cost.
  • Like the sibling writer, it does not count the moment during ArrayUtil.grow when old and new arrays are both alive; neither did the code before 8.11.0.
  • If a cursor call throws in the middle of addOrdinalTuples, :158 is skipped: that already leaves the growth of pending, pendingCounts and docsWithField uncounted until the next updateBytesUsed() of this field, and with the fix the buffer growth waits with them. A maintainer may prefer to call updateBytesUsed() in a finally there (not tried).

Drop the sizeOf(currentValues) terms instead (not recommended)

#

Removing + RamUsageEstimator.sizeOf(currentValues) from the constructor (:80) and updateBytesUsed (:221) restores the pre-8.11 accounting of the buffer: each growth is counted once by the direct charge.

Trade-offs

  • The initial int[8] per field and thread goes uncounted again, which LUCENE-10116 set out to fix.
  • The writer stays different from SortedNumericDocValuesWriter.
  • Checked only on 9.0.0 with the 100,000-value test (passes); not run on main.

Downstream note

#

Services that index documents with very many values in one SORTED_SET field (tags, ids, facet paths) see earlier, smaller flushes; a per-document value limit also bounds the extra charge.

How it was found

#

A semi-formal proof-obligation audit of SortedSetDocValuesWriter's RAM accounting: every byte of its buffers must reach IndexWriter's counter exactly once. The value buffer's growth reaches it twice, and an executable test on main showed the 2x. Independent reviewers re-ran it, wrote their own tests and argued the case for intended behaviour.

The method in full109 words
  • Method: each use of the writer's RAM counter (SortedSetDocValuesWriter.java:74, where it is handed to the term hash, and the additions at :81, :147, :153, :204, :209, :222) was checked against the obligation that every allocated byte is charged once and given back only at flush. The direct growth charges (:153, :209) overlap the sizeOf(currentValues) term in updateBytesUsed (:221), and an executable JUnit test confirmed it on main 5adff78bb168 (2026-11-03).
  • Reviews: an independent reproduction with probes, an adversarial review by a model from another family (OpenAI GPT-5.6), an intended-behaviour review and a final review; see Independent checks.

Impact note

Summary
You index a document with many values in one SortedSetDocValuesField (here the term 'a' 100,000 times) and expect IndexWriter.ramBytesUsed() to grow by the growth of the writer's per-document int buffer, 406,016 bytes. The sibling SortedNumericDocValuesWriter charges its identical buffer once, through sizeOf only; deleting the two direct charges fixes it.
