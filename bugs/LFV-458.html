HNSW merge cannot reuse a graph of more than 805,306,368 vectors

A merge that reuses an HNSW graph of more than 805,306,368 vectors always throws BufferAllocationException: it presizes an IntIntHashMap that cannot hold that many entries. Lucene writes such a segment without error (code reading) but can then never merge it with its graph reused; 9.9.2 handled this size (its own presize failed only from 1,610,612,672 nodes).

The finding in 30 seconds

#

When Lucene merges segments it reuses the biggest HNSW graph instead of rebuilding it. The table it builds to renumber that graph's nodes cannot hold more than 805,306,368 entries.

How a merge reuses an HNSW graph

#
  1. Each segment has its own HNSW graph. Its nodes are numbered 0, 1, 2, ... in the segment's doc order; these numbers are the ordinals.
  2. A merge gives every document a new doc id in the merged segment. Rebuilding a big graph is slow, so the merge copies the existing graph and only renumbers its nodes.
  3. To renumber, it needs each old node's new ordinal. It builds a lookup table from new doc id to old node, then walks the merged documents in order and looks each one up.

The finding, step by step

#
  1. One segment holds an HNSW vector field with 805,306,369 vectors. By code reading, Lucene writes such a segment without complaint, for example by force-merging smaller ones: nothing below IndexWriter.MAX_DOCS (2,147,483,519) limits it (writing one was not run end to end).
  2. A later merge reuses that segment's graph instead of rebuilding it. To renumber the graph's nodes it first fills a lookup table from new doc id to old node, an IntIntHashMap presized to the graph's 805,306,369 nodes.
  3. You expect the merge to go on, as it does with 805,306,368 vectors and as Lucene 9.9.2 did with 805,306,369.
  4. Instead the map's constructor throws BufferAllocationException: Maximum array size exceeded for this load factor. The map keeps a quarter of its slots free and has at most 2^30 = 1,073,741,824 slots, so it fits at most 805,306,368 entries. It throws before the map's arrays are allocated.
  5. Every merge that reuses the graph fails the same way, so the segment can never be merged with its graph reused. By code reading, inside IndexWriter each attempt first rewrites the segment's other data and flat vectors, and the failure is tragic: the writer rolls back to the last commit and closes.

Who is affected

#

Only an index with one segment of more than 805 million vectors in one HNSW field (0.375 x MAX_DOCS), far past the default 5 GB merge cap (built by forceMerge, a raised cap, a custom merge policy or addIndexes), when a merge reuses that graph. Default codec, both mergers, 9.10.0 to 10.6.0, main and branch_11x (10.4.0, 10.5.0: custom codec only).

Mechanism, terms and numbers574 words

When a merge reuses an existing segment's HNSW graph, IncrementalHnswGraphMerger.getNewOrdMapping first maps new doc ids to the graph's old ordinals in an IntIntHashMap presized to the graph's node count. Lucene's hash containers default to a 0.75 load factor and cap the table at 2^30 slots, so the constructor throws BufferAllocationException for more than 805,306,368 expected entries, about 0.375 x IndexWriter.MAX_DOCS. No HNSW limit is documented or enforced below MAX_DOCS, so, by code reading, Lucene writes a segment with a bigger graph (for example by merging smaller ones) and then can never merge it again with its graph reused: every attempt throws, and by code reading IndexWriter treats it as a tragic event. The map came from #12950 (9.10.0), a box/unbox speed-up that replaced a java.util.HashMap; 9.9.2 completes the same mapping (its own presize failed only from 1,610,612,672 nodes). The repro drives the merger directly with a stub graph; no real IndexWriter merge of this size was run. The scale is extreme, the failure is loud, and nothing is corrupted.

The mechanism (main 645d4fe14a20)

#
  1. Default path. The default codec uses Lucene99HnswVectorsFormat (Lucene104Codec.java:123). On a merge, Lucene99HnswVectorsWriter.buildAndWriteGraph calls addReader for every merging segment with the field and then merger.merge(...) On main the per-field reader is itself an HnswGraphProvider (PerFieldKnnVectorsFormat.java:198, :357-369), so default-codec graphs are reused.
  2. Which graphs are mapped. addReader (IncrementalHnswGraphMerger.java:110-147) picks as base the graph with the most live vectors among those with at most 40% deletions (:133-139) and keeps every graph without deletions (:142-144). createBuilder calls getNewOrdMapping (:166); ConcurrentHnswMerger calls the same method (ConcurrentHnswMerger.java:79).
  3. The presize. getNewOrdMapping (:204-250) does new IntIntHashMap(graphReaders.get(i).graphSize) (:221) for each reused graph.
  4. The capacity. The constructor calls ensureCapacity, which computes minBufferSize(expectedElements, 0.75) before allocating (IntIntHashMap.java:85-107, :446-455). HashContainers fixes DEFAULT_LOAD_FACTOR = 0.75f (:33) and MAX_HASH_ARRAY_LENGTH = 2^30 (:48); minBufferSize throws when ceil(n / 0.75), rounded up to a power of two, exceeds 2^30 (:81-99). Largest n that fits: 805,306,368.
  5. Presizing less does not help. Growth stops at the same 2^30-slot table (nextBufferSize, HashContainers.java:56-63): 805,306,368 non-zero keys plus the separately stored key 0 (IntIntHashMap.java:120-124, growth only at :139-140). Without the presize one more entry fits at most; from 805,306,370 only another structure fixes it.
  6. In IndexWriter (code reading, not executed). The exception is a RuntimeException, not a MergeAbortedException, so handleMergeException rethrows it (IndexWriter.java:5043-5057), IndexWriter.merge calls tragicEvent(t, "merge") (:5109-5113), and the writer rolls back and closes (:6098-6106). A waiting forceMerge caller sees an IOException whose cause is this exception (:2292-2301).
  7. Where in an IndexWriter merge (code reading). The map is built in the graph phase: SegmentMerger.merge first writes the merged stored fields, norms, postings, doc values and points (SegmentMerger.java:123-158), then the vectors, where KnnVectorsWriter.merge writes the merged flat vectors in phase 1 (KnnVectorsWriter.java:133-150) and builds the graphs in phase 2 (:152-158). So each failing attempt first rewrites all of that (about 412 GB of vectors alone at 128 dimensions). The concurrent merger also allocates a FixedBitSet of maxOrd bits (about 96 MiB) before the map (ConcurrentHnswMerger.java:78).
Exposure and likelihood404 words
  • Versions through IndexWriter. With the default codec 9.10.0-10.3.2, 10.5.1-10.6.0 and main reach the line. 10.4.0 and 10.5.0 checked the per-field wrapper instead of the unwrapped reader, so with the default codec "every merge rebuilt the graph from scratch" (CHANGES entry of #16400, fixed by #16403 in 10.5.1; the issue itself is still open); there it needs a codec whose vectors format is not wrapped per field. Up to 10.3.2 only graphs without deletions are reused; since 10.4.0 the base may have up to 40% deletions. branch_11x has main's single site; branch_10_6 keeps 10.6.0's two sites (IncrementalHnswGraphMerger.java:210, ConcurrentHnswMerger.java:147).
  • How such a segment arises. Not by flushing, and not by default background merges: TieredMergePolicy caps them at 5 GB, and 805M vectors are about 412 GB of float32 data at 128 dimensions alone. forceMerge(n) overrides the cap, as do a raised maxMergedSegmentMB, a custom merge policy and addIndexes(CodecReader...), which merges the readers it is given; addIndexes(Directory...) copies a giant segment built elsewhere as it is. Two graphs of 500M and 400M vectors each map fine, so by code reading Lucene writes the 900M-vector segment (no count guard found; not run end to end); the next merge that reuses that graph fails.
  • What it costs. Every merge that reuses that graph throws, e.g. forceMerge(1) after new documents arrive (a forceMerge with nothing to merge does nothing). From 10.4.0 (10.5.1 with the default codec) a background merge can hit it too: TieredMergePolicy considers a too-large segment once both its own and the index-wide delete percentages pass the default 20% deletesPctAllowed, which may get it selected, and the graph is reused while at most 40% of it is deleted. On 9.10.0-10.3.2 a graph with deletions is not reused, so such merges rebuild it and succeed. A failing merge, by code reading, closes the writer, losing uncommitted changes, and fails again whenever a later merge reuses that graph; inside IndexWriter each attempt first rewrites the segment's other data and flat vectors before it throws.
  • Scale. Building or merging such a graph needs a very large heap: estimates range from 50-75 GB to 200-300 GB (not measured); the executed 9.9.2 mapping at this size used about 70 GiB. Open work on merge graphs larger than the heap (#16815, #15904) would make the bound easier to reach.
  • Loud, not silent. No wrong results and no corruption; the committed index stays as it was (code reading).

Why it looks unintended

#
  • No limit is documented or enforced below IndexWriter.MAX_DOCS, yet, by code reading, Lucene writes the segment it later cannot merge.
  • The cap came from #12950 (9.10.0), a speed-up that replaced a HashMap; 9.9.2 completes the same mapping.
  • #11905 fixed a smaller single-segment HNSW limit as a bug, and Test2BDocs force-merges MAX_DOCS plain documents (no vectors) into one segment.
The full argument177 words
  • No limit. IndexWriter.MAX_DOCS (IndexWriter.java:201-208, "Hard limit on the maximum number of documents that may be added to the index") is the only count limit. Lucene99HnswVectorsFormat validates only maxConn <= 512 and beamWidth <= 3200 (:102, :112, :271-283). HnswGraphMerger.merge is "Merge and produce the on heap graph" (HnswGraphMerger.java:46).
  • Written, then unmergeable (code reading). Lucene checks its intended limits before data is written (MAX_DOCS when a document is added); this one only appears one merge later.
  • Accidental origin. #12950 (49d521145de, backport 7d62b23ee90, 2023-12-15) replaced CollectionUtil.newHashMap(initGraphSize) with new IntIntHashMap(initGraphSize). The PR has no description; its only discussion is the author's own note on the hppc API. #14331 (3752dba9c51 on main, backport aa1e9f34b37 in 10.2.0) and #16794 moved the presize and kept it; neither discusses capacity.
  • Precedent. #11905 fixed an int overflow above about 16 million vectors in one segment and added the @Monster test TestManyKnnDocs.testLargeSegment (2,088,992 vectors, forceMerge(1)). Test2BDocs force-merges MAX_DOCS plain documents (no vectors) into one segment.
  • No test under lucene/*/src/test asserts this behaviour.
The devil's-advocate check243 words

The strongest case: one HNSW graph of 805M+ vectors is outside the supported envelope. In #15420 a committer (benwtrent) called merging tiny segments into one giant graph "antithetical to Lucene's design" and said "a single 6TB Lucene Segment is likely to hit other scaling issues first"; MAX_DOCS is index-wide, not a promise about one graph; IncrementalHnswGraphMerger and HnswGraphMerger are @lucene.experimental (ConcurrentHnswMerger has no tag of its own) and IntIntHashMap is @lucene.internal; the repro calls the merger with a stub graph.

Why it fails: #15420 is design advice in an RFC about another feature, not a documented limit or a won't-fix, and this failure is not limited to giant-plus-tiny merges. By code reading Lucene itself writes the segment (no count guard below MAX_DOCS; not run end to end), and Test2BDocs force-merges MAX_DOCS plain documents into one segment (the vector monster test reaches only 2,088,992 vectors, about 385x below this bound). The cap is an accident of an internal-structure swap that users cannot see or avoid except by keeping segments small. @lucene.experimental allows API changes, not merges that always throw, and by code reading the default IndexWriter path calls the same method with the same argument. The stub-graph limit stands: no IndexWriter run at this size exists. The argument bears on severity (low priority), not on intent. The cross-model fact check rated this case "moderate" and called the framing (crash, contrived, low priority) fair, provided "crash" means a merge exception, not corruption.

Suggested fix

#

Recommended Sorted (new doc, old ordinal) pairs and a merge walk instead of the hash map

Replace the hash map with one long per reused vector, (newDoc << 32) | oldOrd, sorted only if needed, and walk it alongside the merged vectors, both in new-doc order. The repro then passes with assertions on and off, and 25 HNSW, codec, kNN-query and reorder suites (577 tests) pass. It also uses less memory than the map.

Trade-offs

  • 8 bytes per reused vector, temporary, against the hash map's 10.7-21.3 bytes (8 MB against 16.8 MB at 1M vectors); no capacity limit below MAX_DOCS, which is defined to stay below the JVM array limit (IndexWriter.java:205-208).
  • No hashing on the hot path; the sort (O(n log n)) runs only for a non-monotone doc map. Not benchmarked.
  • At 805M vectors the mapping still needs about 6.4 GB of pairs plus the existing 3.2 GB old-to-new array. The repro stops at the graph copy, so later limits in a real 805M-vector merge were not tested.

What the checks validated

  • 25 suites, 577 tests, 0 failures, 18 skipped: all of org.apache.lucene.util.hnsw and org.apache.lucene.codecs.lucene99, TestLucene104HnswScalarQuantizedVectorsFormat, TestLucene104ScalarQuantizedVectorsFormat, TestKnnGraph, TestHnswMergeAbort, TestSortingCodecReader, TestKnnFloatVectorQuery, TestKnnByteVectorQuery (lucene/core), TestBPReorderingMergePolicy and TestBpVectorReorderer (lucene/misc).
  • :lucene:core:check -x test passes (google-java-format, ecj lint, forbidden APIs).
  • The sort branch: no suite above reaches it (all pass with a throw there). Index-sorted merges map each segment's docs in its own order (MultiSorter.java:111-134); reordered merges can produce any permutation, but IndexWriter wraps those readers in a SortingCodecReader (IndexWriter.java:3560-3565), which is not an HnswGraphProvider, so their graphs are not reused (IncrementalHnswGraphMerger.java:113-115). A scratch probe with a random permutation doc map (1,000 vectors) gives the expected mapping on stock and on the fix. Open PR #16879 would bring non-monotone doc maps to this method.

A dense new-doc to old-ordinal int array (the finder's sketch)

#

A per-graph int[] indexed by new doc id, grown with ArrayUtil.grow. The repro passes with it on a 12 GB heap with -ea and -da; it was not run against the module suites.

Trade-offs

Each array grows to the graph's highest new doc id, so a small graph late in the merge order costs 4 bytes per document of the whole merged segment: a memory regression for ordinary merges (code reading).

Keep IntIntHashMap with load factor 0.99

#

new IntIntHashMap(n, 0.99).

Trade-offs

Only raises the ceiling to 1,063,004,405 entries (computed), still below MAX_DOCS, and slows probing. Not a fix.

Drop the presize

#

new IntIntHashMap() and let it grow.

Trade-offs

Does not work: growth stops at the same 2^30-slot table, so at most 805,306,369 keys (including the separately stored key 0) fit.

Downstream note

#

Engines built on Lucene that let operators force-merge very large vector indexes into one segment inherit this; it fails loudly at merge time and never changes search results or stored data.

How it was found

#

Found by code reading: while modelling HNSW merges, the finder checked every int-sized structure on the merge path against IndexWriter.MAX_DOCS and computed the exact bound with a small script that mirrors the hash map's sizing. A JUnit on the real merger confirmed it, and independent verifiers reproduced it with their own tests.

The method in full91 words

A hunt unit on HNSW parallel repair (a TLA+ model of the merge task protocol plus controlled-schedule runs) had, as a standing step, to check every int-sized structure on the merge path against IndexWriter.MAX_DOCS. The presized IntIntHashMap stood out; a short script mirroring HashContainers.minBufferSize gave the largest size that fits (805,306,368) and the smallest that throws (805,306,369), and a JUnit on the stock main jar with a stub graph of that size failed with -ea and -da (2026-10-26). The signal came from code reading, not from a formal tool's output.

LFV-458, snapshot of 2026-11-08

Registry title
HNSW merge with graph reuse throws BufferAllocationException when the reused graph has more than 805,306,368 vectors
Area
search / HNSW (merge-time graph reuse: old-to-new ordinal mapping in IncrementalHnswGraphMerger and ConcurrentHnswMerger)
Priority
Low, rank 981: A default-codec HNSW merge that reuses a graph of more than 805,306,368 vectors throws on every attempt and, by code reading, closes the writer, so such a segment can never be merged; it is loud, but it needs only about 0.375 x MAX_DOCS vectors in one segment.
Impact class
crash
Impact note
Anyone on the default codec and default merger (9.10.0 to main; on 10.4.0 and 10.5.0 only with a codec whose vectors format is not wrapped per field, because there default-codec merges never reuse graphs) whose HNSW vector field has one segment of more than 805,306,368 vectors (about 0.375 x IndexWriter.MAX_DOCS, far past TieredMergePolicy's default 5 GiB merged-segment cap, so in practice built by forceMerge, a raised maxMergedSegmentMB, a custom merge policy or addIndexes, on a heap of tens to hundreds of GB) and who merges it again with its graph reused: that merge throws BufferAllocationException every time (executed at the merger API), and by code reading IndexWriter then treats it as a tragic event and closes the writer, losing uncommitted changes.
Summary
You merge an HNSW vector field in which one segment's graph has more than 805,306,368 vectors (Lucene writes such a segment without error, for example by merging smaller graphs) and expect the merge to reuse that graph as it does at any smaller size, because no HNSW vector-count limit is documented or enforced below IndexWriter.MAX_DOCS. Instead both mergers presize an IntIntHashMap to the graph size to map old to new ordinals, and that map's fixed 0.75 load factor and 2^30-slot table cap make its constructor throw BufferAllocationException ('Maximum array size exceeded for this load factor') before any other work. The merge fails again on every retry, so such a segment can never be merged with graph reuse; by code reading the IndexWriter is also closed as a tragic event.
