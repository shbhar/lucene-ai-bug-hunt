Flat Lucene104ScalarQuantizedVectorsFormat: a vector similarity search on a field with no vectors left throws NullPointerException

With the opt-in flat Lucene104ScalarQuantizedVectorsFormat, a FloatVectorSimilarityQuery on a segment whose vector field has no vectors left (every vector document deleted and merged away) throws NullPointerException instead of matching nothing. Releases 10.4.0 to 10.6.0 and main are affected.

The finding in 30 seconds

#

This flat reader's search checks only that k is not 0; it never checks that the field has vectors. An emptied field has no quantizer to score the query with.

Background: flat scalar-quantized vectors and an emptied field

#
  1. Lucene104ScalarQuantizedVectorsFormat (opt-in, since 10.4.0) stores each vector quantized to a few bits. It has no graph: its reader's search scores every vector. Before scoring, the query vector is quantized with the field's quantizer and centroid.
  2. When a merge drops every vector document of a field while other documents survive, the merged segment keeps the field's vector FieldInfo (dimension 4 in the repro) and writes 0 vectors. The reader then hands out empty vector values that have no quantizer and no centroid.

The finding, step by step

#
  1. You index 2 documents with the flat Lucene104ScalarQuantizedVectorsFormat: one with a 4-dimensional vector in field v, one without. You delete the vector document and call forceMerge(1). The segment still lists v, but holds 0 vectors.
  2. You run searcher.count(new FloatVectorSimilarityQuery.Adaptive("v", {1, 2, 3, 4}, 0f)) and expect 0, as KnnFloatVectorQuery gives on this index and the default codec and the HNSW formats give after the same steps.
  3. Instead the reader's search returns early only when k is 0, then builds a scorer over the empty vector values, whose quantizer is null: NullPointerException ... because "quantizer" is null, with assertions on and off.
  4. The HNSW reader returns early when the field has 0 vectors. The same two-line guard in this reader's two search methods makes the repro pass.

Who is affected

#

Only indexes that use the flat Lucene104ScalarQuantizedVectorsFormat for a float (or, on main, float16) vector field, once a segment lists the field with zero vectors, for example after all its vector documents were deleted. Then every FloatVectorSimilarityQuery at the default decay and every 4-argument searchNearestVectors fails, until that segment is merged with segments that hold vectors.

Mechanism, terms and numbers393 words

You use the flat Lucene104ScalarQuantizedVectorsFormat for a float vector field, delete every document that has a vector while other documents stay, and merge. The merged segment still lists the field but holds no vectors, the same state Lucene's own testDeleteAllVectorDocs reaches. A FloatVectorSimilarityQuery on it should match nothing; instead IndexSearcher.search throws NullPointerException ("quantizer" is null). The reader's search returns early only when k is 0 and then builds a scorer over the empty vector values, whose quantizer is null. The HNSW reader guards this case with size() == 0; KnnFloatVectorQuery and the 5-argument searchNearestVectors are not affected because they clamp k to the field's size first.

The mechanism (main 5adff78bb168, under lucene/core/src/java/org/apache/lucene/)

#
  1. The query reaches the reader unguarded. FloatVectorSimilarityQuery.Adaptive at its default decay (0.5) takes the approximate path for each leaf (search/AbstractVectorSimilarityQuery.java:190-206) and calls the 4-argument searchNearestVectors with no size check (search/FloatVectorSimilarityQuery.java:254-263). CodecReader.searchNearestVectors checks only the FieldInfo and calls the vectors reader (index/CodecReader.java:283-295).
  2. The reader checks only k. Lucene104ScalarQuantizedVectorsReader.search(String, float[], ...): if (knnCollector.k() == 0) return; (codecs/lucene104/Lucene104ScalarQuantizedVectorsReader.java:358), then exhaustiveBulkScore(getRandomVectorScorer(field, target), ...) (:359). The float16 overload is the same (:365-366).
  3. The empty values have no quantizer. For a field with 0 vectors, OffHeapScalarQuantizedVectorValues.load returns EmptyOffHeapVectorValues (OffHeapScalarQuantizedVectorValues.java:210-211), built with a null centroid and a null quantizer (:503-518).
  4. The scorer dereferences it. Lucene104ScalarQuantizedVectorScorer.getRandomQuantizedVectorScorer reads qv.getQuantizer() (:105) and calls quantizer.scalarQuantize(...) (:119): NullPointerException. exhaustiveBulkScore would accept a null scorer (Lucene104ScalarQuantizedVectorsReader.java:376), but none is returned.

Who guards this case and who does not

#
  • Lucene99HnswVectorsReader (the HNSW formats, including Lucene104HnswScalarQuantizedVectorsFormat): if (fieldEntry.size() == 0 || knnCollector.k() == 0) return; (codecs/lucene99/Lucene99HnswVectorsReader.java:359).
  • KnnFloatVectorQuery (search/KnnFloatVectorQuery.java:115) and the 5-argument LeafReader.searchNearestVectors (index/LeafReader.java:277-290) clamp k to size() and return before the reader, so they give 0 hits on this index.
  • At decay DECAY_MAX_QUALITY (1.0) the query goes straight to exact search, whose empty-values scorer(float[]) returns null by design (OffHeapScalarQuantizedVectorValues.java:537-538): 0 hits. A filter that matches no live document returns before the search.
  • Executed controls: on this index the filtered FloatVectorSimilarityQuery.Adaptive (filter MatchAllDocsQuery), the deprecated FloatVectorSimilarityQuery.Explicit and the 4-argument searchNearestVectors throw the same NPE, while KnnFloatVectorQuery and the 5-argument API return 0 hits; Lucene104HnswScalarQuantizedVectorsFormat and Lucene99HnswVectorsFormat return 0 hits after the same steps; Float16VectorSimilarityQuery.Adaptive on main throws the same NPE.
Exposure and likelihood162 words
  • Opt-in format. The default codec and the HNSW scalar-quantized format return 0 hits after the same steps. The flat format, FloatVectorSimilarityQuery and the 4-argument API are all @lucene.experimental.
  • No scale needed. 2 documents suffice, and no explicit forceMerge is needed (with the default config, an NRT reader opened right after the delete already sees the emptied leaf and throws); it is data-dependent, so it tends to show up in production after deletes and a merge, not in development.
  • Loud, not silent. The whole search call throws (one such leaf is enough); nothing is written wrong and no result is wrong. It lasts until that segment is merged with segments that have vectors for the field: a merge keeps the field (the repro's own forceMerge(1) is one), and adding new vector documents alone does not help.
  • Likelihood: rare. It needs the non-default format, a vector similarity query or the 4-argument API, and an emptied field. No public report was found since 10.4.0.

Why it looks unintended

#
  • testDeleteAllVectorDocs, Lucene's shared format test, reaches this state and says "knn search doesn't fail on a field with all deleted docs", but checks only the 5-argument API.
  • LUCENE-10351 (#580, 2022) fixed the same kind of failure with a size() == 0 return in the HNSW reader.
  • The field keeps its vector FieldInfo, so the javadoc's "undefined" case does not apply.
The full argument233 words
  • The contract in Lucene's own test. BaseKnnVectorsFormatTestCase.testDeleteAllVectorDocs (lucene/test-framework/src/java/org/apache/lucene/tests/index/BaseKnnVectorsFormatTestCase.java:893-929) adds one vector document (with a StringField id and DOT_PRODUCT) and one plain document, commits, deletes the first by term, runs forceMerge(1) and asserts the values have size 0; the comment at :918 reads "assert that knn search doesn't fail on a field with all deleted docs". TestLucene104ScalarQuantizedVectorsFormat inherits it, but the test searches only through the 5-argument searchNearestVectors, which clamps k to 0 and never reaches the reader, so the gap stays untested.
  • The precedent. LUCENE-10351 (#580, 78da7030370, 2022-01-04, "Correct knn search failure with deleted docs") fixed the same kind of failure (a knn search on a field whose vector documents were all deleted then threw IllegalArgumentException) in the HNSW reader of the time with a reader-side size() == 0 return, and added the knn-search assertion (the comment at :918) to the existing testDeleteAllVectorDocs. Lucene99HnswVectorsReader.java:359 keeps the guard.
  • The format is meant to be searched on its own. It is registered in lucene/core/src/resources/META-INF/services/org.apache.lucene.codecs.KnnVectorsFormat:17, its reader overrides search with an exhaustive scan instead of the flat-reader no-op, and TestLucene104ScalarQuantizedVectorsFormat.testSearch (:95) queries it as the per-field format.
  • History. The guard, the empty values with a null quantizer and the scorer all came with #15169; no review comment discusses searching a field with no vectors, and no later commit adds a size guard to search.
The devil's-advocate check117 words

The strongest counter-argument: the 4-argument API's behaviour is "undefined" for a field without vectors, the 5-argument API and KnnFloatVectorQuery show that callers clamp k to size() themselves, and everything involved is @lucene.experimental.

Why it fails. The javadoc carve-out is "doesn't have KNN vectors enabled on its FieldInfo" (index/LeafReader.java:401-402, codecs/KnnVectorsReader.java:112-113); this field keeps a vector FieldInfo, and the repro asserts non-null values of size 0. No javadoc asks callers for a size check, and Lucene's own FloatVectorSimilarityQuery calls the unguarded overload. @lucene.experimental concerns API stability, not an NPE on a writer-produced index. The cross-model refute review rated the intended-behaviour case weak; the devil's-advocate verifier considered six such arguments and rejected all of them.

Suggested fix

#

Recommended Return early when the field has no vectors, in both search overloads (as the HNSW reader does)

Give this reader the HNSW reader's guard: in both search overloads, FieldEntry fi = fields.get(field); if (fi == null || fi.size == 0 || knnCollector.k() == 0) return;. The repro passes; with it the repro and 3 closest suites run 102 tests with 0 failures.

  public void search(String field, float[] target, KnnCollector knnCollector, AcceptDocs acceptDocs)
      throws IOException {
    FieldEntry fi = fields.get(field);
    if (fi == null || fi.size == 0 || knnCollector.k() == 0) return;
    exhaustiveBulkScore(getRandomVectorScorer(field, target), knnCollector, acceptDocs);
  }
  // the same two lines in search(String field, short[] target, ...)

Return a null scorer for an empty field from getRandomVectorScorer

#

Return null from getRandomVectorScorer(String, float[]) and (String, short[]) (:216-238) when the field entry's size is 0; exhaustiveBulkScore already returns on a null scorer (:376).

Trade-offs

Also covers other callers of getRandomVectorScorer, but changes what that public method returns for an empty field, which every caller would see; needs a wider review. Not run.

Clamp k to size() in FloatVectorSimilarityQuery (not recommended)

#

Return no hits in FloatVectorSimilarityQuery.approximateSearch when the leaf's vector values have size 0, as KnnFloatVectorQuery does.

Trade-offs

Fixes the query but leaves the 4-argument searchNearestVectors and any other caller of the reader's search exposed; a reader-side guard is consistent with the approach of LUCENE-10351. Not run.

Downstream note

#

Downstream, Solr's flat ScalarQuantizedDenseVectorField (SOLR-18267) delegates to this format and offers a vector-similarity query parser, so its users can meet the same exception; no downstream report was found.

How it was found

#

A proof-obligation audit of Lucene104ScalarQuantizedVectorsReader's contract: a search on a field whose vectors were all deleted must return no hits, as the HNSW reader's size() == 0 guard ensures. This reader's search does not discharge that obligation; a one-test public-API JUnit then witnessed the NullPointerException.

The method in full122 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The finder listed what the reader's search must guarantee on every index the writer can produce, taking the contract from testDeleteAllVectorDocs and the HNSW reader's guard. The obligation "an emptied field yields no hits" is not discharged: the early return covers only k() == 0, and the empty values carry a null quantizer.
  • The finder then wrote a public-API JUnit test that fails on main with assertions on and off and on 10.6.0 and 10.5.2; a final repro check kept the minimal version as the one repro.
  • An independent reproducer, an executed cross-model review, a devil's-advocate verifier and an adjudication reproduced it ("Prior reports, history and checks").
