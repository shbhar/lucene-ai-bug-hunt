Index-sorted flush: the numeric doc-values and norms iterator ends intoBitSet(maxDoc) on maxDoc instead of NO_MORE_DOCS

With an index sort that reorders the flush, the flush-time iterator of a numeric doc-values or norms field that every document has ends intoBitSet(maxDoc, ...) on docID() == maxDoc instead of NO_MORE_DOCS; the bits are right. Only custom codecs that make this call are hit; 10.5.0-10.6.0 and main are affected.

The finding in 30 seconds

#

Background: index-sorted flush and intoBitSet

#
  1. With IndexWriterConfig.setIndexSort, each flushed segment is written in sort order, so at flush IndexWriter re-orders the buffered doc values and norms before handing them to the codec's consumer (when the documents arrived already sorted, nothing is re-ordered and the defective iterator is not used).
  2. The consumer reads each field through an iterator: nextDoc() walks the documents that have a value, one by one, and returns NO_MORE_DOCS (2147483647) after the last one.
  3. intoBitSet(upTo, bits, offset) is the bulk shortcut: it marks every remaining document below upTo in one call, and its javadoc says it "should behave exactly as" that nextDoc() loop, which implies the same end position.

The finding, step by step

#
  1. Set an index sort and add 2 documents, each with a sort value (0 and -1, so the flush reorders them) and a text field body, so both documents have norms.
  2. At flush, IndexWriter hands your codec's norms consumer an iterator over those norms. The consumer calls nextDoc() (doc 0), then intoBitSet(2, bits, 0) to load every document in one call.
  3. You expect bits 0 and 1 set and the iterator finished: docID() returns NO_MORE_DOCS (2147483647), where the reference nextDoc() loop in the intoBitSet javadoc ends.
  4. Instead the bits are right but docID() returns 2, the segment's maxDoc, which is not a document. A consumer that re-reads docID() until NO_MORE_DOCS never ends: IndexedDISI.writeBitSet fed this iterator fails an assertion, or with assertions off writes empty block headers without end.
  5. Lucene's own doc-values and norms formats skip the bulk load when every document has the field, so default indexes are not affected. Numeric doc values and single-valued sorted-numeric fields share the same iterator.

Who is affected

#

Only code that plugs a custom DocValuesFormat or NormsFormat into an index-sorted IndexWriter and bulk-loads the flush-time iterator of a field every document has, when the flush reorders the documents. A consumer like IndexedDISI.writeBitSet then hangs or fails the flush; other consumer shapes were not tested. Default codecs (in the tested paths), search results and existing indexes are not affected.

Mechanism, terms and numbers581 words

When an index sort is set and the flush actually reorders the documents, IndexWriter re-orders each numeric doc-values field and the norms at flush and hands the codec's consumer a NumericDocValuesWriter.SortingNumericDocValues iterator (already-sorted input gets an unsorted iterator). If every document of the segment has the field, that iterator's intoBitSet(upTo, bitSet, offset) with upTo >= maxDoc sets the right bits but leaves docID() at maxDoc (2 for a 2-document segment) instead of NO_MORE_DOCS. The intoBitSet javadoc says the method "should behave exactly as" the docID()/nextDoc() loop, which ends on NO_MORE_DOCS here, and the sparse branch of the same method does end there. A consumer that re-reads docID() until NO_MORE_DOCS never ends, as IndexedDISI.writeBitSet does. Lucene's own consumers skip the bulk load for such fields, so default indexes are unaffected; a custom codec that bulk-loads the flush-time iterator is. Introduced by #16126 in 10.5.0; one line fixes it.

The mechanism (main 645d4fe14a20)

#
  1. The dense flag. At flush with an index sort, NumericDocValuesWriter.getDocValuesProducer calls sortDocValues(..., sortMap.size() == docsWithField.cardinality()) (NumericDocValuesWriter.java:150-155); norms do the same (NormValuesWriter.java:74-80). The flag is true exactly when every document has a value, and then sortDocValues keeps docsWithField = null (:113-116), the dense representation from #12381 (9.8.0).
  2. The iterator. The consumer gets new SortingNumericDocValues(sorted) (NumericDocValuesWriter.java:169; norms NormValuesWriter.java:95). A single-valued SortedNumericDocValuesField gets the same producer wrapped in DocValues.singleton (SortedNumericDocValuesWriter.java:215-226).
  3. Its nextDoc() returns NO_MORE_DOCS once docID + 1 == maxDoc (:247-254).
  4. Its intoBitSet (:281-293, added by #16126) clamps upTo to maxDoc (:283). The dense branch sets the bits and then docID = upTo; (:287), which is maxDoc whenever the caller asked for maxDoc or more. The sparse branch of the same method maps that case to NO_MORE_DOCS: docID = upTo < dvs.maxDoc ? dvs.advance(upTo) : NO_MORE_DOCS; // set the current doc (:290).
  5. The contract. DocIdSetIterator#intoBitSet "should behave exactly as if implemented as" for (int doc = docID(); doc < upTo; doc = nextDoc()) bitSet.set(doc - offset); (DocIdSetIterator.java:187-195), which ends on NO_MORE_DOCS here; docID() may only be -1, the current document or NO_MORE_DOCS (:113-124). The method is @lucene.internal (:203).

What a consumer sees

#

The bits are right in every run; only the position is wrong. IndexedDISI.writeBitSet loops for (doc = it.nextDoc(); doc != NO_MORE_DOCS; doc = it.docID()) with one intoBitSet per 65,536-document block (IndexedDISI.java:210-213). After the first block the position is maxDoc, so the next intoBitSet sets nothing, and the empty block trips assert cardinality > 0 (IndexedDISI.java:118); with assertions off it writes a 4-byte block header (:117, :119) and loops again without end (the hunt's test stopped it at 1 MiB). That spin comes from re-reading docID(); by reading only, a consumer that calls nextDoc() and longValue() instead would get maxDoc + 1 and index past the values array (NumericDocValuesWriter.java:247-254, :269-270). Other consumer shapes were not tested.

Why default indexes are fine

#

Lucene90DocValuesConsumer writes no IndexedDISI when numDocsWithValue == maxDoc (Lucene90DocValuesConsumer.java:467, before writeDISI at :474), Lucene90NormsConsumer likewise (Lucene90NormsConsumer.java:107, before IndexedDISI.writeBitSet at :117), and SortingCodecReader always builds a non-null docsWithField (SortingCodecReader.java:793-804), so merges never take the dense branch. An executed probe saw 0 intoBitSet calls on dense fields across index-sorted flushes of 1, 2, 3, 100 and 65,543 documents, a sorted forceMerge and addIndexes of a SortingCodecReader, with a clean CheckIndex.

Exposure and likelihood260 words
  • Who is hit. An application or library whose custom doc-values or norms consumer (plugged in through FilterCodec, PerFieldDocValuesFormat or its own codec; DocValuesFormat, DocValuesConsumer and NormsConsumer are @lucene.experimental) calls intoBitSet up to maxDoc or NO_MORE_DOCS on the flush-time iterator, directly or through the @lucene.internal IndexedDISI.writeBitSet, and then reads docID(), for a numeric doc-values, single-valued sorted-numeric or norms field that every document of an index-sorted segment has.
  • Default vs opt-in. Opt-in: in the tested stock paths nothing observable changes, and the index, values, norms and sort order are correct; by reading, the current Lucene90 doc-values and norms consumers (and the backward-codecs Lucene80DocValuesConsumer) skip the docs-with-field encoding for a field every document has.
  • Scale. None needed: 2 documents are enough, and a field present on every document is the ordinary case, so a consumer shaped like IndexedDISI.writeBitSet fails at the first index-sorted flush that reorders such a field.
  • How it shows. It depends on the consumer. In the executed case, IndexedDISI.writeBitSet (which re-reads docID() until NO_MORE_DOCS) fails the flush with an AssertionError or writes until the output fails: no wrong match and no committed segment. Other consumer shapes were not tested; by reading, one that calls nextDoc() and longValue() would fail out of bounds instead.
  • Why fix it anyway. #16126 added these overrides as an optimization (CHANGES "Optimizations"), for callers that bulk-load; the dense case is the common one for such a caller, and the sparse branch next to it already ends correctly. The fix is one line and adds one comparison per bulk call.

Why it looks unintended

#
  • The intoBitSet javadoc says it "should behave exactly as" the nextDoc() loop, which ends on NO_MORE_DOCS here; docID() has no "one past the last document" state.
  • The sparse branch of the same method, from the same commit, ends on NO_MORE_DOCS for the same call.
  • Lucene's test framework checks the position after intoBitSet; 10.4.0, using the default loop, passes the repro.
The full argument258 words
  • The contract. DocIdSetIterator#intoBitSet "should behave exactly as if implemented as" the docID()/nextDoc() loop (DocIdSetIterator.java:187-195); docID() returns -1, NO_MORE_DOCS or "the doc ID it is currently on" (:113-124). The call meets both stated preconditions: the iterator is positioned, and offset (0) is not greater than docID() (:196-197).
  • The same method. The sparse branch, written in the same commit, ends on NO_MORE_DOCS (NumericDocValuesWriter.java:290, "set the current doc"), and the class's nextDoc() ends there too (:247-254).
  • Tests. BaseDocIdSetTestCase checks "if docID() / nextDoc() return the same value after #intoBitSet has been called" (BaseDocIdSetTestCase.java:222), and BaseDocValuesFormatTestCase asserts expected.docID() == values.docID() after intoBitSet (BaseDocValuesFormatTestCase.java:1085-1089). No test covers the writer-side iterators: #16126 added none.
  • History. From 10.2.0 to 10.4.0 the class inherited the default loop and ended on NO_MORE_DOCS (10.4.0 passes the repro). The #16126 PR body describes the change as "mostly iterators wrapping other iterators so we just delegate the method"; this method is not a delegation. The PR had one approval, no comments and no follow-up.
  • Precedent (it shows maintainers fix such edge cases; it does not settle this one). Lucene fixed other intoBitSet edge cases as bugs: #14922 (IndexedDISI, CHANGES 10.3.0 "Bug Fixes"), #16250/#16252 (RoaringDocIdSet, CHANGES 10.5.0 "Bug Fixes") and #16105 (BatchDocValuesRangeIterator, a public class, an end state at the maxDoc boundary). Those were reachable from Lucene's own code or from search; this one is a flush-time state no in-tree caller reaches, so a maintainer may weigh it differently.
The devil's-advocate check184 words

The strongest case for "works as designed" came from the cross-model reviews (OpenAI GPT-5.6): intoBitSet is @lucene.internal ("This API is for internal purposes only and might change in incompatible ways in the next release"), IndexedDISI is @lucene.internal, the consumer APIs are @lucene.experimental, and the stock consumers deliberately encode a field present on every document without a docs-with-field bitset, so the wrong end state is unobservable in supported use; a codec that relies on an internal bulk hook is outside the contract.

Why it does not make the position correct (though it may well decide how a maintainer triages the report): @lucene.internal limits API stability, not the behaviour the method's own javadoc states, and #16126 added this override as an optimization for callers that bulk-load. The same reviewer wrote that its argument "does not establish that maxDoc itself was a deliberate semantic choice" and that the assignment "is an oversight suitable for low-risk internal hardening". The scope argument correctly lowers the severity (latent, minor); it does not make the position right. Verdict: a real, latent defect; no in-tree consumer reaches the branch.

Suggested fix

#

Recommended A. End the dense branch on NO_MORE_DOCS when the call reached maxDoc

End the dense branch the way the sparse branch already does: docID = upTo < dvs.maxDoc ? upTo : NO_MORE_DOCS; in SortingNumericDocValues#intoBitSet. One line; it fixes numeric doc values, norms and single-valued sorted-numeric at once. The repro then passes with assertions on and off, and the closest core suites pass.

Not recommended: document maxDoc as an end state, or harden consumers instead

#

For example let IndexedDISI.writeBitSet treat docID() >= maxDoc as the end.

Trade-offs

Keeps this iterator out of line with the intoBitSet and docID() contracts that the default implementation and the sparse branch follow; hardening one consumer without fixing the iterator leaves other consumers exposed. A maintainer could still reasonably harden the in-tree consumer as well, or decline the report because no in-tree caller reaches the branch.

Downstream note

#

A custom doc-values or norms format that bulk-loads the flush-time iterator of an index-sorted segment should treat docID() >= maxDoc as the end after intoBitSet until a fix ships; Lucene's own formats need no change.

How it was found

#

Non-formal: code reading. While modelling the input contract of IndexedDISI.writeBitSet in a Z3 model, the finder read the iterators that feed it and noticed the dense branch's end position; the model records the consequence but gave no counterexample for this bug. A JUnit test on the stock jars then confirmed it, and independent checkers reproduced it.

The method in full148 words

Method: non-formal (code reading). A hunt unit on IndexedDISI and doc-values bulk iteration wrote a Z3 bit-vector model of IndexedDISI's arithmetic (38 obligations, 0 unexpected). One obligation records what happens when a source iterator's intoBitSet does not move past upTo: writeBitSet then flushes a block of cardinality 0. Reading the iterators that can feed writeBitSet, the finder found that SortingNumericDocValues does exactly that in its dense branch. No tool output gave the first signal, so the find is classed as non-formal.

The finder then wrote a JUnit test with a real index-sorted IndexWriter flush through a FilterCodec on the stock main jars (5 tests, 4 failing with assertions on and off, the unsorted control passing). It was reviewed by a reviewer from another model family (OpenAI GPT-5.6), reproduced independently (which added the single-valued sorted-numeric path), judged, and cut to the one-test repro on 645d4fe14a20.

LFV-165, snapshot of 2026-11-03

Registry title
With an index sort, the flush-time iterator that IndexWriter hands to a doc-values or norms consumer for a numeric field that every document has ends intoBitSet(upTo >= maxDoc) on docID() == maxDoc instead of NO_MORE_DOCS, so a custom consumer that bulk-loads it and loops until NO_MORE_DOCS never finishes (latent: Lucene's own consumers skip the bulk load for such fields)
Area
index / doc values and norms flush with index sorting (NumericDocValuesWriter.SortingNumericDocValues)
Priority
Low, rank 1019: The index-sorted flush iterator ends intoBitSet at maxDoc instead of NO_MORE_DOCS for dense numeric fields, latent because Lucene's own consumers skip that bulk load.
Impact class
minor
Impact note
Latent: only a custom DocValuesFormat or NormsFormat consumer (public codec extension points) that calls the @lucene.internal DocIdSetIterator#intoBitSet up to maxDoc or NO_MORE_DOCS on the flush-time iterator of an index-sorted segment, for a numeric doc-values, single-valued sorted-numeric or norms field that every document of the segment has, and then relies on docID() is hit, and it would be hit at the first flush of ordinary data; stock Lucene never takes the defective branch (the Lucene90 and backward Lucene80 consumers skip the bulk load when every document has a value, SortingCodecReader always passes a docs-with-field set; executed: zero intoBitSet calls on dense fields and a clean CheckIndex), none of the downstream consumers read takes it, the bits it sets are correct, no scale is needed, and 10.5.0 to 10.6.0 are affected.
Summary
You sort an index at flush and every document in the segment has a given numeric doc-values field (or norms, or a single-valued SortedNumericDocValuesField); a custom DocValuesFormat or NormsFormat consumer bulk-loads the iterator it gets at flush with intoBitSet(maxDoc) or intoBitSet(NO_MORE_DOCS) and expects it to end on NO_MORE_DOCS, as the reference loop in the intoBitSet javadoc does. Instead NumericDocValuesWriter.SortingNumericDocValues sets the right bits but leaves docID() at maxDoc, a position the docID() contract never allows, so a consumer that loops until NO_MORE_DOCS never ends; fed to IndexedDISI.writeBitSet it fails the flush with an AssertionError (-ea) or keeps writing empty-block headers until the output fails (-da). Lucene's own consumers never bulk-load a field that every document has, so stock indexes and search results are not affected.
