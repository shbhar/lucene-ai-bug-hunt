ConcatenateGraphFilter without a separator (and CompletionAnalyzer with preserveSep=false) silently drops a path around a position hole

Concatenating "play the who" (synonym "the who" => "thewho", stop word "the") without a separator yields only playwho: playthewho is lost with no error, so the prefix "playth" finds no suggestion. The cause is Automaton.addEpsilon, which copies a state's exits while its own first write re-sorts them.

The finding in 30 seconds

#

Without a separator, the filter turns the arcs between tokens into empty moves (hole arcs always are), which Automaton.addEpsilon implements by copying the next state's exits. Here that state is still being built and unsorted (w, t). The copy's first write sorts it in place, so the copy reads w twice and never t.

Background: concatenating a token graph

#
  1. ConcatenateGraphFilter glues the tokens of every path through a token graph into one output token. The document suggester (CompletionAnalyzer, SuggestField) uses it to index suggestions. With preserveSep=false, or a null tokenSeparator, tokens are glued with nothing in between.
  2. A multi-word synonym adds a token that spans several positions (thewho over "the who"). A stop filter that then removes "the" leaves a hole: a position where no token ends.
  3. Internally the filter builds an automaton with a separator arc between tokens and a hole arc over the gap. The hole arc always becomes an empty (epsilon) move, and with no separator the separator arc does too; an empty move is done by copying the target state's outgoing arcs onto the source state.

The finding, step by step

#
  1. Analyze "play the who" with the synonym "the who" => "thewho" and the stop word "the". You get 3 tokens: play, thewho (spanning 2 positions) and who, so the token graph has 2 paths.
  2. Concatenate them without a separator: new ConcatenateGraphFilter(in, null, true, 100), or CompletionAnalyzer with preserveSep=false. You expect 2 tokens, one per path: playthewho and playwho.
  3. You get 1 token, playwho, and no error. A suggestion indexed for "play the who" is found for "playw" but gets 0 hits for "playth". With assertions on (-ea) the filter throws an AssertionError instead.
  4. Why: the end of play must receive a copy of the next state's 2 exits, stored as w (via the hole) then t (thewho). The copy reads w; writing it makes Automaton finish that state, which sorts it to t, w. The second read sees w again, so t is never copied.
  5. With a separator ('-', '|' and the default U+001F were run on this input), or when the hole branch's letter sorts first, both paths survive. Releases from 5.3.0 (CompletionAnalyzer) and 7.4.0 (ConcatenateGraphFilter) through 10.6.0 have it.

Who is affected

#

Only the opt-in no-separator mode: ConcatenateGraphFilter with a null separator (factory tokenSeparator="") and CompletionAnalyzer or the document suggester with preserveSep=false. It also needs a hole under a multi-position token, from a multi-word synonym containing a stop word, and an unlucky letter order. One value suffices; production is silent, test suites see an AssertionError.

Mechanism, terms and numbers685 words

ConcatenateGraphFilter promises one output token "for every path through the token stream (which is a graph)", and its tokenSeparator may be null to concatenate without separators; CompletionAnalyzer with preserveSep=false uses exactly that mode. For the token graph play | thewho (2 positions) | who, which a multi-word synonym ("the who" => "thewho") followed by a stop filter for "the" produces from "play the who", the filter emits only playwho: playthewho is lost silently with assertions off, and with -ea the same input throws an AssertionError in Automaton.getNextTransition. Through the document suggester, a SuggestField "play the who" gets 0 hits for the prefix "playth".

The cause is Automaton.addEpsilon(source, dest): it reads dest's transition count once and walks dest's transitions with a cursor while calling addTransition(source, ..). When dest is the state still being built, that first addTransition finishes dest, which sorts and merges its transitions in place, so the cursor reads one transition twice and never reads another. ConcatenateGraphFilter.replaceSep fills its automaton in reverse topological order and turns every separator and hole arc into addEpsilon, so dest is often that open state. It needs the opt-in no-separator mode, a hole under a multi-position token, and a hole-branch letter that sorts after the spanning token's letter. The root cause dates from 4.10.0 (LUCENE-5752); it is visible on stock jars from 5.3.0 (CompletionAnalyzer) and 7.4.0 (ConcatenateGraphFilter) through 10.6.0 and main. A five-line fix in addEpsilon (finish an open dest before copying) passes the repro and the automaton, filter and document-suggester suites.

The mechanism (main 5adff78bb168)

#
  1. ConcatenateGraphFilter.toAutomaton builds the token automaton with TokenStreamToAutomaton, then calls replaceSep and determinizes (ConcatenateGraphFilter.java:244-250). Between tokens there is a POS_SEP arc; over a position where no token ends, TokenStreamToAutomaton.addHoles adds a HOLE arc (TokenStreamToAutomaton.java:271-299).
  2. replaceSep fills a plain Automaton, not an Automaton.Builder, in reverse topological order (ConcatenateGraphFilter.java:285-301). With a null separator each POS_SEP arc becomes addEpsilon(state, t.dest) (:311); every HOLE arc becomes addEpsilon too (:323). Because of the visit order, t.dest is often the state just filled, which is still the automaton's open state.
  3. Fix site. Automaton.addEpsilon reads count = initTransition(dest, t) once (Automaton.java:191) and then loops getNextTransition(t) and addTransition(source, ..) (:192-195).
  4. addTransition to a new source first finishes the open state (Automaton.java:162-165): finishCurrentState sorts its transitions, merges adjacent ones in place and sorts again (:239-311).
  5. So when dest is open and unsorted, the first addTransition(source, ..) rewrites dest's block under the cursor, and the remaining reads see the rewritten block. With -ea, the sortedness assert in getNextTransition fires (:493; transitionSorted returns false for two equal transitions, :531-532).

The trace for the repro (executed, same loop as replaceSep)

#

State 1 is the end of play (SEP->5). State 5 has HOLE->13 and 't'->7; the hole branch continues 13: SEP->12, 12: 'w'->14. The visit order ends ... 13 ... 5, 1, ....

  • Visiting 5, the new automaton first copies 'w'->14 (through the hole) and then adds 't'->7: block [w, t], unsorted, still open.
  • Visiting 1, addEpsilon(1, 5) reads 'w'->14 and writes it to state 1. That write finishes state 5, which becomes [t, w]. The second read is 'w'->14 again.
  • State 1 ends with only 'w'->14: the play + thewho path is gone, and the output is [playwho].

Core-only form: Automaton a = new Automaton(); a.createState(); a.createState(); a.createState(); a.addTransition(1, 2, 'b'); a.addTransition(1, 0, 'a'); a.addEpsilon(0, 1); a.finishState(); leaves state 0 with only b->2 (-da, expected:<2> but was:<1>) or asserts (-ea).

Why the letter order matters

#

The hole arc sorts before any letter, so the hole branch's exit is copied into state 5 first and the spanning token's letter is added after it. If the hole branch's letter sorts first (a before w), the block is already sorted, finishing does not move anything, and both paths survive: [playaaa, playwhoa] for play | whoa (2 positions) | aaa.

Exposure and likelihood257 words
  • Who is hit. ConcatenateGraphFilter with a null tokenSeparator (ConcatenateGraphFilter.java:101-102), its factory with tokenSeparator="" (ConcatenateGraphFilterFactory.java:28-30, :85-86), and CompletionAnalyzer with preserveSep=false, whose stream wraps new ConcatenateGraphFilter(input, preserveSep, ..) (CompletionTokenStream.java:54-61; preserveSep=false maps to a null separator, ConcatenateGraphFilter.java:140). At index time a suggestion entry loses a path. By reading, PrefixCompletionQuery and FuzzyCompletionQuery analyze the prefix through the same stream, so a query-side path can be lost too (not run).
  • Default vs opt-in. Not default: DEFAULT_TOKEN_SEPARATOR = SEP_LABEL and DEFAULT_PRESERVE_SEP = true (ConcatenateGraphFilter.java:62-63). For this graph a separator keeps both paths ('-', U+001F and '|' were run); hole arcs still become addEpsilon with a separator, so that is shown for this input only. AnalyzingSuggester and FuzzySuggester are not affected: they build on Automaton.Builder since 5.0.0.
  • What it takes. A position hole under a multi-position token (for example a multi-word synonym that contains a stop word, followed by a stop filter), and a hole-branch first letter that sorts after the spanning token's first letter. preservePositionIncrements does not matter: false loses the path the same way.
  • Scale and visibility. One value with three tokens; no scale needed. With assertions off a suggestion quietly does not appear; with -ea (test suites) indexing throws an AssertionError. After a fix, completion entries already indexed need reindexing to gain the lost path.
  • Likelihood: rare. All three conditions must meet, the effect is easy to overlook, and no public report was found (searched 2026-11-02), although the suggester symptom is on stock jars from 5.3.0 (2015).

Why it looks unintended

#
  • The class promises "one output token for every path through the token stream (which is a graph)" and documents a null separator.
  • addEpsilon only requires that dest "already have all transitions added", which holds here.
  • The same graph with separator '-' keeps both paths, and the same algorithm on Automaton.Builder gives [playthewho, playwho].
The full argument186 words
  • Contracts. "Concatenates/Joins every incoming token with a separator into one output token for every path through the token stream (which is a graph)" (ConcatenateGraphFilter.java:40-41). tokenSeparator: "Can be null, in this case tokens will be concatenated without any separators" (:101-102). addEpsilon: "Dest state must already have all transitions added because this method simply copies those same transitions over to source" (Automaton.java:185-188). State 5 has all its transitions when it is copied.
  • Differentials. With separator '-': [play--who, play-thewho]; with null: [playwho]; the same replaceSep algorithm on Automaton.Builder: [playthewho, playwho]. Dropping separators should not drop a path.
  • Tests. TestConcatenateGraphFilter.testWithNoPreserveSep covers no-separator input without holes (:45-52); testWithStopword covers holes only with a separator (:108-131). Upstream tests treat a hole under a multi-position token as legal input (TestGraphTokenizers.testSynOverHole, TestFlattenGraphFilter.testHoleUnderSyn).
  • History. LUCENE-5963 (#7025, 5.0.0) moved only AnalyzingSuggester.replaceSep to Automaton.Builder, for allocation reasons. Nobody discussed lossy no-separator output there, in LUCENE-6339 (#7400), or in LUCENE-9018 (#10061, which made the separator configurable, null meaning none; the epsilon branch dates from LUCENE-6339 / LUCENE-8332).
The devil's-advocate check140 words

The strongest "intended" case: the Automaton class javadoc says each state "must have all of its transitions added at once" and that a state is finished once you start adding transitions to another state (Automaton.java:36-41). One could read addEpsilon as requiring a finished dest, which would make replaceSep's call a misuse.

Why it fails: addEpsilon's own precondition is "all transitions added", which holds. Under the strict reading the misusing caller is Lucene's own ConcatenateGraphFilter, so the user-visible loss stands and only the fix site is in question. A "lossy by design" reading fails too: nothing documents it, and whether a path survives depends on the letters (swapping them keeps both paths). The intended-behaviour check and the adjudication rejected the intended-behaviour argument, and an independent reviewer from another model family (OpenAI GPT-5.6) rated it weak.

Suggested fix

#

Recommended A. Finish an open dest at the top of addEpsilon

In Automaton.addEpsilon, finish dest first when it is the state still being built (if (curState == dest && source != dest) finishState();, five lines). The repro then passes with assertions on and off, and so do the automaton (238 tests), ConcatenateGraphFilter (19) and document-suggester (58) suites.

  public void addEpsilon(int source, int dest) {
+    if (curState == dest && source != dest) {
+      // dest is still open: finish it now, so that adding to source cannot rewrite (sort and
+      // reduce) dest's transitions while they are being copied
+      finishState();
+    }
     Transition t = new Transition();
     int count = initTransition(dest, t);

Three options; A was validated in a scratch worktree of 5adff78bb168 with gradle.

A. Finish an open dest at the top of addEpsilon (validated by the checks) (recommended)

#

Before copying, finish dest if it is the open state, so that adding to source cannot sort or merge dest's transitions mid-copy.

  public void addEpsilon(int source, int dest) {
+    if (curState == dest && source != dest) {
+      // dest is still open: finish it now, so that adding to source cannot rewrite (sort and
+      // reduce) dest's transitions while they are being copied
+      finishState();
+    }
     Transition t = new Transition();
     int count = initTransition(dest, t);

Trade-offs

Five lines in core; handles the open-dest case inside addEpsilon, so current callers need no change; no change when dest is already finished. It only moves the finishing of dest earlier: the old code also finished dest on the first addTransition(source, ..), so a later addTransition(dest, ..) threw "already had transitions added" before and still does.

What the checks validated

  • Stock: the repro fails with assertions on and off.
  • With A: the repro, TestConcatenateGraphFilter and TestConcatenateGraphFilterFactory pass (19 tests, assertions on); the repro passes with assertions off; :lucene:core:test --tests 'org.apache.lucene.util.automaton.*' --tests TestTokenStreamToAutomaton passes (15 classes, 238 tests, 2 skipped; the second filter matches no class at 5adff78bb168); :lucene:suggest:test --tests 'org.apache.lucene.search.suggest.document.*' passes (6 classes, 58 tests); checkGoogleJavaFormat passes on core and analysis-common.
  • An earlier run with the fix over the stock jars passed TestAutomaton, TestOperations and TestConcatenateGraphFilter, 120 of 120.

B. Snapshot dest's transitions before adding any

#

Read dest's (dest, min, max) triples with getTransition(dest, i, t) into a local int[], then add them to source. An independent reviewer wrote this fix; their filter test and the core-only test pass with it, with assertions on and off.

Trade-offs

One int[3 * count] allocation per call; dest is still finished by the first addTransition(source, ..), as today.

C. Build replaceSep on Automaton.Builder

#

Caller-side: fill replaceSep's result with Automaton.Builder, as AnalyzingSuggester does since LUCENE-5963. The same algorithm on Builder gives [playthewho, playwho] (a probe; not run through the module suites).

Trade-offs

Fixes the filter but leaves the addEpsilon hazard for any other caller that passes an open state (by reading, the plain-Automaton callers in Operations and Automata pass finished states). Both classes are @lucene.experimental and the Automaton javadoc asks for a state's transitions at once, so a maintainer may prefer this site.

Downstream note

#

Applications that offer completion fields with token separators turned off can silently miss suggestions for synonym-expanded values; configuring a separator avoids it.

How it was found

#

A proof-obligation audit of Automaton.addEpsilon's contract: the obligation that addEpsilon(source, dest) copies every transition of dest to source was checked against addTransition, which sorts and merges the open state in place. The gap was then witnessed by a one-test public-API JUnit on stock main.

The method in full133 words

Method: semi-formal, a proof-obligation audit witnessed by an executable repro. The audit stated the obligation of Automaton.addEpsilon(source, dest) (every transition of dest ends up on source) and checked it against the code it calls: addTransition finishes the open state, and finishCurrentState sorts and merges that state's block in place. The obligation fails when dest is the open state. Of the callers, ConcatenateGraphFilter.replaceSep can pass the open state (the core callers in Operations and Automata pass finished states, by reading), and a one-test JUnit on the stock main jars witnessed the lost path with assertions off and the AssertionError with assertions on.

It was then checked by a reproducer, a cross-model reviewer told to refute it, an intended-behaviour devil's advocate, an adjudication, a credibility audit and a final repro check (see "Independent checks").

LFV-1118, snapshot of 2026-11-08

Registry title
ConcatenateGraphFilter without a token separator (and so CompletionAnalyzer with preserveSep=false) silently drops a concatenated path around a position hole, because Automaton.addEpsilon copies from a dest state that its own first addTransition sorts and reduces in place (AssertionError with -ea)
Area
analysis-common / ConcatenateGraphFilter no-separator mode, and core / util.automaton (Automaton.addEpsilon); reached from suggest (CompletionAnalyzer preserveSep=false, document suggester)
Priority
Low, rank 277: In the opt-in no-separator mode of ConcatenateGraphFilter (CompletionAnalyzer with preserveSep=false), a value whose token graph has a position hole under a multi-word token silently loses one concatenated path, and so a suggestion, in every release since 5.3.0. It needs that mode, a stop word inside a multi-word synonym and an unlucky label order, so it is a rare trigger in an opt-in suggester mode and belongs in Low.
Impact class
silent wrong results
Impact note
Only analysis chains that use the opt-in no-separator mode are hit (ConcatenateGraphFilter with a null tokenSeparator, its factory with tokenSeparator="", or CompletionAnalyzer and so the document suggester with preserveSep=false; a non-null separator, including the default, and AnalyzingSuggester/FuzzySuggester are not affected), and then only for values whose token graph has a position hole under a multi-position token (what a multi-word synonym that contains a stop word, followed by a stop filter, produces: 'play the who' with 'the who' => 'thewho' and stop word 'the') and whose hole-branch label sorts after the spanning token's label: with -da one concatenation, and with it one suggestion entry, is silently missing, and with -ea the same value throws AssertionError [exec]; preservePositionIncrements does not matter, no scale is needed, and it is in every release from 5.3.0 (CompletionAnalyzer) and 7.4.0 (ConcatenateGraphFilter) through 10.6.0 and main.
Summary
You concatenate the token graph play | thewho (spanning two positions) | who, which a multi-word synonym ('the who' => 'thewho') followed by a stop filter produces for 'play the who', with ConcatenateGraphFilter and no separator (a null tokenSeparator, or CompletionAnalyzer with preserveSep=false), and expect one token per path, 'playthewho' and 'playwho', as the class javadoc promises. With assertions disabled you get only 'playwho', so a suggestion reached through the synonym (prefix 'playth') is silently missing; with -ea the filter throws an AssertionError in Automaton.getNextTransition. The cause is Automaton.addEpsilon: it copies the transitions of a state that is still being built, and its own first addTransition to the other state sorts and shrinks that state in place mid-copy, so some transitions are copied twice and others never.
