A reader opened with the expert lower-minimum DirectoryReader.open forgets that minimum, so isCurrent(), openIfChanged() and maybeRefresh() throw on an unchanged index

The expert DirectoryReader.open(commit, minSupportedMajorVersion, leafSorter) opens an index from an older major, but the reader forgets that minimum: isCurrent(), openIfChanged() and SearcherManager.maybeRefresh() re-check the unchanged commit against the default minimum and throw IndexFormatTooOldException on every call. Since 9.0.0; keeping the minimum on the reader fixes it.

The finding in 30 seconds

#

The minimum you pass to the expert open is range-checked and handed to the one call that reads the commit, and then dropped. Every later "has the index changed?" check re-reads the commit with the default minimum and rejects the commit the reader already has open.

Three things to know first

#
  1. Each segment records minVersion, the oldest Lucene version that wrote any of its documents. Rewriting a segment (a merge, IndexUpgrader) keeps the oldest one, so an 8.x index upgraded by 9.x still says 8.x.
  2. A normal open refuses a commit when any segment's minVersion major is below Version.MIN_SUPPORTED_MAJOR, which is 9 on 10.x, 11.0 and main (before 10.4.0 the check used the index's created major instead).
  3. The expert DirectoryReader.open(commit, minSupportedMajorVersion, leafSorter) lowers that minimum for one reader, so such an index can be read (read-only: an IndexWriter still refuses it).

The finding, step by step

#
  1. Take Lucene's own 8.11.4 back-compat test index (35 documents) after Lucene 9.12.3's IndexUpgrader: one segment written by 9.12.3 that still records minVersion 8.11.4. Lucene 11 supports majors 9 and later, so the default DirectoryReader.open(dir) refuses it.
  2. Open it with the expert DirectoryReader.open(commit, 8, null): it opens, with 35 documents, and searches work.
  3. Write nothing, then call reader.isCurrent(), DirectoryReader.openIfChanged(reader) or SearcherManager.maybeRefresh(). You expect true, null and a no-op: nothing was committed.
  4. Instead all three throw IndexFormatTooOldException ("Index has segments derived from Lucene version 8.x ... found: 8, minimum supported: 9") from isCurrent(), on every call: the reader re-read its own commit with the default minimum 9, not the 8 it was opened with.
  5. The open reader keeps serving its 35 documents, but it can never be refreshed: to move on, you have to call open(commit, 8, null) again on the latest commit.

Who is affected

#

Applications that open an older-major index with the expert lower-minimum open and then check or refresh it (isCurrent(), openIfChanged(), a SearcherManager / ReaderManager). Main: 8.x-created indexes rewritten by 9.x/10.x; 10.4-10.6: a segment derived from 8.x; 10.0-10.3 and 9.x: any index created by 8.x / 7.x. Loud: every refresh throws, the open reader keeps working.

Mechanism, terms and numbers534 words

DirectoryReader.open(IndexCommit, int minSupportedMajorVersion, Comparator<LeafReader>) (expert, since 9.0) opens an index whose segments come from a major below Version.MIN_SUPPORTED_MAJOR, which the default open refuses. The open range-checks the minimum and passes it to the one call that reads the commit; the reader does not keep it. isCurrent() and the reopen path later re-read the commit through the SegmentInfos overloads that apply the default Version.MIN_SUPPORTED_MAJOR, so the per-segment version gate rejects the very commit the reader already has open. With nothing committed since the open, isCurrent(), openIfChanged(reader) and SearcherManager / ReaderManager.maybeRefresh() all throw IndexFormatTooOldException on every call. The open reader keeps serving its commit (no wrong results, no data loss); to see a newer commit, the application has to call the expert open again (the old reader can stay open until the new one replaces it). The overload's other parameter, leafSorter, is carried to reopened readers; the minimum is not. Keeping the minimum on the reader and passing it to the two re-reads fixes it. Every release from 9.0.0 through 10.6.0 is affected, and so are branch_11x and main.

The bug (main 645d4fe14a20)

#
  1. DirectoryReader.open(commit, minSupportedMajorVersion, leafSorter) (DirectoryReader.java:189-194) calls StandardDirectoryReader.open(directory, minSupportedMajorVersion, commit, leafSorter, null) (StandardDirectoryReader.java:77-108). It range-checks the minimum (:87-93), passes it to the one call that reads the commit, SegmentInfos.readCommit(directory, segmentFileName, minSupportedMajorVersion) (:94-95), and builds the reader with new StandardDirectoryReader(directory, readers, null, sis, leafSorter, false, false) (:100-101). The reader has no field for the minimum (:45-48): it is dropped here.
  2. isCurrent() (:529-544), for a reader without a writer, re-reads the latest commit with SegmentInfos.readLatestCommit(directory) (:537), which is readLatestCommit(directory, Version.MIN_SUPPORTED_MAJOR) (SegmentInfos.java:581-583).
  3. openIfChanged(reader) goes to doOpenNoWriter(null, ...), which calls isCurrent() first (StandardDirectoryReader.java:477-482). SearcherManager.refreshIfNeeded (SearcherManager.java:194-206) and ReaderManager.refreshIfNeeded (ReaderManager.java:92-94) call openIfChanged.
  4. A reopen onto a different commit goes through doOpenFromCommit (StandardDirectoryReader.java:496-505), which reads it with SegmentInfos.readCommit(directory, segmentFileName) (:501), also the default minimum (SegmentInfos.java:293-296). openIfChanged(reader, newerCommit) reaches it directly; openIfChanged(reader) reaches it only after isCurrent() (StandardDirectoryReader.java:479-482), which already throws while the latest commit is one the default gate refuses.
  5. The per-segment gate (SegmentInfos.java:523-545) throws IndexFormatTooOldException when a segment's minVersion major is below the minimum it is given (:529). With the default 9 it rejects the commit the reader opened with 8.
  6. openIfChanged(reader, reader.getIndexCommit()) does return null: it short-circuits on the segments file name before reading anything (StandardDirectoryReader.java:487-490).
  7. The overload's other parameter survives: doOpenIfChanged(SegmentInfos, ...) passes subReadersSorter, the leafSorter, to the reopened reader (:507-511, from LUCENE-9507). There is no minimum to pass.

The numbers

#

Lucene's unsupported.8.11.4-cfs.zip back-compat fixture, upgraded by the stock 9.12.3 IndexUpgrader: created major 8, one segment written by 9.12.3 with minVersion 8.11.4, 35 documents. On main 645d4fe14a20 the default open throws and open(commit, 8, null) opens 35 documents; then isCurrent(), openIfChanged(reader) and SearcherManager.maybeRefresh() throw "Index has segments derived from Lucene version 8.x and is not supported by Lucene 11.0.0. This Lucene version only supports indexes with major version 9 or later (found: 8, minimum supported: 9)" from StandardDirectoryReader.isCurrent:537. With the fix all three return the contract values.

Exposure and likelihood353 words
  • Who is hit. Applications that keep an archived or read-only older-major index searchable after an upgrade, open it with DirectoryReader.open(commit, min, leafSorter) (or its ExecutorService variant), and then call isCurrent(), openIfChanged(), or refresh it through a SearcherManager / ReaderManager. On 11.0 and main (minimum 9) the demonstrated case is an index created by 8.x whose segments were all rewritten by 9.x or 10.x, for example by IndexUpgrader; 8.x's default codec, Lucene87, is no longer shipped there (an application that supplies an older codec itself could reach it with other old indexes too, by reasoning). The line splits at 10.4.0, where #14607 moved the default gate from the commit's created major to each segment's minVersion: on 10.4-10.6 the index is one with a segment derived from 8.x (an 8.x-created index whose segments all have minVersion 9 or later opens by default there and is not hit); on 10.0-10.3 it is any index created by 8.x; on 9.x any index created by 7.x.
  • Opt-in. Default opens and NRT readers are not affected; the way in is the expert open (the public but @lucene.internal StandardDirectoryReader.open(Directory, SegmentInfos, ...), given a SegmentInfos read with a lower minimum, builds the same kind of reader, StandardDirectoryReader.java:168-184).
  • Scale. None: one document is enough, and every call fails, with assertions on and off.
  • Loud, no data damage. A clean IOException on every refresh. The open reader keeps serving exactly its commit: no wrong results, no lost data, no file changes. A probe of 1,500 lifecycle calls on an unchanged index and 901 after a newer commit found no file change, no open input, no ref-count drift, no lock retention, and a newer commit was never reported as current.
  • Why nobody reported it, probably (an inference). The known users of the API open such readers once and never refresh them: Elasticsearch's ReadOnlyEngine (refresh() returns NO_REFRESH), OpenSearch's earlier ReadOnlyEngine (OpenSearch#5429) and a proposed Pinot fallback (apache/pinot#19894, an open PR).
  • Workaround. Call open(commit, min, leafSorter) again on the latest commit, then close the old reader (executed by the devil's advocate with the old reader still open).

Why it looks unintended

#
  • isCurrent() "checks if any further commits ... have occurred"; openIfChanged returns "null if there are no changes" (DirectoryReader.java:628-629, :242). Nothing changed, yet both throw.
  • LUCENE-9669 sets "a minimum index version on a per reader basis"; read-only meant no IndexWriter, not no refresh.
  • The same overload's leafSorter survives reopen (StandardDirectoryReader.java:510), and that is tested; the minimum does not.
The full argument368 words
  • Contract. openIfChanged (DirectoryReader.java:228-229): "If the index has changed since the provided reader was opened, open and return a new reader; else, return null"; @return null if there are no changes (:242). isCurrent (:628-629): "If this reader was created by calling open, then this method checks if any further commits (see IndexWriter#commit) have occurred in the directory." The expert overload is one of those open methods; neither contract excludes it.
  • The expert javadoc (DirectoryReader.java:169-177) says the method "allows to open indices that were created with a Lucene version older than MIN_SUPPORTED_MAJOR" and "All backwards compatibility aside from the file format is optional and applied on a best effort basis." The failure is the file-format version gate itself, on the commit that already opened.
  • Intent. The introducing commit c1ae6dc07c9 (LUCENE-9669): "adds an API on DirectoryReader to specify a minimum index version on a per reader basis. This doesn't apply for the IndexWriter which will fail on opening older indices." CHANGES 9.0 (lucene/CHANGES.txt:5015-5020): such indexes open "in read-only mode", and "Opening an index created with a major version of N-2 with an IndexWriter is not supported."
  • Sibling parameter. leafSorter, from the same overload, is passed to reopened readers (StandardDirectoryReader.java:510), and that is tested with this very overload: in TestIndexWriterReader.testIndexReaderWriterWithLeafSorter, "Test4" opens DirectoryReader.open(latestCommit, Version.MIN_SUPPORTED_MAJOR, leafSorter) and checks the leaf order after openIfChanged (TestIndexWriterReader.java:1305-1328; open at :1311, reopen and check at :1324-1325). It is the only existing test that reopens a reader from the expert open, and it passes the default minimum, so it cannot catch this bug.
  • Tests. No test reopens or calls isCurrent on a lower-minimum reader: TestBasicBackwardsCompatibility.testFailOpenOldIndex opens and closes (:856-871); TestDirectoryReader.testOpenWithInvalidMinCompatVersion (:1195-1207) and testOpenCommitWithMinVersionAndExecutor (:1267-1286) open current indexes and close them.
  • History. Before c1ae6dc07c9 every open used the same default gate as the two re-reads (last rewritten by c4bf601b68f, LUCENE-5969, 2014), so a re-read could not reject a reader's own commit. That commit added the minimum to the initial open only; nobody in its PR (21 inline review comments), the issue or the dev@ RFC thread discussed reopen, isCurrent or refresh.
The devil's-advocate check210 words

The strongest works-as-designed case (the devil's advocate built it and rejected it; the cross-model reviews rated it moderate): the overload is "Expert" and meant for one-shot read-only access; it promises only file-format compatibility and makes the rest "best effort"; the minimum has no getter and is not documented as a property of the reader; isCurrent and openIfChanged declare IOException; the main downstream user never refreshes; and a workaround exists (open again).

Why it fails (our reading of the sources): "best effort" reads as covering semantics on top of the file format (the design thread's examples are analysis and the encoding of norms), not the format gate (no document says so in as many words, and none says the minimum is kept across reopen either); read-only was defined as "you cannot open an IndexWriter on it"; the lifecycle contracts do not exclude these readers, and the failure needs no change to the index at all; the introducing commit calls the minimum per reader; the overload's other parameter survives reopen; and a stock released Lucene produces the trigger state. Verdict: a defect. Residual risk: a maintainer may prefer to document the limit instead. Upstream, it reads best as a reader-lifecycle inconsistency (a wrong error on an unchanged index), not a crash.

Suggested fix

#

Recommended Keep the minimum on the reader and use it in the two re-reads (validated)

Keep the minimum on the reader: a final minSupportedMajorVersion field set through the constructor, passed to readLatestCommit in isCurrent() and to readCommit in doOpenFromCommit, and handed to reopened readers like the leafSorter. +29/-7 in StandardDirectoryReader.java; the repro then passes, and so do all 8,898 lucene/core tests.

  // the minimum major version this reader was opened with: isCurrent() and reopen use it too
  private final int minSupportedMajorVersion;

  // isCurrent()
  SegmentInfos sis = SegmentInfos.readLatestCommit(directory, minSupportedMajorVersion);

  // doOpenFromCommit
  final SegmentInfos infos =
      SegmentInfos.readCommit(directory, segmentFileName, minSupportedMajorVersion);

  // doOpenIfChanged(SegmentInfos, ...): carry it to the new reader, like subReadersSorter
  return StandardDirectoryReader.open(directory, infos, getSequentialSubReaders(),
      subReadersSorter, executorService, minSupportedMajorVersion);

Keep the minimum on the reader and use it in the two re-reads (validated) (recommended)

#

A final field set through the package-private constructor. The expert open passes its argument; the NRT path and the public @lucene.internal open(Directory, SegmentInfos, ...) (used by NRT replication) pass Version.MIN_SUPPORTED_MAJOR; the reopen path (doOpenIfChanged(SegmentInfos, ...)) passes the reader's own value to the new reader through a private overload; isCurrent() and doOpenFromCommit use it. +29/-7, in StandardDirectoryReader.java only. The core of it:

  // the minimum major version this reader was opened with: isCurrent() and reopen use it too
  private final int minSupportedMajorVersion;

  // isCurrent()
  SegmentInfos sis = SegmentInfos.readLatestCommit(directory, minSupportedMajorVersion);

  // doOpenFromCommit
  final SegmentInfos infos =
      SegmentInfos.readCommit(directory, segmentFileName, minSupportedMajorVersion);

  // doOpenIfChanged(SegmentInfos, ...): carry it to the new reader, like subReadersSorter
  return StandardDirectoryReader.open(directory, infos, getSequentialSubReaders(),
      subReadersSorter, executorService, minSupportedMajorVersion);

Trade-offs

  • One int per reader. No change for readers opened with the default minimum (the field is then Version.MIN_SUPPORTED_MAJOR, exactly what the re-reads use today) or for NRT readers.
  • A reader opened with a stricter minimum (above the default) now also applies it on refresh, which is what a fresh open(commit, min, sorter) of the new commit would do; that is a behaviour change maintainers may want to decide on explicitly.
  • No getter is added; one could be, but nothing needs it.

Same idea with a mutable field set after construction (validated by the hunt)

#

The finder's sketch (+14/-6) and the independent reproducer's (+16/-6): a non-final private int minSupportedMajorVersion = Version.MIN_SUPPORTED_MAJOR; assigned after new StandardDirectoryReader(...) in the expert open and after open(...) in doOpenIfChanged (the finder with a cast, the reproducer with an instanceof check), plus the same two re-read changes.

Trade-offs

Same behaviour and a smaller diff, but the field is written after construction and needs a cast or an instanceof check; the recommended option keeps it final.

What the checks validated

The finder's 2 tests, the independent reproducer's 7 synthetic and 4 real-index tests, the reviewers' own tests, TestDirectoryReader (34/34) and TestDirectoryReaderReopen (30/30) pass with it (standalone runner, ea57360912ed), the one-test repro passes on 645d4fe14a20 with assertions on and off, and a 9.0.0 backport passes on 9.0.0.

Document the limitation (not built)

#

Say in the expert javadoc that a reader opened with a lower minimum cannot be refreshed and must be re-opened with the same call.

Trade-offs

Leaves isCurrent() throwing on an unchanged index, against its own contract, and SearcherManager / ReaderManager unusable for such readers.

Downstream note

#

A product that serves archived older-major indexes through this expert open and refreshes them with a SearcherManager sees every refresh fail until it re-opens the reader; Elasticsearch's read-only engine opens such readers but never refreshes them.

How it was found

#

Bounded-exhaustive translation validation of Lucene's index-version gate: 336 synthesized commits times 28 operations on the stock jar, compared with a truth table derived from the source. The two operations "isCurrent / openIfChanged on a reader opened with a lower minimum", added from code reading, failed on every commit whose segments come from an older major.

The method in full125 words

Method: semi-formal, bounded-exhaustive translation validation (hunt unit "backcompat 9.x policy", main ea57360912ed, 2026-10-25).

  • A harness synthesized 336 commits (6 created majors x 7 segment versions x 8 minVersion values including null) and ran 28 operations on each against the stock main jar, comparing every outcome with a truth table derived from the source.
  • The operations "isCurrent and openIfChanged on a reader opened with a lower minimum" mismatched on all 21 structurally valid tuples whose segments' minVersion major is below MIN_SUPPORTED_MAJOR.
  • Those reopen operations were added to the harness from code reading of StandardDirectoryReader while modelling the gate: the hunt chose to look there, and the harness showed that every such reader fails. A deterministic JUnit followed, later reduced to the one-test repro.

History

#

Introduced in 9.0.0 by LUCENE-9669 (c1ae6dc07c9, 2021-01-19), which added the per-reader minimum to the initial open only; the two default-minimum re-reads date from 2014. Every release from 9.0.0 through 10.6.0 is affected, plus branch_11x and main; 8.x has no such API.

Versions tested8 rows

Introduced by c1ae6dc07c9 "LUCENE-9669: Add an expert API to allow opening indices created < N-1 (#2212)" (s1monw, 2021-01-19; apache/lucene-solr#2212, approved by jpountz and mikemccand; issue apache/lucene#10708). It added the minimum to the initial open only; the re-reads in isCurrent and doOpenFromCommit were last rewritten by c4bf601b68f (LUCENE-5969, 2014), when every open used the same gate. Later: LUCENE-9507 (2021) carried leafSorter through reopen; LUCENE-10027 (#214, 2021) gave the overload its current form; #15428 / #15445 (10.4.0) added an ExecutorService variant with the same code path; #14607 (dd70ed5801e, 10.4.0) moved the default gate from the commit's created major to each segment's minVersion, which changed which indexes the default open refuses, and so which indexes reach the bug (and the message), not the bug itself. Upstream on 2026-10-31: main is 12.0.0-SNAPSHOT, branch_10x was decommissioned and replaced by branch_11x, 10.6.0 is released; none of them changes the two calls.

LFV-131, snapshot of 2026-11-02

Registry title
A DirectoryReader opened with open(commit, minSupportedMajorVersion, leafSorter) forgets that minimum: isCurrent(), openIfChanged() and SearcherManager.maybeRefresh() throw IndexFormatTooOldException even on an unchanged index
Area
index / DirectoryReader reopen and isCurrent (expert old-index open)
Priority
Low, rank 686: Since 9.0, readers opened with the expert lower-minimum open throw IndexFormatTooOldException on every isCurrent, openIfChanged and maybeRefresh; loud, a reopen works around it, and the known users of that API never refresh.
Impact class
crash
Impact note
Applications that read an index whose segments come from a major below Version.MIN_SUPPORTED_MAJOR through the expert DirectoryReader.open(IndexCommit, int minSupportedMajorVersion, Comparator) (and, by reading, its ExecutorService variant) and then check or refresh that reader get IndexFormatTooOldException from isCurrent(), openIfChanged(reader) and SearcherManager/ReaderManager.maybeRefresh() on every call, even when nothing changed, while the open reader keeps serving its commit (no wrong results, no data loss, no file change); default opens and NRT readers are unaffected; on main the trigger is an 8.x-created index whose segments were all rewritten by 9.x (for example by IndexUpgrader), on 10.x any 8.x index and on 9.x any 7.x index; no scale needed; workaround: close the reader and call open(commit, min, sorter) again.
Summary
You open an index whose segments come from an older Lucene major, which the default open refuses, through the expert DirectoryReader.open(commit, minSupportedMajorVersion, leafSorter) with a lower minimum, and it opens fine. With nothing committed since, you expect isCurrent() to return true and openIfChanged(reader) to return null, so that SearcherManager.maybeRefresh() does nothing. Instead all three throw IndexFormatTooOldException ('Index has segments derived from Lucene version 8.x and is not supported ...'), because the reader does not keep the minimum it was opened with and re-reads the commit with the default Version.MIN_SUPPORTED_MAJOR.
