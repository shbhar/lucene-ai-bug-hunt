CachingCollector never calls LeafCollector#finish on the collector it wraps or when it replays cached scores, so a FacetsCollector reports no hits

Since 9.8.0, a FacetsCollector wrapped in CachingCollector, or fed by its replay with cached scores, reports 0 hits for a query that matches 20 documents, with no error. CachingCollector never passes the per-segment finish() call on, and FacetsCollector records a segment's hits only in finish().

The bug in 30 seconds

#

CachingCollector sits between IndexSearcher and the collector it wraps, records each segment's hits, and can replay them into another collector later. It drops the per-segment finish() call in two places.

Background: how a collector sees a segment

#
  1. For each segment, IndexSearcher asks the collector for a leaf collector, calls collect(doc) for every match, and then calls finish() once the segment is done.
  2. FacetsCollector buffers a segment's matches in collect and adds them to getMatchingDocs() only in finish().
  3. CachingCollector wraps a collector: it forwards each call to it while recording the doc IDs (and, with cacheScores, the scores), so replay(other) can feed the same hits to another collector without rerunning the query.

The bug, step by step

#
  1. Index 20 documents into one segment, all matching f:a. Wrap a FacetsCollector in CachingCollector.create(fc, true, 1000) (cache doc IDs and scores) and search with it. You expect 20 hits in getMatchingDocs(), as without the cache.
  2. Instead it reports 0. IndexSearcher calls finish() on each segment's leaf collector, but the cache's per-segment wrapper overrides finish() for its own bookkeeping and never forwards it. FacetsCollector adds a segment's hits to getMatchingDocs() only in finish().
  3. Replay the cache into a new FacetsCollector(true): again 0 instead of 20. The replay with cached scores never calls finish(); the replay of a cache without scores does, and gives 20.
  4. No error with assertions off. With assertions on and two or more segments, FacetsCollector throws an AssertionError instead. CachingCollectorManager (main, listed for 10.6.0) behaves the same. After a cache overflow, later segments do get finish(), so results turn partial instead of empty.

Who is affected

#

Applications that put a finish-dependent collector (FacetsCollector, BlockGroupingCollector, the TermGroupFacetCollectorManager collectors, the sandbox HistogramCollector or their own) behind CachingCollector (since 9.8.0) or CachingCollectorManager (main), or replay a score cache into one. For them it fires on every query. Lucene's GroupingSearch is not affected: its collectors do not implement finish().

Mechanism, terms and numbers519 words

CachingCollector lets an application run a query once, keep its hits and later replay them into another collector. Two calls to LeafCollector#finish(), the hook IndexSearcher calls once a segment is collected, are missing in it, both introduced by #12380 (9.8.0), the change that added the hook: it wrote the wrapper's non-forwarding finish() override and gave only the no-score replay a finish() call. The per-segment wrapper NoScoreCachingLeafCollector extends FilterLeafCollector, whose finish() forwards to the wrapped collector, but overrides finish() for its own bookkeeping without super.finish() (CachingCollector.java:214-221 on main 645d4fe14a20), so the wrapped collector never gets finish() while the cache is live. And the replay with cached scores, ScoreCachingCollector#collect (:144-155), overrides the no-score replay (:98-104) and leaves out its collector.finish() (:103). The same commit moved FacetsCollector's per-segment MatchingDocs into finish() (FacetsCollector.java:116-128), so a FacetsCollector behind the cache, or replayed from a score cache, reports no hits: 0 of 20 in the repro, with no error unless assertions are on and a slice has two or more segments. BlockGroupingCollector loses each segment's last group the same way. It is a regression from 9.7.0, affects every release from 9.8.0 to 10.5.2 and main, and the new CachingCollectorManager (main, listed under 10.6.0) inherits it. Forwarding the call at both sites (two lines) fixes it; the core caching tests and the grouping and facet modules pass with the fix.

The two missing calls (main 645d4fe14a20)

#
  1. Wrapped first pass, both cacheScores modes. While the cache is live, getLeafCollector returns a NoScoreCachingLeafCollector (or its subclass ScoreCachingLeafCollector) around the wrapped leaf collector (CachingCollector.java:80-90). It extends FilterLeafCollector, whose finish() is in.finish() (FilterLeafCollector.java:51-54), and its collect forwards every hit (CachingCollector.java:188-206). But it overrides finish() with its own bookkeeping only:
   @Override
   public void finish() {
     if (!hasCache()) {
       collector.invalidate();
     } else {
       postCollect();
     }
   }

(CachingCollector.java:214-221). No super.finish(), so the wrapped collector's finish() never runs.

  1. Replay with cached scores. replay(other) calls collect(collector, i) per cached segment (:106-118). The no-score collect ends with collector.finish() (:103); ScoreCachingCollector#collect overrides it to replay doc IDs with scores and ends without it (:144-155).

What the user sees

#
  • FacetsCollector records MatchingDocs only in finish() (FacetsCollector.java:116-128), so getMatchingDocs() stays empty: 0 of 20 hits. With assertions on and a second segment in the slice, doSetNextReader fails assert docsBuilder == null (:107) first.
  • BlockGroupingCollector processes a segment's last group in finish() (BlockGroupingCollector.java:497-502), so that group is lost; with a full queue a returned group can carry another matched document's sort value (executed security probe).
  • When the cache overflows inside a segment, the following segments get the unwrapped leaf collector (CachingCollector.java:87-88), which IndexSearcher finishes (IndexSearcher.java:862). The result is then partial instead of empty (per-leaf finished=[false, true]).
  • CachingCollectorManager builds one CachingCollector per slice (CachingCollectorManager.java:82-91) and inherits both halves; its javadoc example takes the first-pass result directly (:38). Executed through the manager sequentially and with a thread pool; the manager with intra-segment partitions was not run.
Exposure and likelihood171 words
  • Opt-in. CachingCollector and CachingCollectorManager are @lucene.experimental expert APIs (CachingCollector.java:38, CachingCollectorManager.java:48). Within that usage the default settings suffice, and no scale is needed.
  • Silent. With assertions off the facet result is simply empty (or holds only the segments after an overflow); nothing is persisted. With assertions on and 2+ segments in a slice, tests see an AssertionError instead.
  • Grouping. BlockGroupingCollector drops each segment's pending last group; with a full queue a group can come back with another matched document's sort value (executed probe, main and 10.5.2 only: 408 checks on main with assertions off, 433 with them on, 408 on 10.5.2; 0 with the fix).
  • Releases. Every release from 9.8.0 to 10.5.2 and main; CachingCollectorManager (#16247) is listed under 10.6.0, not yet released.
  • Likelihood: rare. Lucene's own GroupingSearch and Solr's grouping cache (by code reading) put no finish-dependent collector behind the cache; saved GitHub code searches found no CachingCollector use on the Elasticsearch and OpenSearch default branches. The recorded searches found no report in the three years since 9.8.0.

Why it is a bug, not intended

#
  • LeafCollector#finish runs once a segment "has finished collecting successfully" (LeafCollector.java:149-159), and create() calls the wrapped collector "the Collector to wrap and delegate calls to".
  • The replay without scores already calls finish() (CachingCollector.java:103), added by the same commit (#12380).
  • Behaviour regression from 9.7.0 (supporting evidence: the hook is new in 9.8.0); delivery that varies with cache overflow cannot be a design.
The full argument151 words
  • Contract. LeafCollector#finish (LeafCollector.java:149-159); CachingCollector.create: "the Collector to wrap and delegate calls to" (CachingCollector.java:301, :320); the leaf wrapper is a FilterLeafCollector, whose finish() delegates (FilterLeafCollector.java:51-54).
  • Same commit, inconsistent. #12380 added the forwarding FilterLeafCollector#finish and collector.finish() in the no-score replay, but not in the scored replay or the wrapper's override. Its 18 review comments and issue #12375 never discuss CachingCollector's forwarding.
  • The test framework asserts it. AssertingCollector checks that the previous leaf was finished (AssertingCollector.java:62); wrapping one in a CachingCollector trips that check (executed).
  • Precedent. The missing or double finish() in DrillSidewaysScorer was fixed as a bug (#12640, #12642, #12853); as gsmiller wrote on #12853, "We should consider it a bug for MatchingDocs to not be populated". In 2011 LUCENE-3102 (#4175) fixed "CachingCollector.replay was failing to call setScorer per-segment".
  • Why tests missed it. TestCachingCollector and TestCachingCollectorManager only use collectors without finish().
The devil's-advocate check141 words

Strongest case (the intended-behaviour check and the works-as-designed cross-model review): the classes are @lucene.experimental; the replay javadoc promises only to replay "the cached doc IDs (and scores)" (CachingCollector.java:345-354); the only in-tree user, GroupingSearch, needs no finish(); and no test caches or replays into a finish-dependent collector.

Why it fails: the no-score replay already calls finish(); the first pass is documented as delegating; delivery that changes with cache overflow is no contract; and experimental status allows API changes, not silently empty results. The cross-model reviews and the intended-behaviour check rated the case weak; the independent reproduction rated it weak for the first pass and weak-to-moderate for the replay. For the scored replay the contract comes from consistency with the no-score replay and the general LeafCollector contract, not from explicit replay wording; the issue should say so.

Suggested fix

#

Recommended Forward finish() at both sites

Forward the call at both sites (CachingCollector.java, +3/-1): super.finish() at the start of NoScoreCachingLeafCollector#finish, which then declares IOException, and collector.finish() at the end of ScoreCachingCollector#collect. The test passes; the core caching tests and the grouping and facet modules pass, with assertions on and off.

Forward finish() at both sites (validated by the checks) (recommended)

#

super.finish() in the leaf wrapper's finish() (first pass, both cacheScores modes) and collector.finish() after the scored replay loop. The wrapped collector then gets finish() exactly once per segment, whether the cache is live or overflowed (after an overflow IndexSearcher finishes the unwrapped leaf collector, as before).

Trade-offs

The override must declare IOException, as FilterLeafCollector#finish already does. Forwarding first means a throwing wrapped finish() skips the cache's bookkeeping for that segment; the search fails with that exception anyway, and putting super.finish() after the bookkeeping works too.

Method: bounded-exhaustive translation validation (semi-formal). While scoping the harness of a hunt unit (concurrent collector managers), the finder read #12380 and suspected that CachingCollector loses LeafCollector#finish. Registry title
CachingCollector (and CachingCollectorManager) never calls LeafCollector#finish on the collector it wraps, nor on the second-pass collector when it replays cached scores, so finish-dependent collectors such as FacetsCollector silently report no hits
Area
search / CachingCollector first pass and score-caching replay (CachingCollector, CachingCollectorManager)
Priority
Low, rank 490: Since 9.8.0 CachingCollector never forwards LeafCollector#finish, so a FacetsCollector behind it silently reports no hits, a natural combination of an experimental API that no known user builds and that -ea tests on several segments catch.
Impact class
silent wrong results
Impact note
Hits applications that combine CachingCollector (released since 9.8.0, @lucene.experimental) or CachingCollectorManager (main only, unreleased) with a collector that finalizes its per-leaf results in LeafCollector#finish, either as the wrapped first pass (both cacheScores modes) or as the target of a score-caching replay: with the default configuration and assertions off, FacetsCollector then reports no MatchingDocs at all (0 of 20 hits in the repro) and BlockGroupingCollector drops each leaf's pending last group and can return a wrong group order and sort values (executed by the security probe), while with assertions on and two or more leaves in a slice FacetsCollector throws AssertionError ('assert docsBuilder == null') instead; once the cache overflows, only the leaves after the overflowing one get finish, so results turn partial rather than empty; no scale is needed, nothing is persisted, and the no-score replay and in-tree GroupingSearch (whose collectors do not implement finish) are not affected.
Summary
You wrap a FacetsCollector, or any collector that does its per-segment work in LeafCollector#finish, in a CachingCollector or CachingCollectorManager so you can run the query once and replay the hits later, or you replay a score-caching cache into such a collector, and you expect the same facet counts as a plain IndexSearcher search. Instead the collector reports no hits: CachingCollector's per-leaf wrapper overrides finish() for its own bookkeeping and never passes the call on, and the score-caching replay never calls finish() at all, although the no-score replay does. In the repro a query that matches 20 documents gives 0 matching docs, with no error unless assertions are enabled.
