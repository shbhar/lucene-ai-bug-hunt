SharedTermsUniformSplit (experimental postings format): a merge that includes a segment without postings throws NullPointerException and closes the IndexWriter

This affects only SharedTermsUniformSplit, an experimental, non-default postings format, shown here as the codec's own postings format. A merge that includes a segment that has fields but no indexed field (for example one document with only a doc-values field) throws NullPointerException and closes the IndexWriter.

The finding in 30 seconds

#

Lucene's generic merge skips a segment that has no postings. SharedTermsUniformSplit has its own merge, written before such segments could reach it, and it does not skip them.

Background: three pieces

#
  1. A postings format stores the terms of the indexed fields. In a merge, each input segment gives the format one postings reader (a FieldsProducer).
  2. Since 9.1.0 a segment in which no field is indexed writes no postings files, and its postings reader is null.
  3. A postings format can be wired per field (getPostingsFormatForField, the usual way) or directly, by returning it from Codec.postingsFormat(). In an ordinary merge the per-field wrapper shows a format only its own fields, so the format normally does not look at a segment without postings. The direct wiring has no such filter.

The finding, step by step

#
  1. You choose the experimental SharedTermsUniformSplit postings format and make it your codec's postings format: a FilterCodec whose postingsFormat() returns STUniformSplitPostingsFormat.
  2. You add one document with StringField("id", "a") and flush, then one document with only NumericDocValuesField("n", 1) and flush. The index now has 2 segments of 1 document each. The second has no indexed field, so it has no postings.
  3. You call forceMerge(1) and expect 1 segment with both documents and docFreq(id:a) = 1. The default codec gives that, and so did this format on 9.0.0.
  4. Instead the merge throws NullPointerException ("fieldsProducer" is null) in STUniformSplitTermsWriter.merge, and IndexWriter closes itself. A document added but not yet committed is gone, and a new writer on the same index fails the same merge again (two more sessions were tried). The committed index stays readable; nothing wrong is written.
  5. Why: since 9.1.0 a segment without postings gives the merge no postings reader (null). Lucene's generic merge skips it. This format's own merge calls terms(...) on every input without that check. With the usual per-field wiring an ordinary merge did not reach that line in any run on 10.x, the 11.0 branch or main; a partitioned merge (an experimental API, on main and the 11.0 branch only) can.

Who is affected

#

Applications that return SharedTermsUniformSplit from Codec.postingsFormat(), once a merge includes a segment with fields but no indexed field. The writer closes, uncommitted changes are lost and a new writer fails the same merge again. Opt-in and rare; nothing wrong is written. With the usual per-field wiring, ordinary merges were not affected in any run on 10.x or main.

Mechanism, terms and numbers1,042 words

Only SharedTermsUniformSplit is affected: an experimental, non-default postings format in lucene-codecs that keeps the terms of all fields in one shared dictionary. It overrides merge for speed (STUniformSplitTermsWriter.java:280-321 on main 781025d6fe32). The override takes each input's postings producer from mergeState.fieldsProducers (:291) and calls fieldsProducer.terms(fieldInfo.name) for the input's fields (:297) with no null check. Since LUCENE-10291 (9.1.0), a segment in which no field is indexed has no postings producer: SegmentCoreReaders sets fields = null (SegmentCoreReaders.java:95-102) and MergeState keeps the null (MergeState.java:155-158). The generic merge that every postings format inherits skips such an input (FieldsConsumer.java:82). So when the format is returned from Codec.postingsFormat() and a merge includes a segment that has a field but no indexed field, the merge throws NullPointerException, and IndexWriter treats it as a tragic event and closes itself. Uncommitted changes are lost and the same merge failed again in both further writer sessions that were tried, while the committed index stays readable and nothing wrong is written. The merge does not have to be a forceMerge: one that the default merge policy picks by itself fails the same way. With the usual per-field wiring (getPostingsFormatForField) an ordinary merge did not reach the line in any run on 10.x, branch_11x or main, because the per-field merge shows the format only its own fields. Two other known ways reach it with that wiring: an index created by 8.x, on 9.2.0 to 9.12.3, and, on main and branch_11x, a partitioned merge (an experimental API) in which one output takes no document of an input that has the field (DocRangeCodecReader.java:121-124 returns a null producer for the empty range). The same test passes on 9.0.0, so this is a regression of 9.1.0: that change updated the consumers in lucene/core and not this override. A validated fix skips an input without a producer, as the generic merge does.

Terms

#
  • SharedTermsUniformSplit: STUniformSplitPostingsFormat, @lucene.experimental, module lucene-codecs. The terms of all fields share one block file and one dictionary (STUniformSplitPostingsFormat.java:33-42). Its writer overrides merge "for efficiency": the regular merge would scan the shared dictionary once per field (STUniformSplitTermsWriter.java:70-74).
  • Postings producer: the per-segment postings reader. MergeState.fieldsProducers holds one per merge input ("Postings to merge", MergeState.java:73-74).
  • Tragic event: an exception inside a merge that IndexWriter cannot recover from. The writer closes itself and drops what was not committed (IndexWriter.java:5174-5178).

The bug

#
  1. Opening a segment asks the codec for a postings reader only if some field has postings; else fields = null (SegmentCoreReaders.java:95-102). The segment flushed from the doc-values-only document is such a segment.
  2. The merge keeps the null: fieldsProducers[i] = reader.getPostingsReader(); if (fieldsProducers[i] != null) { ... } (MergeState.java:155-158).
  3. SegmentMerger.mergeTerms hands the merge to the codec's postings format when the merged segment has postings (SegmentMerger.java:227-230).
  4. The generic merge skips a null producer: if (f != null) { (FieldsConsumer.java:78-89, the check at :82).
  5. The shared-terms override does not (STUniformSplitTermsWriter.java:280-321): :291 reads fieldsProducers[segmentIndex], :294 loops over the input's field infos, :297 calls fieldsProducer.terms(fieldInfo.name). The second segment has one field info (n) and a null producer, so :297 throws.
  6. IndexWriter.merge passes the exception to tragicEvent(t, "merge") (IndexWriter.java:5174-5178).

Why the per-field wiring was not affected in an ordinary merge: PerFieldPostingsFormat builds its groups from the fields of the non-null producers (PerFieldPostingsFormat.java:171-181) and hands each format a view restricted to its group's fields (:191, PerFieldMergeState.java:44-56). A segment without postings then lists no field of the group, so the loop body at :294 never runs for it. Why it looks unintended

#
  • Lucene's generic merge skips an input without postings (if (f != null)). This format's own merge does not.
  • A regression: the test passes on 9.0.0. LUCENE-10291 (9.1.0) made the reader nullable and updated only the consumers in lucene/core.
  • Lucene's own comment: "A null producer is what a reader with no postings looks like, and the merge already skips those."
The full argument514 words

No javadoc says that an entry of MergeState.fieldsProducers may be null ("Postings to merge", MergeState.java:73-74; CodecReader.getPostingsReader: "Expert: retrieve underlying FieldsProducer", CodecReader.java:66-71). So this is not a broken documented contract. The intent is in the code around it and in its history:

  • The generic merge skips the null (FieldsConsumer.java:82). Its javadoc says an override is "for more sophisticated merging (bulk-byte copying, etc)" (:66-71); nothing narrows the inputs an override gets.
  • The change that made the producer nullable fixed the other consumers. LUCENE-10291 (#11327, PR #539, Yannick Welsch, 9.1.0) changed 13 files, all under lucene/core, among them FieldsConsumer, PerFieldMergeState, PerFieldPostingsFormat, CodecReader, CheckIndex, MergeState, SegmentCoreReaders and SegmentMerger. This override in lucene/codecs reads the array itself and was not touched: the file is byte-identical in 9.0.0 and 9.1.0.
  • That change's own test merges segments without postings under a codec without the per-field wrapper. TestMinimalCodec merges two segments of documents without fields ("test merges", TestMinimalCodec.java:58-71) under a codec whose postingsFormat() throws (:119-122). The issue's description (PR #539 has the same text) gives "if you index with SimpleText" as its example, and Robert Muir asked there that the "test should make sure a merge happens as well". What the test shows and what it does not: both of its segments have no postings, so the merged segment has none and no postings format is asked to merge (SegmentMerger.java:227). It shows that such segments and codecs without the per-field wrapper were in the change's scope. It does not test a merge override that gets a null entry beside non-null ones.
  • Upstream states the expectation in its own words. DocRangeCodecReader.java:115-120: "A null producer is what a reader with no postings looks like, and the merge already skips those."
  • It is a regression. The same test passes on 9.0.0 and fails on 9.1.0. The failing line is from the format's first commit (LUCENE-8753, 2019) and was correct then: until 9.1.0 MergeState called getMergeInstance() on every input's postings producer (fieldsProducers[i] = reader.getPostingsReader().getMergeInstance();, MergeState.java:135 at the 9.0.0 tag), so a merge could not start with a null one.
  • The override expects a MergeState that may or may not be filtered by the per-field wrapper. Its loop comment says the field infos "may be filtered by PerFieldMergeState" (STUniformSplitTermsWriter.java:292-293). That is what the code shows; it is not a statement of the author's intent. Its two other unsupported cases, a merge that an index sort reorders (:282-287) and a wrapped Terms (:299-303), fall back to the generic merge instead of failing.
  • Control. The UniformSplit format without shared terms, wired the same way, merges the same two segments. So the wiring works; the failure belongs to this one override.
  • Why no test saw it. The format's tests use the per-field wiring (TestUniformSplitPostingFormat.java:37), where an ordinary merge does not reach the line, and the test framework's random codec does not pick this format; a run that selects it with tests.postingsformat gets the per-field wiring too (SetupAndRestoreStaticEnv.java:147-176).
The devil's-advocate check251 words

The strongest case for "intended": the test is off the documented wiring. The codecs package documentation says that to customise the postings format you "extend the default codec and override ... getPostingsFormatForField(String)" (package-info.java:59-64). The format is @lucene.experimental, not the default, and its own tests always use the per-field wrapper. MergeState.fieldsProducers never promises anything about null. The failure is loud and writes nothing wrong.

Why it does not make the behaviour intended: the package text is a recommendation, not a precondition. Codec.postingsFormat() is documented only as "Encodes/decodes postings" (Codec.java:84-85), and Lucene returns plain formats from it itself (SimpleTextCodec.java:56-59, CheapBastardCodec.java:34-37, and the benchmark module for any format found by name, CreateIndexTask.java:150-160; these show the wiring only and were not run with this format). Nothing documents a wiring restriction for this format. The documented per-field wiring reaches the same line on main and branch_11x through a partitioned merge; that path is narrow too (an experimental API, in no release, with a merge policy of the application's own). "Experimental" is about API stability, and upstream has fixed defects of this format family before (LUCENE-9105, LUCENE-9135). Loudness decides the priority, not whether it is a bug. What survives of the argument is "narrow reach". A maintainer can reasonably give it a low priority, or decline it, for that reason; "works as designed" is harder to hold, because no non-null precondition is stated and the generic merge skips the null. That is why the priority is Low.

Suggested fix

#

Recommended Skip an input without a postings producer (validated)

Skip an input whose postings producer is null at the top of the per-segment loop of STUniformSplitTermsWriter.merge, as the generic merge does. One file, 5 lines. Validated: the test passes, the uniform-split formats' test packages have no failure (assertions on and off) and check is clean.

for (int segmentIndex = 0; segmentIndex < fieldsProducers.length; segmentIndex++) {
  FieldsProducer fieldsProducer = fieldsProducers[segmentIndex];
  if (fieldsProducer == null) {
    // This segment has no postings (or the merge takes no document from it): nothing to merge,
    // as in FieldsConsumer#merge.
    continue;
  }
  // ... the existing loop over mergeState.fieldInfos[segmentIndex]

Skip an input without a postings producer (validated) (recommended)

#

In STUniformSplitTermsWriter.merge, continue with the next input when fieldsProducers[segmentIndex] is null. An input without postings then contributes nothing, exactly as in FieldsConsumer.merge. One file, 5 added lines.

  • It removes this exception only. In an earlier enumeration of 144 partitioned merges on main with the fix, the per-field wiring still ended 24 merges with an output that cannot be opened. That is another registered defect (LFV-280: an output that holds only documents of inputs without postings), not this one.
  • LFV-249, another defect of the same method (postings of fields from another source group are dropped), is not touched by it. One upstream change could carry both fixes.

Fall back to the generic merge when an input has no producer (not built)

#

Call super.merge(mergeState, normsProducer) and return, as the method already does for a merge that an index sort reorders and for a wrapped Terms.

Trade-offs

The more conservative change: the whole unusual merge goes to the generic implementation, and a maintainer may prefer it for that reason. The cost: the merge loses the single-pass path whenever one input has no postings.

Document the null entry (not built; can go with the fix)

#

Say in the javadoc of MergeState.fieldsProducers that an entry is null for an input without postings, so authors of other FieldsConsumer.merge overrides know.

Trade-offs

Text only. It would not fix this format.

No code change: tell users to wire the format per field

#

With the per-field wiring ordinary merges were not affected in any run on 10.x, branch_11x or main.

Trade-offs

Not enough once the partitioned merge is released: it reaches the same line with the per-field wiring.

Handle the null in one central place (not built, not evaluated)

#

For example MergeState could give an input without postings an empty producer instead of null, so that no merge override has to check.

Trade-offs

It would change, for every consumer, what LUCENE-10291 introduced. Named only because where a null belongs is the maintainers' choice; the recommended fix is enough for every path that was run.

Downstream note

#

An application that uses this format as its codec's postings format and indexes documents whose shape other parties control can have its IndexWriter closed by a merge.

How it was found

#

Semi-formal. A seeded differential test ran each case as an ordinary merge and as a partitioned merge and compared both with a written model. With this postings format selected it reported a merge that threw. The cause was then checked against an exact rule on 80 ordinary and 144 partitioned merges and reduced to one public-API test.

The method in full236 words

Method: semi-formal (differential and bounded-exhaustive runs on the real classes; no model-checking tool, solver or prover was involved).

  • The signal. A seeded differential test of the partitioned merge runs every case twice, as an ordinary one-output merge and as a partitioned merge of the same inputs, and checks ten rules of a written model. Run with the shared-terms postings format selected, it reported "merge threw": the NullPointerException in STUniformSplitTermsWriter.merge under the per-field wiring, in a partitioned merge with an empty document range.
  • The rule. From the code, an exact rule was written for when the shared-terms merge meets a null producer for an input that still lists a field. It was checked on the real classes: 80 ordinary merges (2 or 3 segments; documents that are indexed, doc-values-only or without fields; both wirings; 8 index-sorted cases) on main, 10.6.0, 9.12.3 and 9.1.0: 16 predicted, 16 threw, all under the direct wiring; none on 9.0.0. And 144 partitioned merges with three codecs on main: no mismatch (the exception in 108 of 144 merges under the direct wiring and in 54 of 144 under the per-field wiring).
  • A predicted path. The rule predicted the 9.x path (an index created by 8.x under the per-field wiring), which was then executed on 9.2.0 and 9.12.3.
  • Reduction. The released-code face was reduced to a public-API JUnit test, and a later minimality check replaced it with the one-file test of the repro.
