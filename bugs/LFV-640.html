CheckIndex -exorcise with more than one thread writes the surviving segments in size order, not commit order

When CheckIndex repairs an index with more than one thread, the default on multi-core machines, it writes the surviving segments smallest first instead of in their original order. A one-thread repair keeps the order; because commits are usually largest (oldest) first, the parallel repair typically writes an insertion-ordered index reversed.

The finding in 30 seconds

#

Since 8.11.0 and 9.0.0 CheckIndex checks segments on several threads by default. To print small segments first it sorts them by file size, and the results it hands to the repair stay in that sorted order.

Background in three steps

#
  1. An index is a list of segments in a commit (segments_N). A document's id is the number of documents in the segments before its own plus its position inside the segment, so the segment order is the document order.
  2. CheckIndex verifies every segment. With -exorcise (or exorciseIndex()) it writes a new commit that keeps the good segments and drops the broken ones.
  3. Since 8.11.0 and 9.0.0 the segments can be checked in parallel. The thread count defaults to the number of CPU cores; -threadCount 1 checks them one after another.

The finding, step by step

#
  1. You add 10, 1 and 1 documents (numbered 0 to 11 in insertion order) in three commits, so the index has segments _0, _1 and _2, in that order. Then _1's stored-fields file gets damaged.
  2. You repair it with CheckIndex -exorcise, or checkIndex() then exorciseIndex(), on a machine with 2 or more cores, where the thread count defaults to the number of processors the JVM reports.
  3. You expect what a one-thread repair writes: _1 dropped, the rest in order, [_0, _2], so Sort.INDEXORDER returns ids 0-9, then 11.
  4. Instead the new commit is [_2, _0]: the parallel check sorted the segments by file size so small ones print first, and the repair writes that sorted list. The last document added, id 11, is now first.
  5. Nothing is lost beyond _1; only the order changes. With commits of 40, 10, 25 and 5 documents of similar size (a 100-character stored body each), the default command line writes [_3, _2, _0], fully reversed: Sort.INDEXORDER's top 5 become ids 75-79 instead of 0-4.

Who is affected

#

Anyone who repairs a damaged index with CheckIndex -exorcise, Luke's repair, or checkIndex() plus exorciseIndex() on a machine with 2 or more cores, or with an executor. It matters to applications that rely on insertion order: Sort.INDEXORDER, the order of tied hits, LogMergePolicy. Nothing is lost beyond the broken segments, and repairs are rare emergency actions.

Mechanism, terms and numbers449 words

CheckIndex -exorcise repairs a damaged index by writing a new commit that keeps the good segments and drops the broken ones. Since 8.11.0 and 9.0.0 the check runs on several threads by default (threadCount = the number of cores). In that mode it sorts the segments by file size so that small ones print first, collects the results in that sorted order, and exorciseIndex commits that list as it is. A one-thread repair keeps the commit order. The repaired index has the right documents, deletes and values, but the order of whole segments, and so of all documents, depends on the thread count: commits are usually largest (oldest) first, so an insertion-ordered index typically comes back reversed and Sort.INDEXORDER returns the newest documents first.

The code (main 645d4fe14a20, CheckIndex.java)

#
  1. Default is concurrent. threadCount = Runtime.getRuntime().availableProcessors() (:541); checkIndex(List) creates a fixed pool whenever threadCount > 1 and calls the executor overload (:588-600).
  2. The sequential branch keeps commit order. With no executor it walks lastCommit.info(i) for i = 0..n-1 and calls processSegmentInfoStatusResult (:823-845).
  3. The concurrent branch sorts by size. It copies the commit into segmentCommitInfos (:850-854), sorts the copy by sizeInBytes() ascending (:856-869, commented "smaller segment tends to finish faster, and hence its output can be printed out faster"; a size that throws IOException compares as equal) and submits the largest first (:871-896).
  4. Results are collected in the sorted order. The result loop walks segmentCommitInfos.get(i) (:898-931) and calls processSegmentInfoStatusResult (:929), which appends to Status.segmentInfos and, for a good segment, result.newSegments.add(info.clone()) (:975-985).
  5. The repair writes that list. exorciseIndex calls newSegments.changed() and newSegments.commit(dir) (:4606-4614), with no reordering.

Only the position of whole segments in segments_N changes, and with it the starting doc id of every segment that moves. Once this branch runs the order does not depend on timing: even a single-thread executor reorders. Each surviving segment keeps its deletes, soft deletes and doc-values updates.

Exposure and likelihood300 words
  • Who. The CheckIndex command line with -exorcise ("When not specified, this will default to the number of CPU cores"); Luke's check and "Try to Repair" (a default CheckIndex, then exorciseIndex on the status it returned); any caller of checkIndex() plus exorciseIndex() with the default thread count or setThreadCount(n > 1), or of checkIndex(null, executor) with any executor (a repair needs a full check: exorciseIndex rejects a partial status); and downstream shard-repair commands that call checkIndex(null) without setThreadCount (read in their source, not run).
  • Default vs opt-in. Default whenever Runtime.getRuntime().availableProcessors() is more than 1, so on any multi-core host. -threadCount 1, or a JVM that reports one processor, is sequential and keeps the order.
  • Scale. Independent of index size. Affected: indexes with more than one surviving segment whose commit order differs from ascending sizeInBytes() order. That is the usual case, because commits are usually largest (oldest) first, so the ascending sort typically reverses them. Observed in the intended-behaviour check: an insertion-ordered LogDocMergePolicy index _13(108) _17(12) _1b(12) _1c(4) _1d(1) with _17 broken comes back [_1d, _1c, _1b, _13] instead of [_13, _1b, _1c, _1d] (that run did not log byte sizes).
  • What changes. Sort.INDEXORDER results, the order of equal-score hits (ties go by doc id), and which segments LogMergePolicy later treats as adjacent. Concurrent and sequential repairs of the same index write different commits, and the result depends on the machine's core count.
  • What does not. No document is lost beyond the broken segments, none is added or altered, deletes, soft deletes and doc-values updates are kept, and the repaired index checks clean.
  • How likely. Rare: -exorcise is an emergency action on an index that already has a broken segment, and only applications that rely on relative document order notice. The recorded searches found no report since 8.11.0 (2021).

Why it looks unintended

#
  • The thread count is documented only as a speed-up: -threadCount 1 means "performed sequentially", and the executor overload is "to speed up the check".
  • The size sort's only stated purpose is printing: small segments finish first, "hence its output can be printed out faster".
  • Lucene warns where tools may reorder documents (IndexUpgrader, TieredMergePolicy); CheckIndex only promises to remove broken segments.
The full argument314 words
  • The thread count is a speed knob. CheckIndex.java:532 "Set threadCount used for parallelizing index integrity checking."; :621 "This method allows caller to pass in customized ExecutorService to speed up the check."; usage :4845-4847 "When '-threadCount 1' is used, index checking will be performed sequentially." The originating issue LUCENE-9662 (#10701) asked for concurrency so the check finishes faster.
  • Exorcise only removes. Class javadoc :104-105 "write a new segments file that removes reference to problematic segments"; exorciseIndex :4603-4604 "effectively removing all documents in broken segments from the index"; :4657-4659 "With -exorcise, this tool will remove any segments that have issues and write a new segments_N file."
  • The sort is for printing and scheduling. The code comment (:856-857) and the #128 review, where the author wrote that following the sequential order "is not really needed, especially under concurrent setting", about the printed output. No discussion found in #128, #10701, the 8.x backport or #281 identifies the sort's effect on newSegments or on the order of the repaired commit (exorcise appears there only in pasted tool output and in #281's copy of the command-line usage).
  • Reordering tools warn; CheckIndex does not. IndexUpgrader.java:48-52: "If your application relies on \"monotonicity\" of doc IDs (which means that the order in which the documents were added to the index is preserved), do a full forceMerge instead", and :77 "WARNING: This tool may reorder document IDs!"; UpgradeIndexMergePolicy.java:44-48; TieredMergePolicy.java:46-47 "this policy freely merges non-adjacent segments; if this is a problem, use LogMergePolicy"; ParallelCompositeReader.java:36-44 recommends LogDocMergePolicy "as this one does not reorder documents during merging (like TieredMergePolicy)".
  • History. Before 424192e1704 one loop walked the commit in order and filled newSegments; splitting it into two branches changed the concurrent result order as a side effect.
  • Tests. No Lucene test calls exorciseIndex. TestUtil.checkIndex by default runs the concurrent check with 2-5 threads but never exorcises, so nothing would have caught it.
The devil's-advocate check303 words

The lenses of an independent reviewer from another model family (OpenAI GPT-5.6) returned "not real", high confidence, after reproducing the reorder and agreeing with the root cause and the fix: no javadoc promises any order for Status.segmentInfos (public), Status.newSegments (package-private) or the repaired commit; CheckIndex is @lucene.experimental; doc numbers are "ephemeral" (IndexReader.java:51-54) and docids "internal implementation" (index/package-info.java:101-105); the default TieredMergePolicy already merges non-adjacent segments; and exorcise renumbers every document after a dropped segment anyway.

Why it fails: the ephemeral-docid text is about absolute numbers changing as documents are added, deleted and merged. Relative insertion order is something Lucene treats as relied upon: it names it ("monotonicity"), warns in the tools that may break it (IndexUpgrader, UpgradeIndexMergePolicy, TieredMergePolicy), and sends users who need it to LogMergePolicy, whose users then get a reversed index from exorcise with no warning. And two execution modes, documented only as a faster and a sequential way to run the same check, write different commits from the same input; that equivalence is an implied contract, not a written one. Concession: maintainers may land a fix as a consistency improvement rather than a bug fix (the analogous IndexSearcher parity change GITHUB#12516 was filed under "Changes in runtime behavior"). The hunt's verdict was "confirmed", medium confidence, after a "disputed" judge.

The core of the case is that the repaired index depends on -threadCount, with Sort.INDEXORDER reversed, not that doc ids change; no javadoc promises the order, and the Status.segmentInfos order alone is not a bug. Likely objections are the ephemeral-docid javadoc and #7405 ("Remove checkindex -exorcise"), and (the fact check adds) that readers can already order leaves differently (IndexWriterConfig#setLeafSorter, DirectoryReader.open(dir, leafSorter)): that is opt-in and explicit, while the reorder here is a side effect of the thread count.

Suggested fix

#

Recommended Record the results in commit order; keep size-ordered scheduling and printing

Keep the size-ordered scheduling and printing, but record the results in commit order after the result loop, as the sequential branch does (+11/-1 lines in CheckIndex.java). The repro then passes, and so do the 1,396 tests of the core index package, with assertions on and off.

      Map<SegmentCommitInfo, Status.SegmentInfoStatus> statuses = new IdentityHashMap<>();
      for (int i = 0; i < numSegments; i++) {
        // ... unchanged: wait for futures[i], print its output in size order ...
        statuses.put(info, segmentInfoStatus); // was: processSegmentInfoStatusResult(...)
      }

      // record the results in commit order, as the sequential branch does
      for (SegmentCommitInfo info : lastCommit) {
        if (statuses.containsKey(info)) {
          processSegmentInfoStatusResult(result, info, statuses.get(info));
        }
      }

Record the results in commit order; keep size-ordered scheduling and printing (validated by the checks) (recommended)

#

In the concurrent branch, keep each status in an identity map instead of recording it at once, then walk the commit and record the results in its order. +11/-1 lines (one import, the map, the final loop).

      Map<SegmentCommitInfo, Status.SegmentInfoStatus> statuses = new IdentityHashMap<>();
      for (int i = 0; i < numSegments; i++) {
        // ... unchanged: wait for futures[i], print its output in size order ...
        statuses.put(info, segmentInfoStatus); // was: processSegmentInfoStatusResult(...)
      }

      // record the results in commit order, as the sequential branch does
      for (SegmentCommitInfo info : lastCommit) {
        if (statuses.containsKey(info)) {
          processSegmentInfoStatusResult(result, info, statuses.get(info));
        }
      }

Trade-offs

  • newSegments and Status.segmentInfos match the sequential branch; #128's deliberate print and scheduling order stay.
  • One map entry per segment. SegmentCommitInfo does not override equals, so an identity map is exact.
  • Segments skipped by onlySegments are never put, so they stay skipped; that only affects Status.segmentInfos, since exorciseIndex rejects a partial status. The interrupted-caller path is unchanged (a null status is still passed on; that is a separate bug in the same loop).

  • org.apache.lucene.index.*: 1,396 tests, 56 skipped, 0 failures, assertions on and off (seed DEADBEEF); 22 of these test classes call TestUtil.checkIndex, which by default runs the concurrent check with 2-5 threads.
  • checkGoogleJavaFormat, ecjLintMain and forbiddenApisMain pass for lucene:core.

Collect and print in commit order (validated by the checks)

#

Walk the commit and look up each segment's future (the finder's fix).

Trade-offs

Fixes the order, but moves the per-segment log output back to commit order, which #128 changed on purpose ("so that the smaller ones finishing faster should be printed out earlier"); reviewers may object.

What the checks validated

By the tie-breaker on a9779ef3c193: the finder's, the independent reproduction's, the intended-behaviour check's and the command-line tests pass, and TestCheckIndex 9/9.

Reorder in exorciseIndex (not run)

#

Rebuild newSegments in the commit's order before committing.

Trade-offs

Fixes the written index only; Status.segmentInfos stays size-ordered, and exorciseIndex would have to re-read the commit (Status keeps only segmentsFileName) or newSegments would have to carry each segment's position.

Document the size order (not recommended)

#

Say that with threadCount > 1, -exorcise writes the segments in ascending size order.

Trade-offs

Keeps two execution modes that write different indexes from the same input.

Downstream note

#

Downstream shard-repair commands (Elasticsearch's and OpenSearch's RemoveCorruptedLuceneSegmentsAction) call checkIndex(null) without setThreadCount, so on multi-core hosts they also write the size-ordered repair (read in their source, not run).

How it was found

#

An executor-behaviour sweep ran 13 Lucene APIs with 9 kinds of executor and compared each result with the call without an executor. CheckIndex's per-segment results came back in another order in every cell; reading exorciseIndex showed that the repair writes that order, and a JUnit with one damaged segment confirmed it.

The method in full119 words

Method: non-formal (a differential sweep over a hand-picked set of executor behaviours is testing, not bounded-exhaustive checking; the finder tagged it semi-formal).

  • A hunt unit (executor pluggable-behaviour sweep) ran a harness over 13 API surfaces and 9 executor behaviours on the stock jars, comparing each call with the executor-less call (same result fingerprint expected).
  • The CheckIndex.checkIndex rows differed in every non-rejecting cell (caller-runs, single thread, LIFO pool, interrupted pool thread): on a clean 5-segment index Status.segmentInfos came back _1,_3,_2,_0,_4 instead of _0 to _4.
  • The finder then read exorciseIndex, saw that it commits the same list, and wrote a public-API JUnit with one corrupted segment, which fails with assertions on and off while the sequential control passes.

History

#

Introduced by #128 (424192e1704, merged 2021-09-01; 8.x backport lucene-solr#2567), which made the check concurrent and added the size sort. First released in 8.11.0 and 9.0.0; every release since is affected and it was never fixed. 8.10.1 keeps commit order.

Versions tested6 rows

Introduced by 424192e1704 (apache/lucene#128, "LUCENE-9662: CheckIndex should be concurrent - parallelizing index check across segments", committed 2021-08-31, merged 2021-09-01). Before it, one loop walked the commit in order and filled newSegments; the commit split it into a sequential branch (commit order) and a concurrent branch that sorts a copy by sizeInBytes() and records the results in that order. exorciseIndex was not changed. The 8.x backport is 965b54ce3fd (apache/lucene-solr#2567, 2021-09-10). Follow-up 7f8607b59e0 (#281) made the default thread count all cores instead of min(cores, 4); both defaults are concurrent on any multi-core host. Later commits on these lines (#637, #12530, #12876, #12979) only made printing null-safe, renamed a variable, replaced Collections.sort with List.sort and used StandardCharsets.UTF_8.

8.10.1 and 8.11.0 build the same index with identical segment sizes, and only 8.11.0 reorders, so the change is in CheckIndex alone. The 2021 main snapshots themselves were not built.

Low, rank 638: Concurrent CheckIndex -exorcise permutes surviving segment order only during a rare repair of an already broken index and no API promises that order, so it ends the CheckIndex rows after LFV-561.
Impact class
minor
Impact note
Operators and applications that repair an index with a broken segment through CheckIndex -exorcise (the command line, Luke's 'Try to Repair', or checkIndex() followed by exorciseIndex; downstream shard-repair commands call checkIndex(null) without setThreadCount) on any host with 2 or more CPUs, where threadCount defaults to availableProcessors, get a valid repaired index with exactly the documents, deletes, soft deletes and doc-values updates a sequential run keeps, but with the surviving segments in ascending sizeInBytes order instead of commit order; commits are usually roughly largest (oldest) first, so an insertion-ordered index typically comes back reversed, which changes Sort.INDEXORDER results, the order of equal-score hits and which segments LogMergePolicy later treats as adjacent; nothing is lost or altered beyond the broken segments, doc ids are documented as ephemeral, and no API promises the order, so the visible defect is that sequential and concurrent repairs of the same index write different commits; any index size; every release since 8.11.0 [exec].
Summary
You repair an index that has a broken segment with CheckIndex -exorcise, or checkIndex() followed by exorciseIndex, on a multi-core machine, where threadCount defaults to the number of cores. You expect the same repaired commit that a sequential run (-threadCount 1) writes: the documentation describes the thread count and the executor overload only as ways to speed up the check, and exorcise only as removing the broken segments. Instead the concurrent path collects the segment results in ascending file-size order (a sort added so that small segments print first) and exorciseIndex commits that list as it is, so the surviving segments, and with them the relative order of their documents, are permuted; an index written in insertion order comes back reversed, so Sort.INDEXORDER returns the newest documents first instead of the oldest.
