The finding in 30 seconds

#

The flexible parser and its interval syntax

#
  1. The flexible StandardQueryParser works in two stages: StandardSyntaxParser turns query text into a tree of query nodes, then processors and builders turn the tree into a Lucene Query.
  2. Every node can print itself back as query text with toQueryString; the package docs say that text "can be parsed back by the original text parser". An application can use this to rewrite a parsed tree and pass it on as text.
  3. Since 9.1.0 the syntax has interval functions, for example fn:ordered(a b), fn:wildcard(ab* 5) (a glob and an optional maxExpansions) and fn:fuzzyTerm(abc 1 5) (a term, then optional maxEdits and maxExpansions). An interval node prints field: followed by its function's toString().

The finding, step by step

#
  1. Parse fn:fuzzyTerm(abc) with the flexible StandardSyntaxParser. The node gets the defaults maxEdits 2 and maxExpansions 128. Print the tree with toQueryString.
  2. You expect text that StandardQueryParser parses back to the same query, such as f:fn:fuzzyTerm(abc 2 128): the parser's docs promise "a query string that can be parsed back by the original text parser".
  3. Instead you get f:fn:fuzzyTerm(abc 2128). FuzzyTerm.toString uses the format "fn:fuzzyTerm(%s %d%s)", with no space before the second number. Parsing it reads 2128 as maxEdits and throws IllegalArgumentException: max edits must be 0..2, inclusive; got: 2128.
  4. Two sibling printers fail the same way: fn:wildcard(ab* 5) prints as fn:wildcard(ab* maxExpansions:5) (syntax error), fn:or("a:b" c) loses its quotes (syntax error), and a quoted literal containing the ideographic space U+3000 loses its quotes and silently parses back as two words instead of a phrase; a literal with a closing parenthesis, such as "a)(b", also comes back as a different query with no error.
  5. The query that parse() builds is not affected (it is built from the tree, not from this text); the wrong text reaches applications that print node trees and parse that text again, and Lucene's own error messages (fn:fuzzyTerm(abc 12) for maxEdits 1 and maxExpansions 2). Every release since 9.1.0.

Who is affected

#

Applications that turn flexible-parser node trees with fn: interval functions back into text with toQueryString and parse, store or forward that text: every fn:fuzzyTerm fails, as do wildcards with maxExpansions and some quoted literals; others (with U+3000 or a )) change meaning with no error. The Query that parse() builds is unaffected; Lucene's error messages show the misprint.

Mechanism, terms and numbers719 words

The flexible query parser documents that a query node tree "can also generate a query string that can be parsed back by the original text parser", and QueryNode#toQueryString is "convert to a query string understood by the query parser". For interval functions this fails. IntervalQueryNode#toQueryString prints the field, a colon and the function's toString(), and three of those methods print text the parser rejects or reads differently: FuzzyTerm runs maxEdits and maxExpansions together (fn:fuzzyTerm(abc) prints as fn:fuzzyTerm(abc 2128), which re-parses as maxEdits 2128 and throws), Wildcard prints maxExpansions:5 where the grammar takes a bare number, and AnalyzedText quotes a literal only when Java's \s matches, so literals with : or a keyword print bare (syntax error) and some re-parse with no error as a different query (U+3000 splits a phrase into two words; a ) inside a literal closes the function early). The Query that StandardQueryParser.parse builds is unaffected; applications that round-trip node text and Lucene's own exception messages get the wrong text. Every release from 9.1.0 to 10.6.0 and main; a fix of +12/-4 lines in the three printers passes the repro and the whole queryparser module.

The printers

#
  • IntervalQueryNode#toQueryString is String.format(Locale.ROOT, "%s:%s", field, source) (IntervalQueryNode.java:47-50): the field, a colon and the function's toString(). It ignores its EscapeQuerySyntax argument, and IntervalQueryNode#toString delegates to it (:52-55), so there is no separate display form.
  • FuzzyTerm.toString (FuzzyTerm.java:52-60) formats "fn:fuzzyTerm(%s %d%s)" with the term, maxEdits and the Integer maxExpansions: no space before the second number, so 2 and 128 print as 2128 and 1 and 5 as 15. The grammar reads fn:fuzzyTerm(abc 2128) as term abc with maxEdits 2128 (StandardSyntaxParser.jj:659-679), and building the query throws "max edits must be 0..2, inclusive" (FuzzyAutomatonBuilder.java:38-39, the throw at :39).
  • Wildcard.toString (Wildcard.java:44-51) prints the raw glob and " maxExpansions:" + maxExpansions. The grammar takes the glob as a term, number or quoted token followed by an optional bare number (StandardSyntaxParser.jj:641-657), so maxExpansions:5 is a syntax error, and a quoted glob such as "a b*" loses its quotes.
  • AnalyzedText.requiresQuotes (AnalyzedText.java:53-55) quotes a literal only if Pattern.compile("[\\s]") finds a match. The lexer is stricter: a term cannot start with whitespace (including U+3000) or any of + - ! ( ) : ^ @ < > = [ ] " { } ~ \ / (StandardSyntaxParser.jj:131-133) and ends at any of them except + and - (:134); it reads AND/&&, OR/|| and NOT/! as operators (:144-146) and treats U+3000 as whitespace (:135), which Java's \s does not match by default. So most such literals print bare and fail to parse, some come back as a different query, and a literal such as "x-y" still round-trips. FuzzyTerm reuses this check for its term.

The grid is a test design, not a usage frequency.

Where the text goes

#

StandardQueryParser.parse builds the Query from the tree and never re-parses this text. In-tree, toQueryString output appears only in exception messages (QueryTreeBuilder.java:161, BooleanQueryNodeBuilder.java:72, MatchAllDocsQueryNodeBuilder.java:42, MatchNoDocsQueryNodeBuilder.java:42, AllowLeadingWildcardProcessor.java:74). For example, with a clause limit of 2, parse("a b fn:fuzzyTerm(abc 1 2)", "body") throws "Too many boolean clauses, the maximum supported is 2: body:a body:b body:fn:fuzzyTerm(abc 12)".

Exposure and likelihood178 words
  • Who. Applications that use the flexible parser's node tree as an intermediate form: parse user text with StandardSyntaxParser, inspect or rewrite the tree, then print it with toQueryString and parse, store, cache or forward the text. Also anyone reading logs or exception messages that print interval nodes: fn:fuzzyTerm(abc 12) hides the real maxEdits 1 and maxExpansions 2.
  • Default vs opt-in. Default parser configuration and public API; the trigger needs the fn: interval syntax and an application that re-parses node text (no in-tree caller does).
  • Effect. An exception on the second parse, or, for some quoted literals, a different query with no error: with U+3000 a two-word phrase becomes two separate words, and fn:or("a)(b" c) comes back as body:a (body:b body:c). The results of the original parse() are unaffected.
  • Scale. Any index; deterministic string formatting.
  • How likely: rare. It needs both the niche fn: syntax and a re-parse of toQueryString text; the documented searches found no prior public report since 9.1.0 (2022-03). Two outside ports of the parser copy FuzzyTerm.toString unchanged; no report was found there either.

Why it looks unintended

#
  • toQueryString is documented as "convert to a query string understood by the query parser"; the package docs promise text that "can be parsed back".
  • abc 2128 is not a display form under any reading, and, on inspection, every other interval function prints its grammar syntax.
  • 11.0 fixed the same round-trip failure for range nodes as a bug (GITHUB#7865).
The full argument211 words
  • The contract: QueryNode.java:26 ("convert to a query string understood by the query parser") and core/nodes/package-info.java:42-43 ("A query node tree can also generate a query string that can be parsed back by the original text parser, at this point only the standard lucene syntax is supported"); EscapeQuerySyntax exists "to allow the QueryNode to escape the queries, when the toQueryString method is called" (EscapeQuerySyntax.java:22-23).
  • The inputs are accepted, tested syntax: CHANGES 9.1.0 lists LUCENE-10223 (interval functions) and LUCENE-10414 ("Add fn:fuzzyTerm interval function to flexible query parser", lucene/CHANGES.txt:4415-4417, :4452-4453); upstream tests parse fn:wildcard(foo* 128) ("Explicit maxExpansions") and fn:fuzzyTerm(dfe 2 128) (TestStandardQPEnhancements.java:97-102, :156-162); quoted literals are documented ("Quoted or unquoted character sequences ...", intervalfn/package-info.java:149). The package docs list only fn:wildcard(glob) and not fn:fuzzyTerm, so "accepted, tested syntax" is the accurate wording.
  • The code aims for parseable output: on inspection, the other interval functions print their grammar syntax (the controls round-trip and the 8,352-expression grid shows no failure outside the three printers; there is no dedicated round-trip suite over all functions) and AnalyzedText already quotes when it thinks it must.
  • Precedent: "GITHUB#7865 AbstractRangeQueryNode#toQueryString(EscapeQuerySyntax) now returns a string which can be parsed back into the original node." (lucene/CHANGES.txt:296-298, 11.0.0 Bug Fixes; PR #14697 with regression tests).
The devil's-advocate check172 words

The strongest case for "display only": IntervalFunction#toString has no javadoc; the only upstream test that touches the output prints it "for visual diagnostics" and asserts nothing (TestStandardQPEnhancements.java:180-184); maxExpansions:N looks like a deliberate human-readable label; a 2017 java-user reply said a round trip between a parsed query and its string form was never guaranteed; open #8667 calls the toQueryString design flawed; and no in-tree caller re-parses the text.

Why it fails: IntervalQueryNode#toQueryString, the method whose javadoc promises parser syntax, returns exactly these strings, and IntervalQueryNode#toString delegates to it, so even if IntervalFunction#toString were diagnostic only, toQueryString would still need the fix. The 2017 reply was answered in the same thread with "Why don't we fix this in Lucene?", and the project later fixed the range-node case as a bug (GITHUB#7865). #8667 is about nodes built by custom syntax parsers, while the package docs promise the round trip for "the standard lucene syntax". And abc 2128 cannot be a deliberate display choice. All verifiers and the adjudication rejected the intended-behaviour case.

Suggested fix

#

Recommended Make the three printers emit grammar syntax (+12/-4, validated)

Make the three printers emit the grammar's own syntax: "fn:fuzzyTerm(%s %d %d)" in FuzzyTerm, the bare number (" " + maxExpansions) and a quoted glob when needed in Wildcard, and quote every literal the lexer would not read back as one term in AnalyzedText.requiresQuotes. +12/-4 lines; it passes the repro and the whole queryparser module.

// FuzzyTerm.toString()
"fn:fuzzyTerm(%s %d %d)",
// Wildcard.toString()
AnalyzedText.requiresQuotes(wildcard) ? '"' + wildcard + '"' : wildcard,
maxExpansions == 0 ? "" : " " + maxExpansions);
// AnalyzedText.requiresQuotes(String term)
return term.isEmpty()
    || Pattern.compile("[\\s\\u3000+\\-!():^@<>=\\[\\]\"{}~\\\\/]").matcher(term).find()
    || term.equals("AND") || term.equals("OR") || term.equals("NOT")
    || term.equals("&&") || term.equals("||") || term.startsWith("fn:");

Make the three printers emit grammar syntax (+12/-4, validated) (recommended)

#

The change touches FuzzyTerm.java, Wildcard.java and AnalyzedText.java (the hunt's fix sketch, reformatted by applyGoogleJavaFormat). fn:fuzzyTerm prints both numbers separated (fn:fuzzyTerm(abc 2 128)); fn:wildcard prints the bare number and quotes a glob that needs it; a literal is quoted when it is empty, contains whitespace including U+3000, contains any character a term cannot start with, equals AND, OR, NOT, && or ||, or starts with fn: (redundant, since : is already covered). That covers every literal the lexer would not read back as one term, and a few it would: + and - may follow the first character of a term, so fn:or(a-b c) now prints as fn:or("a-b" c). Quoting more than needed changes the text but not its meaning: a quoted and an unquoted literal build the same node. Apart from such extra quotes, every other printed form is unchanged.

// FuzzyTerm.toString()
"fn:fuzzyTerm(%s %d %d)",
// Wildcard.toString()
AnalyzedText.requiresQuotes(wildcard) ? '"' + wildcard + '"' : wildcard,
maxExpansions == 0 ? "" : " " + maxExpansions);
// AnalyzedText.requiresQuotes(String term)
return term.isEmpty()
    || Pattern.compile("[\\s\\u3000+\\-!():^@<>=\\[\\]\"{}~\\\\/]").matcher(term).find()
    || term.equals("AND") || term.equals("OR") || term.equals("NOT")
    || term.equals("&&") || term.equals("||") || term.startsWith("fn:");

Trade-offs

  • Changes toString only; nothing on a search path. The pattern is compiled per call, as today; a static final Pattern would be a natural cleanup.
  • A hand-built node whose literal holds a raw double quote still prints unparsably (the inner quote is not escaped). The parser itself keeps backslashes inside interval literals (a separate grammar bug); when that is fixed, the printer must also escape " and \ inside quotes, so the two fixes should agree. More generally, the public constructors can build nodes the current syntax cannot represent, so the fix is validated for parser-originated input and the tested grid, not as a general serializer.
  • Not a complete serializer fix: IntervalQueryNode#toQueryString still ignores its EscapeQuerySyntax argument, and the field: prefix is still printed unescaped (LFV-356, a separate fix site).

A dedicated serializer instead of toString (alternative, not written)

#

Give IntervalFunction an explicit toQueryString(EscapeQuerySyntax) and call it from IntervalQueryNode#toQueryString, leaving toString free to be a display form.

Trade-offs

  • Makes the contract explicit and lets the printer use the escaper once the grammar unescapes interval literals.
  • More code and a new method on every interval function class, while, on inspection, the existing toString methods already print grammar syntax for every other function.

Downstream note

#

An application that checks or rewrites a parsed node tree and then re-parses its toQueryString text should not rely on the text meaning the same as the tree, and should add restrictions as separate Query clauses (for example a FILTER clause) instead.

How it was found

#

A hunt that checked the flexible parser against its documented syntax ran a bounded-exhaustive round trip: 8,352 interval expressions were parsed, printed with toQueryString and parsed again on the stock build. 6,100 did not come back the same (121 as a silently different query); with the fix sketch, none failed.

History

#

Introduced in 9.1.0 by LUCENE-10223 (#429: the interval syntax, toQueryString and the literal quoting) and LUCENE-10414 (#668: fn:fuzzyTerm and the wildcard maxExpansions format); the four files are unchanged since, through 10.6.0 and main.

Versions tested4 rows

Introduced in two steps by Dawid Weiss: f725b27e12a "LUCENE-10223: interval support in standard syntax parser (#429)" (2021-11-11) added IntervalQueryNode#toQueryString, the whitespace-only quoting and the unquoted wildcard glob; f6cebac3337 "LUCENE-10414: Add fn:fuzzyTerm interval function to flexible query parser (#668)" (2022-02-10) added the fn:fuzzyTerm(%s %d%s) format and the maxExpansions: suffix. LFV-748, snapshot of 2026-11-09

Registry title
Flexible query parser: IntervalQueryNode#toQueryString prints some fn: interval functions in a form the parser rejects or reads as a different query (fn:fuzzyTerm(abc) prints as fn:fuzzyTerm(abc 2128))
Area
queryparser / flexible StandardQueryParser interval function nodes (IntervalQueryNode#toQueryString; intervalfn FuzzyTerm, Wildcard and AnalyzedText toString)
Priority
Low, rank 799: A minor toQueryString round-trip break for fn: interval nodes that matters only to applications that re-parse node text, which no in-tree caller does.
Impact class
minor
Impact note
A round-trip (contract) defect in a utility method, with no effect on the Query that StandardQueryParser.parse builds: applications that turn flexible-parser node trees with fn: interval functions back into text with toQueryString (or IntervalQueryNode#toString) and parse or forward that text get a string that does not parse for every fn:fuzzyTerm, for fn:wildcard with a maxExpansions argument and for quoted literals that hold a query-syntax character such as ':' or a keyword such as AND, and a silently different query for some quoted literals (one that holds U+3000, or a closing parenthesis as in "a)(b"); inside Lucene the output only feeds exception messages (for example the parser's own too-many-clauses message); default parser configuration, any scale, every release from 9.1.0 to 10.6.0 and main.
Summary
You parse fn:fuzzyTerm(abc), fn:wildcard(ab* 5) or fn:or("a:b" c) with the flexible syntax parser, print the node tree with toQueryString, and expect a string that StandardQueryParser reads back as the same query, as the flexible parser's package documentation promises ('a query string that can be parsed back by the original text parser'). Instead FuzzyTerm prints maxEdits and maxExpansions with no space between them (fn:fuzzyTerm(abc 2128), which re-parses as maxEdits 2128 and throws 'max edits must be 0..2'), Wildcard prints 'maxExpansions:5', a syntax error, and AnalyzedText quotes a literal only when it contains ASCII whitespace, so fn:or("a:b" c) prints the unparsable fn:or(a:b c). A quoted literal with the ideographic space U+3000 prints unquoted and re-parses, with no error, as two separate literals.
