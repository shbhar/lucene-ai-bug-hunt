Expression boolean operators keep only the low 32 bits of a long operand: (1 << 32) ? 1 : 0 is 0

In Lucene expressions, !, &&, || and ?: see only the low 32 bits of a bitwise result or hex literal: (1 << 32) ? 1 : 0 is 0, yet (1 << 32) != 0 is 1. High-bit flag tests on long fields are silently wrong since 4.6.0.

The finding in 30 seconds

#

Lucene compiles an expression to JVM bytecode and gives each sub-expression a type: int, long or double. Bitwise and shift results and hex literals are 64-bit longs. The boolean operators ask for an int, and turning a long into an int keeps only its low 32 bits.

Background in 3 steps

#
  1. The optional lucene-expressions module compiles a formula such as (flags & 0x100000000) ? 10 : 1 into a class whose evaluate returns a double per document; it is used for scores, sort keys and filters.
  2. The syntax is based on JavaScript, but in Lucene & | ^ ~ << >> >>> and hex/octal literals work on 64-bit longs: its own tests check -15 << 62 = 4611686018427387904 and 0x1234ABCDEF = 78193085935.
  3. !, &&, || and ?: treat 0 as false and any non-zero integer as true: the tests check !2 = 0 and -1 ? 2 : 3 = 2.

The finding, step by step

#
  1. Compile (1 << 32) ? 1 : 0 with JavascriptCompiler and evaluate it. In Lucene expressions shifts and & work on 64-bit longs, so 1 << 32 is 4294967296, and any non-zero integer is true (!2 is 0, -1 ? 2 : 3 is 2).
  2. You expect 1: the condition is 4294967296, and (1 << 32) != 0 does give 1.
  3. You get 0, with no error. The compiler asks for the condition as a 32-bit int and narrows the 64-bit value by keeping its low 32 bits. 4294967296 is bit 32 alone, so all 32 kept bits are zero. !, &&, || and hex literals such as 0x100000000 behave the same.
  4. The same number written another way is true: 4294967296 ? 1 : 0 and ((1 << 32) + 0) ? 1 : 0 give 1. Decimal numbers and arithmetic are doubles, and a double too large for an int narrows to the largest int, which is still non-zero.
  5. On a long doc-values field, (flags & 0x100000000) ? 10 : 1 returns 1 for a document with flags = 4294967297 (bits 32 and 0 set). A single-bit mask test such as (flags & 0x100000000) used directly as a condition is false for every document; the same holds for each of bits 32 to 63.

Who is affected

#

Users of the expressions module who apply !, &&, || or ?: directly to a bitwise result, typically to test a bit from 32 to 63 of a long doc-values field: (flags & 0x100000000) ? 10 : 1. The condition is false for every document, so documents with the bit set silently get wrong scores, sort keys or filter results.

Mechanism, terms and numbers856 words

Lucene expressions compile a formula to bytecode, giving every sub-expression a JVM type: int, long or double. The bitwise and shift operators and hex/octal literals are 64-bit longs (1 << 32 is 4294967296), but the four boolean operators !, &&, || and ?: request their operand as an int and narrow a long with l2i, which keeps only the low 32 bits. So a non-zero long whose low 32 bits are zero counts as false: (1 << 32) ? 1 : 0 and 0x100000000 ? 1 : 0 are 0, !(1 << 32) is 1, while (1 << 32) != 0 is 1 and the same number written in decimal is true.

The practical case is a flag test of bits 32 to 63 of a long doc-values field: (flags & 0x100000000) ? 10 : 1 returns 1 and !(flags & 0x100000000) returns 1 for a document with bit 32 set, so the condition is false for every document, and documents with the bit set get the wrong value in scores, sort keys and expression filters, with no error. Bits 0 to 31 and the comparison forms (e) != 0 and (e) == 0 are correct.

The int operand is in the module's first patch (LUCENE-5207, 2013): all 122 lucene-expressions releases from 4.6.0 to 10.6.0 fail, and so does main. Not fixed upstream. Fix: evaluate the operand as a long and compare it with 0L, which changes nothing for double operands.

The mechanism (main 645d4fe14a20)

#
  1. The code generator is type-directed. Each visitor of JavascriptCompiler pushes the type its parent expects onto typeStack, and each child converts its result to typeStack.peek() with gen.conversion(...).
  2. The boolean operators ask for an int. ! pushes TypeKind.INT for its operand (visitUnary, JavascriptCompiler.java:518) and branches with ifeq (:521); && (:694, ifeq at :696, :698), || (:714, ifne at :716, :718) and the ?: condition (:734, ifeq at :737) do the same.
  3. Bitwise and shift results are longs, narrowed to the expected type. pushShift and pushBitwise compute in long (:751-757), and pushBinaryOp ends with gen.conversion(returnType, typeStack.peek()) (:773): long to int is l2i. ~ does the same (:534). A hex or octal literal goes through pushLong, which pushes (int) i in an int position (:796).
  4. l2i and (int) keep the low 32 bits. 4294967296 = 2^32 has only bit 32 set, so it becomes 0 and ifeq takes the false branch. In general a non-zero long operand is false exactly when its low 32 bits are zero (checked with an SMT solver); a single-bit test (x & (1 << k)) is false for every x when 32 <= k <= 62 (solver) and for bit 63 (executed: (1 << 63) ? 1 : 0 is 0).
  5. Doubles of magnitude 1 or more are not affected. A decimal literal (:438-439), a variable (:503), a function result (:494) or arithmetic is a double, narrowed with d2i, which saturates: 4294967296.0 becomes Integer.MAX_VALUE, still non-zero. That is why 4294967296 ? 1 : 0 and ((1 << 32) + 0) ? 1 : 0 are 1. (d2i also makes a fraction false; see the fractions note below.) Comparisons evaluate both sides as doubles (:650): a long result reaches (e) != 0 through l2d, which is non-zero for every non-zero long.

Requesting the four operands as long and comparing them with 0L makes the repro and every row below correct, so the narrowing is the whole cause.

The same code site: fractions

#

The same int operand also makes a fractional double false, through d2i: with x = 0.5, x ? 1 : 0 is 0 while x != 0 is 1. No document states a truth rule for fractions either way, so that case was judged a documentation question rather than a code bug. Fix B below leaves it unchanged; fix A changes it too.

Exposure and likelihood401 words
  • Silent wrong results. The expression returns a number and nothing fails. Scores (getDoubleValuesSource in a FunctionScoreQuery), sort keys (getSortField), rescoring and expression-based filters (FunctionMatchQuery over the values source) take the false branch even where the tested bit is set.
  • Who is exposed. Users of lucene-expressions at default settings, any index size, assertions on or off, who apply a boolean operator directly to a bitwise or shift result or a hex/octal literal that is non-zero with all-zero low 32 bits. In practice: a test of one of bits 32 to 63 of a long bitmask field, written (flags & MASK) ? a : b or !(flags & MASK). Such a single-bit test is false for every document.
  • Expressions are the suggested tool for bitwise flag tests. On #3534 (an open feature request for bitwise filtering on numeric fields), gsmiller suggested in 2024 using expressions over a numeric doc-values field "since the compiler supports bitwise operations"; the comment names no particular form (?:, ! or a comparison). Downstream users write flag tests in expressions too (elastic/elasticsearch#26272, with small values).
  • Filter effect, executed. A FunctionMatchQuery with predicate v != 0 over 5 documents with flags = 0, 1, 2^32, 2^32 | 1 and 2^40: !(flags & 0x100000000) matches 5 of 5 instead of 3, (flags & 0x100000000) ? 1 : 0 matches 0 instead of 2, and the == 0 / != 0 forms match 3 and 2, correctly (main with assertions on and off, 10.5.2).
  • Not affected. Bits 0 to 31, the comparison forms (e) != 0 and (e) == 0, a decimal literal, variable or arithmetic result of magnitude 1 or more used directly as the operand (a fraction is the separate fractions case above), and the index itself.
  • A separate limit, not this bug. A long doc-values field reaches an expression as a double (DoubleValuesSource.fromLongField returns (double) v), so a field value above 2^53 in magnitude can lose low bits before & runs: for flags = 2^53 + 1, (flags & 1) != 0 is 0, before and after fix B. Values up to 2^53, such as every example here, are exact.
  • How likely. Rare: it needs a high-bit test written without a comparison. A single high-bit test is false for every document, so a quick test shows it, and no public report was found in 13 years of releases.

Why it looks unintended

#
  • Lucene's own tests say non-zero integers are true (!2 = 0) and shifts are 64-bit (-15 << 62).
  • Same value, different answer: 0x100000000 ? 1 : 0 = 0 but 4294967296 ? 1 : 0 = 1.
  • No document or recorded decision states a 32-bit test; JavaScript also gives 1 for 0x100000000 ? 1 : 0.
The full argument252 words
  • The tests pin both halves of the conflict. Non-zero integers other than 1 are true: !2 = 0, !-1 = 0 (TestJavascriptOperations.java:178-184), -1 ? 2 : 3 = 2 (:214). The bitwise operators and hex literals are 64-bit: -15 << 62 = 4611686018427387904 (:238), -1 >>> 37 = 134217727 (:260), 0x1234ABCDEF = 78193085935 (:331). 4294967296 is a non-zero integer that the module itself produces, yet it counts as false.
  • The result depends on how the number is written. 0x100000000 ? 1 : 0 = 0 but 4294967296 ? 1 : 0 = 1; (1 << 32) ? 1 : 0 = 0 but ((1 << 32) + 0) ? 1 : 0 = 1 and (1 << 32) != 0 = 1. A sub-expression bound by name through SimpleBindings.add(String, Expression) gives 1 where the same text inlined gives 0.
  • The docs list the operators side by side. The package javadoc lists hex and octal literals, the bitwise operators | & ^ ~ << >> >>> and the boolean operators && || ! ?: in "an expression syntax that's based on JavaScript expressions" (package-info.java:21-28). No javadoc, CHANGES or MIGRATE entry says the boolean operators see only 32 bits.
  • No recorded rationale. The int operand is in the first patch (LUCENE-5207, 2013) and survived four rewrites; no test applies a boolean operator to a long of 2^32 or more, and none of the reviewed commit messages, code comments and discussions mentions it.
The devil's-advocate check185 words

The strongest case for "intended" (an independent reviewer from another model family, rated moderate): JavascriptCompiler and Expression are @lucene.experimental (JavascriptCompiler.java:111), no document defines how a number becomes a boolean, the int lowering is 13 years old, and JavaScript's own & is 32-bit, so JavaScript also takes the false branch for (flags & 0x100000000) ? a : b.

Why it fails: Lucene deliberately makes <<, & and hex literals 64-bit (its own tests), so JavaScript's 32-bit & cannot excuse the result; for (1 << 32) ? 1 : 0 and 0x100000000 ? 1 : 0 JavaScript returns 1 as well (a reference run in node 24; for the first only because JavaScript takes shift counts mod 32, so its 1 << 32 is 1), so Lucene matches neither JavaScript nor 64-bit values; experimental allows API changes, not a non-zero value that is false in one spelling and true in another; and no test, commit or discussion chose the truncation. Verdict: a code bug (every verifier, the cross-model reviews and the adjudication say real; the adjudication and the cross-model reviews with high confidence).

Suggested fix

#

Recommended B: evaluate the boolean operand as a long and compare it with 0L

Evaluate the operand of !, &&, || and ?: as a long and compare it with 0L (a small pushTruth helper used at the four sites). Double operands keep their current truth, so only the broken cases change. The repro passes with assertions on and off; all 170 expressions tests (assertions on) and the module's format and lint checks pass.

  private void pushTruth(ExpressionContext operand) {
    typeStack.push(TypeKind.LONG);
    visit(operand);
    typeStack.pop();
    gen.lconst_0();
    gen.lcmp();
  }

  // in each of the four visitors, for example visitConditional:
- typeStack.push(TypeKind.INT);
- visit(ctx.expression(0));
- typeStack.pop();
+ pushTruth(ctx.expression(0));
  gen.ifeq(condFalse);

B: evaluate the boolean operand as a long and compare it with 0L (validated by the checks) (recommended)

#

A helper replaces the typeStack.push(TypeKind.INT) / visit / pop sequence in visitUnary (BOOLNOT), visitBooland, visitBoolor and visitConditional; the ifeq/ifne branches stay as they are (+19/-14 in JavascriptCompiler.java). With LONG expected, bitwise and shift results and hex/octal literals arrive with all 64 bits, nested boolean results arrive as 0L/1L, and lcmp against 0L leaves 0 exactly when the operand is 0.

  private void pushTruth(ExpressionContext operand) {
    typeStack.push(TypeKind.LONG);
    visit(operand);
    typeStack.pop();
    gen.lconst_0();
    gen.lcmp();
  }

  // in each of the four visitors, for example visitConditional:
- typeStack.push(TypeKind.INT);
- visit(ctx.expression(0));
- typeStack.pop();
+ pushTruth(ctx.expression(0));
  gen.ifeq(condFalse);

Trade-offs

  • Only the broken cases change. A double operand is now converted with d2l instead of d2i; both give 0 for exactly the same doubles (NaN and -1 < v < 1), so decimal literals, variables, functions and arithmetic keep their truth. Executed: 0.5 ? 1 : 0, !0.5, -0.5 ? 1 : 0, NaN, -0, 1e300 and the shift count in 1 << (0x100000000 | 2) give the same values as before.
  • It leaves the fractional case as it is: 0.5 ? 1 : 0 stays 0.
  • One lcmp per operand; no benchmark was run. The shift count, a separate int-typed position (pushShift, :751-753), is not touched.

A: evaluate the operand as a double, true if and only if abs(v) > 0 (validated by the checks)

#

The finder's sketch: a helper evaluates the operand with TypeKind.DOUBLE, calls Math.abs, compares with 0.0 via dcmpl (so NaN stays false) and branches with ifgt/ifle. A long operand reaches it through l2d, which is non-zero for every non-zero long.

Trade-offs

It also makes fractions true: 0.5 ? 1 : 0 goes from 0 to 1, !0.5 from 1 to 0 (NaN, -0 and 0 stay false). That would settle the fractional case as well, but it changes the results of existing expressions for 0 < |v| < 1, so it would need a CHANGES/MIGRATE note and is a policy decision for maintainers.

What the checks validated

The whole :lucene:expressions:test with fix A and the repro: 174 tests, 0 failures; the 17-row probe: 0 rows wrong. The format and lint checks were not run for A.

C (not recommended): saturating long-to-int narrowing

#

Convert long to int through double in pushBinaryOp and ~, and push (int)(double) for literals.

Trade-offs

It fixes the repro and passes the 170 tests, but it also changes long-typed shift counts of 2^31 or more: 1 << (0x100000000 | 2) goes from 4.0 to about -9.22e18, which no upstream test covers. A and B leave it at 4.0.

Downstream note

#

An application that writes an exclusion filter as an expression over flag bits 32 to 63, such as a FunctionMatchQuery on !(flags & 0x100000000), matches the documents it meant to exclude (5 of 5 instead of 3 in a probe); writing (flags & MASK) == 0 instead avoids it.

How it was found

#

Found while modelling the compiler's code generator for a bounded-exhaustive check of all 702,226 expression trees up to size 5; the model, faithful to the compiler, reads boolean operands as an int. Of the 237,419 evaluations that differ from exact-value semantics (first literal alphabet), 145,857 are this case; an SMT solver then characterised it.

The method in full200 words

Method: semi-formal (a hunt unit, the expressions compiler).

  • The finder, an AI tool, wrote an exact model of JavascriptCompiler's type-directed code generation, including the int type of boolean operands, and a bounded-exhaustive translation-validation harness: every expression tree of size up to 5 (702,226 trees, 13,147,954 evaluations per literal alphabet, two literal alphabets, two variables bound to 13 values), each compiled result compared bit for bit with the model (0 mismatches, so the model is faithful) and with a value-semantics reference (over all trees up to size 5 with the first literal alphabet, 237,419 evaluations differ, 145,857 of them a boolean operator over a long operand).
  • Z3 bit-vector and floating-point queries then characterised the class: a non-zero long operand is false exactly when its low 32 bits are zero; the same value through the double path is never false; a single-bit test of bit 32 to 62 is false for every input (with a vacuity probe for bits below 32); bit 63 was later shown the same way by execution.
  • The finder then wrote a public-API JUnit on the stock jar. Independent reproducers wrote their own tests from the claim alone; the one-test repro was cut from those on 2026-10-29.

LFV-181, snapshot of 2026-11-07

Registry title
Expressions: !, &&, || and ?: keep only the low 32 bits of a bitwise/shift result or hex/octal literal, so a non-zero value such as 1 << 32 or 0x100000000 counts as false
Area
expressions / JavascriptCompiler code generation (boolean operators on long-typed operands: bitwise and shift results, hex and octal literals)
Priority
Low, rank 872: Expression boolean operators keep only the low 32 bits of long operands, so high-bit flag tests silently read false, a specific idiom that a quick test reveals.
Impact class
silent wrong results
Impact note
Anyone using the optional expressions module (default settings, every release since 4.6.0, with -ea and -da, at any index size) who applies !, &&, || or ?: directly to a bitwise or shift result or a hex/octal literal whose value is non-zero but has all-zero low 32 bits, typically a test of flag bit 32..62 of a long doc-values field such as '(flags & 0x100000000) ? 10 : 1' or '!(flags & 0x100000000)', silently gets the false outcome for every document, so scores, sort keys or expression-based filter matches are wrong with no error; flag bits 0..31 and the comparison forms '(e) != 0' and '(e) == 0' are evaluated correctly.
Summary
You compile a Lucene expression that tests a high bit of a long field, such as '(flags & 0x100000000) ? 10 : 1' over a NumericDocValuesField with flags = 2^32 + 1, and expect 10, because 'flags & 0x100000000' evaluates to 4294967296 and '(flags & 0x100000000) != 0' is 1. Instead you get 1: the compiler asks for the operand of !, &&, || and ?: as a 32-bit int and narrows a long-typed operand (the result of & | ^ ~ << >> >>>, or a hex/octal literal) by keeping only its low 32 bits, so every non-zero value whose low 32 bits are zero counts as false. The same number is true when written as the decimal literal 4294967296, as a variable or as '((1 << 32) + 0)', but false as '0x100000000' or '(1 << 32)'.
