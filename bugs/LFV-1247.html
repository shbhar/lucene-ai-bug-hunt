The opt-in polygon self-intersection check reports lat=Infinity lon=Infinity (or throws AssertionError) for two nearly collinear edges

With checkSelfIntersections = true, an invalid polygon whose edge runs back over another edge can be rejected with "Polygon self-intersection at lat=Infinity lon=Infinity" (a bare AssertionError with -ea). A rounded test says two nearly collinear edges cross, and the crossing point is divided by a determinant of exactly 0.0.

The finding in 30 seconds

#

For each pair of ring edges, the check first asks a rounded side-of-line test whether they cross, then computes the crossing point by dividing by a determinant. For two nearly collinear edges the test can say "cross" while the determinant rounds to exactly 0.0.

Background: what the check does

#
  1. createIndexableFields(name, polygon, true) asks the Tessellator to check the polygon before cutting it into triangles. The two-argument overload, the default, does not check.
  2. The check looks at pairs of ring edges. If two edges cross, it throws "Polygon self-intersection at lat=.. lon=.." with the crossing point; if they lie on one line and overlap, "Polygon ring self-intersection".
  3. Whether two edges cross is decided by orient, which tells on which side of a line a point lies by comparing two rounded products. Its own comment says it is not exact.

The finding, step by step

#
  1. Index the ring lats {0, 7, 4, 3.85, 1.4, 2, 0}, lons {0, 1, 8, 0.55, 0.2, -7, 0} with LatLonShape.createIndexableFields("shape", polygon, true), which checks it first. The (lon, lat) points (0.55, 3.85) and (0.2, 1.4) lie on the first edge (0,0)-(1,7) (lat = 7 × lon), so the fourth edge runs back over the first: the ring is invalid.
  2. You expect IllegalArgumentException naming where the ring meets itself. A similar ring whose points are exact in binary (on lat = 8 × lon) gets "Polygon ring self-intersection at lat=2.0 lon=0.25".
  3. Instead, without assertions (production) you get "Polygon self-intersection at lat=Infinity lon=Infinity". With -ea a bare java.lang.AssertionError escapes from createIndexableFields.
  4. Why: in binary, the fourth edge sits a hair off the first edge's line. The rounded side-of-line test (orient) says the two edges cross, though exactly they do not. The crossing point needs the determinant 2.45 − 2.45 = 0.0, so the code trips assert determinant != 0 or divides by zero.
  5. The polygon is rejected either way and nothing is indexed: only the error is wrong. Every release from 9.1.0 to 10.6.0 and main.

Who is affected

#

Applications that turn on the opt-in check (checkSelfIntersections = true in LatLonShape.createIndexableFields or createDocValueField, or Tessellator.tessellate(polygon, true)) and get a polygon with an edge that runs back over another. The polygon is still rejected; only the error is wrong. Rare input, so priority Low.

Mechanism, terms and numbers691 words

LatLonShape.createIndexableFields(name, polygon, true) promises that "the validity of the provided polygon is checked", and an invalid polygon is rejected with "Polygon self-intersection at lat=.. lon=.." naming where the ring crosses itself. The check, Tessellator.checkIntersectionPoint, decides that two edges cross with GeoUtils.lineCrossesLine, built on orient, which compares two separately rounded products and is documented as not exact (GeoUtils.java:203). It then computes the crossing point from an independently rounded determinant, asserts that it is not 0 (Tessellator.java:1044) and divides by it (:1046-1047). For two nearly collinear edges, orient can report a crossing while the determinant rounds to exactly 0.0: with -ea a bare AssertionError escapes, and without assertions the message reads lat=Infinity lon=Infinity. The polygon is still rejected and nothing wrong is indexed. It came with the check (#428, LUCENE-9538), is in every release from 9.1.0 to 10.6.0 and on main, and a small zero-determinant guard (+6/-2) fixes it.

The code

if (checkSelfIntersections) {                         // :134
  checkIntersection(outerNode, mortonOptimized);      // :135, pairs of ring edges

private static void checkIntersectionPoint(final Node a, final Node b) {  // :1011
  ... // :1016-1021 skip pairs whose bounding boxes are disjoint or only touch
  if (lineCrossesLine(a.getX(), a.getY(), a.next.getX(), a.next.getY(),
                      b.getX(), b.getY(), b.next.getX(), b.next.getY())) {   // :1023-1031
    double a1 = a.next.getY() - a.getY();                // :1033
    double b1 = a.getX() - a.next.getX();                // :1034
    double c1 = a1 * (a.getX()) + b1 * (a.getY());       // :1035
    double a2 = b.next.getY() - b.getY();                // :1038
    double b2 = b.getX() - b.next.getX();                // :1039
    double c2 = a2 * (b.getX()) + b2 * (b.getY());       // :1040
    double determinant = a1 * b2 - a2 * b1;              // :1042
    assert determinant != 0;                             // :1044
    double x = (b2 * c1 - b1 * c2) / determinant;        // :1046
    double y = (a1 * c2 - a2 * c1) / determinant;        // :1047
    throw new IllegalArgumentException("Polygon self-intersection at lat=" + y + " lon=" + x); // :1049
  }
  ...
}

GeoUtils.orient (GeoUtils.java:203-215) returns the sign of (bx - ax) * (cy - ay) versus (cx - ax) * (by - ay), two separately rounded products, with the comment "Note that this one does not yet have the floating point tricks to be exact!". lineCrossesLine (:217-228) reports a crossing when both end points of each edge lie strictly on opposite sides of the other.

The worked example

#
  • The input ring is counter-clockwise, so the Tessellator walks it in reverse. The flagged pair is a = (0.2, 1.4) -> (0.55, 3.85) (the fourth edge, reversed) and b = (1, 7) -> (0, 0) (the first edge, reversed), in (lon, lat).
  • 0.55, 3.85, 0.2 and 1.4 are not exact in binary, so a sits a hair off b's line. The four rounded orientation answers are -1, +1, -1, +1, which reads as a crossing; in exact arithmetic on the same doubles all four are +1, so the pair does not cross.
  • a1 * b2 = (3.85 - 1.4) * (1 - 0) = 2.45 and a2 * b1 = (0 - 7) * (0.2 - 0.55) = 2.45 round to the same double, so determinant = 0.0. With -ea the assert fires; without it both numerators are tiny positive numbers divided by 0.0, hence lat=Infinity lon=Infinity.
  • The pair that does cross in exact arithmetic, the first edge and (0.2, 1.4) -> (-7, 2), near (0.2, 1.4), is not flagged by lineCrossesLine in the order the check visits the ring.
  • Contrast: a similar ring with binary-exact points on lat = 8 * lon (lats {0, 8, 4, 4, 2, 2, 0}, lons {0, 1, 8, 0.5, 0.25, -7, 0}) is rejected by the overlap branch (:1051-1063) with "Polygon ring self-intersection at lat=2.0 lon=0.25". With the check off the repro ring gives "Unable to Tessellate shape. Possible malformed shape detected."

The code treats a zero determinant as impossible once a crossing is reported, so the divisor is not guarded. In exact arithmetic that is true (two edges that properly cross are not parallel), but here the crossing test and the determinant are each rounded, separately.

Exposure and likelihood173 words
  • Who is hit. Applications that pass checkSelfIntersections = true to LatLonShape.createIndexableFields / createDocValueField (LatLonShape.java:94-115) or call Tessellator.tessellate(polygon, true) to reject invalid polygons. XYShape calls the same code, but there is no XY witness: this ring converted to floats (XYPolygon) is rejected with a finite location, "lat=1.3999999766840654 lon=0.19999999666915222", with assertions on and off.
  • Default vs opt-in. Opt-in: the two-argument overloads do not check.
  • Effect. The polygon is rejected either way and nothing is indexed. Without assertions the location is Infinity, so the user cannot find the bad vertex. With -ea (tests, some development setups) an AssertionError escapes instead of the IllegalArgumentException, so code that catches IllegalArgumentException to reject bad shapes does not catch it.
  • Scale. None needed: one 6-point ring.
  • Likelihood: rare (for the generators tried; no wider sampling). A targeted scan of rings with this retraced-edge layout and two-decimal points hit the Infinity message 20 times before its 20-hit cap; 20000 random rings with overlapping collinear edges in six-decimal coordinates (one seeded generator) hit it 0 times.

Why it looks unintended

#
  • The validation overload promises "the validity of the provided polygon is checked"; the check was added to give a better error for self-intersecting shapes (#10578).
  • Upstream tests pass self-crossing polygons with true and assert finite locations such as "lat=0.5 lon=0.5".
  • The code's own assert determinant != 0 says the authors held this case impossible.
The full argument230 words
  • The contract. LatLonShape.java:95-96: "If checkSelfIntersections is set to true, the validity of the provided polygon is checked with a small performance penalty." The overload runs a validity check, and upstream tests use it on self-crossing polygons (below).
  • A better error is the stated goal. The check came from #10578 (LUCENE-9538), "Tessellator should provide a better error message for self-intersecting shapes"; the introducing commit 78c8d7b7ea6a detects self-intersections "so it can provide a more meaningful error to the users". No doc promises a finite location for every invalid polygon; tests pin it for ordinary examples.
  • Tests. TestTessellator.java:143 asserts "Polygon self-intersection at lat=0.5 lon=0.5" for a self-crossing polygon passed with true; :763, :835 and :855 pin finite locations too.
  • The code. assert determinant != 0 (Tessellator.java:1044) states the authors' belief that a reported crossing has a nonzero determinant. The class javadoc's precision caveat names "subatomic values such as E-200" (:49-50); the trigger uses coordinates of order 1.
  • History. The assert and the division came with the check in #428, which had no reviews or comments; nothing in the issue, the PR or the tests discusses near-parallel edges.
  • Winding. Polygon's javadoc also asks for clockwise outer rings (Polygon.java:31) and the repro ring is counter-clockwise; the same ring in clockwise order fails the same way (AssertionError at :1044 with -ea, lat=Infinity lon=Infinity without).
The devil's-advocate check190 words

The strongest case: Polygon's javadoc says a polygon "must not be self-crossing, otherwise may result in unexpected behavior" (Polygon.java:34), a class-level precondition this ring breaks; Tessellator is @lucene.internal and "Requires valid polygons"; orient is documented as inexact; no javadoc promises a finite or exact location, or an exception type under assertions, and without assertions the shape is still rejected. Both executed reviews by another model family (OpenAI GPT-5.6) voted "not a bug" on this ground (refute lens: high; intended lens: medium), while reproducing both symptoms and agreeing on the root cause and the fix.

Why it does not settle it: the precondition stands, but the true overload is the API Lucene offers to detect such input, upstream tests feed it self-crossing polygons and assert the location, and the code's own assert treats this case as impossible. A similar ring with binary-exact points and this ring converted to floats both get a finite location, so whether the user gets one depends on how the decimals round, which no doc mentions. The contract argument weakens the case without removing it; with only the error wrong, the priority is Low.

Suggested fix

#

Recommended Guard the zero determinant and name the first edge's start vertex

When the determinant is 0, throw the usual IllegalArgumentException naming the start vertex of the first edge instead of asserting and dividing. The repro ring then gets "Polygon self-intersection at lat=1.4 lon=0.2", next to the true crossing. Validated: the repro passes in both modes; 115 related tests and :lucene:core:check -x test pass.

      double determinant = a1 * b2 - a2 * b1;
      if (determinant == 0) {
        // orient() is not exact: it can report a crossing of two nearly collinear edges whose
        // determinant rounds to 0, so report the start of the first edge instead of dividing by 0
        throw new IllegalArgumentException(
            "Polygon self-intersection at lat=" + a.getY() + " lon=" + a.getX());
      }

How it was found

#

A proof-obligation audit of the Tessellator's contract took the code's own assert determinant != 0 as an obligation: a crossing reported by lineCrossesLine has a nonzero determinant. That fails because the crossing is decided by the inexact orient while the determinant is rounded on its own. A one-test JUnit witnessed it on main.

The method in full119 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro), on main 5adff78bb168, 2026-11-03.

  • The obligation: whenever lineCrossesLine reports a crossing, a1 * b2 - a2 * b1 != 0 in doubles. Discharging it needs the crossing test and the determinant to agree, but they are rounded separately, so two nearly collinear edges break it.
  • A JUnit test witnessed it on main with assertions on and off, and an exact-arithmetic probe checked every edge pair of the witness ring. An independent reproducer wrote its own short-decimal test through LatLonShape (the repro shipped here) and ran it on several releases; two executed reviews by another model family (OpenAI GPT-5.6) and a devil's-advocate verifier wrote their own tests.

Summary
You index a polygon with LatLonShape.createIndexableFields(name, polygon, true), asking Lucene to check it for self-intersections, and the polygon is invalid because one edge runs back over part of an earlier edge (lats {0, 7, 4, 3.85, 1.4, 2, 0}, lons {0, 1, 8, 0.55, 0.2, -7, 0}). You expect the IllegalArgumentException 'Polygon self-intersection at lat=.. lon=..' naming where the ring crosses itself, as other invalid polygons get. Instead the check flags two nearly parallel edges whose determinant rounds to exactly 0.0 and divides by it: without assertions (production) the message reads 'Polygon self-intersection at lat=Infinity lon=Infinity', and with -ea the internal 'assert determinant != 0' throws a bare java.lang.AssertionError out of the indexing call.
