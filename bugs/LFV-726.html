addIndexes(CodecReader...) counts soft deletes before OneMerge#wrapForMerge removes documents, and later merges build on the wrong count

A custom merge policy's wrapForMerge that drops documents during addIndexes(CodecReader...) leaves the new segment with the pre-drop soft-delete count: 2 documents written, 1 nonexistent soft delete recorded. With assertions off, a later forceMerge(1) can then fit 3 documents into 2 doc IDs, and a search for one returns another.

The bug in 30 seconds

#

addIndexes(CodecReader...) lets your merge policy wrap each incoming reader, and the wrapper may "add/remove fields or documents". The writer must then describe the segment that was actually written: its document count and how many of its documents are soft-deleted.

  1. Your writer has a soft-deletes field, and your merge policy's findMerges(CodecReader...) returns a OneMerge whose wrapForMerge hides expired documents. The source index holds a (expired, then soft-deleted), c and a2; a reader from DirectoryReader.open still sees all 3, and its leaves go to addIndexes.
  2. You expect the new segment to hold c and a2 with no soft deletes: maxDoc 2, numDocs 2 and getPendingNumDocs 2.
  3. Instead addIndexes counted before the wrapper ran: the segment holds 2 documents but records 1 soft delete, so numDocs is 1 and getPendingNumDocs is 3. CheckIndex notices only at level 2 and up.
  4. With assertions off, later operations trust that count. Add z and run forceMerge(1): with LogDocMergePolicy the merged segment has 2 doc IDs for 3 documents, id:z returns a2's document and CheckIndex is clean; with TieredMergePolicy the merge throws CorruptIndexException.
  5. In other shapes a live document vanishes at a later commit, or that commit fails with invalid softDelCount=2 (maxDoc=1).

Who is affected

#

Only applications whose own merge policy overrides findMerges(CodecReader...) with a OneMerge whose wrapForMerge removes documents; no in-tree policy does. The damaging half also needs a soft-deletes field and a wrapper that drops incoming soft-deleted documents. Then each such call commits a wrong count, with as few as 3 documents, in 9.9.0 to 10.5.2 and main.

Mechanism, terms and numbers1,038 words

IndexWriter.addIndexes(CodecReader...) merges the incoming readers as the merge policy's findMerges(CodecReader...) says, and since 9.9.0 it calls OneMerge#wrapForMerge on each reader, which may "add/remove fields or documents". But it takes two counts from the readers before that call: the documents it reserves (getPendingNumDocs) and the soft-delete count it stores in the new segment. When the wrapper drops an incoming soft-deleted document, the committed segment claims a soft delete it does not hold. In the 3-document example the new segment holds c and a2, records 1 soft delete, reports numDocs 1 instead of 2, and the writer reserves 3 documents instead of 2. With assertions off (production) later operations build on the wrong count: a later ordinary forceMerge(1) after adding z commits a 2-document segment for 3 documents in which id:z returns a2's stored document and CheckIndex finds nothing (LogDocMergePolicy), or the merge throws CorruptIndexException (TieredMergePolicy); in other shapes a live document disappears at a later commit, once an NRT reader is opened or a delete is applied, or that commit throws invalid softDelCount. The regular merge path takes both counts after wrapping. Only a custom findMerges(CodecReader...) with a document-removing wrapForMerge triggers it; no in-tree policy removes documents on this path. Introduced by #12622 (9.9.0); affects 9.9.0 to 10.5.2 and main.

Terms

#
  • addIndexes(CodecReader...): imports readers into the index by merging them into new segments. Which readers go into which merge is decided by MergePolicy#findMerges(CodecReader...), which "can be overridden in custom merge policies"; by default it is one merge for all readers.
  • OneMerge#wrapForMerge: a hook that wraps each reader "prior to merging in order to add/remove fields or documents". IndexWriter calls it on the regular merge path and, since 9.9.0, on the addIndexes path.
  • Soft deletes: with IndexWriterConfig.setSoftDeletesField("soft"), a document is hidden by giving it a doc value in that field (for example by softUpdateDocument). Each segment stores how many of its documents are soft-deleted, and the writer derives the live count from it: numDocs = maxDoc - deletes - soft deletes. A reader from DirectoryReader.open(dir) does not apply soft deletes, so soft-deleted documents arrive at addIndexes as live.
  • getPendingNumDocs: "the number of documents in the index including documents are being added (i.e., reserved)", used to enforce IndexWriter.MAX_DOCS.

The bug

#
  1. OneMerge(CodecReader...) sizes the merge from the incoming readers: totalMaxDoc is the sum of their numDocs() (MergePolicy.java:245-256).
  2. addIndexesReaderMerge counts soft deletes on those same unwrapped readers (IndexWriter.java:3500-3515): 1 in the example (a).
  3. Only then does it wrap them, merge.wrapForMerge(mr.codecReader) (IndexWriter.java:3542-3546). The wrapper hides a, the merge writes c and a2, and the new segment is created with the old count: new SegmentCommitInfo(segInfo, 0, numSoftDeleted, ...) (:3600-3601), that is maxDoc 2 and 1 soft delete.
  4. addIndexes then reserves merge.totalMaxDoc, 3, although the merged segment already knows it holds 2 (IndexWriter.java:3341-3356).
  5. Later code trusts the stored count. The live count becomes 2 - 1 = 1 (PendingDeletes.java:243-250). A segment whose stored deletes equal its maxDoc counts as fully deleted and is dropped at commit (PendingDeletes.java:219-220, IndexWriter.java:6429-6435). A merge sizes its output from the readers' live counts and gives each reader a doc base advanced by its live count (MergeState.java:170-173, :197-208). The segment has no document with the soft-deletes field, so no document is marked deleted, but its live count is 1: c and a2 map to doc 0 and 1, and z, whose doc base is 1, also maps to 1, in a 2-document segment. This explanation is read from the code and fits the LogDocMergePolicy observation; it was not stepped through in a debugger. TieredMergePolicy merges z's segment first (executed: an infoStream run logs "merging _1(11.0.0):c1 _0(11.0.0):c2"); by the same reading that gives doc IDs 0, 1 and 2 in a 2-document segment, which fits its "invalid docCount: 3 maxDoc: 2".

The regular merge path takes both counts after wrapping: commitMerge returns the documents a merge did not write to the reservation (IndexWriter.java:4990-5000), and mergeMiddle derives the soft-delete count from the wrapped reader (:5494-5540). A regular forceMerge with a dropping wrapper keeps getPendingNumDocs equal to maxDoc. (That mergeMiddle code has its own, separate flaw, LFV-730: for a segment without hard deletes it counts every live document a wrapper hides as a dropped soft delete.)

Exposure and likelihood354 words
  • Who. Applications that import with addIndexes(CodecReader...) through their own MergePolicy whose findMerges(CodecReader...) returns a OneMerge with a document-removing wrapForMerge, for example to drop expired or tombstoned documents while importing. MergePolicy is an Expert API. OneMergeWrappingMergePolicy, the base of SoftDeletesRetentionMergePolicy, does not override findMerges(CodecReader...), so it does not wrap these merges. The misc BPReorderingMergePolicy does wrap them (it overrides findMerges(CodecReader...) and delegates wrapForMerge), but it only reorders documents; no in-tree policy removes documents on this path.
  • The soft-delete half also needs a soft-deletes field on the destination writer and a wrapper that drops incoming soft-deleted documents. Readers from DirectoryReader.open(dir) do not apply soft deletes, so such documents arrive as live, and a filter that drops them is a natural thing to write.
  • Effect. A wrong soft-delete count is committed whenever the wrapper changes how many soft-deleted documents survive and the merge writes a non-empty segment; no large size is needed (the repro has 3 documents). A wrapper that removes only documents that are not soft-deleted over-reserves without a wrong soft-delete count. DocStats.numDocs under-counts. With assertions off (production), later operations can drop a live document at a later commit (once an NRT reader is opened or a delete is applied), fail such a commit with invalid softDelCount, or make an ordinary forceMerge commit a segment in which one document's terms point at another document's stored fields; or the forceMerge throws CorruptIndexException.
  • Detection. CheckIndex checks the soft-delete count only at level 2 and up; its command-line default is level 1. After the silent forceMerge, no level reports anything.
  • The over-reservation alone is minor. It lasts for the writer session (a reopened writer recomputes it). Its demonstrated production effect is a stricter MAX_DOCS admission check, shown with a lowered test limit, not near 2^31; it also makes the experimental getPendingNumDocs() wrong and, with assertions on, trips the writer's close-time assertion. A wrapper that revives documents under-reserves instead (shown at small size only).
  • How rare. A judgement: no downstream project with such a policy was found (keyword search only), and nobody has reported it in the almost three years since 9.9.0.

Why it is a bug, not intended

#
  • wrapForMerge's javadoc allows it ("add/remove fields or documents"), wording added by the same change that made addIndexes call it.
  • The regular merge path takes its counts after wrapping, and IndexWriter asserts pendingNumDocs == totalMaxDoc on close.
  • The outcome is a corrupt or silently wrong index, and nothing documents a limitation.
The full argument229 words
  • Contract. OneMerge#wrapForMerge: "Wrap a reader prior to merging in order to add/remove fields or documents" (MergePolicy.java:301-309). #12622 replaced the older wording ("add/remove information to the merged segment") in the same commit that added the wrapForMerge call to addIndexesReaderMerge. findMerges(CodecReader...) "can be overridden in custom merge policies" (MergePolicy.java:619-623), and addIndexes(CodecReader...) says readers "are merged as specified by the MergePolicy#findMerges(CodecReader...) API" and points to overriding it (IndexWriter.java:3264-3267). OneMerge(CodecReader...) is public.
  • Invariants the code enforces. IndexWriter asserts pendingNumDocs == segmentInfos.totalMaxDoc() on close and rollback (IndexWriter.java:2592-2597). CheckIndex.checkSoftDeletes rejects a stored soft-delete count that differs from the segment (CheckIndex.java:4938-4947). TestAddIndexes.testAddIndicesWithSoftDeletes asserts that the added segments' soft-delete counts equal maxDoc minus the live documents (TestAddIndexes.java:1767-1806).
  • History. The count sites come from #633 (LUCENE-10216, 2022); while that PR was in development the same close-time assertion fired ("pendingNumDocs 7 != 5 totalMaxDoc"), and its author suspected their code was "reserving more docs than it should" and fixed it before merge. The counts were right until #12622 (9.9.0) made the merged readers differ from the counted ones; #12622's review never discusses them.
  • Consistency. The regular merge path takes both counts after wrapForMerge (IndexWriter.java:4990-5000, :5494-5540); only addIndexes takes them before. (The regular path has a separate flaw of its own for wrappers that hide live documents in segments without hard deletes, LFV-730.)
The devil's-advocate check201 words

The intended-behaviour verifier and reviews by a model from another family built the strongest case for "not a bug": the javadoc of findMerges(CodecReader...) names only concurrency control as the reason to override it; no in-tree policy and no test removes documents on this path; MergePolicy is Expert and getPendingNumDocs is @lucene.experimental; the usual way to filter is to wrap the readers before calling addIndexes, which is counted correctly; 9.4.0 to 9.8.0 ignored wrapForMerge on this path entirely, and #12622 has no CHANGES entry of its own (the BP algorithm it builds on is listed under GITHUB#12489 in 9.8.0; no entry mentions wrapForMerge on the addIndexes path); and over-reserving is conservative.

Why it fails: #12622 made removal the explicit contract at the moment the hook started running here; the API is public and documented as overridable; the writer's own assertions, CheckIndex and TestAddIndexes treat both counts as invariants; nothing documents a limitation; and the outcome is lost or merged documents, not a clean error. At most, the argument limits how common the trigger is. Verdict: a defect (every reviewer rated the intended-behaviour argument weak). Expect a maintainer to suggest filtering before addIndexes; the issue should answer that up front.

Suggested fix

#

Recommended A: reserve the merged segment's maxDoc and count soft deletes on the wrapped readers

Count what the merge wrote: reserve each merged segment's maxDoc instead of merge.totalMaxDoc, and count soft deletes on the wrapped readers (IndexWriter.java only, +9/-8). The 3 repro classes pass, 11 of 11 with assertions on and off, and so do 12 closest upstream test classes.

All options and trade-offs4 options · 634 words

One fix was applied in a scratch worktree at a9779ef3c193 and run through gradle (seed DEADBEEF) with the three repro classes (stock: 11 tests, 9 failures, assertions on and off) and 12 closest upstream test classes. The other options are sketches, not implemented. Which one, or another design, is the maintainers' call.

A: reserve the merged segment's maxDoc and count soft deletes on the wrapped readers (validated by the checks) (recommended)

#

In addIndexes(CodecReader...), reserve merge.getMergeInfo().info.maxDoc() for each merge that produced a segment, instead of merge.totalMaxDoc. In addIndexesReaderMerge, move the soft-delete count from the loop before wrapping into the wrapping loop, on the wrapped reader and its live docs. One file, +9/-8.

// addIndexes(CodecReader...): reserve each merged segment's real size
for (MergePolicy.OneMerge merge : spec.merges) {
  if (merge.getMergeInfo() != null) {
    totalDocs += merge.getMergeInfo().info.maxDoc(); // was: totalDocs += merge.totalMaxDoc
    infos.add(merge.getMergeInfo());
  }
}
// addIndexesReaderMerge: count soft deletes on the wrapped readers
for (MergeReader mr : merge.getMergeReader()) {
  CodecReader reader = merge.wrapForMerge(mr.codecReader);
  readers.add(reader);
  if (softDeletesEnabled) {
    numSoftDeleted += PendingSoftDeletes.countSoftDeletes(
        FieldExistsQuery.getDocValuesDocIdSetIterator(config.getSoftDeletesField(), reader),
        reader.getLiveDocs());
  }
}

Trade-offs

  • For an identity wrapper the wrapped reader's live docs represent the same liveness state as the old hardLiveDocs, so nothing changes for existing users; the counting work is the same.
  • The best-effort pre-flight checks still use the unwrapped counts (IndexWriter.java:3296, :3518): a removing wrapper can still be rejected near MAX_DOCS for documents it would drop, and a reviving wrapper is caught only by the final reserveDocs. Both reviews by the other model family called this a defensible, conservative trade-off.
  • merge.totalMaxDoc keeps its current values (the inputs' maxDoc sum for segment merges, the unwrapped readers' numDocs() sum for addIndexes merges); only the addIndexes reservation stops using it.
  • Not done: the full core suite, check, a CHANGES entry. The sibling LFV-730 needs its own fix in mergeMiddle.

B: reject wrappers that change the live documents on this path

#

Throw in addIndexesReaderMerge when wrapForMerge returns a reader with different live documents (comparing which documents are live, not only how many, since a wrapper can swap live documents and keep the count), and document the limitation in the wrapForMerge and findMerges(CodecReader...) javadoc.

Trade-offs

Simple and fails loudly, but it takes away a capability the javadoc grants and the regular merge path honours. Not implemented.

C: recount soft deletes from the written segment

#

After merger.merge(), count the documents of the new segment that carry the soft-deletes field (a new segment has no hard deletes).

Trade-offs

Robust to any wrapper and to reorder, but it reads the new segment's soft-deletes doc values once more per addIndexes merge, and the reservation still needs option A's change. Not implemented.

D: documentation only

#

State that removing documents in wrapForMerge is unsupported for addIndexes merges.

Trade-offs

Leaves existing users exposed to silent corruption; not recommended.

Downstream note

#

Lucene's own OneMergeWrappingMergePolicy, the base of SoftDeletesRetentionMergePolicy, does not wrap addIndexes merges, so downstream wrappers built on it do not reach this path; only a merge policy that overrides findMerges(CodecReader...) itself does.

How it was found

#

Code reading, not a formal method. While checking how merge-policy wrappers compose with IndexWriter's merge paths, the finder read addIndexesReaderMerge and saw that both counts are taken before wrapForMerge runs. A public-API JUnit and a patched IndexWriter confirmed it; the unit's randomized composition matrix never reached this path.

The method in full175 words

Method: code reading (non-formal tier), in a hunt unit that tests how merge-policy wrappers compose with IndexWriter's merge paths (a randomized composition matrix with deliberately broken wrappers to check that its oracles can fail).

  • One of those deliberately broken wrappers drops documents; on the regular merge path it exposed the sibling bug LFV-730 (mergeMiddle). Bug record

#

LFV-726, snapshot of 2026-10-29

Registry title
addIndexes(CodecReader...) takes the reserved document count and the new segment's soft-delete count from the readers before OneMerge#wrapForMerge, so a merge whose wrapper removes documents over-reserves documents and, with soft deletes, commits a wrong soft-delete count that can drop live documents or corrupt a later merge (since 9.9.0)
Area
index / IndexWriter addIndexes(CodecReader...) accounting (reserveDocs, addIndexesReaderMerge soft-delete count) x MergePolicy#findMerges(CodecReader...) / OneMerge#wrapForMerge
Priority
Medium, rank 182: This is the addIndexes(CodecReader...) twin of LFV-730 (the wrapForMerge-removes-documents plus soft-deletes miscount, released since 9.9), and it needs an even rarer custom findMerges(CodecReader...) override.
Impact class
data corruption
Impact note
Only applications whose custom (Expert) MergePolicy overrides findMerges(CodecReader...) and returns a OneMerge whose wrapForMerge removes documents are hit, on every such addIndexes(CodecReader...) call and at any size: the over-reserved pending-document count alone is minor (writer session only, it matters near MAX_DOCS), but with a soft-deletes field and a wrapper that drops incoming soft-deleted documents the committed segment records soft deletes it does not hold, which with assertions off (production) can drop live documents on a later commit, make a later commit throw 'invalid softDelCount', or make a later ordinary forceMerge either commit a segment in which one document's terms point at another document's stored fields (silent; CheckIndex clean at every level) or fail with CorruptIndexException; no in-tree merge policy removes documents on this path.
Summary
You install a merge policy whose findMerges(CodecReader...) returns a OneMerge whose wrapForMerge removes documents (its javadoc allows this: 'add/remove fields or documents'), for example to drop soft-deleted or expired documents while importing, and call IndexWriter.addIndexes(CodecReader...); you expect the writer to account for the documents the merge actually wrote, as the regular merge path does. Instead addIndexes reserves the live-document count of the unwrapped readers, so getPendingNumDocs stays too high for the rest of the writer session, and with soft deletes it stores the unwrapped readers' soft-delete count in the new segment, so DocStats.numDocs under-counts and CheckIndex (level 2 and up) reports 'actual soft deletes: 0 but expected: 1'. With assertions off, later operations then build on that wrong count: a live document can vanish from the committed index, and a later ordinary forceMerge can merge two documents into one doc ID (a search for one returns the other) or fail with CorruptIndexException.
