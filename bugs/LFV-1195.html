FileDeleter.getUnrefedFiles() throws NullPointerException with the null messenger its constructor allows

FileDeleter's javadoc says its debug messenger "Can be null", but getUnrefedFiles() calls it unchecked: with a null messenger it throws NullPointerException as soon as one file has ref count 0. Lucene's own callers always pass a messenger, so only direct users of this @lucene.internal class are hit, since 9.6.0.

The finding in 30 seconds

#

Five of FileDeleter's six debug-message calls check if (messenger != null) first. The one in getUnrefedFiles() (FileDeleter.java:165) does not, and it runs for each count-0 file just before the name is added to the result. With a null messenger the first such file throws, so the method can never return a non-empty set.

Background in two steps

#
  1. FileDeleter (in org.apache.lucene.util, public but @lucene.internal) keeps a ref count per index file: how many references (commits, the latest checkpoint, open near-real-time readers) still hold it. IndexWriter uses it through IndexFileDeleter, NRT replicas through ReplicaFileDeleter. A file with count 0 is unreferenced and may be deleted.
  2. Its constructor takes a messenger, a callback for debug messages; the javadoc says it "Can be null if the user do not want debug infos". initRefCount(name) tracks a file with count 0, and getUnrefedFiles() returns every file whose count is 0.

The finding, step by step

#
  1. Build the file ref-counter with debug messages off, as its javadoc allows: new FileDeleter(dir, null).
  2. Track one file with initRefCount("_0.si"). It now has ref count 0: nothing references it.
  3. Ask getUnrefedFiles() for the files nobody references. You expect {"_0.si"}, which is what a no-op messenger gives.
  4. Instead it throws NullPointerException: ... because "this.messenger" is null at FileDeleter.java:165, with assertions on and off. Its "removing unreferenced file" message is the only one of the class's six messenger calls without if (messenger != null).
  5. Nothing is changed or deleted. With no count-0 file the method returns normally, so it fails exactly when it has something to return.

Who is affected

#

Only code that builds FileDeleter itself with a null messenger and then calls getUnrefedFiles() while a file has count 0, for example a custom file deleter that copies IndexFileDeleter's startup scan. IndexWriter and NRT replication always pass a messenger, so default use never hits it. The failure is loud and changes nothing.

Mechanism, terms and numbers389 words

org.apache.lucene.util.FileDeleter (public, final, @lucene.internal) is the ref-counting utility behind IndexFileDeleter and the NRT ReplicaFileDeleter. Its constructor takes a BiConsumer<MsgType, String> messenger for debug messages, and the javadoc says it "Can be null if the user do not want debug infos". Five of the class's six messenger calls are wrapped in if (messenger != null); the "removing unreferenced file" message in getUnrefedFiles() is not.

So with a null messenger, getUnrefedFiles() throws NullPointerException as soon as one tracked file has ref count 0, for example right after initRefCount: exactly when its result would be non-empty. The call throws before it returns, changes no ref count and deletes nothing. Lucene's own two constructions pass non-null messengers, so indexing, commits and NRT replication never reach it; only code that builds FileDeleter itself with null is hit. The unguarded call came with the class (#12126, first released in 9.6.0), and the fix is the same one-line null check the other five calls have.

The mechanism

#
  1. The constructor stores the messenger as given (FileDeleter.java:63-66); its javadoc allows null (:60-61).
  2. The other five messenger calls are each inside if (messenger != null): incRef (:85-87), decRef (:122-124), deleteFilesIfNoRef (:183-185), deleteFileIfNoRef (:200-202) and delete(Collection) (:208-210).
  3. initRefCount (:136-139) adds an entry with count 0 when the file is not yet tracked.
  4. getUnrefedFiles (:158-170) loops over the ref counts. For each entry with rc.count == 0 (:164) it first calls messenger.accept(MsgType.FILE, "removing unreferenced file \"" + fileName + "\"") at :165, with no null check, and only then adds the name to the result (:166). Line 165 is the fix site.
  5. With a null messenger the first count-0 entry throws. The method only reads the map and builds a new set, so nothing is changed.

Lucene's own callers

#

IndexFileDeleter builds new FileDeleter(directory, this::logInfo) (IndexFileDeleter.java:135; logInfo, :593-601, does the infoStream.isEnabled("IFD") check itself), calls initRefCount for each index file it finds when the directory has a commit (:141-151) and getUnrefedFiles() at startup to find leftovers (:222). ReplicaFileDeleter passes a lambda (ReplicaFileDeleter.java:35-41) and calls getUnrefedFiles() in deleteUnknownFiles (:80). These are the only two constructions in Lucene, and no test builds a FileDeleter directly.

Exposure and likelihood151 words
  • Who: code outside Lucene that builds FileDeleter itself (the use #11885 gave for making the class public: a file deleter usable without the nrt module), passes null as the javadoc allows, and follows IndexFileDeleter's pattern: initRefCount for the files on disk, incRef for the ones a commit uses, then getUnrefedFiles() to find leftovers. That call throws on the first leftover, so the caller cannot use the method for its purpose until it passes a non-null messenger.
  • Not hit: Lucene itself: no in-tree construction passes null, so IndexWriter (through IndexFileDeleter) and NRT replication (through ReplicaFileDeleter) always have a messenger. A GitHub code search found no outside new FileDeleter( caller (an exact-text search; it cannot see private code).
  • Effect: a NullPointerException in the caller's thread, with assertions on and off; no state change, nothing deleted, no wrong result.
  • Scale: one call, deterministic; every release from 9.6.0 to 10.6.0, and main.

Why it looks unintended

#
  • The constructor javadoc: the messenger "Can be null if the user do not want debug infos" (FileDeleter.java:60-61).
  • The other five messenger calls check if (messenger != null); line 165, from the same commit, is the odd one out.
  • Before #12126 created the class, IndexFileDeleter logged this message only under infoStream.isEnabled("IFD"); #11885 asked for a public, reusable class.
The full argument236 words
  • The contract: the constructor javadoc invites null (FileDeleter.java:60-61), initRefCount documents the count-0 entry ("will create a new RefCount object with count 0", :136) and getUnrefedFiles documents returning such entries ("get files that are touched but not incref'ed", :158). The trigger is two public calls with documented-legal arguments.
  • The code agrees with the javadoc in five places: :85, :122, :183, :200 and :208 are guarded.
  • History: the class, the null-allowed javadoc, the five guards and the unguarded call all arrived in one commit, d3b6ef3c86b (#12126, by zhaih). Before it, IndexFileDeleter logged "init: removing unreferenced file" only inside if (infoStream.isEnabled("IFD")) (IndexFileDeleter.java:238-240 at d3b6ef3c86b^), so no null-messenger path existed. The refactor kept that guarded message in IndexFileDeleter (now :228-230) and added a copy without "init: " to FileDeleter.getUnrefedFiles, sent through the messenger with no null check; IndexFileDeleter's new logInfo (:593-601) does the isEnabled check for its own messenger.
  • Made public with outside reuse as the motivation: CHANGES for 9.6.0 says "Refactor part of IndexFileDeleter and ReplicaFileDeleter into a public common utility class FileDeleter" (lucene/CHANGES.txt:3664-3665); #11885 asks to "Generalize those two file deleter into one and make it a public class"; module-info.java:53 exports org.apache.lucene.util.
  • Nothing allows the NPE: no test, review comment, issue or list thread treats it as intended; the #12126 review discussed naming, final and @lucene.internal, never a null messenger.
The devil's-advocate check252 words

FileDeleter is @lucene.internal, added at a reviewer's request on #12126 (mikemccand: "Can you add @lucene.internal javadocs tag? Users should not rely on the future stability of this API?"), and the same reviewer first doubted making the classes public at all (#11885: "I'm not sure these classes should be made public? What is the use-case where this would help?"; zhaih answered with segment replication without the nrt module); no Lucene caller passes null; Lucene's usual way to switch logging off is a no-op sink, not null (InfoStream.setDefault: "It cannot be null, to disable logging use NO_OUTPUT", InfoStream.java:69-70); and a maintainer could simply change the javadoc.

Why it fails: @lucene.internal renders as "NOTE: This API is for internal purposes only and might change in incompatible ways in the next release." (RenderJavadocPlugin.java:506 in build-tools): it warns outside users off and withdraws stability, but it does not retract the class's own javadoc, which says null is fine. The class is public in an exported package, and the package javadoc says its classes are "generally not intended for direct use by most applications, but may be useful for advanced integrations or extensions" (util/package-info.java:22-23). The InfoStream convention is not this class's contract: this javadoc says null is fine, and five of six call sites implement exactly that. A javadoc-only change is a legitimate fix option, but it would contradict the five guards. What remains is an impact argument (narrow reach, loud failure, nothing changed), which is why this is Low.

Suggested fix

#

Recommended A. Guard the call like the other five (validated)

Wrap the call at FileDeleter.java:165 in if (messenger != null), like the other five messenger calls (+3/-1). The repro passes with assertions on and off, and with the fix TestIndexFileDeleter, TestCrash and TestDeletionPolicy (25 tests with the repro), the nightly TestNRTReplication (13 tests) and the core format, lint and forbidden-API checks pass.

if (rc.count == 0) {
  if (messenger != null) {
    messenger.accept(MsgType.FILE, "removing unreferenced file \"" + fileName + "\"");
  }

A. Guard the call like the other five (validated) (recommended)

#

In FileDeleter.getUnrefedFiles() (FileDeleter.java:165):

if (rc.count == 0) {
  if (messenger != null) {
    messenger.accept(MsgType.FILE, "removing unreferenced file \"" + fileName + "\"");
  }
  unrefed.add(fileName);
}

Trade-offs

  • No change for non-null messengers: IndexFileDeleter and ReplicaFileDeleter see the same messages.
  • Matches the file's existing style.
  • CHANGES: a Bug Fixes line under the next release.

What the checks validated

  • Gradle in a scratch worktree of 5adff78bb168, OpenJDK 25.0.3, seed DEADBEEF: stock, the repro fails with assertions on and off; with the fix it passes, on and off.
  • With the fix and the repro: TestIndexFileDeleter, TestCrash and TestDeletionPolicy (25 tests with the repro), the nightly TestNRTReplication (13 tests; a regression check, since the null path cannot occur there) and the core format, lint and forbidden-API checks pass.
  • Earlier: the same guard passed the repro outside gradle (assertions on and off, three seeds) and TestIndexFileDeleter (11 of 11); the cross-model reviewer confirmed it with its own two tests.

B. Turn a null messenger into a no-op in the constructor

#

this.messenger = messenger == null ? (type, msg) -> {} : messenger; and drop the five guards.

Trade-offs

One place instead of six, so a future seventh call cannot repeat the mistake; but a bigger diff, and with a null messenger every incRef and decRef would then build its message string only to drop it (the guards skip that today). By reading, not run.

C. Forbid null instead

#

Change the javadoc and add Objects.requireNonNull(messenger) to the constructor.

Trade-offs

Fails fast and matches the InfoStream convention, but it breaks callers that pass null today (the other five methods work with null), contradicts the five existing guards and needs a MIGRATE note. By reading, not run.

Downstream note

#

Downstream, only products whose own code builds FileDeleter with a null messenger see it; no document, query or index file can reach the null path, because Lucene's own constructions always pass a messenger.

How it was found

#

Semi-formal: a proof-obligation audit of FileDeleter's contract, checking every method against the constructor's promise that the messenger may be null. getUnrefedFiles() is the one method with no check that discharges that obligation, and a JUnit test on stock main witnessed the NullPointerException.

The method in full77 words
  • Obligation: every method of a FileDeleter built with a null messenger (allowed by FileDeleter.java:60-61) completes without dereferencing it.
  • Finding: five call sites discharge it with if (messenger != null); the call in getUnrefedFiles() (:165) has no such check, and initRefCount (:136-139) makes it reachable with documented calls.
  • Witness: a three-statement JUnit test on stock main, then an independent reproduction, a cross-model review, an intended-behaviour review and an adjudication (see Independent checks).
