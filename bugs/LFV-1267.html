The compressing term-vectors writer never closes its compressor

With a Deflate-based compression mode such as CompressionMode.HIGH_COMPRESSION, Lucene90CompressingTermVectorsWriter never closes the compressor it creates, so every flushed or merged segment with term vectors leaves a native zlib Deflater for the garbage collector to free. The default codec (LZ4) is unaffected; every release since 6.4.1, when Compressor became Closeable, has it.

The finding in 30 seconds

#

Term vectors are written in compressed chunks. The format asks its CompressionMode for a Compressor. With HIGH_COMPRESSION that compressor wraps a JDK Deflater, whose zlib state lives in native memory and is released at once by Deflater.end(), which only the compressor's close() calls; otherwise it waits for a garbage collection.

  1. Use a codec whose term vectors are Lucene90CompressingTermVectorsFormat with CompressionMode.HIGH_COMPRESSION. Add 1 document with 1 term-vector field and close the IndexWriter.
  2. Indexing the document opens 1 term-vectors writer, which asks the mode for 1 compressor: a Deflate compressor that owns a JDK Deflater. Only the compressor's close() frees its native zlib memory at once; otherwise it waits for a garbage collection.
  3. You expect closing the writer to close that compressor, as the stored-fields writer has done since 6.4.1: 0 compressors left open.
  4. Instead 1 is left open: the writer's close() closes only its outputs (the .tvm and .tvd files and the .tvx index writer). The Deflater's native memory waits for a garbage collection, and each further flush or merge that writes term vectors can leave another Deflater waiting for a GC.

Who is affected

#

Only applications whose codec builds Lucene90CompressingTermVectorsFormat (public, experimental) with a Deflate-based mode such as HIGH_COMPRESSION; Lucene's own test codecs do. Each flushed segment or merge with term vectors then leaves one Deflater until a GC. No wrong results. The default codec uses LZ4 (FAST), which holds nothing native, so it is unaffected.

Mechanism, terms and numbers379 words

Lucene90CompressingTermVectorsWriter creates its own Compressor from the configured CompressionMode (Lucene90CompressingTermVectorsWriter.java:247) and is its only owner. Compressor is Closeable, and the Deflate compressor behind CompressionMode.HIGH_COMPRESSION ends its native java.util.zip.Deflater (frees its zlib state at once) only in close() (CompressionMode.java:300-306). The writer's close() closes only its three outputs (:306-315), and its constructor's failure cleanup lists indexWriter twice and never the compressor (:299-302), while the stored-fields writer closes its compressor (Lucene90CompressingStoredFieldsWriter.java:168). So with a Deflate-based mode every term-vectors writer, one per flushed segment or merge that writes term vectors, leaves its Deflater for the JDK's cleaner to free at a later garbage collection. The repro showed no wrong result, corruption or error; no memory growth or out-of-memory was measured. The default codec uses CompressionMode.FAST (LZ4), whose compressor holds nothing native. LUCENE-7647 made Compressor Closeable for exactly this reason in 6.4.1 but closed it only for stored fields; every release since then, through 10.6.0 and main, is affected (older releases already left the Deflater to the GC, with no close() to call), and adding the compressor to the two close lists fixes it.

The code (main 5adff78bb168)

#
  • Created and owned. this.compressor = compressionMode.newCompressor(); (Lucene90CompressingTermVectorsWriter.java:247), a private final field (:88) used only at :426 (compressor.compress(...)).
  • Never closed. close() is IOUtils.close(metaStream, vectorsStream, indexWriter) (:306-315). The constructor's failure cleanup is closeWhileSuppressingExceptions(t, metaStream, vectorsStream, indexWriter, indexWriter) (:299-302): indexWriter twice, no compressor.
  • The resource. HIGH_COMPRESSION.newCompressor() returns new DeflateCompressor(6) (CompressionMode.java:68, :76), which holds new Deflater(level, true) (:262); its close() (:300-306) is the only caller of Deflater.end() (:303). Without it, the JDK frees the native state only through the Deflater's cleaner once the object is unreachable (JDK 25 java/util/zip/Deflater.java:962-972).
  • The sibling. Lucene90CompressingStoredFieldsWriter.close() is IOUtils.close(metaStream, fieldsStream, indexWriter, compressor) and then compressor = null (:166-175).

When it happens

#

Each in-memory segment creates its term-vectors writer when its first document with term vectors is indexed (TermVectorsConsumer.java:126 -> :106) and closes it when the segment is flushed (:87); a merge that writes term vectors opens one in try-with-resources (SegmentMerger.java:263-265). In the repro, 1 document gives 1 writer, 1 compressor opened and 0 closed.

Exposure and likelihood263 words
  • Who is hit. Code that builds the public, @lucene.experimental Lucene90CompressingTermVectorsFormat (Lucene90CompressingTermVectorsFormat.java:35-37) with a Deflate-based mode, for example a custom codec reusing CompressionMode.HIGH_COMPRESSION, as Lucene's test framework does (CompressingCodec.java:123, HighCompressionCompressingCodec.java:30). The other in-tree Deflate mode, DeflateWithPresetDictCompressionMode (@lucene.internal), also ends its Deflater only in close() (DeflateWithPresetDictCompressionMode.java:227-232), and the test framework's DeflateWithPresetCompressingCodec uses it for term vectors too (DeflateWithPresetCompressingCodec.java:29). One recorded GitHub code search for new Lucene90CompressingTermVectorsFormat found it only in copies of Lucene, no downstream use.
  • Not hit. The default Lucene90TermVectorsFormat uses CompressionMode.FAST (Lucene90TermVectorsFormat.java:170), whose LZ4 compressor's close() is a no-op (CompressionMode.java:166-169); the in-tree SortingTermVectorsConsumer uses a no-compression mode (SortingTermVectorsConsumer.java:41).
  • Scale. Deterministic: one Deflater per term-vectors writer, so one per flushed segment and one per merge that writes term vectors (earlier ones may already have been collected), plus one per writer whose constructor fails (that path was run only by the cross-model reviews' supporting tests, which inject a failure when an output is created; the normal-close repro shows the main defect on its own).
  • Effect. Native memory is held until a garbage collection instead of being released when the writer closes. Lucene's own entry for the stored-fields fix names the risk it guarded against: "This could otherwise result in out-of-memory issues" (CHANGES.txt, 6.4.1, Bug Fixes). No memory was measured here, so no out-of-memory outcome is claimed.
  • Likelihood: plausible; priority Low. It happens every time in such a codec, but it needs an opt-in codec, causes no wrong result, and the JDK frees the memory eventually.

Why it looks unintended

#
  • The writer creates the Closeable compressor and is its only user; nothing else can close it.
  • The stored-fields writer closes its compressor since LUCENE-7647 (#8698), which made it Closeable because a Deflater "may use significant native memory"; term vectors were never mentioned.
  • The format takes any CompressionMode, and Lucene's test codecs store term vectors with HIGH_COMPRESSION.
The full argument176 words
  • Ownership. The compressor is a private final field created in the constructor and used only in flush (:88, :247, :426); the caller never sees it. No javadoc states who owns it, so this is a strong inference from the code, not a documented rule.
  • Precedent. #8698 (LUCENE-7647, 94530940e4d, Adrien Grand, 2017): "we rely on garbage collection to reclaim Deflater/Inflater instances. However these classes use little JVM memory but may use significant native memory". The patch changed only the stored-fields writer, CompressionMode, Compressor, a test codec and CHANGES.txt; term vectors appear nowhere in its description, 13 comments or patch. Earlier, LUCENE-1326 (#2403, 2008) fixed Inflater.end() not always being called in the old FieldsReader.
  • Invited configuration. The format's javadoc says the compressionMode parameter "allows you to choose between compression algorithms" (Lucene90CompressingTermVectorsFormat.java:52-54).
  • A slip in the cleanup list. The constructor's cleanup names indexWriter twice; the second copy replaced indexStream in LUCENE-9147 (597141df6b6, 2020). No commit on any branch ever passed the term-vectors compressor to IOUtils.
The devil's-advocate check149 words

The strongest case: the API is experimental, the default codec is unaffected, the GC frees the Deflater eventually, and LUCENE-7647 was scoped to stored fields; its author wrote that the writer side is "a single instance that is used from a single thread and for a short amount of time".

Why it fails: these points substantially lower the likelihood and the impact (hence Low), but not the defect. The quoted sentence explains why closing on the writer side was easy ("so I just made the compressor implement Closeable"), and it holds equally for the term-vectors writer. In 2017 the stock codecs used Deflate only for stored fields (BEST_COMPRESSION; term vectors used FAST), which explains the scope; nothing in the issue exempts term vectors. Every reviewer, including two executed reviews by another model family (OpenAI GPT-5.6), rated the intended-behaviour case weak or moderate and the bug real.

Recommended Close the compressor in close() and in the constructor's cleanup

Trade-offs

The smallest change: two names, no new code and no cost on the indexing path. The compressor is created before the constructor's try, so it is always set when the cleanup runs. Downstream note

#

Downstream products are affected only if they ship a codec that stores term vectors with a Deflate-based mode; no document or query can choose the codec.

How it was found

#

A proof-obligation audit of the term-vectors writer's contract checked that every Closeable it creates and owns is released by close() and by the failed-constructor cleanup. The compressor is released by neither. A one-test JUnit witnessed it on main; independent checks reproduced it with their own tests.

The method in full108 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro), on main 5adff78bb168, 2026-11-03.

  • The obligation: every Closeable resource the writer creates and owns is released on both exits, a normal close() and a constructor that fails. The output streams and the index writer meet it; the compressor created at :247 meets neither.
  • A one-test JUnit witnessed the normal path on main with assertions on and off. An independent reproducer and two executed reviews by another model family (OpenAI GPT-5.6) wrote their own tests from the claim; the reviews also ran the constructor-failure path and a stored-fields control that does close its compressor.

Versions tested6 rows

Summary
You configure a codec whose term vectors use Lucene90CompressingTermVectorsFormat with CompressionMode.HIGH_COMPRESSION, index one document with a term-vector field and commit. You expect the term-vectors writer to close the Compressor it created when it closes, as the stored-fields writer has done since LUCENE-7647, because the Deflate compressor frees its native Deflater only in close(). Instead the writer's close() and its failed-constructor cleanup close only its output streams, so the compressor is never closed and its Deflater's native memory waits for a garbage collection.
