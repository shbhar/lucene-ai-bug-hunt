If closing the temporary reader of a doc-values update write throws, the segment's fieldInfosGen keeps pointing at a .fnm file the cleanup just deleted, so every later commit and NRT open fails until rollback()

If closing the temporary reader that writes a doc-values update to a just-merged segment throws, the cleanup deletes _2_1.fnm but the segment still points at it. The writer stays open, yet every later commit and NRT open fails on that missing file until rollback(), in every release since 7.0.0.

The finding in 30 seconds

#

writeFieldUpdates writes a doc-values update to a just-merged segment through a temporary reader. It writes the new field-infos file and points the segment's generation at it before it closes that reader. If the close throws, the cleanup deletes the file, but the generation still points at it.

How a doc-values update reaches disk, in one minute

#
  1. A doc-values update does not rewrite its segment. At the next commit or NRT open Lucene writes the new values to new files plus a new field-infos file _<segment>_<gen>.fnm, and the segment's SegmentCommitInfo records that generation (fieldInfosGen). Every reader of the segment opens the .fnm of that generation.
  2. An update that resolves while its segment is being merged is carried over to the merged segment and queued there. The merged segment has no open reader yet (unless a merged-segment warmer is set), so the write opens a temporary read-once reader of it and closes it afterwards.
  3. If the write fails, a cleanup deletes the files it created and moves only the "next write" counters forward, so that a retry writes new files. The update stays queued for that retry.

The finding, step by step

#
  1. Commit two one-document segments (id 0 and 1, numeric doc-values field n = 0 and 1), then forceMerge(1). While the merge runs, updateNumericDocValue(id:0, "n", 100) and flush(): the update is carried over to the merged segment _2, which has no open reader yet.
  2. commit() writes the update through a temporary reader of _2: it writes _2_1.fnm, sets _2's field-infos generation to 1, then closes the reader. The close throws IOException("fake close failure"), commit() throws it, and the cleanup deletes _2_1.fnm. The writer stays open, with no tragic exception.
  3. You expect a second commit(), with the fault gone, to write the still-queued update to a new file, as the cleanup's own comment says: "so that a 2nd attempt to write will write to a new file".
  4. Instead _2 still names generation 1. The retried commit() opens a new temporary reader, which looks for _2_1.fnm and fails with NoSuchFileException: _2_1.fnm; DirectoryReader.open(writer) fails the same way, on every attempt.
  5. Retries stay stuck; rollback() recovers: it returns to the intact last commit (2 segments) and drops the merge and the update.

Who is affected

#

Applications that update doc values on the default configuration, when an update resolves during a merge and closing the temporary reader's inputs throws: possible with NIOFSDirectory or a custom or remote Directory, practically never with the default MMapDirectory. The writer then cannot commit until rollback(), which discards uncommitted work. No scale needed; rare, priority Low.

Mechanism, terms and numbers642 words

A doc-values update that resolves while its segment is being merged is carried over to the merged segment (IndexWriter.java:4537). Its reader-pool entry holds no reader (no merged-segment warmer is set by default), so the next commit or NRT open writes the update through a temporary READONCE SegmentReader (ReadersAndUpdates.java:893-895). writeFieldInfosGen writes the new _N_<gen>.fnm and at once calls info.advanceFieldInfosGen() (:854-855); it runs at the end of the inner try (:944), and the temporary reader is closed only afterwards, in the finally (:945-949). If that close() throws an IOException, the catch (:950-961) deletes every file the write created, the new .fnm included, and advances only the next-write generations "so that a 2nd attempt to write will write to a new file". But fieldInfosGen already names the deleted file. The update stays queued, only an Error is tragic (IndexWriter.java:3879-3880), so the writer stays open, and every later commit and NRT open reads the missing .fnm and fails until rollback(), which discards all work since the last commit. The committed index is intact. The order dates from 2014 (LUCENE-5618/5636, 4.9.0); the failure shows from 7.0.0 (LUCENE-7868) through 10.6.0 and main. It needs an IOException from closing a read-only input, which the default MMapDirectory practically never raises: rare, priority Low. Fix: call writeFieldInfosGen after the finally (validated).

Step by step

#
  1. IndexWriter.commitMergedDeletesAndUpdates carries updates that resolved during the merge over to the merged segment and queues them with addDVUpdate (IndexWriter.java:4484, :4537).
  2. commit() reaches ReaderPool.commit (ReaderPool.java:356), which calls writeFieldUpdates. The merged segment's pool entry holds no reader, so a temporary READONCE reader is opened (ReadersAndUpdates.java:893-895).
  3. writeFieldInfosGen writes _2_1.fnm and sets fieldInfosGen to 1 (:854-855). The javadoc contract: advanceFieldInfosGen is "Called when we succeed in writing a new FieldInfos generation" (SegmentCommitInfo.java:219-224), advanceNextWriteFieldInfosGen is "Called if there was an exception while writing a new generation of FieldInfos" (:226-232).
  4. The finally closes the temporary reader (:945-949); IndexInput.close() is declared to throw IOException (IndexInput.java:59). Here it throws.
  5. The catch deletes _2_1.fnm and advances only the next-write generations (:950-961). The prune of written updates (:963-985) is skipped, so the update stays queued.
  6. prepareCommitInternal treats only an Error as tragic (IndexWriter.java:3879-3880), so the writer stays open. The next commit or NRT open repeats step 2: the new temporary reader reads field-infos generation 1 (SegmentReader.java:110), _2_1.fnm is gone, and it throws, on every attempt until rollback().

fieldInfosGen is the only generation published before the write is complete that names a file new readers open. advanceDocValuesGen() (:615) also runs inside the inner try, but readers take each field's doc-values generation from the .fnm (SegmentDocValuesProducer.java:83), not from that counter. The doc-values overlay generations are staged and published only on success (:597-599, :864-866, :1019-1025, from #16418), and the field-infos files are recorded only on success (:992).

Exposure and likelihood295 words
  • Who is hit. Applications that use doc-values updates (updateNumericDocValue was executed; by reading updateBinaryDocValue, updateDocValues and soft-delete updates share this write path) on the default IndexWriterConfig and codec (no merged-segment warmer), where an update resolves while its segment is merging and closing the temporary reader's inputs throws at the next commit or NRT open.
  • Default vs opt-in. The state is reached with the defaults (reader pooling on, IndexWriterConfig.java:90; ConcurrentMergeScheduler; no merged-segment warmer, LiveIndexWriterConfig.java:131; an independent check reproduced it with a background merge held on a latch, with no IndexWriter call inside the merge hook). With a warmer set (setMergedSegmentWarmer), the merge pools a reader for the merged segment (IndexWriter.java:5784-5795), no temporary reader is closed, and the scenario passes (executed). The fault is not default: MMapDirectory, which FSDirectory.open returns on 64-bit JVMs (FSDirectory.java:155-161), only closes its memory arena (MemorySegmentIndexInput.java:707-719), while NIOFSDirectory's input closes a FileChannel (NIOFSDirectory.java:122-126), and custom or remote Directory implementations may throw.
  • Effect. The open writer can no longer commit or open NRT readers, and there is no tragic exception to tell the application why. Retries stay stuck; rollback() recovers, back to the intact last commit, and discards every change since (in the repro the merge and the update). By reading, deleteAll() would also clear the state, at the cost of every document (not run). The committed index is intact; nothing wrong is persisted.
  • Scale. None: two documents. It fails with assertions on and off.
  • Likelihood: rare. An update resolving during a merge is ordinary in update-heavy applications, but an IOException from closing a read-only input at exactly this step is an uncommon environmental fault; the recorded searches found no public report of it since 7.0.0 (2017).

Why it looks unintended

#
  • The cleanup's own comment promises a retry ("so that a 2nd attempt to write will write to a new file") and keeps the update queued.
  • advanceFieldInfosGen is "Called when we succeed in writing a new FieldInfos generation"; here the write failed.
  • Moving only the advance after the close makes 7.0.0 pass; Lucene's own tests retry commits after one-shot faults.
The full argument272 words
  • The code promises a retry. The catch comment: "Advance only the nextWriteFieldInfosGen and nextWriteDocValuesGen, so that a 2nd attempt to write will write to a new file" (ReadersAndUpdates.java:951-952); the catch leaves the pending updates queued for that attempt. The promise is older than the faulty order: it came with LUCENE-5189 (1120e46961b, 2013-09-15, first in 4.6.0), when the generation still advanced only after reader.close(); c863a7251d5 (2014) only extended it to nextWriteDocValuesGen.
  • The generation contract. advanceFieldInfosGen is "Called when we succeed in writing a new FieldInfos generation" (SegmentCommitInfo.java:219); advanceNextWriteFieldInfosGen is for "an exception while writing" (:226-229). Here the write is treated as failed, its .fnm deleted, yet the generation was advanced.
  • The newest change to the method states the invariant. #16418 stages the overlay generations so that "a later field's failure (whose rollback deletes these gen files) never leaves info referencing them" (ReadersAndUpdates.java:597-599). fieldInfosGen breaks exactly that.
  • Upstream tests keep using the writer after a one-shot fault. TestIndexWriterDelete: "The commit above failed, so we need to retry it (which will succeed, because the failure is a one-shot)" (TestIndexWriterDelete.java:942-943). TestIndexWriterExceptions2.testBasics keeps committing and opening NRT readers after "Fake IOException"s and rethrows any other exception (TestIndexWriterExceptions2.java:211-246).
  • History: a reorder its issues do not discuss. c863a7251d5 (LUCENE-5618/5636, 2014) moved the advance before the close; neither issue (#6680, #6698) discusses close failures. The order alone decides the outcome: stock 7.0.0 fails, and 7.0.0 with only the advance moved after the close passes. (4.8.1, 4.9.0 and 4.10.4 all pass, because before 7.0.0 the write ran inside commitMerge; they do not isolate the cause.)
The devil's-advocate check248 words

The argument: no javadoc promises that commit() can be retried after an IOException; rollback() is the recovery. In open #9738 (LUCENE-8692) Simon Willnauer (s1monw) wrote that exceptions from prepareCommitInternal(), getReader() and others are not treated as tragic "since a user could always call rollback() to go back the the last known safe-point / previous commit" (2019-03-06), and that "if somebody continues after a failed commit / prepareCommit / reopen they will end up with inconsistency and / or dataloss" (2019-03-11). The trigger is unusual, and the repro uses a merge hook and test-only fault injection.

Why it fails: that is one maintainer's view in an open issue about which exceptions should be tragic; it names no mechanism. In the 2019-03-11 comment they floated closing the writer automatically after such exceptions, if rollback() were removed; their latest comment there (2019-03-12) was "I mean we can keep rollback but bet more strict about exceptions during the commit and friends?", that is, stricter handling, not an open writer that cannot commit. Here the writer itself deletes a file its own SegmentCommitInfo still names, against the method's comment and the generation javadoc, and stays open with no tragic exception while no retry can commit. The hook only makes the timing deterministic (a background-merge variant fails the same way), and IndexInput.close() is declared to throw IOException. The argument bears on priority, not on whether the state is wrong; an executed review by another model family (OpenAI GPT-5.6) rated it moderate.

A close failure then leaves fieldInfosGen unchanged and the retry writes a new generation. B: advance the generation in the success path (not run)

#

Split writeFieldInfosGen into write and advance, and call info.advanceFieldInfosGen() after the catch, next to info.setFieldInfosFiles(fieldInfosFiles) (:992) and before the pooled-reader re-open (:1028-1030), which reads the new generation. This is the pre-4.9.0 structure and publishes fieldInfosGen together with the other generations.

Trade-offs

A larger change for the same window: writeFieldInfosGen is already the last statement before the finally, so it covers no extra failure today, only future code added there.

Downstream note

#

A service that answers a failed commit by retrying it instead of calling rollback() stays stuck: every later commit and refresh of that writer fails while its uncommitted work waits.

How it was found

#

A proof-obligation audit of ReadersAndUpdates.writeFieldUpdates: at every step of its error path, a failure must leave the segment's generations naming only files that still exist, as the cleanup's comment and the advanceFieldInfosGen javadoc imply. The step after advanceFieldInfosGen and before the temporary reader's close does not; a one-test JUnit with a one-shot close fault witnessed it on main.

The method in full180 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro), on main 5adff78bb168, 2026-11-02.

  • The obligation: when writeFieldUpdates throws, SegmentCommitInfo must still name only existing files and the pending updates must stay retryable, as the catch block's comment and the generation javadoc imply. Walking the method, fieldInfosGen is the one generation that names a file new readers open and is published inside the try, before the temporary reader's close(), and the catch deletes the file it names.

LFV-1157, snapshot of 2026-11-09

Registry title
If closing the temporary reader of a doc-values update write throws, the segment's fieldInfosGen keeps pointing at a .fnm file the cleanup just deleted, so every later commit and NRT open fails until rollback()
Area
index / IndexWriter doc-values update write path (ReadersAndUpdates.writeFieldUpdates error path, temporary reader of a just-merged segment)
Priority
Low, rank 621: An IOException from closing the temporary reader of a doc-values update write makes every later commit and NRT open fail until rollback(), which discards uncommitted work, in every release since 7.0.0. The failure is loud, the committed index stays intact, and the close() fault practically never happens with the default MMapDirectory, so it is rare.
Impact class
minor
Impact note
Minor (a rare environmental close() fault, loud, committed index intact, rollback() recovers): Applications that use doc-values updates on the default IndexWriterConfig and codec are hit when an update resolves while its segment is being merged (an ordinary event: the update is carried over to the merged segment, which has no pooled reader yet) and the next commit or NRT open, writing that update through a temporary read-once SegmentReader, meets an IOException from that reader's close() (possible with NIOFSDirectory's FileChannel.close() or a custom or remote Directory, practically never with the default MMapDirectory): the writer stays open with no tragic exception, but every later commit and NRT reader open fails with NoSuchFileException or FileNotFoundException for the deleted _N_<gen>.fnm until rollback(), which discards all work since the last commit; the committed index is intact, no scale is needed, it fails with -ea and -da, and every release from 7.0.0 to 10.6.0 and main is affected.
Summary
You update a doc-values field (for example with updateNumericDocValue) of a document whose segment is being merged, so the update is carried over to the merged segment, and the next commit writes it through a temporary reader whose close() throws an IOException; the commit fails and the writer stays open. You expect a second commit, once the fault is gone, to write the update, which is what the cleanup code itself prepares for ('so that a 2nd attempt to write will write to a new file'). Instead the segment's fieldInfosGen was already advanced to the new _N_<gen>.fnm, which the cleanup then deleted, so every later commit and NRT reader open fails on that missing file until rollback(), which throws away everything since the last commit.
