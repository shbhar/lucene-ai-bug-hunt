The finding in 30 seconds

#

Documentation only: one javadoc sentence on a public constant states a cap of four merge threads that the code dropped on purpose in 10.0.0. No code is wrong, nothing runs wrong and no code change is claimed. The two numbers are configured limits that an application can set itself. In the releases 10.0.0 to 10.6.0, on branch_11x and on main.

Background: three pieces

#
  1. ConcurrentMergeScheduler is the merge scheduler of an IndexWriterConfig unless the application sets another. It runs merges on threads of its own.
  2. It has two limits. maxThreadCount: how many merge threads may run at once. maxMergeCount: how many merges may be requested before the threads that index are held back. An application can set both with setMaxMergesAndThreads.
  3. Left alone, both limits have the value AUTO_DETECT_MERGES_AND_THREADS. When a writer initializes the scheduler, the scheduler computes them from the processor count the JVM reports.

The finding, step by step

#
  1. You read the javadoc of the public constant ConcurrentMergeScheduler.AUTO_DETECT_MERGES_AND_THREADS, the automatic setting of an untouched IndexWriterConfig: "maxThreadCount is set to max(1, min(4, cpuCoreCount/2)). maxMergeCount is set to maxThreadCount + 5."
  2. You open an IndexWriter with an untouched IndexWriterConfig where the scheduler sees a core count of 10, and by the sentence you expect the limits 4 and 9. The test sets the core count with the scheduler's own system property.
  3. getMaxThreadCount() returns 5; a program that reads both getters also prints 10 for getMaxMergeCount(). The one test, which compares the thread limit with the javadoc's number, fails with expected:<4> but was:<5> on main 3cee9ed259e9, on branch_11x 8e4ee3d41386 (commits of 2026-11-23) and on each of the thirteen releases 10.0.0 to 10.6.0, with assertions on and off. On 9.12.3 it passes.
  4. The 5 is intended. #13294 dropped the cap of four in 10.0.0 on purpose: the code line is maxThreadCount = Math.max(1, coreCount / 2);, and the 10.0.0 change list states the new default. The stale side is the javadoc sentence.
  5. The two formulas agree up to a core count of 9 and differ from 10 on. Run: 4 and 9 at 9, 5 and 10 at 10, 8 and 13 at 16, 16 and 21 at 32, 32 and 37 at 64. These are configured limits that an application can set itself; no run counted started threads, and this page makes no statement about performance.

Who is affected

#

A reader who takes the default merge limits from the javadoc of the constant, on a JVM that reports ten or more processors, with the scheduler left at its automatic limits. Nothing runs wrong, an application can set both limits itself, and the 10.0.0 change list states the new default. Low: documentation only, and the repair is one javadoc line.

Mechanism, terms and numbers913 words

The limits first. This is a documentation defect. ONE javadoc sentence, on the public constant ConcurrentMergeScheduler.AUTO_DETECT_MERGES_AND_THREADS, gives the default maxThreadCount as max(1, min(4, cpuCoreCount/2)). The code has set max(1, cpuCoreCount/2) since 10.0.0 (#13294), on purpose, and the 10.0.0 change list states the new default. No code is wrong, and no code change is claimed. Nothing runs wrong: no result, exception or stored data is wrong. The two numbers are configured limits that an application can set itself with setMaxMergesAndThreads; no run counted started threads, and this page makes no performance statement. The two formulas agree up to 9 reported processors and differ from 10 on: 5 and 10 at ten processors where the sentence gives 4 and 9, and 32 and 37 at 64. The sentence is in the thirteen releases 10.0.0 to 10.6.0, on branch_11x and on main. 9.12.3, whose code has the cap, passes the test: the sentence was true before the change. The repair is the javadoc line.

You read the javadoc of the constant, which says that maxThreadCount "is set to max(1, min(4, cpuCoreCount/2))" and maxMergeCount to maxThreadCount + 5, and you expect at most 4 and 9. With an untouched IndexWriterConfig on a JVM that reports 10 processors the scheduler's getters return 5 and 10 once a writer has been opened with it, and on one that reports 64 they return 32 and 37; on one that reports 9 they return the documented 4 and 9 (run on the 10.6.0 release jars, on branch_11x 8e4ee3d41386 and on main 3cee9ed259e9, commits of 2026-11-23). The test asserts the documented formula, and that is what its failure shows: java.lang.AssertionError: expected:<4> but was:<5>.

The 10.6.0 release fails the same test as the builds of branch_11x and main, and so does each release from 10.0.0 on.

The sentence

#

The javadoc of the public constant, ConcurrentMergeScheduler.java:61-65 at main 3cee9ed259e9 (a commit of 2026-11-23; the file is the same git blob at branch_11x 8e4ee3d41386, a commit of the same day):

  /**
   * Dynamic default for {@code maxThreadCount} and {@code maxMergeCount}, based on CPU core count.
   * {@code maxThreadCount} is set to {@code max(1, min(4, cpuCoreCount/2))}. {@code maxMergeCount}
   * is set to {@code maxThreadCount + 5}.
   */
  public static final int AUTO_DETECT_MERGES_AND_THREADS = -1;

The stale part is on :63. A search of the tree at 3cee9ed259e9 for the formula finds this line and the code line below and no other place; the class javadoc (:43-58) and the setter's javadoc (:122-131) state no number.

Both fields start as the constant (:84, :88), and the two getters return the fields (:252-254, :257-259): before a writer is opened they return -1 and -1 (run). A writer initializes its scheduler (IndexWriter.java:960); initialize calls initDynamicDefaults (:532-535), which calls setDefaultMaxMergesAndThreads(false) while the thread limit is still the constant (:442-444). The scheduler of an IndexWriterConfig is a ConcurrentMergeScheduler unless the application sets another (LiveIndexWriterConfig.java:137).

Where the two formulas part

#

Integer division: up to a core count of 9, c/2 is at most 4 and the cap changes nothing. From 10 on c/2 is 5 or more, and the cap would hold it at 4. An SMT model of the two formulas (Z3, 32-bit integers) gives 10 as the smallest core count at which they differ.

Why it looks unintended

#
  • The code is intended: #13294 dropped the cap on purpose, and the 10.0.0 change list states the new default.
  • The commit changed the code line and the change list. The sentence, in the same file, kept the cap.
  • The one earlier change of the cap, in 2015, changed the sentence, the code line and the test's bound in one commit.
The full argument445 words
  • The code is intended, and this page claims nothing against it. #13294, "Increase the default number of merge threads." (commit e19238a7bde, 2024-04-11, milestone 10.0.0), changed two files: the code line in ConcurrentMergeScheduler.java, under a new comment, and CHANGES.txt.
  • The sentence was left as it was. It states the old formula as what the scheduler does ("is set to"), on a public constant that carries no experimental or internal mark.
  • Two of Lucene's documents differ from a core count of 10 on. The 10.0.0 change list states up to half the threads of the host; the javadoc of the constant states at most four merge threads.
  • History. The sentence was written in 2014 with a cap of three (commit 33410e30c1a, LUCENE-5951, 2014-12-19). The cap in its formula was changed once before 2024: commit 41fcc722ff0 (LUCENE-6119, 2015-01-05) moved the cap from 3 to 4 in the javadoc sentence, in the code line and in the bound of Lucene's test of the default, in one commit. The change of 2024 changed the code line and the change list.
  • The thread of the change. #13294 was read on 2026-11-23: its description, its 4 comments and its one review, an approval (it has no inline comment). None of these parts holds the word "javadoc" or the word "test".
  • Context. On #895, a proposal of 2022 to raise the cap that was closed unmerged, a Lucene committer (uschindler) wrote on 2022-05-17: "P.S.: When we really want to change this, the documentation (javadocs) needs update, too." The point is uschindler's. The comment is nearly two years older than the change (which was merged on 2024-04-11), so it is context and not a report of this defect.

Lucene's own test of the default. TestConcurrentMergeScheduler.testNonSpinningDefaults (TestConcurrentMergeScheduler.java:913-920 at main 3cee9ed259e9) asserts threadCount <= 4 (:918). For a suite of Lucene's test framework the framework sets the core count that the scheduler reads to a value from 1 to 4 (SetupAndRestoreCpuCoreCount.java:29 at main 3cee9ed259e9: int numCores = TestUtil.nextInt(LuceneTestCaseParent.random(), 1, 4);, a suite-level callback, LuceneTestCaseParent.java:2538-2543; at the tag of 10.6.0 the same draw is LuceneTestCase.java:1913-1920). At those counts the bound holds with the cap and without it: at the core counts 1, 2, 3 and 4 the getters return 1 and 6, 1 and 6, 1 and 6, 2 and 7 on the 9.12.3 jars and on the builds without the cap (main, branch_11x, 10.6.0 and 10.0.0). These are facts about the test and the framework. This page names no cause for the sentence being left as it was: the thread of the change, read as said above, holds no word on the javadoc.

The devil's-advocate check128 words

The strongest case that nothing is wrong: the change is deliberate and announced in the change list; the constant only selects a dynamic default; the superclass MergeScheduler is marked @lucene.experimental (MergeScheduler.java:34); no number is promised across releases; and a caller who needs the limits can read the getters or set them.

All of that holds for the code, which this page does not question. It does not make the sentence true. The sentence gives an exact formula as what the scheduler does, the formula gives another number than the getters from a core count of 10 on, and no text that was found says the sentence was kept on purpose. The file's own history kept the sentence in step with the code once before, in 2015.

Summary
The javadoc of ConcurrentMergeScheduler.AUTO_DETECT_MERGES_AND_THREADS, the automatic setting that an untouched IndexWriterConfig uses, says that the default maxThreadCount is max(1, min(4, cpuCoreCount/2)) and maxMergeCount is maxThreadCount + 5, so a reader expects at most 4 and 9. Since 10.0.0 the code sets max(1, cpuCoreCount/2), without the cap of four (#13294; deliberate, and stated in the 10.0.0 change list): on a JVM that reports 10 processors the scheduler's getters return 5 and 10 once an IndexWriter has been opened with the config, and on one that reports 64 they return 32 and 37, while at 9 they return the documented 4 and 9 (run on the 10.6.0 release jars, branch_11x 262e019500ec and main b5a4546a5964). Nothing runs wrong and the code is the intended side: the defect is the stale javadoc sentence. Lucene's own test of the default (TestConcurrentMergeScheduler.testNonSpinningDefaults, a LuceneTestCase) asserts threadCount <= 4, and for a LuceneTestCase suite the test framework sets the core count that the scheduler reads to a value from 1 to 4, where that bound holds with and without the cap.
