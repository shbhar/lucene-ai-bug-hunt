After a writer reopen, forceMerge(1) rewrites an already merged segment: MergePolicy.isMerged reads the compound-file setting from the shared codec instance, not the writer's (main and branch_11x, unreleased)

On main and branch_11x (unreleased), compound-file settings live on each codec instance, but a segment read back from disk carries the shared Codec.forName instance (default settings unless changed). With your own codec instance and a LogMergePolicy, the first forceMerge(1) after each writer reopen rewrites an already merged segment.

The finding in 30 seconds

#

Two parts of one decision ask different codec objects: the merge asks the writer's, the "already merged?" check asks the one the segment was loaded with.

Background: compound files and codec instances

#
  1. A segment can be stored as one compound file (.cfs) or as separate files. On main, whether a merged segment is compound is decided by the codec's CompoundFormat: compound files on or off, a size threshold of 64 MB (65,536 docs for LogDocMergePolicy), and a maximum size. Each codec instance has its own copy of these settings. (A newly flushed segment follows IndexWriterConfig.getUseCompoundFile() instead, default true.)
  2. When a writer opens an index, every segment read from the commit gets the codec named there, looked up with Codec.forName: one shared instance per name (by default also Codec.getDefault(), unless Codec.setDefault installed another), with default settings unless someone changed it.
  3. Before forceMerge(1) rewrites a lone segment, MergePolicy.isMerged checks whether it already has no deletions and "matches the current compound file setting". If it does, the segment is kept.

The finding, step by step

#
  1. Give the writer its own codec, new Lucene104Codec(BEST_COMPRESSION), turn compound files off on it as MIGRATE.md shows, and use LogByteSizeMergePolicy. Add 2 documents in 2 segments (flushed as compound files: a flush follows IndexWriterConfig.getUseCompoundFile(), not the codec) and forceMerge(1): you get one non-compound segment, _2. Close the writer.
  2. Reopen the writer with the same config and call forceMerge(1) again. You expect _2 to be kept: one segment, no deletions, non-compound as configured. 10.x keeps it with the equivalent settings.
  3. Instead _2 is rewritten into _3. The reopened writer judges _2 by the shared Codec.forName("Lucene104") instance, whose default settings say a segment up to 64 MB (this one is 773 bytes) should be compound, so _2 looks unmerged.
  4. The rewrite is written with the writer's codec, so _3 is non-compound again, and the first forceMerge(1) of the next session rewrites it into _4: one needless rewrite per writer session that force-merges. Content, deletions and CheckIndex stay the same; only I/O is wasted.

Who is affected

#

Unreleased: on main and branch_11x. It takes all four: a LogMergePolicy-family policy (the default TieredMergePolicy never reaches the check), your own codec instance, non-default compound settings on it, and forceMerge after a reopen. Cost: one silent rewrite per session of segments up to 64 MB (or 65,536 docs with LogDocMergePolicy), more with raised thresholds.

Mechanism, terms and numbers691 words

Since #15295 the compound-file settings (setShouldUseCompoundFile, the doc and byte thresholds, the maximum compound segment size) are fields of each CompoundFormat instance, and Lucene104Codec holds one per codec instance. MIGRATE.md tells users to set them on iwc.getCodec().compoundFormat().

A merge decides the compound flag of its new segment with the writer's codec. MergePolicy.isMerged, which decides whether a lone segment needs a forced merge at all, asks the codec the segment carries. For a segment the writer merged in this session that is the writer's codec; for a segment read from a commit it is Codec.forName(name), the shared SPI instance, whose settings are the defaults unless someone changed that instance. So a writer with its own codec instance and non-default compound settings sees its merged segment as "not merged" after every reopen, and the next forceMerge rewrites it through LogMergePolicy.findForcedMerges. The rewrite uses the writer's codec again, so this repeats once in every writer session that force-merges. No result changes; it costs I/O. It is on main and branch_11x only, unreleased.

Why it repeats, and when it does not

#
  • The rewrite is written with the writer's codec, so the new segment has the writer's compound flag again. In the same session it carries the writer's codec and is kept, so one forceMerge call cannot loop; after the next reopen it carries the shared instance again (a reopen alone rewrites nothing; the first forceMerge(1) after it does). Executed: exactly 1 rewrite per writer session over 5 forceMerge(1) calls, in 3 sessions and 3 configurations.
  • A writer that uses the default codec (with no Codec.setDefault call) shares one object with the segments it reads, so nothing goes wrong. Neither does an own instance left at the default settings.
  • LogMergePolicy.findForcedMerges asks isMerged for a lone original segment (LogMergePolicy.java:181-203, 352, 379; also :241, 257, 289 for size-limited and multi-segment forced merges, read only). The default TieredMergePolicy first drops every segment that is not in segmentsToMerge (TieredMergePolicy.java:775-777) and then reports a lone remaining segment as already merged before it asks (:836-843), so its isMerged call is never reached. Background merges and forceMergeDeletes never ask isMerged.

Which segments are rewritten

#

With such a policy, a lone segment without deletions is rewritten when the writer codec's compound decision for its size differs from that of the shared Codec.forName instance as it currently is (the defaults unless changed):

  • setShouldUseCompoundFile(false) (the MIGRATE.md recipe): segments the defaults would make compound, up to 64 MB with byte-size policies or 65,536 docs with LogDocMergePolicy. Measured over 3 sessions: a 60,000-doc LogDocMergePolicy segment rewritten every time; a 70,000-doc one and an 80.4 MB LogByteSizeMergePolicy segment kept.
  • Raised thresholds: setCfsThresholdDocSize(100000) with a 70,000-doc compound segment, rewritten after a reopen; setCfsThresholdByteSize(1 GB) with an 80.4 MB compound segment, rewritten in all 3 sessions.
Exposure and likelihood256 words
  • Who is hit. Applications on Lucene main (11.0.0-SNAPSHOT) that use LogByteSizeMergePolicy, LogDocMergePolicy or a subclass, give the writer a codec instance other than the one Codec.forName returns (new Lucene104Codec(Mode), any per-field subclass, an instance installed with Codec.setDefault(...), or a separately constructed instance of a custom codec registered through SPI; executed only with the first and with TestUtil.getDefaultCodec(false)), set compound-file settings on it whose answer differs from the shared instance's for the segment's size, and call forceMerge after reopening the writer.
  • Default configuration is not hit: the default TieredMergePolicy never reaches its isMerged call (it drops segments outside segmentsToMerge first), and the default codec, with no Codec.setDefault call, is the same object the segments are read with.
  • Cost: one needless rewrite of an already merged segment per writer session that calls forceMerge, with the transient disk space of any forced merge. Small under the MIGRATE.md recipe (segments up to 64 MB, or 65,536 docs with LogDocMergePolicy); large segments only with raised thresholds (an 80.4 MB segment was rewritten in every session under a 1 GB threshold). The runs counted rewrites and checked content; they did not measure bytes written, I/O time, commit or fsync churn, or effects on open readers and caches.
  • Silent: nothing logs it; live documents, stored values, doc values, deletions and CheckIndex are unchanged by the rewrite.
  • Not released yet: it is on main and branch_11x (created from main on 2026-10-29); 10.6.0, earlier releases and branch_10x are not affected, so it can be fixed before 11.0.0 ships.

Why it looks unintended

#
  • isMerged calls a segment merged when it "matches the current compound file setting"; MIGRATE.md says to set that on iwc.getCodec().
  • The merge asks the writer's codec, the check the segment's: the same segment is "merged" in one session, "not merged" after a reopen.
  • A regression from #15295: before it both asked the writer's merge policy; 10.x keeps the segment.
The full argument269 words
  • Documented intent. The isMerged javadoc (since LUCENE-5038, 2013; partly stale, as the body no longer checks the "same dir" part): "Returns true if this single info is already fully merged (has no pending deletes, is in the same dir as the writer, and matches the current compound file setting" (MergePolicy.java:746-749). On main the only place to configure that setting is the codec, and MIGRATE.md's recipe is CompoundFormat cfs = iwc.getCodec().compoundFormat(); cfs.setShouldUseCompoundFile(false); (MIGRATE.md:322-324). LiveIndexWriterConfig.setUseCompoundFile points to CompoundFormat for merges.
  • One decision, two answers. The merge uses the writer's codec; isMerged uses the segment's. Executed: a second forceMerge(1) in the same session keeps the segment, and the first one after a reopen rewrites it.
  • Regression. Before #15295 all three compound-file decisions asked the writer's merge policy, so they always agreed; 10.5.2 and 9.12.3 keep the segment with the equivalent merge-policy settings (executed).
  • Upstream uses private instances itself. TestUtil.getDefaultCodec(boolean) sets compound settings on a fresh Lucene104Codec, and newIndexWriterConfig randomizes them on the config's codec; with that helper and LogDocMergePolicy the bug reproduces (segments _4, _5, _6 over 3 sessions).
  • Precedents fixed as bugs: #15616 (compound settings lost through a different CompoundFormat instance), LUCENE-5481 / #6544 (forceMerge ran an unneeded merge on a merged segment), LUCENE-9905 / #176 (a merge used the SPI default instead of configured format parameters).
  • No upstream test asserts whether forceMerge keeps an already merged single segment after a writer reopen. Tests do reopen writers with per-codec compound settings, for example TestDeletionPolicy (TestDeletionPolicy.java:333, 353, 357-359), but only to merge an index of more than one segment (:342-348).
The devil's-advocate check174 words

The strongest case for "intended": forceMerge promises only "at most n segments" and leaves the choice to the merge policy; MergePolicy and CompoundFormat are @lucene.experimental; a segment's codec is the codec that wrote it, so asking it is self-consistent; Lucene104Codec(Mode) documents its options for "newly flushed/merged segments"; the MIGRATE.md recipe works with the default codec; since LUCENE-8330 the segment's codec is the only codec isMerged can reach; and in an index whose segments use several codecs, a maintainer may prefer to judge each segment by its own codec.

Why it fails: nothing documents that the settings work only on the named instance, and setting them there changes every writer in the JVM; compression-mode and per-field codecs are necessarily separate instances; the merge itself uses the writer's codec, so asking the segment's codec does not answer "would a merge change this segment?"; the outcome flips across a reopen with an identical config; and 10.x behaves as expected. The checkers who built this case rated it moderate and weak to moderate, and both rejected it.

Suggested fix

#

Recommended Give isMerged the writer's CompoundFormat through MergeContext

Let isMerged ask the same CompoundFormat the merge uses: a default method MergeContext#getCompoundFormat() (null keeps today's fallback), implemented by IndexWriter as config.getCodec().compoundFormat() and delegated by CachingMergeContext. Validated on the runs listed, not as broad compatibility proof: the repro passes, and all 1,396 core index tests and the lint checks pass.

// MergePolicy.MergeContext
default CompoundFormat getCompoundFormat() {
  return null; // unknown: isMerged falls back to the segment's codec
}
// IndexWriter (CachingMergeContext delegates to it)
public CompoundFormat getCompoundFormat() {
  return config.getCodec().compoundFormat();
}
// MergePolicy.isMerged
CompoundFormat cf = mergeContext.getCompoundFormat();
if (cf == null) cf = info.info.getCodec().compoundFormat();
return delCount == 0
    && cf.useCompoundFile(size(info, mergeContext), this) == info.info.getUseCompoundFile();
All options and trade-offs4 options · 581 words

One option was built and validated in a scratch checkout of main 645d4fe14a20. A clean fix needs a design choice, because MergeContext exposes no codec and MergePolicy has had no writer access since LUCENE-8330; the other options come from the verifiers and the adjudication.

Give isMerged the writer's CompoundFormat through MergeContext (validated by the checks) (recommended)

#

+35/-1 in three files of lucene/core. A default method MergeContext#getCompoundFormat() returns null (unknown); IndexWriter overrides it with config.getCodec().compoundFormat(); CachingMergeContext, which wraps the writer for findForcedMerges, delegates; isMerged asks it and falls back to the segment's codec when it is null. The check then asks exactly what the merge asks, so "merged" means "a merge would not change the compound flag". Writers on the default codec (with no Codec.setDefault call), and own Lucene104Codec instances with default settings, should see no change (the executed controls). Indexes whose segments use several codecs, and custom-named codecs, were not checked and need a compatibility review.

  return null; // unknown: isMerged falls back to the segment's codec
}
// IndexWriter (CachingMergeContext delegates to it)
public CompoundFormat getCompoundFormat() {
  return config.getCodec().compoundFormat();
}
// MergePolicy.isMerged
CompoundFormat cf = mergeContext.getCompoundFormat();
if (cf == null) cf = info.info.getCodec().compoundFormat();
return delCount == 0
    && cf.useCompoundFile(size(info, mergeContext), this) == info.info.getUseCompoundFile();

Trade-offs

  • A new experimental method on the public MergeContext interface, and so a public IndexWriter#getCompoundFormat().
  • A MergeContext implemented outside Lucene keeps today's behaviour until it overrides the method; any wrapper must delegate it.

Unwrap the merge context inside isMerged (no API change)

#

If the context is the IndexWriter, or the package-private CachingMergeContext around it, ask w.getConfig().getCodec().

Trade-offs

Makes the repro pass (it was used as the root-cause check), but relies on instanceof against a package-private class and silently changes nothing for any other context. Not proposed.

Move the compound-file settings off mutable codec instances

#

For example onto IndexWriterConfig, where the merge and isMerged can both read them.

Trade-offs

Removes this bug class and the JVM-wide mutation of the default codec that the MIGRATE.md recipe causes with the default codec, but reverses part of #15295's API shortly before 11.0. Not run.

Document that the settings must be set on the Codec.forName instance

#

A javadoc and MIGRATE.md change only.

Trade-offs

A workaround, not a fix: it changes every writer in the JVM, and a writer with its own instance (a compression mode, a per-field subclass) would have to keep the same settings on its own instance and on the shared one, which is global and fragile. Not recommended.

Downstream note

#

An open Elasticsearch to-do for Lucene 11 plans to put per-index compound-file settings on the index codec's CompoundFormat, and that server uses LogByteSizeMergePolicy for time-based data, so its force-merges would likely meet this rewrite (not verified).

How it was found

#

While mapping which code answers each merge-policy hook, the hunt read the three calls of CompoundFormat.useCompoundFile. A class-file call-site scan confirmed that the two in IndexWriter ask the merged segment's codec, the writer's, while MergePolicy.isMerged asks the existing segment's. A public-API JUnit then reproduced the rewrite.

The method in full138 words

Method: semi-formal (code reading witnessed by a tool, then an executed test). A hunt unit built a census of merge-policy hooks: for each hook, which code answers it. Reading the compound-file decisions raised the hypothesis; the unit's class-file call-site scanner (written on the JDK class-file API) listed the three calls of CompoundFormat#useCompoundFile and the codec each one asks: the two IndexWriter sites (mergeMiddle, addIndexesReaderMerge) ask the merged segment's codec, and MergePolicy#isMerged asks the existing segment's SegmentInfo#getCodec.

A public-API JUnit then showed the rewrite after a reopen on stock main, with two controls (the Codec.forName instance with the same settings; an own instance with default settings) that pass, and a shadow isMerged that asks the writer's codec made it pass. Independent checkers reproduced it with their own tests; the minimal one-method test above came last.

LFV-572, snapshot of 2026-11-08

Registry title
MergePolicy.isMerged checks a segment read from disk against the codec instance it was loaded with (the shared Codec.forName instance, with default compound-file settings) instead of the writer's codec, so forceMerge(1) with a LogMergePolicy rewrites an already merged segment after every writer reopen
Area
index / merge policy compound-file check (MergePolicy.isMerged vs CompoundFormat settings)
Priority
Low, rank 1023: Unreleased: forceMerge(1) under LogMergePolicy with a custom codec instance needlessly rewrites a merged segment once per session, performance only.
Impact class
minor
Impact note
Main and branch_11x only (unreleased, since #15295): applications that use a LogMergePolicy-family policy (LogByteSizeMergePolicy, LogDocMergePolicy; the default TieredMergePolicy is not affected for an original single segment), give the writer its own codec instance (for example new Lucene104Codec(Mode) or a per-field codec subclass, anything other than the instance Codec.forName returns) and configure compound-file settings on it as MIGRATE.md shows pay one needless rewrite of an already merged segment per writer session on forceMerge(1), but only for segments whose compound-file decision under those settings differs from the default one (with setShouldUseCompoundFile(false): segments up to 64 MB, or up to 65,536 docs with LogDocMergePolicy; larger segments only with raised thresholds, executed for an 80 MB segment under a 1 GB threshold); no wrong results, no corruption, no scale needed.
Summary
You give IndexWriter its own codec instance, for example new Lucene104Codec(Mode.BEST_COMPRESSION), turn compound files off on it as MIGRATE.md says (iwc.getCodec().compoundFormat().setShouldUseCompoundFile(false)), use a LogByteSizeMergePolicy and force-merge the index to one segment. You expect a later forceMerge(1) to leave that already merged segment alone, as it does in the same writer session and as 10.x does with the equivalent merge-policy settings. Instead, after the writer is closed and reopened, MergePolicy.isMerged asks the codec instance the segment was read with (the shared Codec.forName instance, whose settings are the defaults), decides the non-compound segment should have been compound, and forceMerge(1) rewrites it (_3 becomes _4); the merge itself uses the writer's codec and writes a non-compound segment again, so the same rewrite happens in every later writer session.
