On a zero-width geo3d path the squared distance styles are not squared: path-center distance comes back as d, outside distance near the path as d^4

On a geo3d path built with width 0, computePathCenterDistance(LINEAR_SQUARED, p) returns the plain distance (0.0100 where 0.0001 is expected) and computeOutsideDistance(LINEAR_SQUARED, p) its fourth power (1e-8). A 2022 refactor left out two conversions; it ships in every release since 9.5.0, and Lucene's own queries and sorts are not affected.

The finding in 30 seconds

#

geo3d distance methods take a distance style, and the squared styles must return the square of the plain distance. On a zero-width path one method forgets to square at the end and another squares twice.

Background in 3 steps

#
  1. lucene/spatial3d (geo3d) models shapes on a sphere or ellipsoid. A GeoPath is a line through points with a width; GeoPathFactory.makeGeoPath picks a special zero-width class when the width is (almost) 0. Zero-width paths exist since 7.1.0.
  2. Distance methods take a DistanceStyle: ARC (angle), LINEAR (straight-line chord), NORMAL, and the squared variants LINEAR_SQUARED and NORMAL_SQUARED, the squares of LINEAR and NORMAL.
  3. A path's distance is combined from its pieces (segments and end points). Each style has an "aggregation form" for that: the value itself for most styles, the square root for the squared ones. The rule: convert each piece in, combine, convert back once.

The finding, step by step

#
  1. Build a path with GeoPathFactory.makeGeoPath(PlanetModel.SPHERE, 0, points) from (0, 0) to (0, 0.1). A width of 0 (anything below about 3e-12 rad) gives the zero-width path class; a width of 1e-6 gives the regular one.
  2. Take the point (lat 0.01, lon 0.05), 0.01 rad beside the middle of the path. Its LINEAR (straight-line) distance is 0.0099999583, so LINEAR_SQUARED should give 0.000099999 (9.9999e-5). The width-1e-6 path does.
  3. Instead the zero-width path returns 0.0099999583 from computePathCenterDistance(LINEAR_SQUARED, q), the unsquared value, and 9.9998e-9 from computeOutsideDistance(LINEAR_SQUARED, q), the fourth power. NORMAL_SQUARED is wrong the same way; ARC, LINEAR and NORMAL are right.
  4. Why: a squared style combines a path's pieces as square roots and must square once at the end. Since 9.5.0 the pieces return square roots, but computePathCenterDistance never squares back, and one piece of the outside distance still returns the plain square, which is then squared again.
  5. No error is raised. Asking "which path is closest?" under LINEAR_SQUARED can pick a wider path 0.0408 rad away over a zero-width path 0.0100 rad away (0.0017 vs 0.0100). Nothing in Lucene uses the squared styles.

Who is affected

#

Only code that calls GeoPath.computePathCenterDistance or computeOutsideDistance itself with LINEAR_SQUARED or NORMAL_SQUARED on a zero-width path; for it the values are wrong, silently, at every point off the path (outside distance: every such point closer than a chord of 1). Lucene's own queries and distance sorts use ARC and are unaffected. The geom API is @lucene.experimental.

Mechanism, terms and numbers847 words

GeoPathFactory.makeGeoPath turns a path whose width is below Vector.MINIMUM_ANGULAR_RESOLUTION (about 3e-12 rad, for example 0) into a GeoDegeneratePath. For the squared distance styles LINEAR_SQUARED and NORMAL_SQUARED, which combine partial results in an "aggregation form" (the square root) and must convert back once (square) for the final result, this class gets two of its distance methods wrong: computePathCenterDistance returns the plain distance d instead of d^2 at every point off the path, because it never converts back, and computeOutsideDistance returns d^4 at every point off the path closer than a chord of 1 (the planet radius), because one of its pieces returns the plain d^2 into a minimum of aggregation-form values that is then squared. For a point 0.01 rad beside a sphere path that is 0.0099999583 and 9.9998e-9 where 9.9999e-5 is expected; the same path with width 1e-6 returns 9.9999e-5.

The cause is an incomplete edit in commit 839dfb5a2dc (2022-11-24, part of the #11965 spatial3d refactor; branch_9x cherry-pick f69fb6ed99b), first released in 9.5.0: it converted the pieces, not the two places that combine them. 9.4.2 returns d^2. Affected: 9.5.0 to 10.6.0 and main; not fixed upstream. ARC, LINEAR and NORMAL are unaffected, and no Lucene query, sort or comparator uses the squared styles, so the impact is limited to code that calls these GeoPath methods itself. Fix: two lines (validated with the whole lucene/spatial3d test suite).

The mechanism (main 645d4fe14a20, files in lucene/spatial3d/src/java/org/apache/lucene/spatial3d/geom/)

#
  1. The factory picks the class from the width alone. makeGeoPath returns new GeoDegeneratePath(...) when maxCutoffAngle < Vector.MINIMUM_ANGULAR_RESOLUTION (GeoPathFactory.java:40-41), else a GeoStandardPath (:43). GeoDegeneratePath is package-private and @lucene.internal (GeoDegeneratePath.java:33-35); callers only see a GeoPath.
  2. The squared styles' aggregation form is the square root. toAggregationForm returns Math.sqrt(distance) and fromAggregationForm squares (LinearSquaredDistance.java:63-71, NormalSquaredDistance.java:63-71). The defaults are the identity (DistanceStyle.java:116-118, :146-148), so for ARC, LINEAR and NORMAL a missing conversion changes nothing.
  3. Path-center distance: converted in, never converted out. computePathCenterDistance (GeoDegeneratePath.java:160-180) takes the minimum of PathSegment.pathCenterDistance and SegmentEndpoint.pathCenterDistance, which both return toAggregationForm(...) (:739, :522), and ends with return closestDistance; (:179). For a squared style that is sqrt(d^2) = d.
  4. Outside distance: one piece left plain, then converted out. outsideDistance (:270-287) takes the minimum of SegmentEndpoint.outsideDistance (toAggregationForm(...), :534-537) and PathSegment.outsideDistance, which returns the plain value Math.min(Math.min(startDistance, endDistance), distance) (:866-874, :873), i.e. d^2, and then applies fromAggregationForm (:286). For LINEAR_SQUARED the result is min(e, d^2)^2, with d the true LINEAR distance and e the chord to the nearest path vertex. Below d = 1 (geo3d units: the sphere's radius is 1) that is always (d^2)^2 = d^4, beyond the path end too. Above 1 it is d^2 when the nearest path point is a vertex, d^4 while d^2 < e, and e^2, too large, otherwise (executed on the sphere: 1.6084 for d^2 = 1.2753 beside a 2-rad segment). NORMAL_SQUARED never exceeds 1 on the sphere, so it gets NORMAL^4 at every point off the path. computeOutsideDistance reaches it through GeoBaseMembershipShape.java:46-53 (0 for points on the path).
  5. The width > 0 sibling does these two methods right. GeoStandardPath returns fromAggregationForm(...) from both (GeoStandardPath.java:278-285, :326-333). Its computeDistance has a separate defect (LFV-271).
  6. A third plain return, masked. The pole branch of PathSegment.pathCenterDistance returns computeDistance(start, ...) without toAggregationForm (GeoDegeneratePath.java:712-714; same at GeoStandardPath.java:1592-1594). In the one pole probe run, the end points win the minimum, so the result is right once the two lines are fixed.
  7. Scope: only these two methods. On the same zero-width path, computeDistance (a point on the path) and computeNearestDistance (a point on and a point off the path) return the square with LINEAR_SQUARED and NORMAL_SQUARED (executed), and points on the path get 0 from the two affected methods, which is right. At the pole of the path's great circle (the north pole, an equatorial path), computeOutsideDistance throws a NullPointerException from Plane.linearDistance or Plane.arcDistance with ARC, LINEAR and LINEAR_SQUARED alike, on 9.4.2 too: a separate behaviour, not part of this bug.

Exposure and likelihood274 words
  • Silent, wide. With a squared style on a zero-width path, computePathCenterDistance is wrong at every point off the path, and computeOutsideDistance at every point off the path closer than a chord of 1 (with NORMAL_SQUARED on the sphere, at every point off the path) and at many farther ones. No exception, no special input; points on the path get 0, which is right.
  • Who is exposed. Code that calls computePathCenterDistance or computeOutsideDistance with LINEAR_SQUARED or NORMAL_SQUARED on a path whose width is below Vector.MINIMUM_ANGULAR_RESOLUTION (for example 0). Both choices are opt-in, on the @lucene.experimental geom API (GeoPath, GeoPathFactory, DistanceStyle, GeoOutsideDistance).
  • Lucene's own results are not affected. LINEAR_SQUARED and NORMAL_SQUARED appear nowhere in lucene/ outside DistanceStyle.java; nothing in Lucene calls computePathCenterDistance; the in-tree distance sorts, including the outside-path sort of Geo3DDocValuesField, pass DistanceStyle.ARC.
  • Mixed widths can rank wrongly. The GeoPath javadoc says the path-center distance "is meant to allow comparisons between different paths to find the one that goes closest to a point". The class follows from the width, so a zero-width path compared with a wider path under a squared style can get the order wrong: it flips when the zero-width path's unsquared d is larger than the other path's squared value (executed; with the same two paths at q = (0.001, 0.1) the order is still right). Outside distances of a zero-width path cannot be compared with those of a GeoCircle either (d^4 against d^2).
  • Likelihood: plausible. Zero-width paths are a documented, tested feature, but the squared styles have no in-tree caller and no report of the bug was found (see the prior reports).

Why it looks unintended

#
  • DistanceStyle: convert in, combine, convert back once "to yield a final result". One method never converts back; the other converts back a value never converted in.
  • The width > 0 class converts back in both methods, and 9.4.2 returned the square on zero-width paths too.
  • LUCENE-7942 added aggregation forms because squared path distances were not "true squared distances".
The full argument240 words
  • The contract is one conversion back for a final result. DistanceStyle.java:107-148: "Distances should be converted to aggregation form before aggregation is attempted, and they should be converted back from aggregation form to yield a final result." The squared styles are the "Linear distance squared" and "Normal distance squared" calculators (:36-38, :44-46).
  • Why aggregation forms exist. #8991 (LUCENE-7942, 2017, by the geo3d author): "The xxxSquaredDistance computations, for example, do not produce true squared distances but rather a distance metric that is a combination of both squared and linear." Its fix added the three conversion methods (lucene/CHANGES.txt:7864-7865).
  • The same refactor converts back once in the sibling class. GeoStandardPath returns fromAggregationForm(...) from both methods (:278-285, :326-333); c9c27c755a4 ("Make sure use of aggregation form is consistent throughout ...") put those two conversions in a day before the introducing commit. (The same commit left a double conversion behind GeoStandardPath.computeDistance, LFV-271, so "consistent" holds for these two methods only.)
  • 9.4.2 returned d^2: every piece returned the plain value, so the minimum was already the answer. The introducing commit converted the pieces but not the two places that combine them.
  • No test pins the current values. No spatial3d test uses a squared style, nothing calls computePathCenterDistance, and computeOutsideDistance is tested only on boxes, circles and polygons, never on a path. The tests the commit changed compare paths with ARC, which cannot see the bug.
The devil's-advocate check169 words

The strongest case for "intended" (the intended-behaviour check and the cross-model reviews): the geom API is @lucene.experimental and GeoDegeneratePath @lucene.internal; the path-center distance is only "meant to allow comparisons", and since sqrt is monotone, zero-width paths still rank correctly among themselves; the squared styles are second-class (they throw "Reverse mapping not implemented" from findDistancePoints and friends); and the aggregation rule speaks of sums, not minima.

Why it fails: experimental and internal allow API changes, not wrong values from the public GeoPath interface; the comparison the javadoc names is "between different paths", and a zero-width and a wider path swap order under LINEAR_SQUARED (executed); computeOutsideDistance has no comparison-only wording and returns d^4, which across the chord-1 crossover is not even one monotone function of d; the same author's design takes minima in aggregation form and converts back once (GeoStandardPath); and 9.4.2 returned the squares. Verdict: not intended, a defect (the independent reproduction; the refute-lens and intended-lens cross-model reviews; the intended-behaviour check; and the adjudication, with high confidence).

Suggested fix

#

Recommended A: convert back once, and return the segment's outside distance in aggregation form

Two lines in GeoDegeneratePath: return distanceStyle.fromAggregationForm(closestDistance) from computePathCenterDistance, and wrap PathSegment.outsideDistance's result in toAggregationForm, as the sibling GeoStandardPath and the end-point code do. The repro passes, the lucene/spatial3d tests give 182 run, 0 failures (3 skipped), and the module's lint checks pass.

-    return closestDistance;
+    return distanceStyle.fromAggregationForm(closestDistance);
@@ PathSegment.outsideDistance
-      return Math.min(Math.min(startDistance, endDistance), distance);
+      return distanceStyle.toAggregationForm(
+          Math.min(Math.min(startDistance, endDistance), distance));

Downstream note

#

Lucene's own queries and sorts use ARC and are unaffected; an application that ranks paths by computePathCenterDistance under a squared style can pick the wrong path when zero-width and wider paths are mixed.

How it was found

#

A harness recomputed geo3d path distances with an independent 50-digit reference and, on zero-width paths, flagged 2,487 LINEAR_SQUARED and 2,487 NORMAL_SQUARED path-center mismatches on the sphere and 2,554 LINEAR_SQUARED on WGS84, off by up to 1e9 times. Reading the code showed the outside distance is squared twice; a public-API test confirmed both.

The method in full124 words

Method: semi-formal (bounded-exhaustive checking of the real jar against exact semantics).

  • A translation-validation harness recomputed the documented path distances with an independent BigDecimal reference (50-digit precision), the squared styles through the aggregation-form contract. On zero-width paths it flagged computePathCenterDistance: 2,487 LINEAR_SQUARED and 2,487 NORMAL_SQUARED mismatches on the sphere and 2,554 LINEAR_SQUARED on WGS84, off by ratios up to 1e9 (d returned for d^2).
  • The harness checks outside distances in ARC only; the outside-distance half was found by reading the code while writing the aggregation-form part of the reference.
  • The finder, an AI tool, then wrote a public-API JUnit on the stock jar. Independent reproducers wrote their own tests from the claim alone; the one-test repro was cut from the finder's test on 2026-10-29.

LFV-741, snapshot of 2026-11-10

Registry title
On a zero-width geo3d path (GeoDegeneratePath), computePathCenterDistance with DistanceStyle.LINEAR_SQUARED or NORMAL_SQUARED returns the unsquared distance and computeOutsideDistance returns the fourth power, instead of the squared distance, because the 2022 path refactor converted the path components to aggregation form but not the two places that combine them (regression since 9.5.0)
Area
spatial3d / geom path distances (GeoDegeneratePath, the zero-width path; DistanceStyle aggregation forms)
Priority
Low, rank 925: The experimental squared distance styles return a wrong value only to direct callers, and it also needs a zero-width GeoDegeneratePath, so it is narrower.
Impact class
minor
Impact note
Only code that calls the experimental geom API GeoPath.computePathCenterDistance or computeOutsideDistance itself with DistanceStyle.LINEAR_SQUARED or NORMAL_SQUARED on a path whose width is below Vector.MINIMUM_ANGULAR_RESOLUTION (for example width 0, which GeoPathFactory.makeGeoPath turns into a GeoDegeneratePath) gets a wrong value, for every query point and at no special scale: d instead of d^2 from the path-centre distance, and d^4 from the outside distance for points within a chord of 1 planet radius (executed on SPHERE and WGS84); ARC, LINEAR and NORMAL are unaffected and no Lucene query, sort or comparator uses the squared styles, so nothing in-tree changes, but comparing a zero-width path with a path of width > 0 by path-centre distance, the comparison the GeoPath javadoc names, can rank them in the wrong order (executed).
Summary
You build a zero-width path with GeoPathFactory.makeGeoPath(planetModel, 0, points) and call computePathCenterDistance or computeOutsideDistance with DistanceStyle.LINEAR_SQUARED (or NORMAL_SQUARED), expecting the square of the LINEAR (or NORMAL) distance, which is what DistanceStyle's 'convert to aggregation form, aggregate, convert back' contract gives, what the same path with width 1e-6 returns and what Lucene 9.4.2 returned. Instead, for a point 0.01 rad beside the path, computePathCenterDistance returns about 0.01 (the unsquared distance) and computeOutsideDistance returns about 1e-8 (the fourth power) where about 1e-4 is expected. The cause is an incomplete edit in the 2022 path refactor: GeoDegeneratePath's components now return the square root (the aggregation form of the squared styles), but computePathCenterDistance never squares the minimum back, and PathSegment.outsideDistance still returns the plain square, which outsideDistance then squares a second time.
