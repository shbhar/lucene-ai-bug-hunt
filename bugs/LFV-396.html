A shape doc value built from a BytesRef slice relates as the bytes at the start of the array

A LatLonShape or XYShape doc value built from a BytesRef slice (bytes 76-151 of a larger array) answers relate() for the bytes at position 0: with square B stored there, square A's value says OUTSIDE for a box crossing A. Affected since 9.4.0; ordinary indexing and search are not.

The bug in 30 seconds

#

A BytesRef may point into the middle of a larger array. A shape doc value built from such a slice reads its header at the right place, then rewinds to byte 0 of the array, so relate() answers for whatever bytes start the array.

  1. Encode two squares, B (latitude and longitude 40-50) and A (0-10), 76 bytes each, and copy them back to back into one array: B in bytes 0-75, A in bytes 76-151. Build A's doc value with LatLonShape.createLatLonShapeDocValues(new BytesRef(buffer, 76, 76)).
  2. You expect A's answers: box 5-15 crosses A (CROSSES), box -20 to 20 contains it (INSIDE), box 45-55 misses it (OUTSIDE). getBoundingBox() and getCentroid() do report A's.
  3. relate() returns OUTSIDE, OUTSIDE, CROSSES: B's answers. The same with XYShape. In a MemoryIndex that holds the slice as a shape field, an INTERSECTS box query misses A and a DISJOINT one matches it.
  4. Why: the reader reads the header at byte 76, then calls ByteArrayDataInput.rewind(), which goes to position 0 of the array, not of the slice (its own comment says so). Every relate() then decodes B.
  5. Not affected: IndexWriter + IndexSearcher with newSlowDocValuesBoxQuery on Lucene's codecs, whose per-document values start at offset 0. On unreleased branches (main, branch_10x, branch_10_6; listed under 10.6.0), the new bulk BinaryDocValues#binaryValues returns slices, so there doc 1 relates as doc 0.

Who is affected

#

Code that builds shape doc values from slices: the public factories (since 9.5.0), a MemoryIndex field built from a slice (since 9.4.0), or values from the unreleased bulk binaryValues API (10.6.0). Relations are wrong in either direction, silently when a valid shape precedes the slice. Ordinary indexing and search on Lucene's codecs are not affected; experimental API. Rare.

Mechanism, terms and numbers634 words

LatLonShape.createLatLonShapeDocValues(BytesRef), XYShape.createXYShapeDocValues(BytesRef) and createDocValueField(String, BytesRef) accept any BytesRef, which Lucene defines as a slice (offset + length) of a larger array. ShapeDocValues reads the slice's header at the offset, so the bounding box and centroid are right, but its reader then calls ByteArrayDataInput.rewind(), which sets the position to 0 of the whole array; every relate() decodes from there. With square B in bytes 0-75 and square A in bytes 76-151, A's doc value answers OUTSIDE, OUTSIDE, CROSSES for boxes that cross A, contain A and touch only B, instead of CROSSES, INSIDE, OUTSIDE: B's answers; on a MemoryIndex, an INTERSECTS newSlowDocValuesBoxQuery misses A and DISJOINT matches it. With a valid shape before the slice, as here, there is no error, assertions on or off; other prefix bytes give garbage or an exception. Reached through the public factories (since 9.5.0), MemoryIndex (since 9.4.0) and, on unreleased branches (listed under 10.6.0), the bulk BinaryDocValues#binaryValues API, which returns slices; ordinary IndexWriter + IndexSearcher on Lucene's codecs reads values at offset 0 and is not affected. The classes are @lucene.experimental. The defect came with the feature (LUCENE-10654, 2022); a small fix in the inner class ShapeDocValues.Reader that rewinds to the slice's start passes the repros and the shape and MemoryIndex suites.

Terms

#
  • Shape doc values: LatLonShape and XYShape can store a shape as one binary doc value: a header (version, number of triangles, bounding box, centroid) followed by a tree of the shape's triangles. LatLonShapeDocValues / XYShapeDocValues read it back; relate(Component2D) answers whether a query shape is outside, inside or crossing it. The slow doc-values shape queries call it per document.
  • BytesRef slice: a BytesRef is bytes[offset .. offset + length), "a slice (offset + length) into an existing byte[]" (BytesRef.java:22). Several values can share one array at different offsets.
  • ByteArrayDataInput: a reader over a byte array. reset(bytes, offset, len) starts it at the offset; rewind() sets the position to 0, under the comment "NOTE: sets pos to 0, which is not right if you had called reset w/ non-zero offset!!" (ByteArrayDataInput.java:51-55).

The bug

#
  1. ShapeDocValues.Reader opens new ByteArrayDataInput(binaryValue.bytes, binaryValue.offset, binaryValue.length) (ShapeDocValues.java:581-582), so it starts at the slice.
  2. The comparator reads the header there (:685-694) and then rewinds (:695); Reader.rewind() is this.data.rewind() (:594-596), which goes to position 0 of the array.
  3. relate() reads the bounding box from that position, returns at once if the query does not cross it, otherwise walks the tree, and rewinds to 0 again in finally (:743-800). readByte() does not check the slice's end (ByteArrayDataInput.java:131-133), so nothing notices.
  4. getBoundingBox() and getCentroid() are computed once from the header (:91-92), and numberOfTerms() and getHighestDimension() return values read there too (:101-102, :139-140), so they stay correct and hide the problem; relate() is the public method that reads the bytes again.

The numbers

#

Squares B (40-50) and A (0-10) encode to 76 bytes each; B fills bytes 0-75 and A bytes 76-151. For boxes 5-15 (crosses A), -20 to 20 (contains A) and 45-55 (touches only B), A's own bytes give CROSSES, INSIDE, OUTSIDE; the slice at offset 76 gives OUTSIDE, OUTSIDE, CROSSES, B's answers, because a complete valid shape (B) starts the array. The same for XYShape. In a MemoryIndex holding the slice: INTERSECTS for box 5-15 does not match, DISJOINT matches. With bytes before the slice that are not a valid encoding (the finder's 3-byte zero prefix) the answer is garbage: OUTSIDE for a crossing box, or, for XYShape with assertions on, an AssertionError in XYEncodingUtils.decode. From the code, other invalid prefixes can also throw an ArithmeticException or ArrayIndexOutOfBoundsException (:599-605; ByteArrayDataInput.java:80-82, :131-133 do not check the limit; not executed).

Exposure and likelihood374 words
  • Who is exposed. Code that uses the experimental shape doc-values API directly with a BytesRef that does not start at index 0: application or library code that calls createLatLonShapeDocValues / createXYShapeDocValues(BytesRef) on a slice (the factories were made public in #11753 so that clients can relate shape doc values in their own collectors); applications that add a createDocValueField(String, BytesRef) field built from a slice to a MemoryIndex and query it with newSlowDocValuesBoxQuery (MemoryIndex keeps the offset, MemoryIndex.java:954); and, on unreleased branches only (main, branch_10x and branch_10_6; GITHUB#16286, listed under 10.6.0), code that passes values from the bulk BinaryDocValues#binaryValues straight to the factories: for a dense field the default codec returns every value after the first of a batch as a slice of one array (for values of varying length only in a batch of consecutive doc ids; Lucene90DocValuesProducer.java:1341-1357, :1383-1415), so each relates as the first value. Sparse fields get offset-0 copies (BinaryDocValues.java:99-108).
  • Not affected. Ordinary IndexWriter + IndexSearcher with the slow doc-values shape queries on Lucene's codecs: the writer stores the slice's bytes, and per-document binaryValue() returns a buffer at offset 0 (Lucene90DocValuesProducer.java:1331-1338, :1372-1380; the executed control, one segment with the default codec, passes; the other shipped codecs and paths were checked by reading the code only). No Lucene class creates such a slice itself: a slice reaches Lucene's shape queries only when the application supplies one (for example through MemoryIndex), and nothing in Lucene passes bulk values to the shape classes. A custom codec or LeafReader that returns slices would trigger it.
  • Opt-in. The classes are @lucene.experimental; otherwise default configuration. One value suffices for a factory call or a MemoryIndex field; the bulk path needs at least two values in one batch.
  • What you see. CROSSES or INSIDE become OUTSIDE and OUTSIDE becomes CROSSES, so a box query misses shapes it overlaps and DISJOINT matches them. No exception when a valid shape precedes the slice (other prefix bytes give garbage or an exception); nothing is written to the index.
  • How likely. Rare (registry). A downstream remark, from code reading only: one downstream search engine builds its shape doc values from per-document values at offset 0, so it is not affected today.

Why it is a bug, not intended

#
  • A BytesRef is "a slice (offset + length) into an existing byte[]"; no factory restricts the offset.
  • The same class reads its header at the offset, so the bounding box and centroid are right; only relate() goes back to byte 0.
  • ByteArrayDataInput.rewind() warns it "is not right" after a non-zero offset; Lucene's MemoryIndex and bulk API hand out slices.
The full argument219 words
  • The contract. BytesRef.java:22: "Represents byte[], as a slice (offset + length) into an existing byte[]." The factories and field constructors (LatLonShape.java:210-214, :344-352; XYShape.java:193-196, :274-282) take any BytesRef and say nothing about the offset.
  • Inconsistent with itself. The reader starts at the offset and the header is read there (ShapeDocValues.java:582, :685-694); relate() alone rewinds to 0.
  • The helper's own warning. ByteArrayDataInput.java:51-52, "sets pos to 0, which is not right if you had called reset w/ non-zero offset!!", dates from 2011, before ShapeDocValues existed.
  • Lucene produces slices. MemoryIndex.java:954 keeps the caller's offset; and those values reach the shape queries (BaseShapeDocValuesQuery.java:78); the unreleased bulk binaryValues returns slices of one batch array (Lucene90DocValuesProducer.java:1356, :1401), each "a deep copy owned by the caller" (BinaryDocValues.java:75-76) but not at offset 0.
  • Intent. The code came with the feature (#1017, 2022); none of its review comments mentions offsets. #11753 made the BytesRef factories public for "custom collectors that work with shapes", which is where values from doc-values APIs, and so slices, arrive. No test calls the BytesRef factories or uses a non-zero offset.
  • Precedent. Lucene fixed the same class of bug before: "respect bytesref offset" (1b671cfba3a, 2010) and LUCENE-8766 "Pass BytesRef offset/length when decoding from input stream" (2019).
The devil's-advocate check204 words

The strongest case for "intended": the classes and ByteArrayDataInput are @lucene.experimental; the format is opaque; the constructor javadoc speaks of "an already retrieved binary format" (LatLonShapeDocValues.java:41-42), which could mean the field's own value or a per-document binaryValue(), both at offset 0 on Lucene's codecs; and rewind() is documented to go to 0. So offset 0 might be an unwritten precondition, and callers should deep-copy first.

Why it fails: no javadoc states that precondition, and BytesRef defines the value as the slice; the class honours the offset for the header, so offset 0 is not even its own assumption; MemoryIndex and the bulk API, both Lucene's, produce slices; @lucene.experimental relaxes API stability, not the meaning of the bytes passed in; the rewind NOTE warns callers of the helper, and ShapeDocValues is the caller that ignored it; the fix leaves offset-0 behaviour unchanged (not benchmarked). The devil's advocate, a reviewer from another model family (OpenAI GPT-5.6, intended lens) and the adjudication all rated the argument weak, as did the cross-model fact check. For the bulk path alone, a maintainer could instead make binaryValues return offset-0 copies; that would not help the factory and MemoryIndex paths, which are in releases. Verdict: a defect.

Suggested fix

#

Recommended Rewind to the slice's start (validated)

In ShapeDocValues.Reader, remember the slice's start offset and make rewind() call data.setPosition(startOffset) instead of ByteArrayDataInput.rewind(). One inner class (a field, a constructor line and rewind(), +6/-1); identical for offset 0. The new tests and the bulk-API test pass, and so do 30 existing lucene/core and lucene/memory suites (247 tests, the shape doc-values suites among them), with assertions on and off.

/** start of the doc value in the backing array */
private final int startOffset;

Reader(BytesRef binaryValue) {
  this.data = new ByteArrayDataInput(binaryValue.bytes, binaryValue.offset, binaryValue.length);
  this.startOffset = binaryValue.offset;
  ...
}

protected void rewind() {
  // ByteArrayDataInput#rewind() goes to position 0, not to the start of the slice
  this.data.setPosition(startOffset);
}
All options and trade-offs4 options · 499 words

One fix was built and validated through gradle (the same change as the finder's); three alternatives were not built. Workaround for users today: BytesRef.deepCopyOf(value) before building a shape doc value from a slice.

Rewind to the slice's start (validated) (validated by the checks) (recommended)

#

Store binaryValue.offset in the Reader and have rewind() set the position back to it.

/** start of the doc value in the backing array */
private final int startOffset;

Reader(BytesRef binaryValue) {
  this.data = new ByteArrayDataInput(binaryValue.bytes, binaryValue.offset, binaryValue.length);
  this.startOffset = binaryValue.offset;
  ...
}

protected void rewind() {
  // ByteArrayDataInput#rewind() goes to position 0, not to the start of the slice
  this.data.setPosition(startOffset);
}

Trade-offs

One int per reader; setPosition is a field store like rewind(). Identical for offset 0, which is every value Lucene's on-disk codecs hand to the shape queries. Reader.clone() rebuilds from the same BytesRef (ShapeDocValues.java:589-591), and the tree walk's position arithmetic is relative (:813, :823), so nothing else depends on absolute positions. No benchmark was run.

Reset the input instead (equivalent, not built)

#

rewind() calls data.reset(bytes, offset, length) with the BytesRef's fields.

Trade-offs

Same effect as long as nobody changes the BytesRef after construction: ShapeDocValues keeps the caller's mutable BytesRef (ShapeDocValues.java:84-85), and this variant re-reads its fields on every rewind while the recommended one captures the offset once. Also restores the limit, which nothing changes today.

Copy to offset 0 in the constructor (not recommended)

#

In ShapeDocValues(BytesRef), use BytesRef.deepCopyOf(binaryValue) when the offset is not 0.

Trade-offs

Copies every sliced value (for example every bulk value after the first) and leaves the reader's absolute rewind() for the next user of Reader.

Make ByteArrayDataInput.rewind() offset-aware (out of scope)

#

Remember the reset offset and rewind to it, retiring the 2011 NOTE.

Trade-offs

Changes the meaning of a method that other code calls: the blocktreeords and idversion terms enum frames call rewind() on a ByteArrayDataInput (OrdsSegmentTermsEnumFrame.java:244, IDVersionSegmentTermsEnumFrame.java:215); the default lucene103 frame no longer does (its old calls at SegmentTermsEnumFrame.java:300-307 are inside a comment). Needs its own discussion.

Downstream note

#

Downstream code that relates shape doc values in its own collectors or aggregations is hit as soon as it passes slices, for example after moving to the bulk BinaryDocValues#binaryValues API; per-document values at offset 0 are safe.

How it was found

#

Found by reading the code while writing an independent reference decoder for a bounded-exhaustive check of the shape doc-values tree: the reader starts at the BytesRef offset but rewinds to 0. The exhaustive check itself put every value at offset 0 and found nothing; public-API JUnits then confirmed the reading.

The method in full134 words

Method: code reading during semi-formal work (the hunt's semi-formal tier).

  • The hunt unit built a bounded-exhaustive translation-validation harness for the shape doc-values format: every sequence of up to 4 elements over small grids plus random trees, each encoded with the stock jar, decoded by an independent reference decoder and related against brute force. It checked 63,276,054 trees and 499,269,156 relate() calls with 0 mismatches, assertions on and off, and killed 8 of 8 mutants of ShapeDocValues.
  • All of those values sat at offset 0, so the harness could not see this bug. The signal came from writing the reference decoder: Reader opens at binaryValue.offset, rewind() goes to 0, and ByteArrayDataInput.rewind()'s comment warns about exactly that.
  • An executed probe and then public-API JUnits (the factories, MemoryIndex, the bulk API) confirmed it.

Registry title

Area
core / document: shape doc values (ShapeDocValues reader behind LatLonShapeDocValues / XYShapeDocValues relate and the slow doc-values shape queries; MemoryIndex shape doc-values fields)
Priority
Low, rank 325: Needs a BytesRef slice passed to the experimental shape doc-values factories; values read from the index come back at offset 0.
Impact class
silent wrong results
Impact note
Only code that builds a shape doc value from a BytesRef whose offset is not 0 is hit, and then on every relate() call: an application that passes such a slice to LatLonShape.createLatLonShapeDocValues or XYShape.createXYShapeDocValues (released since 9.5.0), or adds a createDocValueField(String, BytesRef) field built from one to a MemoryIndex (since 9.4.0), or, on unreleased main only, feeds values from the new bulk BinaryDocValues#binaryValues API to those factories; ordinary indexing plus IndexSearcher with newSlowDocValuesBoxQuery on Lucene's codecs reads per-document values at offset 0 and is not affected (executed control); the classes are @lucene.experimental; one document suffices, with -ea and -da.
Summary
You build a LatLonShape or XYShape doc value from a BytesRef that points into the middle of a larger byte array (offset != 0), for example with LatLonShape.createLatLonShapeDocValues(BytesRef) or as a MemoryIndex field, and expect relate() and the doc-values shape queries to answer exactly as for the same bytes at offset 0. Instead, ShapeDocValues reads its header at the offset but then rewinds its ByteArrayDataInput to position 0 of the backing array, so relate() decodes whatever bytes sit at the start of that array: the relation is silently wrong in either direction (CROSSES or INSIDE becomes OUTSIDE, OUTSIDE becomes CROSSES), and on a MemoryIndex an overlapping shape is missed by an INTERSECTS box query and matched by a DISJOINT one. getBoundingBox() and getCentroid() stay correct, which hides the problem.
