clear() of Lucene's int/long/char object hash maps keeps every value, so closed terms and points readers keep their per-field objects

Since 9.11.0, clear() on Lucene's internal IntObjectHashMap, LongObjectHashMap and CharObjectHashMap resets the keys but keeps every value. The default codec's terms and points readers call it in close() to free their per-field objects, so an application that keeps a closed reader keeps those objects too (results are never wrong).

The finding in 30 seconds

#

Lucene's small int-, long- and char-keyed object maps forget the keys on clear() but keep the values, and two default-codec readers rely on clear() to free memory when they close.

Lucene's internal hash maps in one minute

#
  1. org.apache.lucene.internal.hppc holds Lucene's own copy of a few HPPC hash maps (@lucene.internal). An IntObjectHashMap keeps two parallel arrays: keys and values. A slot whose key is 0 is empty; key 0 itself lives in an extra slot at the end.
  2. Each segment's terms reader keeps a map from field number to that field's FieldReader, and its points reader a map from field number to that field's BKDReader. Their close() closes the files and then calls clear() on the map, so the per-field objects can be collected even if the application still holds the closed reader.

The finding, step by step

#
  1. Put one object into an IntObjectHashMap with put(1, obj), then call clear(). size() now returns 0.
  2. You expect the map to let go of obj, as java.util.HashMap.clear() does and as the HPPC code this map was forked from does ("Clear all keys and values in the container").
  3. Instead clear() resets only the keys. Slot 6 of the map's values array still points at obj, so it cannot be garbage collected. LongObjectHashMap and CharObjectHashMap have the same clear().
  4. Where it shows: the default codec's terms and points readers call clear() in close() so their per-field objects can be collected "even if app hangs onto us". Index 1 document with one indexed field and one int point, close the reader but keep a reference: its FieldReader and BKDReader survive repeated GCs (9.10.0 and the fix free them).

Who is affected

#

Default-codec users on 9.11.0 through 10.6.0 or main whose application keeps a reference to a reader after closing it. Each closed segment then keeps one FieldReader per field with terms and one BKDReader per point field. That is small per-field on-heap metadata: no wrong results, no open files, off-heap index data untouched. Applications that drop closed readers lose nothing.

Mechanism, terms and numbers550 words

Lucene's internal IntObjectHashMap, LongObjectHashMap and CharObjectHashMap (org.apache.lucene.internal.hppc, forked from HPPC in 9.11.0) implement clear() by resetting assigned, hasEmptyKey and the keys array; where HPPC fills values with null there is an empty /* */ (IntObjectHashMap.java:351-358 at 5adff78bb168). After clear() the map is empty to every method, but its values array still references every former value. The default codec's block-tree terms reader (Lucene90BlockTreeTermsReader through 10.2.x, Lucene103BlockTreeTermsReader since 10.3.0) and Lucene90PointsReader call clear() in close() precisely so that a closed reader's per-field objects can be collected "even if app hangs onto us"; since 9.11.0 these calls free nothing. An application that keeps a closed reader therefore keeps one FieldReader per field with terms and one BKDReader per point field of each closed segment, with their small on-heap metadata. Results are never wrong, no file stays open and the off-heap index data is not involved, so priority Low; Arrays.fill(values, null) in the three clear() methods fixes it.

The code (main 5adff78bb168)

#
// internal/hppc/IntObjectHashMap.java (LongObjectHashMap :351-358, CharObjectHashMap :353-360 are the same)
public Object[] values;          // :58
public void clear() {            // :351
  assigned = 0;
  hasEmptyKey = false;
  Arrays.fill(keys, 0);          // :355  keys reset
  /*  */                         // :357  values never touched; HPPC has Arrays.fill(values, null) here
}
  • remove() does null the vacated slot (shiftConflictingKeys, values[gapSlot] = null, :794); only clear() leaves values behind.
  • The key-based methods check keys first (get, :212-230; containsKey; iteration), so they return nothing stale. The old references stay reachable through the public values field, through indexGet(int) with a slot index obtained before clear() (a misuse its assertions forbid; with assertions off it returns values[index], :298-303), and so for the garbage collector.

The callers

#
  • Lucene103BlockTreeTermsReader.close() (codecs/lucene103/blocktree/Lucene103BlockTreeTermsReader.java:271-280): closes its inputs, then // Clear so refs to terms index is GCable even if // app hangs onto us: and fieldMap.clear(), an IntObjectHashMap<FieldReader> (:100). The backward-codecs Lucene90BlockTreeTermsReader.close() has the same lines (:307-309); from 9.11.0 through 10.2.x that class was in core and was the default codec's terms reader (Lucene103BlockTreeTermsReader came in 10.3.0, #14333).
  • Lucene90PointsReader.close() (codecs/lucene90/Lucene90PointsReader.java:153-157): closes its inputs, then // Free up heap: and readers.clear(), an IntObjectHashMap<PointValues> (:39).
  • A closed SegmentReader still references its SegmentCoreReaders (index/SegmentReader.java:63), which keeps fields and pointsReader (index/SegmentCoreReaders.java:55, :60). So holding a closed DirectoryReader holds these codec readers and, through values, every FieldReader and BKDReader. The codec readers close (and call clear()) when the last reader sharing the segment's core closes (SegmentCoreReaders.decRef(), index/SegmentCoreReaders.java:166-179).

The numbers

#

The repro puts one value under key 1 into a default-size map; after clear() size() is 0 and values[6] still holds the object. The closed-reader probes index 1 document with an indexed field body (a TextField or a StringField) and an IntPoint p (default codec), read terms("body") and getPointValues("p"), close the reader and keep a reference to it (or only to its postings and points readers): after 10 to 20 System.gc() rounds the FieldReader and BKDReader are still reachable on main, 10.6.0 and 9.11.0, and collected on 9.10.0 and with the fix. The probes depend on the garbage collector, so they are supporting evidence; the deterministic map test is the repro.

Exposure and likelihood186 words
  • Who is hit. Applications that keep a reference to a reader after closing it, for example a stale entry in an application-level cache. Default codec, no setting needed, public API only. Applications that drop closed readers lose nothing: the whole reader is collected anyway.
  • Scale. Per closed segment, one FieldReader per field with terms and one BKDReader per point field stay reachable, with their small on-heap metadata (field info, min/max terms or packed values, counters, closed IndexInputs). The terms index and BKD index data are read off-heap and their files are closed. The amount is bounded by the field count of segments already closed and does not grow with queries or documents. It was not measured in bytes.
  • What was promised. close() clears the maps exactly for the "app hangs onto us" case; that protection has been gone since 9.11.0 (2024) without any error.
  • Other callers keep their former values too, with little effect: FieldInfos.FieldNumbers.clear() (index/FieldInfos.java:695, reached from IndexWriter.deleteAll) keeps field-name strings until the slots are reused, and the automaton helper PointTransitionSet.reset() (util/automaton/Operations.java:605-607) holds pooled objects the set keeps anyway.

Why it looks unintended

#
  • The callers rely on it: the terms reader clears "so refs to terms index is GCable even if app hangs onto us", the points reader to "Free up heap".
  • HPPC, the fork's source, nulls values in clear(); Lucene's copy keeps one /* */ and no fill.
  • Its own remove() nulls freed slots (non-zero keys); 9.10.0 freed both objects.
The full argument290 words
  • The callers' comments. "Clear so refs to terms index is GCable even if app hangs onto us" dates from LUCENE-3030 (2011) and "Free up heap" from LUCENE-6861 (2015); both only make sense if clear() drops values.
  • The fork source. The class javadoc says "Mostly forked and trimmed from com.carrotsearch.hppc.IntObjectHashMap ... release 0.10.0"; when the class was added (#13327) it named release 0.9.0, and #13422 changed it to 0.10.0. HPPC 0.10.0's IntObjectMap.clear() javadoc reads "Clear all keys and values in the container.", its generated IntObjectHashMap.clear() ends with Arrays.fill(values, null);, and its template wraps that line in /* #if ($TemplateOptions.VTypeGeneric) */ ... /* #end */. HPPC 0.9.0's generated IntObjectHashMap.clear() ends with /* */, Arrays.fill(values, null);, /* */. Lucene's copy keeps one /* */ and lacks the fill.
  • The class itself. Removing a non-zero key nulls the vacated slot (shiftConflictingKeys, IntObjectHashMap.java:794). (Removing key 0 stores a boxed 0 instead, :192, a separate quirk.)
  • The tests show the same residue. TestIntObjectHashMap.testClear (:365) says "// Check values are cleared." but checks only put/remove return values. TestCharObjectHashMap keeps HPPC's @After checkEmptySlotsUninitialized() with the value assertions expanded away to empty blocks (:85-100); HPPC's test template asserts there that every empty values slot is null.
  • History. In 9.10.0 both readers used java.util maps (Map<String, FieldReader>, Map<Integer, PointValues>), whose clear() drops values; the 9.10.0 probe collects both objects. How the fill line went missing is not recorded: the clear() body matches Lucene's (and HPPC 0.9.0's) primitive-valued IntIntHashMap, where the single empty comment is correct, and fits just as well HPPC 0.9.0's object-valued body with the fill line removed. Both are inferences, stated nowhere. No review comment on #13327 discusses it.
The devil's-advocate check122 words

The strongest case for "intended": the classes are @lucene.internal, clear() has no javadoc, release() exists for freeing memory, IndexReader.close() promises only to close files ("Closes files associated with this index", index/IndexReader.java:345), most other codec readers do not clear their maps in close() at all, and what stays reachable is small.

Why it fails: all of that bears on severity, not intent. The two close() methods still say they clear for the garbage collector, the method was forked from code that clears values, the class's own remove() clears values, and 9.10.0 released the objects. An independent reviewer from another model family (OpenAI GPT-5.6, refute lens) and an intended-behaviour devil's-advocate verifier both built this case and both concluded the bug is real.

Suggested fix

#

Recommended A: fill the values in clear()

In clear() of IntObjectHashMap, LongObjectHashMap and CharObjectHashMap, replace the empty /* */ with Arrays.fill(values, null);, as HPPC does. Validated: the repro passes with assertions on and off, 516 tests of the hppc and caller suites pass, and :lucene:core:check -x test passes.

public void clear() {
  assigned = 0;
  hasEmptyKey = false;

  Arrays.fill(keys, 0);

  Arrays.fill(values, null);
}
All options and trade-offs2 options · 297 words

One fix was validated with gradle in a scratch worktree of 5adff78bb168; the alternative is noted with its trade-offs. Open PR #16201 would change the block-tree close() to release() for an unrelated heap-size reason.

A: fill the values in clear() (validated by the checks) (recommended)

#

Replace the empty /* */ in clear() with Arrays.fill(values, null); in IntObjectHashMap.java:357, LongObjectHashMap.java:357 and CharObjectHashMap.java:359, exactly HPPC's code. Every caller of clear() then drops the old values; no API change.

public void clear() {
  assigned = 0;
  hasEmptyKey = false;

  Arrays.fill(keys, 0);

  Arrays.fill(values, null);
}

Trade-offs

One more Arrays.fill over an array the same size as the keys array clear() already fills. Nothing changes for callers that never call clear().

What the checks validated

  • The repro passes with assertions on and off.
  • --tests 'org.apache.lucene.internal.hppc.*' plus TestLucene90PointsFormat, TestLucene104PostingsFormat, TestFieldInfos and TestOperations: 516 tests, 4 skipped, 0 failures. The three object-map suites in that selection are 28 tests each, 84 in all (the fact check's re-run of the same selection; also a standalone JUnit run).
  • :lucene:core:check -x test passes (google-java-format, ecj lint, forbidden APIs) on the fix and the new test.
  • The closed-reader probes collect the FieldReader and BKDReader with this fix.

B: call release() in the readers' close() (not run)

#

release() drops both arrays (IntObjectHashMap.java:360-367), so calling it instead of clear() in Lucene103BlockTreeTermsReader.close(), the backward-codecs Lucene90BlockTreeTermsReader.close() and Lucene90PointsReader.close() would free the per-field objects.

Trade-offs

It allocates fresh default buffers on every close (ensureCapacity(DEFAULT_EXPECTED_ELEMENTS)), leaves clear() keeping values for every other caller, and overlaps #16201, which does this for the block-tree readers only. A maintainer may prefer it in the readers (it is the direction #16201 takes); on its own it does not fix clear().

What the checks validated

Not run.

Downstream note

#

For downstream services: a service that keeps closed readers referenced (for example in a cache keyed by reader) retains each closed segment's per-field terms and points objects until it drops the reader.

How it was found

#

A proof-obligation audit of IntObjectHashMap's contract took "after clear() the map holds no reference to any former value", which its HPPC source and the readers' close() comments require, as an obligation. clear() does not meet it. A one-test JUnit witnessed it on main; independent checks reproduced it with their own tests and probes.

The method in full127 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro), on main 5adff78bb168, 2026-11-03.

  • The obligation: after clear(), no slot of values references a former value, as HPPC's clear() ("Clear all keys and values in the container"), the class's own remove() and the two codec readers' close() comments require. clear() (IntObjectHashMap.java:351-358) fills only keys.
  • A one-test JUnit witnessed it on main with assertions on and off, and a public-API probe showed the reader-level effect. An independent reproducer (its own tests for all three maps and its own probe), an executed review by another model family (OpenAI GPT-5.6, refute lens) and an intended-behaviour devil's-advocate verifier each ran their own checks; an adjudication re-ran the test with a fresh seed.
