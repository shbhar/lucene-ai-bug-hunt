ProtectedTermFilterFactory does not pass its luceneMatchVersion to the filters it builds from wrappedFilters

ProtectedTermFilterFactory builds its wrappedFilters without its luceneMatchVersion, so they act as the newest version. Since 10.5, a wrapped truncate prefixLength=4 pinned to 10.4.0 cuts ab😀😀cd to ab😀😀 instead of the legacy ab😀, and a document indexed on 10.4.0 gets 0 hits instead of 1.

The bug in 30 seconds

#

ProtectedTermFilterFactory applies other filters to every token that is not protected. In its wrappedFilters form it builds those filters itself and never passes them its luceneMatchVersion, so, unless one is given its own filterName.luceneMatchVersion, they behave like the newest version even when you pin an older one.

  1. You index on Lucene 10.4.0 with ProtectedTermFilterFactory, wrappedFilters=truncate and truncate.prefixLength=4 (the shape of the class javadoc's Solr example). The token ab😀😀cd (8 UTF-16 chars, 6 code points) is indexed as ab😀, its first 4 UTF-16 chars.
  2. You upgrade to 10.5 or later and pin luceneMatchVersion=10.4.0, the documented way to keep old analysis. For the deprecated prefixLength, a version below 10.5 means "count UTF-16 chars"; 10.5 and later count code points.
  3. You expect the query ab😀😀cd to analyse to ab😀 again, as the same truncate does on its own or inside CustomAnalyzer's when()/endwhen(), and to find the document: 1 hit.
  4. You get ab😀😀, the first 4 code points, and 0 hits, with no error. The factory reports version 10.4.0, but it builds each wrapped filter from its truncate.* arguments only, so the wrapped truncate runs as the latest version.
  5. Only tokens with an emoji or another supplementary character in the first prefixLength chars change. Workarounds: add truncate.luceneMatchVersion=10.4.0, or use truncateAfterChars=4.

Who is affected

#

Users of the wrappedFilters form (factory arguments, Solr-style schemas, or CustomAnalyzer.addTokenFilter("protectedTerm", ...)) on 10.5 or later who pin luceneMatchVersion below 10.5 and wrap truncate with prefixLength or no length. Tokens with an emoji in the prefix get different terms, so queries miss documents indexed the legacy way. Opt-in and rare.

Mechanism, terms and numbers607 words

ProtectedTermFilterFactory runs other filters on every token that is not protected. You can name them with CustomAnalyzer's when()/endwhen() or with the factory's own wrappedFilters and filterName.argName parameters (the Solr-style spelling); the class javadoc shows both, each wrapping truncate prefixLength=4. In the wrappedFilters form the factory builds each wrapped filter from the filterName.* arguments only, and its own luceneMatchVersion, already consumed by AbstractAnalysisFactory, is never passed on, so every wrapped factory without its own filterName.luceneMatchVersion runs at Version.LATEST. Since 10.5.0 (#15900) truncate's deprecated prefixLength keeps N UTF-16 chars below version 10.5 and N code points from 10.5, so with luceneMatchVersion=10.4.0 the token ab😀😀cd becomes ab😀 unwrapped and in the when() form, but ab😀😀 in the wrappedFilters form. A document indexed on 10.4.0 with this configuration is found by the when() form on main (1 hit) but not by the wrappedFilters form (0 hits). The missing forwarding is in every release since 7.4.0; with stock filters it silently changes terms since 10.5.0. A one-line putIfAbsent in populateInnerFilters fixes it; the analysis module's tests pass with it.

Terms

#
  • luceneMatchVersion: every analysis factory reads it from its arguments (AbstractAnalysisFactory) and uses Version.LATEST when there is none. Pinning it to an older version keeps that version's analysis after an upgrade. CustomAnalyzer.Builder.withDefaultMatchVersion adds it to every factory it builds.
  • Two spellings of a protected chain: CustomAnalyzer.builder()...when("protectedTerm", ...) + addTokenFilter("truncate", "prefixLength", "4") + endwhen(), or one factory with wrappedFilters=truncate and truncate.prefixLength=4 (the Solr-style spelling). The class javadoc shows both (ProtectedTermFilterFactory.java:38-61).
  • truncate prefixLength (deprecated): since 10.5.0 (#15900) it keeps N UTF-16 chars when the version is below 10.5 and N code points from 10.5 (TruncateTokenFilterFactory.java:93-97). With no length parameter at all it takes the same path with N = 5 (:81-82).

The bug

#
  1. The constructor's super(args) takes luceneMatchVersion out of the argument map into the factory's own field (AbstractAnalysisFactory.java:94-109).
  2. handleWrappedFilterArgs makes a fresh map per wrapped filter and moves only the filterName.argName entries into it (ProtectedTermFilterFactory.java:116-152).
  3. populateInnerFilters calls TokenFilterFactory.forName(filterName, filterArgs) with that map (:154-165, the call at :162). Unless the configuration gave that filter its own filterName.luceneMatchVersion, the map has no version, so the wrapped factory takes Version.LATEST (AbstractAnalysisFactory.java:98-99).
  4. The when() form does not have this gap: ConditionBuilder.addTokenFilter adds the default version to each wrapped filter (CustomAnalyzer.java:646-650, through applyDefaultParams, :596-602).

The same on 10.5.2. Upgrade scenario: one document written with the 10.4.0 jars and this configuration holds the term ab😀; searching it on 10.5.2 or main with the same configuration finds 0 hits in the wrappedFilters form and 1 in the when() form (1 and 1 with the fix).

Exposure and likelihood265 words
  • Who is exposed. The wrappedFilters form of ProtectedTermFilterFactory (SPI name protectedTerm): factory arguments, Solr-style schemas, or CustomAnalyzer.addTokenFilter("protectedTerm", ..., "wrappedFilters", ...). The when()/endwhen() form is not affected.
  • What it takes. Lucene 10.5.0 or later, luceneMatchVersion pinned below 10.5.0, a wrapped truncate with the deprecated prefixLength (or no length parameter), and a supplementary character (emoji, many CJK extension characters) in the first prefixLength chars of a token that is not protected.
  • What changes. Such tokens get the 10.5+ code-point prefix (at most 2 * prefixLength chars) instead of the pinned legacy one. Queries miss documents indexed with the legacy analysis (before an upgrade, or by the when() form): 0 hits instead of 1 in the upgrade probe. Mixed index generations analyse the same text differently. No error and no exception; the extra work is bounded (the code-point branch scans at most prefixLength code points, TruncateTokenFilter.java:97-112).
  • What does not change. BMP-only text, protected terms, unpinned configurations, versions pinned to 10.5.0 or later, and the when() form.
  • Beyond truncate. On main, truncate is the only stock factory whose output reads the version, but any application factory used inside wrappedFilters that reads luceneMatchVersion has received Version.LATEST since 7.4.0, unless it was given its own filterName.luceneMatchVersion. From 8.4.0 to 9.12.3 the only stock consequence was loud: a wrapped concatenateGraph rejected preserveSep under a version below 8.4.0.
  • How likely. Rare: each ingredient is ordinary (the class javadoc's Solr example is this configuration, and pinning the version is how users keep an old index after an upgrade), but all together they are uncommon in direct Lucene use today.

Why it is a bug, not intended

#
  • withDefaultMatchVersion passes the version "as default to all tokenizers or filters"; the when() form gives it to the same wrapped truncate.
  • prefixLength is kept "for backwards compatibility" and "depends on the luceneMatchVersion parameter"; #15900's review: "Old indexes and schemas then use old behaviour".
  • The Synonym factories forward their version to their tokenizer factory; SOLR-4251 fixed a similar defect in 2013.
The full argument332 words
  • CustomAnalyzer's contract. withDefaultMatchVersion's javadoc: "This match version is passed as default to all tokenizers or filters. It is used unless you pass the parameter {code luceneMatchVersion} explicitly." (CustomAnalyzer.java:242-243, verbatim; {code ...} is a malformed tag in the source). The wrapped truncate is a filter of that analyzer and does not get it; in the when() form it does (:648). TestCustomAnalyzer.testVersionAwareFilter (:111-127) checks that version-aware filters receive the default; it checks a top-level filter only, not a filter inside when() or wrappedFilters.
  • truncate's back-compat purpose. prefixLength "is still supported" "for backwards compatibility" and "its behaviour depends on the luceneMatchVersion parameter" (TruncateTokenFilterFactory.java:32-37). In the #15900 review, uschindler wrote "Old indexes and schemas then use old behaviour". Pinning the version is how a schema keeps the old terms; the wrappedFilters path defeats it.
  • The two spellings disagree. The class javadoc shows the when() form and the wrappedFilters form next to each other, both wrapping truncate prefixLength=4; under the same pinned version they give different terms (the two examples also differ in tokenizer and in how they name the factory; the repro removes those differences). The javadoc does not call them equivalent, and nothing promises that wrapped filters inherit the version, so the issue should not claim either.
  • Precedent. SOLR-4251 (fixed in 4.1, 2013): SynonymFilterFactory's delegate "is not propagating the LUCENE_MATCH_VERSION"; its fix (a973191f2de) forwarded the version to the delegate. Today both Synonym factories forward their version to the tokenizer factory they build, through lines from later commits (SynonymFilterFactory.java:112, SOLR-4813, 2013; SynonymGraphFilterFactory.java:109, LUCENE-6664, 2016). They put the version first and then copy the tokenizerFactory.* arguments, so an explicit tokenizerFactory.luceneMatchVersion still wins (executed): the same semantics as the recommended putIfAbsent fix.
  • Nothing pins the current behaviour. The introducing commit and the 87 comments of #9320 never mention the version. TestProtectedTermFilterFactory wraps truncate.prefixLength (testMultipleWrappedFiltersWithParams, :83-99), but only with ASCII text at Version.LATEST. #15900 never mentions ProtectedTermFilterFactory.
The devil's-advocate check238 words

The checkers built the strongest case for "works as designed": (a) no javadoc line says wrapped filters inherit the version; (b) luceneMatchVersion is an ordinary factory argument, so truncate.luceneMatchVersion=10.4.0 is a valid filterName.argName setting, and it works; (c) each component meets its own contract read literally (AbstractAnalysisFactory defaults to LATEST, CustomAnalyzer does pass the version to the factory it builds, truncate follows the version it gets); (d) prefixLength is deprecated, and truncateAfterChars (a parameter since 10.5.0) gives the legacy result at any luceneMatchVersion.

Why it fails: no documentation mentions filterName.luceneMatchVersion for wrapped filters (the class javadoc describes filterName.argName in general), and Solr fills in the schema's default version for every factory that does not set its own, so users normally set it once per schema; withDefaultMatchVersion promises the version to "all tokenizers or filters", and the when() form delivers it; #15900 kept prefixLength so that pinned schemas keep their old terms; the Synonym factories pass their version on to the tokenizer factory they build, and SOLR-4251 fixed the same kind of defect in 2013 by forwarding the version. No test, commit or PR says the gap is deliberate. The strongest remaining reading is that withDefaultMatchVersion covers only the factories CustomAnalyzer builds itself; the when() form and the Synonym factories show that Lucene otherwise passes the version on to child factories. The remaining pushback is about severity (narrow), not validity. Every checker rejected the works-as-designed case.

Suggested fix

#

Recommended Forward the factory's version to each wrapped filter, unless it has its own

Forward the version: in populateInnerFilters, call filterArgs.putIfAbsent(LUCENE_MATCH_VERSION_PARAM, getLuceneMatchVersion().toString()) before TokenFilterFactory.forName(...). An explicit truncate.luceneMatchVersion still wins, and unpinned configurations are unchanged. Validated: the new tests, the closest suites, all analysis-module tests and check pass.

           if (idSuffixPos != -1) { // Strip '-id' suffix, if any, prior to SPI lookup

+          // wrapped filters use this factory's luceneMatchVersion, unless they were given their own

+          filterArgs.putIfAbsent(LUCENE_MATCH_VERSION_PARAM, getLuceneMatchVersion().toString());
           innerFilters.add(TokenFilterFactory.forName(filterName, filterArgs));

Trade-offs

  • A configuration pinned below 10.5 that ran on 10.5.0-10.5.2 indexed code-point terms for affected tokens; after the fix it produces the legacy terms again, so such an index needs a reindex, or the user keeps the code points with truncate.luceneMatchVersion=10.5.0 or truncateAfterCodePoints; that only avoids a reindex when all affected terms were written on 10.5.0-10.5.2, and an index that mixes pre-10.5 and 10.5.x terms needs a reindex either way. Worth a CHANGES line (none drafted).
  • An application factory inside wrappedFilters that reads luceneMatchVersion now sees the configured version instead of LATEST: the point of the fix, but a behaviour change since 7.4.0.
  • The wrapped factories' getOriginalArgs() now include luceneMatchVersion; the wrapped factories are not reachable from outside (ConditionalTokenFilterFactory.innerFilters is private).

The same with put (not recommended)

#

Uses an unconditional put after the per-filter arguments are collected (the Synonym factories also call put, but before they copy the tokenizerFactory.* arguments, so an explicit per-tokenizer version still wins there).

Trade-offs

So it overrides an explicit truncate.luceneMatchVersion with the outer version, which breaks the filterName.argName mechanism for this one argument. With it the guard test testWrappedFilterOwnVersionWins fails (expected:<ab😀[😀]> but was:<ab😀[]>), the other 4 pass.

Documentation only

#

Document that wrapped filters need filterName.luceneMatchVersion, and point to truncateAfterChars / truncateAfterCodePoints.

Trade-offs

Leaves withDefaultMatchVersion's "all tokenizers or filters" broken and the two spellings inconsistent; not validated.

A shared helper for child factories

#

A small protected helper (for example in AbstractAnalysisFactory) that copies the version into a child factory's arguments, used by ProtectedTermFilterFactory and the Synonym factories.

Trade-offs

A broader API change for a one-line bug; only if a reviewer asks. Not validated.

Downstream note

#

Solr passes its schema's luceneMatchVersion to every factory that does not set its own, and its reference guide shows exactly this wrappedFilters="truncate,lowercase" truncate.prefixLength="4" configuration, so pinned Solr schemas would be affected once Solr moves to Lucene 10.5 (read, not run in Solr).

How it was found

#

Code reading: while checking how analysis factories pass their arguments to the factories they create, a finder saw that ProtectedTermFilterFactory builds its wrapped filters without its luceneMatchVersion, and that truncate is the one stock filter whose output depends on it. A public-API JUnit confirmed it; independent checkers followed.

The method in full92 words
  • Method (non-formal): code reading in the hunt's unit on analysis factory/constructor equivalence: every place that builds an inner analysis factory (forName, getConstructor(Map.class) in src/java) was read while modelling how factory arguments reach constructors. luceneMatchVersion is the one argument AbstractAnalysisFactory consumes for every factory, and TruncateTokenFilterFactory (since #15900) is the one stock factory whose output depends on it.
  • Confirmation. A public-API JUnit comparing the wrappedFilters form with the when() form and an unwrapped truncate (2 of 4 fail on main and 10.5.2, assertions on and off), then the checks below.

History

#

The missing forwarding came with wrappedFilters in d91273ddf0b (LUCENE-8273, 2018, 7.4.0). It first changed terms silently with stock filters in 10.5.0, when #15900 made truncate prefixLength depend on the version. Wrong on 10.5.0, 10.5.1, 10.5.2 and main; right on 10.4.0; not fixed upstream.

LFV-510, snapshot of 2026-10-29

Registry title
ProtectedTermFilterFactory does not pass its luceneMatchVersion to the filters it builds from wrappedFilters, so since 10.5 a wrapped truncate with prefixLength under a pinned pre-10.5 version truncates by code points instead of the legacy UTF-16 chars
Area
analysis / common miscellaneous (ProtectedTermFilterFactory#populateInnerFilters: wrappedFilters factory construction; symptom in TruncateTokenFilterFactory prefixLength)
Priority
Low, rank 410: Silent analysis drift only for the wrappedFilters form of ProtectedTermFilterFactory with a pinned pre-10.5 version, a wrapped prefixLength truncate and supplementary characters, so it closes these rare analysis rows.
Impact class
silent wrong results
Impact note
Narrow, opt-in configuration only: analyzers that use ProtectedTermFilterFactory's wrappedFilters form (factory args, Solr-style schemas, or CustomAnalyzer.addTokenFilter("protectedTerm", ..., "wrappedFilters", ...); the when()/endwhen() form is not affected) on Lucene 10.5.0 or later, with luceneMatchVersion pinned below 10.5.0 and a wrapped truncate that uses the deprecated prefixLength (by reading, also truncate with no length parameter); then tokens with supplementary characters such as emoji inside the prefix keep prefixLength code points instead of prefixLength UTF-16 chars, so terms differ from the pinned legacy analysis (missed matches against segments indexed before the upgrade, mixed analysis across index generations) with no error; BMP-only text is unaffected, no scale is needed, and truncate.luceneMatchVersion=<version> or truncateAfterChars are workarounds.
Summary
You configure ProtectedTermFilterFactory with wrappedFilters=truncate and truncate.prefixLength=4 and pin luceneMatchVersion to 10.4.0 (in the factory args, or through CustomAnalyzer.withDefaultMatchVersion), on Lucene 10.5 or later. You expect the wrapped truncate to keep the legacy behaviour that the pinned version selects for back-compat, the first 4 UTF-16 chars, as an unwrapped truncate and the equivalent when()/endwhen() form do under the same version. Instead populateInnerFilters builds the wrapped factory from the 'truncate.*' arguments only, so it runs at Version.LATEST and keeps 4 code points: the token 'ab😀😀cd' becomes 'ab😀😀' instead of 'ab😀', with no error.
