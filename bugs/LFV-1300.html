With an index sort, IndexWriter's RAM accounting leaves out buffered term vectors

With an index sort, term vectors are buffered in a temporary writer that IndexWriter never counts: 10 documents report 168,664 bytes instead of 508,384, so flush-by-RAM fires later. Every release since 8.7.0; the fix is one line per sorting consumer.

The finding in 30 seconds

#

IndexWriter adds up the memory its buffered documents use and flushes when the total reaches the RAM buffer. With an index sort, buffered term vectors sit in a temporary writer that is never added to that total.

Background in three steps

#
  1. IndexWriter buffers new documents in memory, per indexing thread, and adds up what they use: IndexWriter.ramBytesUsed(). When the total reaches setRAMBufferSizeMB (16 MB by default) it flushes a segment.
  2. Term vectors are buffered by a term-vectors writer. Its consumer adds that writer to the total by setting accountable = writer when it creates it; stored fields work the same way.
  3. With an index sort (IndexWriterConfig.setIndexSort), documents are reordered at flush, so term vectors and stored fields first go to temporary writers that sorting subclasses of those consumers create.

The finding, step by step

#
  1. You set an index sort (setIndexSort on a long field) and add 10 documents whose text field stores term vectors with positions and offsets; each document is "a " repeated 10,000 times.
  2. You expect IndexWriter.ramBytesUsed() to equal what the same documents give without the sort: 508,384 bytes.
  3. Instead it reports 168,664 bytes. The 339,720 missing bytes are the two temporary writers' buffers (339,592 of term vectors, 128 of stored fields): with a sort, term vectors sit in a temporary writer, and SortingTermVectorsConsumer never sets accountable = writer as the base consumer does, so the indexing chain counts that writer as 0.
  4. Flush-by-RAM is fooled too: with setRAMBufferSizeMB(0.3) the unsorted writer flushes once (7 documents written, 3 left in RAM), while the sorted writer keeps all 10 in RAM and does not flush during the 10 documents.
  5. No error; only the RAM estimate and the flush timing change. Affects 8.7.0 to 10.6.0 and main; with accountable = writer; added to the two sorting consumers both writers report 508,384 bytes.

Who is affected

#

Applications that set an index sort (opt-in) and store term vectors (opt-in). In each indexing thread the temporary writer's buffers, sized by its largest chunk, are invisible to flush-by-RAM: small for text with many distinct terms, megabytes for documents with few distinct terms and many positions. Only the RAM estimate and flush timing change; no error.

Mechanism, terms and numbers557 words

IndexWriter adds up the heap used by each indexing thread's buffered documents and flushes when the total reaches the RAM buffer. The term-vectors and stored-fields consumers take part by setting a field, accountable = writer, when they create their writer; IndexingChain.ramBytesUsed() sums those fields. With an index sort, the chain uses SortingTermVectorsConsumer and SortingStoredFieldsConsumer instead. They override the init methods without calling super, create a temporary writer, and never set accountable, so it stays NULL_ACCOUNTABLE and the temporary writer's buffered term vectors count as 0 in IndexWriter.ramBytesUsed() and in flush-by-RAM.

In the minimal test, the same 10 documents with term vectors report 508,384 bytes without a sort and 168,664 with one; with setRAMBufferSizeMB(0.3) the unsorted writer flushes and the sorted one does not, within the 10 documents. Per indexing thread, the miss is the temporary writer's buffers, sized by the largest chunk it has held (a chunk ends after 8 KiB of term suffixes or 128 documents): small for text with many distinct terms, megabytes for documents with few distinct terms and many positions. It dates from LUCENE-9514 (8.7.0), which added the field and set it only in the base classes. Adding accountable = writer; in both sorting consumers makes the two writers in the test report the same figure; the nearby core tests pass with it.

The bug

#
  1. IndexingChain picks the plain consumers without an index sort and SortingStoredFieldsConsumer / SortingTermVectorsConsumer with one (IndexingChain.java:140-160).
  2. The base consumers hold Accountable accountable = Accountable.NULL_ACCOUNTABLE, documented as "this accountable either holds the writer or one that returns null" (TermVectorsConsumer.java:55-57, StoredFieldsConsumer.java:34-36), and set accountable = writer; when they create the writer (TermVectorsConsumer.java:108, StoredFieldsConsumer.java:51).
  3. SortingTermVectorsConsumer.initTermVectorsWriter() (SortingTermVectorsConsumer.java:86-94) overrides that method without calling super: it creates the temporary writer on a TrackingTmpOutputDirectoryWrapper and never assigns accountable. SortingStoredFieldsConsumer.initStoredFieldsWriter() (SortingStoredFieldsConsumer.java:94-100) does the same.
  4. IndexingChain.ramBytesUsed() is bytesUsed.get() + storedFieldsConsumer.accountable.ramBytesUsed() + termVectorsWriter.accountable.ramBytesUsed() + ... (IndexingChain.java:1791-1797). DocumentsWriterPerThread.ramBytesUsed() adds it (:717-723), flush control uses that total for flush-by-RAM and the per-thread hard limit (DocumentsWriterFlushControl.java:215-250), and IndexWriter.ramBytesUsed() returns it (IndexWriter.java:796-799). With a sort, the live temporary writer counts as 0.

How much is missed

#

The missed amount is the temporary term-vectors writer's own ramBytesUsed() (Lucene90CompressingTermVectorsWriter.java:994-1003), in the test almost all of it its int[] position and offset buffers. They hold the open chunk, which ends after 8 KiB of term suffixes or 128 documents, checked after each document (SortingTermVectorsConsumer.java:39-41; trigger at :379-381), and they are not shrunk when a chunk is written (:429-433), so the miss is sized by the largest chunk the writer has held, which one long document can make large. In the test, 10 documents of one repeated term never reach 8 KiB of suffixes, so all their positions and offsets stay buffered: the 339,720 missing bytes are 339,592 of the term-vectors writer and 128 of the stored-fields writer, about two thirds of the unsorted total. The term-vectors figure itself counts the int[] buffers at one byte per entry (a separate defect, LFV-1232), so the heap actually held is larger. The temporary stored-fields writer writes out every document (maxDocsPerChunk 1, SortingStoredFieldsConsumer.java:79-81); its byte buffer then reports 0 (ByteBuffersDataOutput.java:488-495) and only its two 16-entry int arrays count: 128 bytes per thread.

Exposure and likelihood245 words
  • Who: IndexWriterConfig.setIndexSort plus a field type with setStoreTermVectors; the gap is large when chunks hold many positions or offsets. Neither is a default.
  • Effect: IndexWriter.ramBytesUsed() under-reports, the writer flushes later than setRAMBufferSizeMB suggests, and the per-thread hard limit check (DocumentsWriterFlushControl.java:247) sees less than is held. Index contents are not involved: accountable is read only by the RAM estimate (IndexingChain.java:1791-1805).
  • Scale: per indexing thread, the temporary writer's buffers, sized by its largest chunk; not a fixed number of bytes, since one long document can fill a chunk. Text with many distinct terms is expected to end a chunk after a few documents (8 KiB of suffixes), so the buffers stay small (not measured). With few distinct terms and many positions a chunk keeps up to 128 documents: 339,592 bytes of term vectors for the test's 10 documents, about 3.2 million for 100 such documents (4,261,656 vs 1,086,168), per thread, by the writer's own figure, which under-counts its int[] buffers (LFV-1232).
  • Likelihood: rare. A noticeable effect needs documents with few distinct terms and many positions, and no public report of it was found since 8.7.0 (2020).
  • Caveats: the figures are ramBytesUsed() estimates, not measured heap. The flush probe is 10 documents on one thread; with more documents the counted pools alone eventually trigger a flush, later than without the sort. The setRAMBufferSizeMB javadoc also says a flush may release only part of the buffer, depending on the flush policy (LiveIndexWriterConfig.java:179-181).

Why it looks unintended

#
  • The base consumers document that accountable "either holds the writer or one that returns null" and set it when they create the writer; the sorting overrides never do.
  • LUCENE-9514 added this accounting because the term-vectors writer is "part of the DWPT lifecycle" and drives flush decisions; it never mentions index sorting.
  • Same setRAMBufferSizeMB, different flushing: only the unsorted writer flushes.
The full argument217 words
  • Contract in code: "this accountable either holds the writer or one that returns null" (TermVectorsConsumer.java:55-57, StoredFieldsConsumer.java:34-36); IndexingChain.ramBytesUsed() and getChildResources() read that field (IndexingChain.java:1791-1805).
  • User-facing promise: "When this is set, the writer will flush whenever buffered documents and deletions use this much RAM" (setRAMBufferSizeMB, LiveIndexWriterConfig.java:162-163).
  • The change that added it: LUCENE-9514 (8f895d90755, Simon Willnauer, #10553 / lucene-solr#1847): "TermVectorsWriter might consume some heap space memory that can have a significant impact on decisions made in the IW if writers should be stalled or DWPTs should be flushed ... This change adds RAM accounting to the TermVectorsWriter since it's part of the DWPT lifecycle and not just present during flush." The temporary writer lives exactly that long.
  • History points to an oversight: six days earlier LUCENE-9511 (98e55f0ea82, lucene-solr#1839) counted stored fields as writer == null ? 0 : writer.ramBytesUsed(), which covered the sorted writer too. LUCENE-9514 replaced it with accountable, set only in the base init methods that the sorting subclasses had overridden without super since LUCENE-7579 (4ccb9fbd2bb, 2016); its only change to SortingTermVectorsConsumer.java was two blank lines. No javadoc, CHANGES entry, test, PR review or issue thread exempts index sorting, and no upstream test checks ramBytesUsed() with an index sort and term vectors.
The devil's-advocate check220 words

The strongest case for "intended": Accountable and these consumers are internal, ramBytesUsed() is an estimate, the setRAMBufferSizeMB javadoc calls the limit "just an indicator when to flush" and the RAM for deletions "only approximate" (LiveIndexWriterConfig.java:167-177) and says a flush may release only part of the buffer (:179-181), the temporary writer's heap is small for normal text, and nothing promises equal figures with and without a sort.

Why it fails: those caveats are about concurrent flushing, delete-by-Query and which documents a flush picks, not about leaving a writer out altogether, and the same javadoc promises a flush "whenever buffered documents and deletions use this much RAM". The unsorted path counts the same writer buffers on purpose, and "small" was explicitly not a reason to skip it: on lucene-solr#1839 s1monw wrote that the stored-fields writer "uses about 650kb memory per DWPT instance and that might add quickly if flushing can't keep up with indexing ... these settings are valid and should never cause OOM" (2020-09-08). The difference is visible through public API (one writer flushes, the other does not), and upstream treated a similar undercount of the kNN vector writers as a bug (#15901, fixed by #15982, 2026). The independent reproduction, the intended-behaviour review, the adjudication and the cross-model reviewer all rejected it (the reviewer rated it weak).

Suggested fix

#

Recommended A. Assign accountable in both sorting init methods (validated)

Add accountable = writer; right after the temporary writer is created in SortingTermVectorsConsumer.initTermVectorsWriter() and SortingStoredFieldsConsumer.initStoredFieldsWriter(), as the base consumers do (+2 lines). The repro passes with assertions on and off, and 7 nearby core test classes plus the repro pass (93 tests, 0 failures).

// SortingTermVectorsConsumer.initTermVectorsWriter()
writer = TEMP_TERM_VECTORS_FORMAT.vectorsWriter(tmpDirectory, info, context);
accountable = writer;

// SortingStoredFieldsConsumer.initStoredFieldsWriter()
this.writer = TEMP_STORED_FIELDS_FORMAT.fieldsWriter(tmpDirectory, info, IOContext.DEFAULT);
accountable = writer;
All options and trade-offs3 options · 406 words

Three options. A was validated with gradle in a scratch worktree of 5adff78bb168; B and C are by reading.

A. Assign accountable in both sorting init methods (validated) (recommended)

#

One line in each of SortingTermVectorsConsumer.java (after :91) and SortingStoredFieldsConsumer.java (after :98), mirroring TermVectorsConsumer.java:108 and StoredFieldsConsumer.java:51.

// SortingTermVectorsConsumer.initTermVectorsWriter()
writer = TEMP_TERM_VECTORS_FORMAT.vectorsWriter(tmpDirectory, info, context);
accountable = writer;

// SortingStoredFieldsConsumer.initStoredFieldsWriter()
this.writer = TEMP_STORED_FIELDS_FORMAT.fieldsWriter(tmpDirectory, info, IOContext.DEFAULT);
accountable = writer;

Trade-offs

  • The smallest change; it makes the sorted path behave like the unsorted one: ramBytesUsed() includes the temporary writers' buffers and flush-by-RAM fires earlier (wanted).
  • The stored-fields line adds little in practice (128 bytes per thread here, since that writer writes out every document) but keeps both consumer pairs consistent. With the fix the test's figures are equal; at 100 documents the fixed sorted writer reports 4,260,888 vs 4,261,656 unsorted, because the two stored-fields writers differ (128 vs 896 bytes).
  • Independent of LFV-1232 (the term-vectors writer's own ramBytesUsed() counts its int[] buffers at one byte per entry): with an index sort, fixing LFV-1232 alone changes nothing; with both fixed, the sorted writer reports the larger, correct figure.

What the checks validated

  • Gradle in a scratch worktree of 5adff78bb168, OpenJDK 25.0.3, seed DEADBEEF: stock, the repro fails with assertions on and off; with the fix it passes, on and off.
  • With the fix and the repro: TestIndexSorting, TestSortingStoredFieldsConsumer, TestStoredFieldsConsumer, TestTermVectors, TestTermVectorsWriter, TestFlushByRamOrCountsPolicy, TestIndexWriterThreadsToSegments and the repro: 8 classes, 93 tests, 0 failures, 1 skipped (testDocsStuckInRAMForever, @Nightly).
  • checkGoogleJavaFormat, ecjLint, forbiddenApisMain and forbiddenApisTest of lucene/core pass.
  • Probe: with the fix the sorted writer reports exactly the unsorted figure (508,384) and, under a 0.3 MB buffer, flushes like it (1 flush, 3 documents left).
  • Earlier shadowed-class checks: the same two lines made three independent tests pass. The full lucene/core suite was not run.

B. Let the base init method set accountable; subclasses override only the writer creation

#

For example a protected createWriter() hook that initTermVectorsWriter() / initStoredFieldsWriter() call, so the assignment cannot be skipped by a subclass.

Trade-offs

Same effect and guards future subclasses, but a larger refactor of internal classes. Not run.

C. Derive the figure from the writer field again

#

Count writer == null ? 0 : writer.ramBytesUsed(), as LUCENE-9511 first did.

Trade-offs

Covers every subclass automatically, but undoes the NULL_ACCOUNTABLE design LUCENE-9514 chose and puts null checks back where the field is read. Not run.

Downstream note

#

Downstream, applications that combine index sorting with term vectors and size their heap close to the RAM buffer may see more indexing heap than configured.

How it was found

#

Semi-formal: a proof-obligation audit of the indexing chain's RAM-accounting contract, that every writer kept for the life of an indexing thread is held in its consumer's accountable. The sorting consumers' init overrides failed the obligation, and a public-API JUnit test witnessed it on stock main.

The method in full77 words
  • Obligation: for each consumer whose accountable IndexingChain.ramBytesUsed() sums, every path that creates its writer must also set accountable = writer (the base consumers' comment and assignment).
  • Finding: the base init methods discharge it (TermVectorsConsumer.java:108, StoredFieldsConsumer.java:51); the overrides in SortingTermVectorsConsumer and SortingStoredFieldsConsumer do not, and do not call super.
  • Witness: one public-API JUnit test comparing ramBytesUsed() with and without an index sort, then independent reproduction, a cross-model review and an adjudication (see Independent checks).

index / IndexWriter RAM accounting with index sorting (SortingTermVectorsConsumer, SortingStoredFieldsConsumer)
Priority

Impact note

Summary
You give IndexWriter an index sort and index documents whose fields store term vectors with positions and offsets. You expect IndexWriter.ramBytesUsed() and flush-by-RAM to count the buffered term vectors as they do without a sort, since the indexing chain sums each consumer's 'accountable', which 'either holds the writer or one that returns null'. Instead the sorting consumers create their temporary writer without assigning it to 'accountable', so it counts as 0: the same 100 documents report 1,086,168 with the sort and 4,261,656 without, and with a small RAM buffer the unsorted writer flushes while the otherwise identical sorted writer does not.
