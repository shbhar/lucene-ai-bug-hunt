SimpleNaiveBayesDocumentClassifier applies a field boost such as title^10 only on its first call

Configure SimpleNaiveBayesDocumentClassifier with a documented field boost such as title^10, and only the first classification uses it: that call rewrites your array entry to plain title, so later calls silently give the unboosted answer (fruit 0.99994, then vehicle 0.55373). Affects 6.0.0 through 10.5.2 and main.

The bug in 30 seconds

#

The naive Bayes document classifier scores each class by adding, for every configured field, how likely the document's words are under that class, multiplied by the field's boost. Its constructor javadoc says the field names "can contain boosting indication e.g. title^10".

  1. Index six documents: three fruit (titles such as "apple banana", bodies such as "sweet juice tree") and three vehicle (titles such as "car truck", bodies such as "wheel engine road fuel"). The new document has a fruit title, "apple banana cherry", and a vehicle body, "engine wheel road fuel".
  2. Build the classifier with {"title^10", "body"}, as its javadoc allows, and classify that document twice. You expect fruit both times: with the title's word log-likelihood weighted by 10, the title wins (fruit 0.99994); with equal weight, the body wins narrowly (vehicle 0.55373).
  3. Call 1 returns fruit 0.99994. While reading title^10 it keeps the 10 only for this call, and then writes the bare name title back into the field-name array, which is the caller's own array.
  4. Call 2 finds no ^ left, uses boost 1 and returns vehicle 0.55373, digit for digit the unboosted answer. So does every later call, and any new classifier built from the same array after that first call. No error is raised.
  5. On upstream's own boosted-classification test data (title^100), call 1 says batman and call 2 says the video-game class. Parsing the boost on every call, without the write-back, fixes it.

Who is affected

#

Applications using the opt-in classification module's naive Bayes document classifier with a field^boost that classify more than one document per classifier, or build classifiers from one shared array. In sequential use, from the second call on, every result is silently the unboosted one, with plausible scores; no special data or scale is needed.

Mechanism, terms and numbers731 words

SimpleNaiveBayesDocumentClassifier documents that its field names "can contain boosting indication e.g. title^10" (SimpleNaiveBayesDocumentClassifier.java:63-64). On every assignClass(Document) or getClasses(Document[, max]) call, analyzeSeedDocument splits "title^10" into the name and the boost, keeps the boost in a map made for that call, and then writes the bare name back with textFieldNames[i] = fieldName (:170). That array is the caller's own varargs array, which the parent class keeps by reference (SimpleNaiveBayesClassifier.java:95). From the second call on it holds "title", no ^ is left, and every boost is 1: the classifier silently returns exactly the unboosted scores and classes. On a six-document index the same document is fruit (0.99994) on call 1 and vehicle (0.55373) on call 2; on upstream's testBoostedDocumentClassification data (title^100) the class flips from batman to the video-game class. A second classifier built from the same String[] after that is unboosted even on its own first call. The write-back came with the class in LUCENE-6631, so every release from 6.0.0 to 10.5.2 and main is affected. Parsing each configured entry per call into local arrays, without writing back, fixes it; the whole lucene/classification test suite passes with that change.

Terms

#
  • SimpleNaiveBayesDocumentClassifier (lucene/classification, @lucene.experimental): classifies a Document against an index whose documents carry a class field. For each class it adds, per configured field and per value of that field, the class's log prior plus the field's average word log-likelihood times the field's boost (SimpleNaiveBayesDocumentClassifier.java:118-131), then normalizes the scores to sum to 1.
  • Field boost: the constructor's textFieldNames "can contain boosting indication e.g. title^10" (:63-64); title^10 multiplies the title's word log-likelihood by 10 (the class log-prior, added once per field value, is not boosted).
  • textFieldNames: the varargs array passed to the constructor; the parent SimpleNaiveBayesClassifier keeps it as a protected final String[] without copying (SimpleNaiveBayesClassifier.java:55, :95).

The bug

#
  1. Every assignClass(Document) and both getClasses(Document[, max]) overloads call assignNormClasses (:77-103), which creates two fresh maps for the call, tokens per field and boost per field (:108-109), and calls analyzeSeedDocument (:115).
  2. analyzeSeedDocument (:148-172) reads textFieldNames[i] (:154); if it contains ^, it splits it into the name and the boost (:157-161); it stores tokens and boost under the bare name (:168-169) and then writes the bare name back: textFieldNames[i] = fieldName (:170). The write-back exists so that the scoring loop, which iterates textFieldNames again (:121), finds the bare name in the maps (:122, :128).
  3. On the next call the array holds title: no ^, so the boost stays 1 (:155), and the title's log-likelihood is multiplied by 1 (:125-128). The result is exactly the unboosted classifier's.
  4. The array is the caller's, so once the first classifier has classified a document, a second one built from the same String[] starts unboosted, and the caller sees its own configuration rewritten.

Applications that use SimpleNaiveBayesDocumentClassifier with the documented field^boost syntax and classify more than one document with one instance, or build several classifiers from one String[].   • Concurrent use (executed). With 8 threads sharing one array or one classifier, every one of 96,000 results was either the boosted or the unboosted result (1 to 8 boosted per round of 1,200 calls, depending on timing), with no exception or hang (a probe of those runs, not a thread-safety proof; nothing promises thread safety).

The factory's lifetime and concurrent first calls were not checked, and nothing was run in Solr.

Why it is a bug, not intended

#
  • The constructor javadoc allows title^10, and nothing limits a classifier to one call.
  • The sibling KNN document classifier parses the same syntax on every call; a stale-boost bug there was fixed as a bug (LUCENE-7991).
  • Upstream's boosted test uses each classifier once; on its data, the second call flips the class back.
The full argument225 words
  • Contract. Constructor javadoc (SimpleNaiveBayesDocumentClassifier.java:63-64): the field names "can contain boosting indication e.g. title^10". No single-use limit in the constructor, DocumentClassifier (DocumentClassifier.java:24-66), package-info.java, MIGRATE.md or CHANGES.txt; the interface classifies "the given Document" and is shaped for repeated calls.
  • Tests. TestSimpleNaiveBayesDocumentClassifier.testBoostedDocumentClassification (:114-138) asserts that title^100 gives batman and that without the boost "wrong classification will appear"; it builds a new classifier per assertion, so the second-call path has been untested since 2015. TestKNearestNeighborDocumentClassifier reuses one instance for two documents (:33-45), and ClassificationTestBase.checkOnlineClassification calls assignClass twice on one classifier (with updateSampleIndex() between the calls) and asserts the same class and score (:121-144).
  • Sibling and precedent. KNearestNeighborDocumentClassifier.knnSearch parses field^boost into locals on every call and never writes back (:126-146). LUCENE-7991 (#9039, 7.2.0, CHANGES.txt:7763-7765): "KNearestNeighborDocumentClassifier.knnSearch no longer applies a previous boosted field's factor to subsequent unboosted fields", a stale-boost bug in the sibling, fixed as a bug.
  • History. The class, the write-back and the boosted test all came in LUCENE-6631 (2015); the private comment "This is done only one time for the Seed Document" (:139-140) comes from a patch revision described as "improved seed document analysis to happen only one time", that is once per call instead of once per class; nothing in that thread discusses reusing a classifier or rewriting the array.
The devil's-advocate check209 words

The strongest "intended" case: the classifier and the DocumentClassifier interface are @lucene.experimental; the private javadoc says the analysis "is done only one time"; every upstream test builds a new classifier per call, so instances could be read as single-use; the parent class documents "NO boosting supported per field"; and no javadoc promises that the caller's array is left alone.

Why it fails: @lucene.experimental is about API stability, not an option that silently stops working; "only one time" means once per call, since the maps are rebuilt on every call (:108-109), so the code re-derives the boost per call by design and only the write-back defeats it; the parent's "NO boosting" covers the parent's text path, while this class's constructor allows title^10; the sibling classifier and the shared test base reuse instances, and LUCENE-7991 treated stale boost state as a bug. A reusable classifier that gives another class for the same document on the second call is not a plausible design. Verdict: a defect (adjudication: confirmed, high; the independent reproducer and the devil's advocate: real; the other-model-family intended-lens review: real, medium, intended argument weak). Present the lost boost as the bug and the rewritten array as the mechanism: no javadoc promises the array is left unchanged.

Suggested fix

#

Recommended Parse per call into per-entry local arrays, never write back

Parse each configured entry on every call into local arrays (name, boost, tokens), score over those, and never write into textFieldNames (+21/-16 in SimpleNaiveBayesDocumentClassifier.java). The repro passes, and so do the whole classification test suite (45 tests, assertions on and off) and the format, lint and forbidden-API checks.

    float[] fieldBoosts = new float[textFieldNames.length];
    List<List<String[]>> fieldTokensArrays = new ArrayList<>(textFieldNames.length);

All options and trade-offs4 options · 834 words

Each call then parses the configured strings afresh, scores one entry per configured field with its own boost, and leaves the caller's array alone. Configurations without a repeated field name give results bit-identical to today's first call (run for {title, body} and {title^10, body}; the general case follows from the code). The verification's smaller sketch (loop over the parsed map's keys, drop the write-back) also fixes the reported bug and passes the suite, but it scores a repeated field name only once, which changes the answer of an unboosted configuration such as {"title", "title", "body"} (fruit 0.70741 today, vehicle 0.55373 with it). Parsing once in the constructor into private arrays would work too, and maintainers may prefer it or an immutable internal (name, boost) list: this doc's fix is one validated option, not the only answer. Workaround until a fix ships: build a new classifier with a new array for every call (inline varargs or names.clone()), as the upstream tests do.

Trade-offs

  • Repeated field names change meaning. Today every copy of a repeated name gets the boost of its last entry, even on call 1 ({"title^10", "title", "body"} scores like {"title", "title", "body"}, fruit 0.70741); with this fix each entry keeps its own boost, and both tested orders give the same score (fruit 0.99998); in larger configurations another order could still change low bits (floating-point sums). No upstream test or javadoc covers repeated names.
  • Parsing (split, Float.parseFloat) still runs on every call, as today. A malformed boost throws the same exception as today on the first call that parses it; unlike stock, which may already have rewritten earlier entries, the array stays untouched. title^10^2 is still read as title^10, as today. As today, the boost multiplies only the log-likelihood, not the class log-prior added per field value.
  • No API change; configurations without repeated names are bit-identical to today's first call (executed for {title, body} and {title^10, body}; the general case follows from the code).

Parse once in the constructor into private arrays

#

Parse textFieldNames into private final name and boost arrays in the constructor (a defensive copy) and use them on every call.

Trade-offs

Same scores as the recommended option, and later changes to the caller's array no longer reach the classifier. A malformed boost (title^x, or title^ with nothing after it) then fails at construction instead of the first call. Not run.

Workaround: a new classifier and a new array for every call

#

Build new SimpleNaiveBayesDocumentClassifier(..., "title^10", "body") (inline varargs make a new array each time) or pass names.clone() for every classification, as the upstream tests do.

Trade-offs

Application-side only; costs a classifier per call; not a fix.

Downstream note

#

From reading Solr's source only (not run): Solr's classification update processor with algorithm=bayes builds every classifier from one shared inputFields array, so in sequential use configured boosts there would apply only to the first document classified through that array (factory lifetime and concurrency not checked).

How it was found

#

An AI tool was transcribing the classifier's scoring code for an SMT (Z3) model of the classification module's arithmetic and noticed the write-back; the model itself does not cover it. A public-API JUnit test confirmed it on the stock jars, and independent AI tools then reproduced, reviewed and judged it.

The method in full118 words

Method: code reading (the hunt's "non-formal" tier), a hunt unit (classification), 2026-10-26, stock main jars.

  • The finder was transcribing SimpleNaiveBayesDocumentClassifier's score pipeline into a Z3 inventory of the classifiers' division and log sites, and read textFieldNames[i] = fieldName in analyzeSeedDocument. The model covers a zero-token division with a boost factor, not the write-back.
  • It wrote a 2-test public-API JUnit test (TestSimpleNaiveBayesDocumentClassifierBoostReuse), which failed on main with assertions on and off and on 10.5.2 and 9.12.3, and a two-line fix sketch that passed it and the upstream classification tests.
  • Then independent AI tools reproduced, reviewed and judged it (see the checks), and the history step ran the test on eight selected releases back to 6.0.0.

Bug record

LFV-382, snapshot of 2026-10-27

Registry title
SimpleNaiveBayesDocumentClassifier applies a documented 'field^boost' (e.g. 'title^10') only on its first call: it writes the stripped field name back into the caller's textFieldNames array, so every later classification silently returns the unboosted result (released since 6.0.0)
Area
classification / document classifiers (SimpleNaiveBayesDocumentClassifier field boosts)
Priority
Medium, rank 188: Once a documented field^boost is configured, the experimental naive Bayes document classifier silently drops the boost on every call after the first, a common-trigger silent wrong result in a niche module like LFV-155, and as a new bug it heads the classification rows.
Impact class
silent wrong results
Impact note
Applications that use the opt-in lucene/classification module's SimpleNaiveBayesDocumentClassifier (@lucene.experimental) with the field^boost syntax its constructor javadoc documents get the boost only on the first assignClass(Document) or getClasses(Document[, max]) call; every later call on the same instance, and every call of a second classifier built from the same String[], silently returns exactly the unboosted scores and classes, with no error, no special data and no scale needed, in every release from 6.0.0 to 10.5.2 and on main.
Summary
You build a SimpleNaiveBayesDocumentClassifier with textFieldNames {"title^10", "body"}, as its constructor javadoc allows, and classify documents with it one after another, expecting the title boost on every call. The first call applies the boost but also overwrites "title^10" with "title" in textFieldNames, which is the caller's own array kept by reference, so from the second call on every boost is 1: classifying the same document twice gives fruit (0.99994) and then vehicle (0.55373), exactly the unboosted classifier's answer, and on the upstream test's own fixture ('title^100') the class flips from batman to the video-game class. No error is raised, and a second classifier built from the same String[] is unboosted even on its first call.
