A refresh after ControlledRealTimeReopenThread.close() undoes the closed state, so waitForGeneration can block forever

ControlledRealTimeReopenThread.close() sets its searchable generation to Long.MAX_VALUE so that waiters return, but never removes its refresh listener. One more refresh of the still-open manager writes an ordinary generation back (1 in the repro), and an untimed waitForGeneration on the closed instance then blocks until a later refresh, an interrupt or a second close(), or forever.

The finding in 30 seconds

#

The reopen thread marks itself closed by setting its searchable generation to Long.MAX_VALUE. A refresh listener it never removes overwrites that value on the next refresh of the manager.

How ControlledRealTimeReopenThread tracks what search can see

#
  1. A SearcherManager hands out searchers. maybeRefresh() or maybeRefreshBlocking() opens a newer one and calls every registered refresh listener before and after the refresh.
  2. Every IndexWriter change returns a generation number. ControlledRealTimeReopenThread refreshes the manager in the background and keeps searchingGen, the newest generation that search is guaranteed to see. A refresh listener, added to the manager in its constructor, updates it after each refresh.
  3. waitForGeneration(gen) blocks while gen > searchingGen, so a request can wait until its own change is searchable. close() stops the background thread and sets searchingGen to Long.MAX_VALUE, so that every waiter returns.

The finding, step by step

#
  1. You use a ControlledRealTimeReopenThread with a SearcherManager: after adding a document, a request calls crt.waitForGeneration(gen) to wait until search can see it. At shutdown you call crt.close(), which sets the searchable generation to Long.MAX_VALUE so that every waiter returns at once.
  2. The application refreshes the still-open manager once more, mgr.maybeRefreshBlocking(). The refresh listener that the reopen thread registered is still there and writes the writer's generation, 1, over Long.MAX_VALUE.
  3. A thread that still holds the closed instance adds a document (generation 2) and calls the untimed crt.waitForGeneration(2). You expect it to return at once, as it does when no refresh comes between close() and the wait.
  4. Instead it is still waiting after 5 s. Since 8.6.0 a later refresh that covers generation 2 releases it; if the manager is closed next, no refresh can come, and only an interrupt or a second crt.close() frees the thread (on 4.4.0-8.5.2 later refreshes do not help either). The timed overload returns false at its bound.

Who is affected

#

Users of the opt-in, experimental ControlledRealTimeReopenThread whose application refreshes the manager after (or while) closing it, for example a shutdown with a final refresh or a replacement reopen thread, while some thread still waits on the closed instance without a timeout. Nothing is corrupted or wrong; one thread parks. Contrived: no report since 2013.

Mechanism, terms and numbers585 words

ControlledRealTimeReopenThread registers a refresh listener on the ReferenceManager in its constructor and never removes it. close() stops the reopen thread and sets searchingGen = Long.MAX_VALUE ("Max it out so any waiting search threads will return"), so a wait issued after close() returns at once. But the manager is a separate object and stays open: one more refresh of it runs the leftover listener, which sets searchingGen to the writer's current generation with no check. An untimed waitForGeneration(gen) on the closed instance for a newer change then waits for a reopen that the stopped thread will never do. Since 8.6.0 a later refresh that covers gen releases it; if refreshes stop (for example the manager is closed next) only an interrupt or a second close() does, and on 4.4.0-8.5.2 no refresh releases it at all. The timed overload returns false at its bound, nothing is corrupted, no result is wrong and no lock is held. Present in every release from 4.4.0 to 10.6.0 and on main; the class it replaced, NRTManager, guarded this value.

The code (main 645d4fe14a20, ControlledRealTimeReopenThread.java)

#
manager.addListener(new HandleRefresh());                     // :85, constructor; never removed

public void beforeRefresh() {
  refreshStartGen = writer.getMaxCompletedSequenceNumber();   // :96
}
public void afterRefresh(boolean didRefresh) {                // :100, runs on EVERY refresh of the manager
  synchronized (waitingRoom) {
    searchingGen = refreshStartGen;                            // :102, no check, also after close()
    waitingRoom.notifyAll();
  }
}

public void close() {                                         // :110
  finish = true; reloadRequests.release(); join();            // :111-117, stops the reopen thread
  // Max it out so any waiting search threads will return:
  searchingGen = Long.MAX_VALUE;                               // :122-123, outside waitingRoom
  synchronized (waitingRoom) { waitingRoom.notifyAll(); }      // :126-128
}

// waitForGeneration(targetGen, maxMS), :159-187
while (targetGen > searchingGen) { if (maxMS < 0) waitingRoom.wait(); ... }   // :171-173
  • Nothing removes the listener. The class has no removeListener call. ReferenceManager calls every registered listener's beforeRefresh and afterRefresh on every refresh, from maybeRefresh() and maybeRefreshBlocking(), whoever calls them (ReferenceManager.java:154-188, listeners at :166 and :182).
  • After close() no reopen thread is left to end a wait. The reopen thread, whose loop is the class's only refresh call (:213), has exited. ReferenceManager.close() calls no listener (ReferenceManager.java:134-142), and after it every refresh throws AlreadyClosedException, so once the manager is closed only an interrupt or another close() call can release the waiter (close() has no closed-state guard: join() on the finished thread returns at once, and it writes Long.MAX_VALUE and notifies again; executed on main and 8.5.2).
  • 4.4.0-8.5.2 are worse. There the start generation was captured by the reopen thread's own loop, not in beforeRefresh (moved by the LUCENE-9304 commit 18af6325ed9, first in 8.6.0). After close() every refresh writes back the same stale value (3 on 8.5.2), so no refresh releases the waiter.
  • A refresh that starts before close() returns and finishes after it overwrites the value too (executed on 4.4.0, 8.5.2, 8.6.0, 9.12.3, 10.5.2 and main, with the waiter started afterwards). The form where a waiter that close() already woke is put back to sleep was shown only by TLA+ model checking, never executed.

Exposure and likelihood327 words
  • Who. The class is opt-in and @lucene.experimental (ControlledRealTimeReopenThread.java:36). It takes an application that refreshes the still-open manager after crt.close() (a final refresh at shutdown, or a new reopen thread on the same manager) and a thread that still holds the closed instance and calls the untimed waitForGeneration(gen) for a newer change.
  • Effect since 8.6.0 (all 9.x, 10.x, main). The thread waits until the next refresh whose start generation covers gen. With a replacement reopen thread that is extra latency (its refreshes released 16 of 16 old waiters in a probe). If refreshes stop, for example because the manager is closed next, it waits until it is interrupted or close() is called again, and forever if neither happens.
  • Effect on 4.4.0-8.5.2. No later refresh releases it; only an interrupt or a second close() does.
  • Bounded parts. The timed waitForGeneration(gen, maxMS) returns false at its bound, which its @return allows (300 ms in the probe). The parked thread holds no Lucene lock and uses no CPU; search, indexing and commit continue (13-19 ms while 16 waiters were pinned). The bug only delays a wait; it never reports a generation as visible early, so no stale or deleted data is served because of it.
  • Leak. Every closed instance stays registered on the manager and runs on every later refresh: about 400 bytes and 65 ns per refresh each (5,000 closed instances: median no-change refresh 2.8 µs -> 330 µs; approximate, one host).
  • Scale. Any index size; nothing depends on the codec or the IndexWriterConfig settings; the repro indexes one empty document.
  • Likelihood: contrived. Every executed trigger waits on an already-closed instance after an extra refresh between close() and the wait. Upstream tests never refresh the manager after closing the reopen thread (TestControlledRealTimeReopenThread.java:327-330, :408-411, :573-574, :592). A read-only code search found no use of the class in the default branches of Elasticsearch, OpenSearch or Solr, and nobody has reported it since 4.4.0 (2013).

Why it looks unintended

#
  • close() says "Max it out so any waiting search threads will return"; on main the @return of waitForGeneration covers "this instance was closed".
  • The closed state sticks: with no refresh in between, a wait after close() returns at once in every version run.
  • The predecessor NRTManager guarded this value; LiveFieldValues removes its listener in close().
The full argument342 words
  • The code says close() releases waiters: "Max it out so any waiting search threads will return" (ControlledRealTimeReopenThread.java:122, in every release since 4.4.0). On main, the @return of waitForGeneration(long, int) (added by #15830, 2026): "true if the targetGen is now available, or false if maxMS wait time was exceeded or this instance was closed. True might also be returned if this call returned due to a close()" (:155-157).
  • Sticky by design: a wait issued after close() with no refresh in between returns at once in every version run, 4.4.0 to main. Only the leftover listener undoes it.
  • The one-argument javadoc says the call blocks "until the searcher is reopened by another thread calling ReferenceManager#maybeRefresh, or until the ReferenceManager is closed" (:132-135). The shutdown sequence (one refresh, then mgr.close()) breaks even that literal text. On its own this is weak support, because closing the manager has no wake-up mechanism in any version.
  • History: NRTManager.close() set its generation to Long.MAX_VALUE from LUCENE-3488 (2011) on; LUCENE-3528 (#4602, 2011) named that closed value MAX_SEARCHER_GEN and added a guard for it in the reopen path, and LUCENE-3776 (#4849, 2012) kept the guard as if (searchingGen != MAX_SEARCHER_GEN) before writing a new generation; on LUCENE-3776, Michael McCandless called it trappy that refreshing that class's manager by another path "can unexpectedly cause threads to block forever" (a different trigger in the older class, fixed then). LUCENE-4967 (#6031, 2013) moved the tracking into the new listener without the guard, and its comments do not discuss close semantics or listener removal. Caveat: NRTManager owned its managers, so a refresh after close was also rejected there.
  • Same package: LiveFieldValues adds itself as a listener in its constructor and removes itself in close() (LiveFieldValues.java:46, :50-52). The Lucene.NET port has guarded the same write since 2017 (finish ? long.MaxValue : refreshStartGen), without describing the Java behaviour.
  • Legal trigger: nothing says the manager must not be refreshed after the reopen thread is closed; maybeRefresh: "You must call this ... periodically" (ReferenceManager.java:190-192).
The devil's-advocate check181 words

The strongest case for "intended" (the second cross-model review, the devil's-advocate verifier, the adjudication and the audit): the class is an experimental Thread whose close() is documented as "Stop this thread. Blocks until it terminates." (:108). Waiting on a closed instance while someone else keeps refreshing the manager is mixed ownership; the one-argument javadoc literally says the call blocks until another thread refreshes, which a further refresh does satisfy on 8.6.0+; and in the shutdown form the waiting thread's next acquire() would fail anyway. The audit's view: a real but minor robustness defect, not a production hang.

Why it fails: nothing documents that waits or refreshes after close() are invalid; the close() comment and, on main, the @return expect close() to release waiters; the closed state is deliberately sticky until a listener that close() never removes undoes it; the shutdown form does not honour even the one-argument javadoc's "or until the ReferenceManager is closed"; and on 4.4.0-8.5.2 no refresh releases the waiter at all. Hence the narrow claim: only the untimed overload, and "can block forever" when refreshes stop.

Suggested fix

#

Recommended Never lower the generation, publish the closed value under the monitor, and remove the listener in close() (validated)

In close(), remove the listener and write Long.MAX_VALUE under the listener's monitor; in the listener, never lower the generation (Math.max). That is +11/-5 lines in one file. The repro then passes, and so does TestControlledRealTimeReopenThread.

public void afterRefresh(boolean didRefresh) {
  synchronized (waitingRoom) {
    searchingGen = Math.max(searchingGen, refreshStartGen);
    waitingRoom.notifyAll();
  }
}
...
  manager.removeListener(refreshListener);   // in close(), after join()
  synchronized (waitingRoom) {
    searchingGen = Long.MAX_VALUE;
    waitingRoom.notifyAll();
  }

  }

...

    searchingGen = Long.MAX_VALUE;
    waitingRoom.notifyAll();

Trade-offs

  • After close() no later refresh calls the listener, and a refresh whose after-refresh loop had already taken its snapshot of the listener list can no longer lower the value. Each closed instance also stops costing memory and refresh time.
  • Math.max changes behaviour only when a refresh's start generation is lower than the current value; outside the post-close case that was not analysed beyond the upstream suite passing.
  • Removing the listener alone would not cover a refresh already in progress during close(), which is why the monotone write stays.

Downstream note

#

Downstream, this matters only to a service that closes or replaces a ControlledRealTimeReopenThread while request threads still call its untimed waitForGeneration; a read-only code search found no use of the class in Elasticsearch, OpenSearch or Solr.

How it was found

#

TLA+ model checking (TLC) of the reopen thread, waitForGeneration, close(), the refresh listener and an application thread that refreshes the same manager. TLC found a waiter that never returns when that refresh comes after close(); the trace was replayed as a public-API JUnit on the stock jar and checked by independent verifiers.

The method in full151 words

Method: formal (TLA+ model checking, the tool's own counterexample, then a public-API JUnit).

  • Model. CRT.tla models the reopen thread with its Semaphore signal (#15830), waitForGeneration's wait/notify, close(), the HandleRefresh listener and an application thread that refreshes the same ReferenceManager.
  • Counterexamples. With the application refresh allowed after close(), TLC reported a deadlock (19-state traces). With the refresh started before close() returns, it reported a violation of the invariant NoReblockAfterClose (16-state trace): a waiter woken by close() is put back to sleep. The fix models are clean (12,451 and 83,460 distinct states).
  • Confirmation. The sequential trace became a JUnit that fails on the stock main jar with assertions on and off. An independent reproducer, a devil's-advocate verifier, an adjudication and a credibility audit re-ran it or their own tests; a follow-up ran the version history, a prior-report search and a security probe. The concurrent re-block form was never executed.

Impact note
Applications on Lucene 4.4.0 through 10.6.0 or main that use the opt-in, @lucene.experimental ControlledRealTimeReopenThread and refresh the still-open ReferenceManager after (or while) the reopen thread is closed, for example in a shutdown or when they replace the reopen thread, are hit when a thread that still holds the closed instance then calls the untimed waitForGeneration(gen) for a newer change: it stays WAITING until a later refresh covers gen (only extra latency if, for example, a replacement reopen thread keeps refreshing) or forever if refreshes stop (for example when the manager is closed next), and only an interrupt or a second close() releases it; on 4.4.0-8.5.2 further refreshes do not release it either; the timed overload returns false at its bound, as documented; any index size, default IndexWriterConfig and codec; no wrong results, no lock is held, and search, indexing and commit keep working.
Summary
You use a ControlledRealTimeReopenThread with a SearcherManager, close the reopen thread (for example at shutdown), the application refreshes the still-open manager once more, and a request thread that still holds the closed instance calls waitForGeneration(gen) for its own new change. You expect the call to return, because close() sets the searching generation to Long.MAX_VALUE 'so any waiting search threads will return', the method's @return says it returns when 'this instance was closed', and a wait with no refresh in between does return at once. Instead the HandleRefresh listener that the constructor registered on the manager is never removed, so that one refresh writes the writer's generation back over Long.MAX_VALUE, and the untimed wait blocks until some later refresh covers gen, which never comes once the manager is closed; only an interrupt or a second close() releases the thread.
