IndexRearranger ignores the IndexWriterConfig it is given, except the analyzer, since 10.0.0

Since 10.0.0, IndexRearranger uses only the analyzer of the IndexWriterConfig you pass: the rearranged copy silently gets the default codec and no index sort, and a rerun with OpenMode.CREATE or an input with a soft-deletes or parent field makes it throw. A regression from #11815, in every release from 10.0.0 to 10.6.0 and on main.

The finding in 30 seconds

#

IndexRearranger copies an index into a new segment layout and takes an IndexWriterConfig. Since 10.0.0 it writes the copy with fresh configs that keep only your analyzer, so the copy gets the defaults: default codec, no index sort, CREATE_OR_APPEND, no soft-deletes or parent field, the current creation major version.

Background

#
  1. The tool. IndexRearranger copies an index into a new directory with a chosen segment layout: each DocumentSelector picks the documents of one output segment. Its javadoc's use case is benchmarking a change to indexing: index the same content twice and rearrange one copy to the shape of the other.
  2. How it writes. It adds each segment with IndexWriter.addIndexes(CodecReader...), which writes the new segment with the writer's codec and index sort. Since 10.0.0 a second writer then applies requested deletes.
  3. The config. Both constructors take an IndexWriterConfig. A config can serve only one writer, so two writers need two configs.

The finding, step by step

#
  1. You have 4 documents sorted by ord, in two segments holding ord {1, 3} and {0, 2}. You rearrange them into one segment: new IndexRearranger(in, out, new IndexWriterConfig().setIndexSort(ordSort), selectors).execute().
  2. You expect the copy to follow your config: doc order [0, 1, 2, 3] and index sort <long: "ord">, as on 8.9.0 to 9.12.3.
  3. Instead the copy has doc order [1, 3, 0, 2] and index sort null, and opening it with a writer configured with the ord sort throws IllegalArgumentException: cannot change previous indexSort=null ....
  4. Why: since 10.0.0 execute() builds both of its writers with new IndexWriterConfig(config.getAnalyzer()). Only the analyzer survives, so a configured SimpleText codec becomes the default codec, a second run with OpenMode.CREATE appends and throws, and soft-deletes or parent-field indexes are rejected.
  5. Search results on the copy stay correct and the input is only read. Using your config for the first writer again, as 9.x did, fixes it.

Who is affected

#

Callers of the experimental misc IndexRearranger on 10.0.0 to 10.6.0 and main: a configured codec or index sort is lost on every run; OpenMode.CREATE, soft-deletes, parent-field and creation-version settings fail in their own scenarios. The javadoc's own use case, benchmarking an indexing change, then measures the default codec. Search results stay correct; a default config is unaffected.

Mechanism, terms and numbers790 words

IndexRearranger (lucene/misc, @lucene.experimental) copies an index into a new directory with a chosen segment layout, and both public constructors take an IndexWriterConfig ("@param config index writer config"). Up to 9.12.3, execute() forced NoMergePolicy on that config and opened its writer with it. Since #11815 ("Support deletions in rearrange", first released in 10.0.0), execute() builds its two writers with new IndexWriterConfig(config.getAnalyzer()) and sets only NoMergePolicy, so every other setting is dropped, and the analyzer it keeps is never used by addIndexes(CodecReader...). The copy is silently written with the default codec and without the configured index sort; a second run with OpenMode.CREATE appends and fails, and an index with a soft-deletes or parent field, or one created with the previous major version, cannot be rearranged. Search results on the copy are correct and the input is only read. Executed on every 10.x release up to 10.6.0 and on main; all 29 releases from 8.9.0 to 9.12.3 (8.9.0 to 8.11.4 and the 21 9.x releases) pass the same assertions.

The code (main 645d4fe14a20, lucene/misc/src/java/org/apache/lucene/misc/index/IndexRearranger.java)

#
  1. The configs. execute() builds createSegmentsConfig and applyDeletesConfig as new IndexWriterConfig(config.getAnalyzer()) (:119-120) and sets only NoMergePolicy on each (:122-124). Nothing else reads the caller's config, which the class keeps in a protected final field (:70).
  2. The defaults they get. Codec.getDefault(), no index sort, OpenMode.CREATE_OR_APPEND, no soft-deletes or parent field (LiveIndexWriterConfig.java:135, :138), creation major Version.LATEST.major (:58).
  3. First writer (:126): addIndexes (:209) writes each segment with the writer's codec and index sort (IndexWriter.java:3525 config.getCodec(), :3540 config.getIndexSort()), so with the default codec and indexSort=null. With no index sort the merge only maps around deletions instead of sorting (MergeState.java:214-226), so two sorted input segments are concatenated: [1, 3] then [0, 2].
  4. Field checks. addIndexes validates every incoming field against the writer's config up front (IndexWriter.java:3288-3293); an input soft-deletes field or parent field is rejected because the fresh config names none (FieldInfos.java:459-467, :484-490), and so is an input segment created with another major version than the new output (IndexWriter.java:3228-3236). These checks run in the executor task that calls addIndexes, so execute() throws them as the cause of an ExecutionException (:189-198).
  5. Open mode. A second run into an existing output appends instead of replacing, so a selector then matches two segments and finalizeRearrange throws (:154-161).
  6. Opening the copy later. A writer configured with the original sort checks every segment's sort and rejects indexSort=null (IndexWriter.java:1213-1229).

In 9.x

#

execute() did config.setMergePolicy(NoMergePolicy.INSTANCE) and new IndexWriter(output, config) with the caller's config (9.12.3 IndexRearranger.java:80-82).

Exposure and likelihood283 words
  • Who. Callers of IndexRearranger who put a non-default codec, an index sort, OpenMode.CREATE, a soft-deletes field, a parent field or an older creation major in the config they pass. A configured codec or index sort is ignored on every run, with assertions on and off, at any size and with no timing condition. The other settings show only in their scenario: OpenMode.CREATE when the output already holds an index, the soft-deletes and parent fields when the input has such a field, the creation major when the input was created with an older major. A default config is not affected. The tool is experimental and in lucene/misc, so it is opt-in.
  • Silent. The copy's codec and index sort differ from the configured ones, and so does its doc order within segments. The class's own use case, testing search performance after a change to indexing, then measures the default codec instead of the configured one when the change is chosen through the config. A writer configured with the original sort cannot open the copy.
  • Loud. OpenMode.CREATE reruns, soft-deletes indexes, parent-field indexes and indexes created with the previous major fail with a clean exception. For the soft-deletes and parent fields there is no workaround through the API short of reimplementing execute() in a subclass (its helper methods are private); for the codec only the global, static Codec.setDefault.
  • Not affected. Search results on the copy, requested deletes, the input index (only read).
  • How likely: plausible. Upstream's own TestIndexRearranger and TestBinaryDocValueSelector pass a config with an index sort and OpenMode.CREATE, but the tool is little used, the codec and sort loss is invisible unless someone inspects the output, and nobody has reported it since 10.0.0.

Why it looks unintended

#
  • Both constructors take and document the config ("@param config index writer config"); on main only its analyzer is read, and addIndexes never analyzes, so the parameter has no effect.
  • Up to 9.12.3 the writer used the caller's config; #11815, CHANGES.txt and MIGRATE.md never mention dropping it.
  • Upstream's tests still pass a config with an index sort and OpenMode.CREATE.
The full argument264 words
  • Contract. "@param config index writer config" (IndexRearranger.java:85), kept in a protected final field (:70). The class javadoc's use case is testing search performance "after a change to indexing" (:57-60).
  • The tool's author on the original contract. Before 10.0, when the tool was new, Patrick Zhai, who wrote it (LUCENE-9694), told a user on java-user (2021-05-24, "Multiple merge-runs from same set of segments") that "the IndexRearranger let you pass in an IndexWriterConfig so that you could set it there", about setIndexSort.
  • Tests. TestIndexRearranger.java:209-214 and TestBinaryDocValueSelector.java:123-128 still build the config they pass with OpenMode.CREATE, NoMergePolicy and setIndexSort(ord). TestIndexRearranger's helper is unchanged from 9.x, where those settings were applied (9.12.3 TestIndexRearranger.java:123-128); TestBinaryDocValueSelector was added by #11815 itself, with the same helper. They check segment contents and live docs, never the output's sort or codec.
  • History. #11815 needed a second writer to apply deletes, and one config cannot serve two writers (IndexWriterConfig.java:125-131). Its issue (#11814), body, comments and review comments never mention the config, codec, index sort or open mode; its only compatibility remark ("This change is technically not backwards compatible") names "changes to the rearrange API" and deleted documents no longer disappearing from the rearranged index ("They become live instead"). CHANGES.txt:2210 says only "GITHUB#11814: Support deletions in IndexRearranger."; MIGRATE.md has no entry. So the loss reads as an unintended side effect; that is an inference, the authors did not say so.
  • Precedent. PKIndexSplitter in the same package solves the same two-writer problem by taking one caller config per output (PKIndexSplitter.java:62-68, LUCENE-3296, #4369).
The devil's-advocate check133 words

The strongest case: the class is @lucene.experimental; "index writer config" promises nothing about which settings apply; even 9.x overrode the merge policy; the tool's purpose is geometry (segment membership and order), which the upstream tests check; and one config cannot serve two writers, so fresh configs were a pragmatic choice.

Why it fails: the merge-policy override is required by the algorithm and commented, while dropping everything but the one setting addIndexes never uses is a choice nobody stated; #11815 lists its incompatible changes and this is not among them; the upstream tests still pass a sort and an open mode; the javadoc's own use case needs the codec kept; and PKIndexSplitter shows the two-writer constraint has a known solution. Cross-model reviews (OpenAI GPT-5.6) and an intended-behaviour verifier rated the works-as-designed case weak.

Suggested fix

#

Recommended Use the caller's config for the first writer, copy the output settings into the second (validated for the listed tests)

Open the rearrange writer with the caller's config, as 9.x did (still forcing NoMergePolicy), and give the apply-deletes writer a fresh config copying codec, similarity, index sort, soft-deletes and parent field, with OpenMode.APPEND (+18/-2). The repro and all 317 misc tests pass. Validated for the listed tests only. Caution: the caller's merge scheduler then reaches addIndexes, and commitOnClose(false) needs handling.

Use the caller's config for the first writer, copy the output settings into the second (validated for the listed tests) (recommended)

#

In execute() (IndexRearranger.java:119-120) replace the two fresh configs: the rearrange writer uses config itself, and the deletes writer gets a fresh config that carries over the output's settings. Of those, only the soft-deletes and parent fields must match when that writer opens the output (IndexWriter.java:1267-1278, FieldInfos.java:417-418), and an index sort, when one is set (IndexWriter.java:1213-1229); the codec and similarity are copied for consistency, as that writer only marks deletes. The rest of execute(), including setMergePolicy(NoMergePolicy.INSTANCE) on both configs, is unchanged.

// The caller's config writes the rearranged segments (as before the deletions support).
IndexWriterConfig createSegmentsConfig = config;
// A writer config can only be used once, so the deletes pass gets a fresh config that
// carries over the output's settings.
IndexWriterConfig applyDeletesConfig =
    new IndexWriterConfig(config.getAnalyzer())
        .setCodec(config.getCodec())
        .setSimilarity(config.getSimilarity())
        .setOpenMode(IndexWriterConfig.OpenMode.APPEND);
if (config.getIndexSort() != null) {
  applyDeletesConfig.setIndexSort(config.getIndexSort());
}
if (config.getSoftDeletesField() != null) {
  applyDeletesConfig.setSoftDeletesField(config.getSoftDeletesField());
}
if (config.getParentField() != null) {
  applyDeletesConfig.setParentField(config.getParentField());
}

Trade-offs

  • Merge scheduler. The first writer also takes the caller's merge scheduler. With NoMergeScheduler, addIndexes(CodecReader...) blocks since 9.4.0 (a separate bug in the registry, LFV-586); today's fresh configs avoid that only because they use the default ConcurrentMergeScheduler (LiveIndexWriterConfig.java:137). On 9.4.0 to 9.12.3 the tool had the same exposure (code reading).
  • Single use. As in 9.x, the caller's config is attached to the first writer and changed (setMergePolicy), so it, and the IndexRearranger holding it, can run execute() once (IndexWriterConfig.java:125-131; code reading, not executed). Today a second execute() into the same output fails anyway (the OpenMode.CREATE row above).
  • Other settings come back too. As in 9.x, the first writer also applies the caller's commitOnClose, deletion policy, setIndexCommit and setIndexCreatedVersionMajor (the last one lets an input created with the previous major be rearranged, as the 9.12.3 probe shows for 9.x; not run with the fix). With commitOnClose(false) the first writer rolls back on close (IndexWriter.java:1363-1368), so the rearranged segments are not committed before finalizeRearrange reads the output (code reading, not executed); the PR should handle it (for example reject it or commit explicitly) or document it.
  • Maintenance. The settings copied into the second config must be kept in step with new IndexWriterConfig settings that must match an existing index.

Copy the output settings into both fresh configs

#

Keep two fresh configs and copy codec, index sort, soft-deletes field and parent field into both (similarity too, for consistency); the first gets the caller's open mode and creation major version, the second APPEND.

Trade-offs

Leaves the caller's config untouched and reusable and keeps the default merge scheduler (no LFV-586 exposure). Copying only these settings is a deliberate choice, not just a list to maintain: the first writer then does not do everything the caller's config would (for example its commitOnClose, deletion policy or merge scheduler), which may be what maintainers want; settings that are not copied stay silently ignored. Not run as a separate test; option A's second config is this copy (without the creation major, which only matters when the output is created).

API change: one caller config per writer, or a Supplier<IndexWriterConfig>

#

Like PKIndexSplitter (PKIndexSplitter.java:62-68), let the caller supply a config for each writer.

Trade-offs

Fully explicit, but changes a public (experimental) API, and callers must make the two configs agree. Not run.

Document that only the analyzer is used

#

Javadoc change only.

Trade-offs

Leaves soft-deletes and parent-field indexes impossible to rearrange and the codec impossible to choose, and contradicts the upstream tests and the 9.x behaviour.

Downstream note

#

No use of IndexRearranger was found in Elasticsearch, OpenSearch or Solr; the luceneutil benchmark's BenchRearranger passes it its full writer config, codec and index sort included (code reading only).

How it was found

#

While building a round-trip harness for BinaryDocValueSelector and IndexRearranger, the finder noticed that execute() reads only the analyzer from its config. A probe of the configured settings against the output segments, and a 9.x versus 10.x run of the same tests, confirmed it on the stock jars.

The method in full117 words

Method: code reading, then executed public-API tests (the hunt classes it as non-formal).

  • Probe. A small program printed the input and output segments' codec and index sort: IN _0 ... sort=<long: "ord">, OUT _0 ... sort=null; reopening with the sort, a second run and a soft-deletes input threw.
  • Release differential. Two JUnit classes on the public API (index sort and codec; OpenMode.CREATE and soft deletes) fail 4 of 4 on main and every 10.x release, and their 9.x-API variants pass on every release from 8.9.0 to 9.12.3. A commit-level A/B on identical 9.4.2 jars pins the change to #11815.
  • The minimal repro above is the index-sort test cut down to one document and one assertion.

LFV-695, snapshot of 2026-11-05

Registry title
Since 10.0.0 IndexRearranger keeps only the analyzer from the IndexWriterConfig it is given, so the rearranged index loses the configured codec and index sort, OpenMode.CREATE is ignored, and an index with a soft-deletes or parent field cannot be rearranged
Area
misc / index tools (IndexRearranger.execute: writer configs of the rearrange pass and the apply-deletes pass)
Priority
Low, rank 662: Since 10.0 the experimental misc IndexRearranger drops the given config's codec and index sort and fails loudly on CREATE, soft-deletes and parent-field inputs while query results stay correct, a slightly broader released sibling of LFV-618.
Impact class
minor
Impact note
Hits callers of the experimental lucene/misc IndexRearranger on 10.0.0 through 10.6.0 (10.6.0 executed) and main who put a non-default setting in the IndexWriterConfig they pass, on every run, with -ea and -da and no scale or timing condition: the rearranged copy is silently written with the default codec and without the configured index sort (so its documents are not in sort order and a writer configured with that sort refuses to open it), a second run into the same output with OpenMode.CREATE appends and throws IllegalStateException, and an input with a soft-deletes or parent field is rejected with IllegalArgumentException with no workaround through the API; query results on the copy are correct and the input index is only read.
Summary
You rearrange an index with IndexRearranger and pass an IndexWriterConfig that sets, for example, a codec, an index sort, OpenMode.CREATE or a soft-deletes field, and expect the rearranged index to be written and opened with those settings, as it was from 8.9.0 through 9.12.3. Instead, since 10.0.0 execute() builds both of its writers with new IndexWriterConfig(config.getAnalyzer()) and sets only NoMergePolicy, so the output silently uses the default codec and has no index sort, a second run with OpenMode.CREATE appends and fails with IllegalStateException ('Document selector ... has matched more than 1 segments'), and an input with a soft-deletes or parent field fails with IllegalArgumentException ('soft-deletes field is not configured in IWC', 'this IndexWriter has no parent document field configured').
