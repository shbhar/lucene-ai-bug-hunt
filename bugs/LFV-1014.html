The finding in 30 seconds

#

Rectangle is Lucene's lat/lon box. Its constructor rejects a bad coordinate with IllegalArgumentException, but it checks that minLat <= maxLat only with a Java assert, which the JVM skips unless it was started with -ea.

Background: lat/lon boxes and asserts

#
  1. new Rectangle(minLat, maxLat, minLon, maxLon) is a lat/lon box. minLon > maxLon is allowed and means the box crosses the dateline; no inversion of latitude is documented.
  2. LatLonShape.newBoxQuery and newSlowDocValuesBoxQuery build a Rectangle from their four arguments, and so does SimpleWKTShapeParser for the text ENVELOPE(minLon, maxLon, maxLat, minLat). LatLonPoint.newBoxQuery builds none.
  3. A Java assert runs only when the JVM is started with -ea; a JVM started without the flag skips every assert. Lucene's gradle test runs enable assertions for about 75% of seeds by default (tests.asserts, since #15325).

The finding, step by step

#
  1. Index four polygons, at latitudes 0..20, 6..8, 12..15 and 1..3. Query the box between latitudes 5 and 10, but pass the two latitudes swapped: LatLonShape.newBoxQuery("shape", INTERSECTS, 10, 5, 0, 1), that is minLatitude 10 and maxLatitude 5.
  2. You expect IllegalArgumentException: what new XYRectangle(0, 1, 10, 5) gives ("minY must be lower than maxY, got 10.0 > 5.0"), and what Rectangle itself gives for latitude 95.
  3. With assertions on (-ea; Lucene's gradle tests enable them for about 75% of seeds) you get a bare AssertionError, no message, from Rectangle.<init>. The same for new Rectangle(10, 5, 0, 1) and for the WKT text ENVELOPE(0, 1, 5, 10).
  4. With assertions off (the JVM default) the box is accepted. INTERSECTS returns 1 polygon, lat 0..20, the only one that crosses both latitude lines. The correctly ordered box returns 2 (lat 6..8 and 0..20), and LatLonPoint.newBoxQuery with the same swapped box returns 0 hits.
  5. Why: the Rectangle constructor rejects an out-of-range coordinate with IllegalArgumentException, but checks the latitude order only with assert maxLat >= minLat. It has done so since the class first shipped, in 5.4.0 (2015).

Who is affected

#

Callers of the core lat/lon box APIs (new Rectangle, LatLonShape.newBoxQuery, newGeometryQuery with a Rectangle, WKT ENVELOPE) that pass swapped latitudes, for example user-entered corners forwarded unchecked. Default settings, every release since 5.4.0. Valid boxes are not affected and nothing is stored. Rare: the recorded searches found no public report since 2015.

Mechanism, terms and numbers533 words

org.apache.lucene.geo.Rectangle(minLat, maxLat, minLon, maxLon) range-checks each coordinate with GeoUtils.checkLatitude / checkLongitude, which throw IllegalArgumentException, but checks the latitude order only with assert maxLat >= minLat (Rectangle.java:94 on main 645d4fe14a20). A box with swapped latitudes, built directly, through LatLonShape.newBoxQuery or newSlowDocValuesBoxQuery, for newGeometryQuery, or from a WKT ENVELOPE(minLon, maxLon, maxLat, minLat), therefore throws a bare AssertionError with assertions on and is accepted with assertions off. A LatLonShape box query then returns hits that match no region: neither the empty result that LatLonPoint.newBoxQuery gives for the same box nor the result of the correctly ordered box. The Cartesian twin XYRectangle had the same assert until LUCENE-9218 (8.5.0) made it throw IllegalArgumentException; Rectangle was not changed. The input is invalid, so this is missing validation, not a wrong answer to a valid query. Every release from 5.4.0 to 10.6.0 is affected; a one-line check in the constructor fixes it.

Terms

#
  • Rectangle (org.apache.lucene.geo): "A rectangle is defined by its minimum and maximum latitude/longitude coordinates. It can cross the dateline, in which case minLon > maxLon" (Rectangle.java:38-39). The fields are "Minimum latitude" and "Maximum latitude" (:67-71).
  • XYRectangle: the same box on a flat (Cartesian) plane, used by XYShape.
  • -ea / -da: JVM flags that turn Java assert statements on or off; off is the default.

The bug

#
  1. The constructor calls GeoUtils.checkLatitude(minLat), checkLatitude(maxLat), checkLongitude(minLon) and checkLongitude(maxLon) (Rectangle.java:86-89); each throws IllegalArgumentException for an out-of-range value. The only check of the order is assert maxLat >= minLat; (:94).
  2. LatLonShape.newBoxQuery (LatLonShape.java:258) and newSlowDocValuesBoxQuery (:283) pass the caller's four values straight into the constructor; SimpleWKTShapeParser.parseBBox reads ENVELOPE(minLon, maxLon, maxLat, minLat) and does the same (SimpleWKTShapeParser.java:252-264).
  3. With -ea that assert throws a bare java.lang.AssertionError with no message. With -da the box Rectangle(lat=10.0 TO 5.0 lon=0.0 TO 1.0) is kept as is.
  4. The shape query encodes it unchanged (LatLonShapeBoundingBoxQuery.java:240-246: min latitude 10, max latitude 5). Its point test y < minY || y > maxY (SpatialQuery.java:824-827) is then true for every latitude, so no vertex is ever inside, and its triangle test drops every triangle that does not reach both above 10 and below 5 (:864-869). INTERSECTS keeps only shapes that cross both latitude lines; DISJOINT returns the rest.
  5. LatLonPoint.newBoxQuery builds no Rectangle: it encodes the range from latitude 10 up to 5, which is empty, so it returns 0 hits with -ea and -da (LatLonPoint.java:243-244).
  6. XYRectangle checks the same order with if (minY > maxY) throw new IllegalArgumentException("minY must be lower than maxY, got ...") (XYRectangle.java:41-44), and the same for X.

Exposure and likelihood256 words
  • Who is hit. Any caller of new Rectangle, LatLonShape.newBoxQuery / newSlowDocValuesBoxQuery, LatLonShape or LatLonPoint.newGeometryQuery with a Rectangle, or SimpleWKTShapeParser.parse of an ENVELOPE, that passes minLat > maxLat. Possible sources: box corners from a user or a map that the application forwards without ordering them, or WKT text, whose ENVELOPE(minLon, maxLon, maxLat, minLat) puts the two latitudes the other way round from the constructor's minLat, maxLat. How often this happens was not measured.
  • Default or opt-in. Default: no setting, any codec, any index. -da is the JVM default. Lucene's gradle test runs enable assertions for about 75% of seeds by default (tests.asserts, randomized since #15325, TestsAndRandomizationPlugin.java:240-249).
  • Effect with -da. No error and a hit set with no meaning: not empty (what the point queries return) and not the correctly ordered box. A bug in the caller's own box code goes unnoticed.
  • Effect with -ea. A bare AssertionError with no message. It is an Error, so catch (IllegalArgumentException e) and catch (Exception e) do not see it.
  • Scale. One invalid query at a time. Valid boxes are not affected, and nothing is written to the index.
  • How likely: rare. Two public records show a caller's own computation building such a box, both caught by the assert in tests: a CI failure posted on LUCENE-9552 (#10591), inside Lucene (quantization of a very thin box), and elastic/elasticsearch#32857 (an overflow in that project's geohash code). The recorded searches found no public report of the missing check itself since 5.4.0.

Why it looks unintended

#
  • XYRectangle had the same assert until LUCENE-9218 (8.5.0) replaced it with IllegalArgumentException("minY must be lower than maxY ..."); Rectangle was not changed.
  • The constructor already throws IllegalArgumentException for every out-of-range coordinate, and spatial3d GeoRectangle and sandbox LatLonBoundingBox reject minLat > maxLat.
  • No test or Lucene caller uses an inverted latitude, and the -da hits match no reading of the box.
The full argument313 words
  • The twin was changed on purpose. XYRectangle shipped in 8.2.0 with assert minX <= maxX; assert minY <= maxY; (sandbox, through 8.4.1). LUCENE-9218 (#10258, apache/lucene-solr#1252, Ignacio Vera, 4a54ffb553a on main and ca3319cdbce on branch_8x, in 8.5.0) replaced both with IllegalArgumentException. Neither the issue nor the PR mentions Rectangle. TestXYRectangle.java:36 documents the rule as "maxY must be gte minY" (in a method whose name does not start with test, so it never runs: LFV-1013).
  • Same class, other checks. Rectangle throws IllegalArgumentException for latitude 95 ("invalid latitude 95.0; must be between -90.0 and 90.0", GeoUtils.java:87).
  • Siblings. spatial3d GeoRectangle throws "Top latitude less than bottom latitude" (GeoRectangle.java:111-112); sandbox LatLonBoundingBox throws "cannot have minLat [..] exceed maxLat [..]" (LatLonBoundingBox.java:124-128); Polygon and Line validate their arguments with IllegalArgumentException (Polygon.java:66-90, Line.java:55-64).
  • Tests and callers. No upstream test passes an inverted latitude; the test framework's random boxes swap the latitudes to avoid one (GeoTestUtil.java:495-499). The Lucene callers reviewed build ordered boxes, and GeoEncodingUtils.createSubBoxes returns an empty grid for a box that quantization inverts before it builds any Rectangle (GeoEncodingUtils.java:237-240; the guard dates from LUCENE-7661, 2017, and has run on the four doubles, before any Rectangle, since LUCENE-9641, 2021).
  • No meaning. With -da the shape hits are neither empty (the point paths), nor those of the ordered box, nor a pole-crossing reading (which would match the lat 12..15 and 1..3 polygons).
  • Direction. #16919 (merged 2026-10-28) turned other AssertionErrors on reachable bad input into regular exceptions; it touched no geo file.
  • Not a promise in the javadoc. "Constructs a bounding box by first validating the provided latitude and longitude coordinates" (Rectangle.java:82-84) was added in 2016 (89db4950b9e2, LUCENE-7015), when the constructor already had its four range checks and only the assert for the order; it does not say the order is checked.
The devil's-advocate check205 words

The case (the read-only cross-model refute review, OpenAI GPT-5.6, and the intended-behaviour devil's advocate). minLat > maxLat is outside the documented domain: only minLon > maxLon is allowed, for the dateline. The assert states a programmer precondition, and behaviour after a broken precondition is unspecified. LatLonShape.newBoxQuery documents no @throws. LatLonPoint.newBoxQuery documents @throws IllegalArgumentException for "invalid coordinates" (LatLonPoint.java:218) and still returns an empty result for this box, so "empty" could be called the de facto answer. In 2015 only computed boxes reached GeoRect; user-supplied bounds came later (the shape box query builds a Rectangle since 7.7.0, LUCENE-8605). SimpleWKTShapeParser came in as a simple utility for tests (LUCENE-8538).

Why it fails. It shows the input is invalid, which the report concedes; it does not show that an AssertionError or silent acceptance is the right answer to invalid input on a public API. The maintainers chose IllegalArgumentException for the identical assert in the twin, the constructor throws it for every other bad coordinate, and the -da hits match neither the empty answer of the point paths nor any other reading. The refute reviewer itself called the exception "reasonable API hardening" and the split "a real defensive-validation inconsistency". Expect it to be triaged as hardening.

Suggested fix

#

Recommended Throw IllegalArgumentException in the Rectangle constructor

Throw IllegalArgumentException in the Rectangle constructor when minLat > maxLat and drop the assert (one file, +4/-1), as XYRectangle does. Validated on main: the repro passes with assertions on and off, and so do the geo and lat/lon test suites. Side effect: LatLonPoint.newGeometryQuery (INTERSECTS) with such a box now throws instead of matching nothing.

GeoUtils.checkLongitude(maxLon);
if (minLat > maxLat) {
  throw new IllegalArgumentException(
      "minLat must be lower than or equal to maxLat, got " + minLat + " > " + maxLat);
}
this.minLon = minLon;
this.maxLon = maxLon;
this.minLat = minLat;
this.maxLat = maxLat;
// removed: assert maxLat >= minLat;

Throw IllegalArgumentException in the Rectangle constructor (validated by the checks) (recommended)

#

In Rectangle(double, double, double, double), after the four range checks (1 file, +4/-1). The finder's fix; the same check XYRectangle has had since 8.5.0.

Trade-offs

  • Fixes every path at once: the constructor, both LatLonShape box factories, newGeometryQuery with a Rectangle and the WKT ENVELOPE. Matches XYRectangle, the constructor's own range checks and the sibling boxes.
  • Behaviour change: LatLonPoint.newGeometryQuery(field, INTERSECTS, new Rectangle(10, 5, ...)) now throws where -da gives 0 hits today (the intended-behaviour check's probe; other relations not run); with -ea it already threw AssertionError.
  • LatLonPoint.newBoxQuery and LatLonDocValuesField.newSlowBoxQuery keep returning 0 hits for the same box, because they never build a Rectangle; making them throw too would change an existing public call and is not proposed.
  • No internal caller was found that would start throwing: the Lucene callers reviewed build ordered boxes, the quantized case of LUCENE-9552 returns an empty grid before any Rectangle is built (GeoEncodingUtils.java:237-240), and the 351 tests pass. That covers the reviewed paths, not every caller.
  • Cost: one double comparison next to the four range checks the constructor already runs (also on the shape doc-values path, LatLonShapeDocValues.computeBoundingBox); not benchmarked.
  • A CHANGES entry would be usual; none is drafted.

Treat the inverted box as empty in the LatLonShape box factories

#

Return a no-match query from LatLonShape.newBoxQuery and newSlowDocValuesBoxQuery when minLatitude > maxLatitude, as the point path effectively does and as LUCENE-9552 chose for quantized boxes. Not built.

Trade-offs

Consistent with the point queries, but new Rectangle(10, 5, ...), the WKT ENVELOPE and newGeometryQuery still accept the box silently with -da or throw AssertionError with -ea, and the relations need care: DISJOINT with an empty box should match every shape, not none.

Check the order only in the callers

#

Throw in LatLonShape.newBoxQuery, newSlowDocValuesBoxQuery and SimpleWKTShapeParser.parseBBox. Not built.

Trade-offs

Leaves new Rectangle itself assert-only, so direct users and newGeometryQuery are not covered.

Document the precondition only

#

Add an @throws or a note to the constructor without changing behaviour. Not built.

Trade-offs

Assertions-off callers still get silent acceptance and meaningless hits.

Downstream note

#

Applications that forward user-entered box corners or WKT envelopes to these APIs should order or check the latitudes themselves until a fix ships; with assertions off nothing else catches the swap.

How it was found

#

A scan of public and protected methods whose only check of an argument is an assert (430 rows on main) flagged the Rectangle constructor. Running it next to its validating twin XYRectangle and the point query LatLonPoint.newBoxQuery on the stock jars showed the AssertionError and the silent -da acceptance; the WKT path came from the constructor's callers.

The method in full121 words

Method: non-formal (a source-level static scan plus differential testing, no model or bounded-exhaustive check). The hunt's hunt unit for assert-only input checks, a follow-up to #16919, ran on main 645d4fe14a20 on 2026-10-29.

  • Scan. A source scanner listed public and protected methods whose only check of a parameter is an assert: 430 rows.
  • Differential run. On the stock jars, Rectangle against XYRectangle / XYShape.newBoxQuery and against LatLonPoint.newBoxQuery: an IllegalArgumentException on the Cartesian side, a bare AssertionError (-ea) or silent acceptance (-da) on the lat/lon side, 0 hits on the point side.
  • Callers. Grepping the constructor's callers added newSlowDocValuesBoxQuery and the WKT ENVELOPE path.
  • Reduction. The finder's 3-test JUnit was reduced to the one-line constructor test above.

LFV-1014, snapshot of 2026-11-10

Registry title
geo.Rectangle checks minLat <= maxLat only with an assert, so a lat/lon box with swapped latitudes (new Rectangle, LatLonShape.newBoxQuery, a WKT ENVELOPE) throws a bare AssertionError with -ea and is silently accepted with -da, where LatLonShape box queries then return hits that match no region; the Cartesian twin XYRectangle throws IllegalArgumentException for the same mistake
Area
core / geo Rectangle (LatLonShape box queries, newGeometryQuery(Rectangle), SimpleWKTShapeParser ENVELOPE)
Priority
Low, rank 435: With assertions off, core LatLonShape box and WKT ENVELOPE queries silently accept swapped latitudes and return meaningless hits only when the caller passes an invalid box.
Impact class
wrong error
Impact note
Any caller of the public lat/lon box APIs (new Rectangle, LatLonShape.newBoxQuery and newSlowDocValuesBoxQuery, LatLonShape or LatLonPoint newGeometryQuery with a Rectangle, SimpleWKTShapeParser ENVELOPE) that passes swapped latitudes, with the default configuration, in every release since 5.4.0: an IllegalArgumentException is due, but with -ea they get a bare AssertionError and with -da (the production default) the invalid box is accepted and shape queries return hits that match no region; valid boxes are not affected and nothing is persisted.
Summary
You build a lat/lon box with the minimum and maximum latitude swapped, for example LatLonShape.newBoxQuery(field, INTERSECTS, 10, 5, 0, 1) or the WKT text ENVELOPE(0, 1, 5, 10), and expect an IllegalArgumentException, as XYRectangle gives for the same mistake and as Rectangle itself gives for an out-of-range latitude. Rectangle's constructor checks the order only with 'assert maxLat >= minLat', so with assertions enabled you get a bare AssertionError, and with assertions disabled the inverted box is accepted. The shape query then matches only shapes that cross both latitude lines (INTERSECTS) or the complement of those (DISJOINT), which is neither the empty result that LatLonPoint.newBoxQuery gives for the same box nor the result of the swapped box.
