The finding in 30 seconds

#

The limits first. The class is an experimental utility of the sandbox module, and a code search found no application that calls it. The failure is loud: an exception, no wrong result, nothing written. IndexSearcher.search with the same collector manager returns the result. The replay was right in the runs in which every segment has the field.

Background: three pieces

#
  1. A search feeds its hits to a Collector segment by segment: the loop asks the collector for a LeafCollector per segment (getLeafCollector) and hands it the segment's hits, one by one (collect(doc)) or several in one call.
  2. A collector can end a segment early by throwing CollectionTerminatedException. The search loop of IndexSearcher catches it and goes on with the next segment.
  3. Two-step faceting: a FacetsCollector first keeps the hits of a search, one record per visited segment. The sandbox class PostCollectionFaceting then replays those hits into other collectors. It is a second loop that feeds collectors, beside the one of IndexSearcher.

The finding, step by step

#
  1. Index two segments of one document each (NoMergePolicy keeps them apart): the first document has the numeric doc-values field price = 5, the second has no price.
  2. Search with MatchAllDocsQuery through the stock FacetsCollectorManager, then replay the kept hits into a histogram: new PostCollectionFaceting<>(new HistogramCollectorManager("price", 10), hits, null).collect().
  3. You expect the histogram {0=1}: bucket 0 (prices 0 to 9) holds one document. IndexSearcher.search with a HistogramCollectorManager("price", 10) returns exactly that on the same index (run).
  4. Instead collect() throws org.apache.lucene.search.CollectionTerminatedException: unchecked, no message, no stack trace, with assertions on and off. No histogram is returned, so the count of the first segment is lost with it. No wrong result is returned and nothing is written.
  5. Why: the histogram collector declines a segment whose field infos lack the field by throwing that exception from getLeafCollector. The search loop of IndexSearcher catches it and goes on with the next segment. The replay loop has no such handler, neither there nor around collect. With price in both segments (5 and 25) the replay returns {0=1, 2=1}, as the search does.

Who is affected

#

An application that computes facets in a second step through this experimental sandbox class and replays into a collector that ends a segment early. With the sandbox histogram collector the trigger is data: a segment whose field infos lack the histogram field. The call throws; no wrong result, nothing written. A code search found no application that calls it. Rare.

The limits first.

  • An experimental utility of the sandbox module. PostCollectionFaceting is in org.apache.lucene.sandbox.facet.utils, a package marked @lucene.experimental, and in the sandbox jar since 10.4.0. No application that calls it was found (a search of public code on 2026-11-22), and Lucene's own tree names the class in its file and its test only.
  • The failure is loud. An unchecked exception that carries no stack trace comes out of collect() and no result is returned. No wrong result is returned and nothing is written to the index.
  • IndexSearcher.search with the same collector manager on the same index returns the result.
  • The replay was right in the runs in which every segment has the field. So a small test index can hide it.
  • Two stock collectors were run. The sandbox HistogramCollectorManager: its collector declines a segment whose field infos lack the histogram field by throwing the exception from getLeafCollector. The trigger is the data (in the runs, a segment in which no document was indexed with the field), not a setting. And core's TopFieldCollectorManager on an index sorted by its sort, which throws from collect: an unusual collector for a faceting step, run as evidence for the second place without a handler, not as a use case.
  • Each release that has the class has it. A first form of the test fails on each release from 10.4.0 to 10.6.0 and on builds of branch_11x and main. The test of this page fails on the 10.6.0 release jars and on builds of branch_11x and main and, in later runs, on the 10.4.0, 10.5.0, 10.5.1 and 10.5.2 release jars.

You index two segments, of which only the first has a document with the numeric doc-values field price, collect the hits of a match-all search into a FacetsCollector and replay them with the sandbox class PostCollectionFaceting into a HistogramCollectorManager("price", 10). You expect the histogram {0=1}, which IndexSearcher.search returns for the same manager on the same index. Instead collect() throws CollectionTerminatedException, an unchecked exception without a stack trace, with and without assertions. The histogram collector declines the segment without the field by throwing that exception from getLeafCollector; the search loop of IndexSearcher catches it and goes on with the next segment; the replay loop has no such handler (nor one around collect), so the exception reaches the caller and no histogram is returned.

With the histogram collector the replay threw in each shape that was run with such a segment in a replayed slice: with a hit in that segment and without one, as the first and as the second of two segments, in an index of one segment in which no document has the field (the search returns an empty histogram there), with an executor given, and with the manager as the collector of a drill-sideways dimension, where the count of the drill-down collector beside it is lost too. These shapes were run on the 10.4.0 and 10.6.0 release jars and on builds of branch_11x and main. With the test's two hits the executor ran nothing: the one replay task ran on the calling thread. A later run with two slices had the collector throw on a pool thread, and the same exception reached the caller of collect().

The two calls without a handler came with the class (#15518, merged 2026-01-12, first released in 10.4.0). No report of this defect was found. The same omission in core's CachingCollector#replay is a separate finding, LFV-154. A handler at the two calls, as the search loop has them, makes the test pass; with it the sandbox module's tests show no failure (426 tests, 72 of them skipped by Lucene itself) and the module's check passes.

Why it looks unintended

#
  • The class calls itself "the second step of two-step collection"; a search with the same manager returned the result.
  • A leaf collector may end a segment by this exception; the sandbox's histogram collector does so on ordinary data.
  • The limit: the javadoc names IndexSearcher as the one swallowing it and covers no throw from getLeafCollector; the replay never calls setWeight.
The full argument775 words
  • What the class says of itself. "Performs post-collection faceting by replaying collected documents through drill-down and drill-sideways collectors" and "this class implements the second step of two-step collection" (PostCollectionFaceting.java:38-44 at main b5a4546a5964). Its constructors take a CollectorManager, and the javadoc names no limit on which one (:68, :116). In the runs IndexSearcher.search with the same manager on the same index returns {0=1}.

In this case, the last docs of the current {@link org.apache.lucene.index.LeafReaderContext} will be skipped and {@link IndexSearcher} will swallow the exception and continue collection with the next leaf." (lucene/core/src/java/org/apache/lucene/search/LeafCollector.java:76-79).
  • The sandbox's own collector uses the exception on ordinary data. HistogramCollectorManager is a public class of the same module; its collector throws for a segment whose field infos lack the field (HistogramCollector.java:70-74).
  • The one input limit the class knows is reported by name. A collector that needs scores when none were kept gets IllegalStateException("Collector requires scores, but FacetCollector doesn't have them.") (:345-349). The exception of this finding has no message and no stack trace.
  • The tests of the sandbox module do not name the exception. No file under lucene/sandbox/src/test holds its name (a word search at main b5a4546a5964). The limit of this argument.

  • The javadoc of the exception reads, whole: "Throw this exception in {@link LeafCollector#collect(int)} to prematurely terminate collection of the current leaf." and "Note: IndexSearcher swallows this exception and never re-throws it. As a consequence, you should not catch it when calling the different search methods that {@link IndexSearcher} exposes as it is unnecessary and might hide misuse of this exception." (lucene/core/src/java/org/apache/lucene/search/CollectionTerminatedException.java:19-26 at main b5a4546a5964; the same file at the 10.6.0 release tag). It names LeafCollector#collect(int) as the place to throw and IndexSearcher as the one that swallows. It says nothing of another class that feeds collectors.
  • No javadoc sentence covers a throw from getLeafCollector, which is the place the test meets: Collector.java does not name the exception. Christoph Kaser wrote the same in 2015 in LUCENE-6326 ("even though this is not documented in the JavaDoc"), and on the java-user list András Péteri asked on 2015-03-02 whether that throw is "an implementation detail"; Adrien Grand answered: "It feels useful to me too, I think we should document this behaviour."
  • The javadoc of PostCollectionFaceting has no sentence on the exception, the package is experimental, the thread of #15518 (its description, 2 comments, 2 review comments and 3 reviews, as read on 2026-11-22) has no word on early termination, and core's CachingCollector#replay passes the exception on as well (the separate finding LFV-154).
  • The replay does not drive a collector as a search does in every respect. A search calls collector.setWeight(weight) before it visits a segment (IndexSearcher.java:790), a hook "to have access to {@link Weight#count} from {@link Collector#getLeafCollector}" (Collector.java:58-63); the replay class has no such call. The histogram collector uses the weight: with one it can count a segment through the point tree and then ends the segment by the same exception (HistogramCollector.java:87-99); in a replay its weight is null and that path is not taken. Run with price as doc values and as points in both segments: the search's collector threw from getLeafCollector of both segments, the replay collected hit by hit, and both returned {0=1, 2=1}. That the replay returns what the search returns is said on this page of the shapes that were run and of no other.
The devil's-advocate check319 words

The strongest case for "works as designed": the only sentences that say who handles the exception name IndexSearcher ("IndexSearcher swallows this exception and never re-throws it"; "IndexSearcher will swallow the exception and continue collection with the next leaf"). PostCollectionFaceting is not IndexSearcher. For a throw from getLeafCollector there is no javadoc sentence at all. The class is a sandbox utility in a package tagged @lucene.experimental, its javadoc promises no equality with a search, it is no complete search either (it never calls Collector#setWeight), and upstream's test replays into collectors that never end a segment. So one could say: a caller that replays into a collector that ends segments has to deal with the exception itself.

Why it does not carry the case: a caller that catches the exception has no result. collect() reduces and returns only after every slice was replayed, so once the exception is out nothing is returned, also not for the segments that were replayed. With the histogram manager the outcome follows from the data: whether the call throws depends on the field infos of each segment, which the caller would have to read for every segment before each call. The exception reaches the caller without a message and without a stack trace; the comment at its fillInStackTrace() reads "never re-thrown so we can save the expensive stacktrace", and its javadoc says of IndexSearcher that it "never re-throws it". The one limit the class does know it reports by name. And the javadoc's two sentences named IndexSearcher already at the commits that repaired the same kind of omission in MultiCollector (2015) and in SuggestIndexSearcher (2023). What the argument does bound is the weight: an experimental helper, a loud failure, no known caller. That is why the finding is Low, and why this page does not speak of a documented contract. Whether a replay loop has to handle the exception is the maintainers' call.
