ImpactsSource#advanceShallow javadoc omits that the current document must not be read after a shallow advance past it

After advanceShallow(target) into a later block, the current document's positions and docIDRunEnd() come from another block, and reading its freq() makes the next legal advance(256) return 261. The codec behaviour is intended; the javadoc never forbids these reads and the test framework never checks them.

The finding in 30 seconds

#

The shallow advance moves the reader's streams to the target block but leaves the document and its decoded buffers on the old block until the next nextDoc()/advance(). Reads of the current document in between mix the two.

Background: block-max scoring and advanceShallow

#
  1. A term's postings are stored in blocks of 256 documents. Each block also stores its "impacts": the best (frequency, length norm) pairs inside it, from which a scorer derives the block's maximum possible score.
  2. ImpactsEnum.advanceShallow(target) moves only to the block that contains target, so that getImpacts() describes it. The iterator's docID() does not change.
  3. If that block cannot produce a competitive hit, the scorer skips it with advance(); if it can, it advances into it. After a shallow advance past the current document, Lucene's own scorers move the iterator before reading a document's data again.

The finding, step by step

#
  1. You index 1,200 documents that all contain t, take an ImpactsEnum from TermsEnum#impacts, and call nextDoc(): you are on doc 0. The postings are stored in blocks of 256 documents.
  2. You call advanceShallow(256) to peek at the next block's score bounds; docID() stays 0. The javadoc now forbids only nextDoc() jumps and advance() targets below 256.
  3. You read freq() of doc 0 (it returns 1, correct) and call advance(256). Every document has t, so you expect 256.
  4. You get 261. The peek had already moved the reader's file position into block 1; the lazy freq() seeked back to block 0's freqs and left the position at the start of block 1's skip data, so the next refill decoded those bytes as doc ids. Without the freq() call: 256.
  5. In two 4,000-document variants, other reads of the current document go wrong too: with t in every third document, a position of 5 instead of 0; with t in docs 0-255 and then in every third document, a docIDRunEnd() of 3328 although doc 256 does not match. Lucene's own queries never read in this order.

Who is affected

#

Only code that drives an ImpactsEnum (or a TermScorer) itself for custom block-max scoring and reads the current document after peeking ahead: it gets silently wrong data or a wrong next document. Default codec, every release since 8.0.0. Stock queries, scorers and CheckIndex move the iterator after such a peek before reading.

Mechanism, terms and numbers737 words

ImpactsSource#advanceShallow(target) lets a caller look at score upper bounds for documents at or after target while docID() stays where it is. Its javadoc lists what becomes illegal afterwards (nextDoc() while docID() < target - 1, advance() below target) and says nothing about the current document. The default codec, however, moves its internal streams to the target block during the shallow advance and refills only at the next nextDoc()/advance(). So code that follows the written contract and reads the current document after peeking ahead gets another block's positions or run end, and a lazily decoded freq() (whose value is still right) breaks the next legal advance(): in the repro, advance(256) returns 261 although every document contains the term.

The codec side is intended (the javadoc calls the shallow advance "cheaper than calling advance", and no checked in-tree caller reads the current document after a shallow advance past it without moving first; AssertingScorer already rejects the Scorer-level form). What is missing is the precondition in the javadoc and a check in the test framework's AssertingImpactsEnum, which passes freq() and nextPosition() through and whose eager freq() hides the symptom from randomized tests. The gap exists in every release from 8.0.0 to 10.6.0 and on main.

The mechanism (main 645d4fe14a20, Lucene104PostingsReader.BlockPostingsEnum)

#
  1. Freqs are decoded lazily. A full-block refill decodes the doc ids, remembers where the block's freqs start (freqFP) and skips over them (Lucene104PostingsReader.java:626-631); freq() seeks back and decodes them on first use (:581-589). After nextDoc() on doc 0, the doc stream sits at the start of block 1's skip data (skip data is stored in front of each block).
  2. The shallow advance moves the streams, not the document. advanceShallow(256) sees target > level0LastDocID (255) and runs doAdvanceShallow / skipLevel0To, which reads block 1's skip data from the doc stream (and, with positions, seeks the position stream), then sets needsRefilling = true (:879-895, :818-876). doc and the decoded buffers stay on block 0. The field comment: "true if we shallow-advanced to a new block that we have not decoded yet" (:406-407).
  3. The lazy freq() moves the doc stream back. It seeks to block 0's freqs and decodes them: the value for doc 0 is right (1), but the stream is left at block 1's skip header again.
  4. The next legal advance() decodes the wrong bytes. advance(256) refills because needsRefilling is set (:924-931), from the current stream position, so it reads the skip header as the block's bits-per-value byte and packed doc deltas (:591-596) and lands on 261.
  5. Other reads. nextPosition() reads the position stream, which already points at the target block; docIDRunEnd() combines the old block's dense bit set with the moved level bounds (:1099-1129); that path exists only when the current block is a fully dense bit set (UNARY encoding), otherwise the default one-doc run is returned, which is correct. The study's security probe also saw intoBitSet() not return within 20 s (5 of 6 cases) and nextPostings() skip matches with assertions off; nextPostings starts with assert needsRefilling == false (:1036).

Why tests never see it

#

For nextDoc()/advance(), AssertingImpactsEnum checks only the two documented limits (AssertingLeafReader.java:701-713) and passes freq() and nextPosition() straight through (:671-679). Its inner AssertingPostingsEnum calls freq() eagerly in every nextDoc()/advance() (:502, :521), which decodes the freqs before any shallow advance: through the wrapper, the repro's advance(256) returns 256 and no assertion fires. SlowImpactsEnum keeps the current document valid.

The numbers

#
  • Minimal repro (1,200 docs, all with t, freq 1 to 5): advance(256) after freq() returns 261; without freq(), 256.
  • Study tests (two 4,000-document indexes, advanceShallow(3000)): with t in every third document, positions of doc 0 [5] instead of [0], of doc 3 [2, ...] instead of [1, 4], and freq() then advance(3000) = 3005, a document without t; with the term in docs 0-255 (one dense block) and then in every third document, docIDRunEnd() from doc 0 = 3328 although doc 256 does not match.
  • Other layouts: EOFException, IndexOutOfBoundsException, or a doc id beyond maxDoc (2897 with 1,200 docs on 9.12.x).
  • One level up, a TermScorer in TOP_SCORES mode: advanceShallow(256), score(), then advance(256) also returns 261 (AssertingScorer rejects that score() with SHALLOW_ADVANCING).
Exposure and likelihood240 words
  • Who. Code that uses ImpactsEnum directly (from the public TermsEnum#impacts, TermsEnum.java:172-177) and reads freq(), positions, docIDRunEnd() or bulk postings of the current document after advanceShallow(target) into a later block. The same order through Scorer#advanceShallow and score() on a TermScorer gives the same result; that javadoc says the call "doesn't modify the current docID()" (Scorer.java:66).
  • What goes wrong. Wrong per-document data, then a wrong next document (one without the term), an EOFException, or a doc id beyond maxDoc. The same with assertions on and off.
  • Who is not hit. TermQuery, PhraseQuery, SynonymQuery, FeatureQuery, WAND, MaxScore, block-max conjunctions, ReqOptSumScorer and CheckIndex move the iterator after a shallow advance past the current document before reading (CheckIndex reads after advanceShallow(docID()), which is harmless); non-scoring clauses get plain postings, at most wrapped in a SlowImpactsEnum whose advanceShallow does nothing; the study's security probe found stock top-scores queries over 20 fixed and 400 random shapes matching exhaustive scoring. No caller was found in Elasticsearch, OpenSearch or Solr main (not exhaustive).
  • Default vs opt-in. Default codec, no configuration; it takes direct use of an @lucene.experimental API in an order the javadoc does not forbid. The freq-then-advance symptom needs a second full 256-doc block after the current one (terms with 334 and 500 postings were fine, 512 to 2,500 were not).
  • Scale and age. 1,200 documents suffice; the gap is in every release from 8.0.0.

Why it looks unintended

#
  • The javadoc lists what is illegal after advanceShallow(target); reading the current document is not on the list, and freq() promises the "term frequency in the current document".
  • Users are sent here: the package overview shows advanceShallow, and its author pointed a java-user reader to this javadoc.
  • AssertingScorer already rejects the Scorer-level form; AssertingImpactsEnum lets freq() through.
The full argument284 words
  • The javadoc enumerates the forbidden calls (ImpactsSource.java:33-37): "After this method has been called, nextDoc() may not be called if the current doc ID is less than target - 1 and advance(int) may not be called on targets that are less than target."
  • The inherited contracts point the other way. PostingsEnum#freq (PostingsEnum.java:74-77): "Returns term frequency in the current document ... Do not call this before nextDoc is first called, nor after nextDoc returns NO_MORE_DOCS." DocIdSetIterator#advance for target > current "behaves as if written" as a nextDoc() loop (DocIdSetIterator.java:144-153), so advance(256) must return 256. docIDRunEnd(): "All docs in range [docID(), docIDRunEnd()) match this iterator" (:251). Scorer#advanceShallow: "Calling this method doesn't modify the current docID()" (Scorer.java:66).
  • Users are sent here. The index package overview shows impactsEnum.advanceShallow(targetDocID) (index/package-info.java:228-248). On java-user ("How to access block-max metadata?", 2020-10-12) Adrien Grand pointed a user to TermsEnum#impacts and the "documentation for ImpactsSource#advanceShallow and ImpactsSource#getImpacts", and wrote that "advanceShallow only advances the cursor for block-max metadata, this allows reasoning about maximum scores without actually advancing the doc ID".
  • Not self-evident to committers. In the #14390 review (2025-03-22) gf2121 asked whether docIDRunEnd should be tested against "advance, intoBitset, advanceShallow", and jpountz answered that "'sane' impls of docIDRun should be free of side effects".
  • The rule exists only in code. AssertingScorer (LUCENE-8135, 2018) enters SHALLOW_ADVANCING after advanceShallow(target != doc) and rejects score() (AssertingScorer.java:110, :127); nextPostings asserts needsRefilling == false (#14679); #14185 removed a special-case eager refill from advanceShallow (fixing its interaction with #14164), so the refill is always deferred since. No javadoc, package doc, CHANGES.txt or MIGRATE.md text states the precondition.
The devil's-advocate check140 words

Strongest case for "works as designed" (the study's intended-behaviour checker and the cross-model refute review): ImpactsSource is @lucene.internal and ImpactsEnum @lucene.experimental; advanceShallow is the skip step of advance(); every checked in-tree caller follows "peek, then move"; AssertingScorer already encodes the rule; and the behaviour has been stable since 2018 with no complaint.

Why it fails. It shows the codec is right, which this page concedes; it does not make the javadoc complete. The javadoc lists the forbidden follow-ups explicitly, so a reader takes the list as complete; ImpactsEnum comes from the public TermsEnum#impacts, is shown in the package overview and was recommended to users by its author; the reviewer itself called the javadoc "genuinely misleading". The fix is one sentence and an assertion, with no behaviour change: a small hardening that upstream may still decline as "internal".

Suggested fix

#

Recommended A. State the precondition in ImpactsSource#advanceShallow (recommended)

No codec change. One javadoc sentence in ImpactsSource#advanceShallow: after advanceShallow(target) with target > docID(), do not read the current document until nextDoc() or advance(). Plus the matching assertion in AssertingImpactsEnum. Validated with gradle: format and javadoc checks pass, the wrapped test passes, and 116 tests of twelve selected suites pass with the Asserting codec forced.

    * - 1} and {@link DocIdSetIterator#advance(int)} may not be called on targets that are less than
-   * {@code target}.
+   * {@code target}. If {@code target} is greater than the current doc ID, methods that read data of
+   * the current document, such as {@link PostingsEnum#freq()}, {@link PostingsEnum#nextPosition()}
+   * or {@link DocIdSetIterator#docIDRunEnd()}, may not be called until the iterator has been moved
+   * with {@link DocIdSetIterator#nextDoc()} or {@link DocIdSetIterator#advance(int)}: the current
+   * doc ID does not change, but implementations may have already moved their internal state past
+   * the current document.
All options and trade-offs4 options · 700 words

Javadoc plus test framework; the codec's deferred refill is intended and should not change. Options A and B were applied together in a scratch worktree of main 645d4fe14a20 and checked with gradle.

A. State the precondition in ImpactsSource#advanceShallow (recommended) (validated by the checks)

#

One sentence after the existing restrictions: per-document reads are not allowed after a shallow advance past docID() until the iterator is moved.

    * - 1} and {@link DocIdSetIterator#advance(int)} may not be called on targets that are less than
-   * {@code target}.
+   * {@code target}. If {@code target} is greater than the current doc ID, methods that read data of
+   * the current document, such as {@link PostingsEnum#freq()}, {@link PostingsEnum#nextPosition()}
+   * or {@link DocIdSetIterator#docIDRunEnd()}, may not be called until the iterator has been moved
+   * with {@link DocIdSetIterator#nextDoc()} or {@link DocIdSetIterator#advance(int)}: the current
+   * doc ID does not change, but implementations may have already moved their internal state past
+   * the current document.

Trade-offs

  • Implementation-neutral (no mention of blocks); it mirrors the rule AssertingScorer already enforces (target != doc).
  • It is stricter than the default codec needs (a target inside the current block moves no state there, Lucene104PostingsReader.java:879), which keeps the rule simple and future-proof. The methods are examples ("such as"); it does not say whether the bulk intoBitSet() and nextPostings() are covered, and B does not check them either.
  • Scorer#advanceShallow has the same gap for score() (option C).

What the checks validated

  • Gradle, scratch worktree of 645d4fe14a20: :lucene:core:checkGoogleJavaFormat and :lucene:core:renderJavadoc pass (together with B, in the second pass; the first stopped at the format check on the copied repro's 101-column comment), and the rendered ImpactsSource.html shows the new sentence.
  • The minimal test was re-run with the fix and still fails (expected:<256> but was:<261>), as it must: the change is in a comment.
  • Not run: gradlew check or the whole core suite.

B. Assert it in AssertingImpactsEnum (recommended together with A) (validated by the checks)

#

Remember whether advanceShallow went past the current doc; assert on freq(), nextPosition(), startOffset(), endOffset() and getPayload(); clear the flag on nextDoc()/advance(). +19 lines in AssertingLeafReader.java (one blank), none removed.

    // true after advanceShallow() to a target beyond the current doc, until nextDoc() or advance()
    private boolean shallowAdvancedPastDoc;
    // advanceShallow(target), after the existing asserts:
      shallowAdvancedPastDoc |= target > docID();
    // first line of freq(), nextPosition(), startOffset(), endOffset(), getPayload():
      assert shallowAdvancedPastDoc == false : shallowAdvancedPastDocMessage("freq");
    // nextDoc() and advance(), before delegating:
      shallowAdvancedPastDoc = false;

Trade-offs

  • Catches the misuse at the call, before any data is read, so the eager freq() in AssertingPostingsEnum no longer hides anything and can stay.
  • It does not cover docIDRunEnd(), intoBitSet() or nextPostings() of the codec enum: AssertingImpactsEnum does not delegate those today (the wrapper runs the safe defaults).

What the checks validated

  • Gradle, same worktree, A and B applied: :lucene:test-framework:checkGoogleJavaFormat and :lucene:core:checkGoogleJavaFormat pass.
  • The wrapped form of the minimal test (reader in AssertingDirectoryReader, expectThrows(AssertionError.class, impacts::freq), then advance(256) = 256) fails on stock main ("Expected exception AssertionError but no exception was thrown") and passes with B (assertions on).
  • None of twelve selected suites tripped the new assertion in the configurations run: TestTermScorer, TestWANDScorer, TestMaxScoreBulkScorer, TestBlockMaxConjunction, TestBlockMaxConjunctionBulkScorer, TestReqOptSumScorer, TestSynonymQuery, TestPhraseQuery, TestDisjunctionScoreBlockBoundaryPropagator, TestBoolean2, TestFeatureField and TestCheckIndex pass with -Ptests.codec=Asserting (the Asserting codec's postings come wrapped in AssertingImpactsEnum), 116 tests with 3 skipped (the log does not name them), seeds DEADBEEF and 5EED1234; TestAssertingLeafReader (test-framework) passes. C. The same sentence on Scorer#advanceShallow (optional, not built)

#

Scorer.java:62-70 has the same gap for score(); AssertingScorer already enforces it, so only the javadoc is missing there.

Not recommended: keep the current document valid in the codec

#

Decode pending freqs before shallow-advancing and defer the position seek and the docCountLeft update to the refill. It would add work to a call the javadoc describes as "cheaper than calling advance" (ImpactsSource.java:30), so it would need a performance evaluation, and every checked in-tree caller already follows the protocol. Not built.

Downstream note

#

Downstream code with custom block-max scoring over TermsEnum#impacts or Scorer#advanceShallow should move the iterator before reading the current document again.

How it was found

#

Non-formal. A hunt unit read the Lucene104 postings reader's state machine while modelling it for a postings differential test and saw that a shallow advance moves the streams while the document stays; that test itself had excluded this call order. A JUnit test on the stock jars is the witness.

The method in full124 words
  • Lead. Code reading of Lucene104PostingsReader.BlockPostingsEnum in a hunt unit (postings), while modelling it for the unit's differential test (191M checks, 0 mismatches). That test excluded per-document reads after a pending shallow advance by design, so no tool output gave the first signal.
  • Witness. A public-API JUnit test on the stock jars, later reduced to the one-method test shown here (1,200 documents, deterministic).
  • Verification. An independent reproducer, cross-model reviews (OpenAI GPT-5.6: an executed intended-lens review, a reading-only refute review in the study and an executed refute review of the reduced test), an intended-behaviour devil's advocate, an adjudication, version-history runs (8.0.0 to main, plus the introducing commit built from source), a security probe, a re-verification and tie-break on main 645d4fe14a20, and this brief's gradle runs.

LFV-156, snapshot of 2026-11-03

Registry title
ImpactsSource#advanceShallow javadoc does not say that the current document's freq(), positions and docIDRunEnd() become invalid after a shallow advance past its block: the default codec then returns another block's data, and a lazy freq() breaks the next legal advance() (javadoc and assertion gap; the codec behaviour is intended)
Area
index / ImpactsEnum shallow-advance contract (ImpactsSource javadoc, test-framework AssertingImpactsEnum); codecs / Lucene104 postings reader
Priority
Low, rank 1133: The ImpactsSource#advanceShallow javadoc omits that the current document's data becomes invalid after a shallow advance into a later block, while the codec behaviour is intended.
Impact class
minor
Impact note
Documentation and assertion gap only: it misleads code that uses the @lucene.experimental ImpactsEnum directly (public TermsEnum#impacts) and reads the current document's data, or bulk-reads, after advanceShallow(target) into a later block without advancing first; with the default codec such code gets wrong positions, freq() or docIDRunEnd(), a following legal advance() that returns a document without the term (in variants a doc id beyond maxDoc or an EOFException), and, in the security probe, an intoBitSet() that did not return and a nextPostings() that skipped matches; no in-tree query, scorer, collector or CheckIndex path uses this call order, so stock searches are not affected; default codec, no scale needed.
Summary
You take an ImpactsEnum from TermsEnum#impacts, stand on a document, call advanceShallow(target) with a target in a later 256-doc block to peek at upcoming impacts, and then read the current document's freq(), positions or docIDRunEnd(); the javadoc forbids only nextDoc() and too-small advance() targets afterwards and says docID() does not change, so you expect the current document's own data and a working advance(target). Instead the default codec has already moved its streams to the target block on purpose: on main the positions of doc 0 read as [5] instead of [0], docIDRunEnd() claims docs 0 to 3327 all match although only every third does, and after freq() the legal advance(3000) returns doc 3005, which does not contain the term. Lucene's own callers always advance before reading, so the codec behaviour is intended; what is missing is this precondition in the ImpactsSource javadoc and a check for it in the test framework's AssertingImpactsEnum.
