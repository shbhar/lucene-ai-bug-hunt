FSTCompletionLookup sorts weights as unsigned bytes, so negative weights get the highest buckets and are suggested before positive ones

FSTCompletionLookup sorts weights by their raw bytes as unsigned numbers, so negative weights are treated as larger than every weight of 0 or more and take the top buckets: built from apple (weight 10) and apricot (weight -10), lookup("ap") suggests apricot first, with no error. Every release from 3.6.0 to 10.5.2 and main.

The bug in 30 seconds

#

FSTCompletionLookup does not keep exact weights. build() sorts the entries by weight, splits them into 10 equal ranges (buckets) and suggests the highest bucket first. The sort compares each weight's 4 bytes as unsigned numbers, and in that order negative ints look bigger than positive ones.

  1. You build an FSTCompletionLookup with the default settings (10 buckets) from two suggestions, apple with weight 10 and apricot with weight -10, and call lookup("ap", true, 2) for the best completions first.
  2. You expect apple first: higher weights mean better suggestions, the javadoc says buckets come from "sorting the input by weight", and the build accepts any int weight.
  3. To sort, build() writes each weight as 4 bytes and compares them as unsigned bytes: 10 is 00 00 00 0A, -10 is FF FF FF F6. So -10 sorts after 10, as if it were larger, and gets bucket 5 while apple gets bucket 0.
  4. You get [apricot/5, apple/0]. Negative weights take the top buckets (with at most 10 entries strictly above every non-negative weight; with more entries, those at the sign boundary can share a bucket); within each sign the order is right. An entry demoted to -1 is suggested first: apple 10, apricot 5, apron -1 give [apron/6, apple/3, apricot/0].
  5. No error; the full set of matches is unchanged but the top-k changes, and a stored lookup keeps the wrong order after reload until it is rebuilt.

Who is affected

#

Applications that build the opt-in, experimental FSTCompletionLookup from weights that mix signs (net votes, a signed score, -1 to demote an entry), through any weight source. The defaults suffice. Order and top-k change silently; the full set of matches does not. Rare by accident: frequencies and counts are never negative.

Mechanism, terms and numbers591 words

FSTCompletionLookup turns weights into a few buckets (10 by default) and suggests higher buckets first. To find the buckets, build() sorts the entries by weight and cuts the sorted list into equal ranges, as its javadoc says. But it sorts each weight's four big-endian two's-complement bytes as unsigned bytes, where every negative int (first byte 0x80 or more) comes after every non-negative int. So the negative weights take the highest buckets: built from {apple: 10, apricot: -10}, lookup("ap", true, 2) returns [apricot/5, apple/0], with no error. encodeWeight accepts every int and InputIterator#weight() says "higher numbers mean better suggestions". Within each sign the order is right and the full set of matches is unchanged; only the sign boundary is inverted, which changes the top-k. The sign handling was dropped in 2012 (LUCENE-3807), before the class was first released, so every release from 3.6.0 to 10.5.2 and main is affected. Flipping the sign bit of the sort key fixes it, with no format change.

Terms

#
  • Weight: the number an InputIterator (or a Dictionary such as FileDictionary or DocumentDictionary) attaches to each suggestion; "higher numbers mean better suggestions" (InputIterator.java:35). A signed long; FSTCompletionLookup accepts any value in the int range (encodeWeight, FSTCompletionLookup.java:254-259).
  • Bucket: FSTCompletionLookup keeps no exact weights. It sorts the entries by weight, cuts the sorted list into buckets equal ranges (10 by default) and stores each suggestion under its range number. lookup(key, true, num) returns the highest bucket first, and LookupResult.value is the bucket number, not the weight (:278).
  • Unsigned byte order: the offline sorter compares byte strings as unsigned bytes (0x00 < ... < 0xFF). A negative int in two's complement starts with a byte of 0x80 or more, a non-negative one with 0x7F or less.

What happens, step by step

#
  1. For each entry build() writes one line: the weight as 4 big-endian two's-complement bytes (output.writeInt(Integer.reverseBytes(encodedWeight)), FSTCompletionLookup.java:187-189, through the little-endian ByteArrayDataOutput.writeInt), then the suggestion bytes. 10 becomes 00 00 00 0A, -10 becomes FF FF FF F6.
  2. OfflineSorter sorts the lines with its default comparator, BytesRef#compareTo, which is Arrays.compareUnsigned (:199; OfflineSorter.java:195, :202-206; BytesRef.java:161-162). The order is 0, 1, ..., Integer.MAX_VALUE, Integer.MIN_VALUE, ..., -1.
  3. Buckets follow that order: bucket = line * buckets / inputLineCount (:226), equal weights share a bucket (:223-224). With 2 entries, line 0 (apple, 10) gets bucket 0 and line 1 (apricot, -10) bucket 5.
  4. Higher buckets are "presented before suggestions placed in smaller buckets" (FSTCompletionBuilder.java:169-171; FSTCompletion.java:147), so lookup("ap", true, 2) returns [apricot/5, apple/0].

Within the negative weights, and within the non-negative weights, unsigned order equals numeric order, so those comparisons are right: {apple: 10, apricot: 5} and {apple: -1, apricot: -10} both give [apple/5, apricot/0]. A stale comment sits right above the loop (:174-175): "For now, assume they are non-negative. If negative floats are allowed some trickery needs to be done to find their byte order."

Exposure and likelihood445 words
  • Who is exposed. Users of FSTCompletionLookup (opt-in, @lucene.experimental, FSTCompletionLookup.java:71) whose weights mix negative and non-negative values. Every public weight source can deliver them: a custom InputIterator, FileDictionary (weights parsed as a signed long, FileDictionary.java:207-213), DocumentDictionary over a signed numeric field (executed) or DocumentValueSourceDictionary. The default constructor and the default 10 buckets suffice.
  • What goes wrong. Negative-weight suggestions come before non-negative ones (with more entries than buckets, the entries at the sign boundary may instead share a bucket), so the top-k changes; an entry an application demotes with -1 is suggested first. The full set of matching suggestions is unchanged (0 mismatches in 168 full-set lookups over a 3,000-entry mixed-sign dictionary; the top 5 differed from an order-preserving control for 84 of 84 prefixes). One probe on 100,000 entries saw the same result counts and FST ramBytesUsed() as that control, with comparable single-run timings (not a benchmark). Nothing throws (executed on main with -ea and -da, and on 10.5.2).
  • When it shows. In lookup(key, true, num) (higher weights first). With higherWeightsFirst = false the results are sorted by text when there is more than one bucket (FSTCompletion.java:202-206), though LookupResult.value and get() still report the inverted buckets (:278, :287-288). With the default exactMatchFirst, an exact match of the key is returned first whatever its bucket (FSTCompletion.java:235-280); no example here has one (by reading).
  • It persists. The buckets are baked into the FST that store() writes (:293-300), so a stored lookup keeps the inverted order after load() until it is rebuilt on a fixed version (executed).
  • Scale. Every mixed-sign build sorts the negative weights above the non-negative ones; it shows as an inversion whenever the bucket ranges separate them, which is always the case with at most buckets entries (the two-entry repro fails every time). With more entries a bucket is a range of lines: 19 entries with weights 0 to 18 plus one of weight -1 put the -1 entry in bucket 9 with weight 18 (above weights 0 to 17); 100 entries, one of weight 5 and 99 of weight -1, all land in bucket 0, so no inversion shows (executed on main). A 600-trial random property check (1 to 60 random weights per build) found at least one bucket inversion in 206 of 206 mixed-sign builds and in 0 of 394 single-sign builds; with the fix in 0.
  • Likelihood. Rare by accident: common weight sources (term or document frequencies, popularity counts) are never negative, and WFSTCompletionLookup, AnalyzingSuggester and SuggestField reject negative weights. No user report was found since 3.6.0 (2012), though a silent mis-ranking may go unnoticed.

Why it is a bug, not intended

#
  • The javadoc assigns buckets by "sorting the input by weight"; InputIterator says higher weights are better suggestions.
  • encodeWeight explicitly accepts every int (its lower bound is Integer.MIN_VALUE), while WFSTCompletionLookup, changed in the same 2012 diff, kept a value < 0 check.
  • Before that change the class ordered negative weights correctly (bisected), and upstream's own test builds it from weight -1.
The full argument285 words
  • The contract. Class javadoc (FSTCompletionLookup.java:59-61): "The range of weights for bucketing/ discretization is determined by sorting the input by weight and then dividing into equal ranges." :63-65: the "overall distinction between \"classes\" of weights will be preserved regardless of the distribution of weights." InputIterator.java:35: "A term's weight, higher numbers mean better suggestions." No sign restriction anywhere in the javadoc, CHANGES or MIGRATE.
  • The input is accepted. encodeWeight throws only outside Integer.MIN_VALUE..MAX_VALUE (:254-259). The LUCENE-3807 diff that introduced it wrote that explicit Integer.MIN_VALUE bound, while WFSTCompletionLookup.encodeWeight, changed in the same diff, kept its existing value < 0 || value > Integer.MAX_VALUE check (today WFSTCompletionLookup.java:262-267). No source records why the two bounds differ.
  • Upstream tests. TestFSTCompletion#testLargeInputConstantWeights builds an FSTCompletionLookup from 5,000 entries of weight -1 (TestFSTCompletion.java:185, :192); TestPersistence asserts bucket values grow with the weight (TestPersistence.java:91-102), for weights 0..n. No test mixes signs.
  • History. SOLR-2888 (92de7e88486, 2011) added the class with FloatMagic.toSortable, "a directly sortable unsigned integer" that sorted negatives below non-negatives. LUCENE-3807 (f303bcd4650, 2012; backport 71bd966a92e) switched weights to long, used (int) value and deleted FloatMagic. Its CHANGES entry says that weights became 64-bit signed integers (it also covers the disk-based sort and the move to CharSequence) and nothing about negative-weight order; its 38 comments never mention negative weights. The parents pass the FileDictionary probe, the two commits fail it, and each passes with the one-line sign-bit patch.
  • Siblings that were checked. WFSTCompletionLookup, AnalyzingSuggester and SuggestField reject negative weights loudly; TSTLookup and AnalyzingInfixSuggester accept them and order them by numeric value (tst/TSTLookup.java:195-196, analyzing/AnalyzingInfixSuggester.java:166). Other suggesters were not checked for this.
The devil's-advocate check237 words

The strongest works-as-designed case (intended-behaviour checker, adjudication, cross-model intended lens): the comment "For now, assume they are non-negative" (:174-175), sibling suggesters that reject negative weights, @lucene.experimental, and lossy bucketing.

It fails: the comment is internal, never enforced, and was stale from the day it was written (it came with SOLR-2888 in the same commit as FloatMagic, which did order negatives correctly, and it still talks about floats); encodeWeight explicitly admits negative ints (its lower bound is Integer.MIN_VALUE) while WFSTCompletionLookup rejects them; the module has no single convention; @lucene.experimental is about API stability, not wrong results; and the lossy-bucketing caveat is about merging nearby weights, while the same paragraph promises the classes are preserved. A reviewer may add that the class javadoc sends users who need "fine-grained control over which weights are assigned to which buckets" to FSTCompletion or TSTLookup (:67-68), which is about precision within the lossy scheme, not order, and that FSTCompletionBuilder.add requires a non-negative bucket (FSTCompletionBuilder.java:169-176), which constrains the bucket number build() computes from the line number, not the weight. Silently inverting accepted input is not a design; rejecting it would be, and a committer may reasonably prefer that to supporting negative weights. The cross-model refute lens said "not real" at low confidence only because its read-only tools could not run the test; it agreed with the root cause and that the inputs are in contract.

Suggested fix

#

Recommended Flip the sign bit of the 4-byte sort key

Flip the sign bit of the sort key: Integer.reverseBytes(encodedWeight ^ Integer.MIN_VALUE) in build(), so unsigned byte order equals numeric order, and drop the stale comment. No format change (the key lives only in the temporary sort file). The repro passes, and all of lucene/suggest passes (238 tests).

-    // Push floats up front before sequences to sort them. For now, assume they are non-negative.
-    // If negative floats are allowed some trickery needs to be done to find their byte order.
+    // Write each weight before its sequence, so that sorting the lines sorts them by weight.
 ...
         final int encodedWeight = encodeWeight(iterator.weight());
-        // write bytes for comparing in lexicographically order
-        output.writeInt(Integer.reverseBytes(encodedWeight));
+        // write big-endian bytes for comparing in lexicographic (unsigned) order; flipping the sign
+        // bit makes that order equal to the numeric order of the weights, negative ones included
+        output.writeInt(Integer.reverseBytes(encodedWeight ^ Integer.MIN_VALUE));

Flip the sign bit of the 4-byte sort key (validated by the checks) (recommended)

#

In FSTCompletionLookup.build, write Integer.reverseBytes(encodedWeight ^ Integer.MIN_VALUE) instead of Integer.reverseBytes(encodedWeight), and replace the stale "assume they are non-negative" comment. XOR with 0x80000000 maps Integer.MIN_VALUE..MAX_VALUE monotonically onto 0x00000000..0xFFFFFFFF: -10 becomes 7F FF FF F6, 10 becomes 80 00 00 0A. The value read back (:220) is only compared for equality (:223), and XOR is a bijection, so ties still share a bucket. FloatMagic applied the same sign-bit XOR to non-negative floats before 2012. Integer.MIN_VALUE is 0x80000000: the diagram writes the same constant in hex.

-    // Push floats up front before sequences to sort them. For now, assume they are non-negative.
-    // If negative floats are allowed some trickery needs to be done to find their byte order.
+    // Write each weight before its sequence, so that sorting the lines sorts them by weight.
 ...
         final int encodedWeight = encodeWeight(iterator.weight());
-        // write bytes for comparing in lexicographically order
-        output.writeInt(Integer.reverseBytes(encodedWeight));
+        // write big-endian bytes for comparing in lexicographic (unsigned) order; flipping the sign
+        // bit makes that order equal to the numeric order of the weights, negative ones included
+        output.writeInt(Integer.reverseBytes(encodedWeight ^ Integer.MIN_VALUE));

Trade-offs

  • No index or file-format change: store() writes the entry count and the FST (:293-300); the key exists only in the temporary sort file.
  • Lookups stored by affected versions keep their inverted buckets until they are rebuilt.
  • Builds whose weights all have the same sign get the same buckets as today (unsigned order within one sign is unchanged; by reading).
  • No cost: one XOR per entry at build time.

Reject negative weights, like WFSTCompletionLookup (not run)

#

Change encodeWeight's bound to value < 0 || value > Integer.MAX_VALUE, as in WFSTCompletionLookup and AnalyzingSuggester.

Trade-offs

  • Loud instead of silent, and consistent with three sibling suggesters.
  • A behaviour change for callers whose negative weights work today (all-negative or constant weights order correctly); one bad entry fails the whole build; needs a CHANGES/MIGRATE note.
  • Breaks upstream TestFSTCompletion#testLargeInputConstantWeights, which builds from weight -1 (by reading).

Downstream note

#

By code reading only (not executed), Solr's SolrSuggester (apache/solr 0d6b2e32f598) falls back to FSTLookupFactory, which builds an FSTCompletionLookup, when no lookupImpl is configured (other Solr suggester classes and versions not checked); its default dictionaries give non-negative weights, so it is reached only with a dictionary file, weight field or weight expression that can go negative.

How it was found

#

End-to-end translation validation of six suggesters on the real jar: 3,000 random sources, the FSTCompletionLookup ones with weights from {MIN, -5, -1, 0, 1, 5, MAX}, checked against the javadoc rule that a higher weight never gets a lower bucket. All 1,768 inversions per wrapper had a negative weight; with the sign-bit fix, 0. Code reading then found the cause.

The method in full197 words

Method: end-to-end translation validation on the stock jar (semi-formal tier), in a hunt unit on how the suggesters preserve the InputIterator (term, weight) tuples.

  • The harness built six suggesters (AnalyzingSuggester, FuzzySuggester, AnalyzingInfixSuggester, FSTCompletionLookup, WFSTCompletionLookup, TSTLookup) from 3,000 seeded random sources of 1-6 entries over 3 keys, passed through 5 InputIterator wrappers (90,000 builds and 292,350 lookups in all), and compared each result with a reference written from the javadoc (for FSTCompletionLookup: a key with a higher weight never gets a lower bucket). The FSTCompletionLookup sources drew weights from {Integer.MIN_VALUE, -5, -1, 0, 1, 5, Integer.MAX_VALUE}; the other suggesters used non-negative weight sets.
  • For FSTCompletionLookup it reported 1,768 bucket-order inversions per wrapper, every one in a source that contains a negative weight, and 0 with the sign-bit fix shadowed onto the jar.
  • The root cause was then located by reading build() and its history, and reduced to a two-test public-API JUnit. Found 2026-10-26 on main ea57360912ed; then checked by an independent reproducer, an intended-behaviour devil's advocate, reading-only reviews by a model from another family (OpenAI GPT-5.6), an adjudication, a history, prior-report and security follow-up, and a credibility audit.

History

#

Introduced by LUCENE-3807 (f303bcd4650, 2012-03-02; backport 71bd966a92e, first in 3.6.0), which replaced a sign-correct encoding with (int) value. Bisected on both branches. Executed and failing on 3.6.0 through 10.5.2 and main; never fixed.

Versions tested6 rows

Introduced by LUCENE-3807 (now GitHub #4880, "Cleanup suggester API"; an SVN-era commit, so no PR): trunk f303bcd4650 "Cleanup Suggest / Lookup API" (2012-03-02) and the branch_3x backport 71bd966a92e "Cleanup Suggest API" (2012-03-07), which shipped first, in 3.6.0. It replaced output.writeInt(FloatMagic.toSortable(weight)) with output.writeInt(encodeWeight(weight)), encodeWeight = (int) value, and deleted FloatMagic, whose mapping had made unsigned byte order equal numeric order.

FSTCompletionLookup itself came with SOLR-2888 (92de7e88486, 2011-12-01), which ordered negative weights correctly but was never released; its released predecessor FSTLookup (3.5.0) also did. So no release of FSTCompletionLookup ever ordered negative weights correctly. Later rewrites of the same line in 9.0.0 (b84e0c272b6 LUCENE-9047, 0e1f9fcf31b LUCENE-10193) keep the same bytes. On 2026-10-28 the last change to the file on main, branch_10x and branch_10_6 was #14228 (2025-02-24, a cleanup) and on branch_9_12 #12951 (2024-02-04); branch_9x was tombstoned in 2024 (#13882), so the file no longer exists there.

LFV-479, snapshot of 2026-10-30

Registry title
FSTCompletionLookup sorts weights as unsigned bytes, so negative weights get the highest buckets and are suggested before positive ones
Area
suggest / FST completion suggester (FSTCompletionLookup.build weight bucketing)
Priority
Low, rank 334: Ranking-only, in the opt-in experimental FSTCompletionLookup, and only with weights that mix signs.
Impact class
silent wrong results
Impact note
Applications that build the opt-in, @lucene.experimental FSTCompletionLookup suggester (default constructor and default 10 buckets suffice; by code reading, Solr's suggester falls back to it when no lookupImpl is configured, and no use was found in Elasticsearch or OpenSearch) from weights that mix negative and non-negative values, for example a signed score or vote field, a negative weight used to demote an entry, or a FileDictionary or DocumentDictionary over signed numbers, get every negative-weight suggestion ranked above every non-negative one with no error, on every release from 3.6.0 through 10.5.2 and on main; the order within the negative and within the non-negative weights is correct, the result set is unchanged, no scale is needed, and stored lookups keep the inverted buckets until they are rebuilt on a fixed version.
Summary
You build an FSTCompletionLookup from two suggestions, apple with weight 10 and apricot with weight -10, and ask lookup("ap", true, 2) for the best completions first. You expect apple first, because the class javadoc says buckets come from 'sorting the input by weight', InputIterator says 'higher numbers mean better suggestions', and encodeWeight accepts every int. Instead you get [apricot/5, apple/0], with no error: build() sorts the weights by their unsigned big-endian bytes, where every negative int (first byte 0x80 or above) comes after every non-negative int, so all negative weights land in the highest buckets and are suggested first.
Introduced
f303bcd4650ac96d88b84dade253fbf4cb407158 (trunk, SVN r1296268, 2012-03-02) and its branch_3x backport 71bd966a92e6abe6aefa929d07194ab1ce95ca0e (SVN r1297946, 2012-03-07; the backport shipped first, in 3.6.0), LUCENE-3807 'Cleanup Suggest / Lookup API' (now GitHub issue #4880; an SVN commit, no pull request): build() changed output.writeInt(FloatMagic.toSortable(weight)) to output.writeInt(encodeWeight(weight)) with encodeWeight = (int) value over the whole int range, and deleted FloatMagic, whose mapping (negatives to ~v, non-negatives to v ^ 0x80000000) had made unsigned byte order equal numeric order [read: git show, git blame] [exec: bisected on both branches; the parent commits 2c94c522fd8 (trunk) and 2fa71777a72 (branch_3x) pass, the introducing commits fail, and a one-line sign-bit patch on each introducing commit passes]. Later rewrites of the same line (b84e0c272b6 LUCENE-9047, 0e1f9fcf31b LUCENE-10193, both 9.0.0) keep the same bytes. FSTCompletionLookup itself came with SOLR-2888 (92de7e88486, 2011-12-01), which ordered negative weights correctly but was never released (2012-03-02 (trunk); 2012-03-07 (branch_3x backport))
