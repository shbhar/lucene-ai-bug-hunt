matchhighlight's default adjuster moves a later value's default passage before its start, so that value's snippet is dropped

When matchhighlight shows the leading text of several values without highlights, its default adjuster can move a later value's passage before its own start. For the values 01234 and 56789 and a 4-character window, pickBest then throws its own assertion, or, with assertions off, drops the second snippet.

The finding in 30 seconds

#

Without highlights, pickBest makes one default passage per value: from the value's start, cut to the window. The adjuster walks each passage end back to the last word end. The only fallback that can fire here covers a walk that reaches offset 0. A later value's walk can stop at an earlier value's word end, before the passage.

  1. Ask matchhighlight's default passage selector for the leading text of a two-valued field without matches: the values 01234 and 56789, joined as MatchHighlighter joins them (01234 56789, ranges [0,5) and [6,11)), a 4-character window, up to 2 passages.
  2. You expect one truncated passage per value, 0123... [0,4) and 5678... [6,10). The same call without an adjuster gives exactly that, and the first value keeps [0,4) with it.
  3. Instead the adjuster pulls the end of [6,10) back to the last word end. None lies inside the passage, so the end walks past the passage start to offset 5, the end of 01234, and the adjuster returns the empty range [5,5).
  4. With assertions on, pickBest throws its own AssertionError: Adjusters must not expand the passage's range. With them off it drops the empty passage and returns only 0123...: the second value silently gets no snippet.
  5. It takes passages built without matches and a later value whose first word is longer than the window (a 240-character Thai value is one word to the default word iterator). Every release since 9.0.0 has it.

Who is affected

#

Users of the matchhighlight package whose passages are built without matches for two or more values: a direct pickBest call, or MatchHighlighter when no match offset survives (zero-width offsets, as in #11976). A later value whose first word is longer than the window (such as long Thai text), or a whitespace-only value, triggers it. maxLeadingCharacters cannot reach it.

Mechanism, terms and numbers702 words

With no highlights, PassageSelector.pickBest builds one default passage per value, from the value's start and cut to the window. The default adjuster, BreakIteratorShrinkingAdjuster, then walks each passage end back to the last word end; when none lies inside the passage, the only fallback that can fire is for a walk that reaches offset 0 (if (to == 0), BreakIteratorShrinkingAdjuster.java:70-72; the in-loop DONE branch at :65-67 cannot fire with the default iterator). For a later value the walk can stop at an earlier value's word end instead, before the passage, and if (from > to) from = to returns an empty range there (:80-82). pickBest asserts that an adjuster never leaves the passage (PassageSelector.java:185-189): with -ea it throws, and with -da it skips the empty passage (:199), so that value gets no snippet while a first value of the same shape keeps its truncated one. For 01234 56789 with ranges [0,5) and [6,11), window 4 and 2 passages, the result is [0,4) only instead of [0,4) and [6,10). The adjuster and the assertion came in one commit (LUCENE-9463) and every release from 9.0.0 to 10.6.0 has it. A one-line guard, if (to <= passage.from) in place of if (to == 0), keeps the passage and passes the repro and the whole highlighter test module.

Terms

#
  • Value ranges. MatchHighlighter joins a field's values with the analyzer's offset gap, one space by default (MatchHighlighter.java:276-299, Analyzer.getOffsetGap returns 1), and passes each value's [start, end) as a permitted range. 01234 and 56789 become 01234 56789 with ranges [0,5) and [6,11).
  • Default passages. When no highlight marker survives, pickDefaultPassage makes one passage per non-empty range, up to maxPassages, each from the range start with length min(window, range length) (PassageSelector.java:168-175, :278-304).
  • The adjuster. FieldValueHighlighters.defaultPassageSelector() is new PassageSelector(DEFAULT_SCORER, new BreakIteratorShrinkingAdjuster()) (FieldValueHighlighters.java:82-86). The adjuster uses Java's ROOT-locale word BreakIterator (BreakIteratorShrinkingAdjuster.java:30-32) and moves the passage start forward and the end back to word boundaries that do not touch whitespace (:45-84).

When it fires

#

A passage without markers (markers widen the range back inside, BreakIteratorShrinkingAdjuster.java:75-78) whose end walk finds no word end inside it and stops at an earlier word end instead of offset 0 (a passage that ends at the end of the whole text is not walked, :62). When that word end lies before the start, as here, the range leaves the passage. When it lies exactly at the start (adjacent ranges in a direct pickBest call: abc,defghij, ranges [0,4) and [4,11), window 3), the empty range [4,4) stays inside: no AssertionError even with -ea, but the second passage is still dropped, and the guard below keeps it (executed). Controls (executed): TestPassageSelector's own input 0123456789 with ranges [0,5) and [5,10) has no word end before the second passage, so the walk reaches 0 and both [0,4) and [5,9) are kept; a 220-character URL after title with window 160 has word breaks inside and keeps [6,26); 128 characters of Japanese text after title, window 20, are segmented and kept. A 240-character Thai value after title, window 20, has no inner boundary for this iterator and fails; so does a whitespace-only value between two others (then nothing visible is lost).

Exposure and likelihood270 words
  • Who is exposed. Code that calls FieldValueHighlighters.defaultPassageSelector() (or a PassageSelector with BreakIteratorShrinkingAdjuster) with no markers and maxPassages >= 2 over several value ranges, for example to show the first N characters of every value; and MatchHighlighter with FieldValueHighlighters.highlighted when match offsets exist but none survives, as with the zero-width ICUNormalizer2CharFilter offsets of #11976. The recorded end-to-end run hits a whitespace-only value: with assertions on the same AssertionError (for [2,3) changed to [1,1)), off that whitespace value is left out, so nothing visible is lost there; the visible loss is shown through pickBest directly.
  • Not reached. maxLeadingCharacters asks for one passage (FieldValueHighlighters.java:68-70); only empty values or gap spaces can precede it, so its walk reaches 0. Passages with highlights are pulled back inside by their markers.
  • Default vs opt-in. The selector and the adjuster are the package defaults; the matchhighlight package itself is opt-in, and a code search found no use of it in Solr, Elasticsearch or OpenSearch.
  • What it takes. A later value whose first word, for Java's ROOT word iterator, is longer than the window, or a whitespace-only value. Executed: 56789 at window 4, abcdefgh at window 3, 240 characters of Thai at window 20. Ordinary words and URLs have word breaks inside the window (a 220-character URL after title, window 160, kept [6,26)).
  • Effect. Deterministic, at any scale. With -ea the highlight call fails; that shows mostly in tests, since the JVM default is -da (Lucene's own test runs enable assertions for about 75% of seeds). With -da one value's unhighlighted leading text is silently missing; hits, scores and passages with highlights are right.

Why it looks unintended

#
  • pickBest asserts "Adjusters must not expand the passage's range", written in the same commit as the adjuster.
  • When the adjuster finds no word end it keeps the original edge: the first value keeps 0123, a later value of the same shape loses 5678.
  • No javadoc, test or CHANGES entry lets an adjuster leave or drop a passage.
The full argument257 words
  • The contract. "Correct passage boundaries from maxExclusive window. Typically shrink boundaries until we're on a proper word/sentence boundary." (PassageSelector.java:177-178), then assert newRange.from >= p.from && newRange.to <= p.to : "Adjusters must not expand the passage's range ..." (:185-189). The class is named Shrinking; its javadoc says it "adjusts the Passage range to word boundaries" (BreakIteratorShrinkingAdjuster.java:22-25).
  • Its own fallbacks keep the edge. if (to == 0) to = passage.to; (BreakIteratorShrinkingAdjuster.java:70-72), if (from == value.length()) from = passage.from; (:56-58) and both DONE branches (:51-54, :65-67): when the walk finds no boundary, the passage keeps its original edge. Offset 0 is the start of the first passage only.
  • History. The adjuster, pickBest and the assertion came in one commit by one author, 150a8dacb59 (LUCENE-9463, Dawid Weiss, 2020-08-14). Then only the first non-empty value got a default passage, and the to == 0 fallback covered it unless that range started after an earlier word end (code reading). 59d83428bcb (LUCENE-9519, 2020-09-10) made one default passage per value; a later one can start after an earlier value's word end. This points to an oversight rather than a design choice (an inference: nothing records the intent).
  • Tests. TestPassageSelector.defaultPassages expects one truncated passage per value, 0123...|5678... (:208-215, no adjuster and no gap); whitespaceBoundaries (:218-224) runs the adjuster only on a passage with a marker; randomizedSanityCheck uses new PassageSelector(), without an adjuster (:298). No javadoc, CHANGES or MIGRATE entry lets an adjuster leave the passage.
The devil's-advocate check204 words

The strongest case for "intended": the result is an empty range, which covers no characters, so it does not grow the shown text, and pickBest drops empty passages on purpose (PassageSelector.java:199). The assertion could then be called over-strict, and "no word end inside the window, show nothing" could be a policy. PassageAdjuster's javadoc only says an adjuster may shift a boundary "to the next or previous word delimiter or white space".

Why it fails: the assertion is the author's own statement of the contract, written in the same commit as the adjuster; the adjuster's fallbacks show its policy is "keep the original edge", which the first value gets; with -da the loss is visible text (5678, or a whole Thai value's lead); and nothing documents that a value's snippet may vanish. Two questions stay apart: the range leaving the passage breaks the selector's stated contract under any policy; whether a value with no word end in its window should show a cut word or nothing is a policy choice (the guard shows the cut word, as the first value already gets). Two executed reviews by another model family (OpenAI GPT-5.6, refute and intended lenses) rated the intended case weak.

Suggested fix

#

Recommended Fall back to the passage end when the walk reaches the passage start (validated)

Change the adjuster's fallback from if (to == 0) to if (to <= passage.from): when the end walk reaches the passage start, keep the passage end, as the first value already does. One line; the repro, the four matchhighlight suites (49 tests), the whole highlighter module (731 tests) and its static checks pass with it.

-      if (to == 0) {
+      if (to <= passage.from) {
         to = passage.to;
       }

Fall back to the passage end when the walk reaches the passage start (validated) (recommended)

#

BreakIteratorShrinkingAdjuster.java:70. It generalizes the existing fallback: offset 0 is the start of the first passage only. The second value then keeps [6,10), as the first keeps [0,4).

-      if (to == 0) {
+      if (to <= passage.from) {
         to = passage.to;
       }

Trade-offs

  • A whitespace-only passage still collapses to an empty range, now inside the passage, and is dropped; nothing visible is lost.
  • For a passage with markers whose end walk crosses passage.from, the end stays at passage.to instead of the last marker end: still inside, just less shrunk. No upstream test covers that case.
  • Policy: it keeps a window that cuts through a word, as the to == 0 fallback already does for the first value. A maintainer may prefer to show nothing for such a value (the clamp below keeps the range inside and drops it).
  • Scope of the evidence: only the tests listed under validated, at f794ff5a505c; an adjuster built with another BreakIterator gets the same guard but was not tested.
  • No cost: one comparison per passage.

What the checks validated

  • Clean scratch worktree of f794ff5a505c, OpenJDK 25.0.3, gradle, 2026-11-09: the repro fails on stock with assertions on and off and passes with the fix, on and off.
  • With the fix: TestPassageSelector, TestMatchHighlighter, TestMatchRegionRetriever and the repro (4 suites, 49 tests) pass; the whole :lucene:highlighter:test module, 35 suites and 731 tests, 0 failures; :lucene:highlighter:check -x test passes with the test file in place.
  • Earlier, a verifier shadowed the same change into the stock jars: this test, the direct adjust() test and the 48 upstream matchhighlight tests passed.

Trade-offs

How it was found

#

Semi-formal. A differential harness compared MatchHighlighter's stock passage selection on char-filtered multi-valued fields with an independent per-value reference (12 configurations, 11 tokenizers). Its 37 assertion failures per passage check all had zero-width match offsets and a whitespace-only value; code reading reduced them to the adjuster, with no char filter. Verifiers showed whitespace is not needed.

The method in full163 words
  • The harness. It ran MatchHighlighter with its stock PassageSelector and PassageFormatter on char-filtered multi-valued fields and checked every passage against a per-item provenance reference, over a sweep of 12 configurations and 11 tokenizers.
  • The signal. 37 AssertionErrors per passage check (assertions on), "Adjusters must not expand the passage's range", all on documents whose only match offsets were zero-width (the ICUNormalizer2CharFilter collapse of #11976) and that held a whitespace-only value.
  • The reduction. Code reading led to the adjuster's end walk; a public-API JUnit on one whitespace-only passage (a b, passage [2,3) becomes [1,1)), with no char filter, failed on main with assertions on and off.
  • The widening. Independent verifiers showed that whitespace is not needed: a later marker-less passage with no word end inside it, after an earlier word end, fails, and with assertions off visible text is lost (x abcdefgh, window 3, loses abc; 01234 56789, window 4, loses 5678). The shipped test is the latter.

Impact note
Hits code that lets matchhighlight's default passage selector (FieldValueHighlighters.defaultPassageSelector(), or a PassageSelector with BreakIteratorShrinkingAdjuster) build default, marker-less passages for several value ranges with maxPassages >= 2: a direct pickBest call without matches, or MatchHighlighter's FieldValueHighlighters.highlighted when no match offset survives (for example the zero-width offsets of #11976). When a later value's default passage holds no word end (its first word is longer than the window, or the value is only whitespace next to the offset gap), pickBest throws an AssertionError with -ea (Lucene's own gradle test runs enable assertions for about 75% of seeds) and with -da silently leaves out that value's unhighlighted leading text (nothing visible is lost in the whitespace case); hits, scores and the other passages are right, maxLeadingCharacters (maxPassages 1) cannot reach it, no scale is needed; 9.0.0 through 10.6.0 and main.
Summary
You ask matchhighlight's default passage selector for up to two passages of a two-valued field without matches, FieldValueHighlighters.defaultPassageSelector().pickBest("01234 56789", List.of(), 4, 2, [0,5), [6,11)) (the values '01234' and '56789' joined with a one-character gap, as MatchHighlighter joins them), and expect one truncated default passage per value, [0,4) and [6,10), just as the first value keeps its truncated passage. Instead BreakIteratorShrinkingAdjuster walks the end of the second passage [6,10) back to the last word end before it, offset 5, and returns the empty range [5,5), which lies before the passage: with -ea pickBest throws 'AssertionError: Adjusters must not expand the passage's range: was [[from=6, to=10], markers=[]] => changed to [from=5, to=5]', and with -da it returns only [0,4), so the second value gets no snippet.
