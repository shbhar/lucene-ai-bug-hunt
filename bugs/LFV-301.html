PointVectorStrategy misses a point at longitude ±180° when a rectangle's dateline edge is written with the other sign

Longitude -180 and +180 are the same meridian, but PointVectorStrategy filters a box that only touches the dateline with a plain number range. So the western hemisphere rect(-180, 0, -90, 90) finds 0 hits for a point at (180, 10) instead of 1, on all 14 releases tested from 4.0.0 to 10.5.2 and on main.

The bug in 30 seconds

#

PointVectorStrategy stores a point's longitude (x) and latitude (y) as two plain numbers and answers a rectangle query with number ranges. A box with minX > maxX crosses the dateline and gets two x ranges; every other box gets one range, x in [minX, maxX], so +180 and -180 are different values to it.

  1. Index one point at longitude 180, latitude 10 with PointVectorStrategy in the standard geo context SpatialContext.GEO (default field type, codec and IndexWriterConfig).
  2. Search the western hemisphere: Intersects (or IsWithin) rect(-180, 0, -90, 90). You expect 1 hit: -180 and +180 are one meridian, SpatialOperation.evaluate says the point is inside, and BBoxStrategy returns 1.
  3. You get 0 hits, with no error. The box does not cross the dateline, so the query is one range, x in [-180, 0], and the stored 180.0 is outside it.
  4. Writing +180 everywhere does not help: spatial4j stores the caller's rect(180, -170, -10, 10) as minX = -180, and it misses (180, 0) too. The mirror case fails the same way: the eastern hemisphere rect(0, 180, -90, 90) misses (-180, 10).
  5. Only missed matches: across 570 boxes x 35 grid points the strategy misses 420 point-box pairs per operation, all at ±180 with the other sign, and returns 0 extra hits.

Who is affected

#

Applications that index points with the experimental PointVectorStrategy in a geo context and run rectangle Intersects or IsWithin queries, with points exactly at ±180. Deterministic with default settings, assertions on or off; the miss follows from the query, not the index size. Only missed matches, never extra ones. Reach is low: Solr removed its wrapper field type in 9.0.

Mechanism, terms and numbers680 words

In a geo SpatialContext, longitude -180 and +180 are the same meridian, and spatial-extras defines Intersects and IsWithin through spatial4j's relate, which treats them as one. PointVectorStrategy stores a point's x as a plain DoublePoint and, for a rectangle that does not cross the dateline, filters x with one closed range [minX, maxX]. To that range +180 and -180 are different numbers: a point stored at +180 is not found by a box whose west edge is -180, and a point at -180 is not found by a box whose east edge is +180. The western hemisphere rect(-180, 0, -90, 90) returns 0 hits for (180, 10), the eastern hemisphere rect(0, 180, -90, 90) 0 hits for (-180, 10), and rect(180, -170, -10, 10), written with +180 by the caller, 0 hits for (180, 0), because spatial4j itself turns that box's west edge into -180. The oracle and BBoxStrategy return 1 in every case. Both operations fail, with assertions on and off; the miss follows from the query itself, not from the index size (executed with one document and with a 609-document, 7-segment index). Only missed matches, never extra ones. It reproduces on all 14 releases tested from 4.0.0 (2012, when the module moved to spatial4j 0.3) to 10.5.2 and on main. A 6-line fix in makeWithin that also matches the other-sign meridian passes the repro and all spatial-extras tests.

Terms

#
  • Geo context: spatial4j's SpatialContext.GEO, the standard context for longitude/latitude in degrees. Longitude runs from -180 to +180, and both values name the same meridian, the antimeridian or dateline.
  • PointVectorStrategy (spatial-extras, @lucene.experimental): indexes one point per document as two DoublePoint fields (x and y) plus doc values, and supports Intersects and IsWithin queries by a rectangle or a circle.
  • Crossing box: a spatial4j rectangle with minX > maxX, for example rect(170, -170), which covers 170 to 180 and -180 to -170. A box with an edge on ±180 that does not wrap, such as rect(-180, 0), is not crossing.
  • The oracle: SpatialOperation.evaluate(indexed, query), which is spatial4j's relate. It defines the predicates for every strategy in the module, and in a geo context it treats x = +180 and x = -180 as one meridian.

What happens, step by step (main a9779ef3c193, PointVectorStrategy.java)

#
  1. createIndexableFields(Point) (:163-180) stores x as given: new DoublePoint(fieldNameX, point.getX()) (:175). spatial4j keeps 180 as 180.0.
  2. makeQuery (:187-206) sends a rectangle to makeWithin (:209-222). Only a crossing box gets two SHOULD ranges, [-inf, maxX] or [minX, +inf] (:212-216); any other box gets one MUST range [minX, maxX] on x (:217-219), closed at both ends (rangeQuery, :228-242).
  3. For the western hemisphere the query is +pv__x:[-180.0 TO 0.0] +pv__y:[-90.0 TO 90.0]. The stored x is 180.0, outside [-180, 0], so the document is missed, while relate says WITHIN.
  4. A non-crossing box lies inside [-180, 180], so a point at ±180 can only sit on one of its edges, and only the opposite sign is wrong. A crossing box already accepts both signs.
  5. spatial4j writes edges with either sign itself: rect(180, -170) becomes minX = -180, rect(170, -180) becomes maxX = 180, both non-crossing. So no single storage convention avoids the miss.

Exposure and likelihood339 words
  • Who is exposed. Users of PointVectorStrategy (@lucene.experimental) in a geo context, typically SpatialContext.GEO, with rectangle Intersects or IsWithin queries. newInstance(ctx, prefix), the default field type, codec and IndexWriterConfig are enough (an independent probe with a plain ByteBuffersDirectory and new IndexWriterConfig() misses the same inputs). Only field types with point values (the default) are affected; without them every rectangle query throws "An index is required for this operation." (PointVectorStrategy.java:241).
  • What it takes. A point stored at exactly longitude +180 or -180, and a box that does not cross the dateline with its edge on that meridian written, or normalized by spatial4j, with the other sign. Box edges on ±180 are ordinary (hemisphere boxes, tiles ending at the dateline); points exactly on the antimeridian are uncommon but real (snapped or rounded coordinates, grid data).
  • What goes wrong. 0 hits where the oracle says 1. A probe of 9,000,000 checks (4.5 million random point-box pairs, each for both operations) found 0 extra hits against an exact reference; its 96 disagreements with spatial4j relate are rounding in spatial4j on crossing boxes, where the strategy gives the exact answer. No error, and nothing stored is wrong, so a fix needs no reindexing.
  • Not affected. Every other strategy class in the module that indexes geo points returns the hit on these inputs: BBoxStrategy, SerializedDVStrategy, CompositeSpatialStrategy, and the prefix-tree strategies on geohash, quad and packed-quad grids (as configured in the probes; these trees are approximate grids, and one quad configuration also matches the outside control at 179.9). Also not affected: boxes that cross the dateline, same-sign edges, the world box. Core LatLonPoint is a different API with its own convention and is not claimed.
  • Reach. Less-used strategy: Solr deprecated its PointVectorStrategy field type in 6.6 and removed it in 9.0 (SOLR-10729, SOLR-13138); a code search of the default branches of Elasticsearch, OpenSearch and Solr found no use (re-run 2026-10-28 with a positive control per repository). No report of this bug was found in the public sources searched.

Why it is a bug, not intended

#
  • spatial-extras defines Intersects and IsWithin through spatial4j relate, which treats -180 and +180 as one meridian; BBoxStrategy handles this case ("-180 == 180").
  • TestBBoxStrategy has dateline-edge tests (LUCENE-5714): a line on +180, rect(180,180), must be within rect(-180,-100).
  • Storing points with one sign does not avoid it: spatial4j itself stores the caller's rect(180, -170) with minX = -180.
The full argument265 words
  • The contract. The class javadoc: "Can query by a rectangle or circle" and "SpatialOperation#Intersects and SpatialOperation#IsWithin is supported" (PointVectorStrategy.java:62-64). SpatialStrategy.makeQuery: "Make a Query based principally on SpatialOperation and Shape" (SpatialStrategy.java:116-117). SpatialOperation: "For more explanation of each predicate, consider looking at the source implementation of evaluate" and "Lucene-spatial makes no distinction of shape boundaries" (SpatialOperation.java:30-34), so a point on an edge counts.
  • The oracle. evaluate is spatial4j relate, which in a geo context says (180, 0) is within rect(-180, -170, -10, 10), for points already from spatial4j 0.3 on (the 4.0.0 run prints WITHIN). In locationtech/spatial4j#85, found through Lucene's TestBBoxStrategy, spatial4j extended the convention to zero-width boxes on the dateline, choosing to "deem longitude +/- 180 zero width as equal longitudinally".
  • The module states the convention elsewhere. BBoxStrategy.java:387,395: "touches dateline; -180 == 180". TestBBoxStrategy.java:108-175: testIntersectsBugDatelineEdge, testWithinBugDatelineEdge, testContainsBugDatelineEdge, testAlongDatelineOppositeSign, added with LUCENE-5714 (#6776), whose randomized tests "uncovered dateline edge cases (e.g. touches but doesn't cross the dateline) and world-wrap (-180 to 180) bugs", fixed then in BBoxStrategy only. TestRandomSpatialOpFuzzyPrefixTree.java:518-519: "in geo, -180 & +180 are the same place".
  • Every other strategy class in the module that indexes geo points returns the hit on these inputs.
  • History. LUCENE-4389 (#5455, 2012) added the crossing branch so that "at least it won't be buggy if you stay with Rectangle query shapes"; it handled only boxes that cross. No javadoc, CHANGES entry, MIGRATE note or test asserts the current behaviour, and the 22 upstream tests that use PointVectorStrategy pass with the fix.
The devil's-advocate check245 words

The strongest case for "intended" (an intended-behaviour checker and a cross-model reviewer): the class is @lucene.experimental and says "This is a simple Strategy. Search works with a pair of range queries on two DoublePoints" (PointVectorStrategy.java:72-73), so read literally x is a plain number and callers should canonicalize. Core LatLonPoint also treats 180 and -180 as different, and in #9767 (core LatLonShape) a committer called the same kind of opposite-sign behaviour "more like a feature". In #10728 (2021) @dsmiley suggested LatLonDocValuesField.newDistanceSort for geospatial distance sorting "or PointVectorStrategy for general 2D".

Why it fails: the javadoc sentence describes the implementation, not a precondition for callers, and the code already departs from a plain pair of ranges for crossing boxes. LatLonPoint and LatLonShape are core APIs with their own types and oracle, while spatial-extras defines its predicates through spatial4j and says "-180 == 180" in its own code and tests. Canonicalizing the stored points alone cannot work: one storage sign is always missed by one of the two hemisphere boxes, and spatial4j turns the caller's rect(180, -170) into minX = -180; callers can avoid the miss by rewriting every query box that touches the dateline (the workaround under Suggested fix), which no documentation asks for. The #10728 remark is about distance sorting: no javadoc limits the strategy to non-geo contexts, and LUCENE-4389 ("Fix TwoDoubles dateline support") added dateline handling to this very method. When filing, expect the #9767 objection and the #10728 "general 2D" remark.

Suggested fix

#

Recommended Also match the other-sign meridian for a geo box that touches the dateline

In makeWithin, when a geo box that does not cross the dateline has an edge on ±180, also match points stored at the other-sign meridian: one exact-value clause, +6 lines, like BBoxStrategy's "-180 == 180" case. The repro passes with assertions on and off, and all spatial-extras tests pass.

       bq.setMinimumNumberShouldMatch(1); // must match at least one of the SHOULD
+    } else if (ctx.isGeo() && (bbox.getMinX() == -180 || bbox.getMaxX() == 180)) {
+      // touches dateline; -180 == 180, so also match points stored with the other sign
+      double otherX = bbox.getMinX() == -180 ? 180 : -180;
+      bq.add(rangeQuery(fieldNameX, bbox.getMinX(), bbox.getMaxX()), BooleanClause.Occur.SHOULD);
+      bq.add(rangeQuery(fieldNameX, otherX, otherX), BooleanClause.Occur.SHOULD);
+      bq.setMinimumNumberShouldMatch(1); // must match at least one of the SHOULD
     } else {
       bq.add(rangeQuery(fieldNameX, bbox.getMinX(), bbox.getMaxX()), MUST);
     }
All options and trade-offs4 options · 725 words

Option A was applied in a scratch worktree at a9779ef3c193 and run through gradle (seed DEADBEEF), and checked against every hunt repro with the patched class shadowed onto the main jars; the other options were not run. Workaround until a fix ships (executed on main): OR the box's query with a second PointVectorStrategy query for the degenerate box on the other-sign meridian, for example rect(180, 180, minY, maxY) next to rect(-180, 0, minY, maxY); the western hemisphere then finds (180, 10) and still misses (179.9, 10).

Also match the other-sign meridian for a geo box that touches the dateline (validated by the checks) (recommended)

#

A new branch in makeWithin between the crossing branch and the plain range: if ctx.isGeo() and the box has minX == -180 or maxX == 180, the x filter becomes two SHOULD clauses with setMinimumNumberShouldMatch(1), the plain range and an exact match on the opposite-sign meridian (+180 for a west edge at -180, -180 for an east edge at +180). It mirrors the crossing branch above it and BBoxStrategy's special case; the closest precedent is BBoxStrategy.makeWithin, which for the same boxes ORs in an exact match on the opposite dateline edge (BBoxStrategy.java:550-559).

       bq.setMinimumNumberShouldMatch(1); // must match at least one of the SHOULD
+    } else if (ctx.isGeo() && (bbox.getMinX() == -180 || bbox.getMaxX() == 180)) {
+      // touches dateline; -180 == 180, so also match points stored with the other sign
+      double otherX = bbox.getMinX() == -180 ? 180 : -180;
+      bq.add(rangeQuery(fieldNameX, bbox.getMinX(), bbox.getMaxX()), BooleanClause.Occur.SHOULD);
+      bq.add(rangeQuery(fieldNameX, otherX, otherX), BooleanClause.Occur.SHOULD);
+      bq.setMinimumNumberShouldMatch(1); // must match at least one of the SHOULD
     } else {
       bq.add(rangeQuery(fieldNameX, bbox.getMinX(), bbox.getMaxX()), MUST);
     }

Trade-offs

  • Behaviour change: only boxes with an edge exactly on ±180 change, and they now also return opposite-sign points on that edge. For the world box the extra clause is redundant but harmless.
  • Circles share makeWithin, so their bounding-box prefilter may now admit a point at the other-sign meridian; the distance check still decides, and the probed circles give the same answers as before.
  • Cost: one more single-value range clause for boxes that touch the dateline; no benchmark was run. No index format or API change, and existing indexes need no rebuild.

Route a touching box through the existing crossing branch (variant of A)

Treat a geo box with minX == -180 like a crossing box with ranges [-inf, maxX] or [180, +inf], and one with maxX == 180 like [-inf, -180] or [minX, +inf], reusing the two-SHOULD code. Not run.

Trade-offs

Same results, since no data lies beyond the world bounds (as the existing comment notes); a less obvious diff.

Store +180 as -180 at index time

#

Normalize x in createIndexableFields. Not recommended; not run.

Trade-offs

Does not fix boxes ending at +180 (the eastern hemisphere would then miss every antimeridian point), so the query side still needs A; existing indexes would have to be rebuilt.

Document that -180 and +180 are different values

#

A javadoc sentence. Not recommended.

Trade-offs

Keeps the wrong results, contradicts SpatialOperation's definition, and to get correct results callers would have to rewrite every query box that touches the dateline (the workaround above), since spatial4j itself writes edges with both signs.

Downstream note

#

Downstream: an application that uses a PointVectorStrategy box with an edge on ±180 as a MUST_NOT exclusion does not exclude opposite-sign points exactly on that edge; points off the edge, and the one crossing exclusion box tested, are handled correctly.

How it was found

#

Bounded-exhaustive comparison of the real spatial-extras jar with spatial4j's relate and an exact reference: every one of 570 grid rectangles against 35 grid points, Intersects and IsWithin. PointVectorStrategy alone missed 420 pairs per operation, all at ±180 with the other sign; code reading found the cause, and a JUnit confirmed it.

The method in full167 words

Method: semi-formal, bounded-exhaustive differential checking (hunt unit on spatial-extras, 2026-10-26, main ea57360912ed).

  • A harness enumerated every distinct geo rectangle over longitudes {-180, -170, -90, 0, 90, 170, 180} and latitudes {-90, -45, 0, 45, 90} (570 rectangles, crossing and degenerate ones included) and queried each against all 35 grid points with the exact strategies of the module.
  • Each answer was compared with two oracles: SpatialOperation.evaluate (spatial4j relate, the module's own test oracle) and an independent exact reference (closed intervals, -180 == 180).
  • PointVectorStrategy showed 420 false negatives per operation out of 19,950 pairs, every one a point at x = ±180 against a non-crossing box edge of the other sign, and 0 other mismatches; spatial4j and the reference agreed on all of them.
  • The finder read makeWithin, found the plain x range, wrote a public-API JUnit on the stock jar and a fix sketch that brought the grid to 0 mismatches. Re-run on main a9779ef3c193 for this doc: 420 stock, 0 with the fix.

History

#

Introduced in 4.0.0 by LUCENE-4351 (2012-09-05), which upgraded spatial4j from 0.2, which turned +180 into -180, to 0.3, which keeps +180; the x filter itself was unchanged. Executed on 14 releases and main: affected from 4.0.0 to 10.5.2; the 4.0.0 pre-releases and the parent commit have no silent miss (one mirror case throws there instead).

Versions tested7 rows

Introduced by LUCENE-4351 (issue #5417, "Upgrade Spatial4j to 0.3"; commit message "Update to Spatial4j 0.3"), branch_4x 6f1fde90512 and trunk 1db287ce640, 2012-09-05, by @dsmiley (SVN and JIRA-patch era, no pull request). It changed no line of the x filter. spatial4j 0.2 normalized +180 to -180 when it built a point or a box, and its relate treated the two as different, so the plain range agreed with the oracle; from 0.3 on, +180 is kept and relate treats both signs as one meridian. The parent 8dd92aa7e90 has no silent miss (the mirror case throws "Crossing dateline not yet supported" there, as in 4.0.0-ALPHA/BETA); 6f1fde90512 misses 2 of 2 cases (commit builds). Bug record

LFV-301, snapshot of 2026-10-29

Registry title
PointVectorStrategy misses a point at longitude +180 or -180 when a rectangle query that does not cross the dateline has its edge on that meridian with the other sign (-180 vs +180)
Area
spatial-extras / PointVectorStrategy (Intersects and IsWithin rectangle queries: makeWithin x filter)
Priority
Low, rank 353: The experimental PointVectorStrategy silently misses points that lie exactly on the antimeridian when a box edge has the opposite sign, a boundary-value geo miss that is rarer than LFV-316.
Impact class
silent wrong results
Impact note
Applications that index points with the @lucene.experimental PointVectorStrategy in its default geo context (SpatialContext.GEO) and run Intersects or IsWithin rectangle queries silently lose a document whose longitude is exactly +180 or -180 when the query box's edge on that meridian is written with the other sign (for example the western-hemisphere box rect(-180,0,-90,90) misses Pt(180,10)), at any index size and with default IndexWriterConfig, codec and searcher; released since 4.0.0; only missed matches, never extra ones, and circle queries are not shown to be affected.
Summary
You index a point with PointVectorStrategy in the default geo context and search it with SpatialOperation.Intersects or IsWithin and a rectangle that does not cross the dateline but has one edge on the antimeridian, expecting the point to be found whenever spatial4j's relate, which defines these predicates, says it is inside (in geo, -180 and +180 are the same meridian). Instead a point stored at x=+180 is missed by a box whose west edge is -180 (Pt(180,0) with rect(-180,-170,-10,10): 0 hits, oracle 1), and a point at x=-180 by a box whose east edge is +180 (Pt(-180,0) with rect(170,180,-10,10)). BBoxStrategy and both prefix-tree strategies in the same module return the hit; PointVectorStrategy.makeWithin filters x with one plain DoublePoint range [minX, maxX] for every non-crossing box, so +180 and -180 are different values to it.
Introduced
6f1fde90512 (branch_4x, svn r1381280; trunk equivalent 1db287ce640, svn r1381230), 'LUCENE-4351 Update to Spatial4j 0.3' (issue apache/lucene#5417), by dsmiley, no PR (SVN + JIRA patch era) [exec: the parent commit 8dd92aa7e90 is not affected, 6f1fde90512 misses 2 of 2 cases]. Behavioural introduction: the commit changed no line of the x filter; it bumped spatial4j 0.2 to 0.3. spatial4j 0.2 normalized longitude +180 to -180 in makePoint/makeRect and its relate treated the two values as different, so the plain range agreed with the oracle; from 0.3 on, +180 is kept and relate treats +/-180 as one meridian.
