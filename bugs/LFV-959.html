Lucene 11.0 (main) turns incremental doc-values updates on by default, but neither its release notes nor the migration guide say so

Lucene 10.6 ships incremental doc-values updates as opt-in; 11.0 (main and branch_11x today) turns them on by default with 8 overlays per field. Its release-note entry still says "Opt-in" and MIGRATE.md says nothing, so a 10.6-to-11.0 upgrader gets a different update write path without being told.

The finding in 30 seconds

#

Lucene 10.6 added incremental doc-values updates, off unless you turn them on. Lucene 11.0 (main and branch_11x) turns them on for everyone (DEFAULT_MAX_DOC_VALUES_OVERLAYS 0 -> 8). Main's own note saying so was moved into the 10.6.0 section and reworded to 10.6.0's correct "Opt-in" text, so the 11.0 notes say nothing.

Background: doc-values updates and overlays

#
  1. A doc-values update (IndexWriter.updateNumericDocValue, updateBinaryDocValue, updateDocValues) changes a column value of existing documents without re-indexing them.
  2. Without overlays, Lucene writes each update as a new copy of the field's whole column in that segment.
  3. With incremental updates (new in 10.6), a set-only update is written as a small sparse overlay holding only the changed documents. A field keeps up to N overlays, then folds them into one; N = 0 turns the feature off.

The finding, step by step

#
  1. On Lucene 10.6 you update a document with IndexWriter.updateNumericDocValue and a default IndexWriterConfig. Incremental doc-values updates are opt-in there (DEFAULT_MAX_DOC_VALUES_OVERLAYS = 0), so the update rewrites the field's whole column.
  2. You plan the upgrade to 11.0 (main and branch_11x today) and read the 11.0 section of CHANGES.txt and MIGRATE.md. You expect a note if this default changed, as both give one for the query cache, which 11.0 turns off by default.
  3. Instead main's default is 8 overlays per field: updating 1 of 1,000 documents writes a 402-byte sparse overlay instead of the 2,892-byte column rewrite you get with the feature off, and up to 8 overlays per field stay live, each with its own files.
  4. The feature's entry (GITHUB#16418) sits in the 10.6.0 section and says "Opt-in; enable with IndexWriterConfig#setMaxDocValuesOverlays(n)". The 11.0.0 section and MIGRATE.md have 0 lines on it. Main had an "Enabled by default" entry until two changelog edits moved it to 10.6.0 and reworded it there.
  5. Search results stay correct, so this is a missing note, not a code bug: one CHANGES line and a short MIGRATE section with the opt-out setMaxDocValuesOverlays(0) fix it.

Who is affected

#

Applications that upgrade from 10.x to 11.0, keep the default IndexWriterConfig and call the doc-values update methods. Their set-only updates silently switch to overlay files, with more live files and open file handles per field (the concern that lowered the default from 16 to 8). Results stay correct, and nothing in the 11.0 notes points them to the opt-out.

Mechanism, terms and numbers695 words

Lucene 10.6.0 added incremental doc-values updates (GITHUB#16418): a doc-values update that only sets values is written as a small sparse overlay holding just the updated documents, layered over the column at read time, instead of a rewrite of the whole column. In 10.6 the feature is off unless the application calls IndexWriterConfig#setMaxDocValuesOverlays(n) (DEFAULT_MAX_DOC_VALUES_OVERLAYS = 0). On main and branch_11x, the future 11.0, it is on by default with up to 8 overlays per field (IndexWriterConfig.java:115), deliberately: the #16418 PR says "On main the feature is on by default".

The release notes do not record that difference. The only GITHUB#16418 entry in CHANGES.txt sits in the 10.6.0 section and says "Opt-in; enable with IndexWriterConfig#setMaxDocValuesOverlays(n)" (CHANGES.txt:501-504), correct for 10.6.0. The 11.0.0 "Changes in Runtime Behavior" list has only "The query cache is now disabled by default" (:341-343), and MIGRATE.md's 10.x-to-11.0 guide has no line on overlays, although it gives the query-cache flip a section with the code to undo it (MIGRATE.md:227-236). Main had an 11.0.0 entry saying "Enabled by default; disable with IndexWriterConfig#setMaxDocValuesOverlays(0)" until ea248114ac4 (2026-09-01) moved it to the 10.6.0 section and the 10.6.0 sync 7cecf795236 (2026-10-21) reworded it to the 10.6.0 text.

An application that upgrades from 10.6 to 11.0 with a default IndexWriterConfig and uses doc-values updates therefore moves to the overlay write path, with more live files per field, and nothing in the 11.0 notes tells it. Results stay correct, and in the measured example (1 of 1,000 documents) the update wrote 402 instead of 2,892 bytes. The fix is text only: an 11.0.0 CHANGES entry and a MIGRATE.md section with the opt-out. Upstream main (now 12.0.0-SNAPSHOT, with 11.0.0 as its second section) and branch_11x still lack it on 2026-11-01.

How the 11.0 note was lost

#
  1. 75eddfaff22 (PR #16418, 2026-08-13): the feature lands on main, default 16, with an 11.0.0 entry ending "Enabled by default; disable with IndexWriterConfig#setMaxDocValuesOverlays(0)".
  2. ea248114ac4 (2026-09-01, "Rename SegmentInfos.VERSION_11_0 to VERSION_10_6", pushed without a PR): the entry moves unchanged from 11.0.0 to 10.6.0, the day the opt-in 10.x backport (#16554) lands. The 11.0.0 section now says nothing.
  3. 92d9f2c7faa (PR #16648, 2026-09-08): default 16 -> 8; its commit message says "The feature is not yet released, so no CHANGES entry is needed."
  4. 7cecf795236 (2026-10-21, "Ensure 10.6.0 changelog in main is consistent with branch_10_6", pushed without a PR): the moved entry gets 10.6.0's "Opt-in" text. Correct for 10.6.0, but no "enabled by default" wording is left in main's notes.
Exposure and likelihood271 words
  • Who. Applications that use doc-values updates (updateNumericDocValue, updateBinaryDocValue, updateDocValues; single-valued sorted-numeric updates per GITHUB#16580) and upgrade to 11.0 with a default IndexWriterConfig. No opt-in or rare setting is needed; the update methods are public and not experimental.
  • What changes. Set-only updates write sparse overlays instead of a full column (402 instead of 2,892 bytes of update files for 1 of 1,000 documents in the measured example), and up to 8 overlays per field stay live until a fold, so more files are live per field and reads merge them (IndexWriterConfig.java:110-114). #16648 lowered the default from 16 to 8 because "open file handles scale with segments times updated fields times the overlay budget", after a CI open-handle guard tripped (#16644).
  • What does not change. Search results: the updated values read back correctly in every mode an independent reproducer tested, and nothing threw in those runs.
  • Upgraders run into it. A downstream issue names this default as one of two Lucene 11 changes that affect a test failing against the Lucene 11 snapshot (elastic/elasticsearch#163787, 2026-10-28: "It also turns on doc-values overlays by default (DEFAULT_MAX_DOC_VALUES_OVERLAYS 0→8)"). It names the constant and does not cite Lucene's CHANGES or MIGRATE; the test still fails "despite the adjustments made", so the issue does not show the default to be the cause.
  • Scale. Every such upgrader whose updates only set values (updates with removals still rewrite the whole column, ReadersAndUpdates.java:363), with no data-size threshold. Unreleased: no release ships the default without a note yet; 11.0.0 would be the first. Impact class minor: a documentation defect with no wrong results.

Why it looks unintended

#
  • Lucene lists default flips: this 11.0.0 "Changes in Runtime Behavior" list has "The query cache is now disabled by default", and MIGRATE.md gives it a section.
  • Main had the note ("Enabled by default") until a commit renaming a SegmentInfos constant moved it to 10.6.0.
  • #16648 skipped an entry because the feature was "not yet released"; 10.6.0 shipped it on 2026-10-29.
The full argument254 words
  • The project's own practice. Default changes are listed under "Changes in Runtime Behavior": in this 11.0.0 section "GITHUB#14187: The query cache is now disabled by default." (CHANGES.txt:343), and earlier "GITHUB#15040: The default ReadAdvice has been changed from RANDOM to NORMAL" (10.3.0, :1739) and "GITHUB13293: Auto I/O throttling is now disabled by default on ConcurrentMergeScheduler" (10.0.0, :2403). MIGRATE.md's 11.0 guide has sections for other default changes, among them the query cache (:227-236) and the filtered-HNSW threshold (:238-244).
  • The record existed and was lost as a side effect. The 11.0.0 entry said "Enabled by default" until ea248114ac4, a commit about renaming a SegmentInfos constant, moved it to 10.6.0; the 10.6.0 sync then reworded it, correctly for 10.6.0. No PR, issue or dev@ thread found discusses leaving 11.0 without a note.
  • The one "no CHANGES entry" decision was about something else. #16648's commit message skips an entry for the 16 -> 8 step because "the feature is not yet released". It was written while main's entry still said "Enabled by default" (by then under 10.6.0), and its premise ended when 10.6.0 shipped the feature opt-in (tag 2026-10-29).
  • Upstream merges this kind of fix. #16912, "Move CHANGES entry for GITHUB#16794 from 10.6.0 to 11.0.0", was merged on 2026-10-26.
  • What is not claimed. That the code is wrong (default-on is deliberate and documented in the javadoc), that the 10.6.0 entry is wrong, that results change, or anything about soft-delete updates or BINARY updates beyond the CHANGES text (not tested separately).
The devil's-advocate check234 words

Strongest case for "intended / noise". Default-on is deliberate and documented where the API is documented: IndexWriterConfig.java:342 says "Enabled by default", the #16418 and #16554 PR texts state the main/10.x difference, and TestIncrementalDocValuesUpdates.testDefaultBudgetHeavyStackingAndFolding "Exercises the shipping default overlay budget". The setter is @lucene.experimental. CHANGES entries are optional (CONTRIBUTING.md:107: "You may want to add a CHANGES entry"), the release manager distills the release notes from CHANGES.txt before a release (dev-tools/scripts/releaseWizard.yaml:606-610), and 11.0 is unreleased. The 10.6.0 entry is correct for 10.6.0, and results never change. The cross-model refute lens argued this and rated it not real; an intended-behaviour verifier built the same case.

Why it fails. It defeats the framing "the code is wrong", which nobody claims, not the narrow claim. Nothing shows that the 11.0 record was meant to go (the history shows the edits, not their intent, and no discussion found decides it): the javadoc of an experimental setter that an upgrader keeping the defaults has no reason to call is not where upgraders look; the same section and MIGRATE.md record the analogous flips; the record existed and disappeared through two changelog edits; and the release manager's draft starts from CHANGES.txt, so an explicit entry is the direct way into it. The refute lens conceded that neither the 11.0 CHANGES nor MIGRATE records the change. The adjudication ruled that these points go to severity (minor), not to reality.

Downstream note

#

Search servers and other projects built on Lucene that rely on the default IndexWriterConfig inherit the overlay write path when they move to Lucene 11, and may want to set setMaxDocValuesOverlays explicitly or mention the change in their own upgrade notes.

How it was found

#

A hunt unit that checked the 10.6.0 CHANGES claims against the release candidate also compared main's notes with main's code. It saw the default 8 under an "Opt-in" note, confirmed the difference with a test that runs the same one-document update with the default config and with the feature off, and traced the note's history in git.

The method in full124 words

Method: non-formal. The oracle is the release notes plus the 10.6 behaviour, checked by reading and a differential test; no model, proof or bounded-exhaustive check took part.

  • The unit's optional main-only part started from a note that main defaults to 8 overlays with no 11.0 CHANGES or MIGRATE entry.
  • The finder compared CHANGES.txt, MIGRATE.md and IndexWriterConfig on main and on the 10.6.0 release-candidate jars, and wrote a public-API JUnit: the same one-document update with a plain new IndexWriterConfig() and with setMaxDocValuesOverlays(0).
  • It traced the provenance of the entry in the full git history; a verifier corrected the introducing commit to ea248114ac4.
  • Because a missing note cannot be unit-tested, a read-only check replaced the JUnit as the minimal repro (this doc's repro).

LFV-959, snapshot of 2026-11-09

Registry title
Main (the future 11.0) turns incremental doc-values updates on by default (IndexWriterConfig.DEFAULT_MAX_DOC_VALUES_OVERLAYS = 8; opt-in, 0, in 10.6), but neither the 11.0.0 section of CHANGES.txt nor MIGRATE.md records the change: the only note is the 10.6.0 'Opt-in' entry, because main's 'Enabled by default' note was moved to 10.6.0 and then reworded (documentation defect, unreleased)
Area
release notes (lucene/CHANGES.txt 11.0.0, lucene/MIGRATE.md 10.x -> 11.0) x index / doc-values updates (IndexWriterConfig#DEFAULT_MAX_DOC_VALUES_OVERLAYS, GITHUB#16418, GITHUB#16648)
Priority
Low, rank 1306: The release notes and MIGRATE.md omit a default change on unreleased main that every 11.0 doc-values-update user meets while results stay correct.
Impact class
minor
Impact note
Only main and branch_11x (unreleased 11.0) are affected: an application that upgrades from 10.6 to 11.0, keeps the default IndexWriterConfig and uses the doc-values update APIs (set-only NUMERIC and BINARY updates, and single-valued SORTED_NUMERIC updates per GITHUB#16580) silently moves from whole-column rewrites to up to 8 sparse overlay generations per field (more live files per field, the concern of GITHUB#16644), and no CHANGES or MIGRATE text tells it; search results stay correct, nothing fails, no scale is needed, and the fix is a release-notes entry, not code.
Summary
You upgrade from Lucene 10.6 to 11.0 and use doc-values updates (for example IndexWriter.updateNumericDocValue) with a default IndexWriterConfig; you expect the 11.0 release notes or the migration guide to say so if the default write path changed, as they do for the query cache, which 11.0 turns off by default. Instead main turns incremental doc-values updates on by default (DEFAULT_MAX_DOC_VALUES_OVERLAYS = 8, against 0 in 10.6), so a one-document update writes a small sparse overlay (402 bytes of update files in the repro) instead of rewriting the column (2892 bytes), yet the only CHANGES.txt entry for the feature is the 10.6.0 one, which says 'Opt-in; enable with IndexWriterConfig#setMaxDocValuesOverlays(n)', and MIGRATE.md says nothing. Main did carry an 'Enabled by default' note until it was moved into the 10.6.0 section and then, correctly for 10.6.0, reworded to the release candidate's text.
