MemoryIndex.addField throws AssertionError for a KnnFloat16VectorField when assertions are enabled: a stale assertion in storeVectorValues predates the FLOAT16 branch

With Java assertions on, as in Lucene's own test runs, adding any KnnFloat16VectorField to a MemoryIndex throws AssertionError, because the first line of storeVectorValues still allows only float32 and byte vector fields. With assertions off the vector is stored and read back exactly; only unreleased main and 11.0 have it.

The finding in 30 seconds

#

MemoryIndex is Lucene's one-document, in-memory index. Its vector code has one branch per encoding, but the check on its first line still lets only the two older vector field classes through.

Background: MemoryIndex and vector fields

#
  1. MemoryIndex holds a single document in memory. You add fields with addField (or build it with fromDocument) and search it like a one-document index; lucene/monitor uses it to match one document against stored queries.
  2. Vector fields come in one class per encoding: KnnFloatVectorField (float32), KnnByteVectorField (byte) and, on main since #16383, KnnFloat16VectorField (float16, values as short[]). Each extends Field directly; none is a subclass of another.
  3. MemoryIndex keeps one vector per field and returns it through getFloatVectorValues, getByteVectorValues or getFloat16VectorValues on its reader. It runs no kNN search for any encoding.

The finding, step by step

#
  1. Run a test with assertions on (Lucene's gradle build does for most seeds). Add one 1-dimensional float16 vector to an empty MemoryIndex: addField(new KnnFloat16VectorField("v", new short[] {Float.floatToFloat16(1f)}, EUCLIDEAN), null).
  2. You expect it to be stored like a float32 or byte vector: getFloat16VectorValues("v").vectorValue(0) should return an equal 1-element vector, 1.0 in half precision. MemoryIndex has code for exactly this since float16 vectors were added.
  3. Instead addField throws java.lang.AssertionError, with no message, at MemoryIndex.java:794, and no vector is stored (the field itself is already registered, with no values). MemoryIndex.fromDocument and Monitor.match on a single document fail the same way.
  4. Why: storeVectorValues starts with assert vectorField instanceof KnnFloatVectorField || vectorField instanceof KnnByteVectorField;, written in 2024 when those were the only two vector field classes. KnnFloat16VectorField is neither, so the FLOAT16 branch right below is never reached.
  5. With assertions off, the JVM default, the same test passes and the vector reads back exactly. Adding || vectorField instanceof KnnFloat16VectorField to the assertion fixes it.

Who is affected

#

Anyone who puts a KnnFloat16VectorField into a MemoryIndex with assertions on: direct addField or fromDocument, or Monitor.match on one document. In practice that means test runs, Lucene's own and applications'. With assertions off, the JVM default, it works. Only unreleased main and 11.0 have the float16 field.

Mechanism, terms and numbers535 words

MemoryIndex.addField(IndexableField, Analyzer) stores a vector field through the private storeVectorValues (MemoryIndex.java:677-679, :793), whose first statement is assert vectorField instanceof KnnFloatVectorField || vectorField instanceof KnnByteVectorField; (:794). #13633 wrote it in 2024 (first released in 9.12.0), when those were the only vector field classes, and it was correct then. #16383 (2026-07-27, unreleased 11.0.0) added KnnFloat16VectorField, which extends Field and is not a KnnFloatVectorField, together with a case FLOAT16 arm in the same method (:819-840), the MemoryIndex reader's getFloat16VectorValues (:1782-1789) and MemoryFloat16VectorValues (:2425), but did not widen the assertion and added no MemoryIndex test. So with -ea, adding any float16 vector field to a MemoryIndex (directly, through fromDocument, or through Monitor.match on one document) throws a message-less AssertionError before the FLOAT16 arm runs. With -da the arm stores the vector and it reads back exactly. Only test runs are affected, and of the upstream refs inspected only main and branch_11x have the code. The fix is one line.

Terms

#
  • storeVectorValues(Info, IndexableField) (MemoryIndex.java:793-865): the private method addField calls when the field type has vectorDimension() > 0 (:677-679). It switches on the field's VectorEncoding (:795), with one arm per encoding: BYTE (:796-817), FLOAT16 (:819-840) and FLOAT32 (:842-863). Each arm checks the field's class, allows one value per field, and copies the vector.
  • KnnFloat16VectorField (lucene/core/.../document/KnnFloat16VectorField.java): public class KnnFloat16VectorField extends Field (:37, @lucene.experimental at :35), whose field type has VectorEncoding.FLOAT16 (:55).

The bug

#
  1. addField (:620) creates the field's FieldInfo from the field type (getInfo at :622, createFieldInfo at :759-783), so the encoding is FLOAT16, and calls storeVectorValues (:678). Every fromDocument overload loops over the document's fields calling addField (:571-573).
  2. The method's first statement is assert vectorField instanceof KnnFloatVectorField || vectorField instanceof KnnByteVectorField; (:794). For a KnnFloat16VectorField both are false, so with -ea it throws java.lang.AssertionError (no message) before any vector value is stored. The field is already registered by then: getInfo put its Info and FieldInfo into the field map (:740-744), so a caller that catches the error is left with a field that FieldExistsQuery matches and getFloat16VectorValues returns null for (executed probe).
  3. With -da the assertion is skipped: the FLOAT16 arm checks instanceof KnnFloat16VectorField, copies the short[] into the field's float16 state (:1273, :1279), and the reader returns it through getFloat16VectorValues (:1782-1789) and MemoryFloat16VectorValues (:2425).
  4. The assertion adds no check the arms lack for the vector field classes: each arm already throws IllegalArgumentException for a field of the wrong class (:813-816, :836-839, :859-862). Its only other effect, with -ea, is that a custom IndexableField with vector attributes that is none of the listed classes fails there with AssertionError instead of the arm's IllegalArgumentException (read).

The numbers

#

One field, one dimension, value Float.floatToFloat16(1f): with -ea, 1 test run, 1 failure at MemoryIndex.java:794 (gradle and standalone, seeds DEADBEEF and 5EED1234); with -da, 1 run, 0 failures and an exact read-back. Nothing depends on data, size, codec or threads.

Exposure and likelihood299 words
  • Who is hit. Code that adds a KnnFloat16VectorField to a MemoryIndex on a JVM with -ea: MemoryIndex.addField, every MemoryIndex.fromDocument overload, and lucene/monitor's Monitor.match(Document, ...) for a single document, which builds a SingletonDocumentBatch that calls addField for every field (DocumentBatch.java:107-113). A public-API probe executed for this doc: with -ea, Monitor.match throws AssertionError from MemoryIndex.java:794 via DocumentBatch$SingletonDocumentBatch.<init>(DocumentBatch.java:110) and DocumentBatch.of(DocumentBatch.java:59); with -da the registered query matches (1 match). Multi-document Monitor batches go through IndexWriter and are not affected (read). The highlighters feed MemoryIndex token streams, not fields, so they are not affected (read).
  • When. Test runs. Lucene's gradle build enables assertions for about 75% of project seeds by default (TestsAndRandomizationPlugin.java:240-248), and LuceneTestCase requires -ea to match -Dtests.asserts (TestRuleAssertionsRequired.java:36-54). Any application test suite run with -ea sees it too: a test that adds a valid float16 field through one of these paths fails.
  • Production is fine. With -da the vector is stored and read back exactly at every affected commit tested (bfe5c847d3c, ea57360912ed, 645d4fe14a20). A service running production JVMs with -ea (unusual) would lose one operation per document with the field; AssertionError is an Error, so catch (Exception e) does not catch it (executed probe).
  • Why Lucene's tests miss it. lucene/memory/src/test has no float16 test, and no test elsewhere puts a float16 field into a MemoryIndex (read, grep).
  • Scale. Deterministic: every float16 vector field that can be constructed (any dimension and similarity; the constructor itself rejects a null or empty vector, a null similarity and a zero vector with COSINE, KnnFloat16VectorField.java:39-53), on the first call. Unreleased: main and branch_11x only, of the refs inspected; KnnFloat16VectorField is @lucene.experimental. No downstream product was tested; one downstream project is still discussing whether to expose float16 at all (elastic/elasticsearch#163176).

More files, environment, full output254 words

The test sits in org.apache.lucene.index.memory next to TestMemoryIndex; it uses only public API, so it needs no package-private access. The failure is Lucene's own message-less AssertionError, so the comment line on the failing call states expected versus actual. As the regression test: the same test, with its comment line wrapped (below), as the first float16 test in lucene/memory/src/test/org/apache/lucene/index/memory/; if the maintainers prefer, the same method can go into the existing TestMemoryIndex next to its float32 and byte vector tests (:769, :824). Its one comment line is longer than 100 columns, which google-java-format (:lucene:memory:check) flags; with the line wrapped the module's checks pass and the test behaves the same.

Not shown by this test, same root cause, executed elsewhere: MemoryIndex.fromDocument (the finder's second test) and Monitor.match on one document (a reach probe).

Why it looks unintended

#
  • #16383 added float16 storage to MemoryIndex on purpose, including a FLOAT16 branch in this very method; the assertion above it makes that branch unreachable with -ea.
  • The assertion dates from 2024, before float16 existed; no javadoc, note or test excludes float16.
  • IndexWriter accepts the same field with assertions on.
The full argument211 words
  • Deliberate support. #16383's MemoryIndex.java diff (+110/-0) adds the KnnFloat16VectorField import, the case FLOAT16 arm with its own one-value and wrong-class checks, the float16 Info state, getFloat16VectorValues and MemoryFloat16VectorValues with a scorer. The unchanged assertion on the method's first line contradicts all of it.
  • The migration note asks for this update. lucene/MIGRATE.md:629-638 ("IEEE FLOAT16 vector APIs (GITHUB#16383)"): "Custom readers and exhaustive VectorEncoding switches need a FLOAT16 arm." This switch got its arm; its guard did not.
  • History. The assertion came with #13633 (9e831ee8097, 2024-08-07, "Add float|byte vector support to memory index", first released in 9.12.0), correct when only two vector field classes existed. #16383 did not touch it, and none of its review discussion mentions MemoryIndex. The earlier, unmerged fp16 PR #15549 had the same omission.
  • No exclusion anywhere. The addField javadoc (MemoryIndex.java:613-619) names no unsupported field type; no CHANGES.txt or MIGRATE.md entry excludes MemoryIndex; no test expects the error, and lucene/memory/src/test has no float16 test. TestMemoryIndex tests the float32 and byte vector fields (:769, :824 and their round-trip helpers).
  • Elsewhere it works. IndexWriter indexes the same float16 field with -ea (verifiers' controls).
  • Precedent. #15334 fixed an NPE in the MemoryIndex vector path as a bug although MemoryIndex has no kNN search (lucene/CHANGES.txt:1493-1494, 10.4.0).
The devil's-advocate check244 words

The case for intended: (1) the failure is assertion-only, so production with -da is unaffected; (2) KnnFloat16VectorField is @lucene.experimental and float16 support is openly incomplete (tracker #16725); (3) MemoryIndex runs no kNN search for any encoding (searchNearestVectors are no-ops, MemoryIndex.java:1800-1811; TestMemoryIndex.java:819: "we don't really do knn search right now for MemoryIndex"), so its vector support is partial anyway; (4) the assertion could be read as a precondition that only the float32 and byte classes may reach storeVectorValues.

Why it fails: (a) the float32 and byte classes carry the same @lucene.experimental tag (KnnFloatVectorField.java:38, KnnByteVectorField.java:38) and are supported and tested in MemoryIndex; (b) if float16 were meant to be excluded, #16383 would not have written a FLOAT16 arm, state, reader and values class for MemoryIndex; (c) the missing kNN search applies to every encoding and concerns searching, not storing; (d) nothing supports the precondition reading: the assertion predates the class it rejects; (e) "assertion-only" lowers the severity, not the validity: the assertion itself is the defect, and it fires in the configuration Lucene's tests use. The cross-model reviews rated the intended argument weak; the devil's advocate and the adjudication rejected it. A later cross-model fact check of this doc rated the same points moderate as a case that the defect is low-value and not worth an issue of its own, and weak as a case that it was designed so: two different questions. Verdict: not intended; a low-severity oversight.

Suggested fix

#

Recommended A. Widen the assertion to the float16 field class

Add || vectorField instanceof KnnFloat16VectorField to the assertion at the top of storeVectorValues (the class is already imported). Validated with gradle: the repro passes, and so do all 52 lucene/memory tests. Dropping the assertion also works, since each branch already rejects a wrong field class.

Downstream note

#

Applications that feed documents with float16 vector fields to MemoryIndex or Monitor see this only in assertion-enabled runs, typically their test suites; production JVMs without -ea are unaffected.

How it was found

#

Non-formal: a differential edge probe. The hunt on float16 vectors ran the same edge cases through float16 and float32 vector fields across Lucene's APIs; the MemoryIndex case failed only with assertions on, and the failing frame pointed at the assertion. Independent reproducers, an adjudication and reviewers from another model family then confirmed it.

The method in full131 words

Method: non-formal (a differential JUnit, not a model or a bounded-exhaustive check). The hunt unit on float16 vectors wrote edge probes that run a float16 field and its float32 twin through the same APIs and compare the outcomes. TestFp16Probes#testMemoryIndex failed with -ea and passed with -da; reading the failing frame (MemoryIndex.java:794) gave the root cause.

The finder wrote a two-test repro (addField, fromDocument): 2/2 fail with -ea, 2/2 pass with -da and with the one-line fix. It was then reviewed by a reviewer from another model family (OpenAI GPT-5.6, refute and works-as-designed lenses), reproduced by independent verifiers (one from a package outside Lucene, with float32 and byte controls), judged, traced through history, cut to the one-test repro on 645d4fe14a20, and reviewed again there.
