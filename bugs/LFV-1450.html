QuantizedByteVectorValues.getCorrectiveTerms documents the EUCLIDEAN corrective term as the l2 norm, but Lucene stores and scores with the squared l2 norm (javadoc only)

The getCorrectiveTerms javadoc calls the EUCLIDEAN corrective term "the l2norm of the centered vector", but Lucene stores and scores with its square: an implementation that follows the javadoc scores a document at squared distance 25 as 1/6, not 1/26. Lucene's own formats are right; the public javadoc has been wrong since 10.4.0.

The finding in 30 seconds

#

Documentation only: the code is intended and correct, and Lucene's own formats store the right value. One word, "squared", is missing from the javadoc.

Background: corrective terms

#
  1. Scalar quantization stores each vector x as small integers measured from a centroid c (the field's mean vector), plus a few float corrective terms per vector that let the scorer turn integer dot products back into real scores.
  2. For EUCLIDEAN the scorer uses ||x - q||^2 = ||x - c||^2 + ||q - c||^2 - 2 <x - c, q - c>. The per-vector term it needs is therefore the squared length ||x - c||^2, not the length ||x - c||.

The finding, step by step

#
  1. Lucene's scalar quantization keeps four corrective numbers per vector. For EUCLIDEAN, the QuantizedByteVectorValues.getCorrectiveTerms javadoc says the third is "the l2norm of the centered vector": the length of x - c, where c is the field's centroid.
  2. You write your own QuantizedByteVectorValues (a public, experimental extension class) for one vector x = (4, 5) with centroid c = (1, 1), and return the documented value: ||(3, 4)|| = 5.
  3. You score the query q = (7, 9) with Lucene's public Lucene104ScalarQuantizedVectorScorer. The true squared distance is 3^2 + 4^2 = 25, so you expect the EUCLIDEAN score 1 / (1 + 25) = 0.0385.
  4. You get 1/6 = 0.1667. The scorer computes the squared distance as ||q - c||^2 + term - 2 <x - c, q - c> = 100 + 5 - 2 x 50 = 5. It needs the squared norm 25, which is what Lucene's own quantizer stores (13, not sqrt(13) = 3.61, for a centered vector (2, 3)).

Who is affected

#

Only developers who implement the public, experimental QuantizedByteVectorValues and compute the corrective terms themselves, or who read the terms and treat the EUCLIDEAN one as a plain norm. Their EUCLIDEAN scores are silently wrong. Lucene's own formats, and implementers that pass OptimizedScalarQuantizer's result through, are not affected.

Mechanism, terms and numbers506 words

The QuantizedByteVectorValues.getCorrectiveTerms javadoc lists the four corrective terms Lucene's optimized scalar quantization keeps per vector and is the only public text that defines the third (EUCLIDEAN) one: "the l2norm of the centered vector". OptimizedScalarQuantizer stores the squared norm there, and the public Lucene104ScalarQuantizedVectorScorer computes squared distances from it, so a developer who implements QuantizedByteVectorValues and supplies the documented value gets silently wrong EUCLIDEAN scores: 1/6 instead of 1/26 for a document at squared distance 25. The code is intended and correct; the fix adds the word "squared". Public since 10.4.0; not fixed upstream.

The javadoc

#

QuantizedByteVectorValues is a public abstract class (QuantizedByteVectorValues.java:25-27, @lucene.experimental). Its getCorrectiveTerms javadoc (:186-211) lists the terms in order. For the dot-product family (:187-195): the lower and upper optimized interval, the dot product of the non-centered vector with the centroid, and the sum of quantized components; that list is right. For EUCLIDEAN (:197-204): the lower and upper optimized interval, "the l2norm of the centered vector" (:202), and the sum of quantized components.

No other public text defines the term: the QuantizationResult record calls it "the additional correction" (OptimizedScalarQuantizer.java:101) and the file-format javadoc "an additional similarity dependent corrective factor" (Lucene104ScalarQuantizedVectorsFormat.java:71-72).

The code

#
  1. OptimizedScalarQuantizer.scalarQuantize (:187) centers the vector (:205), accumulates norm2 += (vector[i] * vector[i]) (:208) and returns new QuantizationResult(..., similarityFunction == EUCLIDEAN ? norm2 : centroidDot, ...) (:232-236): the squared norm. multiScalarQuantize does the same (:135, :138, :169-173).
  2. Lucene104ScalarQuantizedVectorScorer (public, :41) accepts any QuantizedByteVectorValues (getRandomVectorScorer, :59-70). It quantizes the query with the values' own quantizer and centroid (:102-119), so with a EUCLIDEAN quantizer (as in Lucene's formats and the repro) the query side carries ||q - c||^2.
  3. quantizedScore (:261-301), for EUCLIDEAN: the comment says the additional correction is "assumed to be the squared l2norm of the centroid centered vectors" (:292-293); then score = query.additionalCorrection() + index.additionalCorrection() - 2 * score and return 1 / (1f + Math.max(score, 0f)) (:294-301). That identity holds only for squared norms.

The numbers

#

Centroid c = (1, 1), document x = (4, 5), query q = (7, 9): x - c = (3, 4), q - c = (6, 8), <x - c, q - c> = 50, ||q - c||^2 = 100. The scorer computes 100 + term - 100 = term. With the documented norm 5 that is a squared distance of 5 and the score 1/6 = 0.16666667; with the squared norm 25 it is the true 25 and the score 1/26 = 0.03846154 (executed; the arithmetic is the scorer's formula). Lucene's own quantizer, for EUCLIDEAN documents (0, 0) and (4, 6) with centroid (2, 3), stores 13.0 = ||(2, 3)||^2, not sqrt(13) = 3.6055512 (the finder's index-backed test, supporting only: it reads the term through the @lucene.internal CodecReader.getVectorReader).

The same sentence is on the package-private backward-codecs lucene102/BinarizedByteVectorValues.java:46 (class at :28), which users cannot see or implement.

Exposure and likelihood311 words
  • Who. Authors of a custom or downstream quantized vector format that implements QuantizedByteVectorValues and reuses Lucene104ScalarQuantizedVectorScorer, and who compute or carry the corrective terms themselves (for example an offline quantization pipeline). Also code that reads the terms: since 10.5.0 the codec-specific, @lucene.experimental Lucene104ScalarQuantizedVectorsReader.getQuantizedVectorValues returns these values (:510); a reader who squares the documented "norm" to get a distance gets ||x - c||^4.
  • What goes wrong. For such an implementation or reader: silently wrong EUCLIDEAN scores, no exception, 1/6 instead of 1/26 in the repro. In general the scorer's squared distance is an estimate d'^2 from the quantized codes, clamped at 0 (Lucene104ScalarQuantizedVectorScorer.java:290-301); supplying sqrt(s) instead of the squared centered norm s turns it into max(d'^2 - s + sqrt(s), 0). The error depends on each document's own norm, so the order of results can change too (worked out from the formula, not run). In the repro the estimate is exact up to float rounding, because both 2-d vectors quantize to the ends of their 8-bit intervals (codes 0 and 255), so the reconstructed dot product is exactly 50 (executed).
  • Not affected. Lucene's own formats (default or opt-in), their scores and search results, with assertions on or off. Implementers that pass OptimizedScalarQuantizer's QuantizationResult through unchanged: the intervals an implementer needs come from that quantizer, and its result already holds the squared norm. The only in-tree implementer outside the lucene104 format itself, the sandbox de-duplicating format (#16506, DedupScalarQuantizedVectorValues), does this and documents "the additional correction holds the squared norm" (DedupQuantizer.java:66).
  • Scale. Opt-in, expert, codec-level API (@lucene.experimental since 10.5.0; in 10.4.0 the class had no tag). No report of it was found. The repro hand-replaces only the third term in a result the quantizer made; a normal implementation passes the whole QuantizationResult through, which is the main reason real exposure is rare. Hence Low.

Why it looks unintended

#
  • The value is intended: the quantizer has stored the squared norm since its first commit, and the scorer's comment says "assumed to be the squared l2norm".
  • Lucene's own text says "squared l2norm" for the square and "l2-norm" for the plain norm; this javadoc is the only public definition of the term.
  • No test or review discusses the sentence.
The full argument121 words
  • Intended value. OptimizedScalarQuantizer has stored norm2 = sum((x_i - c_i)^2) for EUCLIDEAN since the first commit of this quantizer (#14078, 8856a5f4eb7), and the scorers are written for it. The sentence was written in that same commit, so it was wrong from the start rather than left behind by a code change.
  • Vocabulary. "squared l2norm" (Lucene104ScalarQuantizedVectorScorer.java:293), "squared norm of the vector" (OptimizedScalarQuantizer.java:306, :333), "the centroid square magnitude" (Lucene104ScalarQuantizedVectorsFormat.java:93), while VectorUtil.l2normalize divides "by its l2-norm" (VectorUtil.java:201), the plain norm.
  • Tests. TestLucene104ScalarQuantizedVectorsFormat.java:350-351 and TestOptimizedScalarQuantizer.java:280-282 compare the stored term with scalarQuantize output, never with a norm, which is why no test caught the text. No review comment on #14078, #15169, #15622 or #15783 discusses it.
The devil's-advocate check129 words

The strongest defence: "l2norm" is loose shorthand on an experimental expert API, implementers pass the quantizer's result through, and no Lucene output is wrong, so this is a cosmetic nit.

Why it fails: the javadoc is the only public definition of a number implementers must supply and readers must interpret; the word it uses means the plain norm elsewhere in Lucene; and following it gives a value off by a square and silently wrong scores from Lucene's own public scorer. That is a wrong definition, not a wording nit. The defence is right about reach, though: the intended flow passes the quantizer's whole result through, so few implementers can hit it (tiny audience, no wrong Lucene output), which is why it is Low; the devil's-advocate check called it noise-borderline.

You implement the public abstract QuantizedByteVectorValues for a EUCLIDEAN field and, as getCorrectiveTerms' javadoc says, return 'the l2norm of the centered vector' as the third corrective term: 5 for the vector (4, 5) with centroid (1, 1). Lucene's public Lucene104ScalarQuantizedVectorScorer then scores the query (7, 9), whose true squared distance to (4, 5) is 25, as 0.16666667 (1/6) instead of 0.03846154 (1/26), because it computes the squared distance as queryCorrection + indexCorrection - 2 * dot and needs the squared norm 25 there; Lucene's own quantizer indeed stores the squared norm (13.0, not sqrt(13) = 3.6055512, for a centered vector (2, 3)). The code is intended and correct; only the javadoc, which omits the word 'squared', is wrong.
