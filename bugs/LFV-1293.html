Closing a VerifyingLockFactory lock twice throws AlreadyClosedException instead of doing nothing

A lock from VerifyingLockFactory does not remember that it was closed: a second close() re-checks the inner lock it already released and throws AlreadyClosedException, although Lock is Closeable and every other core lock ignores a second close.

The finding in 30 seconds

#

CheckedLock.close() is try (Lock l = lock) { l.ensureValid(); verify(RELEASED); }, with no closed flag. The first call releases the inner lock. The second runs the same code, and the inner lock's ensureValid() throws because it is already released.

Background in three steps

#
  1. LockStressTest checks a lock implementation: client JVMs take and release one lock in a loop and report each step to a LockVerifyServer, which fails if two clients ever hold the lock at once.
  2. Each client wraps its real (inner) lock factory in VerifyingLockFactory. Its lock, CheckedLock, sends "acquired" (byte 1) after taking the inner lock and "released" (byte 0) before releasing it, and waits for the server's echo each time.
  3. Lock implements Closeable: closing a lock that is already closed must have no effect.

The finding, step by step

#
  1. Wrap a SingleInstanceLockFactory in VerifyingLockFactory, with server streams that echo "acquired" (byte 1) and "released" (byte 0), and obtain test.lock.
  2. Call close(). It checks the inner lock, sends "released" (byte 0), gets the echo and releases the inner lock. All fine.
  3. Call close() again. You expect nothing to happen: Lock is Closeable, and the other core locks return early when already closed.
  4. Instead it throws AlreadyClosedException: Lock instance already released: CheckedLock keeps no closed flag, so it runs ensureValid() again on the released inner lock. With NoLockFactory inside it sends a second "released" byte instead ([1, 0, 0]).

Who is affected

#

Only code that wraps a lock factory in VerifyingLockFactory, the lock-testing wrapper, and then closes a lock twice, for example by closing a CheckIndex twice. LockStressTest closes each lock once. The lock is already released, so nothing stays held; only the error is wrong. Default IndexWriter locking does not use this class.

Mechanism, terms and numbers431 words

Lock implements Closeable, so a second close() must have no effect, and every other core Lock follows that. The lock returned by VerifyingLockFactory, the wrapper that LockFactory's javadoc suggests for testing a lock implementation with LockVerifyServer and LockStressTest, does not: its CheckedLock keeps no closed state, so a second close() runs the release path again and calls ensureValid() on the inner lock that the first close() already released.

With SingleInstanceLockFactory, NativeFSLockFactory or SimpleFSLockFactory inside, that throws AlreadyClosedException: Lock instance already released. With NoLockFactory inside, whose ensureValid() never throws, the second close sends a second "released" message to the verify server instead. Nothing is lost (the first close released the lock), and default IndexWriter locking does not use this class. The fix is a closed flag with an early return, as SingleInstanceLock has.

The bug

#
  1. CheckedLock has one field, the inner lock, and no closed state (VerifyingLockFactory.java:41-47).
  2. close() is try (Lock l = lock) { l.ensureValid(); verify((byte) MSG_LOCK_RELEASED); } (:54-60).
  3. First call: ensureValid() passes, "released" (byte 0) is sent and echoed, and try-with-resources closes the inner lock, which marks itself closed (SingleInstanceLockFactory.java:67-80).
  4. Second call: the same code runs again. ensureValid() on the closed inner lock throws AlreadyClosedException("Lock instance already released: " + this) (SingleInstanceLockFactory.java:54-56); try-with-resources then closes the inner lock once more, which returns at once (:68-69), and the exception leaves CheckedLock.close() at VerifyingLockFactory.java:57.

Other inner locks

#

NativeFSLock and SimpleFSLock throw the same message from ensureValid() once closed (NativeFSLockFactory.java:171-172, SimpleFSLockFactory.java:96-97; by reading). NoLock.ensureValid() does nothing (NoLockFactory.java:42-47) and close() writes MSG_LOCK_RELEASED on every call, so there the second close sends a second byte 0: a JUnit probe with in-memory streams saw [1, 0, 0] sent instead of [1, 0]. A real LockVerifyServer treats a "released" from a client that does not hold the lock as a locking error (LockVerifyServer.java:102-111; by reading). This is an edge case of the wrapper and its protocol only: LockStressTest accepts only an FSLockFactory (LockStressTest.java:149-165), so it cannot run with NoLockFactory.

Through an ordinary caller

#

Directory.obtainLock returns this lock unchanged, and CheckIndex.close() closes its write lock on every call (CheckIndex.java:493-497). Closing a CheckIndex twice on a directory that uses VerifyingLockFactory throws the same exception; with a stock SingleInstanceLockFactory it does not (an independent probe: 2 tests, 1 failure). This needs a directory deliberately set up with VerifyingLockFactory and a repeated close(): it shows the path is reachable through public APIs, not that it is a common one.

Exposure and likelihood156 words
  • Who: only code that wraps a LockFactory in VerifyingLockFactory, which LockFactory's javadoc suggests for testing a lock implementation (LockFactory.java:34-36), and then closes a lock twice, directly or through a Closeable owner that re-closes its lock, such as CheckIndex (CheckIndex.java:493-497).
  • Not hit: LockStressTest, the only in-tree user, closes each lock exactly once with try-with-resources (LockStressTest.java:121, :126). Default IndexWriter locking does not use this class.
  • Effect: a loud exception from a redundant close. The first close already released the lock and reported it, so no lock stays held and mutual exclusion is not weakened. With a NoLockFactory inner lock (possible through the public constructor, not through LockStressTest), the duplicate "released" message would make a real verify server report a locking error that did not happen (by reading).
  • Scale: none; one lock, one extra close().
  • Likelihood: rare; no public report of it was found since 5.3.0 (2015).

Why it looks unintended

#
  • Lock implements Closeable, and Lock.close()'s javadoc inherits Closeable's "If the stream is already closed then invoking this method has no effect".
  • SingleInstanceLock, NativeFSLock and SimpleFSLock return early when closed; BaseLockFactoryTestCase.testDoubleClose: "close again, should be no exception".
  • The change that wrote this code (LUCENE-6508, #7567) stated "close() must be idempotent, so we still need the state".
The full argument216 words
  • The contract: public abstract class Lock implements Closeable (Lock.java:36); the description in Lock.close()'s javadoc ends with {@inheritDoc} (:45), so it carries Closeable.close's "If the stream is already closed then invoking this method has no effect". (AutoCloseable's javadoc contrasts itself with exactly this: unlike Closeable.close, its close is not required to be idempotent.)
  • Every other core lock does it: SingleInstanceLock, NativeFSLock and SimpleFSLock are synchronized close() { if (closed) return; ... } (SingleInstanceLockFactory.java:67-70, NativeFSLockFactory.java:200-203, SimpleFSLockFactory.java:110-113); NoLock.close() is empty.
  • The shared test requires it: BaseLockFactoryTestCase.testDoubleClose: l.close(); // close again, should be no exception (BaseLockFactoryTestCase.java:80-90). No test runs VerifyingLockFactory through it (the wrapper needs a server).
  • The change that wrote this code stated the rule: LUCENE-6508 (#7567) added today's CheckedLock.close(), the {@inheritDoc} and testDoubleClose in one commit (fe6c3dc9397). On that issue Uwe Schindler wrote (2015): "the Closeable interface should still be implemented correctly: close() must be idempotent, so we still need the state". Earlier, LUCENE-6124 (#7186, "Fix broken close() methods", Robert Muir, 2014) opened by quoting Closeable's "has no effect" rule and fixed double-close failures in codec and store code.
  • Nothing allows it: no javadoc, test, CHANGES or MIGRATE entry says a verifying lock may be closed only once.
The devil's-advocate check330 words

The strongest case for "intended": Lock is tagged @lucene.internal (Lock.java:34); VerifyingLockFactory is a single-purpose diagnostic whose only user closes each lock once; its constructor documents the streams as the LockVerifyServer socket (VerifyingLockFactory.java:77-78), while the repro uses in-memory streams; Lock.close()'s javadoc warns that "exceptions thrown from close may require human intervention, as it may mean the lock was no longer valid" (Lock.java:41-43); a strict verifier might want to flag a duplicate release; and the failure is loud and comes after the lock is released. An independent reviewer from another model family (OpenAI GPT-5.6) rated it not a bug, mainly because Lock is @lucene.internal and the test uses in-memory streams instead of the documented server socket, while reproducing it, agreeing on the root cause and calling it "likely worth a tiny hardening patch".

Why it fails: @lucene.internal is about API stability, not an exemption from the Closeable contract the class declares; Directory.obtainLock is public and returns this lock, and VerifyingLockFactory itself is public, untagged and recommended by LockFactory's javadoc. A real server socket would change nothing: ensureValid() throws before any stream I/O. Read with ensureValid()'s javadoc (its examples of an invalid lock are outside causes: a lock file deleted by hand, a network file system, Lock.java:54-56) and with the sibling locks, the "no longer valid" warning does not establish that a normal second close should fail: the three core locks whose ensureValid() throws once closed all return early from a second close. As for a strict verifier: the wrapper's documented job is checking that two processes never hold the lock at once (class javadoc, VerifyingLockFactory.java:24-27), not policing redundant closes, while Closeable's inherited "has no effect" rule, the three sibling locks and testDoubleClose all require a second close to do nothing. What remains is an impact argument, and it is why this is Low. It is a small Closeable-contract fix in a diagnostic class, with no effect on IndexWriter locking.

Suggested fix

#

Recommended A. A closed flag with an early return (validated)

Give CheckedLock a closed flag and make close() synchronized, returning at once when already closed and setting the flag before releasing, as SingleInstanceLock does: +6/-1 in VerifyingLockFactory.java. The repro passes with assertions on and off; the six lock-factory test classes (36 tests), the repro, and the format and lint checks pass.

@Override
public synchronized void close() throws IOException {
  if (closed) {
    return;
  }
  closed = true;
  try (Lock l = lock) {
    l.ensureValid();
    verify((byte) MSG_LOCK_RELEASED);
  }
}
All options and trade-offs3 options · 367 words

Three options. A was validated with gradle in a scratch worktree of 5adff78bb168; B and C are by reading.

A. A closed flag with an early return (validated) (recommended)

#

In CheckedLock (VerifyingLockFactory.java:41-60), add private boolean closed; and:

@Override
public synchronized void close() throws IOException {
  if (closed) {
    return;
  }
  closed = true;
  try (Lock l = lock) {
    l.ensureValid();
    verify((byte) MSG_LOCK_RELEASED);
  }
}

Trade-offs

  • Copies SingleInstanceLock's pattern.
  • synchronized holds the lock's monitor across the "released" round trip in verify(), so a concurrent second close() waits until the first one has finished, as with the sibling locks.
  • The flag is set before the release, so if the first close fails (the "released" handshake or the inner close throws), a second close does nothing rather than retry. The inner lock is still closed by try-with-resources, and SingleInstanceLock and NativeFSLock behave the same (they set closed in a finally).
  • ensureValid() after close still throws through the inner lock. Nothing changes for a single close.
  • CHANGES: a Bug Fixes entry under the next release.

What the checks validated

  • Gradle in a scratch worktree of 5adff78bb168, OpenJDK 25.0.3, seed DEADBEEF: stock, the repro fails with assertions on and off; with the fix it passes, on and off.
  • With the fix and the repro: TestLockFactory, TestSingleInstanceLockFactory, TestSimpleFSLockFactory, TestNativeFSLockFactory, TestSleepingLockWrapper, TestStressLockFactories (which drives VerifyingLockFactory through LockStressTest and a LockVerifyServer on 127.0.0.1) and the repro: 7 classes, 37 tests, 0 failures, 0 skipped.
  • checkGoogleJavaFormat, ecjLint, forbiddenApisMain and forbiddenApisTest of lucene/core pass with the fix and the test.
  • The full lucene/core suite was not run.

B. The same with an AtomicBoolean instead of synchronized

#

if (closed.compareAndSet(false, true) == false) { return; } at the top of close().

Trade-offs

The same for calls one after another, but not under concurrency: a second caller returns at once, possibly before the first close has sent "released" and closed the inner lock. Also differs from the sibling locks' style. By reading, not run.

C. Document that a verifying lock may be closed only once

#

Say in the javadoc that a second close() throws.

Trade-offs

Contradicts Lock's Closeable contract and testDoubleClose. Not recommended.

Downstream note

#

Downstream, only test harnesses or tools that install VerifyingLockFactory and close its locks more than once (directly or through a Closeable owner such as CheckIndex) see the exception; default IndexWriter locking does not use this class.

How it was found

#

Semi-formal: a proof-obligation audit of VerifyingLockFactory's lock against Lock's Closeable contract, that a second close() has no effect. CheckedLock.close() has no state that could discharge it, and a JUnit test on stock main witnessed the failure.

The method in full78 words
  • Obligation: close() on an already closed lock has no effect (Closeable.close, inherited by Lock.close(); required of every lock factory by BaseLockFactoryTestCase.testDoubleClose).
  • Finding: CheckedLock keeps no state, so the second call repeats the release path; whether it throws or sends a second "released" depends on the inner lock's ensureValid().
  • Witness: a JUnit test that closes the lock twice, then an independent reproduction, a cross-model review, an intended-behaviour review and an adjudication (see Independent checks).
