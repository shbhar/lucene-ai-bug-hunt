CompletionScorer ignores the BulkScorer [min, max) window, so a CompletionQuery run through IndexSearcher#search with a timeout or intra-segment partitions repeats some suggestions and drops others

A CompletionQuery run through IndexSearcher#search with a timeout that never fires returns the top 5 of 500 suggestions as [499, 499, 498, 498, 497] instead of [499, 498, 497, 496, 495], with no error. CompletionScorer reruns its whole-segment lookup for every doc-ID window; suggest() is not affected.

The bug in 30 seconds

#

CompletionScorer, the scorer behind every CompletionQuery, is handed a doc-ID window [min, max) but never reads it: each call runs the segment's whole top-N lookup and reports the window as done. One whole-segment call, as suggest() makes, is right; several windows or partitions collect the same suggestions several times.

Background: three pieces

#
  1. The document suggester (lucene/suggest) answers a CompletionQuery with one walk over a segment's suggestion FST that yields the top-N suggestions in score order. Its documented entry point, SuggestIndexSearcher#suggest, calls the scorer once per segment, for all documents.
  2. A BulkScorer scores one doc-ID window per call: score(collector, acceptDocs, min, max) must collect only the matches in [min, max) and return where the next match is, or NO_MORE_DOCS when there is none.
  3. IndexSearcher uses windows in two cases. With setTimeout it scores each segment in growing windows and checks the clock between them. With intra-segment concurrency it splits a segment into doc-ID partitions, each with its own collector, and merges the results.

The bug, step by step

#
  1. Index 500 documents in one segment, one suggestion each: apple0 to apple499 with weights 1 to 500. SuggestIndexSearcher#suggest for the prefix apple, top 5, returns docs [499, 498, 497, 496, 495].
  2. Run the same PrefixCompletionQuery through IndexSearcher#search with a TopSuggestDocsCollector(5, false) per slice: the same five. Now call setTimeout(() -> false), a timeout that never fires. You expect the same five again.
  3. Instead you get [499, 499, 498, 498, 497], an exact total of 5, and timedOut() false. With a timeout the searcher scores the segment in doc-ID windows of 100, 150, 225 ... documents. CompletionScorer ignores the window and reruns the full top-5 lookup on every call, so window 2 adds 499 and 498 again until the queue overflows.
  4. With 5 intra-segment partitions of 100 documents (an executor plus slices(leaves, 100, 1, true)), every partition collects the whole segment and the merge keeps the copies: [499, 499, 499, 499, 499]. One document with one suggestion comes back 5 times under the timeout.

Who is affected

#

Applications that run a CompletionQuery through the generic IndexSearcher#search with a TopSuggestDocsCollector and also set a timeout (silent since 9.4.0) or use intra-segment partitions (since 10.0). Deterministic once there, at any size. Rare: the module documents suggest(), which is correct, and no user of the generic path was found.

Mechanism, terms and numbers917 words

CompletionScorer is the BulkScorer of every CompletionQuery in the document suggester (lucene/suggest). BulkScorer#score(collector, acceptDocs, min, max) must collect only the matches in [min, max) (BulkScorer.java:42-43, :72-73), but CompletionScorer.score never reads min or max: every call runs suggester.lookup over the whole segment, a score-ordered top-N walk of its suggestion FST, and returns max (CompletionScorer.java:68-75 on main 645d4fe14a20). The documented entry point, SuggestIndexSearcher#suggest, makes one whole-range call per segment, so it is correct. Through the generic IndexSearcher#search with a TopSuggestDocsCollector it is correct only without a timeout and without intra-segment partitions. With setTimeout, even a timeout that never fires, TimeLimitingBulkScorer scores each segment in up to 40 growing windows (TimeLimitingBulkScorer.java:70-86), so the same top suggestions are collected again until the collector's queue overflows: 500 suggestions, n = 5 give docs [499, 499, 498, 498, 497] instead of [499, 498, 497, 496, 495], with an EQUAL_TO total and timedOut() false; one document with one suggestion comes back 5 times. With intra-segment partitions every partition collects the whole segment and TopSuggestDocs.merge keeps the copies: [499 x5]. Every hit still passes the query's filter, contexts and live docs. The scorer has ignored the window since it was written (LUCENE-6459, 5.3.0); it turned silent through IndexSearcher in 9.4.0 (#996) and gained the partition leg in 10.0.0 (#13542), whose migration notes say such Weights "need updating". Running the lookup only for the window that starts at doc 0 and returning NO_MORE_DOCS fixes both paths; throwing for any other window, as DrillSidewaysScorer does, is the loud alternative.

Terms

#
  • CompletionQuery (PrefixCompletionQuery, RegexCompletionQuery, FuzzyCompletionQuery, ContextQuery): the queries of the document (NRT) suggester; CompletionWeight's ScorerSupplier#bulkScorer() returns a CompletionScorer (CompletionWeight.java:102-130). The module says: "Use SuggestIndexSearcher#suggest(CompletionQuery, int, boolean) to execute any query" (CompletionQuery.java:36-37).
  • BulkScorer window: "min is the minimum document to be considered for matching. All documents strictly before this value must be ignored" (BulkScorer.java:42-43); "@param max Score up to, but not including, this doc" (:72-73); the return value is NO_MORE_DOCS "if there are no more matches" (:34-40).
  • Timeout windows: with a QueryTimeout, IndexSearcher#searchLeaf wraps the scorer in TimeLimitingBulkScorer (IndexSearcher.java:846-848), which calls it for [min, min + interval) with an interval of 100 that grows by 50% per call, checking the timeout before each, and continues from the returned value (TimeLimitingBulkScorer.java:70-86). An entire segment is the range [0, NO_MORE_DOCS) (IndexSearcher.java:1096-1100).
  • Partitions: with an executor and slices(leaves, maxDocs, maxSegments, true), a segment is split into doc-ID ranges searched with different collectors (MIGRATE.md:1668-1684).

The bug

#
  1. CompletionScorer.score(collector, acceptDocs, min, max) checks the collector type, calls suggester.lookup(this, acceptDocs, (TopSuggestDocsCollector) collector) and returns max (CompletionScorer.java:68-75). min and max are never read; the class javadoc still says score "is called for each leaf reader" (:30).
  2. Under a timeout, the returned max sends TimeLimitingBulkScorer on to the next window, so the loop walks the whole int range: up to 40 calls per segment, each running the full lookup into the same collector.
  3. TopSuggestDocsCollector keeps a top-n queue and throws CollectionTerminatedException at the first insert that overflows, on the assumption that every later hit of the segment scores lower (TopSuggestDocsCollector.java:123-135). searchLeaf catches it and moves on (IndexSearcher.java:853-855), so the search succeeds.
  4. With partitions, each partition's call runs the whole lookup into its own collector, and TopSuggestDocs.merge takes the top n of all of them with no de-duplication and an EQUAL_TO total (TopSuggestDocs.java:115-132).

The numbers

#

500 documents in one segment, suggestion apple<i> with weight i + 1, PrefixCompletionQuery("apple"), n = 5, skipDuplicates false. suggest(): docs [499, 498, 497, 496, 495]. IndexSearcher#search with a TopSuggestDocsCollector per slice and no timeout: the same. With setTimeout(() -> false): window 1 fills the queue with 499 to 495; window 2 adds 499 and 498 again, which push out 495 and 496; 497 then overflows and the segment ends: [499, 499, 498, 498, 497], total 5 EQUAL_TO, timedOut() false. One document with one suggestion: the same hit 5 times. 5 partitions of 100 documents: [499, 499, 499, 499, 499]. A direct bulkScorer.score(collector, null, 0, 100) collects 400 documents outside [0, 100).

When it happens and when not

#
  • Needs: a CompletionQuery executed through IndexSearcher#search with a TopSuggestDocsCollector (a hand-written CollectorManager, or the deprecated search(Query, Collector), which SuggestIndexSearcher inherits), plus any QueryTimeout on that searcher or intra-segment partitions.
  • The shortest trigger: suggestSearcher.setTimeout(() -> false) and then suggestSearcher.search(query, new TopSuggestDocsCollector(5, false)); on 20 suggestions it gives [19, 19, 18, 18, 17], while suggest() with the same timeout gives [19, 18, 17, 16, 15].
  • Not affected: SuggestIndexSearcher#suggest (SuggestIndexSearcher.java:69-76: one score(..., 0, NO_MORE_DOCS) call per segment); the generic path without a timeout or partitions.
  • What stays right: every hit passes the filter and the live docs (NRTSuggester.java:207, CompletionScorer.java:89-92), and contexts are part of the same lookup. The lists are wrong, never foreign.
  • With skipDuplicates=true the timeout leg happens to stay correct (the collector's set of seen surface forms survives across windows); the partition leg does not (the finder's model: 0 and 128 of 240 grid points differ).
  • Other generic calls already fail loudly: search(q, n) throws IllegalArgumentException ("collector is not of type TopSuggestDocsCollector", CompletionScorer.java:71), count(q) throws, explain returns null.
  • Side observation: suggest() itself never applies setTimeout; with an expired timeout it still returns every hit and timedOut() stays false.
Exposure and likelihood170 words
  • Who is hit. Code that executes completion suggestions like any other query: a CollectorManager of TopSuggestDocsCollector, or the inherited search(Query, Collector) on a SuggestIndexSearcher, on a searcher that has a timeout or intra-segment partitions. A developer who wants to bound suggest latency has a reason to try setTimeout, because suggest() ignores it.
  • Default or opt-in. Opt-in: the module documents SuggestIndexSearcher#suggest (CompletionQuery.java:36-37, SuggestField.java:45-46); the generic path, the timeout and the partitions are the application's choices.
  • Effect. Silent wrong suggestion lists: copies of the best suggestions, lower ones missing, an EQUAL_TO total, timedOut() false, no exception. No filtered-out or deleted document comes back.
  • Releases. Silent under a timeout from 9.4.0 (9.3.0 throws CollectionTerminatedException), with partitions from 10.0.0, through 10.5.2 and main.
  • Scale. Ordinary: one document under a timeout, one 500-document segment in 5 partitions.
  • How likely: rare. No upstream test and no downstream user of the generic path was found; on 10.x that path also throws NullPointerException on any segment without the suggest field (LFV-967).

Why it is a bug, not intended

#
  • BulkScorer#score must ignore documents before min and stop before max; nothing exempts this scorer or rejects the call.
  • Lucene 10.0's migration notes: Weights that assume one bulk scorer per segment per search "need updating".
  • A timeout that never fires must not change results; the similar whole-segment-only DrillSidewaysScorer throws instead.
The full argument235 words
  • Contract. BulkScorer.java:42-43: "All documents strictly before this value must be ignored"; :72-73: "max Score up to, but not including, this doc". Returning max tells the caller to come back for the next window; NO_MORE_DOCS is the value for "no more matches" (:34-40).
  • Migration note (10.0). "Weight implementations that rely on the assumption that a scorer, bulk scorer or scorer supplier for a given LeafReaderContext is requested once per search need updating" (MIGRATE.md:1678-1684 on main; :851-857 in 10.0.0, added by #13542). CompletionScorer.java:30 ("is called for each leaf reader", 2015) is that assumption.
  • Timeouts. setTimeout applies "for all searches that run through this IndexSearcher" (IndexSearcher.java:612); the test framework's newSearcher sets setTimeout(() -> false) on half of its searchers (LuceneTestCaseParent.java:2689-2691), treating "a timeout that never fires changes nothing" as an invariant. The suggest tests build SuggestIndexSearcher directly and never meet it.
  • Precedent. DrillSidewaysScorer rejects windows: "min must be 0, got " + min and "maxDoc must be Integer.MAX_VALUE" (DrillSidewaysScorer.java:90-97); facet tests opt it out of the random timeout because it "requires the entire range of docs to be scored at once" (TestRangeFacetCounts.java:473); #12032 (open) treats that as a limitation to fix.
  • History. The silent path was never designed: it appeared when timeouts (#927, #996) and partitions (#13542) began passing the user's collector through windows; none of those PRs touched or discussed the suggest module.
The devil's-advocate check165 words

The intended-behaviour checker and a reviewer from another model family (OpenAI GPT-5.6) built the strongest case: the module documents suggest() as the way to run "any query" (CompletionQuery.java:36-37) and one call per leaf (CompletionScorer.java:30); the generic machinery is visibly unsupported (search(q, n), count(q) and a BooleanQuery clause throw, explain returns null); a score-ordered FST walk cannot honour doc-ID windows; SuggestIndexSearcher refuses an executor; whole-segment-only scorers are a tolerated limitation; the module is @lucene.experimental.

Why it fails: "use suggest()" is guidance, not a prohibition, and nothing rejects the other path; SuggestIndexSearcher is an IndexSearcher and inherits both search(Query, Collector) and setTimeout, and the generic path is correct without a timeout. Where the module did decide against the generic machinery it fails loudly; here it fails silently, unlike the tolerated precedent DrillSideways. Experimental allows API changes, not silent wrong results. The adjudication kept the framing "silently ignores the window instead of rejecting it", a documentation and robustness bug.

Suggested fix

#

Recommended Run the lookup once, on the window that starts the segment (validated)

In CompletionScorer.score, run the lookup only for the window that starts the segment (min == 0) and return NO_MORE_DOCS, so a timed or partitioned search collects each suggestion once. Validated: the three search-level tests pass, and the suggest module and check pass; a direct windowed call still does not honour the window, by design.

// The lookup is a top-N search in score order, not in doc-ID order, so it cannot be split into
// doc-ID windows: run it once, on the window that starts the leaf, and report that this leaf
// has no more matches, so that callers that score in windows (IndexSearcher#setTimeout,
// intra-segment partitions) neither repeat it nor collect it again.
if (min == 0) {
  suggester.lookup(this, acceptDocs, ((TopSuggestDocsCollector) collector));
}
return DocIdSetIterator.NO_MORE_DOCS;

Run the lookup once, on the window that starts the segment (validated) (validated by the checks) (recommended)

#

A change in CompletionScorer.score (1 file, +9/-2; the finder's sketch, unchanged by tidy). Under a timeout, TimeLimitingBulkScorer checks the clock, calls [0, 100) once, gets NO_MORE_DOCS and stops: one lookup per segment, as suggest() makes. With partitions, the one that starts at doc 0 collects the segment's suggestions and the others collect nothing.

// The lookup is a top-N search in score order, not in doc-ID order, so it cannot be split into
// doc-ID windows: run it once, on the window that starts the leaf, and report that this leaf
// has no more matches, so that callers that score in windows (IndexSearcher#setTimeout,
// intra-segment partitions) neither repeat it nor collect it again.
if (min == 0) {
  suggester.lookup(this, acceptDocs, ((TopSuggestDocsCollector) collector));
}
return DocIdSetIterator.NO_MORE_DOCS;

Trade-offs

  • A direct windowed call is still not honoured: score(c, acceptDocs, 0, 100) collects the whole segment and a window that does not start at 0 collects nothing. The repro's direct-window test keeps failing with this fix by design; the PR version of the test leaves it out, and the class javadoc (CompletionScorer.java:30) should say so.
  • The lookup runs as one block, so the timeout is checked once, before it. Before the fix the first window already ran the full lookup, so no check is lost in practice.
  • With partitions, one partition does all of a segment's suggestion work: no intra-segment speed-up, and no repeated work.
  • NO_MORE_DOCS is a legal return value (BulkScorer.java:38).

What the checks validated

  • Scratch worktree of 645d4fe14a20, gradle, OpenJDK 25: the repro test fails 4 of 5 on the stock tree; with the fix 4 of 5 pass and only the direct-window test fails, with assertions on and off; the PR test passes 4 of 4.
  • With the fix and the PR test, the whole lucene/suggest module passes with assertions on and off: 32 suites (31 upstream + the PR test), 240 tests, 7 skipped, 0 failures; the 6 upstream suggest.document suites (58 tests) among them.
  • :lucene:suggest:check -x test (checkGoogleJavaFormat, ecjLint, forbiddenApis) passes after tidy joined one line of the test.
  • Earlier, by the hunt: the finder's model grid drops from 448 to 0 points that differ from suggest() (timeout 0 of 480, partitions 0 of 480).
  • Not run: nightly tests, a benchmark.

Reject any other window loudly, as DrillSidewaysScorer does (built and run)

#

Throw IllegalArgumentException("CompletionScorer can only score a whole segment at once, got [" + min + ", " + max + ")") unless min == 0 && max == NO_MORE_DOCS, and return NO_MORE_DOCS (1 file, +8/-1). The repro's 4 bug tests then throw ... got [0, 100) instead of returning wrong lists; the control passes; the suggest module's 31 upstream suites (236 tests) pass with assertions on.

Trade-offs

Honest, but every CompletionQuery search through IndexSearcher with any timeout or with partitions then throws, including the inherited search(Query, Collector) on a SuggestIndexSearcher with a timeout: the DrillSideways state that #12032 keeps open as a limitation to fix.

Document that IndexSearcher#search, timeouts and partitions are unsupported (not built)

#

A javadoc sentence on CompletionQuery, CompletionWeight or SuggestIndexSearcher (and that suggest() ignores setTimeout).

Trade-offs

Cheap, but on its own it leaves the silent copies for anyone who misses the note. Best combined with one of the two code options.

Honour the window by filtering the lookup's hits to [min, max) (not built)

#

Collect only hits whose doc ID is inside the window.

Trade-offs

Satisfies the contract literally, but every window repeats a full score-ordered walk of the FST (up to 40 per segment under a timeout), and TopSuggestDocsCollector ends the whole segment at the first queue overflow on the assumption of one descending-score pass (TopSuggestDocsCollector.java:123, :128-134), which several windows break. More than a local change.

Downstream note

#

Elasticsearch and OpenSearch run completion suggestions through their own loop with one whole-segment call per segment, as suggest() does, so they are not affected.

How it was found

#

A planning probe that compared IndexSearcher#search under a timeout with suggest() showed the copies. The hunt then checked an explicit model of the scorer under timeout windows and partitions against the stock jar on 1,440 grid points (448 differ from suggest(), 0 with the fix) and reduced it to a public-API JUnit.

The method in full203 words

Method: non-formal first signal, then a model-based differential (the hunt's hunt unit for CompletionWeight and CompletionScorer outside SuggestIndexSearcher, 2026-10-28, main a9779ef3c193).

  • Lead. A planning probe on the stock jars, built from the contract "every BulkScorer collects exactly the matches in [min, max)": under a timeout IndexSearcher returned 499 499 498 498 497 where suggest() returns 499 to 495. Its partition leg had no executor, so no partitions were used.
  • Intent gate. Code, javadoc and history were read first, because the module documents suggest() as the entry point; the bug was filed as a documentation and robustness defect.
  • Model. An explicit model of CompletionScorer under timeout windows and intra-segment partitions, checked against the stock jar on a bounded grid: 6 segment sizes x 4 match counts x 2 key layouts x 5 values of n x skipDuplicates on and off x {suggest(), never-firing timeout, 100-document partitions with an executor} = 1,440 points; 0 model disagreements after one model fix (the real windows run to NO_MORE_DOCS, not to maxDoc). 192 timeout points and 256 partition points differ from suggest(); 0 with the fix.
  • JUnit. Reduced to the public-API test: 4 of 5 fail with assertions on and off.

History

#

Introduced with the class in 5.3.0 (LUCENE-6459, be4d58c7740, 2015); not a regression. It turned silent through IndexSearcher in 9.4.0 (#996 caught the collector's termination exception under a timeout; 9.3.0 throws) and gained the partition leg in 10.0.0 (#13542). Unchanged on main.

Versions tested7 rows

Introduced by be4d58c7740 on trunk, "LUCENE-6459: add common suggest API for document based NRT suggester" (patch by Areek Zillur, committed by Michael McCandless, 2015-05-28; JIRA LUCENE-6459, migrated as #7518, no PR), released through the branch_5x backport 380bb29f395 in 5.3.0. score returned max without reading the window from the start; later commits only added acceptDocs (d671dd8d890, LUCENE-6553), moved the license header and reformatted (2cbf261032d, 2021).

Bug record

#

LFV-969, snapshot of 2026-10-29

Registry title
CompletionScorer silently ignores the BulkScorer [min, max) window instead of rejecting it, so a CompletionQuery run through IndexSearcher#search with a timeout (even one that never fires) or with intra-segment partitions returns repeated suggestions and drops others
Area
suggest / document (NRT) suggester: CompletionScorer under IndexSearcher's windowed execution (setTimeout, intra-segment partitions)
Impact class
silent wrong results
Impact note
Only applications that execute a CompletionQuery through the generic IndexSearcher#search with a TopSuggestDocsCollector (a hand-written CollectorManager, or the search(Query, Collector) that SuggestIndexSearcher inherits), a path the experimental suggest module does not document, together with IndexSearcher#setTimeout (silent from 9.4.0) or intra-segment partitions (from 10.0) get duplicated and missing suggestions with no error; the documented SuggestIndexSearcher#suggest path, and the suggesters of Elasticsearch and OpenSearch, which copy its one-call-per-segment loop, are not affected; deterministic at ordinary scale once on that path.
Summary
You run a CompletionQuery through IndexSearcher#search with a TopSuggestDocsCollector (for example suggestSearcher.search(query, collector)) on a searcher that has a timeout set, even one that never fires, or that splits a segment into intra-segment partitions. You expect the same top suggestions as SuggestIndexSearcher#suggest, or a loud error if this path is unsupported, because BulkScorer#score must score only the documents in [min, max) and a timeout that never fires must not change results. Instead CompletionScorer runs its whole-segment top-N lookup again on every window or partition, so the top suggestions come back several times and lower ones are dropped (500 suggestions, n=5: [499, 499, 498, 498, 497] instead of [499, 498, 497, 496, 495]; one suggestion returned 5 times; partitions: [499 x5]), while the total says EQUAL_TO and timedOut() is false.
