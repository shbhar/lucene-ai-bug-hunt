ConcurrentQueryLoader with a buffer smaller than its thread count loads no queries

A ConcurrentQueryLoader with fewer buffer slots than threads, such as (monitor, 2, 1), never registers a query: each worker's batch size queueSize / threads is 0. close() right away returns with an empty Monitor, a later close() can hang, and add() blocks forever once the buffer is full.

The finding in 30 seconds

#

Each worker's batch size is the buffer size divided by the thread count. With fewer slots than threads it is 0, and a worker that asks for 0 queries never takes any.

Background: the Monitor and its query loader

#
  1. A Monitor (module lucene/monitor) stores queries and, for each incoming document, reports which stored queries match it.
  2. ConcurrentQueryLoader registers many queries at startup in parallel: you add() queries into a bounded buffer of queueSize entries, and threads worker threads take them out in batches and call Monitor.register.
  3. close() waits for the workers to finish. After it returns, the added queries are expected to be in the Monitor (the class javadoc's try-with-resources pattern).

The finding, step by step

#
  1. Create new ConcurrentQueryLoader(monitor, 2, 1): 2 worker threads and a buffer for 1 query. The constructor accepts it.
  2. Add one MonitorQuery and close the loader (try-with-resources, as the class javadoc shows). You expect monitor.getQueryCount() to be 1, as it is with (1, 1) or (2, 2).
  3. But each worker got a batch size of queueSize / threads = 1 / 2 = 0. A worker that asks for 0 queries never takes one, so the query just sits in the buffer.
  4. close() right after the add() returns normally, no error, and getQueryCount() is 0 (called later, close() can hang instead). Add a second query instead of closing, and that add() waits forever: the buffer is full and nothing empties it.
  5. Over 1-6 threads and buffers of 1-8, the query is lost in exactly the 15 settings where the buffer is smaller than the thread count, and in none other.

Who is affected

#

Applications that bulk-load queries into the optional monitor module through ConcurrentQueryLoader(monitor, threads, queueSize) with a buffer smaller than the thread count, for example 64 threads and 50 slots. Up to queueSize queries are lost, silently if close() comes at once (later, close() may hang); more hang the loader. The default constructor and direct Monitor.register calls are not affected.

Mechanism, terms and numbers657 words

ConcurrentQueryLoader loads MonitorQuerys into a Monitor with several worker threads that take queries off a bounded buffer in batches. The 3-argument constructor gives each worker a batch size of queueSize / threads (ConcurrentQueryLoader.java:87 on main 5adff78bb168). When 0 < queueSize < threads that integer division is 0, and drain with 0 requested elements returns at once without taking anything (:184). So in this configuration the loader never registers any query: a load of at most queueSize queries that is closed right away ends with close() returning normally, no error, and an empty Monitor; closed later, on a default JIT close() itself can hang; a larger load blocks forever in add(). The default constructor (availableProcessors() threads, a 2000-entry buffer) is not affected on real hardware. In every lucene-monitor release from 8.2.0 through 10.6.0 and on main; on main with assertions on and off.

The code (main 5adff78bb168, ConcurrentQueryLoader.java)

#
  1. :81-89, the 3-argument constructor: the buffer is new LinkedBlockingQueue<>(queueSize) (:83) and each of the threads workers is new Worker(queueSize / threads) (:87, the fix site). For (2, 1): 1 / 2 = 0. Neither number is validated.
  2. :134-143, Worker.run: in a loop, clear the batch and call drain(queue, workerQueue, queueSize, 100, MILLISECONDS) (:138; queueSize here is the worker's batch size, 0); stop once the batch is empty and shutdown is set (:139); register a non-empty batch (:140-142).
  3. :169-198, drain: all the work happens inside while (added < numElements) (:184). With numElements == 0 the loop never runs: no drainTo, no poll, return 0. No worker ever takes anything from the buffer, under any thread schedule.
  4. :107-120, close(): set shutdown (:108) and wait for the workers (:111). Each sees an empty batch and stops; no errors were collected, so close() returns normally. The query is still in the buffer, which is dropped with the loader.
  5. :99-104, add(): queue.put(mq) (:103). After queueSize adds the buffer is full; nothing drains it, so the next add() waits forever.

The numbers

#

(monitor, 2, 1), one query: getQueryCount() is 0 instead of 1, with assertions on and off, every seed tried (30 of 30 iterations with assertions off). A grid of threads 1..6 x queueSize 1..8 (48 configurations, one query each) loses the query in exactly the 15 configurations with queueSize < threads; with the fix it loses none. With two queries the second add() is still waiting after 5 s (also with -Xint); with the fix both adds return and both queries are registered.

Side effects, not part of the claim

#

Until close(), every batch-0 worker loops without blocking (a CPU spin). Because shutdown is a plain field (:60) read in that loop without synchronization, a later close() may never return. In a fact-check probe (plain java, main jars, (2, 1), one add(), close() after a delay, 10 s wait), every default-JIT run with close() 100 ms to 3 s after construction hung (13 of 13, assertions on and off; both workers busy at :140, the closing thread waiting at :111), while a close() right away returned, and with -XX:TieredStopAtLevel=1 (the flag of Lucene's gradle test JVM) or -Xint close() returns and the query is still lost. So on a production-default JVM a small load that is not closed at once most likely hangs in close() rather than failing silently. That hang depends on timing and the JIT and is not part of the claim (the repro's prompt close() is deterministic). The fix removes it too: a batch of at least 1 makes drain wait in poll for up to 100 ms (:189), and with the fix a close() 100 ms or 1 s after construction returns and the query is registered.

Exposure and likelihood219 words
  • Who. Users of the optional lucene/monitor module who load queries with the public 3-argument constructor and 0 < queueSize < threads, for example threads = availableProcessors() with a small bounded buffer on a many-core host (64 threads and a 50-entry buffer give 50 / 64 = 0).
  • Default vs opt-in. Opt-in: the default constructor uses availableProcessors() threads and DEFAULT_QUEUE_SIZE = 2000 (ConcurrentQueryLoader.java:63, :70-72), so it would need more than 2000 processors. Calling Monitor.register directly is not affected.
  • Scale. Total: in this configuration the loader registers nothing. Up to queueSize queries: all lost (silently, or with a hung close() when it is called late). More: the loading thread hangs at add number queueSize + 1.
  • Silent when close() follows the adds promptly: no exception, close() returns normally, assertions on or off; later match() calls simply never report the lost queries. Called later, close() may hang instead (a JIT-dependent side effect; see "Side effects, not part of the claim").
  • How likely. Rare: a buffer is normally sized well above the worker count, a large load hangs in add() and a small load that is not closed at once may hang in close() (both loud) rather than failing silently, and no public report was found since the class was written (2015) or added to Lucene (8.2.0, 2019).

Why it looks unintended

#
  • The class javadoc shows the loader as the way to load queries with several threads (add() in a loop, then close); the only upstream test asserts every added query is registered after close().
  • The constructor documents threads and queueSize independently and validates neither.
  • add() blocks only "until there is room"; with a batch size of 0 there never is.
The full argument211 words
  • Purpose. Class javadoc: "Utility class for concurrently loading queries into a Monitor." and "You can use multiple threads to parse and index queries before starting matches." (ConcurrentQueryLoader.java:35, :37-38); usage: add() in a loop inside try-with-resources (:42-49; the example's constructor new ConcurrentQueryLoader(monitor, errors) does not exist, a separate javadoc defect, LFV-1034, but the add-then-close shape is clear). close() is the only point where a caller can wait for the load; it has no javadoc of its own, so the expected outcome rests on the class purpose, this example and the upstream test, not on a stated close() contract.
  • Two independent numbers. threads: "the number of threads to use"; queueSize: "the size of the buffer to hold queries in" (:77-79). No relation is stated, neither is validated, and the class is not marked experimental or internal.
  • add(). "If the buffer is full, this will block until there is room to add the MonitorQuery" (:94).
  • The test. TestConcurrentQueryLoader.testLoading (default constructor) asserts assertEquals(numQueries, monitor.getQueryCount()) right after close() (TestConcurrentQueryLoader.java:22-33, :31).
  • History. The division came unchanged from the Luwak library (2015) into LUCENE-8766 (2019) and was never discussed; no issue, commit message, CHANGES or MIGRATE entry states a queueSize >= threads precondition.
The devil's-advocate check104 words

The strongest case for "intended". queueSize is a total budget split across the workers, as the defaults suggest (2000 slots against the processor count); a buffer smaller than the thread count adds no parallelism, so it is a pointless setup; and Closeable#close promises to release resources, not to flush.

Why it fails. Nothing documents or enforces that reading, and the outcome is a lost query (with a normal or a hung close()), not a rejection. A setting the constructor accepts should at worst be slow, not load nothing. Both executed cross-model review lenses and the intended-behaviour devil's advocate rated the intended reading weak.

Suggested fix

#

Recommended A. Clamp the batch size to at least 1 (recommended, validated)

Recommended: clamp each worker's batch size to at least 1, new Worker(Math.max(1, queueSize / threads)) at ConcurrentQueryLoader.java:87. Settings that work today keep their batch size. Validated: the repro passes, all 182 lucene/monitor tests pass (1 skipped) and the formatter check is clean.

     for (int i = 0; i < threads; i++) {
-      this.executor.submit(new Worker(queueSize / threads));
+      this.executor.submit(new Worker(Math.max(1, queueSize / threads)));
     }
All options and trade-offs2 options · 431 words

Option A was applied in a scratch worktree at 5adff78bb168 and run through gradle (seed DEADBEEF, one seed, no nightly tests, not the full Lucene suite): the repro fails without it (assertions on and off) and passes with it; :lucene:monitor:test gives 182 tests (the repro included), 1 skipped, 0 failures; the repro and TestConcurrentQueryLoader pass with assertions off; checkGoogleJavaFormat is clean. A scratch probe (not the repro) shows that with the fix a second add() on (monitor, 2, 1) returns and both queries are registered. Earlier checks: the 48-configuration grid loses no query with the fix, and an independent reviewer ran all 180 upstream monitor tests with it (pass). In the delayed-close probe, with the fix a close() 100 ms or 1 s after construction returns and the query is registered. Making shutdown volatile is separate hardening and not needed for this fix.

A. Clamp the batch size to at least 1 (recommended, validated)

#

ConcurrentQueryLoader.java:87, one line.

     for (int i = 0; i < threads; i++) {
-      this.executor.submit(new Worker(queueSize / threads));
+      this.executor.submit(new Worker(Math.max(1, queueSize / threads)));
     }

Trade-offs

No API change, and no behaviour change for queueSize >= threads (same batch size). With queueSize < threads each worker takes one query at a time: the shared buffer stays bounded by queueSize, and each worker holds at most one more query in its own batch. It also ends the busy loop of the batch-0 workers and the late-close() hang, since drain then waits in poll. It fixes the batch-0 loss only, not a separate and much narrower timing window that exists in every configuration (read, not run): a worker whose poll has just timed out empty (:189-191) and that reads shutdown (:139) only after a final add() and close() stops, and if every worker does so the query stays in the buffer.

What the checks validated

Gradle, scratch worktree of 5adff78bb168: repro fails before, passes after (assertions on and off); :lucene:monitor:test 182 tests, 1 skipped, 0 failures; checkGoogleJavaFormat clean. Probe: the second add() returns, 2 queries registered.

B. Reject queueSize < threads in the constructor (not run)

#

if (queueSize < threads) throw new IllegalArgumentException(...) in the 3-argument constructor, plus a javadoc sentence.

Trade-offs

Loud and explicit, and it documents the assumption. It turns a setting the constructor accepts today into an error: a caller that builds such a loader and never adds a query, or never noticed the loss, gets an IllegalArgumentException at construction instead of a normal run, and the regression test becomes an expectThrows. Not validated here.

Downstream note

#

An alerting or filtering application built on the Monitor would silently miss every match of the lost queries.

How it was found

#

A deterministic public-API test of the documented add-then-close pattern over a grid of (threads, queueSize) values, with an interpreter-only (-Xint) control, showed the lost query. It was reduced to one JUnit test and backed by a bounded-exhaustive grid of 48 configurations whose losses match queueSize < threads exactly.

The method in full139 words

Method: semi-formal. A deterministic test of the class javadoc's add-then-close pattern, through public API only, over a grid of (threads, queueSize) values, run on main 5adff78bb168 with assertions on and off and on the 10.6.0, 9.12.3 and 9.0.0 jars, with an interpreter-only (-Xint) control to separate the deterministic loss from JIT effects. Independent re-runs gave the same result, and a check with the one-line clamp passed.

The finding was then reduced to one JUnit test and backed by a bounded-exhaustive grid: threads 1..6 x queueSize 1..8 (48 configurations), which loses the query in exactly the 15 configurations predicted by queueSize / threads == 0 and in none with the fix shadowed in (vacuity control). After that: an independent reproducer, two executed cross-model review lenses, an intended-behaviour devil's advocate and an adjudication (section "Prior reports, history and checks").
