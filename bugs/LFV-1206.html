DateTools.stringToDate("2024123X") returns 2024-12-03 instead of throwing ParseException

DateTools.stringToDate("2024123X") returns 2024-12-03 instead of the ParseException its javadoc promises for strings not in the yyyyMMdd... format: a string of a supported length goes to a lenient SimpleDateFormat that ignores trailing text and rolls impossible fields over. The ISO date "2019-12-31" silently becomes 2018-10-31T17:00Z.

The finding in 30 seconds

#
  1. You decode a date string with DateTools.stringToDate (or stringToTime) and rely on the documented ParseException to reject strings that are not in the yyyyMMdd... format. It does throw for a wrong length ("2019123") or an unreadable start ("X0191231").
  2. You pass "2024123X": 8 characters, the length of a DAY string, but the last one is a letter. You expect a ParseException.
  3. The length picks the yyyyMMdd format. DateFormat.parse(String) reads 2024, 12 and 3, stops at the X, and does not mind that 1 of the 8 characters is left over.
  4. You get 2024-12-03T00:00:00Z, with no error, assertions on or off.
  5. The same happens to an ISO date ("2019-12-31" gives 2018-10-31T17:00:00Z, the dashes read as minus signs) and to impossible dates ("20041301", month 13, gives 2005-01-01). DateTools' own strings still parse correctly.

Who is affected

#

Applications that call the public static DateTools.stringToDate or stringToTime on strings that did not come from timeToString (user input, an external feed, an ISO date passed by mistake) and count on the ParseException to reject bad ones. No setting is involved and every release since 1.9 has it; no Lucene code calls these methods outside tests.

Mechanism, terms and numbers390 words

DateTools.stringToDate(String) and stringToTime(String) document @throws ParseException if dateString is not in the expected format, the yyyyMMddHHmmssSSS-or-shorter format that timeToString writes. They throw for a wrong length or an unreadable start, but a string of one of the seven supported lengths (4, 6, 8, 10, 12, 14, 17) goes to a lenient SimpleDateFormat through DateFormat.parse(String) (DateTools.java:117 and :198-199 at 5adff78bb168), which ignores trailing text and rolls impossible fields over. So "2024123X" returns 2024-12-03T00:00:00Z, the ISO date "2019-12-31" returns 2018-10-31T17:00:00Z and "20041301" (month 13) returns 2005-01-01T00:00:00Z, with no exception and the same result with assertions on and off. No Lucene code calls these methods outside tests, and DateTools' own strings parse correctly. Every release since 1.9 (2006) has it.

The mechanism (main 5adff78bb168, lucene/core/src/java/org/apache/lucene/document/DateTools.java)

#
  1. Lenient formats. Resolution builds each format as new SimpleDateFormat("yyyyMMddHHmmssSSS".substring(0, formatLen), Locale.ROOT) with the GMT zone (:198-199, a fix site) and never calls setLenient(false). TL_FORMATS keeps per-thread clones indexed by length (:54-65).
  2. Chosen by length. stringToDate calls TL_FORMATS.get()[dateString.length()].parse(dateString) (:117, the other fix site). A length with no format hits an empty slot or an out-of-range index, and the catch-all (:118-121) turns that into ParseException("Input is not a valid date string: " + dateString); that is why wrong lengths are rejected.
  3. Prefix parse. The JDK documents DateFormat.parse(String) as parsing "from the beginning of the given string"; it "may not use the entire text" and throws only if the beginning cannot be parsed. For "2024123X" the yyyyMMdd parse reads 2024, 12, 3 and stops: 7 of 8 characters used.
  4. Roll-over. The lenient calendar turns month 13 of 2004 into January 2005 and Feb 30 into March 1. Minus signs are read as signs: "2019-12-31" is consumed in full and its result equals a lenient calendar set to year 2019, month -1, day 2, hour -31.

Exposure and likelihood132 words
  • Who. Code that decodes or validates date strings it did not write with DateTools, for example a form field or a feed value checked with stringToDate before it becomes a range bound or a stored value.
  • Effect. A silently wrong Date, sometimes far from the input: "2019-12-31" lands about 14 months earlier, "201X" in the year 201.
  • Default vs opt-in. A plain public static utility; no setting.
  • Not hit. Lucene itself: outside tests no Lucene code calls either method (the only callers are TestDateTools and the benchmark's TestTrecContentSource, which decodes DateTools' own output). DateTools' own strings for years AD 1..9999 parse correctly, today and with the fix; outside that range they do not round-trip even today (LFV-645, a different bug).
  • Scale. One call; no data, no concurrency.

Why it looks unintended

#
  • Both methods document @throws ParseException if dateString is not in the expected format (yyyyMMdd...); a letter where a digit belongs is not in it.
  • Upstream TestDateTools already expects ParseException for strings DateTools never writes ("97", "aaaa").
  • The JDK's own javadoc calls leniently parsed input "not in the form" of the format and offers setLenient(false); DateTools never calls it.
The full argument231 words
  • Contract. @throws ParseException if <code>dateString</code> is not in the expected format (DateTools.java:101, :113); the format is yyyyMMddHHmmssSSS or shorter (:75, :87).
  • Tests. TestDateTools.testStringToDate (TestDateTools.java:41-57) expects ParseException for "97", "200401011235009999" and "aaaa", each commented "no date". No test covers a trailing character or an out-of-range field.
  • History. The first DateTools (c7fbb991c3e, 2004) threw its own ParseException("Input is not valid date string: " + dateString) for every unsupported length, then parsed with the default leniency. git log -S'setLenient' and -S'ParsePosition' over the file's full history find no commit, and the prior-report searches found no Lucene issue or thread about it: the leniency is the JDK default, and no recorded decision either way was found.
  • The JDK's words. DateFormat.parse(String, ParsePosition): "By default, parsing is lenient: If the input is not in the form used by this object's format method but can still be parsed as a date, then the parse succeeds. Clients may insist on strict adherence to the format by calling setLenient(false)."
  • Precedent. #9686 (LUCENE-8640, d482312b854, 2019) added delimiter checks and per-field range checks to a sibling date parser, spatial-extras' DateRangePrefixTree.parseCalendar, so that it rejects strings such as 2000-11T13 instead of reinterpreting them. A precedent for validating the syntax, not a fully strict parser: it checks the day only as 1..31 and still rolls Feb 30 over (LFV-619).
The devil's-advocate check204 words

The strongest case for "not a bug" (the independent cross-model reviewer's verdict, high confidence): the javadoc's first sentence is "Converts a string produced by timeToString or dateToString back to a time", so other strings are outside the contract; leniency is the documented JDK default; the design is unchanged since 2004 and no report of it was found; a javadoc sentence would do.

Why it fails: that sentence states the purpose, not a precondition (no "must" or "only"), and the @throws clause in the same javadoc says what happens to other strings. Read strictly, the purpose sentence would leave the clause only DateTools' own output after year 9999 (timeToString writes "10000" and stringToTime throws on it: LFV-645, itself a bug). The reviewer did not read it that strictly: they took the clause to cover "strings that cannot be parsed in a supported resolution format", which already puts strings DateTools never writes in scope, as the upstream test does with "aaaa". What remains is how strict "the expected format" is, and a letter where the format has a digit is outside it under any reading. The argument does bear on likelihood, hence Low; a maintainer may still prefer a javadoc fix (option C).

Suggested fix

#

Recommended Strict parse: setLenient(false) plus a whole-string ParsePosition check (fix A)

Make the parse strict: setLenient(false) on each Resolution format, and parse(String, ParsePosition) with a check that the whole string was used (+9/-1 in DateTools.java). Both parts are needed. The repro passes with assertions on and off; the closest core, query-parser and benchmark suites: 188 tests, 0 failures, 1 skipped by its suite.

      SimpleDateFormat format = TL_FORMATS.get()[dateString.length()];
      ParsePosition pos = new ParsePosition(0);
      Date date = format.parse(dateString, pos);
      if (date == null || pos.getIndex() != dateString.length()) {
        throw new ParseException("Unparseable date: " + dateString, pos.getErrorIndex());
      }
      return date;
      // and in Resolution(int formatLen): this.format.setLenient(false);
All options and trade-offs3 options · 486 words

Option A was built and checked through gradle on 5adff78bb168; B and C were not run. Both parts of A are needed: non-leniency alone still accepts "2024123X" (the prefix parse), and the whole-string check alone still accepts Feb 30 (all 8 characters are used), as a JDK-only replica of the format shows. With A, every malformed string in the table above throws, real DateTools strings parse to the same value, and 2,100,000 timeToString outputs (7 resolutions x 300,000 random times in AD 1..9999) round-trip with 0 rejected and 0 mismatched, as on unpatched main. Separately, a strict, whole-string SimpleDateFormat (not the patched class) read 14,000,000 real timeToString outputs, with the days around the 1582 calendar switch, back identically: compatibility evidence for strict parsing. Outside AD 1..9999 DateTools' output already fails to round-trip today (LFV-645); this fix does not address that. Formatting does not validate fields, so timeToString is unaffected.

Strict parse: setLenient(false) plus a whole-string ParsePosition check (fix A) (validated by the checks) (recommended)

#

In Resolution, call this.format.setLenient(false); in stringToDate, parse with a ParsePosition and throw unless the whole string was used. The inner ParseException goes through the existing catch-all, so callers see the same exception type and message as for a wrong length.

      SimpleDateFormat format = TL_FORMATS.get()[dateString.length()];
      ParsePosition pos = new ParsePosition(0);
      Date date = format.parse(dateString, pos);
      if (date == null || pos.getIndex() != dateString.length()) {
        throw new ParseException("Unparseable date: " + dateString, pos.getErrorIndex());
      }
      return date;
      // and in Resolution(int formatLen): this.format.setLenient(false);

Trade-offs

A caller that relies on today's leniency (Feb 30 on purpose) now gets ParseException; no Lucene code does. It is not a full syntax check: SimpleDateFormat's number parsing still accepts non-ASCII digits (full-width "２０２４１２０３" gives 2024-12-03) and a space before a field ("2004 101" gives 2004-01-01), with and without the fix; an ASCII-digit check before parsing would close those too (not built). One ParsePosition per call.

A java.time formatter with ResolverStyle.STRICT (not built)

#

Parse with a DateTimeFormatter per resolution in strict mode instead of SimpleDateFormat.

Trade-offs

Also strict, but java.time uses the proleptic ISO calendar while DateTools formats with GregorianCalendar (Julian before 1582) and the year-of-era pattern, so dates before 1582 would no longer round-trip unless timeToString changes too: a larger change that overlaps LFV-645.

Document the leniency only (not built)

#

Say in both javadocs that strings of a supported length are parsed leniently and may return a rolled-over date.

Trade-offs

Smallest change, but callers who rely on the @throws clause still get a wrong date silently.

Downstream note

#

Downstream, an application that validates user-supplied date strings with stringToDate accepts a malformed one as a different date instead of rejecting it; Lucene's own code never calls it.

How it was found

#

A proof-obligation audit of DateTools' contract: the @throws ParseException clause obliges both methods to reject every string that is not in the yyyyMMdd... format, and a lenient prefix parse cannot meet that for strings of a supported length. A one-call public-API JUnit test witnessed it.

The method in full115 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The finder read stringToTime and stringToDate against their @throws obligation and traced which strings reach the parse: only the length is checked, then DateFormat.parse(String) on a lenient format, which by its own javadoc needs only a parseable beginning.
  • The finder wrote a public-API test (month 13) that fails on main with assertions on and off, on 10.6.0 and 9.12.3; the tie-breaker replaced it with the trailing-letter test above, which no reading of the format allows.
  • An independent reproducer, an executed cross-model review, a devil's-advocate verifier, an adjudication and the tie-breaker reran it with their own tests ("Prior reports, history and checks").
