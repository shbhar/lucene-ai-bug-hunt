CJKBigramFilter drops the position hole in front of CJK text, so phrases match across a removed word

With a stop filter in front of CJKBigramFilter, a word removed right before CJK text leaves no position hole, so the phrase "foo 東京" matches "foo the 東京" (unlike "foo bar" on "foo the bar"). Reproduced on 13 releases from 3.6.0 to 10.6.0 and main; CJKAnalyzer is not affected.

The finding in 30 seconds

#

CJKBigramFilter rebuilds every CJK token from scratch and forgets the hole in front of it.

Position holes and CJK bigrams, in one minute

#
  1. Every token has a position increment, normally 1. A phrase query matches only when its words sit at consecutive positions.
  2. A StopFilter that removes a word adds that word's position to the next token's increment: "foo the bar" becomes foo +1, bar +2. That hole is what stops the phrase "foo bar" from matching; Lucene documents this as the intended stop-word behaviour.
  3. Chinese and Japanese text has no spaces between words, so CJKBigramFilter turns each run of CJK characters into overlapping two-character tokens: 東京大学 becomes 東京, 京大, 大学. A lone CJK character stays a one-character token.

The finding, step by step

#
  1. Analyze with StandardTokenizer → StopFilter(["the"]) → CJKBigramFilter, at index and query time. "foo the bar" gives foo +1, bar +2: the removed "the" leaves a one-position hole, so the phrase "foo bar" finds 0 documents.
  2. Analyze "foo the 東京". The StopFilter hands the bigram filter 東 with increment +2, the same hole.
  3. You expect foo +1, 東京 +2, so that the phrase "foo 東京" does not match, just like "foo bar".
  4. Instead you get foo +1, 東京 +1: the filter builds 東京 from cleared attributes and never copies the +2. The phrase "foo 東京" finds the document: 1 hit instead of 0. No error, and the offsets are right.
  5. Same with a Japanese particle as the stop word: with の removed, "東京の大学" gives 東京 +1, 大学 +1, and the phrase "東京 大学" matches it.

Who is affected

#

Custom analyzers that put a token-removing filter (StopFilter, TypeTokenFilter, LengthFilter, KeepWordFilter) before CJKBigramFilter, a natural order for CJK stop words, which inside CJK text cannot be removed after bigramming. Phrase and positional queries then match across a word removed right before CJK text. The shipped CJKAnalyzer removes stop words after the bigram filter and is not affected.

Mechanism, terms and numbers531 words

When a StopFilter (or any other FilteringTokenFilter) removes a word, it adds the removed position to the next token's position increment, so an exact phrase cannot match across the removed word. CJKBigramFilter loses that hole whenever the next token is CJK: it buffers the characters and offsets of its CJK input but not the increment, and it builds every bigram and unigram from clearAttributes(), which sets the increment back to 1. Non-CJK tokens pass through and keep the hole.

With StandardTokenizer → StopFilter(["the"]) → CJKBigramFilter at index and query time, "foo the bar" gives [foo +1, bar +2] but "foo the 東京" gives [foo +1, 東京 +1], and the phrase "foo 東京" finds the document "foo the 東京" while "foo bar" does not find "foo the bar". It needs a custom chain with a token-removing filter before the bigram filter, which is the only place a CJK stop word inside running CJK text can be removed. The shipped CJKAnalyzer removes stop words after the bigram filter and is not affected. The filter has behaved this way since it was added (3.6.0).

The code (main f794ff5a505c)

#
  1. Removing filters create the hole. FilteringTokenFilter.incrementToken adds the skipped positions to the next accepted token's increment (FilteringTokenFilter.java:49-58).
  2. CJK tokens are buffered without it. For a CJK-typed token, incrementToken calls refill() (CJKBigramFilter.java:186-207; a run continues while offsets are adjacent, :193). refill() copies the token's code points and offsets into buffer, startOffset and endOffset, and nothing else (:261-302).
  3. Every CJK output starts from cleared attributes. flushBigram() (:307-322) and flushUnigram() (:329-337) begin with clearAttributes() (:308, :330), which resets the increment to 1. The only increment they ever set is 0, for bigrams stacked on unigrams when outputUnigrams=true (:317-320).
  4. Non-CJK tokens keep it. A non-CJK token is returned as is, with its hole (:208-223), as the class javadoc says: "In all cases, all non-CJK input is passed thru unmodified" (:49).

CJKBigramFilter.java:307-315, verbatim (flushUnigram, :329-335, has the same shape). clearAttributes() on line 308 sets the increment back to 1, and nothing after it restores the input's +2:

  private void flushBigram() {
    clearAttributes();
    char[] termBuffer =
        termAtt.resizeBuffer(4); // maximum bigram length in code units (2 supplementaries)
    int len1 = Character.toChars(buffer[index], termBuffer, 0);
    int len2 = len1 + Character.toChars(buffer[index + 1], termBuffer, len1);
    termAtt.setLength(len2);
    offsetAtt.setOffset(startOffset[index], endOffset[index + 1]);
    typeAtt.setType(DOUBLE_TYPE);

Why it looks unintended

#
  • Lucene's analysis docs: a filter that removes tokens must increment the next token's position increment, so the phrase "blue sky" does not find "blue is the sky".
  • The same filter keeps the hole for non-CJK tokens ("all non-CJK input is passed thru unmodified"); only CJK tokens lose it.
  • No test asserts today's behaviour; NGramTokenFilter keeps its input's increment.
The full argument185 words
  • Core contract. "a filter that filters out tokens must increment the position increment in order not to generate corrupt tokenstream graphs" (package-info.java:303-305); "When they remove tokens, token filters should increment the position increment of the following token" (:422-423); the phrase "blue sky" must not find "blue is the sky" (:294-298). PositionIncrementAttribute: increments greater than one "inhibit exact phrase matches" across removed stop words (PositionIncrementAttribute.java:35-39).
  • Asymmetry inside the filter. The same chain keeps the hole for "foo the bar" and drops it for "foo the 東京".
  • Precedent. NGramTokenFilter adds its input's increment to its first gram (NGramTokenFilter.java:108; its positions were reworked in LUCENE-4955, CHANGES.txt:13636). LUCENE-4963 deprecated enablePositionIncrements=false on StopFilter and the other removing filters as an option that generates broken token streams (CHANGES.txt:13660).
  • No test asserts the current behaviour. The introducing commit's own TestCJKAnalyzer.testSingleChar2 puts a StopFilter before CJKBigramFilter (TestCJKAnalyzer.java:354-362), but with CharArraySet.EMPTY_SET, so it never makes a hole.
  • Caveat. No javadoc sentence promises holes for CJK tokens specifically; the case rests on the general contract and the asymmetry.
The devil's-advocate check279 words

The case for "intended". The class javadoc says it bigrams CJK terms "generated from StandardTokenizer or ICUTokenizer" (CJKBigramFilter.java:32), so it is a rewriter for tokenizer output; the shipped CJKAnalyzer applies stop words after it; and it is excluded from random chains as "LUCENE-8092: doesn't handle graph inputs" (:51). Statements by the filter's author, rmuir, point the same way: on #9140 (LUCENE-8092, 2018-03-04) they called it "looking for a flat stream of tokens" and wished one could "simply require that its input is a tokenizer"; on #9496 (LUCENE-8450, 2018-08-09) they listed it among "the offensive filters that really should be tokenizers: they are all a real nightmare: cjkbigramfilter, worddelimiterfilter, etc." A maintainer may quote both.

Why it fails. The full #9140 sentence is "Unfortunately its not so easy to simply require that its input is a tokenizer, see the CJKAnalyzer use-case where the width-filter comes before, because that impacts bigramming": the input is not required to be a tokenizer. The guard proposed in the same comment, "throw a clear exception if it encounters posinc=0 or poslen > 1", lets a stop-word hole through (increment 2, length 1): a stream with holes is still a flat stream, not a graph. The class is a public TokenFilter, nothing forbids filters in front of it, its own test composes one, and it keeps holes for non-CJK tokens. The repro's input is plain StandardTokenizer output with one StopFilter in between, and CJK stop words inside running CJK text can only be removed before it. Both executed reviews by another model family (OpenAI GPT-5.6) and the intended-behaviour verifier rated this defence weak; the verifier had both statements when it did.

Suggested fix

#

Recommended Carry the run's leading increment (validated)

Remember the increment of the token that starts each buffered CJK run and give it to the first unigram or bigram flushed from that run (+12 lines). The repro, the cjk package and the ICU bigram tests then pass. It changes stored positions for such chains: old documents need reindexing, and a migration note may be appropriate.

// refill(), before the code points are buffered
if (bufferLen == 0) {
  runPosInc = Math.max(1, posIncAtt.getPositionIncrement());
}
// flushBigram() and flushUnigram(), after typeAtt.setType(...)
posIncAtt.setPositionIncrement(runPosInc);
runPosInc = 1;
// reset()
runPosInc = 1;

Carry the run's leading increment (validated) (recommended)

#

When refill() starts a new buffered run (bufferLen == 0), remember Math.max(1, posIncAtt.getPositionIncrement()). The first unigram or bigram flushed from that run gets it, then it resets to 1. With outputUnigrams=true the first unigram carries it and the stacked bigram stays at 0. reset() sets it back to 1.

// refill(), before the code points are buffered
if (bufferLen == 0) {
  runPosInc = Math.max(1, posIncAtt.getPositionIncrement());
}
// flushBigram() and flushUnigram(), after typeAtt.setType(...)
posIncAtt.setPositionIncrement(runPosInc);
runPosInc = 1;
// reset()
runPosInc = 1;

Trade-offs

  • Positions change. Chains with a removing filter before the bigram filter index different positions. Until documents are reindexed, a phrase query that contains the removed word ("foo the 東京", now 東京 +2) no longer matches old documents indexed as 東京 +1 (by construction, not run). A CHANGES/MIGRATE note may be appropriate; amatoba raised the same compatibility concern on #15825.
  • Only at the start of a run, so not every hole. A run continues only while a CJK token starts exactly where the previous buffered CJK token ended (CJKBigramFilter.java:193; lastEndOffset is set in refill(), :282). With ordinary tokenizer output a removed word takes up text between the two, so the next CJK token starts a new run and keeps its hole. But increments and offsets are independent attributes: a hole on a CJK token that is offset-adjacent to the previous one (for example after a removed zero-width token, or a removed token whose offsets overlap the CJK text) continues the run and would still be dropped (by construction, not run). Fix B covers that case.
  • Graph input (increment 0) keeps today's behaviour.
  • Open PR #15825 (for #15812, a different position defect) edits the same flush methods and adds a deferredPosInc; whichever lands second must fold the input hole into it. With #15825's patch applied, the repro still fails.

What the checks validated

  • With the fix: :lucene:analysis:common:test --tests 'org.apache.lucene.analysis.cjk.*' passes 44 of 44 in 8 classes (TestCJKBigramFilter 8, TestCJKAnalyzer 17, the factory and width-filter tests and the repro; TestFactories was selected too but is nightly-only and was skipped); :lucene:analysis:icu:test --tests TestWithCJKBigramFilter passes 12 of 12; :lucene:analysis:common:check -x test passes.

Per-character increments

#

Buffer each input token's increment in a parallel array, like startOffset, and apply it to the output token that starts at that character.

Trade-offs

Covers holes anywhere, including inside an offset-adjacent run, at the cost of one more array and more change in the outputUnigrams stacking logic. Not built.

Documentation only

#

Say in the class javadoc that token-removing filters belong after CJKBigramFilter.

Trade-offs

No position change, but CJK stop words inside running CJK text, which can only be removed before bigramming, would have no correct place, and the CJK/non-CJK asymmetry stays. Not recommended.

Downstream note

#

Products that build analyzers from configuration by factory name (cjkBigram) inherit this whenever a stop filter is configured before the bigram filter.

How it was found

#

A semi-formal random sweep: 10,000 analysis chains built from Lucene's filter factories, each run on 12 texts and checked against metamorphic token-stream properties. The property "inserting a word that an earlier StopFilter removes must only add one position hole" failed at several stages, and 13 of its failures were at CJKBigramFilter; one JUnit test on main confirmed it.

The method in full170 words

Method: semi-formal, metamorphic testing of composed analysis chains, on main f794ff5a505c, 2026-11-09.

  • Sweep. 10,000 random chains assembled from the tokenizer and filter factories (seed 4802, assertions on), each run on 12 texts. Each chain was checked against token-stream properties that must hold for any correct chain, for example that inserting a word which a StopFilter earlier in the chain removes adds exactly one position hole to the output.
  • Signal. The hole property failed in 18 groups at 14 blamed stages (431 hits; 241 without the two groups keyed to the stage before the stop filter). 13 of its failures, in one group, were at CJKBigramFilter; the other groups were triaged separately. The filter's @IgnoreRandomChains reason (graph input) was applied only to examples that actually contain graph input (stacked tokens or position length above 1); these examples have none, so they were not skipped.
  • Confirmation. A one-method JUnit test on public API reproduced it on main, and code reading found the cause in refill() and the flush methods.

Registry title
CJKBigramFilter never applies the position increment of its CJK input tokens to the bigrams and unigrams it builds from them, so the hole that a StopFilter (or any token-removing filter) placed before it leaves in front of CJK text disappears and an exact phrase matches across the removed word, while a non-CJK token behind the same hole keeps it; since 3.6.0
Area
analysis / CJK (CJKBigramFilter position increments; a custom chain with a token-removing filter before cjkBigram)
Priority
Low, rank 498: Since 3.6.0, CJKBigramFilter drops the hole that a removed token leaves in front of CJK text, so exact phrase and other positional queries silently match across the removed word. It is Low because it needs a custom chain with a token-removing filter before the bigram filter (the shipped CJKAnalyzer is not affected), and it only loosens positional matching without losing any term or document.
Impact class
silent wrong results
Impact note
Only applications whose custom analyzer puts a token-removing filter (StopFilter, TypeTokenFilter, LengthFilter, KeepWordFilter, ...) in front of CJKBigramFilter are hit: whenever a removed token comes right before CJK text, the CJK bigram or unigram built from it gets position increment 1 instead of the hole, so exact phrase and other positional queries over that field silently match across the removed word, with -ea and -da, in the default and the outputUnigrams mode, behind StandardTokenizer or ICUTokenizer [exec]; the shipped CJKAnalyzer (which removes stop words after the bigram filter) and chains without a removing filter in front are not affected [read], offsets stay correct and nothing fails.
Summary
You build an analyzer StandardTokenizer > StopFilter(['the']) > CJKBigramFilter and analyze 'foo the 東京'. You expect [foo +1, 東京 +2]: the removed 'the' leaves a one-position hole, as it does for 'foo the bar', which the same chain turns into [foo +1, bar +2], so that the phrase 'foo 東京' does not match. Instead CJKBigramFilter builds the bigram 東京 from a cleared attribute state and never copies the position increment of the CJK input token, so the stream is [foo +1, 東京 +1] and, with this analyzer at index and query time, the phrase 'foo 東京' matches the document 'foo the 東京' (the phrase 'foo bar' does not match 'foo the bar').
