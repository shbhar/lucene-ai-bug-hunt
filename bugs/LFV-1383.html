XML query parser ignores text inside CDATA sections

Lucene's XML query parser ignores any text written inside a CDATA section: <TermsQuery fieldName="f">apple <![CDATA[pear]]></TermsQuery> parses to a query for f:apple only, silently dropping "pear". It has been so since the parser was added in Lucene 1.9 (2006) and still is in 10.6.0 and main.

The finding in 30 seconds

#

In XML, <![CDATA[ ... ]]> wraps text that must not be read as markup; its content is ordinary character data (XML 1.0, section 2.7). A DOM parser keeps it as a separate CDATA-section node, a kind of text node, unless coalescing is turned on.

  1. You parse <TermsQuery fieldName="f">apple <![CDATA[pear]]></TermsQuery> with CoreParser, Lucene's XML query parser. In XML, <![CDATA[pear]]> is simply the text pear, written so that characters such as & or < need no escaping.
  2. You expect the same query as for the plain text apple pear: (f:apple f:pear)^1.0. On 4 documents ("apple pie", "apple tart", "plum cake", "pear") it matches 3.
  3. Instead you get (f:apple)^1.0, a query for f:apple only: 2 hits, and no error. The helper that reads an element's text, DOMUtils.getText, collects plain text nodes but has no case for CDATA-section nodes, so their text is skipped.
  4. Every text element reads through that helper. A LikeThisQuery whose text is all CDATA is left with no like-text and rewrites to MatchNoDocsQuery: 0 hits instead of 2. A CDATA-only TermQuery or UserQuery fails with ParserException ("TermQuery has no text", "Cannot parse ''").

Who is affected

#

Applications that use the opt-in XML query parser (CoreParser and its subclasses, default settings) and put query text in CDATA sections, for example database text containing &. Mixed text loses words silently; a CDATA-only LikeThisQuery matches nothing; other CDATA-only queries fail loudly. One CDATA section is enough, with assertions on or off.

Mechanism, terms and numbers481 words

In XML a CDATA section, <![CDATA[ ... ]]>, is ordinary text that may contain & or < without escaping (XML 1.0, section 2.7). Lucene's XML query parser reads every element's text through DOMUtils.getText, whose helper getTextBuffer appends text nodes and descends into child elements and entity references but has no case for CDATA-section nodes (DOMUtils.java:157-177 at 5adff78bb168). CoreParser.parse(InputStream) builds its DOM without coalescing, so each CDATA section is its own node, and its text is skipped without an error. Text mixed with a CDATA section loses the CDATA words in every text element (TermsQuery, TermQuery, SpanTerm, SpanOrTerms, BoostingTermQuery, UserQuery, LikeThisQuery); a CDATA-only LikeThisQuery silently matches nothing; the other CDATA-only elements throw ParserException. The switch has been like this since the parser was added in Lucene 1.9 (2006) and is unchanged in 10.6.0 and main. The fix is one case label.

The code (main 5adff78bb168)

#
  • The DOM. CoreParser.parse(InputStream) (CoreParser.java:137-143) builds the document in the private parseXML (:182-206): a default DocumentBuilderFactory, setValidating(false), secure processing and an entity resolver. It never calls setCoalescing(true), so (the JAXP default) every CDATA section stays its own CDATASection node next to the plain Text nodes. CoreParser has no per-call or protected option for coalescing, so a plain parse(InputStream) call cannot change this (short of a subclass overriding parse to build its own DOM).
  • The text reader. The builders get an element's text from DOMUtils.getText (DOMUtils.java:142-146) or getNonBlankTextOrFail (:64-71, which throws "<tag> has no text" when the trimmed text is empty): TermsQueryBuilder.java:48, TermQueryBuilder.java:34, SpanTermBuilder.java:32, SpanOrTermsBuilder.java:45, BoostingTermBuilder.java:35, UserInputQueryBuilder.java:60, LikeThisQueryBuilder.java:89.
  • The gap. getTextBuffer (DOMUtils.java:157-177) switches on each child's node type: TEXT_NODE appends the value (:160-164); ELEMENT_NODE (:165-169) and ENTITY_REFERENCE_NODE (:170-174) recurse. There is no CDATA_SECTION_NODE case and no default, so CDATA text is dropped.

Exposure and likelihood205 words
  • Who is exposed. Users of CoreParser, CorePlusQueriesParser and CorePlusExtensionsParser through parse(InputStream) (LikeThisQuery needs CorePlusQueriesParser, FuzzyLikeThisQuery its subclass CorePlusExtensionsParser), and of getQuery(Element) on a DOM built without coalescing (the JAXP default). Not exposed: callers who build their own DOM with DocumentBuilderFactory.setCoalescing(true).
  • Default vs opt-in. The XML query parser is an opt-in module; within it the default path is affected.
  • What goes wrong. Silent: fewer terms than written (mixed text), or no hits at all (CDATA-only LikeThisQuery, whose like-text is often a document's text, a natural thing to wrap in CDATA). Loud: a ParserException that says the element "has no text" when it has, or Cannot parse '' for UserQuery. Inside a larger BooleanQuery a lost term can also widen the results: under a MUST_NOT clause it excludes less (by reading, not run).
  • Scale. None needed: one CDATA section in one element.
  • Downstream. Solr's defType=xmlparser passes request XML through SolrCoreParser (extends CoreParser) .parse(InputStream) (XmlQParserPlugin.java:98 in Solr; read, not run). Elasticsearch and OpenSearch do not use the package.
  • How likely. Rare: a niche module, and the most natural CDATA-only forms fail loudly, so they are found in development; no public report of it was found in about 20 years.

Why it looks unintended

#
  • XML 1.0 makes a CDATA section ordinary character data; the shipped DTD declares <!ELEMENT TermsQuery (#PCDATA)>: "Child text is analyzed".
  • getTextBuffer deliberately reads entity references and nested elements; the searches found nothing that documents CDATA as unsupported, and no test uses it.
  • parse(InputStream) builds its own non-coalescing DOM, so a plain parse call cannot work around it.
The full argument249 words
  • XML. XML 1.0 section 2.7: "CDATA sections may occur anywhere character data may occur; they are used to escape blocks of text containing characters which would otherwise be recognized as markup." In DOM, CDATASection extends Text, and DOM Level 3 Node.textContent includes it.
  • The DTDs. LuceneCoreQuery.dtd:226-238: TermsQuery "Child text is analyzed using a field-specific choice of Analyzer to produce a set of terms", with the example Smith & Sons (Ltd) (database text with &, which must be escaped or wrapped in CDATA), then <!ELEMENT TermsQuery (#PCDATA)>. UserQuery (:159), TermQuery (:195), BoostingTermQuery (:218), SpanTerm (:372), SpanOrTerms (:387) and LikeThisQuery (LuceneContribQuery.dtd:118) are #PCDATA too.
  • Public javadocs. CoreParser.parse: "Parses the given stream as XML file and returns a Query" (CoreParser.java:137-140); TermsQueryBuilder: "Builds a BooleanQuery from all of the terms found in the XML element" (TermsQueryBuilder.java:35).
  • The code's intent. It collects text through entity references and nested elements; comments and processing instructions are rightly skipped. Only the CDATA kind of text node is missing. (With the JAXP defaults that parseXML keeps, entity references are expanded while parsing, so the entity-reference case shows the helper's intent for any DOM rather than a path parse(InputStream) takes.)
  • No decision the other way found. The searches recorded here found no javadoc, DTD, README, CHANGES or MIGRATE entry, commit message or list mail that says CDATA is unsupported; no test in lucene/queryparser uses a CDATA section.
The devil's-advocate check165 words

The strongest case for "intended": DOMUtils is @lucene.internal (DOMUtils.java:22-26), its promise "Returns text of node and all child nodes - without markup" is a plain code comment (:139), CDATA delimiters are markup (XML 1.0 section 2.4), and JAXP leaves coalescing to the caller. Also: no report of it was found in about 20 years, and changing a shared helper changes what custom builders receive.

Why it fails: the defect shows through the public CoreParser.parse(InputStream), whose private parseXML builds the DOM and offers no coalescing option. "Without markup" means dropping the <![CDATA[ and ]]> delimiters, not the text inside (section 2.7), just as the method drops an entity reference's &...; but keeps its text. The @lucene.internal tag (2025, #15234) frees the helper from API stability, not the public parser from returning the text it was given. The missing reports speak to how rare it is (rated rare, priority Low), not to intent, and the change only adds text the caller wrote.

Suggested fix

#

Recommended Read CDATA sections like text nodes in getTextBuffer

Add case Node.CDATA_SECTION_NODE: next to case Node.TEXT_NODE: in DOMUtils.getTextBuffer, so CDATA text is appended like plain text. One line; it fixes every text element, through parse(InputStream) and getQuery(Element). Validated with gradle: the repro passes (assertions on and off), all 534 queryparser tests pass, and :lucene:queryparser:check -x test passes.

How it was found

#

Mutation testing of DOMUtils against the module's own XML-parser tests led to reading getTextBuffer, where the missing CDATA case stood out: an omission that no mutant can show. A metamorphic check through the public CoreParser.parse confirmed it: the same text written as plain text and as a CDATA section must give the same query.

The method in full127 words

Method: non-formal (mutation testing, then code reading and a metamorphic test), on main 5adff78bb168, 2026-11-04.

  • A source mutator applied 51 mutants to DOMUtils, with the module's own XML-parser tests as the kill oracle; 19 survived. Reading getTextBuffer while triaging the survivors showed that the switch has no CDATA_SECTION_NODE case.
  • A metamorphic check through CoreParser.parse(InputStream) witnessed it: the same character data written as plain text and as a CDATA section must parse to the same Query; it did not.
  • Afterwards a bounded-exhaustive model compared DOMUtils.getText with DOM Level 3 textContent on all 585 child sequences over 8 node kinds, with coalescing off and on (1,170 checks): 326 mismatches, exactly the sequences that contain a CDATA section, only with coalescing off, and 0 with the fix.

History

#

It dates back to Lucene 1.9 (2006-02-27), the first release with the parser. The switch has had the same three cases since the commit that added the XML query parser (87768c51c632, 2006-02-25); the jars of both 1.9 and 1.9.1 fail when run. Every release through 10.6.0 and main is affected; never fixed.

Versions tested8 rows

Introduced by 87768c51c632 (SVN r380874, 2006-02-25, Mark Harwood), "Added XML-query-parser module for new extensible query parser that handles queries expressed as XML", a direct SVN commit with no JIRA key or PR; its getTextBuffer already had exactly the three cases TEXT_NODE, ELEMENT_NODE and ENTITY_REFERENCE_NODE. It reached the 1.9 branch through the SVN merge 5a2b6cd9a37 (2006-02-27); the 1.9 (2006-02-27) and 1.9.1 (2006-03-02) tags hold the module byte-identical to that commit. Both releases fail when run: 1.9 with the lucene-xml-query-parser-1.9-final.jar of the official 1.9 binary distribution (in the Apache archive; Maven Central starts at 1.9.1), 1.9.1 with its Maven Central jar. Not a regression: all 22 commits that touched DOMUtils.java keep the same three cases, and no commit ever turned coalescing on in CoreParser (git log -S, git blame -w -M -C -C). All 147 release tags in the history clone from 1.9 to 10.6.0 have the same cases; the releases without a tag there (3.0.2, 3.0.3, 8.8.2 to 8.11.4) are covered by the 8.11.4 run and by the unchanged code on either side. The DTDs that declare these elements #PCDATA came later (2007, first released in 2.3.0).
