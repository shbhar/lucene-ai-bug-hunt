A damaged stored-fields or term-vectors meta file leaves the .fdx (.tvx) file open after CorruptIndexException

Opening an index whose stored-fields (.fdm) or term-vectors (.tvm) meta file has one damaged pointer throws CorruptIndexException, as it should, but leaves the .fdx (.tvx) file open: one leaked input per failed open, in every release since 8.7.0.

The finding in 30 seconds

#

Opening a segment reads a few pointers from a small meta file and uses them to map two tables inside .fdx. When a damaged pointer makes that mapping fail, Lucene reports the corruption correctly but never closes .fdx.

Stored-fields files in one minute

#
  1. Each segment keeps its stored fields in three files: .fdt (the compressed documents), .fdx (an index: where each chunk of documents starts in .fdt) and .fdm (a small meta file with pointers saying where each table sits inside .fdx). Term vectors use .tvd, .tvx and .tvm the same way.
  2. Opening the segment reads .fdm, opens .fdx and maps its two tables by those pointers. .fdm ends with a checksum, which is verified once the rest of .fdm has been read, after .fdx is set up.

The finding, step by step

#
  1. You open an index with DirectoryReader.open. One segment, not in a compound file, has one flipped bit in its 157-byte _0.fdm: the pointer to where a table starts in the 64-byte _0.fdx now reads 2^62 + 48 instead of 48, as a disk or copy error could leave it.
  2. You expect CorruptIndexException, with every file the open touched closed again, as Lucene does for other damaged files.
  3. You get the CorruptIndexException ("checksum failed", with slice(offset=4611686018427387952, ...) is out of bounds: 64 bytes suppressed), but _0.fdx stays open: MockDirectoryWrapper.close() reports there are still 1 open files: {_0.fdx=1}, with assertions on and off.
  4. Why: FieldsIndexReader's constructor opens _0.fdx and closes it on failure only around its header and checksum checks. The slice set-up right after runs outside that try, and the caller never received the object, so nobody closes it. Term vectors (.tvm, .tvx) go through the same code.

Who is affected

#

Anyone opening an index whose .fdm/.tvm is damaged in a pointer byte, with the default codec and directory, for segments outside a compound file (by default, large merged segments). The open still fails correctly; each failed attempt leaks one input, with MMapDirectory the segment's mappings. Rare: it needs a damaged meta file.

Mechanism, terms and numbers526 words

FieldsIndexReader's constructor reads a few pointers from the stored-fields meta file (.fdm, or .tvm for term vectors), opens the index file (.fdx or .tvx) and closes it on failure only inside a try around checkIndexHeader and retrieveChecksum (FieldsIndexReader.java:71-82 at 5adff78bb168). The two randomAccessSlice and two DirectMonotonicReader.getInstance calls that follow (:83-89) are outside it. Because the meta checksum is verified only after this constructor, one random damaged byte in a pointer reaches them; they throw IllegalArgumentException, the enclosing reader correctly reports CorruptIndexException, but it never received the object, so the .fdx (.tvx) input stays open. That is one leaked input per failed open (with MMapDirectory, the segment's mappings), for segments not stored in a compound file, in every release since 8.7.0 (LUCENE-9456) and on main. The trigger is a damaged index file and the open fails loudly, so priority Low; moving the four calls into the existing try fixes it at no cost.

Step by step

#
  1. Lucene90CompressingStoredFieldsReader opens .fdt and .fdm, checks the .fdm header and calls new FieldsIndexReader(..., metaIn, context) (Lucene90CompressingStoredFieldsReader.java:199-208). It stores the result in this.indexReader only after the constructor returns (:209, :213).
  2. The .fdm checksum is verified only afterwards: CodecUtil.checkFooter(metaIn, null) on success (:244), checkFooter(metaIn, t) on failure (:249). So a damaged pointer with a stale checksum reaches randomAccessSlice.
  3. In the repro, one flipped bit (0x40 of byte 71 of the 157-byte _0.fdm, the top byte of the little-endian docsStartPointer) turns 48 into 2^62 + 48 = 4,611,686,018,427,387,952. randomAccessSlice on the 64-byte _0.fdx throws IllegalArgumentException: slice(offset=4611686018427387952, length=-4611686018427387904) is out of bounds: 64 bytes at FieldsIndexReader.java:84, outside the try.
  4. The caller's failure path runs checkFooter(metaIn, t), which throws CorruptIndexException: checksum failed (hardware problem?) with the IllegalArgumentException suppressed, then IOUtils.closeWhileSuppressingExceptions(t, this, metaIn) (:246-256). close() closes indexReader, still null, and fieldsStream (:284). Nobody holds the .fdx input. The CorruptIndexException comes from the stale meta checksum: for a crafted meta file with a valid checksum, checkFooter(metaIn, t) would add a suppressed "checksum passed" note and rethrow the IllegalArgumentException itself (CodecUtil.java:471-517); the 8.6.3 probe with a recomputed checksum threw a bare IllegalArgumentException and leaked the same way.
  5. A damaged bits-per-value byte (read by loadMeta, :65, :67) has the same effect through DirectMonotonicReader.getInstance (:88-89): DirectReader.getInstance throws IllegalArgumentException("unsupported bitsPerValue: ...") (util/packed/DirectReader.java:89).
  6. Term vectors: Lucene90CompressingTermVectorsReader calls the same constructor for .tvx (:181-192) with the same failure path (:233-243); independent checks leaked _0.tvx the same way on main.
Exposure and likelihood412 words
  • Who is hit. Anyone who opens an index (DirectoryReader.open, or any segment-reader open that loads stored fields or term vectors) in which one segment's .fdm or .tvm is damaged in a byte that becomes a slice bound or a bits-per-value. No special codec, directory or setting is needed, but the damaged segment must not be in a compound file (next point).
  • Only segments outside a compound file. In a compound segment the leaked input is only a slice of the .cfs. In the executed compound-file probe, the same one-bit damage inside _0.cfs gave the same CorruptIndexException (and the same IllegalArgumentException at FieldsIndexReader.java:84), the failed open closed the .cfs, and dir.close() succeeded. With default settings flushed segments are compound (IndexWriterConfig.DEFAULT_USE_COMPOUND_FILE_SYSTEM = true), but large merged segments are not: on main, merges larger than 64 MB (CompoundFormat.DEFAULT_CFS_THRESHOLD_BYTE_SIZE); in 10.6.0, merges of more than 10% of the index (TieredMergePolicy.DEFAULT_NO_CFS_RATIO = 0.1, MergePolicy.java:754). So in a real index the largest segments are the exposed ones; with compound files off, all are.
  • Effect. The open fails loudly and correctly, and nothing is read wrongly. The defect is one IndexInput left open per failed open, so an application that retries opening a damaged index or replica in one JVM leaks one per attempt. A separate real-directory check on main and 10.6.0 (assertions off; one measured run each on Linux, mappings counted from the process's memory map) found that with MMapDirectory 7 files of the segment (_0.fdx, _0.fdt, _0.nvd and four postings files) stayed mapped after the failed open, dir.close() and System.gc(), against 0 after a healthy open and close: by default MMapDirectory puts a segment's files in one shared arena (GROUP_BY_SEGMENT, MMapDirectory.java:192) and the unclosed .fdx keeps it open. With NIOFSDirectory nothing remained after GC.
  • How likely: rare. It needs a damaged .fdm/.tvm (a disk, memory or copy error), but no crafting: a single-bit sweep of a 3-document segment flipped every bit of _0.fdm (157 bytes) and _0.tvm (162 bytes); of the 1,256 .fdm flips, 189 left _0.fdx open (each with a CorruptIndexException), 1,066 gave a clean CorruptIndexException and 1 an OutOfMemoryError; of the 1,296 .tvm flips, 189 left _0.tvx open, 1,105 were clean and 2 gave an OutOfMemoryError (SECURITY.md lists "excessive memory allocation" for corrupt files; not claimed). No flip went undetected. No public report was found in the documented searches (as of 2026-11-03).

Why it looks unintended

#
  • The constructor already closes .fdx when its header or checksum check fails; the four calls after it are just outside that try.
  • The callers' failure path reports the damaged meta file and closes what it opened; MockDirectoryWrapper fails on any file left open.
  • Upstream fixed the same shape as bugs (LUCENE-9322, 7908df2b7c4).
The full argument322 words
  • The constructor already does this cleanup for earlier failures. It closes the input it opened when the header or checksum step fails (FieldsIndexReader.java:75-82). The four calls after it can fail for the same kind of reason and are just outside that try. Nobody else can close the input: the callers get the object only after the constructor returns. No javadoc states a cleanup contract; the code shows the expectation, it does not document it.
  • The callers' failure path handles this case. catch (Throwable t) runs checkFooter(metaIn, t), which reports a damaged meta file as CorruptIndexException (the original exception suppressed), then closes everything the caller opened (Lucene90CompressingStoredFieldsReader.java:246-256, Lucene90CompressingTermVectorsReader.java:233-243).
  • The test framework enforces it. MockDirectoryWrapper.close() fails on any input left open (MockDirectoryWrapper.java:873-887), and Lucene's own corruption tests open damaged copies usually through it (newDirectory() returns a MockDirectoryWrapper in most runs; TestAllFilesDetectMismatchedChecksum, TestAllFilesDetectTruncation, TestAllFilesCheckIndexHeader). They never reach this path only because they damage footers (the last 16 bytes, TestAllFilesDetectMismatchedChecksum.java:104-107), headers or lengths.
  • Upstream fixed the same shape as bugs. LUCENE-9322 (apache/lucene-solr#2371, 4cdfbbb95be, 2021): "Lucene90VectorReader can leak open files". 7908df2b7c4 (2026-04-22, Lucene90DocValuesProducer): interruptions "could cause the data file to leak, because the open call was outside the relevant try-catch block". LUCENE-8692 (e93313d42c4, 2019): "fix file leak in MockRandomPostingsFormat that surfaces when corrupting files".
  • History: an accident of a refactoring. In LUCENE-9147 (136dcbdbbce on main; 597141df6b6 on branch_8x, released in 8.5.0) the constructor read its own meta file and checked its footer before opening .fdx, so only a checksum-valid (crafted) meta could reach the unguarded calls. LUCENE-9456 (e6fa5a5fc45 on main; 7867080d893 on branch_8x, released in 8.7.0) moved the metadata into the shared .fdm, whose footer the caller checks only after the constructor. #14913 (27d1272984f, 2025) restyled the block and kept its scope. No comment, test, issue or PR review discusses this failure path.
The devil's-advocate check183 words

The strongest case: "SECURITY.md says corrupting index files can cause undefined behaviour, by design (lines 30-32); FieldsIndexReader is package-private with no documented cleanup contract; the open fails loudly anyway." Both executed reviews by another model family (OpenAI GPT-5.6) rated the bug not real on this ground alone, while reproducing the leak and confirming the fix.

Why it does not hold for this defect: that clause defines what is not a security issue and pins the undefined behaviour on not validating contents "for performance reasons". Here Lucene does detect the corruption and reports it as designed; the defect is only the resource cleanup on that error path, and the fix adds no validation and no work on the success path. SECURITY.md line 46 calls out-of-scope issues "still valid bug reports and hardening suggestions" and welcomes "a clean CorruptIndexException on a broken index" when it costs no performance. The code shows a strong cleanup expectation, not a documented contract: a maintainer may call the fix hardening, or close it as won't-fix. That is the claim's main weakness, and why it is Low with medium confidence.

Suggested fix

#

Recommended A: move the four calls into the existing try

Move the two randomAccessSlice and two DirectMonotonicReader.getInstance calls into the existing try/catch that already closes indexInput: 7 lines moved, no new code, no cost when the open succeeds. Validated: the repro passes with assertions on and off; 24 suites (818 tests) and :lucene:core:check -x test pass.

A: move the four calls into the existing try (validated by the checks) (recommended)

#

In FieldsIndexReader's constructor, move the two randomAccessSlice calls and the two DirectMonotonicReader.getInstance calls (:83-89) to the end of the try that already closes indexInput on failure (:75-82). The final fields still compile: definite assignment holds because the catch rethrows. The CorruptIndexException is unchanged; only the .fdx (.tvx) input is now closed.

try {
  CodecUtil.checkIndexHeader(
      indexInput, codecName + "Idx", VERSION_START, VERSION_CURRENT, id, suffix);
  CodecUtil.retrieveChecksum(indexInput);
  final RandomAccessInput docsSlice =
      indexInput.randomAccessSlice(docsStartPointer, docsEndPointer - docsStartPointer);
  final RandomAccessInput startPointersSlice =
      indexInput.randomAccessSlice(
          startPointersStartPointer, startPointersEndPointer - startPointersStartPointer);
  docs = DirectMonotonicReader.getInstance(docsMeta, docsSlice);
  startPointers = DirectMonotonicReader.getInstance(startPointersMeta, startPointersSlice);
} catch (Throwable t) {
  IOUtils.closeWhileSuppressingExceptions(t, indexInput);
  throw t;
}

Trade-offs

The smallest change, on the failure path only: no extra I/O, no new checks, nothing on the success path. It covers both stored fields and term vectors, which share the constructor.

B: check the pointers before opening (complement, untested)

#

Before openInput, throw new CorruptIndexException(..., metaIn) when the pointers read from the meta file are negative or out of order (docsStartPointer <= docsEndPointer <= startPointersEndPointer).

Trade-offs

A clearer message, and no open at all in those cases. But it cannot compare against the .fdx length before the file is open and does not cover a damaged bits-per-value in DirectMonotonicReader.getInstance, so it does not replace A.

Downstream note

#

Services that retry opening a damaged index or replica in one JVM accumulate one leaked .fdx/.tvx input (with MMapDirectory, the segment's mappings) per attempt, although each attempt still fails with CorruptIndexException.

How it was found

#

A proof-obligation audit of FieldsIndexReader's constructor took its own close-on-failure block as an obligation on every exit after the open. The exit through the slice set-up does not meet it. A one-test JUnit witnessed it on main; independent checks reproduced it with their own tests.

The method in full109 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro), on main 5adff78bb168, 2026-11-03.

  • The obligation: an input the constructor opens is closed when the constructor fails, because nobody else holds it yet. The exits through randomAccessSlice and DirectMonotonicReader.getInstance (FieldsIndexReader.java:83-89) do not meet it.
  • A one-test JUnit witnessed it on main with assertions on and off. An independent reproducer (flipping a different pointer, and the term-vectors path), two executed reviews by another model family (OpenAI GPT-5.6) and a devil's-advocate verifier (a single-bit sweep and a real-directory check) each ran their own tests; an adjudication re-ran two of the tests with fresh seeds.

LFV-1231, snapshot of 2026-11-08

Registry title
Opening a segment whose stored-fields (.fdm) or term-vectors (.tvm) meta file has a damaged slice pointer reports CorruptIndexException but leaves the .fdx (.tvx) file open, because FieldsIndexReader's constructor closes its input only when the header or checksum step fails
Area
codecs / stored fields and term vectors (Lucene90 compressing readers: FieldsIndexReader constructor, cleanup when opening a segment fails)
Priority
Low, rank 1106: Opening an index whose stored-fields or term-vectors meta file is damaged in a slice pointer reports CorruptIndexException correctly but leaves the .fdx or .tvx input open (with MMapDirectory, its mappings) once per attempt, on the default codec and directory in every release since 8.7.0. It needs a damaged file and leaks one bounded resource after a loud failure.
Impact class
minor
Impact note
Hits anyone who opens an index (DirectoryReader.open, or any reader open that loads stored fields or term vectors) in which one segment's .fdm or .tvm meta file is damaged in a slice pointer or a DirectMonotonic bits-per-value byte, with the default codec and directory and no scale: random damage is enough because the meta checksum is verified only after this constructor (the intended-behaviour check's single-bit sweep of a 3-document segment: 189 of 1256 .fdm flips and 189 of 1296 .tvm flips leave the file open, none went undetected); the open still fails loudly and correctly with CorruptIndexException, and the defect is one IndexInput left open per failed open, which with the default MMapDirectory kept 7 files of that segment mapped after dir.close() and System.gc() in the intended-behaviour check's run on main and 10.6.0 (NIOFSDirectory: the channel is gone after GC), so an application that retries opening a damaged index leaks once per attempt; in 8.7.0 through 10.6.0 and on main.
Summary
You open an index with DirectoryReader.open, and one segment's stored-fields meta file (.fdm), or term-vectors meta file (.tvm), has a damaged byte in one of the pointers that say where the index data sits in the .fdx (.tvx) file, as a disk or copy error can leave it. You expect what Lucene does for other damaged files: the open fails with CorruptIndexException and every file it opened is closed again. The CorruptIndexException does come, but the .fdx (.tvx) file stays open, because FieldsIndexReader's constructor closes the file it opened only when the header or checksum check fails, not when the slice and DirectMonotonicReader setup right after it throws, and the enclosing reader never received the object, so it cannot close it either.
