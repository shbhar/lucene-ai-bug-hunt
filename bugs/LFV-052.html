FSTMetadata.save always writes the current version, so re-saving a pre-9.0 BYTE2 FST breaks its lookups

Saving an FST always stamps it with the current format version, even when it was loaded from an older file. For a char-keyed (BYTE2) FST from Lucene 8.x, every label then reads back byte-swapped: the re-saved repro copy finds 0 of 9 keys, with no error, since 9.0.0.

The bug in 30 seconds

#

Only the re-saved copy is wrong. The original file, freshly built FSTs, and BYTE1 or BYTE4 FSTs keep every key; BYTE1 and BYTE4 copies are only labelled 9.

  1. Take a char-keyed (INPUT_TYPE.BYTE2) FST that Lucene 8.11.4 saved: 9 keys such as ab → 1, cat → 5 and 日本 → 8 (FST format 7).
  2. Load it on main (or any release since 9.0.0): getVersion() is 7 and all 9 keys are found. Save it with fst.save(...) and load the copy. You expect the same 9 keys.
  3. You get 0 of 9 keys and no exception. The copy is the original byte for byte except one: the header version, 7 → 9.
  4. Why: 8.x stored 2-byte labels in the old byte order, and the reader swaps them back only when the header says a version below 8. save copies the bytes but always writes the current version (9; 8 in 9.0-9.8), so a (0x0061) is read as 0x6100 愀: get("ab") is null, get("愀戀") is 1.
  5. Same line, smaller symptom: an FST built with setVersion(FST.VERSION_90) is saved as version 9, not 8. Lucene 8.11.4 re-saves the old file correctly (header 7, 9 of 9 keys).

Who is affected

#

Applications that keep char-keyed (BYTE2) FSTs in files written by Lucene 7.0.0 to 8.11.4 and save them again on 9.0 or later (copy, migrate, cache). The copy silently answers wrongly (0 of 9 keys in the repro). No setting is involved, but no Lucene code path does this: suggesters use BYTE1, and the bundled dictionaries are regenerated from source.

Mechanism, terms and numbers713 words

FST.FSTMetadata#save writes the constant VERSION_CURRENT (9) into the FST header, whatever version the FST it saves is in, while FST#save copies the FST bytes of an on-heap FST (what FST.read and the FST(FSTMetadata, DataInput) constructor create) unchanged. Lucene 9.0+ still reads FST formats 6 and 7 (written by Lucene 7.0.0-8.3.1 and 8.4.0-8.11.4; older formats are rejected when loaded), and for BYTE2 labels the decoding depends on the header version: before format 8 the two label bytes are in the old order, and readLabel swaps them back only if the header says less than 8. So a char-keyed FST written by Lucene 8.11.4, loaded and saved again on 9.0 or later, comes back with header 9 (8 on 9.0-9.8) over format-7 bytes: every label is read byte-swapped and the lookups go wrong, with no error (in the repro 9 of 9 keys before, 0 of 9 after). The copy differs from the original only in the version byte. Every release from 9.0.0 to 10.5.2 and main have it; 8.11.4 re-saves the same file correctly. The same line also labels an FST built with setVersion(FST.VERSION_90) as version 9 instead of 8.

Terms

#
  • FST: Lucene's compact map from a sequence of labels to an output (terms index, suggesters, dictionaries). It can be written to a file with FST#save and read back with FST.readMetadata plus the FST constructor, or FST.read(Path).
  • BYTE2: the input type whose labels are 2-byte values, used for char-keyed FSTs built over UTF-16 code units (Util.toUTF16). BYTE1 labels are single bytes, BYTE4 labels are vInts.
  • Header version: the FST format version in the file header (CodecUtil header, a big-endian int at bytes 8-11). Lucene 7.x and 8.0-8.3 wrote 6, 8.4-8.11 wrote 7, 9.0-9.8 wrote 8, 9.9 and later write 9.

The bug (FST.java at ea57360912ed)

#
  1. Lucene 8.x wrote BYTE2 labels with the big-endian writeShort. LUCENE-9047 made DataOutput little-endian in 9.0 (MIGRATE.md:1179-1183), and FSTCompiler.writeLabel writes BYTE2 labels with out.writeShort since (FSTCompiler.java:585-587).
  2. readMetadata accepts formats 6 to 9 (:457-459) and keeps the file's version (:493). readLabel swaps BYTE2 labels when that version is below 8: if (metadata.version < VERSION_LITTLE_ENDIAN) v = Short.reverseBytes(in.readShort()) & 0xFFFF; (:553-554). It is the only version-dependent read.
  3. FST#save writes the metadata, then the FST bytes (:524-527): for an on-heap FST, which FST.read and the FST(FSTMetadata, DataInput) constructor create (:419-420, :538-543), the loaded bytes unchanged (OnHeapFSTStore.java:84-90; an off-heap FST cannot be saved, OffHeapFSTStore.java:64-66). FSTMetadata#save writes CodecUtil.writeHeader(metaOut, FILE_FORMAT_NAME, VERSION_CURRENT) (:1214), ignoring its own version field.
  4. Reloading the copy, the header says 9, readLabel no longer swaps, and every BYTE2 label is read with its bytes reversed. Util.get returns null for all 9 keys of the repro; nothing throws.

The numbers

#

The 8.11.4 fixture (16 metadata bytes, 64 FST bytes, 9 keys): the original finds 9 of 9 keys with getVersion() = 7. After save the metadata differs in one byte (offset 11, 07 → 09) and the FST bytes are identical; the copy finds 0 of 9 keys with getVersion() = 9, get("ab") = null and get("愀戀") = 1, the byte-swapped key. Its enumeration lists 愀戀 → 1 ... 挀愀琀 → 5. With BYTE1 or BYTE4 labels the same steps keep every key. The 0 of 9 (and 0 of 45 in the history probe) holds for these fixtures, not for every key of every BYTE2 FST: a key made only of UTF-16 units whose two bytes are equal survives (an executed check: an 8.11.4 FST {a → 1, U+6161 → 2} re-saved on main gives get("a") = null and get("慡") = 2), the empty input keeps its output (stored in the metadata, its lookup reads no label: FST.java:593-596, Util.java:47-65), and byte-swapped keys can resolve instead.

The second symptom

#

FSTCompiler.Builder#setVersion (FSTCompiler.java:335-348) accepts VERSION_90 (8) to VERSION_CURRENT; the compiler honours it (no continuous-arc nodes below 9, :543) and the in-memory version is 8, but save writes 9. After readMetadata, getVersion() returns 9, and a Lucene 9.8 reader rejects the file with IndexFormatTooNewException, although its content is format 8: with only the header int patched to 8, 9.8.0 reads a 50,000-term FST with 0 wrong lookups.

Exposure and likelihood354 words
  • Who is exposed. Applications that persist standalone FSTs (FST.save(Path) / FST.read(Path), or save(DataOutput, DataOutput)) with BYTE2 labels, in format 6 or 7 (written by Lucene 7.0.0 to 8.11.4), and that load such a file on 9.0 or later and save it again: a copy to another place, a migration to a new store, a cache that writes the loaded FST back. The original file keeps working; the copy is silently wrong on every 9.0+ reader, and 8.x readers reject header 8 or 9.
  • No in-tree path. The suggesters that store and load FSTs (AnalyzingSuggester, FSTCompletionLookup, WFSTCompletionLookup, FreeTextSuggester, NRTSuggesterBuilder) build them with BYTE1, so a re-stored old suggester is only mislabelled. The in-tree BYTE2 FSTs (Kuromoji and Nori dictionaries and user dictionaries, NormalizeCharMap, Hunspell ConvTable) are built fresh: the bundled dictionary FSTs are regenerated from source (#12911, #12924), the user dictionaries from the user's text.
  • Default, but rare. No setting is needed; the trigger is the data plus the re-save. How many applications keep pre-9.0 BYTE2 FST files and re-save them is unknown; no downstream report was found. FST and FSTCompiler are @lucene.experimental.
  • Scale. Every key of the test fixtures is lost: 0 of 9 in the repro, 0 of 45 in the history probe on every release from 9.0.0 to 10.5.2 and main, for files written by 7.7.3 (format 6) and 8.11.4 (format 7). Not a rule for every BYTE2 FST: keys made only of UTF-16 units with two equal bytes (such as U+6161, executed) and the empty input can survive, and byte-swapped keys can resolve instead (get("愀戀") = 1 in the repro).
  • Recoverable. The copy differs from the original only in the version byte, so restoring it gives back the original file.
  • Second symptom. Needs the expert setVersion(VERSION_90); the only in-tree caller is the backward-codecs test writer Lucene90BlockTreeTermsWriter. Apart from the wrong reported version (getVersion() = 9 after readMetadata, on current readers too), its only demonstrated compatibility failure is rejection by readers capped at version 8 (9.0 to 9.8), which Lucene does not promise to support.

Why it is a bug, not intended

#
  • Main deliberately reads format 6 and 7 FSTs and decodes their BYTE2 labels correctly (FST.java:553).
  • getVersion() is "the version constant of the binary format this FST was written in"; save copies those bytes but writes 9.
  • The version exists so readers fail with "an understandable error" (#12748). Lucene 8.11.4 re-saves the file correctly.
The full argument393 words
  • Reading old FSTs is offered on purpose. VERSION_START = 6 is "the version that was used when releasing Lucene 7.0" (FST.java:113-114); readMetadata accepts 6 to 9 ("we don't have back-compat promise for FSTs (they are experimental), but we are sometimes able to offer it", :457-459), and readLabel has a branch written for exactly these old BYTE2 files (:553). Main decodes the 8.11.4 file correctly: 9 of 9 keys.
  • The documented meaning of the version. FSTMetadata#getVersion: "Returns the version constant of the binary format this FST was written in" (:1191-1195). save + readMetadata turns 7 into 9 (and 8 into 9) while the bytes stay as they were. Kuromoji's and Nori's TestTokenInfoDictionary.testBinaryFSTIsLatestFormat (#12911) read the bundled FST's header with FST.readMetadata(...).getVersion() to check that its format is current: Lucene's own tests use the header version to tell what format the bytes are in.
  • save has no precondition. "Save the FST to DataOutput" (:518-523) and "Writes an automaton to a file" (:529); the FSTCompiler javadoc lists "save it to other DataOutput, and load it later and use it" as a use (FSTCompiler.java:61-62). TestFSTs.testSaveDifferentMetaOut (:1204-1243) asserts that load, save and reload keep the lookups, for a current-format FST. No test re-saves an older-format FST or checks the header that save writes for one.
  • Design intent. mikemccand on the version bump in #12748 (2023-11-06): if the version is bumped, an older reader "would throw an understandable error". Here a newer reader silently misreads, because the header claims a newer format than the bytes.
  • History. The constant header dates from 2010 and was harmless until LUCENE-9047 (b84e0c272b6, 9.0.0) made BYTE2 decoding depend on the version; that commit did not touch the save line, and its PR lists "adds backwards compatibility for FST" for reading. #12908 (9.9.1) added setVersion for a test writer of "data in the 9.8 format" without threading it into the header.
  • Precedent. LUCENE-8844 (#9888, 2019) treated an encoding change without a header bump, which made older readers "exhibit strange behavior", as a bug. When a break was intended, the project said so (LUCENE-3681, 2012: users "will have to rebuild"); no CHANGES, MIGRATE or javadoc entry says that re-saving a loaded older FST is unsupported. Lucene 8.11.4 itself re-saves the file with header 7 and 9 of 9 keys.
The devil's-advocate check254 words

The strongest case (a cross-model review rated it "moderate"): FST is @lucene.experimental, readMetadata disclaims a back-compat promise, setVersion is "Expert", and LUCENE-3681 once told users to rebuild old FSTs. LUCENE-9011 (#10054, 2019) closed a report of a standalone FST file that no longer loaded (IndexFormatTooOldException): jpountz answered that it "has been created by Lucene 6 or earlier". rmuir wrote on java-user@ in 2013 that "mainly FST (unfortunately) has backwards compatibility because parts of the official index format use it", that is, old formats stay readable for index files, which read their FSTs in place. So old standalone FST files are best effort, and an application should rebuild an old FST rather than copy it. Apart from the wrong reported version, the VERSION_90 header only causes a failure on readers capped at 8, which Lucene does not support.

Why it fails for the main symptom: Lucene offers this compatibility deliberately, with a read branch for exactly these files, and reads them correctly; save then turns a correctly loaded FST into a file that answers wrongly (all 9 keys of the repro "not found"), by writing a header that misdescribes bytes it copies unchanged. Best effort can justify a loud IndexFormatTooOldException, which is what LUCENE-9011 got, not silent wrong answers from a public call with no documented precondition. The index-format reason explains why old formats are read at all, not why save should mislabel them. For the second symptom the case is fair: present it as a mislabel with the same fix.

#

Recommended Write the FST's own version in the header (recommended)

Default-built FSTs are unchanged, and a loaded old FST is re-saved byte-identical. Trade-offs

  • A re-saved old FST stays in its old format; it is not upgraded. If a later release raises VERSION_START, such files fail loudly with IndexFormatTooOldException.
  • FSTMetadata has a public constructor that takes any int version, which now goes into the header as is; an out-of-range value gives a file that readMetadata rejects. A range check in the constructor or in save would catch it early (not tested).
  • The backward-codecs test data in the 9.0-9.8 format now carries FST header 8 instead of 9; its tests pass either way.

Upgrade an old BYTE2 FST to the current format when saving

#

When version < VERSION_LITTLE_ENDIAN and the input type is BYTE2, write a current-format FST instead of copying, for example by rebuilding it from its own enumeration (IntsRefFSTEnum into a new FSTCompiler). Not tested.

Trade-offs

save stops being a byte copy and costs time and memory proportional to the FST. Swapping the labels in place is not practical, because labels sit at variable offsets inside node encodings. Only worth it if save should migrate old FSTs.

Refuse to save an old BYTE2 FST

#

Throw from save when version < VERSION_LITTLE_ENDIAN and the input type is BYTE2, asking the caller to rebuild the FST. Not tested.

Trade-offs

Loud instead of silent, but it breaks copies that work with the recommended fix and leaves the second symptom. A broader "only VERSION_CURRENT" rule would break the backward-codecs writer that saves VERSION_90 FSTs.

Document it (not a fix)

#

Say on FST#save that it always writes the current version and that FSTs loaded from older formats must be rebuilt, not re-saved.

Trade-offs

Leaves the silent failure in place; listed for completeness.

History

#

Introduced in 9.0.0 by LUCENE-9047 (b84e0c272b6, 2021-05-03), which made BYTE2 decoding depend on the header version while save kept writing the constant; pinned by a commit-level A/B. All 33 releases from 9.0.0 to 10.5.2 and main are affected, 8.x is not. Not fixed upstream.

Versions tested6 rows

Introduced by LUCENE-9047 "Directory API is now little endian" (b84e0c272b6, PR #107, by @iverase, merged 2021-05-03, first released in 9.0.0). It added VERSION_LITTLE_ENDIAN = 8, kept the header's version in the FST, and added the BYTE2 byte swap in readLabel; it did not touch the save line, which has written the constant VERSION_CURRENT since the first FST (994aaec2ef5, LUCENE-2792, 2010) and was only moved later (87a3bef50f8, LUCENE-9353; #13549). The second symptom came with #12908 (c0fd4404ea3, @jpountz, 2023-12-11), first released in 9.9.1.

An earlier episode with the same cause: in 4.2.0 to 7.7.3, LUCENE-4677 read format-3 arc targets by version while save wrote the current version, so re-saved format-3 files lost all 45 probe keys; 8.0.0 dropped format 3 (ca22f17662c). Those lines are long out of support.

Bug record

LFV-052, snapshot of 2026-10-28

Registry title
FSTMetadata.save always writes the current version, so re-saving a pre-9.0 BYTE2 FST breaks its lookups
Area
util / FST
Priority
Low, rank 697: Kept in Low but raised: re-saving a pre-9.0 BYTE2 FST writes the current version and deterministically breaks its lookups, a legitimate if old migration step rather than a contrived input, but it needs an app-persisted 8.x char-label FST and shows up immediately.
Impact class
silent wrong results
Impact note
Applications that load a persisted pre-9.0 BYTE2 FST (e.g. a char-keyed dictionary) and save it again on 9.0+, or that use the expert setVersion(VERSION_90); released since 9.0.
Summary
You load an FST that was written before 9.0 with BYTE2 labels and save it again with Lucene 9.0 or later. You expect the re-saved FST to work like the original. Instead save() writes the header version VERSION_CURRENT, so readers decode the labels with the wrong byte order and the lookups fail (0 of 9 keys found in the repro); FSTs built with setVersion(VERSION_90) are also labelled 9 and rejected by 9.8.
Introduced
LUCENE-9047 (b84e0c272b6, PR #107) [exec: commit vs parent] (2021-05-03)
