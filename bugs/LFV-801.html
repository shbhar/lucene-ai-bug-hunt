KNearestFuzzyClassifier reads a documented field boost such as title^10 as part of the field name, so that field is ignored

KNearestFuzzyClassifier documents field names with a boost such as title^10, but looks the whole string up as a field name, so that field adds nothing: alone it gives no class (null); next to other fields it is silently ignored (fruit becomes vehicle). Affects 7.0.0 through 10.5.2 and main.

The bug in 30 seconds

#

The constructor javadoc says the text field names "can contain boosting indication e.g. title^10". The class never strips the ^10: it searches a field named title^10, which does not exist.

  1. Index four documents in one field text: fruit "apple banana cherry" and "apple pear", vehicle "car truck bus" and "bus train". Build a KNearestFuzzyClassifier (k = 3) with the field written text^2, as the javadoc's title^10 example allows, and classify "apple banana".
  2. You expect fruit, the answer for plain text (score 0.848): with one field, a boost cannot change which documents are nearest.
  3. You get null, and getClasses returns an empty list. The classifier looks for a field literally named text^2; there is none, so its fuzzy query has no terms, and because that query is required, no document matches.
  4. With two fields it is silent. Titles point to fruit, bodies to vehicle. For "apple wheel", {"title", "body"} gives fruit (0.667), but {"title^10", "body"} gives vehicle (0.971), exactly the body-only answer. Even the no-op title^1 gives vehicle.
  5. The sibling KNearestNeighborClassifier, whose javadoc has the same sentence, parses the boost and answers fruit. Parsing field^boost here fixes both cases.

Who is affected

#

Applications that use the experimental KNearestFuzzyClassifier and write a boosted field name, the javadoc's own example. Then every call ignores that field, whatever the index settings: one boosted field returns null; with several, the answer comes from the other fields only, with no error. Plain field names are not affected.

Mechanism, terms and numbers537 words

The KNearestFuzzyClassifier constructor documents that its text field names "can contain boosting indication e.g. title^10" (KNearestFuzzyClassifier.java:83-84). The class never parses that syntax: knnSearch passes every entry unchanged to NearestFuzzyQuery.addTerms(text, fieldName) (:137-140), and NearestFuzzyQuery looks up a field literally named title^10, finds none and adds no terms for it (NearestFuzzyQuery.java:133-136). The fuzzy query is a required clause (:141). With one boosted text field nothing matches, so assignClass returns null and getClasses an empty list on every call; with several fields the boosted one is silently left out and the answer comes from the others: on a six-document index, {"title", "body"} classifies "apple wheel" as fruit (0.667) and {"title^10", "body"} as vehicle (0.971), the body-only answer. The sibling KNearestNeighborClassifier carries the same javadoc sentence and parses it. The gap dates from the class's introduction (LUCENE-7838, first released in 7.0.0), so every release from 7.0.0 to 10.5.2 and main is affected. Passing the parsed boost into the one NearestFuzzyQuery the class already builds fixes it; the whole lucene/classification test suite passes with that change.

Terms

#
  • KNearestFuzzyClassifier: a k-nearest-neighbour text classifier in the opt-in lucene-classification module (@lucene.experimental). It turns the input text into a NearestFuzzyQuery over the configured text fields, takes the top k documents that have a class, and votes.
  • NearestFuzzyQuery: a trimmed copy of the sandbox FuzzyLikeThisQuery. For every field it was given, it analyses the text, collects fuzzy variants of each term (one edit; at most 50 per term and field), keeps the best 300 terms over all fields and rewrites to a BooleanQuery of SHOULD term clauses.
  • field^boost: the syntax the constructor javadoc documents for weighting a field, as in title^10. The sibling KNearestNeighborClassifier and both document classifiers parse it.

The bug

#
  1. The constructor stores the caller's textFieldNames unchanged (KNearestFuzzyClassifier.java:94); nothing parses or validates it.
  2. knnSearch calls nearestFuzzyQuery.addTerms(text, fieldName) with each entry as given (:137-140).
  3. NearestFuzzyQuery asks the index for the terms of the field title^10, gets null and returns: that field adds no terms (NearestFuzzyQuery.java:133-136). An index with a field literally named title^5 is read from that field, which shows the entry is used verbatim.
  4. The fuzzy query is added as MUST (KNearestFuzzyClassifier.java:141). With one text field it has no clauses and matches nothing: assignClass returns null (:104-117), getClasses an empty list. With several fields the other fields still match, so the top k come from them alone.

Nothing else is needed: the lookup of the literal name does not depend on the index settings, the codec, the similarity or the index size; the outcomes shown here were run only on the small indexes of this doc.

  • One boosted field is loud: null on every call, so a user would probably notice and drop the boost.

  • Reach. No downstream user is known: a GitHub-wide issue and PR search for the class name found no user report, and the searches found no public report of the bug since 7.0.0 (2017).
  • Not a resource problem. The faulty path does less work than the correct one.
  • Not counted here: getClasses(text, max) on the empty list throws IndexOutOfBoundsException (KNearestFuzzyClassifier.java:132), the known LUCENE-8110 / #9158.

Why it is a bug, not intended

#
  • The constructor javadoc promises the syntax: the text field names "can contain boosting indication e.g. title^10".
  • The module writes "NO boosting supported per field" where boosts are unsupported; the three other classifiers with this sentence parse it.
  • Following the documented example gives null or another class, silently: the contract and the code disagree, so one of them must change.
The full argument183 words
  • Contract. KNearestFuzzyClassifier.java:83-84: "@param textFieldNames the name of the fields used as the inputs for the classifier, they can contain boosting indication e.g. title^10". It is the only documentation of the parameter; no test, CHANGES entry or MIGRATE note says the syntax is unsupported here, and the searches found no issue or list thread that does.
  • Module convention. BM25NBClassifier.java:76-77 and SimpleNaiveBayesClassifier.java:84-85 say "NO boosting supported per field". KNearestNeighborClassifier (:161-168), KNearestNeighborDocumentClassifier (:128-129) and SimpleNaiveBayesDocumentClassifier (:157-158) carry the boost sentence and parse it; the last one writes the stripped name back into the caller's array (:170), so only its first call is boosted (a separate bug, LFV-382).
  • Tests. The upstream tests build this class with plain field names only, so nothing caught it; the document classifiers' tests use title^100.
  • Precedent. LUCENE-7991 (7.2.0) fixed a field-boost bug in KNearestNeighborDocumentClassifier as a bug.
  • History. The sentence and its parsing came to KNearestNeighborClassifier together (LUCENE-6654, 2015). LUCENE-7838 (2017) added this class with the same javadoc block but passed the raw names to the query; it never parsed ^.
The devil's-advocate check191 words

The strongest case for "not a bug" (the intended-behaviour checker and the cross-model reviews): the whole constructor javadoc was copied from KNearestNeighborClassifier when the class was created (the neighbouring "@param k ... in the MLT results" names MoreLikeThis, which this class never used), so the boost sentence may be a copy too; the class is @lucene.experimental; and ^ is legal in a field name, so a field literally named text^2 works today.

Why it fails: the copy explains where the sentence came from, not that the behaviour is wanted; the published contract says the syntax works, and the module labels the classes without boost support. @lucene.experimental allows API changes, not a documented input that silently returns no class. The javadoc reserves ^ for boosts, as the siblings do. Whether the code or the sentence is the wrong half is for the maintainers to decide; either way the two disagree. Verdict: a defect, at the least a contract mismatch; the copy-paste origin, the experimental status and the absence of any public report since 2017 make the javadoc-only fix a reasonable maintainer choice, so offer it next to the code fix.

Suggested fix

#

Recommended Pass the boost into the one shared NearestFuzzyQuery (recommended)

Parse field^boost in knnSearch and pass the boost into the one NearestFuzzyQuery the class already builds, through a new addTerms(text, field, boost) that scales that field's term scores. Unboosted configurations rewrite to the same query as today. The new test, the whole classification test suite and the module's checks pass.

// KNearestFuzzyClassifier.knnSearch
for (String fieldName : textFieldNames) {
  int caret = fieldName.indexOf('^');
  if (caret >= 0) { // "field^boost", e.g. title^10
    float boost = Float.parseFloat(fieldName.substring(caret + 1));
    nearestFuzzyQuery.addTerms(text, fieldName.substring(0, caret), boost);
  } else {
    nearestFuzzyQuery.addTerms(text, fieldName);
  }
}
// NearestFuzzyQuery: new addTerms(String, String, float); FieldVals keeps the boost
st.score = (st.score * st.score) * idf(df, corpusNumDocs) * f.boost;
All options and trade-offs3 options · 783 words

Two code fixes were built and validated; they give the same classes and scores on every probed configuration and, by the code (not run), can differ only when an input yields more than 300 candidate terms. A javadoc-only fix is the third option.

Pass the boost into the one shared NearestFuzzyQuery (recommended) (validated by the checks) (recommended)

#

+29/-4 in KNearestFuzzyClassifier.java and utils/NearestFuzzyQuery.java. knnSearch splits field^boost and calls a new public overload NearestFuzzyQuery.addTerms(String, String, float boost); the old two-argument method delegates with 1f. The new method rejects a negative or non-finite boost; FieldVals keeps the boost (also in equals/hashCode), and each term's score is multiplied by it.

// KNearestFuzzyClassifier.knnSearch
for (String fieldName : textFieldNames) {
  int caret = fieldName.indexOf('^');
  if (caret >= 0) { // "field^boost", e.g. title^10
    float boost = Float.parseFloat(fieldName.substring(caret + 1));
    nearestFuzzyQuery.addTerms(text, fieldName.substring(0, caret), boost);
  } else {
    nearestFuzzyQuery.addTerms(text, fieldName);
  }
}
// NearestFuzzyQuery: new addTerms(String, String, float); FieldVals keeps the boost
st.score = (st.score * st.score) * idf(df, corpusNumDocs) * f.boost;

Trade-offs

  • One query and one shared 300-term budget, as today; the boost scales the field's term weights, like mlt.setBoostFactor in the sibling. Without ^ the only scoring change is a multiplication by 1f, which is exact, so the rewritten query is unchanged (FieldVals also carries the boost, in equals and hashCode, so its hash values change); title^1 equals title.
  • The scaled score is also used for the 300-term cut, so a boosted field wins more of the budget when an input has more candidate terms than that. The earlier cap of 50 variants per term and field is applied before the boost, as today. Neither cap was reached in any run (the probe indexes have at most 8 distinct terms per field), neither was tested with a fix, and the new overload has no direct unit test.
  • Adds one public overload to NearestFuzzyQuery (an exported package of the module).
  • It parses on every call, like KNearestNeighborClassifier (SimpleNaiveBayesDocumentClassifier parses on its first call only), and a field literally named title^5 can no longer be addressed (the mechanism probe now gets fruit instead of tool). A malformed boost (title^x, title^) throws NumberFormatException on every call; parsing once in the constructor would fail fast instead (not run).
  • The accepted grammar is that of Float.parseFloat: title^1e1 is accepted, title^2^3 throws (the sibling reads it as boost 2), and a literal ^ cannot be escaped. The new overload rejects negative (also -0.0) and non-finite boosts but accepts 0, while its message says "positive": reword the message, or reject 0, in the PR. None of these inputs was run.

One boosted NearestFuzzyQuery per field when any entry has a boost (the hunt's sketch) (validated by the checks)

#

+26/-3 in KNearestFuzzyClassifier.java only. Without ^ today's code runs unchanged; otherwise each field gets its own NearestFuzzyQuery, wrapped in a BoostQuery, as a SHOULD clause of a required BooleanQuery. No API change; it mirrors the sibling, which builds one MoreLikeThis query per field.

Trade-offs

Two code paths. With any boost, each field gets its own 300-term budget, so the query can grow to 300 terms per field; and title^1 takes the boosted path, so for long inputs it can differ from title. Raised by the reviewers; not measured.

Delete the javadoc sentence

#

Replace "they can contain boosting indication e.g. title^10" with the module's wording for classes without boost support, "NO boosting supported per field".

Trade-offs

Not run. Removes the broken promise but keeps the silent result for anyone who already writes a boosted name; rejecting entries with ^ would make it loud but would break a field literally named with ^.

How it was found

#

An AI tool building a test baseline for the classification module compared the constructor javadoc's field^boost example with the code and saw that the boost is never parsed. A public-API JUnit test confirmed it on the stock jars; independent AI tools then reproduced, reviewed and judged it.

The method in full127 words

Method: a documented-syntax check (the hunt's "non-formal" tier), 2026-10-26, stock main jars.

  • While a hunt unit built a property-based baseline for the classification module, it checked the constructor javadoc's documented field^boost syntax against knnSearch. Its fuzz harness never passes a boosted field name, so the harness itself could not find it. The lead was left unfiled.
  • On 2026-10-27 a later unit turned the lead into a public-API JUnit test with a differential oracle (the unboosted call and the sibling classifier) and re-ran it on main a9779ef3c193: it failed with assertions on and off and on 10.5.2.
  • Then independent AI tools reproduced, reviewed and judged it (see the checks), and the history step ran one portable probe on eight releases from 7.0.0 to 10.5.2 plus main.

Bug record

LFV-801, snapshot of 2026-10-29

Registry title
KNearestFuzzyClassifier ignores its documented 'field^boost' syntax: an entry such as 'title^10' in textFieldNames is looked up as a literal field name, so that field contributes nothing, and with a single boosted field assignClass returns null
Area
classification / KNearestFuzzyClassifier (textFieldNames 'field^boost' syntax; NearestFuzzyQuery field lookup)
Priority
Medium, rank 211: Following its own javadoc's 'title^10' example makes the experimental KNearestFuzzyClassifier silently drop that field, or return null when it is the only field, which is the same documented-boost failure as LFV-382 but in a less used classifier with an easy-to-notice null case.
Impact class
silent wrong results
Impact note
Hits only applications that use the experimental KNearestFuzzyClassifier and follow its constructor javadoc by passing a boosted field name such as 'title^10'; then on every assignClass/getClasses call, with no error, at any scale and with the default IndexWriterConfig, codec and searcher: a single boosted field gives null (getClasses an empty list), and in a multi-field configuration the boosted field is silently dropped while the other fields still work; every release from 7.0.0 to 10.5.2 and main.
Summary
You build a KNearestFuzzyClassifier with a text field written as 'text^2' or 'title^10', as its constructor javadoc says you may, and expect the same classes as with the plain field name (with that field weighted more). Instead the entry is used verbatim as the name of a field called 'text^2', which does not exist, so that field adds no terms to the query: with one text field assignClass returns null and getClasses an empty list, and with several fields the boosted one is silently ignored. The sibling KNearestNeighborClassifier, whose javadoc has the same sentence, parses the boost and classifies normally.
