FSTCompletion.lookup returns one shared, mutable list for empty results, so adding to it leaks into every other FSTCompletion in the JVM

FSTCompletion.lookup answers every empty key, and every key on an instance with no entries, with the same private static ArrayList. Add one fallback suggestion to that empty result and every other FSTCompletion in the JVM, even one built from a different dictionary, returns it too: [apple/1] instead of [].

The finding in 30 seconds

#

Autocomplete code often adds fallback suggestions when FSTCompletion.lookup finds nothing. Doing that to an empty-key result changes the answer of every other FSTCompletion in the JVM, because all empty answers are one shared, mutable list.

Background: FST autocomplete in Lucene

#
  1. FSTCompletionBuilder collects entries (a term and a weight bucket), and build() compiles them into an FSTCompletion: an automaton for prefix autocomplete in lucene/suggest, marked @lucene.experimental.
  2. FSTCompletion.lookup(prefix, num) returns a List<Completion>; each completion prints as term/bucket, for example apple/1. FSTCompletionLookup, the Lookup implementation built on it, copies those completions into a new list of its own.
  3. An empty prefix has no suggestions, and neither does an instance built with no entries: the upstream test testEmptyInput expects an empty result.

The finding, step by step

#
  1. Build an FSTCompletion from the single entry apple and call lookup("", 1): you get an empty list. Your code appends a fallback suggestion to it, [apple/1], as autocomplete code often does when nothing matches.
  2. You expect only your own list to change: an independent FSTCompletion, built from zebra or from no entries at all, should still answer an empty key with [].
  3. Instead it answers [apple/1], with no error, with assertions on and off, on main and in every release since 3.6.0. An instance with no entries now returns [apple/1] for any key, and FSTCompletionLookup returns it for empty keys too.
  4. Why: lookup returns the static field EMPTY_RESULT itself whenever the key is empty or the instance has no automaton. It is one mutable ArrayList shared by every instance, so the change stays until some code clears the list or the JVM restarts. Non-empty results have been unmodifiable since 10.0.0.

Who is affected

#

Code that uses FSTCompletion directly and adds to a result that came back empty, such as fallback suggestions. Every other FSTCompletion in the JVM then returns those entries for empty keys, silently, until the list is cleared or the JVM restarts. Lucene's own code never modifies a result; FSTCompletionLookup cannot cause it but returns the added entries.

Mechanism, terms and numbers562 words

FSTCompletion (module lucene/suggest, @lucene.experimental) is the FST autocomplete engine behind FSTCompletionLookup. Its lookup(key, num) returns one private static final ArrayList field, EMPTY_RESULT, whenever the key is empty or the instance was built with no entries (its automaton is then null). That list is the same object for every call on every instance (a static field exists once per loaded class, so in a typical application once per JVM), and it is mutable. So when a caller adds to the list it got for an empty key, for example a fallback suggestion, every other FSTCompletion, even one built from a different dictionary, returns that entry for empty keys from then on, with no error, until some code clears the list or the JVM restarts; an instance with no entries returns it for every key, and FSTCompletionLookup, which copies results, returns the polluted entries for empty keys too. Lucene's own code does not modify a result, so it takes application code that writes into a returned list. It has been there since FSTCompletion was created (SOLR-2888, first released in 3.6.0); since 10.0.0 every non-empty result is unmodifiable, so the empty one is the only list that silently accepts the change. The fix is one line: return List.of();.

The mechanism (main e1faeba08bde, lucene/suggest/.../fst/)

#
  1. One static list. FSTCompletion.java:77-81: private static final ArrayList<Completion> EMPTY_RESULT = new ArrayList<>();, with the comment "An empty result. Keep this an ArrayList to keep all the returned lists of single type (monomorphic calls)."
  2. Returned as the result. lookup(CharSequence key, int num) (:197-210) starts with if (key.isEmpty() || automaton == null) { return EMPTY_RESULT; } (:198-200): the object itself, not a copy. The early return also skips num, so after several appends every empty lookup returns all of them (by reading, not executed).
  3. No entries means a null automaton. FSTCompletionBuilder.build() (FSTCompletionBuilder.java:190-197) calls buildAutomaton, which returns null when no entry was added (:223), and the FSTCompletion constructor accepts it (FSTCompletion.java:113-122). Such an instance returns EMPTY_RESULT for every key.
  4. Non-empty results are different. :206 and :208 return lookup(key)...limit(num).toList(), an unmodifiable list, a new one for each non-empty result (java.util.ImmutableCollections$ListN on JDK 25, executed). An unmatched non-empty prefix such as "q" takes this path too and gets an unmodifiable empty list (executed; on JDK 25 that is the JDK's own shared immutable empty list, which nobody can change). Among the paths inspected, only the early return hands out a list a caller can change.
  5. The Lookup wrapper copies, then shows the pollution. FSTCompletionLookup.lookup (FSTCompletionLookup.java:262-281) calls completion.lookup(key, num) and copies each completion into a new ArrayList<LookupResult>, so Lookup users cannot cause the pollution, but after someone else did, their empty-key lookups return the added entries.
  6. Who else uses it. In lucene/*/src/java only FSTCompletionBuilder and FSTCompletionLookup reference FSTCompletion; neither modifies a result.

What one caller's change does (executed, main jars, assertions on)

#

Three instances, apple (from "apple"), zebra (from "zebra") and none (no entries), and zebraLookup = new FSTCompletionLookup(null, null, zebra, true). One caller runs apple.lookup("", 5).addAll(apple.lookup("a", 1)):

callbeforeafter
zebra.lookup("", 5)[][apple/1]
zebraLookup.lookup("", false, 5)[][apple/1]
none.lookup("z", 5)[][apple/1]
zebra.lookup("z", 5)[zebra/1] (unaffected)

zebra.lookup("", 5) is the very list the caller changed (== is true). The zebra dictionary never contained "apple".

Exposure and likelihood276 words
  • Who is exposed. Direct users of the @lucene.experimental FSTCompletion whose code modifies a list that lookup returned for an empty key, or that an instance with no entries returned for any key. The natural pattern is "if the list is empty, add fallback (default, recent, per-user) suggestions".
  • Version nuance. Since 10.0.0 (#12978) modifying a non-empty result throws UnsupportedOperationException, so only "modify when empty" code is silently hit. On 9.x and older every result was a mutable list the caller could change and only the empty one was shared, so any code that modified results was hit whenever a result was empty.
  • Silent and lasting. No error; the change reaches every instance of the class (a class-wide static: one list per class loader, in a typical application the whole JVM) and stays until some code clears the list or the JVM restarts. If the application keeps appending, the shared list keeps growing (by reading, not executed). FSTCompletion may be used by several threads at once (FSTCompletion.java:380-381), so such appends to an unsynchronized ArrayList can also race with other threads reading it, for example a ConcurrentModificationException (by reading, not executed).
  • Default vs opt-in. Lucene's own code does not modify a result (in lucene/*/src/java only FSTCompletionLookup calls lookup, and it copies); no setting, codec or scale is involved. It needs direct use of an experimental class plus application code that writes into a returned list. The Lookup entry point, FSTCompletionLookup, cannot trigger it, but returns the polluted entries for empty keys (executed).
  • How likely. Rare: the pattern is ordinary Java, but no in-tree caller does it and nobody has reported it since 3.6.0 (2012).

Its verdict does not depend on test order: on an unfixed tree it fails even if an earlier test already changed the shared list, and on a fixed tree nothing is shared. On an unfixed tree it does leave [apple/1] in the shared list, so later tests in the same JVM that look up an empty key (such as TestFSTCompletion.testEmptyInput) could fail too (by reading, not executed); the whole-suite gradle run was on the fixed tree only. To make it clean up after itself on an unfixed tree, clear apple.lookup("", 1) in a finally block that catches UnsupportedOperationException (not run).

Why it looks unintended

#
  • Nothing documents the sharing: lookup promises "the suggestions" for the key, the field is private, and the list accepts addAll silently.
  • Sibling suggesters and the predecessor FSTLookup return an unmodifiable empty list; the shared mutable one came with a 2011 rewrite to keep one result type, which no longer holds since 10.0.0.
  • Upstream's testEmptyInput expects no suggestions there.
The full argument249 words
  • Contract. FSTCompletion.lookup (FSTCompletion.java:189-196): "@return Returns the suggestions, sorted by their approximated weight first (decreasing) and then alphabetically (UTF-8 codepoint order)." Lookup.lookup (Lookup.java:191): "@return a list of possible completions". Nothing says the list is shared, read-only or must not be modified, and CHANGES.txt, MIGRATE.md and the package docs say nothing either. The field is private, so a caller cannot know it got a shared object; java.util.List makes mutators optional, but this list supports them, so the defect is undocumented, surprising aliasing rather than a broken mutability promise.
  • Test. TestFSTCompletion.testEmptyInput (TestFSTCompletion.java:238-241) asserts that an instance with no entries returns no suggestions for an empty key.
  • Siblings. WFSTCompletionLookup (:163, :180) and AnalyzingSuggester (:679) return the unmodifiable Collections.emptyList() for empty lookup results.
  • History. The predecessor FSTLookup, released in 3.3.0-3.6.2, returned an unmodifiable Collections.emptyList() (executed on 3.5.0 and 3.6.0). SOLR-2888 (92de7e88486, 2011) replaced it with the mutable ArrayList "to keep all the returned lists of single type (monomorphic calls)", a choice about the runtime class; none of its 21 JIRA comments, the commit message or the CHANGES entry mentions sharing. Since #12978 (10.0.0) non-empty results are ImmutableCollections$ListN, so the ArrayList is now the odd type out; List.of() has that same class (executed).
  • Upstream precedent. #13055, #13087 and #13092 (2024) made other static final collections immutable. Those sweeps covered Set and Map constants, private ones included, but no List field, so this one was left as it was.
The devil's-advocate check196 words

The strongest "intended / misuse" case (built by the devil's-advocate verifier; every reviewer rated it moderate but insufficient): the shared list was deliberate, a constant nobody was meant to modify; the class is @lucene.experimental, List mutators are optional, and no in-tree code modifies a result; since 10.0.0 non-empty results are unmodifiable, which suggests results are read-only; and maintainers called similar hardening cosmetic (#13092, dweiss: "These are cosmetic changes but they're worth backporting"; #13087, uschindler, on a public static Set constant: changing it "would be a downstream bug").

Why it fails: nothing documents a read-only rule, and unlike #13087's public constants this list is private and reaches the caller as its own result. From 3.6.0 to 9.12.3 every non-empty result was a fresh mutable list the caller owned, so modifying results worked; only the empty case aliased global state. #12978, which made non-empty results unmodifiable, had no description, no review comments and no CHANGES entry, so it is no documented contract. The change succeeds silently, crosses instances built from different data, and stays until some code clears the list. Net: not intended; a maintainer may well call the fix hardening, which is why it is Low.

Suggested fix

#

Recommended Return List.of() and drop EMPTY_RESULT (fix A)

Return List.of() instead of the shared field, and delete the field. Empty results become immutable like every non-empty result since 10.0.0, so code that appends to one gets UnsupportedOperationException instead of leaking. The repro, TestFSTCompletion, the whole lucene/suggest suite and :lucene:suggest:check -x test pass.

One fix was built and validated in a scratch worktree of e1faeba08bde; the alternatives are listed with their trade-offs.

Return List.of() and drop EMPTY_RESULT (fix A) (validated by the checks) (recommended)

#

In FSTCompletion.lookup, return List.of() for an empty key or a null automaton and delete the field. The JDK's immutable empty list cannot leak between callers, and it has the same runtime class as the non-empty Stream.toList() results, so the field comment's "single type" aim is met again. On current JDKs List.of() returns one shared immutable empty list, so no allocation is added (an implementation detail, not an API guarantee). java.util.ArrayList stays imported for cacheRootArcs.

Downstream note

#

An application that appends its own (for example per-user) suggestions to an empty result would see them returned by every other FSTCompletion in the same JVM; returning List.of() removes this.

Impact note
Hits only code that uses the @lucene.experimental FSTCompletion class directly and modifies a list that lookup returned for an empty key (or that an instance built with no entries returned for any key), for example by appending fallback suggestions: from then on every FSTCompletion in the JVM, including FSTCompletionLookup's empty-key lookups (which copy the list), silently returns the added entries until some code clears the list or the JVM restarts; no in-tree code modifies a result, no scale or non-default setting is needed, and every release from 3.6.0 through 10.6.0 and main is affected.
Summary
You build two FSTCompletion instances from different inputs ('apple' and 'zebra'), call lookup("", 5) on the first and add a fallback suggestion to the empty list it returns, and expect the second instance's lookup("", 5) to still return no suggestions. Instead it returns [apple/1], with no error: lookup hands out the same private static mutable ArrayList (EMPTY_RESULT) for every empty key and for every instance with no entries, so the change shows up in every FSTCompletion in the JVM. Since 10.0.0 non-empty results are unmodifiable, so only the empty result accepts the change silently.
