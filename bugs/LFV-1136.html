LatLon distance sort used as a tie-breaker drops closer tied hits after 1024 queue updates

When LatLonDocValuesField.newDistanceSort only breaks ties of an earlier sort key, a search with more than 1024 queue updates can silently drop a closer tied hit: in the repro the top hit is doc 1024 (2,002 km away) instead of doc 1025 (1,501 km). Every release since 6.1.0 has it.

The finding in 30 seconds

#

The comparator rebuilds its box on each of the first 1024 bottom updates, then only on every 64th. An old box is fine while the bottom distance shrinks. It is too small once the bottom moves farther away, which can only happen when distance is not the first sort key.

Background: how a sorted top-N search uses the bottom

#
  1. A sorted search keeps the N best hits in a queue. The worst of them is the bottom. A new hit gets in only if it sorts before the bottom; then the bottom is updated (setBottom).
  2. With several sort keys, the second key is compared only when the first key ties, the third only when both tie, and so on.
  3. newDistanceSort sorts by distance from a point. To avoid computing a distance for every hit, it keeps a latitude/longitude box around the bottom's distance and rejects hits outside the box at once.

The finding, step by step

#
  1. Sort 1026 documents by cat, then by distance from (0, 0), top 1: new Sort(new SortField("cat", SortField.Type.INT), LatLonDocValuesField.newDistanceSort("loc", 0, 0)). Docs 0-1023 each have a smaller cat than the one before and lie 1.1 km away; docs 1024 and 1025 share cat 1000 and lie 2,002 km and 1,501 km away.
  2. You expect doc 1025: distance breaks the tie on cat, and 1,501 km is closer than 2,002 km.
  3. You get doc 1024, with no error, with assertions on and off.
  4. Why: the comparator rejects any hit outside a box around the queue's worst distance, and after 1024 queue updates it rebuilds that box only every 64th time. Doc 1024 moves the worst distance to 2,002 km, the box stays at 1.1 km, and doc 1025 is rejected without its distance being computed.
  5. Keeping an old box is safe when distance is the first key, because the worst distance then only shrinks. As a tie-breaker it can grow: sorting newest first, then nearest, over 3,600-6,000 documents gave a wrong top 10 in about half of random trials.

Who is affected

#

Anyone who sorts by another field first and by newDistanceSort after it, for example newest first, then nearest, with default settings. It needs more than 1024 queue updates in one collector (by default, one per search) and ties on the earlier keys. In a newest-then-nearest probe over 3,600-6,000 documents, about half the random trials gave a wrong top 10.

Mechanism, terms and numbers632 words

LatLonDocValuesField.newDistanceSort speeds up distance sorting with a bounding box around the distance of the queue's worst hit (the bottom): compareBottom rejects any point outside the box without computing its distance. setBottom rebuilds the box on each of the first 1024 bottom updates, then only on every 64th. That is safe while the bottom distance only shrinks, which holds when distance is the first sort key. When distance only breaks ties of an earlier key, a hit that wins on that key can move the bottom farther away; the old, smaller box then rejects a tied hit that is closer than the new bottom, and the top N (or a searchAfter page) is silently wrong. One test with 1026 documents and default settings shows it on main; a main() form of an earlier version of this test gives the same wrong top hit on 13 releases from 6.1.0 to 10.6.0, and every release in between has the same guard line. A one-condition fix (also rebuild when the bottom grows) passes the repro and the existing distance-sort tests.

The mechanism (main 5adff78bb168)

#
  1. Every competitive hit updates the bottom. TopFieldCollector calls setBottom after each hit that enters a full queue (search/TopFieldCollector.java:94-100, and :102-112 when the queue first fills). MultiLeafFieldComparator.setBottom passes the bottom slot to every comparator, the later ones too (search/MultiLeafFieldComparator.java:45-49).
  2. The sampled rebuild (fix site). LatLonPointDistanceComparator.setBottom always sets bottom = values[slot] (:89) but rebuilds the box only if setBottomCounter < 1024 || (setBottomCounter & 0x3F) == 0x3F (:93), "if comparator hits a worst case order (e.g. backwards distance order)" (:90-92). The counter is never reset (:66, :112) and getLeafComparator returns the same object for every segment (:185-194), so the count is per collector, not per segment: one collector for all segments with the default IndexSearcher (search/IndexSearcher.java:226-231), one per slice with an executor (:760-772).
  3. The repro, step by step. Doc 0 fills the empty queue (search/TopFieldCollector.java:102-112) and docs 1..1023 each replace the top-1 hit on cat: updates with counter 0..1023, each rebuilding a box of about 1.1 km radius (0.01 degrees of latitude plus the 7 cm pad of geo/Rectangle.java:150). Doc 1024 wins on cat (1000 < 3977) without a distance check; its update has counter 1024, 1024 & 0x3F is 0, so bottom becomes about 2,002 km while the 1.1 km box stays.
  4. The drop. Doc 1025 ties on cat, so MultiLeafFieldComparator.compareBottom asks the distance comparator (:52-64). Latitude 13.5 is outside the box, so compareBottom returns its initial cmp = -1 without computing the distance (LatLonPointDistanceComparator.java:148-160, :176), and thresholdCheck drops the hit (search/TopFieldCollector.java:79-92). Its distance, about 1,501 km, would have won. searchAfter uses the same check (:186, :228); a two-page check probe returns the farther tied document as page 2 on main and the closer one with fix A.
  5. Why the first key is safe. As the first key, a new bottom only arrives with a closer hit, so an old box is always large enough. A later key has no such guarantee, as LeafFieldComparator states.

Mechanism check (N filler documents; run in the earlier test's layout, re-run by the fact check in the repro's own layout with the same table): wrong exactly when the far document's update skips the rebuild (N = 1024, 1086, 1088, 2048), right when it rebuilds (N = 1000, 1023, 1087, 2047).

Also with a missing location (found by reading, then run by the fact check): after 1024 updates, a bottom hit without a location (sort key +Infinity, :212) is another way the bottom grows; main returns that tied document instead of the closer one, and fix A returns the closer one.

Exposure and likelihood262 words
  • Who. Any search with LatLonDocValuesField.newDistanceSort as the second or later SortField: "newest first, then nearest", "category, then nearest", "rating, then nearest". Public API only; default IndexWriterConfig, codec and searcher.
  • When. More than 1024 bottom updates in one collector, which can happen when the earlier key's best values arrive late in doc-id order (for example newest first over documents indexed in date order). Then the bottom distance must grow on one of the 63 of 64 updates that keep the box, and a document tied on the earlier keys must lie between the stale box and the new bottom distance.
  • How often (a probe, not the repro). Sort(day INT desc, distance), top 10, documents indexed in day order, locations uniform in a 2 by 2 degree area, 20 random trials per size, compared with a brute-force sort: a wrong top 10 in 11/20 trials with 6,000 documents, 11/20 with 5,000 and 10/20 with 3,600; 0/20 with 600 documents (fewer than 1024 updates); 0/20 for the three larger sizes with the fix. With an IntField first key sorted by SortedNumericSortField (desc), where the numeric comparator can skip documents, 6,000 documents still gave 11/20 wrong.
  • Effect. Silent: no exception, totalHits the same as with the fix and the match set unchanged, the same with -ea and -da (a check probe prints both). A closer tied document is replaced by a farther one in the top N or on a searchAfter page.
  • Versions. Every release from 6.1.0 (2016) to 10.6.0 (13 of them run, the rest have the same guard line), and main.

Why it looks unintended

#
  • Sort says a later SortField breaks ties of the earlier ones; newDistanceSort documents ascending distance, with no primary-only note.
  • LeafFieldComparator warns that a non-primary comparator's bottom may not be its weakest value, and compareBottom must match compare(bottom, doc).
  • The guard came in as a speed shortcut (LUCENE-7099, 2016), described upstream as rebuilding the box "less often", never as dropping hits.
The full argument259 words

Contract

#
  • search/LeafFieldComparator.java:28-31: the bottom slot "may not hold the weakest value according to your comparator, in cases where your comparator is not the primary one (ie, is only used to break ties from the comparators before it)". The note dates from LUCENE-1779 (2009), before this comparator existed.
  • search/LeafFieldComparator.java:55-57: compareBottom "should return the same result as FieldComparator#compare(int,int) as if bottom were slot1 and the new document were slot 2".
  • search/Sort.java:59-61: "if it produces a tie, then the second SortField is used to break the tie".
  • document/LatLonDocValuesField.java:143: "This sort orders documents by ascending distance from the location." The class javadoc says "Sorting by distance is efficient" (:40).
  • search/FieldValueHitQueue.java:146-151 builds comparators for later sort fields as usual; document/LatLonPointSortField.java:41-43 neither rejects nor special-cases that position.

Tests

#
  • TestLatLonPointDistanceSort always puts distance first (Sort(distanceSort, id), :241).
  • TestLatLonPointDistanceFeatureQuery sorts by score, then distance (:471), but that score falls with the same distance, so the two keys agree and the bottom distance still only shrinks.

History

#
  • The guard came with the box in e169050dc3f (LUCENE-7099, 2016-03-11); its parent computed exact distances.
  • LUCENE-7103 (#8158) treats the worst case, in which the distance function "could still get called many times", as a speed problem only; on LUCENE-7212 (#8267) the author described the box as rejecting "hits that won't compete anyway", with "a guard in the code to start doing it less often (only every Nth update)".
  • Five days later 6f124e10017 removed the javadoc warning that distance sorting may be expensive, because "this sort makes bounding boxes for you".
The devil's-advocate check173 words

The case. The sampling is a deliberate, ten-year-old speed guard that is sound for the use it was designed and tested for (distance first); the same guard was copied into the XY, Geo3D and nearest-neighbour code; and LeafFieldComparator is @lucene.experimental, so users should put distance first or live with it.

Why it fails. The user touches only public, non-experimental API (Sort, SortField, newDistanceSort). Sort makes tie-breaking keys a normal feature, LeafFieldComparator names the non-primary case, and newDistanceSort documents an ascending distance order; the comparator cannot even tell its position. Upstream called the guard a way to rebuild the box less often, never a licence to drop hits, and copying it only spreads the same unstated assumption. Two separately prompted cross-model reviews (both OpenAI GPT-5.6, the same model) and a devil's-advocate check built this case; all three found the bug real and the case weak. The nearest-neighbour search (NearestNeighbor) has the same guard line but is not a sort comparator; it is not part of this finding.

Suggested fix

#

Recommended A. Rebuild the box whenever the bottom grows (recommended)

Remember the bottom the box was built for, and also rebuild the box whenever the new bottom is larger: one extra condition in setBottom, +8/-2 lines. Distance-first sorts keep the sampling as today. The repro passes, and so do 504 document-package tests and the nightly distance-sort tests.

  // the bottom value the current bounding box(es) were built for (infinite: no box yet)
  double boxBottom = Double.POSITIVE_INFINITY;

    bottom = values[slot];
    // Keeping an old box is only safe if the bottom did not grow, which can happen when this

Trade-offs

  • No change when distance is the first key: the bottom only shrinks, so the new condition is never true.
  • As a later key, the box is rebuilt on every update that grows the bottom: the same per-update cost as the first 1024 updates; if the bottom grows on nearly every update (an adversarial order), that is a rebuild on nearly every update, the cost the sampling avoids today. No benchmark was run.
  • Also covers a +Infinity bottom (the rebuilt box is then the whole world; the fact check's missing-location probe passes with fix A) and any other way the bottom can grow.

What the checks validated

  • Gradle, scratch worktree at 5adff78bb168, JDK 25.0.3, -Ptests.seed=DEADBEEF: the repro fails without the fix and passes with it, asserts on and off.
  • With the fix: org.apache.lucene.document.* plus TestNearest, 504 tests, 26 skipped, 0 failures; TestLatLonPointDistanceSort and TestNearest with -Ptests.nightly=true, 9 tests (testRandomHuge included); checkGoogleJavaFormat passes.
  • The finder's version of the same condition removes every wrong top 10 of the probe (0/20 for 3,600, 5,000 and 6,000 documents). Not run: the full lucene/core suite.

B. Turn the sampling off when the comparator is not primary (not built)

#

LatLonPointSortField.getComparator already receives Pruning.NONE for every later sort field (search/FieldValueHitQueue.java:146-151) but ignores it (document/LatLonPointSortField.java:41-43); it could tell the comparator to rebuild on every update.

Trade-offs

Other callers pass Pruning.NONE too (the grouping collectors, NonPruningSortField) and would lose the sampling where it is safe; it does not cover a bottom that grows for another reason.

C. Remove the sampling (control only)

#

Always rebuild the box. A comparator with only this change passes an independent version of the test, and so does 6.1.0 with the same change.

Trade-offs

Brings back the worst-case cost LUCENE-7099 and LUCENE-7103 guarded against (data in decreasing distance order, a huge top N).

D. Document that distance must be the first sort key (not recommended)

#

No code change.

Trade-offs

Contradicts Sort's tie-break contract and LeafFieldComparator's non-primary note; users cannot see the limit coming.

Downstream note

#

Downstream servers that map a geo-distance sort clause onto newDistanceSort (by reading, not run: Solr's geodist(), the Elasticsearch and OpenSearch _geo_distance sort in metres) return the same wrong pages when that clause is not the first sort key.

How it was found

#

A proof-obligation audit of LatLonPointDistanceComparator against the LeafFieldComparator contract: compareBottom must give the same answer as compare(bottom, doc), also when the comparator only breaks ties. The sampled box rebuild meets that obligation only if the bottom never grows, which a tie-breaker cannot promise; a one-test JUnit on the stock main jars witnessed it.

The method in full196 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The obligation: for every document, compareBottom(doc) equals compare(bottom, doc) (LeafFieldComparator.java:55-57), including for a comparator that is not the primary one (:28-31).
  • Discharging it for LatLonPointDistanceComparator needs "every point outside the current box is farther than the current bottom". A rebuilt box gives that; a kept box gives it only if the bottom did not grow since the box was built. Distance as the first key guarantees that; a later key does not.
  • The finder then built a one-test JUnit (public API; an earlier form of the repro shown here, with NoMergePolicy, the default codec set explicitly and fillers at 0.009 degrees) that fails on main with -ea and -da, checked that it passes with the fix, mapped exactly which filler counts fail (the mechanism check) and measured the newest-then-nearest probe. The repro on this page is a later, minimal form of that test with plain default settings.
  • An independent reproducer, cross-model reviews (OpenAI GPT-5.6), a devil's-advocate check, an adjudication, a history and prior-art follow-up, a credibility audit and a final repro check followed (see the checks).

History

#

Introduced in 6.1.0 by LUCENE-7099 (e169050dc3f, 2016-03-11), which added the box and the sampling guard together. Wrong on all 13 releases run from 6.1.0 to 10.6.0 and on main; not fixed upstream.

Versions tested8 rows

Introduced by e169050dc3f (main) and its branch_6x copy a4722845e30, "LUCENE-7099: speed up embarrasingly slow sandbox/ distance sort" (Robert Muir, 2016-03-11; no PR; JIRA LUCENE-7099 = #8154). git blame gives the guard line and its comment to this commit; its parent b3ee746a8b1 computed exact distances with no box and was never released.

The class moved from lucene-sandbox to lucene-core in 7.5.0 (LUCENE-7314). Later edits (LUCENE-7103, -7104, -7123, -7184, -7240, -7407, -7314 and the 2020 reformat 2d6ad2fee6d) kept the guard. Upstream main 1c2072f02843 (2026-11-02) still has it. None of the 408 open apache/lucene PRs whose file lists were read on 2026-11-02 touched the file, and a re-check found nothing new.

Any search sorted with LatLonDocValuesField.newDistanceSort as a later SortField (for example newest first, then nearest) can return a silently wrong top-N or searchAfter page once the search has made more than 1024 bottom updates (any earlier key whose order runs against index order makes every hit competitive), whenever the bottom distance grows on one of the 63 of 64 updates that keep the old box and a hit tied on the earlier keys lies between the old box radius and the new bottom distance; default IndexWriterConfig, codec and searcher, the same with -ea and -da, 1026 documents suffice, and every release from 6.1.0 through 10.6.0 is affected [exec]; in the finder's likelihood probe (newest first, then nearest, documents indexed in day order, top-10) about half of the random trials with 3,600-6,000 documents gave a wrong top-10, and none with the fix.
Summary
You search with Sort(cat INT, LatLonDocValuesField.newDistanceSort("loc", 0, 0)), so distance only breaks ties of cat, over 1026 documents: docs 0..1023 each have a smaller cat than the one before (so each becomes the new top hit) and lie about 1 km from the origin, and docs 1024 and 1025 share the smallest cat, with doc 1025 (about 1500 km away) closer than doc 1024 (about 2000 km). You expect doc 1025 as the top hit, because Sort says a later SortField breaks ties and the distance sort orders by ascending distance. You get doc 1024, with no error: after 1024 bottom updates the comparator rebuilds its competitive bounding box only on every 64th update, so it keeps the 1 km box built for the old bottom, and compareBottom rejects doc 1025 as outside that box without computing its distance.
