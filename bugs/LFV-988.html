FSTCompiler.compile()'s javadoc reads an FST back with two constructors that Lucene 9.12 removed

The FSTCompiler.compile() javadoc reads an FST back from a file with new FST<>(fstMetadata, dataInput, new OffHeapFSTStore()), but Lucene 9.12.0 removed both constructors. Copied as shown, it does not compile on any release from 9.12.0 to 10.6.0; the working form is FST.fromFSTReader(md, new OffHeapFSTStore(in, offset, md)).

The finding in 30 seconds

#

The stale line sits in a <pre> block of the compile() javadoc. Javadoc never compiles such blocks, so when 9.12 changed the constructors nothing in the build failed, and Lucene's own code already uses the new form.

Background: building and reading back an FST

#
  1. An FST is Lucene's compact map from byte strings to outputs; term dictionaries and suggesters use it. You build one with FSTCompiler: add keys in sorted order, then call compile().
  2. compile() returns only the FST's metadata (null if the FST accepts nothing). The FST bytes went to the compiler's output: an in-memory one by default, or your own file, such as an IndexOutput, set with Builder.dataOutput(...).
  3. To use an FST you wrote to a file, you open the file again and wrap it: on heap with new FST<>(metadata, dataInput), or off heap with FST.fromFSTReader(metadata, new OffHeapFSTStore(indexInput, offset, metadata)).

The finding, step by step

#
  1. You stream a small FST (cat -> 5, dog -> 7) to your own IndexOutput with FSTCompiler.Builder.dataOutput(out), call compile(), and open its javadoc to see how to read the FST back.
  2. The javadoc says to open the matching input, "then pass it to the FST construct" (an unfinished sentence, no full stop), and shows fst = new FST<>(fstMetadata, dataInput, new OffHeapFSTStore());. You expect that to compile.
  3. It does not, on 9.12.0 to 10.6.0 and main: javac reports constructor OffHeapFSTStore in class OffHeapFSTStore cannot be applied to given types;, followed by required: IndexInput,long,FSTMetadata<?> and found: no arguments. The 3-argument FST constructor is gone as well; javac reports only the inner error.
  4. A 2024 change (#13524, in 9.12.0) removed both constructors and moved all of Lucene's callers of those constructors to FST.fromFSTReader(md, new OffHeapFSTStore(in, offset, md)), but not this javadoc. With that form and a null check, the example compiles and reads back 5 and 7.

Who is affected

#

Developers who stream an FST to their own file with the public Builder.dataOutput (custom codecs, suggesters, dictionaries) and start from this javadoc, the only off-heap read-back example in the util/fst docs. They get one compile error on each of the 17 releases from 9.12.0 to 10.6.0 and on main. Opt-in, experimental API; documentation only.

Mechanism, terms and numbers445 words

FSTCompiler.compile() returns only an FST's metadata, and its javadoc explains how to turn that into an FST. For an FST written to an ordinary DataOutput such as an IndexOutput (set through the public FSTCompiler.Builder.dataOutput), it shows fst = new FST<>(fstMetadata, dataInput, new OffHeapFSTStore()); (FSTCompiler.java:993). Since 9.12.0 neither constructor exists: OffHeapFSTStore has only (IndexInput, long, FST.FSTMetadata<?>), and FST has only the public on-heap FST(FSTMetadata, DataInput) and a package-private FST(FSTMetadata, FSTReader).

Copied into code, the example fails with one javac error on every release from 9.12.0 to 10.6.0 and on main; on 9.10.0 and 9.11.1, where it was written, it compiles. #13524 removed both constructors on purpose, moved every caller of those constructors to FST.fromFSTReader(md, new OffHeapFSTStore(in, offset, md)), and left this javadoc as it was. The sentence before the example is also unfinished ("pass it to the FST construct", with no full stop). Documentation only: nothing in Lucene runs differently.

What exists since 9.12.0

#

What javac reports

#

Only the inner error, the missing no-argument OffHeapFSTStore constructor. The missing 3-argument FST constructor is hidden behind it; an independent verifier's ablation (valid OffHeapFSTStore arguments, the documented FST call kept) fails with cannot infer type arguments for FST<> on main, 10.5.2 and 9.12.3.

The form Lucene's own code uses

#

FST.fromFSTReader(md, new OffHeapFSTStore(in, offset, md)), where offset is the file pointer of the first FST byte: inline with in.getFilePointer() in Test2BFSTOffHeap and FSTDictionary; through a local store variable, followed by skipBytes(store.size()) past the FST bytes, in FSTTermsReader and NRTSuggester; with its stored indexStartFP in the backward-codecs lucene90 FieldReader.

#

The class javadoc (lines 64-66) and the Builder.dataOutput javadoc (lines 305-306) say "use the FST constructor to read it", which is still true for the public on-heap constructor.

Why it looks unintended

#
  • The javadoc presents it as the way to do it ("To create the FST, you need to:"), and its first example, two lines above, compiles.
  • It compiled verbatim on 9.10.0 and 9.11.1; #13524 removed both constructors on purpose, updated every code caller, and missed this javadoc.
  • Lucene fixed a non-compiling FST package example as a defect before (LUCENE-6112, 2014).
The full argument170 words
  • Offered as working code. "To create the FST, you need to:" followed by two cases; nothing marks the block as pseudo-code (FSTCompiler.java:976-994).
  • Correct when written. #12831 (Dzung Bui, 2024-02-06, first released in 9.10.0) added both examples when FST still had the (FSTMetadata, DataInput, FSTStore) constructor and OffHeapFSTStore a no-argument one. The verbatim example compiles on 9.10.0 and 9.11.1.
  • A missed update, not a choice. On #13524 Adrien Grand (jpountz) called OffHeapFSTStore "an internal class so it's ok to break the API" (their view). The PR moved every caller of the removed constructors to fromFSTReader, did not touch FSTCompiler.java, and no review comment mentions this javadoc; there is no CHANGES or MIGRATE entry for the removal.
  • Precedent. LUCENE-6112 (#7174, 2014, fixed) was a compile error in the util/fst package example, reported on java-user@. On #12758 a contributor wrote "The Javadoc could be outdated. Will update it" about FST.java (before this example existed). Both were surfaced by the finder and a reviewer from another model family (OpenAI GPT-5.6).
The devil's-advocate check133 words

Strongest case for "intended" or "noise": the three types are @lucene.experimental; maintainers called them internal (Adrien Grand on #13524, as quoted; Michael McCandless on #12831 called FSTCompiler "effectively an internal Lucene datastructure", their view); the block already leaves four names undeclared, so it reads like pseudo-code; Lucene does not compile javadoc snippets; the error is loud.

Why it fails: experimental status explains why the API could change, not why the example was left stale. The failure is two constructors that no longer exist, not missing declarations: with the same placeholders the example compiled on 9.10.0 and 9.11.1, and the corrected form compiles today. The package is exported and the classes are not @lucene.internal, and the public Builder.dataOutput javadoc sends users down this path. Every verifier and the adjudication called it real.

Show the current off-heap form, with a null check (validated) (recommended)

#

Javadoc only, lucene/core/src/java/org/apache/lucene/util/fst/FSTCompiler.java:986-994 (7 lines added, 4 removed in all). The snippet shows the code block; the sentence above it becomes "... you need to first open the corresponding {@link org.apache.lucene.store.IndexInput}, then pass it to an {@link OffHeapFSTStore}, together with the file pointer where the FST bytes start", which also removes the cut-off word "construct". The null check matters: compile() returns null for an FST that accepts nothing, and the OffHeapFSTStore constructor reads metadata.numBytes before fromFSTReader could check for null (a point raised by the cross-model refute-lens reviewer and refined by an independent verifier).

    * <pre><code class="language-java">
    *     fstMetadata = fstCompiler.compile();
-   *     fst = new FST&lt;&gt;(fstMetadata, dataInput, new OffHeapFSTStore());
+   *     if (fstMetadata != null) {
+   *       OffHeapFSTStore store = new OffHeapFSTStore(indexInput, offset, fstMetadata);
+   *       fst = FST.fromFSTReader(fstMetadata, store);
+   *     }
    * </code></pre>

Trade-offs

None for users: documentation only, no CHANGES entry strictly needed. It keeps the off-heap read the example was written for and matches Lucene's own callers. Caveats worth a clause: the off-heap form needs an IndexInput (an arbitrary DataInput cannot back an OffHeapFSTStore); the store keeps that IndexInput and slices it when the FST is read, so it must stay open while the FST is used; offset must be the first FST byte, and a caller with more data after the FST skips past it itself (as FSTTermsReader and NRTSuggester do); the IndexOutput is normally closed before the IndexInput is opened.

What the checks validated

  • The second compile() example extracted from the patched file and compiled in the same one-test check (declaring indexInput and offset instead of dataInput): passes 1 of 1 on main with assertions on and off, on the 10.6.0 jars and on the 9.12.0 jars. The stock block fails the same check, so the check detects the bug.
  • An end-to-end control: an FST with cat -> 5, dog -> 7 streamed to an IndexOutput through Builder.dataOutput and read back exactly as the patched example shows returns 5 and 7 (and null for cow); compile() with no input returns null. 2 tests, 0 failures.
  • ./gradlew :lucene:core:test --tests "org.apache.lucene.util.fst.*" -Ptests.seed=DEADBEEF: 37 tests, 0 failures, 5 skipped (2 @Nightly, 3 @Ignored).
  • ./gradlew :lucene:core:checkGoogleJavaFormat and :lucene:core:renderJavadoc pass; the rendered page shows the new code, links OffHeapFSTStore, and no longer contains new OffHeapFSTStore() or "FST construct".

Use the on-heap constructor instead (not run)

#

fst = new FST<>(fstMetadata, dataInput); (FST.java:419), plus "construct" -> "constructor". Smallest diff; matches the "use the FST constructor" wording of the class and Builder.dataOutput javadocs, and works for any DataInput positioned at the first FST byte (with non-null metadata). It compiles on main and 10.6.0 (the fact check's standalone javac); not run end to end.

Trade-offs

Loads the whole FST onto the heap, so the javadoc no longer shows the off-heap path; it needs the same null check (FST.java:420 reads metadata.numBytes).
