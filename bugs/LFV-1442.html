ConjunctionUtils.createConjunction's javadoc never says that allIterators must also drive each two-phase iterator's approximation

ConjunctionUtils.createConjunction calls both of its lists "to combine", but only the first drives the iteration, so a two-phase iterator passed only in the second list never has its approximation advanced. A filter over docs 0-9 plus a two-phase iterator over docs 4-6 silently returns all 10 documents, not [4, 5, 6].

The finding in 30 seconds

#

createConjunction takes two lists. Only the first, allIterators, decides which documents are visited; the second, twoPhaseIterators, only confirms each visited document. The helper addTwoPhaseIterator puts every approximation (or the iterators it is made of) into the first list for you, but the javadoc never says you must.

Background: two-phase iterators and conjunctions

#
  1. A TwoPhaseIterator has a cheap approximation(), a superset of its matches, and a matches() check for the document the approximation is on. A phrase query, for example, approximates with the documents that have all its terms and checks positions in matches().
  2. A conjunction intersects several iterators: it moves a lead iterator and advances the others to the same document.
  3. With two-phase iterators it intersects the approximations first and calls each matches() only on documents that all of them share.

The finding, step by step

#
  1. You want the documents that are both in a filter over docs 0-9 (DocIdSetIterator.all(10)) and in a two-phase iterator T whose approximation is docs 4-6 and whose matches() always says yes. The javadoc calls both arguments of createConjunction lists "to combine", so you call createConjunction([all(10)], [T]).
  2. You expect [4, 5, 6]. That is what intersectIterators with TwoPhaseIterator.asDocIdSetIterator(T) returns, and what the same two inputs give when the lists are built with addIterator and addTwoPhaseIterator.
  3. You get all 10 documents, [0, 1, ..., 9], with no error, with assertions on and off. Only the first list is iterated; the second is only asked "does this document match?". T's approximation is never moved: it stays at -1, and matches() runs anyway.
  4. With a matches() that reads its approximation, the error flips to missing hits: a real PhraseQuery two-phase iterator passed the same way returned [] instead of its hits [0, 3].

Who is affected

#

Only code outside Lucene that calls the expert factory ConjunctionUtils.createConjunction directly with a hand-built two-phase list. Lucene's own callers and the Elasticsearch, OpenSearch and Solr code found build the lists with the helpers or pass no two-phase iterators. When hit, results are silently wrong, with assertions on and off, in every release since 9.0.0.

Mechanism, terms and numbers462 words

ConjunctionUtils.createConjunction(List<DocIdSetIterator> allIterators, List<TwoPhaseIterator> twoPhaseIterators) is a public factory in a public, untagged class. Its javadoc says it creates "a conjunction over the provided set of DocIdSetIterators and TwoPhaseIterators" and describes each parameter only as a list "to combine" (ConjunctionUtils.java:65-73).

The code treats the two lists differently. The lead iterator is built from allIterators only (ConjunctionDISI.java:114-138); twoPhaseIterators is only wrapped as per-document checks (ConjunctionDISI.java:140-144). In the factory code only the helper addTwoPhaseIterator (ConjunctionDISI.java:84) puts a two-phase iterator's approximation into allIterators, or, when addIterator flattens a nested conjunction (:55-78), the iterators it is made of; the javadoc never asks for it or points to it.

So createConjunction([all(10)], [T]), with T over range(4, 7) and matches() always true, returns all 10 documents instead of [4, 5, 6], and matches() is called while T's approximation is still at -1, which TwoPhaseIterator.matches()'s own javadoc forbids (TwoPhaseIterator.java:96-102). With a matches() that reads its approximation, true hits are dropped instead. Lucene's own callers build the lists with the helpers, so no Lucene query is affected. The code looks deliberate, so the proposed fix is the missing sentence. It has been there since the factory became public in 9.0.0.

Why it looks unintended

#
  • The javadoc reads as two independent inputs: both lists are only "to combine", with no word on approximations or the helpers.
  • The result breaks TwoPhaseIterator's own rule that matches() must not run while the approximation is at -1.
  • Before 9.0.0 these methods were private and always fed through the helpers; #148 made them public without the requirement.
The full argument145 words
  • Contract. ConjunctionUtils.java:65-73: "Create a conjunction over the provided set of DocIdSetIterators and TwoPhaseIterators", both @params "to combine". approximation() "is a superset of the matching documents" (TwoPhaseIterator.java:87-94), so a conjunction with T must be a subset of T's approximation; here it is not.
  • The code breaks a documented rule of its own: matches() must not run while the approximation is at -1 (TwoPhaseIterator.java:96-102).
  • Nothing states the requirement where a user would see it: no javadoc, no test (no test in the tree calls createConjunction; TestConjunctionDISI uses intersectIterators and intersectScorers), no CHANGES or MIGRATE entry, no code comment. PR #148, which made the method public, never states it.
  • History. Before 5e0e7a5479b the list-taking createConjunction and both helpers were private, and every public entry point filled the lists through the helpers, so the rule could not be broken from outside.
The devil's-advocate check180 words

The case: the three methods were made public together, for spans and intervals, and are meant to be used together; the name allIterators hints at it; every in-tree caller, and every downstream caller found, keeps the rule; TwoPhaseIterator is @lucene.experimental; and on #10581 (LUCENE-9541) @jpountz called a similar case "a bug in how ConjunctionDISI was used".

Why it fails: it shows the code is right, not that the rule is documented. #10581 itself ended with a check and a "Requires that ..." sentence in the class javadoc of ConjunctionDISI (ConjunctionDISI.java:30-33, 6b8288445f9), a package-private class; the public wrapper has no such sentence. A likely committer answer, "build the lists with the helpers", is exactly the missing sentence (our guess, not a maintainer statement). A maintainer may still close it as misuse, or accept only a short pointer to the helpers, which is what fix A is. On #10977 (LUCENE-9938, closed 2021-04-27, a month before the factory became public) @dsmiley noted the same internal rule: "The TPI design requires that the "approximation" DISI coupled with it is positioned".

How it was found

#

Semi-formal: an audit of the proof obligations in the public createConjunction javadoc against what the factory does with a two-phase iterator's approximation. The gap was then witnessed by a public-API JUnit test on main, and independent checks reproduced it with their own tests.

The method in full69 words
  • Obligation checked: for any two lists the javadoc allows ("to combine"), the conjunction must return the documents in every DocIdSetIterator that every TwoPhaseIterator matches. The code discharges it only when each approximation, or the iterators it is made of, is also in allIterators, which addTwoPhaseIterator guarantees.
  • Witness: the minimal JUnit test fails on main with assertions on and off.
  • Tier: semi-formal (a proof-obligation audit plus an executable witness).
