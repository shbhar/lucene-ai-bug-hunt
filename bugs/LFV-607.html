JapaneseIterationMarkCharFilter turns なゝめ into などめ: the unvoiced iteration mark after な..の, っ or ぱ..ぺ yields a different kana

With the opt-in JapaneseIterationMarkCharFilter, なゝめ (an older spelling of ななめ, "diagonal") comes out as などめ, so a search for ななめ finds nothing. It happens after each of the 10 kana without a voiced form (な..の, っ, ぱ..ぺ) and their katakana forms, in every release since 4.0.0-BETA (2012).

The bug in 30 seconds

#

JapaneseIterationMarkCharFilter expands Japanese iteration marks before tokenizing: ゝ (ヽ in katakana) repeats the kana before it without a voicing mark, ゞ (ヾ) repeats it voiced.

  1. You put JapaneseIterationMarkCharFilter with its default flags in front of a tokenizer and index なゝめ, the older spelling of ななめ ("diagonal"). The mark ゝ means "repeat the kana before me, without a voicing mark".
  2. You expect ななめ, just as こゝろ gives こころ and じゝ gives じし, so a TermQuery for ななめ finds the document.
  3. Instead the filter writes などめ, with no error: the query for ななめ finds 0 documents, the one for などめ finds 1. The same happens for 19 more pairs, such as のゝ → のね, っゝ → っぢ, ぱゝ → ぱば and ナヽ → ナド.
  4. Why: the voicing table maps が to が because it is voiced, but also な to な because it has no voiced form. isHiraganaDakuten calls every such self-mapping voiced, and for a voiced kana ゝ gives the code point before it (が → か), so な (U+306A) becomes ど (U+3069).
  5. The voiced mark is right for the same kana (なゞ → なな), and so are the other 40 kana of the table and ぽゝ → ぽぽ. A two-line fix passes the repro and all 200 kuromoji tests.

Who is affected

#

Applications that add the opt-in char filter (the class, the SPI name japaneseIterationMark, or a search server's iteration-mark char filter) with default flags; JapaneseAnalyzer does not install it. It hits older orthography and names such as なゝめ, なゝつ and のゝしる: such words are indexed misspelled, and searches for the modern spelling miss them.

Mechanism, terms and numbers663 words

JapaneseIterationMarkCharFilter (kuromoji, opt-in, SPI name japaneseIterationMark) expands the Japanese iteration marks: ゝ (ヽ in katakana) repeats the kana before it without a voicing mark, ゞ (ヾ) repeats it voiced. For 10 hiragana that have no voiced form, っ, な に ぬ ね の and ぱ ぴ ぷ ぺ, and their 10 katakana forms, the unvoiced mark becomes the code point before the kana instead: なゝめ → などめ instead of ななめ, のゝしる → のねしる, ぱゝ → ぱば, ナヽメ → ナドメ. The voicing table stores a kana without a voiced form as a self-mapping, exactly like a voiced kana, and isHiraganaDakuten treats every self-mapping as voiced. Words in older orthography are indexed misspelled and searches for the modern spelling miss them, with no error, in every release from 4.0.0-BETA (2012) to 10.5.2 and on main. A two-line fix checks the code point before the kana instead.

Terms

#
  • Iteration marks (odoriji): ゝ (U+309D, hiragana) and ヽ (U+30FD, katakana) repeat the kana before them; older texts write ななめ ("diagonal") as なゝめ and ののしる ("to revile") as のゝしる. The voiced marks ゞ/ヾ repeat the kana with a voicing mark (みすゞ → みすず).
  • Voicing mark (dakuten): か → が, し → じ, は → ば. The unvoiced mark repeats a voiced kana without it: じゝ → じし. Kana of the na-row (な に ぬ ね の), the small っ and the p-sounds ぱ ぴ ぷ ぺ (which carry a handakuten) have no voiced form.
  • JapaneseIterationMarkCharFilter: opt-in, in kuromoji since 4.0.0; SPI name japaneseIterationMark. Its javadoc: "Normalizes Japanese horizontal iteration marks (odoriji) to their expanded form" (JapaneseIterationMarkCharFilter.java:26). Kana normalization is on by default (:48).

The bug

#
  1. The voicing table h2d has 50 entries for か (U+304B) .. ぼ (U+307C) (:82-131; katakana k2d is derived from it, :133-138). A kana maps to its voiced form (か => が), a voiced kana to itself (が => が), and a kana without a voiced form also to itself, at index 24 (っ, :106), 31-35 (な..の, :113-117) and 38, 41, 44, 47 (ぱ ぴ ぷ ぺ, :120, :123, :126, :129). lookupHiraganaDakuten documents a self-mapping as "c itself if no dakuten variant exists" (:385).
  2. isHiraganaDakuten(c) is inside(c, h2d, '\u304b') && c == lookupHiraganaDakuten(c) (:408; katakana :418). That is true for が and equally for な.
  3. For ゝ, normalizedHiragana returns isHiraganaDakuten(c) ? (char) (c - 1) : c (:303; katakana :321). For が that removes the dakuten (U+304C - 1 = か); for な (U+306A) it gives ど (U+3069), for の ね, for っ ぢ, for ぱ ば.
  4. The voiced mark returns lookupHiraganaDakuten(c) directly (:305), so なゞ → なな is right. ぽゝ → ぽぽ is right only because ぽ (U+307D) lies one code point past the table.

The numbers

#

20 of 20 pairs wrong on main with assertions on and off. A document indexed as なゝめ (keyword tokenizer): TermQuery ななめ → 0 hits, などめ → 1 hit. With JapaneseTokenizer behind the filter, なゝめに切る becomes [など, め, に, 切る] while ななめに切る gives [ななめ, に, 切る]; のゝしる声 becomes [の, ね, しる, 声]. In the pair and sequence sections of the exhaustive check this is the only discrepancy: over all strings of length up to 5 on a 14-symbol alphabet (of the affected kana it contains only な) under all 4 flag combinations, 0 mismatches in the strings without な (1,608,932 checks), 24,985 in those with な (707,844 checks), 0 with the fix. Exposure and likelihood274 words
  • Who. Applications that add JapaneseIterationMarkCharFilter to an analyzer: the class, the factory (SPI name japaneseIterationMark, for example in CustomAnalyzer), or a downstream search server's iteration-mark char filter, which constructs this class with Lucene's default flags (read from their source; not run there). Opt-in: JapaneseAnalyzer installs only CJKWidthCharFilter. It reproduces with the default flags.
  • What triggers it. Text that writes one of the 10 kana (or its katakana form) before the unvoiced mark: older orthography and names such as なゝめ (ななめ), なゝつ (ななつ), のゝしる (ののしる), ナヽ. っゝ is not attested in real text, and handakuten kana before ゝ are uncommon. No frequency was measured. Deterministic: no scale, seed or assertion dependence.
  • What breaks. The filter exists to make the marked and the expanded spelling match; for these words they do not. A document written なゝめ is not found by ななめ and is found by などめ. Query text analyzed by the same analyzer goes through the same filter (for multi-term queries the factory's normalize() builds it too), so a query typed with the mark matches the marked documents but not those written ななめ.
  • Silent. No exception, no log line. The output keeps the input length, so offsets stay right.
  • After a fix. Documents indexed with the filter keep the wrong terms until they are reindexed; query-side analysis is right as soon as the fix is deployed.
  • Workaround today. A MappingCharFilter in front of this filter that maps the 20 pairs (なゝ => なな, ナヽ => ナナ, ...) fixes the single mark (なゝめ → ななめ), but not a span of marks: なのゝゝ (expected なのなの) gives なのどね on stock main and なののね with the workaround.

Why it is a bug, not intended

#
  • The class's javadoc says a self-mapping means "no dakuten variant exists"; isHiraganaDakuten reads it as "is a dakuten".
  • The contract is "their expanded form"; even the documented fallback for illegal sequences gives なな, never など.
  • The voiced mark gets these kana right (なゞ → なな); the coverage tests skip exactly the 10 affected kana.
The full argument213 words
  • The javadoc contradicts the predicate. lookupHiraganaDakuten returns "c itself if no dakuten variant exists" (JapaneseIterationMarkCharFilter.java:385); isHiraganaDakuten (javadoc "true if c is a hiragana dakuten", :405) reads that same self-mapping as voiced (:408). な, の, っ and ぱ are not voiced kana.
  • The contract. "Normalizes Japanese horizontal iteration marks (odoriji) to their expanded form" (:26). The expanded form of なゝ repeats な; など is a different word.
  • The documented fallback. For an illegal sequence the filter "emits the illegal source character as-is" (:28-30), which would give なな again. No documented reading produces など, のね or ぱば.
  • One branch away it is right. The voiced mark uses the lookup directly: なゞ → なな.
  • Internally inconsistent. ぽゝ → ぽぽ is asserted upstream (TestJapaneseIterationMarkCharFilter.java:135), yet ぱゝ → ぱば, only because ぽ lies just outside the table and ぱ inside it.
  • Never tested, never discussed. The coverage tests (:189-215) list the か..ぼ kana that have a voiced form, each followed by its voiced form, and skip the 10 affected kana; no Lucene test has an affected kana before ゝ/ヽ. The introducing issue (LUCENE-4201, now #5273) discusses illegal sequences, the full stop, surrogates, offsets and random tests, never these kana. CHANGES has only the "Added" entry.
The devil's-advocate check165 words

The strongest case (the intended-behaviour checker and the cross-model review): the author wrote the self-mapping entries on purpose, kana iteration marks are rare in modern text, the class already lists limitations (illegal sequences, the full stop, no vertical marks) and carries @IgnoreRandomChains, so odd inputs could be called unsupported; and handakuten kana with ゝ have no settled rule.

Why it fails: the self-mapping is the class's own documented sentinel for "no variant", and the predicate misreads it; the listed limitations do not cover these kana, and the documented illegal-sequence fallback would give なな anyway; @IgnoreRandomChains and the open #11394 concern offsets and an index-out-of-bounds exception, a different symptom and code path; and an unvoiced mark that outputs a voiced kana (ぱば) or a kana of another row (のね) is wrong under any rule. Rarity lowers the priority; it does not make the output intended. Not claimed: that ぱぱ, rather than ぱは, is the required answer for handakuten kana; the docs only rule out ぱば.

Suggested fix

#

Recommended Voiced means "the voiced form of the code point before it" (recommended)

Count c as voiced only if it is the voiced form of the code point before it: base = c - 1; inside(base) && lookup(base) == c, in isHiraganaDakuten and isKatakanaDakuten. Same cost. The repro passes and all 200 kuromoji tests pass, assertions on and off. Indexes built with the filter need reindexing.

   private boolean isHiraganaDakuten(char c) {
-    return inside(c, h2d, '\u304b') && c == lookupHiraganaDakuten(c);
+    char base = (char) (c - 1);
+    return inside(base, h2d, '\u304b') && lookupHiraganaDakuten(base) == c;
   }
   private boolean isKatakanaDakuten(char c) {
-    return inside(c, k2d, '\u30ab') && c == lookupKatakanaDakuten(c);
+    char base = (char) (c - 1);
+    return inside(base, k2d, '\u30ab') && lookupKatakanaDakuten(base) == c;
   }

Voiced means "the voiced form of the code point before it" (recommended) (validated by the checks) (recommended)

#

Two lines per predicate, with a short comment, plus a test method testKanaWithoutVoicedForm in TestJapaneseIterationMarkCharFilter (なゝめ, のゝしる, the 10 hiragana and the 10 katakana pairs). Voiced kana stay voiced (が: か maps to が), unvoiced kana stay unvoiced (か: the code point before it is outside the table), and the 10 kana become unvoiced (な: ど maps to ど, not な), so ゝ repeats them: なな, っっ, ぱぱ.

   private boolean isHiraganaDakuten(char c) {
-    return inside(c, h2d, '\u304b') && c == lookupHiraganaDakuten(c);
+    char base = (char) (c - 1);
+    return inside(base, h2d, '\u304b') && lookupHiraganaDakuten(base) == c;
   }
   private boolean isKatakanaDakuten(char c) {
-    return inside(c, k2d, '\u30ab') && c == lookupKatakanaDakuten(c);
+    char base = (char) (c - 1);
+    return inside(base, k2d, '\u30ab') && lookupKatakanaDakuten(base) == c;
   }

Trade-offs

  • Reuses the table; one lookup per unvoiced mark, as today. Only the unvoiced-mark branch changes; the voiced mark and the span logic are untouched.
  • For handakuten kana it gives ぱぱ, consistent with the existing ぽゝ → ぽぽ test; a maintainer may prefer ぱは. Either way ぱば is gone.
  • Leaves the separate gap outside the table (ゔゝ, ヴヽ, ヷヽ..ヺヽ repeated unchanged; うゞ, ウヾ, ワヾ..ヲヾ not voiced; 12 pairs) as it is.
  • Existing indexes keep the wrong terms until reindexed.

Decide voicing by Unicode canonical decomposition (untested)

#

Treat c as voiced when its NFD form ends with U+3099, and use the first character as the unvoiced kana (java.text.Normalizer).

Trade-offs

Independent of the table, and it would also cover the voiced kana outside it (ゔ, ヴ, ヷ..ヺ). But it adds a Normalizer call per unvoiced mark and changes output for those out-of-table kana (ゔゝ would become ゔう), a separate gap that needs its own decision. Not run.

Mark "no voiced form" in the table itself (untested)

#

For example a separate flag array, or a sentinel value that lookup turns back into c.

Trade-offs

Makes the table self-describing, at the cost of a larger diff that also touches the voiced-mark path. Not run.

Workaround without a Lucene change: a MappingCharFilter in front (validated by the checks)

#

Map the 20 pairs (なゝ => なな, ナヽ => ナナ, ...) before this filter.

Trade-offs

Fixes the single mark (なゝめ → ななめ, ぱゝ → ぱぱ) but not a span of marks: なのゝゝ gives なののね instead of なのなの.

What the checks validated

Run in the probe on stock main: right for the 6 single-mark words, wrong for the span.

Downstream note

#

Search servers that expose this char filter as kuromoji_iteration_mark build it from the same Lucene class with its default flags, so their Japanese analysis should produce the same wrong kana (read from their source; not run there).

How it was found

#

A bounded-exhaustive check compared the filter with a reference expander that uses Unicode decomposition to tell voiced kana: 890 character/mark pairs and all strings of length up to 5 over a 14-symbol alphabet (2.3 million checks). 20 pairs differed, and among the strings only those containing な; the finder then reduced it to a public-API JUnit.

The method in full246 words
  • Method: bounded-exhaustive translation validation (the hunt's semi-formal tier). A harness ran the stock main jar against a reference expander written from the class javadoc and the upstream tests, with Unicode canonical decomposition (U+3099) as the independent voicing oracle.
  • Pair section. Every character from U+3041 to U+30FF except the four kana marks (and a kanji, a letter and a question mark) followed by each of the five iteration marks, except the 60 pairs that need a voiced form outside the table: 890 checks (178 sources x 5 marks), 20 mismatches (the 20 pairs), 0 with the fix. The 60 out-of-table pairs were counted separately (the gap noted below).
  • Sequence section. All strings of length up to 5 over a 14-symbol alphabet (か が な ぽ カ ガ 時, the five marks, 。 and a supplementary character) under all 4 flag combinations: 1,608,932 checks without な, 0 mismatches; 707,844 with な, 24,985 mismatches, 0 with the fix. So the per-kana rule is the only discrepancy in that alphabet. Non-vacuity: a reference without the full-stop barrier gives 98,884 mismatches.
  • Reduction. A public-API JUnit (keyword analyzer behind the filter) on the stock main jars, 2026-10-26; this doc's paste-ready test adds the search miss.
  • Also seen, not part of this bug: the table stops at か..ぼ, so 12 pairs outside it (ゔゝ, ヴヽ, ヷヽ..ヺヽ, うゞ, ウヾ, ワヾ..ヲヾ) are not voiced or unvoiced; read(cbuf, off, 0) returns -1 instead of 0. Both are the same on stock main and with the fix.

LFV-607, snapshot of 2026-10-30

Registry title
JapaneseIterationMarkCharFilter expands the unvoiced kana iteration mark ゝ/ヽ after the na-row, the small tsu and the handakuten kana (な に ぬ ね の, っ, ぱ ぴ ぷ ぺ and their katakana forms) to a different kana, so なゝめ becomes などめ instead of ななめ (のゝしる becomes のねしる, ぱゝ becomes ぱば), because kana that have no voiced form are stored as self-mappings in the voicing table and the 'is voiced' check reads every self-mapping as voiced
Area
analysis-kuromoji / Japanese char filters (JapaneseIterationMarkCharFilter kana iteration marks ゝ/ヽ: isHiraganaDakuten / isKatakanaDakuten over the h2d / k2d voicing tables, used by normalizedHiragana / normalizedKatakana; JapaneseIterationMarkCharFilterFactory 'japaneseIterationMark')
Priority
Low, rank 447: The opt-in JapaneseIterationMarkCharFilter mis-expands the unvoiced mark after 10 kana, which in practice shows up only in older orthography, so it is rarer than its kuromoji sibling LFV-605.
Impact class
silent wrong results
Impact note
Hits only applications that add the opt-in JapaneseIterationMarkCharFilter (the class, or the factory name 'japaneseIterationMark') with its default normalizeKana=true in front of an analyzer (JapaneseAnalyzer does not install it) and that index or query text in which one of 20 kana (っ, な, に, ぬ, ね, の, ぱ, ぴ, ぷ, ぺ, or the katakana form) is followed by the unvoiced mark ゝ/ヽ, which in practice means older orthography and names such as なゝめ, なゝつ or のゝしる: the filter silently emits a different kana (などめ), so the indexed term is not the expanded spelling and a query for ななめ misses the document (executed), deterministically at any size, with -ea and -da, in every release since 4.0.0-BETA; the voiced mark ゞ/ヾ, the kana that do have a voiced form, sequences of marks and offsets are correct.
Summary
You put JapaneseIterationMarkCharFilter in front of an analyzer and index なゝめ, the older spelling of ななめ ('diagonal'), and expect the filter to replace the iteration mark ゝ with the repeated kana, as its javadoc promises ('normalizes ... iteration marks to their expanded form'). Instead it emits などめ, so the index holds a different word and a search for ななめ finds nothing; the same happens for 19 more kana (のゝ becomes のね, ぱゝ becomes ぱば, っゝ becomes っぢ, and the katakana forms with ヽ). The filter decides whether the preceding kana is voiced by checking whether it maps to itself in its voicing table, but the kana that have no voiced form (っ, な..の, ぱ ぴ ぷ ぺ) are stored there as self-mappings too, so it strips a dakuten they never had and emits the preceding code point.
