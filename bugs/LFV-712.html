Kuromoji's DictionaryBuilder silently truncates readings of 128 or more chars

Kuromoji's DictionaryBuilder stores reading and pronunciation lengths in 7 bits unchecked, so in a custom dictionary a 136-char reading silently comes back as 8 chars, a 128-char one as "", and the pronunciation after it as garbage; long pronunciations wrap too. The bundled dictionary is unaffected; releases since 3.6.0 are.

The bug in 30 seconds

#

Each dictionary entry can store a reading and a pronunciation, each behind a one-byte header: 7 bits of length plus a kana flag. The writer never checks the length, and the reader trusts the header, so it returns length mod 128 chars, and after a wrapped reading it looks for the pronunciation in the wrong place.

  1. You build a custom system dictionary with DictionaryBuilder from one CSV row: a 64-char proper noun (国立研究開発法人, the name of a class of public research agencies, eight times), its 136-char reading コクリツケンキュウカイハツホウジン × 8, and its 136-char pronunciation (the same with ー for long vowels).
  2. You expect the build to fail, as it does for a base form of 16 or more chars ("Length of base form ... is >= 16"), or the reading to come back as written.
  3. Instead the build succeeds. The writer keeps each length in 7 bits of one byte, so 136 is stored as 136 mod 128 = 8, and 128 as 0.
  4. JapaneseTokenizer gives the reading コクリツケンキュ (8 chars) and a pronunciation of 3 unrelated chars (U+0B04 U+2F24 U+3B06) decoded from the reading's own bytes; JapaneseReadingFormFilter emits the 8 chars as the term. A 128-char reading comes back as "" (an empty term); 127 chars round-trip.

Who is affected

#

Only applications that build their own system dictionary with DictionaryBuilder and load it with the custom-dictionary JapaneseTokenizer constructor, and only rows whose stored reading or pronunciation has 128 or more chars: very long entries, with kanji or with a pronunciation that differs from the reading. The default analyzer, the japanese factory and user dictionaries are not affected.

Mechanism, terms and numbers670 words

Kuromoji lets an application build its own system dictionary from IPADIC- or UniDic-format CSV files with the public, @lucene.experimental DictionaryBuilder, and load it with the JapaneseTokenizer constructor that takes custom dictionaries. The builder stores each entry's reading and pronunciation behind a one-byte header, (byte) (length << 1 | kanaFlag), and never checks the length. A stored reading or pronunciation of 128 or more chars therefore keeps only its length mod 128: 128 chars come back as "" and 136 as the first 8, each field on its own, and a pronunciation stored after a wrapped reading is decoded from the reading's own bytes. ReadingAttribute passes the wrong values on, and JapaneseReadingFormFilter indexes a wrapped reading as the term. The same method rejects a stored base form of 16 or more chars and the ids its format cannot hold with an IllegalArgumentException; the reading and pronunciation lengths are the unguarded limits. The bundled dictionary (longest reading 32 chars) and the default analyzer are not affected. Present since kuromoji's first release, 3.6.0; an 8-line check fixes it.

Terms

#
  • System dictionary: kuromoji's main dictionary of known words, compiled from CSV rows. Each row has the surface (the word as written), ids and costs, part-of-speech fields, the base form, the reading (how the word is read, in katakana) and the pronunciation (how it is said, for example with ー for a long vowel).
  • Custom system dictionary: one an application compiles itself with DictionaryBuilder.build (ja/dict/DictionaryBuilder.java:58-73) and loads with the custom-dictionary JapaneseTokenizer constructor (ja/JapaneseTokenizer.java:191-217). The bundled dictionary is compiled the same way at Lucene build time.
  • Stored only when needed: a reading is stored only when it differs from the katakana form of the surface, and a pronunciation only when it differs from the reading (ja/dict/TokenInfoDictionaryEntryWriter.java:110-114). Otherwise the reader derives them.

The bug

#
  1. putEntry writes the reading as buffer.put((byte) (reading.length() << 1 | 1)) plus one byte per char for an all-katakana reading, or (byte) (reading.length() << 1) plus two bytes per char otherwise (TokenInfoDictionaryEntryWriter.java:151-161); the pronunciation the same way (:163-177). No range check. A few lines earlier, a stored base form of 16 or more chars throws IllegalArgumentException (:139-141).
  2. The reader decodes the header as (b & 0xff) >>> 1 (TokenInfoMorphData.java:104-108, :130-134) and finds the pronunciation by skipping the reading by that decoded length (pronunciationOffset, :160-174).

Worked example: the 136-char reading

#
  1. Header 136 << 1 | 1 = 273; one byte keeps 273 - 256 = 17; 17 >>> 1 = 8, kana. The reading comes back as its first 8 chars, コクリツケンキュ.
  2. The pronunciation really starts after all 136 reading bytes, but the reader skips only 8 and lands on the reading's 9th char, ウ, stored as byte 0x06: a header for 3 UTF-16 chars. The next 6 bytes are the reading's chars 10-15 (カイハツホウ = 0x0B 0x04 0x2F 0x24 0x3B 0x06), read as U+0B04 U+2F24 U+3B06.
  3. A 128-char reading has the header 257, kept as 1: length 0, "".

Exposure and likelihood353 words
  • Who is hit. Applications with a custom system dictionary (IPADIC or UNIDIC format; both go through the same writer). The JapaneseTokenizer constructor that takes one says it "provides an entry point for users that want to construct custom language models that can be used as input to DictionaryBuilder" (JapaneseTokenizer.java:192-195).
  • Not hit. The default JapaneseAnalyzer and JapaneseTokenizer (bundled dictionary, longest reading 32 chars over all 392,127 source rows); the japanese tokenizer factory, which takes only a user dictionary (JapaneseTokenizerFactory.java:86-88, :125-126); user dictionaries, which are separate code.
  • Which rows. Only rows whose stored reading or pronunciation has 128 or more chars. A reading is not stored when it equals the katakana form of the surface, and a pronunciation is not stored when it equals the reading (TokenInfoDictionaryEntryWriter.java:110-114). So an all-kana entry whose reading and pronunciation both equal its katakana form is not affected. A long all-kana entry is still hit through a pronunciation that differs from its reading (for example ー for long vowels; executed by the fact check), and an entry with kanji through either field, such as a long proper noun or title. No real-world dictionary was measured for such rows.
  • Effect. Silent and deterministic: every match of the row gets an empty or truncated value for the field that wrapped, and a garbage pronunciation when the reading wrapped, through getReading / getPronunciation and ReadingAttribute. JapaneseReadingFormFilter uses only the reading, so it emits a wrong term when the reading wrapped (JapaneseReadingFormFilter.java:63-95); JapaneseCompletionFilter also reads ReadingAttribute (read, not executed). In every executed case there was no error at build or analysis time (a misdecoded header could in principle read past the buffer end and throw; read, not observed); one row is enough.
  • Why nobody noticed. Dictionary build tooling for Lucene filters rows by base-form length, because Lucene rejects long base forms; nothing filters readings. Two community walkthroughs of the format (a committer's 2019 slides and a 2019-2020 dictionary checker) list only the ids and the 16-char base form as size limits; the checker also flags an empty reading. No user report in 14 years.

Why it is a bug, not intended

#
  • The writer rejects the other limits of its format, a stored base form of 16+ chars and the ids; LUCENE-8863 made those asserts exceptions (8.2.0). The reading length never had a check.
  • The 2012 original asserted baseForm.length() < 128 for the same 7-bit length, but not for the reading.
  • No javadoc, test or changelog states a 127-char limit.
The full argument252 words
  • Fail fast is the writer's pattern. putEntry throws IllegalArgumentException for empty POS fields (:72-74), an empty base form (:104-106), leftId != rightId (:117-119), leftId >= 8192 (:120-122), conflicting POS data (:130-133) and a stored base form of 16 or more chars (:139-141); an empty POS part is still a plain assert (:62). TestTokenInfoDictionary.testPutException (:91-105) asserts the pattern for the ids and the column count.
  • LUCENE-8863 (#9906; in 8.2.0 through the branch_8x commit bdaf10ffa826, on main 4502065f0365, first released in 9.0.0) replaced assert baseForm.length() < 16, the id asserts and the conflicting-POS assert with IllegalArgumentException, and added the empty-POS and empty-base-form checks. In the thread @mocobeta wrote "+1 for changing assertions to \"real\" exceptions", and @rmuir, about an empty base form, "It sounds like a missing check in the code ... I see it as bug in your dictionary, we should fail :)". The reading length had no assert, so it was left out.
  • The limit was known for the base form. The original import (cd372bdc8383, LUCENE-3305, 2012) stored the base form with the same 7-bit header and asserted baseForm.length() < 128; the reading and pronunciation lines next to it had no assert.
  • Nothing documents a limit. Not DictionaryBuilder, JaMorphData (getReading: "Reading of the token"; getPronunciation: "Pronunciation of the token"), JapaneseTokenizer, the package docs, MIGRATE.md or CHANGES.txt; no test covers reading or pronunciation lengths.
The devil's-advocate check170 words

The strongest case for "intended": DictionaryBuilder is @lucene.experimental and its input only "roughly" follows IPADIC (DictionaryBuilder.java:32-35); the compact format was designed around the bundled dictionary (@rmuir in #5128, about another assert: "an optimization that works for ipadic and naist-jdic, and I knew i was making an assumption doing it"; in #9906: "I don't think its good to try to support N different ways of doing things when only one is tested (the ipadic way)"); readings of 128 or more chars are far outside IPADIC (32 at most); and the dictionary is trusted input.

Why it fails: "experimental" allows the API to change, not silently wrong output; the "ipadic way" remark argues for rejecting input the format cannot hold, which the builder does for the base-form length and the ids; nothing documents a 127-char limit; trusted input rules out a security mark, not a correctness bug. The cross-model reviews rated the argument weak; the other reviewers likewise concluded that the behaviour is not intended or recommended rejecting such rows.

Suggested fix

#

Recommended Reject a stored reading or pronunciation of 128 or more chars

In TokenInfoDictionaryEntryWriter.putEntry, throw IllegalArgumentException when a reading or pronunciation that is actually stored (inside the HAS_READING / HAS_PRONUNCIATION branches) has 128 or more chars, like the base-form check (+8 lines). The repro then passes, and so does the whole kuromoji test task (200 tests), assertions on and off.

if ((flags & TokenInfoMorphData.HAS_READING) != 0) {
  // the length is stored in the upper 7 bits of one byte
  if (reading.length() >= 128) {
    throw new IllegalArgumentException("Length of reading " + reading + " is >= 128");
  }
  ...
if ((flags & TokenInfoMorphData.HAS_PRONUNCIATION) != 0) {
  ...
  if (pronunciation.length() >= 128) {
    throw new IllegalArgumentException(
        "Length of pronunciation " + pronunciation + " is >= 128");
  }

Trade-offs

  • A custom dictionary that builds today with such rows will fail to build, with a message that names the field and its value, as long base forms have since 8.2.0. Worth a CHANGES.txt line.
  • The bundled dictionary cannot change: a stricter sketch (it threw for any reading or pronunciation of 128 or more chars, stored or not) rebuilt the bundled source with no exception and 9 byte-identical files, and this fix throws in a subset of those cases and writes the same bytes. Inferred, not re-run with this fix.

Widen the length field

#

Store the length as a vInt or in two bytes, so long readings survive.

Trade-offs

A format change: the reader changes, a vInt header would take two bytes for readings of 64-127 chars, so the dictionary version needs a bump and custom dictionaries a rebuild. Not run.

Skip invalid rows with a warning (opt-in)

#

Trade-offs

Downstream note

#

Any product on Lucene that lets operators load a custom kuromoji system dictionary inherits the silent truncation; Lucene's own japanese tokenizer factory takes only a user dictionary, which is not affected.

How it was found

#

Semi-formal. A bounded-exhaustive check compared kuromoji's bundled compiled dictionary with its source: 392,127 rows, 0 mismatches, longest reading 32 chars. Reviewing how each field is encoded, the finder saw that the base form has a length limit and the 7-bit reading and pronunciation lengths have none, and confirmed it with a dictionary built through the public builder.

The method in full133 words
  • Round trip. A hunt unit on compiled CJK dictionaries ran a bounded-exhaustive translation validation of kuromoji's bundled dictionary against its mecab-ipadic source: all 392,127 rows, 1,731,856 connection-cost cells, all 65,536 chars and every unknown-word class, with 0 mismatches. The longest source reading is 32 chars, so the bundled dictionary cannot show the bug.
  • Signal. While checking each field's encoding, the finder noticed that the base form has an explicit limit with an exception and the reading and pronunciation lengths, packed into one byte, have none.
  • Witness. The finder built a one-row custom dictionary through the public DictionaryBuilder and reduced it to a 3-test public-API JUnit (2 of 3 fail on main with assertions on and off, and on 10.5.2 and 9.12.3). No formal tool (model checker, SMT solver or proof) produced the signal.

History

#

Present since kuromoji's import (cd372bdc8383, LUCENE-3305, 2012; first release 3.6.0); the builder became public API in the jar in 8.2.0 (LUCENE-8871), the release that turned the base-form assert into an exception. Executed on 9 versions from 3.6.0 to main: all affected; never fixed.

Versions tested7 rows

Introduced with kuromoji itself: LUCENE-3305 (#4378), trunk commit cd372bdc8383 by @rmuir (2012-01-12), the merge of the development branch where the one-byte reading and pronunciation header was written (63700e75cb3a, 2012-01-06, "more efficient tokeninfodictionary"); the branch_3x backport 8c9485fb6642 shipped in 3.6.0. Not a regression: no version ever checked these lengths. Until 8.1.1 the builder was a build tool in the source release only; LUCENE-8871 made it public API in the 8.2.0 jar, and LUCENE-8863 (same release, through the branch_8x commit bdaf10ffa826; 4502065f0365 on main) turned the base-form and id asserts into exceptions without adding a reading check. LUCENE-8971 (8.3.0) added the custom-dictionary JapaneseTokenizer constructor, LUCENE-10400 (9.1.0) the Path constructors, and LUCENE-10393 (#740) moved the lines unchanged into TokenInfoDictionaryEntryWriter.

Bug record

#

LFV-712, snapshot of 2026-10-29

Registry title
Kuromoji's DictionaryBuilder silently accepts a reading or pronunciation of 128 or more chars and stores its length in 7 bits, so the built system dictionary returns an empty or truncated reading and a garbage pronunciation (a too-long base form, by contrast, is rejected)
Area
analysis / kuromoji system dictionary builder (ja.dict.TokenInfoDictionaryEntryWriter reading and pronunciation length bytes; TokenInfoMorphData decoding; custom dictionaries built with DictionaryBuilder)
Priority
Low, rank 448: Kuromoji's DictionaryBuilder silently truncates readings of 128 or more chars, but only in an opt-in custom system dictionary with very long entries that nobody has reported in 14 years, so it follows the runtime ICU row LFV-720.
Impact class
silent wrong results
Impact note
Hits only applications that build their own kuromoji system dictionary with the public, @lucene.experimental DictionaryBuilder (IPADIC or UNIDIC format) and load it through the custom-dictionary JapaneseTokenizer constructor (opt-in; the bundled dictionary's longest reading is 32 chars, so the default analyzer is unaffected), and only rows whose stored reading or pronunciation has 128 or more chars (a reading is stored only when it differs from the katakana form of the surface, a pronunciation only when it differs from the reading): such a row builds without error, and every match of it deterministically gets a reading of the real length mod 128 (empty at 128 chars, an 8-char prefix at 136) and, when the reading wraps, a pronunciation decoded from the reading's own bytes, through getReading/getPronunciation, ReadingAttribute and JapaneseReadingFormFilter (which then indexes an empty or truncated term), with -ea and -da and no scale needed, in every release from 3.6.0 (where the builder was a source-release tool; public in the jar since 8.2.0) to 10.5.2 and on main.
Summary
You build a custom kuromoji system dictionary with DictionaryBuilder from an IPADIC-format CSV that has a row whose reading is 128 katakana chars long (or, more naturally, a 64-char proper noun with a 136-char reading), and you expect either an IllegalArgumentException at build time, as the builder throws for a stored base form of 16 or more chars that its compact format cannot hold, or the reading back unchanged. Instead the build succeeds, because putEntry writes each length as (byte) (length << 1 | kanaFlag) with no check, so the stored length is the real length mod 128: getReading and JapaneseTokenizer's ReadingAttribute return "" for the 128-char reading and only the first 8 chars of the 136-char one, a 128-char pronunciation comes back empty, a pronunciation stored after a wrapped reading is decoded from the reading's own bytes (a 4-char pronunciation came back as the single char U+0304), and JapaneseReadingFormFilter indexes the empty or truncated reading as the term.
