Hunspell: a Dictionary load that fails while reading the .dic leaves its offline-sort temp output open (regression in 9.9.0)

When a hunspell Dictionary load with a temp Directory fails while reading the .dic, the constructor throws without closing the temp file it opened for sorting. Each failure keeps one file descriptor open until GC and can leave the file on disk; a regression in 9.9.0.

The finding in 30 seconds

#

Background: how a hunspell dictionary is loaded with a temp directory

#
  1. Dictionary must sort all .dic entries before it builds its word table. The constructors that take a temp Directory, and HunspellStemFilterFactory, sort on disk (SortingStrategy.offline), so a large dictionary needs little memory.
  2. The load opens a temp file in that directory (<prefix>_dat_0.tmp), writes every .dic entry to it, closes it, sorts it into a second temp file, reads that back, and deletes both.
  3. The other strategy, SortingStrategy.inMemory(), sorts a list in memory and uses no files. A successful load leaves nothing behind either way.

The finding, step by step

#
  1. Load a dictionary with new Dictionary(tempDir, "dict", affix, dic), the constructor that sorts the .dic entries in a temp file inside tempDir. Here the .dic stream throws an IOException on its first read, a failure the constructor documents.
  2. You expect the constructor to throw that IOException and release what it created, as after a successful load and as 9.8.0 did: closing tempDir afterwards succeeds.
  3. Instead the temp output dict_dat_0.tmp, opened just before the .dic is read, stays open: closing the test directory fails with there are still 1 open files: {dict_dat_0.tmp=1}. The caller got no object, so it cannot close the file.
  4. With a real directory each failed load keeps one descriptor until GC and one temp file on disk (5 failed loads: 5 files, 5 descriptors). Through HunspellStemFilterFactory the file is deleted but stays open: 10 failed loads, 10 descriptors on deleted files.

Who is affected

#

Users of the opt-in hunspell analysis component who load through the Dictionary(Directory, ...) constructors or HunspellStemFilterFactory (offline sorting is what they always use), when a load fails after its temp file was opened: a .dic read error, a full temp disk, or an undefined AM alias. Each failure holds one descriptor until GC; the load itself fails loudly.

Mechanism, terms and numbers587 words

The Dictionary(Directory tempDir, ...) constructors and HunspellStemFilterFactory sort the .dic entries on disk: Dictionary's constructor calls sortingStrategy.start(), which opens a temp IndexOutput in tempDir, and then mergeDictionaries(...), which reads the .dic and writes every entry to it, with no failure handling. Only finishAndSort() closes the output. So when reading the .dic throws (an IOException the constructor documents), or a write to tempDir fails, the constructor throws and the output stays open; the caller has no object to close, and FSDirectory.close() does not close it. Each failed load keeps one file descriptor open until garbage collection and, in a caller-supplied temp directory, leaves the file on disk; through the factory, which deletes its private temp directory, the file is unlinked but its descriptor stays open. Before #12834 (9.8.0) the entries were written inside a try-with-resources and the output was closed on failure; every release from 9.9.0 to 10.6.0 and main has the leak. The load itself fails loudly, and there are no wrong results. A catch (Throwable t) { ...; throw t; } cleanup at each step of the offline load fixes it.

Terms

#
  • Offline sorting (SortingStrategy.offline(tempDir, prefix)): what the Dictionary(Directory, ...) constructors (Dictionary.java:213) and HunspellStemFilterFactory use. Its start() opens the temp IndexOutput; finishAndSort() writes the footer, closes it, sorts, and returns a supplier that reads the sorted file and deletes it on close().
  • Temp output: the IndexOutput from tempDir.createTempOutput(prefix, "dat", ...), a file such as dict_dat_0.tmp with an open file handle.

The bug

#
  1. The constructor runs EntryAccumulator acc = sortingStrategy.start(); (Dictionary.java:267), which opens the temp output and its writer (SortingStrategy.java:71-72).
  2. Then mergeDictionaries(dictionaries, decoder, acc); (:268) reads the .dic (:1016, :1019) and writes each entry (:1034, SortingStrategy.java:77-80). It is outside any try: only the supplier returned by finishAndSort() is in a try-with-resources (:269).
  3. If it throws (a .dic read error, a write error in tempDir, or an undefined AM alias, LFV-1012), finishAndSort() never runs, and it is the only code that closes the output (SortingStrategy.java:83-88).
  4. The constructor throws, so the caller has no Dictionary and no handle; FSDirectory.close() only marks the directory closed and retries pending deletes; it closes no open outputs (FSDirectory.java:277-280). The descriptor stays until the output's channel is garbage-collected; the file stays in tempDir.
  5. HunspellStemFilterFactory.inform loads into a fresh directory under java.io.tmpdir and calls IOUtils.rm(tempPath) in finally (HunspellStemFilterFactory.java:109-113): the open file is unlinked, and its descriptor stays open until GC.
  6. The same gap exists at later steps (fault injection, below): a failing footer write or writer close, a failing delete of the unsorted input after the sort, a failing open of the sorted file, and a failing reader close in the supplier's close(). Failures inside the sort itself and while reading the sorted entries are cleaned up.

Exposure and likelihood195 words
  • Who is hit. Applications that load hunspell dictionaries through Dictionary(Directory, String, InputStream, InputStream), Dictionary(Directory, String, InputStream, List<InputStream>, boolean) or HunspellStemFilterFactory (SPI name hunspellStem, for example in CustomAnalyzer). Users of the SortingStrategy.inMemory() constructor are not affected.
  • What it takes. A load that fails after the temp file was opened: an I/O error while reading the .dic stream, a full or failing temp disk, or a .dic entry with an undefined AM morphological alias (LFV-1012). These are exceptional events, so it is rated rare. Failures while parsing the .aff happen before the file is opened and leak nothing.
  • What happens. The load fails loudly with its original exception; the leak is silent. One file descriptor per failed load until GC. With a caller-supplied persistent temp directory, one small temp file per failure stays on disk (not removed by Directory.close() or a later successful load). Through the factory the file is unlinked at once and only the descriptor remains. An application that retries a failing load accumulates one descriptor per attempt until a GC runs.
  • Not claimed. Windows was not tested (an open file cannot be deleted there, so the factory's IOUtils.rm may behave differently).

Why it looks unintended

#
  • Until 9.8.0 a try-with-resources closed the temp output on failure; #12834 moved the writer out of it.
  • The neighbouring steps clean up on failure: the sort deletes its input; the sorted file is closed and deleted.
  • Maintainers wanted no leftovers: the factory deletes its temp dir "because the temp dir is likely not empty on exception" (Michael McCandless, LUCENE-6829).
The full argument245 words
  • It worked before. 9.8.0 wrote the entries inside try (ByteSequencesWriter writer = new ByteSequencesWriter(output)) (9.8.0 Dictionary.java:992). #12834 moved the writer into SortingStrategy.offline().start() and its close into finishAndSort(); its review threads (Dawid Weiss and Peter Gromov, 2023-11-22) discuss only the sorted file's cleanup. On 9.9.0 jars with only the parent commit's Dictionary.java swapped in, the open output and the factory descriptor leak disappear.
  • The neighbouring steps release on failure. sortWordsOffline deletes its input when the sort throws (SortingStrategy.java:116-121, the catch-and-rethrow of #14633); the sorted file is closed and deleted by the try-with-resources at Dictionary.java:269; OfflineSorter wraps its directory "So we can remove any partially written temp files on exception" (OfflineSorter.java:295).
  • Maintainer intent. In LUCENE-6829 (#7887, 2015-10-13) Michael McCandless wanted the factory "to recursively remove the temp dir, and any files under it, because the temp dir is likely not empty on exception", and Dawid Weiss answered "we always attempt to remove the temp. stuff ... Otherwise you'd have temp files piling up without any visible reason?". That cleanup is still in the factory; since 9.9.0 the still-open output defeats it.
  • Contract. @throws IOException Can be thrown while reading from the InputStreams (Dictionary.java:186, :203, :223): a read error is an expected outcome, not misuse.
  • Test oracle. MockDirectoryWrapper.close() refuses to close a directory with open files. No hunspell test makes the .dic phase fail (TestDictionary.testInvalidData fails in the .aff, before the temp file is opened).
The devil's-advocate check117 words

The strongest case for "intended" (an intended-behaviour checker, and read-only reviewers from another model family, OpenAI GPT-5.6): no javadoc promises cleanup after a failed load; the caller owns tempDir and can delete it, as the factory does; HunspellStemFilterFactory is @lucene.experimental; and the load fails loudly while GC reclaims the descriptor.

Why it fails: it speaks to severity, not intent. A caller can delete files but cannot close an output it never received, and FSDirectory.close() does not close it; the same code closed it before 9.9.0; every neighbouring step releases on failure; and the 2015 maintainers explicitly did not want temp files piling up. Hence a minor leak on a failure path, a bug of low priority.

Suggested fix

#

Recommended A. Release on failure at every step of the offline load (catch Throwable and rethrow)

Release on failure at every step of the offline load, in the catch (Throwable t) { ...; throw t; } style of #14633: a new abort(Throwable) closes the writer and deletes the temp file when reading the .dic fails; later steps get the same cleanup. Validated: the repro and the hunspell tests pass; 0 of 228 fault-injection checks leak.

       EntryAccumulator acc = sortingStrategy.start();
-      mergeDictionaries(dictionaries, decoder, acc);
+      try {
+        mergeDictionaries(dictionaries, decoder, acc);
+      } catch (Throwable t) {
+        acc.abort(t);
+        throw t;
+      }
       try (EntrySupplier sorted = acc.finishAndSort()) {
All options and trade-offs3 options · 605 words

Two options were run through gradle in a scratch worktree of 645d4fe14a20 and through the fault-injection harness; the full one is recommended.

A. Release on failure at every step of the offline load (catch Throwable and rethrow) (validated by the checks) (recommended)

#

Dictionary.java:267-268 wraps mergeDictionaries and calls a new EntryAccumulator.abort(Throwable) (a no-op default; the offline accumulator closes the writer and deletes the temp file, adding its own exceptions to t as suppressed; as in IOUtils, an Error thrown while releasing propagates instead, with t attached). In SortingStrategy.offline(): finishAndSort aborts when the footer write or the writer close fails, deletes the sorted file when deleting the unsorted input or opening the sorted file fails, and the supplier's close() becomes IOUtils.close(reader, () -> tempDir.deleteFile(sortedFile)), the form Dawid Weiss suggested in the #12834 review. +39/-8 lines in two files. The constructor hunk:

       EntryAccumulator acc = sortingStrategy.start();
-      mergeDictionaries(dictionaries, decoder, acc);
+      try {
+        mergeDictionaries(dictionaries, decoder, acc);
+      } catch (Throwable t) {
+        acc.abort(t);
+        throw t;
+      }
       try (EntrySupplier sorted = acc.finishAndSort()) {

Trade-offs

  • Same style as the existing sortWordsOffline cleanup (#14633) and the later success-flag removals (#15134); no public API change (EntryAccumulator is package-private).
  • Cleanup exceptions are added to the original exception as suppressed, so the caller still sees the real cause; only an Error during cleanup is thrown in its place, with the original attached (the convention of IOUtils.closeWhileSuppressingExceptions and deleteFilesSuppressingExceptions, IOUtils.java:114-136, :247-267).
  • Nothing changes on the success path or for SortingStrategy.inMemory().

  • Fault injection on the stock jars with the fix's two classes swapped in: 228 checks (a fault-free baseline and 227 injected failures), 0 leak (stock: 80).

B. Fix only the reading phase (the 9.9.0 regression) (validated by the checks)

#

The constructor hunk and abort(Throwable) from A, without the changes to finishAndSort, sortWordsOffline and the supplier's close().

Trade-offs

Smallest change and enough for the minimal test's case, a failure while the .dic is read (all 60 reading-phase leaks of the fault run go away), but 20 of the 228 checks still leak at the later steps (footer write, writer close, input delete, sorted-file open, reader close); a full disk that the 8 KiB output buffer reports only at the footer write or the writer close is one of them.

The repro passes in gradle (the seed's default, assertions off, alone and in the hunspell package: 159 tests, 0 failures) and standalone with -ea and -da. Fault injection: 20 of 228 checks leak.

C. The same cleanup with boolean success flags and finally

Trade-offs

Equivalent behaviour, but upstream has been replacing this pattern with catch-and-rethrow (#14633, #15134); a cleanup failure is swallowed instead of being attached to the original exception. Validated earlier by the hunt (the 4-test JUnit 4/4, 76 upstream hunspell tests, 0 of 228 checks leak).

Downstream note

#

Products that retry a failing dictionary or analysis-configuration load in a loop accumulate one open descriptor per attempt until GC, and one file per attempt with a persistent temp directory.

How it was found

#

Non-formal first signal: an executed exception-safety probe that made hunspell loads fail at chosen bytes saw the temp file stay open. The hunt then model-checked the load's resource lifecycle in TLA+ (56 violating traces on 6 steps) and replayed it on the real code with fault injection: 80 of 228 checks leaked, matching the model.

The method in full174 words

Method: non-formal first signal, then formal characterisation. On 2026-10-28 an exception-safety probe (HunspellTempLeakProbe) made the .dic stream fail at byte 2, 8 or 14 and the temp directory fail after 0, 5 or 20 bytes; every case left hunspell_dat_0.tmp open and in the temp directory (13 of 20 checks failed, also on the 10.6.0 release candidate). The hunt unit for analysis loaders then wrote a TLA+ model of the offline load with an exception allowed at every throwing step (TLC: 168 distinct states, 56 traces violating the release invariant on 6 edges; the fixed variant satisfies it; 5 vacuity probes) and replayed it on the real jar with model-based bounded-exhaustive fault injection: one IOException at each of 142 directory and file operations and at every byte of the .dic (38) and .aff (45) streams, plus two content-driven exceptions and a fault-free baseline: 228 checks, 80 leaking, 0 mismatches with the model. A public-API JUnit test followed; independent checkers reproduced it with their own tests, and it was cut to the one-test repro.

History

#

The open output is a regression from #12834 (f460d612b5e, 2023-11-24), first released in 9.9.0; every release through 10.6.0 and main has it. A closed file left in the caller's temp directory is older (since 6.0.0; 4.8.0-5.5.5 in java.io.tmpdir).

Versions tested6 rows

Introduced by #12834 "hunspell: allow in-memory entry sorting for faster dictionary loading" (Peter Gromov, co-authored and approved by Dawid Weiss, merged 2023-11-24): main f460d612b5e, branch_9x backport 41da5c0b6a9. It moved the temp output's creation into SortingStrategy.offline().start() and its close into finishAndSort(), and left mergeDictionaries(...) outside any try. git tag --contains: 9.9.0-9.12.3 and 10.0.0-10.6.0. On 9.9.0 jars with only the parent's Dictionary.java swapped in, the behaviour is that of 9.8.0. Older layer: since 4.8.0 (LUCENE-5468) a closed temp file is left after a failed load, in java.io.tmpdir until 5.5.5 and in the caller's tempDir from 6.0.0 (LUCENE-6829), when the factory started deleting its own temp directory; so through the factory it was clean from 6.0.0 until 9.9.0.

analysis-common / hunspell Dictionary loading (SortingStrategy.offline, HunspellStemFilterFactory)
Priority
Low, rank 1077: A failure-path IndexOutput and temp-file leak on an already-failing opt-in hunspell Dictionary load, in the offline-sort temp-file class.
Impact class
minor
Impact note
Hits applications that load hunspell dictionaries through the Dictionary(Directory, ...) constructors (offline sorting is what those constructors use) or through HunspellStemFilterFactory (CustomAnalyzer 'hunspellStem'), and only when a load fails after the temp file was created, for example an IOException from the .dic stream or a write error in tempDir (disk full); each failed load holds one file descriptor until garbage collection and, on a caller-supplied persistent tempDir, leaves one small temp file on disk, so an application that keeps retrying a failing load accumulates them; the load itself fails loudly with its original exception, a successful load leaves nothing, and SortingStrategy.inMemory() is not affected.
Summary
You load a hunspell Dictionary with a temp Directory (or through HunspellStemFilterFactory) and the load fails while the .dic entries are being written to the offline-sort temp file, for example because the .dic InputStream throws an IOException, which the constructor documents, or a write to the temp directory fails; you expect the failed constructor to close and delete the temp file it created, as it does on success and at the neighbouring steps. Instead Dictionary calls sortingStrategy.start(), which opens the temp IndexOutput, and then mergeDictionaries(...) with no failure handling, so the output stays open: MockDirectoryWrapper refuses to close ('there are still 1 open files: {dictionary_dat_0.tmp=1}'), and 10 failed HunspellStemFilterFactory.inform() calls leave 10 descriptors open on deleted hunspell_dat_0.tmp files until GC. The open handle is a regression from #12834 (9.9.0), which moved the entry writer out of its try-with-resources; the closed temp file that the direct constructor leaves in a caller-supplied tempDir is older (6.0.0).
