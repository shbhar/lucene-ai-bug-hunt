IndexReader#decRef javadoc says the refCount is unchanged on exception, but a failing final decRef leaves the reader closed at refCount 0

IndexReader.decRef() documents "If an exception is hit, the refCount is unchanged", but when the final decRef() throws (a closed listener or doClose() fails), the reader is left closed at refCount 0, not 1. The code is intended since 4.7.1 (LUCENE-5553); only the javadoc is stale.

The finding in 30 seconds

#

decRef() decrements the count first; at 0 it marks the reader closed and runs doClose(), with the closed listeners notified in a try-with-resources (IndexReader.java:222-227). Nothing puts the count back if either throws, while the javadoc a few lines above (:208-209) says the count is unchanged.

Background: reader reference counting

#
  1. Every IndexReader has a reference count. It is 1 when you open the reader; incRef() adds one and decRef() removes one.
  2. When decRef() takes the count to 0, the reader closes: doClose() releases what it holds, and its closed listeners (registered through getReaderCacheHelper().addClosedListener) are notified, typically to evict cache entries.
  3. close() simply calls decRef(). After the reader is closed, a retried decRef() and most other uses of it throw AlreadyClosedException.
  4. Both doClose() and ClosedListener.onClose are declared to throw IOException.

The finding, step by step

#
  1. You open a DirectoryReader (refCount 1) and register a reader-closed listener whose onClose throws IOException, which the ClosedListener interface allows.
  2. You call decRef() to release your reference, and it throws the listener's IOException.
  3. The javadoc says "If an exception is hit, the refCount is unchanged", so you expect getRefCount() to still be 1 and the reference to still be yours.
  4. Instead getRefCount() is 0 and the reader is closed: a second decRef() throws AlreadyClosedException. A reader whose own doClose() throws ends the same way.
  5. That outcome is right: since 4.7.1 (LUCENE-5553, 2014) a failing final close really closes the reader and still notifies its listeners. The sentence predates that change and was never updated.

Who is affected

#

Code that manages reader references itself (the Expert incRef/decRef API, or close()), sees the final release throw, and then trusts the sentence: it retries decRef() or keeps the reader. A retried decRef() gets an immediate AlreadyClosedException; no wrong result, hang or leak was found. Every release from 4.7.1 to 10.6.0, and main.

Mechanism, terms and numbers479 words

The javadoc of IndexReader#decRef says "If the refCount drops to 0, then this reader is closed. If an exception is hit, the refCount is unchanged." The method decrements first; at 0 it marks the reader closed and runs doClose() with the closed-listener notification in a try-with-resources, and nothing puts the count back if either throws. So after a final decRef() that throws, getRefCount() is 0, the reader is closed, and a retried decRef() throws AlreadyClosedException.

The code is the intended side. The sentence was written in 2009 (LUCENE-2156) together with a "Put reference back on failure" block; LUCENE-5553 (#6615, first released in 4.7.1) removed that block on purpose so that a failing close really closes the reader and still notifies its closed listeners, and left the sentence. The fix is javadoc-only. It affects the documentation in every release from 4.7.1 to 10.6.0 and on main.

The mechanism (main 645d4fe14a20)

#
  1. The javadoc. IndexReader.java:207-213: "Expert: decreases the refCount of this IndexReader instance. If the refCount drops to 0, then this reader is closed. If an exception is hit, the refCount is unchanged." and "@throws IOException in case an IOException occurs in doClose()".
  2. The code (IndexReader.java:215-232): :218-220 throws AlreadyClosedException if the count is already <= 0 (here the count really is unchanged); :222 refCount.decrementAndGet(); :223-227 at 0: closed = true; then try (Closeable _ = this::notifyReaderClosedListeners) { doClose(); }; :228-231 below 0: IllegalStateException ("too many decRef calls"). No line restores the count, so an exception from doClose() or from a listener leaves 0.
  3. Every listener is still called. StandardDirectoryReader.java:668-672 and SegmentReader.java:318-322 notify the listeners through IOUtils.applyToAll, so one that throws does not skip the others; the try-with-resources runs the notification also when doClose() throws (if both throw, the listener's exception is attached to the doClose() one as suppressed). The base notifyReaderClosedListeners() is a no-op (:153-155); only these two readers override it.
  4. Afterwards the reader is closed for good. ensureOpen() throws AlreadyClosedException when the count is <= 0 (:238-241); a retried decRef() hits :218-220; close() is a no-op because closed is already true (:351-356). So most reader operations (for example terms()) fail. A few accessors skip ensureOpen() on purpose and still answer: getRefCount(), "so that callers can see refCount is 0 (reader is closed)" (:159-160), and numDocs() / maxDoc() (BaseCompositeReader.java:141-166, SegmentReader.java:234-243).
  5. Both triggers are legal. ClosedListener.onClose(CacheKey key) throws IOException (:141-146, @lucene.experimental); doClose() is a protected hook declared to throw IOException (:358-359); Lucene's own TestIndexReaderClose uses both a throwing doClose() and throwing listeners.

In the repro

#

An empty commit, DirectoryReader.open (count 1), one closed listener that throws IOException. decRef(): the count goes to 0, closed is set, doClose() succeeds, then the listener throws and decRef() rethrows its IOException. getRefCount() returns 0; the javadoc promises 1.

Exposure and likelihood239 words
  • Who. Code that drives reader reference counting itself through the Expert incRef/decRef API (or close(), which calls decRef()) and, after the final release throws, follows the javadoc: it retries decRef(), or keeps the reader (for example in its own pool) believing it still holds a reference.
  • When. Only when closing a reader throws: a closed listener that throws, a reader subclass whose doClose() throws, or an I/O error while index files are released. All uncommon.
  • What goes wrong. A retried decRef() throws AlreadyClosedException at once, and so do most later reader operations; a few metadata accessors (numDocs(), maxDoc()) skip that check on purpose. No wrong result, hang or extra resource use was found; whatever a failing doClose() did not release stays unreleased whichever way the javadoc reads. The @throws clause names only doClose(), so the javadoc also hides that a listener can be the source.
  • Scope of the repro. It covers one StandardDirectoryReader; composite readers close or decRef() their children in their own doClose() with their own exception handling, which this page does not examine.
  • Default vs opt-in. No configuration changes the behaviour; the text is on a public final method of the core reader class, read by anyone writing reader-lifecycle code.
  • Scale and age. Every release from 4.7.1 (2014) to 10.6.0 and main (a few untagged 8.x releases inferred); the recorded searches found no report of the mismatch.

Why it looks unintended

#
  • Written in 2009 (LUCENE-2156) with a "Put reference back on failure" block that restored the count when doClose() failed; true then.
  • LUCENE-5553 (4.7.1) removed that block on purpose, "close really closes and throws first exc", and left the sentence.
  • Lucene's TestIndexReaderClose expects a close that threw to have really closed the reader: the code is right, the sentence is stale.
The full argument214 words
  • Written for the removed code. LUCENE-2156 (dc3f92e6e58c, Michael McCandless, 2009-12-16, first in 3.1) added the sentence in the same hunk as boolean success = false; try { ... doClose(); success = true; } finally { if (!success) { // Put reference back on failure refCount.incrementAndGet(); } }.
  • The change that made it false was deliberate. LUCENE-5553 / #6615, "IndexReader#ReaderClosedListener is not always called on IndexReader#close()" (Simon Willnauer, 2014-03-25), replaced the put-back with closed = true and unconditional listener notification. In the issue Simon Willnauer wrote that they "dropped putting the reference back since this should really just close everything and hand the exception back", and Michael McCandless gave "+1 for the patch and to change to 'close really closes and throws first exc' behavior". Nobody in the issue mentions the javadoc.
  • The new behaviour is tested. TestIndexReaderClose.testCloseUnderException, added by LUCENE-5553, expects IllegalStateException from close() when doClose() or a listener throws (TestIndexReaderClose.java:89), may then call close() again, which must not throw (:99-101), and checks that every counting listener was notified despite the failure (:102): "close really closes".
  • Later edits kept the sentence. LUCENE-8215 (2018), the 2020 reformat (which only re-wrapped it), #14302 (2025, which renamed the try-with-resources variables) and #15002 (2025) all touched decRef.
The devil's-advocate check156 words

Strongest case for "not a defect" (the study's intended-behaviour devil's advocate and the credibility audit): (1) the sentence can be read as covering only the already-closed pre-check (IndexReader.java:218-220), where the count really is unchanged; (2) it is a cosmetic nit in an Expert API: the behaviour is intended, a caller who trusts the sentence and retries gets AlreadyClosedException at once, and no complaint since 2014 was found.

Why it fails. (1) History rules out the narrow reading: the sentence was written in the same hunk as the put-back block it described, and the @throws line under it names doClose(), the path that block covered. (2) It is a concrete, false statement about the reader's state after an exception, on the method whose callers must write the exception handling, and it is read exactly then; the fix is two javadoc lines with no behaviour change. Upstream may still call it a cosmetic javadoc cleanup.

Suggested fix

#

Recommended A. Correct the sentence and the @throws clause (recommended)

Javadoc only: say that the reader stays closed (refCount 0) even if closing it throws, and name closed listeners in @throws. No behaviour change. Validated with gradle: format check and javadoc render pass; the same test expecting 0 and the closest reader-close suites pass.

   * Expert: decreases the refCount of this IndexReader instance. If the refCount drops to 0, then
-  * this reader is closed. If an exception is hit, the refCount is unchanged.
+  * this reader is closed. It stays closed (refCount 0) even if closing it throws an exception.
   *
-  * @throws IOException in case an IOException occurs in doClose()
+  * @throws IOException in case an IOException occurs in doClose() or in a closed listener

A. Correct the sentence and the @throws clause (recommended) (validated by the checks)

#

Say that the reader stays closed (refCount 0) even if closing it throws, and name closed listeners in @throws. It makes no promise about closed listeners, which not every reader keeps or notifies itself.

   * Expert: decreases the refCount of this IndexReader instance. If the refCount drops to 0, then
-  * this reader is closed. If an exception is hit, the refCount is unchanged.
+  * this reader is closed. It stays closed (refCount 0) even if closing it throws an exception.
   *
-  * @throws IOException in case an IOException occurs in doClose()
+  * @throws IOException in case an IOException occurs in doClose() or in a closed listener

Trade-offs

  • No behaviour change. It tells callers what they need after a failed final release (the reader is gone: do not retry, do not reuse).
  • No listener promise on purpose: the base notifyReaderClosedListeners() is a no-op, only StandardDirectoryReader and SegmentReader override it, and readers such as MultiReader return a null cache helper or delegate to a sub-reader. An earlier draft said "its closed listeners are still notified"; it was dropped after review.

What the checks validated

  • Gradle, scratch worktree of 645d4fe14a20, seed DEADBEEF, this exact wording: :lucene:core:checkGoogleJavaFormat and :lucene:core:renderJavadoc pass, and the rendered IndexReader.html shows the new text.
  • The minimal test in its corrected form (expecting 0) together with TestIndexReaderClose (3 tests) and TestReaderClosed (1 test): 5 tests pass with assertions on; the corrected test also passes with assertions off.
  • The minimal test as written was re-run with the fix and still fails (expected:<1> but was:<0>), as it must for a comment-only change.
  • Not run: gradlew check or the whole core test suite (the change is inside a javadoc comment).

B. Delete the sentence only (validated by the checks)

#

Drop "If an exception is hit, the refCount is unchanged." and leave the rest.

-  * this reader is closed. If an exception is hit, the refCount is unchanged.
+  * this reader is closed.

Trade-offs

  • The smallest change that removes the false promise; it leaves @throws incomplete and does not tell callers what state the reader is in after a failure.

What the checks validated

  • Same worktree: :lucene:core:checkGoogleJavaFormat passes. Nothing else was run (a comment-only change).

Not an option: restore the count (validated by the checks)

#

Putting the reference back on failure would make the sentence true, but it would bring back the pre-4.7.1 state that LUCENE-5553 removed on purpose: a partly closed reader that still looks open, so a retried decRef() would run doClose() again (read from the 4.7.0 code). Related: facet TaxonomyReader.decRef still puts the reference back on failure, and its javadoc makes no promise either way; a different class, not part of this finding.

Trade-offs

  • Reverts a deliberate design decision; not proposed.

Downstream note

Downstream code that pools or wraps readers should treat any failed final decRef() or close() as closed; the Lucene.NET port carries the same sentence.
