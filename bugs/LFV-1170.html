A stored field built from a StringBuilder makes addDocument throw since 9.6.0

Since 9.6.0, a stored field whose value is a StringBuilder (or any CharSequence other than String) makes IndexWriter.addDocument throw IllegalStateException: Cannot store value of type class java.lang.StringBuilder, although the public StoredField(String, CharSequence, FieldType) constructor accepts it and 9.5.0 stored it. Only that document is rejected; toString() avoids it.

The finding in 30 seconds

#

StoredField and Field have public constructors that take any CharSequence. Since 9.6.0 the indexing chain stores what storedValue() returns, and Field.storedValue() treats only an exact String as text.

  1. You add a document with new StoredField("f", new StringBuilder("x"), StoredField.TYPE). This public (Expert) constructor takes any CharSequence. No setting is needed: a plain new IndexWriterConfig() with the default codec fails.
  2. You expect the field to be stored and read back as "x", as Lucene 7.7.0 to 9.5.0 did.
  3. To store the field, the indexing chain asks Field.storedValue() for the value. That method picks the stored type from the value's Java class and has a text case only for String: a StringBuilder matches no case and reaches the default case, which throws.
  4. You get IllegalStateException: Cannot store value of type class java.lang.StringBuilder from addDocument, with assertions on and off, on 9.6.0 to 10.6.0 and main. A CharsRef value, or new Field("t", new StringBuilder("x"), TextField.TYPE_STORED), fails the same way.
  5. Only that document is rejected: the writer stays open, nothing is corrupted, and passing value.toString() instead avoids the error.

Who is affected

#

Code that passes a StringBuilder, CharsRef or its own CharSequence to StoredField(String, CharSequence, FieldType) (Expert) or to Field(String, CharSequence, ...) with a stored type such as TextField.TYPE_STORED. Default settings suffice; every such document fails, loudly. String values and indexed-only fields are not hit.

Mechanism, terms and numbers454 words

StoredField(String, CharSequence, FieldType) and Field(String, CharSequence, IndexableFieldType) are public constructors that accept any CharSequence. Since 9.6.0 (#12116), the indexing chain stores what IndexableField.storedValue() returns; for a Field that is Field.storedValue(), which picks the stored type from the value's runtime class (on main a switch with arms for Integer, Long, Float, Double, BytesRef, StoredFieldDataInput and exactly String, Field.java:608-624 at 5adff78bb168). A StringBuilder, CharsRef or an application's own CharSequence reaches the default arm, so IndexWriter.addDocument throws IllegalStateException: Cannot store value of type class java.lang.StringBuilder for every such document, with assertions on and off. Up to 9.5.0 Lucene's default stored-fields writer stored stringValue(), which converts any CharSequence, and the same document was stored and read back. The exception comes before the aborting stored-fields write, so only the document is rejected and the writer stays usable. Affected: 9.6.0 to 10.6.0 and main.

The mechanism (main 5adff78bb168, lucene/core/src/java/org/apache/lucene/)

#
  1. Both constructors keep any CharSequence. StoredField(String, CharSequence, FieldType) (document/StoredField.java:147-157) calls Field(String, CharSequence, IndexableFieldType) (document/Field.java:230-257), which checks only for nulls and for a type that is neither indexed nor stored, and keeps the value as is (fieldsData = value, :255). stringValue() turns any CharSequence into a String (:263-270).
  2. Storing asks storedValue(). For a stored field, IndexingChain.invertAndStore calls field.storedValue() (index/IndexingChain.java:1492, after inverting the field if it is also indexed) and writes what it returns.
  3. Only String is text. Field.storedValue() (document/Field.java:608-624) switches on the runtime class of the value: Integer, Long, Float, Double, BytesRef, StoredFieldDataInput, String (:620). Everything else reaches default -> throw new IllegalStateException("Cannot store value of type " + fieldsData.getClass()) (:621-622, the fix site).
  4. Only the document is rejected. The throw comes before the aborting try around storedFieldsConsumer.writeField (IndexingChain.java:1504-1509). A probe on main added three such documents (a StringBuilder and a CharsRef through StoredField, a StringBuilder through Field with TextField.TYPE_STORED): each threw, then isOpen=true tragic=null, and a following String document was added and read back. As with any non-aborting per-document failure, the rejected document is marked deleted internally (index/DocumentsWriterPerThread.java:283-306, :392-414).

Before 9.6.0

#

Each stored-fields writer chose the type itself; Lucene's default one took numericValue(), else binaryValue(), else stringValue() (Lucene90CompressingStoredFieldsWriter.writeField, :270-300 at the parent of 96136b42821). So a StringBuilder was stored as text. #12116 moved that choice into Field.storedValue() and kept a text arm only for String.

Not hit

#

String values (all sugar classes such as TextField, StringField and StoredField(String, String) take a String), and indexed-only CharSequence fields: those are tokenized from stringValue() and never call storedValue().

Exposure and likelihood135 words
  • Who. Application code that hands a non-String CharSequence to one of the two CharSequence constructors with a stored type, for example text assembled in a StringBuilder, or a CharsRef.
  • Default vs opt-in. No setting is involved: a plain new IndexWriterConfig() with the default codec fails (executed, probe). The trigger is an opt-in call shape: the CharSequence overloads (the StoredField one is marked Expert) with a value that is not a String.
  • Effect. Every such document is rejected with IllegalStateException. Nothing is corrupted or lost without notice, and the writer stays usable; value.toString() avoids it.
  • Scale. None needed: one document with one field.
  • Likelihood. Rare: the developer sees the exception on the first such document, and our searches found no report in the three and a half years since 9.6.0. Priority Low.

Why it looks unintended

#
  • StoredField's constructor documents @param value CharSequence value and throws only for null arguments; storing is that class's only job.
  • IndexableField.storedValue() must return a non-null value for a stored field; Field throws instead, for a value its own constructor accepted.
  • Lucene 7.7.0 to 9.5.0 stored these values; #12116, CHANGES.txt and MIGRATE.md announce no restriction.
The full argument184 words
  • Contract. StoredField(String, CharSequence, FieldType): "@param value CharSequence value", "@throws IllegalArgumentException if the field name, value or type is null" (StoredField.java:151, :153). Field(String, CharSequence, IndexableFieldType) documents @throws only for nulls and for invalid type combinations (Field.java:236-238). IndexableField.storedValue() "must return a non-null value if the field stored" (index/IndexableField.java:74-78).
  • History. 7.7.0, 8.11.4 and 9.5.0 store the value (executed). #12116's commit message lists its goals: find a missing value early, and separate the stored value from the doc-values value; nothing about dropping CharSequence values. On the PR, Robert Muir described it as moving "type-guessing" into "the one place that should be doing it, which is the generic Field.java" (#12116 comment, 2023-01-27). CHANGES.txt (lucene/CHANGES.txt:3623-3625) says only "Introduce IndexableField#storedValue() to expose the value that should be stored to IndexingChain without needing to guess the field's type"; MIGRATE.md has no entry.
  • Tests. No test asserts the rejection: the message appears only in Field.java, and no core or test-framework test stores a non-String CharSequence (the finder's grep).
  • Accepted, then rejected. The value passes the constructor and fails only at addDocument.
The devil's-advocate check199 words

The strongest case for "intended": both constructors are Expert; Field's constructor javadoc still says "Create field with String value" and "@param value string value" (Field.java:231, :234); the class javadoc lists text values as "String, Reader or pre-analyzed TokenStream" (:53-54); StoredValue's only text type is STRING, built from a String (StoredValue.java:32-47, :95-98); the overloads came from a Solr read-side change (SOLR-12885, c651cbfd9a8), and in 2019, reviewing LUCENE-8805 (#9849), Adrien Grand noted that Solr's document fetcher can "pass the String directly" instead of wrapping it in a ByteArrayUtf8CharSequence. The failure is loud, the workaround trivial, and our searches found no report in the three and a half years since 9.6.0.

Why it fails: StoredField's own javadoc promises a CharSequence value for a class whose only job is storing, nothing documents a restriction, and an unannounced change in a minor release turned a working call into an exception. In our reading the accept-then-reject behaviour is what needs fixing, but narrowing or documenting the API instead of adding the arm (Suggested fix, options B and C) is a legitimate maintainer choice. The argument bears on likelihood, hence priority Low.

Suggested fix

#

Recommended Store any CharSequence as its String (fix A)

Add one case after the String case in Field.storedValue(): case CharSequence cs -> new StoredValue(cs.toString());. It restores what Lucene's default stored-fields writer did up to 9.5.0. The repro passes with assertions on and off, and the closest suites (65 classes, 525 tests, 0 failures, 28 skipped by their suites) pass.

      case String s -> new StoredValue(s);
      case CharSequence cs -> new StoredValue(cs.toString());
      default ->
          throw new IllegalStateException("Cannot store value of type " + fieldsData.getClass());

Store any CharSequence as its String (fix A) (validated by the checks) (recommended)

#

One arm after case String s in Field.storedValue() (Field.java:620). The text is copied into a String when the document is added, as stringValue() did for the stored-fields writer before 9.6.0.

      case String s -> new StoredValue(s);
      case CharSequence cs -> new StoredValue(cs.toString());
      default ->
          throw new IllegalStateException("Cannot store value of type " + fieldsData.getClass());

Trade-offs

The arm must stay after case String s: a String is a CharSequence, and Java rejects a case label dominated by an earlier one. It relies on toString() returning the text, as stringValue() already does. The existing stored-string length check (IndexingChain.java:1495-1502) then applies to these values too. The repro passes unchanged as the regression test.

What the checks validated

  • Gradle in a scratch worktree at 5adff78bb168, seed DEADBEEF: the repro fails without the fix (assertions on and off) and passes with it (on and off).
  • With the fix: the repro, all of org.apache.lucene.document.*, TestIndexableField, TestFieldsReader, TestStoredFieldsConsumer, TestSortingStoredFieldsConsumer and TestLucene90StoredFieldsFormat: 65 classes, 525 tests, 0 failures, 28 skipped by their suites. :lucene:core:checkGoogleJavaFormat passes.

Narrow the API instead (not built)

#

Reject a non-String CharSequence for a stored type in the constructors, or deprecate the CharSequence overloads (main is 12.0, where deprecated APIs are being removed).

Trade-offs

Fails at construction instead of at addDocument, but it breaks callers that store such values; deprecating the overloads would also drop indexed-only CharSequence fields, which work today. The regression test would have to expect the exception.

Document the restriction only (not built)

#

A javadoc line on both constructors saying a stored value must be a String.

Trade-offs

Smallest change, but the constructors still accept what addDocument rejects.

Downstream note

#

Downstream, Solr met the same 9.6.0 change in two of its own field classes (an anonymous Field subclass in EnumFieldType and its IndexableField LargeLazyField) and adapted them on its side by overriding or implementing storedValue() (SOLR-16799), without a report to Lucene; other downstream products were not surveyed.

How it was found

#

A proof-obligation audit of Field's contract: a public constructor that accepts any CharSequence for a stored type obliges storedValue() to return a value for it. The switch in storedValue() covers only String; a one-document public-API JUnit test then witnessed the exception.

The method in full104 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The finder read the CharSequence constructors of Field and StoredField against IndexableField.storedValue()'s obligation ("must return a non-null value if the field stored") and checked which runtime classes storedValue() handles. Every non-String CharSequence falls to the default arm.
  • The finder then wrote a public-API JUnit test that fails on main with assertions on and off and on the 10.6.0 and 9.6.0 jars, and passes on 9.5.0.
  • An independent reproducer, two executed cross-model reviews, a devil's-advocate verifier and an adjudication reproduced it with their own tests ("Prior reports, history and checks").
