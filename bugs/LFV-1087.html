The documentation front page links benchmark-jmh javadocs that no build renders

Since 10.6.0 the documentation front page lists 32 modules under "API Javadocs", but only 31 have javadocs: the benchmark-jmh link leads to a missing page. The Java port of the documentation build lists modules whose site-javadoc task is disabled; the Groovy build it replaced skipped them.

The finding in 30 seconds

#

One generated line on the documentation front page: the "API Javadocs" list links a module whose javadocs the build deliberately skips.

Background: how the front page lists modules

#
  1. Each published Lucene module gets a Gradle task, renderSiteJavadoc, that writes its javadocs into the documentation tree, for example docs/core/.
  2. A module keeps its javadocs off the site by disabling that task. Luke was taken off this way in 2021 (PR #120); benchmark-jmh disables it too: "No special javadocs for JMH benchmarks."
  3. The createDocumentationIndex task writes the front page. Its "API Javadocs" list should have one link per module whose javadocs are written.

The finding, step by step

#
  1. You open the Lucene 10.6.0 documentation front page (docs/index.html in the binary release, or a documentation build of main) and look at "API Javadocs": 32 modules, one more than in 10.5.2. The new one is benchmark-jmh, "Lucene JMH micro-benchmarking module".
  2. You expect each link to open that module's javadocs, as the other 31 do, or the module not to be listed, as in 10.5.2.
  3. Instead benchmark-jmh/index.html does not exist. The module's build turns its site javadocs off ("No special javadocs for JMH benchmarks"), the build log shows that task SKIPPED, and the docs have no benchmark-jmh/ folder.
  4. Why: the code that writes the list keeps every module that has a renderSiteJavadoc task and never asks whether the task is enabled. The Groovy original checked ?.enabled; the check was lost when the documentation build moved to Java (#15350, in 10.6.0 via #16592).
  5. Adding && t.getEnabled() to that filter removes exactly this one line from the page; nothing else changes.

Who is affected

#

Every reader of the 10.6.0 documentation front page, and of documentation builds of main, branch_11x and branch_10_6, who clicks benchmark-jmh gets a missing page. Nothing else breaks: no code, API or index effect, and no setting is involved. It is one link of 32, to an internal micro-benchmark module, so priority is low.

Mechanism, terms and numbers391 words

The documentation front page (docs/index.html) has an "API Javadocs" list with one link per module. In 10.6.0 it lists 32 modules; 10.5.2 listed 31. The extra entry, benchmark-jmh/index.html on line 59, leads to a page that a standard documentation build does not write: lucene/benchmark-jmh/build.gradle disables the module's renderSiteJavadoc task on purpose, and the 10.6.0 binary archive has no docs/benchmark-jmh/ folder.

The list comes from MarkdownTemplateTask.withProjectList() in DocumentationConfigPlugin. Its javadoc says it lists "all subprojects with javadocs", but its filter keeps every :lucene subproject that has a task named renderSiteJavadoc, enabled or not. The Groovy version it replaced (up to 10.5.2) kept only subprojects whose task is enabled. #15350 dropped that check when it moved the documentation scripts to Java (main, 2025-10-22); the backport #16592 brought it into 10.6.0. benchmark-jmh has the task at all only because its exclusion from the published projects is spelled :lucene:benchmarks-jmh, so it never matches; until the port the enabled filter hid that.

It is a documentation defect only: code, APIs and indexes are not affected. The fix is one condition, && t.getEnabled(), which removes exactly the benchmark-jmh line.

Mechanism (main e1faeba08bde)

#
  1. DocumentationConfigPlugin.java:256: createDocumentationIndex calls task.withProjectList(), which fills ${projectList} under "## API Javadocs" in lucene/documentation/src/markdown/index.template.md:65-67.
  2. DocumentationConfigPlugin.java:344-347, the method's javadoc: adds a property "projectList" containing all subprojects with javadocs as markdown bullet list.
  3. DocumentationConfigPlugin.java:355-363, the filter: .filter(p -> p.getTasks().matching(t -> t.getName().equals("renderSiteJavadoc")).stream().findAny().isPresent()). It checks that the task exists, not that it is enabled. Lines 370-385 turn each kept module into **[name](path/index.html):** description.
  4. RenderJavadocPlugin.java:143-150 registers renderSiteJavadoc for every published project except :lucene:luke; it writes to the documentation root plus the module path (:180-185).
  5. RegisterBuildGlobalsPlugin.java:111-115 excludes ":lucene:misc:native", ":lucene:spatial-test-fixtures", ":lucene:benchmarks-jmh" from the published projects. The module is lucene:benchmark-jmh (settings.gradle:67), so the exclusion never matches and the module gets the task.
  6. lucene/benchmark-jmh/build.gradle:40-49 disables renderSiteJavadoc and renderJavadoc ("// No special javadocs for JMH benchmarks.", it.enabled = false). The task is SKIPPED and writes nothing.
  7. The Groovy original, 10.5.2 gradle/documentation/markdown.gradle:152-155, same javadoc: def projects = productProject.subprojects.findAll{ it.tasks.findByName('renderSiteJavadoc')?.enabled }.

A Gradle build model over all 32 :lucene subprojects that have the task: listed 32, rendered 31, listed-not-rendered [benchmark-jmh], rendered-not-listed [], on main, branch_11x and branch_10_6. benchmark-jmh is the only module with the task disabled, so it is the only wrong entry.

Why it looks unintended

#
  • The method's own javadoc says the list holds "all subprojects with javadocs"; benchmark-jmh turns its javadocs off on purpose.
  • The Groovy build up to 10.5.2 listed only modules whose task is enabled; the Java port (#15350) dropped that check without saying so.
  • The maintainer fixed and backported a sibling wrong link on the same page from the same port (#16939).
The full argument211 words
  • The contract: DocumentationConfigPlugin.java:345: "all subprojects with javadocs". benchmark-jmh/build.gradle:43: "No special javadocs for JMH benchmarks."
  • Disabling the task is how a module leaves the site. PR #120 (LUCENE-9947): "This excludes Javadocs of luke module from the documentation site by explicitly disable \"renderSiteJavadoc\" task for it. While removing the link to javadocs, ...". The Groovy ?.enabled filter (since LUCENE-9321, 06df50e759a, 2020) is what made that work.
  • A port, not a redesign. #15350 and #16592 carried over the link format, descriptions, core styling and sort keys, minus one dead sort key (the Groovy sort also put a solrj module right after core, 10.5.2 markdown.gradle:157; Lucene has no such module). The only change to which modules are listed is the dropped ?.enabled. No PR text, commit message, CHANGES or MIGRATE entry mentions which modules are listed.
  • No test covers it, and, as Uwe Schindler pointed out on #16939, #14905 removed the link checker, so "the markdown files on top level were no longer checked for incorrect links". That is why it went unnoticed, not the defect.
  • Precedent: #16939 ("We should fix this, but respin not needed."), the wrong File Formats link on the same page from the same port, fixed by #16941 and backported to branch_10_6.
The devil's-advocate check128 words

Strongest case for "intended": the port redefined "rendered" as "has the task". In the Java build luke is kept off the site by not registering the task at all (RenderJavadocPlugin.java:145), and #15350 allowed "some minor tweaks here and there". A second reading: the real cause is the old :lucene:benchmarks-jmh typo.

Why it fails: the method's javadoc still says "with javadocs", benchmark-jmh's build still disables the task to keep its javadocs out, nothing announces a change, and no reading makes a link to a folder the same build never writes intended. The typo dates from 10.0.0 and was harmless to the front page until the port dropped the filter (10.0.0 and 10.5.2 list 31 modules); it offers a second fix site, not an intended behaviour.

Suggested fix

#

Recommended Keep only modules whose renderSiteJavadoc task is enabled (validated)

Add && t.getEnabled() to the renderSiteJavadoc filter in withProjectList(). Validated on main: the rebuilt page loses only the benchmark-jmh line, the test passes with assertions on and off, and build-infra's format, lint and forbidden-API checks pass. The same diff applies to branch_11x and branch_10_6 (on branch_10_6 with an 8-line offset).

Trade-offs

None seen in the recorded builds. The enabled flag is set while the build is configured (configureEach in benchmark-jmh/build.gradle); the list is computed later, when createDocumentationIndex resolves its binding, so the check sees the final value, as the regenerated page shows. Like the Groovy ?.enabled, getEnabled() reads only that flag: an enabled task skipped for another reason (an onlyIf condition, say) would still be listed. On main today that changes nothing: with the fix, listed = rendered = 31 in the build model.
