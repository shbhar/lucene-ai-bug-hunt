A deleteAll() that overlaps addIndexes erases the added fields from the writer's schema, so a later commit cannot be opened by an IndexWriter

If deleteAll() runs while another thread's addIndexes copies files, the added segment survives but the writer forgets its fields. A later document can then re-type such a field, the commit succeeds, and every later new IndexWriter throws; only OpenMode.CREATE, which drops every document, opens it.

The finding in 30 seconds

#

addIndexes(Directory...) registers the incoming fields in the writer-wide schema, copies the files without holding the IndexWriter lock, and only then publishes the segment. deleteAll() can run in between: it clears the schema, but the segment is published afterwards and survives, with fields the writer no longer knows.

How IndexWriter keeps one schema per field, in one minute

#
  1. The writer keeps one schema per field name for the whole index (FieldNumbers): its number and its doc-values type, for example f = NUMERIC. A document that gives f another type is rejected with IllegalArgumentException.
  2. addIndexes(Directory...) adds the segments of another index by copying their files. Before the copy it registers their fields in that schema, which is also its check that they fit.
  3. deleteAll() drops every segment and clears the schema, as if the index were re-created with OpenMode.CREATE; afterwards f may take any type.
  4. A new IndexWriter rebuilds the schema from all segments on disk and refuses an index in which one field has two types.

The finding, step by step

#
  1. Thread A calls addIndexes(src); src holds one document whose field f has NUMERIC doc values. While A copies the files, the main thread calls deleteAll(). The writer reports deleteAll as sequence number 3 and addIndexes as 4.
  2. Then add one document with SortedDocValuesField("f", "x") and close() the writer, which commits.
  3. You expect one of the two orders. deleteAll first: the added document stays, f stays NUMERIC and the SORTED document is rejected. addIndexes first: its document is deleted and the SORTED one is fine. Either way the commit holds 1 document and opens again.
  4. Instead both happen: the added document survives and the SORTED document is accepted. The commit holds 2 segments, f NUMERIC in one and SORTED in the other, and new IndexWriter(dir, new IndexWriterConfig()) throws IllegalArgumentException: cannot change field "f" from doc values type=NUMERIC to inconsistent doc values type=SORTED.
  5. Nothing failed at commit time and CheckIndex reports the index clean. Only OpenMode.CREATE opens a writer, and it drops every document.

Who is affected

#

Applications that call deleteAll() (or delete a MatchAllDocsQuery) while another thread's addIndexes runs, then index a document that re-types an added field. Default configuration, no scale: the window is the whole file copy. Rare, but the commit succeeds silently and leaves an index no writer opens without dropping it.

Mechanism, terms and numbers563 words

IndexWriter.addIndexes(Directory...) registers every incoming field in the writer-wide schema (globalFieldNumberMap.addOrGet, IndexWriter.java:3177-3181 at 5adff78bb168) and copies the segment files (:3183) without holding the IndexWriter lock; only then does it publish the copied segments under synchronized (this) (:3194-3210), without registering or checking the fields again. deleteAll() clears that schema under the same lock (globalFieldNumberMap.clear(), :2800) and waits for running merges, not for an addIndexes(Directory...) call that is copying. A deleteAll() in that window therefore leaves a published segment whose fields the writer no longer knows. A later document can register one of them with another doc-values type; the writer accepts it and the commit succeeds, but the next new IndexWriter rebuilds the schema from every segment (:1274) and throws IllegalArgumentException: cannot change field "f" from doc values type=NUMERIC to inconsistent doc values type=SORTED. Only OpenMode.CREATE, which drops every document, opens a writer on it. addIndexes(CodecReader...) has the same gap between its merge and its publication (:3350-3368). Default configuration, public API, every release since 4.2.0 (2013). The fix registers the incoming fields again inside the publication block.

Step by step

#
  1. addIndexes registers f as NUMERIC. The code comment says this registration is its schema check (:3179-3180).
  2. deleteAll runs to completion while the files are copied: it drops all segments, then clears the schema. Its stop-the-world covers indexing threads (lockAndAbortAll) and merges, including the merges of addIndexes(CodecReader...) (runningAddIndexesMerges, :2849); an addIndexes(Directory...) call that is copying is in neither.
  3. addIndexes publishes the copied segment. It survives deleteAll (it is added after the clear), but the schema has no f: getFieldNames() returns [] (supplementary probe).
  4. The SORTED document registers f afresh (field number 0) and is accepted. The commit holds f as NUMERIC (number 1) in the copied segment and SORTED (number 0) in the new one (probe).
  5. A new IndexWriter rebuilds the schema from every segment (getFieldNumberMap, :1267-1278, addOrGet at :1274); FieldNumbers.addOrGet (FieldInfos.java:415) rejects the second type (FieldInfo.verifySameDocValuesType, FieldInfo.java:297).

addIndexes(CodecReader...) has the same shape: its merge registers the incoming fields, and the merged segment is published later in a separate synchronized (this) block (:3350-3368) without registering again. deleteAll waits for that merge (LUCENE-9309, #10349) but not for the gap between its end and the publication; a two-method test (one per overload) fails for both on main 5adff78bb168 (assertions off) and earlier on 645d4fe14a20, and passes for both with the fix (supplementary probe).

Exposure and likelihood533 words
  • Who is hit. An application that calls deleteAll(), or deleteDocuments(MatchAllDocsQuery) (which IndexWriter.java:1886-1889 routes to deleteAll()), on one thread while another thread's addIndexes(Directory...) is copying files, or while an addIndexes(CodecReader...) is between its merge and its publication. For the hard failure it then indexes a document that gives one of the added fields another doc-values type; deleteAll's javadoc says doc-values types "are cleared" (:2739), so an application that wipes an index to re-define its schema is the natural case.
  • Default vs opt-in. Default IndexWriterConfig, codec, directory, merge policy and ConcurrentMergeScheduler; public API only.
  • Scale and timing. No scale is needed. The addIndexes(Directory...) window is the whole file copy, so it grows with the source index. Without any hook, a loop built to overlap the two calls (4,000-document source, assertions off, 400 rounds each) lost the schema in 39 of 400 rounds for addIndexes(Directory...) and 4 of 400 for addIndexes(CodecReader...) (a supplementary stress run on main a9779ef3c193, not the repro). The loop starts both threads together and varies a short spin delay per round, so it shows the window is reached without a hook, not how often an application would hit it.
  • Silent, then lasting. Nothing fails when the document is added or committed. Afterwards no IndexWriter opens the index with the default OpenMode (CREATE_OR_APPEND), and by reading the code APPEND takes the same path; OpenMode.CREATE opens it but drops every document. Readers still open the commit (2 documents), but f has two doc-values types across segments, so no single sort type fits every segment: a sort on f as a number throws IllegalStateException: unexpected docvalues type SORTED for field 'f' (expected=NUMERIC), and by reading a string sort would fail on the NUMERIC segment. CheckIndex at its default level reports the index clean. A merge of the two segments in the still-open writer (forceMerge(1)) is a tragic event: the writer closes itself with the same IllegalArgumentException (supplementary probe re-run on 5adff78bb168; that run reports 1 of its 5 cases failed because the test framework charged the next case with the merge thread's uncaught exception from the forceMerge case, the same tragic IllegalArgumentException; every case printed its full output).
  • Without the re-typing document the effect stays inside the open writer and ends when it is reopened: getFieldNames() (@lucene.experimental) omits the added fields, and updateNumericDocValue(term, "f", ...) is rejected with "Can't update [NUMERIC] doc values; the field [f] doesn't exist." (same probe).
  • Not only doc-values types. An earlier test with an indexed field whose index options change (DOCS to NONE) failed the same way at the reopen, for both overloads ("cannot change field \"f\" from index options=DOCS to inconsistent index options=NONE", main a9779ef3c193).
  • Bound. Unaligned field numbers alone (new names taking the copied segment's numbers) do not corrupt data: forceMerge(1) keeps every value with its field and a new writer opens. The damage needs a schema conflict.
  • How likely. Rare: wiping an index while adding another one into it, then re-typing an added field, is an unusual sequence, and no user report was found. But the window is not a few statements; it is the whole copy.

Why it looks unintended

#
  • IndexWriter is "completely thread safe" (IndexWriter.java:167-168), and deleteAll's javadoc expects concurrent addIndexes callers, naming only MergeAbortedException for them.
  • Sequence numbers put deleteAll (3) before addIndexes (4), so f must stay NUMERIC; neither legal order leaves an unopenable commit.
  • A field "never changes DV type, even across segments / IndexWriter sessions" (FieldInfos.java:358-360).
The full argument289 words
  • Thread safety. Class javadoc, IndexWriter.java:167-168: "IndexWriter instances are completely thread safe, meaning multiple threads can call any of its methods, concurrently." The only "no other threads" precondition is on close() (:1359); the test closes after the second thread has finished.
  • Effective order. Each change returns a sequence number "which expresses the effective order in which each change was applied" (:117-118). Here deleteAll (3) precedes addIndexes (4).
  • deleteAll. It clears doc-values types, is "equivalent to creating a new IndexWriter with OpenMode#CREATE", and for other threads running addIndexes(CodecReader[]) names one consequence: "they may receive MergePolicy.MergeAbortedExceptions" (:2737-2745). Its first version (64a55ede8b5, LUCENE-1705, 2009) said the same for "any of the addIndexes methods".
  • The schema rule. FieldInfos.java:358-360: "to enforce that a given field never changes DV type, even across segments / IndexWriter sessions". addIndexes relies on its registration as the check: "This will throw exceptions if any of the incoming fields has an illegal schema change" (IndexWriter.java:3179-3180).
  • Tests. TestDocValuesIndexing.testMixedTypesViaAddIndexes (:592) and testIllegalTypeChangeAcrossSegments (:648) assert that a type conflict with an added or earlier segment is rejected; testTypeChangeAfterDeleteAll (:690), testTypeChangeAfterCommitAndDeleteAll (:705) and testTypeChangeAfterCloseAndDeleteAll (:671) assert that after deleteAll a field may change from NUMERIC to SORTED. The race applies deleteAll's permission to a segment that survives deleteAll. TestIndexWriterDelete.testDeleteAllNoDeadLock (:326) runs deleteAll concurrently with indexing on purpose.
  • History. LUCENE-8785 (#9829, fixed in 7.7.2 and 8.2.0) fixed "potentially broken field attributes in the IndexWriter when IndexWriter#deleteAll is called while actively indexing" as a bug (lucene/CHANGES.txt:6400-6402). On java-user@ (2014-05-22, "IndexWriter.addIndexes() multithread correct?") Uwe Schindler answered that addIndexes is "thread safe, like all other methods in IndexWriter".
The devil's-advocate check302 words

The argument: concurrent deleteAll has no defined semantics; it is a stop-the-world call, and users who need a clean slate should close the writer and open one with OpenMode.CREATE. In the lucene-solr#2088 review (2020) rmuir asked whether FieldNumbers.clear() is safe while another thread indexes; msfroh and s1monw answered that deleteAll stops the world (IW lock, all DWPTs locked, merges aborted), and s1monw added that they had asked to remove deleteAll and would rather have users re-create the index. mikemccand proposed a javadoc warning that concurrent operations "may or may not be deleted, i.e. the behavior of such concurrent operations are not defined / predictable". Open #6070 asks to "define the allowed concurrent behavior eg when an app calls deleteAll while other threads are indexing".

Why it fails: the warning was never added, and even as proposed it allows either outcome for the overlapping operation, not a commit that the next writer refuses to open. The stop-the-world covers indexing threads and merges; addIndexes(Directory...) registers and copies outside both, so the 2020 safety argument does not reach this path. deleteAll is public, documented and not deprecated, its javadoc expects concurrent addIndexes callers, and in the same thread mikemccand wrote "I think we should fix its bugs instead!" (2020-12-01). The re-typing document is allowed after deleteAll (the tests above); the writer's own schema check, which in the reported order should reject it, accepts it. One point stands: thread safety alone does not promise a particular outcome for a deleteAll and an addIndexes that overlap. The claim is narrower: no order, and no outcome a maintainer might call undefined but legal, should leave a commit, written by the writer itself, that the next writer refuses to open. Two executed reviews by another model family (OpenAI GPT-5.6) and an intended-behaviour verifier rated the intended-behaviour argument weak.

Suggested fix

#

Recommended Register the incoming fields again under the publication lock (validated on the race tests)

Register the incoming fields again inside the synchronized (this) publication block of both addIndexes overloads (registerSchema(infos) before reserveDocs, +16 lines). deleteAll clears under the same lock, so it can no longer slip in between; the test and the gradle org.apache.lucene.index.* selection pass. LFV-124's fix edits the same block and also closes the Directory case.

// in both publication blocks, right before reserveDocs(...):
registerSchema(infos);

private void registerSchema(List<SegmentCommitInfo> infos) throws IOException {
  assert Thread.holdsLock(this);
  for (SegmentCommitInfo info : infos) {
    for (FieldInfo fi : readFieldInfos(info)) {
      globalFieldNumberMap.addOrGet(fi);
    }
  }
}
All options and trade-offs3 options · 673 words

One fix was built and validated in a scratch worktree of 5adff78bb168; the other two are design alternatives a maintainer may prefer. Coordinate with LFV-635's fix (the same clear(), another caller) and with LFV-124's fix (a failed addIndexes(Directory...) leaves its fields registered), which edits the same publication block. LFV-124's recommended fix checks every incoming field up front without registering it and then registers them all at once, all or nothing, with one synchronized FieldNumbers.addAll inside the synchronized (this) publication block. Applied on 5adff78bb168, it also makes this bug's test pass (assertions on and off), and in the two-overload test it fixes the addIndexes(Directory...) case but not the addIndexes(CodecReader...) one. So the two fixes fit together: LFV-124's register-at-publish for addIndexes(Directory...) plus this bug's re-registration (all or nothing) in the addIndexes(CodecReader...) publication block.

Register the incoming fields again under the publication lock (validated on the race tests) (recommended)

#

In both publication blocks, right after ensureOpen() (IndexWriter.java:3196 and :3354), call a new registerSchema(infos) before reserveDocs. It reads each incoming segment's FieldInfos and calls globalFieldNumberMap.addOrGet while holding the monitor that deleteAll clears under, so registration and publication become one step relative to it. The early loop stays as a fail-fast check before the copy. If a document registered a conflicting type after the deleteAll, the call throws IllegalArgumentException inside the block and the existing handlers delete the copied files (:3202-3208, :3358-3365): the outcome of the legal order deleteAll, addDocument, addIndexes (by reading the code; not executed).

// in both publication blocks, right before reserveDocs(...):
registerSchema(infos);

private void registerSchema(List<SegmentCommitInfo> infos) throws IOException {
  assert Thread.holdsLock(this);
  for (SegmentCommitInfo info : infos) {
    for (FieldInfo fi : readFieldInfos(info)) {
      globalFieldNumberMap.addOrGet(fi);
    }
  }
}

Trade-offs

  • Re-reads each incoming segment's FieldInfos while holding the IndexWriter monitor (one small file per segment). A variant that keeps the FieldInfos read in the first loop and registers those avoids the re-read; a Directory-only form of it passed TestAddIndexes (39/39) and TestIndexWriterDelete (21/21) on main a9779ef3c193, whose IndexWriter.java differs from 5adff78bb168 only in the #16963 InfoStream line.
  • Keeping the early addOrGet loop keeps LFV-124's leak (a call that fails after it leaves its fields registered), and registerSchema registers field by field, so a conflict found at publication leaves the incoming fields registered before it (by reading; not executed). An all-or-nothing registration (verify every field first, then register, as LFV-124's FieldNumbers.addAll does) avoids both; with LFV-124's fix in place, only the addIndexes(CodecReader...) publication block still needs this change (the combination was not built).
  • In the common case (no deleteAll) the extra addOrGet calls find the same schema and change nothing.

What the checks validated

  • Gradle, clean scratch worktree of 5adff78bb168, OpenJDK 25.0.3, seed DEADBEEF: the test fails on stock with assertions on and off and passes with the fix, on and off.
  • With the fix: TestAddIndexes 39/39, TestIndexWriterDelete 23 passed + 6 skipped, TestDocValuesIndexing 33/33; the gradle selection --tests org.apache.lucene.index.* (one seed, no nightly or monster runs): 215 classes, 1,398 tests, 0 failures, 56 skipped; :lucene:core:check -x test passes with the fix and the test in place.
  • Both overloads: a two-method test (one per overload) fails 2 of 2 on stock and passes 2 of 2 with the same change (main 5adff78bb168, assertions off; earlier on 645d4fe14a20).

deleteAll waits for in-flight addIndexes(Directory...) calls

#

Count running addIndexes(Directory...) calls, as abortMerges already counts runningAddIndexesMerges, and have deleteAll wait for them.

Trade-offs

deleteAll then blocks for up to a whole copy while it holds the full-flush lock and every DWPT lock, which needs care to avoid a new lock-order problem (compare LFV-1137). The regression test must run deleteAll() on its own thread. Not built.

A schema generation checked at publication

#

FieldNumbers.clear() bumps a counter; addIndexes records it when it registers and, under the publication lock, re-registers (as the recommended option) or fails if it changed.

Trade-offs

Avoids the re-read when no deleteAll intervened, but adds state; failing instead of re-registering would give callers a new exception for a legal call order. Not built.

Downstream note

#

A service that lets the same caller trigger both a full wipe and an index addition, and then choose field types, can be left with an index no writer opens until it is rebuilt.

How it was found

#

TLA+ model checking of the writer-wide field schema. Mapping the model to the Java code put addIndexes' field registration outside the IndexWriter lock and its publication inside it; TLC then found a 4-state trace (register, deleteAll, publish) that breaks the invariant "every published segment's fields are in the schema". It was reduced to one JUnit test.

The method in full201 words

Method: semi-formal (a hypothesis formed by code reading while writing a TLA+ model, witnessed by the model checker), 2026-10-26.

  • A TLA+ model of the writer-wide field schema treats the field registration of addIndexes (outside the IndexWriter monitor) and its publication (inside it) as separate actions, with a map from each model step to the Java file:line. Writing that map raised the question of what deleteAll does in between.
  • TLC 1.8.0 reported the invariant SchemaCovers (every field of a published segment is in the schema) violated in a 4-state trace: register, deleteAll, publish. The same model is clean with the fix modelled and without deleteAll. A re-run of the model on main 645d4fe14a20 (code identical to its map) gave the same trace.
  • Two other analyses in the hunt reached the same interleaving independently the same evening: a model-based linearizability test that held addIndexes at 7 points against 7 concurrent operations (49 combinations; the only 2 outside the sequential model were deleteAll at two points inside the copy loop) and a second TLA+ model of addIndexes and its merge source.
  • The three were reduced to the one public-API JUnit test of this page, with a latch so that it is deterministic.

Finding record

LFV-1074, snapshot of 2026-11-09

Registry title
A deleteAll() that overlaps addIndexes clears the incoming fields from the writer's field schema, but addIndexes still publishes its segment, so a later document can give such a field another doc-values type and the committed index can no longer be opened by an IndexWriter
Area
index / IndexWriter addIndexes vs deleteAll (writer-wide field schema, FieldInfos.FieldNumbers)
Priority
Medium, rank 112: On the default IndexWriter of every release since 4.2.0, a deleteAll() that overlaps addIndexes drops the imported fields from the writer schema, and a later document that re-types one of them commits an index that no IndexWriter can open except with OpenMode.CREATE, which drops every document. The overlap needs no hooks but the full sequence is unusual, so it is rare, and it stays in Medium because the committed index is left unwritable.
Impact class
index unusable
Impact note
Hits applications that call deleteAll() (or deleteDocuments(MatchAllDocsQuery), which delegates to it) on one thread while another thread's addIndexes(Directory...) is copying files, or while addIndexes(CodecReader...) is between its merge and its publication, with the default IndexWriterConfig, codec, directory and merge scheduler and no scale needed: the imported segment survives but the writer forgets its fields, a later document may give one of them another doc-values type, the commit succeeds, and afterwards no IndexWriter opens the index except with OpenMode.CREATE, which drops every document [exec, -ea and -da]; per the finder's probes, a merge of the two conflicting segments closes the still-open writer as a tragic event, sorting on the field fails on readers, and CheckIndex at its default level reports the index clean; without the re-typing document the effect stays inside the open writer (getFieldNames() omits the imported fields, updateNumericDocValue on one of them is rejected) and ends when the writer is reopened; released 4.2.0 to 10.6.0.
Summary
One thread imports an index with IndexWriter.addIndexes while another thread calls deleteAll() on the same writer. You expect the outcome of one of the two orders: either the imported documents are deleted, or they stay and their fields keep their doc-values types, and in both cases the committed index opens again in a new IndexWriter. Instead deleteAll can clear the imported fields from the writer's schema while addIndexes still publishes the imported segment, so a later document can give an imported field another doc-values type, the commit succeeds, and the next new IndexWriter on that index throws IllegalArgumentException ('cannot change field "f" from doc values type=NUMERIC to inconsistent doc values type=SORTED').
