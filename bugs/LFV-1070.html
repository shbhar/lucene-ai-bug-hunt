BpVectorReorderer never calls the Executor it is given and forks its work onto ForkJoinPool.commonPool()

BpVectorReorderer never uses the executor you pass it: any non-null executor only turns forking on, and the forked-off work runs on the JVM-wide ForkJoinPool.commonPool(), even with the same-thread executor that means "stay on my thread". The order is correct; only where the CPU work runs is wrong (unreleased main).

The finding in 30 seconds

#

The reorderer carries the executor through every task but never calls it. Its tasks are ForkJoin RecursiveActions forked with ForkJoinTask.invokeAll from a thread outside any pool, so each forked half lands on the common pool.

Background: BP reordering and the merge executor

#
  1. BP ("recursive graph bisection") renumbers documents so that similar ones get nearby doc ids. BpVectorReorderer does it by a float vector field: it splits the documents into two halves around two centroids, moves vectors to the closer half, and recurses into each half.
  2. BPReorderingMergePolicy runs a reorderer on each merge. IndexWriter passes it an Executor from the merge scheduler: by default a same-thread executor ("all intra-merge actions occur in their calling thread"); ConcurrentMergeScheduler gives big merges a few threads, bounded by its maxThreadCount.
  3. The two halves of each split can run in parallel, and the executor is meant to be how: the sibling BPIndexReorderer runs its halves through it, so a same-thread executor keeps all its work on the caller.

The finding, step by step

#
  1. You reorder by a vector field on merges: new BPReorderingMergePolicy(mp, new BpVectorReorderer("v")). IndexWriter hands each merge's reorder the scheduler's executor; with SerialMergeScheduler or a small merge that is a same-thread executor.
  2. You expect the reorder to run on the merge thread, or on the executor's threads when it is a pool, as the sibling BPIndexReorderer does.
  3. Instead the executor is never called. Reordering 4,096 two-dimensional vectors with the executor Runnable::run reads vectors on the caller and on ForkJoinPool.commonPool-worker-1; the executor receives 0 tasks.
  4. Bigger inputs spread further: with a 2-thread pool as the executor and 65,536 vectors, the pool never starts a thread and 9 common-pool workers share the work. The resulting order is still correct.

Who is affected

#

Only users of unreleased main who opt in to BpVectorReorderer: every reordering merge (IndexWriter always passes an executor), direct computeDocMap calls with an executor, and the command line. The reorder then runs on common-pool threads (by default up to cores - 1), outside the merge scheduler's thread budget. Results are correct; no slowdown was measured.

Mechanism, terms and numbers644 words

BpVectorReorderer (lucene/misc, main and branch_11x only) renumbers documents by a float vector field, through BPReorderingMergePolicy, computeDocMap(reader, tempDir, executor) or its command line. The merge API describes the executor as the means of parallelism, and IndexWriter always passes the merge scheduler's intra-merge executor, which by default runs everything on the calling thread. The reorderer wraps that executor in a TaskExecutor and carries it through every task, but never calls it: its tasks are ForkJoin RecursiveActions forked with ForkJoinTask.invokeAll from a thread outside any pool, so a non-null executor only switches forking on and each forked half runs on ForkJoinPool.commonPool(). The command line's --thread-count pool never receives a task and is never shut down. The order is correct (each thread reads its own copy of the vectors); the reorder's CPU work just runs on common-pool threads (by default up to cores - 1) outside the merge scheduler's thread budget. The sibling BPIndexReorderer was moved to the executor in #13289, four months before this class was added with the old pattern. Main and branch_11x only; no release has the class.

The mechanism (main 645d4fe14a20)

#
  1. The executor is wrapped and carried, never called. computeDocMap builds new TaskExecutor(executor) when the executor is non-null (BpVectorReorderer.java:580-585) and passes it through computeValueMap (:591, :596-607) to the root ReorderTask (:627). Every task stores it (:151-157) and hands it to its children (:254-257, :526-547). Nothing calls invokeAll, submit or execute on it.
  2. It is only a switch. shouldFork returns false when the executor is null (:160-162); otherwise it consults the ForkJoin-only getSurplusQueuedTaskCount() (:163-167) and forks at the root and above FORK_THRESHOLD = 8192 (:78, :168-173).
  3. Forking goes through ForkJoin. BaseRecursiveAction extends RecursiveAction (:149); ReorderTask (:259-260) and ComputeBiasTask (:523-547) call ForkJoinTask.invokeAll, which forks one half and runs the other on the current thread.
  4. The caller is outside any pool. The root runs with .compute() on the calling thread (:627). fork() from a thread that is not in a ForkJoinPool uses ForkJoinPool.commonPool(), so a common-pool worker takes the forked half while the caller works on the other; its own forks stay in the common pool.
  5. The command line's pool is dead code. main() builds new ForkJoinPool(threadCount, ...) when --thread-count is not 1 (default: the core count, :660, :673-678) and passes it as the executor (:679-681); nothing submits to it and it is never shut down.
  6. Results stay correct. Each thread gets its own vectors.copy() (:108-110, :619-625), and tasks work on disjoint slices of the shared arrays (:252-253).

The sibling for comparison: BPIndexReorderer.java:158-191 has a task base class and shouldFork of the same shape (its shouldFork has no queue-depth check) but implements Callable<Void> and forks with executor.invokeAll(...); TaskExecutor submits all but one task to the executor and runs the rest on the calling thread (TaskExecutor.java:37-45).

Exposure and likelihood316 words
  • Who. Users of main or branch_11x (would ship in 11.0.0) who opt in: BPReorderingMergePolicy with a BpVectorReorderer, on every reordering merge with any merge scheduler, since IndexWriter always passes getIntraMergeExecutor(merge) (IndexWriter.java:3558-3562 for addIndexes(CodecReader...), :5542-5558 for merges; BPReorderingMergePolicy.java:133-138); a direct computeDocMap call with a non-null executor; the command line with --thread-count other than 1, which includes the default (the core count) on any multi-core host.
  • What goes wrong. The reorder's CPU work runs on common-pool threads (with the JVM's default common-pool size, up to cores - 1) instead of the merge thread (SerialMergeScheduler, "using the current thread"; small ConcurrentMergeScheduler merges, "don't do multithreaded merges for small merges"), instead of ConcurrentMergeScheduler's intra-merge executor, which "provides a limited number of threads" tied to maxThreadCount, or instead of the application's own pool. It competes with everything else in the JVM that uses the common pool (parallel streams, default async CompletableFuture methods). Among valid (positive) values, --thread-count T only matters as 1 versus not 1; 0 or a negative value makes the ForkJoinPool constructor throw IllegalArgumentException.
  • Not hit. The document order is correct; no exception, hang or corruption; a null executor stays on the caller.
  • Default vs opt-in, scale. Opt-in class in lucene/misc, used by no default codec or merge policy. Any input big enough to be split (at least 2 x minPartitionSize, 64 vectors by default): the root split then always forks when an executor is given, and 64 vectors already reach the common pool. Smaller inputs are not split, so nothing reaches the common pool (63 vectors: no reader in 20 of 20 iterations). Same with assertions on and off.
  • How likely to be noticed. Silent: only applications that budget merge threads or share the common pool feel it, and no public report was found. No benchmark of the harm was run, so it stands as a consistency fix.

Why it looks unintended

#
  • The merge API calls the executor the way to parallelize: "May be null if no concurrency is supported"; the default one runs everything "in their calling thread".
  • #13289 moved the sibling BPIndexReorderer onto the executor; this class came four months later with the old code.
  • Its --thread-count pool never gets a task.
The full argument253 words
  • IndexReorderer#computeDocMap: "@param executor may be used to parallelize reordering work." (IndexReorderer.java:32)
  • OneMerge#reorder: "An executor that can be used to parallelize the reordering logic. May be {@code null} if no concurrency is supported." (MergePolicy.java:321-322)
  • MergeScheduler#getIntraMergeExecutor: "By default, the method returns a SameThreadExecutorService where all intra-merge actions occur in their calling thread." (MergeScheduler.java:60-66). SerialMergeScheduler does each merge "using the current thread"; ConcurrentMergeScheduler returns the same-thread executor for small merges on purpose.
  • #13289 (Adrien Grand, 2024-09-12): "Index reordering can benefit greatly from parallelism, so it should try to use the intra-merge executor when possible." It moved BPIndexReorderer from RecursiveAction to Callable tasks forked through TaskExecutor.invokeAll, whose javadoc says "A value of null indicates that reordering should be performed in the current thread" (BPIndexReorderer.java:831-832). BpVectorReorderer (#14097, 2025-01-07) has the old RecursiveAction code with the new TaskExecutor field.
  • The class expects it too. It carries the executor through every task and builds a --thread-count pool for the command line; neither is used.
  • Tests. TestBpVectorReorderer builds its own ForkJoinPool "to avoid tests failing with FS-based directories" and passes it (:132-144); on main it runs nothing. No test asserts where the work runs.
  • The class author and other contributors assume it is used. Open #16729, from another contributor, describes the class as using executor capacity at each recursion node; on open PR #15430 the class author credits a merge-time speedup to "passing the mergestate intra-merge executor in", which with this code comes from the common pool.
The devil's-advocate check147 words

The case for intended: read literally, "may be used" and "May be null if no concurrency is supported" make a non-null executor a licence to parallelize; no javadoc names the pool the work must run on; results are correct and OneMerge#reorder is experimental. The cross-model reviewer (OpenAI GPT-5.6, refute lens) rated this a moderate argument.

Why it fails. (1) Lucene's own schedulers pass a non-null same-thread executor precisely to mean "no concurrency"; under the licence reading every reordering SerialMergeScheduler merge would spread over the common pool, contradicting "using the current thread". (2) "May be used" permits not parallelizing, not parallelizing on a different, JVM-wide pool. (3) The carried-but-unused executor and the dead command-line pool show the work was meant to run there. (4) #13289 fixed the same pattern in the sibling for this reason. The reviewer, the intended-behaviour devil's advocate and the adjudication all called it real.

Suggested fix

#

Recommended A. Fork through the given executor, as BPIndexReorderer does since #13289

Port #13289's pattern from BPIndexReorderer: make the tasks Callable<Void> forked through TaskExecutor.invokeAll, drop the ForkJoin-only queue check, and shut down the command line's pool. Validated with gradle: the repro passes, and so do the reorder suites (incl. nightly), all of lucene/misc, and the format and lint checks.

All options and trade-offs3 options · 705 words

Option A was applied in a scratch worktree of main 645d4fe14a20 and run with gradle and the standalone JUnit runner; B and C are alternatives from reading the code, not run. Workaround today (from the code, not run as such; the null-executor controls stay on the caller): wrap the reorderer so it gets a null executor, for example new BPReorderingMergePolicy(mp, (reader, dir, executor) -> bpv.computeDocMap(reader, dir, null)); the reorder then stays on the merge thread, serially (shouldFork returns false for null).

A. Fork through the given executor, as BPIndexReorderer does since #13289 (validated by the checks) (recommended)

#

BaseRecursiveAction implements Callable<Void> with an abstract compute(); call() runs it, and a local invokeAll(BaseRecursiveAction...) forks through executor.invokeAll(Arrays.asList(actions)) (as in BPIndexReorderer.java:183-190). Drop the ForkJoin-only getSurplusQueuedTaskCount() check. Shut down the pool that main() creates: without that, the command-line pool now starts threads that are never stopped, and the upstream suite fails its thread-leak check.

Trade-offs

Parallelism is then bounded by the given executor: a same-thread executor (serial merges, small ConcurrentMergeScheduler merges) gives a serial reorder, so a reorder that today silently gets common-pool parallelism may take longer, and speedups measured with the current code (such as the one reported on #15430) may change. Forking is decided by size alone, as in BPIndexReorderer. No benchmark was run. Open PR #15430 moves the class, so the fix site may move.

B. Run the root task inside the given pool when it is a ForkJoinPool

#

What BPIndexReorderer did before #13289 (it submitted its root task to the given pool); do not fork for any other executor. Keeps RecursiveAction.

Trade-offs

The merge schedulers' executors are not ForkJoinPools (MergeScheduler.java:38, ConcurrentMergeScheduler.java:945), so every merge would reorder serially, the opposite of #13289's goal. Not run.

C. Document the current behaviour

#

Say that the executor only switches forking on and the common pool does the work.

Trade-offs

Contradicts OneMerge#reorder, SerialMergeScheduler and the sibling's contract, and leaves --thread-count meaningless. Not recommended.

Downstream note

#

Applications that cap merge threads, or run latency-sensitive work on the common pool, get extra common-pool load from vector BP reordering on main until this is fixed; results are unaffected.

How it was found

#

Non-formal. A hunt unit testing the misc reorderers saw identical doc maps for null, pool, direct and rejecting executors, read the executor handling and witnessed the bug with a test that records the reading threads. A follow-up unit reduced it to one test and ran an executor, size and similarity matrix on main and on the fix.

LFV-1070, snapshot of 2026-11-04

Registry title
BpVectorReorderer never calls the Executor it is given; any non-null executor makes it fork its work onto ForkJoinPool.commonPool()
Area
misc / index: BpVectorReorderer (BP doc-id reordering over a vector field, through BPReorderingMergePolicy, computeDocMap and the command line)
Priority
Low, rank 754: Only on unreleased main and branch_11x and only for the opt-in BpVectorReorderer, the given executor is ignored and the work runs on the JVM-wide common pool. That changes thread placement and CPU contention but not the computed order, so it is Low.
Impact class
minor
Impact note
Only users of unreleased main and branch_11x who opt in to BpVectorReorderer (BPReorderingMergePolicy with a BpVectorReorderer, a direct computeDocMap call with an executor, or the command line with --thread-count other than 1) are hit, and then on every reorder of an input big enough to be split (at least 2 x minPartitionSize, 64 vectors by default): the reordering CPU work runs on the JVM-wide common pool (by default up to cores - 1 threads) instead of the given executor or the merge scheduler's thread budget, also when the scheduler passes a same-thread executor to mean 'no concurrency'; the computed order is correct, so the effect is thread placement and CPU contention only.
Summary
You reorder a segment with BpVectorReorderer and pass an Executor, for example the same-thread intra-merge executor that IndexWriter hands to BPReorderingMergePolicy under SerialMergeScheduler, or the pool the command line builds for --thread-count, and expect the work to run on the calling thread or on that executor, as it does for the sibling BPIndexReorderer. Instead the executor is never called: the tasks are RecursiveActions forked with ForkJoinTask.invokeAll from a thread outside any ForkJoinPool, so any non-null executor only switches forking on and the forked work runs on ForkJoinPool.commonPool(). With a run-on-caller executor and 4,096 two-dimensional vectors, vectors are read on a common-pool worker as well as on the caller; the resulting order is still correct.
