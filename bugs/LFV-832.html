FastVectorHighlighter loses a match at a position with stacked index-time synonyms when the first stacked token starts a phrase that does not continue

With index-time synonyms, FastVectorHighlighter can drop a match because another token at the same position starts a query phrase: on my dogs (synonym dog stacked on dogs), dogs OR "dog house" matches, but getBestFragment returns null instead of my <b>dogs</b>. A silent regression since 4.7.1; 4.7.0 highlights it.

The finding in 30 seconds

#

At a position that holds several tokens, FastVectorHighlighter starts with the first token the query knows, even when it is only the first word of a phrase. If the phrase does not continue there, it gives up on the whole position, so another token there that the query matches is never highlighted.

Background in three steps

#
  1. Index-time synonyms put several tokens at one position: my dogs with the synonym dog is indexed as my (position 0), dogs and dog (both position 1, offsets 3-7).
  2. FastVectorHighlighter reads the document's term vector and keeps the query's terms in a stack ordered by position. Since 4.7.1 the tokens of one position form one stack entry, in term order: dog, then dogs.
  3. It turns the query into a phrase map: a term (dogs) is a complete entry; a phrase ("dog house") is a chain whose first word (dog) is not complete on its own.

The finding, step by step

#
  1. Index my dogs with an index-time synonym filter that adds dog at the position of dogs (a field with term vectors, positions and offsets). Search dogs OR "dog house": 1 hit, through dogs; the phrase matches nothing.
  2. You expect getBestFragment to return my <b>dogs</b>: Weight#matches reports dogs at offsets 3-7, and the query dogs alone gives exactly that fragment.
  3. Instead you get null. Position 1 holds dog and dogs, tried in term order. dog is the first word of "dog house", so it becomes the start; no house follows, nothing is added, and dogs is never tried.
  4. No error, and hits and scores are correct. Lucene 4.7.0 highlights it; every release since 4.7.1 (LUCENE-5538) returns null. SynonymGraphFilter + FlattenGraphFilter and KeywordRepeatFilter + a stemmer hit it the same way.

Who is affected

#

Users of FastVectorHighlighter with phrase highlighting (the default) on term-vector fields whose index-time analysis stacks tokens at one position: synonyms, KeywordRepeatFilter plus a stemmer. It takes a query phrase that starts with the stacked token that sorts first and does not continue there. Hits and scores are unaffected.

Mechanism, terms and numbers605 words

With phrase highlighting (the default), FastVectorHighlighter groups all tokens of one position into one entry of its FieldTermStack, as a circular list in term order. FieldPhraseList starts a candidate with the first of those tokens that has any entry in the query's phrase map, even when that entry is only the first word of a phrase. If the phrase does not continue there, nothing is added and the other tokens of the position are never tried. Index my dogs with an index-time synonym dog stacked on dogs and search dogs OR "dog house": the document matches through dogs (Weight#matches reports offsets 3-7), but getBestFragment returns null instead of my <b>dogs</b>, which dogs alone gives. Search hits and scores are unaffected and nothing fails loudly. Lucene 4.7.0 highlights the input; the loop came with LUCENE-5538 in 4.7.1 (2014), and every release since is affected, up to 10.6.0 and main. A one-file fix that tries each token of the start position passes the repro and every highlighter-module test.

The mechanism (main 5adff78bb168, lucene/highlighter/.../vectorhighlight/)

#
  1. One entry per position. FieldTermStack collects the query's terms from the term vector in term order, sorts them by position (FieldTermStack.java:105-106; TermInfo.compareTo compares positions only, :225-227) and links the tokens of one position into a circular next list, removing all but the first from the stack (:108-130). For my dogs the stack holds one entry, position 1: dog -> dogs -> dog (my is not a query term).
  2. The phrase map. QueryPhraseMap.add gives a PhraseQuery a non-terminal map for each leading term and marks only the last one terminal; a TermQuery gets a terminal map (FieldQuery.java:398-418).
  3. The start loop. The FieldPhraseList constructor pops the entry and walks its alternatives only while getFieldTermMap(...) returns null (FieldPhraseList.java:73-78). dog sorts first and has a (non-terminal) map, so the walk stops at dog. The entry is skipped only when no token has a map (:80-81).
  4. The dead end. The next pop finds nothing (:86), so the phrase cannot continue (:95). The one-token candidate [dog] is not a valid term or phrase, because its map is not terminal (FieldQuery.java:460-465), and backtracking runs only while the candidate has more than one token (FieldPhraseList.java:102). Nothing is added (:97-113), and dogs, which shares the popped entry, is never tried. The phrase list is empty and getBestFragment returns null.
  5. Order matters. With dog indexed and dogs stacked on it, dog OR "dogs house" is highlighted. The analysis docs leave that order undefined (lucene/core/.../analysis/package-info.java:341-344). A token pushed back after a failed phrase can also become the one tried first: the exhaustive check shows a OR "b b" losing the a of b z a/b (a and b stacked at position 2).
  6. Why 4.7.0 was right. Before LUCENE-5538 every stacked token was its own stack entry, so after the dead end at dog the next pop was dogs, which was added. LUCENE-5538 collapsed them into one entry and added the start loop, which stops at the first token with any map.

Exposure and likelihood305 words
  • Who is exposed. Applications that highlight with FastVectorHighlighter and phrase highlighting on (DEFAULT_PHRASE_HIGHLIGHT = true, FastVectorHighlighter.java:28, default constructor :37-38), on a field with term vectors, positions and offsets (an opt-in field setting FVH requires), analyzed at index time with a chain that stacks tokens.
  • Production chains (executed on 5adff78bb168). SynonymGraphFilter + FlattenGraphFilter, as the SynonymGraphFilter javadoc prescribes for indexing (tv -> television; the classic QueryParser query tv OR "television stand" on my tv returns null); KeywordRepeatFilter + PorterStemFilter (running OR "run fast" on she was running returns null). By reading, any other filter that stacks tokens (for example a word-delimiter filter that keeps the original) can do it too.
  • The trigger. At a position with a query match, the token tried first (the one that sorts first among the position's tokens the query knows, or one pushed back after a failed phrase) is only the first word of a query phrase, and that phrase does not continue there. Phrase OR phrase is hit too: "dogs bark" OR "dog house" on dogs bark returns null.
  • Silent. No exception with assertions on or off. getBestFragment returns null when it was the field's only match; otherwise that occurrence is just not marked. Search hits, counts and scores are correct.
  • Not affected in the tested cases, and workarounds. The UnifiedHighlighter and FastVectorHighlighter with phraseHighlight=false both give my <b>dogs</b> for dogs OR "dog house" on my dogs, and both highlight tv OR "television stand" on my tv (SynonymGraphFilter + FlattenGraphFilter). This is shown for the tested inputs only.
  • How likely. Rare: each ingredient is ordinary for FVH users with index-time synonyms, but the combination is narrow, and the searches found no report of it in the 12 years since 4.7.1. No scale is needed: one two-word document.

Why it looks unintended

#
  • LUCENE-5538 added this code in 4.7.1 as a bug fix for this symptom class: "(P1 OR PQ) returns no results, even though individually, both P1 or P2 by themselves will highlight correctly". 4.7.0 highlights the input.
  • A SHOULD phrase that matches nothing removes the highlight of a matching term.
  • The package docs' worked example is a term OR phrase query.
The full argument354 words
  • A regression of a bug fix. CHANGES for 4.7.1: "LUCENE-5538: Fix FastVectorHighlighter bug with index-time synonyms when the query is more complex than a single phrase." (lucene/CHANGES.txt:12742-12743). The issue text (#6601): "in some situations a query of (P1 OR PQ) returns no results, even though individually, both P1 or P2 by themselves will highlight correctly". The shape is similar but the input is not the same: in #6601 both phrases highlight on their own; here the term alone highlights and the phrase alone matches nothing, yet the disjunction loses the term's highlight.
  • The fix author's intent. On #6601, Robert Muir described their first patch: "when we reach a dead-end (nextMap == null), we keep looking as long as the incoming position is the same until we find a match", and the final one: "This should be correct for all crazy combinations." Adrien Grand gave a +1. The committed code keeps looking for the continuation token (FieldPhraseList.java:90-93), but at the start only while no map is found (:75).
  • 4.7.0 highlights the input; 4.7.1 returns null, and swapping only the two source files LUCENE-5538 changed (FieldPhraseList.java, FieldTermStack.java) flips the result in both directions. 4.7.0 gets this input right because each stacked token was its own stack entry there; it is not more correct in general (it lacks LUCENE-5538's own fix).
  • Documented feature. The package javadoc lists "support phrase-unit highlighting with slops" (package-info.java:26); its worked example is a TermQuery OR a PhraseQuery (Lucene^2 OR "search library"~1, :47-53), whose phrase list holds one entry for the term and one for the phrase (:124-137). Stacked tokens are a documented analysis pattern with undefined order (analysis/package-info.java:341-344), and SynonymGraphFilter tells index-time users to stack with FlattenGraphFilter (SynonymGraphFilter.java:67-68).
  • No test pins the current output. TestIndexTimeSynonym's term-or-phrase cases (pc OR "personal computer", TestIndexTimeSynonym.java:167-175, :218) put the term first in sort order, so the dead end is never reached; LUCENE-5538's testBooleanPhraseWithSynonym (TestFastVectorHighlighter.java:714) uses two phrases that both match. All 723 highlighter-module tests pass with the fix.
The devil's-advocate check302 words

The strongest case for "intended": FastVectorHighlighter is a greedy heuristic that promises fragments, not every match. On LUCENE-4734 (#5799, open since 2013) a contributor wrote "FVH works great for simple phrase and single term queries but it has so many corner cases", and Adrien Grand ("This is my feeling too") and Simon Willnauer agreed; a broader FieldPhraseList rewrite that also handled "several terms at the same position" was committed and reverted before any release because "it makes the runtime of FastVectorHighlighter very bad". #16820 (open) proposes deprecating FVH. getBestFragments documents a null result "when no fragments created" (FastVectorHighlighter.java:131; getBestFragment itself only says "the best fragment (snippet) string", :107). Users who need exact highlights should use the UnifiedHighlighter.

Why it fails: the revert was in 2013; the defective lines came later, in 2014, from LUCENE-5538, a bug fix whose stated goal this input violates and which turned a correct 4.7.0 result into null. No document states the limitation. This is not a missed corner of a complex query but the loss of a plain term match caused by adding a SHOULD clause that matches nothing. The documented null of getBestFragments ("when no fragments created") does not say that a matching term query may go unhighlighted. The fix is bounded to the tokens of the start position (not the reverted search), and FVH is not deprecated on main. The cross-model intended-behaviour review (OpenAI GPT-5.6, with executed tests) rated the argument weak and the bug real (high); the devil's-advocate verifier found that no intended-behaviour argument survives; the independent reproducer rated the argument medium-strong before rebutting it, and rated the bug real. Expect the answer "won't fix, use the UnifiedHighlighter" anyway, especially without a worst-case cost bound for the fix: a later cross-model review rated the "intended" case moderate for that reason.

Suggested fix

#

Recommended A. Try every token of the start position (validated)

In the FieldPhraseList constructor, try every token of the start position in turn until one yields a term or phrase, instead of stopping at the first that has any query-map entry (one file). The repro passes with assertions on and off, and all 723 highlighter-module tests pass.

final TermInfo start = fieldTermStack.pop();
TermInfo alt = start;
do {
  QueryPhraseMap startMap = fieldQuery.getFieldTermMap(field, alt.getText());
  if (startMap != null && searchFrom(fieldTermStack, fieldQuery, field, alt, startMap)) {
    break;
  }
  alt = alt.getNext();
} while (alt != start);
All options and trade-offs2 options · 588 words

Two options. A was built and validated on main 5adff78bb168; B was not built. Until a fix lands, new FastVectorHighlighter(false, true) (no phrase highlighting) or the UnifiedHighlighter highlight the match in the tested cases.

A. Try every token of the start position (validated) (recommended)

#

Pop the entry and walk its alternatives; for each one with a map, run the existing longest-phrase search from it, and stop at the first that reaches addIfNoOverlap. The search moves unchanged into a private helper searchFrom(...) that returns whether it did; a dead end restores the stack, as today's backtracking already does. One file, +51/-46.

final TermInfo start = fieldTermStack.pop();
TermInfo alt = start;
do {
  QueryPhraseMap startMap = fieldQuery.getFieldTermMap(field, alt.getText());
  if (startMap != null && searchFrom(fieldTermStack, fieldQuery, field, alt, startMap)) {
    break;
  }
  alt = alt.getNext();
} while (alt != start);

Trade-offs

  • Cost: at most one more run of the existing phrase search per extra token at a start position, and only after a dead end: at a position with k stacked tokens, at most k runs instead of one, each walking at most as far as today's search and restoring the stack when it fails. Bounded, not the combinatorial search reverted in LUCENE-4734, but no worst-case benchmark was run, and the passing tests are not a proof that every dead-end path restores the stack. It keeps LUCENE-5538's data structure and tests.
  • It keeps term order as the preference among a position's tokens: when several of them start a valid term or phrase (with different boosts, or overlapping other hits), the first in term order still wins, and no test settles which one should.
  • It does not cover a related trigger where the first-tried token's candidate is valid but rejected by addIfNoOverlap for overlap (the helper returns true once it calls addIfNoOverlap); that trigger did not lose highlights on main in the earlier probe. The helper's javadoc ("returns true if a phrase was added") should say "offered to addIfNoOverlap".

  • checkGoogleJavaFormat, ecjLint, forbiddenApisMain and renderJavadoc of lucene/highlighter pass (the build disables the stock javadoc task, which the log shows as SKIPPED, in favour of renderJavadoc).
  • The independent reproducer's and the devil's-advocate verifier's suites (production analysis chains included) pass 5 of 5 each with the fix applied on 5adff78bb168.
  • In the bounded-exhaustive run, with the study's fix sketches for several highlighter findings on the classpath together (among them a start-token retry like fix A; the run does not isolate fix A), the class "term OR phrase, a clause not highlighted" dropped from 401 cases to 0 and "phrase OR phrase" from 118 to 0. An independent verifier's own equivalent fix passed the same tests.

B. Also retry when the candidate is rejected for overlap (not built)

#

Make the helper return whether the candidate was actually added (a private boolean variant of addIfNoOverlap, which is public void), so the next token of the start position is tried after an overlap rejection too.

Trade-offs

Covers the related trigger as well, but changes which highlight wins when stacked tokens overlap an earlier hit, which #8644 (LUCENE-7593) shows is already delicate; it needs its own tests.

Downstream note

#

Products that show FastVectorHighlighter snippets as evidence of what matched (for example review views over synonym-expanded fields) can show no snippet, or an unmarked one, for a document that does match; search results and filtering are unaffected.

How it was found

#

Semi-formal. A bounded-exhaustive check compared FastVectorHighlighter's phrase list with an exact match reference, cross-checked with Weight#matches: 152 documents of 1-3 words, some with stacked tokens, 2,139 queries, 153,082 checks. 401 term-OR-phrase cases lost a clause's highlight; code reading traced them to this loop, and a public-API JUnit test confirmed it.

The method in full196 words

Method: semi-formal (bounded-exhaustive translation validation). A test program enumerated every single-valued document of 1 to 3 words over {a, b, c, a position hole, and a/b, two tokens stacked at one position with the same offsets} (152 documents) and 2,139 queries (terms, SynonymQuery, phrases with gaps and slop, MultiPhraseQuery, and term OR phrase / phrase OR phrase booleans). It compared the offsets in FastVectorHighlighter's FieldPhraseList (and the classic Highlighter's marks) with an exact match semantics written independently from the code, cross-checked against Weight#matches on every hit: 153,082 document-query checks on the stock main jars.

  • The mismatch class "term OR phrase, a matching clause not highlighted" had 401 cases (for example a OR "b b" on b z a/b highlights nothing).
  • Code reading traced it to the start-position loop; the case was reduced to a public-API JUnit test on the stock jar, which failed with assertions on and off.
  • With the study's fix sketches for several highlighter findings on the classpath together (among them a start-token retry like fix A) the class dropped to 0 (and "phrase OR phrase" from 118 to 0); the remaining highlighter mismatches belong to other, already reported defects.

History

#

Introduced in 4.7.1 by LUCENE-5538 (673b1f8d73c, 2014-03-19; shipped through 88df0bca7cc). 4.7.0 passes, and swapping only the two changed source files between the 4.7.0 and 4.7.1 jars flips the result both ways. Fails on every release run from 4.7.1 to 10.6.0 and on main. Not fixed upstream.

Versions tested6 rows

Introduced by LUCENE-5538, "FastVectorHighlighter fails with booleans of phrases" (#6601), by Robert Muir with a +1 from Adrien Grand; a JIRA patch, no pull request. Commit 673b1f8d73c (trunk, svn r1579255, 2014-03-19), backported the same day as 6c9608f484d (branch_4x, r1579264) and 88df0bca7cc (lucene_solr_4_7, r1579269), which shipped in 4.7.1 (tagged 2014-04-01). It added the circular same-position list in FieldTermStack and the start loop in FieldPhraseList; git log -S 'getNext() != first' on main's history finds only this commit (with --all it also lists the two backports and aad44bc6e36, a 2021 commit that removed the whole tree on an old branch).

Commit-level proof. The only highlighter source change between the 4.7.0 and 4.7.1 tags is 88df0bca7cc. On the 4.7.0 jars, swapping in only the two source files at 88df0bca7cc makes the test fail; on the 4.7.1 jars, swapping in the two files at 88df0bca7cc^ makes it pass.

LFV-832, snapshot of 2026-11-10

Registry title
FastVectorHighlighter drops a match at a position that holds stacked tokens (index-time synonyms, stems) when the token that sorts first there starts a query phrase that does not continue: FieldPhraseList tries only the first stacked token with any query-map entry, so dogs OR "dog house" on 'my dogs' (synonym dog stacked on dogs) highlights nothing (a LUCENE-5538 regression, 4.7.1 on)
Area
highlighter / vectorhighlight FieldPhraseList and FieldTermStack (FastVectorHighlighter phrase search over stacked tokens)
Priority
Medium, rank 221: FastVectorHighlighter has silently dropped highlights since 4.7.1 on its default phrase path when index-time stacked tokens meet a term-or-phrase query, with hits still correct, a narrow silent-highlight-loss case.
Impact class
silent wrong results
Impact note
Applications on 4.7.1 through 10.6.0 or main that highlight with FastVectorHighlighter (a field with term vectors, positions and offsets; the default phraseHighlight=true) over text indexed with several tokens at one position (index-time SynonymGraphFilter+FlattenGraphFilter, KeywordRepeatFilter plus a stemmer, the test framework's MockSynonymAnalyzer) lose the highlight of a matching term or phrase whenever the query also holds a phrase that starts with the token that sorts first at that position and does not continue there: getBestFragment returns null if that was the field's only match, otherwise that occurrence is silently left unmarked; hits, counts and scores are correct, there is no error with -ea or -da, no scale is needed, and the UnifiedHighlighter, FastVectorHighlighter with phraseHighlight=false, and the lexically mirrored token order all highlight the same match.
Summary
You index 'my dogs' with an index-time synonym filter that stacks 'dog' on 'dogs' (term vectors with positions and offsets), search dogs OR "dog house", which matches through dogs (Weight#matches reports offsets 3-7), and call FastVectorHighlighter.getBestFragment, expecting 'my <b>dogs</b>', which the TermQuery alone gives. Instead you get null, with no error. FieldPhraseList starts a candidate with the first token at that position that has any entry in the query's phrase map ('dog', which sorts first and only starts the phrase "dog house"), finds that the phrase does not continue, adds nothing and never tries 'dogs' at the same position; Lucene 4.7.0 highlights this correctly, and the LUCENE-5538 fix in 4.7.1 introduced the loop.
