The finding in 30 seconds

#

Needs three things together: the experimental column batch API, one batch with 39 or more stored or indexed columns, and a JVM where Lucene takes an object reference to be 8 bytes. It is loud, before any row is processed. With compressed references on the full JDK (the default flags at a 2 GB heap) the same batch is indexed.

Background: three pieces

#
  1. The column batch API (experimental, since 10.5.0) takes documents column by column: IndexWriter.addBatch(ColumnBatch). A column is one field across the documents of the batch.
  2. Stored fields and the inverted index are still written row by row. For that row pass Lucene first collects the batch's stored or indexed columns into three parallel arrays: one array of references and two int arrays. A column that is neither stored nor indexed (doc values, points or vectors alone) is not collected there.
  3. A 64-bit JVM keeps an object reference in 4 bytes (compressed references) or in 8. Lucene reads which from the JVM and sizes a reference array by it when the array grows; when it cannot read the JVM's option it takes 8.

The finding, step by step

#
  1. Build one batch for the experimental column API: one document and 39 stored LongColumn columns, f0 to f38, each with the value 0. On a JVM started with -XX:-UseCompressedOops (a 2 GB heap), call IndexWriter.addBatch(batch) on a writer with an untouched IndexWriterConfig.
  2. You expect the document with its 39 stored fields. The same batch gives it with the JVM's default flags at a 2 GB heap on the full JDK, and a batch of 38 such columns gives its document under the flag (both run).
  3. Instead addBatch throws java.lang.ArrayIndexOutOfBoundsException: Index 38 out of bounds for length 38 from IndexingChain.processRowColumns, before any row is processed, with assertions on and off. In the runs without a term-vector column the writer stayed usable.
  4. Why: the row pass keeps one reference array and two int arrays for the stored or indexed columns and grows them by three separate ArrayUtil.grow calls under one test that reads the reference array's length. With 8-byte references the lengths part: 37/38/38 at column 33, then 42/38/38 at column 38. Column 39 passes the test (38 < 42) and is written at index 38 of an int array of length 38. With 4-byte references the three lengths stay equal.
  5. Where it was run: -XX:-UseCompressedOops on each release from 10.5.0 to 10.6.0 and on builds of branch_11x and main; -XX:+UseZGC, a runtime without the jdk.management module and a 34 GB heap, each on 10.6.0 and on builds of branch_11x and main. 34 GB is the one heap size of 32 GB or more that was run; for the others there is only the JDK's flag print (compressed references off at 32, 33, 48, 64, 128 and 512 GB, on at 31 GB).

Who is affected

#

An application on the experimental column batch API that puts 39 or more stored or indexed columns into one batch and runs where Lucene takes a reference to be 8 bytes. It throws before any row is processed; in the runs without a term-vector column the writer stayed usable. With compressed references on the full JDK no run threw. Rare.

The row pass keeps one reference array and two int arrays for the stored or indexed columns of a batch and grows them by three separate ArrayUtil.grow calls under a test that reads the reference array's length alone. ArrayUtil.oversize picks a new length from the element size, so when Lucene takes a reference to be 8 bytes the three lengths part (42, 38 and 38) and the 39th such column is written past the end of an int array. With 4-byte references a replay of the lengths finds no such column up to 2^24 columns.

Exposure and likelihood681 words
  • Who. An application that indexes through IndexWriter.addBatch, or updateDocuments with a ColumnBatch (10.5.0 and later), with 39 or more stored or indexed columns in one batch, on a JVM in which Lucene takes an object reference to be 8 bytes. It can meet the exception on its first such batch; one document is enough.
  • Which JVMs, as run and as the JDK prints. With -XX:-UseCompressedOops. With -XX:+UseZGC: the JVM then turns compressed references off by itself (the program read the option as false in that JVM). On a runtime without the jdk.management module, where Lucene cannot read the option and takes 8 bytes. At a heap of 34 GB with no flag that names the object layout: the JVM reports the option as false there. Other heap sizes of 32 GB or more were not run: their only basis is the JDK's flag print (java -Xmx32g -XX:+PrintFlagsFinal -version and the same line with the other sizes, JDK 25.0.3), which shows UseCompressedOops false at 32, 33, 48, 64, 128 and 512 GB and true at 31 GB. No count of installations is claimed.
  • Not with compressed references on the full JDK. The JVM's default flags give them at a 2 GB heap, and the same batch was indexed in each such run. The words "on the full JDK" matter: on the JDK limited to java.base and java.logging the JVM has compressed references too (the JDK's flag print for these flags gives UseCompressedOops true), but Lucene cannot read the option, takes 8 bytes, and the batch throws.
  • What happens. java.lang.ArrayIndexOutOfBoundsException: Index 38 out of bounds for length 38 out of the call, before any row is processed, with assertions on and off. updateDocuments with a term and 39 stored columns throws the same exception, and the document that the term matches is still there afterwards (run for this page; with a query in the first runs).
  • The writer afterwards, in the runs without a term-vector column. No document and no stored value of the batch was in the index, the writer stayed open without a tragic exception, a following batch of 38 columns was indexed, commit and close returned, and the index held the documents that were accepted. Two things of the refused batch were left. Its field names: the validation pass registers a batch's fields before the row pass runs (IndexingChain.java:722-785 at main 3cee9ed259e9), and the commit that followed lists 39 fields, the 39th from the refused batch. And the document id it had reserved, which is marked deleted (DocumentsWriterPerThread.java:349-354 at the same commit): with NoMergePolicy the commit shows two document slots of which one is deleted, with an untouched IndexWriterConfig one document and no deleted slot.
  • The reach into LFV-096, a related finding of this list. With a term-vector column among the columns, on a field new to an in-memory segment that holds an earlier document, an application that goes on after the exception can get a commit that fails or cannot be opened. Run: one buffered document, then a one-document batch of 39 indexed columns with term vectors on each. With an untouched IndexWriterConfig, commit() and close() then throw CorruptIndexException; with NoMergePolicy they return and DirectoryReader.open throws it. With NoMergePolicy the same end state was also run with term vectors on the first column alone and on the last alone. That end state needs the root of LFV-096 and is counted there, not here.   • Likelihood: rare (a judgement, not measured). It needs the API, the width and the JVM together. The one use of the API that its author describes on the design thread has about 150 fields of which one is inverted and stored and the rest are doc values (Tim Brooks, dev@lucene.apache.org, 2026-05-06); that use does not reach the block.

Why it looks unintended

#
  • No javadoc limits the number of columns; the block is a growth branch.
  • The outcome follows the JVM, not the input: with compressed references on the full JDK the same batch is indexed.
  • The same kind of defect in another class was fixed as a bug in 2013 (LUCENE-4948), with Uwe Schindler's rule: parallel arrays get one computed size.
The full argument543 words
  • No document limits the number of columns. IndexWriter.addBatch: "Adds a batch of documents in column-oriented format. The batch's columns are processed field-by-field rather than document-by-document." (IndexWriter.java:1528-1539). Neither it nor the two updateDocuments overloads (:1541-1573), ColumnBatch and columns() (ColumnBatch.java:19-43), Column (Column.java:22-32) or the package documentation names a limit; the package documentation lists stored fields among the features of LongColumn, BinaryColumn and DictionaryColumn and term inversion among those of BinaryColumn, DictionaryColumn and TokenStreamColumn (package-info.java:31-50). A word search of the 18 files of the package for "limit", "maximum", "at most" and "too many" finds two sentences, both about other things (one column for each feature of a field; each document at most once in a single-valued column).
  • The block is a growth branch. It grows the arrays for more than four such columns (IndexingChain.java:867-871), and no document names a limit. ArrayUtil.oversize promises "an array size >= minTargetSize" and no more, so equal lengths of separately grown arrays are an assumption of this block alone.
  • The outcome follows the JVM, not the input. The same batch is indexed with compressed references on the full JDK; 38 columns are indexed under the flag; the same 39 fields in one Document through addDocument are indexed under the flag.
  • "Experimental" speaks of API changes. The tag renders as "WARNING: This API is experimental and might change in incompatible ways in the next release." (RenderJavadocPlugin.java:488). #16553, a defect of the same method, is listed under Bug Fixes (lucene/CHANGES.txt:431 and :1007).
  • The same kind of defect was fixed as a bug in 2013, in another class. LUCENE-4948 (#6012): the old PostingsHighlighter grew int arrays and a reference array apart and threw ArrayIndexOutOfBoundsException without compressed references; fixed in 4.3.1. Uwe Schindler explained the mechanism there on 2013-04-22 and stated the rule: "Whenever we use ArrayUtil.grow() we have to take care that the sizes may differ. Please don't change the growing pattern, the code should (when it requires that several arrays are sized in parallel) calculate the new size before and use a suitable type to do that." In a review remark of 2010-10-14 on LUCENE-2690 (#3764) Uwe Schindler wrote of the parallel arrays of that patch: "all should be equal size, so we should only use grow/oversize only for the base array and resize the others to same size." Both items are about other classes and are older than this block; neither is a report of this defect.
  • Lucene's own column batch suites did not meet the block in two runs. On the unchanged tree of main 3cee9ed259e9 the seven suites (167 tests) pass with -XX:-UseCompressedOops and with -XX:+UseZGC in the test JVM (seed DEADBEEF).
  • History. The block came with the first version of the API (#15990; on the 10.x line #16066); #16118 put the third array under the same test. The description, the 7 comments, the 11 reviews and the 20 inline comments of #15990 and the description and the one review of #16066, as read on 2026-11-23, have no sentence on the growth of the block's arrays or on a limit of the number of columns. The description of #16118, as read the same day, names rowPfIndices and not its growth.
The devil's-advocate check163 words

The strongest case for "intended": the API is experimental, and a wide row batch on a JVM without compressed references is not what it was built for (the use its author describes has one stored and inverted field among about 150), so a refusal of such a batch that depends on the JVM is an accepted rough edge.

Why it fails: nothing documents a limit of columns or a dependence on the JVM. The code has a growth branch for exactly this case, and it goes wrong by an assumption about ArrayUtil.grow that was repaired as a bug in another class in 2013. The input is legal and is indexed with compressed references on the full JDK and, field for field, through addDocument. The experimental tag warns of API changes, and another defect of the same method was listed as a bug fix. What the argument does limit is how often the block is reached, which is why the finding is Low.
