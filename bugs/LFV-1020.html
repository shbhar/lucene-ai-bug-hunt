TemporalMergePolicy's javadoc configuration example calls setBaseTimeSeconds, a method that does not exist

The only configuration example in the TemporalMergePolicy javadoc calls .setBaseTimeSeconds(3600), but the setter is setBaseTimeInSeconds(long): it was renamed during review and the example kept the old name. Copied as shown, the example does not compile on any release that has the class (10.5.0 to 10.6.0).

The finding in 30 seconds

#

The example sits in a plain <pre> block of the class javadoc. Javadoc does not compile such blocks, so when the setter was renamed nothing failed, and Lucene's own tests use the new name.

  1. You adopt the time-series merge policy added in Lucene 10.5 and copy the "Configuration:" example from its class javadoc: new TemporalMergePolicy().setTemporalField("timestamp").setBaseTimeSeconds(3600).setMinThreshold(4).setMaxThreshold(8).setCompactionRatio(1.2).
  2. You expect it to compile and give a policy with a 1-hour (3600 s) base window, thresholds 4 and 8 and compaction ratio 1.2, as its comments say.
  3. Instead javac stops with one error: cannot find symbol: method setBaseTimeSeconds(int). The class has no such method; its setter is setBaseTimeInSeconds(long), about 100 lines further down the same file.
  4. The setter was renamed on a reviewer's suggestion while the feature was in review; a commit the same day edited the example three lines below and left this line alone. With setBaseTimeInSeconds(3600) the example compiles and sets exactly the commented values.

Who is affected

#

Developers adopting the opt-in, experimental TemporalMergePolicy who start from its only configuration example: they get one compile error every time, on 10.5.0 to 10.6.0 and main. Documentation only: nothing in Lucene runs differently, and the error names the missing method.

Mechanism, terms and numbers354 words

TemporalMergePolicy (new in 10.5.0, @lucene.experimental) groups segments into time windows for time-series data. Its class javadoc has one "Configuration:" example, a fluent chain setTemporalField("timestamp"), .setBaseTimeSeconds(3600), .setMinThreshold(4), .setMaxThreshold(8), .setCompactionRatio(1.2), followed by IndexWriterConfig.setMergePolicy(policy). The class has no setBaseTimeSeconds method: its base-time setter is setBaseTimeInSeconds(long). Copied into a project, the example fails with the single javac error cannot find symbol: method setBaseTimeSeconds(int), location: class org.apache.lucene.index.TemporalMergePolicy, on 10.5.0, 10.5.1, 10.5.2, 10.6.0 and main. In PR #15620 the setter first had the old name and the example matched; a reviewer suggested the clearer name, the rename went in, and the example kept the old one. With setBaseTimeInSeconds(3600) the example compiles and configures exactly what its comments say. Nothing in Lucene behaves wrongly; only the example is stale.

The real setter

#

public TemporalMergePolicy setBaseTimeInSeconds(long baseTimeInSeconds) (line 159), documented "Default is 3600 seconds (1 hour)." Its getter getBaseTimeInSeconds() (line 172) carries @see #setBaseTimeInSeconds. In Lucene's sources the name setBaseTimeSeconds occurs only on line 61, on main and at every release tag that has the class (10.5.0 to 10.6.0). A bytecode scan of 159 core jars finds that the class declares no setBaseTimeSeconds of any arity in any release, and javac finds no inherited one either.

Why nothing caught it

#

Javadoc does not compile <pre class="prettyprint"> blocks, and the example has no {@link} that javadoc would check. Lucene's tests use the real name: TestTemporalMergePolicy.testMergesWorkWithUncommittedSegments calls .setBaseTimeInSeconds(3600) in a chain of its own, with other values (field timestamp_tl, thresholds 3 and 4, ratio 1.0).

Not claimed

#

The private field baseTimeSeconds (line 102) and the exception text "baseTimeSeconds must be positive" (line 161) still use the old name; neither is public API. The undeclared analyzer is normal for a fragment.

Exposure and likelihood101 words
  • Who. Readers of the TemporalMergePolicy class javadoc who copy its example. No query, document or index file reaches it.
  • Default vs opt-in. The policy is opt-in (set on IndexWriterConfig by the application) and @lucene.experimental. No configuration or special input is involved: the copied example always fails.
  • Scale. One error on every release that has the class: 10.5.0, 10.5.1, 10.5.2 and 10.6.0, and on main.
  • Effect. A compile error, not wrong behaviour. The right name is setBaseTimeInSeconds, listed in the same javadoc page.
  • Priority. Low; the same kind of defect as the stale javadoc examples LFV-1018, LFV-1019, LFV-1021 and LFV-1026.

Why it looks unintended

#
  • The block is headed "Configuration:", nothing marks it as pseudo-code, and every other call in it exists with exactly those types.
  • The PR history shows a missed update: the same day the setter was renamed, a review commit edited the example three lines below and left this line alone.
  • Lucene's own test uses setBaseTimeInSeconds(3600), in a chain with other values.
The full argument208 words
  • Offered as working code. The example is the class's only configuration recipe, under "Configuration:", with no pseudo-code marker.
  • History of PR #15620. In the first PR commit (bd45e5dbce8e, 2026-01-26) the setter was setBaseTimeSeconds(long) and the example matched. 3560f73a24a6 (2026-02-11) applied a reviewer's suggestion (shubhamsrkdev, review comment r2791054529) to rename it setBaseTimeInSeconds. b4bc4b7ff4b4 "Changes per PR review", the same day, replaced .setUseExponentialBuckets(true) in the example with the comment about disableExponentialBuckets() and renamed the @see tag to #setBaseTimeInSeconds; its diff hunk starts at line 61 and shows .setBaseTimeSeconds(3600) as unchanged context. The review's other API change reached the example; the setter rename did not.
  • No record accepts the old name. No CHANGES or MIGRATE text, review comment, issue or list thread mentions it; none of the 38 comments on #15620 mentions the example.
  • Precedent: a stale example fixed as an ordinary doc fix. Issue #12666 (the "Simple example" in the Analyzer class javadoc overrides normalize() without its String fieldName parameter) was closed by PR #12693, "chore: update the Javadoc example in Analyzer", merged by msokolov on 2023-10-18 (commit 6fde1db2281, one javadoc line). Similar outside reports for other classes are open now (issue #16922, PRs #16904 and #16949); LUCENE-8488 (#9534) asks for compile-checked examples in general.
The devil's-advocate check153 words

Strongest case for "noise, not a bug": the block is an illustrative fragment that already uses an undeclared analyzer; the class is @lucene.experimental; 3600 is the default anyway; the error is loud, the right name differs only by "In" and is documented in the same javadoc. A similar javadoc typo (advannceExact in a NumericDocValues example) was set aside as too trivial. The devil's-advocate verifier rated this "moderate" as a triviality argument and "weak" as an intended-behaviour argument.

Why it fails: a reader supplies context such as analyzer, but no context makes a nonexistent method compile. @lucene.experimental allows the API to change; it does not make the shipped example right. The name is API drift from a review rename, not a misspelling, in the only configuration example of a public class shipped in four releases. Every verifier and the adjudication called it real; the adjudication kept it at Low priority.

Suggested fix

#

Recommended Use the real setter name in the example (validated)

Change line 61 of the example to .setBaseTimeInSeconds(3600) (javadoc only, one line). Validated: the patched example compiles on main and on 10.6.0 and sets the commented values, and the 11 TemporalMergePolicy tests pass.
