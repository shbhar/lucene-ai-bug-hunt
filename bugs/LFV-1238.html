HnswGraphSearcher.search throws NegativeArraySizeException for a graph whose maxConn() is HnswGraph.UNKNOWN_MAX_CONN

Since Lucene 10.3.0, HnswGraphSearcher.search throws NegativeArraySizeException: -2 on every search of an HnswGraph with an entry node whose maxConn() returns the public constant HnswGraph.UNKNOWN_MAX_CONN (-1), because it sizes a scratch array as maxConn() * 2. Lucene's own formats report a real maxConn, so only custom graph implementations are hit.

The finding in 30 seconds

#

Lucene's HNSW searcher accepts a graph that reports an unknown maxConn, then uses that value, -1, as an array size.

Background

#
  1. HnswGraph is the public abstract class that Lucene's HNSW search walks. Lucene's vectors formats implement it, and so can your own code, for example an adapter over another library's graph.
  2. maxConn() reports M, the maximum number of links per node. A graph that does not know M can return the public constant HnswGraph.UNKNOWN_MAX_CONN, which is -1.
  3. HnswGraphSearcher.search has two searchers. The filtered one needs M, so a graph that reports -1 always gets the plain one: "We can only use filtered search if we know the maxConn".

The finding, step by step

#
  1. You implement HnswGraph for a tiny graph, one node (node 0) with no links, and return HnswGraph.UNKNOWN_MAX_CONN (-1) from maxConn().
  2. You search it with HnswGraphSearcher.search(scorer, collector, graph, null) for k = 1.
  3. You expect 1 hit, node 0. Lucene 10.2.2 returns it, and so does main when maxConn() returns 16.
  4. Instead every search throws NegativeArraySizeException: -2: since 10.3.0 the plain searcher allocates its bulk-scoring scratch as new int[maxConn() * 2], and -1 x 2 = -2.

Who is affected

#

Only code that implements its own HnswGraph without knowing M (a custom vectors format, or an adapter over another library's graph), reports UNKNOWN_MAX_CONN, and searches it with HnswGraphSearcher.search, on 10.3.0 to 10.6.0 and main. Lucene's own indexing, merges and kNN queries are not affected. Every such search of a graph with an entry node throws; no wrong hit is returned.

Mechanism, terms and numbers424 words

HnswGraph declares the public constant UNKNOWN_MAX_CONN = -1 for a graph that does not know M, and HnswGraphSearcher.search checks for it explicitly: such a graph skips only the filtered searcher ("We can only use filtered search if we know the maxConn") and gets the plain one. Since 10.3.0 the plain searcher sizes its bulk-scoring scratch as graph.maxConn() * 2, so the first search of a graph that reports the constant and has an entry node runs new int[-2] and throws NegativeArraySizeException: -2, with assertions on and off. Lucene 10.2.x searched the same graph fine. No Lucene format, merge or kNN query reaches the path; only HnswGraph implementations from outside Lucene do, and they fail loudly, never with a wrong hit.

Mechanism (main 5adff78bb168, lucene/core/src/java/org/apache/lucene/util/hnsw/)

#
  1. The constant is public API. HnswGraph is a public abstract class with a protected constructor in an exported package (HnswGraph.java:53-57, module-info.java:50). maxConn() "returns M, the maximum number of connections for a node" (:88-89), with no lower bound; HnswGraph.EMPTY returns the constant (:137-140).
  2. The dispatch keeps such graphs on the plain searcher. The filtered searcher is chosen only if graph.maxConn() != HnswGraph.UNKNOWN_MAX_CONN (HnswGraphSearcher.java:133-139); otherwise a plain HnswGraphSearcher is built (:141-144), with or without acceptOrds.
  3. The plain searcher sizes its scratch from maxConn. searchLevel first calls prepareScratchState(size, graph.maxConn() * 2) (:284); for a graph with more than one level, findBestEntryPoint makes the same call before scoring the entry (:223).
  4. The throw. prepareScratchState allocates bulkNodes = new int[bulkScoreSize] when the scratch is missing or too small (:370-373). bulkNodes starts null (:42), so the first search runs new int[-2] (:371). The JVM refuses the allocation before any array exists. Only a graph without an entry node (entryNode() = -1) returns earlier, before the sizing (:218-220, AbstractHnswGraphSearcher.java:77-81).
  5. Why Lucene itself never hits it. Every current format reports its stored M (Lucene99HnswVectorsReader.java:652-653, OnHeapHnswGraph.java:205-206); the reader never runs HNSW search on an empty graph (Lucene99HnswVectorsReader.java:368, :376-378), so HnswGraph.EMPTY is never searched; the Lucene 9.0 backward codec's graph, the only other non-test source of the constant, is searched by its own Lucene90OnHeapHnswGraph.search. One test graph also returns it (TestHnswUtil.MockGraph, TestHnswUtil.java:277-279); it is used only by the HnswUtil tests and never searched.

The same failure happens with acceptOrds set (the filtered searcher is skipped, the plain one throws) and, for a two-level graph, already in the entry-point phase at :223.

Exposure and likelihood213 words
  • Who. Code that implements HnswGraph itself without knowing M and searches it with Lucene's HnswGraphSearcher. No default path: Lucene's formats always report their stored M.
  • Effect. Every search of such a graph that has an entry node throws, from the first call, with assertions on and off. Nothing is written out of bounds, the graph and index are unchanged, and no wrong hit is returned.
  • Scale. Any graph size; one node is enough. With acceptOrds set, and for graphs with more than one level, it throws the same way.
  • Workaround. Report a real value. The scratch holds 2 * maxConn() entries, so any value of at least half the longest neighbour list, rounded up, avoids the exception; for an HNSW graph its M does (level 0 holds up to 2 * M links, HnswGraphBuilder.java:131-132). A real value also makes filtered searches eligible for FilteredHnswGraphSearcher when the strategy picks it (HnswGraphSearcher.java:133-139), and that searcher's exploration is computed from maxConn() (FilteredHnswGraphSearcher.java:51-54): filtered behaviour changes too, and a value that is only a bound, not the graph's M, tunes it from that bound.
  • Likelihood: rare. One known downstream graph adapter returned the constant for a few days under 10.2.1 and switched to a real value before 10.3.0 shipped; no failure was reported.

Why it looks unintended

#
  • The dispatch checks for the constant explicitly ("We can only use filtered search if we know the maxConn") and keeps such graphs on the plain searcher.
  • Only FilteredHnswGraphSearcher asserts a known maxConn; nothing documents that limit for the plain searcher.
  • 10.2.x searched such graphs fine; the sizing came with bulk scoring in 10.3.0 (#14978), never discussing an unknown maxConn.
The full argument194 words
  • Checked explicitly. The dispatch names the constant and excludes it only from filtered search, so such graphs stay on the plain searcher (HnswGraphSearcher.java:133-144); "graph must have known max connections" is asserted only in FilteredHnswGraphSearcher (:51).
  • No restriction anywhere. HnswGraph, HnswGraphSearcher and its public static search methods carry no @lucene.internal or @lucene.experimental tag (only the package-private base AbstractHnswGraphSearcher is experimental). No javadoc, CHANGES or MIGRATE entry says the plain searcher needs a known maxConn.
  • It worked before. #14160 (0614fe9ebd7, 10.2.0) added the constant, made HnswGraph.EMPTY report it and added the dispatch guard; in 10.2.x the plain searcher read maxConn() only in that guard. The same commit made a test graph, TestHnswUtil.MockGraph, return the constant. #14978 (10.3.0) added the maxConn() * 2 sizing and #15500 (10.4.0) widened it; neither review thread mentions an unknown maxConn.
  • Incidental failure. A NegativeArraySizeException from an array allocation, not a validation with a message.
  • Not claimed. Searching HnswGraph.EMPTY directly also throws, but searching an empty graph is meaningless and no reader does it. A graph that reports a maxConn smaller than half its real degree can overflow the same scratch; that graph misreports M.
The devil's-advocate check118 words

maxConn() is documented as "M", the constant has no javadoc and arrived for empty and legacy graphs, no Lucene graph reaches the path, and the failure is loud with an easy workaround, so "report a bound" may be the expected answer. This doc's cross-model fact check rated that case moderate: a maintainer could reasonably close the issue as "report a real M". Why it does not settle it: the dispatch excludes the constant only from filtered search, the plain path worked for it until 10.2.x, and nothing documents the new requirement. These points lower the priority, not the reality. Whether the fix makes it work again or rejects the constant with a clear error is the maintainers' call.

Suggested fix

#

Recommended A. Clamp the initial size at 0 and grow while filling (recommended)

In prepareScratchState, clamp the initial scratch size at 0, and where the scratch is filled, grow bulkNodes and bulkScores when the next neighbour does not fit. The repro passes with assertions on and off, and 218 HNSW and kNN query tests pass.

   private void prepareScratchState(int capacity, int bulkScoreSize) {
     ...
+    // graph.maxConn() may be HnswGraph.UNKNOWN_MAX_CONN (-1): start empty and grow while filling
+    bulkScoreSize = Math.max(0, bulkScoreSize);
     if (bulkNodes == null || bulkNodes.length < bulkScoreSize) {

   // at both fill sites (findBestEntryPoint and searchLevel):
+        if (numNodes == bulkNodes.length) {
+          growBulkScratch(numNodes + 1); // ArrayUtil.grow on bulkNodes, growExact on bulkScores
+        }
         bulkNodes[numNodes++] = friendOrd;
All options and trade-offs3 options · 512 words

Three directions; the choice is the maintainers'. A restores the 10.2.x behaviour, B makes the requirement explicit, C avoids the per-neighbour check but relies on an undocumented method. A is recommended because it restores what 10.2.x did and is the validated option; this doc's cross-model fact check called B the more defensible default for a maintainer and A the more compatible one.

A. Clamp the initial size at 0 and grow while filling (recommended) (validated by the checks)

#

In prepareScratchState clamp bulkScoreSize at 0; at the two fill sites (findBestEntryPoint, searchLevel) grow bulkNodes with ArrayUtil.grow and bulkScores with ArrayUtil.growExact when the next neighbour does not fit. 16 added lines in HnswGraphSearcher.java.

   private void prepareScratchState(int capacity, int bulkScoreSize) {
     ...
+    // graph.maxConn() may be HnswGraph.UNKNOWN_MAX_CONN (-1): start empty and grow while filling

     if (bulkNodes == null || bulkNodes.length < bulkScoreSize) {

   // at both fill sites (findBestEntryPoint and searchLevel):
+        if (numNodes == bulkNodes.length) {
+          growBulkScratch(numNodes + 1); // ArrayUtil.grow on bulkNodes, growExact on bulkScores
+        }
         bulkNodes[numNodes++] = friendOrd;

Trade-offs

Restores the 10.2.x behaviour for the documented constant and keeps the dispatch as it is. It adds one compare per neighbour in the two inner loops; not benchmarked, and SECURITY.md asks that robustness changes not slow hot paths, so a quick benchmark may be wanted. It also changes behaviour on purpose for a graph that reports a real maxConn but has a node with more than 2 * maxConn() new neighbours: that graph no longer throws ArrayIndexOutOfBoundsException in the plain searcher. That is a hardening choice for the maintainers to accept or drop (read, not claimed).

What the checks validated

  • Gradle in a scratch worktree at 5adff78bb168, seed DEADBEEF: the repro fails without the fix (assertions on and off) and passes with it (both).
  • With the fix, assertions on: every org.apache.lucene.util.hnsw test plus TestKnnFloatVectorQuery and TestKnnByteVectorQuery pass (14 classes, 218 tests, 0 failures, 3 skipped), and :lucene:core:checkGoogleJavaFormat passes.
  • The grow path, which the one-node repro does not reach, was exercised by a probe on the same build: a two-node graph with one and with two levels, and with acceptOrds, returns the better node with the fix and throws without it.

B. Reject an unknown maxConn with a clear error

#

Throw IllegalArgumentException at the top of HnswGraphSearcher.search when graph.maxConn() is negative (the constant is -1; testing < 1 would also reject 0, which a graph with no links can report and today's plain path handles), drop the special case in the dispatch, and document that search needs a real M.

Trade-offs

No hot-path cost and a clear message, but it turns the 10.2.x behaviour into a documented error; callers then have to report a bound. Not run.

C. Size the scratch per expanded node from neighborCount()

#

After graphSeek, make sure the scratch holds neighborCount() entries.

Trade-offs

One check per expanded node instead of per neighbour, but neighborCount() has no javadoc, and the on-heap searcher's graphSeek does not move the graph's own cursor, so it is less safe. Not run.

Downstream note

#

Graph adapters that search another library's HNSW graph with Lucene's HnswGraphSearcher need to report a real maxConn() (the graph's M, or at least half the longest neighbour list, rounded up) on 10.3.0 and later until this is fixed.

How it was found

#

A proof-obligation audit of HnswGraphSearcher's contract: because the dispatch sends graphs with UNKNOWN_MAX_CONN to the plain searcher, that searcher must not use maxConn() as a size. The obligation fails at maxConn() * 2; a one-method JUnit test on the public API witnessed it.

The method in full74 words

The obligation: the dispatch (HnswGraphSearcher.java:133-137) sends a graph that reports UNKNOWN_MAX_CONN to the plain searcher, so every use of maxConn() on that path must accept -1. The guard discharges it for the filtered searcher; the sizing at :223 and :284 breaks it for the plain one. A one-method JUnit test on the public API then witnessed the failure on main, and runs on release jars placed the regression between 10.2.2 and 10.3.0.
