IndexWriter.addIndexes admits an index without the parent field, and the next merge closes the writer

A writer configured with setParentField refuses to open an index that lacks the parent field, but addIndexes lets that same index in. The next merge of that segment with the writer's own block-free segments (no index sort) throws IllegalStateException and closes the writer, losing its uncommitted documents, since 9.10.0.

The finding in 30 seconds

#

addIndexes checks each incoming field against the writer's parent-field setting, but a segment without the parent field has no field to check, so nothing rejects it. The next merge with the writer's own segments, when none of them holds document blocks and there is no index sort, builds a merged view that requires one parent field across all segments; that check throws, and IndexWriter treats the exception as tragic.

Background in three steps

#
  1. IndexWriterConfig#setParentField("_parent") (opt-in, since 9.10.0) makes IndexWriter add an internal doc-values field to every root document: the last document of each block, and every single document. Index sorting with document blocks needs it.
  2. Each segment records its parent field in its FieldInfos. A merge expects all the segments it combines to agree on it.
  3. Documents without the marker would later be treated as children, so the IndexWriter constructor refuses to open an existing index without the parent field when the config sets one (#13016).

The finding, step by step

#
  1. Write index A with a default IndexWriterConfig: 1 document, no parent field. new IndexWriter(A, config with setParentField("_parent")) refuses it: "can't add a parent field to an already existing index without a parent field".
  2. Open writer B on an empty directory with the same settings (a new config: a config can be attached to one writer only), add 1 document and call B.addIndexes(A). You expect the same IllegalArgumentException, or a writer that keeps working.
  3. addIndexes returns normally. B now has 2 segments: its own, which declares the parent field _parent, and the copy of A's, which has none.
  4. forceMerge(1) (with default settings, a background merge) throws IllegalStateException: expected parent doc field to be "_parent " across all segments but found a segment with different field "null", and B closes: its uncommitted documents are lost.
  5. After a commit, a writer with the same settings fails that merge again, and one with no or another parent field is refused at open. Readers still see both documents and CheckIndex is clean.

Who is affected

#

Applications that set setParentField without an index sort and call either addIndexes overload with an index written without it (one from before they turned the setting on, or sub-indexes built with a plain config). A background merge under default settings closes the writer; after a commit no writer config can merge that segment with the writer's own block-free segments.

Mechanism, terms and numbers736 words

When an IndexWriterConfig sets a parent field (setParentField, opt-in since 9.10.0), the IndexWriter constructor refuses to open an existing index that lacks that field (#13016). Both addIndexes overloads accept the very same index: they check each incoming field, but never that the parent field is there. The added segment therefore has no parent field while the writer's own segments have one, and the next merge that combines them (an explicit forceMerge, or a background merge under the default merge settings) builds a merged view whose FieldInfos check requires one parent field across all segments. It throws IllegalStateException, IndexWriter treats that as a tragic event, and the writer closes, losing its uncommitted documents. After a commit a writer with the same settings fails that merge again and a writer with no or another parent field is refused at open, so no writer configuration can merge the added segment with the writer's own block-free segments any more. Readers see every document and CheckIndex stays clean. It needs a writer without an index sort and a merge whose segments hold no document blocks, and it affects every release from 9.10.0 through 10.6.0 and main.

The mechanism (main 5adff78bb168)

#
  1. Constructor guard (IndexWriter.java:1125-1131): when the index exists, the config has a parent field, the index has fields and none of them is the parent field, it throws IllegalArgumentException("can't add a parent field to an already existing index without a parent field").
  2. addIndexes(Directory...) (IndexWriter.java:3103-3226) checks the index-created major version (:3131-3138), the index sort (:3154-3159) and, for every field of every incoming segment, the schema through globalFieldNumberMap.addOrGet(fi) (:3177-3182); then it copies the segment as it is (:3183). addIndexes(CodecReader...) (:3275-3297) runs validateMergeReader (version and index sort, :3228-3252) and globalFieldNumberMap.verifyFieldInfo(fi) for every incoming field (:3289-3295).
  3. The per-field parent check, FieldNumbers.verifyParentFieldName (FieldInfos.java:484-509), rejects an incoming parent field when the writer has none (:486-490), one with another name (:491-497) and a regular field named like the writer's parent field, commented "think addIndices" (:499-507). It runs once per incoming field, so a segment that simply has no parent field gives it nothing to check. Nothing else in either overload looks for the parent field.
  4. The merge. Unless the writer has an index sort, or some input has blocks and some input (possibly the same one) lacks the parent field (IndexWriter.java:5543-5554), mergeMiddle builds SlowCompositeCodecReaderWrapper.wrap(mergeReaders) (:5556). Its constructor calls FieldInfos.getMergedFieldInfos (SlowCompositeCodecReaderWrapper.java:96), which calls getAndValidateParentField (FieldInfos.java:209); that throws as soon as two leaves disagree, here "_parent" and null (:220-238, the throw at :226-231; the space before the closing quote in the message comes from there).
  5. The writer closes. IndexWriter.merge passes the exception to tragicEvent(t, "merge") (IndexWriter.java:5108-5112), which rolls the writer back and closes it (:6089-6104).

When it happens, and what is not claimed

#

The merged view is skipped when the writer has an index sort, and when some merged segment has multi-document blocks and some merged segment (possibly the same one) has no parent field (IndexWriter.java:5547-5554, two independent anyMatch checks, #13128). The added segment never has the parent field, so a merge that includes it skips the view as soon as any of its segments holds blocks. So the claimed failure needs a writer without an index sort and a merge whose segments hold no document blocks.

Not claimed (same root, same fix, no wrong user-visible result established): when a merged segment does hold blocks, in the source or in the writer's own segment, the merge skips the check and succeeds, and the added documents sit unmarked in a merged segment that declares the parent field, the state #13016 meant to prevent. Fix A rejects those shapes in addIndexes too. Also not claimed: the index-sort case (the merge takes another path) and an existing field-less index reopened with a parent field (the constructor's #13341 exemption).

Exposure and likelihood373 words
  • Who is hit. Applications that set the opt-in IndexWriterConfig#setParentField without an index sort and call addIndexes(Directory...) or addIndexes(CodecReader...) with a source written without that setting. Two plausible flows: bringing in an index of the same major version written before the application turned the setting on (the constructor refuses to open it with the parent field, so addIndexes looks like the way in), and the parallel batch indexing the addIndexes(Directory...) javadoc describes ("A large document collection can be broken into sub-collections ... The complete index can then be created by merging sub-collection indexes with this method") when the sub-indexes are built with a plain IndexWriterConfig. A parent field without an index sort is a documented setup: CHANGES for #13125 says recursive graph bisection works on indexes with blocks "as long as they configure a parent field via IndexWriterConfig#setParentField" (merges whose segments hold blocks take the silent path instead of the exception).
  • Default merge settings suffice. With the default ConcurrentMergeScheduler and TieredMergePolicy, one recorded run that added and flushed one document at a time saw the first background merge (Lucene Merge Thread #0) throw the same exception, and the writer was closed within 8 adds. When such a merge comes depends on the merge policy and on scheduling (another probe needed about 120 adds).
  • What is lost. The writer closes tragically and loses its uncommitted, already acknowledged documents. After a commit, a writer reopened with the same settings fails the merge again and closes; a writer without a parent field ("... this IndexWriter has no parent document field configured") or with another name ("... this IndexWriter is configured with [other] as parent document field") is refused at open.
  • What is not lost. Readers see every document (2 leaves, parentField=_parent and null) and CheckIndex is clean, so "index unusable" means unusable for further writing with merges, not unreadable.
  • Scale and likelihood. One document per index is enough. It needs the opt-in parent field without an index sort and a source written without it. The downstream servers checked, Solr and OpenSearch, set the parent field together with an index sort, where this path is not taken, and no report of it was found since 9.10.0 (2024), so it is rated rare.

Why it looks unintended

#
  • The constructor refuses this exact state; #13016 added that check "to prevent documents without the parent field from being indexed".
  • addIndexes already rejects every other parent-field mismatch up front (two of them asserted in TestAddIndexes); only a missing one passes.
  • In #12829's review, Michael McCandless wrote that users "should never be able to" trigger the merge-time check; Simon Willnauer agreed.
The full argument254 words
  • The constructor refuses this exact state, and its commit says why (IndexWriter.java:1125-1131). #13016 (340d9d2f9c61, Simon Willnauer, 2024-01-16): "Parent field must be added before any documents are added to the index to prevent documents without the parent field from being indexed and later to be treated as child documents upon merge." addIndexes brings in exactly such documents.
  • addIndexes checks every other parent-field mismatch itself (FieldInfos.java:484-509): another parent-field name, a regular field named like the parent field, and the reverse direction (a source with a parent field into a writer without one). TestAddIndexes#testIllegalParentDocChange (TestAddIndexes.java:1945) and #testIllegalNonParentField (:1998) assert the first two messages for both overloads; the second even uses this bug's shape, a source written without setParentField added to a writer with it, and expects an up-front IllegalArgumentException because of its field-name clash.
  • The merge-time throw is not a designed input check. Reviewing #12829, which added it, Michael McCandless asked on getAndValidateParentField: "As far as we know, users should never be able to do anything that would trigger this? This means we have some bug that allowed broken schema into the index?" (2023-12-23); Simon Willnauer replied "yeah I think so too" (2023-12-27).
  • No documented precondition. The addIndexes(Directory...) javadoc lists its IllegalArgumentException cases (exceeding MAX_DOCS, a mismatched index sort, IndexWriter.java:3100-3101) and requires the same Lucene version (:3095); addIndexes(CodecReader...) lists only MAX_DOCS (:3272-3273). Neither mentions the parent field, and no CHANGES or MIGRATE entry about the parent field mentions addIndexes.
The devil's-advocate check200 words

Strongest case for "intended": setParentField's javadoc speaks of documents "added to the index writer", and #13016 says the parent field "must be added before any documents are added to the index". addIndexes copies segments as they are, so building every source with the same configuration is the caller's job, and bringing in an index without the parent field is the same misuse the constructor forbids, through another door. The failure is loud, not corrupt. A reviewer from another model family raised "callers must make sources match" as its strongest objection.

Why it fails: nothing documents that precondition, and addIndexes checks the other parent-field mismatches itself, up front, so the gap is one-sided, not a policy. The constructor answers the same misuse with an immediate IllegalArgumentException; here the call succeeds and the error comes later, from an unrelated merge, as a tragic close that loses acknowledged documents and leaves a committed index whose added segment no writer config can merge with the writer's own block-free segments. The intended-behaviour devil's advocate and the reviewer from another model family (refute lens) both concluded: real, not intended. A maintainer may still legitimately prefer to document the precondition instead of adding a check.

Suggested fix

#

Recommended A: reject a source without the parent field in both addIndexes overloads (validated)

Reject a source without the parent field in both addIndexes overloads, up front, with an IllegalArgumentException like the constructor's (fix A). The repro then passes, and so do TestAddIndexes, TestIndexSorting, TestIndexWriter and TestIndexWriterReader with assertions on and off. It is stricter than the constructor for documents that have no fields.

      throw new IllegalArgumentException(

    }
  }
All options and trade-offs4 options · 753 words

Fix A closes the gap where the contract (#13016) puts it, at the door, and was validated. B is an alternative that would accept such sources by marking their documents; it was not run. Relaxing the merge-time check, or only documenting the precondition, is not recommended.

A: reject a source without the parent field in both addIndexes overloads (validated) (recommended)

#

When the writer has a parent field, an incoming segment (maxDoc > 0) or reader (numDocs > 0) whose FieldInfos have no parent field is rejected with IllegalArgumentException before anything is copied or registered. addIndexes(Directory...) runs it in a pre-pass over all incoming segments, after the existing non-mutating verifyFieldInfo checks so that TestAddIndexes' messages come before the new rejection; addIndexes(CodecReader...) calls it in its up-front validation loop. +30 lines in IndexWriter.java; the helper is below.

  private void validateIncomingParentField(FieldInfos incoming, int numDocs, String source) {
    if (config.getParentField() != null && numDocs > 0 && incoming.getParentField() == null) {
      throw new IllegalArgumentException(
          "can't add "
              + source
              + " without a parent field to an index configured with ["
              + config.getParentField()
              + "] as parent document field");
    }
  }

Trade-offs

  • Stricter than the constructor for one shape. Since #13341 the constructor accepts an existing index whose documents have no fields; this guard rejects any non-empty source without the parent field, field-less ones included. Mirroring #13341 would not be safe: an existing field-less index reopened with a parent field hits the same merge exception after one more document (a separate constructor path, not part of this bug). The maintainers may prefer to tighten the constructor too.
  • addIndexes(Directory...) reads each incoming segment's FieldInfos once more, so a rejection happens before any field is registered in the writer's global field map or any file is copied.
  • It also rejects sources whose blocks would merge silently today (the "not claimed" case under the mechanism).
  • Fully deleted sources. The Directory overload tests maxDoc > 0 (that overload copies a segment as it is, deletions included); the CodecReader overload tests numDocs > 0 (that overload merges only live documents and drops empty segments, IndexWriter.java:3262). So a source segment whose documents are all deleted is rejected by the first and not by the second.
  • Order of checks. The Directory pre-pass runs before the existing per-segment index-sort check (IndexWriter.java:3154-3159). For a writer with a parent field, a source with both an index-sort mismatch and a schema or parent-field mismatch now fails with the schema or parent-field message instead of the index-sort one.

B: mark the incoming documents as roots (not run)

#

A source without blocks (LeafMetaData#hasBlocks() == false) consists of root documents only, which setParentField's javadoc calls parent documents, so addIndexes could add the parent field to every incoming document instead of rejecting the source. That reading of hasBlocks() holds for segments written by Lucene 9.9.0 or later; the flag is not recorded for older segments (LeafMetaData.java:34-38), and custom LeafReaders set it themselves, so it is not an API guarantee.

Trade-offs

Works only for sources without blocks (with blocks the parents cannot be told apart without the field); addIndexes(Directory...) copies files as they are, so it would have to rewrite such segments; more code and a new behaviour to specify.

Relax the merge-time check (not recommended)

#

Let getAndValidateParentField accept segments without the parent field.

Trade-offs

Puts unmarked documents into a merged segment that declares the parent field, the state #13016 prevents and the silent block case already shows.

Document the precondition only (not recommended)

#

Say in both addIndexes javadocs that sources must carry the writer's parent field.

Trade-offs

No code change, but the delayed tragic close stays.

Downstream note

#

A product that restores or combines indexes through addIndexes into a writer with a parent field would see a later merge close that writer.

How it was found

#

Semi-formal: while modelling how addIndexes composes with index sorting and the parent field, the constructor's parent-field check had no counterpart in addIndexes. A bounded-exhaustive model-based test on the real jar then hit the merge failure, and a model-based test of document blocks hit it too. It was reduced to one JUnit test.

The method in full130 words

Method: semi-formal. The hypothesis came from modelling addIndexes composed with index sorting and the parent field: the IndexWriter constructor refuses an index without the parent field, but nothing in addIndexes checks that an incoming segment has it. That model's bounded-exhaustive model-based test witnessed it on the stock main jar (first executed witness 2026-11-08), and a model of document blocks hit the same failure with its own model-based test. It was then reduced to the one-test JUnit above.

Checks after that: a separate AI tool reproduced it with its own test written from the claim only, an intended-behaviour devil's advocate looked for a reading that makes it intended, and an independent reviewer from another model family (OpenAI GPT-5.6) tried to refute it with its own executed tests; an adjudication confirmed it.

LFV-1400, snapshot of 2026-11-08

Registry title
IndexWriter.addIndexes (both overloads) accepts an index without the parent field into a writer configured with IndexWriterConfig#setParentField, although the IndexWriter constructor refuses such an index; the next merge of an added segment with the writer's own segments that hold no document blocks throws IllegalStateException and closes the writer, and after a commit that merge fails again under every writer configuration (since 9.10.0)
Area
index / IndexWriter.addIndexes validation vs. IndexWriterConfig#setParentField (document blocks, parent field) and the merge-time parent-field check (FieldInfos.getAndValidateParentField through SlowCompositeCodecReaderWrapper in IndexWriter.mergeMiddle)
Priority
Medium, rank 161: Since 9.10.0, addIndexes accepts a source index written without the parent field into a writer that has the opt-in setParentField and no index sort, and the next merge of an added segment with the writer's segments that hold no document blocks throws, closes the writer and loses its uncommitted documents; after a commit, every writer configuration either fails that merge again or is refused at open, although readers still see every document. It is Medium because this lasting merge failure comes from the core addIndexes API with default merge settings and needs no scale or fault, and it is rare because the downstream servers checked set the parent field only together with an index sort.
Impact class
index unusable
Impact note
Hits applications that set the opt-in IndexWriterConfig#setParentField without an index sort and call addIndexes(Directory...) or addIndexes(CodecReader...) with a source index written without that setting (for example an index of the same major version written before the application turned the setting on, or sub-indexes built with a plain IndexWriterConfig for the parallel batch indexing that the addIndexes javadoc describes); addIndexes returns normally, and the next merge that combines an added segment with segments of this writer that hold no multi-document blocks (forceMerge, or with the default merge scheduler and policy the first natural background merge) throws IllegalStateException and closes the writer, losing its uncommitted documents; after a commit a writer with the same config fails that merge again and a writer with no or another parent field is refused at open; readers see every document and CheckIndex stays clean, and no scale is needed.
Summary
You write a small index with a default IndexWriterConfig, open a second writer configured with setParentField("_parent"), add one document and call addIndexes with the first index. You expect addIndexes either to reject the source with an IllegalArgumentException, as new IndexWriter on that index with the same config does ('can't add a parent field to an already existing index without a parent field'), or the writer to keep working. Instead addIndexes returns normally and the next merge of the two segments (forceMerge(1) in the repro) throws IllegalStateException 'expected parent doc field to be "_parent " across all segments but found a segment with different field "null"', which IndexWriter treats as tragic, so the writer closes and its uncommitted documents are lost.
