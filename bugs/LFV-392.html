BytesRefArray.iterator(Comparator) throws NullPointerException for a null comparator instead of iterating in append order

BytesRefArray.iterator(Comparator) documents that a null comparator returns the values in append order, but since 8.5.0 it always sorts, so with 2 or more values a null comparator throws NullPointerException. Lucene never supplies one; only applications passing null, directly or via InMemorySorter or OfflineSorter, are hit.

The finding in 30 seconds

#

Background: BytesRefArray and its iterators

#
  1. BytesRefArray is an internal, append-only list of byte strings (BytesRef). Lucene uses it as an in-memory buffer, for example in OfflineSorter and when buffering doc-values updates.
  2. It has three iterators. iterator() returns the values in append order. iterator(Comparator) returns them sorted by the comparator, or, by its javadoc, in append order when the comparator is null. iterator(SortState) replays a sort computed earlier, or append order for null.
  3. Sorting goes through StringSorter: a radix sort for a BytesRefComparator, otherwise a comparison sort that calls the comparator on pairs of values.

The finding, step by step

#
  1. Append two values to a BytesRefArray, b then a, and call array.iterator((Comparator<BytesRef>) null). The cast is needed: since 8.5 a bare iterator(null) does not compile, because two overloads match.
  2. You expect b, then a. The javadoc says "If a non null Comparator is provided the iterator will iterate the byte values in the order specified by the comparator. Otherwise the order is the same as the values were appended." Releases 8.0.0 to 8.4.1 do exactly that.
  3. Instead the call throws NullPointerException: Cannot invoke "java.util.Comparator.compare(Object, Object)" because "this.val$cmp" is null, from StringSorter, with assertions on and off.
  4. Why: the body is return iterator(sort(comp, false)); (BytesRefArray.java:200), a sort even for null. A null comparator falls to StringSorter's comparison sort, which calls cmp.compare on the first pair (StringSorter.java:102). With 0 or 1 values nothing is compared, so it takes 2.
  5. LUCENE-9228 (8.5.0) removed the old comp == null ? null : sort(comp) check and left the javadoc as it was. Every release from 8.5.0 to 10.6.0 throws; the no-arg iterator() is not affected.

Who is affected

#

Only an application that itself supplies a null comparator ("no sorting") on 2 or more values: to this internal utility, or to the internal InMemorySorter or OfflineSorter, which pass it on. Lucene's own code never does; no null call of BytesRefArray.iterator was found in Solr, Elasticsearch or OpenSearch. The call fails at once; no results are wrong. Rare.

Mechanism, terms and numbers618 words

BytesRefArray (core, @lucene.internal, @lucene.experimental) is an append-only list of byte strings. Its iterator(Comparator) javadoc says a non-null comparator gives sorted order and otherwise "the order is the same as the values were appended" (BytesRefArray.java:192-194), and iterator() is documented as "sugar for iterator(Comparator) with a null comparator" (:183). Since 8.5.0 the body is an unconditional sort, return iterator(sort(comp, false)); (:200). A null comparator is not a BytesRefComparator, so StringSorter takes its comparison sort, which calls cmp.compare at the first comparison (StringSorter.java:52-57, :102): with 2 or more values the call throws NullPointerException; with 0 or 1 values nothing is compared. Until 8.4.1 the body was comp == null ? null : sort(comp), and iterator() itself called iterator(null), so this path ran on every iterator() call for 8 years; LUCENE-9228 (a0b8f5c7c28, a doc-values update performance change) removed the check, moved iterator() to a new iterator((SortState) null) overload and left both javadocs unchanged. No Lucene code supplies a null comparator (OfflineSorter and InMemorySorter pass on the comparator they were built with, never null in the tree, and FieldUpdatesBuffer passes a SortState), so it went unnoticed; an application can still reach it by giving either sorter a null comparator. Executed: 8.0.0-8.4.1 iterate in append order, every release from 8.5.0 to 10.6.0 and main throws. A one-line null check restores the documented behaviour; correcting the javadoc is the alternative a maintainer may prefer.

Terms

#
  • BytesRefArray (org.apache.lucene.util, core): an append-only list of BytesRef values stored in a ByteBlockPool. Marked @lucene.internal and @lucene.experimental (BytesRefArray.java:29-30).
  • StringSorter (org.apache.lucene.util, core): the sorter BytesRefArray.sort uses since 9.9.0 (#12591). It radix-sorts when the comparator is a BytesRefComparator and otherwise falls back to an IntroSorter that calls the comparator.
  • SortState: the result of BytesRefArray.sort(comp, stable), a permutation that iterator(SortState) replays.

The bug

#
  1. iterator(Comparator) (BytesRefArray.java:198-201) is return iterator(sort(comp, false)); (:200). Nothing checks for null.
  2. sort(comp, stable) (:128-180) fills a local int[] orderedEntries = new int[size()] (:129), wraps it in new StringSorter(comp) (:164; StableStringSorter at :136 when stable) and calls sorter.sort(0, size()) (:179).
  3. StringSorter.sort (StringSorter.java:52-57) radix-sorts only if (cmp instanceof BytesRefComparator bCmp); null is not an instance of anything, so it calls fallbackSorter(cmp).sort(from, to) (:56). The fallback IntroSorter's compare (:98-103) calls cmp.compare(scratchBytes1, scratchBytes2) (:102).
  4. For 2 values IntroSorter goes straight to insertion sort (IntroSorter.java:128), whose first step compares values 0 and 1 (Sorter.java:244): NullPointerException. With 0 or 1 values no pair is compared, so no exception.
  5. The append-order code is one overload away: iterator(SortState) (:209-211) uses indices = sortState == null ? null : sortState.indices, with the same null rule in its javadoc (:203-207), and iterator() calls it with (SortState) null (:185). iterator(Comparator) just never routes null there.
  6. Since 8.5 a bare array.iterator(null) does not compile: javac reports "reference to iterator is ambiguous ... both method iterator(Comparator<BytesRef>) in BytesRefArray and method iterator(SortState) in BytesRefArray match". A caller reaches the bug with a typed null: a cast, or a Comparator variable that is null when no order is wanted.

The numbers

#

Two values b, a: iterator((Comparator<BytesRef>) null) throws on main, 10.6.0, 10.5.2 and 9.12.3, with assertions on and off. The history probe (values c, a, b) prints cab on all 8 releases from 8.0.0 to 8.4.1 (and on 4.8.0 and 7.7.3) and throws on all 52 releases from 8.5.0 to 10.5.2. The no-arg iterator(), a null comparator on 0 or 1 values, and any non-null comparator work.

Exposure and likelihood415 words
  • Who is hit. Code that uses BytesRefArray directly and passes a null comparator to mean "append order", as the javadoc invites, on 2 or more values. For example (illustrative, not found in any project): a helper that takes an optional Comparator<BytesRef> order and calls array.iterator(order), or code written for 8.4 or earlier as array.iterator(null), which stopped compiling in 8.5 and was fixed with a (Comparator<BytesRef>) cast.
  • Also hit, indirectly. Code that builds an InMemorySorter (suggest module) or an OfflineSorter with a null comparator. Both store it without a check and pass it on to iterator(Comparator) (InMemorySorter.java:38-39, :51; OfflineSorter.java:219-221, :268, :637), so new InMemorySorter(null) and new OfflineSorter(dir, "tmp", null).sort(...) on b, a throw the same NullPointerException (executed on main, assertions on and off). Both classes are @lucene.internal and @lucene.experimental, and their constructors are documented as "sorting entries by the provided comparator" and "with a custom comparator", so a null there is outside their own documented use.
  • What happens. That one call fails at once with an internal NullPointerException from StringSorter, which points at the sorter, not at the argument.
  • What does not happen. No wrong results, no hang, no lasting resource use: before it throws, the call allocates a temporary int[size()] and a sorter (:129, :164), which become garbage. sort only permutes that local orderedEntries array, so the array's pool, offsets and size are untouched and it stays usable: after the exception on c, a, b, size() is still 3, iterator() gives cab, a naturalOrder() iterator gives abc, and a further append works (executed, assertions on and off). No index is written from this path.
  • No Lucene code supplies a null comparator. OfflineSorter passes its configured comparator (OfflineSorter.java:637), and every new OfflineSorter( in the tree gives it a non-null one (the default naturalOrder(), BytesRefComparator.NATURAL or a suggester comparator); InMemorySorter passes its constructor's comparator (InMemorySorter.java:51), and both in-tree constructions use Comparator.naturalOrder() (main source FSTCompletionBuilder.java:133, test TestBytesRefSorters.java:56); FieldUpdatesBuffer sorts with BytesRefComparator.NATURAL and iterates with iterator(SortState) or iterator() (FieldUpdatesBuffer.java:226, 234, 325-328). No test or main source in the tree calls iterator with a null comparator.
  • Default vs opt-in, scale. Opt-in: the application itself supplies the null comparator, to this internal utility or to one of the two internal sorters above. Any 2 values trigger it; data size plays no part. Likelihood: rare. No report of it since 8.5.0 (2020) was found (see Prior reports).

Why it looks unintended

#
  • Its own javadoc: a non-null comparator sorts, "Otherwise the order is the same as the values were appended"; iterator() is "sugar for iterator(Comparator) with a null comparator".
  • It worked from 2012 to 8.4.1; LUCENE-9228, a performance change, dropped the null check and left the javadoc unchanged.
  • Nothing says the exception is intended: no test, review comment or migration note.
The full argument241 words
  • Contract, this exact method. iterator(Comparator): "If a non null Comparator is provided the iterator will iterate the byte values in the order specified by the comparator. Otherwise the order is the same as the values were appended." (BytesRefArray.java:192-194). iterator(): "sugar for iterator(Comparator) with a null comparator" (:183). iterator(SortState) states the same null rule (:203-207). No @throws, nothing says null is rejected.
  • History: the null path worked for 8 years; then LUCENE-9228 changed it without updating the javadoc. f303bcd4650 (LUCENE-3807, 2012-03-02) wrote comp == null ? null : sort(comp) together with this javadoc (then BytesRefList in the suggest module; in core as BytesRefArray since 4.8.0). Until 8.4.1, iterator() was literally return iterator(null);, so every iterator() call used the null path. a0b8f5c7c28 (LUCENE-9228, "Sort dvUpdates by terms before apply", 2020-02-20) replaced the body with an unconditional sort, sent iterator() to the new iterator((SortState) null) and left both javadocs unchanged. After that no in-tree caller or test passed null, which is why nothing caught it.
  • No sign of intent. The review (apache/lucene-solr#1263), the issue (#10268) and the later rewrite #12591 do not mention null comparators; CHANGES.txt and MIGRATE.md say nothing about it. That shows nobody documented or discussed a change to the null contract; it does not prove the change was an accident.
  • Tests. No upstream test passes a null comparator; TestBytesRefArray uses iterator(), a non-null comparator (TestBytesRefArray.java:93-95) and iterator(SortState).
The devil's-advocate check205 words

The strongest case for "not a bug" (the intended-behaviour checker's and the cross-model refute reviewer's): BytesRefArray is @lucene.internal and @lucene.experimental; the package-private interface it implements only says "Sort all values by the provided comparator and return an iterator over the sorted values" (SortableBytesRefArray.java:32-33); the sibling FixedLengthBytesRefArray.iterator documents no null case (FixedLengthBytesRefArray.java:153-162) and also sorts unconditionally (:166), so a null comparator throws the same NullPointerException there on 2 values (executed); and no Lucene code supplies null. So the null sentence may be a stale leftover and this a documentation defect.

Why it fails: the public javadoc of this exact method, and of iterator(), state the null behaviour and its result; the behaviour was implemented and exercised from 2012 to 8.4.1; it changed in a performance commit that updated neither javadoc and recorded no contract change; and @lucene.internal means the API may change between releases, not that a method may contradict its current javadoc. The sibling's behaviour supports the stale-leftover reading, but it does not change what this method's own javadoc promises. Residual: a maintainer may still prefer to drop the null case and fix the javadoc (option B). That is a choice of fix, not "works as designed".

Suggested fix

#

Recommended A. Restore the null check in iterator(Comparator) (append order for null)

Restore the null check that 8.4.1 had: return iterator(comp == null ? null : sort(comp, false)); in BytesRefArray.iterator(Comparator). A null comparator then gives append order again, as documented. With it the repro passes with assertions on and off, and the closest core suites, the FST suggester tests and core's static checks pass.

Trade-offs

  • Restores the documented behaviour of 2012 to 8.4.1 and makes iterator() truly "sugar for iterator(Comparator) with a null comparator" again; no javadoc change needed.
  • No change for any non-null comparator, which is every in-tree caller.
  • Cost: one null check per call; a null call also skips the int[size()] allocation and the sort.
  • It keeps a null-means-unsorted convention that the sibling FixedLengthBytesRefArray and the package-private SortableBytesRefArray interface do not have.
  • Coverage: the minimal test checks 2 values; the fix covers every size by construction, because a null comparator skips sort and goes to iterator((SortState) null), which iterates in append order (BytesRefArray.java:209-211, code reading).

B. Drop the null case and correct the javadoc

#

Reword iterator(Comparator) to say the comparator must not be null and point append-order callers to iterator(); reword iterator() to describe append order directly; optionally add Objects.requireNonNull(comp, "comp") at the top of iterator(Comparator).

Trade-offs

  • Matches what 8.5.0 to 10.6.0 already do with 2 or more values, and the comparator-only wording of SortableBytesRefArray and FixedLengthBytesRefArray (neither says null is allowed or rejected; FixedLengthBytesRefArray throws the same NullPointerException for it).
  • Removes a documented feature (of an internal API, so allowed between releases) instead of restoring it.
  • With requireNonNull, a null call on 0 or 1 values, which works today, would start to throw; without it, the failure stays an obscure NPE inside StringSorter.
  • The regression test becomes an expectThrows(NullPointerException.class, ...).

Downstream note

#

A code search found no null-comparator call of BytesRefArray.iterator(Comparator) in Solr, Elasticsearch or OpenSearch; applications that pass null to get append order can call the no-arg iterator() instead, which works on every version.

How it was found

#

Non-formal: code reading. While an AI tool wrote a reference model of BytesRefArray from its javadoc (the model itself only tried non-null comparators), it noticed that iterator(Comparator) sorts even when the comparator is null. A public-API JUnit test on the stock jars then showed the exception.

The method in full142 words
  • Method: code reading, the hunt's non-formal tier, in the hunt unit on indexing-time pools (BytesRefHash, byte pools, BytesRefArray). The unit wrote a javadoc-derived reference model for BytesRefArray and compared it with the real class. That differential only exercised non-null comparators, so it did not find this; reading iterator(Comparator) while writing the model's null case showed the unconditional sort.
  • Witness: a JUnit test on the stock main jar (three values c, a, b, plus a no-arg iterator() control) failed with the NPE while the control passed; a shadowed one-line fix made it pass.
  • Later: an independent reproducer, an intended-behaviour devil's advocate, cross-model reviews and an adjudication checked it (2026-10-26); the history was bisected by execution over 60 releases; the test was reduced to one test method on two values (2026-10-29) and re-verified on main 645d4fe14a20.

LFV-392, snapshot of 2026-11-05

Registry title
BytesRefArray.iterator(Comparator) throws NullPointerException for a null comparator once the array holds 2 or more values, instead of iterating in append order as its javadoc says (regression since 8.5.0, LUCENE-9228)
Area
util / BytesRefArray (iterator(Comparator) with a null comparator)
Priority
Low, rank 1132: The internal BytesRefArray API throws NullPointerException at once, and only for an explicit typed null comparator that no known caller passes, so it is a contract-only edge case.
Impact class
minor
Impact note
Only code that supplies a null comparator on an array of 2 or more values is hit, directly to the @lucene.internal/@lucene.experimental BytesRefArray.iterator(Comparator) or to an InMemorySorter or OfflineSorter built with a null comparator, which pass it on (executed on main 645d4fe14a20, 2026-11-01), and it gets an immediate NullPointerException (never wrong results, a hang or an index change); no Lucene caller passes null (OfflineSorter and InMemorySorter pass their configured comparator, FieldUpdatesBuffer and the no-arg iterator() use iterator(SortState)), so default indexing, search, merging, doc-values updates and suggester builds never reach it, no use was found in Solr, Elasticsearch or OpenSearch, and every release from 8.5.0 to 10.6.0 is affected.
Summary
You append two or more values (for example c, a, b) to a BytesRefArray and call iterator((Comparator<BytesRef>) null), expecting the values back in append order, as the method's javadoc promises ('Otherwise the order is the same as the values were appended') and as Lucene 8.4.1 and earlier do. Instead the call throws NullPointerException ('Cannot invoke Comparator.compare ... because this.val$cmp is null', from StringSorter$1.compare via BytesRefArray.sort), because the method now always sorts with the given comparator; with 0 or 1 values, or with the no-arg iterator(), append order still comes back. The one-line fix restores the pre-8.5 null check ('return iterator(comp == null ? null : sort(comp, false));'); a maintainer may instead prefer to correct the javadoc.
Introduced
a0b8f5c7c28bd897bdf48ed7af20b385a236b3a9 'LUCENE-9228: Sort dvUpdates by terms before apply' (by GitHub dnhatn; issue apache/lucene#10268; reviewed in apache/lucene-solr#1263 and committed directly; branch_8x backport 83ccb8d2a2204c78de0cf119d63ef452ef95fcc6, same diff, first released in 8.5.0): it removed 'final int[] indices = comp == null ? null : sort(comp);', made iterator(Comparator) sort unconditionally, sent iterator() to the new iterator((SortState) null) overload and left the iterator(Comparator) javadoc unchanged [read: git log -S and git show in the full-history clone; exec: 8.4.1 passes, 8.5.0 fails]. 3cb71436a7b (apache/lucene#12591, 9.x backport 7c1d1147beb, first in 9.9.0) rewrote the body to 'return iterator(sort(comp, false));' through StringSorter and kept the defect (the NPE frame moved from BytesRefArray$1.compare to StringSorter$1.compare, executed at 9.8.0 -> 9.9.0).
