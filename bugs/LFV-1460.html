TimSorter's merge gallop overflows int, so timSort of more than 2^30 elements can throw IndexOutOfBoundsException

Sorting more than 2^30 (about 1.07 billion) elements with CollectionUtil.timSort, where a short run sits before a long sorted run of smaller values, makes TimSorter's merge double its probe index past the int maximum. The index wraps negative, still passes t < to, and the sort throws IndexOutOfBoundsException.

The finding in 30 seconds

#

One sort of more than 2^30 elements, shaped as a short run followed by a long sorted run of smaller values, makes TimSorter's merge probe a negative slot.

Background: how TimSort merges and gallops

#
  1. TimSort splits the input into runs that are already sorted and merges neighbouring runs. CollectionUtil.timSort gives the merge a temp buffer of n / 64 slots.
  2. To merge a short left run with a long right run, it copies the short run into the temp buffer and refills the slice, each time taking the smaller head element of the two runs.
  3. When the right run keeps winning, the merge gallops: it probes 1, 3, 7, 15, ... slots ahead, doubling the step, to find in a few comparisons how far it can copy in one go. A Java int holds at most 2,147,483,647.

The finding, step by step

#
  1. You sort a list of 1,073,741,896 Booleans (2^30 + 72) with CollectionUtil.timSort in natural order: 64 true values, then 1,073,741,832 false values.
  2. You expect 1,073,741,832 false values followed by the 64 true values.
  3. TimSort merges the two runs. It sets the 64 true values aside and, since every false comes first, gallops through the false run, probing slots 73, 75, 79, 87, ... with a step that doubles each time, in int.
  4. From slot 1,073,741,895 (the last one) the step is 2^30: 1,073,741,895 + 1,073,741,824 = 2,147,483,719, past the int maximum 2,147,483,647, so it wraps to -2,147,483,577.
  5. The loop check t < to accepts the negative index, the sorter asks the list for that slot, and the sort throws IndexOutOfBoundsException: Index -2147483577 out of bounds for length 1073741896. With one element fewer it sorts correctly.

Who is affected

#

Code that runs CollectionUtil.timSort, ArrayUtil.timSort or its own TimSorter on more than 2^30 (about 1.07 billion) elements, where a short run precedes a longer sorted run of smaller values. Default code path, no option involved. Index sorting of a segment with more than 2^30 documents uses the same merge (by reading, not run).

Mechanism, terms and numbers628 words

TimSorter (behind CollectionUtil.timSort and ArrayUtil.timSort, and the base of index sorting's DocValueSorter) merges runs with a galloping search. In lowerSaved3 it probes t = from + 2^k - 1 and advances with t += delta << 1 in int (TimSorter.java:344). Nothing checks that addition. When a gallop that starts at slot s >= 1 has to run 2^30 slots, the next probe is s + 2^31 - 1, which wraps to a negative int; while (t < to) accepts it and compareSaved(val, t) (:339) reads that slot.

On a RandomAccess list of 64 true values followed by 2^30 + 8 false values, the merge saves the 64 true values, copies 8 false values down, gallops from slot 72 and asks for slot -2,147,483,577: the list throws IndexOutOfBoundsException, with assertions on and off. Because the throw comes in the middle of the merge, the list is left with 56 of its 64 true values (the other 8 are only in the sorter's temp buffer); that is a consequence of the exception, not a separate claim. The JDK's java.util.TimSort clamps the same step (if (ofs <= 0) // int overflow). The code dates from LUCENE-4946 (2013); every release from 4.4.0 to 10.6.0 and main is affected.

  1. CollectionUtil.timSort (CollectionUtil.java:163-167) runs new ListTimSorter<>(list, comp, list.size() / 64).sort(0, size): 1,073,741,896 / 64 = 16,777,217 temp slots.
  2. TimSorter.sort (TimSorter.java:196-208) finds two runs, [0, 64) and [64, n), and exhaustStack (:155-159) calls merge(0, 64, n) (:179-193).
  3. merge keeps lo = 0 and hi = n (:183-184). The right run (1,073,741,832) is longer than the temp buffer, the left run (64) fits, so it calls mergeLo(0, 64, n) (:188-189).
  4. mergeLo (:241-271) saves the 64 true values (save(lo, len1), :244), copies 8 false values to slots 0-7 (:245, :249-259, until MIN_GALLOP = 7, :46) and gallops with lowerSaved3(72, n, 0) (:261).
  5. lowerSaved3 (:336-347) probes t = 72 + 2^k - 1 = 73, 75, 79, ...; each probe sees false < true, so it advances with delta = t - f; f = t; t += delta << 1; (:342-344).
  6. At t = 1,073,741,895 the step is 2^30 and the sum 2,147,483,719 wraps to -2,147,483,577. while (t < to) (:338) accepts it, and compareSaved(val, t) (:339) calls list.get(-2147483577) (CollectionUtil.java:121), which throws as the List contract requires.

General condition: one gallop in mergeLo starts at a slot s >= 1 and the first 2^30 slots from s all sort before the saved element, which needs a run of more than 2^30 elements. From s = 0 the probes are 2^k - 1, and the last value t reaches is exactly Integer.MAX_VALUE: it does not wrap, and it ends the loop without being probed. With 2^30 + 71 elements the last step lands exactly on t == to, which ends the loop, and the sort completes (executed). The downward gallops lower2 and upperSaved3 cannot wrap. Sorter.upper2 (Sorter.java:165-176, step at :173), the left-run gallop merge calls at TimSorter.java:183, has the same unchecked step; it wraps only for a left run longer than 2^30 that starts above slot 0. No public entry point reached it in our runs; a direct call of the package-private TimSorter.merge(1, 2^30 + 2, 2^30 + 3) on a synthetic TimSorter subclass (left run 0, ..., 0, 2, right run 1) makes upper2 ask compare for slot -2,147,483,648 (1 + 2^31 - 1 wraps to -2^31) at Sorter.java:168, before any element moves, with assertions on and off (executed).

Exposure and likelihood218 words
  • Entry points: CollectionUtil.timSort (executed) and ArrayUtil.timSort (ArrayUtil.java:566-569, new ArrayTimSorter<>(a, comp, a.length / 64); by reading, a real array of that size needs more than 4 GB of heap), and any TimSorter subclass whose shorter run fits in its temp slots (otherwise merge uses mergeInPlace).
  • In-tree, by reading: index.Sorter.DocValueSorter extends TimSorter with docs.length / 64 temp slots (index/Sorter.java:85-92) and sorts [0, maxDoc) (:154); it is reached from SortingCodecReader.wrap over an existing segment (SortingCodecReader.java:445-446) and from the sort at flush of an index-sorted writer (IndexingChain.java:251-299). A segment may hold up to IndexWriter.MAX_DOCS = 2,147,483,519 documents (IndexWriter.java:208); whether one flush can buffer more than 2^30 documents under the per-thread RAM limit was not checked. Not executed.
  • Effect: a loud IndexOutOfBoundsException (ArrayIndexOutOfBoundsException for array-backed sorters, by reading). In the in-tree sorters (ListTimSorter, ArrayTimSorter, index.Sorter.DocValueSorter, FreqProxTermsWriter's DocOffsetSorter) the wrapped index goes to a bounds-checked Java access. The list or array being sorted is left without some of its elements (8 of 64 in the repro).
  • Likelihood: contrived. It needs more than 2^30 elements in one sort and this run shape; the searches below found no report of it since 2013. The repro itself is cheap: about 200 MB of heap and seconds.

Minimal repro

#

One JUnit test, public API only: CollectionUtil.timSort on a compact RandomAccess list of 2^30 + 72 Booleans (64 true, then false), stored in a FixedBitSet. About 200 MB of heap, deterministic, single thread.

Expected
The list comes back sorted (1,073,741,832 false, then 64 true), so the first true is at slot 1,073,741,832.
Observed
IndexOutOfBoundsException: Index -2147483577 out of bounds for length 1073741896 from TimSorter.lowerSaved3(TimSorter.java:339), with assertions on and off.

All files of this repro: repro/LFV-1460/

More files, environment, full output221 words

Why this input: Boolean values in a FixedBitSet keep the list compact (the bits take about 134 MB, the sorter's temp buffer of 16,777,217 references most of the rest); the 64 true values form the short left run; after that head, 2^30 + 8 false values are the smallest right run whose gallop crosses 2^30 slots (2^30 + 7 sort correctly). The final assertion checks that the first true sits at slot size - 64; on stock Lucene the sort throws before it.

Under Gradle's test JVM flags (-XX:TieredStopAtLevel=1) the test fails after about 28 s and, with the fix, passes in about 45 s; a plain JVM run fails in about 4.6 s. The default 512 MB test heap is enough. As a regression test it is this same test; given its run time, upstream may prefer it @Nightly, like TestTimSorterWorstCase.

Why it looks unintended

#
  • CollectionUtil.timSort and Sorter.sort promise to sort the list or the slice; no size limit is documented.
  • The JDK's TimSort clamps this exact step on int overflow; TimSorter's javadoc lists no size limit among its differences from TimSort.
  • A similar large-input TimSorter exception (LUCENE-6293) was fixed as a bug.
The full argument222 words
  • Contract. CollectionUtil.timSort "Sorts the given random access List using the Comparator" and documents only IllegalArgumentException for a non-random-access list (CollectionUtil.java:155-162). Sorter.sort sorts "the slice which starts at from (inclusive) and ends at to (exclusive)" (Sorter.java:75-79), and checkRange rejects only to < from (:81-86). No javadoc, CHANGES.txt or MIGRATE.md text sets a 2^30 limit.
  • Reference behaviour. TimSorter's javadoc names its differences from the original TimSort: configurable temp memory, and only the fast merge gallops (TimSorter.java:28-37). The JDK's implementation of the same algorithm guards this step in all four gallop loops: ofs = (ofs << 1) + 1; if (ofs <= 0) // int overflow ofs = maxOfs; (java/util/TimSort.java:552, 567, 623, 639, OpenJDK 25.0.3).
  • Tests. Upstream sorter tests use small inputs; the largest, the @Nightly TestTimSorterWorstCase, sorts 140 to 400 million elements (TestTimSorterWorstCase.java:26-36), below 2^30. The path is untested, not specified.
  • History. The gallop came in with LUCENE-4946 (#6010, 2013) and is unchanged since. That review discussed int overflow only for the exclusive to (Uwe Schindler: "The overflow issue is no real issue as the meximum array size is limited, too", sic).
  • Precedent. LUCENE-6293 (#7355), an ArrayIndexOutOfBoundsException from TimSorter on a huge, specially patterned array, was fixed in 5.1.0, although Adrien Grand called it "rather unlikely to happen in practice".
The devil's-advocate check222 words

The strongest case: every class on the path (CollectionUtil, ArrayUtil, Sorter, TimSorter) is @lucene.internal; the util package doc says these classes "are generally not intended for direct use by most applications"; CollectionUtil's class doc speaks of "medium size collections"; and the trigger needs more than 2^30 elements and then fails loudly. An independent reviewer from another model family (OpenAI GPT-5.6), asked to refute the bug, called it out of contract on internal-API grounds alone (@lucene.internal, and the package doc's "APIs in this package are primarily internal and may change between releases"), while reproducing it with its own test and agreeing with the root cause and the fix.

Why it fails: @lucene.internal renders as "This API is for internal purposes only and might change in incompatible ways in the next release", an API-stability notice, not an input limit ("may change between releases" is the same kind of notice), and the same package doc says the classes "may be useful for advanced integrations or extensions". "Medium size" is about efficiency. Lucene itself runs this merge for index sorting, and LUCENE-6293 shows a large-input TimSorter exception treated as a bug. The input is the simplest one TimSort is built for: one short head, one long sorted run, natural order, and a List that keeps its contract.

Suggested fix

#

Recommended Compute the next probe in long and clamp it to to (both gallop sites)

Compute the next probe in long and clamp it to the range end, t = (int) Math.min(to, t + 2L * delta), in TimSorter.lowerSaved3 and in Sorter.upper2, which has the same line. Inputs that do not overflow probe as before. Validated: the repro (assertions on and off), the closest sorter suites and a direct probe of the upper2 half pass.

// TimSorter.lowerSaved3 (TimSorter.java:344) and Sorter.upper2 (Sorter.java:173):
-      t += delta << 1;
+      t = (int) Math.min(to, t + 2L * delta);
All options and trade-offs2 options · 427 words

Two equivalent fixes; the first was run through Gradle in a scratch worktree of f794ff5a505c. Documenting a 2^30 limit instead is not proposed: nothing else in Lucene sets one, index sorting reaches the same code, and the JDK's implementation handles the case.

Compute the next probe in long and clamp it to to (both gallop sites) (validated by the checks) (recommended)

#

The probe can no longer pass to, so it can no longer wrap. A clamped t == to ends the loop exactly as an overshoot t >= to does today, and both then binary-search [f, to).

// TimSorter.lowerSaved3 (TimSorter.java:344) and Sorter.upper2 (Sorter.java:173):
-      t += delta << 1;
+      t = (int) Math.min(to, t + 2L * delta);

Trade-offs

No API change; the same probes and comparisons as today for every input that does not overflow. One long add and a min per gallop step (a gallop runs at most 30 iterations); performance not measured.

  • With the fix it passes with assertions on and off (-Ptests.asserts=false), in about 45 s, because the full sort now completes.
  • Closest suites (TestTimSorter, TestTimSorterWorstCase (@Nightly, skipped), TestInPlaceMergeSorter, TestCollectionUtil, TestArrayUtil, TestIntroSorter, TestStringSorter): 7 classes, 58 tests, 0 failures, 1 skipped.
  • ./gradlew :lucene:core:check -x test (google-java-format, ecj lint, forbidden APIs) passes with the test in place. The full test suite was not run.
  • The minimal test reaches only the lowerSaved3 half. For the Sorter.upper2 half, a direct call of the package-private TimSorter.merge on a synthetic sorter (plain JVM, main f794ff5a505c) throws at slot -2147483648 from Sorter.upper2:168 without the fix and completes with every slot in range with it, assertions on and off.
  • Earlier, the same fix shadowed into the stock jars passed the test with -ea and -da, and 41 upstream sorter tests passed with it.

The same clamp in int arithmetic (not run)

#

Inside the loop the step delta << 1 is at most 2^30 and to - t > 0, so neither expression can overflow: final int step = delta << 1; t = step < to - t ? t + step : to;.

Trade-offs

The same effect as the first option without long, but its safety rests on that bound instead of being obvious at a glance.

Downstream note

#

Downstream code that sorts more than 2^30 elements with these utilities in the run shape above, or (by reading, not run) index-sorts a single segment of more than 2^30 documents, can hit this exception until it is fixed; it fails loudly, through a bounds-checked access.

How it was found

#

Semi-formal: TimSorter's merge was checked against one proof obligation, that every slot it passes to compare, compareSaved or copy lies inside [from, to). The gallop's doubling step was the one place where it fails; a JUnit test on the public API then confirmed it.

The method in full78 words

Under this obligation the downward gallops (lower2, upperSaved3) cannot wrap, and the binary searches stay inside their range. lowerSaved3 and Sorter.upper2 add a doubled step to an absolute index without a bound, so the obligation holds only while t + 2 * delta fits in an int. A test was then built whose merge gallops over 2^30 slots from slot 72; its failing index (-2,147,483,577) matched the hand computation, and one element fewer sorts correctly.

Summary
You sort a legal RandomAccess list of 1,073,741,896 Booleans (64 true values, then 2^30 + 8 false values) with CollectionUtil.timSort in natural order and expect it back sorted. Instead TimSorter's merge gallop doubles its probe index in int: after 2^30 slots the index wraps to -2147483577, which still passes the 't < to' check, so the sort asks the list for slot -2147483577 and throws IndexOutOfBoundsException. Because the merge had already moved the 64 true values into its temp buffer, the aborted list holds only 56 of them.
