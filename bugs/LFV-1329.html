CharArrayMap.entrySet().contains returns true for an absent key paired with a null value, even on an empty map

CharArrayMap.entrySet().contains returns true for an entry whose value is null and whose key is not in the map, even on an empty map, because a lookup of a missing key also returns null. The map's own get, containsKey and equals stay right; affected since 3.1.0.

The finding in 30 seconds

#

entrySet() is the set of key/value pairs a map holds. CharArrayMap answers "is this pair in the map?" by looking up the key and comparing values, but a lookup of a missing key returns null, so a pair whose value is null always matches, even when the map is empty.

Background: a map's entry set and null values

#
  1. Map.entrySet() returns a set view of the mappings a map contains, so entrySet().contains((k, v)) should be true only when the map maps k to v.
  2. CharArrayMap (a char[]-keyed map used by analysis code) accepts null values: put("x", null) stores a mapping, and containsKey("x") is then true.
  3. get(key) returns null both when the key is missing and when it is mapped to null; containsKey is what tells the two apart.

The finding, step by step

#
  1. Make an empty map, CharArrayMap<Object> map = new CharArrayMap<>(0, false): map.size() and map.entrySet().size() are both 0.
  2. Ask the entry set map.entrySet().contains(new SimpleEntry<>("missing", null)). You expect false, as java.util.HashMap answers: the view holds no mappings at all.
  3. You get true. The same happens on CharArrayMap.emptyMap() and, for any absent key, on a non-empty map such as {present=v}. For two maps {x=null} and {y=null}, entrySet().equals is true while the maps' own equals is false.
  4. Why: contains looks the key up with get(key) and counts "get returned null and the entry's value is null" as a match. get also returns null for a key that is not there, and the key itself is never checked.

Who is affected

#

Only application code that asks a CharArrayMap's entry set, through contains, containsAll or entrySet().equals, about an entry with a null value. No in-tree Lucene source does: analyzers use get and containsKey, which are right, and CharArraySet answers membership through containsKey and never asks an entry set.

Mechanism, terms and numbers486 words

CharArrayMap extends AbstractMap<Object, V>, and entrySet() returns its public EntrySet, a set view of the mappings. EntrySet.contains(o) computes v = get(key) and returns v == null ? val == null : v.equals(val) (CharArrayMap.java:486-493, the return at :492). get returns null both for a key that is not in the map and for a key mapped to null, so an entry whose value is null is reported as contained whenever its key is absent.

An empty map, whose entry set has size 0, therefore says it contains ("missing", null); so does CharArrayMap.emptyMap(), whose javadoc promises that contains checks always return false, and so does a non-empty map for any absent key. containsAll and entrySet().equals build on contains and inherit the wrong answer. java.util.HashMap answers false in each case. The one-line fix adds containsKey(key) to the null branch.

Why it looks unintended

#
  • Map.entrySet() is "a Set view of the mappings contained in this map"; an empty map's view has size 0, so it contains nothing.
  • The class disagrees with itself: emptyMap()'s javadoc says contains checks always return false, and the map's equals tells {x=null} from {y=null}.
  • The "not a general purpose class" note names missing removal and shrinking, not wrong answers.
The full argument227 words
  • The contracts. Map.entrySet(): "Returns a Set view of the mappings contained in this map". Set.contains: true "if and only if this set contains an element e such that Objects.equals(o, e)". Map.get: "If this map permits null values, then a return value of null does not necessarily indicate that the map contains no mapping for the key ... The containsKey operation may be used to distinguish these two cases" (JDK 25 javadoc). CharArrayMap permits null values: put accepts them and containsKey tells them apart.
  • The class contradicts itself. EmptyCharArrayMap's javadoc: "Contains checks will always return false or throw NPE if necessary" (CharArrayMap.java:605-607), yet emptyMap().entrySet().contains(("missing", null)) is true. For {x=null} and {y=null}, the map's equals says "different" while entrySet().equals says "same".
  • The same method already answers false for an absent key with a non-null value, and it applies the map's key matching (char[] or String keys, ignoreCase), which still needs a present key.
  • No test or document endorses it. TestCharArrayMap uses the entry set only for iteration, clear, size and toString (TestCharArrayMap.java:102-216); no CHANGES or MIGRATE entry mentions entry-set membership or null values; the #3323 thread does not discuss them.
  • Precedent. Lucene fixed an earlier wrong membership answer in these classes as a bug: LUCENE-1163 (53d3a0cfab2, 2008, CharArraySet.contains(char[], offset, length) ignored the offset).
The devil's-advocate check121 words

The strongest case for "intended": the class javadoc says CharArrayMap "is not a general purpose class" (CharArrayMap.java:27-32), null values are unusual, and no Lucene code calls these methods, so full Set conformance of the entry-set view was never promised.

Why it fails: the javadoc's examples are missing capabilities ("it cannot remove items from the map, nor does it resize its hash table to be smaller, etc."), not wrong membership answers; the empty-map trigger needs no stored null at all, only a probe entry with a null value, which Set.contains accepts; and the class's own equals and EmptyCharArrayMap javadoc already give the correct answer. Both passes of the cross-model review rated the argument weak, and the adjudication kept high confidence.

Suggested fix

#

Recommended A. Require the key in the null branch (recommended; validated)

In EntrySet.contains, require the key in the null branch: return v == null ? val == null && containsKey(key) : v.equals(val);. Validated through gradle: the repro passes with assertions on and off, the core analysis tests (169) pass, and the formatter check is clean.

       final Object v = get(key);
-      return v == null ? val == null : v.equals(val);
+      return v == null ? val == null && containsKey(key) : v.equals(val);
All options and trade-offs3 options · 350 words

Option A is the whole fix for this false positive: emptyMap(), the unmodifiable views, containsAll and entrySet().equals all go through EntrySet.contains. It does not make the entry set an ordinary Set<Map.Entry> in every respect: its entries carry cloned char[] keys and MapEntry overrides neither equals nor hashCode (CharArrayMap.java:434-469), a separate matter. One seed, no nightly tests; the full upstream test suite was not run.

A. Require the key in the null branch (recommended; validated)

#

CharArrayMap.java:492, one line. The same check AbstractMap.equals makes for a null value.

       final Object v = get(key);
-      return v == null ? val == null : v.equals(val);
+      return v == null ? val == null && containsKey(key) : v.equals(val);

Trade-offs

The extra lookup happens only when get(key) returns null and the probed value is null (an absent key or a key mapped to null); every other call is unchanged. EmptyCharArrayMap.containsKey returns false, so emptyMap() is fixed by the same line.

What the checks validated

  • Without the fix the repro fails with assertions on and off (gradle, seed DEADBEEF).
  • With the fix the repro passes with assertions off; with assertions on the repro and the core org.apache.lucene.analysis.* tests pass: 22 classes, 169 tests, 0 failures (among them TestCharArrayMap 4, TestCharArraySet 15, TestStopFilter 5).
  • :lucene:core:checkGoogleJavaFormat passes with the fix and the test in place.
  • A value probe with the fix patched in: every wrong answer turns false, the controls are unchanged.

B. Check the key first

#

if (!containsKey(key)) return false; return Objects.equals(get(key), val);, or a single-lookup variant that finds the slot once with the private getSlot and tests keys[slot] != null.

Trade-offs

Not validated. Reads more plainly, but the simple form costs a second hash lookup on every call; the single-lookup form duplicates the char[]/CharSequence/Object key dispatch of get.

C. Document the behaviour on entrySet()

#

A javadoc note that the entry set's contains may answer true for an absent key paired with null.

Trade-offs

Not recommended: it leaves Set.contains wrong for a legal input that a one-line change fixes.

Downstream note

#

Downstream code that asks a CharArrayMap entry set about null-valued entries can, until a fix ships, also check map.containsKey(key) or compare two CharArrayMaps with the map's own equals, which is right.

How it was found

#

A semi-formal proof-obligation audit of CharArrayMap's entry-set view against the java.util contract: Set.contains on a Map.entrySet() view is true only for a mapping the map contains. A public-API JUnit test witnessed the violation on stock main.

The method in full63 words

The obligation comes from Map.entrySet() and Set.contains, which CharArrayMap.EntrySet inherits by extending AbstractSet, checked against each branch of EntrySet.contains. The null-value branch accepts an entry without checking that its key is present. An executable JUnit test on the stock main build confirmed it, and independent reproducers, a cross-model review and an adjudication then checked it (see the checks below).

Impact note

Summary
You create an empty CharArrayMap (new CharArrayMap<>(0, false)) and ask its entry set whether it contains the entry ("missing", null). You expect false, because the map has no mappings (entrySet().size() is 0), Map.entrySet() is a set view of the mappings the map contains, and java.util.HashMap answers false. Instead contains returns true, because EntrySet.contains treats get(key) == null as a match for a null value without checking that the key is present; the same happens for any absent key on a non-empty map, and entrySet().containsAll and entrySet().equals inherit the wrong answer.
