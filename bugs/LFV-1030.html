MIGRATE.md's 11.0 upgrade example says forceMerge(1) rewrites all segments, but it leaves a single-segment index in its old format

The code is right; the guide should use UpgradeIndexMergePolicy.

The finding in 30 seconds

#

Segments, versions and forceMerge

#
  1. A Lucene index is a set of segments. Each segment records the Lucene version that wrote it and its codec (file format): a segment written by 9.0.0 has version 9.0.0 and codec Lucene90.
  2. Lucene 11 still reads such segments, through lucene-backward-codecs. A segment moves to the current format only when a merge copies it into a new segment.
  3. forceMerge(n) asks the merge policy to merge until at most n segments remain. The policy picks the merges, and when the index is already at n segments with nothing to clean up it may pick none.

The finding, step by step

#
  1. You move to Lucene 11 an index that Lucene 9.0.0 wrote and that was force-merged long ago: one segment, 50 documents, no deletions, codec Lucene90. You follow MIGRATE.md's "Upgrade Example": open an IndexWriter with a default IndexWriterConfig and call forceMerge(1).
  2. You expect what the comment promises, "Rewrites all segments to latest format": one segment at version 11.0.0, codec Lucene104.
  3. Instead nothing happens. forceMerge(1) only promises at most one segment, and the default TieredMergePolicy treats one segment without deletions as "already merged" and picks no merge. The call returns normally; the segment is still 9.0.0 with codec Lucene90.
  4. So the index still needs lucene-backward-codecs: opened without it, it fails with IndexFormatTooOldException ("Could not load codec 'Lucene90'"). With the policy wrapped in UpgradeIndexMergePolicy, the tool made for this, the same call rewrites it to 11.0.0, and it opens with lucene-core alone.
  5. Indexes with two or more segments or any deletion are rewritten as the guide says; only the one-segment, no-deletion shape (what a force-merged static index looks like) is skipped.

Who is affected

#

Anyone who upgrades a 9.x or 10.x index to 11.0 with the guide's optional forceMerge(1) step when the index already has one segment and no deletions, the shape of a force-merged static index. Default config, every time, silently. The index stays readable and its lifetime is unchanged; 9.x and 10.0-10.3 segments keep needing lucene-backward-codecs. Unreleased.

Mechanism, terms and numbers603 words

Lucene main's MIGRATE.md, in the 11.0 section "Relaxed Index Upgrade Policy", tells users who open an index created with Lucene 9.x or 10.x how to upgrade its segment formats: Scenario 1 says "Optional: Call forceMerge() or use UpgradeIndexMergePolicy to upgrade segment formats immediately", and the "Upgrade Example" opens new IndexWriter(dir, config) and calls writer.forceMerge(1); // Rewrites all segments to latest format.

forceMerge(1) only promises to leave at most one segment, and the merge policy picks the merges. The default TieredMergePolicy returns no merge for an index that already has one segment and no deletions ("already merged"), so the old segment is never rewritten and the call returns normally. On Lucene's own backward-compatibility index moreterms.9.0.0 (one segment, 50 documents) the segment is still version 9.0.0 with codec Lucene90 afterwards; without lucene-backward-codecs that index then fails to open with IndexFormatTooOldException. Indexes with two or more segments or any deletion are rewritten as promised.

The no-op is old and deliberate (LUCENE-3082 added IndexUpgrader and UpgradeIndexMergePolicy for exactly this case in 2011), so the code is correct and only the guide is wrong. The text came with #15012 (2025-09-18) and is on main and on the 11.0 release branch branch_11x, not in any release. Fix: wrap the configured merge policy in UpgradeIndexMergePolicy in the example and correct Scenario 1; with that one line the same test passes.

The code (correct and intended)

#
  • IndexWriter.forceMerge javadoc (IndexWriter.java:2187-2189): "Forces merge policy to merge segments until there are <= maxNumSegments. The actual merges to be executed are determined by the MergePolicy." It ties the call to static indexes: "usually you should only call this if the index is static" (:2191-2193).
  • forceMerge marks every current segment as an original segment to merge (IndexWriter.java:2251-2255). new IndexWriterConfig() uses TieredMergePolicy (LiveIndexWriterConfig.java:143).
  • TieredMergePolicy.findForcedMerges (TieredMergePolicy.java:834-847): with no deletions, maxSegmentCount == 1, one eligible segment and that segment in segmentsToMerge, it logs "already merged" and returns null. The segment's version and codec play no part.
  • UpgradeIndexMergePolicy (UpgradeIndexMergePolicy.java:26-31) "is used for upgrading all existing segments of an index when calling IndexWriter#forceMerge(int)": it selects every segment whose version is not Version.LATEST (:68-70) and merges the ones its delegate declines itself (:117-137). IndexUpgrader.upgrade() uses it (IndexUpgrader.java:180, :196).
  • The LogMergePolicy variants also skip a lone segment without deletions when its compound-file flag already matches (MergePolicy.isMerged, MergePolicy.java:750-758).

The executed matrix

#

On the stock main jars, 10 index states (Lucene's own fixtures plus states derived from them) x 6 policy setups = 60 runs. A decision model written from the code predicts all 60. The guide's claim holds in 50 and fails in 10, all on a single segment without deletions: both TieredMergePolicy setups on the 9.0.0, 9.12.3 and 10.5.2 fixtures, and both LogMergePolicy setups on the compound 9.12.3 and 10.5.2 fixtures. The other 8 single-segment, deletion-free runs are rewritten (UpgradeIndexMergePolicy and IndexUpgrader on all three, and the LogMergePolicy setups on the non-compound 9.0.0 fixture). UpgradeIndexMergePolicy and IndexUpgrader rewrite all 20 of their cases; document counts are unchanged in all 60.

  • Scale and timing. Deterministic for any such index the writer configuration can open (20 of 20 random seeds). Unreleased: main and the 11.0 release branch only, so it would first reach users in 11.0.0.

Why it looks unintended

#
  • The guide says it unconditionally: the comment on forceMerge(1) reads "Rewrites all segments to latest format", and Scenario 1 offers forceMerge() as an alternative to UpgradeIndexMergePolicy.
  • The no-op is deliberate and old: LUCENE-3082 added UpgradeIndexMergePolicy in 2011 because "optimizing a one-segment index is a no-op without the special merge-policy" (Uwe Schindler).
The full argument199 words
  • Unconditional text. Line 179 credits the rewrite to forceMerge(1) itself, and line 153 offers "Call forceMerge() or use UpgradeIndexMergePolicy" as two alternatives.
  • No recorded decision to accept this limitation. markrmiller's proposal comment on #13797 says "Merging rewrites segments to the current codec" and lists "optional forceMerge" as the upgrade step. Uwe Schindler's comment there named IndexUpgrader / UpgradeIndexMergePolicy as the existing rewrite path, but that did not reach MIGRATE.md. The #15012, #16741 and #16756 threads never mention forceMerge, single segments or IndexUpgrader.
  • The code is intended, and documented as such elsewhere. LUCENE-3082 (#4155, 2011) added IndexUpgrader and UpgradeIndexMergePolicy; as Uwe Schindler put it there, "The optimize() approach fails if your index is already optimized" and "optimizing a one-segment index is a no-op without the special merge-policy". LUCENE-5526 (#6589, 2014) says forcing a merge of a lone segment needs "a custom merge policy such as UpgradeIndexMergePolicy". LUCENE-5481 (#6544, 2014) removed unneeded forced merges, and BaseMergePolicyTestCase.testForceMergeNotNeeded fails any policy that merges when nothing is needed. Lucene's own upgrade tests use IndexUpgrader, not a bare forceMerge.
  • Every completed review called it real: an independent reproducer, a reviewer from another model family (OpenAI GPT-5.6) under lenses, a devil's-advocate check and the adjudication.
The devil's-advocate check147 words

Strongest case for "intended" or "noise": forceMerge is a segment-count operation, never a format converter, as its javadoc, TieredMergePolicy's "already merged", LUCENE-5481 and testForceMergeNotNeeded all say. The snippet leaves config undefined, so the reader may be meant to supply an UpgradeIndexMergePolicy. Line 152 already says segments are upgraded "gradually through normal merging", and the index works either way.

Why it fails: the first point defends the code, which nobody proposes to change; it does not make the sentence true. The undefined-config reading is ruled out by the guide itself, because line 153 presents forceMerge() as an alternative to UpgradeIndexMergePolicy and the comment on line 179 is unconditional. "It still works" only lowers the severity, which is already Low: a reader who runs the guide's recipe is told the index is in the latest format when it is not. Verdict: a real, minor documentation defect.

Suggested fix

#

Recommended Wrap the merge policy in UpgradeIndexMergePolicy in the example, and correct Scenario 1 (validated)

Docs only. In the example, wrap the configured policy before opening the writer, config.setMergePolicy(new UpgradeIndexMergePolicy(config.getMergePolicy()));, and make Scenario 1 point to UpgradeIndexMergePolicy or IndexUpgrader, noting that a plain forceMerge(1) skips a single segment without deletions. Validated: the same test passes with that line.

Trade-offs

  • UpgradeIndexMergePolicy rewrites only old segments: an index that also has new-format segments can end with more than one segment, all at the latest version. That is what an upgrade step needs.
  • Its javadoc warns it may reorder documents if the index was partially upgraded; not an issue for a single segment.
  • Its own class-javadoc example calls a removed constructor (LFV-1021), so a reader the guide sends there meets that error too.
  • With a SoftDeletesRetentionMergePolicy inside, its leftover merge bypasses retention (LFV-617); at most a caveat.
  • UpgradeIndexMergePolicy is marked @lucene.experimental; it has existed since 2011 and is what IndexUpgrader uses.
  • The snippet stays a sketch: it still leaves config to the reader, and real code also needs import org.apache.lucene.index.UpgradeIndexMergePolicy. Whatever config is must match the index (for example its index sort or parent field), or new IndexWriter(dir, config) fails before forceMerge runs; that holds for the current example too.

What the checks validated

  • The diff applies cleanly to 645d4fe14a20 and, with an offset of 14 lines, to today's upstream main.
  • The minimal test with the fix's one extra line passes 1 of 1 through the same Gradle command with assertions on and off; the stock example fails it, so the test detects the bug. After the corrected example the index opens with lucene-core alone.
  • TestIndexUpgradeBackwardsCompatibility, TestUpgradeIndexMergePolicy and TestTieredMergePolicy pass (340 + 5 + 17 tests, 0 failures); a sanity check, since the change is documentation only.
  • ./gradlew :lucene:documentation:markdownToHtml succeeds and the rendered page shows the corrected text.

Point to IndexUpgrader only

#

new IndexUpgrader(dir).upgrade() or the command line java -cp lucene-core.jar:lucene-backward-codecs.jar org.apache.lucene.index.IndexUpgrader indexDir. Simple and already tested upstream. A 9.x or 10.0-10.3 index needs lucene-backward-codecs on the class path to be read at all: with lucene-core alone the command fails with IndexFormatTooOldException ("Could not load codec 'Lucene90'"); with both jars it prints "All segments upgraded to version 11.0.0". (IndexUpgrader's own javadoc shows only lucene-core.jar.)

Trade-offs

It refuses an index with more than one commit unless told to delete prior commits, keeps only the last commit, and its convenience constructors use a bare IndexWriterConfig, which drops an index sort and cannot upgrade an index with a parent field (LFV-615, known upstream). The recommended option keeps the application's own config.

Fix the wording only

#

Say that forceMerge(1) rewrites only the segments it merges, and that an index already at one segment without deletions needs UpgradeIndexMergePolicy or IndexUpgrader.

Trade-offs

Correct, but leaves the guide without a working recipe for the single-segment, deletion-free shape of a force-merged static index.

Make forceMerge rewrite old-format segments (not recommended)

#

Change TieredMergePolicy (and the other policies) to merge a lone segment whose version is not current.

Trade-offs

Contradicts LUCENE-5481 and testForceMergeNotNeeded, changes the cost of every forceMerge, and duplicates UpgradeIndexMergePolicy. Every completed review agreed the code should not change.

Downstream note

#

Downstream products whose index-upgrade step is a plain force merge to one segment see the same no-op on single-segment shards; it was raised in Elasticsearch in 2014 (elastic/elasticsearch#5243, "Force single-segment merges").

How it was found

#

No formal method. A probe ran the guide's upgrade example against an index written by 9.12.3 and saw its single segment stay in the old format while a three-segment index was rewritten. The hunt then checked a decision model of forceMerge(1) against 60 executed index-and-policy runs and wrote the one-test repro on Lucene's own 9.0.0 test index.

The method in full100 words
  • First signal. A pass that looked for upgrade problems ran the MIGRATE.md example on the stock main 645d4fe14a20 jars against indexes written by the 9.12.3 jar (2026-10-29): the single-segment index stayed Lucene912 / 9.12.3, a three-segment index was rewritten.
  • Hunt. A decision model of "forceMerge(1) leaves every segment at the latest version", written from the code, was checked against 60 executed (index state x merge policy) runs: the model matched 60 of 60, the guide's claim 50 of 60. The one-test repro uses Lucene's own moreterms.9.0.0 fixture.
  • Tier. Non-formal: an executed check of a documentation claim, with a model-based cross-check.

Summary
Lucene main's MIGRATE.md tells users who open a Lucene 9.x or 10.x index to upgrade its segments by opening an IndexWriter and calling forceMerge(1), with the comment 'Rewrites all segments to latest format' (line 179), and line 153 offers forceMerge() as a way 'to upgrade segment formats immediately'. With the default merge policy, forceMerge(1) does nothing on an index that already has one segment and no deletions: TieredMergePolicy reports it as already merged, so on Lucene's own single-segment 9.0.0 test index the segment is still version 9.0.0 with codec Lucene90 afterwards. The code behaves as designed (forceMerge only promises a segment count, and UpgradeIndexMergePolicy and IndexUpgrader exist for exactly this case); the guide should wrap the merge policy in UpgradeIndexMergePolicy or point to IndexUpgrader.
