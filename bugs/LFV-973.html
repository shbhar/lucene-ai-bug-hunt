BoostQueryNode's javadoc limits the boost to 0.0-1.0, but the parser's own example jones^2 gives 2.0

The flexible query parser's BoostQueryNode javadoc says the boost "may vary from 0.0 to 1.0", but boosts above 1 are ordinary syntax: the parser's own example jones^2 gives 2.0. The code is right; only the javadoc is wrong, in every release since 2.9.0.

The finding in 30 seconds

#

jones^2 reaches the node unchanged: the grammar stores Float.parseFloat("2") (StandardSyntaxParser.jj:701), the constructor checks nothing (BoostQueryNode.java:47), and the builder makes BoostQuery 2.0. The javadoc's 0.0-1.0 range (BoostQueryNode.java:29, :39, :67) matches none of this.

Background: boosts in the flexible query parser

#
  1. StandardQueryParser works in three phases: a syntax parser turns the text into a tree of query nodes, processors rewrite the tree, and builders turn each node into a Lucene Query. Developers can plug in their own processors and builders.
  2. The ^ operator, as in jones^2, becomes a BoostQueryNode around the boosted part of the tree; its getValue() is the number after ^.
  3. A boost above 1 makes a clause count more in the score and a boost below 1 less, as BoostQuery and the parser's syntax docs say. Boosts can also come from configuration: setFieldsBoost gives each field a boost.

The finding, step by step

#
  1. You write a custom processor or builder for the flexible query parser that reads BoostQueryNode.getValue(). Its javadoc says "The boost value may vary from 0.0 to 1.0", and says it again on the constructor and on getValue.
  2. You parse jones^2 OR smith^0.5, the example in StandardQueryParser's own javadoc, and expect node values between 0 and 1.
  3. You get 2.0 and 0.5. Field boosts set with setFieldsBoost, say 5 and 10, arrive as 5.0 and 10.0. Nothing clamps or checks the value, and nothing should.
  4. Lucene itself is fine: it builds BoostQuery 2.0 and scores correctly. Only code that trusts the javadoc goes wrong, for example by clamping jones^2 to 1.0 or rejecting it as out of range.

Who is affected

#

Developers who extend the flexible query parser with processors, builders or validators that read BoostQueryNode and trust the stated range. Users who only call StandardQueryParser.parse are not affected: queries are built and scored correctly. No setting or scale is involved; the text is in every release since 2.9.0.

Mechanism, terms and numbers440 words

In the flexible query parser (StandardQueryParser), a boost such as jones^2 becomes a BoostQueryNode in the query-node tree, and a builder later turns it into a BoostQuery. The node's javadoc says three times that the value "may vary from 0.0 to 1.0": in the class javadoc, the constructor @param and getValue. Nothing in Lucene keeps the value in that range, and nothing should: the grammar and the field-boost processor store the user's number unchanged, BoostQuery sets no upper bound, and the parser's own documentation uses jones^2 and (a OR b NOT c)^2.5 as examples. StandardSyntaxParser.parse("jones^2", "f") returns a node whose getValue() is 2.0.

Parsing, query building and scoring are correct. The only people misled are developers who extend the parser with their own processors, builders or validators and take the stated range at face value. The text has been there since the flexible parser was added in 2009 (LUCENE-1567) and is in every release since 2.9.0. The fix is three javadoc lines.

The mechanism (main 645d4fe14a20)

#
  1. The text. BoostQueryNode.java:29 "The boost value may vary from 0.0 to 1.0."; :39 "@param value the boost value, it may vary from 0.0 to 1.0"; :67 "Returns the boost value. It may vary from 0.0 to 1.0."
  2. The node checks nothing. The constructor (:41-51) checks only that the child is not null and stores this.value = value (:47); getValue returns it (:71-73).
  3. Producer 1, the grammar. Boost ::= '^' <NUMBER> (StandardSyntaxParser.jj:692) returns new BoostQueryNode(node, parseFloat(boost)) (:701), and parseFloat is Float.parseFloat(token.image) (:115-116): no clamp, no range check.
  4. Producer 2, field boosts. For a field node whose parent is not itself a field node, BoostQueryNodeProcessor reads that field's configured boost and, if there is one, returns new BoostQueryNode(node, boost) with the value unchanged (BoostQueryNodeProcessor.java:44-57); the map comes from StandardQueryParser.setFieldsBoost (StandardQueryParser.java:526).
  5. Consumer. BoostQueryNodeBuilder returns new BoostQuery(query, boostNode.getValue()) (BoostQueryNodeBuilder.java:48). BoostQuery rejects only non-finite or negative boosts (BoostQuery.java:40-41, "boost must be a positive float"; it compares with Float.compare, so -0.0f counts as negative and +0.0f passes) and documents that values greater than one give more importance (:23-25).
  6. So every boost the standard syntax accepts (an unsigned decimal number, StandardSyntaxParser.jj:160) reaches the node unchanged: jones^2 gives 2.0, smith^0.5 gives 0.5, (a OR b)^2.5 gives 2.5, jakarta^4 gives 4.0, and setFieldsBoost({b=5, t=10}) builds (b:one)^5.0 (t:one)^10.0. Negative and non-finite values also reach the node and are rejected only when BoostQuery is built (a field boost of -1; a literal beyond Float.MAX_VALUE, which parses to Infinity). That matters for the fix wording.
Exposure and likelihood119 words
  • Who. Code that reads BoostQueryNode.getValue(): custom QueryNodeProcessors, QueryBuilders or validators plugged into StandardQueryParser. If it trusted the javadoc it could clamp boosts to 1.0 (silently turning jones^2 into jones^1) or reject the parser's own documented example.
  • Who not. Applications that only call StandardQueryParser.parse: the boost reaches BoostQuery unchanged and scoring is correct.
  • Default vs opt-in. The javadoc is what everyone sees, and the documented example hits the contradiction; acting on it needs custom code, which is opt-in and rare.
  • Scale. None: it is static text.
  • Why fix it anyway. A public class states a range that its only producers in Lucene violate, in every release since 2.9.0; the fix is three javadoc lines.

Why it looks unintended

#
  • The same module's syntax docs use jones^2 and (a OR b NOT c)^2.5; the classic syntax page uses jakarta^4.
  • BoostQuery, which the node becomes, says values above one give more importance and sets no upper bound.
  • Upstream tests assert boosts of 2.0, 5.0 and 10.0 on queries built through this node; the 2009 commit that wrote the sentence tested term^2.
The full argument244 words
  • The same module documents boosts above 1. StandardQueryParser.java:161-173 ("Term boosting"): jones^2 OR smith^0.5 and field:(a OR b NOT c)^2.5 OR field:d. The classic syntax page: "The higher the boost factor, the more relevant the term will be" (classic/package-info.java:250-251), jakarta^4 apache (:261), and "By default, the boost factor is 1. Although the boost factor must be positive, it can be less than 1 (e.g. 0.2)" (:268-269).
  • The query it builds says so too. BoostQuery.java:23-25: "values that are greater than one will give more importance to the scores returned by this query"; the constructor sets no upper bound and rejects only negative values (-0.0f too), NaN and infinities (:40-41).
  • Upstream tests. TestQPHelper.java:974-976 ("hello"^2.0 builds BoostQuery with boost 2.0) and TestMultiFieldQPHelper.java:154-166 (testBoostsSimple: field boosts 5 and 10, asserted as (b:one)^5.0 (t:one)^10.0); both check the built query, not the node itself. No test asserts a value in [0, 1] for BoostQueryNode; no queryparser test names the class.
  • History. The commit that wrote the three sentences, 343992fcbb4 (LUCENE-1567, 2009), also added tests asserting term^2 gives term^2.0 (with ^3 and ^4 cases and field boosts 5 and 10), and the query syntax page of that time already said jakarta^4. The saved history and prior-art searches found no commit, issue or list thread that discusses or defends a [0, 1] range; a 2025 clean-up of this file (#14737) left the line untouched without comment.
The devil's-advocate check134 words

The strongest case for "not a bug": "may vary" is permissive, a loose hint rather than a contract; or the range is a caller precondition of a generic core node that some other syntax could honour. The intended-behaviour checker also tried "normalized-boost design", "accepted / won't fix" and "unreachable".

Why it fails: the text names a closed range, and the only producers in Lucene (the only new BoostQueryNode sites in the source tree), the standard grammar and BoostQueryNodeProcessor, put values above 1 into the node as designed, starting with the module's own documented example. A hint that is wrong for every value above 1 the documented syntax produces is still wrong, and no saved search found a discussion defending it. Verdict: a documentation defect; the code is right and should not change.

Suggested fix

#

Recommended A. State what the value means once; drop the range from @param and getValue (recommended)

Javadoc only. Say that boost values above 1.0 raise the score and values below 1.0 lower it (jones^2 gives 2.0), and that the node does not check the value while BoostQuery rejects negative and non-finite boosts; drop the range from @param and getValue. Validated: format, lint and javadoc checks and the flexible-parser tests pass.

Trade-offs

  • It does not imply that the node validates anything: the node stores whatever it gets, and BoostQuery is where negative and non-finite boosts are rejected.
  • It adds a cross-module {@link} from a core node to org.apache.lucene.search.BoostQuery (the standard package's javadoc already links org.apache.lucene.search.Query). A custom builder that builds something else is not covered by that sentence; "This node does not check the value." alone also works.
  • Option C (delete the range, add nothing) makes no new claim and is the most conservative alternative. "Negative" in the last sentence means what BoostQuery checks (Float.compare, so -0.0f is rejected too); "This node does not check the value." alone avoids the point.
  • Backport: not tested on a maintenance branch. BoostQueryNode.java is byte-identical (the same git blob) on main, at the 10.6.0 tag and on branch_10_6, so the diff applies as is; the checks were not run there.
