A failed addIndexes(CodecReader...) leaves the incoming fields registered in the writer's field schema, so later valid documents that use those names differently are rejected until the writer is reopened

When IndexWriter.addIndexes(CodecReader...) fails during its merge, for example on a full disk, it adds no documents but keeps the incoming fields registered, so the same writer rejects valid documents that use those names differently until it is reopened. Every release since 4.2.0; nothing on disk is damaged.

The finding in 30 seconds

#

The writer keeps one in-memory registry of field names and their schemas. addIndexes(CodecReader...) checks the incoming fields without touching it, then merges, and the merge's first step adds the incoming fields to it. When a later write fails, the call throws and adds nothing, but the fields stay registered.

Three things to know first

#
  1. Every field name in an index has one schema: indexed or not (index options), doc values type, points, vectors. The first document indexed with a name fixes it; a later document that gives the name another schema is rejected with IllegalArgumentException.
  2. IndexWriter checks that against an in-memory registry of every name it knows, built from the segments when the writer opens. getFieldNames() returns the registry's names.
  3. addIndexes(CodecReader...) merges the given readers into a new segment of this index. Its javadoc promises that if an exception occurs ("for example disk full"), "either no indexes will have been added or they all will have been".

The finding, step by step

#
  1. The source index has 1 document with StringField("f", "x"): f is indexed and has no doc values. The destination is a new, empty index with a default IndexWriterConfig.
  2. w.addIndexes(reader) hits a disk-full IOException while it writes the merged segment. As the javadoc promises, nothing is added: 0 documents, the writer stays open, no tragic error.
  3. You expect the writer to be as before: no document with f ever reached it, so a document with NumericDocValuesField("f", 1) is accepted, as by a reopened writer.
  4. Instead it is rejected: cannot change field "f" from index options=DOCS to inconsistent index options=NONE, and getFieldNames() lists f. The merge registered f before the write failed, and nothing takes it back until a reopen, rollback() or deleteAll().
  5. No I/O error is needed on an index-sorted writer, with incoming document blocks without a parent field, or with a one-merge-per-reader policy: a rejected import of two indexes that disagree on f keeps one index's f (with a single merge, the first one's), and then even importing the other index alone is rejected.

Who is affected

#

Applications that keep using a writer after addIndexes(CodecReader...) failed: after an I/O error during the merge (any configuration), or after a rejected import of conflicting indexes on an index-sorted writer, with document blocks without a parent field, or with a per-reader merge policy. Later documents that use an incoming name differently are rejected until the writer is reopened.

Mechanism, terms and numbers727 words

IndexWriter keeps one in-memory registry of field names and their schemas, built from the segments when it opens, and checks every new document against it. addIndexes(CodecReader...) first checks the incoming fields without changing that registry, then merges the readers into a new segment. The merge is built over the writer's own registry, and its first step registers the incoming fields. When a later step of the merge fails (for example a full disk), the call throws and publishes nothing, but nothing removes the registrations. No document is added, as the javadoc promises, but for the rest of the writer session the incoming names keep the incoming schema: a later document that uses such a name differently is rejected with IllegalArgumentException, and getFieldNames() lists the name. With an index sort, incoming document blocks without a parent field, or a one-merge-per-reader merge policy, a rejected import of two conflicting indexes leaves the same residue without any I/O error. Reopening the writer, rollback() or deleteAll() clears it; the index on disk is not damaged. Every release from 4.2.0 through 10.6.0 and main is affected. Merging with private field numbers and registering the fields only when the merged segment is published fixes every executed trigger.

The bug (main 5adff78bb168)

#
  1. The registry (FieldInfos.FieldNumbers) is built when the writer opens (IndexWriter.java:1124).
  2. addIndexes(CodecReader...) (:3275) runs "Best effort up front validations": globalFieldNumberMap.verifyFieldInfo(fi) for every incoming field (:3288-3293). verifyFieldInfo only checks (FieldInfos.java:401-408), so a conflict found here leaves nothing behind.
  3. The merge runs in addIndexesReaderMerge (IndexWriter.java:3491), whose SegmentMerger is given globalFieldNumberMap, the writer's registry itself (:3568-3577).
  4. SegmentMerger.merge() calls mergeFieldInfos() first (SegmentMerger.java:121; the builder over the registry at :75), which adds the incoming FieldInfos one by one (:232-239; a conflict stops the loop) through FieldInfos.Builder.add -> FieldNumbers.addOrGet (FieldInfos.java:788, :415): each new name is registered with its incoming schema. Stored fields, norms, postings, doc values, points, vectors and the .fnm are written after that (SegmentMerger.java:123 on), then the compound file and the .si (IndexWriter.java:3620-3641).
  5. When one of those steps fails, the exception reaches the caller: with SerialMergeScheduler straight out of mergeScheduler.merge (IndexWriter.java:3312), with ConcurrentMergeScheduler rethrown at :3376-3384. The finally (:3316-3324) deletes files only of merges whose merge info is set, which happens after merger.merge() returns (:3600); for a failure inside the merge it deletes nothing, and files already written stay unreferenced until the writer is closed or rolled back. Only an Error is tragic (:3390-3393), so the writer stays open. FieldNumbers has no removal except clear() (FieldInfos.java:694-698), which only deleteAll() calls (IndexWriter.java:2800).
  6. A later document reaches FieldNumbers.addOrGet -> verifySameSchema (FieldInfos.java:422) and is rejected against the leftover schema; getFieldNames() (IndexWriter.java:2135-2137) lists the name.

The fault-free trigger

#

Unless the writer has an index sort, or at least one reader of the merge has document blocks and at least one (possibly another) has no parent field (IndexWriter.java:3549-3556), addIndexesReaderMerge first wraps the readers of one merge with SlowCompositeCodecReaderWrapper.wrap (:3560-3566), which merges their FieldInfos in a private FieldNumbers (FieldInfos.java:196-218) and throws on a conflict before anything is registered. With an index sort, in that blocks case (the wrap is skipped), or with a merge policy whose findMerges(CodecReader...) returns one merge per reader (allowed by the javadoc, IndexWriter.java:3264-3267), step 4 registers one reader's f and throws IllegalArgumentException on the other's (within one merge the first reader's; with one merge per reader under the default concurrent scheduler, whichever merge registers first). The rejected call leaves that schema behind: a later document, and even importing the other index alone, is rejected (executed with the first reader's f left behind: addIndexes(c2) is rejected), while a fresh writer accepts c2. The wrap came with #12622 (9.9.0) and the blocks skip with #13128 (9.11.0), so before 9.9.0 a conflicting two-reader import left the residue with the default configuration too.

Exposure and likelihood270 words
  • Who is hit. Applications that keep using an IndexWriter after addIndexes(CodecReader...) failed. Two ways in: an I/O error once the merge has started (any configuration; the javadoc's own "disk full" example), or a rejected import of indexes that disagree on a field's schema on an index-sorted writer, with incoming document blocks without a parent field, or with a merge policy that returns one merge per reader (and with the default configuration on every release before 9.9.0).
  • What they see. Every later document that gives an incoming name another schema fails with IllegalArgumentException; getFieldNames() lists the name. After the conflict trigger, importing only the second index is rejected too.
  • Loud, no data damage. Nothing of the failed import is added or committed, no commit references its files, and documents that do not use those names are accepted as usual. After an I/O error, a retry of the same import works (it has the same schema). Files a failed merge already wrote stay in the directory, unreferenced, until the writer is closed or rolled back; they are harmless and not part of this bug.
  • How long. Until the writer is reopened, rolled back or deleteAll() is called.
  • Default configuration. The I/O trigger needs no setting: a default-configuration check with ConcurrentMergeScheduler shows the same residue; the repro uses SerialMergeScheduler to keep the merge and its exception on the test thread.
  • Likelihood. Contrived (rare in practice): accidental harm needs an application that abandons the import, keeps the same writer without rollback() or a reopen, and then indexes an incoming name differently.
  • Workaround. Reopen or roll back the writer after a failed addIndexes(CodecReader...).

Why it looks unintended

#
  • The javadoc: after an exception ("for example disk full"), "either no indexes will have been added or they all will have been" (IndexWriter.java:3084-3086, :3259).
  • #633 added the non-mutating up-front check to keep this overload transactional; only merge-time failures leave fields behind.
  • A field's schema comes from "the first document indexed" with it (MIGRATE.md); none reached this writer.
The full argument307 words
  • Contract. addIndexes(CodecReader...) refers to the addIndexes javadoc "for details on transactional semantics" (IndexWriter.java:3259): "This method is transactional in how Exceptions are handled: it does not commit a new segments_N file until all indexes are added. This means if an Exception occurs (for example disk full), then either no indexes will have been added or they all will have been" (:3084-3086). After the disk-full failure, the incoming index still decides which documents the writer accepts. And getFieldNames() is documented as "all field names as visible from this IndexWriter, across all segments of the index" (:2130-2131); after the failed call it lists f, which no segment, flushed or in memory, holds.
  • The overload avoids it on purpose for validation failures. The commit that added the up-front check, 698f40ad51af (LUCENE-10216, #633), lists "verify field info schemas upfront from incoming readers", "Keep addIndexes API transactional" and "Maintain transactionality - register segments with iw after all merges complete". Segment registration was deferred until the merges complete; field registration was not, so failures found up front leave no residue and failures in the merge do.
  • Schema definition. lucene/MIGRATE.md:1586-1593: "The per field data-structures are implicitly defined by the first document indexed that contains a certain field." No document with f reached this writer, and a reopened writer on the same files accepts the document.
  • Precedent. lucene/CHANGES.txt:21400-21408 (LUCENE-702) made addIndexes(*) transactional and fixed other paths "to clean up and keep the instance state consistent to what's actually in the index"; :20905-20910 (LUCENE-846) fixed a failed addIndexes that could "corrupt the instance of IndexWriter (but, not the index itself)".
  • Tests. Upstream's transactional tests check documents and files only; TestIndexWriterOnDiskFull rolls the writer back after a failed attempt (TestIndexWriterOnDiskFull.java:383-392), and we found no upstream test that adds a document to the writer after a failed addIndexes(CodecReader...).
The devil's-advocate check236 words

The strongest case for "accepted behaviour": the javadoc sentence is literally about segments_N and the documents added, and that part holds. The registry only grows within a session by design: field infos are "(almost) append-only" (#9597), and in #13369 (the fix of #13353, failed documents) delaying or reverting the registration was tried and not adopted. On #9738 (LUCENE-8692, 2019) a maintainer (s1monw) listed addIndexes() among the methods whose exceptions "might cause documents go missing etc. but we treated them not as fatal or tragic events since a user could always call rollback()". Upstream's disk-full test rolls back, and getFieldNames is @lucene.experimental (IndexWriter.java:2129-2134).

Why it fails: no javadoc, test or discussion says a failed addIndexes may define a field's schema. In #13353 a document with the field did reach the indexing chain; here none did. rollback() discards all uncommitted work, a heavy remedy for a call that promises all or nothing, and the fix is local to addIndexes, where #633 already defers segment registration. Our reading: a defect (the devil's advocate stayed at "uncertain", not "not real"). The usual counter, "call rollback()", is met by the javadoc, #633 and the validation-versus-merge difference. No javadoc promises to undo in-memory bookkeeping (this is an inconsistency in the writer's session state: a call that adds nothing still changes which documents the writer accepts), and the claim is not that every failed call must undo its schema changes.

Suggested fix

#

Recommended Merge with private field numbers, register at publication (recommended; a tested prototype)

Let the merge number its fields privately and register them only when the merged segment is published, after checking all merges of the call against the writer and against each other. 35 added lines in IndexWriter.java; the repro, a two-block conflict check and every lucene/core test (8,923) pass with it.

// addIndexesReaderMerge: number the merged fields privately
new SegmentMerger(readers, segInfo, infoStream, trackingDir,
    new FieldNumbers(config.getSoftDeletesField(), config.getParentField()), ...);

// addIndexes(CodecReader...), in synchronized (this), before segmentInfos.addAll(infos)
synchronized (globalFieldNumberMap) {
  FieldNumbers check = new FieldNumbers(config.getSoftDeletesField(), config.getParentField());
  for (FieldInfos fis : incoming)
    for (FieldInfo fi : fis) { globalFieldNumberMap.verifyFieldInfo(fi); check.addOrGet(fi); }
  reserveDocs(totalDocs);
  for (FieldInfos fis : incoming)
    for (FieldInfo fi : fis) globalFieldNumberMap.addOrGet(fi);
}
All options and trade-offs3 options · 564 words

Three options. Only the first, recommended one covers both triggers and was validated with gradle; the second is a partial fix and the third a documentation change.

Merge with private field numbers, register at publication (recommended; a tested prototype) (validated by the checks)

#

In addIndexesReaderMerge, give the SegmentMerger a merge-private FieldNumbers(config.getSoftDeletesField(), config.getParentField()) instead of globalFieldNumberMap (IndexWriter.java:3574) and keep the merge's MergeState.mergeFieldInfos. In addIndexes(CodecReader...), inside the existing synchronized (this) publication block and under synchronized (globalFieldNumberMap), check every merge's fields against the writer (verifyFieldInfo) and against each other (a scratch FieldNumbers), then reserveDocs, then addOrGet them all, before segmentInfos.addAll(infos) (:3366). When a merge fails, drop the kept FieldInfos. One file, 35 insertions and 4 deletions. The core of it:

// addIndexesReaderMerge: number the merged fields privately
new SegmentMerger(readers, segInfo, infoStream, trackingDir,
    new FieldNumbers(config.getSoftDeletesField(), config.getParentField()), ...);

// addIndexes(CodecReader...), in synchronized (this), before segmentInfos.addAll(infos)
synchronized (globalFieldNumberMap) {
  FieldNumbers check = new FieldNumbers(config.getSoftDeletesField(), config.getParentField());
  for (FieldInfos fis : incoming)
    for (FieldInfo fi : fis) { globalFieldNumberMap.verifyFieldInfo(fi); check.addOrGet(fi); }
  reserveDocs(totalDocs);
  for (FieldInfos fis : incoming)
    for (FieldInfo fi : fis) globalFieldNumberMap.addOrGet(fi);
}

Trade-offs

  • The new segment's field numbers can differ from the writer's, as segments copied by addIndexes(Directory...) already can.
  • A concurrent document that introduces an incoming name with another schema while the merge runs is now accepted, and the addIndexes call then fails at publication with its files deleted (all or nothing); today that document is rejected.
  • The cross-check is needed: registering merge by merge still leaves the first merge's fields when a per-reader merge policy splits a conflicting import (executed with an earlier variant of this fix).
  • Open #16571 changes SegmentMerger.cleanupMerge and adds a partitioned-merge guard to addIndexes(CodecReader...) right after findMerges; it leaves mergeFieldInfos alone, but whichever lands second may need a small rebase in IndexWriter.java.
  • As a prototype, the diff drops the kept FieldInfos after the ensureOpen() at publication; a final patch should drop them first, so a writer closed in between keeps nothing.

Cross-check the incoming readers up front (smaller, partial; not built)

#

Extend the up-front check (IndexWriter.java:3288-3293) to also add every reader's fields to a scratch FieldNumbers, so readers that disagree with each other are rejected before the merge.

Trade-offs

Fixes only the fault-free conflict trigger; an I/O error during the merge still leaves the residue.

Document that a failed call needs rollback() or a reopen (not recommended)

#

State in the javadoc that after a failed addIndexes(CodecReader...) the writer's field schema may contain the incoming fields.

Trade-offs

Contradicts the transactional javadoc and the purpose of the up-front check; rollback() also discards all other uncommitted work.

Downstream note

#

Services that import indexes into a long-lived writer should reopen or roll back the writer after a failed addIndexes(CodecReader...) until this is fixed; nothing on disk needs repair.

How it was found

#

Code reading of IndexWriter's addIndexes failure paths and fault-injection probes (a simulated disk full while the merged segment is written, and an incoming reader whose stored fields throw during the merge) showed the leftover. A semi-formal bounded-exhaustive enumeration then injected one fault at every write of one call: all 14,802 runs left it.

The method in full207 words

Method: non-formal, then semi-formal.

  • Code reading of the addIndexes(CodecReader...) merge and its failure path, and hand-written probes on the stock jar: a simulated disk full while the merged segment is written, and a FilterCodecReader whose stored-fields reader throws during the merge. Both left the incoming name registered and a later document rejected; a reopened writer accepted it.
  • A bounded-exhaustive single-fault enumeration on the stock jar: one IOException at every destination createOutput and every IndexOutput write of one call, with SerialMergeScheduler and with ConcurrentMergeScheduler, against the javadoc's all-or-none promise (after a failed call that added no document, getFieldNames() is unchanged and every incoming-only name accepts a document with another schema). It found violations in 14,802 of 14,802 runs, in every merge phase after the field-info step (stored fields, norms, terms, doc values, points, vectors, .fnm, compound file, .si); a no-fault control registers and rejects (the oracle is not vacuous) and a validation-time failure leaves nothing. With the deferred registration the enumeration found 0 violations in 14,786 runs.
  • A later code reading of addIndexesReaderMerge found the fault-free trigger (the SlowCompositeCodecReaderWrapper.wrap skip for index sorts and blocks, and per-reader merges), executed with probes on main and on releases back to 8.11.4, and reduced to a one-test check.

History

#

Introduced in 4.2.0 (2013) by the LUCENE-4547 doc-values work (041ff1140f3f), first through addIndexes(IndexReader...); addIndexes(CodecReader...) has it since its first release, 5.0.0. Executed as failing from 4.2.0 through 10.6.0 and on main; 4.1.0 is not affected.

Versions tested7 rows

Introduced by 041ff1140f3f "make DV strongly typed; fix solr" (Michael McCandless, 2012-11-23, on the LUCENE-4547 branch), which gave FieldNumbers a per-field doc-values type that addOrGet enforces; it reached trunk as a181dc073539 and branch_4x as 5cbaddcbc7ff ("LUCENE-4547: DocValues improvements", 2013-02-07/08), first in 4.2.0. No PR (Subversion era).

Precondition: 54d3be3ad36 (LUCENE-2881, 2011, 4.0.0) made the addIndexes merger number its fields through the writer-wide map; until 4.2.0 that map held only names and numbers, so nothing was visible.

Later changes kept the shape: LUCENE-6158 and LUCENE-6165 (5.0.0) renamed the overload to addIndexes(CodecReader...) without changing the merge path; LUCENE-9334 (9.0.0) widened the enforced schema to every per-field attribute (so the repro's exact input conflicts only from 9.0.0); LUCENE-10216 (#633, 9.4.0) added the up-front check but kept the merge over the writer's map; #12622 (9.9.0) wrapped the readers of one merge, so the default configuration rejects a conflicting import cleanly, and #13128 (9.11.0) skips that wrap when readers have blocks but no parent field; since then the fault-free trigger needs an index sort, that blocks case or per-reader merges.

Releases between the executed ones were not run; a read of every release tag from 4.2.0 to 10.6.0 shows the addIndexes merger built over the writer's map. Not new in 10.6.

LFV-1081, snapshot of 2026-11-09

Registry title
A failed addIndexes(CodecReader...) leaves the incoming fields registered in the writer's field schema, so later valid documents that use those names differently are rejected until the writer is reopened
Area
index / IndexWriter addIndexes(CodecReader...) merge (SegmentMerger) and the writer-wide field registry (FieldInfos.FieldNumbers)
Priority
Low, rank 858: After an I/O failure during addIndexes(CodecReader...), the writer keeps the incoming field registrations and rejects later documents that use those names differently until it is reopened. The failure is loud and nothing is corrupted, and it needs an application that keeps using the writer after the failure, so it is Low.
Impact class
minor
Impact note
Hits applications that keep using an IndexWriter after an addIndexes(CodecReader...) call failed, in two ways: (1) the call is rejected because two incoming indexes disagree on a field's schema (a user error Lucene rightly rejects) on a writer with an index sort, or when the incoming indexes contain document blocks and have no parent field, or with a merge policy whose findMerges(CodecReader...) returns one merge per reader, and on every release before 9.9.0 with the default configuration; (2) an I/O error (for example a full disk) interrupts the merge, with any configuration. From then on every document that gives one of the incoming field names another schema is rejected with IllegalArgumentException, getFieldNames() lists those names, and retrying the import with only the second index (the one whose schema differs from the registered residue) is rejected too, until the writer is reopened, rolled back or deleteAll() is called; nothing on disk is corrupted, nothing of the failed import becomes visible, after an I/O error (2) a retry of the same import works, and documents without those names are unaffected; ordinary scale; every release from 4.2.0 through 10.6.0 (through addIndexes(IndexReader...) before 5.0.0).
Summary
You import an index with IndexWriter.addIndexes(CodecReader...) and the call fails with an IOException (for example a full disk) while the merged segment is written; as its javadoc promises, no documents are added, and the writer stays open. You expect the writer to behave as if the call had never happened, so that a later document may use an imported field name with any schema, as it may on a fresh or reopened writer and after a validation-time failure of the same call. Instead the merge has already registered every incoming field in the writer-wide field schema before it failed, and nothing undoes that: a later document with NumericDocValuesField("f") is rejected ('cannot change field "f" from index options=DOCS to inconsistent index options=NONE') although no document with "f" was ever indexed into this writer, until the writer is reopened. No I/O error is needed: on a writer with an index sort, when the incoming indexes contain document blocks without a parent field, or with a merge policy that returns one merge per incoming reader, two incoming indexes that use a field differently make the call fail with IllegalArgumentException and leave the first index's schema registered in the same way, so a later document, or an import of only the second index, is rejected; before 9.9.0 every conflicting two-reader import did so.
