Circle's javadoc example does not compile: LatLonShape.newDistanceQuery needs a QueryRelation

The only code example in the geo.Circle javadoc calls LatLonShape.newDistanceQuery("location", circle), but that method has always needed a QueryRelation as well, so the example has not compiled on any release since it was added in 10.3.0. Documentation only: with ShapeField.QueryRelation.INTERSECTS added, it compiles and finds what it should.

The finding in 30 seconds

#

A javadoc example that shows how to build a geo distance query calls a method signature that does not exist.

Background: shape queries and QueryRelation

#
  1. LatLonShape indexes points, lines and polygons given in latitude and longitude. Its query factories take the field, a query geometry such as a Circle (a centre and a radius in metres), and a ShapeField.QueryRelation.
  2. The relation says which indexed shapes match: INTERSECTS (the shape touches or overlaps the geometry), WITHIN, DISJOINT or CONTAINS. For indexed points, INTERSECTS with a circle means "within the radius".

The finding, step by step

#
  1. You want a geo distance query, so you copy the example from the Circle class javadoc: a circle of 1 km around the Eiffel Tower, new Circle(48.8584, 2.2945, 1000), then Query query = LatLonShape.newDistanceQuery("location", circle);.
  2. You expect it to compile and, on an index with two points 500 m and 5 km north of the centre, to match 1 document: the near one.
  3. Instead javac stops with 1 error, on 10.3.0, 10.6.0 and main: "incompatible types: Circle cannot be converted to QueryRelation".
  4. Why: the only overload is newDistanceQuery(String field, QueryRelation queryRelation, Circle... circle), unchanged since 8.5.0. The circles are varargs, so javac reads circle as the missing relation. No two-argument form has ever existed, so the example never compiled.
  5. Fix: write LatLonShape.newDistanceQuery("location", ShapeField.QueryRelation.INTERSECTS, circle). It compiles and matches exactly the point 500 m away.

Who is affected

#

Developers who start with Lucene's geo shape queries from the Circle javadoc (an @lucene.experimental class) and copy its only example, on any release from 10.3.0 to 10.6.0 or main. Nothing wrong ever runs: javac refuses the line and names the missing QueryRelation. Low impact, but plainly wrong.

Mechanism, terms and numbers438 words

The class javadoc of org.apache.lucene.geo.Circle has one "Example usage" (Circle.java:37-45 on main 645d4fe14a20): a circle of 1 km around the Eiffel Tower, then Query query = LatLonShape.newDistanceQuery("location", circle); (:44). Copied into code, that line does not compile on any release that has the example (10.3.0 to 10.6.0) or on main. The only LatLonShape.newDistanceQuery is newDistanceQuery(String field, QueryRelation queryRelation, Circle... circle) (LatLonShape.java:316-319), which has needed a ShapeField.QueryRelation since LUCENE-8707 added it in 8.5.0; no two-argument form has ever existed, so the example, added by #14534 in 10.3.0, could not compile on the day it was written. With ShapeField.QueryRelation.INTERSECTS the call compiles and, of two points 500 m and 5 km from the centre, matches only the near one. No runtime code is wrong.

The example (main 645d4fe14a20, Circle.java:37-45)

#
// Create a circle with 1km radius around the Eiffel Tower
Circle circle = new Circle(48.8584, 2.2945, 1000);

// Create a query using this circle
Query query = LatLonShape.newDistanceQuery("location", circle);

The mismatch

#
  • LatLonShape.java:315-319: the only overload is public static Query newDistanceQuery(String field, QueryRelation queryRelation, Circle... circle), documented as "create a query to find all polygons that intersect a provided circle."
  • Because the circles are varargs, a two-argument call has a matching arity (field, relation, zero circles), so javac tries to pass circle as the QueryRelation and reports incompatible types: Circle cannot be converted to QueryRelation at the query line (the test, which calls the compiler through javax.tools, prints the type names in full). A single non-varargs method with the same three parameters would get an arity error instead ("actual and formal argument lists differ in length"); -Xdiags:verbose confirms the mechanism: "required: String,QueryRelation,Circle[] found: String,Circle reason: argument mismatch".
  • No (String, Circle) method exists anywhere: LatLonPoint.newDistanceQuery takes (String, double, double, double) (LatLonPoint.java:296-297), LatLonPoint.newGeometryQuery takes (String, ShapeField.QueryRelation, LatLonGeometry...) (:327-328), and XYShape.newDistanceQuery takes (String, QueryRelation, XYCircle...) (XYShape.java:252-253). A class-file scan of 159 core jars, 1.9.1 to main, finds no (String, Circle) overload in any build.
  • ShapeField.QueryRelation (ShapeField.java:119-128) has the values INTERSECTS, WITHIN, DISJOINT and CONTAINS; INTERSECTS matches the method's own javadoc.

Why the build never noticed

#

Nothing in the build compiles <pre>{@code} blocks. The build enables Error Prone's InvalidSnippet check, which covers @snippet tags only (an observation of the hunt's devil's-advocate verifier). The open issue #9534 (LUCENE-8488) asks for compile-checked javadoc examples in general.

Not wider

#

The other code examples the same change added (Rectangle.java:53-60, geo/package-info.java:64-65) compile and run once Rectangle's free names lat, lon and radiusMeters are declared, so this is the one broken example in it.

Exposure and likelihood156 words
  • Who is hit. Anyone who copies the only code example in the Circle class javadoc to build a distance query on a LatLonShape field. Circle is @lucene.experimental (Circle.java:47).
  • Default vs opt-in. Not a configuration matter: every copy fails, on every release that has the example (10.3.0 to 10.6.0) and on main.
  • Scale. One line, one compile error. The message names ShapeField.QueryRelation, so a developer can recover from the method signature, but must then choose a relation the example does not explain: for indexed points INTERSECTS means "within 1 km", for lines and polygons "touches or overlaps the circle" (a point the hunt's refute reviewer made).
  • What it does not do. No wrong results, no runtime path, no index change. LatLonShape's API is right; only the Circle example is wrong. (The method's one-line javadoc, "find all polygons that intersect a provided circle", describes only the INTERSECTS case; the method takes any QueryRelation.)

Why it looks unintended

#
  • It calls a two-argument newDistanceQuery that has never existed: since 8.5.0 the only form is (String, QueryRelation, Circle...).
  • It is headed "Example usage" with no omission marker, in a change meant to improve user-facing geo docs.
  • The other examples from that change compile, and upstream has fixed wrong javadoc examples before.
The full argument163 words
  • Contract text. Circle.java:37: "Example usage:". LatLonShape.java:316-317: newDistanceQuery(String field, QueryRelation queryRelation, Circle... circle). LatLonShape's class javadoc describes each query factory it lists (box, line, polygon and geometry queries) as matching shapes "that have some {@link QueryRelation}" with the geometry (LatLonShape.java:61-68), and every LatLonShape query factory, newDistanceQuery included, takes a QueryRelation (LatLonShape.java:239-326).
  • History. LUCENE-8707 (d48bafb2999, apache/lucene-solr#587, Ignacio Vera, 2020-02-19; 8.5.0) added the method with this one signature. #14534 (bb8b1397b01, jainankitk, 2025-05-06; 10.3.0), "Improve user-facing docs for geo package", added the example; its one review (an approval by jpountz, "Great!") and its one comment (about the commit message) do not discuss it. The only later commit on the file, #15874 (2026-04-01), does not touch it.
  • Precedent. #10088 (LUCENE-9046, "Fix wrong example in Javadoc of TermInSetQuery") and #12693 ("chore: update the Javadoc example in Analyzer", merged 2023-10-18) fixed wrong javadoc examples.
  • Tests. No test compiles javadoc examples; #9534 (LUCENE-8488, open) asks for that in general.
The devil's-advocate check120 words

Strongest case for "intended" (built by the intended-behaviour checks and the refute review): javadoc <pre>{@code} blocks are uncompiled sketches that also leave out imports; the explicit relation is a deliberate API choice, shared by XYShape and LatLonPoint.newGeometryQuery; Circle is @lucene.experimental; and the error is loud and names the missing type.

Why it fails: a reader can supply missing imports, but not a missing mandatory argument. The defect is the example, not the API. @lucene.experimental warns that the API may change incompatibly, not that its current docs may be wrong. Loud means low impact, not intended. Every verifier and the adjudication rejected the "intended" reading; it stays at Low because it is a wrong API call, not a typo.
