NFARunAutomaton.step() throws on a 0-state automaton such as Operations.repeat(Automata.makeEmpty(), 2, 2) instead of returning MISSING

Every 10.x release is affected; queries are guarded, so only code that builds this internal runner itself hits it.

The finding in 30 seconds

#

The constructor always makes NFA state 0 the start state. For an automaton with no states, the first step asks it for state 0's transitions, and the read fails.

Background: NFARunAutomaton

#
  1. An Automaton stores each state's transitions as an offset and a count in an int array: state i uses states[2i] and states[2i + 1]. An automaton with 0 states is legal; it is the empty language, which Automata.makeEmpty() returns.
  2. NFARunAutomaton runs a non-deterministic automaton by building DFA states on demand. DFA state 0 is the start; step(state, c) returns the next state, or -1 (MISSING) when there is none.
  3. Queries such as RegexpQuery build the runner through CompiledAutomaton, and only for non-deterministic patterns.

The finding, step by step

#
  1. Build an automaton that matches nothing: Operations.repeat(Automata.makeEmpty(), 2, 2) has 0 states and is deterministic. new RegExp("#{2}").toAutomaton() gives the same.
  2. Wrap it in new NFARunAutomaton(a); that works. You expect step(0, 'x') to return -1 (MISSING), as its javadoc says and as a 1-state automaton with no transitions returns.
  3. You get ArrayIndexOutOfBoundsException: Index 0 out of bounds for length 0 (assertions off) or AssertionError: state=0 nextState=0 (assertions on).
  4. Why: the constructor always makes NFA state 0 the start state and never checks getNumStates(). The first step reads state 0's slot in a states array that Builder.finish() sized to exactly 0 entries. Automata.makeEmpty() keeps spare zero-filled slots, so with assertions off it returns -1 by luck.
  5. RegexpQuery and other queries are safe: CompiledAutomaton swaps a 0-state automaton for a 1-state one first. Only code that constructs the @lucene.internal runner itself is hit, and loudly.

Who is affected

#

Code that constructs NFARunAutomaton itself on an automaton whose language came out empty, for example a bounded repeat of something that never matches (#{2}, (a&b){2}), and then calls step, getNumTransitions or initTransition. Not the default: queries are guarded. Loud: an exception, never a wrong answer.

Mechanism, terms and numbers455 words

An automaton with 0 states is Lucene's ordinary empty language: Automata.makeEmpty() returns one, and Operations.repeat(Automata.makeEmpty(), 2, 2), new RegExp("#{2}").toAutomaton() and new RegExp("(a&b){2}").toAutomaton() produce one. new NFARunAutomaton(a) accepts it, and step(0, c) is documented to return the next state or MISSING (-1). Instead, for every 0-state automaton, the first step(0, c), getNumTransitions(0) or initTransition(0, t) fails with AssertionError: state=0 nextState=0 when assertions are on; for the last three, which are built with exact-size arrays, it throws ArrayIndexOutOfBoundsException: Index 0 out of bounds for length 0 with assertions off. The constructor registers the DFA start state as {NFA state 0} without checking that the automaton has a state 0, and Automaton.initTransition(0, ..) then reads a slot that does not exist. For Automata.makeEmpty(), whose arrays have spare capacity, the read returns 0 and step returns -1 by accident with assertions off. Lucene's own queries never reach this: CompiledAutomaton replaces a 0-state automaton with a 1-state one before it builds the runner. Every 10.x release, 10.0.0 to 10.6.0, and main are affected.

Exposure and likelihood111 words
  • Who. Application or library code that builds the runner directly from an empty-language automaton. No Lucene query or analysis path does: CompiledAutomaton guards 0 states and is the only in-tree caller.
  • Effect. An unchecked exception in the calling thread instead of "no match". No wrong result, nothing written, no hang. Only transition queries fail: the constructor succeeds, isAccept(0) is false, and run(bytes, 0, 0) on empty input returns false without calling step (ByteRunnable.java:49-56).
  • Scale. The smallest input triggers it; data size plays no part. Every 10.x release is affected.
  • Inconsistency. Two automata with the same empty language answer differently: makeEmpty() gives -1 with assertions off, repeat(makeEmpty(), 2, 2) throws.

Why it looks unintended

#
  • step() is documented to take state 0 and return the next state or MISSING (-1) when there is no transition; the constructor checks nothing.
  • 0 states is Lucene's normal empty language: Automata.makeEmpty() returns it, and Operations and CompiledAutomaton handle it.
  • Hidden array capacity decides the outcome: makeEmpty() gives -1 with assertions off, repeat(makeEmpty(), 2, 2) throws.
The full argument227 words
  • Contract. NFARunAutomaton.java:97-104: step takes a state that "should either be 0 or some state that is returned previously by this function" and returns "the next state or MISSING if the transition doesn't exist". ByteRunnable.java:22-30, which the class implements: "Returns -1 if not obtaining any such state".
  • No precondition. The constructor's only guidance is "should be NFA, for DFA please use RunAutomaton for better efficiency" (:58-59, :68-69). It does not reject deterministic or 0-state input, and its wording gives efficiency as the reason to prefer RunAutomaton. RunAutomaton, by contrast, enforces its precondition with IllegalArgumentException("Automaton must be deterministic") (RunAutomaton.java:55-65).
  • 0 states is first-class. new Automaton() "creates an automaton with no states" (Automaton.java:79); Automata.makeEmpty() returns "a new (deterministic) automaton with the empty language" (Automata.java:55); Operations.isEmpty treats no states as the common case (Operations.java:800-802); concatenate returns makeEmpty() for an empty operand (:79-81); CompiledAutomaton handles it (:154-157).
  • Tests and history are silent. TestNFARunAutomaton has no 0-state case: the three tests that step or walk transitions skip deterministic automata (:60-62, :90-92, :181-183), and the fourth, testRamUsageEstimation (:46-53), only calls ramBytesUsed(). The constructor line is unchanged since the class was added. In the sources checked (javadoc, CHANGES, MIGRATE, tests, the review comments on #225) nothing excludes 0-state input.
The devil's-advocate check173 words

Argument. The class is @lucene.internal, its only production caller guards 0 states, and that caller builds it only for non-deterministic input, while every 0-state automaton is deterministic. On #15689 (closed unmerged, 2026-02) dweiss wrote "Lucene's purpose is information retrieval, it's not a general-purpose regexp library". The cross-model reviewer (OpenAI GPT-5.6) rated this strong and called the bug not real on scope.

Why we still think it is a bug. It limits reach and severity, hence Low. @lucene.internal, which Lucene renders as "NOTE: This API is for internal purposes only and might change in incompatible ways in the next release.", warns outside callers off and reserves the right to change the API, but it does not narrow what step() documents. The public constructor accepts the input and then breaks its own documented return value. Following the "use RunAutomaton for a DFA" advice does not help: RunAutomaton crashes on the same input (LFV-029). The argument is still fair: a maintainer could reasonably prefer a documented precondition or close it as unsupported direct use.

Suggested fix

#

Recommended A. Substitute a 1-state automaton in the constructor

In the constructor, swap a 0-state automaton for a 1-state one with no transitions, as CompiledAutomaton already does. Same language, and state 0 now exists, so step returns -1. Constructor only. Validated with gradle: the test fails before and passes after; 307 automaton and query tests, 0 failures.

// NFARunAutomaton.java:72
 public NFARunAutomaton(Automaton automaton, int alphabetSize) {
+  if (automaton.getNumStates() == 0) {
+    automaton = new Automaton();
+    automaton.createState();
+    automaton.finishState();
+  }
   this.automaton = automaton;
All options and trade-offs3 options · 407 words

One validated option and two alternatives that were not run. A is the smallest change, at the place that invents the start state, and copies an existing in-tree guard.

A. Substitute a 1-state automaton in the constructor (validated by the checks) (recommended)

#

When automaton.getNumStates() == 0, use a fresh automaton with one non-accepting state and no transitions: the same empty language, but state 0 exists. The same pattern as CompiledAutomaton.java:154-157.

// NFARunAutomaton.java:72
 public NFARunAutomaton(Automaton automaton, int alphabetSize) {
+  if (automaton.getNumStates() == 0) {
+    automaton = new Automaton();
+    automaton.createState();
+    automaton.finishState();
+  }
   this.automaton = automaton;

Trade-offs

  • Constructor only, no hot-path change; automata with at least one state are untouched.
  • For 0-state input the package-private getAutomaton() returns the substitute; its only user, CompiledAutomaton.sharesAutomaton (:508-510), never passes a 0-state automaton.
  • equals/hashCode (NFARunAutomaton.java:271-281) then compare the 1-state substitute instead of the caller's automaton, and ramBytesUsed() (:261-267) measures the substitute.
  • The runner no longer holds the caller's object, so later changes to it would not reach the runner (which already fixes getStartPoints() at construction, :74). Option B avoids this.

B. Mark the start state dead instead

#

Keep the caller's automaton; when it has 0 states, pre-fill the start DState's transitions with MISSING and mark them computed, so nextState returns MISSING and determinize() returns early with 0 outgoing transitions.

Trade-offs

Keeps getAutomaton() identity, but needs a helper inside DState: more code to review. Not run.

C. One change in Automaton for all sibling sites

#

Give Builder.finish() spare capacity like new Automaton(), or let Automaton.initTransition return 0 for a missing state.

Trade-offs

Spare capacity only hides the read with assertions off; the assertion at Automaton.java:481 still fails, as makeEmpty() shows today. Relaxing initTransition changes a widely used method, needs a wider compatibility review and could hide other invalid-state bugs. A shared 0-state policy for all four sibling sites is a reasonable alternative for maintainers to weigh. Not run.

Downstream note

#

Products that run user regexes through RegexpQuery are not affected, because CompiledAutomaton guards first; only code that hands automata straight to this internal runner sees the exception.

How it was found

#

Semi-formal. A proof-obligation analysis of NFARunAutomaton's contract asked whether step() returns MISSING for every automaton the constructor accepts, including the 0-state empty language; a one-test JUnit repro on main showed it does not. Independent verifiers then reproduced and confirmed it.

The method in full78 words
  • Obligation. For every automaton the public constructor accepts, step(0, c) must return a state or MISSING; the empty language is a standard 0-state value, so it is in scope.
  • Witness. One JUnit test on the stock main jars, run with assertions on and off and on the 10.6.0 release jars.
  • Checks. An independent reproducer, a cross-model reviewer (OpenAI GPT-5.6), an intended-behaviour devil's advocate, an adjudication and a separate re-run, each with its own runs (see Independent checks).

Summary

The step() javadoc promises the next state or MISSING (-1) when no transition exists, so you expect -1, which is what a 1-state automaton with the same empty language returns.
