ConfusionMatrix.getPrecision() skips classes that are assigned but never correct, so macro precision is too high

ConfusionMatrix.getPrecision() averages the per-class precision only over classes that are some document's correct answer, so a class the classifier assigns but no evaluated document has never lowers it. Four "sports" documents answered "politics" three times give 1.0 instead of 0.5; every release since 6.1.0 does this.

The bug in 30 seconds

#

Lucene's classification module can score a classifier on labelled documents: ConfusionMatrixGenerator.getConfusionMatrix builds a confusion matrix with one row per correct answer and, inside each row, a count per assigned class. getPrecision(String) gives one class's precision; getPrecision() is their macro average.

  1. Evaluate a classifier with ConfusionMatrixGenerator.getConfusionMatrix on four documents labelled "sports". It answers "sports" once and "politics" three times: the matrix is {sports={sports=1, politics=3}}.
  2. Per class, precision is right: getPrecision("sports") = 1/1 = 1.0 and getPrecision("politics") = 0/3 = 0.0.
  3. getPrecision() is "the macro averaged precision (see getPrecision(String)) over all the classes", so you expect (1.0 + 0.0) / 2 = 0.5.
  4. You get 1.0. The macro loop runs over the matrix rows, which are the correct answers only; "politics" is only a column, so it is in neither the sum nor the count. getF1Measure() is too high with it: 0.4 instead of 0.333.
  5. Real workflow: the built-in SimpleNaiveBayesClassifier, trained on one index and evaluated on a held-out index of four "sports" documents, answers "politics" twice; macro precision reads 1.0, not 0.5.

Who is affected

#

Applications and tests that evaluate a classifier with ConfusionMatrixGenerator (opt-in lucene/classification module) and read getPrecision() or getF1Measure(), whenever an assigned class has no evaluated document: a held-out split that lacks a rare class, or a custom classifier. The value is never too low, and too high whenever at least one answer is right. Per-class numbers, indexing and search are unaffected.

Mechanism, terms and numbers674 words

ConfusionMatrixGenerator.getConfusionMatrix runs a classifier over the labelled documents of a reader and files each document under its correct answer, counting the class it was assigned inside that row. ConfusionMatrix.getPrecision(), documented as "the macro averaged precision (see getPrecision(String)) over all the classes", then averages getPrecision(klass) over the rows only and divides by the number of rows. A class that the classifier assigns but that no evaluated document has as its correct answer exists only as a column: its precision is well defined and 0, but it is left out of the sum and the count, so its wrong answers never lower the macro value, which is too high whenever at least one answer is right. Four "sports" documents answered "politics" three times give 1.0 instead of 0.5; the built-in SimpleNaiveBayesClassifier evaluated on a held-out index gives 1.0 with half its answers wrong; getF1Measure(), built from it, is too high as well. Per-class precision, the matrix, indexing and search are unaffected. Every release from 6.1.0 to 10.5.2 and main is affected; averaging over the union of the matrix's rows and columns fixes it.

Terms

#
  • Confusion matrix: getConfusionMatrix(reader, classifier, classField, textField, timeout) asks the classifier for a class for every document of reader that has a class value and a stored text, and counts (correct class, assigned class) pairs. getLinearizedMatrix() returns it as "a Map whose keys are the correct classification answers and whose values are the actual answers' counts" (ConfusionMatrixGenerator.java:172-177): rows are correct answers, the inner keys are assigned classes.
  • Precision of a class: of the documents the classifier assigned to that class, the share whose correct answer it is: tp / (tp + fp). getPrecision(String) computes it from the class's row and column (:188-205).
  • Macro average: the plain mean of a per-class metric over the classes, so that small classes count as much as big ones. getPrecision() is documented as "the macro averaged precision (see getPrecision(String)) over all the classes" (:287).
  • Assigned-only class: a class the classifier returns that is the correct answer of no evaluated document. It appears only as an inner key (a column), never as a row.

The bug

#
  1. getConfusionMatrix files each document under its correct answer: the assigned class if it is one of the document's correct answers, else correctAnswers[0] (:118-123), and counts the assigned class inside that row (:125-137). So rows are correct answers only.
  2. getPrecision(String) for an assigned-only class finds no row, so tp is 0 and it returns 0 (:204): right, since none of its answers was right.
  3. getPrecision() sums getPrecision(klass) over linearizedMatrix.entrySet() and returns p / linearizedMatrix.size() (:291-299): rows only. The assigned-only class, with its precision of 0, is in neither the sum nor the divisor.
  4. Leaving out a 0 never lowers a mean. With an assigned-only class the reported macro precision is too high whenever at least one answer is right (if none is, every precision is 0 and both means are 0); without one it is exact. getF1Measure() (:246-250) is the harmonic mean of getPrecision() and getRecall(), so it is too high too.

Exposure and likelihood315 words
  • Who is exposed. Callers of getConfusionMatrix who read getPrecision() or getF1Measure(). Inside Lucene only tests call it (a grep of lucene/*/src/java finds only the class itself), so the users are direct API users. getPrecision(String), getRecall(String) and the matrix are correct.
  • When. Whenever at least one assigned class has no evaluated document with it as the correct answer: evaluating on an index other than the training index (the reader's @param describes the training index, but the module ships DatasetSplitter, and its Test20NewsgroupsClassification, a @Monster test skipped in normal runs, calls getConfusionMatrix(testReader, ...) on its held-out reader); any custom Classifier, since assignClass has no label restriction (upstream's own TestConfusionMatrixGenerator stub returns new BytesRef(), a class no document has); and, by reading only, documents that getConfusionMatrix leaves out (no stored class or text, a null result, the hard-coded 5-second per-call timeout, the cumulative cutoff) while their class is still assigned to others. With a built-in classifier evaluated on its own training reader and a single-valued class field it is uncommon, but it can happen: the built-in naive Bayes classifiers take their classes from the class field's index terms, which still include a class whose documents are all deleted but not yet merged away. The fact check ran this: 3 live "sports" and 30 deleted "politics" documents give {sports={politics=2, sports=1}} and macro precision 1.0 instead of 0.5.
  • Default vs opt-in. No setting is needed: it is the only behaviour of getPrecision(). The module is opt-in.
  • Size. Up to the full gap to 1.0: three wrong answers out of four leave it at 1.0. Two documents are enough.
  • Silent. A plausible number between 0 and 1, no exception, no warning. A comparison of classifiers by macro precision or F1 can favour one that sends its mistakes into a class the test set lacks.
  • Versions. Every release from 6.1.0 (2016) to 10.5.2 and main.

Why it is a bug, not intended

#
  • The javadoc promises the macro average "over all the classes", and getPrecision("politics") is defined: 0.0.
  • LUCENE-7305 added it "to avoid bias ... from imbalanced classes"; dropping these classes biases it upward only.
  • A never-assigned class (0/0) is averaged in as 0, an always-wrong one (0/3) is left out; no doc, test or issue asks for that.
The full argument294 words
  • Contract. getPrecision(): "get the macro averaged precision (see {@link #getPrecision(String)}) over all the classes." (ConfusionMatrixGenerator.java:287). It points to the per-class method, which accepts any class and is defined for an assigned-only class. The classes of a confusion matrix are its rows and its columns.
  • Stated goal. LUCENE-7305 (#8359), which introduced the macro average: "ConfusionMatrix multi class measures should be based on macro average to avoid bias (for the good or the bad) from imbalanced classes." A class with zero correct-answer documents is the extreme imbalance.
  • Not an "undefined values are skipped" rule. A correct-answer class that is never assigned has precision 0/0; getPrecision(String) returns 0 for it and it is averaged in (control: 0.25). The assigned-only class has a defined precision of 0 and is the one left out.
  • Not a "gold classes" rule either. With a multi-valued class field a wrong answer is filed under correctAnswers[0] only (:118-123): gold {a, b} answered c plus gold {c} answered c gives rows {a, c}, so "b", a correct answer, has no row (executed by the devil's advocate). The row set is a by-product of how documents are filed.
  • Nothing documents or tests it. No javadoc, CHANGES or MIGRATE entry; every aggregate assertion in the upstream tests is only 0 <= value <= 1, including the test whose stub assigns a class no document has; the five related issues (#7538, #7912, #8211, #8248, #8359) have one-line bodies (a feature or fix request each) and only commit notices as comments, plus one thank-you; none discusses which classes the averages run over.
  • History. The row-only loop came from LUCENE-6854 (d9f4eb84cfb, 2016-01-08), when getPrecision() was a micro average; LUCENE-7305 (dc50b79a146) kept the loop and changed the formula around it.
The devil's-advocate check257 words

The strongest "works as designed" case (the cross-model reviews rated it moderate; the devil's advocate moderate overall, strong for recall and weak for precision; the independent reproducer moderate-to-weak): getLinearizedMatrix() documents its keys as the correct answers, so "all the classes" can mean "all the correct-answer classes"; averaging over the test set's classes is a recognized convention (Weka 3.8's unweightedMacroFmeasure skips classes with no test instance "since recall is undefined there anyway"; scikit-learn with labels set to the gold labels gives Lucene's numbers); getConfusionMatrix documents its reader as "the IndexReader containing the index used for creating the Classifier", and with that setup the built-in classifiers rarely assign a class with no evaluated document; and precision is not meant to count misses, while macro recall (0.25) does show them.

Why it fails for precision: Weka's reason, undefined recall, does not apply to precision, which is defined and 0; the code does not implement the gold-class convention (multi-valued case); scikit-learn's default macro average uses the union of true and predicted labels (0.5 and 0.667 on the two examples); the module's own split workflow (a @Monster test, and a use the reader's @param does not describe) evaluates on another reader, where the built-in naive Bayes classifier reads 1.0 with half its answers wrong; even the training reader can produce it; and nothing documents the exclusion. The union is one recognized convention, not the only one. A javadoc fix is still a legitimate answer for the maintainers. Recall is not claimed: a class that is never a correct answer has recall 0/0.

Suggested fix

#

Recommended Average precision over the rows and columns; document recall's set (fix A)

Average getPrecision(String) over the union of the matrix's rows and columns, the correct and the assigned classes (+13/-5 lines with javadoc), and document that getRecall() averages over the correct answers. Nothing changes when every assigned class is also a correct answer. The new test and the whole classification suite pass with it.

public double getPrecision() {
  // a class that is assigned but never a correct answer is only a column key
  Set<String> classes = new HashSet<>(linearizedMatrix.keySet());
  for (Map<String, Long> answers : linearizedMatrix.values()) {
    classes.addAll(answers.keySet());
  }
  double p = 0;
  for (String klass : classes) {
    p += getPrecision(klass);
  }

  return p / classes.size();
}
All options and trade-offs4 options · 661 words

Fix A is the narrow change; fix B uses one class set for both macro averages. Both were validated the same way. The choice between them, or a javadoc-only answer (C), is the maintainers': say in the issue that recall uses the same row-only loop but that the recall of a class that is never a correct answer is 0/0.

Average precision over the rows and columns; document recall's set (fix A) (validated by the checks) (recommended)

#

ConfusionMatrixGenerator.getPrecision() collects the row keys and every inner key into a set and averages getPrecision(klass) over it; the javadoc of getPrecision() names the set, and the javadoc of getRecall() says it averages over the correct answers. The algorithm is the finder's fix sketch, with a revised comment and javadoc. With a multi-valued class field the matrix keys are the correct answer each document is filed under, so the owner may word recall's javadoc that way.

public double getPrecision() {
  // a class that is assigned but never a correct answer is only a column key
  Set<String> classes = new HashSet<>(linearizedMatrix.keySet());
  for (Map<String, Long> answers : linearizedMatrix.values()) {
    classes.addAll(answers.keySet());
  }
  double p = 0;
  for (String klass : classes) {
    p += getPrecision(klass);
  }

  return p / classes.size();
}

Trade-offs

  • No change when every assigned class is also a correct answer (both controls unchanged); an empty matrix still gives NaN (0/0), as today.
  • Precision and recall then average over different class sets and getF1Measure() combines them; the javadoc says so. Lead example: F1 0.4 becomes 0.333.
  • Cost: one extra pass over the matrix, negligible next to classifying the documents.

One class set for both macro averages (fix B) (validated by the checks)

#

A private getClasses() returns the rows plus the columns; getPrecision() and getRecall() both average over it, and both javadocs say "over all the classes: the correct answers and the assigned classes" (+24/-8).

Trade-offs

  • Matches scikit-learn's default macro average for both metrics, and F1 is computed on one set.
  • Also lowers getRecall(): an assigned-only class adds a recall of 0 (the code's 0-for-undefined convention), so the lead example's macro recall goes from 0.25 to 0.125 and F1 from 0.4 to 0.2. Under the Weka convention that recall is undefined and should be skipped.

What the checks validated

Scratch worktree, gradle: the new test with TestConfusionMatrixGenerator (2 suites, 10 tests), the whole :lucene:classification:test with assertions on and off (13 suites, 46 tests, 1 skipped, 0 failures each) and :lucene:classification:check -x test pass. Standalone runner: the new test 3 of 3, the independent reproducer's test 3 of 3.

Document the row-only set (fix C)

#

Say in the javadoc of getPrecision() and getRecall() that they average over the keys of getLinearizedMatrix() (the correct answer each document is filed under) and that classes only ever assigned are not counted.

Trade-offs

No behaviour change, so the upward bias stays, but it becomes documented. Nothing to run.

Let the caller pass the class set (not built)

#

An overload such as getPrecision(Collection<String> classes), so a caller can average over the classifier's full label set, for example the class field's terms.

Trade-offs

New API; leaves the default as it is unless combined with A or B.

Downstream note

#

A product that gates a model rollout or a threshold on this macro precision or F1 would base that decision on a number that is too high.

How it was found

#

An AI finder drove the public getConfusionMatrix with a stub classifier over every dataset of 1 to 5 documents (15,503) and compared each metric with reference formulas. Per-class precision, recall and F1 always matched; macro precision was above the mean over all the matrix's classes in 7,056 datasets. It then reduced this to a public-API JUnit test.

The method in full237 words

Method: semi-formal, bounded-exhaustive translation validation: the real metrics against reference formulas (per class, and macro averages over all the matrix's classes and over the correct-answer classes), over every case in a small bounded space, on the stock main jar.

  • Space: every multiset of 1-5 evaluated documents, correct class in {a, b, c}, assigned class in {a, b, c, d}, or a null result, which leaves the document out: 15,503 datasets, each driven through the public getConfusionMatrix with a stub classifier.
  • Result: per-class precision, recall and F1 equal their formulas in all 15,448 datasets with an evaluated document (the 55 with none give NaN). Macro precision differs from the mean over all the matrix's classes in 7,056 (always higher) and equals the mean over the correct-answer classes only in all 15,448. That pointed straight at the label set of the macro loop. The harness also recorded 7,056 macro-recall and macro-F1 differences from the all-classes reference (recall is not claimed) and 13,950 getAccuracy() differences from correct / evaluated (a separate, unregistered lead).
  • With the union fix, the harness has 0 macro-precision mismatches against the all-classes mean and 7,056 against the correct-answer-only mean (macro recall and F1, untouched by the fix, still differ in 7,056), so the harness tells the two readings apart.
  • The finder then wrote the 2-test JUnit; an independent reproducer, the cross-model reviews, a devil's advocate, an adjudication and an audit each re-ran or rewrote it.

#

Bug record

LFV-768, snapshot of 2026-10-27

Registry title
ConfusionMatrix.getPrecision() leaves out classes that are assigned but never the correct answer, so their false positives do not lower macro precision (1.0 instead of 0.5 when 3 of 4 'sports' documents are answered 'politics')
Area
classification / ConfusionMatrixGenerator.ConfusionMatrix (classifier evaluation utility: macro-averaged precision)
Priority
Medium, rank 198: ConfusionMatrixGenerator silently overstates macro precision and F1 in the ordinary case where some class is only ever assigned, the same silent wrong evaluation output as the Medium DatasetSplitter utility rows, so it closes the classification block right after LFV-682 instead of sitting in Low with the timeout row LFV-633.
Impact class
minor
Impact note
Applications or tests that evaluate a Classifier with ConfusionMatrixGenerator.getConfusionMatrix (an opt-in evaluation utility in lucene/classification; in-tree only tests call it) and read getPrecision() or getF1Measure() get an overstated macro precision, with no error, whenever the classifier assigns at least one class that no evaluated document has as its correct answer (for example a class missing from a held-out test split, or any label a custom Classifier returns): that class's false positives are left out (minimal case 1.0 instead of 0.5; the built-in SimpleNaiveBayesClassifier evaluated on a held-out index reads 1.0 with half its answers wrong); per-class getPrecision(String) stays correct, no index, search or stored data is touched, and it is in every release from 6.1.0 to 10.5.2 and main.
Summary
You evaluate a classifier with ConfusionMatrixGenerator.getConfusionMatrix and read ConfusionMatrix.getPrecision(), documented as 'the macro averaged precision (see getPrecision(String)) over all the classes', and expect the mean of getPrecision(String) over every class in the matrix, including a class the classifier assigned but that no evaluated document has as its correct answer (its per-class precision is correctly 0). Instead getPrecision() averages only over the matrix's row keys, which are the correct answers, so such an assigned-only class is left out of both the sum and the count: four 'sports' documents of which three are answered 'politics' give macro precision 1.0 instead of 0.5, and getF1Measure(), which is built from it, is overstated too.
