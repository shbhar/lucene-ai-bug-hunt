Vector similarity queries tell the query cache they are cacheable, so one reader's or one search's result is served to another

FloatVectorSimilarityQuery and siblings tell the query cache their per-segment result is shareable, but it has one reader's deletions, one search's timeout and the filter baked in: other readers and searches get 2 hits instead of 3, 0 instead of 3, or a document the filter rejects. Affected: 9.10.0-10.5.2 and main.

The bug in 30 seconds

#

The query cache stores one doc set per query and segment and shares it between readers whose deletions differ, so the set must ignore deletions; each search removes its own deleted docs afterwards. This query builds its set with the current reader's deletions, the search's timeout and the filter, and still says "cacheable".

  1. Index docs 0-5 in one segment, doc i with vector (i, 1). FloatVectorSimilarityQuery with target (0, 1) and threshold 0.15 matches docs 0, 1, 2 (similarity 1.0, 0.5, 0.2). Run it as a count or filter, so the query cache may store its result.
  2. Open reader A, delete doc 1, reopen as reader B. Both share the segment, and the cache keys entries on query + segment, so one entry serves both. B counts first and correctly gets 2.
  3. You expect A, where doc 1 still exists, to count 3. Instead it gets 2, hits [0, 2]: the cache hands A set B built with B's deletion applied. TermQuery in the same order gives 3.
  4. Same flaw, two more ways: a search whose timeout fires caches its empty result, so a later search without a timeout gets 0, not 3 (10.0.0 and later, approximate path); and after doc 2's filter field is updated in place, the newer reader still gets 3, doc 2 included, although the filter now rejects it.
  5. No error is raised. On 9.10.0-10.5.2 a plain new IndexSearcher(reader) already shares a default cache: a zero-configuration probe fails on every release, and with the same settings installed explicitly on main, 12,000 docs and 6 repeated searches give the older reader 11,999 instead of 12,000.

Who is affected

#

Anyone running a vector similarity query without scores (IndexSearcher#count, ConstantScoreQuery, a FILTER or MUST_NOT clause) through a query cache shared by readers or searchers: the default on 9.10.0-10.5.2, an installed cache on main. It then takes an older reader searched after a newer one, a timed-out search, or a filter on doc values updated in place.

Mechanism, terms and numbers876 words

FloatVectorSimilarityQuery, ByteVectorSimilarityQuery and Float16VectorSimilarityQuery (the last on main only) share one Weight that runs the vector search per segment and builds the matching set with three inputs that are not part of the segment: the reader's live docs, the searcher's timeout (on the approximate path), and the filter. Yet its isCacheable returns true. LRUQueryCache keys entries on the query and the segment core, which readers that differ only in deletions or doc-values updates share, so the first reader or search that fills the entry decides what the others get in non-scoring use (IndexSearcher#count, ConstantScoreQuery, a FILTER or MUST_NOT clause, also inside a scoring query): an older point-in-time reader misses a document only a newer reader deleted (2 instead of 3 in the diagram's example, 99 instead of 100 in the test), a search without a timeout gets an earlier timed-out search's empty result (0 instead of 100), and a filter on doc values updated in place lets through a document it now rejects (100 instead of 99). As a MUST_NOT clause the stale set excludes too little, so the parent query returns too much (1 instead of 0; 100 instead of 0 after a timeout). No error is raised. It has been in every release since the query appeared in 9.10.0 (the timeout case since 10.0.0); on 9.10.0-10.5.2 the default IndexSearcher cache is enough, on main an application must install a cache.

Terms

#
  • Query cache: LRUQueryCache stores, per query and per segment, the set of documents a non-scoring query matches, and reuses it. Its javadoc: "these cache and policy instances can be shared across several queries and readers" (LRUQueryCache.java:80). In 9.x and 10.x releases every IndexSearcher shares one static default cache with UsageTrackingQueryCachingPolicy (10.5.2 IndexSearcher.java:83-99); on main the default is null (IndexSearcher.java:84, #14187).
  • Segment core: readers opened at different times, or wrapped views of one reader, share a segment's core when only its deletions or doc-values updates differ. The cache key uses the core (getCoreCacheHelper()), documented to cache "regardless of deletions"; readers with "different sets of deleted documents or doc values updates may be considered equal" (LeafReader.java:65-69). That is safe because an ordinary query's cached set ignores deletions and every search applies its own reader's live docs afterwards.
  • Vector similarity query: new FloatVectorSimilarityQuery.Adaptive(field, target, resultSimilarity, decay, filter) matches every document whose vector similarity to target is at least resultSimilarity; decay 1 is the exact path, the default 0.5 an approximate graph search. @lucene.experimental.

The bug

#
  1. createWeight (AbstractVectorSimilarityQuery.java:146) builds the filter Weight (:149-152) and captures searcher.getTimeout() with a TimeLimitingKnnCollectorManager (:154-156).
  2. scorerSupplier reads leafReader.getLiveDocs() (:188) and builds the set from it on every path: exact "to guarantee completeness" (:192-198, AcceptDocs.fromLiveDocs at :196), approximate (:200-207, :204), and filtered (AcceptDocs.fromIteratorSupplier(filter iterator, liveDocs, maxDoc), :209-220). With a filter, decay 1 goes straight to an exact search (:228-233); otherwise a graph search runs first and its result is returned when it is complete or the timeout has fired ("Return partial results only when timeout is met", :239-243), else the Weight falls back to an exact scan (:244-248). Without a filter, the approximate path returns its partial result after a timeout as is (:200-207). So the timeout is read only on the approximate paths (decay below 1).
  3. isCacheable(ctx) returns true (:252-255) and never asks filterWeight.isCacheable(ctx), whereas BooleanWeight and ConstantScoreQuery pass on their children's answer (BooleanWeight.java:273-285, ConstantScoreQuery.java:193-194).
  4. LRUQueryCache trusts it (LRUQueryCache.java:816) and stores or finds the set under the query plus getCoreCacheHelper() (:827, :834); count returns the cached count for a reader without deletions (:892-924).
  5. The next reader or search on that core gets the cached set intersected with its own live docs: it loses documents (live docs, timeout) or, through the filter, keeps one that no longer matches.

The top-k Knn*VectorQuery avoids this: it rewrites to DocAndScoreQuery, whose equals/hashCode include the reader context identity (DocAndScoreQuery.java:294-306) and whose createWeight rejects another reader (:170).

Exposure and likelihood543 words
  • Who is exposed. Non-scoring use (count, ConstantScoreQuery, a FILTER or MUST_NOT clause, also inside a scoring query) of FloatVectorSimilarityQuery, ByteVectorSimilarityQuery (both since 9.10.0) or Float16VectorSimilarityQuery (main only) with a query cache shared by several readers or searchers, plus one of: an older point-in-time reader searched after a newer one with fresh deletions on the same segment (a documented pattern: SearcherLifetimeManager "Keeps track of current plus old IndexSearchers", for example when "the user clicks next page", SearcherLifetimeManager.java:30, :48; also in-flight requests on the previous searcher after a refresh), or a soft-deletes view next to the raw view of one commit; a search with IndexSearcher#setTimeout whose timeout fires on the approximate path (10.0.0 and later); or a filter on a doc-values field updated in place.
  • Not exposed. A direct scoring use, with the similarity query at the top of search(q, n): IndexSearcher wraps a Weight in the cache only when scores are not needed (IndexSearcher.java:979-981; the probe's scoring search(q, 10) is right). But FILTER and MUST_NOT clauses of a scoring BooleanQuery are created without scores (BooleanClause.java:84-86, BooleanWeight.java:58-59) and are cached, so they are exposed (executed). Also not exposed: separate caches, and main without an installed cache.
  • Default or opt-in. On 9.10.0-10.5.2 no configuration is needed: IndexSearcher installs a static LRUQueryCache(1000, min(32 MB, heap/20)) with UsageTrackingQueryCachingPolicy, shared by every searcher. A zero-configuration probe (new IndexSearcher(reader), default IndexWriterConfig) fails on every release 9.10.0-10.5.2 and passes on main, where #14187 (in no release yet) removed the default cache. The query itself is @lucene.experimental, and a threshold vector query used as a filter is a niche use.
  • Scale. None with an always-cache policy (6 documents). With the default policy the query becomes eligible on its 5th use (UsageTrackingQueryCachingPolicy.java:122-138) and is then cached on segments of at least 10,000 documents that are not much smaller than the average (LRUQueryCache.java:251-253, :278-296), if the worst-case entry fits and the lead-cost check passes (:792-807, :816-853). The doc's test installs these settings explicitly; its 12,000-document case goes wrong after 6 searches.
  • How long. A wrong entry stays until LRU eviction, an explicit clearQuery, clearCoreCacheKey or clear (LRUQueryCache.java:443-457), or until its segment core closes, after a merge has replaced the segment and the last reader holding it is closed (:1133-1135). A poisoned timeout entry survived an NRT reopen with an unrelated deletion (0 instead of 11,999) in the security probe.
  • What you see. No error, assertions on or off. Fewer hits or a lower count (live docs, timeout), or a document the filter rejects (filter); as a MUST_NOT clause, documents the clause should exclude (1 hit instead of 0; 100 instead of 0 after a timeout). It is not approximate recall: the exact path (decay 1) is affected and separate caches are right.
  • Downstream (source reading only, nothing run there): OpenSearch's k-NN plugin builds these queries for radial search (already in 2.x releases); since 3.7.0 the server also sets IndexSearcher#setTimeout, and it uses a node-level LRUQueryCache, so the timeout case may reach its users on 3.7.0 and later. Solr's searcher disables Lucene's query cache; a code search found no use of these queries in Elasticsearch.

Why it is a bug, not intended

#
  • SegmentCacheable: only objects that "depend only on segment-immutable structures" may return true. Live docs, a timeout and an updated filter are not.
  • The cache key ignores deletions and doc-values updates by contract (LeafReader#getCoreCacheHelper).
  • The exact path, documented "to guarantee completeness", is affected too; TermQuery and separate caches are right in the same sequences.
The full argument341 words
  • The contracts. SegmentCacheable.java:24-35: "Objects that depend only on segment-immutable structures such as Points or postings lists can just return true"; "Objects that depend on doc values should return DocValues#isCacheable ... Updated doc values fields are not suitable for caching"; "Objects that are not segment-immutable ... should return false". LeafReader.java:65-69: the core cache helper caches "regardless of deletions"; readers with "different sets of deleted documents or doc values updates may be considered equal". QueryCache.java:26-30: the returned weight "will only be equivalent if scores are not needed". LRUQueryCache.java:893: "Our cache won't have an accurate count if there are deletions", so cached sets are meant to be computed without applying deletions.
  • Upstream tests. testTimeout turns the cache off: "This query is cacheable, explicitly prevent it" (BaseVectorSimilarityQueryTestCase.java:623-624, added by #13285; copied into BaseExplicitVectorSimilarityQueryTestCase.java:503-504 by #16654). That avoids only the harmless direction, a cached full result hiding a timeout. The test framework installs query caches at random (LuceneTestCaseParent.java:2635, :2686), which is why the test must turn the cache off; the upstream similarity-query tests never reopen a reader, update doc values, or share one cache across readers or searchers. TestLRUQueryCache asserts that cached counts equal uncached ones across SearcherManager refreshes with deletions: the repro's oracle.
  • History. #12679 (2023) added the query with isCacheable returning true; #13285 (2024) added the timeout input; neither thread discusses query caching. The query's author later commented, in another contributor's open PR #13594, that "the similarity query is cacheable" as a design difference from the top-k query, and that top-k kNN queries are not cacheable because deletes invalidate per-segment results (#15379): the same principle, applied to the other family.
  • Precedent. LUCENE-8017 (#9065): FunctionRangeQuery and FunctionMatchQuery could "pollute the QueryCache" and were made non-cacheable, which led to the SegmentCacheable contract (LUCENE-8042, #9090). In LUCENE-10060 (#11098) jpountz wrote that the cache keys on the segment core, "everything but live docs and doc-value updates", which "requires cache entries to be computed on the entire segment and follow-up searches to apply deletes on top of cache entries".
The devil's-advocate check308 words

The strongest case for "intended" (built by a devil's-advocate verifier, an OpenAI GPT-5.6 reviewer arguing "works as designed" and the adjudication): the author says the query is cacheable by design (#13594); the upstream timeout test knowingly disables the cache; the classes are @lucene.experimental and search "all (approximate) vectors"; Weight#scorer only says live docs "need to be checked on top", which does not forbid a Weight from applying them; and timeouts deliberately allow partial results, so an application could be expected to turn off or partition caching for searches with a timeout.

Why it fails: "cacheable" claims that caching is legal, not that serving one reader's or search's result to another is right, and no javadoc, CHANGES, MIGRATE entry or PR comment accepts that; the test comment covers only the harmless direction and says nothing about live docs or filters; the exact path promises completeness and separate caches give the right answer, so this is cross-reader reuse, not approximation; applying live docs is fine for an uncached Weight, the bug is applying them and also saying true; @lucene.experimental does not permit wrong results. The timeout part is the strongest: no javadoc says setTimeout and the cache must not be combined, and turning the cache off in a test does not accept that later searches reuse a partial result, but a maintainer could prefer documenting it or skipping the cache when a timeout is set (fix B does the latter). The case also misses scoring parents: as a FILTER or MUST_NOT clause the stale set is used too. The GPT-5.6 reviews rated the intended argument weak, and moderate for the timeout part only; the independent reproduction and the intended-behaviour check gave no rating but found none that holds; none could apply it to the live-docs part. File it leading with SegmentCacheable and the core-key contract, not with Weight.java:121-122.

Suggested fix

#

Recommended B: cacheable only without deletions, without a timeout and with a cacheable filter

Let isCacheable say true only when the cached set cannot differ between readers: no deletions in the segment, no searcher timeout, and a cacheable filter (+6/-1). All 5 tests, every earlier check and 139 tests in 11 suites pass, and the safe case is still cached. The one-line return false also passes every bug test but never caches.

@Override
public boolean isCacheable(LeafReaderContext ctx) {
  // The per-segment result is computed with the reader's live docs, the searcher's timeout
  // and the filter. The query cache keys entries on the segment core, which ignores
  // deletions and doc-values updates, so only cache a result that depends on none of them.
  return ctx.reader().getLiveDocs() == null
      && queryTimeout == null
      && (filterWeight == null || filterWeight.isCacheable(ctx));
}
All options and trade-offs4 options · 937 words

The Weight must stop claiming that a set built from per-reader and per-search inputs is shareable. Two options were built and validated in a scratch worktree at ea57360912ed (removed afterwards); the others are untested or partial.

B: cacheable only without deletions, without a timeout and with a cacheable filter (validated by the checks) (recommended)

#

In AbstractVectorSimilarityQuery's Weight, isCacheable(ctx) returns ctx.reader().getLiveDocs() == null && queryTimeout == null && (filterWeight == null || filterWeight.isCacheable(ctx)). A cached set is then always computed with every document live, no timeout and a segment-immutable filter, so it is the same for every reader sharing the core, and each reader applies its own live docs on top as for any other query. A reader with deletions, a searcher with a timeout or a non-cacheable filter neither reads nor writes the entry. +6/-1, one file.

@Override
public boolean isCacheable(LeafReaderContext ctx) {
  // The per-segment result is computed with the reader's live docs, the searcher's timeout
  // and the filter. The query cache keys entries on the segment core, which ignores
  // deletions and doc-values updates, so only cache a result that depends on none of them.
  return ctx.reader().getLiveDocs() == null
      && queryTimeout == null
      && (filterWeight == null || filterWeight.isCacheable(ctx));
}

Trade-offs

  • Segments with deletions never cache this query, and nor does a searcher with a timeout, so NRT indexes with deletes lose part of the caching benefit. No benchmark was run.
  • queryTimeout == null is conservative: a timeout that never fires still skips the cache.
  • Letting readers with deletions also read an entry filled by a reader without them would be exact for decay 1, but isCacheable governs reading and writing alike, so that needs a change beyond this method.
  • Open draft #15802 by the query's author rewrites this Weight (keeping isCacheable); a PR may need to coordinate with it.
  • Assumes readers, filters and query parts that keep Lucene's cacheability and core-key contracts, and immutable query state. Main also accepts a caller-supplied KnnSearchStrategy (FloatVectorSimilarityQuery.java:58-64); its Seeded variant holds a DocIdSetIterator that the graph search consumes (KnnSearchStrategy.java:107-171, SeededHnswGraphSearcher.java:37-52). No test covers such strategies or custom reader wrappers.

A: isCacheable returns false (validated by the checks)

#

Replace return true; with return false; and a comment naming the three inputs. +3/-1. The filter query itself is part of the cache key (equals/hashCode, AbstractVectorSimilarityQuery.java:273, :279); its per-reader matches are not. It was validated first by the finder, the independent reproducer, the devil's advocate, the security probe and the GPT-5.6 reviewers, and endorsed by the adjudication, who did not re-run it.

@Override
public boolean isCacheable(LeafReaderContext ctx) {
  // The result depends on the reader's live docs, the searcher's timeout and the filter's
  // per-reader matches, none of which the cache key (query + segment core) captures.
  return false;
}

Trade-offs

The query is never cached, even where that is safe, so every reuse as a filter or count repeats the vector search per segment (an exact scan for decay 1). It contradicts the author's stated intent that the query be cacheable (#13594).

What the checks validated

  • This doc's test 5 of 5 and the same 139 upstream tests pass, assertions on and off; :lucene:core:check -x test passes; with the reworded comment, google-java-format, ecjLint and forbiddenApis pass again. The caching probe fails, as expected.
  • Re-run on main with the reworded comment, assertions on and off: the finder's 3, the independent reproducer's 9, the security probe's 6, both reviewers' 4 each and the scoring-parent probe's 4 pass. The devil's advocate's 9 give 8: its reverse-direction control first asserts that the query was cached, which this fix rules out (the same expected failure as the caching probe).
  • Earlier: 137 upstream tests with the finder's version, and the history probe on main and 9.12.3.

C: never apply live docs inside the Weight (untested)

#

Build the per-segment set without live docs and let collection apply them, as other queries do; still refuse caching with a timeout or a non-cacheable filter.

Trade-offs

Keeps caching on segments with deletions, but changes the approximate path: the graph search already visits and scores rejected nodes and checks the accepted docs only before collecting one (AbstractHnswGraphSearcher.java:98-104, HnswGraphSearcher.java:328-349), so without live docs deleted documents would also be collected and dropped only later, and the filtered path's accepted count and its exact fallback would count them. Needs recall and latency checks.

Not sufficient: fix only the filter, or only skip caching after a timeout

#

Asking filterWeight.isCacheable(ctx), or refusing to cache after a timeout, fixes one input and leaves the other two.

Trade-offs

The finder's first alternative left out the filter; a verifier and the adjudication caught it.

Downstream note

#

Why: the cache key ignores deletions and doc-values updates, so whichever search fills the entry, even a timed-out one or one on a restricted view, decides what others get. Hidden or deleted documents never leak. A filter on in-place-updated doc values fails open, and one timed-out search can empty a MUST_NOT exclusion for later searches. No exploit known.

How it was found

#

Code reading. An AI tool compared what each vector query's per-segment result depends on with the query-cache key (query plus segment core), saw that this query reads live docs and the timeout while isCacheable returns true, and confirmed it with a JUnit test on the stock jar. A small TLA+ model written afterwards illustrates the mechanism.

The method in full160 words

Method: code reading (the hunt's non-formal tier).

  • A hunt unit (the kNN query layer, 2026-10-25). The finder, an AI tool, compared for each vector query Weight the inputs of its per-segment result with what the LRUQueryCache key contains. AbstractVectorSimilarityQuery's scorerSupplier reads the reader's live docs and the searcher's timeout, while isCacheable returns true.
  • Public-API probes and a deterministic JUnit test on the stock jar then showed both the live-docs and the timeout cases.
  • A small TLA+ model written afterwards (two readers sharing a core, a timeout flag; invariant Correct) is violated with Cacheable = TRUE and holds with Cacheable = FALSE. It illustrates the mechanism; its files are timestamped after the finding, so it was not the first signal.
  • An independent reviewer from another model family (OpenAI GPT-5.6) then tried to refute it; verifiers and an adjudication confirmed it, one of them adding the soft-deletes and doc-values filter triggers; the history, prior-report and security checks followed.

Bug record

LFV-106, snapshot of 2026-10-27

Registry title
Vector similarity queries report isCacheable() == true although their per-segment result depends on live docs, the search timeout and the filter, so a shared query cache serves one reader's or one search's result to another
Area
search / vector similarity queries and the query cache
Priority
High, rank 5: Released 9.10-10.5.2 with the default shared query cache, a vector similarity query used as a filter or count can cache another reader's live-docs view, a timed-out result or a non-cacheable filter and keep serving wrong hits from ordinary point-in-time and timeout patterns, just below LFV-044 because the threshold vector query in a non-scoring context is a niche experimental API.
Impact class
silent wrong results
Impact note
Applications that run a Float/Byte/Float16VectorSimilarityQuery in a non-scoring context (IndexSearcher#count, ConstantScoreQuery, a FILTER clause) through a query cache shared by several readers or searchers, which on 9.10.0-10.5.2 the default IndexSearcher setup already is (a static LRUQueryCache; zero-configuration repro executed) and on main only an application-installed cache is (#14187), and that then search an older point-in-time reader (or another live-docs view of the same segment) after a newer one, or let a timed-out search fill the entry (10.0.0 and later), or pass a filter on in-place-updated doc values; ordinary scale (100 docs with an always-cache policy, 12,000 docs with the default cache settings); released 9.10.0-10.5.2.
Summary
You search with a vector similarity (threshold) query, for example FloatVectorSimilarityQuery, in a non-scoring context such as IndexSearcher#count or ConstantScoreQuery, with a query cache that several readers or searchers share (the IndexSearcher default in 9.10.0-10.5.2). You expect every reader and every search to get the hits it gets without the cache. Instead the cache hands one reader's or one search's per-segment result to another: an older point-in-time reader misses a document that only a newer reader has deleted (99 hits instead of 100), a search without a timeout gets the empty result of an earlier timed-out search (0 instead of 100), and with a filter on an updated doc-values field a newer reader gets a document that no longer matches the filter (100 instead of 99).
