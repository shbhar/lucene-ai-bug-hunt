PackedInts' int[] -> long[] encoder sign-extends the low part of a straddling negative int when that part exceeds 32 bits: -1 at 35 bits decodes as 17179869183

PackedInts' int[] -> long[] encoder sign-extends the low part of a value that straddles two 64-bit blocks; when that part exceeds 32 bits, a negative int decodes too large: at 35 bits, -1 at position 53 decodes as 17179869183, not 4294967295. Only direct callers of this internal API are hit.

The finding in 30 seconds

#

The int[] encoder masks each int with & 0xFFFFFFFFL on three of its four branches. The fourth, for the low part of a straddling value, masks the sign-extended int. When that low part is wider than 32 bits, a negative int keeps extra 1-bits from its sign, inside its own field.

Background in three steps

#
  1. PackedInts stores numbers with a fixed number of bits each (bits per value) back to back in 64-bit long blocks. At 35 bits, 64 values fill exactly 35 blocks.
  2. Values do not line up with blocks: a value can start near the end of one block and finish in the next. The encoder then writes its high part into the first block and its low part into the top of the next.
  3. The encoder also accepts an int[]. An int is read as an unsigned 32-bit number: -1 means 4294967295 (32 one-bits), and the field's bits above bit 31 must stay 0.

The finding, step by step

#
  1. Get the PACKED encoder for 35 bits per value and encode one iteration of 64 ints, all 0 except values[53] = -1, into 35 long blocks. The int[] encoder reads ints as unsigned, so -1 stands for 4294967295.
  2. Value 53 starts at bit 53 x 35 = 1855 = 28 x 64 + 63: 1 bit lands at the end of block 28, the other 34 bits at the top of block 29.
  3. You expect the decoder to return 4294967295 for value 53, as it does for -1 at any position that stays inside one block, and at 33, 34, 36, 40, 48 or 64 bits per value.
  4. Instead the 34-bit low part is cut from the sign-extended int, which has two extra 1-bits: block 29 is 0xffffffffc0000000, not 0x3fffffffc0000000, and value 53 decodes as 17179869183 (2^34 - 1).
  5. No error, with assertions on or off. It happens only at 35, 37-39, 41-47 or 49-63 bits per value, and only at straddling positions whose low part is wider than 32 bits (at 35 bits, 2 of the 34 straddling positions: 42 and 53).

Who is affected

#

Only code that calls PackedInts.getEncoder(...) and then encode(int[], .., long[], ..) itself, at 35, 37-39, 41-47 or 49-63 bits per value, with an int whose top bit is set at a straddling position whose low part is wider than 32 bits. PackedInts is @lucene.internal and every Lucene writer passes a long[], so Lucene's indexing, codecs and search are not affected.

Mechanism, terms and numbers503 words

PackedInts.getEncoder(PACKED, VERSION_CURRENT, bpv) returns an encoder whose encode(int[], .., long[], ..) reads each int as an unsigned 32-bit value (-1 stands for 4294967295): three of its four branches mask the int with & 0xFFFFFFFFL. The fourth, which writes the low part of a value that straddles two 64-bit blocks, masks the sign-extended int instead (BulkOperationPacked.java:209). When that low part is wider than 32 bits, an int with its top bit set picks up extra 1-bits inside its own field and decodes too large.

At 35 bits per value, -1 at position 53 decodes as 17179869183 (2^34 - 1) instead of 4294967295, with assertions on and off. The affected widths are 35, 37-39, 41-47 and 49-63 bits per value. No Lucene production code encodes an int[] with PackedInts (only TestPackedInts does, at 32 bits per value or fewer), so only external code that calls this @lucene.internal API directly is hit. Every release from 4.0.0 (2012) to 10.6.0 has it. The related row LFV-1168 is the sibling int[] -> byte[] encoder of the same class, at its own site.

The mechanism (main 5adff78bb168)

#
  1. The encoder. BulkOperationPacked.encode(int[] values, .., long[] blocks, ..) (BulkOperationPacked.java:192-213) packs values left to right; bitsLeft is the free space left in the current block after the value.
  2. Three branches zero-extend. Value fits (:200), value ends the block exactly (:202), and the high part of a value that crosses into the next block (:207): all use values[i] & 0xFFFFFFFFL.
  3. The fix site, :209. The low part of a crossing value is (values[valuesOffset++] & ((1L << -bitsLeft) - 1)) << (64 + bitsLeft). The int is widened to long with sign extension before the mask, so when the low part has more than 32 bits (-bitsLeft > 32) and the int is negative, bits 32 and up of the sign extension survive the mask.
  4. The example. At 35 bits, value 53 starts at bit 1855 = 28 x 64 + 63: 1 bit in block 28, 34 bits in block 29. The 34-bit low part of 0xFFFFFFFF should be 0x0FFFFFFFF; :209 keeps 0x3FFFFFFFF. Block 29 becomes 0xffffffffc0000000 instead of 0x3fffffffc0000000, and the decoder reads 2^34 - 1.
  5. Which widths. The widest low part is bpv - gcd(bpv, 64) bits, so the bug needs bpv - gcd(bpv, 64) > 32: 35, 37-39, 41-47 and 49-63 bits per value. Even there only straddling values whose own low part is wider than 32 bits are hit: at 35 bits, 2 of the 34 straddling positions in each group of 64 (42 and 53). Non-negative ints have no bits above 31 and are never affected; the extra bits stay inside the value's own field. An executed width probe gives exactly this set and shows Integer.MAX_VALUE never mis-encodes.

Related row: LFV-1168 is the sibling encode(int[] -> byte[]) of the same class (its own method and fix site, BulkOperationPacked.java:243-269), wrong at every width from 33 to 64.

Exposure and likelihood155 words
  • Who: code that calls the public static PackedInts.getEncoder(...) and then encode(int[], .., long[], ..) at one of those widths, with an int whose top bit is set (an unsigned value of 2^31 or more) at a block-straddling position whose low part is wider than 32 bits. PackedInts is @lucene.internal (PackedInts.java:27-32).
  • Not hit: Lucene itself. Every in-tree production encoder user passes a long[]: LegacyDirectWriter.java:65/:102 (backward-codecs), AbstractBlockPackedWriter.java:120/:129, PackedWriter.java:42/:83, Packed64.java:157/:176, Packed64SingleBlock.java:137/:142. The only int[] encodes in the tree are in TestPackedInts (:882, :909), at 32 bits per value or fewer (:880, :907).
  • Effect for a direct caller: one silently wrong value per affected position, with assertions on and off; no exception; neighbouring values and memory are untouched.
  • Since: 4.0.0, the first release that has this API; no public report of it was found since 2012.

Why it looks unintended

#
  • The method reads the int as unsigned (& 0xFFFFFFFFL) on its other three branches; only the low part of a straddling value is cut from the signed int.
  • encode(int[])'s javadoc states no width or sign rule; getEncoder accepts every width.
  • Upstream TestPackedInts reads an int as (int & 0xFFFFFFFFL) and requires encode(int[]) to equal encode(long[]) (checked up to 32 bits).
The full argument272 words
  • The method's own reading. Three of its four branches read the int as unsigned (BulkOperationPacked.java:200, :202, :207), and the sibling int[] -> byte[] encoder asserts PackedInts.bitsRequired(v & 0xFFFFFFFFL) <= bitsPerValue (:250). If int[] input at these widths is supported at all, nothing explains why the same int encodes differently only because it straddles a block; and 2^34 - 1 is neither the unsigned value (2^32 - 1) nor -1 sign-extended to 35 bits (2^35 - 1).
  • The contract. Encoder.encode(int[], .., long[], ..) states no width or sign rule (PackedInts.java:327-337), and the public static getEncoder accepts every width (:657-660).
  • "Each value is >= 0". The class javadoc says so (PackedInts.java:27-29), which could be read to put -1 out of contract. The int[] methods read an int as unsigned instead, and the upstream test relies on it: at 32 bits per value it decodes random blocks into int[] (many ints with the top bit set), compares them as (int & 0xFFFFFFFFL) and re-encodes them, expecting the same blocks (TestPackedInts.java:864-869, :880-884, :916-925). The javadoc does not spell this out for int[] input above 32 bits.
  • The upstream oracle. TestPackedInts treats an int as (int & 0xFFFFFFFFL) (TestPackedInts.java:916-925) and requires encode(int[]) to write the same blocks as encode(long[]) (:879-884), checked only for 32 bits per value or fewer.
  • History. The generated per-width encoders that LUCENE-4322 replaced masked every int fragment with & 0xffffffffL, and the parents of the introducing commits pass the repro. The change was a JAR-size reduction; nothing in it discusses sign handling.
The devil's-advocate check191 words

"int[] input above 32 bits per value is an unsupported internal corner." The paired long[] -> int[] decoder throws above 32 bits (BulkOperationPacked.java:123-126), the tests use int[] only up to 32 bits, no Lucene code calls it, and on #5389 in 2012 Adrien Grand wrote that they "can't think of a use-case" for encoding int[] values when bitsPerValue > 32, and Michael McCandless replied "if we have pointless code (int[] values with bpv > 32) we should remove it". An independent reviewer from another model family (OpenAI GPT-5.6) returned not real on exactly this scope argument, after reproducing the bug and agreeing on the cause and the fix. (A second review from the same model family, with an intended-behaviour lens, returned real, high confidence.)

Our answer (a judgment; the maintainers decide): that bears on reach, not on intent. Nothing documents the limit, getEncoder hands out the encoder for every width, the method itself treats ints as unsigned on its other branches, and the result is silent wrong data rather than a rejection. If the maintainers agree the path is pointless, fix B (reject it) is the natural answer.

Suggested fix

#

Recommended A. Zero-extend the low part at :209

Suggested: zero-extend the int at BulkOperationPacked.java:209, as the other three branches do: ((values[valuesOffset++] & 0xFFFFFFFFL) & ((1L << -bitsLeft) - 1)), plus the file's SHA-1 in the packed checksums file. The repro and all packed tests pass. Rejecting int[] above 32 bits (B) is as defensible; maintainers choose.

        nextBlock =
            ((values[valuesOffset++] & 0xFFFFFFFFL) & ((1L << -bitsLeft) - 1)) << (64 + bitsLeft);
All options and trade-offs2 options · 481 words

Two options, both run with gradle in a scratch worktree of 5adff78bb168. A is the smallest correct fix and leaves LFV-1168's int[] -> byte[] site to its own fix; B closes the whole int[]-above-32-bits path, which the 2012 remarks on #5389 called pointless, and covers both rows. Either way the patch must refresh the SHA-1 of BulkOperationPacked.java in lucene/core/src/generated/checksums/regeneratePacked64SingleBlock.json, because the packed regeneration task tracks BulkOperation*.java and check runs regeneratePacked64SingleBlockChecksumCheck. The generator itself needs no change: gradle/regenerate/packed/gen_BulkOperation.py writes BulkOperation.java and BulkOperationPacked1-24.java only, so BulkOperationPacked.java is checksum-tracked only because the output glob matches it. Given the 2012 remarks, the maintainers may well prefer B (a judgment).

A. Zero-extend the low part at :209 (validated by the checks) (recommended)

#

In encode(int[] -> long[]) (BulkOperationPacked.java:209), mask the int like the other branches; and update the file's SHA-1 in regeneratePacked64SingleBlock.json:

        nextBlock =
            ((values[valuesOffset++] & 0xFFFFFFFFL) & ((1L << -bitsLeft) - 1)) << (64 + bitsLeft);

Trade-offs

  • No change for non-negative ints or widths up to 32 bits; one extra AND per straddling value.
  • Without the checksum update, regeneratePacked64SingleBlockChecksumCheck fails with "Checksums mismatch for generated resources".
  • Leaves LFV-1168's int[] -> byte[] site unfixed.

B. Reject bitsPerValue > 32 in both int[] encode overloads (validated by the checks)

#

At the top of encode(int[], .., long[], ..) and encode(int[], .., byte[], ..), throw as decode(long[] -> int[]) does (:123-126):

    if (bitsPerValue > 32) {
      throw new UnsupportedOperationException(
          "Cannot encode " + bitsPerValue + "-bits values from an int[]");
    }

Trade-offs

  • Closes the path the 2012 remarks called pointless and covers LFV-1168's site too.
  • Turns a silent result into an exception for any external caller at those widths; the regression test becomes an expectThrows test. Needs the same checksum update (by reading).
  • Also rejects int[] -> long[] encodings that are right today: every int at 33, 34, 36, 40, 48 or 64 bits per value, and non-negative ints at any width above 32 (by reading: the guard is on bitsPerValue alone).

What the checks validated

  • Same worktree and seed: the repro now fails by design with UnsupportedOperationException: Cannot encode 35-bits values from an int[]; the 43 upstream tests of org.apache.lucene.util.packed give 40 passes, 3 skips and no failure (TestPackedInts 25 passed and 3 skipped, TestDirectMonotonic 9, TestDirectPacked 6), assertions on only. Lint and the checksum check were not run for B.

Downstream note

#

Only downstream code that calls this internal int[] encoder itself is affected, as one silently wrong value; Lucene's own indexing and search paths never call it.

How it was found

#

Semi-formal: a proof-obligation audit of BulkOperationPacked's contract, where encode(int[] -> long[]) must write the blocks encode(long[] -> long[]) writes for the ints' unsigned values. One branch of the four breaks that for negative ints; a one-test JUnit repro on stock main witnessed it.

The method in full88 words
  • Obligation: for every width and input, encode(int[], .., long[], ..) writes the same blocks as encode(long[], .., long[], ..) given (int & 0xFFFFFFFFL) for each int (the upstream TestPackedInts oracle, :879-884, :916-925).
  • Finding: the branches at BulkOperationPacked.java:200, :202 and :207 discharge it by masking; the low-part branch at :209 masks the sign-extended int, so it fails once the low part exceeds 32 bits.
  • Witness: a JUnit test on stock main, then an independent reproduction, cross-model reviews, an intended-behaviour review and an adjudication (see Independent checks).

LFV-1164, snapshot of 2026-11-08

Registry title
PackedInts' int[] -> long[] encoder sign-extends the low part of a value that crosses a 64-bit block, so at 35, 37-39, 41-47 or 49-63 bits per value an int with its top bit set (for example -1, which the encoder reads as 4294967295 everywhere else) gets extra high bits and decodes too large; latent, no Lucene code encodes int[] this way (since 4.0.0)
Area
util / packed (PackedInts bulk encoders: BulkOperationPacked.encode(int[] -> long[]))
Priority
Low, rank 1216: Latent: the @lucene.internal PackedInts int[] to long[] encoder makes an int with its top bit set decode too large at some widths above 32 bits when the value straddles two blocks, in every release since 4.0.0. No Lucene code encodes int[] this way, and only top-bit values at block-crossing positions at those widths are affected, so it is contrived.
Impact class
minor
Impact note
Latent: no Lucene feature, codec or writer encodes an int[] with a PackedInts encoder (LegacyDirectWriter, AbstractBlockPackedWriter, PackedWriter, Packed64 and Packed64SingleBlock all pass long[]), so only external code that calls the public static but @lucene.internal PackedInts.getEncoder(...).encode(int[], .., long[], ..) at 35, 37-39, 41-47 or 49-63 bits per value with an int whose top bit is set at a position that straddles two blocks is hit: that one value silently decodes too large, with -ea and -da (the extra bits stay inside its own bit field; neighbouring values, array bounds and memory are untouched); every release from 4.0.0 to 10.6.0 and main.
Summary
You get the PACKED encoder for 35 bits per value from PackedInts.getEncoder, encode one iteration of 64 ints that are all 0 except values[53] = -1 into long blocks, and decode the blocks back to long[]. You expect value 53 to come back as 4294967295, because the int[] encoder reads each int as its unsigned 32-bit value (it does so on its other branches, and the upstream TestPackedInts oracle defines an int that way), and that is what you get at any position that does not straddle two blocks and at 33, 34, 36, 40, 48 or 64 bits per value. Instead it comes back as 17179869183 (2^34 - 1): value 53 straddles blocks 28 and 29, and BulkOperationPacked.java:209 masks its 34-bit low part out of the sign-extended int instead of the zero-extended one, so two extra bits are set.
Introduced
ebde32f31f0bc05ca2b6f29ce68bc44de04e7740 'LUCENE-4322: Start reducing the JAR size by only specializing decode for bitsPerValue in [1-24].' (Adrien Grand, GitHub jpountz; svn r1378492 on trunk; merged to branch_4x as 62942bd9d2e, svn r1378497, the commit in the 4.x release tags; JIRA-patch era, no GitHub PR; the issue is migrated as apache/lucene#5389).
