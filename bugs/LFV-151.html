Range facet totals count the hits that the fastMatchQuery skipped

With a fastMatchQuery, range facet counters add the hits it skipped to the dimension total FacetResult.value: three documents, one in the range, give a total of 3 instead of 1 while the range count stays 1. Every release tested since 4.7.0 does this.

The bug in 30 seconds

#

Range facet counters count, for each range, the hits whose value falls in it, and FacetResult.value is the number of hits in at least one range. An optional fastMatchQuery lets them skip hits that cannot be in any range, such as a bounding box around distance rings.

  1. Index three documents with prices 0, 10 and 20 and count one range, [0, 5], with LongRangeFacetCounts. One document is in the range, so the range count and the dimension total FacetResult.value are both 1.
  2. Pass a fastMatchQuery that matches only the document priced 0. That is its documented use: a cheap filter that skips documents that cannot be in any range. You expect the same two numbers.
  3. You get a range count of 1 but a total of 3, with LongRangeFacetCounts, DoubleRangeFacetCounts and both range-on-range counters, default index settings and no error.
  4. Why: each segment first adds all its hits to the total, then subtracts only the checked hits that fall in no range. The two hits the fastMatchQuery skipped are added and never subtracted.
  5. On main, put the documents priced 10 and 20 in their own segment and the total is 1: the fastMatchQuery, a term query, has no scorer there, so that segment is skipped before the add. A small fix (four loops, +6/-8 lines) that counts each checked document gives 1 in both layouts.

Who is affected

#

Anyone who passes a fastMatchQuery to LongRangeFacetCounts or DoubleRangeFacetCounts (single-valued values or fields) or to the range-on-range counters and shows the dimension total, on 4.7.0 to 10.5.2 and main. The total is inflated by the skipped hits; per-range counts, hits and drill-down are right.

Mechanism, terms and numbers748 words

LongRangeFacetCounts, DoubleRangeFacetCounts and Long/DoubleRangeOnRangeFacetCounts accept an optional fastMatchQuery: only hits that match it are checked against the ranges. In the single-valued and range-on-range counting loops each segment first adds its whole hits.totalHits() to the dimension total, then subtracts only the checked hits that have no value or fall in no range, so the hits the fastMatchQuery rejected stay in FacetResult.value. With the values 0, 10 and 20, the range [0, 5] and a fastMatchQuery that matches only the document with 0, the range count is 1 but the total is 3 instead of 1. On main, a segment where the fastMatchQuery has no scorer is skipped before the add, so the same documents in two segments give 1: the total depends on the segment layout. The multi-valued path of the same classes counts each checked document and gives 1. Per-range counts, hits and drill-down are correct. Every release tested from 4.7.0 (LUCENE-5418, 2014) to 10.5.2, and main, is affected (the releases not run have the same code), range-on-range since 9.5.0. Counting each checked document instead of the bulk add fixes it; the whole lucene/facet test suite passes with that change.

Terms

#
  • Range facets: LongRangeFacetCounts and DoubleRangeFacetCounts count, per range, the collected hits whose value (from field doc values or a LongValuesSource / DoubleValuesSource) falls in it; LongRangeOnRangeFacetCounts and DoubleRangeOnRangeFacetCounts do the same for indexed ranges (LongRangeDocValuesField).
  • Dimension total: FacetResult.value, the "Total number of documents containing a value for this path" (FacetResult.java:30-34). For range facets that is the hits in at least one range: upstream testBasicLong collects 101 documents and asserts value=22.
  • fastMatchQuery: optional; "we first test this Query to see whether the document should be checked for matching ranges" (FacetCountsWithFilterQuery.java:41-44). createIterator(hits) intersects the segment's hits with it and returns null when it has no scorer in the segment (:59-90, :75-78).

The bug

#
  1. The single-valued loops skip a segment whose iterator is null, then add the whole segment's hit count: totCount += hits.totalHits(); (RangeFacetCounts.java:140 for field doc values, LongRangeFacetCounts.java:150, DoubleRangeFacetCounts.java:177, RangeOnRangeFacetCounts.java:100).
  2. The loop visits only the documents of the intersected iterator. Checked documents with no value, or in no range (LongRangeCounter.finish(), LongRangeCounter.java:163-167), are subtracted: totCount -= missingCount (RangeFacetCounts.java:190-191, LongRangeFacetCounts.java:165-166, DoubleRangeFacetCounts.java:192-193, RangeOnRangeFacetCounts.java:123).
  3. A hit the fastMatchQuery rejects is never visited, so it is added and never subtracted. The total becomes "documents in some range" plus "rejected hits of segments where the fastMatchQuery has a scorer".
  4. A segment where the fastMatchQuery has no scorer is skipped before the add, so its rejected hits are not counted: the total depends on how documents are spread over segments. A term query has no scorer in a segment that lacks its term; a point range query has none in a segment with no points for the field or whose minimum and maximum values lie outside the range (PointRangeQuery.java:252-275), but a segment whose values straddle the range without a match gets an empty scorer, and its rejected hits are counted. A doc-values range query returns no scorer only when the segment lacks the field or a doc-values skip index rules the range out (SortedNumericDocValuesRangeQuery.java:124-132, :182-186); in the diagram's probe (no skip index) it had a scorer in both segments, so every rejected hit was counted.
  5. The multi-valued loops count each checked document (totCount++, RangeFacetCounts.java:168, :180; LongRangeFacetCounts.java:199, :211; DoubleRangeFacetCounts.java:226, :238) and are right. The field path switches every segment to the multi-valued loop when one hit segment is truly multi-valued (RangeFacetCounts.java:95-106, :126).

Exposure and likelihood272 words
  • Who is exposed. Applications that pass a fastMatchQuery to LongRangeFacetCounts or DoubleRangeFacetCounts (with a LongValuesSource / DoubleValuesSource, or field doc values when no hit segment is truly multi-valued) or to LongRangeOnRangeFacetCounts / DoubleRangeOnRangeFacetCounts, and read FacetResult.value, for example to show "N results within 10 km". Lucene's own DistanceFacetsExample passes a bounding box as the fastMatchQuery (DistanceFacetsExample.java:215-231); on java-user@ (2022) gsmiller described it as extra filtering "to only documents that might match one of the ranges being faceted on", such as a price filter around price ranges.
  • Default vs opt-in. The fastMatchQuery is optional (the constructors without it pass null). RangeFacetCounts, LongRangeFacetCounts, DoubleRangeFacetCounts and FacetCountsWithFilterQuery are @lucene.experimental; the range-on-range counters carry no such tag. Nothing else needs a non-default setting: IndexWriterConfig, codec and searcher can be the defaults (the repro sets NoMergePolicy only to pin the segment layout).
  • Scale. Any index size. The total is too high by the hits the fastMatchQuery rejects in segments where it has a scorer, at most all main-query hits. In 60 random indexes, 2,160 of 4,800 counter checks were overcounted, by up to 1,269.
  • Silent. No exception and no log line, and the per-range counts look right. Nothing is stored wrong, so a fix needs no reindex.
  • Not affected. Per-range counts, childCount, hits, scores and drill-down; the multi-valued paths; MatchingFacetSetsCounts; any counter without a fastMatchQuery over an ordinary FacetsCollector (a sampled collector is a separate case, see the fix). No use of these classes was found on the default branches of three large downstream search engines (9 code searches); that is "no known use", not proof.

Why it is a bug, not intended

#
  • FacetResult.value is the "Total number of documents containing a value for this path"; testBasicLong asserts 22 for 101 hits.
  • The fastMatchQuery is a speed-up: "only documents passing the filter are checked for the matching ranges".
  • The same documents give 3 in one segment and 1 in two, and the multi-valued path of the same class gives 1.
The full argument310 words
  • Contract. FacetResult.java:30-34: "Total number of documents containing a value for this path ... it will only be counted once in this value." FacetCountsWithFilterQuery.java:41-44: "we first test this Query to see whether the document should be checked for matching ranges. If this is null, all documents are checked." LongRangeFacetCounts.java:76-79: "only documents passing the filter are checked for the matching ranges, which is helpful when the provided LongValuesSource is costly per-document, such as a geo distance." LongRangeOnRangeFacetCounts.java:27-31: the class counts "all the documents in the FacetsCollector (or that match a fast match query) that contain ranges that "match" the provided ranges". CHANGES.txt:12787-12792 (LUCENE-5418): a fast-match filter "to avoid computing the value for documents that are out of bounds".
  • Tests. testBasicLong asserts value=22 for 101 collected documents (TestRangeFacetCounts.java:73-107). The randomized tests that pass a fastMatchQuery assert only per-range counts; testCustomDoubleValuesSource asserts value=3 with a fastMatchQuery that wraps MatchAllDocsQuery and rejects nothing (:1671-1700); the demo test's three documents all lie inside the bounding box. No test asserts the total under a fastMatchQuery that rejects hits, and the fix breaks none.
  • History. LUCENE-5371 (2013) made the total subtract the hits in no range. LUCENE-5418 (2014) added the fast-match filter in front of the older bulk add; its 16 comments, and the 80 texts of #11901 (range-on-range, 2022), never mention the total. The field doc-values loop (since 9.0.0) and range-on-range (since 9.5.0) put the add after the null check from the start, so their totals have depended on segment layout since they were added; #12408 (9.11.0 / 10.0.0), a lazy-initialisation change, did the same for the LongValuesSource / DoubleValuesSource loops, which until then counted every rejected hit.
  • Precedent. The 2021 dev@ thread "FacetResult#value semantics?" (mikemccand: "we really should strive to count each hit only once") led to LUCENE-9952, 9953 and 9964, which fixed double counting in other classes.
The devil's-advocate check150 words

The strongest "intended" case: the classic range classes are @lucene.experimental; the totCount field comment says "Total number of hits" (RangeFacetCounts.java:49, RangeOnRangeFacetCounts.java:45) and the code seeds it with hits.totalHits(); the bulk add has stood since 2014; and the range-on-range javadoc calls the fastMatchQuery a way "to quickly discard hits using some heuristic" (LongRangeOnRangeFacetCounts.java:63).

Why it fails: the code already subtracts the checked hits in no range, so the total is not "all hits" in any configuration (the comment is stale since LUCENE-5371, and testBasicLong asserts 22 for 101 hits); no reading gives 3 in one segment and 1 in two for the same documents; the same class gives 1 on its multi-valued path; @lucene.experimental is about API stability, not wrong numbers. Verdict: a defect (adjudication: confirmed, high; the cross-model review rated the intended case weak). It lowers the severity: only the aggregate is wrong.

Suggested fix

#

Recommended Count each checked document

Count each document the loop checks (totCount++) instead of adding the segment's hits.totalHits() up front, in the four single-valued loops, and fix the stale totCount comment. The repro and the whole lucene/facet suite (308 tests) pass with assertions on and off.

// RangeFacetCounts, LongRangeFacetCounts, DoubleRangeFacetCounts, RangeOnRangeFacetCounts
-      totCount += hits.totalHits();
       for (int doc = it.nextDoc(); doc != DocIdSetIterator.NO_MORE_DOCS; ) {
+        totCount++; // count checked documents only: the fastMatchQuery may skip some hits
         ... // unchanged: count the value, or missingCount++
       }
     ...
     totCount -= missingCount; // unchanged
All options and trade-offs4 options · 560 words

Over an ordinary FacetsCollector without a fastMatchQuery every hit is checked, so totals do not change; with one, the total becomes the checked documents in some range, which the multi-valued loops and MatchingFacetSetsCounts already compute. Side effect, executed: RandomSamplingFacetsCollector keeps each segment's unsampled totalHits() but passes only the sampled documents, so a sampled range facet today reports value=950 next to a range count of 50 (1,000 documents, range [0, 499], sample of 100), even without a fastMatchQuery; with the fix it reports 50, consistent with the sampled count. After amortizeFacetCounts, which divides the total by the sampling rate and caps it at the live documents, that is 1,000 today and 500 with the fix (read, not run). No upstream test combines sampling with range facets, but callers may rely on the raw or the amortized value, so a maintainer may want to decide it explicitly or handle sampling in a separate change. The fix conflicts textually with open PR #16439. Only query-time numbers change, so no reindex is needed.

Downstream note

#

Products that build distance or price range facets with a fastMatchQuery inherit the inflated totals until they upgrade; nothing wrong is stored, so the fix needs no reindex.

How it was found

#

An AI finder read the range-on-range counting code while wiring it into a bounded-exhaustive check, saw that the total adds every hit before the fastMatchQuery filters, and confirmed it with a JUnit test. A second unit re-found the same root cause independently with an SMT model of the counting loops.

The method in full207 words

Method: code reading (the hunt's "non-formal" tier), a hunt unit (document and field factories), 2026-10-26.

  • The finder was wiring RangeOnRangeFacetCounts into the unit's bounded-exhaustive differential check of BinaryRangeDocValues / QueryType.matches. That harness passes no fastMatchQuery, so it could not see the bug; the finder noticed the bulk add while reading the counting loop, confirmed it with a probe and a public-API JUnit on the stock jars, and found the same pattern in the classic range counters.
  • About two hours later a hunt unit re-found the same root cause, by its own record independently, with an SMT model (linear integer arithmetic, Z3) of the counting loops: obligation O7c (a fastMatchQuery that excludes hits makes the single-valued total differ from the documents in a range) is satisfiable, so the model has such a case. Three properties hold in the model, because their negations are unsatisfiable: O7a (without a fastMatchQuery the single-valued total equals the documents in a range), O7b (the multi-valued total equals the documents in a range) and O7d (the overcount is exactly the number of excluded hits). A 24-seed randomized differential against a brute-force oracle agreed. That candidate was withdrawn as a duplicate.
  • Then independent AI tools reproduced, reviewed and judged it (see the checks).

History

#

Introduced by LUCENE-5418 (2014, first released in 4.7.0) and copied into range-on-range by #11901 (9.5.0). Release probes fail on every tested release from 4.7.0 to 10.5.2 and main. The overcount has depended on segment layout since 9.0.0 for the field doc-values path, since 9.5.0 for range-on-range and since 9.11.0 for the values-source paths. Not fixed upstream.

Versions tested8 rows

Introduced by LUCENE-5418 "Don't use .advance on costly (e.g. distance range facets) filters" (commit subject "faster drill-down/sideways on costly filters"; mikemccand; an svn patch, JIRA migrated as #6481): trunk 20a280c33cd, branch_4x 5c0bbfb86f5 (2014-02-06), released in 4.7.0. It added the fast-match filter in front of the bulk add from LUCENE-5339 / LUCENE-5371 (2013). The range-on-range counters copied the same accounting in #11901 (mdmarshmallow, cbfed77fd33 / d9fc418914a, 2022-12-30, released in 9.5.0). #12408 (179b45bc23e, main since 10.0.0; backport #13300 26ec4c600d7, 9.11.0) moved the add after the null check in the LongValuesSource / DoubleValuesSource loops (which before 9.0.0 also served the field constructors): until then they counted every rejected hit, and from 9.11.0 only those of segments where the fastMatchQuery has a scorer. The field doc-values loop (since 9.0.0) and range-on-range (since 9.5.0) had the add after the null check from the start. No commit-level builds: the parents of the introducing commits lack the API.

Bug record

LFV-151, snapshot of 2026-10-27

Registry title
Range facet counters add every hit the fastMatchQuery rejects to FacetResult.value, so the dimension total is too high and depends on the segment layout
Area
facet / range and range-on-range facet counts (FacetResult.value with a fastMatchQuery)
Priority
Medium, rank 169: When the documented fastMatchQuery rejects hits, range facet dimension totals are inflated on essentially every query since 4.7, a plausible normal-path error in the facet module, but only the aggregate total is wrong while per-range counts and hits are correct.
Impact class
silent wrong results
Impact note
Users of LongRangeFacetCounts or DoubleRangeFacetCounts on the single-valued paths (a LongValuesSource or DoubleValuesSource, or field doc values when no hit segment is truly multi-valued) or of Long/DoubleRangeOnRangeFacetCounts who pass the optional fastMatchQuery and let it reject some hits (its documented use, for example the bounding box around distance ranges in Lucene's DistanceFacetsExample) get a dimension total FacetResult.value that is too high by the rejected hits of every segment where the fastMatchQuery has a scorer, with the default IndexWriterConfig, codec and searcher at any scale; per-range counts, childCount, hits and drill-down are correct, the classes are @lucene.experimental, and every release since 4.7.0 (range-on-range since 9.5.0) is affected.
Summary
You build a range facet counter (LongRangeFacetCounts or DoubleRangeFacetCounts on a single-valued field or values source, or a range-on-range counter) with a fastMatchQuery that removes only hits outside every range, which is what it is for, and read FacetResult.value. You expect the same dimension total as without the fastMatchQuery: the number of hits that fall into at least one range. Instead each segment adds all of its hits up front but subtracts only the documents the fastMatchQuery let through, so the hits it rejected stay in the total (3 instead of 1 in the minimal repro, while the range count is 1), and the same documents and query give 3 in one segment and 1 in two.
Introduced
20a280c33cd9 (trunk, 'LUCENE-5418: faster drill-down/sideways on costly filters', by mikemccand; same-day branch_4x commit 5c0bbfb86f5e, the one released in 4.7.0; JIRA LUCENE-5418, migrated as apache/lucene#6481, svn patch without a GitHub PR): it added the optional fast-match filter to LongRangeFacetCounts and DoubleRangeFacetCounts and kept the older per-segment 'totCount += hits.totalHits' (LUCENE-5339/5371, 2013), so rejected documents are added and never subtracted [read: git log -L / -S and git show in the history clone; exec: release level only, 4.6.1 has no such API, 4.7.0 fails, the per-checked-document fix shadowed over the 4.7.0 jars passes; no commit-level build]; the range-on-range copy came with cbfed77fd33c (apache/lucene#11901 'Github#11869: Add RangeOnRangeFacetCounts', by mdmarshmallow, merged 2022-12-30; branch_9x d9fc418914ae, released in 9.5.0) (2014-02-06 (LUCENE-5418, classic range facets); 2022-12-30 (#11901, range-on-range facets))
