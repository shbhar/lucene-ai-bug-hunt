FuzzyQuery on a term whose bytes are not valid UTF-8 fuzzes the hex string "[ff 61 62 63]" and misses the term itself

A FuzzyQuery on a binary term, such as the id bytes ff 61 62 63, builds its automaton from the hex display string "[ff 61 62 63]", so with maxEdits 1 or 2 it misses the identical term that maxEdits = 0 finds. Silent, in every release since 4.0.0.

The finding in 30 seconds

#

FuzzyQuery with maxEdits 1 or 2 takes its pattern from Term.text(), which for bytes that are not UTF-8 is a printable hex string, not the term.

  1. You index one document whose id is the 4 raw bytes ff 61 62 63, with new StringField("id", bytes, Store.NO): a supported binary keyword value, such as a raw id or hash.
  2. You search new FuzzyQuery(new Term("id", bytes), 1) and expect 1 hit: the identical term is 0 edits away, and FuzzyQuery(term, 0) and TermQuery both count 1.
  3. FuzzyTermsEnum builds its automaton from Term.text(). The byte 0xff never occurs in UTF-8, so text() falls back to the hex display string "[ff 61 62 63]", 13 characters.
  4. You get 0 hits, with no error, assertions on or off. The automaton matches terms within 1 edit of that 13-character text instead: a document holding the text [ff 61 62 63] is found.

Who is affected

#

Applications that run fuzzy queries over binary keyword values (raw ids, hashes) with new Term(field, BytesRef) or the public FuzzyTermsEnum, on default settings. One niche parser path: classic QueryParser over a CollationKeyAnalyzer field, where 東京都~1 returns nothing. Patterns built from a String are never affected. Rare: no report found since 2012.

Mechanism, terms and numbers415 words

FuzzyQuery (with maxEdits 1 or 2) and the public FuzzyTermsEnum build their Levenshtein automaton from Term.text() (FuzzyTermsEnum.java:101 and :132 at 5adff78bb168). For a term whose bytes are not valid UTF-8, which new Term(field, BytesRef) accepts and StringField(String, BytesRef, Store) indexes, Term.text() does not return the term: it falls back to BytesRef.toString(), a human-readable hex rendering such as "[ff 61 62 63]" (13 characters for 4 bytes). The automaton accepts strings within maxEdits of that rendering and can never accept the raw bytes. With one document holding the bytes ff 61 62 63, new FuzzyQuery(new Term("id", bytes), 1) counts 0 hits while FuzzyQuery(term, 0) and TermQuery count 1; documents holding the text [ff 61 62 63] are matched instead. No exception, with assertions on and off. Every release since 4.0.0 has it.

The mechanism (main 5adff78bb168, under lucene/core/src/java/org/apache/lucene/)

#
  1. Two paths. FuzzyQuery.getTermsEnum (search/FuzzyQuery.java:204-209) uses new SingleTermsEnum(terms.iterator(), term.bytes()) for maxEdits == 0 (:205-206), the bytes, which is correct; otherwise it creates a FuzzyTermsEnum (:208).
  2. The pattern is the text. Both FuzzyTermsEnum constructors, the public one (search/FuzzyTermsEnum.java:101) and the one FuzzyQuery uses (:132), supply new FuzzyAutomatonBuilder(term.text(), maxEdits, prefixLength, transpositions), the fix site. FuzzyQuery.getAutomata() (FuzzyQuery.java:172), used by visit() (:197-201), does the same.
  3. The text of a binary term is its display string. Term.text() is toString(bytes) (index/Term.java:100-102): a strict UTF-8 decode that, on failure, returns BytesRef.toString() (:108-122), documented as "human-readable form of the term text. If the term is not unicode, the raw bytes will be printed instead." (:104-107). BytesRef.toString() is [ + hex bytes separated by spaces + ] (util/BytesRef.java:143-157).
  4. The raw term is unreachable. FuzzyAutomatonBuilder takes the code points of [ff 61 62 63] (search/FuzzyAutomatonBuilder.java:50) and builds a Unicode automaton compiled to UTF-8 bytes; it can never accept a 0xff byte. The independent reproducer's diagnostic on main: "automaton accepts raw bytes: false", "automaton accepts display string: true".

So the results of a FuzzyQuery search are not monotone in maxEdits: 0 finds the term, 1 and 2 do not. Only that search path special-cases 0: the public FuzzyTermsEnum with maxEdits 0, and getAutomata() / visit() of a FuzzyQuery with maxEdits 0, also work on the display string (executed; see "Suggested fixes", fix A, "Open decision"). Before 4.3.0, text() was a lenient decode, so the pattern was garbled instead (no hit; with assertions on, an AssertionError in UnicodeUtil).

Exposure and likelihood153 words
  • Who. Code that builds a fuzzy pattern from raw bytes that are not UTF-8: new FuzzyQuery(new Term(field, bytes), maxEdits) or new FuzzyTermsEnum(terms, term, ...) over a field of binary keyword values (raw ids, hashes, other byte keys). Term(String, String) always encodes well-formed UTF-8, so text patterns are never affected.
  • One parser path. The classic QueryParser builds the fuzzy Term from Analyzer.normalize() bytes (QueryParserBase.java:729-730). With the stock CollationKeyAnalyzer, the key bytes of the text 東京都 start with 0x80; 東京都~1 returns no hit while the plain term query matches (the devil's-advocate verifier's probe). Niche.
  • Effect. Silently missing results (the exact match is dropped) and, when the index holds such text, extra hits near the hex string. No exception, no log.
  • Default vs opt-in. Under the default settings the repro uses, a non-UTF-8 pattern is enough to trigger it.
  • Scale. Deterministic: every recorded run without the fix failed; one document is enough.

Why it looks unintended

#
  • The constructor promises terms "with an edit distance of at most maxEdits to term"; the identical bytes are a 0-edit match, which maxEdits = 0 finds.
  • No checked javadoc, test or history states a UTF-8 precondition, yet Term(String, BytesRef) and StringField(String, BytesRef, Store) accept any bytes.
  • The hex fallback of Term.text() is a documented "human-readable form" for printing (4.3.0).
The full argument194 words
  • Contract. "Create a new FuzzyQuery that will match terms with an edit distance of at most maxEdits to term" (FuzzyQuery.java:70-72). If a binary Term is within the pattern domain this API accepts, the identical bytes are a 0-edit match, and maxEdits = 0 does match them.
  • No UTF-8 precondition in the checked docs. No javadoc or test says the pattern must be UTF-8, and no CHANGES entry says what happens otherwise. The closest entry, LUCENE-2265 (lucene/CHANGES.txt:15525-15528, 4.0.0-ALPHA), says "FuzzyQuery and WildcardQuery now operate on Unicode codepoints, not unicode code units"; it predates byte-based terms (its commit 5b74a4ec611 is from 2010-05-03, two months before LUCENE-2514) and states no rule for non-UTF-8 patterns. Term(String, BytesRef) (Term.java:52) and StringField(String, BytesRef, Store) (StringField.java:79) accept any bytes, and TestBinaryTerms indexes and searches binary terms.
  • A display aid. The hex fallback came with LUCENE-4934 (#5998, 4.3.0) so that toString() works on binary terms; the same commit added TestBinaryTerms.testToString ("foo:[ff fe]"). Neither the commit nor its issue discusses fuzzy matching.
  • Inconsistent paths. The maxEdits = 0 path uses term.bytes(), the others term.text().
  • Tests. TestFuzzyQuery uses text patterns only.
The devil's-advocate check155 words

The strongest case for "not a bug": fuzzy edit distance is defined over Unicode code points (LUCENE-2265, #3341, where Robert Muir wrote "fuzzy, regex, wildcard, all of our users are defined on unicode characters ... bytes is an implementation detail"; its CHANGES entry, lucene/CHANGES.txt:15525, says FuzzyQuery and WildcardQuery "now operate on Unicode codepoints"), so a binary pattern is outside the query's domain; WildcardQuery and RegexpQuery also read Term.text().

Why it fails: that justifies rejecting or documenting such patterns, not silently fuzzing a display string and dropping the 0-edit match, and nothing tells the caller. The verifiers rated the argument moderate and rejected it; it is also why the recommended fix rejects, and a maintainer may still prefer the documentation-only fix. The WildcardQuery and RegexpQuery siblings share the assumption (a WildcardQuery without wildcards behaves the same way in the devil's-advocate verifier's probe, executed; RegexpQuery was only read, not run), but are not claimed here.

Suggested fix

#

Recommended Reject non-UTF-8 fuzzy patterns when maxEdits > 0 (fix A)

Reject a non-UTF-8 pattern when maxEdits > 0: IllegalArgumentException from the FuzzyQuery and public FuzzyTermsEnum constructors (+33/-1, two files). The repro passes with assertions on and off; 203 tests of 11 classes run with 0 failures. Still open: the maxEdits = 0 paths of the public FuzzyTermsEnum, getAutomata() and visit() keep the display string.

  /** The edit distance is defined over the pattern's code points (FuzzyAutomatonBuilder). */
  static Term checkUtf8Pattern(Term term, int maxEdits) {
    if (maxEdits > 0 && isUtf8(term.bytes()) == false) {
      throw new IllegalArgumentException(
          "fuzzy matching with maxEdits > 0 needs a term whose bytes are valid UTF-8; got " + term);
    }
    return term;
  }

Reject non-UTF-8 fuzzy patterns when maxEdits > 0 (fix A) (validated by the checks) (recommended)

#

A package-private FuzzyQuery.checkUtf8Pattern(term, maxEdits) runs the same strict UTF-8 check Term.toString(BytesRef) uses and throws when it fails. The FuzzyQuery constructor calls it after its other argument checks; the public FuzzyTermsEnum constructor passes its term through it.

  /** The edit distance is defined over the pattern's code points (FuzzyAutomatonBuilder). */
  static Term checkUtf8Pattern(Term term, int maxEdits) {
    if (maxEdits > 0 && isUtf8(term.bytes()) == false) {
      throw new IllegalArgumentException(
          "fuzzy matching with maxEdits > 0 needs a term whose bytes are valid UTF-8; got " + term);
    }
    return term;
  }

Trade-offs

A behaviour change: code that builds such queries today gets an exception instead of silent wrong results. That includes the classic QueryParser over a CollationKeyAnalyzer field, where 東京都~1 would throw instead of returning nothing (not run), and the three main-source callers of the public FuzzyTermsEnum constructor: DirectSpellChecker (DirectSpellChecker.java:425, suggest), the sandbox FuzzyLikeThisQuery (FuzzyLikeThisQuery.java:217) and the classification module's NearestFuzzyQuery (NearestFuzzyQuery.java:153); the suites of the first two ran with the fix, the classification tests did not. The first sketch guarded only FuzzyQuery; the cross-model refute review found the public constructor unguarded, so both are guarded.

Open decision: the other maxEdits = 0 paths (left as they are by fix A). The guard fires only for maxEdits > 0, but maxEdits = 0 is special-cased only in FuzzyQuery.getTermsEnum. The public FuzzyTermsEnum constructor (FuzzyTermsEnum.java:94-102) and FuzzyQuery.getAutomata() (:172, used by visit(), :197-201) build the automaton from term.text() for maxEdits = 0 too. Executed on main and with fix A shadowed (same output): FuzzyQuery(term, 0) counts 1, but new FuzzyTermsEnum(terms, term, 0, 0, false) enumerates only the text term [ff 61 62 63] (bytes 5b 66 66 20 ...), and the automata from getAutomata() and visit() accept that text and reject the raw bytes. A complete fix needs a choice: reject non-UTF-8 terms in the public FuzzyTermsEnum constructor for every maxEdits (it always builds an automaton), and for getAutomata() / visit() either reject them in FuzzyQuery for every maxEdits or build the 0-edit automaton from the bytes. Not built or run.

Document the limit only (not built)

#

A javadoc note on FuzzyQuery and FuzzyTermsEnum that the pattern must be UTF-8 text.

Trade-offs

Smallest change and no behaviour change, but callers who miss the note still get 0 hits silently. Given the Unicode-only design (#3341), a maintainer may well choose this.

Fuzzy-match non-UTF-8 patterns over bytes (not built)

#

Build a byte-alphabet Levenshtein automaton when the pattern is not UTF-8.

Trade-offs

Real fuzzy matches on binary terms, but distances would mean bytes for some patterns and code points for others; a larger design change that the Unicode-only design (#3341) argues against.

Downstream note

#

Downstream, a service that offers fuzzy search on binary keyword fields silently returns no match for the exact value; the documents it wrongly matches are ones an ordinary query on the same field reaches anyway.

How it was found

#

A proof-obligation audit of FuzzyTermsEnum's contract: the enumerated terms must be those within maxEdits of the pattern term's bytes, for every legal Term. The pattern is built from Term.text(), which is not the term for non-UTF-8 bytes; a one-document public-API JUnit test then witnessed the missed match.

The method in full109 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The finder read FuzzyTermsEnum and FuzzyQuery against their obligation (terms within maxEdits of the pattern term) and the inputs Term accepts (any bytes). The automaton is built from term.text(), and Term.text() is the term only for valid UTF-8; for other bytes it is the hex display string.
  • The finder then wrote a public-API JUnit test that fails on main with assertions on and off and on 10.6.0, 9.12.3 and 8.11.4.
  • An independent reproducer, two executed cross-model reviews, a devil's-advocate verifier and an adjudication reproduced it with their own tests ("Prior reports, history and checks").

History

#
