The finding in 30 seconds

#

Every commit first writes pending_segments_N and later renames it to segments_N. If writing fails, a clean-up closes the output and deletes the file. Since #14913 the close step throws again when the failure is an Error, so the delete after it is skipped.

Background: the one block, before and after #14913

#
  1. SegmentInfos.write(Directory) is the first half of every commit: it creates, writes, closes and syncs pending_segments_N. The second half renames the file to segments_N. Readers only open segments_N.
  2. 10.6.0 (SegmentInfos.java:617-634 at the release tag): try { create; write; close; sync; success = true; } finally { if (!success) { closeWhileHandlingException(out); deleteFilesIgnoringExceptions(dir, name); } }. Neither helper is handed the failure, so after an Error in the try both run and the file is deleted.
  3. branch_11x daa54f2e0cd3 (SegmentInfos.java:616-629; main 781025d6fe32 has the same file): try { create; write; close; sync; } catch (Throwable t) { closeWhileSuppressingExceptions(t, out); deleteFilesSuppressingExceptions(t, dir, name); throw t; }. The first helper ends by throwing t when t is an Error, so control leaves the block before the delete.

The finding, step by step

#
  1. A commit starts by writing a new file, pending_segments_N: create, write, close, sync. Once the file exists and before its sync returns, the JVM throws a java.lang.Error. In the test, a new SegmentInfos is committed to an empty heap directory whose sync throws OutOfMemoryError.
  2. You expect the failed commit to remove its half-made file. On the 10.6.0 release jars it does: the directory lists 0 files, and the test passes 1 of 1 with assertions on and off.
  3. On branch_11x daa54f2e0cd3 and on main 781025d6fe32 the directory still lists 1 file, pending_segments_1. The test fails 1 of 1 with assertions on and off.
  4. Why: since #14913 the clean-up is catch (Throwable t) { close helper; delete; throw t; }, and the close helper throws t itself when t is an Error. The delete on the next line never runs. An IOException at the same place is still cleaned up.
  5. What follows, on a real index with segments_2: readers ignore the leftover pending_segments_3, and the next IndexWriter deletes it. Before that, a commit made without an IndexWriter from a freshly read SegmentInfos throws FileAlreadyExistsException: .../pending_segments_3 once, removes the leftover, and works when repeated.

Who is affected

#

Nobody on a release. On main and branch_11x: an application that gets a java.lang.Error (in practice an OutOfMemoryError) while the commit file is written (once the file exists), and then runs CheckIndex -exorcise or IndexSplitter -d before any IndexWriter opens the directory. That run fails once, loudly; the next one works. No committed data is touched. Rare.

Mechanism, terms and numbers1,214 words

In no release. The defect is on main and branch_11x, both unreleased. The newest release, 10.6.0, does not have it, and 11.0.0 would be the first release with it: the one test fails 1 of 1 on branch_11x daa54f2e0cd3 (11.0.0-SNAPSHOT) and on main 781025d6fe32 (12.0.0-SNAPSHOT), with assertions on and off, and passes 1 of 1 on the 10.6.0 release jars, with assertions on and off. It was introduced by the merged #14913 (commit 27d1272984f, 2025-07-14).

Every commit first writes a file pending_segments_N and later renames it to segments_N. When writing that file fails, SegmentInfos.write(Directory) closes the output and deletes the half-made file. #14913, "Remove a few more boolean success flags", turned the finally block that did this into catch (Throwable t) with the close helper, the delete and throw t in that order (SegmentInfos.java:622-628). The close helper, IOUtils.closeWhileSuppressingExceptions(t, ...), throws t itself when t is an Error (IOUtils.java:116, :134-136), so for an Error the delete is never reached. For an IOException or a RuntimeException it still runs, unless the close inside the clean-up itself throws an Error; that case leaves the file on 10.6.0 as well.

Reach, all conditions. (1) A java.lang.Error, in practice an OutOfMemoryError, thrown after pending_segments_N exists and before its sync returns: inside the create once the file is made, the write, the close or the sync, in SegmentInfos.commit or inside IndexWriter.commit. An Error from a create that made no file leaves nothing. (2) Then a commit made without an IndexWriter from a freshly read SegmentInfos (a new object or a new process, as in CheckIndex.exorciseIndex, the -exorcise option, and IndexSplitter.remove, the -d option), before any IndexWriter has opened the directory. That one commit fails with FileAlreadyExistsException, removes the leftover while failing, and the attempt after it works. Without (2) no failure was found: readers ignore the file, the next IndexWriter deletes it, and a second commit on the same SegmentInfos object takes the next generation and works.

Limits. No corruption, no lost commit, no writer that cannot recover. Every run injects the Error from a test directory; there is no witness without an injected Error. The exception itself is not new: a stale pending_segments_N that is already in the directory gives the same single FileAlreadyExistsException on 10.6.0 (the runs put such a file there by hand; by the code, a JVM that dies in the middle of a commit leaves one on any release). New on main and branch_11x is one more way to leave such a file. Low priority.

The helper

#

IOUtils.closeWhileSuppressingExceptions(Throwable ex, ...) (IOUtils.java:114-137) starts with Error firstError = ex instanceof Error err ? err : null; (:116), closes everything, and ends with if (firstError != null) { throw firstError; } (:134-136). Handed an Error, it throws that Error. Its javadoc (:108-113) does not say so. deleteFilesSuppressingExceptions (:247-268) has the same shape: handed an Error, it deletes every file and then throws the Error (:249, :265-267). So the block is written to delete for an Error as well; the order of its two statements prevents it.

Suggested fix

#

Recommended Run the delete in a finally block around the close helper (validated)

Inside the catch block, put the close helper in a try and the delete in its finally: three added lines. When the failure is an Error, the caller still gets that same Error. Run the delete in a finally block around the close helper (validated) (recommended)

#

In the catch block of SegmentInfos.write(Directory), the close helper goes into a try and the delete into its finally. Three lines are added (try {, } finally {, }), the two calls move in, and one comment gets a clause: 8 lines added, 5 removed, one file.

When the first failure is an Error, both helpers end by throwing that same object, so the caller sees the same exception as today (executed: the Error that comes out is the injected object, with no suppressed exception, with and without the fix). It is the form that IndexWriter.getReader already has around the same helper (IndexWriter.java:717-722), and that Lucene104ScalarQuantizedVectorsReader.java:654-661 has for the same pair of a close helper and a delete.

} catch (Throwable t) {

    // the index (also when t is an Error, which the helper above rethrows):

  throw t;
}
