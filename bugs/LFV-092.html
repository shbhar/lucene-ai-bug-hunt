The finding in 30 seconds

#

Background: float16 vectors and constant-vector function queries

#
  1. A float16 (half-precision) value is stored in a short. It has 5 exponent bits; when all 5 are set the value is +Infinity, -Infinity or NaN. The largest finite half is 65504.
  2. Lucene's float16 kNN field and queries reject a vector with such a component (VectorUtil.checkFiniteFloat16), as the float32 field and query have since 9.7.0 (VectorUtil.checkFinite).
  3. For exact scoring with a function query, ConstKnnFloat16ValueSource supplies the query vector for every document and Float16KnnVectorFieldSource each document's own vector; Float16VectorSimilarityFunction compares the two inside a FunctionQuery. ConstKnnFloatValueSource is the float32 twin.

The finding, step by step

#
  1. Turn a float32 query into float16 with Float.floatToFloat16. The largest finite half is 65504, so a component of 65520 becomes +Infinity (0x7C00), and NaN stays NaN (0x7E00). Pass it to new ConstKnnFloat16ValueSource(q) to score KnnFloat16VectorField documents with a FunctionQuery over Float16VectorSimilarityFunction.
  2. You expect IllegalArgumentException right there: new ConstKnnFloatValueSource(new float[] {Float.NaN}) throws it, and so do KnnFloat16VectorQuery and KnnFloat16VectorField for the same float16 vector.
  3. Instead the constructor returns normally, with assertions on and off. It only null-checks the array; the float32 twin wraps the same argument in VectorUtil.checkFinite.
  4. The bad value surfaces while scoring. Documents [1, 2, 3], [-1, 2, 3], [0, 2, 3], query [+Inf, 1, 2]: with assertions on, EUCLIDEAN and DOT_PRODUCT end in an AssertionError inside VectorUtil that does not point at the constructor argument (no message for EUCLIDEAN; not finite: ... from <raw shorts> for DOT_PRODUCT; COSINE scores all three 0); with assertions off, EUCLIDEAN scores all three 0 and DOT_PRODUCT gives doc 0 a score of +Infinity (default boost 1).

Who is affected

#

Only applications on unreleased main (and branch_11x) that build ConstKnnFloat16ValueSource themselves; no Lucene code or query parser does, and its author called it a benchmark helper. A NaN or infinite component, such as a float32 value of 65520 or more cast to float16, then gives a late AssertionError or silent 0 or +Infinity scores. No index damage.

Mechanism, terms and numbers636 words

ConstKnnFloat16ValueSource (lucene/queries, added with float16 vectors in #16383) returns the same float16 query vector for every document; with Float16KnnVectorFieldSource and Float16VectorSimilarityFunction inside a FunctionQuery it scores documents by exact similarity to that vector. Its constructor only null-checks the short[] (ConstKnnFloat16ValueSource.java:31-33), while its float32 twin ConstKnnFloatValueSource wraps the argument in VectorUtil.checkFinite (ConstKnnFloatValueSource.java:33) and the float16 kNN query, similarity query and field call VectorUtil.checkFiniteFloat16. So a NaN or infinite half is accepted, with assertions on and off, and reaches VectorUtil at scoring time: with -ea, EUCLIDEAN, DOT_PRODUCT and MAXIMUM_INNER_PRODUCT fail an internal assert Float.isFinite(...) and COSINE silently scores 0; with -da, documents score 0 through FunctionQuery's intended NaN/negative clamp, or +Infinity under DOT_PRODUCT and MAXIMUM_INNER_PRODUCT with an infinite component (at the default boost of 1). Float.floatToFloat16 maps any float32 of magnitude 65520 or more to infinity, so one large component is enough. It is a missing fail-fast check and a parity gap with the twin, fixed by one line, on unreleased main only (also on branch_11x); no index damage, the match set is unchanged, and no Lucene code builds the class.

Terms

#
  • ConstKnnFloat16ValueSource (org.apache.lucene.queries.function.valuesource): "Function that returns a constant float16 vector value for every document." (ConstKnnFloat16ValueSource.java:27). Its float16VectorVal(doc) returns the stored array for every document (:40-42).
  • ConstKnnFloatValueSource: the float32 twin, in the same package since #12253 (9.7.0).
  • VectorUtil.checkFiniteFloat16 (VectorUtil.java:494-513): throws IllegalArgumentException when a half has all five exponent bits set, (v[i] & 0x7C00) == 0x7C00 (:507); "@throws IllegalArgumentException if any component of the vector is not finite" (:503).

The bug

#
  1. The constructor is this.vector = Objects.requireNonNull(constVector, "constVector"); (ConstKnnFloat16ValueSource.java:31-33). Nothing checks the components.
  2. The float32 twin is this.vector = VectorUtil.checkFinite(Objects.requireNonNull(constVector, "constVector")); (ConstKnnFloatValueSource.java:32-34). The two files differ only in that line, the VectorUtil import, the element type and the names.
  3. checkFiniteFloat16 is called by KnnFloat16VectorQuery (:97), Float16VectorSimilarityQuery (:132) and KnnFloat16VectorField (:72, :97), not here.
  4. At search time FunctionQuery.AllScorer visits every document (DocIdSetIterator.all, FunctionQuery.java:115); Float16VectorSimilarityFunction.func returns similarityFunction.compare(v1, v2) with the document's vector and the constant (Float16VectorSimilarityFunction.java:46).
  5. With -ea, VectorUtil.squareDistance(short[], short[]) (EUCLIDEAN) and dotProduct(short[], short[]) (DOT_PRODUCT, MAXIMUM_INNER_PRODUCT) assert a finite result (VectorUtil.java:149, :84-91) and throw an AssertionError: with no message from squareDistance, with not finite: <result> from <a>,<b> (the raw shorts) from dotProduct; neither names the constructor argument. cosine(short[], short[]) has no such assert (:117-123).
  6. With -da, FunctionQuery's score maps NaN and negative values to 0 (if (val >= 0 == false) ... return 0;, FunctionQuery.java:132-133), which is intended; a positive infinity passes the clamp and the score is boost * val (:135), so at the default boost of 1 it stays +Infinity.

Exposure and likelihood345 words
  • Who is hit. Code on main that constructs ConstKnnFloat16ValueSource from a query vector with a NaN or infinite half. No Lucene code builds the class (it appears only in its own file) and no query parser does. In the #16383 review its author said it serves the benchmark's exact-scoring path and is "not needed in production path".
  • How a bad vector arises. Float.floatToFloat16 turns any float32 of magnitude 65520 or more into an infinity and keeps NaN, so a float32 query with one large component, or a NaN from an upstream normalization, is enough.
  • What happens. The constructor accepts it and the failure moves to scoring: with -ea (Lucene's gradle test runs enable it for about 75% of seeds by default) an AssertionError from inside VectorUtil that does not point at the constructor argument (no message for EUCLIDEAN; not finite: ... from <raw shorts> for DOT_PRODUCT and MAXIMUM_INNER_PRODUCT); with -da (production) silent 0 scores, or +Infinity for one document under DOT_PRODUCT or MAXIMUM_INNER_PRODUCT. The same vector gets a clear IllegalArgumentException from KnnFloat16VectorQuery.
  • What does not happen. No hang and no extra work (the per-document work is the same as for a finite vector), no change to which documents match (FunctionQuery matches every document), no index effect (the class is query-side only and KnnFloat16VectorField rejects non-finite halves at index time).
  • Default vs opt-in, scale. Default codec and searcher suffice, but the API is opt-in and rare: float16 vectors, the @lucene.experimental FunctionQuery and a non-finite query vector. Any index size; the repro needs no index at all. Likelihood: rare.
  • The same through FunctionScoreQuery. The value source can also be scored with FunctionScoreQuery through ValueSource.asDoubleValuesSource(), an adapter from 2017 (LUCENE-7610); #15329 (for #15328) made the vector-similarity value source implement doubleVal, "allowing its use in FunctionScoreQuery". FunctionScoreQuery has its own equivalent clamp: a missing, negative or NaN value scores 0 (FunctionScoreQuery.java:246-251). Executed with MatchAllDocsQuery as the inner query, the same three documents and the halves 0x7C00, 0xFC00, 0x7E00: the outcomes match the table above, with -ea and -da.

Why it looks unintended

#
  • The float32 twin has rejected non-finite vectors since 9.7.0; a reviewer asked for that check "so no bad thing happen".
  • CHANGES 9.7.0: "Require indexed KNN float vectors and query vectors to be finite." The float16 query and field enforce it.
  • #16383 added the class "to be consistent with" the float32 one; nothing records a deliberate exception.
The full argument238 words
  • The twin's check was requested in review. In #12253 uschindler wrote that ConstKnnFloatVectorValueSource "should call VectorUtil.checkFinite(vector) in its constructor to make sure the float array is finite (like the Lucene KNNQuery and Field types), so no bad thing happen", and suggested exactly today's line.
  • The rule for the kNN APIs. CHANGES.txt (9.7.0): "GITHUB#12281: Require indexed KNN float vectors and query vectors to be finite." It set this for Lucene's kNN field and query APIs; it is not stated as a contract for every value source.
  • The PR that added the class applied the rule to its siblings. In the #16383 review danmuzi wrote on KnnFloat16VectorQuery: "The float32 implementation validates the target vector", and that a NaN from compare() "is only caught when assertions are enabled", proposing checkFiniteFloat16; they asked for the same on KnnFloat16VectorField; both landed. On this class the author said it is "just there to be consistent with other classes ConstKnnFloatValueSource and ConstKnnByteValueSource", and msokolov replied "we may as well follow the existing pattern". Nobody discussed validation for this class.
  • No sign of intent. No test covers the class or any float16 function-query class; no comment, CHANGES entry or javadoc allows non-finite input here.
  • A similar parity fix. #16708 (backport #16732) closed a similar validation-parity gap: columnar addBatch skipped the Knn*VectorField checks. CHANGES.txt lists it under Improvements (10.6.0), so it is precedent for this kind of hardening, not for calling it a bug.
The devil's-advocate check172 words

The strongest case for "not a bug" (the intended-behaviour devil's advocate and the cross-model "intended" review): no javadoc promises the exception (neither constructor has javadoc, and VectorSimilarityFunction.compare(short[], short[]) states no finiteness precondition); FunctionQuery is @lucene.experimental and clamps NaN to 0 on purpose; the class is a benchmark helper; and Lucene does not validate query vectors everywhere: DoubleValuesSource.similarityToQueryVector(..., short[], ...), FullPrecisionFloat16VectorSimilarityValuesSource and RescoreTopNQuery.createFullPrecisionRescorerQuery(short[]) accept a NaN query vector too (executed).

Why it fails: those three paths' float32 twins do not validate either, so they match their twins; of the four float32 classes that call VectorUtil.checkFinite (KnnFloatVectorField, KnnFloatVectorQuery, FloatVectorSimilarityQuery, ConstKnnFloatValueSource), only ConstKnnFloatValueSource has a float16 counterpart that does not validate. The twin's check was asked for in review, the class was added "to be consistent" with the twin, the same PR added checkFiniteFloat16 for exactly this input, and #12281 set the finite-vector rule for the kNN field and query APIs. Residual: a maintainer may call it hardening rather than a bug; not every other float16 entry point validates.

Suggested fix

#

Recommended A. Validate in the constructor with checkFiniteFloat16, as the twin does

Wrap the argument in VectorUtil.checkFiniteFloat16, exactly as the float32 twin uses VectorUtil.checkFinite: one line plus the import. With it the repro passes with assertions on and off, all 112 org.apache.lucene.queries.function tests pass, and the module's static checks pass.

  • Parity with ConstKnnFloatValueSource, KnnFloat16VectorQuery, Float16VectorSimilarityQuery and KnnFloat16VectorField; the error names the bad component.

Downstream note

#

No released version has the class; an application on main that passes user-supplied query vectors to it can reject non-finite components itself until a fix lands, as Lucene's own float16 kNN query does.

How it was found

#

Non-formal: an automated comparison rewrote each float16 class into its float32 twin's spelling and diffed the pair; only this class drops the twin's finiteness check. A JUnit test on the stock jars then confirmed it with assertions on and off.

The method in full136 words
  • Method: twin diff, the hunt's non-formal tier, in the hunt unit on float16 vectors. Every float16 class was rewritten into its float32 twin's spelling and diffed; the ConstKnnFloat16ValueSource pair differs only in the missing VectorUtil import and checkFinite call.
  • Alongside: a bounded-exhaustive check over all 65,536 half bit patterns showed that KnnFloat16VectorField, KnnFloat16VectorQuery and Float16VectorSimilarityQuery reject exactly the non-finite halves; it did not cover this class, which is why the diff found it.
  • Witness: a 3-test JUnit on the stock main jar (float32-twin control, +Infinity, end-to-end EUCLIDEAN scoring) failed 2 of 3 with -ea and -da; a shadowed one-line fix made it pass.
  • Later: an independent reproducer, an intended-behaviour devil's advocate, cross-model reviews and an adjudication checked it (2026-10-25); the test was reduced to one statement (2026-10-29) and re-verified on main 645d4fe14a20.

You build a ConstKnnFloat16ValueSource from a float16 query vector that contains an infinity or NaN half and score it against a KnnFloat16VectorField with a FunctionQuery over Float16VectorSimilarityFunction. You expect the constructor to throw IllegalArgumentException, as its float32 twin ConstKnnFloatValueSource does (VectorUtil.checkFinite) and as KnnFloat16VectorQuery and KnnFloat16VectorField do for the same halves (VectorUtil.checkFiniteFloat16). Instead the constructor only null-checks the array, so with -ea scoring later fails with an AssertionError inside VectorUtil (no message for EUCLIDEAN; 'not finite: ... from <raw shorts>' for DOT_PRODUCT and MAXIMUM_INNER_PRODUCT; COSINE silently scores 0), and with -da documents score 0 through FunctionQuery's intended NaN/negative clamp or, for DOT_PRODUCT and MAXIMUM_INNER_PRODUCT with an infinite component, +Infinity.
