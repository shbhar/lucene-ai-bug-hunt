A failed IndexRearranger.execute() never shuts down its thread pool, so its threads keep the JVM alive

When IndexRearranger.execute() fails after it has started work (say, a selector throws its declared IOException), it throws correctly but never shuts down its own thread pool. The pool's non-daemon threads stay until the JVM ends, so a program whose rearrange failed does not exit on its own; affected since 8.9.0.

The finding in 30 seconds

#

execute() creates its own pool and shuts it down only in its last statement. Any failure after the first task skips that line, and the pool's non-daemon threads wait for work until the JVM ends.

Background: what IndexRearranger does

#
  1. IndexRearranger (module lucene/misc, @lucene.experimental) copies an index into a chosen segment layout, mainly to build comparable indexes for benchmarks. You give it an input and an output Directory and a list of DocumentSelectors; each selector picks the documents of one output segment.
  2. execute() starts a pool of min(processors, selectors) threads for this call and runs one task per selector on it; each task calls its selector and then writer.addIndexes(...).
  3. A fixed thread pool's worker threads keep waiting for new tasks until someone calls shutdown() on the pool. Non-daemon threads keep the JVM running after main returns.

The finding, step by step

#
  1. Index one document and run IndexRearranger.execute() with one DocumentSelector that throws IOException. execute() creates a pool of min(processors, selectors) = 1 thread, rearranger-2-thread-1, and runs the selector there.
  2. You expect execute() to throw that error and to shut down the pool it created, as it does at the end of a successful run.
  3. Instead the exception skips executor.shutdown(), which is only the last line of execute(), not in a finally. The worker is still alive 10 s later, waiting for work, and stays until the JVM ends: nothing can reach the pool to shut it down, the threads are non-daemon and a fixed pool's threads never time out.
  4. A plain main() that does this prints the exception and then does not exit on its own (still running at a 20 s timeout; with the fix this one-selector run exits in 0.52 s). Each such failed call leaves min(processors, selectors) idle threads; Lucene's own CI listed 10 after a failed test task, twice in 2022.
  5. The right exception is still thrown, the input index is not changed and a successful run is unaffected. The fix is try { ... } finally { executor.shutdown(); }.

Who is affected

#

Callers of the experimental lucene/misc IndexRearranger whose run fails after it started work: a selector throws, addIndexes fails, and since 10.0.0 overlapping selectors or a failing deletes selector. A command-line JVM then does not exit; a process that retries collects idle threads. The input index is not changed; successful runs are unaffected.

Mechanism, terms and numbers566 words

IndexRearranger.execute() creates its own fixed pool, Executors.newFixedThreadPool(min(availableProcessors, #selectors), new NamedThreadFactory("rearranger")), for every call, and calls executor.shutdown() only as the last statement of the method, not in a finally. Any exception after the first task was submitted skips that line: a selector that throws, an addIndexes error, and since 10.0.0 also the class's own overlapping-selector IllegalStateException or a failing deletes selector. execute() still throws the right exception, but the pool's threads are non-daemon (NamedThreadFactory) and a fixed pool's threads "will exist until it is explicitly shutdown" (JDK javadoc), and the caller has no reference to the pool. So each such failed call leaves min(availableProcessors, #selectors) idle threads alive until the JVM ends, and a command-line program whose rearrange failed does not exit on its own after the exception leaves main.

The one-test repro fails on main (assertions on and off) and passes with a try/finally fix that also keeps the misc module's tests and :lucene:misc:check green. An equivalent one-test check fails on every release that was run, from 8.9.0 to 10.6.0; the releases in between have identical source or bytecode. It is minor: an experimental offline tool, a run that already failed loudly, the input index not changed.

Terms

#
  • Segment selector (IndexRearranger.DocumentSelector): user code, BitSet getFilteredDocs(CodecReader reader) throws IOException (IndexRearranger.java:283).
  • Fixed thread pool: Executors.newFixedThreadPool(n, factory) is a ThreadPoolExecutor(n, n, 0L, ...). Its idle threads never time out; the JDK javadoc: "The threads in the pool will exist until it is explicitly shutdown."
  • Non-daemon thread: the JVM does not exit while one is alive. NamedThreadFactory.newThread calls t.setDaemon(false) (NamedThreadFactory.java:73) and names threads <prefix>-<pool number>-thread-<n>: the pool number comes from a static, so JVM-wide, counter (:30, used with NAME_PATTERN in the constructor, :33, :41-48) and <n> from the factory's own counter (:70-71), hence rearranger-2-thread-1.

The bug (main e1faeba08bde, IndexRearranger.java)

#
  1. execute() (:113-137) creates the pool as a local variable (:114-117).
  2. createRearrangedIndex (:180-200) submits one task per selector (:194); each runs addOneSegment (:202-210), whose filtered reader's constructor calls selector.getFilteredDocs(in) (:256), then writer.addIndexes(readers) (:209).
  3. It waits with for (Future<Void> future : futures) { future.get(); } (:197-199). A failed task makes get() throw ExecutionException, which leaves execute().
  4. executor.shutdown() is the last statement (:136), outside any finally, so it is skipped. Nothing else references the pool: no executor parameter, no field, no close().

Exposure and likelihood260 words
  • Who is hit. Callers of IndexRearranger (@lucene.experimental, IndexRearranger.java:66) whose execute() fails after it submitted at least one task. In 8.9.0-9.12.3 only an exception out of the future.get() loop leaks (a failing segment selector or addIndexes, or an interrupted caller); from 10.0.0 (#11815) also the overlapping-selector IllegalStateException and a failing deletes selector. 8.9.0-9.0.0 have neither the ordering check nor a delete phase, and 9.1.0-9.12.3 call shutdown() before the ordering check (read from source).
  • Triggers are ordinary. getFilteredDocs is declared throws IOException; addIndexes can fail on I/O; the overlap check is the class's own validation.
  • Default vs opt-in. The tool is opt-in (a misc module, mainly for building benchmark indexes). Inside it nothing needs to be configured: every exception that leaves execute() after the first task was submitted skips shutdown().
  • Scale. min(availableProcessors, #selectors) idle threads per such failed call, until the JVM ends. The repro shows one; Lucene's CI showed 10 after a failed TestIndexRearranger task (2022).
  • Visible effects. A batch JVM does not exit on its own after main throws (executed with one selector: still alive at 20 s, 0.52 s with the fix); a long-lived process that retries collects threads; tests get ThreadLeakError.
  • What does not happen. execute() throws the right exception, the input index is only read (what a failed run leaves in the output directory was not examined), a successful run is unaffected, and assertions on or off make no difference.
  • Likelihood: rare. It needs a run that already fails; the searches found no user report since 8.9.0 (2021). Priority Low.

Why it looks unintended

#
  • execute() creates the pool itself and shuts it down only on success; the caller cannot reach it.
  • CheckIndex shuts the same kind of pool down in a finally; #14971 fixed the same failure-path leak in ConcurrentMergeScheduler.
  • Lucene's test framework flags it: ThreadLeakError: 1 thread leaked from SUITE scope.
The full argument225 words
  • Ownership. execute() creates the pool (IndexRearranger.java:114-117) and calls shutdown() on success (:136). There is no executor parameter, field or close(), so only execute() can release it.
  • In-tree code does it right. CheckIndex.checkIndex(List<String>) creates Executors.newFixedThreadPool(threadCount, new NamedThreadFactory("async-check-index")) and shuts it down in a finally (CheckIndex.java:588-616). The benchmark module's JoinIndices makes its pool daemon: "daemon, since Benchmark never closes PerfRunData, and the pool must not keep the JVM alive" (JoinIndices.java:90).
  • Precedent. Issue #14971 (Dawid Weiss, 2025): "ConcurrentMergeScheduler is used and it creates an instance of CachedExecutor but - upon failure - the thread pool is never shut down (LuceneTestCase does have a grace period of 20 seconds, so it's indeed a leak)." Fixed by #15675: "GITHUB#14971: Fix CachedExecutor thread pool leak in ConcurrentMergeScheduler when IndexWriter initialization fails." (lucene/CHANGES.txt:362-363).
  • The test framework calls it a leak. Without @ThreadLeakScope(NONE) the repro fails with ThreadLeakError: 1 thread leaked from SUITE scope ... rearranger-2-thread-1, state=WAITING and "There are still zombie threads that couldn't be terminated"; the 2022 CI mails show the same for TestIndexRearranger.
  • Legal trigger, nothing documented. getFilteredDocs is declared throws IOException (:283). execute() has no javadoc, the class javadoc says nothing about threads or failures, and the existing tests call execute() only on successful runs. No review comment on lucene-solr#2246 or #11815 discusses failure cleanup.
The devil's-advocate check98 words

The strongest case for "works as designed": IndexRearranger is an @lucene.experimental offline tool, execute() promises nothing on failure, the run has already failed loudly, and a command-line caller can call System.exit.

Why it fails: @lucene.experimental is about API stability, not resource leaks; the caller cannot reach the pool; a JVM that does not exit after main throws is exactly what the in-tree JoinIndices comment avoids; and maintainers treated the same failure-path pool leak as a bug in #14971. These points lower the severity (Low), not the fact that it is a bug. There is no explicit contract.

Suggested fix

#

Recommended A. Shut the pool down in a finally

Wrap everything after the pool creation in try { ... } finally { executor.shutdown(); } (+12/-9 in IndexRearranger.java). The repro then passes with assertions on and off, the misc module's 317 tests pass, and so does :lucene:misc:check with the test's committable form. It does not wait for tasks still running; that is a separate bug, LFV-1011.

All options and trade-offs4 options · 599 words

Option A was run through gradle in a scratch worktree of e1faeba08bde and is recommended. B and C are alternatives a maintainer may prefer; neither was run as written here. No open PR changes the executor lines (#14996 and #16847 touch the file elsewhere).

Trade-offs

  • shutdown() neither waits nor interrupts running tasks (JDK: "previously submitted tasks are executed ... This method does not wait"; it interrupts only idle workers, which is how they exit), so tasks still running or queued when another task fails run to the end, and only then do the threads exit; a task that blocks keeps its thread, and the JVM, alive until it returns. That they run on a reader and writer being closed is the separate LFV-1011; this fix neither fixes nor worsens it.
  • Error path only; the success path already called shutdown(). No API or format change.

What the checks validated

  • Gradle, JDK 25, scratch worktree of e1faeba08bde (removed afterwards): the repro fails on the stock build with assertions on and off (10.3 s) and passes with the fix with assertions on and off (0.28 s).
  • With the fix: TestIndexRearranger, TestBinaryDocValueSelector and the repro with -Ptests.iters=5 and -XX:ActiveProcessorCount=4: 30 tests, 0 failures; the whole :lucene:misc:test: 24 classes, 317 tests, 0 failures, 9 skipped.
  • With the fix, the committable copy of the test passes :lucene:misc:check -x test; a copy without @ThreadLeakScope(NONE) passes the framework's leak check (on stock it fails with ThreadLeakError).
  • Earlier: the finder's and the verifier's tests and the exit-path harness (all 5 exit cases) pass with the fix shadowed; a cross-model reviewer's run kept TestIndexRearranger green.

B. shutdownNow() on the failure path

#

Also drops queued tasks and interrupts running ones, so a failed run stops sooner.

Trade-offs

Interrupting a thread blocked on I/O is risky in Lucene: NIOFSDirectory's javadoc warns it "can close the underlying file descriptor immediately" (NIOFSDirectory.java:41-46). Not tried.

C. Fix it together with LFV-1011

#

Wait for every task before rethrowing (LFV-1011's fix) and shut the pool down in a finally. Or give each phase its own pool as the last resource of its try-with-resources, so that ExecutorService.close() (JDK 19+; main requires Java 25) shuts down and waits before the reader and writer close.

Trade-offs

The combined diff (+35/-13) was validated for LFV-1011 on 645d4fe14a20, whose IndexRearranger.java is the same file; the close() variant was not tried, and a 9.x backport would need explicit shutdown() and awaitTermination().

Not enough alone: daemon threads

#

Make the pool's threads daemon, as the benchmark module's JoinIndices does.

Trade-offs

Lets the JVM exit, but a long-lived process still collects idle threads per failed call.

Downstream note

#

Only code that runs IndexRearranger itself, an offline operator-run tool, can hit it; no query or document path reaches it.

How it was found

#

Non-formal: in a sweep that passes unusual executors into Lucene components, the hunting AI tool found that IndexRearranger owns its pool, read its failure paths instead and saw shutdown() outside a finally. A JUnit counting live rearranger threads after a failed execute() confirmed it.

The method in full130 words

Method: non-formal (code reading during an executor sweep, 2026-10-26). The sweep passed unusual executors into the Lucene components that accept one; IndexRearranger creates its own, so none could be injected, and the hunting AI tool read its failure paths instead and saw executor.shutdown() as the last statement, outside any finally.

  • A JUnit that counts live rearranger- threads after a failed execute() failed 2 of 3 (failing selector, overlapping selectors; the success control passed). A cross-model review (an independent reviewer from another model family, OpenAI GPT-5.6, refute lens, executed) reproduced both paths.
  • A later hunt unit (2026-11-02) re-ran the lead on main e1faeba08bde, ran five exit cases of execute() through an exit-path harness on the stock jar and on a try/finally shadow, and reduced the repro to one test.

History

#

Introduced with the class by LUCENE-9694 (e4cede0e8c5, 2021-01-29, first released in 8.9.0); #11815 (10.0.0) moved shutdown() to the end of execute(), so two more exits leak. Executed as affected from 8.9.0 to 10.6.0 and on main; not fixed upstream.

Versions tested6 rows

Introduced by LUCENE-9694 "New tool for creating a deterministic index" (apache/lucene-solr#2246 by Patrick Zhai, merged by Mike McCandless on 2021-01-29 as e4cede0e8c5; branch_8x backport 3da86cb5b36 the same day, which 8.9.0 ships). From the PR's first commit, shutdown() was the last statement of the try block, after the future.get() loop, with no finally.

#683 (9.1.0, the backport of #630) added the segment-ordering check after the block; in 9.x shutdown() still ran before it. #11815 "Support deletions in rearrange" (369a70f2894, Stefan Vodita, 2022-11-22, 10.0.0) moved the pool creation to the top of execute() and shutdown() to its last line so the delete phase could reuse the pool. That made the existing overlapping-selector exit leak and added the delete phase's exit, which leaks too. The file has not changed since.

Impact note
Hits only callers of the experimental lucene/misc IndexRearranger (8.9.0 through 10.6.0 and main) whose execute() fails after it has submitted at least one task (a DocumentSelector that throws its declared IOException or an addIndexes error, and from 10.0.0 also the class's own overlapping-selector IllegalStateException or a failing deletes selector): execute() still throws the right exception, but each such call leaves min(availableProcessors, #selectors) idle non-daemon 'rearranger' pool threads that never end, so a command-line program whose rearrange failed does not exit after the exception leaves main (executed: still alive at a 20 s timeout, exits in 0.52 s with the fix) and a long-lived process that retries collects idle threads; the input index is only read, a failure before the first task starts no thread, and a successful execute() is unaffected [exec, -ea and -da].
Summary
You run IndexRearranger.execute() and it fails after it has started its work, for example because one of your DocumentSelectors throws an IOException. You expect execute() to throw that error and to release the thread pool it created for the run, as it does when the run succeeds. Instead executor.shutdown() is only the last statement of execute(), not in a finally, so on the failure path the pool's worker threads, which are non-daemon and never time out, stay alive forever: a program whose rearrange failed does not exit, and every failed call leaves more idle threads.
