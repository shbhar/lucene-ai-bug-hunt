All findings · Lucene finding · LFV-958 · searchgroup-merge-presized-by-topn

SearchGroup.merge pre-sizes its result by topN, so merging shard groups with topN = Integer.MAX_VALUE throws OutOfMemoryError (and NullPointerException for offset >= 1)

Asking SearchGroup.merge for every group of your shards with topN = Integer.MAX_VALUE throws OutOfMemoryError, even for 2 groups, because since 6.2.0 it reserves a result slot per requested group. With offset = 1, offset + topN overflows and the call throws NullPointerException instead.

The finding in 30 seconds

#

SearchGroup.merge reserves a result slot for every requested group before it knows how many groups the shards hold, and it adds offset to topN in an int.

Grouped search across shards in 3 steps

#
  1. Grouped search runs in two passes; the first pass finds each shard's (or slice's) top groups as SearchGroup objects, each with its group value and sort values.
  2. SearchGroup.merge(shardGroups, offset, topN, groupSort) combines them: it keeps a sorted candidate queue of at most offset + topN groups, skips the first offset and returns up to topN.
  3. Lucene's FirstPassGroupingCollectorManager calls it to combine the slices of one searcher; for shards, the grouping docs leave the merge to your code.

The finding, step by step

#
  1. You merge the top groups of two shards yourself, as the grouping docs suggest for sharding: shard 1 returned group a, shard 2 group b.
  2. To get every group you call SearchGroup.merge(shards, 0, Integer.MAX_VALUE, sort). You expect [a, b], what topN = 10 returns and what 6.1.0 returned for this call.
  3. You get OutOfMemoryError: Requested array size exceeds VM limit. The merger creates its result list as new ArrayList<>(topN): room for 2,147,483,647 groups to hold 2. Smaller "all" values stay under that limit but still reserve about 4 bytes per requested group: 400 MB for topN = 100,000,000, which throws OutOfMemoryError: Java heap space on a heap smaller than that (64 MiB, probe).
  4. With offset = 1 it fails sooner: the queue bound offset + topN wraps to -2,147,483,648, so the loop that trims the candidate queue empties it, takes one more and throws NullPointerException. That overflow dates from 3.3.0 (NoSuchElementException on 3.x, NullPointerException since 4.0.0).

Who is affected

#

Code that merges shard groups itself with SearchGroup.merge and passes Integer.MAX_VALUE (or MAX - 1) for "all groups", or any offset + topN >= 2^31 with a non-empty shard. Lucene's own FirstPassGroupingCollectorManager and GroupingSearch fail earlier for these values, in a separate bug. The failure is loud; large legal topN reserves about 4 bytes per requested group.

Mechanism, terms and numbers617 words

SearchGroup.merge(topGroups, offset, topN, groupSort) is the public, @lucene.experimental helper that merges the first-pass top groups of several shards. It creates its result list as new ArrayList<>(topN) (SearchGroup.java:294), sized by the request rather than by the groups the shards hold, so topN = Integer.MAX_VALUE (or MAX - 1), a common way to ask for every group, throws OutOfMemoryError: Requested array size exceeds VM limit at any offset, even when only 2 groups exist; smaller large values reserve about 4 bytes per requested group (400 MB at 10^8) and throw Java heap space when the heap is smaller than that. Up to 6.1.0 the offset-0 call returned the groups: the pre-size came with LUCENE-7356 in 6.2.0. Independently, the queue bound offset + topN is an int sum (:281), so with offset >= 1 and offset + topN >= 2^31 it wraps negative and, as soon as one shard holds a group, the pruning loop dereferences null (:274), as it has since the method was added in 3.3.0. The javadoc sets no bound and nothing checks the arguments.

Reach is narrow: Lucene's own FirstPassGroupingCollectorManager and GroupingSearch fail earlier for these values, in the first-pass collector (LFV-964), so only code that calls SearchGroup.merge directly is hit. The failure is loud: no wrong groups. A small fix in GroupMerger.merge (saturate the sum at :281 and size the list at :294 by the groups the shards hold, counted in a short loop) removes both failures and passes the grouping module's tests (57 with the repro).

The code (main 645d4fe14a20, SearchGroup.java)

#
  • :281: final int maxQueueSize = offset + topN; an int sum that wraps for offset + topN >= 2^31.
  • :271-275: after each insertion updateNextGroup prunes while (queue.size() > topN) (here topN is maxQueueSize) with queue.pollLast() and then group.inQueue = false, with no null check. With a negative bound it empties the TreeSet, pollLast() returns null and :274 throws NullPointerException: Cannot assign field "inQueue" because "group" is null.
  • :294: new ArrayList<>(topN): the result list is sized by the caller's topN. For Integer.MAX_VALUE and MAX - 1 the tested JVM (OpenJDK 25.0.3) refuses the array before allocating (Requested array size exceeds VM limit), with a 64 MiB heap as with the default heap; for smaller large values it allocates topN references, about 4 bytes each with compressed references.
  • :298-320: the pull loop stops when the queue is empty or at topN results, so it never needs more slots than there are groups.

Memory below the limit

#

One merge of three groups allocates 1,360 bytes for topN = 10, 4,001,320 for 10^6 and 400,001,320 for 10^8; with the fix 1,368 bytes for all three (measured on main a9779ef3c193, identical grouping code, OpenJDK 25.0.3 with compressed references). Below the VM limit the call needs that much free heap: topN = 10^8 throws OutOfMemoryError: Java heap space with -Xmx64m and returns the groups with -Xmx1g; 10^9 throws with -Xmx1g.

Exposure and likelihood310 words
  • Who is hit. Code that merges first-pass top groups itself with SearchGroup.merge and passes topN = Integer.MAX_VALUE (or MAX - 1) for "all remaining groups": every such call throws, at any offset, however few groups exist. With offset >= 1, any offset + topN >= 2^31 throws NullPointerException as soon as at least one shard holds a group (with only empty shards the pruning loop never runs, so there is no NullPointerException: the call returns no groups, or fails at the pre-size when topN itself is near Integer.MAX_VALUE; probe). Two executed examples: each shard collected by a bounded FirstPassGroupingCollectorManager(..., 0, 10) and then merged with merge(shardGroups, 0, Integer.MAX_VALUE, sort); and each shard collected completely (topNGroups = the shard's maxDoc) and merged with "all". Both throw; the same merge with a finite topN returns the groups.
  • Who is not. FirstPassGroupingCollectorManager and GroupingSearch callers with these values fail earlier, in the first-pass collector constructor: NegativeArraySizeException for (0, MAX), IllegalArgumentException "topNGroups must be >= 1 (got -2147483648)" for (1, MAX), OutOfMemoryError for (0, MAX - 1). That is LFV-964, with its own fix site. Callers with ordinary page sizes are unaffected.
  • Large but legal topN. Values such as 10^8 used as "all" reserve about 4 bytes per requested group per merge (400 MB at 10^8): they return the right groups when the heap has room, and throw OutOfMemoryError: Java heap space when it does not (10^8 with a 64 MiB heap, probe).
  • Default vs opt-in. No setting or index is involved; SearchGroup is @lucene.experimental; the trigger is the topN value of a direct call.
  • Severity and scale. An exception for that call; no wrong or missing groups, nothing persisted. Every release from 6.2.0 (offset 0) or 3.3.0 (offset >= 1) through 10.6.0, and main. Rare: the documented searches (Prior reports, below) found no public report.

Why it looks unintended

#
  • The javadoc sets no bound on offset or topN, and the method checks neither.
  • Up to 6.1.0 the same call returned the groups; the 6.2.0 change (LUCENE-7356) was a capacity tweak.
  • Grouped facet paging fixed the same offset + limit overflow (SOLR-3956) and still tests Integer.MAX_VALUE as "no limit"; core TopDocs.merge sizes by the hits available.
The full argument196 words
  • No documented bound. The javadoc (SearchGroup.java:326-331) only asks for a matching groupSort and fillFields=true; nothing checks offset or topN (:332-335). The package docs tell sharded users to do this merge themselves (package-info.java:76-77).
  • A regression from a micro-optimisation. LUCENE-7356 "SearchGroup tweaks (initialCapacity, size==0 vs. isEmpty)" (#8410, by Christine Poerschke, one "+1" from Adrien Grand) changed new ArrayList<>() to new ArrayList<>(topN). The issue text is just "initialCapacity" and "size()==0 vs. isEmpty()"; nobody discussed large topN. Every release from 3.3.0 (the first with the method) to 6.1.0 returns the groups for topN = Integer.MAX_VALUE (47 releases executed).
  • Same module, same pattern, fixed and tested. SOLR-3956 (1ad382f3046, Chris M. Hostetter, 2013) removed an offset + limit overflow from grouped-facet paging; its test still loops limit over {2, 10, 100, Integer.MAX_VALUE} (TestTermGroupFacetCollectorManager.java:106-139). Today GroupedFacetResult.getFacetEntries sizes by Math.min(limit, facetEntries.size() - offset) (GroupedFacetResult.java:91), and core TopDocs.merge by Math.min(size, availHitCount - start) (TopDocs.java:313).
  • An internal NPE is no answer. Whatever range is intended, a NullPointerException from polling an empty queue after a signed overflow names an internal field, not an argument. An IllegalArgumentException would be an acceptable alternative.
The devil's-advocate check135 words

The strongest case for "works as designed": topN is a concrete count on an @lucene.experimental expert helper; the grouping first pass deliberately allocates by topNGroups (FirstPassGroupingCollector.java:116, :121); Michael McCandless's LUCENE-2119 description calls Integer.MAX_VALUE "a nonsense value to pass in, since our PQ impl allocates the array up front"; and Lucene's own manager never reaches the merge with such values.

Why it fails: SearchGroup.merge has no pre-allocated priority queue; it prunes a TreeSet lazily and worked with Integer.MAX_VALUE for offset 0 from 3.3.0 to 6.1.0. LUCENE-2119 itself was resolved Fixed (IndexSearcher caps n at maxDoc) because "This trips users up fairly often". The module's own SOLR-3956 test treats Integer.MAX_VALUE as "no limit". The reach argument limits who is hit, not whether it is a bug, and the doc states that limit plainly.

Suggested fix

#

Recommended A: saturate offset + topN and size the result by the shard groups (validated)

Saturate the queue bound at Integer.MAX_VALUE and size the result list by the groups the shards hold (lines :281 and :294 plus a short count loop in GroupMerger.merge). The grouping module's tests, 57 with the repro, pass with assertions on and off. By reading, calls that work today return the same results: only the capacity and overflowing sums change.

// GroupMerger.merge, at the queue bound (was: final int maxQueueSize = offset + topN;)
final int maxQueueSize = (int) Math.min((long) offset + topN, Integer.MAX_VALUE);
long shardGroupCount = 0;
for (Collection<SearchGroup<T>> shard : shards) {
  shardGroupCount += shard.size();
}
// ... and at the result list (was: new ArrayList<>(topN))
final List<SearchGroup<T>> newTopGroups =
    new ArrayList<>((int) Math.min(topN, shardGroupCount));

A: saturate offset + topN and size the result by the shard groups (validated) (recommended)

#

Compute the queue bound in long and clamp it to Integer.MAX_VALUE, and create the result list with min(topN, total groups in the shard lists) slots. Both reproduced failures go away: the bound cannot wrap, and the list never reserves more slots than the shards hold groups, so LUCENE-7356's capacity hint stays useful for ordinary topN.

// GroupMerger.merge, at the queue bound (was: final int maxQueueSize = offset + topN;)
final int maxQueueSize = (int) Math.min((long) offset + topN, Integer.MAX_VALUE);
long shardGroupCount = 0;
for (Collection<SearchGroup<T>> shard : shards) {
  shardGroupCount += shard.size();
}
// ... and at the result list (was: new ArrayList<>(topN))
final List<SearchGroup<T>> newTopGroups =
    new ArrayList<>((int) Math.min(topN, shardGroupCount));

Trade-offs

One size() call per shard collection; the capacity is an upper bound (a group returned by several shards is counted once per shard), so it is only large when the shards really hold that many groups. Results unchanged is argued from the code and the module's tests, not tested exhaustively. Full diff:

B: revert the pre-size and saturate the sum

#

Go back to new ArrayList<>() at :294 and saturate :281. The smallest diff.

Trade-offs

Gives up LUCENE-7356's capacity hint. Not built as one change; the version-history runs ran each half alone: reverting only :294 fixes offset 0 but keeps the NPE, saturating only :281 turns the NPE into the OOM, so both lines are needed.

C: reject out-of-range arguments with IllegalArgumentException

#

Validate offset >= 0, topN >= 1 and that offset + topN does not overflow.

Trade-offs

A clear error instead of an internal NPE, but it turns topN = Integer.MAX_VALUE, which worked for offset 0 up to 6.1.0 and which core TopDocs.merge accepts for hits, into an error. Not built; the adjudication and the audit call it an acceptable alternative.

Downstream note

#

Services that pass a client-chosen group page offset or size into SearchGroup.merge should bound both, since Integer.MAX_VALUE throws and large values reserve heap in proportion to the value.

How it was found

#

AI tools built a Z3 bit-vector model of every int size computation in the grouping module. It predicted that offset + topN wraps at SearchGroup.java:281 and that the pre-size at :294 exceeds the VM array limit; a shard-merge probe on the stock jar then threw both errors, while finite topN returned the groups.

The method in full130 words

Hunt unit "grouping offset + limit overflow" (2026-10-28), a semi-formal hunt:

  • The finder wrote a Z3 bit-vector model of every int size site in the grouping module. Site S6 is SearchGroup.java:281 (the sum) and :294 (the pre-size). Query Q6 is satisfiable at offset 1, topN Integer.MAX_VALUE (Java int sum -2^31); Q6b is satisfiable for the offset-0 pre-size above the VM array limit.
  • A shard-merge probe on the stock main jar, assertions off, witnessed both: OutOfMemoryError at :294 for topN MAX - 2 to MAX, and NullPointerException at :274 for offsets 1 and 2 with topN MAX, while finite topN returned the groups.
  • The unit was planned from a "top-n size parameters" area and an earlier, never-executed read-only lead on the same int-sum pattern (LFV-262, in core TopDocs.merge).

History

#

The offset-0 OutOfMemoryError is a 6.2.0 regression from LUCENE-7356 (2016): 6.1.0 returns the groups. The offset >= 1 crash is as old as the method (LUCENE-3191, 3.3.0, 2011). A 136-release sweep confirms both boundaries; 10.6.0 and main fail both ways.

Versions tested7 rows
  • Pre-size leg. LUCENE-7356 "SearchGroup tweaks (initialCapacity, size==0 vs. isEmpty)" (#8410, by Christine Poerschke): e0c45f400f8 (master) and 0c43ae2b5c2 (branch_6x), both 2016-06-28, changed new ArrayList<>() to new ArrayList<>(topN). 0c43ae2b5c2 is not in 6.1.0; 6.2.0 is the first release with it. Swapping only SearchGroup.java between 6.1.0 and 6.2.0 flips the offset-0 result both ways.
  • Overflow leg. LUCENE-3191 (#4264, by Michael McCandless): a1e74fd6c94 (trunk, 2011-06-15) and c0713158f8c (branch_3x, 2011-06-16) added SearchGroup.merge with maxQueueSize = offset + topN; first release 3.3.0. LUCENE-3239 (b843dfe8396, Simon Willnauer, 2011-06-30) replaced queue.last() with pollLast(), which turned the 3.x NoSuchElementException into the NullPointerException from 4.0.0 on.
  • Sweep. 136 releases from 3.3.0 to 10.5.2, one run each with assertions off (6.1.0, 6.2.0, 9.12.3 and 10.5.2 also on): offset 0 returns the groups on 3.3.0-6.1.0 and on 5.5.3-5.5.5 (released after 6.2.0 from branch_5_5, without LUCENE-7356), and throws OutOfMemoryError on the 89 releases 6.2.0-10.5.2. LFV-958, snapshot of 2026-11-08

Registry title
SearchGroup.merge (the shard-merge helper of grouped search) with topN = Integer.MAX_VALUE ('all remaining groups') throws OutOfMemoryError because it pre-sizes its result list by topN (regression in 6.2.0, LUCENE-7356), and with offset >= 1 throws NullPointerException because offset + topN wraps to a negative queue bound (since 3.3.0)
Area
grouping / SearchGroup.merge (merging first-pass top groups across shards or slices; reduce step of FirstPassGroupingCollectorManager)
Priority
Low, rank 662: SearchGroup.merge pre-sizes its list by topN and throws OutOfMemoryError at Integer.MAX_VALUE, which matches LFV-574's MoreLikeThis pre-size OOM that only direct callers hit.
Impact class
crash
Impact note
Hits only code that calls the public, @lucene.experimental static SearchGroup.merge directly, for example a manual shard merge as the grouping package docs suggest for sharding, with topN = Integer.MAX_VALUE or MAX - 1 as 'all remaining groups' (OutOfMemoryError 'Requested array size exceeds VM limit' at any offset, even when only three groups exist) or with offset >= 1 and offset + topN >= 2^31 (NullPointerException); Lucene's own FirstPassGroupingCollectorManager.reduce, GroupingSearch and the usual per-shard (offset + topN) recipe fail earlier, in the first-pass collector constructor, for the same values (LFV-964); smaller large topN values only cost about 4 bytes per requested group (400 MB for topN = 10^8 on three groups); no setting or index size is needed, the failure is loud, returns no wrong groups and leaves no state behind; every release from 6.2.0 (OutOfMemoryError) or 3.3.0 (offset >= 1) to 10.6.0 and main is affected.
Summary
You merge the first-pass top groups of two shards (three groups in all) with SearchGroup.merge(shardGroups, 0, Integer.MAX_VALUE, groupSort) to get every group, and expect the three groups, the same as topN = 10 returns, as 6.1.0 and earlier returned for the same call, and as core TopDocs.merge(0, Integer.MAX_VALUE, ...) does for hits. Instead merge throws OutOfMemoryError 'Requested array size exceeds VM limit', because since 6.2.0 (LUCENE-7356) it pre-sizes its result list with new ArrayList<>(topN). With offset 1 it throws NullPointerException, because maxQueueSize = offset + topN wraps to a negative int and the pruning loop polls an empty queue (NoSuchElementException on 3.x).
