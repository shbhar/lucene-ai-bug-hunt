ByteBuffersIndexOutput.getChecksum returns 0 for an empty output without asking the supplied Checksum

ByteBuffersIndexOutput.getChecksum() on an output with nothing written returns 0 without asking the Checksum you passed in: with Adler32, whose checksum of no bytes is 1, you get 0. Lucene itself only passes CRC32, whose empty value really is 0, so its own files are unaffected.

The finding in 30 seconds

#

getChecksum() caches its last result together with the output size it was computed for. The cache fields start at Java's default 0, so an empty output always looks "already computed" and the cached 0 comes back.

Background

#
  1. A java.util.zip.Checksum starts at its algorithm's initial value and reset() returns it there: CRC32 and CRC32C start at 0, Adler32 at 1.
  2. ByteBuffersIndexOutput is Lucene's in-memory IndexOutput (used by ByteBuffersDirectory and as a scratch buffer). Its 3-argument constructor uses CRC32; the public 5-argument one takes any Checksum.

The finding, step by step

#
  1. Build an in-memory output with your own checksum through the public 5-argument constructor: new ByteBuffersIndexOutput(new ByteBuffersDataOutput(), "d", "n", new Adler32(), null). Write nothing.
  2. Call getChecksum(). You expect 1: Adler-32 of no bytes is 1 (new Adler32().getValue()), and getChecksum() returns "the current checksum of bytes written so far".
  3. Instead you get 0. getChecksum() remembers its last answer together with the output size it was computed for, and that memory starts as "size 0, answer 0". At size 0 it sees a match and never asks the Checksum.
  4. Write one byte (7) and ask again: 524296, the right Adler32 value. With CRC32, the only checksum Lucene passes, size 0 gives 0, which is correct, so Lucene's own files never see a wrong value.

Who is affected

#

Only application code that builds a ByteBuffersIndexOutput itself through the public 5-argument constructor, with a Checksum whose empty value is not 0 (such as Adler32), and asks for the checksum before writing anything. It is then silent and deterministic. Lucene passes CRC32 everywhere, so its own files and footers are unaffected. Every release since 7.5.0.

Mechanism, terms and numbers549 words

ByteBuffersIndexOutput has a public 5-argument constructor that takes any java.util.zip.Checksum. To avoid re-reading the buffer on every call, getChecksum() caches its last result keyed by the output size. The two cache fields have no initializer, so the cache starts as "size 0, value 0": for an output with nothing written, getChecksum() sees a cache hit and returns 0 without resetting or reading the Checksum.

For CRC32 and CRC32C the checksum of no bytes is 0, so the shortcut happens to be right; for Adler32 it is 1, so the caller gets 0 instead of 1. Once something is written the size no longer matches, the class recomputes the caller's Checksum over the buffer, and the Adler32 value is right (executed: one byte). Every in-tree construction passes CRC32, so Lucene's own files and footers are never affected; only application code that uses the 5-argument constructor with a Checksum whose empty value is not 0 is. Present since the class was added (LUCENE-8468, 7.5.0); the fix is a few lines in ByteBuffersIndexOutput.

Mechanism (Lucene main 5adff78bb168)

#
  1. ByteBuffersIndexOutput.java:32-33: private long lastChecksumPosition; and private long lastChecksum; have no initializer, so they start as 0 and 0. This is the fix site.
  2. :37-40: the 3-argument constructor passes new CRC32(). :42-52: the public 5-argument constructor stores whatever Checksum it is given (only null is special: getChecksum() then throws, :75-77).
  3. getChecksum() (:72-95): if (lastChecksumPosition != delegate.size()) (:86) guards the computation (checksum.reset(), update over delegate.toBufferList(), lastChecksum = checksum.getValue(), :88-92); :94 returns lastChecksum.
  4. For an empty output delegate.size() is 0, equal to the start value of lastChecksumPosition, so the guard is false, the Checksum is never consulted, and the start value 0 of lastChecksum is returned.

Controls (executed)

#
  • Adler32 after one byte (7): 524296, correct.
  • CRC32: 0 at size 0 (correct) and 1281784366 at size 1 (correct); CRC32C: 0 at size 0 (correct).
  • Of these cases only the empty output is wrong, and only for a Checksum whose empty value is not 0.

Side note, not claimed

#

The size is stored at :87, before reset/update/getValue. If the caller's Checksum throws there, the new size is already marked as computed, and the next call returns the previous size's value (a probe with a CRC32-backed Checksum that throws once: 2724731650, the value for one byte, instead of 3586999183 for two). Behaviour after an unchecked exception from caller code is not promised, so this stays a side note; the recommended fix covers it anyway.

A second unclaimed note: the cache is keyed only on the size (:86), so it assumes the bytes cannot change without the size changing. The output keeps the ByteBuffersDataOutput the caller passed in (:49), whose reset() is public (ByteBuffersDataOutput.java:481-495; its javadoc warns that sharing its buffers for reads and writes "is dangerous ... use with great care"). A caller who resets it behind the output and writes the same number of other bytes gets the old value, with CRC32 and the 3-argument constructor too (a probe: 2768625435, the CRC32 of byte 1, instead of 1007455905 for byte 2). That is a different trigger (changing the buffer behind an append-only output), and the recommended fix does not change it.

Exposure and likelihood124 words
  • Who: application code that constructs the class directly with its own Checksum whose value over zero bytes is not 0 (java.util.zip.Adler32 is the standard JDK example) and calls getChecksum() before any byte is written. Deterministic, assertions on and off, no setting or scale needed.
  • Not hit: Lucene itself. Every in-tree construction uses CRC32: ByteBuffersDirectory.java:259-263 passes new CRC32(), and Lucene90DocValuesConsumer.java:768, :874, backward-codecs Lucene80DocValuesConsumer.java:767, :880 and replicator PrimaryNode.java:302 use the 3-argument constructor. CodecUtil.writeFooter writes the magic and the algorithm id before it asks for the checksum (CodecUtil.java:410-414, :680-681), so it never asks on an empty output.
  • Downstream: the recorded public code searches found only 5-argument constructions that pass new CRC32().
  • Effect: one wrong long return value.

Why it looks unintended

#
  • IndexOutput.getChecksum() promises "the current checksum of bytes written so far"; nothing restricts the public constructor's Checksum to CRC32.
  • Once the size changes, the class recomputes the caller's Checksum (one byte executed: correct); only size 0 skips it.
  • No test, javadoc, CHANGES entry or commit message makes the 0 intended: the cache fields simply have no initializer.
The full argument204 words
  • The contract: IndexOutput.getChecksum(): "Returns the current checksum of bytes written so far" (IndexOutput.java:69-70). The code comment in getChecksum() says the checksum is "correctly computed on the current content of the output buffer" (ByteBuffersIndexOutput.java:79-85). JDK Checksum.reset() "Resets the checksum to its initial value".
  • The API invites other checksums: the 5-argument constructor is public and takes a plain java.util.zip.Checksum; neither IndexOutput nor this class states a CRC32-only (or "empty value must be 0") precondition, and the class has no @lucene.internal or @lucene.experimental tag (:27-28, :42-52).
  • The class uses the caller's Checksum everywhere else: whenever the size differs from the cached one it resets the caller's Checksum and recomputes it over the whole buffer (:86-92), and after one byte the Adler32 value is right (executed); so the 0 at size 0 is an unstated CRC32 assumption in a cache shortcut, not a design choice.
  • Nothing says otherwise: no test constructs this class with a non-CRC32 Checksum or asserts an empty-output value (the test constructions in TestCodecUtil, TestFilterIndexOutput and TestBlockWriter use the 3-argument constructor), and no javadoc, CHANGES or MIGRATE entry or commit message makes the 0 intended; the prior-report searches found no discussion that does.
The devil's-advocate check161 words

Lucene's file format fixes the footer checksum as zlib-crc32 ("Currently this is always 0, for zlib-crc32", CodecUtil.java:402; a header and footer written through an Adler32-backed output fail checkFooter with CorruptIndexException: checksum failed), every in-tree caller and every downstream caller the recorded code searches found passes CRC32, and the Checksum parameter may just be plumbing for ByteBuffersDirectory. So a maintainer could say non-CRC32 checksums were never contemplated and the 0 start is right for the only real use. The class author also wrote on #10444 that "the choice of built-in Checksum class was arbitrary".

Why it fails: none of that is written on the API: the public constructor takes any Checksum with no stated precondition, and the class does compute the caller's Checksum at every size it has not cached yet. "Arbitrary" is about which implementation was picked, not a CRC32-only contract. What remains is an impact argument (latent for Lucene itself), which is why this is Low.

Suggested fix

#

Recommended Start the cache at -1 and record the size after the value (recommended)

Start the cache at "nothing computed" (lastChecksumPosition = -1) and record the size only after getValue() returned: +4/-3 lines in ByteBuffersIndexOutput. The test passes with assertions on and off, and so do every org.apache.lucene.store test class of lucene/core and TestCodecUtil (30 classes with the repro, 798 tests, 0 failures).

  private long lastChecksumPosition = -1;
...
    long size = delegate.size();
    if (lastChecksumPosition != size) {
      checksum.reset();
      for (ByteBuffer bb : delegate.toBufferList()) {
        checksum.update(bb);
      }
      lastChecksum = checksum.getValue();
      lastChecksumPosition = size;
    }
    return lastChecksum;

Trade-offs

The first getChecksum() on an empty output now does one reset() and getValue() (no bytes to read). CRC32 results are unchanged, since its empty value is 0. Recording the size last also closes the stale value after a throwing Checksum (the side note).

How it was found

#

Semi-formal: a proof-obligation audit of getChecksum() against its contract, that the value returned is the supplied Checksum's value over the bytes written so far. Nothing discharges the obligation at size 0, where the cache looks valid before anything was computed, and a JUnit test on stock main witnessed the failure.

The method in full80 words
  • Obligation: getChecksum() returns the supplied Checksum's value over the bytes written so far (IndexOutput.java:69-70), for any Checksum the public constructor accepts.
  • Finding: the cache test at ByteBuffersIndexOutput.java:86 can be false before any value was computed, because both cache fields start at 0; at size 0 the result is then the field default, not the Checksum's value.
  • Witness: the one-test JUnit repro, then an independent reproduction, cross-model reviews, an intended-behaviour review and an adjudication (see Independent checks).
