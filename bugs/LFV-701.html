Doc-values CONTAINS with several points matches documents that hold only one of them

Ask for the documents that contain both point P1 and point P2: LatLonPoint.newGeometryQuery returns only those, but its documented doc-values partner LatLonDocValuesField.newSlowGeometryQuery returns every document holding P1 or P2 ([A, B, C] instead of [C]). So IndexOrDocValuesQuery answers depend on which side runs, in every release since 8.8.0.

The bug in 30 seconds

#

CONTAINS with several points should match only documents that hold all of them. The points query does that with one MUST clause per point; the doc-values query accepts a document as soon as one of its points equals one query point.

  1. Index four documents with LatLonPoint and LatLonDocValuesField on one field: A = {P1}, B = {P2}, C = {P1, P2}, D = {P3}.
  2. Ask for CONTAINS(P1, P2), the documents whose points include both P1 and P2. You expect [C], and LatLonPoint.newGeometryQuery returns [C].
  3. LatLonDocValuesField.newSlowGeometryQuery, which its javadoc tells you to pair with that query, returns [A, B, C]: every document holding P1 or P2, exactly what INTERSECTS(P1, P2) returns.
  4. So the documented pair IndexOrDocValuesQuery(points, docValues) depends on which side runs: with 2,000 more one-point documents it returns [C] on its own, but id:A AND it returns A, which holds only P1, and explain() says A matches.
  5. Why: the doc-values CONTAINS keeps one flag per document and sets it as soon as any document point equals any query point; nothing checks that every query point was found. The points query adds one MUST clause per point.

Who is affected

#

Anyone running CONTAINS with two or more points on a LatLonDocValuesField: on its own (for example a doc-values-only field), through the documented IndexOrDocValuesQuery pair under a selective clause, or via that pair's explain(). Default configuration, any index size; extra hits only. Rare: a niche query; no user report was found since 2021.

Mechanism, terms and numbers587 words

LatLonDocValuesField.newSlowGeometryQuery(field, CONTAINS, p1, p2, ...) should match the documents whose points include every query point, as LatLonPoint.newGeometryQuery(field, CONTAINS, p1, p2, ...) does with one MUST clause per point. Its javadoc says to wrap it in an IndexOrDocValuesQuery alongside exactly that query, and IndexOrDocValuesQuery requires that "Both provided queries must match the same documents". Instead LatLonDocValuesQuery.contains() keeps a single flag per document and sets it as soon as any document point equals any query point, so it computes an OR: on four documents A = {P1}, B = {P2}, C = {P1, P2}, D = {P3}, CONTAINS(P1, P2) returns [C] on the points path and [A, B, C] on the doc-values path, the INTERSECTS hit set. The wrapper's answer then depends on which side runs: with 2,000 more one-point documents it returns [C] alone, A under id:A AND, and its explain() reports a match for A. No error; default configuration; extra hits only. LUCENE-9641 (14009f4424d, 8.8.0) added the AND and the OR in the same commit; every release since is affected, and a one-method fix that requires every query point passes the repro and the closest existing suites.

Terms

#
  • Point fields: LatLonPoint indexes a location in a points (BKD) index; LatLonDocValuesField stores it as doc values, read one document at a time. A document may hold several points on one field.
  • CONTAINS on points: newGeometryQuery(field, CONTAINS, p1, ..., pk) and newSlowGeometryQuery(field, CONTAINS, p1, ..., pk) accept only Point geometries for CONTAINS (others give MatchNoDocsQuery, LatLonDocValuesField.java:255-262). A query point is contained when a document point equals it on the encoding grid: the query point is rounded up to the grid (Point2D.java:168-181) and compared with exact == (Point2D.java:56-57).
  • IndexOrDocValuesQuery: wraps a points query and an equivalent doc-values query and picks a side per segment: the doc-values one only when the points cost shifted right by 3 (divided by 8, rounded down) is greater than the lead clause's cost, cost() >>> 3 > leadCost (IndexOrDocValuesQuery.java:183-193), otherwise the points one; explain() and matches() always use the doc-values one (:153-163). "Both provided queries must match the same documents" (:61-62).

The bug

#
  1. LatLonDocValuesQuery.contains() (LatLonDocValuesQuery.java:244-273) builds one component per query point (:245-248), because a multi-component tree cannot answer withinPoint (ComponentTree.java:284-289).
  2. Per document it starts with answer = DISJOINT (:252) and, for every (document point, query point) pair, sets answer to any relation other than DISJOINT (:261-262); it returns answer == CANDIDATE (:266).
  3. A point component answers only CANDIDATE or DISJOINT (Point2D.java:126-127), so the NOTWITHIN exit never fires and the document matches as soon as one of its points equals one query point: an OR.
  4. LatLonPoint.newGeometryQuery sends CONTAINS to makeContainsGeometryQuery, one MUST LatLonPointQuery(CONTAINS, point) per point (LatLonPoint.java:337-354): an AND. LatLonShape and XYShape also AND one clause per geometry.

The numbers

#

P1 = 22.5° N 45° E, P2 = 45° N 135° E, P3 = 22.5° S 90° W (exact on the grid); A = {P1}, B = {P2}, C = {P1, P2}, D = {P3}. CONTAINS(P1): [A, C] on both paths. CONTAINS(P1, P2): points [C], doc values [A, B, C], the same as INTERSECTS(P1, P2). With 2,000 more one-point documents (alternately at P1 and P2): points and the wrapper alone [C], doc values 2,003 hits instead of 1, FILTER(id:A) + FILTER(wrapper) [A], wrapper explain(A).isMatch() true. The same on main and 10.5.2 (assertions on and off), 10.0.0 and 9.12.3.

Exposure and likelihood303 words
  • Who is exposed. Applications that call newSlowGeometryQuery(field, CONTAINS, p1, p2, ...) directly (for example on a field with doc values but no points index), or the documented pair IndexOrDocValuesQuery(LatLonPoint.newGeometryQuery(...), newSlowGeometryQuery(...)) when a selective lead clause makes it run the doc-values side, or explain()/matches() of that pair, which always use the doc-values side, so explain() can report a match that search() does not return.
  • Default, not opt-in. Default IndexWriterConfig, codec and searcher; both factories are public and not deprecated (IndexOrDocValuesQuery is @lucene.experimental). Four documents suffice for the doc-values query alone; the wrapper runs the doc-values side only under a lead clause more than 8 times cheaper than the points query (exactly: cost() >>> 3 > leadCost).
  • What you see. Extra hits, silently: documents that hold some but not all of the query points. The doc-values CONTAINS(P1, ..., Pk) returns the INTERSECTS hits. Documents that hold all points still match.
  • Query cache. A cached entry is built from the points side (LRUQueryCache.java:609 with IndexOrDocValuesQuery.java:196-201), so where a query cache is in use the same query can change its answer once it is cached (read from the code, not executed). That needs a cache configured explicitly (main's IndexSearcher has none by default), a segment the cache accepts (the default LRUQueryCache skips segments under 10,000 documents) and a query used often enough for the caching policy; neither repro index qualifies.
  • Not affected. Single-point CONTAINS, the other relations, the points-only query; XYDocValuesField has no relation-taking factory.
  • How likely. Rare: "documents that hold all of these locations" is a niche query, and the searches of 2026-10-27 found no user report since 8.8.0. A downstream remark (code reading only, not executed): one downstream search engine builds exactly this pair for its geo-point field and uses the doc-values query alone for doc-values-only fields.

Why it is a bug, not intended

#
  • The javadoc pairs it with LatLonPoint#newGeometryQuery in an IndexOrDocValuesQuery, which requires: "Both provided queries must match the same documents".
  • LatLonPoint, LatLonShape and XYShape all add one MUST clause per CONTAINS geometry; the commit that added both paths says "Equivalent to LatLonShape".
  • Read as OR, the doc-values CONTAINS is just INTERSECTS; no test sends more than one CONTAINS point.
The full argument193 words
  • The pairing is documented. LatLonDocValuesField.java:232-238: "It is best used wrapped in an {@link IndexOrDocValuesQuery} alongside a {@link LatLonPoint#newGeometryQuery(String, ShapeField.QueryRelation, LatLonGeometry...)}". IndexOrDocValuesQuery.java:61-62: "Both provided queries must match the same documents and give the same scores." The code relies on it: "Both index and dv query should return the same values" (:212-213).
  • CONTAINS over several geometries is an AND elsewhere. LatLonPoint.java:343-354, LatLonShape.java:354-370 and XYShape.java:263-267 add one MUST clause per geometry.
  • One commit added both. 14009f4424d (LUCENE-9641, 2021-01-08): "Equivalent to LatLonShape, LatLonPoint can be queried now using spatial relationships." It added the AND and the OR together, with no comment on a difference; issue #10680 states the goal that LatLonShape and LatLonPoint return the same results. contains() is unchanged since.
  • The author's intent elsewhere. The LUCENE-9641 author's downstream test expects 0 hits for CONTAINS(MULTIPOINT(a, b)) on a document holding only a (it runs the points side). Their open PR #12162 documents CONTAINS for newSlowGeometryQuery as "one or more points of the field matches all the provided LatLonGeometry".
  • The test gap. BaseSpatialTestCase.java:562-565 sends only queryPoints[0] for CONTAINS, so the two paths were never compared with several points. No test asserts the OR.
The devil's-advocate check233 words

The strongest case for "intended": LatLonPoint.newGeometryQuery's javadoc says "@return query matching points within at least one geometry" (LatLonPoint.java:322), which reads like OR; the pairing is only "best used"; a committer has said relations make little sense for points; and no javadoc spells out multi-point CONTAINS. Independent reviews by another model family (OpenAI GPT-5.6, refute lens and intended lens) rated this moderate; the devil's advocate rejected it point by point; the adjudication called it weak. A maintainer may also cite the IndexOrDocValuesQuery class note ("only works well with point range/exact queries and their equivalent doc values queries", IndexOrDocValuesQuery.java:51-52).

Why it fails: that @return line dates from LUCENE-9552, before relations existed, and the same method builds an AND for CONTAINS, so it does not follow it either. The javadoc names the exact counterpart with the same arguments, and the wrapper forbids operands that disagree. The committer's remark is about API design; both factories are public and shipped since 8.8.0. Under OR, CONTAINS would duplicate INTERSECTS. The IndexOrDocValuesQuery class note is about performance ("works well") and does not relax "must match the same documents"; newSlowGeometryQuery's own javadoc recommends this wrapping. #12162's wording is not literally the per-point AND (read literally, one document point equal to every query point, it would reject C too), but neither reading admits A or B, which hold only one of the two points. Verdict: a defect.

Suggested fix

#

Recommended Require every query point in contains() (validated)

In LatLonDocValuesQuery.contains(), remember for each query point whether some document point equals it, and match only when all are found: one reused boolean[] and a counter, +11/-6. The new test passes 2 of 2, and 31 existing LatLon, XY and IndexOrDocValuesQuery suites (224 tests) pass with assertions on and off.

final boolean[] contained = new boolean[component2Ds.size()];
// in matches():
Arrays.fill(contained, false);
int numContained = 0;
// for each document point (lat, lon) and each query component c:
Component2D.WithinRelation relation = component2Ds.get(c).withinPoint(lon, lat);
if (relation == Component2D.WithinRelation.NOTWITHIN) {
  return false;
} else if (relation == Component2D.WithinRelation.CANDIDATE && contained[c] == false) {
  contained[c] = true;
  numContained++;
}
// after the loop:
return numContained == contained.length;

Trade-offs

Same loop and cost as today plus an Arrays.fill of k booleans per document (k = number of query points); no allocation per document. The array is created once per scorer supplier (per segment or intra-segment partition, and also when IndexOrDocValuesQuery then runs the points side, since it creates both suppliers first); the stock code already allocates a list and one Component2D per query point there. One-point CONTAINS behaves as before. The diff keeps the full loop; it could return true as soon as every point is found, since only Point geometries reach contains() and they never return NOTWITHIN. No benchmark was run.

Downstream note

#

An application that uses a multi-point CONTAINS on a point field as a restriction ("only documents that hold all of these locations") also gets documents that hold just one of them whenever the doc-values side runs.

How it was found

#

A bounded-exhaustive differential check: the same grid-exact documents were indexed as shapes, as points and as doc-values points, queried with all four relations, and compared with an exact geometry reference (JTS). Only the doc-values point path disagreed, on multi-point CONTAINS; the cause was then read from the code.

The method in full183 words

Method: bounded-exhaustive differential testing against an exact reference (the hunt's semi-formal tier).

  • The hunt unit compared Lucene's shape and point relation queries with JTS 1.20 DE-9IM relations on the decoded coordinates, with a strict and a permissive boundary band per relation, so a boundary convention cannot show up as a bug.
  • Inputs: lattices of 6 x 6 grid-exact coordinates in nine families (around the origin, the poles and the antimeridian, and XY), every point, segment and small polygon of the lattice plus random ones, multi-part and multi-point documents, and 2-3-point CONTAINS queries, each document indexed as LatLonShape, LatLonPoint and LatLonDocValuesField.
  • At scale 1 the doc-values point path disagreed with the reference and with both index paths in 606 (document, query) pairs in six of the seven LatLon families (490 with a multi-point document, 116 with a one-point document) and 585 in the dateline family, all multi-point CONTAINS; the index paths agreed with the reference. The root cause was read from LatLonDocValuesQuery.contains() and reduced to a public-API JUnit.
  • The same harness also explained every other mismatch by known bugs or documented conventions.

Bug record

LFV-701, snapshot of 2026-10-29

Registry title
LatLonDocValuesField.newSlowGeometryQuery with CONTAINS and two or more Point geometries matches documents that hold only some of the query points, while its documented IndexOrDocValuesQuery partner LatLonPoint.newGeometryQuery requires all of them
Area
core / document: LatLon point geometry queries (LatLonDocValuesQuery CONTAINS on the doc-values path vs LatLonPoint.newGeometryQuery, and their IndexOrDocValuesQuery pairing)
Priority
Medium, rank 168: The core LatLonDocValuesField CONTAINS query over two or more points silently computes OR instead of AND since 8.8.0, but multi-point CONTAINS on a point field is niche and no user report was found, so it follows the spatial3d wrong-result row LFV-247 and precedes the spatial-extras rows.
Impact class
silent wrong results
Impact note
Applications that run a CONTAINS geometry query with two or more Point geometries against a LatLonDocValuesField (default IndexWriterConfig, codec and searcher, any index size, -ea and -da, every release from 8.8.0 to 10.5.2 and main) get extra hits, documents that hold some but not all of the query points, whenever the doc-values side runs: newSlowGeometryQuery on its own (for example on a doc-values-only field), IndexOrDocValuesQuery(LatLonPoint.newGeometryQuery, newSlowGeometryQuery) under a selective lead clause, and IndexOrDocValuesQuery's explain(); the points-only query is correct, documents that hold all of the points still match, and single-point CONTAINS and the other relations are not affected.
Summary
You index points with LatLonPoint and LatLonDocValuesField and ask for the documents that contain both P1 and P2 (CONTAINS with two Point geometries); a document that holds only P1 must not match, and LatLonPoint.newGeometryQuery, which builds one MUST clause per query point, indeed matches none. LatLonDocValuesField.newSlowGeometryQuery, which its javadoc says to pair with that query in an IndexOrDocValuesQuery (whose two queries 'must match the same documents'), accepts a document as soon as any one of its points equals any one query point, so it computes an OR instead of an AND.
