CheckIndex.doCheck with a hand-built CheckIndex.Options checks no segment and reports a corrupt index as clean

doCheck with an Options from new CheckIndex.Options() (plus the required setOut) skips every segment and returns 0 ("clean") for a broken index: the constructor's segment list starts empty, and only parseOptions turns empty into "every segment". Every release since 5.5.0; the command-line tool and checkIndex() are unaffected.

The finding in 30 seconds

#

CheckIndex.Options.onlySegments names the segments to check; null means every segment. The public constructor starts it as an empty list instead, and only parseOptions, the command-line parser, turns empty into null. doCheck hands the empty list to checkIndex, which then checks none of the segments and calls the index clean.

  1. Index 1 document into one segment, then delete that segment's stored-fields file _0.fdt. checkIndex() on this index says clean=false, 1 bad segment, 1 document to lose.
  2. Check the same index the other documented way: opts = new CheckIndex.Options(), opts.setOut(...), then checker.doCheck(opts). You expect 1, since its javadoc says "@return 0 iff the index is clean, 1 otherwise".
  3. You get 0. The log says Checking only these segments:: with nothing after it, then No problems were detected with this index.
  4. Why: new Options() sets onlySegments to an empty list [], not null. doCheck passes it to checkIndex(List) unchanged, which reads any non-null list as "check only these" and skips 1 of 1 segments. Only parseOptions (the command line) maps [] to null, meaning every segment.
  5. The caller cannot work around it through Options: onlySegments is package-private and setOut is the only public setter.

Who is affected

#

Code that checks an index with doCheck and an Options from new CheckIndex.Options(), for example as a health gate: nothing the per-segment check would find is reported (commit-level problems still give 1). Opt-in and rare: no in-tree caller; the searches found no public downstream one. The command line, parseOptions and checkIndex() callers are unaffected. Every release since 5.5.0; priority Low.

Mechanism, terms and numbers546 words

CheckIndex.Options has a public constructor and one public setter, setOut. Its package-private field onlySegments starts as an empty list (CheckIndex.java:4675 at 5adff78bb168), and only parseOptions turns an empty list into null, which checkIndex(List) reads as "check every segment" (:4871-4873). doCheck passes the field unchanged (:4896), so with an Options from the constructor checkIndex treats [] as a selection, skips every segment (:828, :875, :900), finds no bad segment, sets clean = true (:933-934) and prints "No problems were detected with this index."; doCheck returns 0 (:4927) although its javadoc promises "0 iff the index is clean, 1 otherwise" (:4884). On an index whose only segment has lost _0.fdt, checkIndex() reports 1 bad segment and doCheck with a constructor-built Options returns 0. The commit-level checks still run: an unreadable segments_N or .si still gives 1 through missingSegments (:4898-4900; executed with _0.si deleted), and the segment-name counter is still checked; only the per-segment check is skipped. The command-line tool, parseOptions callers and checkIndex() callers are not affected. It came with SOLR-7928 (2015) and is in every release from 5.5.0 through 10.6.0 and on main.

Terms

#
  • CheckIndex reads every segment of the latest commit and reports what is broken. From code you call checkIndex() (every segment) or checkIndex(List) ("list of specific segment names to check", CheckIndex.java:584), which return a Status; or doCheck(Options), the command-line driver, which returns an exit code: "0 iff the index is clean, 1 otherwise" (:4884).
  • CheckIndex.Options ("Run-time configuration options for CheckIndex commands.", :4669) has a public "Sole constructor." (:4680-4681) and one public setter, setOut (:4693-4696). Its fields, including onlySegments, are package-private. parseOptions(String[]) (:4781) fills one from command-line arguments; -segment X adds X to onlySegments (:4804).
  • Status.partial: "True if we checked only specific segments (checkIndex(List) was called with non-null argument)" (:177-181).

Exposure and likelihood196 words
  • Who is hit. Code that runs CheckIndex through doCheck(Options) with an Options built by the public constructor plus setOut. For it, doCheck returns 0 and prints "No problems were detected with this index." however damaged the segments' data files are.
  • Default vs opt-in. Opt-in: an uncommon entry point of the @lucene.experimental class (CheckIndex.java:110). The only in-tree caller of doCheck is the command-line doMain, which builds its Options with parseOptions (:4704, :4733). Solr's CheckHdfsIndex uses parseOptions; Elasticsearch, OpenSearch and Luke call checkIndex() or checkIndex(null).
  • Effect. A silent false "clean", not a loud error. Nothing is written (doExorcise cannot be set from outside the package). Commit-level problems still give 1: an unreadable segments_N or .si sets missingSegments (:670-716, :4898-4900; executed with _0.si deleted), and an invalid segment-name counter makes the index not clean (:945-955). A directory with no segments_N throws IndexNotFoundException (:632-637).
  • Scale. Any index: with the default Options, no segment goes through the per-segment check.
  • Likelihood: rare. It needs that caller and an index that is actually corrupt; the searches found no public code that builds Options by hand.

Why it looks unintended

#
  • doCheck promises "@return 0 iff the index is clean, 1 otherwise", with no precondition on how its Options were built; Options() is public.
  • The caller never chose an empty selection: it cannot change onlySegments on a constructor-built Options, and parseOptions never yields one.
  • Lucene's own command line maps "no -segment given" to null, every segment.
The full argument197 words
  • The contract. doCheck: "Actually perform the index check ... @return 0 iff the index is clean, 1 otherwise" (CheckIndex.java:4881-4884). Options: "Run-time configuration options for CheckIndex commands." (:4669), "Sole constructor." (:4680-4681).
  • Status.partial records that only specific segments were checked (checkIndex(List) "was called with non-null argument", :177-181); doCheck ignores it. A caller outside the package cannot change onlySegments on a constructor-built Options, and parseOptions never yields an empty selection (no -segment gives null; -segment without a name throws, :4799-4802), so the empty selection is never the caller's choice.
  • Intended meaning of the default. parseOptions maps an empty list to null (:4871-4873); before Options existed, main did the same itself (since LUCENE-1147, 2008).
  • Tests and docs. No test builds Options by hand or calls doCheck (TestCheckIndex.java:221 only checks that parseOptions rejects bad arguments). No CHANGES or MIGRATE entry says a constructed Options checks nothing.
  • History. SOLR-7928 (2015) created Options, parseOptions and doCheck, moved the empty-to-null step from main into parseOptions only, and kept new ArrayList<>() as the field initializer. Nobody in that thread discussed the default or a hand-built Options.
The devil's-advocate check192 words

The strongest case for "intended": Options is the command-line holder. In SOLR-7928 the explicit public constructor was added only for the javadoc lint ("Added an explicit 0-arg constructor (there are other place[s] in the code that do that for javadoc)"), the fields were kept package-private on purpose, on a readable index doCheck without setOut throws NullPointerException, programmatic callers should use checkIndex(), and checkIndex(List.of()) checking nothing is what that method's javadoc says. This reading is credible, and a maintainer could reasonably answer with documentation rather than a code change.

Why it still fails as a reason to keep the behaviour: none of that is documented. Options() and doCheck(Options) are public and javadoc'd, nothing says an Options must come from parseOptions, and doCheck promises "0 iff the index is clean" unconditionally. The history explains how the trap arose, not why a false "clean" is acceptable; the defect is doCheck feeding checkIndex an empty list the caller never chose, not checkIndex(List.of()) itself. An intended-behaviour review by another model family (OpenAI GPT-5.6) agreed: "Historical intent explains the accidental API shape but does not override its published contract" (real bug, maintainer pushback risk medium).

Suggested fix

#

Recommended In doCheck, treat an empty onlySegments like null

In doCheck, pass null (every segment) when onlySegments is empty, as parseOptions already does: a one-line change. Validated with gradle: the repro passes with assertions on and off, TestCheckIndex and TestAllFilesCheckIndexHeader pass, and so does :lucene:core:check -x test.

-    Status result = checkIndex(opts.onlySegments);
+    // empty (the default of new Options()) means all segments, as after parseOptions
+    Status result =
+        checkIndex(
+            opts.onlySegments == null || opts.onlySegments.isEmpty() ? null : opts.onlySegments);

Downstream note

#

Downstream tools that wrap doCheck with their own new CheckIndex.Options(), for example a health check after copying or restoring an index, should call checkIndex() or build the Options with parseOptions until a fix lands.

How it was found

#

A proof-obligation audit of CheckIndex's doCheck/Options contract took "doCheck returns 1 for an index with a corrupt segment, whichever public way its Options were built" as an obligation. The constructor path breaks it: its empty segment list reaches checkIndex unchanged. A one-test JUnit witnessed it on main; independent checks reproduced it with their own tests.

The method in full137 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro), on main 5adff78bb168, 2026-11-03.

  • The obligation: doCheck(opts) returns 1 for an index with a corrupt segment (CheckIndex.java:4884), for every opts a caller can build through public API: parseOptions(args) or new Options() plus setOut.
  • Discharging it for new Options() fails: the field default [] (:4675) is never normalised outside parseOptions (:4871-4873), and checkIndex(List) skips every segment not in a non-null list.
  • A one-test JUnit witnessed it on main with assertions on and off; a probe on the same corrupt index showed exit 1 through parseOptions and clean=false through checkIndex(). An independent reproducer wrote its own test from the claim alone, a devil's-advocate verifier argued intended behaviour, and an adjudication re-ran both tests with new seeds.
