The default term-vectors writer counts its int[] position and offset buffers at one byte per entry, so IndexWriter under-counts buffered term-vector heap

The default term-vectors writer reports its buffered positions and offsets to IndexWriter at one byte per int instead of four, so IndexWriter flushes later than configured. With 65,536 term-vector positions in one document, IndexWriter reports 356,924 bytes, below the 786,432 those buffers need; data and results stay correct.

The finding in 30 seconds

#

IndexWriter starts a flush, of its largest thread's buffered documents, when the heap that all buffered documents and deletes use, summed from each component's ramBytesUsed(), reaches ramBufferSizeMB (16 MB by default); each thread also has a 1945 MB hard limit. For fields with term vectors, the term-vectors writer is one of those components, and it reports its biggest buffers in the wrong unit.

  1. Index one document whose field stores term vectors with positions and offsets, text: the word "x" 65,536 times (default codec and IndexWriterConfig).
  2. The term-vectors writer keeps the not-yet-written positions, start offsets and lengths in int[] buffers, here 73,728 entries each, 888,896 bytes in all with the payload-length buffer. You expect IndexWriter.ramBytesUsed() to be at least 786,432.
  3. You get 356,924 for the whole IndexWriter. With the fix it reports 1,023,612, so 666,688 bytes were missing.
  4. Why: the writer's ramBytesUsed() adds positionsBuf.length + startOffsetsBuf.length + lengthsBuf.length + payloadLengthsBuf.length, array lengths, as if each int took one byte.
  5. Effect: IndexWriter decides when to flush from this number, summed over its threads, so flushes come later than ramBufferSizeMB intends. With about a million positions in one document, 10.6 MB go uncounted. Index data and results stay correct.

Who is affected

#

Any application with a term-vector field that stores positions or offsets, on the default codec, through plain IndexWriter.addDocument (FastVectorHighlighter needs them). With positions and offsets, about 9 bytes per buffered position go uncounted: about 12 KB per fresh writer, megabytes once a pending chunk holds about 10^5 positions, typically one very long document. Data and results stay correct.

Mechanism, terms and numbers589 words

Since 8.7.0 (LUCENE-9514), IndexWriter adds the term-vectors writer's ramBytesUsed() to each indexing thread's RAM, so that flush and stall decisions see the heap it holds (IndexingChain.java:1792-1797, CHANGES.txt:5627-5629 at 5adff78bb168). The default writer, Lucene90CompressingTermVectorsWriter, keeps the positions, start offsets, lengths and payload lengths of not-yet-written documents in four int[] buffers (:225), but its ramBytesUsed() adds their .length values (:993-1003), as if each int took one byte, so three quarters of that memory is never counted. With one document of 65,536 term-vector positions and offsets, IndexWriter.ramBytesUsed() is 356,924 bytes, below the 786,432 the three position/offset arrays need at minimum; with RamUsageEstimator.sizeOf per buffer it is 1,023,612. The stored-fields writer, added to the same accounting a week earlier, multiplies by Integer.BYTES. No index data or search result is wrong; IndexWriter only flushes later than ramBufferSizeMB and the per-thread hard limit intend.

The bug, step by step

#
  1. Buffers. Lucene90CompressingTermVectorsWriter declares private int[] positionsBuf, startOffsetsBuf, lengthsBuf, payloadLengthsBuf; (:225 at 5adff78bb168), allocates each as new int[1024] (:295-298) and grows them as positions, start offsets and lengths are buffered, and payload lengths only for fields with payloads (addPosition :194-217, addProx :734-788). Nothing shrinks them until the segment flushes.
  2. A pending chunk keeps all its positions. A chunk is written only once its term suffixes and payload bytes reach 4 KiB (finishDocument appends the payload bytes to the suffixes, :323-329) or it holds 128 documents (:379-381; Lucene90TermVectorsFormat.java:170). Until then the positions of all its documents sit in the buffers at once: one long document with few distinct terms is enough, and up to 128 shorter ones add up the same way. Writing a chunk clears the pending documents but keeps the grown buffers (:429-434).
  3. Through IndexWriter. TermVectorsConsumerPerField calls addProx(freq, ...) once per term (TermVectorsConsumerPerField.java:119); positionsBuf grows through ArrayUtil.grow and startOffsetsBuf and lengthsBuf through ArrayUtil.growExact(..., ArrayUtil.oversize(n, 4)); both give ArrayUtil.oversize(n, 4) = 73,728 entries for n = 65,536. Without payloads, payloadLengthsBuf keeps its 1,024.
  4. The count. ramBytesUsed() (:993-1003) returns positionsBuf.length + startOffsetsBuf.length + lengthsBuf.length + payloadLengthsBuf.length + termSuffixes.ramBytesUsed() + payloadBytes.ramBytesUsed() + lastTerm.bytes.length + scratchBuffer.ramBytesUsed(): four element counts of int[] next to four byte counts.
  5. Where the number goes. TermVectorsConsumer creates the writer when a thread first indexes a term-vector field and sets accountable = writer (TermVectorsConsumer.java:103-109); IndexingChain.ramBytesUsed() adds it (IndexingChain.java:1795); DocumentsWriterPerThread.ramBytesUsed() adds the chain (DocumentsWriterPerThread.java:718-723). DocumentsWriterFlushControl adds each thread's change to activeBytes, the RAM of all active threads (DocumentsWriterFlushControl.java:244); the flush policy compares activeBytes plus buffered deletes with ramBufferSizeMB and marks the largest thread for flushing (FlushByRamOrCountsPolicy.java:45-55, :84); the per-thread hard limit checks the thread's own total (DocumentsWriterFlushControl.java:247). IndexWriter.ramBytesUsed() reports delete bytes plus the committed bytes of all threads (IndexWriter.java:796-799, DocumentsWriter.java:748-750, DocumentsWriterFlushControl.java:513-516): with one thread and no deletes, as here, this thread's total.

Exposure and likelihood262 words
  • Reach. The default Lucene104Codec uses Lucene90TermVectorsFormat (Lucene104Codec.java:71). Term-vector positions and offsets are an opt-in field option; the FastVectorHighlighter requires them and advertises itself as "fast for large docs" (vectorhighlight/package-info.java:24, :28).
  • Effect. ramBufferSizeMB (default 16 MB, IndexWriterConfig.java:83) is compared with the RAM of all threads, so flushes come later than it intends, and a thread reaches the per-thread hard limit (default 1945 MB, :93) later. With the default buffer, one document of about a million term-vector positions with offsets holds 10.6 MB the flush policy does not see (measured).
  • Scale. 3 bytes per int of buffer capacity, for each buffer the field uses: per buffered position about 3 bytes with positions only, 6 with offsets only, 9 with both (about 10 with growth slack), 12 with payloads as well. About 12 KB per term-vectors writer from the start (four int[1024] counted as 4,096 bytes instead of 16,448); the writer exists once a thread indexes a term-vector field, one per thread's segment. Megabytes once one pending chunk has buffered on the order of 10^5 positions or more: typically one very long document, but many repetitive shorter ones in one chunk do it too (127 documents of 8,192 positions: 9,956,416 bytes uncounted, measured). The gap then lasts until the segment flushes.
  • Not a cap, before or after the fix. ramBufferSizeMB stays an indicator of when to flush, and a flush may release only part of the buffer (LiveIndexWriterConfig.java:167-181); the fix makes that indicator count these buffers correctly.
  • Not affected. Indexed data, segment files and search results.

Why it looks unintended

#
  • Accountable#ramBytesUsed returns "an estimate of the JVM heap memory used by this object in bytes"; LUCENE-9514 added this method so IndexWriter's flush and stall decisions count the writer's heap.
  • The same return adds real byte counts next to the int[] lengths.
  • The stored-fields writer, added a week earlier by the same author, multiplies its int[] lengths by Integer.BYTES.
The full argument143 words
  • Contract. "Returns an estimate of the JVM heap memory used by this object in bytes" (util/Accountable.java:35).
  • Purpose. The introducing commit 8f895d90755 (LUCENE-9514): "TermVectorsWriter might consume some heap space memory that can have a significant impact on decisions made in the IW if writers should be stalled or DWPTs should be flushed if memory settings are small in IWC and flushes are frequent"; CHANGES, under 8.7.0: "to ensure that it's heap consumption is taken into account when IndexWriter stalls or should flush DWPTs" (CHANGES.txt:5627-5629).
  • Sibling. 98e55f0ea82 (LUCENE-9511, 2020-09-08, same author) counted the stored-fields writer's int[] as length * Integer.BYTES; #11923 later widened it to (long) Integer.BYTES (Lucene90CompressingStoredFieldsWriter.java:726-730) and left the term-vectors method alone.
  • No record of a choice found. We found no comment, test, CHANGES or MIGRATE entry, or review comment on apache/lucene-solr#1847 that mentions counting per element.
The devil's-advocate check171 words

The strongest case for "intended": Accountable is @lucene.internal (Accountable.java:30) and promises only "an estimate", the writer is @lucene.experimental (Lucene90CompressingTermVectorsWriter.java:63), and the RAM-buffer docs say an IndexWriter "can consume a significantly larger amount of memory than the given RAM limit since this limit is just an indicator when to flush" (LiveIndexWriterConfig.java:167-171).

Why it fails: an estimate may skip headers or small objects; counting the dominant owned payload in element units is a 4x unit error. The same javadoc says "the writer will flush whenever buffered documents and deletions use this much RAM" (:162-163). The javadoc does not document this per-element accounting; concurrent and partial flushing (:167-181) separately mean the setting is not a hard heap cap. The tags limit API stability, not the correctness of a number IndexWriter acts on, and the trigger is ordinary IndexWriter.addDocument. The independent reviewer from another model family rated the intended case weak in both its refute and its intended-behaviour pass. Verdict: a real Low bug.

Suggested fix

#

Recommended A. RamUsageEstimator.sizeOf per buffer (validated)

Count each buffer with RamUsageEstimator.sizeOf(positionsBuf) (and the same for the other three) instead of .length: one file, five lines. The repro passes with assertions on and off, and 82 term-vector and flush-policy tests pass. Alternative: length * (long) Integer.BYTES, the stored-fields writer's idiom.

-        + lengthsBuf.length
-        + payloadLengthsBuf.length

Trade-offs

Counts the array headers too, as Lucene's other accounting does. ramBytesUsed() is called after each document (DocumentsWriterFlushControl.java:216; the change is committed once it is large enough, :218-223); the fix adds four small computations, nothing per position. Writers with many term-vector positions now report more and flush earlier, closer to their configured RAM, which is the point; ramBufferSizeMB stays an indicator, not a heap cap.

Downstream note

#

Products that index very long documents into term-vector fields with positions or offsets, with a heap sized close to the RAM buffer, can use noticeably more heap than their flush settings suggest until it is fixed.

How it was found

#

A proof-obligation audit of the term-vectors writer's Accountable#ramBytesUsed contract: the method must report the heap it holds in bytes. Checking each term of its sum against the field types showed four int[] lengths added as bytes. A one-method JUnit test through IndexWriter.addDocument witnessed it.

The method in full71 words

The obligation came from the Accountable#ramBytesUsed javadoc and the purpose stated in LUCENE-9514, checked term by term against the declared types of the summed fields (:225). The first witness drove the writer directly with one term of 2^20 positions (ramBytesUsed()=3217630 while three buffered arrays need at least 12,582,912 bytes, main with assertions on and off and 10.6.0); the minimal repro then showed the same through public IndexWriter API.

Impact class

Impact note
Any application that stores term vectors with positions or offsets on the default codec (8.7.0 through 10.6.0 and main) has each indexing thread's RAM under-counted by 3 bytes per int of these buffers, so that thread flushes, and reaches its per-thread hard limit, later than configured; the gap is about 12 KB for a fresh writer and grows to megabytes only after one chunk has buffered a very long document (the buffers never shrink until the segment flushes); no index data or search result is wrong.
Summary
You index documents with a field that stores term vectors with positions or offsets (default codec and IndexWriterConfig) and expect IndexWriter's RAM accounting, which since 8.7.0 adds the term-vectors writer's ramBytesUsed() so that flush and stall decisions see its heap, to count the writer's buffered positions and offsets in bytes. Instead Lucene90CompressingTermVectorsWriter.ramBytesUsed() adds the lengths of its four int[] buffers (positions, start offsets, lengths, payload lengths) as if each entry took one byte: with one pending document holding one term with 2^20 positions and offsets, the writer reports 3,217,630 bytes while those three int[] alone take at least 12,582,912 bytes (with the one-line fix it reports 12,867,380). Indexed data and search results are unaffected; IndexWriter only flushes later than ramBufferSizeMB and the per-thread hard limit intend.
