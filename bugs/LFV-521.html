DirectoryTaxonomyWriter gives an existing category a second ordinal after an IOException in addCategory

If DirectoryTaxonomyWriter hits an IOException while opening its internal reader in addCategory, it keeps trusting its cache, so re-adding an existing label creates a second ordinal: dim/v0 ends up at ordinals 2 and 4001, counted 1 instead of 2. commit() persists it, and CheckIndex reports the taxonomy clean.

The bug in 30 seconds

#

The taxonomy writer gives every facet label a number, its ordinal, and caches label-to-ordinal entries. A flag says the cache holds every label, so a cache miss can be taken to mean "new label". The bug: after a failed reader open, the writer keeps trusting that flag, or its old reader.

  1. Index 3,998 documents with FacetField("dim", "v0") to ("dim", "v3997") through FacetsConfig.build and a default DirectoryTaxonomyWriter. Its label cache (4,000 entries) is now full; dim/v0 has ordinal 2.
  2. The next new value evicts the 1,335 least recently used cache entries, dim/v0 among them, so the writer refreshes its internal reader. Opening a segment file fails once with an IOException, as a failed memory map would. IndexWriter stays open; the application skips that document.
  3. You index one more document with dim/v0 and expect its count to be 2: addCategory returns the existing ordinal of a label that is already there.
  4. Instead the writer's "cache is complete" flag is still set, because it is cleared only after the refresh succeeds. The miss counts as new: dim/v0 gets ordinal 4001, and getSpecificValue("dim", "v0") returns 1.
  5. commit() persists both ordinals and CheckIndex reports the taxonomy clean. A second path: once an existing taxonomy is read into the cache, a failed reader open while adding the label new makes the retry return 14 instead of 13.

Who is affected

#

Applications that index taxonomy facets with a default DirectoryTaxonomyWriter and keep using it after addCategory or FacetsConfig.build threw an IOException (skip or retry the document). The failure must hit the writer's internal reader open, which is rare. The duplicate it leaves is silent: CheckIndex misses it, and once committed it stays until the taxonomy is restored or rebuilt.

Mechanism, terms and numbers674 words

DirectoryTaxonomyWriter keeps a label-to-ordinal cache (LruTaxonomyWriterCache(4000) by default since 9.5.0) and a flag, cacheIsComplete, that lets it treat a cache miss as a new label. When a put evicts entries, addToCache first refreshes the writer's near-real-time reader and only then clears the flag. If that refresh throws an IOException, for example because a segment file cannot be opened, the flag stays set although a third of the cache was just evicted, and IndexWriter stays open. The next addCategory of an evicted label indexes it again under a new ordinal, and commit() persists both: dim/v0 at ordinals 2 and 4001, facet count 1 instead of 2, CheckIndex clean. A second path: after an existing taxonomy is read into the cache, addCategoryDocument indexes a new category before it opens a reader for the parent array; if that open throws, a retry gives the category a second ordinal (13 and 14). Every release from 3.4.0 (with an evicting LRU cache) to 10.5.2 and main is affected; with the default writer from 4.1.0 (second path) and 9.5.0 (first path).

Terms

#
  • Taxonomy and ordinal. Taxonomy facets store each label, such as dim/v0, once in a side index, as one document; its document number is the label's ordinal. Documents in the main index store ordinals, and facet counts are kept per ordinal. TaxonomyWriter.addCategory must return the existing ordinal of a label that is already there.
  • Cache and the "complete" flag. DirectoryTaxonomyWriter caches label-to-ordinal entries. The default LruTaxonomyWriterCache(4000) evicts: when a put makes it exceed 4,000 entries, it drops the least recently used ones down to 2,666, so the 4,001st entry evicts 1,335. While the flag cacheIsComplete is set, a cache miss means "new label" and nothing is looked up on disk.
  • The writer's reader. To answer a miss when the cache is not complete, the writer looks the label up through a near-real-time reader of its own index. After an eviction it must refresh that reader, because evicted labels may have been added after the reader was opened.

Site A: the refresh after an eviction (default writer since 9.5.0)

#
  1. addToCache (DirectoryTaxonomyWriter.java:484-494): cache.put reports an eviction; the writer calls refreshReaderManager() (:491) and only then sets cacheIsComplete = false (:492).
  2. The refresh reaches IndexWriter.getReader, which flushes and then opens the new segments. If opening a file throws an IOException, getReader rethrows it without closing IndexWriter (it treats only an Error as tragic, IndexWriter.java:711-721). The flag stays set and the reader stays old.
  3. The next addCategory(dim/v0) misses in the cache; findCategory returns the miss at once because the flag is set (:327), and the label is indexed again as ordinal 4001.
  4. Clearing the flag first is not enough: the on-disk lookup and the cache fill (perhapsFillCache) would then use the old reader, which does not see the evicted labels either. Nothing on the addCategory path refreshes it until the next eviction.

Site B: the reader open after a complete cache fill (default writer since 4.1.0)

#
  1. A reopened taxonomy reads all its labels into the cache after 11 misses; if they all fit, it sets the flag and closes its reader (:652-662).
  2. The next new label is indexed (:468) before the writer re-opens a reader for the parent array (getTaxoArrays(), :475); the cache update comes last on purpose (:477-479, LUCENE-4596). If that open throws, the label is in the index but not in a cache that is still marked complete, and a retry indexes it again: new at 13 and 14.

The numbers

#

Default writer and FacetsConfig: 3,998 values fill the cache (root, dim and 3,998 values); the 3,999th document's refresh fails and the document is skipped; one more dim/v0 document is indexed. Committed taxonomy: 4,002 ordinals, dim/v0 at 2 and 4001; FastTaxonomyFacetCounts.getSpecificValue("dim", "v0") = 1 instead of 2. Writer view: addCategory("l0") returns 4001 instead of 1. Site B: the retry returns 14 instead of 13. Same with assertions on and off, on main and 10.5.2.

Exposure and likelihood371 words
  • Who is exposed. Users of the opt-in taxonomy facet module with the default writer constructor (and the IndexWriterConfig it builds itself), cache and codec, on any Directory, who continue after a failed addCategory or FacetsConfig.build, as ordinary per-document error handling does: the wrapped IndexWriter stays open, and no javadoc asks for a rollback (none explicitly promises reuse either). A read-only code search of the default branches of Elasticsearch, OpenSearch and Solr found no use of DirectoryTaxonomyWriter; custom applications that embed the module are the ones exposed.
  • What triggers it. A non-Error IOException exactly while the writer opens its reader inside addCategory: the refresh after an eviction (with the default cache about once per 1,335 new categories once it is full; a probe saw 13 reader opens in 20,000 addCategory calls), or the first reader open after an existing taxonomy that fits in the cache was read into it. Realistic causes: a failed memory map (MMapDirectory reports it as a plain IOException) or running out of file handles. A failure in the flush itself closes IndexWriter instead; every repro injects the failure in the reader open after a successful flush. Labels alone never cause it (0 duplicates in 80,000 adds and re-adds).
  • Effect. One label, two category documents, persisted by commit(); CheckIndex reports the taxonomy clean. Rolling back both writers before the next commit discards it (with every other uncommitted change); after a commit it takes a clean backup or a rebuild. Counts for the label are split, getAllChildren lists it twice, and when the evicted label is a dimension, getAllDims lists the dimension twice. Drill-down matching stays correct (it uses path terms): 0 mismatches over 3,998 labels. Merging the damaged taxonomy with addTaxonomy after a one-segment merge mapped the second copy to ordinal 0, or threw EOFException with DiskOrdinalMap.
  • Scale. None needed: the first eviction comes at the 4,001st cache entry.
  • Not a separate bug. The failed call's own document is also persisted, which matches IndexWriter's "this document may not have been added" wording. In the end-user scenario FacetsConfig.build throws before the main index's addDocument, so the taxonomy then holds a category (dim/v3998) that no main-index document uses.

Why it is a bug, not intended

#
  • TaxonomyWriter.addCategory: "If the category was already present in the taxonomy, its existing ordinal is returned." No exception carve-out.
  • The cache javadoc: a miss proves absence only if the cache is complete "and since then no put() returned true". Here put() returned true.
  • The writer stays open, commit() persists the duplicate, and upstream fixed this outcome as a bug before (LUCENE-4061).
The full argument362 words
  • Contract. TaxonomyWriter.java:51-53: "If the category was already present in the taxonomy, its existing ordinal is returned." TaxonomyWriterCache.java:30-32 (the same rule in other words at :55-58): the caller "can only infer that the category doesn't exist if it knows the cache to be complete (because all the categories were loaded into the cache, and since then no put() returned true)". The writer's own comments: the cache "becomes incomplete ... if a put() to the cache ever returned true" (DirectoryTaxonomyWriter.java:110-117); after an eviction "we must now refresh the reader" (:486-490); "when this method returns, we must know that the reader manager's state is current" (:497-499); "each term has exactly one document" (:366, :628-629).
  • The wrapped IndexWriter keeps working after non-fatal exceptions. It closes itself only "if you hit an Error, or disaster strikes during a checkpoint" (IndexWriter.java:162-165); after an exception in addDocument "the index will be consistent, but this document may not have been added" (:1465-1466). Nothing says the taxonomy writer must be discarded after an exception (nor, explicitly, that it may be reused: continued use is implicit); the rollback() javadoc only describes rollback (DirectoryTaxonomyWriter.java:855-859).
  • Site A is the clean case. The label that gets the second ordinal (dim/v0, l0) was added successfully long before; the failed call was for a different label.
  • Tests. No facet test injects I/O failures into the taxonomy writer, so the exception path is untested, not waived.
  • Precedent. Upstream fixed "an existing category gets a second ordinal" as a bug three times; in none did the duplicate come from a failed addCategory call: LUCENE-4061 (#5133, 2012; a statement-order bug skipped the refresh; shaie: "NoOpCache in this case simulates the case where e.g. LruTaxoWriterCache just evicts entries from it and we fail to refresh the reader, so this is a true bug"), LUCENE-4633 (#5698, replaceTaxonomy left the reader stale) and LUCENE-5048 (#6112, a huge label re-added with a different ordinal; it was reported as a NegativeArraySizeException from the old cache inside addCategory, but the second ordinal came from a short cast on the label length, not from the exception).
The devil's-advocate check233 words

Strongest case (the devil's advocate; the cross-model intended-lens reviewer rated it moderate): both classes are @lucene.experimental (TaxonomyWriter.java:47, DirectoryTaxonomyWriter.java:76); no exception-safety guarantee is documented; rollback() exists and TwoPhaseCommit frames it as the recovery tool; IndexWriter itself says a document "may not have been added" after an exception; the facet module never had failure-injection tests; the trigger window is narrow.

Why it fails: @lucene.experimental permits API changes, not duplicate ordinals; the addCategory contract and the cache rule are unconditional, and the code breaks its own stated invariants; "roll back after any IOException" is documented nowhere, is stricter than the IndexWriter the writer wraps (which stays usable after such exceptions), and would discard every uncommitted category for a failure IndexWriter survives; the damage is silent and persisted; upstream treated the same symptom as a bug before. In site A duplicated label was added successfully long before the failed call, so "the failed call may not have added its document" does not cover it. A rare trigger lowers severity, not intent. For site B the rebuttal is weaker: the retried label is the one whose call threw, and a maintainer could reasonably prefer fail-stop semantics (option D); there it rests on the missing documentation, not on a documented reuse guarantee. Verdict: a defect. Expect the reply "roll back after an IOException"; answer with the contract, the cache rule and the IndexWriter exception contract.

Suggested fix

#

Recommended Clear the flag first and track a possibly stale reader (validated)

Clear cacheIsComplete before the eviction refresh, and mark the reader as possibly stale until a refresh succeeds, also when anything after indexWriter.addDocument throws; findCategory then refreshes it before the cache fill and the on-disk lookup (+29/-7). The new test passes 5 of 5 and the facet module's 311 tests pass, assertions on and off.

// addToCache, after cache.put(...) evicted entries
cacheIsComplete = false; // before the refresh, which may throw
readerMayMissCategories = true;
refreshReaderManager();
readerMayMissCategories = false;

// addCategoryDocument: catch (Throwable t) after the document is indexed
cacheIsComplete = false; readerMayMissCategories = true; throw t;

// findCategory, before perhapsFillCache() and the on-disk lookup
if (readerMayMissCategories) {
  refreshReaderManager(); // no-op when no reader manager is open
  readerMayMissCategories = false;
}

Option A was built and validated with gradle in a scratch worktree; option B was run and is not enough; options C to E were not run in Java. Do not revert LUCENE-4596's order (the cache entry must stay last).

Clear the flag first and track a possibly stale reader (validated) (validated by the checks) (recommended)

#

One file, DirectoryTaxonomyWriter.java. A new volatile field readerMayMissCategories. addToCache sets cacheIsComplete = false and the new flag before refreshReaderManager(), and clears the new flag once the refresh returns. addCategoryDocument wraps the parent-array update and addToCache (order unchanged) and, if either throws, clears cacheIsComplete, sets the new flag and rethrows. findCategory, after counting the miss, refreshes the reader when the new flag is set, before perhapsFillCache() and the on-disk lookup.

// addToCache, after cache.put(...) evicted entries
cacheIsComplete = false; // before the refresh, which may throw
readerMayMissCategories = true;
refreshReaderManager();
readerMayMissCategories = false;

// addCategoryDocument: catch (Throwable t) after the document is indexed
cacheIsComplete = false; readerMayMissCategories = true; throw t;

// findCategory, before perhapsFillCache() and the on-disk lookup
if (readerMayMissCategories) {
  refreshReaderManager(); // no-op when no reader manager is open
  readerMayMissCategories = false;
}

Trade-offs

  • Keeps LUCENE-4596's order: the cache entry is still published last, so a lock-free cache hit never sees an ordinal whose parent is not stored yet.
  • A retry of the failed label finds its already indexed document and returns that ordinal (13); the failed call's document stays, as IndexWriter's wording allows.
  • Cost: one extra reader refresh on the first cache miss after a failure; on the normal path a volatile read per cache miss and two writes per eviction. Not benchmarked.
  • Taxonomies that already hold a duplicate are not repaired; they need a rebuild.
  • DirectoryTaxonomyWriter.java is byte-identical from 10.0.0 to main; the 9.x files differ but have the same two orders, so a 9.x backport needs its own patch. Only main was built with gradle.
  • Scope: it covers failures after indexWriter.addDocument succeeded (the reader opens), not an exception from addDocument itself, which is a different root cause tracked separately.

What the checks validated

  • Scratch worktree at a9779ef3c193, gradle, JDK 25: the new test fails 4 of 5 on stock and passes 5 of 5 with the fix, assertions on and off; with TestDirectoryTaxonomyWriter: 20 tests, 0 failures.
  • The whole facet module: 40 suites, 311 tests (306 upstream + 5 new), 0 failures, with assertions on (7 skipped) and off (8 skipped); :lucene:facet:check -x test (google-java-format, ecjLint, forbiddenApis) passes.
  • Standalone runner with the patched class: the new test, the finder's 3 tests, the independent reproducer's tests and control, and the end-user test and control all pass, assertions on and off (the second mode of the finder's, the independent reproduction's and the intended-behaviour check's suites was run by the fact check). In the finder's bounded TLA+ model the same logic has no violation in any of 96 configurations: the 84 with one injected failure check the six observable invariants (no duplicate label, sizes, add results, parents, cache soundness), the 12 failure-free ones also the protocol invariant LookupComplete, which the fix deliberately relaxes after a failure. The model abstracts the reader as a prefix of the indexed documents: corroboration, not a proof.

Refresh in findCategory whenever a refresh is pending

#

Refresh whenever shouldRefreshReaderManager is set, not only after a failure.

Trade-offs

Correct in the finder's model (variant fixFull), but it reopens the near-real-time reader on cache misses after any new label. Not run in Java.

Fail-stop: close the taxonomy writer on such a failure

#

Treat an exception after indexWriter.addDocument, or a failed eviction refresh, as fatal: roll back and close, so later calls throw AlreadyClosedException and nothing is committed.

Trade-offs

Loses every uncommitted label and forces the application to reopen both writers; stricter than IndexWriter, which survives these exceptions. Not run.

Document that the writer must be rolled back after an IOException

#

Javadoc only.

Trade-offs

No code risk, but nothing stops the silent corruption, and rollback discards uncommitted labels.

Downstream note

#

Elasticsearch, OpenSearch and Solr do not use DirectoryTaxonomyWriter (code search of their default branches), so the exposed users are applications that embed Lucene's taxonomy facets directly.

How it was found

#

TLA+ model checking of the writer's cache, completeness flag and reader, with optional I/O failures. The finder noticed the statement order while mapping the model to the code; the model checker then gave minimal counterexamples, which were reduced to a JUnit on the stock jars.

The method in full189 words

Method: TLA+ model checking (TLC 1.8.0) (semi-formal tier: a hypothesis formed while modelling, then witnessed by the tool), in a hunt unit on concurrent adds to the taxonomy writer.

  • The model covers addCategory, the LRU cache with its exact eviction rule, the lazily opened reader, cacheIsComplete, perhapsFillCache and the parent array, with optional I/O failure points. Without failures, every invariant holds in all 96 bounded configurations. The model is bounded and abstracts the reader as a prefix of the indexed documents, so it corroborates the Java finding rather than proving anything about the Java code.
  • With one injected failure, the protocol invariant LookupComplete fails in 37 of 48 configurations; minimal traces: a refresh failure after an eviction (18 states) and a reader re-open failure after a complete cache fill (9 states). Clearing the flag first is not enough (NoDuplicateLabel fails), and the stale-reader cache fill came from the model too.
  • The traces were reduced to a same-package JUnit on the stock jars, then checked by an independent reproducer, a devil's advocate, a reviewer from another model family (OpenAI GPT-5.6, reading only), an adjudication and an audit.

History

#

The eviction-refresh path dates from the facet module's first commit (LUCENE-3079, 2011, released in 3.4.0); the reader-open path from LUCENE-4596 (2012, 4.1.0). The evicting cache became the default in 9.5.0 (#12093). Every release from 3.4.0 to 10.5.2 and main is affected; it was never fixed.

Impact note
Applications that index taxonomy facets with the default DirectoryTaxonomyWriter (its default LruTaxonomyWriterCache(4000) since 9.5.0 for site A; for site B any cache, on an existing taxonomy small enough to be read into the cache; default IndexWriterConfig, codec and Directory) and keep using the writer after an addCategory or FacetsConfig.build call threw are hit when that IOException came from opening the writer's near-real-time reader (the refresh after a cache eviction, or the lazy reader open after an existing taxonomy was read into the cache), for example a failed memory map or running out of file handles: a category already in the taxonomy is indexed again under a new ordinal, commit() persists both, CheckIndex reports the taxonomy clean, and facet counts and listings for that label are split or doubled (executed: getSpecificValue 1 instead of 2) until the taxonomy is rebuilt, while drill-down matching stays correct; no scale is needed, and an I/O failure in the flush itself is tragic and closes the writer instead.
Summary
You index facet categories with a default DirectoryTaxonomyWriter; one addCategory call throws an IOException because the writer could not open its near-real-time reader (for example on the call whose new category makes the 4000-entry cache evict), and you keep using the writer, as IndexWriter allows after a non-fatal exception. You expect a later addCategory of a category that is already in the taxonomy to return its existing ordinal, as TaxonomyWriter.addCategory promises. Instead the writer still trusts its cache as complete (or its old reader), indexes the category again and returns a new ordinal (l0: 4001 instead of 1; a retried 'new': 14 instead of 13), and commit() persists one label under two ordinals, so its facet counts are split between them.
