With beamWidth = 1 no HNSW graph can be built: the builder sizes a queue beamWidth / 2 = 0, and a merge closes the IndexWriter

The HNSW vector formats accept beamWidth = 1, but since 10.2.0 the graph builder also creates a queue of beamWidth / 2 slots, which is 0, and the queue rejects size 0. So no HNSW graph can be built, and the first merge that needs one closes the IndexWriter.

The finding in 30 seconds

#

beamWidth (also called efConstruction) is how many candidates the HNSW graph builder keeps while it links a new vector into the graph. Since 10.2.0 the builder also keeps an extra queue of half that size for merges, and half of 1 is 0 in integer arithmetic.

Background: how Lucene builds HNSW graphs

#
  1. Each segment's kNN vectors get an HNSW graph. To insert a vector, the builder searches the graph and keeps the best beamWidth candidates in a priority queue; the default beamWidth is 100, maxConn (M) is 16.
  2. Small segments skip the graph: with the default threshold a segment gets one only from 648 vectors. A merge then builds the graph of the merged segment.
  3. Since 10.2.0, merges that combine existing graphs search level 0 from known neighbours with a smaller queue of min(beamWidth / 2, M * 3) slots. Every builder allocates it up front, whether or not it is used.

The finding, step by step

#
  1. You configure a vector field with Lucene99HnswVectorsFormat(16, 1): the default 16 connections and a beam width of 1, which the format accepts (any value from 1 to 3200). You index 1,000 2-d vectors, flush after 500, and call forceMerge(1).
  2. You expect one merged segment with an HNSW graph, as beamWidth = 2 gives, and as beamWidth = 1 gave up to 10.1.0.
  3. You get IllegalArgumentException: initialCapacity must be > 0 and < 2147483630; got: 0 from inside HnswGraphBuilder. The IndexWriter closes as a tragic event, and the 1,000 uncommitted documents are lost.
  4. Why: the builder sizes its level-0 merge queue Math.min(beamWidth / 2, M * 3). Integer division makes 1 / 2 = 0, and the queue's heap rejects size 0. The two 500-vector segments flushed only because segments below 648 vectors skip the graph.
  5. A flush cannot get past that size either: the 648th vector document of a segment and the next one are rejected at addDocument. On 10.2.x and 10.3.x even the first vector document fails.

Who is affected

#

Only applications that set beamWidth = 1 on an HNSW vector format; the default is 100. Then any maxConn and any data fail on the first graph build, loudly. The last commit stays intact, but a merge failure closes the writer and discards uncommitted documents. Rare: no upstream test uses 1, and the recorded searches found no report.

Mechanism, terms and numbers600 words

The HNSW vector formats (Lucene99HnswVectorsFormat, and by code reading the scalar-quantized and bit-vector HNSW formats and two sandbox formats) accept any beamWidth from 1 to 3200, and HnswGraphBuilder rejects only beamWidth <= 0. Since 10.2.0 (#14331, "Speedup merging of HNSW graphs") every builder also allocates an extra candidate queue for merge-time level-0 searches, sized Math.min(beamWidth / 2, M * 3). For beamWidth = 1 that is 0, and the heap under the queue throws IllegalArgumentException: initialCapacity must be > 0 and < 2147483630; got: 0. So no HNSW graph can be built with a beam width of 1, for any maxConn and any data. From 10.4.0, segments below the tiny-segment threshold (648 vectors by default) still flush without a graph; then the first merge that has to build one throws, and IndexWriter treats it as a tragic event: the writer closes and everything added since the last commit is discarded. On the flush path the 648th vector document of a segment is rejected, and so is the next one, while the writer stays open. On 10.2.x and 10.3.x the first vector document already fails. 10.1.0 and earlier work; every release from 10.2.0 to 10.6.0 and main fail. The fix is one line, Math.max(1, ...).

#
  • Accepted range. Lucene99HnswVectorsFormat.java:278-283: if (beamWidth <= 0 || beamWidth > MAXIMUM_BEAM_WIDTH) throws "beamWidth must be positive and less than or equal to 3200" (:112). The same check in Lucene104HnswScalarQuantizedVectorsFormat.java:171-173, HnswBitVectorsFormat.java:116-118 and the sandbox DedupHnswVectorsFormat.java:175-180 and DedupHnswScalarQuantizedVectorsFormat.java:189-194 (both write through Lucene99HnswVectorsWriter). HnswGraphBuilder.java:177-179: "beamWidth must be positive".
  • Three queues. The base constructor (HnswGraphBuilder.java:166-196), which every other constructor and subclass reaches, allocates entryCandidates = new GraphBuilderKnnCollector(1) (:193), beamCandidates = new GraphBuilderKnnCollector(beamWidth) (:194) and beamCandidates0 = new GraphBuilderKnnCollector(Math.min(beamWidth / 2, M * 3)) (:195). GraphBuilderKnnCollector(int k) makes new NeighborQueue(k, false) (:821-822), which makes new TernaryLongHeap(initialSize) (NeighborQueue.java:59-60), which throws for initialCapacity < 1 (TernaryLongHeap.java:57-59).
  • Only merges that reuse graphs use the third queue (:349-351, level == 0 && eps0 != null && eps0.size() > 0, called from MergingHnswGraphBuilder.java:229 and, on main, from the concurrent merge's HnswConcurrentMergeBuilder.java:602), but it is allocated in every builder, so all graph building fails: the merge without a source graph (IncrementalHnswGraphMerger.java:159-161, the repro), the flush (Lucene99HnswVectorsWriter.java:832-836 -> :809-814), the merge of segments with graphs (MergingHnswGraphBuilder.java:73; by code reading) and the concurrent merge workers (HnswConcurrentMergeBuilder.java:493, :519; by code reading).
  • When a graph is needed. shouldCreateGraph(100, n) is n > (int) (ln(n) * 100) (Lucene99HnswVectorsWriter.java:716-722, HnswGraphSearcher.java:56-58, HNSW_GRAPH_THRESHOLD = 100 at Lucene99HnswVectorsFormat.java:137): false for 500 (621), true from 648 (647) and for 1,000 (690).
  • Why the flush keeps failing. In addValue the exception comes from initializeGraphBuilder() (:835) before node++ (:841), so the next vector document meets the same condition and throws again (the next one was executed). "Rejected" is what addDocument reports: the field writer has already buffered the vector (flatFieldVectorsWriter.addValue, :832), and DocumentsWriterPerThread marks the failed document deleted (DocumentsWriterPerThread.java:302-307, :399).
  • Why the writer closes. IndexWriter.merge catches the Throwable and calls tragicEvent(t, "merge") (IndexWriter.java:5109-5113), which closes the writer and rolls back uncommitted changes (tragicEvent -> maybeCloseOnTragicEvent -> rollbackInternal, :6090-6105). Only a failed merge does this; a flush-path failure leaves the writer open.
  • Exhaustive check. Over all 1,638,400 accepted (maxConn, beamWidth) pairs (1..512 x 1..3200), 512 give a non-positive queue size, all with beamWidth = 1; with the fix, none.
Exposure and likelihood302 words
  • Who is hit. Lucene99HnswVectorsFormat(maxConn, 1) (executed); by code reading also Lucene104HnswScalarQuantizedVectorsFormat, HnswBitVectorsFormat and the sandbox DedupHnswVectorsFormat / DedupHnswScalarQuantizedVectorsFormat, which accept the same range. Any maxConn, any data, any similarity.
  • What goes wrong (10.4.0 and later). Small segments flush; the first merge, forced or natural, whose result needs a graph throws, and the writer closes as a tragic event, which rolls it back: every document added since the last commit is lost (all 1,000 in the repro, which never commits; executed: afterwards the directory holds no index). A flush of 648 or more vectors rejects the threshold-crossing document and the next one at addDocument, while the writer stays open.
  • 10.2.x and 10.3.x build the flush graph eagerly, so the first vector addDocument already throws (LongHeap "maxSize must be > 0 ... got: 0").
  • Upgrades. An index written with beamWidth = 1 on 10.1.0 or earlier keeps working on 10.2.0 or later only until its first graph build: a merge that needs a graph, or a new vector document (on 10.2.x-10.3.x the first one, from 10.4.0 the one that takes a segment to 648 vectors). By code reading: beamWidth is not stored in the index.
  • What was not seen. Every executed failure is a loud exception; no silent corruption, hang or wrong search result was observed in the executed tests, and the last commit stayed readable (the independent reproduction's probe: 800 committed documents in 2 segments after the failed merge).
  • Workaround. Use beamWidth >= 2; 2 passes on main, 10.6.0 and 10.1.0.
  • How likely. Rare: upstream randomized tests draw beam widths from 5 or more (HnswGraphTestCase nextInt(10) + 5, RandomCodec 10 to 50), and the recorded searches found no report in the five affected release lines; whoever sets 1 hits it on the first graph build.

Why it looks unintended

#
  • The formats and the builder state the rule as "beamWidth must be positive"; the limit tests reject only 0 and below.
  • It worked through 10.1.0, which has no such queue; within the #14331 PR, min(beamWidth, M * 2) became min(beamWidth / 2, M * 3).
  • The error is an internal heap check at merge time that closes the writer, not a validation.
The full argument234 words
  • Contract. The format javadoc calls beamWidth "the size of the queue maintained during graph construction" (Lucene99HnswVectorsFormat.java:191), the builder javadoc "the size of the beam search to use when finding nearest neighbors" (HnswGraphBuilder.java:133, :161). Nothing documents a minimum of 2 or says that half the beam sizes another queue; the merge builder's javadoc describes the merge-time level-0 search as "We also limit beamWidth (efConstruction to M*3)" (MergingHnswGraphBuilder.java:47-49), a cap, which for beamWidth = 1 would be 1, not 0.
  • Tests. TestLucene99HnswVectorsFormat.testLimits rejects beamWidth 0, -1 and 3201 only (:64-74); HnswGraphTestCase.testHnswGraphBuilderInvalid says // beamWidth must be > 0 (:888-890).
  • History. Inside the #14331 PR branch, commit 09735cf80a1 ("Adjust beamCandidates0", 2025-03-18) replaced Math.min(beamWidth, M * 2) with Math.min(beamWidth / 2, M * 3); the discussion covers only the cap (M * 2 to M * 3). The builder's beamWidth <= 0 check dates from 2020: it was added by 09f78e2927c (LUCENE-9610); git blame shows e1cd426bce39 (LUCENE-9644), which moved it.
  • A beam width below maxConn has been called valid. In #13752 (2024, closed as not planned) Michael McCandless asked whether beamWidth < maxConn should throw; Ben Trent answered "It is a weird configuration for sure, but I am not sure its invalid", and no validation was added.
  • A sibling edge case in the same merger was fixed as a bug: #14407 / #14420 (an empty join-set heap, fixed in 10.2.0).
The devil's-advocate check223 words

The case (built by the intended-behaviour devil's advocate and the cross-model reviews, all rating it weak): a beam of one gives a poor graph and nobody should run it in production; the formats are @lucene.experimental (Lucene99HnswVectorsFormat.java:83); a maintainer may prefer to reject beamWidth < 2.

Why it fails: the documented and tested rule is "positive", the value worked through 10.1.0, and today's failure is an opaque internal error that closes the writer at merge time, not a clear validation. @lucene.experimental allows API changes, not crashes on accepted input. Rejecting beamWidth < 2 is one of the fixes (option B), and it still changes code. The argument bears on priority (Low), not on whether it is a bug.

The hunt's no-noise rule does not claim behaviour that "needs absurd parameters and then fails loudly". This bug does fail loudly, and 1 is an unusual value: that is the main argument for Low priority, and it is conceded. It is still claimed because the value is inside the documented and tested contract ("positive"), it worked through 10.1.0 (a regression), and the failure does not come where the value is set: it comes later, at the first graph build, often at a merge, where it closes the writer and rolls back uncommitted documents. The cross-model fact check reached the same call: claim, Low.

Suggested fix

#

Recommended Clamp the level-0 merge queue to at least 1 (one line in HnswGraphBuilder)

Clamp the level-0 merge queue to at least one slot: Math.max(1, Math.min(beamWidth / 2, M * 3)) in the HnswGraphBuilder constructor. Nothing changes for beamWidth >= 2. The test, a graph-merge probe and the closest HNSW and codec suites (526 lucene/core tests and 8 bit-vector tests) pass.

beamCandidates0 = new GraphBuilderKnnCollector(Math.max(1, Math.min(beamWidth / 2, M * 3)));
// was: new GraphBuilderKnnCollector(Math.min(beamWidth / 2, M * 3))
All options and trade-offs3 options · 539 words

Three options; A was validated with gradle in a fresh scratch worktree at 645d4fe14a20, B and C were not executed. A maintainer may prefer B, a clear early rejection; either resolves the bug. Not a fix: allocating beamCandidates0 lazily, only when the eps0 path needs it. Flushes and graph-free merges would work, but the merge of two segments that have graphs would still hit the zero size.

Clamp the level-0 merge queue to at least 1 (one line in HnswGraphBuilder) (validated by the checks) (recommended)

#

HnswGraphBuilder.java:195 becomes beamCandidates0 = new GraphBuilderKnnCollector(Math.max(1, Math.min(beamWidth / 2, M * 3)));.

beamCandidates0 = new GraphBuilderKnnCollector(Math.max(1, Math.min(beamWidth / 2, M * 3)));
// was: new GraphBuilderKnnCollector(Math.min(beamWidth / 2, M * 3))

Trade-offs

  • No change for beamWidth >= 2: there min(beamWidth / 2, M * 3) is already at least 1 (M >= 1), so every graph built today is built the same way.
  • For beamWidth = 1 the level-0 merge search keeps 1 candidate, the same as the main beam queue.
  • Keeps the documented "positive" contract, and beamWidth = 1 works again as it did up to 10.1.0.

Reject beamWidth < 2 with a clear message

#

In Lucene99HnswVectorsFormat, Lucene104HnswScalarQuantizedVectorsFormat, HnswBitVectorsFormat and HnswGraphBuilder. Not executed.

Trade-offs

Fails fast at codec construction instead of at a merge, but changes the documented "positive" contract and the testLimits / testHnswGraphBuilderInvalid expectations, rejects configurations that worked through 10.1.0, and must be repeated in every format with the same check (the sandbox dedup formats have it too).

Round up: Math.min((beamWidth + 1) / 2, M * 3)

#

Not executed. Never 0 either.

Trade-offs

Changes the queue size for every odd beamWidth below 6 * M (3 -> 2, 5 -> 3, ...), so merge-built graphs change for those settings; option A changes nothing outside beamWidth = 1.

Downstream note

#

By code reading only, saved snapshots suggest a user-chosen value of 1 can reach this crash downstream: Solr's DenseVectorField passes hnswEfConstruction to Lucene99HnswVectorsFormat, and the OpenSearch k-NN plugin's Lucene HNSW method accepts any ef_construction > 0. Their revisions and the OpenSearch mapping to beamWidth were not confirmed.

How it was found

#

Two independent hunts found it in the same minute, by reading the HNSW graph builder's constructor while deriving the parameter domain of their models; one hunt's bounded parameter sweep then hit the exception at beamWidth = 1 for every maxConn. A later hunt reduced it to one test and checked every accepted parameter pair.

The method in full223 words

Method: code reading during model building, then executed tests and an exhaustive check (the hunt's non-formal tier: the bug was seen in the code, not reported by a model checker).

  • First signal (2026-10-25). A unit modelling the HNSW graph format derived the legal parameter domain from the format's validation (1 <= beamWidth <= 3200) and checked that every buffer sized from maxConn and beamWidth is legal on it; beamWidth / 2 is not. It confirmed this with an executed probe and a JUnit on the stock main jars. In the same minute a unit modelling merge-time graph reuse noticed the line while modelling the eps0 path, and its bounded-exhaustive harness reported the builder exception for beamWidth = 1 at every M and for no other beam width.
  • Hunt. An adjudication-take-over unit re-ran the earliest repro on main (-ea, -da: fails), reduced it to one JUnit test with no package-private member, checked the three queue sizes over all 1,638,400 accepted (maxConn, beamWidth) pairs (512 non-positive, all at beamWidth = 1; 0 with the fix) and wrote the one-line fix.
  • Checks. An independent reproducer, an intended-behaviour devil's advocate, two executed reviews by an independent reviewer from another model family (OpenAI GPT-5.6), an adjudication, a credibility audit and a no-noise gate confirmed it; the version-history runs ran the release matrix.

LFV-1056, snapshot of 2026-11-09

Registry title
With beamWidth = 1, which the HNSW formats accept, every HnswGraphBuilder sizes its level-0 merge queue min(beamWidth / 2, M * 3) = 0 and throws, so building any HNSW graph fails and a merge closes the IndexWriter (since 10.2.0)
Area
core / HNSW graph construction (util/hnsw HnswGraphBuilder constructor; codecs/lucene99 Lucene99HnswVectorsFormat beamWidth range)
Priority
Low, rank 704: BeamWidth = 1 is accepted by the core HNSW formats but makes every graph build throw, so a merge closes the IndexWriter (released since 10.2.0), the same accepted-setting crash class as LFV-589.
Impact class
crash
Impact note
Hits only applications whose vector field uses an HNSW format built with beamWidth = 1 (Lucene99HnswVectorsFormat(maxConn, 1) [exec]; by code reading also Lucene104HnswScalarQuantizedVectorsFormat and HnswBitVectorsFormat, which accept the same 1..3200 range), for any maxConn, data and scale: from 10.4.0 segments below the tiny-segment threshold (about 650 vectors with the defaults) flush without a graph, then the first merge that has to build one throws IllegalArgumentException and closes the IndexWriter as a tragic event, which discards every document added since the last commit (the last commit stays intact), and on the flush path the vector document that pushes a segment over the threshold and every later one in that segment are rejected; on 10.2.x-10.3.x the first vector document already fails; -ea and -da, released 10.2.0 through 10.6.0.
Summary
You configure a vector field with an HNSW format and beamWidth = 1, the smallest value the format and the graph builder accept ('beamWidth must be positive'), index vectors and merge, and you expect it to work as it did up to 10.1.0, only with a poorer graph. Instead every HnswGraphBuilder constructor sizes its level-0 merge candidate queue as Math.min(beamWidth / 2, M * 3), which integer division makes 0, and the heap rejects capacity 0 ('initialCapacity must be > 0 ... got: 0'), so no HNSW graph can be built at all. Small segments still flush without a graph, then the first merge that needs one throws and closes the IndexWriter, and the vector document that would push a segment past the graph threshold is rejected.
