IndexWriter.deleteDocuments(Term...) and deleteDocuments(Query...) keep the caller's array, so reusing it after the call deletes the wrong documents

IndexWriter.deleteDocuments keeps the Term[] or Query[] you pass and reads it again later for documents still in RAM, so refilling it for the next batch deletes the wrong documents: deleting 6 ids in 3 batches of 2 leaves 4 of them. Every release since 4.0 is affected.

The bug in 30 seconds

#

deleteDocuments takes an array of terms or queries. Documents already flushed to a segment are deleted by what the array holds during the call; documents still in the writer's RAM buffer are deleted later, by what it holds then.

  1. Index 7 documents, d0 to d5 and keep, with the default IndexWriterConfig. They wait in the writer's RAM buffer until the next flush.
  2. Delete d0 to d5 in 3 batches with one reused array: fill a Term[2] with {d0, d1} and call deleteDocuments(batch), refill it with {d2, d3} and call again, then {d4, d5}. Then commit().
  3. You expect only keep to be left. That is what you get with a new array per call, or when the documents were flushed before the deletes.
  4. Instead the commit keeps [d0, d1, d2, d3, keep]. The writer stored the array itself, once per call, and read it only at commit, when it held {d4, d5}. No error.
  5. A slot change alone is enough: after deleteDocuments(queries) with queries = {id:delete-me}, setting queries[0] = id:keep keeps delete-me and deletes keep.

Who is affected

#

Applications that pass their own Term[] or Query[] and change it before the writer's next document or flush, such as a batch loop with one reused buffer or clearing it after use. Default configuration, any index size; silent and committed. Literal varargs like deleteDocuments(t1, t2) are safe.

Mechanism, terms and numbers652 words

IndexWriter.deleteDocuments(Term...) and deleteDocuments(Query...) hand the caller's array itself to the writer's delete queue. During the call the queue copies the elements into the buffer that serves segments already flushed, so those documents are deleted by what the array held at the call. Each per-thread writer applies the delete to the documents it still buffers in RAM only later, at its next addDocument or at flush, and reads the array as it is then.

So a caller that refills or reuses its array after the call deletes buffered documents by the new contents. With the default IndexWriterConfig, a loop that refills one Term[2] with {d0, d1}, {d2, d3}, {d4, d5} commits [d0, d1, d2, d3, keep] instead of [keep]; the same loop with a new array per call, or with the documents flushed first, commits [keep]. Reassigning queries[0] after the call deletes a document no call named. Clearing a Query[] after the call makes the next commit a tragic writer failure that loses all uncommitted documents. Every release from 4.0.0-ALPHA (2012) through 10.5.2 and main is affected; a 2-line copy in IndexWriter fixes it.

Terms

#
  • RAM buffer, per-thread writer: IndexWriter collects new documents in memory, in one or more per-thread writers, until a flush writes them as a new segment. A flush happens at commit(), when an NRT reader is opened or refreshed, when the RAM buffer is full (16 MB by default) or on flush().
  • Delete queue: deletes are appended to one shared queue. A global slice of it serves the segments that are already flushed; each per-thread writer has its own delete slice for the documents it buffers.
  • Node: one queue entry per deleteDocuments call, so all of a call's deletes become visible together.

What happens (main a9779ef3c193)

#
  1. deleteDocuments(Term... terms) calls docWriter.deleteTerms(terms) (IndexWriter.java:1867); the Query... overload calls docWriter.deleteQueries(queries) (:1894). DocumentsWriter passes the array on (DocumentsWriter.java:141-147), and DocumentsWriterDeleteQueue.addDelete appends new TermArrayNode(terms) / new QueryArrayNode(queries) (DocumentsWriterDeleteQueue.java:123-133). The node stores the array itself, not a copy (:462-465, :475-478).
  2. Flushed segments, call-time contents. addDelete then calls tryApplyGlobalSlice() (:125, :131). When its tryLock succeeds (always with one thread) it applies the node to the global buffer during the call (:198-215), copying each element (:467-472, :480-485). That buffer is applied to segments already flushed.
  3. Buffered documents, later contents. A per-thread writer applies its slice only when it finishes its next document (DocumentsWriterPerThread.java:361-389, apply at :377 and :383) or when it flushes (prepareFlush, :427-436, apply at :434). The node's apply loops over the stored array as it is at that moment (for (Term term : item), DocumentsWriterDeleteQueue.java:482).
  4. The batch loop. Three calls with one array add three nodes that point at the same array. At commit the per-thread writer applies all three; each reads {d4, d5}. So the {d4, d5} terms are added three times (BufferedUpdates.addTerm keeps one entry per term, so d4 and d5 are deleted once) and d0 to d3 are never deleted.
  5. Clearing the array. A null slot reaches BufferedUpdates.addTerm at the next addDocument (which throws a NullPointerException, and the delete is dropped), or, for queries, IndexSearcher.rewrite while the commit applies the segment's deletes; an exception there is a tragic event (IndexWriter.java:2933-2942) that closes the writer.

For one indexing thread the window closes at that writer's next indexed document (any add or update call, such as addDocument or updateDocument) or at the next flush (such as commit(), an NRT reopen or flush()); another delete call does not close it. With several threads each per-thread writer applies the node at its own next document, and if tryApplyGlobalSlice misses its tryLock, flushed segments read the array late too; both come from code reading only, every run was single-threaded.

Exposure and likelihood263 words
  • Who is hit. Code that passes an explicit Term[] or Query[] to deleteDocuments and then changes it before that per-thread writer indexes another document or flushes: refilling one buffer per batch, clearing it with Arrays.fill(buf, null), or reusing it for something else. Literal varargs (deleteDocuments(t), deleteDocuments(t1, t2)) get a fresh array from the compiler, and code that builds a new array per call is safe.
  • Default configuration, mainstream API. The repro uses the default IndexWriterConfig, codec and merge policy and one thread; nothing is opted into.
  • Scale. Every document added since the last flush can be affected; the repros use 2 to 7 documents because size does not matter.
  • Silent and durable. The call returns its sequence number, there is no exception, and the commit persists both errors: documents the caller deleted stay searchable (also through NRT readers), and documents nobody named are gone. No structural corruption was observed (readers open the committed index normally; CheckIndex was not run).
  • Clearing is worse. After deleteDocuments(Query[]), Arrays.fill(buf, null) makes the next commit() throw a NullPointerException; the writer closes on the tragic event and every uncommitted document is lost (committed live set []). After deleteDocuments(Term[]), the next unrelated addDocument throws a NullPointerException and the delete is dropped (the writer stays open).
  • How likely. Rare. Code search found no Lucene module and no Elasticsearch, OpenSearch or Solr main-code call site that reuses an array (they pass one argument or build a new array per call), and nobody has reported it since 4.0. Code search can miss call sites.

Why it is a bug, not intended

#
  • The javadoc speaks of "all given deletes" and never says the array is kept; the other APIs checked that keep caller data say so (MultiPhraseQuery.Builder.add(Term[])).
  • One call gives two answers: flushed documents are deleted by the call-time terms, buffered ones by later contents.
  • Lucene 3.x copied the elements during the call; no test or discussion asks for retention.
The full argument338 words
  • The contract speaks of the deletes given. "Deletes the document(s) containing any of the terms. All given deletes are applied and flushed atomically at the same time." and "@param terms array of terms to identify the documents to be deleted" (IndexWriter.java:1856-1860; the same for queries at :1875-1879). Nothing says the array is kept or must not be changed.
  • Lucene documents retention in the other places checked where it keeps caller data. MultiPhraseQuery.Builder.add(Term[]): "The array is not copied or mutated, the caller should consider it immutable subsequent to calling this method" (MultiPhraseQuery.java:111-112, :122-123). Field/StoredField: "the provided byte[] is not copied so be sure not to change it until you're done with this field" (Field.java:156, :172; StoredField.java:68). The Term objects passed in are already protected: "The provided BytesRef is copied when it is non null." (Term.java:50).
  • The result depends on flush timing. In one call, flushed documents see the call-time contents and buffered documents the later contents. The class javadoc presents flushing as buffering ("These changes are buffered in memory and periodically flushed", IndexWriter.java:123) and says a change's sequence number "expresses the effective order in which each change was applied" (:117-118); here what the change deletes is decided after its number is assigned.
  • History. 3.x applied the elements inside the call (Term[] deletes since 2.1.0, Query[] since 2.4.0). Retention came with the new (then lock-free) delete queue of LUCENE-2956 (#4030, 2011), whose review asked that a Term[]/Query[] delete be atomic, hence one node per call; nobody discussed copying or reusing the array.
  • Tests. No upstream test reuses an array at the public API. The only identity assertion is the package-private queue test TestDocumentsWriterDeleteQueue.testUpdateDeleteSlices ("create an array here since we compare identity below against tailItem", TestDocumentsWriterDeleteQueue.java:51-56); it passes with the boundary copy.
  • Precedent. LUCENE-6821 (#7879, 2015) made Term copy its BytesRef because the aliasing had "bitten a few people"; #12158 (2023) cloned a caller's BytesRef[] in KeywordField#newSetQuery.
The devil's-advocate check144 words

The strongest case for "works as designed" (the intended-behaviour checker and an intended-lens review by OpenAI GPT-5.6): IndexWriter buffers its changes, Java does not require defensive copies, and the delete queue keeps its payload on purpose (an internal test asserts identity), so a caller must not modify an array after passing it in.

Why it fails: the public methods say nothing, while Lucene documents retention in the other places checked where it keeps caller data (MultiPhraseQuery.Builder, Field, StoredField); within one call the outcome depends on whether a document was flushed; the identity test covers the internal queue only; upstream removed the same kind of trap by copying; and a routine cleanup (Arrays.fill(buf, null)) turns into a tragic writer failure. The intended-behaviour checker remains only moderately sure about the remedy: upstream may prefer a javadoc note to a copy.

Suggested fix

#

Recommended Copy the array in IndexWriter.deleteDocuments (validated)

Copy the array where it enters IndexWriter: docWriter.deleteTerms(terms.clone()) and docWriter.deleteQueries(queries.clone()) (2 lines). The test then passes 3 of 3 with assertions on and off, and the core index test package passes with it (215 suites, 1,398 tests, 0 failed). Cost: one shallow array copy per call.

   public long deleteDocuments(Term... terms) throws IOException {
     ensureOpen();
     try {
-      return maybeProcessEvents(docWriter.deleteTerms(terms));
+      // copy: the deletes are resolved against buffered documents after this call returns
+      return maybeProcessEvents(docWriter.deleteTerms(terms.clone()));
@@ deleteDocuments(Query... queries)
-      return maybeProcessEvents(docWriter.deleteQueries(queries));
+      // copy: the deletes are resolved against buffered documents after this call returns
+      return maybeProcessEvents(docWriter.deleteQueries(queries.clone()));

Copy the array in IndexWriter.deleteDocuments (validated) (validated by the checks) (recommended)

#

Clone the varargs array before it is handed to the delete queue, in both overloads (IndexWriter.java:1867, :1894). The Term and Query objects are not copied; Term already copies its bytes.

   public long deleteDocuments(Term... terms) throws IOException {
     ensureOpen();
     try {
-      return maybeProcessEvents(docWriter.deleteTerms(terms));
+      // copy: the deletes are resolved against buffered documents after this call returns
+      return maybeProcessEvents(docWriter.deleteTerms(terms.clone()));
@@ deleteDocuments(Query... queries)
-      return maybeProcessEvents(docWriter.deleteQueries(queries));
+      // copy: the deletes are resolved against buffered documents after this call returns
+      return maybeProcessEvents(docWriter.deleteQueries(queries.clone()));

Trade-offs

One shallow copy of the varargs array per call (one reference per term or query), not per document. It also removes the cleared-array failures. In the Query... overload the copy is taken after the MatchAllDocsQuery check, so another thread could still change the array between the two; a variant, not run, clones once at the top and uses the copy for both the check and the delete. The copy covers the array slots only: a caller that later mutates a custom Query object it passed in is still exposed.

Copy inside DocumentsWriterDeleteQueue.addDelete (validated by the checks)

#

Store terms.clone() / queries.clone() in the queue node (DocumentsWriterDeleteQueue.java:123-133).

Trade-offs

Also removes the bug (shown at the introducing commit), but it fails the internal identity assertion of TestDocumentsWriterDeleteQueue.testUpdateDeleteSlices (1 failure; stock passes), so that test would change too. The only production entry path is IndexWriter, through DocumentsWriter (package tests call addDelete directly), so it gains nothing over the boundary copy today.

What the checks validated

Executed: the queue-level copy fails testUpdateDeleteSlices and passes TestIndexWriterDelete; at the introducing commit it turns the failing scenario into a pass.

Document that the array is kept

#

Add "The array is not copied; do not modify it after this call" to both javadocs, in the style of MultiPhraseQuery.Builder.add(Term[]).

Trade-offs

Zero cost, but the trap stays: the flush-timing-dependent result, the lost and unrequested deletes, and the tragic commit after a cleared Query[]. Existing callers that reuse arrays stay broken.

Apply the elements to every per-thread writer during the call (not recommended)

#

What Lucene 3.x did.

Trade-offs

Gives up the shared-queue, one-node-per-call design of the delete queue for no gain over the boundary copy.

Downstream note

#

Only the application's own code can trigger this, by changing its array after the call; an application that routes delete requests through one shared buffer can leave a document it deleted (for example for erasure) searchable and delete another user's buffered document instead.

How it was found

#

An AI tool listed every IndexWriter method that takes a caller-owned mutable argument and classified each argument, from the code, as copied, consumed in the call, or kept. A probe then changed each argument after the call returned and compared a buffered document with a flushed one; for deleteDocuments they disagreed.

The method in full134 words

Method: an argument-ownership table checked by mutate-after-return probes (the study's "semi-formal" tier). A hunt unit (IndexWriter update-value ownership), leg 2.

  • From code reading, the AI tool built a table of every IndexWriter entry point that takes a caller-owned mutable object (arrays, BytesRefs, fields) and classified each argument as copied, consumed inside the call, or kept.
  • Each row was witnessed by an executed probe on the real main jars: change the argument after the call returned, then compare a document buffered in RAM with one in a flushed segment.
  • For deleteDocuments(Term...) the same call deleted the flushed document and not the buffered one. The AI tool minimised that to the 2-test JUnit repro, and the fix and the checks followed.
  • No model checker, solver or prover was involved; the table guided where to probe.

History

#

Introduced by LUCENE-2956 (e95097a7c8d, 2011), whose new delete queue holds the caller's array; first released in 4.0.0-ALPHA (2012). Every release from 4.0.0-ALPHA through 10.5.2 and main fails; 3.6.2 copied the elements. Both introducing commits were bisected by execution.

Versions tested7 rows

Introduced by e95097a7c8d (LUCENE-2956 "Support updateDocument() with DWPTs", #4030, by @s1monw, 2011-04-13, on the realtime_search branch). It added DocumentsWriterDeleteQueue, whose TermArrayNode/QueryArrayNode hold the caller's array (one node per call, so a call's deletes become visible atomically, as the review asked), and replaced the loop that copied the elements into every per-thread writer during the call. It reached trunk with the merge 2a969f828c1 (LUCENE-3023 "Land DWPT on trunk", #4097, 2011-05-01). Later edits (generics, the BufferedUpdates rename, sequence numbers in 2016) kept passing the array through.

Releases before 9.12.3 ran a main() port of the same scenario adapted to their API. By reading, all 123 release tags in the history clone from 4.0.0-alpha to 10.5.2 build the node from the array with no copy; the clone has no tags for 8.8.2 to 8.11.3, which lie between executed failing releases.

data corruption
Impact note
Hits applications that pass an explicit Term[] or Query[] to IndexWriter.deleteDocuments and then change that array's slots (refill it for the next batch, clear it, reuse it) before the per-thread writer holding the targets indexes its next document or flushes; with the default IndexWriterConfig, codec and merge policy, one thread, any size, deterministically and the same with -ea and -da, the committed index keeps documents the call deleted and loses still-buffered documents nobody asked to delete (the intended-behaviour check: a default-config batch loop that refilled one Term[2] three times lost two batches and applied the third three times), and clearing a Query[] after the call makes the next commit a tragic writer failure that loses all uncommitted documents [exec]; calls with literal varargs (deleteDocuments(t1, t2)) get a fresh array from the compiler and are safe, documents in already-flushed segments see the call-time contents (single-threaded runs), and code search found no Lucene module and no Solr, Elasticsearch or OpenSearch main-code caller that reuses the array.
Summary
You pass a Term[] or Query[] to IndexWriter.deleteDocuments, the call returns its sequence number, and you then reuse the array, for example refill it with the next batch of ids; the delete should mean the terms or queries the array held at the call, as it already does for documents in flushed segments. IndexWriter hands the array itself to its delete queue, and each per-thread writer reads it only later, at its next addDocument or flush, so documents still buffered in RAM are deleted by the array's new contents. In the repro, deleting {flushed1, buffered1} and then refilling the same array with {flushed2, buffered2} and deleting again leaves buffered1 alive after commit, and reassigning the slot of a one-element Query[] after the call keeps 'delete-me' and deletes 'keep', which no delete call named; no exception is thrown.
