FacetsCollectorManager.search and DrillSideways.search with a Sort never rewrite it, so query-dependent sorts differ from IndexSearcher.search or throw

The facet module's sorted-search helpers, FacetsCollectorManager.search(..., sort, ...) and DrillSideways.search(..., sort, ...), use the caller's Sort without sort.rewrite(searcher), the step IndexSearcher#search(query, n, sort) takes first. A sort by a query's score then gets wrong sort values and can come back in a different order, or throws "must be rewritten".

The finding in 30 seconds

#

Both helpers hand the caller's Sort straight to the hit collector and skip the rewrite step, although they hold the searcher.

Background: rewriting a Sort

#
  1. A Sort can depend on the searcher, for example "by each document's score for another query": DoubleValuesSource.fromQuery(q).getSortField(true), or a legacy function ValueSource such as QueryValueSource.
  2. Such a sort must be rewritten before use: sort.rewrite(searcher) binds its values to that searcher (its statistics and Similarity). Unrewritten, some sources throw and some fall back to a fresh default searcher.
  3. Since 7.2.0, IndexSearcher#search(query, n, sort) rewrites the Sort itself, so callers no longer have to.
  4. The facet module has two helpers that run a sorted search and collect facets in one call: FacetsCollectorManager.search/searchAfter(..., sort, ...) and DrillSideways.search(..., sort, ...).

The finding, step by step

#
  1. Index two documents tagged color=red: doc0 with body "a a a a a a a a x x", doc1 with body "a". Give the searcher ClassicSimilarity and sort by each document's score for body:a, highest first (a QueryValueSource sort).
  2. IndexSearcher#search(query, 10, sort) returns [doc1=1.0, doc0=0.894], the searcher's own scores. You expect the facet helpers, given the same searcher, query and sort, to return the same.
  3. FacetsCollectorManager.search and DrillSideways.search both return [doc0=0.147, doc1=0.125]: the first hit flips, and the values are the scores of a fresh default (BM25) searcher. No error.
  4. Why: a query-dependent sort must be rewritten against the searcher before use. IndexSearcher does that itself since 7.2.0; the two helpers pass the Sort to the hit collector unchanged, so its values never see the searcher.
  5. Other such sorts fail loudly: a DoubleValuesSource.fromQuery sort throws "This DoubleValuesSource must be rewritten" from both helpers, while IndexSearcher sorts fine. Field sorts are unaffected.

Who is affected

#

Applications that sort a faceted or drill-sideways search by a query-dependent value (DoubleValuesSource.fromQuery, IndexReaderFunctions, legacy ValueSource sorts) through these helpers without rewriting the Sort themselves. The silent variant also needs a non-default searcher Similarity, such as ClassicSimilarity or a tuned BM25. Field sorts are unaffected, and in the silent form so are the facet counts. Workaround: pass sort.rewrite(searcher).

Mechanism, terms and numbers807 words

FacetsCollectorManager.doSearch, behind every search/searchAfter overload that takes a Sort, builds (for any n > 0) new TopFieldCollectorManager(sort, n, (FieldDoc) after, Integer.MAX_VALUE) from the caller's Sort (FacetsCollectorManager.java:287-288), and DrillSideways.search(DrillDownQuery, Query, FieldDoc, int, Sort, boolean) builds new TopFieldCollectorManager(sort, fTopN, after, Integer.MAX_VALUE) (DrillSideways.java:200-201). Both hold the IndexSearcher; neither calls sort.rewrite(searcher), which IndexSearcher#search(Query, int, Sort) has done since 7.2.0 (IndexSearcher.java:730).

Sorts whose rewrite matters then differ from IndexSearcher only in these helpers: a DoubleValuesSource.fromQuery sort throws UnsupportedOperationException: This DoubleValuesSource must be rewritten; a legacy ValueSource#getSortField sort throws IllegalStateException: SortField needs to be rewritten through Sort.rewrite(..) and SortField.rewrite(..); and a legacy QueryValueSource sort viewed through asDoubleValuesSource() silently scores with a fresh default-Similarity searcher, so on a searcher with any other Similarity the sort values are wrong and the order of the top hits can change (it does in the example below). Field sorts are unaffected; in the silent form so are the set of matching documents and the facet counts. Passing sort.rewrite(searcher) works around it; the fix is that same call at the two construction sites.

The mechanism (main 5adff78bb168)

#
  1. The helpers take the Sort as given. FacetsCollectorManager.doSearch (:243-302) is reached from search(IndexSearcher, Query, int, Sort, FacetsCollectorManager) (:170-177), search(..., Sort, boolean, ...) (:184-196) and both searchAfter overloads with a Sort (:214-221, :228-241). It caps n by maxDoc (:253), checks after, then, for any n > 0 (the n == 0 branch at :269-279 only counts hits and ignores the sort):
   TopFieldCollectorManager topFieldCollectorManager =
       new TopFieldCollectorManager(sort, n, (FieldDoc) after, Integer.MAX_VALUE);   // :287-288
   multiCollectorManager = new MultiCollectorManager(topFieldCollectorManager, fcm);
   ...
   Object[] result = searcher.search(q, multiCollectorManager);                     // :295

DrillSideways.search(DrillDownQuery, Query, FieldDoc, int, Sort, boolean) (DrillSideways.java:187-217) does the same: new TopFieldCollectorManager(sort, fTopN, after, Integer.MAX_VALUE) (:200-201), then search(query, collectorManager) (:202), which serves both the sequential and the executor path.

  1. IndexSearcher rewrites first. Its private searchAfter (IndexSearcher.java:719-740), behind search(Query, int, Sort) (:677) and searchAfter(ScoreDoc, Query, int, Sort) (:691), checks after, caps numHits by maxDoc, then calls final Sort rewrittenSort = sort.rewrite(this); (:730) and builds the collector from rewrittenSort (:732-733). doSearch takes the same two preparatory steps (in the other order) but no rewrite; its Integer.MAX_VALUE total-hits threshold, where IndexSearcher passes TOTAL_HITS_THRESHOLD, does not affect this bug.
  2. What the rewrite does. Sort#rewrite rewrites each SortField (Sort.java:88-99); the base SortField#rewrite returns this (SortField.java:575-577), so field sorts are unaffected. Query-dependent fields bind to the searcher there: fromQuery's source builds a Weight against it (DoubleValuesSource.java:777-780), the legacy WrappedDoubleValuesSource makes a copy that holds it (ValueSource.java:244-246), and ValueSourceSortField builds a comparator over a searcher context (ValueSource.java:378-382).
  3. Unrewritten, they throw or fall back. fromQuery's source throws "This DoubleValuesSource must be rewritten" (DoubleValuesSource.java:768); a REWRITEABLE field throws "SortField needs to be rewritten ..." (SortField.java:555-557). ValueSource#asDoubleValuesSource() returns new WrappedDoubleValuesSource(this, null) (ValueSource.java:184-186), so its context's "searcher" is null (:199-200, :74-78), and QueryValueSource then creates new IndexSearcher(ReaderUtil.getTopLevelContext(readerContext)) (QueryValueSource.java:114-125) with the default BM25 Similarity. On a default searcher the values agree by coincidence; with ClassicSimilarity, BooleanSimilarity or a BM25 with other k1/b they differ.
  4. Scope. In the silent form the main query still decides which documents match and the facet collectors see the same hits, so facet counts do not change; only the top-hit order and the returned sort values change. That is read from the code (the Sort reaches only the TopFieldCollectorManager); the minimal test asserts hits and sort values, not counts, and the diagram's probe on the same two documents shows red (2) from both helpers with and without the rewrite. In the loud forms the call throws, so there are no hits and no counts.

The numbers in the example

#

Under ClassicSimilarity doc1 (tf=1, length 1) scores 1.0 and doc0 (tf=8, length 10) scores sqrt(8)/sqrt(10) = 0.894. Under BM25 with its defaults (k1=1.2, b=0.75; idf ln(1.2) = 0.1823, average length 5.5), doc0 scores 0.1823 * 8/(8 + 1.2 * (0.25 + 0.75 * 10/5.5)) = 0.1468 and doc1 0.1823 * 1/(1 + 1.2 * (0.25 + 0.75/5.5)) = 0.1246. The helpers return exactly these BM25 values.

Exposure and likelihood237 words
  • Who can hit it. Callers of FacetsCollectorManager.search/searchAfter(..., Sort, ...) (before 10.0 also the static FacetsCollector.search/searchAfter(..., Sort, ...) helpers, deprecated only in 9.12.x and removed in 10.0) or DrillSideways.search(..., Sort, ...) whose Sort has a query-dependent field: DoubleValuesSource.fromQuery (core), the IndexReaderFunctions statistics docFreq and sumTotalTermFreq (found throwing by the exhaustive run; termFreq agreed everywhere), legacy ValueSource sorts from the queries module.   • Not hit. Field sorts, relevance sorts and index-order sorts; in the silent form, which documents match and the facet counts.
  • What it takes. Public API, default codec and IndexWriterConfig, two documents. The loud variants need only the sort; the silent one also needs a non-default searcher Similarity, a supported setting (ClassicSimilarity, BooleanSimilarity, or a BM25 with non-default k1/b).
  • Effect. Loud: a deterministic exception on the first search where IndexSearcher#search with the same Sort works.   • Workaround. Pass sort.rewrite(searcher) to the helper; the verifiers' caller-rewrite controls pass.

Why it looks unintended

#
  • The facet javadoc calls the helpers an "ordinary" search "by a specified Sort". Both hold the searcher, and no javadoc asks for a pre-rewritten Sort.
  • Core requires a rewrite "before it can be used for sorting" (SortField.Type.REWRITEABLE); IndexSearcher does it itself since 7.2.0.
  • LUCENE-7736 added the rewrite to IndexSearcher only: 7.1.0 and older agree, 7.2.0 and later differ.
The full argument380 words
  • The helpers' own contract. "The various FacetsCollectorManager#search utility methods are useful for doing an "ordinary" search (sorting by score, or by a specified Sort) but also collecting into a FacetsCollectorManager for subsequent faceting" (package-info.java:49-51). "Search, sorting by Sort, and computing drill down and sideways counts" (DrillSideways.java:187). "Utility method, to search and also populate a FacetsCollector with hits" (FacetsCollectorManager.java:166-169). No javadoc in either class, in TopFieldCollectorManager or on Sort#rewrite asks for a pre-rewritten Sort.
  • Core's contract. "To obtain a DoubleValues object for a leaf reader, clients should call rewrite(IndexSearcher) against the top-level searcher, and then call getValues(LeafReaderContext, DoubleValues) on the resulting DoubleValuesSource" (DoubleValuesSource.java:34-36). SortField.Type.REWRITEABLE: "Force rewriting of SortField using SortField#rewrite(IndexSearcher) before it can be used for sorting" (SortField.java:113-117). Both helpers receive the searcher with the Sort, so they have what the rewrite needs, and they document no precondition on the caller. Of the Lucene components in the call they are the only ones that have the searcher (TopFieldCollectorManager never sees it); the caller has it too, and rewriting there is the workaround.
  • Supporting context: LUCENE-7736. In LUCENE-7736 (#8787) Alan Woodward wrote on 2017-04-10: "we already have a Sort.rewrite() method, but it wasn't being called by IndexSearcher or SortRescorer, for example - but I think ends up with things being neater", and on 2017-10-19 "the only callers of rewrite are internal lucene classes". The quotes name IndexSearcher and SortRescorer as examples: they support having the search APIs that hold a searcher do the rewrite, but set no rule for every Sort consumer. The commit changed 25 files (among them IndexSearcher, DoubleValuesSource, LongValuesSource, ValueSource, IndexReaderFunctions, function queries and spatial value sources); of the Sort consumers only IndexSearcher was made to rewrite, no facet source changed, and its one facet file is the test TestRangeFacetCounts.
  • History, executed. The helpers never rewrote the Sort, but before 7.2.0 IndexSearcher did not either, so all APIs agreed (6.6.6, 7.0.0, 7.1.0). On 7.2.0, reverting only the new IndexSearcher line removes every difference, and adding the rewrite to the two helpers does too.
  • No test pins the current behaviour. The facet tests with a Sort use field sorts only; no test asserts that a consumer must reject an unrewritten Sort.
The devil's-advocate check382 words

The strongest case for "intended" (built by the devil's-advocate verifier and the cross-model reviewer's intended lens, both rating it moderate): before 7.2.0 every caller had to rewrite the Sort; the loud sources are documented to need it ("clients should call rewrite(IndexSearcher)", DoubleValuesSource.java:34-36; REWRITEABLE, SortField.java:113-117), the REWRITEABLE exception still tells the user to call Sort.rewrite(..) (SortField.java:555-557), and TestFunctionQuerySort still pre-rewrites its sort fields (:65-90, :127); Sort#rewrite and SortField#rewrite are @lucene.experimental (Sort.java:86, SortField.java:573); TopFieldCollectorManager and the grouping collectors take no searcher; the open #5619 calls the status quo an enhancement; the facet module documents that rewrite is never called on its Multi*ValuesSource wrappers ("The faceting use-cases don't call rewrite or provide scores", MultiDoubleValuesSource.java:41-47); in #12890 Greg Miller called the old helpers "a little trappy" (because they always count all hits, 2023-12-08) and Michael McCandless agreed to deprecate them without replacement (2024-01-04); the helpers never promise equivalence with IndexSearcher#search; and the silent form comes from a fallback in the legacy QueryValueSource, which builds its own default IndexSearcher when it has none (QueryValueSource.java:114-125), so a maintainer may prefer to change that fallback rather than the helpers.

Why it fails: the helpers receive the searcher and present themselves as an ordinary sorted search; the caller-rewrites convention is the pre-7.2 one that LUCENE-7736 replaced for IndexSearcher, and the same documented sources work unrewritten through IndexSearcher#search; the Multi* note concerns facet counting sources, which never get a searcher, not the Sort used to collect hits; the deprecation talk was about API shape and hit counting, nobody said the Sort may behave differently, and #13733 re-created the Sort helpers as supported API in 2024; #5619 was never rejected; changing the QueryValueSource fallback would not fix the loud forms, which throw in the helpers only. The fix also keeps the old convention working for the tested sorts: rewriting an already rewritten Sort gives identical hits, which IndexSearcher already does (Sort#rewrite is experimental and promises nothing about rewriting twice). Residual risk: the documented "caller must rewrite" lines make "caller misuse" a reasonable answer for the loud forms, and a maintainer may prefer deprecation or treat it as part of #5619; those are framing choices, not a ruling that the divergence is intended.

Suggested fix

#

Recommended Rewrite the Sort in both helpers, as IndexSearcher does

Rewrite the Sort in both helpers, as IndexSearcher does: pass sort.rewrite(searcher) to TopFieldCollectorManager in FacetsCollectorManager.doSearch and DrillSideways.search (2 files, +5/-2). The repro, TestDrillSideways, TestDrillDownQuery and :lucene:facet:check (307 tests) pass with it.

Trade-offs

  • One Sort#rewrite per call, the step IndexSearcher already takes; for field sorts it returns the same Sort (SortField.java:575-577, Sort.java:98). No benchmark was run.
  • A Sort the caller already rewrote (today's workaround) is rewritten again; for the tested sorts the hits are identical (the caller-rewrite control passes with the fix; IndexSearcher already re-rewrites such Sorts). Sort#rewrite is experimental and promises nothing about rewriting twice, so a custom SortField#rewrite could behave differently, as it already would in IndexSearcher.
  • A CHANGES.txt entry under Bug Fixes would be expected in a PR.

Document that the Sort must be pre-rewritten

#

Add to the javadoc of the helpers' Sort overloads that a Sort with query-dependent fields must be passed as sort.rewrite(searcher).

Trade-offs

No behaviour change; but the helpers stay the only sorted searches that hold the searcher and still differ from IndexSearcher#search, and the silent QueryValueSource case stays a trap that nothing reports.

Deprecate the Sort helpers

#

The direction maintainers once agreed on for the old FacetsCollector statics (#12890, open PR #13334).

Trade-offs

No fix for released versions; users then build TopFieldCollectorManager themselves, which never sees the searcher, so they must still remember the rewrite.

Make the silent QueryValueSource form throw

#

QueryValueSource could throw, as the other query-dependent sources do, instead of building a default IndexSearcher when its context has no searcher (QueryValueSource.java:114-125).

Trade-offs

The silent case would then fail loudly, but the helpers would still differ from IndexSearcher#search (they would throw where it sorts), and other code paths that reach QueryValueSource without a searcher would start to throw too; not analysed further.

Downstream note

#

Downstream relevance is limited to products that sort faceted results by a query score or function through these helpers: they get a clear exception, or, with a non-default Similarity, a different order of the same matching documents.

How it was found

#

A bounded-exhaustive translation-validation check ran 23 selected APIs that take a Sort or a values source on every tiny index (36 million runs) and compared each with the same API given the Sort or source pre-rewritten. It flagged both facet helpers, silently different or throwing, while IndexSearcher#search never silently differed. A public-API test confirmed it; independent verifiers reproduced it.

The method in full220 words

Method: semi-formal, bounded-exhaustive translation validation. On the stock main jars, with assertions off, the check enumerated every index of 1-3 documents over a 12-value per-document alphabet, every split into 1-2 segments and every deletion mask (42,648 index configurations), times 3 searcher Similarities (BM25, Classic, Boolean), times the 282 applicable (consumer, values source) pairs of 18 values sources and 23 consumer APIs (some consumers take only double or only long sources): 36,080,208 runs. Each run compared a consumer fed the raw Sort or source with the same consumer fed it pre-rewritten against the searcher, as the documented rewrite protocol prescribes.

It flagged FacetsCollectorManager.search and DrillSideways.search with a Sort. Under the Classic and Boolean Similarities every legacy QueryValueSource-based source tested was silently different through both helpers on some of the index configurations (29,832 of 42,648 for the plain asDoubleValuesSource() view; the rest gave the same hits). fromQuery-based sources and the IndexReaderFunctions statistics docFreq and sumTotalTermFreq threw (termFreq agreed everywhere). The control IndexSearcher#search(Query, int, Sort) was never silently different. A scan of every TopFieldCollectorManager construction outside IndexSearcher located the two construction sites, and a public-API JUnit witnessed both symptoms (2026-10-27). An independent reproducer, an independent reviewer from another model family (OpenAI GPT-5.6) and a devil's-advocate verifier each confirmed it with their own tests; the adjudication confirmed it with high confidence.

Related items, none a report of this defect:

  • #5619 (LUCENE-4553, open since 2012, no comments): "Don't require users to call Sort.rewrite()", a general wish that Lucene call Sort.rewrite() the way it calls Query.rewrite(). It predates the 7.2.0 change that made IndexSearcher rewrite, and names no consumer, no facet API and no symptom. LFV-814, snapshot of 2026-11-05

Registry title
FacetsCollectorManager#search/searchAfter with a Sort and DrillSideways#search(..., Sort, ...) never call Sort#rewrite(searcher), so a query-dependent sort returns a different hit order than IndexSearcher#search(query, n, sort) or throws
Area
facet / sorted-search helpers (FacetsCollectorManager static search/searchAfter, DrillSideways sorted search)
Priority
Medium, rank 216: The facet module's sorted FacetsCollectorManager and DrillSideways helpers skip Sort#rewrite, with correct facet counts and an easy sort.rewrite(searcher) workaround.
Impact class
silent wrong results
Impact note
Applications that run a faceted or drill-sideways search sorted by a query-dependent Sort through FacetsCollectorManager#search/searchAfter(..., Sort, ...) or DrillSideways#search(..., Sort, ...) and do not rewrite the Sort themselves are hit at any index size: a legacy QueryValueSource function sort (via asDoubleValuesSource) on a searcher with a non-default Similarity silently comes back in a different order with different sort values (in the repro the first hit changes), and DoubleValuesSource.fromQuery or ValueSource#getSortField sorts throw UnsupportedOperationException or IllegalStateException, while IndexSearcher#search with the same Sort works; field sorts, the common case, are unaffected, the matching documents and facet counts do not change, passing sort.rewrite(searcher) works around it, and every release from 7.2.0 to 10.6.0 has it.
Summary
You run a faceted search with FacetsCollectorManager.search(searcher, query, n, sort, fcm) or DrillSideways.search(query, filter, after, n, sort, doDocScores), sorted by a function of a query's score, and expect the same hits, order and sort values as IndexSearcher#search(query, n, sort), which rewrites the Sort against the searcher first. Instead both helpers hand the caller's Sort to TopFieldCollectorManager as given: on a ClassicSimilarity searcher a QueryValueSource(body:a) sort returns [doc0=0.147, doc1=0.125] (scores from a fresh default-BM25 searcher) where IndexSearcher#search returns [doc1=1.0, doc0=0.894]. A DoubleValuesSource.fromQuery sort throws 'This DoubleValuesSource must be rewritten' from both helpers, and a ValueSource#getSortField sort throws 'SortField needs to be rewritten'.
