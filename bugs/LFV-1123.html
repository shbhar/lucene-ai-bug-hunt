DateTools.round(Long.MIN_VALUE, DAY) returns a time in AD 292278994 instead of rounding down

For Long.MIN_VALUE, the usual "no lower bound" value, the start of its day lies below the long range, and DateTools.round(Long.MIN_VALUE, DAY) silently returns 9223372036794351616, a time in AD 292278994. A date range whose lower bound is rounded this way matches nothing.

The finding in 30 seconds

#
  1. You round the open lower bound of a date range: DateTools.round(Long.MIN_VALUE, Resolution.DAY). Long.MIN_VALUE is the value LongPoint's javadoc suggests for a half-open range; as a date it is 292269055 BC, Dec 2, at 16:47:04.192 in GMT.
  2. You expect a result no later than the input. The start of that day is 16.8 hours (60,424,192 ms) earlier, below the long range, so Long.MIN_VALUE itself is the closest possible answer.
  3. round sets hour, minute, second and millisecond to 0 on a lenient GregorianCalendar and reads the time back with getTimeInMillis(). The value below Long.MIN_VALUE wraps around by 2^64, unchecked.
  4. You get 9223372036794351616 (AD 292278994-08-16 14:25:51.616), 16.8 hours before Long.MAX_VALUE, with no error. A LongPoint range that found 1 document with Long.MIN_VALUE as its lower bound finds 0 with the rounded one.
  5. YEAR to SECOND do the same for any time before the first year, month, day, hour, minute or second boundary above Long.MIN_VALUE (up to 29.3 days for YEAR and MONTH, 7.2 h for DAY, down to 808 ms for SECOND); MILLISECOND never does. Real dates are never that close.

Who is affected

#

Only code that calls DateTools.round(long|Date, Resolution) directly with Long.MIN_VALUE (or new Date(Long.MIN_VALUE)) as a "no lower bound" sentinel, or a time within one unit above it. No setting is involved, and every release since 1.9 has it. Lucene's own string methods (timeToString, and dateToString through it) give wrong strings for such dates anyway (LFV-645).

Mechanism, terms and numbers377 words

DateTools.round(long, Resolution) and round(Date, Resolution) promise the input with every field finer than the resolution set to 0 or 1, so the result is never later than the input. For Long.MIN_VALUE (292269055 BC, Dec 2, at 16:47:04.192 in GMT) the start of its day lies 60,424,192 ms below the long range. round sets the fields on a lenient GregorianCalendar and returns getTimeInMillis() (DateTools.java:146-171 at 5adff78bb168), whose long arithmetic wraps by 2^64: round(Long.MIN_VALUE, DAY) is 9223372036794351616, AD 292278994-08-16 14:25:51.616, with no error and the same result with assertions on and off. YEAR to SECOND wrap the same way for every input before the first year, month, day, hour, minute or second boundary above Long.MIN_VALUE (up to 29.3 days for YEAR and MONTH, 7.2 h for DAY, down to 808 ms for SECOND). A LongPoint range whose open lower bound is rounded this way matches nothing. Every release since 1.9 (2006) has it.

The mechanism (main 5adff78bb168, lucene/core/src/java/org/apache/lucene/document/DateTools.java)

#
  1. A lenient calendar. round uses a per-thread Calendar.getInstance(GMT, Locale.ROOT) (:46-52), a GregorianCalendar, lenient by default, and loads the input with setTimeInMillis(time) (:148). The fields come out correct: BC 292269055, Dec 2, 16:47:04.192.
  2. Fields cleared. A deliberate fall-through switch sets every field finer than the resolution to 0 or 1 (:150-168); for DAY: hour, minute, second and millisecond.
  3. The read-back wraps. return calInstance.getTimeInMillis(); (:170, the fix site) recomputes the time from the fields. The true value, -9223372036915200000, is below Long.MIN_VALUE; the calendar's long arithmetic wraps by 2^64 and nothing checks it. Math.floorDiv(Long.MIN_VALUE, 86400000) * 86400000 gives the same value.
  4. Both overloads. round(Date, Resolution) is new Date(round(date.getTime(), resolution)) (:132-134).

Exposure and likelihood188 words
  • Who. Code that rounds the Long.MIN_VALUE sentinel, for example a helper that aligns both ends of a LongPoint date range to a resolution after filling an open start with Long.MIN_VALUE, the form LongPoint.newRangeQuery's javadoc suggests (LongPoint.java:202-203). The same sentinel-into-date-rounding slip happened in Elasticsearch's own code (elastic/elasticsearch #138757, #142725), so the pattern is real, though not in Lucene.
  • Effect. A silently wrong value: the lower bound becomes later than every real date. With one document dated 2004-09-21, LongPoint.newRangeQuery("date", Long.MIN_VALUE, day) counts 1 hit and the same query with the rounded bound counts 0.
  • Default vs opt-in. A plain public static utility; no setting.
  • Not hit. Real dates: the windows lie within 29.3 days of 292 million BC. Lucene's only production caller of round is timeToString (DateTools.java:91; dateToString reaches it through timeToString, :79). There the wrap shows as a far-future string, timeToString(Long.MIN_VALUE, DAY) = "2922789940816" (year 292278994); without the wrap the string would still be wrong for LFV-645's reason (years outside AD 1..9999), so the effect that matters is for code that calls round directly.
  • Scale. One call; no data, no concurrency.

Why it looks unintended

#
  • Both round overloads promise the input with finer fields "set to 0 or 1" and state no range or exception; the wrapped result reads 14:25:51.616 and is later than the input.
  • Lucene's DateRangePrefixTree already warns about this very Calendar underflow.
  • A non-lenient Calendar and java.time both throw instead of wrapping.
The full argument134 words
  • Contract. round(Date, Resolution) and round(long, Resolution) promise "the date with all values more precise than resolution set to 0 or 1" (DateTools.java:130, :142-143), with no range, precondition or @throws; the class javadoc states no range either (:28-41).
  • Tests. TestDateTools uses ordinary dates only (years 1961 to 2005, and 1970); nothing near Long.MIN_VALUE.
  • History. No commit on DateTools.java or TestDateTools.java mentions MIN_VALUE (git log -S'MIN_VALUE': 0 commits).
  • The project knows the pitfall. DateRangePrefixTree (spatial-extras, DateRangePrefixTree.java:47-48, from #6710 / LUCENE-5648): "Beware Calendar underflow of the underlying long. If you create a Calendar from LONG.MIN_VALUE, and clear a field, it will underflow and appear close to LONG.MAX_VALUE (BC to AD)."
  • Loud alternatives. A non-lenient Calendar throws IllegalArgumentException ("HOUR_OF_DAY: 0 -> 14"); Instant.ofEpochMilli(Long.MIN_VALUE).truncatedTo(DAYS).toEpochMilli() throws ArithmeticException: long overflow.
The devil's-advocate check130 words

The strongest case for "not a bug": no long can hold the floor; the JDK's Calendar.setTime javadoc warns that Date(Long.MIN_VALUE) may give incorrect field values; the class author wrote on java-user@ in 2006 "There is no limit on the given dates in DateTools (within the limits of what Java's Calendar/Date class can do)"; and a sentinel is not a date.

Why it fails: Lucene documents none of this to its callers. The JDK caveat is about the fields read with get(), which are correct here; the wrap happens later, in getTimeInMillis. Jumping silently to the far end of the range is worse than either loud alternative. The argument does bear on likelihood, hence priority Low; a credibility audit also rated it real but minor, with a small fix.

Suggested fix

#

Recommended Saturate to Long.MIN_VALUE when the result would be later than the input (fix A)

Return Long.MIN_VALUE when the rounded time comes out later than the input, which in the scope probe happened only when the floor lies below the long range (+6/-1 in DateTools.java, with one javadoc sentence). The repro passes with assertions on and off; the repro, TestDateTools, two date-sort and four query-parser suites: 182 tests, 0 failures, 1 skipped by its suite.

    final long rounded = calInstance.getTimeInMillis();
    // a start below Long.MIN_VALUE wraps around to a time near Long.MAX_VALUE
    return rounded > time ? Long.MIN_VALUE : rounded;
All options and trade-offs3 options · 451 words

Option A was built and checked through gradle on 5adff78bb168; B and C were not run. By construction the fix changes only results later than their input. In a scope probe on unpatched main the check fired only at the wrap: of 35,377,755 sampled inputs (uniform over the whole long range, years about 1653 to 2286, the 1582 calendar switch at about 1-minute steps, and both ends), round(t, r) > t held for 6, all Long.MIN_VALUE at YEAR to SECOND (a sample, not a proof over every long).

Saturate to Long.MIN_VALUE when the result would be later than the input (fix A) (validated by the checks) (recommended)

#

A result later than the input is exactly the bad outcome, and in the scope probe it came only from a floor below the long range, so check exactly that after getTimeInMillis(), and say so in the javadoc of round(long, Resolution). Saturating is a policy choice, not the only correct answer: at Long.MIN_VALUE no long can meet the literal @return, and throwing is the other reasonable choice.

    final long rounded = calInstance.getTimeInMillis();
    // a start below Long.MIN_VALUE wraps around to a time near Long.MAX_VALUE
    return rounded > time ? Long.MIN_VALUE : rounded;

Trade-offs

At Long.MIN_VALUE the result is not at midnight, so the literal @return still cannot hold there (no long can); the added javadoc sentence says so. As a range lower bound it is exactly right, since no long lies below it, so a rounded open bound stays open, and the repro passes unchanged as the regression test. Lucene saturates range bounds the same way in Lucene90DocValuesProducer.saturatingShiftLower (Lucene90DocValuesProducer.java:585-600).

Throw IllegalArgumentException instead (not built)

#

The same check with throw new IllegalArgumentException(...) in place of the clamp.

Trade-offs

Fails loudly, like java.time and a non-lenient Calendar, but turns today's silent value into an exception for timeToString/dateToString callers too, and the regression test has to expect the exception (expectThrows) instead.

Document the supported range only (not built)

#

State in the javadoc of both round overloads that inputs less than one unit above Long.MIN_VALUE are not supported (a simple bound that covers every input that wraps).

Trade-offs

Smallest change, and it could go with LFV-645's documentation of years AD 1..9999, but callers who do not read it still get the far-future value.

Downstream note

#

Downstream, a date restriction written as a range whose open lower bound Long.MIN_VALUE is first passed through DateTools.round matches nothing, so a rule built that way silently covers no documents.

How it was found

#

A proof-obligation audit of DateTools.round's contract: the result must be the input with its finer fields set to 0 or 1, so never later than the input, for every long. At Long.MIN_VALUE that floor is not representable; a one-call public-API JUnit test then witnessed the wrapped value.

The method in full123 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The finder read both round overloads against their @return obligation and the domain they accept (any long, any Date; no range, precondition or @throws). The obligation "not later than the input" needs a representable floor; for times before the first unit boundary above Long.MIN_VALUE there is none, and the code reads the time back without a check.
  • The finder then wrote a public-API JUnit test that fails on main with assertions on and off and on 10.6.0.
  • An independent reproducer, two executed cross-model reviews and a devil's-advocate verifier reproduced it with their own tests, and an adjudication re-ran the reproducer's test ("Prior reports, history and checks").

Summary
