DirectIODirectory (experimental, opt-in) ignores the byte count FileChannel.write returns: a short final write leaves a truncated file without an exception

DirectIODirectory is an experimental, opt-in class of lucene/misc. Its output ignores the byte count FileChannel.write returns, so when the operating system writes only part of a file's last buffer (a process file-size limit does this), close() returns normally on a truncated file, where FSDirectory throws File too large.

The finding in 30 seconds

#

The output collects bytes in a 262,144-byte buffer and hands each buffer to FileChannel.write in one call. The JDK passes the operating system's count through, and that count can be smaller than the request. The output drops it and counts the whole buffer as written. close() then only truncates, which never makes a file longer.

Background: three pieces

#
  1. DirectIODirectory wraps an FSDirectory. Files opened with a merge context are written with direct I/O, which bypasses the operating system's file cache; with the defaults, IndexWriter sends only the files of merges estimated at 10 MB or more that way. Everything else goes to the wrapped directory.
  2. Direct I/O writes whole blocks. The output therefore writes its last buffer with padding after the data, and close() cuts the padding off with truncate.
  3. A write to a file can be short: the operating system writes fewer bytes than asked and returns that count. At a process file-size limit, the write that crosses the limit is short. Only a write that starts at or past the limit fails with File too large.

The finding, step by step

#
  1. You wrap your index directory in DirectIODirectory, an experimental, opt-in class of lucene/misc that writes the files of large merges with direct I/O. The process has a file-size limit: ulimit -f 384 in bash, which is 393,216 bytes.
  2. Write 400,000 bytes to one output opened with a merge context, as a merge does, and close it. You expect what plain FSDirectory does under the same limit: IOException: File too large.
  3. Instead nothing is thrown. close() returns, and the file has 393,216 bytes: 6,784 short. The output handed its last buffer to FileChannel.write in one call. The operating system wrote up to the limit and returned the smaller count. The output never reads that count, and the truncate in close() cannot make a file longer.
  4. In a forced merge of a 12 MB index with the limit inside the last buffer of the merged file, forceMerge(1) and close() return normally, _2.cfs has 12,238,848 of 12,242,609 bytes, the source segments are deleted, and DirectoryReader.open throws CorruptIndexException: codec footer mismatch (file truncated?). Through FSDirectory the merge fails with File too large and the index keeps its 600 documents.
  5. The window is narrow. The limit must fall inside the data of the file's last buffer (262,144 bytes by default). A limit in an earlier buffer, or a whole multiple of the buffer such as 1 MiB, fails loudly with File too large. Linux sets no such limit unless a login or service configuration does, and a full disk was not shown to cause it.

Who is affected

#

Applications that wrap their index directory in DirectIODirectory (opt-in, lucene/misc, experimental), under a finite file-size limit that falls inside the last buffer of a merged file. Linux sets no such limit unless a login or service configuration does; with the default buffer, a limit in whole MiB or GiB is never silent. Low priority: severe outcome, very narrow reach.

Mechanism, terms and numbers1,707 words

DirectIODirectory is an experimental, opt-in wrapper in lucene/misc (@lucene.experimental; its javadoc warns "this code is very new and quite easily could contain horrible bugs" and "Use at your own risk"). It writes the files of merges with direct I/O; by default it takes over for a merge context whose estimated size is at least 10 MB or, since 10.6.0, unknown. Its output collects bytes in a buffer of 262,144 bytes and hands each buffer to the file channel with one call, channel.write(buffer, filePos); (DirectIODirectory.java:267-277 on main 781025d6fe32). The count that call returns is dropped and the file position moves on by the full size. close() writes the last buffer the same way and then truncates the file to the bytes written (:290-301); a truncate never extends a file. So when the operating system writes only a part of that last buffer, close() returns normally on a file that is shorter than the bytes written.

The one cause that was produced is a per-process file-size limit (ulimit -f, a service's file-size limit; Linux sets none unless a login or service configuration does). The write that crosses the limit transfers the bytes up to it and returns that count; only a write that starts at or past the limit fails with File too large. With nothing injected, on stock jars and a real directory: under a limit of 393,216 bytes a 400,000-byte output ends with 393,216 bytes and no exception, where plain FSDirectory throws IOException: File too large. In a forced merge of a 12 MB index with the limit inside the last buffer of the merged file, forceMerge(1) and close() return normally, the committed _2.cfs is 3,761 bytes short, the source segments are deleted and the index fails to open with CorruptIndexException: codec footer mismatch (file truncated?); through FSDirectory the merge fails with File too large and the index keeps its 2 segments and 600 documents.

The window is narrow: the limit must fall inside the data of the file's last buffer and be a multiple of the device's sector size. A limit in an earlier buffer fails loudly, a limit past the data is harmless, and a limit that is a whole multiple of the buffer (with the default buffer, every limit in whole MiB or GiB) can never be silent. A full disk, a quota or a network file system were not shown to cause it. Priority Low.

Today's class is from LUCENE-8982 (a7747b63b4a, 2021, first in 9.0.0); the single unchecked write was carried over from the class's first form (LUCENE-2500, 2010). Every release from 9.0.0 to 10.6.0, branch_11x and main have it; it is not new in 11.0. A validated fix of 11 added lines keeps writing until the data bytes are out and throws when a write makes no progress.

Terms

#
  • DirectIODirectory. "A Directory implementation for all Unixes and Windows that uses DIRECT I/O to bypass OS level IO caching during merging." The javadoc continues: "WARNING: this code is very new and quite easily could contain horrible bugs", "Use at your own risk", @lucene.experimental (DirectIODirectory.java:45-61). An application opts in with new DirectIODirectory(FSDirectory.open(path)).
  • When the output is used. createOutput returns the direct-I/O output when useDirectIO says so: a merge context, and a merge whose estimated size is at least minBytesDirect (10 MB by default) or unknown (:168-173, :186-194, :72). A merge context without a size exists since 10.6.0 (#16749); IndexWriter's own merge contexts carry an estimate (IndexWriter.java:4113, :5776, :5995).
  • The buffer. One block-aligned buffer of mergeBufferSize bytes, 262,144 by default (:69, :233). writeBytes fills it and calls dump() each time it is full (:249-265).
  • A process file-size limit. The operating system's per-process limit on the size of files the process may write (ulimit -f in a shell, a file-size limit in a service definition). bash counts the value in blocks of 1,024 bytes, so ulimit -f 384 is 393,216 bytes. Linux sets none unless a login or service configuration does: the kernel starts the first process without a file-size limit and a process inherits its parent's limits (the kernel's INIT_RLIMITS; getrlimit(2)). On the machine used ulimit -f prints unlimited. No survey of distributions or service managers was made.

The bug

#
  1. dump() (DirectIODirectory.java:267-277) takes size = buffer.position(), rewinds the buffer and calls channel.write(buffer, filePos); (:273). The returned count is not stored or compared. Then filePos += size; (:274).
  2. close() (:290-301) calls dump() for the last, partly filled buffer. The whole buffer is written, data plus padding, because direct I/O needs whole blocks. Then ch.truncate(getFilePointer()) cuts the padding off (:297). A truncate shortens a file that is too long and leaves a file that is too short as it is.
  3. The JDK's file channel makes one pwrite call per write and returns its count; it does not loop on a short count and repeats only an interrupted call (OpenJDK 25, FileChannelImpl.java:1249-1272, IOUtil.java:113-145).
  4. At a process file-size limit the operating system writes the bytes up to the limit and returns that count. Only a write that starts at or past the limit fails with File too large. Executed without Lucene: under a limit of 393,216 bytes, FileChannel.write of 262,144 bytes at position 262,144 returns 131,072 and throws nothing, with and without the direct option; the same write at position 393,216 throws IOException: File too large.
  5. So a short write in an earlier buffer is followed by a loud failure: dump() has moved the position on by the full buffer, so the next buffer's write starts past the limit (executed: under a limit of 131,072 bytes the first write stops at 131,072 and the next one, at position 262,144, throws File too large). A short write in the last buffer is followed by nothing. There is no next write, and the truncate does not notice.
  6. FSDirectory's output writes through Files.newOutputStream (FSDirectory.java:370-402). The JDK stream behind it calls the channel until every byte is out (ChannelOutputStream.java:66-72), so its retry starts at the limit and throws.
  7. IndexWriter treats an output that closed normally as written. It commits the merged segment and deletes the segments it replaces. The cut shows only when the file is opened and its footer is checked (CodecUtil.java:587: "codec footer mismatch (file truncated?)").

The window, exactly

#

With n bytes written, buffer size C and limit L, the cut is silent when floor(n/C)*C < L < n and L is a multiple of the device's logical sector size (512 bytes on the machines used). Seen from the limit: L < n < ceil(L/C)*C, so the file must end before the next buffer boundary above the limit. For a limit that is not a multiple of C, that means less than C - (L mod C) bytes over the limit. For a limit that is a multiple of C no size is silent, and every limit in whole MiB or GiB is one with the default buffer.

In a merge

#

600 documents with 20,300 random stored bytes each, in 2 segments (about 6 MB each). Without a limit, forceMerge(1) writes _2.cfs with 12,242,609 bytes; its last buffer starts at byte 12,058,624. Under ulimit -f 11952 (12,238,848 bytes), with a default IndexWriterConfig:

  • Through DirectIODirectory. forceMerge(1) and close() return normally. The only index files left are _2.cfe, _2.cfs (12,238,848 bytes, 3,761 short), _2.si and segments_3. DirectoryReader.open throws CorruptIndexException: codec footer mismatch (file truncated?).
  • Through FSDirectory. forceMerge(1) throws, and the root cause is java.io.IOException: File too large in every run. The exception around it differs between runs, because the merge runs in its own thread: either IOException: background merge hit exception: ... or IllegalStateException: this writer hit an unrecoverable error; cannot complete forceMerge (20 further runs on main and branch_11x: 15 and 5). The directory still holds _0 and _1 with segments_2, and the index opens with 2 segments and 600 documents.

Lucene detects the cut file when the index is opened, so no wrong result is returned. The index no longer opens and the segments the merge replaced have been deleted; whether anything can be recovered from what is left of the merged file was not looked at.

Exposure and likelihood389 words
  • Who. Applications that wrap their index directory in DirectIODirectory. The class is opt-in, in lucene/misc and marked @lucene.experimental. With the defaults, IndexWriter sends only the files of merges estimated at 10 MB or more through this output.
  • What else it needs. A finite per-process file-size limit. Linux sets none unless a login or service configuration does. The limit must fall inside the data of the last buffer of a merged file (at most 262,144 bytes with the default buffer) and be a multiple of the device's sector size.
  • Outcome when it hits. Nothing at write time. forceMerge and close() return normally, the commit names the short file, the source segments are deleted, and the index no longer opens (CorruptIndexException: codec footer mismatch (file truncated?)). No wrong result is returned. The segments the merge replaced are gone from the directory; whether anything can be recovered from the cut file was not looked at.
  • What an operator would almost always see first. The loud case. A merged file that passes the limit by more than the window fails with File too large, exactly as with FSDirectory.
  • Never with a round limit. A limit in whole MiB or GiB is a multiple of the 262,144-byte buffer and cannot be silent (executed: limits of 262,144 and 1,048,576 bytes here; 5 of 5 such runs in an earlier check).
  • Scale. None beyond a merge of 10 MB. One thread. Assertions on and off.
  • Likelihood: contrived (an estimate, not usage data). It needs three things at once: the opt-in class, a finite file-size limit, and a merged file that ends above that limit and before the next buffer boundary. The limit itself occurs in practice: a java-user thread of 2012 shows a merge under FSDirectory failing with File too large because of a shell's file-size limit. No report of the silent case was found, although the class has been released since 9.0.0 (2021).
  • Not claimed. A full disk, a quota, the file system's maximum file size, or a network or FUSE file system as a cause (no short write was produced with any of them). A short write in an earlier buffer followed by successful writes. The read side: DirectIOIndexInput.fill also drops the count of channel.read (DirectIODirectory.java:496-510), and nothing was shown there. Windows and macOS (not run).

Why it looks unintended

#
  • close() returned normally, so IndexWriter committed the merged segment and deleted its sources. Every other in-tree output writes all bytes or throws.
  • The wrapped FSDirectory throws File too large under the same limit.
  • The JDK's maintainers say a caller of FileChannel.write must use the count and call again (JDK-8274549); JDK 26 rewrote the javadoc to say so.
The full argument339 words

No javadoc sentence spells out "all bytes or an exception" for an IndexOutput (DataOutput.writeBytes says "Writes an array of bytes"). It is the implicit contract that every other in-tree output keeps and that IndexWriter relies on when it commits a merged segment and deletes its sources. So this is not a broken javadoc promise; the intent is in the code around it and in its history.

  • The wrapped directory is loud. FSDirectory under the same limit throws IOException: File too large, for a single output and for a forced merge.
  • What forceMerge intends. "If an Exception is hit, for example due to disk full, the index will not be corrupted and no documents will be lost" (IndexWriter.java:2215-2216). This shows the intent. It is not a broken promise: the sentence starts "If an Exception is hit", and here none is hit. That is the defect.
  • A precedent in Lucene. LUCENE-2537 (#3611, 2010, fixed in 3.1 and 4.0), "FSDirectory.copy() impl is unsafe". Shai Erera: "FileChannel.transferFrom documents that it may not copy the number of bytes requested, however we don't check the return value. So need to fix the code to read in a loop until all bytes were copied." The same kind of defect in another method, filed as a bug and fixed with a loop.
  • Defects of this class are handled as bugs. LUCENE-9686 ("Fix read past EOF handling in DirectIODirectory") and GITHUB#14320 are listed under "Bug fixes" in lucene/CHANGES.txt (:5065-5066, :2109).
  • History. The single write is from the class's first form (LUCENE-2500, 2010) and was carried through two rewrites. The threads of LUCENE-2500, LUCENE-2795 and LUCENE-8982 and the discussion of apache/lucene-solr#2052 do not mention the returned count. On that pull request Uwe Schindler wrote (2020-12-19): "I am not sure if the truncate is still needed, but I left it for now."
  • Why no test saw it. dump() is the only place where Lucene's production code writes to a FileChannel, and no file system of the test framework returns a short count.
The devil's-advocate check266 words

The strongest case for "intended": the JDK javadoc that FileChannel.write inherits says "Unless otherwise specified, a write operation will return only after writing all of the r requested bytes" (WritableByteChannel.java:68-72), so a caller could assume that a file channel writes everything or throws. The class is experimental and warns "Use at your own risk". And one system call per buffer is how the class has worked since 2010.

Why it fails: the same javadoc goes on "Some types of channels, depending upon their state, may write only some of the bytes or possibly none at all", and both write methods say "@return The number of bytes written, possibly zero". The JDK's file channel passes the operating system's count through: executed without Lucene, it returns 131,072 of 262,144 bytes at a file-size limit and throws nothing. The OpenJDK record JDK-8274549 (2021, a FileChannel on Linux, closed "Not an Issue") says "Short writes are allowed, so the calling code should re-invoke the write method", and JDK 26 rewrote the sentence (JDK-8369854): the write method "may need to be invoked more than once". The JDK's own stream over the same channel loops. The class warning lowers what a user can expect, which is why this is Low; it does not say that written bytes may be dropped without an exception. Age is not intent: nobody discussed the count, and the first version already had the truncate that hides the short file. A maintainer may still treat it as a small robustness fix for an experimental class and not as an urgent report; that is a fair reading.

Suggested fix

#

Recommended Write until the data is out (validated)

In dump(), call channel.write again until the data bytes of the buffer are written, and throw an IOException when a call writes nothing. One method, 11 added lines. Validated: the test passes, the misc.store package and the whole lucene/misc test module have no failure, and under a real limit the merge fails with File too large, like FSDirectory.

      // FileChannel#write may write fewer bytes than requested: write until the data is out
      // (the padding after the data is truncated in close(), so it does not have to arrive)
      int written = 0;
      while (written < size) {
        final int n = channel.write(buffer, filePos + written);
        if (n <= 0) {
          throw new IOException(
              "wrote " + n + " bytes at position " + (filePos + written) + ": " + this);
        }
        written += n;
      }
      filePos += size;

Write until the data is out (validated) (recommended)

#

One method, 11 lines added, 1 removed. dump() keeps calling channel.write until the size data bytes of the buffer are written. A call that writes nothing throws an IOException. The padding after the data may be cut short, because close() truncates it anyway.

The no-progress check answers a concern Uwe Schindler raised on elastic/elasticsearch#6576 (2014): a write loop must not spin when a write keeps returning 0.

The excerpt replaces the single channel.write(buffer, filePos); in dump().

      // FileChannel#write may write fewer bytes than requested: write until the data is out
      // (the padding after the data is truncated in close(), so it does not have to arrive)
      int written = 0;
      while (written < size) {
        final int n = channel.write(buffer, filePos + written);
        if (n <= 0) {
          throw new IOException(
              "wrote " + n + " bytes at position " + (filePos + written) + ": " + this);
        }
        written += n;
      }
      filePos += size;

Trade-offs

  • A successful write is unchanged, with one exception: an empty buffer is no longer written at all. Today close() writes a whole buffer of padding even when the buffer is empty and truncates it afterwards. One visible effect: today an output that is exactly one buffer long and ends exactly at the limit fails with File too large although every byte is on disk; with the fix it completes, as FSDirectory does (executed).
  • The message at the limit. When the short count is a block multiple, the retried write starts at the limit and fails with the operating system's File too large. When it is not, the JDK rejects the retry with Channel position (...) is not a multiple of the block size (4096). Both are IOExceptions.
  • New. It was built for this page and has had this page's runs, not the earlier independent checks that the second option had.

Write only the blocks that hold data, until they are out (validated; one harmless case becomes an exception)

#

The earlier sketch of this finding: 13 lines added, 2 removed (git diff --stat of the tree after applying it counts 14 and 3). A blockSize field, the buffer's limit set to the data rounded up to a whole block, and while (buffer.hasRemaining()) with the same no-progress check.

Trade-offs

With a limit that lies past the data but inside the data's last 4,096-byte block and is not a block multiple, the loop retries a write that only carries padding. Executed: under ulimit -f 391 (400,384 bytes) with 400,000 bytes of data, every data byte is on disk, the stock class and FSDirectory complete without an exception, and this fix throws IOException: Channel position (400384) is not a multiple of the block size (4096). The first option stops once the data is out.

What the checks validated

The same steps and the same counts as the first option (the whole-module run with assertions on only), and the 612-case model with 0 silent cases. Earlier independent re-runs also passed their own tests and both upstream DirectIODirectory suites with it.

Throw on a short count, no retry (not built)

#

Compare the returned count with the data size and throw an IOException when it is smaller. Three lines.

Trade-offs

Loud in exactly the right cases, but a short write that a retry would complete becomes a failure, and the message is Lucene's own instead of the operating system's reason. Not built.

No code change

#

Leave the output as it is and keep this as a record.

Trade-offs

Defensible for an experimental class and a contrived trigger. The output keeps dropping the count, and when it hits, nothing reports it.

Downstream note

#

Elasticsearch has a subclass of this class and can write merge-time raw-vector files through this output when a mapping option is on (default off), but Elasticsearch and OpenSearch refuse to start in production mode unless the file-size limit is unlimited, so the produced cause cannot occur on such a node (read, not executed).

How it was found

#

Semi-formal. A fault-injection harness under Lucene's file-system directories fails the n-th file-system call. While a fault for a write that returns a short count was being added, dump() was read and seen to drop the count; the harness then flagged all 3 write positions of its direct-I/O leg. The defect was then produced under a real file-size limit.

The method in full236 words

Method: semi-formal (fault injection on the real jars, then a bounded reference model).

  • The harness. A java.nio.file provider that sits under the real FSDirectory family and fails the n-th file-system call. With faults that throw, its leg for DirectIODirectory outputs showed nothing (5 positions, 0 violations).
  • The signal. While the fault kind for a partial FileChannel.write(ByteBuffer, long) was written, DirectIOIndexOutput.dump was read and the dropped count was seen. With a short-write fault kind the harness reports all 3 write positions of the leg (3 fired, 0 threw, 3 violating).
  • A real cause. The defect was then produced with nothing injected, under a per-process file-size limit, for a single output and for a forced merge.
  • The model. A reference model of the output under a size limit (silent exactly when the limit lies above the start of the last buffer and below the end of the data) was checked against the real class on 612 (size, limit) cases: 0 mismatches after two corrections of the model, 23 silent cases; two vacuity runs mismatch as they should. No model checking, SMT solving or proof tool was involved.
  • Reduction. The first test used a file system that writes one block per call. Independent checks replaced it with a file system that models the produced cause (a short count at the limit, then File too large), and a minimality check cut it to the one-method test of the repro.

Finding record

LFV-1500, snapshot of 2026-11-21

Registry title
DirectIODirectory's output ignores the byte count that FileChannel.write returns, so a short write in the output's final flush (produced with a process file-size limit) leaves a truncated file without any exception; a forced merge then commits the truncated file, deletes the source segments, and the index no longer opens (since 9.0.0)
Area
misc / store: DirectIODirectory (direct I/O for merge files): the output's flush to the file channel
Priority
Low, rank 1002: In every release since 9.0.0, a merge through DirectIODirectory commits a truncated segment file without any error when the process's file-size limit cuts the last buffer of the merged file, so the index no longer opens and the segments the merge replaced are deleted. It is Low because the class is opt-in and experimental, Linux sets no file-size limit unless a login or service configuration does, and the limit must fall inside the final buffer (262,144 bytes by default) of a merged file, which with the default buffer a limit in whole MiB or GiB never does, while a limit anywhere else fails loudly or does no harm.
Impact class
index unusable
Impact note
Hits applications that wrap their index directory in DirectIODirectory (opt-in, lucene/misc, @lucene.experimental; it takes over for a merge context whose estimated size is at least 10 MB or, since 10.6.0, unknown; with the defaults IndexWriter sends only the files of merges estimated at 10 MB or more through it), and only when the operating system writes just a part of the final buffer of such a file; the one cause produced is a per-process file-size limit (ulimit -f, a service's file-size limit; Linux sets none unless a login or service configuration does) that falls inside the data of the last buffer (262,144 bytes by default) of a merged file and is a multiple of the device's sector size: forceMerge and close() return normally, the merged file is cut short, the commit names it, the source segments are deleted and the index no longer opens (CorruptIndexException 'codec footer mismatch (file truncated?)'); what can be recovered from the cut file was not looked at; plain FSDirectory under the same limit fails with 'File too large' and keeps the index; a limit anywhere else in the file fails loudly or does no harm; no scale beyond a merge of 10 MB; every release since 9.0.0, branch_11x and main [exec on 8 of the 34 releases and on both branches, see Affected versions; the others by reading the source and the bytecode of the released jars]; on 9.0.0, 9.12.3, 10.5.2, 10.6.0, branch_11x and main the same with -ea and -da.
Summary
You merge an index through DirectIODirectory (an opt-in, experimental directory of the misc module that uses direct I/O for merges) in a process that has a file-size limit (ulimit -f), and the limit falls inside the last buffer of a merged file. You expect what FSDirectory does under the same limit: the merge fails with 'File too large' and the index stays as it was. Instead the operating system writes only the bytes up to the limit, the output drops the count that FileChannel.write returns, close() succeeds on a file that is too short, IndexWriter commits the merged segment and deletes its sources, and the index no longer opens (CorruptIndexException 'codec footer mismatch (file truncated?)').

Everything in Lucene is simple OutputStreams (FileOutputStream)' and warned that a write loop must not spin when a write returns 0; Lucene's direct-I/O output is not mentioned. #6623 (LUCENE-5561, 'NativeUnixDirectory is broken', open since 2014): lists the old class's faults (alignment, the exception for a missing file, no test, checksum buffering); the write count is not among them. #10025 (LUCENE-8982) with apache/lucene-solr#2052: the change that wrote today's dump(); 68 review comments, 70 comments and 62 reviews read, the count is never raised. #3574 (LUCENE-2500) with #3689, #3861 and #3869: origin and early history of the single write; not discussed. #12185 (BufferOverflowException with a buffer size that is not a block multiple; this site's finding LFV-226), #10827 (LUCENE-9788, file systems without direct I/O), #6135 (LUCENE-5071, input side) and #15224 (closed, reads): other code. A java-user thread of 2012-09, 'MergeException: java.io.IOException: File too large' (lists.apache.org thread ow4pzjlhxtyd712s81nf8xzx750636st), shows the trigger in practice: a merge under FSDirectory failed because the user's shell had a file-size limit (Mike McCandless suggested checking it with ulimit -f); it says nothing about the direct-I/O class. Downstream: no Elasticsearch, OpenSearch, Solr or Lucene.NET issue or PR describes it; elastic/elasticsearch#155919 (merged 2026-09-23) uses the output and does not mention short writes. Not fixed upstream: main is still 781025d6fe32 and branch_11x still daa54f2e0cd3 (git ls-remote 2026-11-14).
