Stempel: Trie.reduce with Gener or Lift rewrites the trie it is given, even PolishAnalyzer's shared default table

Reducing Stempel's shared Polish table with PolishAnalyzer.getDefaultTable().reduce(new Gener()) also rewrites that table, so every Polish analyzer in the JVM stems differently afterwards: 'książkami' becomes 'książk' instead of 'książek'. Lift does the same to tries that are not lifted yet; every release since 3.1.0 is affected.

The bug in 30 seconds

#

Stempel keeps its stemmer table as a trie of rows and cells. Lift and Gener shrink a trie by rewriting cells, and they do it on the input's own rows before copying them into the result. So the input is changed too, and for the shared Polish table that change reaches every analyzer in the JVM.

  1. You want a smaller Polish stemmer table and call PolishAnalyzer.getDefaultTable().reduce(new Gener()). The javadoc calls that table "unmodifiable", and reduce returns "the newly reduced Trie".
  2. You expect the shared table, and so every other PolishAnalyzer, to stay as it was: "książkami rzekami pracowali" still stems to [książek, rzekść, pracować].
  3. Instead Gener clears rare commands in the shared table's own cells, 42,134 of its 121,822, before it copies the rows into the new trie. 'książkami' loses the last piece of its command, Ie (insert e): that piece had count 2 in a row whose threshold is 4, a tenth of its total 43.
  4. From then on every new PolishAnalyzer gives [książk, rzekami, pracowali], with no error, for as long as the class stays loaded (normally until the JVM exits). A document indexed before the call with 'książkami' is no longer found by the query 'książkami': 1 hit before, 0 after.
  5. Lift does the same to a trie that is not lifted yet: after reduce(new Lift(false)) of a trie that holds only aa -> Da, the input itself answers Da for the word 'a'. Optimizer and Optimizer2 leave their input alone.

Who is affected

#

Only applications whose own code calls reduce(new Gener()) or reduce(new Lift(..)) on a trie they keep using, for example on PolishAnalyzer.getDefaultTable(): then every PolishAnalyzer and stempelPolishStem factory in the JVM stems differently. Normal analysis, the factory and the Compile tool never do this, and no public caller of getDefaultTable().reduce was found.

Mechanism, terms and numbers651 words

Trie.reduce(Reduce) is documented to "return the newly reduced Trie", and PolishAnalyzer.getDefaultTable() "Returns an unmodifiable instance of the default stemmer table". But Lift.optimize and Gener.optimize work on the input's own list of rows (List<Row> orows = orig.rows;) and rewrite its cells in place (Lift moves a child row's command up into the parent cell and cuts the link; Gener drops infrequent commands, and links to rows left empty) before they copy the rows into the returned trie. The input trie answers differently afterwards. For the shared default table this is visible in the whole JVM: after getDefaultTable().reduce(new Gener()) every new PolishAnalyzer, and every stempelPolishStem factory stream, stems "książkami rzekami pracowali" to [książk, rzekami, pracowali] instead of [książek, rzekść, pracować]. Optimizer and Optimizer2 leave their input unchanged. Only application code that calls reduce triggers it; every release from 3.1.0 (the default-table form from 4.0.0) to 10.5.2 and main is affected. Copying the rows first fixes it; upstream TestStemmer, which reduces one trie five times in a row, then needs one entry made explicit.

Terms

#
  • Trie, row, cell. Stempel's table is a trie: one row per node, and in each row one cell per next character. A cell holds cmd (an index into the list of patch commands that turn a word into its stem), ref (the child row, or -1), skip and cnt (a frequency count). Stemming walks the word through the trie with getLastOnPath and applies the last command it finds.
  • Patch command. Read from the end of the word: Dc-aIe is delete 3 letters, skip 1, insert e, so książkami -> książek.
  • Reduction. trie.reduce(r) calls r.optimize(trie). Optimizer and Optimizer2 merge rows; Lift moves a command shared by a whole child row up into the parent cell; Gener drops commands that are rare in their row.

The bug

#
  1. Lift.optimize takes the input's own list, List<Row> orows = orig.rows; (Lift.java:92), and calls liftUp on every row. liftUp writes skip, cnt, cmd and ref = -1 into those cells (Lift.java:114-146).
  2. Gener.optimize does the same (Gener.java:81): eat sets ref = -1 on a link to a row that became empty and clears cmd and cnt of a cell whose count is under a tenth of its row's total (Gener.java:105-129).
  3. Only then does Reduce.removeGaps copy each reachable row into a new Remap row with new Cell objects (Reduce.java:88-128). The result shares nothing with the input; the input keeps the rewritten cells.
  4. Optimizer builds its new rows before it changes anything (Optimizer.java:86), so it never writes its input.
  5. PolishAnalyzer.getDefaultTable() returns one static MultiTrie2, loaded once; every PolishAnalyzer and StempelPolishStemFilterFactory stems with it (PolishAnalyzer.java:60-63, :121; StempelPolishStemFilterFactory.java:50). MultiTrie2.reduce reduces every sub-trie (MultiTrie2.java:279), so all of them are rewritten.

Exposure and likelihood270 words
  • Who is hit. Applications that call reduce with Gener or Lift on a trie they keep using. Two plausible shapes: reducing getDefaultTable() to get a smaller table for a custom StempelStemmer, which silently changes every Polish analyzer in the JVM; or trying several reductions on one table being built, as Lucene's own TestStemmer does, where each reduction runs on what the previous one left.
  • Not the default path. Stemming only reads the table (getLastOnPath), and Compile always does trie = trie.reduce(..) and drops its input. A public code search found no getDefaultTable().reduce caller and only copies of TestStemmer reducing with Gener or Lift. No prior report of it was found.
  • What goes wrong. Silent wrong stems, no error. Index-time and query-time analysis disagree: affected terms indexed before the call stop matching queries analysed after it, and documents indexed after it get different terms. Analyzers created before the call hold the same table, so they change too (code reading). The shared table stays changed for as long as the PolishAnalyzer class stays loaded, normally until the JVM exits (a static final loaded once).
  • Scale. Deterministic in every executed case (one-key tries, the exhaustive small tries, the bundled table), with assertions on and off. On a loaded copy of the bundled table Gener changed the stems of 193,552 of 366,667 probe words in one probe, 14,075 of 67,668 answers in another and 3,352 of 20,012 stemmed words in a third.
  • Concurrency (not executed). Analysis on another thread during a reduce call reads cell fields while they are rewritten, without synchronization; by code reading that gives wrong stems there.

Why it is a bug, not intended

#
  • getDefaultTable() "Returns an unmodifiable instance of the default stemmer table"; its CHANGES entry (SOLR-3737) says "ensure immutability".
  • Trie.reduce returns "the newly reduced Trie"; the sibling reductions Optimizer and Optimizer2 leave their input unchanged.
  • Upstream TestStemmer reduces one trie five times, then re-checks the original, as if its author expected the input to stay intact (the test does not say so).
The full argument230 words
  • The contract. Trie.reduce: "Remove empty rows from the given Trie and return the newly reduced Trie. ... @return the newly reduced Trie" (Trie.java:361-369). Gener.optimize: "@return a new optimized Trie" (Gener.java:75). PolishAnalyzer.getDefaultTable(): "Returns an unmodifiable instance of the default stemmer table." (PolishAnalyzer.java:60).
  • Lucene's own intent for the table. SOLR-3737 (04f3188bf9b, 2012) added getDefaultTable() with that javadoc, made the factory share the one table and, in the same commit, made Trie.add package-private. CHANGES: "Also, ensure immutability and use only one instance of this table in RAM (lazy loaded) since it's quite large." (lucene/CHANGES.txt:15072-15074). reduce() is still a public way to change it.
  • The siblings. Optimizer and Optimizer2 copy before they change anything; three independent controls show their input unchanged. Writing into the input is not the reduction family's design.
  • The upstream test. TestStemmer.assertTrieContents (from the 2010 import) builds {trie, reduce(Optimizer), reduce(Optimizer2), reduce(Gener), reduce(Lift(true)), reduce(Lift(false))} from one trie and checks every entry, the original included. It passes today only because its Lift(false) entry runs on the trie that Lift(true) already rewrote: on a fresh trie reduce(new Lift(false)).getFully("ba") is null. It does check the original trie, for the inserted keys only, which this rewrite happens not to break.
  • Public API. org.egothor.stemmer is exported by the module, with no internal or experimental marker; the repro needs no cast and no reflection.
The devil's-advocate check245 words

The strongest case for "intended" (the adjudication rated it "moderate at most"; the cross-model intended-lens review rated it moderate, and the devil's advocate found a moderate reading only for caller-built tries): Lift and Gener are legacy egothor compiler passes; Compile always rebinds trie = trie.reduce(..) and discards the input; Trie.reduce's first sentence, "Remove empty rows from the given Trie", can be read as working on the given trie; Lift.optimize's own javadoc says only "return the reduced Trie"; liftUp and eat are public helpers that work in place (liftUp's javadoc describes propagating commands up the trie; eat's calls it a test of whether a row should stay, yet it clears ref, cnt and cmd); every reducer's result shares the input's command list, so reduce never promised a fully independent copy; and "unmodifiable" was never deeply enforced, because the default table is a MultiTrie2 whose add is still public, reachable with a downcast.

Why it fails: for the default table the promise is Lucene's own text (javadoc and CHANGES), not inherited egothor wording; reduce needs no cast, is a method of the declared Trie type, says "newly reduced" and names no side effect; no reducer ever writes the shared command list; the optimizers keep their input. For a trie the caller built, the argument survives in weaker form, and a maintainer may prefer a javadoc note for that half. Verdict: a defect; lead the issue with the default table.

Suggested fix

#

Recommended Copy the rows in Lift.optimize and Gener.optimize

Copy the rows before Lift and Gener rewrite them: a small Reduce.copyRows helper and one line in each reduction (+20/-2). Upstream TestStemmer then needs its Lift(false) entry made explicit as reduce(Lift(true)).reduce(Lift(false)), which is what it always tested. Validated: the repro passes, the whole stempel module passes (21 tests) and check -x test passes (format, ecjLint, forbiddenApis).

static List<Row> copyRows(List<Row> rows) {   // in Reduce
  List<Row> copy = new ArrayList<>(rows.size());
  for (Row row : rows) {
    Row r = new Row();
    for (CharCursor ch : row.cells.keys()) {
      r.cells.put(ch.value, new Cell(row.at(ch.value)));
    }
    copy.add(r);
  }
  return copy;
}
// Lift.optimize and Gener.optimize:
-    List<Row> orows = orig.rows;
+    List<Row> orows = copyRows(orig.rows);

Copy the rows in Lift.optimize and Gener.optimize (validated by the checks) (recommended)

#

Add a package-private Reduce.copyRows(List<Row>) that copies every row and cell, and use it in Lift.optimize and Gener.optimize instead of orig.rows. liftUp and eat stay what they are, in-place steps on the rows they are given. Update TestStemmer in the same change (below). The snippet is condensed; the full patch is fix-validation/fix.diff (+20/-2), and the test update is fix-validation/teststemmer.diff.

static List<Row> copyRows(List<Row> rows) {   // in Reduce
  List<Row> copy = new ArrayList<>(rows.size());
  for (Row row : rows) {
    Row r = new Row();
    for (CharCursor ch : row.cells.keys()) {
      r.cells.put(ch.value, new Cell(row.at(ch.value)));
    }
    copy.add(r);
  }
  return copy;
}
// Lift.optimize and Gener.optimize:
-    List<Row> orows = orig.rows;
+    List<Row> orows = copyRows(orig.rows);

Trade-offs

  • Not test-neutral; say so up front. With the fix alone, upstream TestStemmer fails 5 of 6, on getFully for its Lift(false) entry. That entry has always tested Lift(false) after Lift(true), because Lift(true) had already rewritten the test's own trie. On a fresh trie Lift(false) folds a uniform child row into its parent cell with skip = 0, so getFully("ba") is null while getLastOnPath("ba"), which the stemmer uses, is still 2. The test update keeps the existing assertion statements but changes what the sixth entry means: it is now written as the chain it has always run, trie.reduce(new Lift(true)).reduce(new Lift(false)); a new loop checks Lift(false) on the unchanged trie with getLastOnPath only, not getFully. Whether getFully after Lift(false) should keep the longer keys is a separate question; open issue #6584 may touch it (code reading).
  • Cost. One extra copy of every row per Lift or Gener reduction; the bundled table has 6,815 rows over 8 sub-tries. Not benchmarked; reductions run when a table is built, not during analysis.
  • No API change. A trie reduced once gets the same answers as before, because the reduction runs on an identical copy (code reading).

What the checks validated

Gradle (--no-daemon) in a clean scratch worktree of a9779ef3c193, JDK 25, seed DEADBEEF, removed afterwards:

  • fix only: the 2 new tests pass; TestStemmer fails 5 of 6 (all but testMultiTrie2), with assertions on and off.
  • fix + TestStemmer update: 8 of 8 with assertions on and off; the whole :lucene:analysis:stempel:test passes, 6 classes and 21 tests (TestPolishAnalyzer, TestPolishSnowballAnalyzer, TestStempelPolishStemFilterFactory, TestCompile, TestStemmer, TestReduceKeepsInput); :lucene:analysis:stempel:check -x test passes (checkGoogleJavaFormat, ecjLint, forbiddenApis; error-prone and eclint did not run in that build).
  • An equivalent inline copy (the finder's patch) also passed the independent reproducer's 9 tests, a cross-model reviewer's 5 and the devil's advocate's 2 expectation tests.

Copy inside Trie.reduce

#

Have Trie.reduce hand a deep copy of itself to by.optimize(..).

Trade-offs

Covers Reduce subclasses written by users too, but Reduce.optimize is public and can be called directly, bypassing Trie.reduce, and the copy is wasted for Optimizer and Optimizer2. Needs the same TestStemmer update. Not run.

Protect only the shared default table

#

Make the default table copy itself before any reduction.

Trade-offs

Settles the "unmodifiable" contract with the smallest change, but leaves tries the caller built rewritten in place. Not run.

Document that Lift and Gener modify their input

#

State it in the javadoc of Trie.reduce, Lift and Gener, and say in getDefaultTable() that it must not be reduced.

Trade-offs

Cheapest, but "unmodifiable" then holds only by convention. A maintainer may prefer this for caller-built tries, combined with the previous option.

Downstream note

#

Downstream, every index in a JVM that analyses Polish with PolishAnalyzer or the stempelPolishStem factory reads this one table, so one component's reduce(new Gener()) call changes stemming for all of them.

How it was found

#

Bounded-exhaustive testing of the stempel reductions: a harness queried each input trie again after reducing it, over 183,540 small tries (1 to 4 keys of up to 3 letters on {a, b}, three fixed commands, both directions). Lift changed its input in most, Optimizer and Optimizer2 never; a bundled-table probe showed Gener. A public-API JUnit reproduced it.

The method in full189 words

Method: bounded-exhaustive translation validation (the semi-formal tier), in a hunt unit on the stempel trie code (diff, store/load round trips and reductions).

  • The harness built every set of 1 to 4 keys of length at most 3 on the alphabet {a, b}, each key given one of three fixed commands (Da, Db, -aDa), in both directions (183,540 tries), applied single reductions and pairs of them, and compared the answers with a reference; one column queried the input trie again after each single reduction.
  • That column listed input changes only for Lift(false) (168,462 tries) and Lift(true) (160,590); Optimizer and Optimizer2 never changed their input. Gener drops nothing in tries that small (its threshold is a tenth of a row's total count).
  • A companion probe on a loaded copy of the bundled table found that reduce(new Gener()) changes the stems of 193,552 of 366,667 probe words on that copy, while Lift changes none (the table is already lifted).
  • The hypothesis came while modelling the reduction step from the code; the harness witnessed it, and it was reduced to the 2-test public-API JUnit on the stock main jar.

History

#

In Lucene since the stempel import (98c47c57e0a, LUCENE-2298, 2010; first release 3.1.0). SOLR-3737 (04f3188bf9b, 2012; first in 4.0.0) made the table a public JVM-wide singleton. A portable probe fails on all 138 releases from 3.1.0 to 10.5.2 and on main; not fixed upstream.

Versions tested6 rows

LFV-696, snapshot of 2026-10-28

Registry title
Stempel's Trie.reduce with Gener or Lift rewrites the cells of the trie it is given, so reducing PolishAnalyzer.getDefaultTable(), documented as unmodifiable, silently changes the stems of every later PolishAnalyzer and StempelPolishStemFilterFactory in the JVM
Area
analysis/stempel / egothor stemmer trie reductions (Trie.reduce with Lift and Gener; the shared PolishAnalyzer.getDefaultTable() table)
Priority
Low, rank 414: Once triggered every Polish stemmer in the JVM silently changes its stems, but only when application code calls Trie.reduce with Gener or Lift on a table it keeps using, which normal analysis, the factory and Compile never do.
Impact class
silent wrong results
Impact note
Hits only applications whose own code calls Trie.reduce (or MultiTrie/MultiTrie2.reduce) with Gener or Lift on a trie it keeps using, most visibly PolishAnalyzer.getDefaultTable(): after getDefaultTable().reduce(new Gener()) every PolishAnalyzer and StempelPolishStemFilterFactory in the JVM stems differently (on a loaded copy of the bundled table 14,075 of 67,668 probe answers change in the independent reproduction's test, and 'książkami' becomes 'książk' instead of 'książek'), so terms indexed before the call stop matching queries analysed after it, deterministically with -ea and -da, at any size, in every release from 3.1.0 (the default-table form from 4.0.0) to 10.5.2 and on main; normal analysis, the factory and the Compile tool never reduce a table they keep using, and on the shipped table only Gener changes answers (it is already lifted), so the Lift half shows only on a trie that has not been lifted yet, such as a custom table being built.
Summary
You call reduce(new Gener()) or reduce(new Lift(..)) on a stempel Trie, for example on PolishAnalyzer.getDefaultTable(), which is documented as 'an unmodifiable instance of the default stemmer table', and expect what Trie.reduce's javadoc says, 'the newly reduced Trie', with the input left as it was (Optimizer and Optimizer2 behave so). Instead Lift.optimize and Gener.optimize take the input's own row list and rewrite its cells in place (Lift moves commands up a level and clears references, Gener drops infrequent commands and references) before copying them into the result, so the input answers differently afterwards: after PolishAnalyzer.getDefaultTable().reduce(new Gener()) every new PolishAnalyzer stems 'książkami rzekami pracowali' to [książk, rzekami, pracowali] instead of [książek, rzekść, pracować], and a one-key trie {aa -> Da} reduced with Lift(false) starts to answer getLastOnPath('a') = Da instead of nothing. Copying the rows before the rewrite fixes it; upstream TestStemmer, which reduces one trie five times, then needs a fresh trie per reduction.
