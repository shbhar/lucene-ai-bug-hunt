ICUTokenizer with cjkAsWords=false drops the Japanese iteration mark 々: 人々 is indexed as 人

With cjkAsWords=false, ICUTokenizer silently drops the Japanese iteration mark 々 (U+3005): 人々 ("people") is indexed as just 人, so 々 cannot be searched and 人々 can no longer be told apart from 人. Every release since 4.7.0 does this; one line in the break rules fixes it.

The bug in 30 seconds

#

ICUTokenizer first splits text into script runs. With cjkAsWords=false, a Han run is cut into pieces by Lucene's own rules, Default.brk, and each piece gets a status number; pieces with status 0 (spaces, punctuation) are skipped, the others become tokens.

  1. Build ICUTokenizer with new DefaultICUTokenizerConfig(false, true) (or the icu factory with cjkAsWords="false"), the mode the module's own tests put in front of CJKBigramFilter. Analyze 人々 ("people"): the kanji 人 followed by 々, which repeats it.
  2. You expect [人, 々]. The javadoc promises "UAX#29 defaults" for this mode, and under UAX #29 々 is a letter. StandardTokenizer and Lucene 4.6.1 give [人, 々]; the default cjkAsWords=true gives [人々].
  3. You get [人]. 様々な人々 gives [様, な, 人] and 佐々木 gives [佐, 木]: every 々 is gone, with no error, with assertions on or off.
  4. Search changes too. With CJKBigramFilter, the documents 人々 and 人 are both indexed as the one term 人, so no search on the field can tell them apart and no term contains 々. With the default mode or the recommended fix, the 人々 document gets the bigram 人々; with <ALPHANUM> typing, as StandardTokenizer gives, it gets the term 々.
  5. Why: the rule file Default.rbbi takes every Han-script character out of its letter rule and gives a word status only to Ideographic ones. 々 is Han but not Ideographic, so its piece gets status 0, and ICUTokenizer skips status-0 pieces just as it skips punctuation.

Who is affected

#

Applications that tokenize Japanese with the ICU module's non-default cjkAsWords=false: DefaultICUTokenizerConfig(false, ...) in Java, or cjkAsWords="false" on the icu factory (for example in a Solr schema), usually to feed CJKBigramFilter. Every 々 in everyday words (人々, 時々, 様々) and names (佐々木) is lost. The default mode is not affected.

Mechanism, terms and numbers635 words

ICUTokenizer has a switch, cjkAsWords (default true). With cjkAsWords=false (new DefaultICUTokenizerConfig(false, true), or the icu factory with cjkAsWords="false"), CJK text is "segmented according to UAX#29 defaults" by Lucene's own break rules, Default.brk, instead of ICU's dictionary; the module's own tests use this mode, also in front of CJKBigramFilter. In this mode every U+3005 IDEOGRAPHIC ITERATION MARK vanishes: 人々 ("people") gives [人], 時々 ("sometimes") [時], 様々な人々 [様, な, 人], 佐々木 [佐, 木], where StandardTokenizer and Lucene 4.6.1 give [人, 々] and the default mode [人々]. The cause is Default.rbbi: it removes every Han-script character from the letter class and gives a status only to Ideographic characters; 々 is Han but not Ideographic, so its segment gets rule status 0, and ICUTokenizer skips status-0 segments like punctuation. The other two Han-script letters, U+303B and U+16FE3, are dropped the same way. Nothing throws; 々 is simply not in the index, and with CJKBigramFilter 人々 is indexed as the term 人. It came with LUCENE-4381 (4.7.0) and is in every release up to 10.5.2 and on main; a one-line rule change, with Default.brk regenerated, fixes it.

Terms

#
  • cjkAsWords (default true): with true, Han, Hiragana and Katakana text goes to ICU's own word iterator, which uses a dictionary and keeps 人々 as one word. With false, CJK text is "segmented according to UAX#29 defaults" (DefaultICUTokenizerConfig.java:94-96) by Lucene's rule file Default.rbbi, compiled to Default.brk. That is the mode for CJKBigramFilter users: the module's own TestWithCJKBigramFilter uses it.
  • Rule status: ICU break rules give each piece of text a number. In Default.rbbi, letters get 200, kana 300 and ideographs 400 (Default.rbbi:125-131); pieces that no status rule matches get 0, ICU's "none" status for spaces and punctuation.
  • 々 (U+3005): the Japanese iteration mark; it repeats the kanji before it (人々 = 人 + 人, "people"). It is Script=Han, Ideographic=No and Word_Break=ALetter, a letter under UAX #29.

The bug

#
  1. Default.rbbi defines $Han = [:Han:] (:54), puts it into $dictionaryCJK (:88-89) and removes $dictionaryCJK from the letter class: $ALetterPlus = [$ALetter-$dictionaryCJK ...] (:95). So no Han-script character gets the letter status 200.
  2. The only status rule left for Han is $Ideographic $ExFm* {400}; (:131): Lucene's tailoring removed ICU's rule that chains Han and kana (header :23). 人 is Ideographic and gets 400. 々 is not, so its piece gets status 0. The Han exclusion and this status rule are ICU's own word.txt text; in ICU, the final rule $KanaKanji $KanaKanji {400} and the dictionary keep a 々 after a kanji inside a status-400 word, and Lucene's mode removes both.
  3. ICUTokenizer.incrementTokenBuffer skips status-0 pieces (ICUTokenizer.java:209-214), the loop that skips spaces and punctuation. 々 is dropped exactly like a comma: in 486 of 486 tested contexts the tokens equal those of the same text with 、 in its place.
  4. The boundaries are right (人 | 々, as UAX #29 says); only the status is wrong.

The numbers

#

人々 -> [人]; 時々 -> [時]; 様々な人々 -> [様, な, 人]; 佐々木さん -> [佐, 木, さ, ん]; 人〻 (U+303B) and 人𖿣 (U+16FE3) -> [人]. StandardTokenizer gives [人, 々], the default mode [人々]. With CJKBigramFilter, 人々 gives the unigram [人] instead of the bigram [人々], and 様々な人々 gives [様, な人] instead of [様々, 々な, な人, 人々]. Indexing the documents 人々 and 人 through that chain leaves one term, 人 (df=2), for both documents: TermQuery 人々 finds 0 documents, 人 finds 2 and 々 finds 0. With the default mode or the recommended fix the 人々 document gets the bigram 人々 (1 and 1); with <ALPHANUM> typing, as StandardTokenizer gives, it gets the term 々 (人々 0, 人 2, 々 1).

Exposure and likelihood274 words
  • Who is exposed. Users of the opt-in analysis-icu module who choose cjkAsWords=false: new ICUTokenizer(new DefaultICUTokenizerConfig(false, ...)), or ICUTokenizerFactory (SPI name icu) with cjkAsWords="false" (the factory default is true, ICUTokenizerFactory.java:96). A maintainer described this as a supported setup on #13239: "the user can configure false here and use CJKBigramFilter if they prefer an n-gram approach". ICUTokenizer and DefaultICUTokenizerConfig are @lucene.experimental (the factory is not). All of this is with the stock rules: a factory rulefiles entry for the Han script replaces Default.brk for Han text (ICUTokenizerFactory.java:54-66, :86-95, :120-131).
  • Not exposed. The default ICUTokenizer() and the factory default (cjkAsWords=true). Elasticsearch and OpenSearch hard-code cjkAsWords=true in their icu_tokenizer.
  • What triggers it. Ordinary Japanese text: 々 is in common words (人々, 時々, 様々, 色々, 我々, 日々) and names (佐々木). Deterministic: every occurrence, every document, assertions on or off.
  • Effect. 々 is never indexed and cannot be searched. 人々 is indexed as 人: with CJKBigramFilter, the 人々 and 人 documents get the same single term 人, so no search on the field can tell them apart; a query for 人々 analysed the same way becomes 人, so it still finds the 人々 document but also every document with an isolated 人 (lower precision). Bigrams across the mark are lost.
  • Not affected. Other tokens and their offsets, index integrity (CheckIndex clean over 3,000 documents), cost (linear, the same order of growth as punctuation and no amplification; all-々 input was about 40% slower than all-、 input in the recorded run). Existing indexes keep the missing terms until reindexed.
  • Scale. Every release from 4.7.0 (2014) to 10.5.2, and main.

Why it is a bug, not intended

#
  • The javadoc says cjkAsWords=false segments text "according to UAX#29 defaults" (DefaultICUTokenizerConfig.java:94-96); under UAX #29, 々 is a letter.
  • Every reference keeps 々: StandardTokenizer, ICU's root iterator, the default mode, and Lucene 4.6.1.
  • The rule file's header lists two tailorings, neither about Han letters; no test, CHANGES entry or discussion found accepts the loss.
The full argument400 words
  • The contract. "@param cjkAsWords true if cjk text should undergo dictionary-based segmentation, otherwise text will be segmented according to UAX#29 defaults. If this is true, all Han+Hiragana+Katakana words will be tagged as IDEOGRAPHIC." (DefaultICUTokenizerConfig.java:94-96). The class javadoc: "Generally tokenizes Unicode text according to UAX#29 (BreakIterator.getWordInstance(ULocale.ROOT))" with a dictionary as the only CJK tailoring (:30-36); next to Default.brk: "the same as ROOT, except no dictionary segmentation for cjk" (:80). ICUTokenizer: "Breaks text into words according to UAX #29" (ICUTokenizer.java:30-32). Under UAX #29, U+3005 is Word_Break=ALetter, a letter. UAX #29 sets the boundary and the letter class, not ICU's rule statuses or which segments a tokenizer emits; ICUTokenizer drops only status-0 segments, ICU's status for spaces and punctuation.
  • The tailorings on record. The Default.rbbi header names two: "Prevent dictionary break: disable final rule that would chain han and kana" and "For kana rules, change from 400 to 300 status" (:23-24). A diff against ICU 77.1's word.txt shows exactly those two changes. Neither says Han-script letters stop being tokens.
  • ICU's convention. Status 0 is ICU's "none" status, documented for spaces and most punctuation; 々 is gc=Lm, a letter.
  • Every reference keeps it. StandardTokenizer ([人, 々]), ICU's root word iterator (人々 as one status-400 word), the default cjkAsWords=true ([人々]), and Lucene 4.6.1 ([人, 々]).
  • History. LUCENE-4381 (4.7.0) added cjkAsWords, changed the letter class to [$ALetter-$dictionaryCJK ...], and moved the module's existing tests to DefaultICUTokenizerConfig(false), which suggests that false was meant to keep the earlier UAX #29 behaviour (the commit message does not say so). Its only CHANGES entry is "Upgrade analysis/icu to 52.1" under Build. With the ICU version held fixed, the 4.6.1 rules give 々 status 200 and the 4.7.0 rules 0.
  • Maintainer on record. #13239 (2024): Default.rbbi "is used only when the user overrides defaults to disable ICU's dictionary-based CJK segmentation", quoting the "UAX#29 defaults" javadoc, with cjkAsWords=false plus CJKBigramFilter as the use case.
  • Tests. TestICUTokenizer (main analyzer at :78, used by testJapanese at :436) and TestWithCJKBigramFilter (:49) run in this mode. No test in analysis/icu contains 々; the only tests that do are in kuromoji (the iteration-mark char filter tests, TestJapaneseCompletionFilter, TestJapaneseAnalyzer).
  • Outside Lucene. Unicode CLDR decided in 2009 that 々 should behave as an ideograph for Japanese word break (CLDR-2009).
The devil's-advocate check258 words

The intended-behaviour checker and the cross-model lenses built the strongest case for "works as designed": Lucene only removed ICU's chain rule, and status 0 is what ICU's grammar then gives; UAX #29 defines boundaries, not which pieces are words, and the boundary is right; status-0 pieces are skipped on purpose; the broad Han exclusion survived every later rule change and is ICU's own grammar text; a TODO calls cjkAsWords "super-expert stuff" (DefaultICUTokenizerConfig.java:86); the classes are @lucene.experimental; ICU root itself drops a lone 々; kuromoji's JapaneseIterationMarkCharFilter can expand 々 first.

Why it fails: the javadoc promises UAX #29 defaults and 々 is a letter there; status 0 is ICU's status for spaces and punctuation, and ICUTokenizer turns it into a deletion. Every reference keeps the character, including the 4.6.1 behaviour that the test migration suggests cjkAsWords=false was meant to keep. No javadoc, CHANGES entry, test, commit message or discussion found accepts the loss. The lone-々 point holds only for the default mode (ICU root's own behaviour), which is not claimed here; with cjkAsWords=false even a lone 々 is in scope. The char filter is a partial workaround, not a contract. Not settled by this: the recommended fix is itself a tailoring (CLDR-2009's "treat 々 as ideograph"), and a maintainer may call this a long-standing limitation of an experimental mode. Verdict: not intended (the cross-model reviews rated the works-as-designed case weak and the independent reproduction, the intended-behaviour check and the adjudication found the bug real; the later cross-model fact check of this doc rated that case moderate).

Trade-offs

  • Changes analysis output for cjkAsWords=false users (new tokens 々, new bigrams): needs a CHANGES line and a reindex note.
  • With cjkAsWords=true, Han-script text goes to ICU's root iterator, not Default.brk, so the default mode should not change (from the code; the cjkAsWords=true suite is @AwaitsFix and was not run).
  • Not plain UAX #29: each Han letter gets its own single-character rule, so 々々 (as in 部分々々) gives [々, 々], where StandardTokenizer gives one <ALPHANUM> token [々々] (fix B splits it too). The two Han Word_Break=Extend marks (U+16FF0, U+16FF1) stay outside every token, as on main and as with StandardTokenizer. It is a tailoring in the direction of CLDR-2009.

Workarounds until a fix ships

#

Use the default cjkAsWords=true, which keeps 人々 as one word; or put kuromoji's JapaneseIterationMarkCharFilter in front of the tokenizer, in both the index and the query analyzer: it expands a 々 that follows a kanji (人々 -> 人人, tokens [人, 人]).

Trade-offs

The first changes CJK segmentation as a whole. The second needs the kuromoji module and is partial: it passes a lone or leading 々 through unchanged (JapaneseIterationMarkCharFilter.java:28-34), which the tokenizer still drops (々 -> [], 々人 -> [人]), and it does not handle U+303B or U+16FE3 (executed).

Downstream note

#

Elasticsearch and OpenSearch hard-code cjkAsWords=true in their icu_tokenizer, so their users cannot reach this mode; Solr exposes cjkAsWords on ICUTokenizerFactory, so a Solr schema can.

How it was found

#

Semi-formal: a bounded-exhaustive check ran the stock ICUTokenizer on 2,593,337 short strings in both cjkAsWords modes against one oracle: every letter that StandardTokenizer puts in a token must be inside some ICUTokenizer token. It flagged 々; an AI tool then traced it to the Default.rbbi status rule and wrote the JUnit.

The method in full197 words

Method: bounded-exhaustive translation validation (the hunt's "semi-formal" tier), hunt unit "ICU script iterator and ICUTokenizer against reference semantics", 2026-10-27, on main a9779ef3c193. No model checker, SMT solver or proof produced the signal.

  • A harness ran the stock ICUTokenizer on every string over a 35-character alphabet up to length 4 and a 16-character alphabet at length 5: 2,593,337 strings x 2 configurations (cjkAsWords true and false), 25.9 million checks, against reference semantics for the script iterator and the token loop (0 mismatches there).
  • A "content dropped" oracle compared it with StandardTokenizer, the core UAX #29 tokenizer: every letter or digit StandardTokenizer puts in a token must lie inside some ICUTokenizer token. It flagged three dropped-content classes; U+3005 was one, the other two became separate rows (a word joined to an emoji by ZWJ, and Hangul followed by a combining mark).
  • An AI tool listed the 335 Han-script code points that are not Ideographic with ICU's UnicodeSet, separated the cjkAsWords=false defect from ICU root's own handling of a lone 々 in the default mode, found the status rule in Default.rbbi, and wrote the public-API JUnit. Independent AI tools then reproduced and judged it (see the checks).

History

#

A regression from LUCENE-4381 (#5447, the ICU 52.1 upgrade, committed 2013-12-03), first released in 4.7.0. 4.6.1 keeps 々; 19 releases from 4.7.0 to 10.5.2 and main drop it. With the ICU version held fixed, the rule change alone flips 々 from kept to dropped.

Versions tested6 rows

Introduced by LUCENE-4381, "upgrade ICU to icu4j 52.1" (JIRA LUCENE-4381, migrated as #5447; a direct SVN commit with the patch on the JIRA issue, no PR): trunk b5dbac5e3582 and branch_4x 2924e5286330 (the copy that shipped in 4.7.0), both 2013-12-03. It added cjkAsWords and changed the letter class from [$ALetter [$dictionary-$Extend-$Control]] to [$ALetter-$dictionaryCJK [$ComplexContext-$Extend-$Control]] with all of [:Han:] in $dictionaryCJK; it also moved the module's tests to DefaultICUTokenizerConfig(false). Its only CHANGES entry is "Upgrade analysis/icu to 52.1" under Build.

The rules are the cause, not the ICU upgrade: with ICU4J held at 52.1 and at 78.3, the 4.6.1 rules give 々 status 200 and the 4.7.0 rules give 0.

Never fixed: later Default.rbbi changes (7.4.0, 7.5.0, #13239 in 9.11.0/10.0.0, #14386 in 10.2.0) and every Default.brk rebuild since kept the line; on 2026-10-27 no commit after a9779ef3c193 touches lucene/analysis/icu (upstream main a95c754ee003).

Coverage: 19 releases and main were executed; the releases in between are affected by history (every release tag in the history clone contains the change and the line is unchanged), not by a run. Bug record

#

LFV-653, snapshot of 2026-10-30

Registry title
ICUTokenizer with cjkAsWords=false silently drops the Japanese iteration mark 々 (U+3005), as in 人々, 時々 and 様々, and the other Han-script letters that are not Ideographic (U+303B, U+16FE3), because Default.rbbi gives them rule status 0
Area
analysis / ICU (DefaultICUTokenizerConfig break rules Default.rbbi / Default.brk, used for CJK text when cjkAsWords=false; ICUTokenizerFactory 'icu' with cjkAsWords="false")
Priority
Low, rank 258: Only the non-default cjkAsWords=false mode of the opt-in ICU tokenizer is affected, and same-analyzer search largely masks the precision loss.
Impact class
silent wrong results
Impact note
Applications that tokenize Japanese text with ICUTokenizer in its non-default cjkAsWords=false mode (new DefaultICUTokenizerConfig(false, ...), or ICUTokenizerFactory cjkAsWords="false", for example in a Solr schema; this is the setup the module's own TestWithCJKBigramFilter uses to feed CJKBigramFilter) lose every 々 from the token stream (after a kanji as in 人々, and in every other context probed: alone, doubled, before a kanji or a Latin word), deterministically and silently, with -ea and -da, at any size, in every release from 4.7.0 to 10.5.2: 人々 is indexed and queried as 人 and 佐々木 as 佐/木, so 々 cannot be searched and term and phrase matching on such words loses precision (a same-analyzer query for 人々 still finds 人々 but also matches an isolated 人); the default cjkAsWords=true mode and the Elasticsearch and OpenSearch icu_tokenizer (which hard-code true) are not affected, and nothing throws or damages the index.
Summary
You build ICUTokenizer with cjkAsWords=false, whose javadoc promises that text 'will be segmented according to UAX#29 defaults', and index Japanese text such as 人々 ('people'), 時々 ('sometimes') or 様々な人々; you expect 々, a Word_Break=ALetter letter under UAX #29, to end up in a token, as it does with StandardTokenizer, with the default cjkAsWords=true mode and with Lucene 4.6.1. Instead Default.rbbi takes every Han-script character out of its letter rule and gives a status only to Ideographic characters, and 々 is Han but not Ideographic, so its segment gets rule status 0 and ICUTokenizer skips it like punctuation: 人々 -> [人], 様々な人々 -> [様, な, 人], and with CJKBigramFilter 人々 becomes the unigram 人. Nothing throws; the character is simply missing from the index.
