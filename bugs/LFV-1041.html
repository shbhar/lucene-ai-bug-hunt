The analysis compound package overview's examples do not compile on any release since 4.0.0, and its output table shows offsets the filters no longer emit

The compound package overview's three examples call methods removed in Lucene 4.0 and 5.0, so copied code does not compile on any release since 4.0.0 (5 errors on main). Its output table shows word parts with their own offsets, (Rind,0,4), but since 4.4.0 (unconditionally since 5.0.0) every part carries the whole word's: (Rind,0,29).

The finding in 30 seconds

#

The examples date from Lucene 3.1 and the table was last right in 4.3; the API changes since then never updated the page. The filters themselves work as designed.

What you need to know first

#
  1. A decompounding filter keeps each compound word and adds the parts it finds as extra tokens at the same position (posIncr=0): "Drahtschere" (wire cutters) becomes Drahtschere, Draht, schere.
  2. HyphenationCompoundWordTokenFilter finds candidate parts with a hyphenation grammar (an XML file you download separately); DictionaryCompoundWordTokenFilter checks substrings against a dictionary.
  3. Every token carries a start and an end offset, its character positions in the original text. Highlighters use them to mark what matched.

The finding, step by step

#
  1. You want to split German compound words and copy the package overview's first example: it loads a grammar with getHyphenationTree(new FileReader("de_DR.xml")), tokenizes "Rindfleischüberwachungsgesetz Drahtschere abba" with new WhitespaceTokenizer(new StringReader(...)) and passes a String[] dictionary.
  2. You expect it to compile and to produce the page's output table, which "shows what it does": the word itself plus Rind (offsets 0-4), fleisch (4-11), überwachung (11-22) and gesetz (23-29).
  3. Instead javac reports 5 errors for the three examples on main: getHyphenationTree(Reader) and WhitespaceTokenizer(Reader) no longer exist. Fix those and 2 more appear, because both filters now take a CharArraySet dictionary. No release since 4.0.0 compiles them (4.10.x, which briefly had WhitespaceTokenizer(Reader) again, reports 4 errors).
  4. Port it and the loop throws IllegalStateException ("reset()/close() call missing"): it never calls reset(). Add reset() and it runs, but every part has the whole word's offsets: (Rind,0,29), (fleisch,0,29), not the table's (Rind,0,4), (fleisch,4,11).
  5. Why: deliberate changes (methods removed in 4.0.0 and 5.0.0, the reset() check in 4.6.0, whole-word offsets in 4.4.0, unconditional from 5.0.0) never updated the page, and nothing compiles code inside javadoc <pre> blocks.

Who is affected

#

Developers who adopt the opt-in decompounding filters from the package overview, which is also on the Lucene website. Copying the examples fails loudly, at compile time and then with an exception. The table quietly suggests word parts carry their own offsets, which matters for highlighting. No index, query or search result changes.

Mechanism, terms and numbers586 words

The org.apache.lucene.analysis.compound package overview shows how to split German and Swedish compound words with HyphenationCompoundWordTokenFilter and DictionaryCompoundWordTokenFilter, in three examples and a table of the tokens the filter produces. Copied into code, none of the three examples compiles on any release since 4.0.0: they call getHyphenationTree(Reader), new WhitespaceTokenizer(Reader) and the String[] dictionary constructors, all gone on main (the Version-less WhitespaceTokenizer(Reader) was back in 4.10.x only; today: getHyphenationTree(String) or (InputSource), new WhitespaceTokenizer() plus setReader, and a CharArraySet dictionary). Once ported, the page's loop throws IllegalStateException because it never calls reset(). With reset() it runs, but every word part carries the offsets of the whole word, for example (Rind,0,29) where the table shows (Rind,0,4): a deliberate change of 4.4.0 (LUCENE-5018, for a match version of 4.4 or later; unconditional since 5.0.0) that the table never picked up. The filters work as designed; only the page is wrong, and a javadoc-only fix solves it (validated); shrinking the block is an alternative (not run).

Why the ported loop throws

#

A tokenizer reads from a placeholder reader until reset() swaps in the reader given to setReader (Tokenizer.java:100-104). Reading the placeholder throws IllegalStateException("TokenStream contract violation: reset()/close() call missing, ...") (Tokenizer.java:111-118).

Why every part has the whole word's offsets

#

Each part is a CompoundToken, which copies the current token's offsets (CompoundWordTokenFilterBase.java:163-165):

      // offsets of the original word
      this.startOffset = CompoundWordTokenFilterBase.this.offsetAtt.startOffset();
      this.endOffset = CompoundWordTokenFilterBase.this.offsetAtt.endOffset();

So "Rindfleischüberwachungsgesetz" (offsets 0-29) yields (Rind,0,29), (fleisch,0,29), ... and "Drahtschere" (30-41) yields (Draht,30,41), (schere,30,41). Lucene's own TestCompoundWordTokenFilter.testDumbCompoundWordsSE (:147), the page's example 3 with the same name, dictionary and input, asserts start offsets 0, 0, 0, 8, 8, 8, ... and end offsets 7, 7, 7, 16, 16, 16, ... (:207-215).

The term list itself depends on the grammar: the page's de_DR.xml cannot be bundled (package-info.java:88-98), and the hunt checked the terms with a hand-written 4-pattern grammar only. The offsets do not depend on the grammar.

Why it looks unintended

#
  • The page presents working code: a section headed "Examples", shown as highlighted Java, and a table that "shows what it does".
  • The errors name removed members, the loop skips the documented reset(), and Lucene's own test of example 3 asserts whole-word offsets.
  • The removals and the offset change were deliberate, but none of those commits touched the page.
The full argument241 words
  • The page presents them as working examples. The section is headed "Examples" (package-info.java:139) with no pseudo-code marker, and the table is introduced with "This example shows what it does" (:20). In January 2026 the block was re-tagged as highlighted Java, <pre><code class="language-java"> (#15573, 378ca8d1bbf, Dawid Weiss).
  • Not missing boilerplate. The errors name removed members: getHyphenationTree(Reader), WhitespaceTokenizer(Reader) and the String[] dictionary constructors. The loop breaks the documented consumer workflow ("The consumer calls reset()", TokenStream.java:54).
  • The changes that broke it never touched the page (git show --stat): LUCENE-2781 (a58c26978f5), LUCENE-3530 (a91efbedd1b), LUCENE-5388 (ab0e85fafed on trunk; on branch_5x inside 55594bad9b0, the LUCENE-5944 backport commit), LUCENE-5235 (cdb6ea3c022) and LUCENE-5018 (3e893624367 / 2e92d089832, which changed only CHANGES.txt, CompoundWordTokenFilterBase and its test). Main's CHANGES.txt lists LUCENE-5018 under 4.4.0 ("... don't update offsets anymore"), LUCENE-5235 under 4.6.0 and LUCENE-5388 under 5.0.0. A 2012 commit titled "code snippet improvements: fix out of date api usage" (647b5091697) changed only this block's markup.
  • Lucene's tests use the current API for the same examples.   • Maintainers fix such pages. LUCENE-4788 ("Out of date code examples", #5853) was fixed in 4.2; #16904 (stale examples on the collation page) was approved by a committer on 2026-10-29 and is still open.
The devil's-advocate check187 words

Strongest case for "not a bug": every behaviour involved is deliberate (the removals, the reset() check, the whole-word offsets; per-part offsets were later proposed on #9496, LUCENE-8450, and opposed); the block is informal (test-method names, no imports, a grammar file that is not bundled); the TokenStream contract makes reset() the caller's job; and maintainers know examples rot. Robert Muir wrote on #15225 (2025-10-25): "Code examples need to be kept extremely minimal in the rare cases where it does make sense: the maintenance cost is very high and we don't have great validation for these" (their view).

Why it fails: the deliberate changes are the root cause and place the defect in the page, which is exactly the claim. Nothing marks the code as pseudo-code, the table is presented as what the filter does, and the examples are the page's only usage guidance, so a reader who copies them breaks no rule. The #15225 view argues for fewer, smaller examples: it changes the remedy (port, shrink or delete), not the verdict, and records no decision to keep stale ones. Every verifier and the adjudication reached the same conclusion.

Trade-offs

  • Case-insensitive on purpose: the old String[] constructors built a case-insensitive set; with false, example 1 finds only "Rind" and "Draht". Lucene's own compound tests build their dictionaries the same way.
  • Grammar by file name, getHyphenationTree(String) ("the filename of the XML grammar to load"). Wrapping new FileReader(...) in an InputSource, as a first draft did, decodes with the platform charset: the pattern LUCENE-2732 deprecated. A relative name resolves against the working directory.
  • getHyphenationTree(String) hands the name to the XML parser as a system id (new InputSource(hyphenationFilename)); only a relative name in the working directory was run, and with the 4-pattern test grammar, not the OFFO de_DR.xml.
  • The diff is against main; the 10.6.0 page still has <pre class="prettyprint"> (it lacks #15573's markup change), so a backport needs a rebased diff.
  • The ported block is still unchecked text and can drift again.

Registry title
The org.apache.lucene.analysis.compound package overview's three code examples do not compile on any release since 4.0.0: they call HyphenationCompoundWordTokenFilter.getHyphenationTree(Reader), WhitespaceTokenizer(Reader) and the String[] dictionary constructors of both decompounding filters, all removed; their loop never calls reset(), and the page's output table shows per-part offsets that the filters stopped emitting in 4.4.0 (documentation defect)
Area
analysis-common / compound (package overview examples and output table, package-info.java)
Priority
Low, rank 1270: A compile-time-broken overview page with an outdated offsets table for the opt-in decompounding filters, with no runtime effect.
Impact class
minor
Impact note
Documentation only, with no runtime effect: a developer who adopts the opt-in decompounding filters (HyphenationCompoundWordTokenFilter, DictionaryCompoundWordTokenFilter) by copying the package overview's three examples gets compile errors on every release since 4.0.0 (5 on main, the 10.6.0 RC1, 10.5.2 and 9.12.3, then 2 more once those are fixed), a loud IllegalStateException once the code is ported, because the loop never calls reset(), and an output table whose per-part offsets the filters have not produced since 4.4.0; no configuration, scale or special input is involved.
Summary
The compound package overview shows how to split German and Swedish compound words with HyphenationCompoundWordTokenFilter and DictionaryCompoundWordTokenFilter, in three examples and a table of the tokens the filter produces. Copied into code, none of the three examples compiles on any release since 4.0.0, because getHyphenationTree(Reader), WhitespaceTokenizer(Reader) and the String[] dictionary constructors no longer exist (today: getHyphenationTree(String or InputSource), new WhitespaceTokenizer() plus setReader, and a CharArraySet dictionary), and once ported the loop throws IllegalStateException because it never calls reset(). With those fixes the examples run, but every word part carries the offsets of the whole word, for example (Rind,0,29) where the table shows (Rind,0,4), a deliberate 4.4.0 change (LUCENE-5018) the table never picked up; only the page is wrong.
