The finding in 30 seconds

#

One float sum, added in an order that changes from document to document, gives identical documents different last digits.

Background

#
  1. SynonymQuery treats several terms as one: for each document it adds up the terms' frequencies, each multiplied by its boost (a number in (0, 1]), and asks the similarity (BM25 by default) for one score from that sum.
  2. A Java float keeps about 7 significant digits, so every addition rounds, and the result can depend on the order: in float, (0.2 + 0.2) + 0.3 is 0.70000005, while (0.2 + 0.3) + 0.2 is 0.7.
  3. To find which terms a document contains, the scorer keeps the terms' postings in a heap. The order in which it lists the matching terms follows the heap's layout at that moment, which depends on the documents it visited before.

The finding, step by step

#
  1. You weight synonyms, e.g. Synonym(a^0.2, b^0.2, c^0.3), built with SynonymQuery.Builder#addTerm(term, boost) or by QueryBuilder from tokens that carry a boost. The query scores a document from one sum: 0.2 x freq(a) + 0.2 x freq(b) + 0.3 x freq(c).
  2. Index four identical documents a b c and search with the default BM25. You expect four equal scores, hits in doc-id order, and explain() equal to each hit's score.
  3. You get docs 0 and 3 at 0.038817033 and docs 1 and 2 at 0.038817026, so doc 3 ranks above docs 1 and 2, and explain() reports 0.038817033 for all four.
  4. Why: the scorer adds the boosted freqs in float, in the order its internal heap lists the terms, which depends on the documents visited before. In float, (0.2 + 0.2) + 0.3 = 0.70000005 but (0.2 + 0.3) + 0.2 = 0.7. explain() starts a fresh scorer and can add in another order.
  5. Rarely, with more than 2^24 (16.7 million) synonym occurrences in one field and ClassicSimilarity, the float sum also rounds above the max-score bound: a document scores 1.032795 while getMaxScore() says 1.0327948, and pruned and exhaustive top-1 differ. Which documents match never changes.

Who is affected

#

Applications that run a scoring SynonymQuery with three or more terms and boosts below 1, from SynonymQuery.Builder or a QueryBuilder-based parser fed tokens with boosts (since 8.5.0), with the default codec, BM25 and searcher. In the study's probe 568 of 729 one-decimal boost triples hit it (one 60-document corpus), but the effect is 1-2 ulps; matching never changes.

Mechanism, terms and numbers705 words

SynonymQuery scores "the sum of all term frequencies for the document", each frequency multiplied by its per-term boost. SynonymScorer.freq() adds boost * freq in a float running sum, in the order of the disjunction's topList(), and that order follows the heap layout, which depends on how the iterator reached the document. Float addition is not associative, so with three or more terms whose boosted freqs do not add exactly, the same document gets slightly different scores on different paths: identical documents in one search score 1-2 ulps apart and come back out of doc-id order, and explain(), which builds a fresh scorer and calls advance(doc), reports a value the hit did not get. Separately, the max-score bound comes from the merged impacts, an exact integer sum of per-norm impact freqs (boosted ones rounded up); above 2^24 occurrences in one field the float sum can round above it, so score() exceeds getMaxScore() and pruned and exhaustive top-k disagree. It came with per-term boosts in 8.1.0 (LUCENE-8652) and is in every release up to 10.6.0 and main. CombinedFieldQuery has the same float sum (LFV-277, merged here). Summing in double and rounding once removes both symptoms in every executed probe.

The bug

#
  1. SynonymScorer.freq() walks disjunctionDisi.topList() and keeps a float running sum: float freq = w.freq(); ... freq += w.freq(); (SynonymQuery.java:610-617 at 645d4fe14a20), where DisiWrapperFreq.freq() is the float product boost * pe.freq() (:659-661).
  2. topList() returns the lead iterators' list or prepends the matching other iterators (DisjunctionDISIApproximation.java:196-218); DisiPriorityQueueN.topList() walks heap[0], then the heap[1] and heap[2] subtrees (DisiPriorityQueueN.java:71-84). The order is the heap layout, a product of the iteration history.
  3. A search drives the scorer with nextDoc(). SynonymWeight.explain builds a fresh scorer and calls advance(doc) (SynonymQuery.java:246-249), then freq() (:253). The two paths can add the same three products in different orders.
  4. It needs at least three of the query's terms matching the same document (two float operands commute) and boosted freqs that do not add exactly. With all boosts 1 and a summed freq below 2^24 the sums are exact.

The numbers

#
  • Minimal input (four identical documents a b c, BM25, Synonym(a^0.2, b^0.2, c^0.3)): the nextDoc() path scores doc0 = doc3 = 0.038817033 and doc1 = doc2 = 0.038817026 (freq 0.7); a fresh advance(doc) scores all four 0.038817033 (freq 0.70000005). The exact sum of the three floats, 0.7000000178813934..., lies exactly halfway between the floats 0.7 and 0.70000005; rounded once (the fix) it is 0.70000005, and all four hits score 0.038817033.
  • How common in its setup: three-term queries built through QueryBuilder from tokens with one-decimal boosts 0.1..0.9 (all 729 triples), 60 documents, BM25: 568 of 729 fail CheckHits.checkExplanations, the first being Synonym(f:a^0.1 f:b^0.1 f:c^0.1); 0 with the fix.

The second, rare symptom: score above getMaxScore()

#

mergeImpacts bounds each norm's frequency with the exact long sum of the (ceil-boosted) impact freqs (SynonymQuery.java:503, :543-564), and MaxScoreCache converts that int to float once (MaxScoreCache.java:80). The scorer converts each freq to float first and sums in float, which above 2^24 can round above the bound. ClassicSimilarity, boosts 1, 600 documents: doc 300 holds a x (2^24+3) and b x 3; (float) (2^24+3) is 2^24+4, and adding 3 rounds to 2^24+8, while the bound is the exact 2^24+6. Doc 300 scores 1.032795 > getMaxScore(511) = 1.0327948; a pruned top-1 search returns doc 0 (a x (2^24+6), 1.0327948) and an exhaustive one doc 300. Under exact arithmetic the two tie, so the pruned answer is the exact one; the defect is the broken bound and the disagreement. In the tested BM25 settings (k1=1.2/b=0.75 and k1=1e7/b=1) a scan of freqs 2^24..2^24+63 plus 1..7 found no score change, under that probe's statistics.

The same pattern in CombinedFieldQuery (LFV-277, merged here)

#

CombinedFieldScorer.freq() sums freq * weight in float over the same kind of topList() (CombinedFieldQuery.java:424-434), and its explain also uses a fresh advance(doc) (:323-326). With 3 or more matching fields and non-dyadic weights such as 1.1 and 1.2, explain() can differ from the hit by 1 ulp; no ranking change was shown there. Its if (freq < 0) // overflow check, inherited from the old int loop, cannot fire for a float sum.

Exposure and likelihood230 words
  • Who is exposed. A scoring SynonymQuery with three or more terms matching the same document and per-term boosts below 1: from SynonymQuery.Builder#addTerm(term, boost), or since 8.5.0 (LUCENE-9171) from QueryBuilder, which copies each stacked token's BoostAttribute into the query (QueryBuilder.java:385-395, :603-609), for example from DelimitedBoostTokenFilter ("foo|0.7"). Default IndexWriterConfig, codec, BM25 and IndexSearcher; ordinary small documents; any index size.
  • What users see. Equally relevant documents score 1-2 ulps apart within one search and come back out of doc-id order; explain() reports a value the hit did not get. Test suites that compare explain() with the score exactly, as Lucene's CheckHits.checkExplanations does, fail. Nothing throws or logs.
  • Not affected. Which documents match: without scores (FILTER, MUST_NOT, ConstantScoreQuery, the query cache) createWeight builds a weight over TermQuery SHOULD clauses instead (SynonymQuery.java:181-195), which never runs this code. Single-term queries use a TermScorer.
  • The bound part is rare. More than 2^24 occurrences of the synonym terms in one field of one document and a similarity such as ClassicSimilarity or LMDirichlet; TOP_SCORES and COMPLETE then return different top hits, so CheckHits.checkTopScores fails. AssertingScorer (score <= getMaxScore(docID()), AssertingScorer.java:130) checks the bound only after advanceShallow, so it trips only in tests that shallow-advance the scorer, not in ordinary searches.
  • How likely. Common in its setup, tiny in effect: priority low (registry: minor, common, low).

Why it looks unintended

#
  • The javadoc scores "the sum of all term frequencies for the document": the same for identical documents.
  • Lucene's test framework requires explain() to equal the score exactly; LUCENE-8008 removed the tolerance for "a slightly different order of operations".
  • Up to 8.0.0 the sum was an exact int; #12682 fixed the same order-dependent float sum elsewhere with a double sum.
The full argument256 words
  • A per-document contract. "it will match any of the terms but only invoke the similarity a single time, scoring the sum of all term frequencies for the document" (SynonymQuery.java:47-49).
  • explain() == score, exactly, in Lucene's test framework. CheckHits.verifyExplanation asserts assertEquals(score, value, 0d) (CheckHits.java:393); it is the test framework's rule, not a public API promise. LUCENE-8008 (#9056, d27ddcb409d, 2017) made it exact and removed EXPLAIN_SCORE_TOLERANCE_DELTA, whose javadoc read "Some explains methods calculate their values though a slightly different order of operations from the actual scoring method".
  • The max score is a bound. Scorer#getMaxScore returns "the maximum score that documents between the last target ... and upTo included" (Scorer.java:75-79); AssertingScorer.java:130 asserts score <= getMaxScore(docID()) once a caller has shallow-advanced the scorer. LUCENE-8652's second patch wrapped the boosted impacts "to scale the term frequency for max scores".
  • Precedent. #12675 ("We generally prefer scores to not depend on the order of clauses ... sum up scores into a double") and PR #12682 (merged 2023-10-23) fixed this in MultiSimilarity and PassageScorer; DisjunctionSumScorer.score sums the same kind of topList in double (DisjunctionSumScorer.java:39-47).
  • It worked before. Up to 8.0.0 SynonymScorer.freq() was an exact int sum; LUCENE-8652 (2019) made it a float sum when it added per-term boosts, and its discussion never mentions rounding, order or explain.
  • Tests never reach it. testBoosts uses boosts 0.25, 0.5 and 1 with small freqs, which add exactly (TestSynonymQuery.java:222-280); testScores and testRandomTopDocs use exactly two terms (:178-220, :453-514), where float addition commutes.
The devil's-advocate check265 words

The strongest case, from the refute review, the works-as-designed review and the devil's-advocate verifier: scoring is float arithmetic and no javadoc promises bit-identical scores across iteration paths; QueryUtils.checkSkipTo and checkFirstSkipTo tolerate 1e-5 and 1e-3 between nextDoc and advance (QueryUtils.java:356, :410) CheckHits.checkEqual tolerates 1e-6 between hit lists (CheckHits.java:223), and CheckHits.verifyExplanation allows 2 ulps per detail inside a "sum of" explanation ("TODO: remove this leniency", CheckHits.java:476-483); MIGRATE.md:852-856 says Lucene "does not guarantee identical scoring or document ranking behavior across major version upgrades"; maintainers have declined accuracy-only scoring work ("In general scoring doesn't focus on accuracy", #9547 / LUCENE-8501); and the bound part needs more than 2^24 occurrences.

Why it fails: this is consistency, not accuracy. The same document gets two scores from the same query on the same index, explain() reports a value the hit did not get, which is the exact rule LUCENE-8008 restored, and identical documents tie-break out of doc-id order. The tolerances cover only nextDoc/advance and hit-list comparisons and the inner sums of an explanation tree, not the top-level explain == score or score <= getMaxScore; MIGRATE.md is about upgrades, not one search; and the fix makes the score more accurate, not less (the correctly rounded sum for the repro operands; in general it greatly reduces the order dependence without removing it for every input). The refute review and the works-as-designed review rated the intended-behaviour argument weak; the devil's-advocate verifier called the nextDoc-vs-advance difference on its own tolerated but found the bug real, and the adjudication found no convincing not-real argument. Verdict: not intended, a defect, low priority.

Suggested fix

#

Recommended Sum in double and round once; same double product in mergeImpacts (validated)

Sum the boosted frequencies in double and round to float once, in SynonymScorer.freq() and DisiWrapperFreq.freq(), and use the same double product before Math.ceil in mergeImpacts, so the bound still dominates; the same change in CombinedFieldScorer.freq() fixes the CombinedFieldQuery copy. With it the repro passes, and so do the whole org.apache.lucene.search test package (2,342 tests) and TestQueryBuilder.

// SynonymQuery.SynonymScorer
float freq() throws IOException {
  DisiWrapperFreq w = (DisiWrapperFreq) disjunctionDisi.topList();
  double freq = w.freq();
  for (w = (DisiWrapperFreq) w.next; w != null; w = (DisiWrapperFreq) w.next) {
    freq += w.freq();
  }
  return (float) freq;
}
// SynonymQuery.DisiWrapperFreq
double freq() throws IOException {
  return (double) boost * pe.freq();
}

Sum in double and round once; same double product in mergeImpacts (validated) (recommended)

#

In SynonymQuery, DisiWrapperFreq.freq() returns (double) boost * pe.freq(), SynonymScorer.freq() accumulates in a double and returns (float) freq, and mergeImpacts computes (int) Math.ceil(freq * (double) boost) so the bound uses the same product as the score. In CombinedFieldQuery, CombinedFieldScorer.freq() does the same with (double) freq * weight and drops the freq < 0 overflow check, which a float or double sum never triggers. 2 files, +14/-11, formatted with ./gradlew :lucene:core:tidy.

// SynonymQuery.SynonymScorer
float freq() throws IOException {
  DisiWrapperFreq w = (DisiWrapperFreq) disjunctionDisi.topList();
  double freq = w.freq();
  for (w = (DisiWrapperFreq) w.next; w != null; w = (DisiWrapperFreq) w.next) {
    freq += w.freq();
  }
  return (float) freq;
}
// SynonymQuery.DisiWrapperFreq
double freq() throws IOException {
  return (double) boost * pe.freq();
}

Trade-offs

  • Why it works. A float times an int below 2^29 is exact in double, and the sum of such products is exact whenever they fit one 53-bit window, which covers ordinary boosts and frequencies; an exact sum does not depend on the order, and rounding it once gives the correctly rounded float. The bound is an exact integer sum of per-norm impact freqs, each boosted one Math.ceil of the same double product and so never below it; it is therefore at least the exact sum, and since rounding is monotone it dominates the score's freq again.
  • Not every possible input. As the adjudication and the intended-behaviour check put it, a double sum is exact for the repro operands but not order-independent for every possible input (for example boosts many binades apart); option C is the strictly order-independent variant.
  • Scores change in the last bits, to the correctly rounded sum: in the repro the summed freq of docs 1 and 2 moves up 1 ulp (0.7 to 0.70000005) and their score 2 float ulps (0.038817026 to 0.038817033). Worth a CHANGES.txt line, since exact scores change.
  • Cost. Double arithmetic per matching term per scored document; no benchmark was run.
  • Review. No reviewer has read the diff line by line yet; #418 (stale, open) rewrites mergeImpacts and may conflict.

Sum in a fixed term order, still in float (fixes the order symptom only)

#

Collect the matching wrappers, sort them by term index and add them in that order, in float.

Trade-offs

The independent reproducer's shadow of exactly this fixes the identical-documents and explain tests but not the max-score tests (2 of 5 still fail), because the float sum can still round above the exact integer bound above 2^24. It also costs a sort per scored document.

Sum in term order, in double (strictly order-independent)

#

Accumulate each term's boost * freq in double in term-index order (for example into a small array indexed by term), then round once.

Trade-offs

The adjudication's strictly order-independent variant: the result never depends on the heap layout, for any input. Costs an array write and an ordered pass per scored document; not built or run.

Document that scores may differ in the last bits

#

Say in the javadoc that a SynonymQuery's score can differ by a few ulps depending on how the scorer reached the document.

Trade-offs

Leaves explain() disagreeing with the hit, against the exact rule of CheckHits.verifyExplanation, leaves identical documents out of doc-id order, and leaves the score above getMaxScore() in the 2^24 case. Not recommended.

Downstream note

#

Only score values move: for filters, exclusions, ConstantScoreQuery and cached clauses createWeight builds a plain term disjunction instead, which never runs this code, so which documents match, and any filter-based access restriction, are unaffected. The one cross-document effect measured is tiny: rearranging deleted documents changed 80 of 5,986 visible scores by at most 2 ulps (0 with the fix).

How it was found

#

While writing SMT (Z3) floating-point lemmas for SynonymQuery's max-score bound, the finder dropped a size precondition and asked for a counterexample; Z3 found one in 0.4 s, which became the 2^24 test. Separately, Lucene's own explanation check failed on three-term boosted synonym queries in the unit's differential test, and a search minimised it.

The method in full147 words

Method: semi-formal (the hypothesis came from code reading while modelling; the lemma was posed as a counterexample search).

  • A hunt unit (DisjunctionMax, Synonym and CombinedField queries) split SynonymQuery's merged-impacts bound into Z3 floating-point lemmas with a model-to-Java line map. Lemma S1 (boost 1, no size precondition) came back sat in 0.4 s: freqs 778,681,664 and 1,281,827,656 give a float sum of 1.9189989566802978515625 x 2^30, above the bound 1.91899883747100830078125 x 2^30. With the precondition "sum < 2^24" the same lemma is unsat. The witness became the public-API max-score test.
  • The merge logic itself was checked bounded-exhaustively on the real mergeImpacts: 7,743,376 configurations, 0 failures (mutants killed).
  • The order symptom came from the unit's differential baseline: QueryUtils.check reported explanation mismatches on three-term boosted SynonymQuery, and a random search over small indexes minimised it to a six-document test; the four-document test came later, from the independent reproducer.

History

#

Introduced with per-term synonym boosts in 8.1.0 (LUCENE-8652, 2019), which replaced the exact int sum with a float running sum. Every release from 8.1.0 to 10.6.0 and main is affected; 8.0.0 is not.

Versions tested6 rows

LFV-272, snapshot of 2026-11-06

Registry title
SynonymQuery adds up boosted term frequencies in float in heap order, so identical documents can score differently and explain() can differ from the hit score; with more than 2^24 occurrences in one field a score can exceed getMaxScore()
Area
search / SynonymQuery scoring (SynonymScorer.freq float sum) and its merged-impacts max-score bound
Priority
Low, rank 764: Weighted SynonymQuery scores differ by 1 ulp depending on the path, which reorders tied documents and breaks explain(); it is common in its configuration but tiny in effect.
Impact class
minor
Impact note
Applications that run a SynonymQuery with three or more terms and per-term boosts below 1 (built with SynonymQuery.Builder#addTerm(term, boost), or since 8.5.0 by QueryBuilder-based query parsers from a synonym token stream that sets BoostAttribute), with the default BM25, codec and IndexSearcher and on ordinary small documents, get scores that differ by about 1 ulp depending on how the scorer reached the document, so identical documents in one segment can score differently and rank out of doc-id order, and explain() differs from the hit score (with -ea and -da, 8.1.0 to 10.5.2 and main); separately and rarely, a field that holds more than 2^24 occurrences of the synonym terms, scored with ClassicSimilarity or LMDirichletSimilarity (BM25 showed no effect in the probes), can score above getMaxScore(), so pruned and exhaustive top-k disagree; which documents match never changes.
Summary
You run a SynonymQuery with three or more boosted terms, for example Synonym(a^0.2, b^0.2, c^0.3) over four identical documents 'a b c' with the default BM25, and expect identical documents to score the same and explain() to report the hit's score, because the query scores 'the sum of all term frequencies for the document'. SynonymScorer.freq() adds boost * freq in float, in the order of the disjunction's topList(), and that order depends on how the iterator reached the document, so the rounding differs: docs 0 and 3 score 0.038817033, docs 1 and 2 score 0.038817026, and explain(doc 1) reports 0.038817033. The same float sum can also round above the exact integer sum that the merged impacts use as the max-score bound once a field holds more than 2^24 occurrences of the terms: under ClassicSimilarity a document scores 1.032795 while getMaxScore() is 1.0327948, and a pruned top-1 search returns a different document than an exhaustive one.
