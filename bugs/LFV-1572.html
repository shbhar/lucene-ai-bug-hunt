The finding in 30 seconds

#

The limits first. It needs three things together: Lucene's jars on the module path, an explicit resource loader and a file of this one package. It fails loudly, with an IOException that names the file, while the chain is built. new AlbanianAnalyzer() and the class path are not affected. A launch flag works around it. No release has the package.

Background: modules, opened packages and the two loaders

#
  1. Lucene's jars carry module descriptors. On the module path each jar runs as a named module, here org.apache.lucene.analysis.common and org.apache.lucene.core. On the class path the descriptors play no part.
  2. exports makes a package's public classes usable by other modules. A resource file such as stopwords.txt is another matter: the JDK's resource lookup gives it to code in another module only if the package is open to that module (in a descriptor: opens <package> to <module>).
  3. ModuleResourceLoader and ClasspathResourceLoader are classes of lucene-core that read such files for factory chains, for example the words file of a stop filter in a CustomAnalyzer. So lucene-analysis-common opens its packages that hold a word-list file to org.apache.lucene.core (since 9.1.0).

The finding, step by step

#
  1. You run Lucene as named modules (the jars on the module path) and build a CustomAnalyzer with new ModuleResourceLoader(AlbanianAnalyzer.class.getModule()), a whitespace tokenizer and a stop filter whose words file is org/apache/lucene/analysis/sq/stopwords.txt, the Albanian list that the jar ships.
  2. You expect the chain to build and libri dhe to give [libri] (dhe is on the list). The same code gives that on the class path, and the same chain over the Bulgarian list gives [книга] for книга и on the module path.
  3. Instead the builder throws java.io.IOException: Resource not found: org/apache/lucene/analysis/sq/stopwords.txt from its addTokenFilter call, with assertions on and off (run on main b5a4546a5964 and branch_11x 262e019500ec, commits of 2026-11-22).
  4. Why: the JDK's resource lookup gives a file of a package of a named module, other than a class file, to code in another module only when the package is open to that module. At those commits the descriptor of lucene-analysis-common has 26 clauses opens <package> to org.apache.lucene.core, one for each other package with a word-list file, and none for org.apache.lucene.analysis.sq, which it only exports.
  5. What did not fail in the runs: new AlbanianAnalyzer() (it reads its own file from inside the module; 262 stop words), the 40 word-list files of the 26 other packages, and each run on the class path. With the launch flag --add-opens=org.apache.lucene.analysis.common/org.apache.lucene.analysis.sq=org.apache.lucene.core the chain builds and gives [libri].

Who is affected

#

Applications that run Lucene as named modules, pass an explicit ModuleResourceLoader (or a ClasspathResourceLoader built from a class of lucene-analysis-common) and name a word-list file of the Albanian package in a factory chain. The module path and the loader are the application's choices; no scale is needed. The failure is loud, and one launch flag works around it.

Mechanism, terms and numbers1,022 words

The limits first. It needs three things together: Lucene's jars on the module path (as named modules), an explicit resource loader (ModuleResourceLoader, or ClasspathResourceLoader built from a class of lucene-analysis-common) and a word-list file of this one package, org.apache.lucene.analysis.sq. The package is new code on branch_11x and main and in no release, so no released Lucene has the defect. Each run was made with OpenJDK 25.0.3 on Linux aarch64; no other JDK or system was run.

The cause is one missing clause. Since 9.1.0 the module opens its packages that hold a word-list file to org.apache.lucene.core, so that ModuleResourceLoader and ClasspathResourceLoader can read them (LUCENE-10348, by Uwe Schindler), and Lucene's check TestModularLayer.testAllOpenAnalysisPackagesInSync states that rule. At the two commits the descriptor exports the new package (module-info.java:80) and has 26 opens clauses (:96-147), none for it: the jar has 27 packages with a word-list file, and sq is the one that is not opened. The loaders behave as documented for a package that is not opened; the defect is the descriptor. 11.0.0 would be the first release with the package if branch_11x is released with the descriptor as it was at the commits that were run (3221dd4cf3a1 of 2026-11-20, 262e019500ec of 2026-11-22).

The call that is refused

#
  1. ModuleResourceLoader.openResource is module.getResourceAsStream(resource) with an IOException for null (lucene/core/src/java/org/apache/lucene/util/ModuleResourceLoader.java:38-43). ClasspathResourceLoader built from a class calls clazz.getResourceAsStream(resource) (ClasspathResourceLoader.java:58-71). Both run in the module org.apache.lucene.core.
  2. Both calls are the JDK's resource lookup. It gives a file of a package of a named module, other than a class file, to a caller in another module only when the package is open to the caller's module. Inside the failing launch the module reports sq exported=true, sq open to core=false, bg open to core=true. Both calls get null and the loaders throw.
  3. A factory chain reaches the loader while it is built, when the filter is added: addTokenFilter hands the builder's loader to the stop filter factory (lucene/analysis/common/src/java/org/apache/lucene/analysis/custom/CustomAnalyzer.java:389-395, :618-622), and the factory reads its words file through it (lucene/core/src/java/org/apache/lucene/analysis/AbstractAnalysisFactory.java:300-301). The IOException leaves addTokenFilter as it is, without a wrapper; build() (CustomAnalyzer.java:584-594) is not reached (run on both builds, assertions on and off).

What is not claimed

#
  • That the Albanian analyzer does not work on the module path. It does: AlbanianAnalyzer reads stopwords.txt through its own class (AlbanianAnalyzer.java:76-82) and AlbanianNormalizer reads cwords.txt through its own class (AlbanianNormalizer.java:77-82); the light-stem filter reads no file.
  • That a loader misbehaves. The exception is the loaders' documented answer for a package that is not opened.
  • That CustomAnalyzer.builder() or builder(Path) without a loader is affected by this. Those use a class-loader lookup, which is the separate finding LFV-1513 (known upstream, another cause); the clause changes nothing for it.
  • That a custom chain over the raw file gives the analyzer's stop set: the analyzer normalizes the list when it loads it. The finding is about opening the file.

Why it looks unintended

#
  • The rule is Lucene's own: since 9.1.0 (LUCENE-10348, by Uwe Schindler) analysis packages with a word-list file are opened to org.apache.lucene.core for these two loaders.
  • Lucene's check of that rule, run with @Test on its method, fails on org.apache.lucene.analysis.sq alone.
  • The loaders are right: the exception is their documented answer. The missing clause is the defect.
The full argument389 words
  • The rule in the project's words (LUCENE-10348: #11384 and pull request #581, by Uwe Schindler, in 9.1.0). #11384: "it is currently impossible to use CustomAnalyzer and refer to stopwords files in the analyzers module, because those are hidden" and "my proposal is to only open those packages only to lucene core, so the ModuleResourceLoader and ClasspathResourceLoader can see those resources". #581: "For now I made the distribution test assert that all analysis modules open up all packages to lucene core if they contain at least one of those file types", which it lists as "stopwords (*.txt)" and "ICU break iterator files (*.brk)".
  • The check states it as an equality. lucene/distribution.tests/src/test/org/apache/lucene/distribution/TestModularLayer.java:363: "This test ensures that all analysis modules open their resources files to core." The method (:364-386) requires the opened packages of each analysis module to be exactly the packages of its jar with a .txt or .brk file, each opened only to org.apache.lucene.core.
  • The check, run on main b5a4546a5964. With @org.junit.Test on that one method it fails with could not find the following elements: ["org.apache.lucene.analysis.sq"]; with the one clause in the descriptor it passes. As the class is, the build runs no method of it: that is the separate finding LFV-389, which has another fix site and is cited here, not claimed.
  • The list was kept in step by hand once before. #13209 (Robert Muir, 2024) removed the ga clause when the Irish stop-word file left that package: "I removed the now-unnecessary opens. Nice test :)". The 26 clauses at b5a4546a5964 are the 27 of 9.1.0 without ga, and their 52 lines date from LUCENE-10348. sq is the first package with a word-list file added to this jar since the rule exists (by the trees of the release tags).
  • The file is meant for this use. AlbanianAnalyzer.DEFAULT_STOPWORD_FILE is public (AlbanianAnalyzer.java:54), as in the sibling analyzers, and the list's header says the spellings with ë and ç were "added so that the list also works without AlbanianNormalizationFilter in front of it" (stopwords.txt:8-10).
  • Nothing says the package is meant to stay closed. The descriptor hunk of #16957 is one exports line and two provides entries, and its description, comments, reviews and commit messages have no word on opens, the module path or a resource loader (read on 2026-11-22).
The devil's-advocate check224 words

The strongest case for "intended". The loaders' javadoc puts the duty on the user: "To use this class, you must open the module to the org.apache.lucene.core module, otherwise resources can't be looked up." (ModuleResourceLoader.java:27-28; ClasspathResourceLoader.java:26-29 says the like). Core's own test expects this very exception for a package that is not opened (lucene/core.tests/src/test/org/apache/lucene/core/tests/TestModuleResourceLoader.java:35-50). And a package's resources may be internal: pt and compound.hyphenation hold non-class files and are not opened.

Why it fails. The sentence addresses whoever writes the descriptor of the module that holds the resource, and for lucene-analysis-common that is Lucene. An application cannot add a clause to another module's descriptor; it can work around the missing clause on its own side (the launch flag, or, where it defines the module layer of Lucene's jars itself, a call on that layer's controller: both were run), and neither is the clause. Lucene met that duty on purpose for its word-list packages and has a check that requires the set to be exact. The loader's test shows that the loader behaves as designed, which this finding does not dispute. And sq is not an internal-only package: it holds a stopwords.txt, the first file kind the rule names, with a public file-name constant. What the argument bounds is the weight, Low, and the limits are said first on this page.

Suggested fix

#

No patch is proposed. A shape that was tried: one clause, opens org.apache.lucene.analysis.sq to org.apache.lucene.core;, written on two lines like its 26 neighbours. With it the test passes, Lucene's own check passes once it runs, and the module's suite shows no failure. The maintainers choose the form.

Limits and trade-offs. The clause gives org.apache.lucene.core deep-reflection access to the package, as each of the 26 existing clauses does for its package. cwords.txt, which the normalizer reads for itself, becomes readable through the loaders too; gl is the precedent (galician.rslp sits in a package that is opened for its stop-word file). The clause helps the first release with the package only if it is on branch_11x as well as on main. It is no remedy for the separate findings LFV-389 (the check that would have flagged the package runs no method) and LFV-1513 (the class-loader lookup of the builders without a loader). The suites ran with one seed, on one JDK and one platform.

Two other ways

#
  • Keep the package closed and say so: not built, not run. The descriptor would stay as it is and the Albanian word lists would be stated to be internal. It would be the one word-list package that the rule of 9.1.0 does not cover: Lucene's check would need an exception for it, and the stop-word file of the jar could not be named in a factory chain on the module path.
  • Nothing in the code, the launch flag: run, a workaround for an application. --add-opens=org.apache.lucene.analysis.common/org.apache.lucene.analysis.sq=org.apache.lucene.core on the command line of the application. On the built jars of main b5a4546a5964 and branch_11x 262e019500ec the test passes with it, assertions on and off. It leaves the descriptor out of step with Lucene's own check.
