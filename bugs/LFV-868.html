AutomatonToTokenStream rejects an acyclic automaton that has an unreachable state with a false "Cycle found in automaton" error

AutomatonToTokenStream.toTokenStream silently needs every state with a transition to be reachable from the start state; its javadoc asks only for a finite DAG. A 3-state acyclic automaton with one unreachable state gets IllegalArgumentException: Cycle found in automaton instead of its one token or an accurate error, since 8.10.0.

The finding in 30 seconds

#

A token graph is built from an automaton by walking it from the start state. The walk only reaches what the start can reach; the in-degree count looks at every state.

Background: automata and AutomatonToTokenStream

#
  1. An Automaton is a set of numbered states joined by labelled transitions. State 0 is always the start; a string matches when its labels lead from state 0 to an accepting state.
  2. Automaton.Builder lets you create states and transitions freely, so a state can exist that no transition leads to. It is unreachable: no string ever passes through it.
  3. AutomatonToTokenStream.toTokenStream turns an acyclic automaton into a token graph. It orders the states with a Kahn-style sort started from state 0 only: take a state from the queue, subtract its outgoing edges, and queue each state whose count of unprocessed incoming edges drops to 0. Nodes "that have the same distance from the start" (the javadoc) become one position, and each transition a token.

The finding, step by step

#
  1. Build a 3-state automaton with Automaton.Builder: 0 -a-> 2 and 1 -b-> 2, state 2 accepting. It has no cycle; nothing leads to state 1. (Lucene's own TokenStreamToAutomaton builds the same kind of automaton for the text "the" after a stop filter removed it.)
  2. Convert it with AutomatonToTokenStream.toTokenStream. Its javadoc asks only for "a finite DAG", which holds.
  3. You expect the one path from the start state, the token a, or at least an error saying that state 1 cannot be reached.
  4. Instead it throws IllegalArgumentException: Cycle found in automaton. It counts 2 edges into state 2, from state 0 and from state 1, but its walk starts at state 0 and never visits state 1, so 1 edge is left over and read as a cycle.
  5. The same with assertions on and off, on every release since 8.10.0. The reachability rule was noted when the class was designed (#157), but it never reached the javadoc or the message.

Who is affected

#

Only applications that call the public AutomatonToTokenStream.toTokenStream themselves with an automaton that has a transition out of an unreachable state: a hand-built one with an unused state, or TokenStreamToAutomaton output for stop-word-only text. No Lucene query, analyzer or index path calls it, and no use was found in Solr, Elasticsearch or OpenSearch. Rare; loud, never wrong output.

Mechanism, terms and numbers695 words

AutomatonToTokenStream.toTokenStream(Automaton) (lucene-core, public, no @lucene.internal or @lucene.experimental tag) turns an acyclic automaton into a token graph. Its javadoc states one precondition, "This requires the automaton be a finite DAG" (AutomatonToTokenStream.java:44, :46). The method counts incoming edges over the transitions of every state (:54-60) but starts its topological walk only at state 0 (:67), so an edge out of a state the walk never reaches is never subtracted: the method then reports "Cycle found in automaton" (:87-91), or "Start node has incoming edges, creating cycle" (:61-63) when that edge points at state 0. For 0 -a-> 2, 1 -b-> 2 (state 2 accepting) it throws instead of returning the token a or naming the unreachable state. Lucene's TokenStreamToAutomaton builds such an automaton for the text "the" after a stop filter removed it. The restriction was stated when the class was designed (#157 issue comment 862439629), but neither the javadoc nor the messages say so, and both messages name a cycle that does not exist. Every release since 8.10.0 is affected; it is not fixed upstream. Ignoring unreachable states with one reachability pass fixes it (validated); documenting the rule and throwing an accurate message is the alternative (validated). Low impact: no Lucene production code calls the converter.

Terms

#
  • Automaton (org.apache.lucene.util.automaton, @lucene.experimental): integer states, "State 0 is always the initial state"; transitions carry character ranges; accept states end a match. Automaton.Builder does not require every state to be reachable.
  • AutomatonToTokenStream.toTokenStream (org.apache.lucene.analysis, lucene-core, public): "Nodes that have the same distance from the start are grouped together to form the position nodes for the TokenStream ... This requires the automaton be a finite DAG." (AutomatonToTokenStream.java:41-44); @param automaton automaton to convert. Must be a finite DAG to avoid infinite loops! (:46).

The bug, step by step (AutomatonToTokenStream.java at 5adff78bb168)

#

For 0 -a-> 2, 1 -b-> 2, state 2 accepting:

  1. :54-60 count the incoming edges of every state over the transitions of all states: indegree = [0, 0, 2].
  2. :61-63 reject any edge into state 0 ("Start node has incoming edges, creating cycle"): here indegree[0] is 0, so it passes.
  3. :67 seeds the walk with state 0 only. Popping it subtracts its one edge: indegree[2] becomes 1, which is not 0, so state 2 is not queued and the queue is empty. State 1 also has in-degree 0, but the walk only ever enqueues state 0 and states whose in-degree drops to 0 during the walk (:71-75), so state 1 is never popped and its edge is never subtracted.
  4. :87-91 find indegree[2] == 1 and throw "Cycle found in automaton".

If the unreachable state's edge points at state 0 instead (0 -a-> 1, 2 -b-> 0), step 2 throws "Start node has incoming edges, creating cycle". Both checks are sound cycle tests only when every state can be reached from state 0.

The exact rule

#

Bounded-exhaustive translation validation on the stock jar found the law: for an acyclic automaton (with at least one state), the method throws exactly when some transition leaves a state that state 0 cannot reach. Over all 33,554,432 topologically numbered 5-state automata over {a, b} (all acyclic) it rejects 10,048,896, every one for that reason, with 0 exceptions to the law either way; over all 8,503,056 4-state automata over {a, b} with at most one transition per ordered pair of distinct states (any numbering), it rejects 120,800 of the 151,184 acyclic ones. An unreachable state without transitions changes no in-degree and is accepted. (A cycle reachable from state 0 is rejected too, correctly; a 0-state automaton throws ArrayIndexOutOfBoundsException, LFV-865.) A separate re-run re-executed these counts on the stock jar.

Why it looks unintended

#
  • The javadoc's only precondition is "a finite DAG"; the example is one, and Automaton.Builder allows unreachable states.
  • Both messages say "cycle", and there is none: the repro's automaton has 2 edges and no path back to any state.
  • The design comment in #157 says such graphs are not supported, but that never reached the javadoc or the message.
The full argument134 words
  • Contract. AutomatonToTokenStream.java:44: "This requires the automaton be a finite DAG." :46: "@param automaton automaton to convert. Must be a finite DAG to avoid infinite loops!" Nothing mentions reachability. ("Requires" states a necessary condition, so a maintainer may read it as no promise that every finite DAG is accepted; the message stays false under that reading.)
  • A legal input. Automaton.Builder does not require reachability, and Lucene's own TokenStreamToAutomaton (@lucene.experimental, TokenStreamToAutomaton.java:35) emits such automata.
  • A false message. "Cycle found in automaton" and "Start node has incoming edges, creating cycle" both report a cycle for an automaton that has none.
  • Positions are defined from the start. "Nodes that have the same distance from the start are grouped together" (:42): unreachable states have no position and add nothing to the stream.
The devil's-advocate check164 words

The strongest case for "intended" (the intended-behaviour checker's; the adjudication read the comment itself): while sketching the algorithm in #157, Michael McCandless (mikemccand) wrote in issue comment 862439629 (2021-06-16) that it "cannot handle fully disconnected graphs (\"isolated subgraphs\"). All nodes must be reachable from any other node." The author acknowledged it (issue comment 865702423), the checks assume it, and the class was written as test infrastructure for FlattenGraphFilter.

Why it does not settle the issue: it shows the rejection is a known limitation, not that it is documented or that it should be reported as a cycle. The same comment's other precondition, finiteness, became an isFinite check and the javadoc's "finite DAG" in the same PR; reachability became neither. The class is public API in the lucene-core jar, so "test infrastructure" bears on severity, not on validity. Verdict: a documentation and error-message defect (the adjudication's category). A maintainer may prefer to keep rejecting such input with an accurate message; the repro accepts that.

Suggested fix

#

Recommended B. Ignore states that are not reachable from the start state

Ignore states the start state cannot reach: one reachability pass before the in-degree count; the javadoc says the DAG rule applies to the reachable part. The repro then gets the token a, cycles reachable from the start are still rejected, and the core analysis tests, TestFlattenGraphFilter and core's static checks pass.

// states that cannot be reached from the start state (state 0) are on no path of the automaton
FixedBitSet reachable = new FixedBitSet(transitions.length);
IntArrayList stack = new IntArrayList();
reachable.set(0);
stack.add(0);
while (stack.isEmpty() == false) {
  for (Transition t : transitions[stack.removeLast()]) {
    if (reachable.getAndSet(t.dest) == false) {
      stack.add(t.dest);
    }
  }
}
// then, in the in-degree loop: if (reachable.get(i) == false) continue;

Trade-offs

  • The stream is that of the reachable part, as if the unreachable states were not there: the token a for the repro and for 0 -a-> 1, 2 -b-> 0; 0 tokens for the stop-word text "the".
  • A cycle confined to unreachable states is no longer reported; it cannot affect the stream, and the new javadoc says so.
  • Cost: one extra pass over states and transitions.
  • For a 0-state automaton reachable.set(0) also fails, like indegree[0] today (LFV-865): an AssertionError from FixedBitSet with assertions on, an ArrayIndexOutOfBoundsException with them off; put that guard first.

Downstream note

#

No use of AutomatonToTokenStream was found in Elasticsearch, OpenSearch or Solr; code that converts its own automata can avoid the false error by calling Operations.removeDeadStates first, unless the language may be empty.

How it was found

#

Semi-formal: the converter on the stock jar was compared with a model of its documented construction on every automaton in bounded scopes (up to 5 states over {a, b}). It rejected many acyclic ones; for acyclic input it throws exactly when a transition leaves a state that state 0 cannot reach. The TokenStreamToAutomaton trigger came from reading its trailing-hole code.

The method in full163 words
  • Method: bounded-exhaustive translation validation. A model of the documented construction (positions by distance from the start, one token per transition label) was compared with the stock main jar on every automaton in bounded scopes, with an exception law as one of the obligations. The jar rejected acyclic automata (10,048,896 of all 33,554,432 topologically numbered 5-state automata over {a, b}; 120,800 of the 151,184 acyclic ones among all 8,503,056 4-state automata over {a, b} with at most one transition per ordered pair of distinct states, any numbering): the first signal.
  • The law: for an acyclic automaton, the method throws exactly when some transition leaves a state unreachable from state 0; it held with 0 violations in every scope.
  • Second trigger: reading TokenStreamToAutomaton's trailing-hole code (:221-242) showed that a stream whose only token was removed yields such an automaton; confirmed on the stock jar.
  • Witness: a public-API JUnit test on the stock jars, found 2026-10-28; this doc's repro is its one-test reduction.

LFV-868, snapshot of 2026-11-10

Registry title
AutomatonToTokenStream.toTokenStream silently requires every state to be reachable from state 0, which its javadoc does not say, and rejects an acyclic automaton with an unreachable state with a false 'Cycle found in automaton' / 'Start node has incoming edges, creating cycle' message (documentation and error-message defect; the restriction itself was stated at design time)
Area
core / analysis: AutomatonToTokenStream (automaton to token-graph conversion)
Priority
Low, rank 1287: A loud IllegalArgumentException with a false 'cycle' message and an undocumented reachability rule in a converter nothing in production calls, so it is Low, like the acyclic-input automaton contract row LFV-062.
Impact class
wrong error
Impact note
Code that calls the public lucene-core converter AutomatonToTokenStream.toTokenStream (no in-tree production caller: only TestFlattenGraphFilter and its own test use it; no downstream use found) with a finite acyclic automaton that has a transition out of a state not reachable from state 0 (a hand-built Automaton.Builder automaton with an unused state, or TokenStreamToAutomaton's output for text whose only tokens a StopFilter removed) gets an IllegalArgumentException naming a cycle that does not exist, while the javadoc's only stated requirement is 'finite DAG'; the failure is immediate and loud, never wrong output, no setting or scale is involved, every release since 8.10.0 is affected (executed), and Operations.removeDeadStates is a workaround except for an empty language, which then hits the sibling 0-state crash LFV-865.
Summary
You build a finite acyclic automaton with one extra state that nothing leads to, for example 0 -a-> 2 and 1 -b-> 2 with state 2 accepting, or you take TokenStreamToAutomaton's output for the text 'the' after a stop filter removed it, and convert it with AutomatonToTokenStream.toTokenStream, whose javadoc asks only for a finite DAG. You expect the token graph of the part reachable from the start (here the single token 'a'), or at least an error that says what is wrong. Instead it throws IllegalArgumentException 'Cycle found in automaton' ('Start node has incoming edges, creating cycle' when the unreachable state points at state 0), because it counts incoming edges over all states but walks only from state 0; the designers knew such input is unsupported (PR #157), but the javadoc never says so and the message is false.

The reachability requirement was stated in that PR's design discussion (#157 issue comment 862439629) but never reached the javadoc.
