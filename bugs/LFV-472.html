Merge-on-refresh never releases the files of a merged segment whose documents were all deleted during the merge

When every document of a refresh-time merge (merge-on-refresh, the default since 9.3) is deleted while it runs, IndexWriter drops the merged segment but never releases the file reference the refresh took on it. Its files stay on disk, even after close() or rollback(), until the next writer opens the index.

The finding in 30 seconds

#

The refresh takes its file reference (deleter.incRef) at the start of commitMerge, before the deletes made during the merge are carried over. commitMerge then drops the 100%-deleted segment but skips its referenced files. finishGetReaderMerge closes the unused reader and clears the map without decRef, so the cleanup that would release it finds nothing.

How a refresh merge holds on to files

#
  1. Opening or refreshing a near-real-time reader flushes, then (by default since 9.3) asks the merge policy to merge tiny segments and waits up to 500 ms, so the new reader sees fewer segments.
  2. IndexWriter counts references per index file and deletes a file when its count drops to zero.
  3. When a refresh merge finishes, the refresh opens a reader on the merged segment and takes a reference on its files, so that nothing deletes them before the new reader uses them.
  4. If every document of a merge was deleted while it ran, IndexWriter drops the merged segment instead of adding it, and deletes its files.

The finding, step by step

#
  1. Open an IndexWriter with the default config apart from the merge policy and a serial merge scheduler (so merge-on-refresh is on, 500 ms wait) and flush two one-document segments, _0 and _1.
  2. Refresh with DirectoryReader.open(writer): it merges _0 and _1 into _2. While that merge runs, both documents are deleted (in the test by a delete plus flush() from a merge hook; in real use by another thread's update and commit).
  3. IndexWriter sees that _2 is 100% deleted and drops it. You expect its files to be deleted, as they are when forceMerge drops the same segment.
  4. Instead the refresh had already taken a reference on _2's files for the new reader, and it closes that unused reader without releasing the reference. After w.close() all 10 files of _2 are still on disk and no commit references them; only the next IndexWriter deletes them.
  5. No hook is needed: a tight default-config loop of updates, commits and refreshes leaked 675 merged segments (2,025 files) in 4 s; with the fix, none.

Who is affected

#

Applications on 9.3.0 or later with the default IndexWriterConfig that refresh NRT readers while their own commits or flushes apply updates or deletes (8.7.0 to 9.2.0: only with merge-on-refresh turned on). Each hit leaks one small merged segment until the writer is reopened. Disk only; results stay correct; real-workload rates were not measured.

Mechanism, terms and numbers675 words

Merge-on-refresh (LUCENE-8962, on by default since 9.3.0) makes a near-real-time refresh wait up to 500 ms for merges of small segments. When such a merge completes, the refresh opens a reader on the merged segment and takes a reference on its files (deleter.incRef), at the start of commitMerge and before the deletes made during the merge are carried over. If those deletes removed every document, commitMerge drops the merged segment, and its file deletion skips the referenced files. finishGetReaderMerge then closes the unused reader and clears mergedReaders without decRef, so the cleanup that pairs close with decRef finds nothing. The files keep their reference for the rest of the writer's life: deleteUnusedFiles(), commit(), forceMerge, close() and rollback() leave them, and only the next IndexWriter open deletes them. Searches, commits and CheckIndex stay correct; it is a disk-space and file-count leak, one small merged segment per hit. A one-test repro fails on main 645d4fe14a20, 10.6.0, 10.5.2, 9.12.3 and 9.3.0; deleting the two offending lines fixes it.

Step by step (the minimal test)

#
  1. DirectoryReader.open(w) runs getReader. With maxFullFlushMergeWaitMillis > 0 (500 by default) it prepares point-in-time merges for MergeTrigger.GET_READER (:619-648), then finishGetReaderMerge runs the merge and waits for it (:738-739).
  2. The merge writes _2. commitMerge starts with merge.onMergeComplete() (:4894-4896). The wrapper's onMergeComplete (:4031-4045) has three conditions (:4034-4037); its only check against a dropped segment is info.info.maxDoc() > 0 /* never do this if the segment is dropped / empty */ (:4036-4037), and the other two (collection not stopped, merge not aborted) hold here. _2 has maxDoc 2, so the callback runs: reader opened, put in mergedReaders, incRef of _2's files.
  3. commitMerge carries over the deletes made during the merge (:4936-4937), finds the segment allDeleted (:4946-4949) and drops it with readerPool.drop and deleteNewFiles (:5002-5007). deleteNewFiles deletes only files without a reference (IndexFileDeleter.java:633-636, FileDeleter.java:154-156, 173-191), so _2's files survive.
  4. The wrapper's mergeFinished applies a merge to the point-in-time SegmentInfos only when segmentDropped == false (:3978-3980). maybeReopenMergedNRTReader removes a reader from mergedReaders, and later decRefs its files, only when its segment is in those SegmentInfos (:772, :780, :787-789). _2 is not, so its reader stays in the map.
  5. finishGetReaderMerge closes it and clears the map (:749-750). onGetReaderMergeResources.close() at the end of getReader (:723) finds nothing to release.
  6. _2's files keep a reference count of 1 for the rest of the writer's life. IndexFileDeleter.refresh(), which rollback() uses, also skips referenced files (IndexFileDeleter.java:455-486, :467). The next IndexWriter starts with fresh counts and deletes them as unreferenced.

Exposure and likelihood287 words
  • Who. Applications on 9.3.0 or later with the default IndexWriterConfig that refresh NRT readers (DirectoryReader.openIfChanged, SearcherManager.maybeRefresh) while their own commits or flushes apply updates or deletes. 8.7.0 to 9.2.0: only with setMaxFullFlushMergeWaitMillis > 0 and a merge policy that returns full-flush merges.
  • Settings. The default TieredMergePolicy proposes full-flush merges of segments each below its 16 MB floor (MergePolicy.java:689-714, TieredMergePolicy.java:79, 187-189); the default wait is 500 ms (IndexWriterConfig.java:108).
  • Trigger. Every document of a refresh merge's input segments must be deleted, and the deletes applied, while that merge runs. That favours workloads that keep rewriting the same documents.
  • Effect. One small merged segment's files per hit, kept through deleteUnusedFiles(), commit(), forceMerge, close() and rollback(); the next IndexWriter open deletes them. In one probe a leaked segment was 3 files, 2,378 bytes. The deleted documents' bytes stay in those files until then (raw file access only). No premature delete, no wrong result, no corruption, CheckIndex clean, no open file handle after close().
  • How often. Timing-dependent and not measured on real workloads. A tight default-config loop (one thread updating 2 ids, one committing continuously, refreshes for 4 s) leaked 675 merged segments; a milder loop (a commit every 2 updates, 5 s) leaked 1 to 13 merged segments per run on 2026-10-26 and none in 5 runs on 2026-10-31.
  • Likelihood: plausible. No fault is needed, but the window is narrow.
  • Workaround until fixed (by reading, not run on main): setMaxFullFlushMergeWaitMillis(0) turns off full-flush merges ("Set to 0 to disable merging on full flush"; this also turns off merge-on-commit), or reopen the IndexWriter from time to time. 9.2.0, where the wait is 0 by default, passes the minimal test.

Why it looks unintended

#
  • The code's own cleanup, onGetReaderMergeResources, pairs each close of a leftover reader with a decRef; finishGetReaderMerge empties the map before it runs.
  • rollback() promises to remove "any temporary files that had been created", deleteUnusedFiles() "any index files that are no longer used"; neither does here.
  • The same drop through forceMerge or merge-on-commit deletes the files.
The full argument238 words
  • The code's own cleanup releases the reference. onGetReaderMergeResources "closes the merged readers and decrements the files references ... for readers that haven't been removed from the mergedReaders and release elsewhere" and does decRef then close for each (IndexWriter.java:651-664); maybeReopenMergedNRTReader decRefs the readers it consumes (:787-789). Only finishGetReaderMerge closes without decRef, and by clearing the map it hides the leftovers from the cleanup.
  • The guard shows the intent. The callback is skipped for segments that are "dropped / empty" (:4036-4037); it misses only a segment that becomes 100% deleted later in the same commitMerge.
  • Public contracts. rollback(): "This removes any temporary files that had been created, after which the state of the index will be the same as it was when commit() was last called" (:2567-2570). deleteUnusedFiles(): "Expert: remove any index files that are no longer used" (:6171). Internal: "When all the commits referencing a certain file have been deleted, the refcount for that file becomes zero, and the file is deleted" (IndexFileDeleter.java:47-50).
  • Lucene's tests treat leftover files as failures: TestIndexWriter.assertNoUnreferencedFiles fails when a fresh writer would delete anything.
  • History. The feature author fixed the mirror-image problem on merge-on-commit before release (a premature delete of a "fully deleted and dropped" segment, #10005 comment of 2020-06-22). None of the 81 comments and reviews on lucene-solr#1623 discusses a dropped merged segment or leftover files.
The devil's-advocate check171 words

The strongest case for "works as designed": the next IndexWriter open cleans up, and Lucene tolerates unreferenced files elsewhere (MockDirectoryWrapper's check is "off by default; see LUCENE-5574"); LUCENE-8324 called a dropped segment's leftover files "not a massive issue"; the refcount promise is in an internal javadoc; deleting from wrapForMerge is an unusual hook; and four years passed without a CI report, although the test framework turns merge-on-refresh on.

Why it fails: LUCENE-5574 covers a reader that outlives its writer, while the repro closes every reader first, and next-open cleanup is the crash-recovery path. LUCENE-8324 was fixed anyway, "for correctness", which is the right framing here: real and minor. The public rollback() and deleteUnusedFiles() javadocs promise the deletion. The hook only makes the timing deterministic: a hook-free default-config loop leaks too, and the fix removes that leak. CI is silent because the unreferenced-files check is off by default and the merge-on-getReader tests do not delete all documents of a refresh merge while it runs. Verdict: not intended, a minor defect.

Suggested fix

#

Recommended Leave the leftover readers to the existing cleanup

Delete the two lines IOUtils.close(mergedReaders.values()); mergedReaders.clear(); in finishGetReaderMerge. The leftover readers then stay in the map, and the existing onGetReaderMergeResources cleanup, run at the end of getReader, closes them and releases their files. With it the repro and all 1,396 core org.apache.lucene.index tests pass, assertions on and off.

Release the leftovers in finishGetReaderMerge (the hunt's fix v2) (validated by the checks)

#

Copy the leftovers out of mergedReaders, clear the map, then decRef each leftover's files and close it; if that throws, close the reopened reader too (+17/-1 lines).

List<SegmentReader> leftovers = new ArrayList<>(mergedReaders.values());
mergedReaders.clear();
try {
  IOUtils.close(
      leftovers.stream()
          .flatMap(
              sr ->
                  Stream.<Closeable>of(() -> deleter.decRef(sr.getSegmentInfo().files()), sr))
          .toList());
} catch (Throwable t) {
  IOUtils.closeWhileSuppressingExceptions(t, reader);
  throw t;
}

Trade-offs

Releases the files right away, but duplicates the cleanup logic. Its first version decRef'd before clearing the map, so an exception while closing could let onGetReaderMergeResources decRef the same files again (found by the cross-model review); v2 clears first.

Take the reference only when the merge is applied (not suitable)

#

As merge-on-commit does, in mergeFinished when segmentDropped == false.

Trade-offs

The refresh must open the merged reader before the merge's own deletes are carried over, to keep point-in-time semantics (:3940-3948), so the reader and its files must be held from onMergeComplete on (by reading).

Polish for either fix: close each reader before its decRef

#

onGetReaderMergeResources (and v2) decRef first, so a released file is deleted while its reader is still open: 6 delete-while-open attempts in a probe with the fix.

Trade-offs

Harmless on POSIX; where the OS refuses to delete an open file, FSDirectory keeps a pending delete and retries later. Not run.

Workaround for users until a fix ships (not a fix)

Trade-offs

By reading, not run on main; loses the merge-on-refresh benefit.

Downstream note

#

Elasticsearch turns merge-on-refresh off and Solr leaves it opt-in (read in their sources, not run), so the exposure is mainly applications that use Lucene's default IndexWriterConfig or turn the feature on.

How it was found

#

While writing a TLA+ model of how IndexWriter counts file references, the finder noticed that the refresh's incRef has no matching decRef when the merged segment is dropped. The TLC model checker then found a 9-state trace ending with the files still referenced after rollback(), and a public-API test reproduced it on the real code.

The method in full183 words

Method: semi-formal (a code-reading hypothesis during modelling, witnessed by a model checker, then executed).

  • A hunt unit modelled the IndexFileDeleter reference-count protocol in TLA+ (IFDRefcount.tla): flushes, commits, merges, merge-on-commit, merge-on-refresh, NRT readers and rollback.
  • While writing the merge-on-refresh part, the finder saw that the callback's incRef has no decRef on the dropped-segment path. TLC confirmed it: invariant RcExact is violated in an 8-state trace and NoLeakAtQuiescence in a 9-state trace (flush, flush, refresh with a refresh merge, the merge writes, all its documents are deleted, commitMerge drops it, the refresh finishes, rollback: the merged segment's files keep a reference). With one thread (no deletes during the merge) the model is clean (1,572,782 states); with the fix every invariant holds (up to 71,975,928 states). The stock model never deletes a referenced file (up to 5,705,664 states).
  • The finder then replayed the trace as a public-API JUnit test on the real jars and measured a hook-free default-config loop. Independent reproducers, cross-model reviews (OpenAI GPT-5.6, reading only), an adjudication, an audit, the version-history runs, a prior-report search, a repro-minimization step and this doc followed.

LFV-472, snapshot of 2026-11-03

Registry title
Merge-on-refresh never releases the file references of a merged segment that is dropped because all its documents were deleted during the merge, so IndexWriter leaves that segment's files on disk until the next writer opens the index
Area
index / IndexWriter NRT merge-on-refresh (getReader point-in-time merges) and IndexFileDeleter refcounts
Priority
Low, rank 896: Merge-on-refresh in the default config since 9.3 can leak a dropped merged segment's files with no fault needed, but they only take up disk space until the next writer opens and results stay correct.
Impact class
minor
Impact note
Applications on 9.3.0 or later with the default IndexWriterConfig (merge-on-refresh on with a 500 ms wait, TieredMergePolicy proposing refresh merges of segments below its 16 MB floor) that refresh NRT readers while their own commits or flushes apply deletes or updates leak one small merged segment each time every document of a refresh merge is deleted while it runs (8.7.0 to 9.2.0: only with merge-on-refresh opted in); the files stay on disk and in the directory listing for the rest of that writer's life, through deleteUnusedFiles(), commit(), forceMerge, close() and rollback(), and the next IndexWriter opened on the directory deletes them; nothing is deleted too early, searches and commits stay correct, CheckIndex is clean, no scale is needed (three documents), and real-workload leak rates were not measured.
Summary
You keep an IndexWriter open, refresh near-real-time readers from it (DirectoryReader.openIfChanged) with merge-on-refresh on, which is the default since 9.3, and while a refresh-triggered merge of small segments runs, a commit or flush applies deletes that remove every document of that merge. You expect the merged segment, which IndexWriter drops as 100% deleted, to have its files deleted, as happens when the same segment is dropped by an ordinary merge. Instead the refresh has already taken a file reference on it and later closes its reader without releasing that reference, so the segment's files stay in the directory through deleteUnusedFiles(), commit(), close() and rollback(), until the next IndexWriter opens the index.
