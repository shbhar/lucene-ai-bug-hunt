The finding in 30 seconds

#

The documented layout misses four fields the writer writes, gives NameCounter the wrong type, and links little-endian writers for fields written big-endian.

What you need to know first

#
  1. Every commit writes a small file segments_N (N is the commit generation) that lists the index's segments: name, id, codec, deletes and update generations. Lucene reads it back with SegmentInfos.readCommit.
  2. The SegmentInfos class javadoc documents that file as an ordered list of fields, each with a type and a link to the method that writes it (for example Int32 via DataOutput#writeInt). The default codec's file-formats overview links this page as the Segments File.
  3. Since 9.0, DataOutput#writeInt and #writeLong write little-endian. segments_N stays big-endian on purpose, written with CodecUtil.writeBEInt / writeBELong.

The finding, step by step

#
  1. Open and close an IndexWriter on an empty directory (main). Lucene writes segments_1: 69 bytes, a 35-byte header, 18 bytes of commit data and a 16-byte footer.
  2. Read it the way the SegmentInfos javadoc says: after the header comes LuceneVersion (three vInts: 11, 0, 0), then Version, an Int64 written by DataOutput#writeLong.
  3. You expect Version = 2, what SegmentInfos.getVersion() returns for this commit.
  4. You get 11. The next bytes are 0B and 00 00 00 00 00 00 00 02: an undocumented vInt, IndexCreatedVersionMajor = 11, then Version = 2 written big-endian, while writeLong is little-endian. From there every field is read at the wrong offset.
  5. The rest is stale too: NameCounter is a vLong, not an Int32, and each segment entry has three undocumented fields (SoftDelCount, a segment-commit id, FieldInfosFiles). Lucene's own reader matches the writer, so only hand-written readers break.

Who is affected

#

No Lucene user who goes through the API: writer and reader agree, so commits, search and CheckIndex work. It misleads anyone who writes their own segments_N reader, inspector, port or recovery tool from this javadoc, which the file-formats overview links as the Segments File. They go wrong right after LuceneVersion in every commit written since 7.0.

Mechanism, terms and numbers584 words

Every Lucene commit writes a small file, segments_N, that lists the index's segments, and the SegmentInfos class javadoc documents it field by field; the default codec's file-formats overview links that page as the Segments File. The documented layout no longer matches the bytes: the writer adds IndexCreatedVersionMajor (a vInt right after LuceneVersion, since 7.0.0), and per segment SoftDelCount (7.4.0), a segment-commit id (a flag byte plus 16 bytes, 8.6.0) and FieldInfosFiles (4.9.0), none of them listed; NameCounter is written as a vLong (7.2.0), not the documented Int32; and the fixed-width integers are written big-endian while the text links DataOutput#writeInt / #writeLong, which write little-endian since 9.0.0. SegID is also called the codec's identifier; it is the segment's id. Lucene's writer and reader agree, so nothing goes wrong at runtime; a reader that follows the text misreads the field right after LuceneVersion of every commit written since 7.0 (Version = 11 instead of 2 for an empty commit on main) and is out of sync from there on. The fix is a javadoc edit.

The bytes of an empty commit

#

new IndexWriter(dir, new IndexWriterConfig()).close() on main writes segments_1, 69 bytes. Between the 35-byte header and the 16-byte footer (which starts C0 28 93 E8) are 18 bytes:

0B 00 00                  LuceneVersion 11.0.0 (three vInts)
0B                        IndexCreatedVersionMajor 11 (vInt, undocumented)
00 00 00 00 00 00 00 02   Version 2 (big-endian Int64)
00                        NameCounter 0 (vLong)
00 00 00 00               SegCount 0 (big-endian Int32)
00                        CommitUserData, empty map

Read as documented, Version takes 0B 00 00 00 00 00 00 00 = 11 (little-endian), NameCounter 02 00 00 00 = 2, and SegCount 00 00 00 C0 = -1073741824, already one byte into the footer.

With segments

#

Fixing only the commit-level items is not enough. On an independent verifier's index (3 segments, NameCounter 160, a hard delete, a soft delete, a doc-values update, user data), applying IndexCreatedVersionMajor, big-endian integers and the vLong counter one by one, the read still fails in the first segment entry at UpdatesFiles until SoftDelCount, the segment-commit id and FieldInfosFiles are added; only the full writer layout parses exactly to the footer.

Exposure and likelihood175 words
  • Who. People who read, inspect or re-implement segments_N from the javadoc: ports to other languages, index inspectors, recovery or forensic tools, format tooling. The default codec's overview sends them there: "This document defines the index file formats used in this version of Lucene" (lucene104/package-info.java:50), "Details on each of these are provided in their linked pages" (:188), and the file table links SegmentInfos as the Segments File (:221-222).
  • Default vs opt-in. No setting is involved. Every commit written since 7.0 has the IndexCreatedVersionMajor byte where the text puts Version; every commit since 4.9.0 has FieldInfosFiles in each segment entry.
  • What they lose. A reader built from the text is out of sync from the field after LuceneVersion on; they have to read write() to find the real layout.
  • Scale. Small audience; the searches found no report since 2014. The prior-art search found two StackOverflow questions about decoding segments_N for recovery, so people do try; neither cites the javadoc.
  • Not affected. Lucene's behaviour, results and indexes. Nothing to fix in code.

Why it looks unintended

#
  • The page is an exact, typed, ordered grammar, and the file-formats overview says the details are "provided in their linked pages".
  • Extended as the format grew, though not every time (#16418 added DocValuesOverlays in 2026); the gaps come from changes that updated write() but not the text.
  • A stale segments-file doc was fixed as a defect before (LUCENE-350, 2005).
The full argument202 words
  • The contract is the page. An ordered element sequence, a type and a writer link for each element, and field descriptions (SegmentInfos.java:61-117); nothing marks it approximate. The overview: "This document defines the index file formats used in this version of Lucene" (package-info.java:50), "Details on each of these are provided in their linked pages" (:188).
  • Updated as the format evolved, though not every time. LUCENE-5618 (2014) added DocValuesGen and the map form of UpdatesFiles; LUCENE-5954 (2015) added LuceneVersion and MinSegmentLuceneVersion; #16418 (Jim Ferenczi, 2026-08-13) added DocValuesOverlays to the sequence, data types and descriptions. LUCENE-7756, LUCENE-7999, LUCENE-8341 and LUCENE-9324 changed the bytes without touching the text; none of their issues or reviews mentions it.
  • The oldest gap was made while editing the grammar. LUCENE-5618's commit (2014-05-21) rewrote the sequence in the same diff that added writeStringSet(getFieldInfosFiles()), and did not list it.
  • Precedent. LUCENE-350 (2005, "counter field in segments file is not documented in fileformats.xml"), LUCENE-3072 ("3.1 fileformats out of date") and LUCENE-7532 (a missing 6.2 file-format description) were fixed as defects. LUCENE-7532 came from a java-user@ thread ("an overview of the index format on Javadoc", 2016-10-29) in which Michael McCandless wrote "Yes please! This is a bug."
The devil's-advocate check199 words

The strongest case for "not a bug", built by the refute reviewer, the intended-lens reviewer and the devil's-advocate verifier (the cross-model reviewers rated it moderate; the devil's-advocate verifier found it fails for the core claim and conceded only the byte-order item): SegmentInfos is @lucene.experimental (SegmentInfos.java:119); the overview "attempts to provide a high-level definition" (package-info.java:54, the LUCENE-2946 policy of 2012); the supported reader is SegmentInfos.readCommit; and big-endian was chosen on purpose (on PR #107 rmuir wrote "I think its fine that segments_N and codec headers just stay bigendian"), so the writeInt / writeLong links may be width labels.

Why it fails: experimental allows the format to change, not a wrong description of the current one; LUCENE-2946 itself kept detailed docs for "the simple metadata files" ("its fine (for now)", rmuir), and this grammar stayed element-level and was extended in 2026; the page exists for people who need the layout. The byte-order point is the only one that survives, so it is the secondary item: CodecUtil's own header/footer javadoc uses the same links for big-endian fields (CodecUtil.java:60, :64, :399-403). The missing fields and the NameCounter type are wrong under any reading.

Trade-offs

The smallest change that makes the page an accurate spec again, in the existing style and with the element names readers know; SegCommitID, UpdatesCount and FieldNumber are new names, any will do. Linking CodecUtil#writeBEInt / #writeBELong (documented as "big endian order") states the byte order without a new convention. It does not prevent future drift. Optional extras the validated diff leaves out: the untouched MinSegmentLuceneVersion line still says "this is only written only if" (an older typo, SegmentInfos.java:76), and the SegID and SegCommitID rows could link DataOutput#writeBytes, which the writer calls, instead of #writeByte.

Downstream note

#

Relevant only to tools outside Lucene that parse segments_N themselves (ports, index inspectors, recovery tools); Lucene's own writer and reader agree.

How it was found

#

A differential grammar check: each default-codec file's layout was transcribed once from its javadoc and once from its writer, and one interpreter parsed the real bytes of 64 generated indexes under both, comparing every value with Lucene's own reader. All 64 segments_N files diverged under the javadoc; the writer's layout parsed all exactly.

The method in full147 words
  • Method (semi-formal). Every file grammar is data in a small grammar language: the documented grammar transcribed only from the class javadoc, the layout grammar from the writer. A generic interpreter parsed the real bytes of 64 generated default-codec index configurations (fixed and seeded random; 1,114 file checks) under both and compared every parsed value with Lucene's reader. Positive control: the layout grammar parses every file exactly to the footer. Vacuity check: 14 of 14 single-element layout mutants are killed.
  • Result for this file. 64 of 64 segments_N files diverge under the documented grammar, also under a big-endian reading of it (2026-10-28).
  • Lead. The hunt started from a probe of the .fnm format only; segments_N came from the grammar check.
  • Then. A reviewer from another model family (OpenAI GPT-5.6) wrote and ran its own test; independent verifiers, an intended-lens reviewer and an adjudication re-ran or rebuilt the evidence.

LFV-943, snapshot of 2026-11-03

Registry title
The SegmentInfos class javadoc gives a wrong segments_N (commit point) grammar: IndexCreatedVersionMajor, SoftDelCount, the SegmentCommitInfo id and FieldInfosFiles are missing, NameCounter is documented as an Int32 but written as a VLong, the fixed-width integers are written big-endian although the javadoc links the little-endian DataOutput#writeInt/#writeLong, and SegID is called the codec's identifier (documentation defect; the writer and reader agree)
Area
index / SegmentInfos (segments_N file-format javadoc vs its writer and reader)
Priority
Low, rank 1120: It is a documentation-only file-format defect where writer and reader agree; segments_N is the central commit file, and a parser built from the text misreads the field right after LuceneVersion.
Impact class
minor
Impact note
Documentation only: Lucene's writer and reader agree, so commits, reopen, CheckIndex and search are unaffected in every configuration; the people misled are those who read, inspect or re-implement segments_N from this class javadoc (the default codec's package docs link it as the Segments File format), and a parser that follows the text misreads the field right after LuceneVersion in every commit written since 7.0, and loses sync from then on (executed); no scale or special setting is needed.
Summary
You decode a segments_N commit file by following the SegmentInfos class javadoc, which gives the order Header, LuceneVersion, Version, NameCounter, SegCount, MinSegmentLuceneVersion, then per segment SegName, SegID, SegCodec, DelGen, DeletionCount, FieldInfosGen, DocValuesGen, UpdatesFiles, DocValuesOverlays, and types NameCounter as an Int32 and the fixed-width fields with links to DataOutput#writeInt/#writeLong (little-endian since 9.0). The writer instead puts an IndexCreatedVersionMajor VInt right after LuceneVersion, writes NameCounter as a VLong, writes Version, SegCount, DelGen, DeletionCount and the other fixed-width fields big-endian, and adds SoftDelCount, a flag byte plus the 16-byte SegmentCommitInfo id and the FieldInfosFiles set to every segment entry, so a parser built from the text reads the VInt 11 where Version should be and every later field is misaligned. Lucene's own reader matches the writer, so nothing breaks at runtime; only the documentation is wrong, and it has not matched the bytes since 4.9.0 (2014).
