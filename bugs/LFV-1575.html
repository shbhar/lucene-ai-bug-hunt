Background: three pieces

#
  1. A span query matches positions of terms in one field. SpanOrQuery and SpanNearQuery combine span clauses, and all clauses must report the same field.
  2. FieldMaskingSpanQuery wraps a span clause on one field and reports another field name, the masking field, so that clauses on different fields can be combined. Its terms still come from the real field.
  3. To score, a Similarity such as the default BM25Similarity gets statistics of the query's field, for example the number of documents that have a term in it. IndexSearcher answers null for a field in which no document has an indexed term.

The finding, step by step

#
  1. You index one document with the term james in the field first. No document has an indexed term in the field other.
  2. You build a query by hand: a SpanOrQuery around FieldMaskingSpanQuery(SpanTermQuery(first:james), "other"). The term is in first; the query reports the masking field, other, as its field.
  3. IndexSearcher.count(query) returns 1. You expect IndexSearcher.search(query, 10) to return that one document.
  4. On Lucene 10.6.0 the search throws NullPointerException in BM25Similarity, with assertions on and off, and explain(query, 0) throws the same way. On main 1640b5c394de (run on 2026-11-25), which has upstream's fix, the search returns the document.
  5. Why: to score, the span weight asks the searcher for the statistics of the query's own field, other. For a field without indexed terms the searcher answers null, as its javadoc says, and the weight hands the null to the Similarity. On 10.6.0, once one document has an indexed term in other, the same search returns the hit.

Who is affected

#

An application on one of the 61 releases run from 8.0.0 to 10.6.0 that builds a span query around a FieldMaskingSpanQuery clause by hand and searches it with scores, or calls explain on it, while no document has an indexed term in the masking field. The call throws; nothing wrong is returned or stored. No rate was measured.

The span weight asks for the statistics of the query's own field, which for this query is the masking field. The searcher answers null for a field without indexed terms, as its javadoc says, and the weight passes the null to the Similarity. Where no scores are needed, the test's query hands the weight no term states and the lookup is not made; a FieldMaskingSpanQuery searched by itself asks for the real field; and one document with an indexed term in the masking field gives the lookup an answer.

The one test fails on each of the 61 releases from 8.0.0 to 10.6.0 that were run. On the 14 releases of 7.x that were run the same search returns the document (runs of an earlier form of the test, which also asserts the count). On main 1640b5c394de (run on 2026-11-25) the test passes.

At the 10.6.0 tag (where the code is)

#

SpanWeight.java, SpanOrQuery.java and FieldMaskingSpanQuery.java are in lucene/queries/src/java/org/apache/lucene/queries/spans/, IndexSearcher.java in lucene/core/src/java/org/apache/lucene/search/, BM25Similarity.java in lucene/core/src/java/org/apache/lucene/search/similarities/.

  1. The weight's field is the query's own field. The constructor of SpanWeight takes query.getField() (SpanWeight.java:96) and calls buildSimWeight (:98).
  2. A composite span query takes its field from its clauses (SpanOrQuery.java:49-56, :64-66), and a FieldMaskingSpanQuery clause reports the masking field (FieldMaskingSpanQuery.java:77-79) while its terms come from the real field. So the query's field can be one in which no document has an indexed term.
  3. buildSimWeight asks for that field's statistics and passes the answer on (SpanWeight.java:101-121): CollectionStatistics collectionStats = searcher.collectionStatistics(query.getField()); (:114), then, when at least one of the query's terms exists, return similarity.scorer(boost, collectionStats, ...) (:115-117). The answer is not checked for null before it is passed on.
  4. The searcher answers null for a field without indexed terms, and says so. The javadoc of IndexSearcher#collectionStatistics: "Returns {@link CollectionStatistics} for a field, or {@code null} if the field does not exist (has no indexed terms)" (IndexSearcher.java:1149-1150). The method is marked @lucene.experimental (:1155) and returns null when the summed document count is 0 (:1168-1170). Its javadoc adds that it can be overridden (:1152-1153): in a run on 10.6.0, a searcher subclass that answers null for the field threw also on an index in which a document has an indexed term in that field.
  5. BM25Similarity dereferences it. scorer calls idfExplain (BM25Similarity.java:177), which reads collectionStats.docCount() (:142). The Lucene frames of the run on 10.6.0, innermost first: BM25Similarity.idfExplain(BM25Similarity.java:142), BM25Similarity.scorer(BM25Similarity.java:177), SpanWeight.buildSimWeight(SpanWeight.java:116), SpanWeight.<init>(SpanWeight.java:98), SpanOrQuery$SpanOrWeight.<init>(SpanOrQuery.java:147), SpanOrQuery.createWeight(SpanOrQuery.java:129), the compiler's bridge method SpanOrQuery.createWeight(SpanOrQuery.java:36), IndexSearcher.createWeight(IndexSearcher.java:990), IndexSearcher.search(IndexSearcher.java:760), IndexSearcher.searchAfter(IndexSearcher.java:607), IndexSearcher.search(IndexSearcher.java:630).
  6. Why the other shapes do not throw. Without scores the composite query hands the weight no term states (SpanOrQuery.java:128-129: scoreMode.needsScores() ? getTermStates(subWeights) : null), and buildSimWeight returns before the lookup (SpanWeight.java:104). A FieldMaskingSpanQuery searched by itself hands back the masked query's weight (FieldMaskingSpanQuery.java:89-92), whose field is the real one.

Why it looks unintended

#
  • Upstream fixed it as a bug: #17018's entry reads "Fix NPE when a span query searches over masked fields that don't have any indexed docs in them".
  • The null is the statistics lookup's documented answer; Lucene's own SpanWeight passes it on.
  • The same query returns its hit on 7.7.3 and throws on 8.0.0 (both run for this page).
The full argument188 words
  • Upstream's own word. #17018 was merged as a bug fix. Its CHANGES entry reads "Fix NPE when a span query searches over masked fields that don't have any indexed docs in them", and its test testMaskingFieldNotIndexed expects four hits with scores above 0 for a SpanOrQuery of clauses masked onto a field that is not indexed (TestFieldMaskingSpanQuery.java:258-278 on main 1640b5c394de).
  • The null is the lookup's documented answer, and the caller that ignores it is Lucene's own. Similarity#scorer describes its parameter as "collection-level statistics, such as the number of tokens in the collection." and names no null (Similarity.java:170-171 at the 10.6.0 tag). The test framework's checking Similarity asserts collectionStats != null (AssertingSimilarity.java:54).
  • The constructor accepts it. FieldMaskingSpanQuery requires two non-null arguments and nothing else (FieldMaskingSpanQuery.java:71-74). Its javadoc says "the masked SpanQuery will function as normal" and names SpanNearQuery and SpanOrQuery across different fields as its use (:28-33).
  • It came with a later change. On the 14 releases of 7.x that were run the search returns the hit; on the 61 releases from 8.0.0 to 10.6.0 that were run it throws.
The devil's-advocate check271 words

The strongest case for "documented": the class javadoc ends with "Note: as {@link #getField()} returns the masked field, scoring will be done using the Similarity and collection statistics of the field name supplied, but with the term statistics of the real field. This may lead to exceptions, poor performance, and unexpected scoring behaviour." (FieldMaskingSpanQuery.java:63-65 at the 10.6.0 tag). Read by the letter, an exception that comes from the masking field's statistics is covered. One of the second opinions voted "not real" on that reading, and the fix did not touch the sentence: it is in the file on main 1640b5c394de.

Why it does not settle it: upstream's own classification comes first. #17018 fixed it as a bug: the pull request's own CHANGES entry begins "Fix NPE", and its test expects scored hits. The history adds that the sentence was not written about this exception: it is of 2012 (1b9e732bedab, 2012-01-25, LUCENE-3723, together with assertions on inconsistent statistics; its issue #4797 was open with the label type:bug when read on 2026-11-25), more than five years before the statistics lookup could answer null (e0bde579815a, 2017-10-30), and the same query returns its hit on 7.7.3, whose javadoc has the sentence, and throws on 8.0.0 (both run for this page). The history does not show that a warning in general words leaves a later exception out.

What stays true: the class javadoc warns in general terms about its scoring, the fix left the warning as it was, #4797 was open when read on 2026-11-25, and the failure is loud. This page says nothing about the scores of the class.

Upstream's fix, #17018 (merged; checked here on main) (validated by the checks) (recommended)

#

SpanWeight.buildSimWeight looks up the statistics of the query's field as before. When the answer is null it takes statistics of the fields the query's terms come from, under the query's field name, and when those are null too it makes statistics from the term statistics (SpanWeight.java:116-134 on main 1640b5c394de; the two helpers at :136-175). The change is thecoop's; the lines below are from that file, with its comments left out.

      FieldStats fieldStats = searcher.fieldStats(query.getField());
      if (fieldStats == null) {
        fieldStats = fieldStatsFromTermFields(query.getField(), searcher, termStates);
      }
      if (fieldStats == null) {
        fieldStats = fieldStatsFromTerms(query.getField(), searcher, termStats);
      }
      return similarity.scorer(boost, fieldStats, termStats);

  • The javadoc note of the class is unchanged by the fix.

Area

Priority
