TaskExecutor#invokeAll returns while a task is still running when the calling thread is interrupted

When the thread running a concurrent search is interrupted, TaskExecutor#invokeAll stops waiting for the task it was blocked on and returns while that task still runs. With -ea Lucene's own AssertionError: Some tasks are still running? fires; with -da the search throws ThreadInterruptedException and the running slice's exception is lost.

The finding in 30 seconds

#

invokeAll waits for its tasks one future at a time. When the waiting thread is interrupted, Future.get() throws at once; the catch records the interrupt and moves to the next future, and never waits for the interrupted one again.

How concurrent search waits for its slices

#
  1. new IndexSearcher(reader, executor) splits the segments into slices and runs one task per slice through TaskExecutor#invokeAll.
  2. invokeAll submits count - 1 workers to the executor, which take tasks one at a time, and the calling thread takes tasks too until none is left. Then it calls Future.get() on each task in turn, so it returns only when every task is done.
  3. If the calling thread is interrupted while it waits, the JDK's Future.get() on a task that is still not done throws InterruptedException at once and clears the interrupt flag.

The finding, step by step

#
  1. You search with new IndexSearcher(reader, executor) and 2 slices: one slice runs on an executor thread, the other on your request thread, which then waits for the first one inside TaskExecutor#invokeAll.
  2. While the executor's slice is still running, the request is cancelled with Future.cancel(true), which interrupts the request thread.
  3. You expect the search to throw ThreadInterruptedException only after both slices have finished: the javadoc says invokeAll will "wait for them to complete", and the code asserts that no task is left running.
  4. Instead it ends at once. In the repro the executor's task waits on a latch for up to 10 s, yet invokeAll ends long before that bound (17-18 ms in a timing probe; with the fix it waits the full 10 s). With -ea: AssertionError: Some tasks are still running?; with -da: ThreadInterruptedException.
  5. The abandoned slice keeps running: its exception is never reported to you, and if you close the reader while the slice still reads it, the slice fails with an AlreadyClosedException that is never reported either.

Who is affected

#

Applications that run concurrent search (an IndexSearcher with an executor and at least 2 slices) and interrupt the searching thread, for example Future.cancel(true) for a request timeout or shutdownNow on the request pool. The default IndexSearcher without an executor is not affected. Rare: interrupt-based cancellation is unusual, and a Lucene committer said Lucene will not support it.

Mechanism, terms and numbers589 words

TaskExecutor#invokeAll runs some tasks on the executor and the rest on the calling thread, then waits for each future in turn. If the calling thread is interrupted while it waits, Future.get() throws InterruptedException; collectResults records it as a ThreadInterruptedException and moves on to the next future, but never waits for that one again. So invokeAll ends while the task is still running, against its javadoc ("wait for them to complete"), a code comment ("invokeAll does not leave any running tasks behind when it returns") and its own assertion, which fires with -ea. With -da the call throws ThreadInterruptedException; through IndexSearcher#search a slice keeps collecting after search has thrown, its exception is lost, and if the caller closes the reader while the slice still reads it, the slice fails with an AlreadyClosedException that is never reported. It needs concurrent search with an executor and an application that interrupts the searching thread. Present in this form since 9.9.0, when #12523 made invokeAll wait for all tasks on failure but left the interrupt path behind; every release through 10.6.0 and main.

The code (main 645d4fe14a20, TaskExecutor.java)

#
// invokeAll: count - 1 workers go to the executor, the caller runs tasks until none is left (:91-114)
return collectResults(futures);                                          // :115

for (Future<T> future : futures) {                                      // collectResults, :121
  try {
    results.add(future.get());                                           // :123
  } catch (InterruptedException e) {
    exc = IOUtils.useOrSuppress(exc, new ThreadInterruptedException(e)); // :124-125, then the next future
  } catch (ExecutionException e) {
    exc = IOUtils.useOrSuppress(exc, e.getCause());                      // :126-127
  }
}
assert assertAllFuturesCompleted(futures) : "Some tasks are still running?";   // :130
if (exc != null) { throw IOUtils.rethrowAlways(exc); }                   // :131-133
  • Every task is claimed before the wait. The caller keeps claiming task ids until none is left (:107-114), so in collectResults a future that is not done has been claimed by another thread, which is running it or about to start it.
  • Only the interrupted future is abandoned (one per interrupt). FutureTask.get() on a task that is still not done checks and clears the interrupt flag and throws. The loop records it and calls get() on the next future, which now blocks normally. An independent test with 3 tasks shows it: after the interrupt invokeAll kept waiting while both pool tasks were blocked, and returned as soon as task 2 was released, with task 0 still blocked ("done at return: [false, true, true]"). A second interrupt during a later wait would abandon a second future.
  • Outcome. -ea: the assertion at :130 fails. -da: :131-133 rethrow ThreadInterruptedException. The abandoned task's value or exception is never read.
  • Through IndexSearcher. search(Query, CollectorManager) runs one task per slice through taskExecutor.invokeAll(listTasks) (IndexSearcher.java:778-789). The throw skips reduce; the abandoned slice keeps collecting and reading the reader.
  • Not without an executor. new IndexSearcher(reader) uses new TaskExecutor(Runnable::run) (IndexSearcher.java:223): every task runs on the calling thread before the wait, so nothing is left running.

Minimal repro

#

One JUnit class, one method, public API only, no index. Two tasks: the executor's task waits on a latch (up to 10 s), the caller's task interrupts the calling thread. The test checks that invokeAll ended only after the executor's task finished. It fails with assertions on and off.

Expected
invokeAll ends, normally or with ThreadInterruptedException, only after task 0 has completed.
Observed
It ends at once while task 0 still runs: AssertionError: Some tasks are still running? with -ea, ThreadInterruptedException with -da.

All files of this repro: repro/LFV-056/

More files, environment, full output331 words

The class sits in org.apache.lucene.search next to TestTaskExecutor and uses only TaskExecutor(Executor) and invokeAll. Concurrency is the bug, so it needs one executor thread, but the order is fixed by a Semaphore and a latch, without sleeps: the executor starts a new thread per execute() and returns only once that thread's task has started, so the executor thread always runs task 0 and the calling thread runs task 1, the last one. Task 1 sets the calling thread's interrupt flag, standing for a cancellation interrupt that lands while the caller runs its own share; the independent test shows the same with a real Future.cancel(true) from another thread. Task 0's 10 s bound only lets a correct invokeAll, which keeps waiting for it, end.

The test applies to 9.12.0 and later, where the caller runs the last task itself; before 9.12.0 a port was used (run on 9.8.0, 9.9.0 and 9.11.1).

Regression test: this same class (or its one method in TestTaskExecutor); with the recommended fix it passes in about 10 s, the length of task 0's bound.

Why it looks unintended

#
  • The javadoc says invokeAll will "wait for them to complete", a comment says it "does not leave any running tasks behind", and it asserts exactly that.
  • Since #12523 invokeAll waits for all tasks when a task fails; only the interrupt path still skips one.
  • Not a return-at-once policy either: after the interrupt it keeps waiting for the other tasks.
The full argument251 words
  • The class states the opposite. Class javadoc: "then waits for all tasks that have been executed in parallel on the executor to be completed and then returns" (TaskExecutor.java:41-43). invokeAll: "wait for them to complete and return the obtained results" (:71). Task#cancel comment: "We rather want to make sure that invokeAll does not leave any running tasks behind when it returns." (:185-186). The assertion: assertAllFuturesCompleted(futures) : "Some tasks are still running?" (:130).
  • History. #12523 (2023, first in 9.9.0): "This commit ensures that it instead waits for all tasks to complete before it re-throws the exception." It turned throw new ThreadInterruptedException(e) into record-and-continue, without waiting for the interrupted future again. #12689 (2023, 9.9.0) added the assertion and the comment. None of the PR threads that shaped the class (#12523, #12689, #13472, #13609, #13622, #13861) mentions interrupts.
  • The expectation upstream. #12278 (open): "Is it a reasonable expectation that once IndexSearcher#search(Query, CollectorManager) returns, that specific search has completed and has left no threads behind still working on it? I would expect this to be true". It is about task exceptions, not interrupts.
  • Tests. TestTaskExecutor has 10 tests; none mentions interrupts.
  • Not a coherent alternative. After the interrupt the loop still waits for every other running task and abandons only the one it was blocked on (executed).
  • A legal, anticipated trigger. Lucene's javadoc addresses "Applications using Thread#interrupt() or Future#cancel(boolean)" (FSDirectory.java:65-67, :77-82; NIOFSDirectory.java:41-46), and IndexWriter documents its own interrupt handling (IndexWriter.java:172-175).
The devil's-advocate check207 words

The strongest case for "intended" (a read-only cross-model review and the tie-break): Lucene does not support Thread#interrupt as cancellation (#12023), TaskExecutor is @lucene.experimental, and the JDK's own ExecutorService#invokeAll returns at once when interrupted, so an interrupted caller cannot expect the wait-for-all guarantee.

Why it fails: #12023 rejects making Lucene stop its work on interrupt; this report asks only that the existing interrupt handling keeps the invariant the class states, comments and asserts. @lucene.experimental marks API instability, not a licence to break a stated invariant. The JDK cancels the remaining tasks with cancel(true) before it returns (cooperatively, so a task that ignores interrupts can outlive its invokeAll too, but every task is asked to stop); Lucene's Task#cancel rejects that (assert mayInterruptIfRunning == false : "cancelling tasks that are running is not supported", :183), and today's code does wait for the other tasks, so it follows neither policy. The reviewers' one request, a genuine interrupt from another thread with standard pools and a control, was executed and fails the same way. Still, whether invokeAll should wait for all tasks or return at once after an interrupt is a policy choice for maintainers, not an established Lucene-wide guarantee; the report is that today's code follows neither.

Suggested fix

#

Recommended After an interrupt, keep waiting for the same future and report the interrupt at the end (validated)

In collectResults, when Future.get() throws InterruptedException, remember the interrupt once and call get() again on the same task; throw ThreadInterruptedException after every task is done (+16/-6 in TaskExecutor.java). The repro, TestTaskExecutor and TestIndexSearcher pass. Trade-off: an interrupted caller now waits for its running tasks.

while (true) {
  try {
    results.add(future.get());
    break;
  } catch (InterruptedException e) {
    if (interrupted == false) {   // report the interrupt once, keep waiting
      interrupted = true;
      exc = IOUtils.useOrSuppress(exc, new ThreadInterruptedException(e));
    }
  } catch (ExecutionException e) {
    exc = IOUtils.useOrSuppress(exc, e.getCause());
    break;
  }
}
All options and trade-offs2 options · 444 words

One fix was validated through gradle in a scratch worktree of 645d4fe14a20. The alternative, returning at once and documenting it, is a policy choice for maintainers; it was not run.

After an interrupt, keep waiting for the same future and report the interrupt at the end (validated) (recommended)

#

Wrap the get() in a loop: on InterruptedException record one ThreadInterruptedException and retry; on a result or an ExecutionException leave the loop.

while (true) {
  try {
    results.add(future.get());
    break;
  } catch (InterruptedException e) {
    if (interrupted == false) {   // report the interrupt once, keep waiting
      interrupted = true;
      exc = IOUtils.useOrSuppress(exc, new ThreadInterruptedException(e));
    }
  } catch (ExecutionException e) {
    exc = IOUtils.useOrSuppress(exc, e.getCause());
    break;
  }
}

Trade-offs

  • An interrupt no longer frees the calling thread before its running tasks end. It waits as long as it already waits for the other tasks today, and as after a task failure. Cancellation stays with the supported mechanisms (query timeouts, ExitableDirectoryReader).
  • The interrupt flag stays cleared, as today and as IndexWriter documents for its own interrupts; restoring it before the throw is a separate choice (not run). Further interrupts during the same wait are not recorded separately, and the flag is not restored for them.
  • Cancelling not-yet-started tasks would not help: when collectResults runs every task is already claimed, and cancel(false) cannot stop a task that is running (at most it would skip one claimed in the instant before its run() starts).

Return at once on interrupt, and document it (not run)

#

On InterruptedException, stop waiting and throw; change the javadoc and the cancel comment to say that running tasks may outlive the call, and make the assertion skip the interrupted case.

Trade-offs

Frees the interrupted caller at once, like the JDK's invokeAll, but brings back what #12523 removed for task failures: tasks that outlive the call, lost exceptions, and slices that can touch a reader the caller closes next. Running tasks cannot be interrupted either, because Task#cancel rejects mayInterruptIfRunning.

Downstream note

#

Downstream, this matters to a search service that cancels requests by interrupting threads that run concurrent search: the cancelled request returns while a slice still runs on the shared pool, and that slice's failure is never reported.

How it was found

#

TLA+ model checking (TLC) of TaskExecutor#invokeAll, with an interrupt of the calling thread as one modelled event. TLC found a 10-state trace in which invokeAll returns while a task is still running (invariant NoRunningAfterReturn). An independent verifier reproduced it in Java; a one-test repro and a tie-break test with standard pools followed.

The method in full161 words

Method: formal (TLA+ model checking, the tool's own counterexample, then public-API JUnit tests).

  • Model. TaskExec.tla models invokeAll with nesting, rejecting executors, exceptions, cancellation and interrupts of the application thread (the JDK's FutureTask.get() throws only if the task is not done and the flag is set).
  • Counterexamples. Configuration te_intr: the worker runs task 1, the caller runs task 2, the caller is interrupted while it waits on future 1, and invokeAll completes while task 1 is still running: invariant NoRunningAfterReturn violated, 10-state trace. te_intr_exc_lost: the task then throws, and the exception is never reported (NoLostException). With the fix (keep waiting after an interrupt) every configuration is clean.
  • Confirmation. A separate verifier wrote a 5-test class (4 fail, the control passes, on 10.1.0, 10.5.2 and main). The repro was reduced to one test; a later tie-break wrote an independent test with standard JDK pools and a real Future.cancel(true), which fails 10 of 10 on main, 10.5.2 and 10.6.0.
