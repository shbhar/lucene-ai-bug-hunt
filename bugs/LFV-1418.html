FiniteStringsIterator returns strings the automaton does not accept after an arc ending at Integer.MAX_VALUE

FiniteStringsIterator should list exactly the strings an automaton accepts, but it steps through an arc's labels with an int label++. On an arc ending at Integer.MAX_VALUE the counter wraps to Integer.MIN_VALUE, so after the one right string it returns 2,147,483,647 rejected ones (4.8.1 to 10.6.0, main).

The finding in 30 seconds

#

An automaton's finite-strings iterator should return each accepted string once and then null. For an arc ending at the largest int label, its label counter overflows and it never notices the arc has ended.

Background: how the iterator walks an automaton

#
  1. A Lucene Automaton has states joined by arcs. Each arc carries a label range [min, max] of int values; addTransition(0, 1, 7) adds an arc with the single label 7.
  2. An automaton without cycles accepts a finite set of strings, each a sequence of labels. FiniteStringsIterator.next() returns them one at a time as an IntsRef, printed in hex ([7fffffff] is the one-label string 2147483647), and null when there are no more.
  3. For each arc it steps a counter through min, min + 1, ..., max; internally it returns -1 when a state has no more arcs.

The finding, step by step

#
  1. Build an automaton with one arc labelled Integer.MAX_VALUE (2147483647) from state 0 to an accepting state 1. It accepts exactly one string, printed [7fffffff].
  2. Enumerate it with new FiniteStringsIterator(a). You expect [7fffffff], then null. With the label 2147483646 that is exactly what you get.
  3. Instead the second next() returns [80000000] (the label -2147483648), which the automaton rejects, and it keeps going: 2,147,483,648 strings in all, 1 right and 2,147,483,647 wrong. A LimitedFiniteStringsIterator with limit 10 over the range [2147483646, 2147483647] returns 10 strings instead of 2.
  4. Why: nextLabel ends an arc when label > t.max, else returns label++. After returning 2147483647 the int wraps to -2147483648, which is never greater than t.max. The walk stops only when the counter reaches -1, the iterator's "no more arcs" value.

Who is affected

#

Only application code that builds its own automaton with an arc ending at exactly Integer.MAX_VALUE (a sentinel or an open upper end) and enumerates it with FiniteStringsIterator or LimitedFiniteStringsIterator, both experimental. One arc fails every time, silently. Lucene's suggesters, ConcatenateGraphFilter and query-graph code never build such labels.

Mechanism, terms and numbers427 words

FiniteStringsIterator "Iterates all accepted strings" (FiniteStringsIterator.java:26 at f794ff5a505c), and next() returns "null, if no more finite strings are available" (:99). It walks an arc's labels with an int counter: nextLabel tests label > t.max (:198) and otherwise returns label++ (:211). When an arc ends at Integer.MAX_VALUE, returning that last label leaves the counter at Integer.MIN_VALUE, which is never greater than t.max, so the iterator returns Integer.MIN_VALUE, Integer.MIN_VALUE + 1, ... as labels of the arc until the counter reaches -1, which next() reads as "no more transitions" (:112-113).

For 0 -[Integer.MAX_VALUE]-> 1 (accepting), which accepts one string, the second next() returns [80000000] instead of null, assertions on and off; an unlimited run returns 2,147,483,648 strings. LimitedFiniteStringsIterator delegates to it and fills its limit with such strings. Non-negative labels up to Integer.MAX_VALUE - 1 are enumerated correctly.

The fix holds the counter as a long (return (int) label++). Only automata the application builds itself can carry the label; Lucene's own suggesters, ConcatenateGraphFilter and query-graph code use bytes, code points or small term ids.

The mechanism (main f794ff5a505c, lucene/core/src/java/org/apache/lucene/util/automaton/FiniteStringsIterator.java)

#
  1. resetState (:184-191) loads the state's first arc and sets label = t.min (:189), here 2147483647; the field is public int label (:180).
  2. First next(): nextLabel (:197-212) tests 2147483647 > 2147483647, false, and returns label++ (:211): it returns 2147483647 and leaves label at -2147483648. The destination accepts, so next() returns [7fffffff] (:130-133).
  3. Second next() (the fix site): -2147483648 > 2147483647 is false, so nextLabel returns -2147483648 and next() returns [80000000].
  4. This repeats for every int up to -2. At -1, nextLabel returns -1, which next() treats as "no more transitions" (:112-113, :134-146); it pops the state and returns null. A probe counted 2,147,483,648 strings, the last [fffffffe].
  5. LimitedFiniteStringsIterator.next() (LimitedFiniteStringsIterator.java:57-69) only counts what super.next() returns (:63), so it inherits the wrong strings: for one arc [2147483646, 2147483647] and limit 10 it returns 7ffffffe 7fffffff 80000000 ... 80000007.

The package's own membership test disagrees with the iterator: Operations.run(a, [7fffffff]) is true; Operations.run(a, [80000000]) is false with assertions off and trips assert label >= 0 (Automaton.java:692) with them on.

Side observation, not claimed: in a non-deterministic automaton, an arc that follows the one ending at Integer.MAX_VALUE in the same state is never visited, because the counter reaches -1 first. The same fix covers it.

Exposure and likelihood191 words
  • Who. Application code that builds its own automaton with an arc whose last label is exactly Integer.MAX_VALUE (a sentinel label, or an open upper end via addTransition(s, d, min, Integer.MAX_VALUE) or Automata.makeCharRange(x, Integer.MAX_VALUE)) and enumerates it. No configuration and no scale.
  • Not affected. The direct production call sites of the iterators (AnalyzingSuggester, FuzzySuggester, FuzzyCompletionQuery, ConcatenateGraphFilter, GraphTokenStreamFiniteStrings) build labels from bytes, code points or small term ids; QueryBuilder and IntervalBuilder reach the iterator only through GraphTokenStreamFiniteStrings.
  • Effect. Silent wrong output: strings the automaton rejects, no exception. Without a limit about 2^31 extra strings (a probe took about 2-5 s); with LimitedFiniteStringsIterator the limit fills with wrong strings and real ones can be crowded out. No index data is involved.
  • In practice. A wide range [x, Integer.MAX_VALUE] with small x already holds about 2^31 accepted strings, so wrong strings show only for a label at, or within the iteration limit of, Integer.MAX_VALUE.
  • API status. Both iterators are @lucene.experimental (FiniteStringsIterator.java:35, LimitedFiniteStringsIterator.java:30).
  • Likelihood: rare. No Lucene producer emits the label and the recorded searches found no public report, but the shape fails deterministically.

Why it looks unintended

#
  • It promises to iterate "all accepted strings", then null; Lucene's own Operations.run rejects [80000000].
  • addTransition accepts any int label and checks no label bound; 2147483646 works. An overflow, not a limit.
  • Disputed: "Unicode alphabet" and the run automata's code-point asserts let a maintainer call labels above 0x10FFFF out of contract.
The full argument331 words
  • Contract. "Iterates all accepted strings." (FiniteStringsIterator.java:26); the only caveats are cycles, iteration order and duplicates for non-determinized automata (:28-33). next(): "Finite string or null, if no more finite strings are available." (:99). LimitedFiniteStringsIterator: "If more than limit strings are accepted, the first limit strings found are returned" (LimitedFiniteStringsIterator.java:22-23).
  • The input is legal for Automaton. addTransition (Automaton.java:149-183) takes any int label: it checks the state indexes (:158-159) and the order transitions are added in (:169-172), never the label. Automaton itself asserts only label >= 0 (in step's lookup, :692), which Integer.MAX_VALUE meets. It is the iterator that produces negative labels. (The run automata do assert an alphabet bound; see the devil's advocate.)
  • Among the tested non-negative boundary labels, only 0x7FFFFFFF fails. 0x10FFFF, 0x110000 and 0x7FFFFFFE are enumerated exactly. A label of -1, outside Automaton's label >= 0, collides with the iterator's end marker and yields no string; that is a separate edge, and fix A leaves it as it is.
  • Lucene uses such labels. TestRegExpParsing writes makeCharRange('d', Integer.MAX_VALUE) and makeCharRange('e', Integer.MAX_VALUE) as an open upper end (TestRegExpParsing.java:193, :243; weak support, as the cross-model reviewer noted, because its language check stops at Character.MAX_CODE_POINT, AutomatonTestUtil.java:681-685). Core runs the iterator over term-id labels (GraphTokenStreamFiniteStrings.java:231). On #6094 (LUCENE-5030), about suggester automata, a maintainer asked "Maybe, we should just use Integer.MAX_VALUE and MAX_VALUE-1?" and then wrote "Oh, right, we can't just use MAX_VALUE: it must be a valid unicode char since we will send it through UTF32toUTF8." It cuts both ways: a conceivable label, but not one that pipeline can carry.
  • History. The int counter came with the iterative rewrite in LUCENE-5628 (#6690, 2014) and moved unchanged into FiniteStringsIterator (LUCENE-6365, #7425, 2015). Neither discussion mentions the label range or integer overflow (#6690 mentions only stack overflows from recursion); no upstream iterator test uses a label near Integer.MAX_VALUE.
The devil's-advocate check287 words

The strongest case for "intended": the package documents "a full DFA/NFA implementation with Unicode alphabet" (package-info.java:33); makeCharRange (Automata.java:137), step (Automaton.java:654) and run (Operations.java:902) speak of code points. The run side asserts a code-point alphabet: RunAutomaton.step and NFARunAutomaton.getCharClass assert c < alphabetSize (RunAutomaton.java:173, NFARunAutomaton.java:181), CharacterRunAutomaton and NFARunAutomaton(Automaton) set that size to Character.MAX_CODE_POINT + 1 (CharacterRunAutomaton.java:27, NFARunAutomaton.java:62), and getStartPoints stops adding end points at Character.MAX_CODE_POINT (Automaton.java:639). With assertions on, stepping 0x110000 or 0x7FFFFFFF trips those asserts, and since alphabetSize is an int, no runner's alphabet can contain Integer.MAX_VALUE: even new NFARunAutomaton(a, Integer.MAX_VALUE) trips for it (with assertions off all of them step normally). Both iterators are @lucene.experimental. So a maintainer could call any label above 0x10FFFF out of contract and the fix mere hardening.

Why it fails (a judgement): those bounds belong to the runners. Each declares its own alphabet (ByteRunAutomaton 256, ByteRunAutomaton.java:37; NFARunAutomaton takes it as a parameter), while neither iterator nor addTransition declares or checks one. Operations.run, which steps the Automaton itself (Operations.java:909-920), accepts [7fffffff]. The iterator enumerates 0x110000 and 0x7FFFFFFE exactly although both lie outside CharacterRunAutomaton's alphabet; only the wrap at 0x7FFFFFFF goes wrong. Core itself feeds the iterator labels that are not code points, and the repro uses addTransition directly, not a code-point helper. Even for an out-of-domain label, silently returning strings the automaton rejects is not a defensible response. The independent reproducer, the devil's-advocate verifier and three executed cross-model reviews (OpenAI GPT-5.6) rated the counter-argument moderate and the bug real; the adjudication accepted that rating and confirmed the bug. It argues for Low priority, not for intended behaviour.

Suggested fix

#

Recommended Hold the counter as a long (validated)

Hold the label counter as a long in FiniteStringsIterator.PathNode and return (int) label++. Stepping past 2147483647 then gives 2147483648, the end test fires and next() returns null. The repro passes with assertions on and off, and core's automaton and graph tests run 255 with 0 failures.

How it was found

#

A bounded comparison of Operations and the public automaton consumers (the two iterators and the run automata) against a simple NFA-simulation oracle over a small word universe, on arcs ending at Integer.MAX_VALUE. The iterators returned strings the oracle rejects; a public-API JUnit test then witnessed it.

History

#

Introduced in 2014 by LUCENE-5628 (8c4e8268181), which rewrote getFiniteStrings iteratively with an int label counter; first released in 4.8.1; the int label++ step moved unchanged into FiniteStringsIterator in 5.3.0. Every release through 10.6.0 fails. Not fixed upstream.

Versions tested6 rows

Introduced by 8c4e8268181 (Michael McCandless, 2014-05-04), "LUCENE-5628: change getFiniteStrings to iterative impl" (#6690; svn era, no pull request), which added public int label, if (label > ...max) and return label++. The backport c0d92be5095 (2014-05-05) shipped first, in 4.8.1. LUCENE-5752 (46132142cc2, 4.10.0) moved the code into Operations.getFiniteStrings and rewrote PathNode for the int-state API; LUCENE-6365 (#7425, 3d8bfad40b0, 2015-07-04) moved it into the new public FiniteStringsIterator (5.3.0), adding a label = -1 reset in nextLabel's exhausted branch. Through both moves the int counter, the end test and return label++ stayed unchanged; since then only reformatting and a comment typo fix touched those lines.

The older recursive getFiniteStrings (4.1.0-4.8.0) wraps the same way in a different loop (for (int n = t.min; n <= t.max; n++)); that is a predecessor, not this fix site. Upstream main b00bfc373570 (2026-11-09) still has both lines, and FiniteStringsIterator.java is unchanged at the later main e0a3a951e7ef. All 107 release tags from 4.8.1 to 10.6.0 in the history clone carry the code; the clone lacks the 8.9.0-8.11.x tags, and 8.11.4 was executed.

Summary
You build an automaton with one arc labelled Integer.MAX_VALUE from the start state to an accepting state, so it accepts exactly one string, [Integer.MAX_VALUE], and enumerate it with new FiniteStringsIterator(a). You expect next() to return [7fffffff] and then null, as the class javadoc ('Iterates all accepted strings.') and next() ('null, if no more finite strings are available') promise. Instead the second next() returns [80000000] (Integer.MIN_VALUE), a string the automaton rejects, and the iterator keeps going: PathNode.nextLabel returns label++ on an int, which wraps from Integer.MAX_VALUE to Integer.MIN_VALUE, so its end test 'label > t.max' never fires until the label reaches -1, the iterator's end sentinel.
