FeatureField.newSigmoidQuery scores NaN when pivot^exp leaves the double range

FeatureField.newSigmoidQuery precomputes pivot^exp as a double: pivot 2^20 with exponent 60 gives 2^1200, which overflows to Infinity, so every hit scores NaN, not the documented 0.5 at S = pivot. With assertions off this is silent on every release since 7.4.0 and main; since 10.2.0 NaN hits rank first.

The finding in 30 seconds

#

One precomputed power, pivot^exp, leaves the double range, and the query's scores become NaN.

Background

#
  1. FeatureField stores a static per-document value S, such as a popularity or pagerank signal, and newSigmoidQuery turns it into a score: weight * S^a / (S^a + pivot^a). The score grows from 0 to weight and is weight/2 when S equals the pivot.
  2. The exponent a sets how sharply the score switches on around the pivot: a large exponent makes it almost a step, "slower before 'pivot' and faster after 'pivot'".
  3. A Java double holds values up to about 1.8e308, just under 2^1024. A larger result becomes +Infinity, and Infinity / Infinity is NaN; a result below about 2^-1074 becomes 0, and 0 / 0 is NaN too.

The finding, step by step

#
  1. Index one document with new FeatureField("f", "x", 1 << 20) (feature value S = 1,048,576) and search FeatureField.newSigmoidQuery("f", "x", 1, 1 << 20, 60): weight 1, pivot 2^20, exponent 60. The factory accepts both; it only rejects values that are not positive and finite.
  2. You expect 0.5: the javadoc gives the score as weight * S^a / (S^a + pivot^a), which is weight/2 when S equals the pivot.
  3. You get NaN, and no exception. The sigmoid computes pivot^60 = 2^1200 once, as a double. The largest double is just under 2^1024, so it becomes +Infinity, and every document scores 1 - Infinity/Infinity = NaN.
  4. In a real query the ranking breaks: with body:lucene as MUST and this sigmoid as a SHOULD boost, a document with feature value 1 (documented boost about 0) comes first with score NaN, ahead of a better text match that scores 0.130.
  5. It needs a steep exponent: the first failing pivot is close to 2^(1024/exp), e.g. about 137,271 at exponent 60 or about 1,209.3 at exponent 100, and nothing fails for exponents up to 8. A tiny pivot can underflow to 0 and give 0/0 = NaN; the 4-argument IntervalQuery repeats the same arithmetic.

Who is affected

#

Applications that rank with the opt-in FeatureField.newSigmoidQuery, or the 4-argument IntervalQuery, and choose a steep exponent with a large pivot, or a tiny pivot with tiny feature values. It reproduces with one document and default index and searcher settings. Elasticsearch, OpenSearch and Solr pass a request's sigmoid pivot and exponent straight through. Typical exponents, below 2, are safe.

Mechanism, terms and numbers710 words

FeatureField.newSigmoidQuery(field, feature, weight, pivot, exp) documents the score weight * S^a / (S^a + pivot^a) and accepts any finite pivot and exponent above 0. Its SigmoidFunction evaluates it as weight * (1 - pivot^a / (S^a + pivot^a)) with pivot^a precomputed once per query as a double. When pivot^a overflows (above about 1.8e308) every document scores Inf/Inf = NaN; when it underflows to 0 and S^a does too, the score is 0/0 = NaN. With pivot 2^20 and exponent 60, a document with S = pivot, documented to score 0.5, scores NaN, silently. Since 10.2.0 NaN hits rank ahead of correctly scored ones; older releases return placeholder hits or throw an assertion from the collector. Every release since 7.4.0 and main are affected, and IntervalScoreFunction (behind the 4-argument IntervalQuery) copies the arithmetic. Scoring as weight / (1 + (pivot / S)^a) removes it.

The bug

#
  1. SigmoidFunction stores pivotPa = Math.pow(pivot, a) once per query (FeatureField.java:495, :500 at 645d4fe14a20).
  2. Each document scores (float) (weight * (1 - pivotPa / (Math.pow(f, a) + pivotPa))) (:531), where weight is the scorer's boost: newSigmoidQuery passes a weight other than 1 through a BoostQuery (:706-709). The comment above it (:528-530) explains the rewrite of f^a / (f^a + k^a): "to make sure it doesn't decrease with f in spite of rounding".
  3. Overflow. If pivot^a rounds past Double.MAX_VALUE (about 2^1024), pivotPa is +Infinity; the denominator is +Infinity for every finite f^a, so every document that has the feature scores 1 - Inf/Inf = NaN, whatever its value.
  4. Underflow. If pivot^a is below about 2^-1074, pivotPa is 0; documents whose f^a also underflows score 1 - 0/0 = NaN, the others score weight.
  5. An SMT model of the final expression (cvc5, floating-point theory, with the two powers as independent non-negative doubles) finds no other way to NaN. It does not model Math.pow or how FeatureField encodes values.
  6. The bulk scorer (:540-550) and explain() (:556-558) use the same arithmetic, and FeatureQuery passes the scorer straight into a TermScorer (FeatureQuery.java:135-137); nothing on the way to the collector checks for NaN.
  7. newSigmoidQuery rejects only pivot <= 0, exp <= 0 and non-finite values (FeatureField.java:700-705). The weight is capped at 64 (MAX_WEIGHT, :576-582); the exponent is not.

The numbers

#
  • One document, S = pivot = 2^20 = 1,048,576, weight 1, exponent 60: pivot^60 = 2^1200 overflows and the hit scores NaN instead of 0.5, with assertions on and off.
  • Boundary at the same pivot: exponent 51 (2^1020, finite) gives 0.5, exponent 52 (2^1040) gives NaN.
  • First failing float pivot, measured on the real scorer (S set to the pivot as FeatureField stores it; the overflow does not depend on S), close to 2^(1024/exp): exponent 9: 1.7804262e34; 20: 2.586639e15; 35: 6.416196e8; 50: 1,462,494.8; 60: 137,270.94; 100: 1,209.3365. Exponent 8 gives no NaN for any pivot up to Float.MAX_VALUE, because a float is below 2^128 and 128 * 8 = 1024, and none through underflow either: a stored feature value is at least 2^-126 (FeatureField.java:162-171), so S^8 >= 2^-1008 > 0.
  • A finite wrong value right next to the overflow: where pivot^a is finite but S^a + pivot^a overflows (about 2^1023 <= pivot^a < 2^1024; at pivot 2^20, exponents from about 51.15 to just under 51.2, measured at 51.16, 51.18 and 51.19) the score at S = pivot is 1.0 instead of 0.5.
  • Ranking: body:lucene as MUST plus newSigmoidQuery("f", "x", 1, 2^20, 60) as SHOULD, over doc0 "lucene apache apache" with feature value 1.0 (documented boost 1/(1+2^1200), about 0) and doc1 "lucene lucene lucene" without the feature: the result is [doc=0 score=NaN, doc=1 score=0.13022968]. With the fix doc1 ranks first.
  • Underflow (study test): pivot 2^-20 with exponent 60 over 4 documents gives 3 NaN scores, and the best document (score 1.0) is ranked last.

The second copy

#

IntervalScoreFunction.SigmoidFunction (IntervalScoreFunction.java:109-131, :117, :128), behind new IntervalQuery(field, source, pivot, exp) (IntervalQuery.java:97-99), has the same arithmetic and the same checks (IntervalScoreFunction.java:33-41). Sloppy frequencies are small, so it needs exponents in the hundreds: with pivot 4 and exponent 600, all 4 documents score NaN.

Exposure and likelihood287 words
  • Who is exposed. Users of the sigmoid feature function (FeatureField is @lucene.experimental) who want the boost to switch on sharply around the pivot, for example to approximate a popularity threshold; a steep exponent is the documented way to get that ("higher values make the function grow slower before 'pivot' and faster after 'pivot'", FeatureField.java:689-690).
  • No special setup. One document, the default IndexWriterConfig and codec and a plain IndexSearcher are enough; no special codec or concurrency setting was needed. The score depends only on the query's parameters and the document's feature value (FeatureField.java:527-532).
  • Silent. With assertions off there is no exception or warning. TopScoreDocCollector's javadoc says NaN values "are not valid scores. This collector will not properly collect hits with such scores" (TopScoreDocCollector.java:30-31).
  • What users see depends on the release (4-document probe; the arithmetic never changed):
    • 7.4.0-10.0.0: with -ea, search() throws an AssertionError in TopScoreDocCollector; with -da, TopDocs holds placeholder hits (doc 2147483647, score -Infinity) in place of real documents;
    • 10.1.0: only 1 of 4 hits;
    • 10.2.0 to main: every hit, with NaN scores ranked ahead of finite ones (overflow: all NaN, in doc-id order);
    • explain() reports NaN on every release.
  • Downstream. Elasticsearch's and OpenSearch's rank_feature sigmoid and Solr's {!rank function=sigm} pass the request's pivot and exponent to newSigmoidQuery unchanged, so a search client can hit it with one query parameter. Their intervals queries use the 2-argument IntervalQuery, so the interval copy needs an application that calls the 4-argument constructor itself.
  • How likely. Rare: the exponents involved are far above typical ones (Lucene's tests use 0.6 and 2; Elasticsearch documents the exponent as "typically in [0.5, 1]"), and nobody has reported it since 2018. Priority low.

More files, environment, full output288 words

ByteBuffersDirectory, the default IndexWriterConfig, a plain IndexSearcher; nothing random, one thread. 2^20 is a positive normal float that FeatureField stores exactly, and the fixed formula gives exactly 0.5 for it. The test asserts the documented value (weight/2 at S = pivot) rather than just "not NaN", so the failure reads expected:<0.5> but was:<NaN>.

It covers the overflow case of the FeatureField copy, the common one. The same root cause also gives NaN through underflow (tiny pivots with tiny feature values) and through the 4-argument IntervalQuery (for example pivot 4 with exponent 600); those were executed by the study and are described in the text, not added as more tests.

Why it looks unintended

#
  • The javadoc promises weight/2 at S = pivot for any pivot and exponent in (0, +Infinity); Lucene calls NaN "not valid scores".
  • Upstream's own TestFeatureField check demands a finite max score from the sigmoid; at (2^20, 60) it is NaN.
  • Nothing documents an exponent limit: the weight is capped at 64, the exponent is not.
The full argument289 words
  • The contract is exact. newSigmoidQuery: the score is "weight * S^a / (S^a + pivot^a)", pivot is the "feature value that would give a score contribution equal to weight/2, must be in (0, +Infinity)", exp "must be in (0, +Infinity)" (FeatureField.java:680-693). Class javadoc: "values are in the 0..1 range and 0.5 is obtained when S and k are equal" (:76-77); with a weight the formula's range is [0, weight], so the 0..1 wording holds for weight 1, as in the repro. IntervalQuery: "Scores are bounded to between 0 and 1" (IntervalQuery.java:56) and pivot is "the sloppy frequency value at which the score will be 0.5" (:92).
  • Lucene treats NaN as invalid. TopScoreDocCollector.java:30-31; the test framework's AssertingScorer asserts !Float.isNaN(score) (AssertingScorer.java:129).
  • Upstream's own oracle. TestFeatureField.doTestSimScorer (:279-287) asserts Float.isFinite(maxScore) // used to compute max scores and that the score never decreases with the value. It is run for SigmoidFunction(20f, 0.6f) (:275-277); run on (2^20, 60) and (1e16, 20) it fails with max score NaN.
  • Robustness was a goal. The code comment (FeatureField.java:528-530) says the formula was rewritten so the score does not decrease "in spite of rounding".
  • No limit or NaN in the recorded and archived material. No javadoc, test, CHANGES or MIGRATE entry or commit message at 645d4fe14a20, and no discussion the searches found, limits the exponent or presents NaN as intended. In the archived LUCENE-8197 review (#9244) reviewers asked for documented and validated parameter ranges, and the committed code has the (0, +Infinity) checks; no archived comment discusses pivot^exp overflowing.
  • Tests never reach the region. Every upstream sigmoid test uses exponent 0.6 (TestFeatureField) or 2 (TestIntervalQuery.java:439).
The devil's-advocate check156 words

The strongest case, built by the cross-model reviews and by the devil's-advocate verifier: FeatureField is @lucene.experimental, its constants "typically need training" (FeatureField.java:84), and exponents of 50 to 150 are unrealistic, so a committer could say the function was never meant for them.

Why it fails: @lucene.experimental is about API stability ("might change in incompatible ways in the next release"), not about returning invalid scores; the domain is documented as (0, +Infinity) and validated, so these inputs are legal; the authors capped the one parameter they found unreasonable (MAX_WEIGHT) but not the exponent; the javadoc describes high exponents as the way to make the function steeper; and an algebraically equal one-line rewrite removes the failure, at the price of one more division per document. The realistic-exponent point lowers the priority, not the reality, and maintainers may reasonably prefer validating the parameters (option B) to changing the formula. Verdict: not intended, a defect.

Suggested fix

#

Recommended Score as weight / (1 + (pivot / S)^a) (validated)

Score as weight / (1 + (pivot / S)^a): the same function without a precomputed power, so it cannot form Infinity/Infinity or 0/0. The repro passes, and so do the document and intervals test packages (499 and 117 tests); on a test grid, scores of at least 1e-6 * weight move by at most 1 ulp.

// FeatureField.SigmoidFunction.doScore; the same line in IntervalScoreFunction.SigmoidFunction
return (float) (weight / (1 + Math.pow((double) pivot / f, a)));
All options and trade-offs4 options · 684 words

Option A was built and run through gradle in both copies. B (validate the exponent) is a possible addition that turns NaN into an error, C (document a range) leaves NaN, and D (guard in the collector) treats the symptom. Workaround without a fix: use exponents up to 8, which never fail. With a larger exponent keep pivot^exp well inside the double range on both sides: no overflow (exp * log2(pivot) well below 1024) and, for a pivot below 1, no underflow (pivot 2^-14 with exponent 100 already underflows).

Score as weight / (1 + (pivot / S)^a) (validated) (recommended)

#

Drop pivotPa from FeatureField.SigmoidFunction and IntervalScoreFunction.SigmoidFunction and compute the same function as weight / (1 + (pivot / S)^a) (2 files, +7/-10). For positive finite inputs pivot / S lies in [0, +Inf], so does its power, 1 + x lies in [1, +Inf] and the result in [0, weight]: no NaN. At S = pivot it is exactly weight / 2. It stays non-decreasing in S, the property the old comment protects: the division is monotone, Math.pow is specified as semi-monotonic, and 1 + x and w / x are monotone.

// FeatureField.SigmoidFunction.doScore; the same line in IntervalScoreFunction.SigmoidFunction
return (float) (weight / (1 + Math.pow((double) pivot / f, a)));

Trade-offs

  • Ordinary scores barely change, but not bit for bit. A copy of the old and new expressions in plain double arithmetic (not the real scorer) on 1,320,480 points (7 pivots from 0.01 to 1e6, exponents 0.5 to 8, weights 1 and 3, S from Float.MIN_NORMAL to 1e30 in 1% steps): 73% bit-identical; where the old score is at least 1e-6 * weight, at most 1 ulp apart. The largest absolute difference, 9.1e-13 (2^-40), is a 1-ulp difference at a score of about 1e-5 (weight 1, pivot 4.5, exponent 2, S 0.014), and every score above about 1e-5 is bit-identical. Where the old form rounds a tiny score to 0 by cancellation, the new form keeps it (at most 3.3e-16); that gives the largest ulp distance. The new form gave no NaN, nothing outside [0, weight] and no decreasing step on the grid. A ranking that depends on exact score values can still change, so it is worth a CHANGES.txt line.
  • Cost. One more division per scored document (two instead of one) and no precomputed constant; no benchmark was run.
  • Review. No reviewer has read the diff line by line yet.

Reject parameters whose pivot^exp is not a finite positive double

#

In newSigmoidQuery and IntervalScoreFunction.sigmoidFunction, throw IllegalArgumentException when Math.pow(pivot, exp) is +Infinity or 0, or reject exponents above a documented bound.

Trade-offs

Turns silent NaN into an error that downstream engines would surface to the client. Leaves the finite band where S^a + pivot^a overflows (score weight instead of weight / 2) unless the bound is tighter, and rejects parameters option A handles. An exponent bound is a judgement call; none is documented today. Not run.

Document a usable exponent range

#

Say in the javadoc which exponents are safe for a given pivot.

Trade-offs

Leaves NaN scores for anyone who misses the note, and contradicts the documented (0, +Infinity) domain unless that changes too.

Guard against NaN in the collector

#

Make top-k collection tolerate NaN scores.

Trade-offs

TopScoreDocCollector already documents that it does not handle NaN; the related collector-side issue #3347 (LUCENE-2271) has been open since 2010. Fixing the producer is local and cheap.

Downstream note

#

Engines that pass a request's sigmoid pivot and exponent straight to newSigmoidQuery (Elasticsearch and OpenSearch rank_feature, Solr {!rank function=sigm}) let a search client trigger it, for its own scores and order only; matching, filters and deletions are unaffected. If an application itself fixes an underflowing pivot^exp, a document with a tiny feature value can rank first with NaN.

How it was found

#

An exhaustive run of every FeatureField score function on the real jar, 6.8e9 checks of properties such as "never NaN", found NaN only in the sigmoid. An SMT model of the final expression then showed NaN needs pivot^exp to overflow, or to underflow together with S^exp, and a JUnit test was written from those parameters.

The method in full206 words

Method: bounded-exhaustive translation validation of the real jar (the study's "semi-formal" tier: the first signal came from executing the stock code against exact properties).

  • A harness drove every FeatureField score function on the stock main jar over every integer frequency from 1 to 65,535 plus Integer.MAX_VALUE and Float.MAX_VALUE (for the sigmoid: 287 pivots covering every float binade, 21 exponents, 2 weights), about 6.8e9 checks against seven properties: no NaN or negative score, non-decreasing in the value, within the max-score bound, a finite max score, bulk scoring equals single scoring, explanation equals score, at most the weight. Only the sigmoid produced NaN (as a score and as its max score). The only other failures were +Infinity max scores of the linear and log functions at a feature value of Float.MAX_VALUE, which were not reported.
  • cvc5 queries over the final score expression (floating-point theory, the two powers modelled as independent non-negative doubles) then showed NaN is possible only if pivot^a = +Inf, or pivot^a = 0 and S^a = 0 (the "only if" query unsat, both vacuity variants sat), and a region probe mapped which accepted (pivot, exponent) pairs fail.
  • The JUnit repro was written by hand from those parameters; the one-test minimal repro came later.

History

#

LFV-258, snapshot of 2026-11-10

Registry title
FeatureField.newSigmoidQuery (and the IntervalQuery sigmoid) return NaN scores when pivot^exp overflows or underflows a double, for pivot and exp values the factories accept
Area
document / FeatureField sigmoid scoring (FeatureField.SigmoidFunction behind newSigmoidQuery; the same arithmetic is copied in queries / intervals IntervalScoreFunction.SigmoidFunction behind the 4-argument IntervalQuery constructor)
Priority
Low, rank 756: FeatureField sigmoid queries return NaN scores only for extreme pivot and exponent values, which is silent but boundary-value only.
Impact class
silent wrong results
Impact note
Applications on Lucene 7.4.0 through 10.5.2 or main that rank with a FeatureField sigmoid query (FeatureField.newSigmoidQuery, which downstream engines' rank_feature sigmoid and Solr's {!rank function=sigm} call with the request's pivot and exponent) and choose a steep exponent with a large or tiny pivot, so that pivot^exp leaves the double range (exp*log2(pivot) >= 1024, for example exp 50 with pivot >= 1.46e6 or exp 100 with pivot >= 1209, or pivot^exp below 2^-1074 together with small feature values; never for exp <= 8, and typical exponents are below 2), get NaN scores and no error at any index size with the default IndexWriterConfig, codec and searcher: on 10.2.0 and later the NaN hits come back ranked ahead of correctly scored documents (in the overflow case every hit is NaN, in doc-id order), on 7.4.0-10.0.0 TopDocs also holds placeholder hits (doc 2147483647, score -Infinity) in place of real ones and 10.1.0 returned 1 of 4 hits, with -ea a collector assertion fires instead on 7.4.0-10.0.0, and explain() reports NaN; the 4-argument IntervalQuery constructor has the same arithmetic but needs exponents in the hundreds (600 at pivot 4) because sloppy frequencies are small.
Summary
You rank documents with FeatureField.newSigmoidQuery (or IntervalQuery's pivot-and-exponent constructor) and pick a steep exponent with a large or tiny pivot, values the factory accepts because it only requires both to be positive and finite. You expect the documented score weight * S^exp / (S^exp + pivot^exp), a number between 0 and weight that equals weight/2 at S = pivot. Instead SigmoidFunction precomputes pivot^exp as a double, which becomes +Infinity or 0 for such parameters, so scores come out as Inf/Inf or 0/0 = NaN: with pivot 2^20 and exponent 60 every document scores NaN; since 10.2.0 NaN hits rank ahead of correctly scored ones, so the best document can come last, and on 9.x (assertions off) TopDocs even returns placeholder hits with doc id 2147483647.
