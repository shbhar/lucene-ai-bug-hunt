After a non-tragic addDocument failure, the next document resets the delete slice and the next commit silently lacks an acknowledged delete

When addDocument fails because an in-memory segment could not finish copying its queued deletes and doc-values updates, the writer stays open and the segment's next document drops the uncopied rest. The next commit() succeeds with a deleted document still in it (9.8.0 through 10.6.0 and main).

The finding in 30 seconds

#

Each time an in-memory segment indexes a new document, it then applies to its earlier documents every delete and update queued since its last document. If that copy throws part-way, the rest stays queued. The segment's next document finds no new operations and calls reset(), which marks the whole queue done. The uncopied delete never reaches the document.

How deletes reach buffered documents, in one minute

#
  1. Each indexing thread fills its own in-memory segment (a DWPT). Deletes and doc-values updates go into one writer-wide queue, and every call returns a sequence number.
  2. Each in-memory segment keeps a slice of that queue: everything queued since its last document. Each time it indexes a new document, it then applies the slice to the documents it buffered before, node by node. That is how a delete reaches a document that is still in memory.
  3. commit() also returns a sequence number: every operation with a smaller or equal number is in the commit.

The finding, step by step

#
  1. Add a document buffered; it waits in its in-memory segment. Then call updateNumericDocValue 2,200,000 times with one 1 KB term, and deleteDocuments(id:buffered) (sequence number 2,200,002). ramBytesUsed() reports 2.6 MB.
  2. addDocument(next) throws ArithmeticException: integer overflow: after indexing next, the segment copies the 2.2 million queued operations into its own buffer, for the documents buffered before next, and passes the 2 GiB a byte pool can address. The delete, queued last, is never copied. isOpen() is true, getTragicException() null.
  3. addDocument(later) finds no new operations and marks the segment's queue as done, the uncopied part included.
  4. You expect the writer to close itself, or commit() (sequence number 2,200,005) to reflect the delete: 0 hits for id:buffered.
  5. Instead the commit succeeds and id:buffered has 1 hit. Nothing reports the lost delete, and CheckIndex is clean.

Who is affected

#

Applications on the default config that keep indexing after one addDocument failed (its javadoc promises "the index will be consistent"). The executed triggers are extreme: about 2 GiB of update or delete terms behind one in-memory segment that receives no documents, with no commit, refresh or flush in between, which the writer's RAM accounting does not count.

Mechanism, terms and numbers846 words

After an in-memory segment (a DWPT) has indexed a new document, and before addDocument returns, DocumentsWriterPerThread.finishDocuments applies to the documents buffered before it every delete and doc-values update queued since the segment's last document, its slice of the writer-wide delete queue (DocumentsWriterPerThread.java:291, :300-301, :361-390). DeleteSlice.apply walks the slice node by node and empties it only after the last node (DocumentsWriterDeleteQueue.java:348-367). When a node throws, the slice keeps its unapplied nodes, and the exception is not aborting: finishDocuments runs after allDocsIndexed = true and outside any onAbortingException guard, so isOpen() stays true and getTragicException() null. On the segment's next document updateSlice finds no new operation, and finishDocuments calls deleteSlice.reset() (:385), which marks the unapplied nodes done. The segment flushes without them, and the next commit() returns a sequence number that covers an acknowledged delete it lacks. Since 9.8.0 a legal workload reaches the throw: #12392 made ByteBlockPool.nextBuffer throw ArithmeticException at 2 GiB (ByteBlockPool.java:199), and an idle segment's copy of 2.2 million doc-values updates on a 1 KB term gets there. On 9.7.0 the same workload closes the writer. Treating a throw out of finishDocuments as aborting, as the indexing chain does for a byte-pool overflow while indexing, fixes it.

Step by step (the repro)

#
  1. addDocument(buffered) leaves the thread's in-memory segment with one document and an empty slice.
  2. Each updateNumericDocValue call and the deleteDocuments call append one node to the writer-wide queue. The writer-wide buffer is frozen and applied whenever it reaches the 16 MB RAM buffer, but the segment makes its own copy only at its next document, so its slice spans all 2,200,001 nodes. Nothing counts that backlog (LFV-1077): ramBytesUsed() reads 2,555,912 bytes.
  3. addDocument(next): updateSlice moves sliceTail to the queue tail and returns a negative sequence number (DocumentsWriterDeleteQueue.java:284-293). apply copies every update, term bytes included, into the segment's private BufferedUpdates (BufferedUpdates.java:134-144). About 2 GiB in, ByteBlockPool.nextBuffer throws at byteOffset = Math.addExact(byteOffset, BYTE_BLOCK_SIZE) (ByteBlockPool.java:199). Executed stack, from there up to finishDocuments: ByteBlockPool.nextBuffer:199 <- ByteBlockPool.append:301 <- ByteBlockPool.append:228 <- BytesRefArray.append:70 <- FieldUpdatesBuffer.append:215 <- FieldUpdatesBuffer.addUpdate:184 <- BufferedUpdates.addNumericUpdate:139 <- DocValuesUpdatesNode.apply:507 <- DeleteSlice.apply:364 <- DocumentsWriterPerThread.finishDocuments:383. apply never reaches its reset(), so the slice still holds the rest of the updates and the delete of buffered.
  4. The exception is not aborting: maybeAbort (DocumentsWriterPerThread.java:310, :594-605) acts only on an exception passed to onAbortingException, and nothing passes this one. DocumentsWriter.updateDocuments skips doAfterDocument (DocumentsWriter.java:434) and returns the segment to the pool (:444). Executed: isOpen()=true, getTragicException()=null, numRamDocs()=2.
  5. addDocument(later): nothing was queued since step 3, so updateSlice returns a positive number and finishDocuments calls reset() (:385): sliceHead = sliceTail. The delete of buffered is gone from the segment. doAfterDocument then sees the segment's 2 GiB of pending updates and flushes it (executed: numRamDocs() 2 -> 0).
  6. A delete reaches a document that is still buffered only through its segment's slice: the delete queue's javadoc says each DWPT keeps its own head of the queue, for "its segments private deletes" (DocumentsWriterDeleteQueue.java:34-38), while the writer-wide slice records deletes "against all prior (already written to disk) segments" (:73-75). Executed: the committed index still has buffered. commit() returns 2,200,005.

Why the reset() is the defect, not the overflow

#
  • In normal operation that reset() changes nothing: after every successful apply the slice is already empty (:366), and a positive updateSlice means nothing was queued. It acts only after a failed apply; a bounded exhaustive model of the slice protocol found no other path within its bound (every sequence of up to 7 operations on one modelled segment).
  • One transient fault is enough: a fault-injection check that makes one queue node throw once (no overflow, 128 MB heap, through the real IndexWriter/DWPT path) loses the delete the same way (delete sequence number 3 missing from commit 7). It injects the fault through package-private writer internals, so it is evidence for the mechanism, not a public-API repro.
  • Read, not executed: for updateDocument and delete by term, add(node, slice) sets slice.sliceTail (DocumentsWriterDeleteQueue.java:166) before tryApplyGlobalSlice() (:168), so a throw there (the writer-wide buffer's overflow) leaves the same unapplied slice for the same reset(). On that path later freezes of the broken writer-wide buffer fail too, so a loss would not be the only symptom.
Exposure and likelihood421 words
  • What is lost. Deletes, and by code also doc-values updates, of documents buffered in that in-memory segment that were queued behind the failing node. Deletes acknowledged after the failure are applied (executed with the delete-term trigger, 75,000 distinct 30,000-byte delete terms: of three acknowledged deletes, buffered before the failure and b2, b3 after it, only buffered, queued behind the failing node, is missing). CheckIndex is clean, on that commit and on the commit of this doc's doc-values workload, but it checks structure only; it does not see a missing delete. By code, deletes of documents in already-flushed segments go through the writer-wide buffer, not this slice.
  • Silent. The exception surfaces on a later addDocument that has nothing to do with the delete, and the writer's own health signals say nothing is wrong: isOpen() is true and getTragicException() null. The addDocument javadoc promises that after an exception "the index will be consistent, but this document may not have been added" (IndexWriter.java:1465-1466); it does not tell the caller to stop using the writer or to roll back.
  • Default vs opt-in. An otherwise default IndexWriterConfig (the test pins the default codec with TestUtil.getDefaultCodec()), a plain ByteBuffersDirectory, one thread, assertions on or off. The workload calls only public IndexWriter API; the test class itself uses the test framework (LuceneTestCase, TestUtil).
  • Scale, the counterweight. About 2^31 bytes of buffered update or delete terms must pass one in-memory segment that holds documents but receives none, with no commit, NRT reopen or flush in between. Executed: 2.2 million updateNumericDocValue calls on one 1 KB term (3 GB heap), or 75,000 deleteDocuments calls with distinct 30,000-byte terms (8 GB heap, 9.9.0 and later). The writer's accounting does not count the backlog (LFV-1077), and neither safeguard stops the private copy: when buffered deletes reach the 16 MB RAM buffer the writer freezes and applies its writer-wide buffer (FlushByRamOrCountsPolicy.java:45-53), which does not touch the idle segment's slice; the flush-by-RAM check and the 1,945 MB per-thread hard limit (IndexWriterConfig.java:93) both run in doAfterDocument (DocumentsWriterFlushControl.java:215-251), which is reached only after finishDocuments returned (DocumentsWriter.java:428, :434). They first see the 2 GiB copy at addDocument(later), after the reset, and the segment is flushed then. Likelihood: contrived.
  • The same throw site in production (related, not a report of this loss): elastic/elasticsearch#160939 (Lucene 10.5.1) shows the same non-tragic ArithmeticException out of DeleteSlice.apply inside finishDocuments, on the writer-wide-buffer path; its reporter says it is still hitting production.

Why it looks unintended

#
  • commit(): "All sequence numbers <= this value will be reflected in the commit". It returns 2,200,005 but lacks the delete (2,200,002).
  • addDocument on an exception: "this document may not have been added". Here an earlier, acknowledged delete is lost.
  • The same byte-pool overflow, hit while indexing a document's terms, already closes the writer (LUCENE-5987: no silent data loss).
The full argument431 words
  • commit(). "it returns the sequence number such that all indexing operations prior to this sequence will be included in the commit point" and "All sequence numbers <= this value will be reflected in the commit, and all others will not." (IndexWriter.java:4202-4204, :4207-4209). The class javadoc introduces sequence numbers as "describing which changes are in the commit point and which are not" (IndexWriter.java:117-121).
  • addDocument. "if an Exception is hit (for example disk full) then the index will be consistent, but this document may not have been added." (IndexWriter.java:1465-1466). The exception may cost this document, not an earlier acknowledged delete.
  • The design rule. LUCENE-5987: "IndexWriter will now forcefully close itself on aborting exception (an exception that would otherwise cause silent data loss)." (lucene/CHANGES.txt:11614-11616). The indexing chain follows it for a byte-pool overflow while indexing a document's terms: "If we hit an exception in here, we abort all buffered documents since the last flush, on the likelihood that the internal state of the terms hash is now corrupt" (IndexingChain.java:2068-2073; catch (Throwable th) { onAbortingException(th); throw th; } at :2098-2100). finishDocuments is the gap. An older precedent: LUCENE-938 "Fixed cases where an unhandled exception in IndexWriter's methods could cause deletes to be lost." (lucene/CHANGES.txt:20501-20503).
  • The reset() was not written for this case. It came with LUCENE-5006 (trunk 75ab79f0aa3, 2013-08-19, "if we don't need to apply we must reset!"; release 4.5.0 got it through the branch_4x commit 8003cc78298), where it also skipped applying while the segment had no documents (applySlice = numDocsInRAM != 0). The block path (updateDocuments) got today's form, a reset only when nothing new was queued, in 76fb616bdf5 (2016); the single-document path kept applySlice = numDocsInRAM != 0 until LUCENE-9276 (#1346, c0cf7bb4b0e, Simon Willnauer, 2020-03-13) sent addDocument through finishDocuments. In today's form the branch changes nothing unless an apply failed. We found no comment, test or PR that discusses a failed apply (in the history of these lines, the test tree and the prior-report searches); TestDocumentsWriterDeleteQueue, the only test that touches DeleteSlice, applies successfully.
  • No documented limit was exceeded. Every term is 1 KB (the indexed-term limit is 32,766 bytes, IndexWriter.java:258), the IndexWriterConfig settings are the defaults, and ramBytesUsed() stays below 16 MB. The per-thread hard limit is "a safety limit to prevent a DocumentsWriterPerThread from address space exhaustion due to its internal 32 bit signed integer based memory addressing" (IndexWriterConfig.java:373-378); it is checked only after finishDocuments returns, so it cannot stop this copy.
The devil's-advocate check203 words

Unsupported scale. On #15330 a maintainer (rmuir) wrote that "the limits on IndexWriter are 2GB". That remark is about one document's postings pool, which the per-thread hard limit bounds. Here the application never sees a number near 2 GB, and #16867 treats the same 2 GB overflow of the writer-wide buffer as a bug to fix (lucene/CHANGES.txt:324-326). Scale goes to severity (contrived), not to validity.

"After a non-tragic failure, call rollback()." On open #9738 (2019) a maintainer (s1monw) said that non-tragic exceptions from some methods may lose documents and that a user can always call rollback(). Their list (getReader, deleteAll, addIndexes, flushNextBuffer, doFlush, prepareCommitInternal, startCommit) leaves out addDocument, and they describe unrecoverable exceptions during indexing as handled in DocumentsWriter. No javadoc tells a caller to roll back after a failed addDocument; its javadoc promises a consistent index.

The class javadoc promises a self-close only "if you hit an Error, or disaster strikes during a checkpoint" (IndexWriter.java:162-165). Staying open is not the defect; commit() then breaking its own contract is.

Verdict: not intended, a defect. An independent reviewer from another model family (OpenAI GPT-5.6) rated the intended-behaviour argument weak; the devil's-advocate verifier rejected each case above.

Suggested fix

#

Recommended A: a throw out of finishDocuments is aborting

Treat any exception out of finishDocuments as aborting (onAbortingException), as the indexing chain does for a byte-pool overflow: the segment is aborted, the writer closes itself and the last commit stays intact. Validated: the repro passes on and off; the org.apache.lucene.index tests (1,397) and :lucene:core:check pass.

long seqNo;
try {
  if (deleteNode != null) {
    ... unchanged ...
  } else {
    ... unchanged, including deleteSlice.reset() ...
  }
} catch (Throwable t) {
  // The slice may now hold deletes that were never applied to pendingUpdates, and a later
  // finishDocuments would reset() past them: this DWPT can no longer honour them.
  onAbortingException(t);
  throw t;
}
return seqNo;

A: a throw out of finishDocuments is aborting (validated by the checks) (recommended)

#

Wrap the body of DocumentsWriterPerThread.finishDocuments in a try whose catch (Throwable t) calls onAbortingException(t) and rethrows. The finally of updateDocuments and updateBatch then calls maybeAbort, which aborts the segment and fires the tragic event (DocumentsWriterPerThread.java:594-605), and the writer closes itself. +17/-10 lines in one file, mostly the re-indented existing body. It mirrors the indexing chain (IndexingChain.java:2098-2100).

long seqNo;
try {
  if (deleteNode != null) {
    ... unchanged ...
  } else {
    ... unchanged, including deleteSlice.reset() ...
  }
} catch (Throwable t) {
  // The slice may now hold deletes that were never applied to pendingUpdates, and a later
  // finishDocuments would reset() past them: this DWPT can no longer honour them.
  onAbortingException(t);
  throw t;
}
return seqNo;

Trade-offs

The segment's buffered documents are lost with the abort (here buffered and next), and the application must open a new writer; the last commit stays the recovery point. That is the stance LUCENE-5987 took for every exception that would otherwise lose data silently. By code it also covers the writer-wide-buffer path (add(node, slice) -> tryApplyGlobalSlice, not executed). It makes any throw aborting, also an AlreadyClosedException from a closed delete queue, but a queue is closed only after every segment using it was flushed (DocumentsWriter.java:707), and the index test package passes. It also makes every other runtime failure out of finishDocuments aborting, where the writer used to stay open; the nearby suites and the index package pass, but no stress, concurrency, full-flush or performance test was run, so a reviewer may want the catch narrowed or argued case by case. Optional cleanup: the comment at the top of finishDocuments (DocumentsWriterPerThread.java:362-365) still describes the earlier order (update the slice, then increment the doc id); today the doc id is assigned first (:291).

B: recover without closing (not enough alone)

#

Apply instead of reset() when the slice is not empty, or let apply advance sliceHead node by node so a retry resumes at the failing node.

Trade-offs

The per-thread BufferedUpdates is left mid-update: nextBuffer installs the new block and advances bufferUpto before Math.addExact throws (ByteBlockPool.java:196-199), so the pool is left half-advanced and appending to it again is not safe; the segment would still have to be flushed or aborted. Read, not validated.

C: bound the idle segment's backlog (the trigger, LFV-1077)

#

Count the bytes an idle segment's slice pins, or flush such a segment early, so its copy never nears 2 GiB.

Trade-offs

Removes the executed per-thread trigger on a default config, and a maintainer may reasonably want it first. It leaves the handling, though: the writer-wide-buffer path and any future non-aborting throw from a queue node still reach the reset(), and the transient-fault check loses a delete with no overflow at all. Do it in addition to A, not instead. Not validated here.

Downstream note

#

An application that relies on deleteDocuments to withdraw a document (removed content, revoked access) could keep serving it after the next commit, but only after about 2 GiB of buffered update or delete terms reach one writer without a flush or commit.

How it was found

#

Code reading next to the recent upstream fix #16867, which caps the writer-wide delete buffer, looked for the per-segment copy of the same stream that #16867 leaves unbounded. A public-API probe then showed a delete missing from a commit after a non-tragic failure. It was reduced to one test and checked with a bounded exhaustive model of the slice protocol.

The method in full187 words

Method: non-formal (code reading witnessed by an executed public-API probe), confirmed with a bounded exhaustive model.

  • #16867 (merged 2026-10-30) caps the bytes of buffered deletes and updates in the writer-wide delete queue, because the byte pools use 32-bit offsets, and assumes the per-thread buffers cannot overflow. Reading the code around it for other copies of the same stream found the copy an in-memory segment makes in finishDocuments, which has no cap, and the non-aborting handling when it throws.
  • A public-API probe (large distinct delete terms behind an idle in-memory segment, then a delete of the buffered document, 8 GB heap) showed addDocument failing there, the writer staying open and the next commit missing the delete. The case was then reduced to the one 3 GB doc-values-update JUnit test of this page.
  • A bounded exhaustive model of one segment's delete slice (every sequence of up to 7 deletes, adds, updates and commits with one injected non-aborting fault: 19,420 fault scenarios per mode) found 1,073 (transient fault) and 1,767 (persistent fault) runs where a commit lacks an acknowledged operation, 0 with the fix and 0 without a fault.

History

#

Users can hit it since 9.8.0: #12392 (2023, correct in itself) made the 2 GiB overflow throw inside finishDocuments; on 9.7.0 the same workload closes the writer. The apply-then-reset dates from 2011, the reset() branch from 2013. Affected through 10.6.0 and main; not fixed upstream as of 2026-11-03.

Versions tested7 rows

Exposing change: #12392 "Catch offset overflows in byte pool (#9660)" (Stefan Vodita, 2023-06-28; main b88d3e19889, 9.x backport 445b30d421c, first released in 9.8.0) changed byteOffset += BYTE_BLOCK_SIZE to byteOffset = Math.addExact(byteOffset, BYTE_BLOCK_SIZE): a correct fix that turns a silent int wrap into an exception, which for this workload is thrown inside finishDocuments. On the 9.7.0 jars with only that ByteBlockPool.java swapped in, the loss appears. The handling itself: DeleteSlice.apply resets only after every node succeeds since LUCENE-2956 (e95097a7c8d, Simon Willnauer, 2011-04-13, release 4.0.0); the no-new-deletes reset() dates from LUCENE-5006 (trunk 75ab79f0aa3, 2013-08-19; in release 4.5.0 through the branch_4x commit 8003cc78298). Its current form came for the block path with 76fb616bdf5 (2016) and for addDocument with LUCENE-9276 (#1346, c0cf7bb4b0e, 2020-03-13), which sent single documents through finishDocuments. From 4.5.0 to 9.7.0 no legal-input, non-tragic exception out of DeleteSlice.apply is known. Not fixed upstream: on upstream main f72004515ec (2026-11-03), branch_11x and branch_10_6 the last commits on the files involved predate 5adff78bb168.

Finding record

LFV-1090, snapshot of 2026-11-08

Registry title
After addDocument fails with a non-tragic exception while an in-memory segment copies its backlog of buffered deletes and doc-values updates, the segment's next document resets its delete slice past the operations that were never applied, so IndexWriter stays open and the next successful commit silently lacks an acknowledged delete of a buffered document
Area
index / IndexWriter delete queue (DocumentsWriterPerThread.finishDocuments, DeleteSlice failure handling)
Priority
Medium, rank 113: Durable silent data loss on the default IndexWriter in every release from 9.8.0 to 10.6.0 and on main. A non-tragic failure while an in-memory segment copies its backlog of buffered deletes and doc-values updates leaves the writer open, and the next successful commit lacks an acknowledged delete, which keeps it in Medium. Its known triggers are contrived: about 2 GiB of buffered update or delete terms must pass one idle in-memory segment with no flush, refresh or commit.
Impact class
data corruption
Impact note
Hits applications on the default IndexWriterConfig, codec and directory that keep indexing after an addDocument failed with a non-tragic exception while the in-memory segment applied its backlog of buffered deletes and doc-values updates: the writer stays open (isOpen() true, getTragicException() null) and the next successful commit, whose sequence number covers it, silently lacks an acknowledged delete of a document buffered in that segment [exec; by code also any doc-values update of those documents queued behind the failing node, read]; the only executed triggers are extreme (about 2^31 bytes of buffered update or delete terms passing one idle in-memory segment with no flush, refresh or commit, for example 2.2 million updateNumericDocValue calls on one 1 KB term, which the RAM buffer never counts, LFV-1077); every release from 9.8.0 to 10.6.0 is affected, while 9.7.0 closes the writer instead.
Summary
You add a document to an IndexWriter, then send a long run of doc-values updates (executed: 2.2 million updateNumericDocValue calls selected by one 1 KB term) and delete the buffered document; the next addDocument fails with ArithmeticException 'integer overflow' while the in-memory segment copies that backlog into its own buffer, and the writer stays open with no tragic exception. You expect either the writer to close itself or the next successful commit, whose sequence number is above the delete's, to reflect the delete. Instead the following addDocument finds no new deletes and resets the segment's delete slice past the operations the failed copy never reached, so the commit succeeds and the deleted document is still in the index.
Introduced
b88d3e19889f (main) and its branch_9x backport 445b30d421c7 (first released in 9.8.0), apache/lucene#12392 'Catch offset overflows in byte pool (#9660)' by stefanvodita: the exposing change, correct in itself. Its Math.addExact in ByteBlockPool.nextBuffer turns the 2 GiB overflow of this workload into a non-tragic ArithmeticException thrown inside the per-thread DeleteSlice.apply that finishDocuments calls [exec: on the 9.7.0 jars with only ByteBlockPool.java from 445b30d421c7 swapped in the JUnit fails; plain 9.7.0 passes]. The handling defect itself is older [read: git log -S and git blame in the full-history clone]: DeleteSlice.apply resets only after every node succeeds since e95097a7c8d (LUCENE-2956 'Support updateDocument() with DWPTs', 2011-04-13, release 4.0.0), and finishDocument resets the slice when no new deletes arrived ('if we don't need to apply we must reset!') since 75ab79f0aa3 (LUCENE-5006, trunk, 2013-08-19; in release 4.5.0 through the branch_4x commit 8003cc78298); the current seqNo-based form comes from 76fb616bdf5 (2016-06-01, block path) and c0cf7bb4b0e (#1346, LUCENE-9276, 2020-03-13, addDocument path) (2023-06-28 (author date of b88d3e19889f and 445b30d421c7, the exposing change); the handling defect 2011-04-13 (e95097a7c8d) and 2013-08-19 (75ab79f0aa3))
First affected version
9.8.0 [exec: the JUnit fails; 9.7.0 passes because the same workload makes the writer close itself with a tragic ArrayIndexOutOfBoundsException, so nothing is lost silently]; the handling defect is latent from 4.5.0 through 9.7.0, with no legal-input, non-tragic exception out of DeleteSlice.apply known to us there [read]
