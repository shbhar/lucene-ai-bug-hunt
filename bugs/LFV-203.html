The finding in 30 seconds

#

FunctionScoreQuery turns a negative value into a score of 0, but since #16431 its block bound has no such clamp and can be negative. A top-k BooleanQuery trusts that bound and can conclude that the block cannot reach the top hits and skip it: in a disjunction, when the summed bounds stay below the minimum competitive score. Where the bounds of the other clauses cover the negative one, the search can instead enter a loop that does not advance: in the runs, at a minimum competitive score of 0 or, after that, where the negative bound was about 1 billion to 10^15 times that score.

Background

#
  1. Negative values score 0. FunctionScoreQuery scores a document with a value, here the field delta. A negative value scores 0 (since Lucene 8.0), because Lucene scores must not be negative.
  2. Skip index. A numeric doc-values field can opt in to a skip index (NumericDocValuesField.indexedField): per block of documents (4,096 documents with the default codec; a block of equal values in consecutive documents can be longer) it stores the smallest and the largest value.
  3. Block bounds. In a top-k search each clause reports, per block, an upper bound of its scores (getMaxScore). The search adds the bounds. It skips a block whose summed bound cannot reach the minimum competitive score, the lowest score still worth collecting; in a disjunction it also stops looking for candidates in clauses whose bounds together cannot reach it, and such clauses still add their scores to the candidates of the others. The minimum competitive score starts at 0.
  4. New since #16431. For a skip-indexed field read through a field source with a declared direction (fromLongField and the like), FunctionScoreQuery reports (the wrapped query's bound) × (the block's largest value after decoding) × boost; where the source reports no bound it still reports +∞. 10.6.0 reports +∞, which never leaves anything out.

The finding, step by step

#
  1. Index one document: body:b and NumericDocValuesField.indexedField("delta", -1000). Search BooleanQuery(SHOULD FunctionScoreQuery(MatchAllDocsQuery, DoubleValuesSource.fromLongField("delta")), SHOULD TermQuery(body:b)) with IndexSearcher.search(q, 1).
  2. You expect 1 hit with score 0.131: the negative value scores 0, the term 0.131. The 10.6.0 release returns it.
  3. On branch_11x and main you get 0 hits, no error, assertions on or off. The function clause reports the bound 1 × -1000 = -1000 for a document that scores 0. The search adds the bounds, -1000 + 0.131, finds the sum below 0 and skips the block.
  4. Make the value -1 and boost the term clause by 10 (bound 1.31). The sum, 0.31, is not below 0, so the block is not skipped. With assertions off search(q, 1) does not return within 10 s: its thread stays in a loop that starts at 1.0 and subtracts 1.4e-45, which leaves 1.0. With assertions on the search throws an AssertionError. 10.6.0 returns the hit.
  5. The loop is not new: it is LFV-1016, in releases since 10.3.0 (labelled known upstream on this site through #11464, the report of the same failure in the loop's predecessor; no report of the present loop was found). New on the 11.0 branch is the route into it. Two narrower shapes do not return with assertions on either: two SHOULD function clauses (1,002 documents) and two MUST function clauses (4,097 documents). Many other shapes return the right hits. With a one-line clamp of the bound, every test and every shape that was run with it returned the right hits.

Who is affected

#

Applications on branch_11x or main (unreleased) that rank with FunctionScoreQuery over a skip-indexed numeric field (opt-in) as a SHOULD or MUST clause can be affected when every value of a skip block is negative after decoding. Rare. A wrapped TermQuery, blocks with both signs, fields without skip index and boostByValue returned the right hits.

Mechanism, terms and numbers5,537 words

FunctionScoreQuery maps a negative function value to a score of 0 (LUCENE-7996, Lucene 8.0). Since #16431, which is on main and branch_11x and in no release, its scorer also reports a block bound for top-k pruning: innerMaxScore * valueMaxScore * boost, where valueMaxScore is the decoded skip-index maximum of the block. The bound has no clamp at 0. For a block whose values are all negative after decoding it is negative, below the 0 that its documents score, where the wrapped query's bound is above 0 (around a TermQuery it is -0.0).

What a BooleanQuery does with that bound depends on its other clauses and their bounds, and neither of the two consequences is a rule. In a disjunction, a block whose summed bounds stay below the minimum competitive score is skipped, and its hits can be missing: one document with -1000 gives 0 hits instead of 1, with assertions on and off. Where the other bounds cover the negative one, the block is not skipped, and the bulk scorer calls ScorerUtil.minRequiredScore with a negative remaining bound; the loop in that method can then make no progress. In the runs it did so while the minimum competitive score was still 0 or, once that score was positive, where the size of the negative bound was between about 1 billion and about 10^15 times it. At a minimum competitive score of 0 (one document with -1) the search did not return within 10 s with assertions off and threw an AssertionError with assertions on. Once the minimum competitive score is positive, two narrower shapes did not return in either assertion mode: two SHOULD function clauses (1,002 documents) and two MUST function clauses (4,097 documents).

The loop is not new and is not this finding: it is LFV-1016, in releases since 10.3.0 (labelled known upstream on this site through #11464, the report of the same failure in the loop's predecessor; no report of the present loop was found). New on the 11.0 branch is the route into it through FunctionScoreQuery. The 10.6.0 release returns the right hits in every shape that was run, and many shapes return them on branch_11x and main as well, among them shapes whose other bounds cover the negative one. With one changed line, a clamp of the bound at 0, every test and every shape that was run with it returned the right hits.

The code (main 781025d6fe32; the same files on branch_11x daa54f2e0cd3, except IndexSearcher.java, whose two cited lines are the same there)

#
  1. The score clamps. FunctionScoreQuery.java:243-252: score() returns (float) (factor * boost) only when factor >= 0, else 0 ("default: missing value, negative value or NaN", :250). For a negative value explain() returns "truncated score, max of:" with a child "minimum score" (:191-195).
  2. The bound does not. FunctionScoreQuery.java:262-269 returns innerMaxScore * valueMaxScore * boost and guards only Float.isInfinite(valueMaxScore).
  3. Where the negative factor comes from. fromLongField is fromField(field, v -> (double) v, Monotonicity.INCREASING), fromIntField returns fromLongField, and fromDoubleField and fromFloatField are declared INCREASING too (DoubleValuesSource.java:330-347). With a skip index, the values' getMaxScore returns the decoded skipper.maxValue(level), or minValue(level) for DECREASING, of the first level that covers upTo (:571-584). That is negative when every value of the interval decodes negative. A negative bound is correct for the values. The defect is that the scorer does not turn it into a bound of its clamped scores. (For negative raw-bit doubles and floats the value bound itself is also off; that is the separate LFV-189.)
  4. Sparse fields. For a document without a value, advanceShallow(target) moves the skipper on to the next interval (DoubleValuesSource.java:541-550), and that interval's bound then covers the span from target. So one negative value also lowers the bound for the documents without a value before it.
  5. A disjunction: which consequence. A BooleanQuery of two or more SHOULD clauses under TOP_SCORES, with setMinimumNumberShouldMatch at most 1, gets a MaxScoreBulkScorer (BooleanScorerSupplier.java:210-232, :308-328; above 1 it does not, :316-321); so does a FILTER clause with SHOULD clauses and setMinimumNumberShouldMatch(1) (:233-234, :340-364). partitionScorers() sorts the clauses, adds their bounds and makes a clause non-essential while the running sum is below the minimum competitive score (MaxScoreBulkScorer.java:474-517, the test at :502). The negative bound makes the function clause non-essential even at the starting value 0.
    • If every clause is non-essential, the window is skipped ("No matches in this window", :134-137, :515-517): hits are missing.
    • Otherwise an essential clause yields candidates, and scoreNonEssentialClauses calls ScorerUtil.filterCompetitiveHits(buffer, maxScoreSums[i], minCompetitiveScore, n) with a negative maxScoreSums[i] (:447-466, the call at :457). The line before the call is assert scorable.minCompetitiveScore > 0 : "All clauses are essential if minCompetitiveScore is equal to zero" (:454-455). It fires only while the minimum competitive score is 0, and only with assertions on.
  6. The loop (ScorerUtil.java:131-142, called at :156). It starts at minCompetitiveScore - maxRemainingScore and subtracts Math.ulp(minCompetitiveScore), a float ulp, in double arithmetic, while the start is above 0 and (float) MathUtil.sumUpperBound(minRequiredScore + maxRemainingScore, numScorers) >= minCompetitiveScore. With a negative maxRemainingScore the start can be so far above the step that the subtraction changes nothing. This loop is LFV-1016: known upstream, in releases since 10.3.0, and not fixed at the commits run. (Known upstream through the report of the same failure in its predecessor; no report of the present loop itself was found. The prior reports are listed further down.)
  7. A conjunction. Two or more MUST clauses with no SHOULD clause, under TOP_SCORES and with no two-phase iterator in a MUST or FILTER clause, get a BlockMaxConjunctionBulkScorer (BooleanScorerSupplier.java:235-236, :428-438; FILTER clauses become zero-score clauses of it). It skips a window whose summed bound is below the minimum competitive score (BlockMaxConjunctionBulkScorer.java:164): hits are missing. Otherwise it filters the candidates of the first clause before each later clause i with the summed bounds of the clauses from i on (:182-189), through the same loop. The class has no assert statement. It sorts its clauses by cost (:55, a stable sort), so between clauses that match equally many documents the written order decides.
  8. Required plus optional. MUST text + SHOULD function runs through ReqOptSumScorer. Its bound adds the optional clause's bound (ReqOptSumScorer.java:273-279), and once the minimum competitive score is above 0 it skips blocks whose summed bound is below it (:89-107, :127-129).
  9. Default searcher. IndexSearcher.search(q, n) collects with a total-hits threshold of 1,000 (IndexSearcher.java:100, :599), which is TOP_SCORES (TopScoreDocCollector.java:59). The minimum competitive score stays 0 until more than 1,000 hits are counted.
  10. 10.6.0. Its scorer returns Float.POSITIVE_INFINITY from getMaxScore, so its function clause is never non-essential. The loop and both of its callers are in 10.6.0 as well.

Why it looks unintended

#
  • A negative value is accepted input that scores 0: MIGRATE.md says "FunctionScoreQuery maps negative values to 0", and Lucene's own testTruncateNegativeScores covers it.
  • Scorer#getMaxScore must bound the scores; here it is -1 for a score of 0.
  • 10.6.0 returns the hits (its bound is +∞); the discussion of #16431 covered decreasing functions such as -x, never a negative bound or the clamp.
The full argument395 words
  • Accepted input. MIGRATE.md:1471-1478 on main (:1458-1465 on branch_11x), "Scorer must produce positive scores (LUCENE-7996)": "As a side-effect of this change, negative boosts are now rejected and FunctionScoreQuery maps negative values to 0." CHANGES.txt:6833-6834 on main (:6803-6804 on branch_11x), 8.0.0: "FunctionQuery and FunctionScoreQuery now return a score of 0 when the function produces a negative value." The score() comment and the explain() branch say the same (FunctionScoreQuery.java:250, :191-195). Upstream's testTruncateNegativeScores (TestFunctionScoreQuery.java:236-253) scores a negative long through fromLongField under MatchAllDocsQuery, which is the function clause of the tests here. What LUCENE-7996 forbids is a negative score. This clause scores the document 0; only its bound is negative.
  • Limits of that argument. The class javadoc says nothing about negative values: it neither forbids them nor documents the clamp. Upstream's test uses a field without skip index, so it never reaches the bound (the test class has no indexedField at all). That limits what upstream's tests cover, not what input is accepted.
  • Bounds bound scores. Scorer#getMaxScore returns "the maximum score that documents between the last target ... and upTo" can have (Scorer.java:75-79). CheckHits.java:760 (:766 on branch_11x) and AssertingScorer.java:130 assert score <= maxScore. MaxScoreBulkScorer.java:454-455 asserts "All clauses are essential if minCompetitiveScore is equal to zero", which holds only if no bound is negative. In the minimal repro that assertion is never reached (the window is skipped before any clause is scored, so assertions on stay silent); in the one-document test with -1 it is reached and throws; in the tests of shape 2 the minimum competitive score is already positive when it is reached, so it passes and the search does not return; the test of shape 3 runs under BlockMaxConjunctionBulkScorer, which has no assert statement.
  • History. Before #16431 the bound was +Infinity, useless for pruning but always safe; 10.0.0, 10.5.2 and 10.6.0 return the hit. In the discussion of #16431 uschindler noted that functions like 1/x or -x are not increasing, which led to Monotonicity.DECREASING (direction, not sign); no comment mentions the clamp or a negative bound. The follow-up #16697 fixed bounds that covered the wrong range, so an unsafe bound of this feature has been treated as a defect.
  • Upstream's own tests see neither consequence. TestFunctionScoreQuery (17 tests) and TestDoubleValuesSource (11) pass on branch_11x and main as they are.
The devil's-advocate check186 words

The strongest case: in #9044 (LUCENE-7996), in a comment of 2018-10-14, Adrien Grand wrote that "FunctionScoreQuery is probably the easiest way to mistakenly create a scorer that returns negative scores, in which case one should sort by the function rather than using this function to compute scores". So a negative-valued function could be called a user mistake. A second argument: a negative DoubleValues bound is correct for the values.

Why it fails: the project had already chosen to truncate negative values to 0 ten months earlier. Alan Woodward proposed in the same issue on 2017-11-30 to "document that functions that return negative values will be truncated to 0 for scoring purposes", and a8a63464e7d (Adrien Grand, 2017-12-06) added the clamp, the migration note and testTruncateNegativeScores. All three are still there. The remark bears on how many users meet the bug. It does not make it acceptable that a top-k search drops a hit that an exhaustive search returns, or does not return. The second argument is true and not in dispute; it only places the defect in FunctionScoreQuery, whose bound must cover its clamped scores.

// score() maps negative values to 0, so the bound must not be negative
return Math.max(0f, innerMaxScore * valueMaxScore * boost);

Trade-offs

  • Both consequences of the negative bound end. With a bound of 0 the function clause is no longer left out at a minimum competitive score of 0, a negative value no longer pulls the summed bounds down, and no caller hands the loop a negative remaining bound through this query.
  • Clamp after the multiply. innerMaxScore and boost are never negative (negative boosts are rejected), so for a finite inner bound this equals clamping the value bound first. For a positive boost and a negative value bound it also covers a wrapped query whose bound is +∞: 0.0, where the unchanged code gives -∞. (With a boost of 0 or a value bound of 0 an infinite inner bound gives NaN, with the clamp as without it.)
  • Pruning kept. Non-negative bounds are unchanged; DoubleValues bounds stay as they are, since they are correct for the values.
  • NaN. Math.max(0f, NaN) is NaN, so a NaN bound from a NaN stored double (the separate LFV-189) passes through unchanged.
  • Cost. One Math.max per bound computation; no benchmark was run.
  • Scope. It fixes the negative bound only. The loop in ScorerUtil.minRequiredScore (LFV-1016) stays for other queries: that finding's own test still does not return with assertions off on both builds with this clamp in. The other findings of the same change (LFV-211, LFV-189, LFV-214, LFV-221) need their own changes.

Downstream note

#

An application that lets its users write the values of a skip-indexed field that it adds to scores through FunctionScoreQuery hands them the trigger: one negative value in a block of its own can drop other documents from the top hits or, in the shapes above, keep a search from returning.

How it was found

#

While modelling the new bound, the analysis noticed that score() clamps negative values to 0 and the bound does not. SMT solvers (Z3, cvc5) found a block whose bound lies below the clamped score; a JUnit test confirmed the missing hit. The search that does not return was recorded in November, from runs on 10.6.0 and the 11.0 branch.

The method in full245 words

Method: semi-formal (a hypothesis witnessed by a solver and confirmed by execution).

  • Model. The scorer's score and bound were written in floating-point SMT (QF_FP) with the question whether a score can exceed its bound. Z3 4.12.2 and cvc5 1.4.2 both answered SAT for a block whose maximum value is negative: the bound lies below the clamped score 0. A Java replay confirmed the witness.
  • Differential. A randomized comparison of the default top-k search with an exhaustive search over several hundred random indexes found mismatches for blocks of negative values. They disappear with the clamp, and none occur without a skip index or for boostByValue and boostByQuery.
  • JUnit. A directed public-API test (5,000 documents) failed on main with assertions on and off and passed on 10.5.2; the minimal repro is that test cut down to one document and one assertion.
  • The search that does not return (November). The record of the loop's own finding (LFV-1016) had named this bound as a way into the loop in October. In November a comparison of the 10.6.0 release with the 11.0 branch on generated indexes and queries gave the one-document test. Follow-up runs asked whether an enabled assertion always ends the search and whether a MUST clause rules it out, and gave the tests at a positive minimum competitive score (two SHOULD function clauses, two MUST function clauses). Each was run again independently, with the shapes written a second time as a separate program, before it was recorded.

You index a numeric doc-values field with a skip index (NumericDocValuesField.indexedField("delta", v)) and search BooleanQuery(SHOULD FunctionScoreQuery(MatchAllDocsQuery, DoubleValuesSource.fromLongField("delta")), SHOULD TermQuery(body:b)) for the top hit, expecting the same hit as an exhaustive search, because Lucene's MIGRATE.md documents that FunctionScoreQuery maps negative values to 0 (LUCENE-7996). Instead, with 5,000 documents where doc 0 has delta 1 and all others have -1000, doc 4999 has body:b and every other document has body:x, TOP_SCORES and the plain IndexSearcher.search(q, 1) return doc 0 (score 1.0) instead of doc 4999. The cause is that the scorer's getMaxScore returns innerMaxScore * valueMaxScore * boost without the clamp at 0 that score() applies, so a block of negative values reports a bound of -1000 for documents that all score 0, and MaxScoreBulkScorer skips windows that hold competitive documents.
