MinHashFilter with hashSetSize >= 2 can drop a kept min hash when a token repeats

With hashSetSize 2 or more, MinHashFilter can drop a kept hash value when a token repeats into a full set, so the signature depends on repeats and order ("b a a" keeps 1 value, "b a" keeps 2). Every release since 6.2.0 is affected; the default hashSetSize 1 is safe.

The bug in 30 seconds

#

MinHashFilter turns a text into a fingerprint for near-duplicate search: per hash it keeps the N lowest hash values of the tokens, usually 5-word shingles. Texts with the same set of shingles should get the same fingerprint.

  1. Run MinHashFilter with 1 hash, 1 bucket and hashSetSize 2: keep the 2 lowest hash values of the tokens. For the three words used here the hashes order as c < a < b.
  2. You expect the 2 lowest values of the set of words, whatever the repeats and the order: "b a a" keeps a and b like "b a", and "c a c b" and "c a b c" keep c and a like "c a b".
  3. You get: "b a a" keeps only a; "c a c b" keeps c and b, the largest hash; "c a b c" keeps only c. No error, the same with assertions on and off.
  4. Why: on a full set, FixedSizeTreeSet.add removes the largest value (pollLast()) before calling TreeSet.add, which does nothing for a value already kept. The repeated c evicts a, and the next new word, b, takes the free slot.
  5. In the javadoc's own setting, 1 hash and keep the 100 lowest values of 5-word shingles, a 150-word cycle (154 words, wrapping around) read twice (304 words) has the same 150 shingles as when read once, but keeps 99 values instead of 100.

Who is affected

#

Applications that run MinHashFilter, or the minHash factory that downstream min_hash filters wrap, with hashSetSize of 2 or more (opt-in; the default 1 is safe), on text where a token or shingle repeats. Only the N-th slot of each (hash, bucket) set can be wrong (missing, or holding a larger value), so similarity estimates shift silently. Every release since 6.2.0.

Mechanism, terms and numbers529 words

MinHashFilter hashes every token (typically 5-word shingles) and keeps, per hash and bucket, the hashSetSize lowest hash values; its javadoc says "You could have 1 hash and keep the 100 lowest values". The kept values live in FixedSizeTreeSet, a TreeSet with a capacity. When that set is full and a value below its largest one arrives, add first removes the largest (pollLast()) and then calls TreeSet.add. If the value is already in the set, because the token repeats, TreeSet.add does nothing: the set has lost its largest value and gained nothing, and the next new value, however large, fills the free slot. Only the N-th slot of a (hash, bucket) set can be wrong: the lowest N-1 values are always kept. No exception; the default hashSetSize of 1 is safe. The code dates from the filter's introduction (6.2.0), and a one-line guard fixes it.

Terms

#
  • Min hash, bottom-k. Each token is hashed to a 128-bit value. With one hash the filter keeps the hashSetSize lowest values (a bottom-k sketch); with several hashes or buckets it keeps that many per hash and bucket. The overlap of two such sets estimates how similar the two texts' token sets are (Jaccard).
  • FixedSizeTreeSet. The package-private TreeSet subclass that holds the kept values of one (hash, bucket), with a capacity of hashSetSize.

The bug

#
  1. On the first incrementToken() the filter reads the whole input and adds every token's hash, repeats included, to the set of its hash and bucket (MinHashFilter.java:159-171, the insert at :168).
  2. FixedSizeTreeSet.add (:333-345): if the set is full and the new value is not below last(), it returns false (:337-338); otherwise it calls pollLast() (:340) and then TreeSet.add (:343).
  3. TreeSet.add leaves the set unchanged when the value is already in it. So a repeat of a kept value below the maximum removes the maximum and adds nothing: the set shrinks by one.
  4. The next new value is added without any check because the set is no longer full, however large it is.
  5. With hashSetSize 1 the only kept value is also the largest, so its repeat compares equal and is rejected at :337: the default is safe.

Exposure and likelihood359 words
  • Who. Users of MinHashFilter or MinHashFilterFactory (SPI name minHash) with hashSetSize >= 2. The javadoc's first example is exactly that: "1 hash and keep the 100 lowest values". hashSetSize is a public constructor and factory parameter, validated only as > 0. Downstream engines wrap the factory as a min_hash token filter and pass hash_set_size through; one of them allows up to 10,000. How many applications use hashSetSize >= 2 is not known.
  • Not affected. The default hashSetSize of 1, which published downstream example configurations also use. With many buckets (the default is 512) a bucket must first hold hashSetSize values before a repeat can do harm, so short documents in bucketed setups are less exposed (a code argument; not measured).
  • Trigger. Ordinary text: a token or shingle that repeats while its (hash, bucket) set is full and whose hash is below that set's largest kept value. No crafted input; deterministic.
  • Size. Only the N-th slot of each (hash, bucket) set can be wrong: the true lowest N-1 values are always kept, and the N-th slot is right, empty or holds a larger value (a code argument, then 1,464,843 exhaustive set sequences and 20,000 random end-to-end inputs). In the javadoc setting that is at most 1 of 100 values; "b a a" loses 1 of 2. With keep 2 and many buckets up to half the values can change: in a constructed worst case (1 hash, 64 buckets, keep 2, plain whitespace tokens) two texts with the same 2,000 words share 64 of 128 values, an overlap of 0.5 where the same word set should give 1.0 (no downstream similarity estimator was run).
  • Effect. The indexed min-hash terms, and every near-duplicate or similarity estimate built on them, depend on how often and in what order shingles occur; a value that is not among the lowest can be indexed. No exception, the same with assertions on and off, and the index is well-formed.
  • Not re-measured. The finder's synthetic-corpus rates (5 to 49 of 50 documents with a wrong signature, depending on the configuration) were not re-checked by a verifier, and how often real text hits the trigger was not measured.

Why it is a bug, not intended

#
  • The javadoc says the filter can "keep the 100 lowest values"; repeating a token cannot change those.
  • FixedSizeTreeSet overrides TreeSet.add, which must leave the set unchanged for an element already present; it evicts the largest instead.
  • "c a c b" and "c a b c" (same tokens, same counts) give different signatures, which no set or multiset bottom-k allows.
The full argument268 words
  • Javadoc (MinHashFilter.java:38-40): "The number of hashes used and the number of minimum values for each hash can be set. You could have 1 hash and keep the 100 lowest values or 100 hashes and keep the lowest one for each." @param hashSetSize (:112): "the no. of min hashes to keep".
  • TreeSet.add (JDK): "If this set already contains the element, the call leaves the set unchanged and returns false." FixedSizeTreeSet returns false too, although it has removed the largest element, contrary to that inherited contract (the filter's own call sites ignore the return value).
  • Design discussion of LUCENE-6968 (now #8025), by one of the credited patch authors: "Let's start with 5 word shingles, one hash and keep the minimum 100 hash values. ... For a 100 word doc where all the shingles/words are the same we get one hash.", and the min set of one hash is "a random sample without replacement": bottom-k over distinct values. Nobody discusses a repeat arriving at a full set.
  • Downstream documentation of the same parameters states frequency independence, for example: "it doesn't matter how many times a document contains a certain token, only that if it contains it or not."
  • Tests. The upstream TestMinHashFilter feeds FixedSizeTreeSet only distinct values (testCollisions, testHashNotRepeated), and its bookkeeping assumes that add() == false removed nothing; testTokenStream3 (hashSetSize 10, two distinct shingles) never fills a set. No test asserts repeat-dependent output.
  • History. No CHANGES or MIGRATE entry, javadoc caveat, issue or list thread documents a distinct-input precondition; the add body is unchanged in behaviour since the filter was added.
The devil's-advocate check164 words

The strongest case for "intended": the javadoc never literally says "distinct"; FixedSizeTreeSet is package-private, so its TreeSet contract is internal; the default hashSetSize of 1 is immune and the published examples use 1; MinHash is an approximation anyway.

Why it fails: the output is not a function of the token multiset either. "c a c b" and "c a b c" have the same tokens with the same counts and give {c, b} and {c}; neither a set nor a multiset bottom-k reading lets the output depend on token order or keeps b, which is above the true 2 lowest of either. The design discussion and the downstream documentation state set semantics, and a safe default limits reach, not validity. The verifiers, the cross-model reviews and the adjudication found the intended-behaviour argument weak or unconvincing. Verdict: not intended, a defect. In the issue, cite the javadoc together with the TreeSet.add contract and the design comment, and say up front that hashSetSize 1 is unaffected.

Trade-offs

  • One extra O(log hashSetSize) lookup, only when the set is full and the value is below its largest. With the default hashSetSize 1 that is a lookup in a one-element set, made only for a new value below the kept one (a repeat or a larger value is rejected by the first comparison). Negligible either way.
  • Signatures can change (to the correct ones) for documents whose repeated tokens left an incorrect final set, once re-analysed (a later token can repair the damage: "c b c a" ends correct, "c a c b" does not); until such documents are re-analysed or reindexed, a field mixes old and new signatures across segments. Worth a CHANGES line.

Insert first, trim after (classpath runner only) (validated by the checks)

#

Reject a value that is not below the largest of a full set; otherwise TreeSet.add first, and only when it added something, pollLast() if the set is over capacity.

public boolean add(final E toAdd) {
  if (capacity <= size() && toAdd.compareTo(last()) >= 0) {
    return false;
  }
  if (super.add(toAdd) == false) {
    return false; // already kept: the set is unchanged
  }
  if (size() > capacity) {
    pollLast();
  }
  return true;
}

Trade-offs

Avoids the extra lookup, but is a larger diff of an internal class, and the set briefly holds capacity + 1 elements.

How it was found

#

Bounded-exhaustive translation validation: an executable model of the javadoc (the lowest distinct hashes per hash and bucket) was compared with the real filter on 524,256 small inputs. 92,628 differed, all with hashSetSize >= 2 and a repeated token; a model of the add rule matched the filter on every input, which pinned the cause.

The method in full166 words

Method: bounded-exhaustive translation validation (the hunt's "semi-formal" tier), a hunt unit (analysis-common filters), 2026-10-26.

  • The finder wrote an executable model of the class javadoc: per hash and bucket, the exact hashSetSize lowest distinct values, with its own murmur3 checked against a known-answer vector and 20,000 random inputs, and the filter's bucketing, rotation and term encoding mapped line by line.

Bug record

LFV-649, snapshot of 2026-10-29

Registry title
MinHashFilter with hashSetSize >= 2 drops one of the kept lowest hash values when a token repeats while its (hash, bucket) set is full, so the min-hash signature depends on token repeats and order instead of only on the token set ('b a a' keeps 1 of 2 values; 'c a c b' and 'c a b c' give different signatures)
Area
analysis-common / minhash (MinHashFilter.FixedSizeTreeSet bottom-k set; MinHashFilterFactory 'minHash')
Priority
Low, rank 327: Needs the opt-in hashSetSize of 2 or more, and at most one value per set is wrong.
Impact class
silent wrong results
Impact note
Hits applications that run MinHashFilter (directly, or through MinHashFilterFactory 'minHash', which downstream min_hash token filters wrap) with hashSetSize >= 2, such as the javadoc's own '1 hash and keep the 100 lowest values': whenever a token or shingle repeats while its (hash, bucket) set is full and its hash is below that set's largest kept value, the set loses that largest value and may later admit a larger one, so near-duplicate and similarity estimates computed from the indexed signature are skewed (at most one wrong value per set: 1 of 100 for a text read twice in the javadoc setting, up to 1 of 2 per bucket with keep 2); ordinary text, no scale, deterministic, with -ea and -da, no exception; the default hashSetSize = 1 is not affected.
Summary
You analyse 'b a a' with MinHashFilter(hashCount 1, bucketCount 1, hashSetSize 2) and expect the same two min hashes as for 'b a', because the filter keeps 'the N lowest values' of the tokens' hashes (MinHashFilter.java:38-40; hashSetSize is 'the no. of min hashes to keep') and the lowest values of a token set do not change when a token repeats. Instead, FixedSizeTreeSet.add removes the full set's largest value (pollLast) before TreeSet.add finds that the repeated value is already there, so 'b a a' gives one value; a later new token, however large its hash, then fills the free slot ('c a c b' keeps the hashes of c and b, not the true lowest two, c and a), and the same tokens in another order ('c a b c') give yet another signature.
