HTMLStripCharFilter leaves six-hex-digit character references such as &#x0000E9; undecoded: its length check counts the 'x'

The finding in 30 seconds

#

Numeric character references in HTML

#
  1. HTML can write any character as a numeric reference: &#233; (decimal) and &#xE9; (hex) both mean é. Leading zeros are allowed, so &#x000E9; and &#x0000E9; mean é too.
  2. HTMLStripCharFilter decodes these references before the tokenizer runs, so b&#x61;d reaches the index as the word bad.
  3. The largest code point, U+10FFFF, needs six hex digits or seven decimal digits. The scanner is meant to cap references at exactly these lengths; longer ones are left as text on purpose.

The finding, step by step

#
  1. Strip HTML with HTMLStripCharFilter (or the htmlStrip char filter) in front of StandardTokenizer, and index b&#x000061;d: the word "bad" with its a written as a zero-padded six-hex-digit reference, which is valid HTML.
  2. You expect the token bad, as you get for b&#x61;d (2 hex digits), b&#x00061;d (5 hex digits) and b&#0000097;d (7 decimal digits). The scanner's comment allows hex references of "max 6 hex chars".
  3. Instead the reference stays literal and is indexed as three tokens: b, x000061, d. A TermQuery for bad finds the 2-digit, 5-digit and decimal versions (3 hits) but not this one.
  4. Why: the hex rule matches the x plus the digits, and the check matchLength <= 6 counts the x. Six digits make 7, so the reference is passed through unchanged. The decimal rule beside it counts only digits and is right.
  5. Only references with exactly six hex digits are hit: zero-padded ones such as &#x0000E9; and plane-16 characters (U+100000 to U+10FFFD). Offsets stay correct and nothing throws.

Who is affected

#

Applications that strip HTML with HTMLStripCharFilter or the htmlStrip factory, at default settings. Only hex references with exactly six digits are hit: zero-padded ones (&#x0000E9;) and plane-16 private-use characters (U+100000 to U+10FFFD). A word containing one is indexed in pieces and not found by its decoded form. Rare; no error, no index damage.

Mechanism, terms and numbers405 words

HTMLStripCharFilter turns numeric character references back into the characters they name before the text is tokenized. Its hexadecimal rule is meant to accept up to six hex digits, enough for the largest code point 10FFFF, as the comment next to the check says ("10FFFF: max 6 hex chars"). But the length it checks is the length of the whole match, x included, so only five digits get through.

A reference with exactly six hex digits, such as the zero-padded &#x0000E9; (é) or the plane-16 &#x100000; and &#x10FFFF;, is therefore emitted unchanged, as literal text, while &#x000E9;, &#0000233; and &#1114111; are decoded. With StandardTokenizer, b&#x000061;d is indexed as b, x000061, d, and a TermQuery for bad misses the document. It has been this way since the JFlex scanner shipped in 3.6.0. The fix is one character in the grammar plus regenerating the scanner.

The scanner rule

#

After &# the scanner enters the state NUMERIC_CHARACTER (HTMLStripCharFilter.jflex:351). Its hex rule (:494-527):

[xX] [0-9A-Fa-f]+ {                       // the match is the x plus every digit
  int matchLength = yylength();             // :495, counts the x
  ...
  if (matchLength <= 6) { // 10FFFF: max 6 hex chars        :497
    String hexCharRef
        = new String(zzBuffer, zzStartRead + 1, matchLength - 1);   // skips the x
    ...
    if (codePoint <= 0x10FFFF) { ... decode ... }            :506
    else { pass through as text }                            :517-521
  } else { pass through as text }                            :522-526

Six hex digits make matchLength 7, so the reference takes the last branch and its original characters are emitted unchanged. The decimal rule (:528-531, [0-9]+) matches digits only and checks matchLength <= 7 // 0x10FFFF = 1114111: max 7 decimal chars, which is right. The generated scanner has the same two checks (HTMLStripCharFilter.java:6557 and :6327).

End to end (StandardTokenizer + LowerCaseFilter): b&#x000061;d gives the tokens b (offsets 0-1), x000061 (3-10) and d (11-12); TermQuery(body:bad) finds the 2-digit, 5-digit and 7-decimal-digit documents (3 hits) and misses the six-digit one; CheckIndex is clean. a &#x10FFFF; z gives a, x10ffff, z.

Exposure and likelihood148 words
  • Trigger. A hex reference with exactly six hex digits whose value is at most 0x10FFFF: a plane-16 character (U+100000 to U+10FFFD, Supplementary Private Use Area-B; U+10FFFE and U+10FFFF are noncharacters) or a smaller code point zero-padded to six digits (HTML allows leading zeros). Reached through new HTMLStripCharFilter(reader) or the factory (SPI name htmlStrip), with no option to set.
  • Effect. The reference is indexed as text, for example the token x000061 or x10ffff, so a word that contains it is not found by its decoded form. The text around it is tokenized normally, offsets point at the original text, nothing throws, CheckIndex is clean.
  • Not affected. Every code point below U+100000 in its shortest hex form (at most five digits), decimal references of up to seven digits, and named entities.
  • Likelihood. Rare: the recorded searches found no public report of it since it shipped in 2012.

Why it looks unintended

#
  • The check's comment says "10FFFF: max 6 hex chars", and the next line skips the x to parse the digits; the check counts it.
  • The decimal rule beside it counts only digits: &#0000233; decodes, &#x0000E9; does not.
  • With five digits the hex rule's own out-of-range branch is dead code; no checked document states a five-digit limit.
The full argument190 words
  • The stated limit. HTMLStripCharFilter.jflex:497: "10FFFF: max 6 hex chars": six hex digits, the length of the largest code point. The implementation admits five.
  • The code knows the x is in the match. :498-499 parses new String(zzBuffer, zzStartRead + 1, matchLength - 1).
  • The sibling is right. :531 admits seven decimal digits for 1114111; &#1114111; and &#0000233; decode, &#x10FFFF; and &#x0000E9; do not (executed).
  • Dead code. With at most five digits the largest value is 0xFFFFF, so the codePoint <= 0x10FFFF else-branch (:517-521) is unreachable.
  • No checked document states five digits. Not the class javadoc (:31), the factory or the package docs, no CHANGES or MIGRATE entry, and not the LUCENE-3690 discussion (#4764). Upstream tests assert that numeric references decode (TestHTMLStripCharFilter.java:115-119 testEntities, :601-634 testUTF16Surrogates) but never use more than four hex digits.
  • Partly a regression, in lineage only. The Solr class that LUCENE-3690 replaced read up to 10 hex digits and decoded &#x0000e9; (executed on the Solr 3.5.0 jar). It is not a regression between Lucene releases: Lucene 3.5.0 had no Lucene HTMLStripCharFilter. Neither version ever decoded six-digit supplementary references correctly.
The devil's-advocate check102 words

The strongest case for "intended": the class only "attempts to strip out HTML constructs" (HTMLStripCharFilter.jflex:31); it does not follow HTML5's numeric-reference rules anyway (values above 0x10FFFF and long zero padding stay literal), so a digit cap is an implementation choice; and six-digit references are uncommon. A cross-model reviewer rated this "moderate".

Why it fails: the cap's intended value is written next to the check, and the code misses its own stated limit by one. That is an implementation slip, not a choice about HTML5 conformance, and "uncommon" is about impact, not intent. Every reviewer and the adjudication rejected the argument.

Suggested fix

#

Recommended Allow seven characters: the x plus six digits (validated)

Count the x: change matchLength <= 6 to <= 7 in HTMLStripCharFilter.jflex and regenerate the scanner (one generated line changes). The repro, the 64 charfilter tests and the whole analysis-common module pass. Six-digit references then decode like their shorter spellings (old documents keep their tokens until reindexed); seven-digit hex and out-of-range values stay literal.

Trade-offs

  • A visible analysis change for every hex reference with exactly six digits, not only the headline examples. Each now decodes the way its shorter spelling already does (executed): &#x000000; becomes U+0000 like &#x0;; the zero-padded surrogate &#x00D800; becomes U+FFFD like &#xD800; (HTMLStripCharFilter.jflex:509-511; the paired-surrogate rules at :355-489 match only adjacent unpadded pairs); an unterminated &#x000061 at the end of the input becomes a like &#x00061.
  • The tokens of such text change, so documents indexed before the fix keep the old tokens until they are reindexed. Worth a CHANGES entry under Bug Fixes.
  • Unchanged: seven or more hex digits and eight or more decimal digits stay literal (the stated limits); values above 0x10FFFF such as &#x110000; stay literal through the range check.

Accept any zero padding (larger, not recommended, not run)

#

Skip leading zeros, then cap at six significant hex digits (and seven decimal), as HTML5 decoders do.

Trade-offs

Also decodes &#x0000061;, but changes the stated limits for seven or more digits: a behaviour change beyond this bug. Dropping the cap alone is not an option: Integer.parseInt throws for values of 0x80000000 and above, and its catch block only asserts (HTMLStripCharFilter.jflex:501-505): with assertions off codePoint stays 0 and the reference would become U+0000.

How it was found

#

Found by reading the hex branch of the scanner's grammar while building a fuzzer for HTMLStripCharFilter; the fuzzer's offset and chunking checks cannot see an undecoded reference. A public-API test then confirmed it on main and on releases back to 3.6.0.

The method in full129 words

Method: non-formal (code reading, then an executed test).

  • Finder. The hunt unit for analysis char filters and stemmers was building a grammar fuzzer for HTMLStripCharFilter whose fragment list includes &#x10FFFF; and &#1114111;. Reading the hex rule showed the check counts the x. The fuzzer's oracles (offset range and order, final offset, chunking independence) reported 0 violations over 2,000,000 documents, because an undecoded reference breaks none of them.
  • Confirmation. A public-API JUnit (3 six-digit cases fail, the five-digit and decimal controls pass) on main with assertions on and off and on 9.12.3, and a main() probe on 9 releases back to 4.0.0.
