IndriAndQuery returns documents that match none of its clauses when a clause is a phrase or doc-values range query

An IndriAndQuery that combines a phrase or doc-values range clause with another clause also returns documents that match neither, such as n=50 for the range n in [1, 10]: IndriDisjunctionScorer never runs the clauses' exact matches() check. Hits and count() are silently wrong in every release since 8.9.0.

The finding in 30 seconds

#

IndriAndQuery should return the documents that match at least one clause. With a phrase or doc-values range clause next to another clause, it also returns documents that only pass that clause's cheap candidate step.

Background: two-phase iteration

#
  1. Some queries are costly to check per document. Their scorer offers a TwoPhaseIterator: a cheap approximation(), a superset of the matches, and matches(), the exact check for the current document.
  2. For a phrase, the approximation is "has all the words" and matches() checks their positions. For a slow doc-values range, the approximation is "has a value" and matches() checks the range.
  3. Code that walks an approximation must call matches() before it counts a document as a hit. The core DisjunctionScorer, which BooleanQuery uses for SHOULD clauses, does.

The finding, step by step

#
  1. Index three documents: doc 0 with the doc-values field n=1, doc 1 with n=50, doc 2 with body=c and no n.
  2. Search IndriAndQuery with two SHOULD clauses, the doc-values range n:[1 TO 10] and the term body:c. You expect docs 0 and 2, which a BooleanQuery with the same clauses returns.
  3. Instead you get docs 0, 1 and 2, and count() says 3: doc 1 (n=50) matches neither clause. All three hits score 0.0. A phrase does the same: on "a b", "b a", "c", "x", the phrase "a b" next to body:c returns "b a" too.
  4. Why: a range or phrase query checks a document in two steps, a cheap candidate step (has a value, has all the words) and the exact matches(). IndriDisjunctionScorer merges the candidate steps of its clauses and never calls matches().
  5. It happens only in segments where two or more clauses have a scorer, so the same document can be a hit in one segment and not in another.

Who is affected

#

Applications that build IndriAndQuery themselves (a public core API that no Lucene parser creates) with a phrase, doc-values range or other two-phase clause next to another clause. Default settings, any index size. Hits and count() are wrong with no error, every hit scores 0.0 (clause types tested), and the answer can change when segments flush or merge.

Mechanism, terms and numbers688 words

IndriAndQuery should return the documents that match at least one of its clauses ("matches documents matching combinations of subqueries", IndriAndQuery.java:22). When two or more clauses have a scorer in a segment, IndriAndWeight scores them with an IndriAndScorer, an IndriDisjunctionScorer (IndriAndWeight.java:47-65). That scorer wraps each clause scorer in a DisiWrapper, whose approximation for a two-phase clause is twoPhaseView.approximation() (DisiWrapper.java:69-73), merges those approximations in a DisjunctionDISIApproximation (IndriDisjunctionScorer.java:36-41) and returns the merge from iterator() (:44-47) without a twoPhaseIterator(). Nobody ever calls a clause's matches(), so every document in a phrase clause's "has all the words" set or a doc-values range's "has a value" set (for a field without a skip index, the default) becomes a hit. In the three-document repro the range n:[1 TO 10] next to body:c returns [0, 1, 2], count() 3, instead of [0, 2]; all hits score 0.0, and no error is raised. A segment where only one clause has a scorer uses that scorer directly and is exact, so the result depends on which documents share a segment. Present since the Indri classes were added (LUCENE-9537, first released in 8.9.0), in every release to 10.6.0 and on main 5adff78bb168.

The mechanism (main 5adff78bb168, lucene/core/src/java/org/apache/lucene/search/)

#
  1. Two-phase clauses. A TwoPhaseIterator's matches() "needs to be checked in order to know whether the returned doc ID actually matches" (TwoPhaseIterator.java:23-27). PhraseScorer returns one (PhraseScorer.java:51-52); so does the slow doc-values range without a skip index (TwoPhaseIterator.asDocIdSetIterator(DocValuesRangeIterator.forRange(...)), lucene/core/src/java/org/apache/lucene/document/SortedNumericDocValuesRangeQuery.java:152-163).
  2. Scorer choice. IndriAndWeight.getScorer collects the non-null clause scorers; a single one is returned as is, two or more are wrapped in new IndriAndScorer(subScorers, ...) (IndriAndWeight.java:47-65), a subclass of IndriDisjunctionScorer (IndriAndScorer.java:26).
  3. The defect. The IndriDisjunctionScorer constructor wraps every clause scorer in new DisiWrapper(scorer, false) (IndriDisjunctionScorer.java:36-40); for a two-phase scorer the wrapper's approximation is twoPhaseView.approximation() (DisiWrapper.java:69-73). It merges them with new DisjunctionDISIApproximation(wrappers, Long.MAX_VALUE) (:41), "a disjunction of the approximations of the provided iterators" (DisjunctionDISIApproximation.java:26-28), and returns that from iterator() (:44-47). It does not override twoPhaseIterator(), so it inherits return null (Scorer.java:58-60).
  4. Nobody filters. A consumer that sees no two-phase view treats iterator() as exact: DefaultBulkScorer uses scorer.iterator() when twoPhaseIterator() is null (Weight.java:236-243). Executed on the repro's index: the query's scorer is an IndriAndScorer, twoPhaseIterator() is null, and iterator() yields [0, 1, 2].
  5. What the core does. DisjunctionScorer builds the same merge but, when any sub-scorer is two-phase, wraps it in a TwoPhase (DisjunctionScorer.java:42-63), returns TwoPhaseIterator.asDocIdSetIterator(twoPhase) from iterator() and exposes it from twoPhaseIterator() (:66-78); its matches() accepts a document only when a sub-scorer without a two-phase view is on it or a two-phase view matches (:118-157).
  6. Scores cannot hide it. IndriAndScorer.scoreDoc adds only children that are IndriScorers (IndriAndScorer.java:47-62); term, phrase and doc-values scorers are not, so the score is 0 (:64-65) for real and false hits alike. That all-zero scoring is a separate, already-discussed issue (#10577); here it only means ranking cannot push the false hits down.
  7. Segment dependence. Because of step 2, a segment where only the two-phase clause has a scorer is exact. Executed with two segments, {n=50} and {n=50}, {body=c}: the first segment uses the range's own scorer and its n=50 document is not returned; the second uses an IndriAndScorer and its identical n=50 document is returned (hits [1, 2]; BooleanQuery gives [2]).

Exposure and likelihood396 words
  • Who is hit. Code that calls new IndriAndQuery(List<BooleanClause>) (public, in org.apache.lucene.search); outside tests only IndriAndQuery.java and IndriAndWeight.java mention the class, so no parser or other Lucene code builds it.
  • Trigger. Two or more clauses with a scorer in the same segment, at least one of them two-phase. Executed with PhraseQuery, SortedNumericDocValuesField.newSlowRangeQuery and NumericDocValuesField.newSlowRangeQuery. By reading, not run, any clause whose scorer returns a TwoPhaseIterator takes the same path, for example MultiPhraseQuery, the SortedNumericDocValuesField and NumericDocValuesField newSlowSetQuery, and the SortedDocValuesField and SortedSetDocValuesField newSlowRangeQuery. The SortedDocValuesField and SortedSetDocValuesField newSlowSetQuery do not get this far: they return a rewrite-only TermInSetQuery, and since IndriAndWeight never rewrites its clauses (IndriAndWeight.java:41-44) they throw UnsupportedOperationException, a separate defect (LFV-299). All runs use SHOULD clauses only; IndriAndWeight ignores the clauses' Occur, a separate defect (LFV-871).
  • Default vs opt-in. A plain IndexWriterConfig and IndexSearcher, no skip index; assertions on or off; opt-in only in choosing IndriAndQuery. The runs used the test framework's randomized codec (seed DEADBEEF: Asserting(Lucene104)); by reading, the path depends on the scorers, not on the codec.
  • Size. Every document in the two-phase clause's approximation becomes a hit (in each segment where another clause also has a scorer): for a doc-values range on a field without a skip index (the default), every document with any value in the field; for a phrase, every document that has all its words (from the mechanism). With a skip index the candidates are instead every document of each skip block whose value range overlaps the query, documents with no value included (SkipBlockRangeIterator.java:67-87; by reading, not run). count() agrees with the wrong hits, so totals and paging are wrong too.
  • Silent and unstable. No exception; all hits score 0.0 (with the clause types tested); whether a document is returned depends on which documents share its segment, so results can change after a flush or merge.
  • Bounded. An enclosing BooleanQuery FILTER still restricts every hit, deleted documents never appear, and every extra hit lies in some clause's approximation (an executed bounds probe, 4 of 4 checks pass with assertions on and off). The index is never changed.
  • Why tests missed it. Upstream TestIndriAndQuery uses only plain TermQuery clauses: both tests call the two-argument tq() (TestIndriAndQuery.java:113-114, :130-131); a boosted tq(f, t, b) helper exists (:151-154) but is never called.

Why it looks unintended

#
  • Scorer#iterator is "a DocIdSetIterator over matching documents"; only a TwoPhaseIterator may over-match, and its matches() "needs to be checked".
  • IndriAndQuery "matches documents matching combinations of subqueries"; upstream tests expect exactly the clauses' matches, and the core DisjunctionScorer calls matches().
  • A hit with n=50 for the range [1, 10], and hits that change with segment layout, break those contracts.
The full argument141 words
  • Contracts. Scorer.java:33-34: "Return a DocIdSetIterator over matching documents". TwoPhaseIterator.java:23-27: after the approximation moves, matches() "needs to be checked in order to know whether the returned doc ID actually matches". IndriAndQuery.java:22: "A Query that matches documents matching combinations of subqueries".
  • Tests. TestIndriAndQuery.testSimpleQuery1 asserts "2 docs should match" for [george, washington], testSimpleQuery2 "all docs should match" (TestIndriAndQuery.java:111-144).
  • The author's description. "We iterate through all documents that that [sic] have a posting for at least one of the search terms" (cammiemw, lucene-solr#2097 r555482275, 2021-01-12). On #10577 (2020-09-22) Cameron VandenBerg, the feature's author, wrote: "For the IndriDisjuctionScorer, I was using Lucene's DisjunctionScorer as an example for implementing the docID function."
  • The core counterpart confirms matches (DisjunctionScorer.java:42-78, :118-157).
  • Precedent. #7477 (LUCENE-6418, "SpanNot sometimes forgets to call matches() on excl approximation") was fixed as a bug in 2015.
The devil's-advocate check242 words

Strongest case for "misuse". The Indri code was designed for term clauses and nested IndriAndQuery clauses only: the PR's first javadoc read "combinations of {@link TermQuery}s or other IndriAndQuerys"; mikemccand asked on the introducing PR "it looks like we are only supporting TermQuery and other IndriAndQuery clauses ... If so, should we check/enforce this?" (lucene-solr#2097 r532221029, 2020-11-29); jpountz later proposed on #11194 that IndriAnd and IndriOr "only accept instances of IndriQuery as opposed to Query". Read that way, a phrase or range clause is outside the design.

Why it fails. The day after that review comment, the PR commit 8e784de47c27 ("Addressed first set of git pull request comments", 2020-11-30) changed the javadoc to "combinations of subqueries", and no check was added. The reviewer pinged once more on 2020-12-14 and the thread has no reply. The public constructor accepts any BooleanClause (IndriAndQuery.java:25-27), no javadoc, CHANGES or MIGRATE text warns about two-phase clauses, and the restriction proposed on #11194 was never made. Even under an Indri "candidate set" reading, returning n=50 for the range [1, 10] breaks the Scorer#iterator and TwoPhaseIterator contracts above, and the same document is a hit in one segment and not in another. Whether maintainers prefer the scorer fix or a restrictive one (rejecting such clauses, or a move to the sandbox) is their call. Verdict: a defect. Not security: the application builds the query, it is a disjunction rather than a restriction, and enclosing filters still apply.

Suggested fix

#

Recommended Expose a TwoPhaseIterator that confirms a clause match

Give IndriDisjunctionScorer a TwoPhaseIterator when any clause is two-phase, as DisjunctionScorer does: matches() accepts the document if some clause on it has no two-phase view or its view matches, and iterator() returns TwoPhaseIterator.asDocIdSetIterator(twoPhase). With it the repro passes and the whole core org.apache.lucene.search test package passes (216 classes, 2,351 tests, 0 failures).

All options and trade-offs3 options · 662 words

The recommended fix was applied to a scratch worktree of 5adff78bb168 and run through gradle; the other options were not run.

Expose a TwoPhaseIterator that confirms a clause match (validated by the checks) (recommended)

#

In the IndriDisjunctionScorer constructor, note whether any DisiWrapper has a twoPhaseView; if so, build a TwoPhaseIterator over the DisjunctionDISIApproximation whose matches() walks approximation.topList() and returns true at the first wrapper with no two-phase view or whose view matches. iterator() returns TwoPhaseIterator.asDocIdSetIterator(twoPhase) and twoPhaseIterator() returns twoPhase; with no two-phase clause nothing changes. +36/-2 lines in IndriDisjunctionScorer.java.

private final DisjunctionDISIApproximation approximation;
private final TwoPhaseIterator twoPhase; // null when no clause is two-phase

// constructor, after building the approximation:
if (hasTwoPhase) {
  final DisjunctionDISIApproximation approx = this.approximation;
  this.twoPhase =
      new TwoPhaseIterator(approx) {
        @Override
        public boolean matches() throws IOException {
          for (DisiWrapper w = approx.topList(); w != null; w = w.next) {
            if (w.twoPhaseView == null || w.twoPhaseView.matches()) {
              return true;
            }
          }
          return false;
        }

        @Override
        public float matchCost() {
          float cost = 0;
          for (DisiWrapper w : wrappers) {
            cost += w.matchCost;
          }
          return cost;
        }
      };
} else {
  this.twoPhase = null;
}

@Override
public DocIdSetIterator iterator() {
  return twoPhase == null ? approximation : TwoPhaseIterator.asDocIdSetIterator(twoPhase);
}

@Override
public TwoPhaseIterator twoPhaseIterator() {
  return twoPhase;
}

Trade-offs

  • The same check the core DisjunctionScorer.TwoPhase makes; queries with term clauses only are unchanged. When some clause is two-phase, the new matches() runs on every document of the merged approximation and stops at the first wrapper on it with no two-phase view or a matching view. Unlike DisjunctionScorer.TwoPhase, which checks the exact clauses first (DisjunctionScorer.java:123-143), it may call a two-phase clause's matches() on a document an exact clause already matches; same result, but a reviewer may want that order.
  • matchCost is a plain sum of the clauses' costs, a rough upper bound; DisjunctionScorer uses a cost-weighted average (DisjunctionScorer.java:48-61), which a reviewer may prefer.
  • Scoring caveat: IndriAndScorer.scoreDoc treats an IndriScorer child as present when its docID() equals the document (IndriAndScorer.java:49-58), so a nested IndriAndQuery child standing on an unconfirmed candidate would still be scored as present. With today's all-zero scores that changes nothing; the next option closes it.
  • The open, stale PR #463 would need the same change if it is ever revived: it changes only the superclass of IndriDisjunctionScorer (+2/-2) and adds an IndriOrScorer that extends it.

Also confirm nested Indri children when scoring

#

On top of the first option, have IndriAndScorer.scoreDoc treat a child with a two-phase view as present only when its match on this document was confirmed. Not run.

Trade-offs

Makes scores of nested Indri queries exact once Indri scoring is non-zero. More code: the confirmation must be remembered, because matches() may be called at most once per document (TwoPhaseIterator.java:96-101). No visible effect while all Indri scores are 0.

Reject clause types other than term and Indri queries

#

Validate in the IndriAndQuery constructor that every clause is a (boosted) TermQuery or an IndriQuery, as asked in the 2020 review and proposed on #11194. Not run.

Trade-offs

Stops the wrong hits by refusing phrase and range clauses: it breaks callers that pass them today and takes phrase matching away from Indri queries, while the scorer fix is small. Not recommended.

Downstream note

#

Downstream products are affected only if they build IndriAndQuery with phrase or doc-values clauses; issue searches of Elasticsearch, OpenSearch and Solr for IndriAndQuery found nothing.

How it was found

#

While writing a Z3 model of how IndriAndQuery decides which documents match, reading IndriDisjunctionScorer showed that it never calls matches(). A Z3 query then produced a hit that matches no clause, and a bounded-exhaustive check of the real jar found 119 such hits in 6,708 cases, all gone with the fix.

The method in full156 words

Method: semi-formal. The hypothesis came from code reading while modelling IndriDisjunctionScorer for a Z3 model of IndriAndQuery matching (2026-10-28, main a9779ef3c193). A Z3 query for "a hit that matches none of its clauses" is satisfiable when two or more clause scorers are present in a segment and one is two-phase, and unsatisfiable with a single scorer, with no two-phase clause, and with the fix.

A bounded-exhaustive translation validation of the real core jar then compared the jar with the model: 258 SHOULD-only clause lists over 3 terms and 3 phrases, 13 documents, 2 segment layouts, 6,708 checks, 0 model mismatches; 119 hits matched none of their clauses (92 in one layout, 27 in the other). With the fix applied to the jar's classes, exactly those 119 hits disappeared and no miss appeared. A public-API JUnit (the finder's four-document test) confirmed it on the stock jars; this doc's minimal test is a smaller version of it.

LFV-874, snapshot of 2026-11-05

Registry title
IndriAndQuery returns documents that match none of its clauses when a clause uses two-phase iteration (PhraseQuery, doc-values range queries), because IndriDisjunctionScorer iterates the clauses' approximations and never calls TwoPhaseIterator.matches()
Area
search / IndriAndQuery (IndriDisjunctionScorer iteration over two-phase clauses)
Priority
Medium, rank 64: Since 8.9 the opt-in IndriAndQuery silently returns extra hits when a phrase or doc-values range clause is combined with another clause; that changes hits, where LFV-744 only changes scores.
Impact class
silent wrong results
Impact note
Applications that build an IndriAndQuery (a rarely used core query that no Lucene query parser produces) with two or more clauses that have a scorer in the same segment, at least one of them two-phase (PhraseQuery, MultiPhraseQuery, doc-values range or set queries), get extra hits and an inflated count(): every document in that clause's approximation (all phrase terms present but not the phrase, or any value in the doc-values field) is returned, scoring the same as the real hits, with no error; default codec, IndexWriterConfig and searcher, any index size, -ea and -da, every release since 8.9.0; whether a document is returned depends on which other documents share its segment; the index is untouched.
Summary
You build an IndriAndQuery from SHOULD clauses, for example the phrase "a b" plus the term c, or a doc-values range n in [1, 10] plus the term c, and expect the documents that match at least one clause, as its javadoc ('matches documents matching combinations of subqueries') says. Instead it also returns documents that are only cheap candidates of the phrase or range clause: 'b a' (both terms, no phrase) in the phrase case and the documents with n=50 and n=100 in the range case, and count() agrees with the wrong hits (3 instead of 2, and 4 instead of 2, in the 4-document repro). IndriDisjunctionScorer walks the approximations of its two-phase clauses and never runs their exact matches() check; a segment where only one clause has a scorer is exact, so the same document can be rejected in one segment and returned in another.
