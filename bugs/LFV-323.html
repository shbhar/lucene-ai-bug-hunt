The finding in 30 seconds

#

One line of integer arithmetic: the method adds the modelled array, 16 + n × 4 bytes, as an int, which is wrong once n reaches 536,870,908.

Background: how RamUsageEstimator sizes a collection

#
  1. RamUsageEstimator is Lucene's helper for estimating how many bytes a Java object takes on the heap. Lucene's query cache sizes queries with it, and downstream memory budgets add up its estimates.
  2. For a collection, sizeOfCollection assumes it is backed by an array, like ArrayList: the collection object, plus one array of references (a 16-byte header and 4 bytes per element with compressed references; 24 and 8 without), plus each element's own estimate.
  3. A Java int holds at most 2,147,483,647. Arithmetic past that silently wraps around to negative numbers; a long holds up to about 9.2 × 10^18.

The finding, step by step

#
  1. Make a list of 536,870,908 elements, for example Arrays.asList(new Object[536870908]), and ask RamUsageEstimator.sizeOfCollection(list) how many bytes it uses.
  2. You expect at least its backing array: a 16-byte header plus 536,870,908 references of 4 bytes (compressed references, the usual case), 2,147,483,648 bytes, which RamUsageEstimator.shallowSizeOf(array) reports correctly. With the 24-byte list object: 2,147,483,672.
  3. The method adds 16 + 536,870,908 × 4 in an int. The largest int is 2,147,483,647, so 2,147,483,648 wraps to -2,147,483,648; with the 24-byte list object and rounding to 8 bytes you get -2,147,483,616.
  4. One element fewer gives the right 2,147,483,672. From 536,870,908 elements on (268,435,453 with 8-byte references) every estimate is 4 GiB or more too small; with real elements it usually stays positive, for example 40% too small for Integer elements at the threshold.

Who is affected

#

Only code that sizes one collection of 536,870,908 or more elements (2 GiB of references) with this @lucene.internal estimator, typically downstream memory accounting. By default no Lucene code path does (the sandbox CoveringQuery could, with a clause limit raised far above 1024). A budget that sums the estimates under-counts by 4 GiB or more.

Mechanism, terms and numbers793 words

RamUsageEstimator.sizeOfCollection estimates a collection's heap size as the collection object, plus one array of references, plus each element's estimate. It adds the array part as NUM_BYTES_ARRAY_HEADER + collection.size() * NUM_BYTES_OBJECT_REF (RamUsageEstimator.java:307), where both constants and Collection.size() are int, so the sum is computed in 32-bit arithmetic and only then widened to long. From 536,870,908 elements on (2^29 - 4, with 4-byte references and a 16-byte array header; 268,435,453 with 8-byte references and a 24-byte header; both with the default 8-byte object alignment) it wraps. sizeOfCollection(Arrays.asList(new Object[536870908])) returns -2,147,483,616 bytes, while shallowSizeOf of the backing array correctly returns 2,147,483,648.

The estimate is then always too small by a multiple of 4 GiB (with 4-byte references 8 GiB from 1,610,612,732 elements on; up to 16 GiB with 8-byte references), and it is negative only when the elements add little: with Integer elements it is positive but 40% low at the threshold. sizeOfObject on a collection and sizeOfMap on a map with collection values reach the same line. Every other array formula in the class widens to long first. With default settings no Lucene code path sizes a collection that large (the sandbox CoveringQuery would, but only after the application raises the clause limit from 1024 to more than 536,870,907), so in practice only callers of this @lucene.internal helper, typically downstream memory accounting, are affected. It is in every release since 8.2.0 (2019) and on main; the one-line cast (long) collection.size() * NUM_BYTES_OBJECT_REF fixes it and passes Lucene's core tests.

The code

#
private static long sizeOfCollection(Collection<?> collection, int depth, long defSize) {   // RamUsageEstimator.java:298
  if (collection == null) {
    return 0;
  }
  long size = shallowSizeOf(collection);                                                   // :302
  if (depth > MAX_DEPTH) {
    return size;
  }
  // assume array-backed collection and add per-object references                         // :306
  size += NUM_BYTES_ARRAY_HEADER + collection.size() * NUM_BYTES_OBJECT_REF;               // :307, all int
  for (Object o : collection) {
    size += sizeOfObject(o, depth, defSize);
  }
  return alignObjectSize(size);                                                            // :311
}

The same class sizes the same array correctly in shallowSizeOf(Object[]):

return alignObjectSize(
    (long) NUM_BYTES_ARRAY_HEADER + (long) NUM_BYTES_OBJECT_REF * arr.length);             // :512-513

The walk for Arrays.asList(new Object[536870908]), 4-byte references

#
  1. shallowSizeOf(list) = 24 bytes (:302).
  2. :307, in int: 16 + 536,870,908 × 4 = 2,147,483,648. That is one more than Integer.MAX_VALUE, so it wraps to -2,147,483,648, and size = 24 - 2,147,483,648 = -2,147,483,624.
  3. The elements are null and add 0.
  4. alignObjectSize rounds with Java's %, which keeps the sign, so the negative sum moves 8 bytes toward zero: -2,147,483,616.

With 536,870,907 elements the sum is 2,147,483,644, which fits, and the result is the correct 2,147,483,672. Adding one null element drops the estimate by 4,294,967,288 bytes (2^32 - 8).

What bounds it

#
  • Threshold. (2^31 - 1 - header) / ref + 1: 536,870,908 = 2^29 - 4 with 4-byte references and a 16-byte header, 268,435,453 with 8-byte references and a 24-byte header (:129, :133; both with the default 8-byte object alignment). The header addition overflows first. For these two layouts a Z3 bit-vector model of the line found these minimal sizes and proved that no smaller size overflows.
  • Size of the error. Always a multiple of 2^32 bytes before alignment (2^32 - 8 after it where the result is negative). With 4-byte references it is 4 GiB from 536,870,908 to 1,610,612,731 elements and 8 GiB from 1,610,612,732 on (nCopies(Integer.MAX_VALUE, null) gives 40 bytes instead of 8,589,934,632). With 8-byte references it reaches 16 GiB (48 bytes instead of 17,179,869,232 at Integer.MAX_VALUE).
  • Negative only sometimes. With null elements (4-byte references) the result is negative in two ranges: from 536,870,908 to 1,073,741,810 elements, and again from 1,610,612,732 to 2,147,483,634, where the int sum wraps a second time. In between it is positive but 4 GiB low (it climbs from 0 back to 2,147,483,672); above the second range it is 0 to 40 bytes, 8 GiB low. With real elements it is usually positive but 4 GiB low: about 3% of the total with the default 256-byte size for unknown objects, 40-50% with shared Integer elements at the threshold (20-25% further up). A "not negative" check alone misses most cases.
  • Entry points. Both public sizeOfCollection overloads (:285, :294); sizeOfObject on a Collection (:393, :403, the Collection case at :434); a collection value in a map passed to the public sizeOfMap (:247, :256, via :275). The hppc *ObjectHashMap.ramBytesUsed methods do not reach it: they pass the iteration cursor, not the value, to sizeOfObject (IntObjectHashMap.java:446-447).
  • Not affected. sizeOfMap's own sums (:269-277), shallowSizeOf(Object[]) (:511-514) and shallowSizeOfArray (:561-574) add in long. Of the file's 16 multiplications (on 15 lines), :307 is the only one done in int.
Exposure and likelihood359 words
  • Who. Code that passes one huge collection to sizeOfCollection, sizeOfObject or (as a map value) sizeOfMap. RamUsageEstimator is public and @lucene.internal; downstream projects use it for memory accounting. A read-only code search found sizeOfCollection call sites in 26 files of one downstream search engine, among them a query circuit breaker (read, not run).
  • Not Lucene itself, by default. No in-tree production code calls sizeOfCollection directly. The only in-tree caller that passes a Collection is the sandbox CoveringQuery (sizeOfObject(queries, ...), CoveringQuery.java:82-85), whose constructor rejects more than IndexSearcher.getMaxClauseCount() sub-queries (:70-72; default 1024). The limit is the application's to set: IndexSearcher.setMaxClauseCount(int) is public and accepts any value of at least 1, so an application that raises it above 536,870,907 and passes that many sub-queries does reach the line. No query parser builds a CoveringQuery. The other callers pass arrays, maps whose values are not collections, or scalars.
  • Default vs opt-in. No setting is involved, apart from that clause limit. The threshold depends only on the JVM's object layout: the reference size and the array header, which the class derives from the reference size and the object alignment. With the default 8-byte alignment it is 536,870,908 with compressed references and 268,435,453 with 8-byte references (-XX:-UseCompressedOops, or heaps too large for compressed references). A non-default -XX:ObjectAlignmentInBytes can change the header (for example 32 bytes with 8-byte references and 16-byte alignment, which gives 268,435,452, by arithmetic); the test computes n from the runtime constants.
  • Scale. Either threshold is 2 GiB of references in one collection.
  • Effect. A memory budget that sums these estimates under-counts by 4 GiB (at most 8 or 16 GiB) and trips later than intended. Nothing in Lucene uses the value to decide matching, filtering, deletions or what is written. With compressed references, elements of 28 bytes or more push the correct estimate to about 16 GiB before the threshold, so a budget of half the heap trips first (executed probe).
  • Likelihood: contrived (a judgement). It takes one collection with 2 GiB of references, sized by this estimator, and no default Lucene path builds or sizes one; accidental triggering looks unlikely.

Minimal repro

#

One JUnit test, public API only, deterministic and heap-free: Collections.nCopies makes a virtual list of 536,870,908 nulls (the size is computed from the JVM's constants), and the test asserts that its estimated size is not negative. It runs in about 5 s.

Expected
sizeOfCollection(Collections.nCopies(536870908, null)) returns a size of at least 0 bytes (2,147,483,672 with the fix).
Observed
AssertionError: sizeOfCollection of 536870908 elements: expected >= 0, got -2147483616, with assertions on and off.

All files of this repro: repro/LFV-323/

More files, environment, full output302 words
  • Why nCopies. It is a virtual list, so the test needs no heap beyond the default; the method still iterates the 536,870,908 nulls (about 5 s). The stronger, contract-based form compares sizeOfCollection(Arrays.asList(backing)) with shallowSizeOf(backing) (-2,147,483,616 against 2,147,483,648), but it needs a 2 GiB array (-Xmx4g). The virtual list holds no backing array, so for nCopies the "expected" size is the method's own array model, not memory the list retains; the Arrays.asList comparison is the stronger demonstration.
  • Smallest input. n is computed from the runtime constants, so it is the smallest failing size on any JVM layout: with the default 8-byte alignment 536,870,908 with compressed references, 268,435,453 with -XX:-UseCompressedOops (then: expected >= 0, got -2147483608). 536,870,907 gives the correct 2,147,483,672.
  • As the regression test: this same test, for example as a method of TestRamUsageEstimator. It passes with the fix.

Why it looks unintended

#
  • The javadoc promises "the size in bytes of a Collection object, including sizes of its values", with no size limit.
  • The class's other array formulas widen to long first, a rule adopted in 2012 for arrays above 2 GB.
  • A negative or 4 GiB-low byte count is no "best effort" estimate: the method gets its own formula wrong.
The full argument175 words
  • The contract. Both public overloads: "Returns the size in bytes of a Collection object, including sizes of its values" (RamUsageEstimator.java:281, :290), with no size limit. The comment above the line says the method models an array-backed collection (:306). 536,870,908 is a legal array length; the finder's test allocated it.
  • The class gets the same array right elsewhere. shallowSizeOf(Object[]) (:511-514) and shallowSizeOfArray (:561-574) cast to long before multiplying. Those casts came in with LUCENE-3867 (#4940, 2012), because the array formulas "can overflow if arrays are greater than 2 GB".
  • History shows no intent. The line came in with the LUCENE-8855 follow-up 7989a863faad "Fix some size estimates and relax test assertions to work under different JVMs." (2019), which replaced the constant NUM_BYTES_ARRAY_HEADER * 2 with the element-count term. Neither the commit nor the LUCENE-8855 discussion (#9898) mentions a size limit.
  • Tests. The only collection test, TestRamUsageEstimator.testCollection (:165-181), uses a 102-element list and accepts a 10% error (:174). No test or javadoc sets a size limit.
The devil's-advocate check195 words

The intended-behaviour checker built the strongest case for "not a bug": RamUsageEstimator is @lucene.internal; its class javadoc says the measurements "may be slightly wrong" and sizeOfObject is a "Best effort attempt"; the array-backed model is itself a heuristic; no Lucene code reaches the size; and with the default 256-byte element size the error is only about 3%.

Why it fails: @lucene.internal is about API stability ("might change in incompatible ways in the next release"), not a waiver for wrong results, and the methods are public and documented without a size limit. "May be slightly wrong" is the class javadoc's caveat for a non-OpenJDK/Oracle-based JVM, that is, for layout assumptions, and "Best effort attempt" describes sizing objects of undetermined type, which fall back to a default size; neither covers wraparound. Here the method gets its own array formula wrong, on HotSpot, by a multiple of 2^32. A negative byte count is never a valid estimate, and with shared Integer elements the error is 40-50% at the threshold, outside the 10% that testCollection accepts. What the argument does establish: priority is low, and "no Lucene code reaches the size" holds only with the default clause limit.

Suggested fix

#

Recommended A. Cast the element count to long

Widen before multiplying: NUM_BYTES_ARRAY_HEADER + (long) collection.size() * NUM_BYTES_OBJECT_REF, as the class's other array formulas already do. Results below the threshold do not change. Validated: the test passes, and so do the closest suites and all of :lucene:core:test.

     // assume array-backed collection and add per-object references
-    size += NUM_BYTES_ARRAY_HEADER + collection.size() * NUM_BYTES_OBJECT_REF;
+    size += NUM_BYTES_ARRAY_HEADER + (long) collection.size() * NUM_BYTES_OBJECT_REF;
All options and trade-offs3 options · 347 words

Three options; option A was applied in a scratch worktree of main 645d4fe14a20 and run against the minimal test, the closest suites, all core tests and core's static checks.

A. Cast the element count to long (validated by the checks) (recommended)

#

One line in sizeOfCollection (RamUsageEstimator.java:307). (long) collection.size() * NUM_BYTES_OBJECT_REF is at most (2^31 - 1) × 8, far inside long, and the header is then added in long. Below the threshold the int expression was exact, so no existing estimate moves.

     // assume array-backed collection and add per-object references
-    size += NUM_BYTES_ARRAY_HEADER + collection.size() * NUM_BYTES_OBJECT_REF;
+    size += NUM_BYTES_ARRAY_HEADER + (long) collection.size() * NUM_BYTES_OBJECT_REF;

Trade-offs

None found: sizeOfCollection is not on a search hot path, and one widening costs nothing next to the per-element loop.

What the checks validated

  • The minimal test passes with assertions on and off (gradle, scratch worktree of 645d4fe14a20; also standalone).
  • Closest suites, seed DEADBEEF: TestRamUsageEstimator, the minimal test, the 15 hppc collection and map test classes and TestLRUQueryCache, 482 tests (4 skipped), 0 failures; sandbox TestCoveringQuery, 5 tests (2 skipped), 0 failures.
  • All of :lucene:core:test passes (random seed, 8,898 tests, 321 skipped, 0 failures, the minimal test included).
  • :lucene:core:check -x test passes (formatting, ecj lint, forbidden APIs, license checks).
  • Earlier, on main ea57360912ed: the finder's 3 tests, an independent verifier's 4 tests (with 4-byte and 8-byte references) and a boundary check at every size pass with the same cast.

B. Mirror shallowSizeOf(Object[])

#

size += alignObjectSize((long) NUM_BYTES_ARRAY_HEADER + (long) NUM_BYTES_OBJECT_REF * collection.size()); also aligns the modelled array on its own, as a real array is.

Trade-offs

More faithful, but with 4-byte references it can raise the estimate of a collection with an odd number of elements by up to 8 bytes: a behaviour change beyond the bug. Not validated.

C. Clamp the result or throw on overflow

#

Clamp a negative estimate, or use Math.multiplyExact / Math.addExact.

Trade-offs

Not recommended: a clamp misses the more common positive-but-4 GiB-low case, and an exception from an estimator breaks callers that only want a number. Not validated.

Downstream note

#

Downstream memory accounting, such as a cache or a circuit breaker, that sizes a collection of 536,870,908 or more elements with this estimator under-counts it by 4 GiB or more and so trips later than intended.

How it was found

#

Semi-formal. While modelling RamUsageEstimator, an AI tool listed the file's 16 multiplications and found only this one computed in int. A Z3 bit-vector model of the line for the default layouts gave the smallest overflowing sizes and proved that no smaller one overflows; a JUnit test on the stock build then reproduced it.

The method in full142 words
  • The hunt unit covered numeric, string and version utilities; the finder was modelling RamUsageEstimator for a no-throw property.
  • Its inventory of the file's 16 multiplications (on 15 lines) showed :307 as the only one evaluated in int; the others multiply in long.
  • A Z3 32-bit bit-vector model of NUM_BYTES_ARRAY_HEADER + n * NUM_BYTES_OBJECT_REF gave the minimal overflowing n: 536,870,908 for 4-byte references and a 16-byte header, 268,435,453 for 8-byte references and a 24-byte header; below each, the expression is exact (unsat). Both sizes are legal array lengths.
  • A public-API JUnit test on the stock main build then failed: Arrays.asList(new Object[536870908]) sized at -2,147,483,616 bytes against 2,147,483,648 for its backing array. Independent verifiers reproduced it with their own tests, corrected the wording (the threshold is 2^29 - 4; the result is not always negative) and found no sign that it is intended.

RamUsageEstimator.sizeOfCollection adds the assumed backing-array bytes in int arithmetic, so a collection of 536,870,908 or more elements (268,435,453 with 8-byte references) gets a size estimate that is a multiple of 4 GiB too low, and negative when the elements add little
Area
util / RamUsageEstimator
Priority
Low, rank 1062: RamUsageEstimator.sizeOfCollection overflows only for collections of 536M+ elements and has no Lucene caller.
Impact class
minor
Impact note
Only code that passes one Collection of 536,870,908 or more elements (268,435,453 with 8-byte references, that is at least 2 GiB of references) to the @lucene.internal RamUsageEstimator.sizeOfCollection or sizeOfObject (directly, or as a value inside sizeOfMap or an hppc *ObjectHashMap) gets an estimate that is 4 GiB too low at the threshold (up to 8 GiB, or 16 GiB with 8-byte references, near Integer.MAX_VALUE), negative only when the elements add little; no Lucene code path reaches it (the only in-tree caller that passes a Collection is the sandbox CoveringQuery, capped by the default clause limit of 1024), so it matters only to downstream memory accounting; any configuration, released since 8.2.0.
Summary
You ask RamUsageEstimator.sizeOfCollection (or sizeOfObject) for the size of a very large list, for example Arrays.asList(new Object[536870908]). You expect a size in bytes that is at least the 2,147,483,648 bytes of its backing array, which shallowSizeOf(Object[]) reports correctly. Instead the method adds the array header and the per-element references in int arithmetic, which wraps, so it returns -2,147,483,616; in general the estimate is too low by a multiple of 2^32 bytes from 536,870,908 elements on (268,435,453 with 8-byte references), and it is negative only when the elements' own sizes add little.
