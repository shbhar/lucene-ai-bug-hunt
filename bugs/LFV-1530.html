Flexible StandardQueryParser turns a one-sided range such as [abc TO *] into a closed range when the analyzer's normalization of the empty string is not empty (7.0.0 to 10.6.0, branch_11x and main)

A narrow case: the opt-in flexible StandardQueryParser with an analyzer that normalizes the empty string to a term (a textual sort key or marker). [abc TO *] silently becomes the closed range [collatedabc TO collated], which matches the wrong documents (none in every executed case where that term sorts before every indexed term).

The finding in 30 seconds

#

The analyzer must turn the empty string into a term. Among the stock analyzers the java.text CollationKeyAnalyzer does ([a TO *] on a field that holds b: 0 documents instead of 1), a pairing a comment at the same site already limits for another reason, its binary terms: "because we call utf8ToString, this will only work with the default TermToBytesRefAttribute".

Background: three pieces

#
  1. The flexible parser turns the query text into a tree of nodes, passes the tree through a fixed list of processors, and a builder turns the result into a Query. A range has two bound nodes, each holding a text.
  2. Analyzer.normalize(field, text) turns one term, such as a range bound, into the form it has in the index, without tokenizing: lower-casing, folding or, for a collation analyzer, a sort key.
  3. An open bound is written *. The classic parser carries it as null. The flexible parser carries it as an empty text, and its builder reads an empty text as "open".

The finding, step by step

#
  1. Parse queries with the flexible parser, new StandardQueryParser(analyzer), and an analyzer that writes collated + term as text, when indexing and in normalize (the shape of the mock collation analyzer in Lucene's own query-parser tests). It normalizes abc to collatedabc and the empty string to collated.
  2. Parse the one-sided range [abc TO *] on field. You expect field:[collatedabc TO *]: the parser's javadoc documents {2.5 TO *] as a "one-sided range", and the classic QueryParser builds exactly this query from the same text with the same analyzer.
  3. You get field:[collatedabc TO collated], a closed range, with no error. On three documents abb, abc and xyz it matches 0 documents; the classic parser's query matches 2.
  4. Why: inside the parser the open bound is an empty text. A later step passes both bound texts through Analyzer.normalize, the empty one too. The empty text becomes collated, and only an empty text counts as an open bound when the query is built.
  5. With most analyzers the empty string stays empty and nothing shows: none of the 55 stock analyzers with a public no-argument constructor triggers it. The classic QueryParser, [* TO *] and a range on a field with a PointsConfig are not affected. An open lower bound is closed the same way; its hits were right in the executed cases where the term of the empty string sorts before every indexed term.

Who is affected

#

Only applications that use the flexible StandardQueryParser with an analyzer that normalizes the empty string to a non-empty term: a sort key, a prefix or a marker written as text, or the stock java.text CollationKeyAnalyzer. There a one-sided term range is built closed (the exceptions are under "What is not affected"); where that term sorts before every indexed term, an open upper bound matches nothing, so it would be noticed quickly there.

Mechanism, terms and numbers1,745 words

Small. It needs two things at once: the flexible StandardQueryParser (org.apache.lucene.queryparser.flexible.standard; its subclass PrecedenceQueryParser behaves the same), which is opt-in in the sense that an application has to choose it, and an analyzer whose Analyzer.normalize turns the empty string into a non-empty term. The parser documents one-sided ranges such as [abc TO *]. Inside it the open bound is an empty text (OpenRangeQueryNodeProcessor.java:44-57, lines at main 9965d34e3c77). A later step, TermRangeQueryNodeProcessor, passes both bound texts through Analyzer.normalize like real bounds (TermRangeQueryNodeProcessor.java:138-141), and the builder reads only an empty text as an open bound (TermRangeQueryNodeBuilder.java:45-51). With most analyzers the empty string stays empty and nothing shows. With an analyzer whose normalization of the empty string is not empty, the open bound becomes a real term and the range a closed range: field:[collatedabc TO collated] instead of field:[collatedabc TO *], with no error. It matches the wrong documents: none in every executed case where the analyzer's term for the empty string sorts before every indexed term, as a prefix or the java.text collation key of the empty string did in the runs. The classic QueryParser builds the open range from the same text with the same analyzer: it normalizes a bound only when it is not open (QueryParserBase.java:547-557).

Such analyzers are unusual: an application analyzer that writes a sort key, a prefix or a marker as text in normalize, or, among the stock analyzer classes, the java.text CollationKeyAnalyzer ([a TO *] on a field that holds b returns 0 documents instead of 1); a CustomAnalyzer can also be configured into one. A comment at the same code site already limits that stock pairing for another reason, because that analyzer's terms are binary: "because we call utf8ToString, this will only work with the default TermToBytesRefAttribute" (TermRangeQueryNodeProcessor.java:136-137). None of the 55 stock analyzers with a public no-argument constructor triggers it; the classic QueryParser, [* TO *] and a range on a field with a PointsConfig are not affected. In the executed cases where the term of the empty string sorts before every indexed term, the range with the open upper bound, used as an exclusion, excludes nothing, while an open lower bound, which is closed the same way, kept its hits. Where that term sorts after every indexed term (a marker written after the term, run) it is the other way round: the open upper bound kept its hits and the open lower bound matched nothing; with one more document above the marker the open upper bound lost that document. In an affected setup every one-sided term range is built closed from the first query (the exceptions are listed under what is not affected), and in every case that was run in which the analyzer's term for the empty string sorts before or after all the indexed terms, one of the two directions then matched nothing, so it would be noticed quickly there. Update 2026-11-17: that term can also sort between the indexed terms or be one of them, and then a one-sided range of either direction can return a part of the right documents (the 10.6.0 release, branch_11x 89e68e0f3a50 and main 596ef11ddf96, with assertions on and off): with a key padded on the right to eight characters with ~ and the values abd, zebra and émile, field<=émile returned 1 of the 3 documents and [abc TO *] 2 of 3, and used as an exclusion that range left out only those 2; with a key padded on the left with 0 and the values 0, 5, 42 and 1000, [0 TO *] returned 1 of the 4 documents.

Every release from 7.0.0 to 10.6.0 does it, and so do the builds of branch_11x 9d2b5a15427a and main 9965d34e3c77 that were run: the two normalize calls came with LUCENE-7355 (2016), without the check for the empty text that the date branch of the same method has. On 2026-11-17 the test also failed 1 of 1 on branch_11x 89e68e0f3a50 and on main 596ef11ddf96, with assertions on and off, and passed there with the change below. One small change was run: normalize a bound only when its text is not empty.

Inside the parser an open bound is an empty text. TermRangeQueryNodeProcessor passes both bound texts through Analyzer.normalize and does not check for the empty one. If the analyzer returns a term for the empty string, the builder no longer sees an open bound and builds a closed range.

The code (main 9965d34e3c77; the same three files on branch_11x 9d2b5a15427a and at the 10.6.0 tag)

#
  1. The processors run in a fixed order (StandardQueryNodeProcessorPipeline.java:48-69). OpenRangeQueryNodeProcessor (:53) replaces an unescaped * bound by the empty text (OpenRangeQueryNodeProcessor.java:44-57); a quoted "*" counts as unescaped too (see the trade-offs of the fix).
  2. TermRangeQueryNodeProcessor (:56) reads the two bound texts (TermRangeQueryNodeProcessor.java:97-98) and first tries to parse them as dates, each only when it is not empty (:104, :110). For abc the date parse throws and the catch branch runs (:130-143); it is shown below the list. Both texts are normalized, with no check for the empty one.
  3. TermRangeQueryNodeBuilder turns a bound into null, the open bound, only when its text is empty (TermRangeQueryNodeBuilder.java:45-51). The text is now collated, so the bound is closed.
  4. The classic parser has no marker text: it carries an open bound as null (QueryParser.java:627-645) and normalizes a bound only when it is not null (QueryParserBase.java:547-557).

The stock java.text CollationKeyAnalyzer (root collator, one document b; run)

#

Its normalization of the empty string is the four bytes [0 0 0 0]. [a TO c] counts 1 through both parsers. [a TO *] counts 1 through the classic parser and 0 through the flexible parser, whose upper bound is [0 0 0 0]. [* TO c] counts 1 through both; the flexible parser's lower bound is [0 0 0 0].

Other analyzers and parsers (run on main 9965d34e3c77)

#
  • A marker after the term instead of before it (normalize("") is |k, normalize("abc") is abc|k; documents abb, abc, xyz). [abc TO *] is built closed too, as field:[abc|k TO |k], but |k sorts after these terms, so it counts 2 like the classic parser; with a fourth document ~z it counts 2 where the classic parser counts 3. [* TO abc] becomes field:[|k TO abc|k] and counts 0 instead of 2. *:* -field:[abc TO *] counts 1 through both. So which direction loses its documents depends on where the term of the empty string sorts.
  • No token for the empty string. With an analyzer whose normalize gives no token for the empty string, [abc TO *] does not become a closed range: parse() throws IllegalStateException ("The normalization token stream is expected to produce exactly 1 token, but got 0", Analyzer.java:239-247). Why it looks unintended

#
  • The parser's javadoc documents {2.5 TO *] as a "one-sided range", with no caveat about the analyzer.
  • The classic QueryParser builds field:[collatedabc TO *] from the same text with the same analyzer.
  • The same method leaves an empty bound alone in its date branch, and Lucene's own tests require [a TO *] to stay open.

The devil's-advocate check288 words

The strongest case for "works as designed": the comment two lines above the site says the code "will only work with the default TermToBytesRefAttribute" (TermRangeQueryNodeProcessor.java:136-137), and the author of LUCENE-7355, Adrien Grand, wrote on the issue (2016-06-30): "Other query parsers could be fixed too but it will require more work as they are using String representations for terms rather than binary". The one stock analyzer class that triggers the defect by itself has binary terms. The collation package's examples use the classic parser, and the syntax documentation of the classic parser, which this parser's javadoc links to where it says that it "borrows most of its syntax from the classic query parser", advises in its overview: "Untokenized fields are best added directly to queries, and not through the query parser." (classic/package-info.java:79-95). And it has shipped since 2017 with no report.

Why it fails: the stated limit is about term bytes that do not survive a String. This defect is another mechanism: the empty marker text is normalized at all. It reproduces with an analyzer that keeps the default term attribute, where the comment does not apply, and that analyzer shape is the one Lucene's own test runs through this parser. The classic documentation gives advice, not a limit on open ranges, and Lucene's own test runs a collated closed range through this parser. The date branch of the same method, [* TO *] and the classic parser keep the bound open. What is left of the argument is about weight, not about correctness: an analyzer whose normalization of the empty string is not empty is an unusual thing to write. A maintainer may fairly answer that, and this page says the limit first.

Trade-offs

  • Smallest change. For an analyzer that normalizes the empty string to the empty string, which all 55 stock analyzers with a no-argument constructor do, the query is the same before and after.
  • It does not touch the stated limit. A bound whose normalized bytes are not valid UTF-8 still goes through utf8ToString. That is not part of this finding.
  • It also covers the second face (run): with an analyzer that gives no token for the empty string the one-sided range no longer throws; the bound stays open.
  • It leaves the mirror case as it is (run, the same with the guard and without it): a real bound that the analyzer normalizes to the empty string becomes an open bound. With an analyzer that strips z, [abc TO zzz] gives field:[abc TO *] where the classic parser builds field:[abc TO ], because the builder reads every empty text as open (TermRangeQueryNodeBuilder.java:45-51; the node model's javadoc names null as the open bound, AbstractRangeQueryNode.java:124-125).
  • It leaves the quoted star as it is (run): a quoted star is an open bound in this parser. [abc TO "*"] gives field:[collatedabc TO *] with the guard (field:[collatedabc TO collated] without it) where the classic parser builds field:[collatedabc TO collated*]; Lucene's own test pins that reading with a question in its comment (TestStandardQP.java:116-123). So the classic parser is the reference for the bare star, which is all this page uses it for.
  • Not benchmarked. Two length checks per range, at parse time.

Downstream note

#

Used as an exclusion (for example -field:[c TO *]), the closed range excluded nothing in the runs where the term of the empty string sorts before the indexed terms, so the query returns documents it should leave out; that matters only to an application that writes a restriction of its own as such a clause through the flexible parser with such an analyzer.

How it was found

#

Semi-formal: a differential, then code reading. Range queries of several forms were run through the classic and the flexible parser with collation-key analyzers and compared with the collator's own order. Through the flexible parser the two forms with an open upper bound returned 0 documents. The cause was read in TermRangeQueryNodeProcessor and confirmed with a default-attribute analyzer.

The method in full194 words

Method: semi-formal (a differential witnessed by running, then located by reading; a strict reading that counts a differential over generated queries as testing would call it non-formal). No model-checking, SMT or proof tool was involved.

  • Signal. The callers of Analyzer.normalize were being compared: the same range forms through the classic and the flexible parser, against the order the collator itself gives. With the java.text CollationKeyAnalyzer on the unchanged code, [c TO *] returned 0 documents where 10 were expected and {b TO *} 0 where 12 were expected; the closed forms were right.
  • Reading. The cause was read in TermRangeQueryNodeProcessor: the empty text of the open bound is normalized like a real bound.
  • Confirmation without binary terms. An analyzer that keeps the default term attribute and writes collated + term showed the same closed bound, so the cause is not the binary term bytes of the collation analyzer. The case was then reduced to one assertion on the built query.
  • A related finding. This defect showed while the range forms of the earlier finding LFV-1053 (ICUCollationKeyAnalyzer and Analyzer.normalize) were run through both parsers; LFV-1053 has another cause and its own fix.
