Classic and flexible query parsers: a tab, line break or ideographic space touching a range bound becomes part of the bound

In the classic and flexible query parsers, a tab, line break or full-width space (U+3000) that touches a range bound becomes part of the bound: date:[<LF>20200101 TO 20201231<LF>] silently matches 4 dates instead of 3, and date:[20200101<TAB>TO<TAB>20201231] fails to parse. Default settings, every release since 1.3-rc1.

The bug in 30 seconds

#

Lucene's classic and flexible query parsers separate clauses at a tab, a line break or a full-width space (U+3000) just as at a space, but not next to a range bound. The token for a bound stops only at a plain space, ] or }, so such a character becomes part of the bound: the parse fails, or the bounds change silently.

Background: how the parser reads a range

#
  1. The query parser's lexer cuts the text into tokens. After [ or { it switches to a Range state with its own token rules, until ] or }.
  2. In the Range state a bound is one RANGE_GOOP token: a run of any characters except a plain space, ] and }. TO and quoted bounds are their own tokens.
  3. Whitespace is a SKIP rule: matched and thrown away. When two rules match, the lexer keeps the longest match; on a tie, the rule declared first.

The bug, step by step

#
  1. Index five dates as StringFields: 20191231, 20200101, 20200615, 20201231, 20210101. Type a range over three lines, date:[ / 20200101 TO 20201231 / ], and parse it with the classic QueryParser or StandardQueryParser and StandardAnalyzer.
  2. You expect the 3 hits of date:[20200101 TO 20201231]: both grammars declare tab, LF, CR and U+3000 as whitespace, and skip whitespace inside ranges too.
  3. You get 4 hits, 20191231 included, and no error. The bound token stops only at a plain space, ] or }, so it swallows each line break: the bounds are <LF>20200101 and 20201231<LF>, and LF sorts before 2.
  4. The same rule breaks other shapes: date:[20200101<TAB>TO<TAB>20201231] throws a ParseException (one bound, no TO); date:{20200101 TO 20201231<TAB>} gives 2 hits instead of 1 (its own excluded endpoint); a leading U+3000, as CJK input methods type it, gives 0 instead of 3.

Who is affected

#

Anyone who parses user-typed query text with the classic QueryParser (or a subclass), StandardQueryParser or PrecedenceQueryParser with default parser settings, on every release since 1.3-rc1. Multi-line or tab-separated ranges and full-width spaces from CJK input methods reach it. A character that touches TO gives a ParseException; one glued to a bound but not to TO silently changes that bound. Rare.

Mechanism, terms and numbers752 words

Both query grammars, the classic QueryParser.jj and the flexible StandardSyntaxParser.jj, declare U+0020, TAB, LF, CR and U+3000 as whitespace and skip it in the Range lexical state as well. But the token for a range bound, RANGE_GOOP, is any run of characters other than U+0020, ] and }. The lexer keeps the longest match, so a TAB, LF, CR or U+3000 that touches a bound is swallowed into it.

Two outcomes follow. When the character separates a bound from TO, the bound and TO become one token and the parse fails: date:[20200101<TAB>TO<TAB>20201231] throws in both parsers. When it is glued to a bound but not to TO (right after [/{, right before ]/}, or between a bound and the space next to TO), the query parses without error and the bound carries the character: over five dates date:[<LF>20200101 TO 20201231<LF>] matches 4 instead of 3, date:{20200101 TO 20201231<TAB>} admits its own exclusive endpoint, date:[<U+3000>20200101 TO 20201231] matches nothing, and date:[20200101<LF> TO 20201231], a value pasted with a trailing newline, matches 2 instead of 3. It affects the classic parser and its subclasses, StandardQueryParser and PrecedenceQueryParser with default parser settings, and every release since the TO syntax arrived in 1.3-rc1. The fix adds the four characters to the exclusion list in both grammars and regenerates the token managers.

Terms

#
  • Grammar whitespace: <#_WHITESPACE: ( " " | "\t" | "\n" | "\r" | "\u3000") > (QueryParser.jj:187; the same at StandardSyntaxParser.jj:135). Outside ranges these five characters are also excluded from terms (_TERM_START_CHAR, QueryParser.jj:183-185), so there they always separate clauses: upstream testTabNewlineCarriageReturn and testCJK assert it.
  • Range state: after [/{ the lexer uses the rules RANGE_TO (TO), RANGEIN_END (]), RANGEEX_END (}), RANGE_QUOTED and RANGE_GOOP (QueryParser.jj:221-227; StandardSyntaxParser.jj:195-201), and the whitespace SKIP rule <DEFAULT, Range> SKIP : { < <_WHITESPACE>> } (QueryParser.jj:191-193; <DEFAULT, Range, Function> at StandardSyntaxParser.jj:139-141).
  • Range rule: bound, TO, bound, closing bracket (QueryParser.jj:343-347; StandardSyntaxParser.jj:855-859).

The bug

#
  1. RANGE_GOOP is (~[ " ", "]", "}" ])+ (QueryParser.jj:226, StandardSyntaxParser.jj:200): it excludes only U+0020 of the five whitespace characters.
  2. At a TAB that starts a token and is followed by a letter or digit, SKIP matches 1 character and RANGE_GOOP matches more, so the TAB joins the bound. SKIP wins only a tie, when the character starts a token and is followed by U+0020, ], } or the end of the input. Inside a bound there is no token start: RANGE_GOOP runs on through the character, so one glued to the end of a bound is swallowed whatever follows it (20200101<LF> TO gives the bound 20200101<LF>).
  3. Loud: in [20200101<TAB>TO<TAB>20201231] the whole inside is one RANGE_GOOP, the parser meets ] where it needs TO, and throws (Was expecting: "TO" in the classic parser, INVALID_SYNTAX_CANNOT_PARSE in the flexible one).
  4. Silent: a character glued to a bound but not to TO (right after [/{, right before ]/}, or between a bound and the space next to TO) stays in the bound text. The classic parser passes it to newRangeQuery, where Analyzer.normalize (QueryParserBase.java:550, :556) only lowercases for StandardAnalyzer; the flexible parser builds its bound nodes from the token text the same way (StandardSyntaxParser.jj:870-873). The result is a TermRangeQuery whose bound contains the character. The open-bound check "*".equals(goop1.image) (QueryParser.jj:354) also fails, so [<LF>* TO b] searches from the literal term <LF>*.

Exposure and likelihood462 words
  • Who is exposed. Applications that parse query text with the classic QueryParser or its subclasses MultiFieldQueryParser, ComplexPhraseQueryParser and ExtendableQueryParser, with StandardQueryParser, or with PrecedenceQueryParser (which extends it), with default parser settings (the caller supplies the analyzer; the repro passes StandardAnalyzer, and the defect is in the lexer, before any analysis). Executed for QueryParser, MultiFieldQueryParser, StandardQueryParser and PrecedenceQueryParser; the other two inherit the classic grammar. Only these two grammars have a range syntax: the surround parser (its grammar has no Range state) and SimpleQueryParser (no range operator) are not affected.
  • Inputs that reach it. A range typed over several lines or with tabs in a query text area; a value with a trailing newline or tab pasted between the brackets; Windows line endings (<CR><LF> breaks even indented input); the full-width space U+3000 that CJK input methods type, the case LUCENE-1528 added U+3000 for; generated query strings built from templates.
  • Loud vs silent. A character that touches TO makes TO part of a bound token and the parse fails: a ParseException for a range whose parts are separated by one of these characters, and quoting the bounds does not help. A character glued to a bound but not to TO silently changes that bound (extra hits, an exclusive endpoint admitted, or no hits at all): right after [/{, right before ]/}, a value pasted with a trailing newline (date:[20200101<LF> TO 20201231]: 2 hits instead of 3) or a tab typed after TO (date:[20200101 TO <TAB>20201231]: 0 instead of 3). A character with a space or bracket on both sides is skipped.
  • Scale. One query string reproduces it; no setting, index size or concurrency is involved, and assertions on or off behave the same.
  • Setup after lexing. The hit counts are for StringField terms and StandardAnalyzer, whose normalize only lowercases; an analyzer whose normalization strips or maps these characters would hide part of the silent outcome (not run). Both parsers first try to read each bound as a date in their locale, but with no date resolution configured (the default, as in the repro) DateTools.dateToString throws on the null resolution and both keep the bound text, so the random test locale cannot change the results; with a date resolution set, a bound the locale's date format reads as a date is rewritten first (not run).
  • How likely. Rare: it needs one of these characters inside the brackets of a range, the parse fails whenever one touches TO, and the searches (see Prior reports) found no public report in over 20 years of releases.
  • Downstream. Solr's fork of the classic grammar has the same RANGE_GOOP line and Range-state SKIP (read on apache/solr main by the finder).

Why it is a bug, not intended

#
  • The grammar declares tab, LF, CR and U+3000 as whitespace and skips it inside ranges (QueryParser.jj:187-193); the bound token lets that rule fire only at a token start before a space or bracket.
  • Upstream tests treat all five characters as one class (testTabNewlineCarriageReturn, testCJK); no test pins the range behaviour.
  • The 2002 author described ranges as "using whitespace as delimiters".
The full argument313 words
  • The grammar's own rules. _WHITESPACE lists U+0020, TAB, LF, CR and U+3000 and is skipped in the Range state (QueryParser.jj:187, :191-193; StandardSyntaxParser.jj:135, :139-141). Because RANGE_GOOP swallows the other four, that SKIP fires for them only in a tie, so the same character is skipped or kept depending on its neighbours: date:[<TAB> 20200101 ... gives the lower bound 20200101, date:[<TAB>20200101 ... gives <TAB>20200101. No design note, test or discussion found explains this distinction.
  • Tests. testTabNewlineCarriageReturn (QueryParserTestBase.java:896, TestQPHelper.java:937) asserts that "+weltbank\n+worlbank", "+weltbank\r\n+worlbank" and similar equal "+weltbank +worlbank"; testCJK (QueryParserTestBase.java:250-255, TestQPHelper.java:324-329) that "term\u3000term\u3000term" equals the space form. No test has a range with a raw TAB, LF, CR or U+3000; with the fix all 30 upstream queryparser suites pass.
  • History. The 2002 commit that added the TO syntax also extended the whitespace SKIP, then " " and TAB, to the new range states, and defined a bound token that excludes only " ". Later the same day (about 17 hours after the commit), its author wrote on dev@: "right now, we're using whitespace as delimiters in the range -- which means that dates like 2002-01-01 1:35 PM are no good unless enclosed in quotes". The 2004 change (LUCENE-93) "treats \n and \r characters in query strings the same way that \t and " " are treated"; LUCENE-1528 (2009) added U+3000 for CJK text. Neither touched the bound token. The LUCENE-1528 review asked how to avoid "defining the whitespace chars in two places" and missed this third copy.
  • Committer remark. In the merged test PR #13323, dweiss wrote that range terms "are parsed differently compared to normal tokens. This is strange but I bet there was a reason for it - now long forgotten. I think, logically, it should accept the same term notation that is used elsewhere" (said about escapes).
The devil's-advocate check239 words

The strongest case for "intended" (built by the devil's-advocate verifier; the cross-model reviews rated it weak, the cross-model fact check of this doc moderate): the delimiter has always been written " TO " with ASCII spaces (the 2002 commit message, the LUCENE-7821 CHANGES entry, the test comment // " TO " is required between range endpoints at QueryParserTestBase.java:637); the user docs show only space-separated ranges; the package docs call the parser "designed for human-entered text, not for program-generated text" and say date ranges "are better added directly through the query API"; the behaviour is over 20 years old with no report found; and today a raw TAB inside an unquoted bound (k:[a<TAB>b TO c]) parses, which the fix would break.

Why it fails: " TO " is about the keyword being required and delimited (LUCENE-7821 was about ranges without TO and never discusses the kind of whitespace). The docs' silence is filled by the grammar's own declarations and the tests. "Human-entered text" argues for the fix: people press Enter in a text area, and CJK input methods type U+3000. Age shows the case was never exercised, not that it was chosen. The raw TAB inside an unquoted bound is the real compatibility question: no doc, test or design note mentions it, the 2002 author named quoting for a date containing spaces, and quoting keeps working with the fix; maintainers should weigh it against consistent Range-state whitespace.

Suggested fix

#

Recommended Add TAB, LF, CR and U+3000 to the RANGE_GOOP exclusions and regenerate

Exclude the grammar's other whitespace from the bound token in both grammars, (~[ " ", "\t", "\n", "\r", "\u3000", "]", "}" ])+, and regenerate the token managers. The repro and all 539 queryparser tests pass. An unquoted bound with a raw tab inside (k:[a<TAB>b TO c]) then needs quotes, so target main with a CHANGES entry.

-| <RANGE_GOOP:   (~[ " ", "]", "}" ])+ >
+| <RANGE_GOOP:   (~[ " ", "\t", "\n", "\r", "\u3000", "]", "}" ])+ >

Trade-offs

  • An unquoted bound that contains one of the four characters stops parsing: k:[a<TAB>b TO c] gives the bounds a<TAB>b and c today and a ParseException with the fix, while k:["a<TAB>b" TO c] keeps working. The 2002 author described whitespace as the range delimiter and said a date containing spaces needed quotes; propose it for main / 11.0 with a CHANGES entry ("the query parser syntax may change from release to release", classic package-info.java:74-75).
  • A JavaCC character list holds characters only and cannot name _WHITESPACE, so the whitespace list is now written three times per grammar. Add a comment that ties _WHITESPACE, _TERM_START_CHAR and RANGE_GOOP together (the LUCENE-1528 review already worried about two copies), and keep them in step if _WHITESPACE ever grows.
  • Nothing else changes: the rule differs only on the four characters and only in the Range state, so only ranges that contain one of them parse differently; with the fix quoted bounds next to a TAB parse too.

Downstream note

#

Search applications and servers that hand user-typed query text to these parsers inherit the bug (Solr's fork of the classic grammar has the same RANGE_GOOP line); building range clauses through the query API avoids it.

How it was found

#

A program compared the character lists of both grammars and found that the bound token's exclusions miss four of the five declared whitespace characters. A bounded-exhaustive check of the real generated lexers then showed whitespace inside a token only there, and a public-API JUnit reproduced it.

The method in full206 words

Method: static comparison of the grammars' lexer tables, then bounded-exhaustive checking of the generated token managers (the study's "semi-formal" tier; the finder tagged it formal). A hunt unit, query-parser whitespace tables versus Unicode White_Space, 2026-10-28.

  • Table diff. A custom program (not a solver) extracted the character classes from QueryParser.jj and StandardSyntaxParser.jj and checked set obligations between them. Obligation O3, "the grammar's _WHITESPACE is a subset of the RANGE_GOOP exclusions", was violated for U+0009, U+000A, U+000D and U+3000 in both grammars. The signal came from this leg.
  • Lexer check. All 111,150 inputs of length 1 to 4 over an 18-symbol alphabet, run through the real generated token managers per lexer and lexical state: the grammar's own whitespace ends up inside a token only in the Range state and only in RANGE_GOOP; the DEFAULT state is clean. With the regenerated (fixed) token managers the property holds in all four lexer/state pairs.
  • Parser sweep. A metamorphic sweep (replace a space by each whitespace character and compare the parsed query) found 720 mismatches in 2,358 hard-oracle checks, all in the 10 range templates.
  • Then a public-API JUnit on the stock main jars, followed by independent reproduction, cross-model reviews, a devil's advocate, an adjudication and an audit (see the checks).

History

#

Introduced with the TO range syntax in 2002 (8ab0396cfcc, first released in 1.3-rc1) for TAB; LF and CR joined in 2004 (LUCENE-93), U+3000 and the flexible parser in 2.9.0. A history probe found all 160 releases it ran, 1.3-rc1 to 10.5.2, affected (the 9 without a published jar have the same rules); 1.2 is not.

Versions tested10 rows

Introduced by 8ab0396cfcc (svn r149785, 2002-06-25, "Support for new range query syntax. The delimiter is " TO ", but is optional for backward compatibility with previous syntax."; no issue; CHANGES 1.3 RC1 item 5). It replaced the one-token range, whose inside the analyzer split, with range lexical states, extended the whitespace SKIP to them (whitespace was then " " and TAB) and defined bound tokens that exclude only " ". Widened without touching the bound token by 9ada9671259 (2004, LUCENE-93 / #1171: LF and CR), 13d5245314e (2009, LUCENE-1528 / #2602: U+3000) and 343992fcbb4 (2009, LUCENE-1567 / #2641: the flexible parser, with a copy of the rules). LUCENE-996 (c8c9ee2cb20, 2010) and the 2011 flexible-grammar commit cffd01664bc merged the two bound tokens into today's RANGE_GOOP with the same exclusions. Not fixed upstream.

LFV-845, snapshot of 2026-10-30

Registry title
Classic QueryParser and flexible StandardQueryParser: a TAB, LF, CR or U+3000 next to a range bound inside [..] or {..} becomes part of the bound, because RANGE_GOOP excludes only U+0020 although both grammars declare these characters as whitespace and skip them in the Range state; such ranges fail to parse or, when the character touches a bracket, silently change their bounds
Area
queryparser / classic and flexible standard grammars (Range lexical state, RANGE_GOOP token)
Priority
Low, rank 469: It hits the default classic and flexible parsers in every release, but the input is rare (a TAB, line break or U+3000 inside a range), the usual result is a loud ParseException and bounds change silently only when the character touches a bracket.
Impact class
silent wrong results
Impact note
Applications that parse query text with the classic QueryParser (or MultiFieldQueryParser, ComplexPhraseQueryParser, ExtendableQueryParser), StandardQueryParser or PrecedenceQueryParser in their default configuration are exposed whenever a range is written with a TAB, a line break or a full-width space (U+3000, as typed by CJK input methods) next to a bound: the common outcome is a ParseException for a tab-separated or multi-line range, and the silent outcome (changed bounds: extra hits, an exclusive endpoint admitted, or no hits at all) needs the character directly after '[' / '{' or directly before ']' / '}'; no scale is needed, and every release since 1.3-rc1 is affected [exec].
Summary
You parse 'date:[20200101<TAB>TO<TAB>20201231]' or the multi-line 'date:[<LF>20200101 TO 20201231<LF>]' with the classic or the flexible standard query parser; both grammars declare TAB, LF, CR and U+3000 as whitespace and skip it inside ranges too, so you expect the same query as with spaces. Instead the range-bound token RANGE_GOOP, which excludes only U+0020 and the closing brackets, swallows any of these characters that touches a bound: the first query throws ParseException ('Was expecting: "TO"'), and the second parses without error into a TermRangeQuery whose bounds are '<LF>20200101' and '20201231<LF>', so it also matches 20191231 (4 hits instead of 3). In the same way 'date:{20200101 TO 20201231<TAB>}' admits its own exclusive endpoint, and a leading U+3000 makes the range match nothing.
Introduced
8ab0396cfccdafe51e6b741ea8e35a6491e1aa09 (svn r149785, author Brian Goetz, 'Support for new range query syntax. The delimiter is " TO ", but is optional for backward compatibility with previous syntax.'; no issue or PR; CHANGES.txt 1.3 RC1 item 5): it replaced the one-token range, whose inside the analyzer split, with the RangeIn/RangeEx lexical states, extended the whitespace SKIP rule to them ('<DEFAULT, RangeIn, RangeEx> SKIP', _WHITESPACE then ' ' | TAB) and defined RANGEIN_GOOP (~[' ', ']'])+ and RANGEEX_GOOP (~[' ', '}'])+, which exclude only U+0020, so a TAB next to a bound has been part of the bound since then [exec: commit-level, the grammars of the parent b1b3d33cf77 and of 8ab0396cfcc regenerated with JavaCC 7 in front of the 1.2 jar: parent not affected, 8ab0396cfcc affected for TAB]. Widened without touching the goop rule by 9ada9671259 (2004, LUCENE-93 / #1171, Bugzilla 18847: LF and CR added to _WHITESPACE) [exec: commit-level against its parent cf06b516bc0], 13d5245314e (2009, LUCENE-1528 / #2602: U+3000 added) [read; bracketed by the releases 2.4.1 and 2.9.0, exec] and 343992fcbb4 (2009, LUCENE-1567 / #2641: the flexible parser created with a copy of the same token rules) [read]; c8c9ee2cb20 (LUCENE-996, 2010) and cffd01664bc (2011, flexible grammar) merged the two goop rules into RANGE_GOOP (~[' ', ']', '}'])+ with the same exclusions [read] (2002-06-25 (author date of 8ab0396cfcc, TAB); widened 2004-03-03 (LF, CR), 2009-01-28 (U+3000) and 2009-08-03 (flexible parser))
