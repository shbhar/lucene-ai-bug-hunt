Kuromoji completion: while an input method shows a small tsu plus a pending c, j, f or v (まっｃ while typing maccha), nothing is suggested

With JapaneseCompletionAnalyzer in QUERY mode, what an input method shows while you type maccha for 抹茶 (まっｃ) is romanized maxtuc and suggests nothing, while さっｋ still suggests サッカー. The bundled romaji_map.txt has small-tsu-plus-pending-letter rows for 13 letters but not for c, j, f or v; every release since 9.0.0.

The bug in 30 seconds

#

QUERY mode joins a kana token with the letter the input method is still composing and romanizes the pair from the bundled table romaji_map.txt. For a small tsu plus a pending c, j, f or v the table has no row.

  1. You index 抹茶 (maccha), バッジ (bajji), スタッフ (sutaffu) and サッカー (sakkaa) as suggestions with JapaneseCompletionAnalyzer, and send the text the input method is still composing to a QUERY-mode PrefixCompletionQuery.
  2. Typing m-a-c-c shows まっｃ. You expect 抹茶 to stay suggested, as さっｋ (typing sakk) keeps サッカー: QUERY mode joins まっ + c, and macc is a prefix of 抹茶's indexed maccha.
  3. Instead まっｃ becomes maxtuc and matches nothing; so does まっｃｈ (maxtuch). まｃ one keystroke earlier and まっちゃ two later do suggest 抹茶. ばっｊ (baxtuj) and すたっｆ (sutaxtuf) are the same. No error.
  4. Why: the table's rows for a small tsu plus a pending letter, ッk,kk to ッw,ww, cover 13 letters. Its full small-tsu rows also double c, j, f and v (ッチャ,ttya,ccha,ccya, ッジ,zzi,jji, ッフ,hhu,ffu, ッヴ,vvu). Without a ッc row, ッ falls back to xtu and the letter is appended.

Who is affected

#

Applications using the opt-in JapaneseCompletionAnalyzer or JapaneseCompletionFilter in QUERY mode (search servers expose it as kuromoji_completion) whose front end sends in-progress input-method text. Users who type the Hepburn or wapuro way (cc, jj, ff, vv) lose all suggestions for one or two keystrokes. Kunrei typing and committed kana are unaffected; nothing throws.

Mechanism, terms and numbers663 words

Kuromoji's completion analyzer (JapaneseCompletionAnalyzer, JapaneseCompletionFilter) adds romaji tokens to each Japanese word so an autocomplete can match Latin-letter input. Its QUERY mode is documented as "Input Method aware romanization": when the input method still shows a small tsu plus a pending letter, as in さっｋ while typing sakkaa, it joins the two tokens and romanizes them (sakk), so サッカー stays suggested. The bundled table romaji_map.txt has such rows only for k, g, s, z, t, d, h, b, p, m, y, r and w, although its own full small-tsu rows also double c, j, f and v. So まっｃ (typing maccha), ばっｊ (bajji), すたっｆ (sutaffu) are romanized maxtuc, baxtuj, sutaxtuf and suggest nothing for one or two keystrokes. Every release from 9.0.0 to 10.5.2 and main; the fix is four table rows.

Terms

#
  • Small tsu (っ / ッ): doubles the next consonant. 抹茶 is read マッチャ, ma-ccha.
  • Composition text: a Japanese input method shows what you type before you commit it. Doubling a consonant shows a small tsu plus the still-pending letter: s-a-k-k shows さっｋ, m-a-c-c shows まっｃ. The open-source Mozc input method's romaji table maps kk, cc, jj, ff, vv (and Hepburn tch) this way.
  • QUERY mode: JapaneseCompletionFilter.Mode.QUERY, "Input Method aware romanization. Expected to be used when querying." When a token with a reading (here the kana まっ) is followed by a lowercase-letter token it joins them and romanizes the result: the code comment says "words that are in mid-IME composition are split into two tokens by JapaneseTokenizer; should be recovered when querying ... e.g.: "サッ" + "k" => "サッk"" (JapaneseCompletionFilter.java:180-193). A test asserts サッｋ → sakk.
  • romaji_map.txt: each row maps a key to its romaji; KatakanaRomanizer matches the longest key first; at the first position no key matches it stops and appends the rest of the reading, unchanged, to what it has built so far. Rows :326-338 cover a small tsu plus one pending letter: ッk,kk ッg,gg ッs,ss ッz,zz ッt,tt ッd,dd ッh,hh ッb,bb ッp,pp ッm,mm ッy,yy ッr,rr ッw,ww.

No indexed spelling of 抹茶 starts with maxtuc, so the prefix query matches nothing.

The numbers

#

Typing maccha: まｃ → mac suggests 抹茶; まっｃ → maxtuc and まっｃｈ → maxtuch suggest nothing; まっちゃ → [mattya, maccha, maccya] suggests 抹茶 again. Likewise ばっｊ → baxtuj (バッジ is [bazzi, bajji]), すたっｆ → sutaxtuf (スタッフ is [sutahhu, sutaffu]), じゃっｊ → [zyaxtuj, jaxtuj] (ジャッジ has jajji), きゃっｃ → kyaxtuc (キャッチャー). Kunrei typing keeps it: まっｔ → matt. Half-width まっc behaves the same.

The code follows the table: romanize() equals an independently coded longest-match model of the same table on 59,120,615 inputs (0 mismatches; a shortest-match mutant was caught). A sweep that checked 367,780 simulated composition states of 43,775 synthetic one- and two-unit words found failing tails only after っc, っf, っj, っv (and っh, which belongs to a sibling bug's malformed ッへ row).

Exposure and likelihood277 words
  • Who. Applications that build Japanese autocomplete with JapaneseCompletionAnalyzer or JapaneseCompletionFilter in QUERY mode (also through the analysis SPI as japaneseCompletion; search servers built on Lucene expose it as a kuromoji_completion token filter) and whose front end sends the text the input method is still composing, the use the feature was built for (#11140). Opt-in.
  • What triggers it. Ordinary typing of words with っち/っちゃ, っじ, っふ/っふぁ or っゔ the Hepburn or wapuro way: 抹茶 maccha, キャッチャー kyacchaa, バッジ bajji, ブリッジ burijji, スタッフ sutaffu, バッファ baffa. Hepburn match... also passes through まっｃｈ. How often users type this way was not measured.
  • How long. One keystroke (っｊ, っｆ, っｖ) or two (っｃ, then っｃｈ); the states before and after suggest normally.
  • Not hit. Kunrei typists (tt, zz, hh), kana typed or committed in full, raw romaji queries (not joined to kana) and INDEX-mode tokens of kana readings. Nothing throws and the index is unchanged.
  • After a fix the new rows match only a small tsu directly followed by a Latin letter. QUERY mode builds that by joining tokens; INDEX mode romanizes each token's reading as it is, and a kana-only reading can never match the new keys. The index-side tokens of the 9 probed words are identical with and without the fix. One exception: a user-dictionary reading may contain Latin letters (readings are not checked), and an entry 試験 read アッc is indexed as axtuc on main but acc with the fix. So existing suggest fields need no reindexing unless a user dictionary has readings with a Latin letter after ッ.

Why it is a bug, not intended

#
  • The full small-tsu rows double 17 letters, the partial-input rows only 13; the missing four are exactly c, j, f, v.
  • QUERY mode is "Input Method aware romanization" and joins a pending letter for this very state; a test pins サッｋ → sakk.
  • In the introducing PR's review, jji was added on request, but no ッj partial row.
The full argument299 words
  • The table contradicts itself. Its full small-tsu rows double 17 letters, its partial-input rows cover 13, and the four missing (c, j, f, v) are the letters that no Kunrei-shiki or Nihon-shiki spelling uses (per a reference table of the three systems; modified Hepburn uses all four; the table itself does not label its spellings by system). The javadoc and the table header list "(modified) Hepburn-shiki, Kunrei-shiki (Nihon-shiki) and Wāpuro shiki" as supported (JapaneseCompletionFilter.java:41-42, romaji_map.txt:3).
  • The state is handled on purpose. Mode.QUERY is "Input Method aware romanization" (:77); the join exists for exactly this state (:184-188); TestJapaneseCompletionFilter asserts サッｋ → sakk and TestKatakanaRomanizer asserts コダッk → kodakk.
  • The design goal names it. #11140: "When querying, mid-IME composition strings will be sent to the search systems, and auto-complete systems should handle them (or, it may just ignore such inputs, but it hurts users' experience)."
  • The jj gap arose in review. In PR #297 a reviewer (GitHub johtani) asked: "Should we add jji? I usually use jajji for ジャッジ. What do you think?"; the author (GitHub mocobeta) answered "yes, of course" and added jji/jja/jju/jjo to the full rows (review commit fc90e452474), but no ッj,jj row. The reviewer's own jajji passes through じゃっｊ, which romanizes to [zyaxtuj, jaxtuj] and matches nothing. The c, f and v gaps were already in the PR's first commit, next to full rows with ccha, ffu and vvu.
  • No documented or tested behaviour depends on it. For kana readings, maxtuc, baxtuj, sutaxtuf start an indexed spelling only after a doubled small tsu. The javadoc's only example of an unsupported case is circumflex/macron long vowels; no comment, test, CHANGES or MIGRATE entry mentions the partial rows.
The devil's-advocate check172 words

The strongest case (the intended-behaviour checker and the cross-model review): the javadoc says the filter "does not strictly comply ... but tries to cover possible keystroke supported by various Input Methods" (best effort); the 13 partial rows are all Kunrei-shiki consonants (every one except n, which no full small-tsu row doubles), so they could be a deliberate Kunrei-only set; #11140 allows that a system "may just ignore such inputs"; only k is tested; the suggester classes are @lucene.experimental.

Why it fails: the same table accepts cc, jj, ff, vv in its full rows, so a Kunrei-only rule is not what the table does; jji was added on request without the matching partial row, which reads as an oversight; the "may just ignore" clause describes systems that ignore composition text altogether, while this filter handles it for 13 of the 17 letters; and the defect is in the kuromoji filter's tokens, not in the experimental suggester API. What remains is a labelling question (bug fix or improvement), not intent.

Trade-offs

  • Each new row has one spelling, so it adds no romaji combinations (a separate expansion issue is untouched).
  • For kana readings only query-side tokens change (the new keys contain a Latin letter); the index-side tokens of the 9 probed words are identical with and without the fix, so existing suggest fields should not need reindexing. A user-dictionary reading with a Latin letter after ッ does change (アッc: axtuc before, acc after), so such fields would need reindexing.
  • Where a full row lacks the doubled spelling, this fix alone does not bring the suggestion back: ッチ has only tti (a sibling bug), so マッチ typed macchi still misses at まっｃ (macc against matti). The examples here fail for this root cause alone.
  • A PR could add one assertion per letter to TestKatakanaRomanizer.testRomanizeWithAlphabets (like コダッk → kodakk) and a まっｃ case to TestJapaneseCompletionFilter.testCompletionQuery (like サッｋ).

How it was found

#

Semi-formal. A table consistency check (partial-input rows must cover every letter the full small-tsu rows double) flagged c, f, j and v; a sweep of 367,780 simulated input-method states through the real query-side romanizer failed only after those four letters, plus a っh tail from a sibling bug. A public-API suggester test then reproduced the missing suggestions.

The method in full279 words
  • Table laws. A model of the table's rules; law L2p (partial-input rows ッ<letter> must cover every letter the full ッ rows double) flagged exactly ッc, ッf, ッj, ッv.
  • Translation validation (bounded-exhaustive). Part A: romanize() equals an independent longest-match model of the table on all 1,830,854 inputs of length up to 3 and all 57,289,761 inputs of length 4 over the key katakana (0 mismatches; a shortest-match mutant was caught), so the code agrees with the table on those inputs and the fault is in the data. The same log then ends with an out-of-memory error in a later part that is not used here.
  • Composition sweep. Part C2 took all 43,775 one- and two-unit katakana words (up to 4 kana, no ン) and typed each index-side spelling that a model input method (the open-source Mozc romaji table) composes back to the word (5,643 word/spelling pairs that do not were skipped). Each composition state, romanized by the stock QUERY path, had to stay a prefix of an indexed spelling, checked up to the first failing state of each spelling: 367,780 states. The only failing tails: っc 918, っf 1,993, っj 1,075, っv 1,687 word/spelling pairs, and っh 463 (a sibling bug's ッへ row). With all table fixes: 0 of 432,288 checked states fail (8,344 pairs skipped). The two totals are not comparable: the fixed table has more spellings and the stock run stops each failing spelling early.
  • Reduction. A public-API JUnit with the document suggester on the stock main jars (2026-10-28), then this doc's kuromoji-only test.
  • Tier. Semi-formal: the first signal came from a table self-consistency script, not from a solver's or model checker's own output.

LFV-854, snapshot of 2026-10-30

Registry title
Kuromoji completion suggester (JapaneseCompletionAnalyzer / JapaneseCompletionFilter, QUERY mode) suggests nothing while an input method shows a small tsu plus a pending c, j, f or v ('まっｃ' while typing maccha for 抹茶, 'ばっｊ' for bajji, 'すたっｆ' for sutaffu), because romaji_map.txt has the partial-input rows ッk..ッw but none for ッc, ッj, ッf or ッv, although its full rows double those letters (ッチャ ccha, ッジ jji, ッフ ffu, ッヴ vvu)
Area
analysis / kuromoji completion (JapaneseCompletionFilter QUERY-mode handling of mid-IME composition; the partial-input rows of romaji_map.txt, read by KatakanaRomanizer)
Priority
Low, rank 446: In the opt-in kuromoji completion QUERY mode, suggestions disappear for only one or two keystrokes while っc, っj, っf or っv is still being composed and nothing is wrong once the kana is complete, so it closes the Kuromoji completion-table cluster after LFV-848 rather than sitting apart from its siblings after LFV-669.
Impact class
minor
Impact note
Applications that use the opt-in kuromoji JapaneseCompletionAnalyzer or JapaneseCompletionFilter in QUERY mode (default constructors once chosen; downstream search servers expose it as kuromoji_completion) and send the text an input method is still composing, the use the feature was built for (#11140), lose all suggestions for one keystroke (っj, っf, っv) or two (っc, then っch) whenever a user types a small tsu before ch, j, f or v the Hepburn or wapuro way (maccha 抹茶, bajji バッジ, sutaffu スタッフ, キャッチャー); the suggestions come back once the input method turns the pending letter into kana, kana typed in full and Kunrei-style typing (tt, zz, hh) are unaffected, nothing throws and the index is unchanged; every release from 9.0.0 to 10.5.2, branch_10_6 (10.6.0) and main.
Summary
You build Japanese autocomplete with JapaneseCompletionAnalyzer, whose QUERY mode is documented as 'Input Method aware romanization' and joins a kana token with a still-pending romaji letter ('サッ' + 'k' => 'サッk', so 'さっｋ' keeps suggesting サッカー), and expect the same while a user types 'maccha' and the input method shows 'まっｃ'. Instead 'まっｃ' is romanized 'maxtuc' and nothing is suggested, and the same happens for 'ばっｊ' (bajji, バッジ) and 'ばっｆ' (baffa, バッファ), because the bundled romaji_map.txt has partial-input rows (small tsu plus one pending letter) only for k, g, s, z, t, d, h, b, p, m, y, r and w, although its own full rows double c, j, f and v (ッチャ ccha, ッジ jji, ッフ ffu, ッヴ vvu). The suggestions return one or two keystrokes later, when the input method converts the pending letters to kana.
