Compressor.compress on an input of 2^32 + k bytes (k < 2^31), e.g. 4 GiB + 1 MiB, compresses only the first k bytes and returns normally

Give a built-in Lucene Compressor an input of 4 GiB + 1 MiB and it compresses only the first 1 MiB and returns normally, because it narrows the long input length to int with a plain cast. Present since 9.4.0; Lucene's own writers are not known to pass such inputs.

The finding in 30 seconds

#

Compressor.compress takes a ByteBuffersDataInput: a read view over a list of buffers, whose length() is a long. Each built-in compressor narrows that length to an int with a plain (int) cast and reads that many bytes (the three CompressionMode compressors into one byte[] of that size, the two preset-dictionary ones in sub-blocks into a reused buffer), so above 4 GiB the length wraps around.

  1. Build a 4 GiB + 1 MiB input without using 4 GiB of memory: new ByteBuffersDataInput(Collections.nCopies(4097, ByteBuffer.allocate(1 << 20))), 4097 views of one 1 MiB buffer, so length() is 4,296,015,872.
  2. Compress it with CompressionMode.FAST.newCompressor().compress(in, out). You expect all 4,296,015,872 bytes compressed, or an exception if that is too big.
  3. Instead compress returns normally and in.position() is 1,048,576: one MiB was read and compressed, and the block it wrote decodes to just that MiB. All five built-in compressors do the same.
  4. Why: each one starts with final int len = (int) buffersInput.length(); (CompressionMode.java:160). The cast keeps the low 32 bits, so 2^32 + 2^20 becomes 2^20.
  5. One band lower fails loudly: at 2 GiB + 1 MiB the cast is negative and all five compressors throw. The pattern repeats every 2^32 bytes: when the length mod 2^32 is below 2^31 (4 GiB + 1 MiB, 8 GiB + 1 MiB) only that remainder is compressed, silently; otherwise compress throws, except in the last few bytes below each multiple of 2^32, where the two preset-dictionary compressors return normally having read nothing.

Who is affected

#

Only code that calls a compressor itself with one input of 2^32 + k bytes: a custom codec, plugin or application using CompressionMode.FAST, FAST_DECOMPRESSION or HIGH_COMPRESSION (experimental API) or the internal preset-dictionary modes. Lucene's stored-fields and term-vectors writers pass chunk-sized blocks and are not known to reach it. The caller gets no error and stores only a prefix.

Mechanism, terms and numbers610 words

Since 9.4.0, Compressor.compress takes a ByteBuffersDataInput, whose length() is a long and can exceed 4 GiB when the input spans many buffers. All five core compressors (CompressionMode.FAST, FAST_DECOMPRESSION, HIGH_COMPRESSION and the two preset-dictionary modes behind the stored-fields BEST_SPEED and BEST_COMPRESSION) first narrow that length with a plain (int) cast (CompressionMode.java:160, :182, :268; LZ4WithPresetDictCompressionMode.java:174; DeflateWithPresetDictCompressionMode.java:205 at 5adff78bb168). For an input of 2^32 + k bytes with k < 2^31 the cast gives k, so the compressor compresses only the first k bytes, writes a valid block for them and returns normally; this repeats every 2^32 bytes. When the length mod 2^32 is 2^31 or more the cast is negative and the call fails loudly, except in the last few bytes below a multiple of 2^32, where the two preset-dictionary compressors return normally having read nothing. No Lucene writer is known to pass more than 4 GiB to one call, so only code that calls a compressor directly is hit. Math.toIntExact at the five casts fixes it.

The bug, step by step

#
  1. Input. ByteBuffersDataInput.length() returns a long (ByteBuffersDataInput.java:206 at 5adff78bb168), and the constructor (:55) only requires a non-empty list, a power-of-two first page and equal-sized intermediate pages at position 0 (ensureAssumptions, :448-478), so views of one 1 MiB buffer make an input longer than 2^32 bytes without copying anything.
  2. The cast. LZ4FastCompressor.compress (CompressionMode.java:159-164) does final int len = (int) buffersInput.length(); byte[] bytes = new byte[len]; buffersInput.readBytes(bytes, 0, len); LZ4.compress(bytes, 0, len, out, ht);. LZ4HighCompressor (:182) and DeflateCompressor (:268) start the same way; the preset-dictionary compressors compute len from length() - position() with the same cast (LZ4WithPresetDictCompressionMode.java:174, DeflateWithPresetDictCompressionMode.java:205) and then read len bytes in sub-blocks.
  3. The wrap. A long to int cast keeps the low 32 bits. 4,296,015,872 = 2^32 + 1,048,576, so len is 1,048,576: the compressor reads one MiB, compresses it, writes a well-formed block and returns. Nothing checks that the input was consumed.

Exposure and likelihood219 words
  • Opt-in only. Compressor is public with no experimental tag (Compressor.java:24-36); CompressionMode, which hands out the three standard compressors, is public and @lucene.experimental (CompressionMode.java:35); the two preset-dictionary modes are @lucene.internal (LZ4WithPresetDictCompressionMode.java:36, DeflateWithPresetDictCompressionMode.java:38).
  • In-tree callers (read, not proven unreachable): the only callers of Compressor.compress in Lucene's main sources are the stored-fields writer, which bounds its buffer with Math.toIntExact(bufferedDocs.size()) per document (Lucene90CompressingStoredFieldsWriter.java:191) and compresses chunk-sized slices (:255-262); the term-vectors writer flushes once a chunk reaches its chunk size (4 KiB by default, Lucene90TermVectorsFormat.java:170; Lucene90CompressingTermVectorsWriter.java:328, :379-380) and compresses at :426. Only one document with more than 4 GiB of term-vector data could come near it. The per-thread RAM hard limit (below 2048 MB, IndexWriterConfig.java:383-385) does not stop that in advance: it is checked after each document (DocumentsWriterFlushControl.java:215-251) and only marks the thread for flushing. No IndexWriter path is claimed. The other in-tree Compressor implementations (SortingStoredFieldsConsumer.NO_COMPRESSION, the test framework's DummyCompressingCodec) pass the long length to out.copyBytes and have no cast.
  • Effect. No error; the stored block holds only the first k bytes of the caller's data, and the input is left at position k.
  • Scale. More than 4 GiB in one compress call. The recorded searches found no report since 9.4.0 (2022).

Why it looks unintended

#
  • Compressor.compress promises to "compress bytes into out", states no size limit and takes an input with a long length.
  • Nothing checks the range and no test comes near it; 2 GiB + 1 MiB already fails loudly.
  • Even if over 2 GiB is misuse, the answer is an exception, not a normal return after compressing 1 MiB.
The full argument200 words
  • Contract. "Compress bytes into out. It is the responsibility of the compressor to add all necessary information so that a Decompressor will know when to stop decompressing bytes from the stream." (Compressor.java:30-34). No size limit, no check at any of the five sites, no CHANGES or MIGRATE entry about one.
  • Tests. AbstractTestCompressionMode.randomArray uses at most 33 KiB (192 KiB nightly) (AbstractTestCompressionMode.java:36-39), and the largest compression test, testExtremelyLargeInput, uses 16 MiB (:158-164). Lucene's own TestByteBuffersDataInput.testSlicingLargeBuffers builds a ByteBuffersDataInput longer than 4 GB by duplicating pages (:231-241), the repro's technique, so such inputs are normal objects.
  • History. The casts arrived in 34154736c6e (LUCENE-10627, #987), which changed compress(byte[] bytes, int off, int len, DataOutput out) to compress(ByteBuffersDataInput, DataOutput). The review comment on the cast line asked only "Should position() always be 0?". One week later, on #1047 (LUCENE-10661, same author and reviewer), the reviewer flagged a similar int len = (int) numBytes ("We could make len a long and avoid the unchecked cast, couldn't we?") then commented "the cast is safe now because the number we're casting is guaranteed to fit in a 32-bits integer" (2022-07-27) and merged the PR right after.
The devil's-advocate check157 words

The strongest case for "intended": compressor blocks are implicitly int-sized. Decompressor.decompress takes int originalLength (Decompressor.java:42-43), the API took an int length before 9.4, and the stored-fields format "does not support documents larger than (2^31 - chunkSize) bytes" (Lucene90CompressingStoredFieldsFormat.java:36-37). So more than 2 GiB is misuse, on an experimental API with no in-tree caller that does it.

Why it fails: that limit is documented for the stored-fields format, not for Compressor, and nothing enforces it there. Read as an unstated precondition it argues for rejecting the input, as the same code already does, loudly, for most of 2^31 to 2^32 - 1 bytes (all of it in the three CompressionMode compressors); it does not justify a normal return after compressing 1 MiB of 4 GiB + 1 MiB. The experimental tag and the missing in-tree caller limit the impact, hence Low, not the intent. Verdict: an unchecked narrowing, a real Low bug.

Suggested fix

#

Recommended A. Math.toIntExact at all five casts (validated)

Replace the five (int) casts with Math.toIntExact(...), so an input above 2^31 - 1 bytes throws instead of being cut. The repro passes with assertions on and off, and 145 compression-mode, stored-fields and term-vectors tests pass. Alternative: an explicit check that throws IllegalArgumentException naming the length.

-      final int len = (int) buffersInput.length();
+      final int len = Math.toIntExact(buffersInput.length());

-      final int len = (int) (buffersInput.length() - buffersInput.position());
+      final int len = Math.toIntExact(buffersInput.length() - buffersInput.position());

Trade-offs

One comparison per compress call (per chunk), nothing per byte. Inputs above 2^31 - 1 bytes fail with ArithmeticException: integer overflow, which names no argument. For 2^31 to 2^32 - 1 bytes it replaces NegativeArraySizeException, the preset-dictionary modes' AssertionError (assertions on) or out-of-bounds exception (off), and their silent normal return just below 2^32. For inputs whose length fits in an int, the changed expressions give the same value as before. It is range hardening, not support for every int length: an input of exactly Integer.MAX_VALUE bytes still passes, and the three CompressionMode compressors then allocate an array of that size, which can fail on VM array-size or heap limits (not executed).

What the checks validated

  • The repro passes with assertions on and off (gradle, seed 5EED1150).
  • With the fix, the five compression-mode tests, TestCompressingStoredFieldsFormat, TestCompressingTermVectorsFormat, TestStoredFieldsInt and the three TestLucene90StoredFieldsFormat* classes pass with assertions on (12 classes with the repro, 145 tests, 0 failures, 8 skipped: the @Nightly testLineFileDocs and testBigDocuments of the four stored-fields classes).
  • :lucene:core:checkGoogleJavaFormat passes with the fix and the test file.
  • A five-compressor check against the fixed classes: all five throw ArithmeticException for 2,148,532,224- and 4,296,015,872-byte inputs, and a 3 MiB control still round-trips, so the two preset-dict sites, which the one test does not reach, are covered too. The diagram's probe adds 2^32 - 1 bytes: with the fix all five throw ArithmeticException there too.

B. An explicit check with a clear message

#

At the same five places, or once in a small helper: if (length > Integer.MAX_VALUE) throw new IllegalArgumentException("Compressor input too large: " + length + " bytes");. Either option can also add "at most Integer.MAX_VALUE bytes" to the Compressor.compress javadoc.

Trade-offs

A clearer error for a little more code; the repro's catch becomes IllegalArgumentException. Not built or tested.

Downstream note

#

A product with its own codec that hands one input of 2^32 + k bytes (k < 2^31) to these compressors would store a prefix with no error; keeping each call below 2 GiB, or checking the length first, avoids it.

How it was found

#

A proof-obligation audit of Compressor's contract: compress must consume its whole input or fail, for every legal ByteBuffersDataInput, including ones longer than Integer.MAX_VALUE bytes. Each compressor's first line narrows the long length to int, which breaks that obligation above 4 GiB. A one-method JUnit test on the public API witnessed it.

The method in full69 words

The obligation came from Compressor.compress's javadoc and its long-length parameter type, checked against the first statement of each of the five core compressors. The witness test (an earlier one-test repro with the same trigger) fails on main with assertions on and off and on the 10.6.0 and 10.0.0 jars; a five-compressor probe showed the same silent prefix in every mode and the loud failure one band lower.
