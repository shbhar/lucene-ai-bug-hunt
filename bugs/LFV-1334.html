HNSW search drops a whole batch of neighbours when one of them scores NaN

Since 10.4.0, HNSW search skips a whole batch of neighbours when one similarity in it is NaN, because the batch's best score, taken with Math.max, becomes NaN. In the repro the best document (score 4.0) disappears and KnnFloatVectorQuery with k = 2 returns one hit, with no error.

Summary

Priority
Low, rank 577HNSW search silently skips every finite neighbour that shares a scoring batch with a NaN similarity, so kNN queries on the default vector format return fewer and worse hits, a regression released in 10.4.0 through 10.6.0. The finding in 30 seconds

#

HNSW search scores a node's neighbours as one batch and skips the batch when its best score cannot compete. One NaN similarity makes the "best score" NaN, so the batch is skipped even when it holds the best document.

How HNSW search uses a batch

#
  1. A kNN search keeps the k best documents found so far. While it holds fewer than k, its threshold (the minimum competitive similarity) is -Infinity: any document can get in.
  2. The search walks the HNSW graph: it takes the best node not yet expanded, collects that node's neighbours it has not seen, marks them visited (so each document is scored at most once per search) and scores them together as one batch (only as many as the search's visit budget still allows; an unfiltered query has no such limit).
  3. Since 10.4.0, bulk scoring also returns the batch's best score, and the search looks at the batch's documents only if that best score beats the threshold; otherwise it skips the whole batch.

The finding, step by step

#
  1. Index three 36-dimension MAXIMUM_INNER_PRODUCT vectors in one segment with an HNSW graph: doc 0 = (0, 0, 1, ...), doc 1 = (1e38, 1e38, 0, ...), doc 2 = (0, 0, 3, ...). The query is (1e38, -1e38, 1, ...). Every component is finite, so Lucene accepts them.
  2. Against the query, doc 0 scores 2.0 and doc 2 scores 4.0. Doc 1's two huge products overflow to +Infinity and -Infinity in different partial sums, and their sum is NaN.
  3. You run KnnFloatVectorQuery with k = 2 and expect doc 2 (4.0) and doc 0 (2.0), which Lucene 10.3.2 returns on the same graph.
  4. You get only doc 0. The search starts at doc 0, marks its neighbours 1 and 2 visited and scores them as one batch. It looks inside the batch only if the batch's best score beats the threshold (-Infinity here), but Math.max makes that best score NaN, and NaN > -Infinity is false.
  5. So doc 2 is thrown away with the NaN document and never revisited. Before 10.4.0 a per-node check dropped only the NaN document.

Who is affected

#

Applications whose kNN similarities can be NaN: MAXIMUM_INNER_PRODUCT (or other non-normalized) float vectors with components of roughly 2e19 or more, so dot products overflow to both infinities, or a custom scorer that returns NaN. The trigger is extreme next to typical embeddings. Graph and exhaustive kNN search, 10.4.0 to 10.6.0 and main.

Mechanism, terms and numbers614 words

Since 10.4.0, HNSW graph search marks a node's unvisited neighbours visited, scores them (up to the remaining visit budget) as one batch and processes the batch only if RandomVectorScorer.bulkScore's returned maximum beats minCompetitiveSimilarity(). bulkScore takes that maximum with Math.max, so one NaN similarity makes it NaN, and NaN > x is false even while the collector is not full (threshold -Infinity). The finite neighbours in that batch are already marked visited, so they are never collected or expanded. In the repro, three finite MAXIMUM_INNER_PRODUCT vectors and a finite query, one of whose dot products overflows to +Inf + -Inf = NaN, give KnnFloatVectorQuery(k=2) one hit, doc 0 (score 2.0); the best document, doc 2 (score 4.0), is missing. 10.3.2 returns doc 2 and doc 0 on the same graph. It is silent with assertions off, and with assertions on through the vectorized off-heap scorer. The fix is the same single comparison, written so that NaN falls through to the per-node checks that already exist.

Step by step in the repro

#
  1. The graph has entry doc 0, whose neighbours are [1, 2] (graph dump of the same index).
  2. The search collects doc 0 (score 2.0). The collector wants 2 hits and has 1, so minCompetitiveSimilarity() is -Infinity (KnnCollector.java:71-74).
  3. Expanding doc 0 marks docs 1 and 2 visited and scores them together: [NaN, 4.0]. Math.max returns NaN if either argument is NaN, so bulkScore returns NaN; the vectorized off-heap float scorer folds the same way (Lucene99MemorySegmentFloatVectorScorer.java:94-117).
  4. NaN > -Infinity is false, so the batch is skipped. Doc 2 is not collected, not queued, and already visited; the queue is empty and the search ends with doc 0.
  5. Without the gate (10.3.2), every score went to the per-node test at :341, which is false for NaN and true for 4.0: only the NaN document was dropped.

Why 36 dimensions

#

The scalar dot product keeps four partial sums only for vectors longer than 32 (DefaultVectorUtilSupport.java:46-58), and the vectorized one uses lanes, so 1e38 x 1e38 and 1e38 x (-1e38) land in different partial sums, +Infinity and -Infinity, whose sum is NaN. With 3 dimensions a single fused multiply-add chain gives +Infinity instead, a different behaviour.

The other gates

#
  • findBestEntryPoint (maxScore > currentScore, HnswGraphSearcher.java:251) and the filtered search (maxScore > results.minCompetitiveSimilarity(), FilteredHnswGraphSearcher.java:198) have the same shape; a supporting test of both fails on main and passes with the fix.
  • Exhaustive search (segments without a graph, k not below the vector count, or an expected visit count for k that reaches the number of accepted documents; Lucene99HnswVectorsReader.java:373-414) gates blocks of 64 vectors the same way (:396, :408) and then collects the whole block with no per-node test. With the default format the same 3-document segment has no graph, and the query returns 0 hits on main. 10.3.2's loop had no gate and collected every score, NaN included (by reading). The flat scalar-quantized reader's search (Lucene104ScalarQuantizedVectorsReader.java:390, :402) has the same gate and whole-block collection (by reading, not run).
  • HnswGraphBuilder.diversityCheck (bulkScore(chunk) >= score, :568) was only read and is not claimed.
Exposure and likelihood260 words
  • What they see. Fewer and worse hits, no error, with assertions off (and with assertions on through the vectorized off-heap scorer on MMapDirectory; on the scalar provider or an on-heap directory, -ea stops at VectorUtil.dotProduct's not finite: NaN assertion).
  • More than the NaN document. Every finite neighbour that shares the NaN document's batch, up to one full neighbour list (32 on level 0 with the default M = 16), is skipped for the rest of the query. With k = 1 the same 3-document graph returns doc 0 (2.0) instead of doc 2 (4.0). In a 33-document graph where the NaN document is a hub, k = 2 returns one filler hit (score 1.5) instead of docs 2 and 0; that probe passes on 10.3.2 and with the fix.
  • Exhaustive search. A whole block of 64 vectors is dropped there: 0 hits for the 3-document segment with the default format.
  • Where. The default HNSW searcher on any segment that has a graph. The repro forces a graph for its 3-document segment (tinySegmentsThreshold 0, through the test framework's codec helper); with the default format that tiny segment takes the exhaustive path instead. For comparable components a product overflows from about 1.84e19 (the square root of the float limit, about 3.4e38): 1e19 x 1e19 = 1e38 is still finite.
  • How likely. Contrived: it needs NaN similarities and a NaN node that shares a batch with better nodes (a probe layout where the NaN document's only neighbour is doc 0 passes). The recorded searches found no public report since 10.4.0.

Why it looks unintended

#
  • bulkScore returns "the maximum scored value of any node", and the threshold exists "to ensure only competitive results are explored": 4.0 beats -Infinity.
  • The gate is an optimization (#15021). Before 10.4.0 only the NaN document was dropped, and 10.3.2 returns docs 2 and 0 on the same graph.
  • The vectors pass Lucene's finiteness checks; a magnitude bound was declined (#12373).
The full argument229 words
  • Contract. RandomVectorScorer.bulkScore: "@return the maximum scored value of any node" (RandomVectorScorer.java:45). KnnCollector.minCompetitiveSimilarity: "utilized during search to ensure only competitive results are explored", NEGATIVE_INFINITY when not full (KnnCollector.java:71-74).
  • Intent. #15021's commit message (0421a8de771): "skip any topN heap manipulation for any bulk scored batches that do not meet the minimum score". Removing only that gate on 10.4.0 makes the test pass.
  • Legal input. KnnFloatVectorField and KnnFloatVectorQuery check only that each component is finite (KnnFloatVectorField.java:105, KnnFloatVectorQuery.java:97, VectorUtil.checkFinite at VectorUtil.java:485). MIP "does not require normalization of the inputs" (VectorSimilarityFunction.java:99-103). #12373 ("require that float vector components are smaller than 1E17 to prevent overflowing to Infinity") was closed unmerged on 2023-11-02. Accepted input is not the same as supported overflow: the score itself is still treated as invalid (devil's advocate below).
  • Undocumented. No javadoc, CHANGES or MIGRATE entry, or test describes the batch drop.
  • Framing. The kNN API is approximate: LeafReader's javadoc says the results "are not guaranteed to be the true k closest neighbors" and that for k close to the document count the search "may also retrieve fewer than k documents" (LeafReader.java:259-261). The claim is a deterministic traversal regression that loses finite, competitive candidates 10.3.2 kept, not a proven breach of an exact top-k guarantee; whether it breaks the contract is for the maintainers to judge.
The devil's-advocate check222 words

The strongest case, and the main won't-fix risk: Lucene treats NaN scores as invalid data to prevent, not handle. TopScoreDocCollector's javadoc says NaN and NEGATIVE_INFINITY "are not valid scores" (TopScoreDocCollector.java:30-31); VectorUtil.dotProduct asserts a finite result; on #12281 uschindler wrote "We also do not allow other queries to return scores of NaN ... We do not check for invalid float scores on each scored document"; on #16099 (closed 2026-06-01) benwtrent declined NaN handling in HNSW hot paths as "unnecessary overhead to production paths for something that is data input validation and is obviously incorrect data". The cross-model reviewer added that the kNN API is approximate and that with k = 2 of 3 documents the reader may return fewer than k; it rated the case for intended behaviour strong.

Why it fails: no validation rejects these vectors (#12373 declined the bound); the damage reaches finite, valid documents that 10.3.2 returned; the fix adds no comparison (still one per batch; not benchmarked), in line with SECURITY.md line 46, which asks that hardening not slow down hot paths. k = 1 returns the wrong top hit, and the 33-document k = 2 probe loses both true hits, so the narrow "fewer than k" case does not explain it; the approximate-API point stays the maintainers' call. Verdict: not intended as a traversal regression.

Suggested fix

#

Recommended A: NaN-tolerant gates in the graph searchers

Write the three batch gates as (max <= threshold) == false, so a NaN maximum falls through to the per-node checks that already drop NaN nodes one by one, as before 10.4.0: still one comparison. Validated: the repro and 237 HNSW and kNN tests pass. Exhaustive search keeps its gate and needs its own change.

Trade-offs

  • No added comparison (still one per batch); performance not benchmarked. The two forms differ only when the maximum or the threshold is NaN, so results for finite scores and thresholds do not change.
  • Leaves exhaustive search (and the same gate in Lucene104ScalarQuantizedVectorsReader.java:390, :402): negating its gate alone would make that loop collect the NaN document too, because it has no per-node test (Lucene99HnswVectorsReader.java:397-399, :409-411); it needs the negated gate plus a per-node skip of NaN scores (not run).
  • With assertions on and the scalar provider, the repro still stops at VectorUtil.dotProduct's assertion (the NaN itself is unchanged).

B: a NaN-ignoring maximum in bulkScore (not run)

#

Replace max = Math.max(max, s) with if (s > max) max = s in RandomVectorScorer.bulkScore and the two vectorized float scorers in java25 (Lucene99MemorySegmentFloatVectorScorer, Lucene99MemorySegmentFloatVectorScorerSupplier), the only folds at 5adff78bb168. The other overrides (PrefetchableFlatVectorScorer, the sandbox DedupFlatVectorsScorer) delegate and inherit the change.

Trade-offs

Covers every gate at once, including diversityCheck and exhaustive search, but touches more implementations and every future override, and the exhaustive loops would then collect the NaN document.

C: reject vectors that can overflow (not run)

#

A magnitude bound at index and query time, the maintainers' usual direction for invalid data.

Trade-offs

Declined once already (#12373, no consensus); does not cover a custom or quantized scorer that returns NaN; a behaviour change for existing indexes.

Downstream note

#

For a downstream service that passes untrusted vectors to a MAXIMUM_INNER_PRODUCT field, the effect is fewer or worse kNN hits only (no crash, hang or data exposure), and bounding vector component magnitudes avoids it.

How it was found

#

A semi-formal proof-obligation check: may HNSW's batch gate skip a batch only when no node in it can be competitive, as bulkScore's contract and #15021 intend? The obligation fails for NaN, because Math.max propagates it. An executable public-API JUnit test then showed the best hit lost.

The method in full109 words

Method: semi-formal (2026-11-04, main 5adff78bb168).

  • The obligation: the gate bulkScore(batch) > minCompetitiveSimilarity() may skip a batch only if no node in it passes the per-node test score >= minAcceptedSimilarity. It holds for finite scores, because the maximum bounds every score; it fails when a score is NaN, because Math.max returns NaN and every comparison with NaN is false.
  • Witness: a public-API JUnit test with finite MAXIMUM_INNER_PRODUCT vectors whose dot product with the query overflows to +Infinity and -Infinity, plus a graph dump to confirm the batch layout; then a supporting test of the entry-point and filtered gates. The test was later reduced to the one shown here.

Priority
Low, rank 577: HNSW search silently skips every finite neighbour that shares a scoring batch with a NaN similarity, so kNN queries on the default vector format return fewer and worse hits, a regression released in 10.4.0 through 10.6.0. A NaN score needs both document and query vector components of about 1e19 or more (for example on a MAXIMUM_INNER_PRODUCT field) or a custom scorer that returns NaN, and real embeddings never reach such magnitudes.
Impact class
minor
Impact note
Applications with a MAXIMUM_INNER_PRODUCT (or other non-normalized) float vector field whose document and query vectors have components large enough that one dot product overflows float to +Inf + -Inf (about 1e19 and up; all components finite, so field and query validation accept them) get fewer and worse kNN hits with no error: every finite neighbour that shares a scoring batch with the NaN-scoring node is skipped and, already marked visited, never revisited, not only the NaN node; a regression of 10.4.0 (#15021), silent with -ea and -da on the default MMapDirectory and vectorized scorer path [exec]; real embeddings do not reach it.
Summary
You index three MAXIMUM_INNER_PRODUCT float vectors with finite components into one segment with an HNSW graph (one document and the query have components of 1e38, so their dot product overflows to +Inf + -Inf = NaN) and run KnnFloatVectorQuery with k=2. You expect the two finite best documents, doc 2 (score 4.0) and doc 0 (score 2.0), which 10.3.2 returns on the identical graph. Instead main and 10.4.0 through 10.6.0 return only doc 0: doc 2 is in the same neighbour batch as the NaN document, Math.max makes the batch maximum NaN, 'NaN > minCompetitiveSimilarity()' is false even though the collector is not full, so the whole batch is skipped and doc 2 is never collected or explored.
