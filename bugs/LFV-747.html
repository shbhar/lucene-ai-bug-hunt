StandardQueryParser keeps escape backslashes in fn: interval term literals

StandardQueryParser reads a\:b as the term a:b, but inside an interval function it keeps the backslash: fn:or(a\:b) searches for the text a\:b. The query silently misses the a:b document and can hit an a\:b document instead, in every release since 9.1.0.

The bug in 30 seconds

#

The flexible parser removes escape backslashes from every term, except from the term literals of fn: interval functions.

  1. Index two documents with a whitespace analyzer: doc 0 holds a:b c, doc 1 holds a\:b c (with a real backslash).
  2. Search a\:b with StandardQueryParser. The backslash escapes the colon, as the parser documents ("any character can be quoted with a backslash"): the query is body:a:b and it finds doc 0.
  3. Put the same word inside an interval function: fn:or(a\:b). You expect the same term a:b and doc 0.
  4. Instead the query is body:a\:b and finds doc 1. The two grammar rules that read fn: literals pass the raw token on and never remove the backslash, unlike Term, QuotedTerm and the other rules that produce plain term text.
  5. No error. All 10 fn: forms tried behave the same (fn:ordered, nested functions, fn:fuzzyTerm); with StandardAnalyzer, fn:or(a\:b) becomes the phrase a b. Quoting (fn:or("a:b")) avoids it, but no fn: term literal can hold a double quote.

Who is affected

#

Applications that let users, or the helper QueryParserUtil.escape, put an escaped character into a term inside fn:. No configuration needed: the fn: syntax is always on. With whitespace or keyword analyzers every escaped character gives wrong hits; with StandardAnalyzer mainly an escaped colon. One query is enough, and nothing reports an error.

Mechanism, terms and numbers481 words

The flexible StandardQueryParser documents that "any character can be quoted with a backslash", and outside interval functions it removes the backslash: a\:b is the term a:b. Inside fn: it does not. The two grammar productions that read an fn: term literal, IntervalText (every literal under fn:or, fn:ordered and the other composite functions, at any depth) and IntervalFuzzyTerm (fn:fuzzyTerm), pass the raw token text to AnalyzedText and FuzzyTerm without discardEscapeChar, which every other production that yields plain term text calls. So fn:or(a\:b) searches for the text a\:b: with a whitespace analyzer it misses the document a:b c and finds a\:b c; with StandardAnalyzer it becomes the phrase BLOCK(a,b) and finds a b c. Nothing throws. The lexer already treats the backslash as an escape inside fn:; the parser just never removes it. Quoting is a workaround except for a double quote, which no fn: term literal can express (only fn:wildcard(a\"b) reaches it, as one unanalyzed term). Every release since 9.1.0, when fn: arrived, is affected; four discardEscapeChar calls fix it.

Terms

#
  • Escaping: in StandardQueryParser query text, a backslash makes the next character literal: a\:b is the term a:b, not field a and term b (StandardQueryParser.java:175-186).
  • Interval functions: fn:or(...), fn:ordered(...), fn:fuzzyTerm(...) and 18 more build an IntervalQuery; their leaves are term literals, "converted into (analyzed) text intervals" (intervalfn/package-info.java:147-152).

The bug

#
  1. The lexer treats \x as an escape everywhere (StandardSyntaxParser.jj:129-136, :159-161); after fn: the ( switches it back to the default state (:147, :167-168), so a\:b inside fn: is one term token with the image a\:b. The escape protects the structure: fn:or(x\)) parses, fn:or(x)) does not.
  2. Every other production that yields plain term text removes the backslash with discardEscapeChar: Term (:803-804), QuotedTerm (:828-831), FuzzyOp (:727), the range productions and field names. The only others that keep it, Term's /regexp/ branch (:798-801) and fn:wildcard (:649-650), pass it to RegExp and WildcardQuery, which read it as an escape.
  3. IntervalFuzzyTerm (:668-669) and IntervalText (:684-685) do not: they hand token.image (or the quoted image minus its quotes) to FuzzyTerm and AnalyzedText (generated parser :980, :986, :1022, :1046).
  4. AnalyzedText passes the text to Intervals.analyzedText and FuzzyTerm to Intervals.fuzzyTerm (AnalyzedText.java:34-41, FuzzyTerm.java:43-50). Neither knows query escapes, so the backslash becomes part of the searched text.
  5. IntervalFun (:383-409) is recursive and every term-literal leaf ends in one of the two productions, so every literal under every composite function is affected. fn:wildcard, the one other leaf, keeps backslashes too, but there WildcardQuery reads them as escapes, which is consistent for glob escapes such as \* (its handling of \uXXXX escapes was not tested); it is not part of this bug.
Exposure and likelihood340 words
  • Who. Applications that pass query text to the flexible StandardQueryParser and use its fn: interval functions, when a term literal inside fn: contains a backslash-escaped character: typed by a user, or produced by the documented helper QueryParserUtil.escape (escape("a:b") is a\:b), for example when an application wraps escaped user words in fn:ordered(...).
  • Effect. Silently wrong hits for that literal: it misses the documents with the intended text and can match documents with the backslash text, or, with StandardAnalyzer, the phrase of the split pieces. No exception; the index is not touched.
  • Default vs opt-in. Default parser settings, IndexWriterConfig, codec and searcher. The fn: syntax is part of the standard syntax; the trigger is query text that uses it.
  • Depends on the analyzer. With whitespace or keyword-style analyzers (codes, identifiers, paths) every escaped character changes the result. With StandardAnalyzer the backslash is usually split off and dropped, so the visible cases are mainly an escaped colon (a:b is one token, a\:b gives a, b), escapes a user types before other in-word punctuation (a\.b is body:a.b, but fn:or(a\.b) is BLOCK(a,b)) and \uXXXX escapes.
  • Workaround. Quote without escapes: fn:or("a:b") works. A double quote is the exception: no fn: term literal can express it, since fn:or("a\"b"), fn:or(a\"b), fn:or(a\u0022b) and fn:fuzzyTerm("a\"b" 0) all keep the escape sequence. The only escape hatch is fn:wildcard(a\"b): it finds the a"b document because WildcardQuery reads \" as an escape, but it matches one indexed term without analysis, so it cannot stand in for an analyzed literal or a phrase.
  • Scale. None: one document and one query, deterministic, every time.
  • Frequency. Not measured, and likely low: it needs the fn: interval syntax plus an escaped character inside an fn: term literal, and quoting usually avoids it. The registry rates the likelihood rare, and no user report was found in the searched sources since 9.1.0.
  • Not affected. Escaped terms outside fn:; quoted fn: literals without backslashes; fn:wildcard; the classic QueryParser, which has no fn: syntax.

Why it is a bug, not intended

#
  • The parser says "any character can be quoted with a backslash", with no fn: exception; its own example \:\(quoted\+term\)\: fails inside fn:or(...).
  • The lexer already treats \x as an escape inside fn:; only the removal is missing (the plain-term rules do it).
  • As raw text, no fn: term literal could hold a double quote; nothing upstream calls fn: literals raw.
The full argument249 words
  • The contract. StandardQueryParser.java:175-186, "Special character escaping": "If the search term contains the quote character (or cannot be quoted for some reason), any character can be quoted with a backslash", with \:\(quoted\+term\)\: and ":(quoted+term):" as two spellings of one term. The fn: section (:204-223) adds no exception. intervalfn/package-info.java:149: term literals are "converted into (analyzed) text intervals". FuzzyTerm.java:26: "An interval function equivalent to FuzzyQuery", and a\:b~1 outside fn: is unescaped.
  • The javadoc example fails inside fn:. fn:or(\:\(quoted\+term\)\:) finds the document with the backslash text; the documented quoted form fn:or(":(quoted+term):") finds the right one (executed by the independent reproducer).
  • The grammar disagrees with itself. The lexer honours the escape inside fn:, and Term, QuotedTerm, FuzzyOp, the range productions and field names all call discardEscapeChar. The only other rules that keep the raw image, Term's /regexp/ branch and fn:wildcard, hand it to RegExp and WildcardQuery, which read backslashes as escapes; IntervalText and IntervalFuzzyTerm hand it to the analyzer and the fuzzy automaton, which do not.
  • History. Both productions skipped it from their first version (LUCENE-10223, #429, 2021; LUCENE-10414, #668, 2022). The escaping javadoc and the term-literal docs came in the same commit as IntervalText, so code and docs have disagreed from the start. Neither PR discusses escaping.
  • Tests. No queryparser test uses a backslash inside fn:; none asserts either behaviour. In #11800 (2022) the fn: author advised escaping (am\@zing) or quoting, with no fn: exception.
The devil's-advocate check212 words

The strongest works-as-designed case, built by the intended-behaviour verifier: fn: literals are a raw sub-language. The interval docs never mention escaping, every fn: leaf takes the raw token the same way, fn:wildcard keeps backslashes, and AnalyzedText.toString prints the stored text back unescaped.

Why it fails: the escaping rule is stated for the whole parser and the lexer applies it inside fn:; fn:wildcard and Term's /regexp/ branch keep backslashes only because WildcardQuery and RegExp read them as escapes, while the analyzer and the fuzzy automaton do not; under the raw reading no fn: term literal could contain a double quote (only fn:wildcard, one unanalyzed term, can reach one), exactly the case the javadoc says needs backslash escaping; toString does not round-trip anyway (LFV-748); and no test, commit message, CHANGES or MIGRATE entry, JIRA or PR discussion says fn: literals are raw. All the reviews by a model from another family rated the argument weak. The weakest point for a filing: the contract is a general rule, not a sentence about fn:, so lead with the lexer point and the javadoc example that fails inside fn:. The double quote supports them; say "no fn: term literal", since a maintainer can point to fn:wildcard(a\"b), which reaches one unanalyzed term.

Suggested fix

#

Recommended Unescape the four token images in the grammar

Remove the escapes in the two fn: literal rules with discardEscapeChar, as Term and QuotedTerm do, and regenerate the parser. Validated: the repro passes, as do all 544 lucene/queryparser tests and the module checks. Land it with the printing fix of LFV-748 (option B), or printed fn: queries stop parsing back.

// StandardSyntaxParser.jj, IntervalFuzzyTerm (:668-669)
  (<TERM> | <NUMBER>) { term = discardEscapeChar(token.image).toString(); }
| <QUOTED>            { term = discardEscapeChar(token.image.substring(1, token.image.length() - 1)).toString(); }
// IntervalText (:684-685)
  (<QUOTED>)          { return new AnalyzedText(discardEscapeChar(token.image.substring(1, token.image.length() - 1)).toString()); }
| (<TERM> | <NUMBER>) { return new AnalyzedText(discardEscapeChar(token.image).toString()); }
// then: ./gradlew :lucene:queryparser:regenerateFlexibleStandardSyntaxParser

Unescape the four token images in the grammar (validated by the checks) (recommended)

#

Wrap the four token images of IntervalFuzzyTerm and IntervalText in discardEscapeChar(...).toString() (already imported, StandardSyntaxParser.jj:83), then regenerate the parser; the diff also carries the regenerated StandardSyntaxParser.java and its checksum file. fn:wildcard stays as it is on purpose.

  (<TERM> | <NUMBER>) { term = discardEscapeChar(token.image).toString(); }
| <QUOTED>            { term = discardEscapeChar(token.image.substring(1, token.image.length() - 1)).toString(); }
// IntervalText (:684-685)
  (<QUOTED>)          { return new AnalyzedText(discardEscapeChar(token.image.substring(1, token.image.length() - 1)).toString()); }
| (<TERM> | <NUMBER>) { return new AnalyzedText(discardEscapeChar(token.image).toString()); }
// then: ./gradlew :lucene:queryparser:regenerateFlexibleStandardSyntaxParser

Trade-offs

Escaped fn: literals now mean the unescaped text; anyone who relied on the raw text (no such use is documented) sees different hits, worth a CHANGES line. Malformed unicode escapes inside fn: (fn:or(a\u00)) now throw ParseException, as they already do outside fn:. Alone, it makes toQueryString print escaped literals in a form that no longer parses back (fn:or(a\:b) prints fn:or(a:b), a ParseException; fn:or(x\\y) prints fn:or(x\y), which re-parses as xy): pair it with option B's printing.

What the checks validated

Stock: the two repro files fail 9 of 10 (assertions on and off), and the whole module run fails exactly those 9. Fix: 10 of 10 pass (on and off); the whole lucene/queryparser suite (544 tests: 533 upstream + 10 repro + 1 probe; 0 failures, 1 upstream @Ignore) and the highlighter's TestMatchHighlighter (6) pass; :lucene:queryparser:check -x test (javacc checksums, google-java-format, ecjLint, forbiddenApis) passes. The regenerated parser equals the hunt's hand-patched one up to line wrapping; with that one shadowed onto the stock jars all 11 scope-probe queries hit doc 0 and the hunt's exhaustive escape check goes from 0 to 5,208 of 5,208 equal.

A plus the printing fix shared with LFV-748 (validated by the checks)

#

Option A plus the LFV-748 printing fix (quote every literal the grammar would not read back as one term; fn:fuzzyTerm prints %d %d; fn:wildcard prints a bare maxExpansions) and one helper, AnalyzedText.toLiteral, that escapes \ and " inside the quotes; FuzzyTerm.toString uses it. With it every parsed fn: query in the probe prints a string that parses back to the same query.

static String toLiteral(String term) {  // AnalyzedText; FuzzyTerm.toString uses it too
  if (requiresQuotes(term)) {            // requiresQuotes as broadened by the LFV-748 fix
    return '"' + term.replace("\\", "\\\\").replace("\"", "\\\"") + '"';
  } else {
    return term;
  }
}

Trade-offs

toString/toQueryString now quote literals with query-syntax characters. fn:wildcard keeps its raw glob inside the quotes, because the wildcard rule does not unescape. Filed separately, A is this bug's fix and the printing belongs to LFV-748; say in each that they land together, and do not count the printing failures twice. Neither diff adds a test: the round-trip probe prints whether each re-parse equals the original and asserts nothing, so a PR should add the repro tests and a round-trip assertion.

What the checks validated

Downstream note

#

An application that wraps user words escaped with QueryParserUtil.escape in fn: functions gets wrong hits for words with special characters, while the escapes still keep the query structure intact (an escaped ) stays in the literal, an escaped : does not switch the field).

How it was found

#

While writing an independent reference for fn: expressions (a printer plus an Intervals builder, compared with the parser on a 389-document index), reading the grammar showed that the fn: literal rule never unescapes. The reference's escaped-literal cases then disagreed every time: 0 of 5,208 checks equal, and 5,208 of 5,208 with the fix.

The method in full175 words

Method: bounded-exhaustive translation validation (semi-formal tier), in a hunt unit on the standard query parser's documented syntax.

  • The reference prints each fn: expression from an abstract syntax tree in the documented syntax and builds the IntervalsSource with the Intervals factory of the same name, unescaping term literals by the documented rule; it compares the parser's result by Query.equals and by match sets and positions on a 389-document two-field index.
  • Plain scope: 11,520 exhaustive checks (12 leaves, every depth-1 function, 3 field modes) and 75,000 random depth-2 and depth-3 checks, 0 mismatches; four deliberately broken references were all caught.
  • Escape dimension (7 escaped literals): 5,208 checks, 0 equal, 2,250 with different match sets; with the four-call fix 5,208 of 5,208 equal.
  • The signal came from reading the grammar while writing the reference (IntervalText has no discardEscapeChar); the run measured it. Found 2026-10-27, then checked by an independent reproducer, reviews by a model from another family (OpenAI GPT-5.6, reading only), an intended-behaviour devil's advocate, an adjudication, a history and prior-report follow-up and a credibility audit.

Bug record

LFV-747, snapshot of 2026-10-28

Registry title
Flexible StandardQueryParser: term literals inside fn: interval functions keep their escape backslashes, so fn:or(a\:b) searches for the text a\:b instead of the term a:b
Area
queryparser / flexible StandardQueryParser interval functions (StandardSyntaxParser.jj IntervalText and IntervalFuzzyTerm, intervalfn AnalyzedText and FuzzyTerm)
Priority
Medium, rank 309: It silently changes matches every time since 9.1.0 but only with the niche fn: interval syntax plus an escaped character in a term literal, the same narrow escaping profile as its surround-parser twin LFV-687.
Impact class
silent wrong results
Impact note
Hits applications that pass query text to the flexible StandardQueryParser and use its fn: interval functions (default parser settings, IndexWriterConfig, codec and searcher; any scale; -ea and -da) when a term literal inside fn: contains a backslash-escaped character, typed by a user or produced by QueryParserUtil.escape: in fn:or, fn:ordered and every other composite function (at any nesting depth) and in fn:fuzzyTerm the backslashes reach the analyzer or the fuzzy automaton, so the query silently misses the documents that hold the intended text and may match documents that hold the backslash text instead (with whitespace or keyword-style analyzers every escaped character changes the result; with StandardAnalyzer mainly an escaped colon, because a:b is one token while a\:b becomes the phrase a b); quoting avoids it except for a double quote, which no fn: term literal can express today (only fn:wildcard(a\"b) reaches it, as one unanalyzed term); nothing throws and the index is not touched.
Summary
You parse fn:or(a\:b) (or fn:ordered(a\:b c), fn:fuzzyTerm(a\:b 0), fn:or("a\"b")) with StandardQueryParser and expect it to find the documents that hold a:b (or a"b), because the parser's javadoc says 'any character can be quoted with a backslash' and the same escaped literal outside fn: is parsed as the term a:b. Instead the IntervalText and IntervalFuzzyTerm grammar productions pass the raw token text, backslashes included, to AnalyzedText and FuzzyTerm, so the interval query searches for the text a\:b. With WhitespaceAnalyzer it misses the a:b document and matches a document that holds a\:b; with StandardAnalyzer it becomes BLOCK(a,b) and matches 'a b c'; no error is raised.
