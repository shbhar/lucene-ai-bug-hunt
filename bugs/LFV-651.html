TeeSinkTokenFilter: a keyword marker on a sink stops stemming every word after the first protected one

With a keyword marker and a stemmer on a TeeSinkTokenFilter sink, nothing after the first protected word is stemmed: The quick foxes jumped, quick protected, is indexed as [the, quick, foxes, jumped], not [the, quick, fox, jump]. The sink never resets attributes only its own filters add; silent since 2.9.0.

The bug in 30 seconds

#

TeeSinkTokenFilter lets one analysis feed several fields: the tee saves every token's state, and a sink replays those states later, where more filters can be added.

  1. Tee The quick foxes jumped (whitespace tokenizer, lowercased) into a field plain, and wrap a sink of the tee in SetKeywordMarkerFilter (protect quick) and PorterStemFilter for a field stemmed.
  2. You expect stemmed to get [the, quick, fox, jump], which the same two filters give directly on the tokenizer.
  3. The sink replays each token from the tee's saved state. The keyword flag exists only on the sink side, so no saved state holds it and nothing resets it: once quick switches it on, foxes and jumped still carry it and the stemmer skips them.
  4. You get [the, quick, foxes, jumped], and stemmed:fox finds 0 documents instead of 1. No error: the plain field and CheckIndex are fine.

Who is affected

#

Applications that build a TeeSinkTokenFilter in their own Java code (it has no factory; no use found in Solr, Elasticsearch or OpenSearch) and wrap a sink in a filter that flags some tokens: a keyword marker or StemmerOverrideFilter before a stemmer, PatternTypingFilter with DropIfFlaggedFilter, or NumericPayloadTokenFilter. Each value is then indexed wrong after its first flagged token.

Mechanism, terms and numbers505 words

TeeSinkTokenFilter lets one analysis chain feed several fields: the tee saves each token's state and a sink replays it later, where more filters can be added. A sink has its own copy of the tee's attributes, and SinkTokenStream.incrementToken() only calls restoreState(), never clearAttributes(). So an attribute that only the sink's own filters add is never reset between tokens. With SetKeywordMarkerFilter protecting quick before PorterStemFilter on a sink, The quick foxes jumped is indexed as [the, quick, foxes, jumped] instead of [the, quick, fox, jump], and stemmed:fox finds nothing. Silent, deterministic, in every release from 2.9.0 to 10.5.2 and main; the fix adds clearAttributes() to SinkTokenStream.incrementToken(), plus a separate super.end() hardening in end().

Terms

#
  • Attributes. A token stream describes the current token through attribute objects: the term text, offsets, position, type, and optional flags such as KeywordAttribute ("do not stem this word"). All filters of one chain share one set of attribute objects.
  • Clearing. The source at the start of a chain resets every attribute before each token ("Tokenizers must call clearAttributes() in incrementToken()", a rule LUCENE-1801 applied to every token source). Filters that only ever switch a flag on rely on that reset.
  • Tee and sink. TeeSinkTokenFilter saves each token's state with captureState(); each sink from newSinkTokenStream() replays the saved states with restoreState(). The class javadoc wraps sinks in further filters (new EntityDetect(sink1)).

The bug

#
  1. newSinkTokenStream() gives each sink its own attribute source, a copy of the tee's attributes (new SinkTokenStream(this.cloneAttributes(), cachedStates), TeeSinkTokenFilter.java:69).
  2. SetKeywordMarkerFilter and PorterStemFilter wrapped around the sink add KeywordAttribute to that copy. The tee never has it, so none of the tee's saved states (:85) contains it.
  3. SinkTokenStream.incrementToken() only calls restoreState(state) (:121). restoreState "does not affect attributes of the targetStream that are not contained in this state"; to reset them "the caller should first call TokenStream#clearAttributes() on the targetStream" (AttributeSource.java:312-316). The sink never does.
  4. KeywordMarkerFilter only ever sets the flag to true (KeywordMarkerFilter.java:45-46), and PorterStemFilter skips keyword tokens (PorterStemFilter.java:64).
  5. So: the (flag false) is stemmed; quick is protected and the flag turns on; foxes and jumped get their terms restored but keep the flag, and are not stemmed.

On the tee side the same filters are fine: they share the tokenizer's attributes, which the tokenizer clears for every token. Attributes the tee already has when the sink is created (term, type, offsets, position increment and length) are in every saved state and are restored correctly.

The numbers

#

The quick foxes jumped: the sink chain gives [the, quick, foxes, jumped], the same chain on the tokenizer [the, quick, fox, jump]. Indexed with the tee as plain and the sink as stemmed (the documented order), stemmed:fox and stemmed:jump find 0 documents and plain:foxes finds 1. Adding KeywordAttribute to the tee before creating the sink gives the right terms. The test framework's own check reports "clearAttributes() was not called correctly in TokenStream chain at token 0" on a plain sink.

Exposure and likelihood285 words
  • Who is exposed. Only chains built in Java: TeeSinkTokenFilter has no analysis factory (Lucene's factory test lists it as a "crazy component" without one), so CustomAnalyzer and factory-based schemas cannot reach it. A read-only code search found no use in Elasticsearch, OpenSearch or Solr (default branches only; private applications are unknown).
  • What triggers it. A sink-side filter that sets an attribute on some tokens only and relies on the chain's source to reset it. Executed: SetKeywordMarkerFilter, PatternKeywordMarkerFilter or StemmerOverrideFilter before PorterStemFilter, EnglishMinimalStemFilter ([cat, exempt, dogs] instead of [cat, exempt, dog]) or KStemFilter; StemmerOverrideFilter {dogs->canine, mice->mouse} also blocks its own second override ([canine, running, mice, walking] instead of [canine, run, mouse, walk]); PatternTypingFilter (digit tokens) + DropIfFlaggedFilter keeps only [order] of order 42 shipped to alice instead of [order, shipped, to, alice]; NumericPayloadTokenFilter gives later tokens the number's payload.
  • Scale. In every value with a flagged token, the flagged token itself is right, but the attribute stays stale on all later tokens, and the output is wrong wherever a later filter depends on its default (here every later word the stemmer would change); deterministic, any size, assertions on or off. If one tee/sink chain is reused for several documents, the flag carries into the next document (foxes jumped indexed as [foxes, jumped]).
  • Effect. Wrong terms or payloads in the sink field only; queries on it miss documents (or over-match on payloads). The tee's field and stored values are right, CheckIndex is clean, and documents stay wrong until reindexed.
  • Not affected. The same filters on the tee side; attributes added to the tee before the sink is created; sink-side filters that set their attribute on every token.

Why it is a bug, not intended

#
  • restoreState leaves attributes the state lacks unchanged and tells the caller, here the sink, to call clearAttributes() first.
  • The javadoc and the 5.5.0 CHANGES entry (LUCENE-6973) say to wrap sinks in "any other TokenFilter"; nothing limits their attributes.
  • Lucene's test-framework check fails on a plain sink; the upstream test avoids it by also adding its check attribute to the tee.
The full argument245 words
  • Contract. AttributeSource.restoreState (AttributeSource.java:312-316): attributes not in the state "remain unchanged"; to reset them "the caller should first call TokenStream#clearAttributes() on the targetStream". The package docs: "Tokenizers must call AttributeSource#clearAttributes() in incrementToken()" (package-info.java:404-405). LUCENE-1801 (#2876, 2009) applied that rule to "All Tokenizers/TokenStreams that are source of tokens"; a reviewer there noted that restoreState() alone is not enough. SinkTokenStream already existed and was not changed.
  • Documented use. Class javadoc: sinks "will further do additional token filtering" (TeeSinkTokenFilter.java:49-51, example new EntityDetect(sink1) at :41). CHANGES 5.5.0 (API Changes), LUCENE-6973: "If you wish to filter the sinks, you can wrap them with any other TokenFilter (e.g. a FilteringTokenFilter)." PorterStemFilter alone adds KeywordAttribute to the sink.
  • Tests. TestTeeSinkTokenFilter.testGeneral adds CheckClearAttributesAttribute to the tee and to the sink (:123-124), so the check value rides in the saved states. No upstream test puts an attribute on the sink only. With it on the sink only the check fails; that is supporting evidence, and the stock filters' wrong terms are the stronger evidence.
  • end(). TokenStream.end(): "If you override this method, always call super.end()" (TokenStream.java:156); SinkTokenStream.end() does not, so a sink-only attribute keeps its last-token value after end(). This is a separate, smaller contract gap: the wrong terms come from incrementToken() alone.
  • History. The restore-only incrementToken() came with the class (LUCENE-1693, 2009) and survived the LUCENE-6973 rewrite (2016, first released in 5.5.0); no commit ever added clearAttributes() to the sink.
The devil's-advocate check235 words

Strongest case (rated weak by the intended-lens reviewer from another model family, the independent reproducer and the devil's advocate; moderate by the refute-lens reviewer and by the cross-model fact check of this doc): the package rule names only Tokenizers; restoreState says a reset "might be desirable"; CachingTokenFilter also restores without clearing and its end() also skips super.end(); the 2009 design wanted a sink with "exactly the same attributes as the TeeSinkTokenFilter"; a committer wrote on dev@ in 2014 that "clearAttributes() is not needed before restoreState()"; the Lucene.NET port suppressed its warning about the missing base.End() as intended.

Why it fails: CachingTokenFilter shares its chain's attributes, so filters after it are in its states (the same keyword chain over a CachingTokenFilter replay is correct), while a sink has a separate copy by construction. The javadoc puts the reset on the caller; the package rule's wording names Tokenizers, and LUCENE-1801 applied it to every TokenStream that is a source of tokens, which a sink is. The "same attributes" remark was about creating the sink; the same javadoc wraps sinks in filters. The 2014 remark was about a filter whose state covers the whole shared chain. The Lucene.NET rationale ("calling base.End() would clear the attributes that RestoreState then sets") does not hold when super.end() runs before restoreState. Verdict: a defect. Expect the reply "add the attribute to the tee first": it works, but nothing documents it.

Suggested fix

#

Recommended Clear before restoring, and call super.end() (validated)

In SinkTokenStream, call clearAttributes() before restoreState(state) (this alone fixes the wrong terms) and, as separate end-of-stream hardening, super.end() first in end() (+3 lines). The new test then passes 5 of 5; the lucene/analysis/common module (1,914 tests, 18 skipped) has 0 failures, assertions on and off. Tee attributes are unchanged: the restored state overwrites them.

#

Two calls in SinkTokenStream (TeeSinkTokenFilter.java:121, :126): each sink token starts from cleared attributes, as on any tokenizer-rooted chain, and end() runs endAttributes() before restoring the tee's final state. Trade-offs

  • Tee attributes do not change: every one is in every saved state and is restored right after the clear (assuming, as TokenStream requires, that the tee's attributes are all added before tokens are captured). Only sink-only attributes change, to their per-token default.
  • Cost: one clearAttributes() per sink token; not benchmarked.
  • A sink-side filter that relied on its attribute persisting across tokens would change; none is known.
  • Existing indexes keep their wrong terms until reindexed.
  • In a path the model treats as a caller error (consumeAllTokens() without the tee's end(), so no final state exists), the sink's end-of-stream values are wrong with or without the fix (3,579 of 4,092 model inputs on stock, 4,089 with it).
  • The same lines are in every 9.x and 10.x release, and the +3-line diff applies cleanly (git apply --check) to the 10.5.2 and 9.12.3 sources; only main was built with gradle.

Document the limitation

#

Say in the class javadoc that sink-side filters' attributes are never reset and must be added to the tee before newSinkTokenStream().

Trade-offs

No code change, so every existing chain stays wrong; stock filters such as PorterStemFilter add KeywordAttribute without the user asking.

How it was found

#

Bounded-exhaustive translation validation of TeeSinkTokenFilter against a reference model. While modelling a sibling bug, the finder read the sink code and added a scenario with a sink-side filter that flags one token: the real class mismatched on 4,032 of 4,092 inputs, every input with two or more tokens.

The method in full173 words

Method: bounded-exhaustive translation validation (semi-formal tier). A reference model of the tee and its sinks was compared with the stock jar on every input up to a small scope: 0 to 4 tokens, position increments 1 or 2, offset gaps 0 or 1, final position increment 0 or 1, final offset slack 0 or 1, and 1 to 3 sinks.

  • The hypothesis came from reading SinkTokenStream while modelling the sibling bug (an attribute added to the tee after a sink exists makes restoreState throw).
  • New scenario F wraps each sink in a filter that adds KeywordAttribute and sets it on one token only, relying on the source's clear, and compares the result with the same filter run on the input itself. Stock main: 4,032 of 4,092 inputs mismatch; the documented-use scenarios A, C and D: 0.
  • The finding was reduced to a public-API JUnit on the stock main jars, then checked by a reviewer from another model family (OpenAI GPT-5.6) in lenses, an independent reproducer, a devil's advocate, an adjudication and an audit.

Bug record

LFV-651, snapshot of 2026-10-29

Registry title
TeeSinkTokenFilter: a sink never clears attributes that only its own filter chain adds (SinkTokenStream.incrementToken() calls restoreState() without clearAttributes()), so a keyword marker or StemmerOverrideFilter before a stemmer on a sink silently leaves every token after the first protected word unstemmed
Area
analysis / TeeSinkTokenFilter (SinkTokenStream replay through AttributeSource.restoreState without clearAttributes(): attributes that only the sink's chain adds)
Priority
Medium, rank 143: A keyword marker or stemmer override on a TeeSinkTokenFilter sink silently stops stemming everything after the first protected word on ordinary text, but the class has no factory and no downstream engine uses it, so it closes the KeywordAttribute group after LFV-360 and LFV-620.
Impact class
silent wrong results
Impact note
Hits applications whose own Java code builds a TeeSinkTokenFilter (the class has no factory, so analysis configuration cannot reach it, and a code search finds no use in Solr, Elasticsearch or OpenSearch) and wraps a sink in a filter that sets an attribute on some tokens only and relies on the chain's source to clear it: a keyword marker (SetKeywordMarkerFilter, PatternKeywordMarkerFilter) or StemmerOverrideFilter before a stemmer, PatternTypingFilter with DropIfFlaggedFilter, or NumericPayloadTokenFilter; then every value that contains one marked token is indexed wrong in the sink field after that token (later words unstemmed, dropped or given a payload), silently and deterministically with -ea and -da at any size, so queries on that field miss or over-match; the tee's own field, the stored value and CheckIndex are fine, a reused tee/sink chain carries the stale value into the next document, and the same filters on the tee side, or adding the attribute to the tee before newSinkTokenStream() (undocumented), avoid it.
Summary
You index one field from a TeeSinkTokenFilter and a second field from one of its sinks, wrapped in a keyword marker and a stemmer (for example SetKeywordMarkerFilter protecting 'quick', then PorterStemFilter), and expect the sink field to get what the same chain gives on the tokenizer: [the, quick, fox, jump] for 'The quick foxes jumped'. Instead it gets [the, quick, foxes, jumped]: the sink replays each token with restoreState() but never calls clearAttributes(), and the KeywordAttribute that only the sink's chain added is not in the tee's captured states, so once 'quick' is marked as a keyword every later token stays marked and is not stemmed.
