An empty reader in an index-sorted addIndexes(CodecReader...) takes a merged doc id, so the postings of later documents point one document too far

Add a sorted segment {a, c} and an empty reader to an index-sorted writer with addIndexes(CodecReader...), and the empty reader's nonexistent doc 0 takes merged id 0. The postings shift by one: id:a returns the document that stores c, and with assertions off addIndexes and the commit report no error.

The finding in 30 seconds

#

Background: how an index-sorted merge numbers documents

#
  1. With IndexWriterConfig.setIndexSort, every segment keeps its documents in sort order. When inputs are merged, for example by addIndexes(CodecReader...), MultiSorter merge-sorts them: a priority queue holds one cursor per input, and each pop gives the next document the next merged doc id.
  2. The result is one doc map per input (old id to merged id). Postings are rewritten through these maps; stored fields are copied in merge order, one after the other, so the two agree only if the maps are dense: 0, 1, 2, ...

The finding, step by step

#
  1. Index two documents, a (k = 1) and c (k = 2), into a writer sorted by the long field k. On a second writer with the same sort, call addIndexes(segment, empty), where empty has maxDoc() == 0 and advertises the sort: SortingCodecReader.wrap(SlowCodecReaderWrapper.wrap(new ParallelLeafReader()), sort).
  2. You expect a 2-document segment in which id:a finds the document that stores a, as you get without an index sort or with the empty reader listed first.
  3. The sorting merge also puts a cursor at doc 0 of the empty reader. That document does not exist and has no k, so it sorts as the missing value 0, before a, and takes merged id 0. a gets 1 and c gets 2, but the new segment has maxDoc 2.
  4. Stored fields are written in order (doc 0 = a, doc 1 = c), postings at the shifted ids. id:a returns doc 1, which stores c; id:c points at doc 2, past the end.
  5. With assertions off, addIndexes and commit succeed; of the integrity checks only CheckIndex at level 2 or higher reports doc 2 >= maxDoc 2, and loading the id:c hit throws IllegalArgumentException. With assertions on, a stored-fields merge assertion fails inside addIndexes.

Who is affected

#

Applications that call addIndexes(CodecReader...) on an index-sorted writer and pass a reader with no documents that advertises the sort, such as an empty ParallelLeafReader wrapped with SortingCodecReader. Readers of real indexes never have empty leaves, so ordinary indexing and merging are safe. Two documents are enough, and every release since 6.2.0 has it.

Mechanism, terms and numbers527 words

With an index sort, IndexWriter.addIndexes(CodecReader...) merge-sorts its inputs with MultiSorter.sort. Its init loop puts a cursor at doc 0 of every input, including one with maxDoc() == 0, and the merge loop gives that nonexistent document a merged doc id before it notices the reader is exhausted (MultiSorter.java:106-135 at 5adff78bb168). Every real document the merge places after it is mapped one id too far, while the merged segment's maxDoc counts only real documents. Stored fields are written in merge order and postings at the shifted ids: with a sorted segment {a k=1, c k=2} and an empty reader that advertises the sort, id:a returns the document that stores c, and id:c points at doc 2 of a 2-document segment. With assertions off the commit succeeds and id:a silently returns the wrong document; loading the id:c hit throws, and of the integrity checks only CheckIndex at level 2 or higher reports it; with assertions on a stored-fields merge assertion fails inside addIndexes. Every release since 6.2.0 (LUCENE-6766, 2016) has it. The empty input must be built by the application, so the priority is Low.

The mechanism (main 5adff78bb168, lucene/core/src/java/org/apache/lucene/index/)

#
  1. Accepted input. addIndexes(CodecReader...) validates each reader's created version, minVersion and index sort, not its size (IndexWriter.java:3228-3252). With an index sort, addIndexesReaderMerge skips the reorder path (:3548-3560) and MergeState calls MultiSorter.sort (MergeState.java:223).
  2. A cursor for an empty input. The init loop creates a cursor at doc 0 for every reader and reads its sort value, with no maxDoc() > 0 check (MultiSorter.java:106-112, the fix site). For the empty reader advanceExact(0) finds no value (IndexSorter.java:297), so the LONG sorter uses its missing value 0L (:285-290). That call is outside the advanceExact contract: the target "must be a valid doc ID, ie. >= 0 and < maxDoc" (DocValuesIterator.java:25-27).
  3. The phantom takes an id. The queue pops the smallest value: the phantom doc 0 (value 0) before a (1). The loop records builders[1].add(0) and increments mappedDocID (MultiSorter.java:125-128; no deletions), and only then sees docID 1 >= maxDoc 0 and pops the reader (:129-135). a gets 1 and c gets 2.
  4. The shifted maps are used. Reader 0 popped after reader 1, so isSorted is false (:120-123) and the maps are returned (:137-155) instead of null.
  5. Two views disagree. The merged maxDoc is the sum of the inputs' numDocs(), 2 (MergeState.java:170-173). Stored fields are written with a running count (codecs/StoredFieldsWriter.java:146-158; with assertions on, assert sub.mappedDocID == docCount at :152 fails), so doc 0 stores a and doc 1 stores c, while the postings use the mapped ids 1 and 2.

Only documents the merge places after the phantom are shifted: with three inputs, a document with k = -3 sorts before the phantom and keeps id 0, while documents with k = 5 and 7 get ids 2 and 3 in a segment of maxDoc 3 (executed). A reader whose documents are all deleted is not the trigger: deleted documents take no merged id (MultiSorter.java:126-128).

Exposure and likelihood200 words
  • Who. Callers of addIndexes(CodecReader...) on an index-sorted writer whose inputs include a reader with maxDoc() == 0 that advertises the same sort (since 8.0 a sorted writer rejects inputs that do not, LUCENE-8505). SortingCodecReader's javadoc names this use: re-sorting by wrapping readers and adding them to a fresh writer "via IndexWriter#addIndexes(CodecReader...)" (SortingCodecReader.java:47-50).
  • Not hit. Lucene has not written 0-document segments since LUCENE-5173 (lucene/CHANGES.txt:13474), so DirectoryReader leaves are never empty and ordinary indexing, merges and addIndexes(Directory...) never see this input. The same inputs into an unsorted writer pass, and so does the empty reader listed first, where the pop order equals the reader order and sort returns null (both executed).
  • Default vs opt-in. Opt-in: index sorting, the expert addIndexes(CodecReader...) and, in practice, the @lucene.experimental SortingCodecReader.
  • Effect. Silent, durable corruption: the commit succeeds and a term query returns the neighbouring document; a hit at doc == maxDoc makes StoredFields.document throw IllegalArgumentException ("docID must be >= 0 and < maxDoc=2 (got docID=2)" in the history runs, and in a cross-model reviewer's run). The default CheckIndex level 1 checks checksums only (CheckIndex.java:4742-4754); postings are checked from level 2 (:1114-1125).
  • Scale. Two documents; no concurrency.

Why it looks unintended

#
  • MultiSorter.sort promises doc maps that "map each leaf's documents into the merged segment"; an empty leaf has nothing to map, yet takes an id.
  • addIndexes(CodecReader...) says "empty segments are dropped", and upstream TestParallelReaderEmptyIndex passes the same empty reader, unwrapped, to addIndexes.
  • MultiSorter calls advanceExact(0) on a reader with maxDoc 0, which DocValuesIterator forbids (the target must be below maxDoc).
The full argument173 words
  • Contract. MultiSorter.sort returns doc maps "to map each leaf's documents into the merged segment" (MultiSorter.java:35-40). addIndexes(CodecReader...): "empty segments are dropped by this method and not added to this index" (IndexWriter.java:3262). Since LUCENE-5173 that is enforced on the merged output (SegmentMerger.shouldMerge, SegmentMerger.java:101-103), so it is the API promise that an empty input is harmless, not a filter that was bypassed.
  • Tests. TestParallelReaderEmptyIndex.testEmptyIndex calls addIndexes(SlowCodecReaderWrapper.wrap(new ParallelLeafReader())) ("should not throw any exception", TestParallelReaderEmptyIndex.java:34-50); TestAddIndexes.testAddEmpty and testFakeAllDeleted assert "empty segments should be dropped by addIndexes" (TestAddIndexes.java:1568-1604). No upstream test combines an empty input with an index sort.
  • History. LUCENE-5173 (fe938c64edd, 2013) replaced LUCENE-5116's per-input empty filter with the check on the merged output, so empty inputs reach the merge code; in that thread Uwe Schindler expected that something outside SegmentMerger "could maybe insert empty readers into the merge queue" (#6237). The 2016 MultiSorter (LUCENE-6766) queued every reader, and its issue (#7824, 40 comments) never discusses empty inputs.
  • Effect. Silent corruption, not a clean rejection.
The devil's-advocate check104 words

The strongest case for "not a bug": Lucene never writes 0-document segments, so the input exists only if the application builds it and wraps it in the experimental SortingCodecReader; the "dropped" promise is about the output; and the effect needs a reader order that forces a reorder.

Why it fails: that bears on likelihood, not intent. The API accepts the input, an upstream test uses the same empty reader, MultiSorter breaks the advanceExact contract on it, and the result is silent corruption. A credibility audit's committer-style view agreed it is real and the fix small, while pushing back on severity; hence priority Low.

Suggested fix

#

Recommended Skip readers with maxDoc() == 0 in MultiSorter's init loop (fix A)

Skip readers with maxDoc() == 0 in MultiSorter's init loop, after creating their (unused) doc-map builder: +4/-1 in MultiSorter.java. The repro passes with assertions on and off, and 107 tests of TestIndexSorting, TestAddIndexes, TestSortingCodecReader and TestParallelReaderEmptyIndex pass.

    for (int i = 0; i < leafCount; i++) {
      CodecReader reader = readers.get(i);
      builders[i] = PackedLongValues.monotonicBuilder(PackedInts.COMPACT);
      if (reader.maxDoc() == 0) {
        continue; // nothing to map; a cursor at doc 0 would take a merged doc id
      }
      LeafAndDocID leaf = new LeafAndDocID(i, reader.getLiveDocs(), reader.maxDoc());
      setComparableValues(comparables, parents[i], i, leaf.docID);
      queue.add(leaf);
    }

Skip readers with maxDoc() == 0 in MultiSorter's init loop (fix A) (validated by the checks) (recommended)

#

Create every builder first (an empty reader's doc map is never called), then skip the empty reader, so it never enters the queue and takes no merged id.

    for (int i = 0; i < leafCount; i++) {
      CodecReader reader = readers.get(i);
      builders[i] = PackedLongValues.monotonicBuilder(PackedInts.COMPACT);
      if (reader.maxDoc() == 0) {
        continue; // nothing to map; a cursor at doc 0 would take a merged doc id
      }
      LeafAndDocID leaf = new LeafAndDocID(i, reader.getLiveDocs(), reader.maxDoc());
      setComparableValues(comparables, parents[i], i, leaf.docID);
      queue.add(leaf);
    }

Trade-offs

One maxDoc() call per input; by reading the diff, non-empty inputs go through the loop as before; it also removes the out-of-contract advanceExact(0) call. Without the empty reader in the queue, the remaining pop order decides isSorted as if it were absent.

  • Earlier runs: equivalent changes (same logic; headers and comment differ) pass the finder's and reviewers' tests and 64, 103 and 67 upstream tests; the equivalent change at 6.2.0 makes the scenario pass there.

Drop maxDoc() == 0 inputs in addIndexes(CodecReader...) (not built)

#

Filter empty readers at the entry point, as the javadoc's "empty segments are dropped" suggests.

Trade-offs

Would also cover LFV-318, a different failure from the same kind of empty input on the unsorted reorder path: the first document after the empty reader loses its stored fields and term vectors (fix site SlowCompositeCodecReaderWrapper.docIdToReaderId). It changes what the merge policy's findMerges(CodecReader...) sees and leaves MultiSorter itself unguarded; it can complement A.

Rely on open PR #16571 (not run)

#

In Jim Ferenczi's PR "Let a merge write more than one segment", a MultiSorter commit by Michael Marshall queues a reader only when docID < maxDoc after skipping deleted documents; by reading its head e869d510b30, that also removes this bug.

Trade-offs

The PR is about range-restricted readers, never mentions empty ones and is not merged; the regression test is worth adding either way.

Downstream note

#

Downstream, a term query or filter over a segment built this way returns the neighbouring document's stored fields, so an application that filters by a term (for example a tenant or access term) can show a document the filter did not select.

How it was found

#

A proof-obligation audit of MultiSorter.sort's contract: its doc maps must map every input's documents into the merged segment, for every input that addIndexes(CodecReader...) accepts. A reader with maxDoc 0 is accepted, and the init loop still queues a cursor for it; a public-API JUnit test then witnessed the shifted ids.

The method in full147 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The finder read MultiSorter.sort against its javadoc obligation (doc maps that "map each leaf's documents into the merged segment") and against what addIndexes(CodecReader...) accepts (validateMergeReader checks version and sort, not size). For an input with maxDoc 0 the obligation is that it maps nothing; the init loop and merge loop give it one id.
  • The finder then wrote a public-API JUnit test (three inputs: two documents, the empty reader, one document) that fails on main with assertions on and off and on 10.6.0 and 10.0.0, and a skip-empty fix that passes it and 64 upstream tests.
  • An independent reproducer wrote the smaller 2-document test that this doc's repro is trimmed from; two executed cross-model reviews, a devil's-advocate verifier and an adjudication reproduced it with their own tests ("Prior reports, history and checks").

History

#

Introduced in 6.2.0 by LUCENE-6766 ("LUCENE-6766: initial patch", Mike McCandless, 2016), which made index sorting a core IndexWriterConfig feature and added MultiSorter; the loop is unchanged since. It fails on every release that was run, 6.2.0 to 10.6.0, and on main; not fixed upstream.

No PR. The trigger form changed, the bug did not: 6.2.0-7.7.3 accept any maxDoc-0 reader into a sorted writer; from 8.0.0 the input must advertise the sort (LUCENE-8505); 8.7.0 added SortingCodecReader (LUCENE-9484). Before 6.4.0 even the empty-first order corrupts; LUCENE-7568's isSorted fast path (6.4.0) masks that order. Not fixed upstream: the last commit to MultiSorter.java is e6f12f31d08 (#16202, 2026-06-05).

Impact note

Summary
You sort an IndexWriter by a long field k and call addIndexes(CodecReader...) with the single segment of a sorted 2-document index {a k=1, c k=2} followed by an empty reader that advertises the same sort (SortingCodecReader.wrap(SlowCodecReaderWrapper.wrap(new ParallelLeafReader()), sort)), and you expect a 2-document segment in which a TermQuery on id:a returns the document that stores a, as it does without an index sort or with the empty reader listed first. Instead MultiSorter.sort also queues a cursor at doc 0 for the empty reader, whose nonexistent doc 0 (missing sort value 0) is popped first and takes merged doc id 0, so a and c are mapped to 1 and 2 while the new segment has maxDoc 2. With assertions disabled addIndexes and commit succeed, but id:a returns the document that stores c and the posting of id:c points at doc 2 (>= maxDoc 2), which only CheckIndex at level 2 or higher reports.
