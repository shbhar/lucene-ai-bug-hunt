docIDRunEnd() on a two-phase disjunction's approximation rewrites the scorer's list of matching clauses, so score() adds a non-matching clause or never returns

Calling docIDRunEnd() on the approximation of an OR query with a phrase clause, between the match check and score(), rewrites the scorer's list of matching clauses: score() returns 0.59193045 instead of 0.06880058, or hangs if the phrase matches. No Lucene code makes this call; only custom scorer-driving code is hit.

The finding in 30 seconds

#

A disjunction scorer keeps the clauses that match the current document in a linked list, and a call on its approximation that is documented not to move it rewrites those links.

Background: two-phase disjunctions and docIDRunEnd()

#
  1. Some queries check a document in two phases. A phrase query first finds the documents that contain all its terms (its approximation), then matches() checks that the terms are adjacent and in order. An OR query (a disjunction) with such a clause is two-phase too: its approximation is the union of its clauses' approximations.
  2. Once matches() says yes, the disjunction scorer remembers which clauses really match the current document, so that score() adds up exactly their scores and getChildren() lists exactly them.
  3. docIDRunEnd() asks an iterator where the run of consecutive matching documents that starts at the current one ends, so that bulk scorers can handle whole ranges at once. It is documented not to affect the iterator's position.

The finding, step by step

#
  1. Index two documents, 0: "b a c" and 1: "c", and score BooleanQuery(SHOULD f:c, SHOULD "a b") with ScoreMode.COMPLETE and a plain IndexSearcher. Only f:c matches doc 0 ("a b" is not in "b a c"); a fresh scorer gives doc 0 the score 0.06880058.
  2. Move a second scorer to doc 0 with iterator().nextDoc() and call twoPhaseIterator().approximation().docIDRunEnd(). It returns 1 and the scorer stays on doc 0. The method is documented not to affect the iterator's position, so you expect score() to give 0.06880058 again.
  3. Instead score() returns 0.59193045, with no error, assertions on or off: the phrase, which does not match doc 0, is added in. getChildren() also lists the phrase as a second child.
  4. Why: the match check chains the clauses that match doc 0 through the shared field DisiWrapper.next (here only f:c). docIDRunEnd() walks the clause heap with topList(), which rewrites the same field; because the cheaper phrase is the heap's top, it links the phrase behind f:c (with the costs swapped the score stays correct). If the phrase does match doc 0 (doc 0 = "a b c"), the chain becomes a loop and score() never returns.

Who is affected

#

Only custom code that drives a scorer itself (a BulkScorer, collector or scorer wrapper) and calls docIDRunEnd() on a two-phase disjunction's approximation between the match check and score(), when the two-phase clause is ahead of the plain clause in the heap. IndexSearcher and Lucene's own collectors and bulk scorers never make this call. Default settings; two documents suffice.

Mechanism, terms and numbers576 words

A disjunction scorer with a two-phase clause (a phrase, a doc-values range, ...) records in matches() which clauses really match the current document, by chaining them through the shared field DisiWrapper.next; score() and getChildren() later walk that chain (DisjunctionScorer.java:83-157, :178-193 at 5adff78bb168). DisjunctionDISIApproximation.docIDRunEnd() walks its clause heap with topList(), which rewrites the same fields (DisjunctionDISIApproximation.java:220-233, DisiPriorityQueue2.java:55-66). Called on twoPhaseIterator().approximation() between matches() and score(), when the two-phase clause is ahead of the plain clause in the heap, it puts a non-matching clause onto the chain: with {0: "b a c", 1: "c"} and BooleanQuery(SHOULD f:c, SHOULD "a b"), score() on doc 0 returns 0.59193045 instead of 0.06880058 (and getChildren() lists the phrase); when the phrase does match, the chain becomes a cycle and score() never returns. Assertions on and off, every release since 10.2.0 (#14363). docIDRunEnd() is documented not to affect the iterator's position; no Lucene code makes this call, so only application code that drives scorers itself is hit, and tests that go through newSearcher() cannot see it.

The mechanism (main 5adff78bb168, lucene/core/src/java/org/apache/lucene/search/)

#
  1. The list of verified matches. DisjunctionScorer.TwoPhase.matches() builds "the list of verified matches on the current doc" (DisjunctionScorer.java:83-84) through DisiWrapper.next: it walks approximation.topList() (:123), moves each plain clause onto verifiedMatches with w.next = verifiedMatches (:126-129), queues two-phase clauses as unverified (:136), and returns true without checking them when a plain clause matched (:141-143). In the repro the list is f:c with f:c.next = null, and the phrase is queued.
  2. Reading it. score() and getChildren() call getSubMatches() (:178-181, :186-193), which checks the queued two-phase clauses and prepends each one that matches with w.next = verifiedMatches (:95-106, :99), then walk the list until null (DisjunctionSumScorer.java:40-46).
  3. The relinking call (fix site). DisjunctionDISIApproximation.docIDRunEnd() walks leadIterators.topList() when the heap top is on the current doc (DisjunctionDISIApproximation.java:220-233, loop at :228). DisiPriorityQueue2.topList() writes top.next = null and, when both entries are on the same doc, top2.next = top (DisiPriorityQueue2.java:55-66); DisiPriorityQueueN.topList() relinks the same way for larger heaps (DisiPriorityQueueN.java:72-106). next is that shared field ("see #topList", DisiWrapper.java:36).
  4. The result. In the repro the phrase is the heap's top and f:c the second entry, so the call sets f:c.next = phrase. getSubMatches() finds that the phrase does not match, and the walk f:c -> phrase adds the phrase's score and lists it as a child. When the phrase matches, getSubMatches() prepends it (phrase.next = f:c) and the list is the cycle phrase -> f:c -> phrase: score() spins in the loop at DisjunctionSumScorer.java:43 (with -ea in the assertion loop at DisjunctionScorer.java:108-116). getChildren() was not run alone in this state; by the code it spins in the same assertion loop with -ea, and with -da its loop (DisjunctionScorer.java:186-193) keeps adding children until it runs out of memory.
  5. Heap order decides. With the clause costs swapped (the term clause on top of the heap) the relinking leaves f:c.next = null and the score is correct. A three-clause heap (f:c, f:d, "a b" on {0: "b a c d", 1: "c d", 2: "c d"}, a DisiPriorityQueueN) was run too: the call adds the phrase and drops one of the two matching term clauses (0.7906376 instead of 0.1007784), and fix B corrects it.
Exposure and likelihood310 words

Code that drives scorers itself (a custom BulkScorer, collector or scorer wrapper) and calls docIDRunEnd() on twoPhaseIterator().approximation() of a positioned disjunction scorer that has a two-phase clause, after matches() and before score() or getChildren(). Why it looks unintended

#
  • docIDRunEnd() is documented not to move the iterator ("The current position of this iterator is not affected"); score() must give "the score of the current document".
  • The repro calls matches() once and never moves the approximation; Lucene itself calls docIDRunEnd() on positioned iterators.
  • Heap order decides: correct with the costs swapped, wrong otherwise, a hang if the phrase matches.
The full argument202 words
  • Contract. DocIdSetIterator.docIDRunEnd(): "The current position of this iterator is not affected by calling docIDRunEnd()" (DocIdSetIterator.java:245-263, item 3 at :252). Scorable.score(): "Returns the score of the current document matching the query" (Scorable.java:27); getChildren(): "Returns child sub-scorers positioned on the current document" (:57). Nothing in Scorer, TwoPhaseIterator or DisjunctionScorer says docIDRunEnd() invalidates matches().
  • Protocol followed. matches() is called once (through iterator().nextDoc()), as TwoPhaseIterator requires (TwoPhaseIterator.java:96-102), and the approximation never moves, so it stays in step with the iterator (Scorer.java:49-51).
  • Lucene itself asks positioned iterators for docIDRunEnd() and keeps using them. DisjunctionDISIApproximation.docIDRunEnd() calls docIDRunEnd() on the lead-heap clauses positioned on the current doc (DisjunctionDISIApproximation.java:227-230), and DenseConjunctionBulkScorer calls it on plain clauses' approximations (:49).
  • History. The verified-match list via next dates from LUCENE-6815 (1967050202d, 2015) and was harmless alone. #14363 (jpountz, 2025) added the topList()-based override ("takes the max #docIDRunEnd() across top clauses"); #16142 (costin, 2026) narrowed it to leadIterators.topList(). Neither PR or its reviews mention the shared links (#14363 has one empty review and no comments; #16142's comment, review comments and reviews discuss tests, run length, cost and CHANGES only).
The devil's-advocate check155 words

The strongest case for "not a bug": docIDRunEnd() literally promises only an unchanged position; DisjunctionDISIApproximation is @lucene.internal and TwoPhaseIterator @lucene.experimental; for two-phase iterators the run-end API is TwoPhaseIterator.docIDRunEnd(), which Lucene's own consumers use; and no in-tree caller makes the call.

Why it fails: the caller never names the internal class, it gets a plain DocIdSetIterator from public methods; the two methods answer different questions (the TwoPhaseIterator default means "no known run", TwoPhaseIterator.java:120-132); Lucene calls the approximation's docIDRunEnd() itself; "experimental" means the API may change, not that it may silently corrupt state. What survives is reach, hence priority Low. The closest precedent, #15324 / #15380, was fixed in the caller because MaxScoreBulkScorer advanced the approximation without matches(), which does break the protocol; here nothing moves. The contract does not promise that docIDRunEnd() has no other effect, so documenting the restriction or a caller-side answer (fix option D) would be a legitimate resolution.

Suggested fix

#

Recommended Walk the heap's top entries without writing next (fix B)

Walk the clause heap's top entries without topList(): a new package-private DisiPriorityQueue.maxDocIDRunEndOnTop(int) visits the same entries but never writes DisiWrapper.next (+40/-3 in 4 files, same cost as today). The repro passes with assertions on and off, the hang probe returns, and 156 tests in 13 classes (12 related suites and the repro) pass.

// DisjunctionDISIApproximation.docIDRunEnd(): no topList(), which rewrites DisiWrapper.next
if (leadTop.doc == doc) {
  maxDocIDRunEnd = leadIterators.maxDocIDRunEndOnTop(maxDocIDRunEnd);
}
// DisiPriorityQueueN (DisiPriorityQueue2 checks top and top2 the same way)
private int maxDocIDRunEndOnTop(int runEnd, int doc, int i) throws IOException {
  if (i < size && heap[i].doc == doc) {
    runEnd = Math.max(runEnd, heap[i].approximation.docIDRunEnd());
    final int left = leftNode(i);
    runEnd = maxDocIDRunEndOnTop(runEnd, doc, left);
    runEnd = maxDocIDRunEndOnTop(runEnd, doc, rightNode(left));
  }
  return runEnd;
}

Walk the heap's top entries without writing next (fix B) (validated by the checks) (recommended)

#

Add a package-private DisiPriorityQueue.maxDocIDRunEndOnTop(int), implemented in DisiPriorityQueue2 (top, and top2 if on the same doc) and DisiPriorityQueueN (the same recursion as topList()), that returns the max of the entries' approximation docIDRunEnd() without touching DisiWrapper.next, and call it from DisjunctionDISIApproximation.docIDRunEnd().

// DisjunctionDISIApproximation.docIDRunEnd(): no topList(), which rewrites DisiWrapper.next
if (leadTop.doc == doc) {
  maxDocIDRunEnd = leadIterators.maxDocIDRunEndOnTop(maxDocIDRunEnd);
}
// DisiPriorityQueueN (DisiPriorityQueue2 checks top and top2 the same way)
private int maxDocIDRunEndOnTop(int runEnd, int doc, int i) throws IOException {
  if (i < size && heap[i].doc == doc) {
    runEnd = Math.max(runEnd, heap[i].approximation.docIDRunEnd());
    final int left = leftNode(i);
    runEnd = maxDocIDRunEndOnTop(runEnd, doc, left);
    runEnd = maxDocIDRunEndOnTop(runEnd, doc, rightNode(left));
  }
  return runEnd;
}

Trade-offs

Same cost as today: only the entries on the current doc are visited. The price is a new method on a sealed internal class and a second heap walk to keep in step with topList(). No benchmark was run.

In DisjunctionDISIApproximation.docIDRunEnd(), replace the topList() loop with for (DisiWrapper w : leadIterators) and if (w.doc == doc). +6/-2 in one file.

Trade-offs

The smallest change, but O(lead heap size) per call instead of O(lead clauses on the current doc), plus an iterator allocation; the method's comment (DisjunctionDISIApproximation.java:222-225) and #16142 show that this per-call cost was a deliberate concern. Equal cost for a two-entry heap.

Let DisjunctionScorer.TwoPhase keep its own links (not built)

#

Record the verified clauses in an array in matches() and link them in getSubMatches().

Trade-offs

Robust against any other walk of next between matches() and score(), but it adds work to the per-document scoring path of every two-phase disjunction.

Document the restriction (not built)

#

Say on Scorer#twoPhaseIterator() or in DisjunctionScorer that the approximation's docIDRunEnd() must not be called between matches() and score().

Trade-offs

No code change, and a legitimate answer for an expert, @lucene.experimental API; but it leaves a silent wrong score and a hang behind a call that the DocIdSetIterator contract documents as not affecting the iterator's position, and that nothing documents as invalidating matches().

Downstream note

#

A downstream engine whose own bulk scorer or collector added this run-length call would give ordinary phrase-plus-term OR queries wrong scores, or a search thread that never finishes.

How it was found

#

A proof-obligation audit of DisjunctionScorer's contract: score() and getChildren() must reflect exactly the clauses that match the current document after any call the API allows between matches() and scoring. docIDRunEnd() on the approximation is such a call and rewrites the links that list is built from; a public-API JUnit test then witnessed the wrong score.

The method in full149 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The finder read DisjunctionScorer.TwoPhase against its obligation (the list of verified matches on the current doc stays valid until score() / getChildren()) and listed what may run in between under the documented API. docIDRunEnd() on the approximation is documented as position-neutral, but its override walks topList(), which writes the same next fields.
  • The finder then wrote a public-API JUnit test that fails on main with assertions on and off and on 10.6.0 and 10.2.0, a probe that shows the hang and the heap-order dependence, and the fix sketch (fix A).
  • An independent reproducer wrote its own test from the claim before reading the finder's; cross-model reviews, a devil's-advocate verifier and an adjudication reproduced it; a final repro check trimmed the test to the two-document repro on this page ("Prior reports, history and checks").

LFV-1143, snapshot of 2026-11-05

Registry title
Calling docIDRunEnd() on a two-phase disjunction's approximation between matches() and score() corrupts DisjunctionScorer's list of verified matches, so score() and getChildren() include a clause that does not match the current document, or never return (since 10.2.0)
Area
core / search (DisjunctionScorer two-phase verified matches vs DisjunctionDISIApproximation.docIDRunEnd)
Priority
Low, rank 603: Calling docIDRunEnd() on a disjunction scorer's approximation between matches() and score() gives a wrong score, or a score() call that never returns, in every release since 10.2.0. Nothing in Lucene makes that call, so only contrived custom scorer code hits it.
Impact class
minor
Impact note
Only application code that drives scorers itself (a custom BulkScorer, collector or scorer composition) and calls docIDRunEnd() on twoPhaseIterator().approximation() of a positioned disjunction scorer (for example BooleanQuery SHOULD term + SHOULD phrase or doc-values range clause, scored with COMPLETE) after matches() and before score()/getChildren() is hit; then, when the two-phase clause sits on top of the lead heap, score() silently adds that non-matching clause and getChildren() reports it, and when the two-phase clause also matches, score()/getChildren() loop forever (-ea and -da alike); default codec, IndexWriterConfig and a plain IndexSearcher suffice and no scale is needed, but no Lucene code makes this call, and tests run through newSearcher()/AssertingScorer cannot see it because its approximation wrapper does not forward docIDRunEnd() [exec + read].
Summary
You index two documents {0: "b a c", 1: "c"} and build BooleanQuery(SHOULD f:c, SHOULD phrase "a b") with ScoreMode.COMPLETE; you move a scorer to doc 0 with iterator().nextDoc() and ask twoPhaseIterator().approximation().docIDRunEnd() (it returns 1 and the scorer stays on doc 0). You expect score() to return 0.06880058, the f:c score a fresh scorer gives, because docIDRunEnd() is documented not to affect the iterator; you get 0.59193045 with no error, because the phrase, which does not match doc 0, is added in. docIDRunEnd() walks the lead heap's topList(), which rewrites the same DisiWrapper.next links that matches() used to build the list of verified matches, and if the phrase also matches doc 0 the list becomes a cycle and score() never returns.
