BpVectorReorderer's in-place command-line reorder commits an empty or partial index over the original when reordering fails

If BpVectorReorderer's in-place command line fails part-way, for example with its documented NotEnoughRAMException, try-with-resources closes its CREATE-mode writer and close() commits: the index is replaced by an empty or partial one (601,000 documents became 1,000 in one run). Unreleased (main and branch_11x); rolling the writer back on failure fixes it.

The finding in 30 seconds

#

The tool's main() calls reorderIndexDirectory, which opens the index for reading, then an IndexWriter in OpenMode.CREATE on the same directory inside try-with-resources, and calls addIndexes once per segment with a reordered view of it. There is no catch and no rollback, so any exception goes straight to close().

Three things to know first

#
  1. An index on disk is its last commit: a segments_N file that lists the segments. A writer opened with OpenMode.CREATE starts a new, empty index in the same directory; until it commits, readers still see the old one.
  2. IndexWriter.close() commits whatever the writer holds, because commitOnClose is true by default; rollback() discards it and keeps the last commit.
  3. After a commit, the default deletion policy keeps only that commit: the previous commit and the files only it used are deleted.

The finding, step by step

#
  1. You run the reorder tool on a vector index, BpVectorReorderer <indexDir> <field>, to renumber its documents in place. It opens a writer in OpenMode.CREATE on the same directory and adds the segments back one at a time, reordered.
  2. One segment needs at least the tool's RAM budget, a tenth of the JVM's starting heap: with -Xms8m the test JVM started with a 32 MB heap, so the budget is 3.2 MB, and a 600,000-vector segment needs 4.6 MB. You expect NotEnoughRAMException and an untouched index.
  3. Instead try-with-resources closes the writer, and close() commits by default. The new commit holds only the 1,000-document segment added before the failure, and the old commit is deleted: 601,000 documents become 1,000.
  4. No big data is needed: with default options the tool also fails at the first segment of indexes written by Lucene 9.x or 10.x and of indexes with soft deletes or a parent field, and leaves 0 documents (10 to 12 before, 0 after, in the runs).
  5. The minimal test: 1 document, budget Double.MIN_VALUE. reorderIndexDirectory throws NotEnoughRAMException, and the index then has 0 documents. With rollback() on failure it keeps its 1 document.

Who is affected

#

Users of unreleased main or branch_11x who run this offline lucene/misc tool and whose run fails; the merge policy is not affected. Runs fail often: on indexes created by 9.x or 10.x, with soft deletes or a parent field, or with a segment at or over the budget (about 3.4 million vectors on 16 GB with HotSpot defaults).

Mechanism, terms and numbers660 words

BpVectorReorderer (lucene/misc, added for 11.0 by #14097) has a command line, main(indexPath, field), that renumbers the documents of an existing index in place so that documents with similar vectors get nearby doc ids. It calls the package-private reorderIndexDirectory, which opens a reader on the index, then an IndexWriter in OpenMode.CREATE on the same directory inside try-with-resources, and adds each segment back reordered with one addIndexes call per segment, with no catch and no rollback. If computing a doc map or addIndexes throws, for example the documented NotEnoughRAMException when a segment's doc-map metadata (8 bytes per vector) reaches the RAM budget (by default a tenth of the JVM's current heap), try-with-resources calls close(), which commits by default. The new commit holds only the segments added before the failure, and the default deletion policy deletes the original commit. In the minimal test 1 document becomes 0; through main() with default options 601,000 documents became 1,000 in a small-heap JVM, and indexes written by Lucene 9.12.3 or 10.5.2, or with soft deletes or a parent field, became empty. Unreleased: the tool is on main and on the 11.0 release branch branch_11x, and in no release, so it can be fixed on both before 11.0.0.

The bug (main 645d4fe14a20)

#
  1. main (BpVectorReorderer.java:653-682) takes the index path, the field and three tuning options (--max-iters, --min-partition-size, --thread-count); it has no option for the RAM budget or the writer configuration. It calls reorderIndexDirectory(dir, executor) on FSDirectory.open(...) (:679-681).
  2. The RAM budget is set in the constructor to a tenth of Runtime.getRuntime().totalMemory() (:97), the JVM's current heap, which early in main() is about the initial heap. computeValueMap throws NotEnoughRAMException when a segment's vectors, at 8 bytes each (:642-646), need at least that budget (>=, :596-605); computeDocMap (:578-593) runs once per segment.
  3. reorderIndexDirectory (:684-697) opens a reader on the directory, then try (IndexWriter writer = new IndexWriter(directory, iwc)) with OpenMode.CREATE and an otherwise default IndexWriterConfig, and calls writer.addIndexes(SortingCodecReader.wrap(leaf, computeDocMap(leaf, null, executor), null)) for each segment. Each addIndexes call is transactional on its own (IndexWriter.java:3084-3086), not the loop.
  4. When computeDocMap throws (NotEnoughRAMException; an AssertionError under -ea) or addIndexes throws (an IllegalArgumentException for a 9.x/10.x-created, soft-deletes or parent-field index; an IOException), try-with-resources calls close(). With commitOnClose (IndexWriterConfig.java:102) close() writes, waits for merges and commits (IndexWriter.java:1363-1369).
  5. The new commit, segments_2, lists only the segments added before the failure; the default KeepOnlyLastCommitDeletionPolicy deletes the original commit and its files. After the 9.12.3, 10.5.2, soft-update and parent-field runs the directory holds only segments_2 and write.lock.
  6. A failure that also breaks the commit (a disk that stays full) keeps the old index, because the commit itself fails. So the loss needs a failure before the commit that does not recur in it, which is what NotEnoughRAMException and the IllegalArgumentExceptions are.

Exposure and likelihood290 words
  • Who is exposed. Users of unreleased main or the 11.0 release branch branch_11x (11.0.0-SNAPSHOT) who run BpVectorReorderer's command line on an index, or call reorderIndexDirectory from the same package. Applications that use BPReorderingMergePolicy or computeDocMap with their own IndexWriter are not affected.
  • Default vs opt-in. The tool is opt-in, an expert tool run by hand. Once it runs, everything is default, and it has no option that avoids the loss.
  • How often a run fails. With default options the tool's writer refuses every segment of a non-empty index created by Lucene 9.x or 10.x and every segment that carries a soft-deletes or parent field (the sibling bug LFV-1023 and the parent-field check); in every such run it was the first segment, and the index was wiped to 0 documents (executed on small non-empty indexes; the general form is read from addIndexes' per-segment checks). Independently, the budget runs out on a segment whose vectors need at least the budget at 8 bytes each. HotSpot's default initial heap is 1/64 of physical memory (InitialRAMPercentage 1.5625, printed on the test host), which gives about 3.4 million vectors on a 16 GB machine (computed, not run); other JVMs, container limits or -Xms change it. The tool reorders each segment as a whole, so the limit is hit by large segments, such as those of a force-merged index (reasoning; upstream's dense-index test force-merges to one segment before calling main()).
  • Effect. Durable: the original commit is gone, and only the exception tells the user. When a later segment fails, the partial index opens without error (12 of 52 documents). Recovery needs a backup or a re-index.
  • Mitigating. Unreleased, offline, and loud (an exception). A user who copies the index first loses nothing.

Why it looks unintended

#
  • The documented outcome of too little RAM is a report: "a NotEnoughRAMException will be thrown" (setRAMBudgetMB).
  • The sibling BPReorderingMergePolicy skips reordering when RAM is short; its test checks that this "does not corrupt its content".
  • The tool owns the writer, so its user cannot roll back, and unlike CheckIndex -exorcise ("LOSES DATA") it warns of nothing.
The full argument269 words
  • Contract. No javadoc promises failure atomicity in so many words. main: "a path containing an index to reorder" (BpVectorReorderer.java:648-651), a permutation of its documents; the upstream test calls it "the index reordering tool" (TestBpVectorReorderer.java:353, :412). setRAMBudgetMB: "If not enough RAM is provided, a {@link NotEnoughRAMException} will be thrown" (AbstractBPReorderer.java:63-67).
  • The sibling handles the same error without damage. BPReorderingMergePolicy: "When reordering doesn't have enough RAM, it simply skips reordering in order not to fail the merge" (BPReorderingMergePolicy.java:34-39); testReorderDoesntHaveEnoughRAM uses the same Double.MIN_VALUE budget and "makes sure that reordering the index on merge does not corrupt its content" (TestBPReorderingMergePolicy.java:248-251).
  • IndexWriter semantics. A CREATE writer replaces the old index only when it commits: old readers "won't see the newly created index until they re-open" (IndexWriter.java:103-107); addIndexes "does not commit a new segments_N file until all indexes are added" (:3084-3086). The half-added commit is made by the tool's own try-with-resources.
  • Lucene's other tools. CheckIndex -exorcise: "LOSES DATA" and "Always make a backup" (CheckIndex.java:4645, :4652, :4856); IndexSplitter: "be careful!" (IndexSplitter.java:44). The in-place IndexUpgrader also closes its writer in try-with-resources, but on the existing index (default CREATE_OR_APPEND), so a commit after a failure still holds every document (read, not executed). BpVectorReorderer carries no warning, no @lucene.experimental and no backup advice.
  • Tests and history. Upstream tests call reorderIndexDirectory (TestBpVectorReorderer.java:175) and main (:354, :413) on successful runs only. The comments and reviews of #13565, #13683, #14097 and #14117 never discuss a failing run.
The devil's-advocate check256 words

Strongest case (the refute-lens cross-model review rated it moderate; the devil's-advocate check built it in full and rated it weak): it is a research tool (in #13565 its author wrote "it would be easier to start with a tool that rewrites the index" to get an idea of the impact; CHANGES never mentions the command line, and even a successful run drops commit user data and any index sort, executed as a side observation and not claimed); OpenMode.CREATE is documented as "Creates a new index or overwrites an existing one" (IndexWriterConfig.java:58); close() committing is documented and was restored as the default on purpose (LUCENE-5871); and the minimal test needs the package-private method and a budget a command-line user cannot set.

Why it fails: nothing says research-only or "make a backup", main() is public in lucene/misc (not the sandbox), and Lucene's data-losing tools warn loudly. Granted, CREATE is documented to overwrite and an IndexWriter caller normally owns rollback; but here the tool picks CREATE and owns the writer's whole lifecycle, so the tool is the caller that should roll back. What CREATE is meant to put in place is the reordered index; the empty or partial commit is made by the tool's own try-with-resources after it has thrown. commitOnClose leaves rollback to the caller, and the caller here is Lucene's own tool, which gives its user no hook. Public main() with default options reaches it on ordinary indexes. Verdict: a defect. Residual risk: a maintainer may prefer to remove main() or document "back up first".

Suggested fix

#

Recommended Roll back on failure; close (commit) only after every segment was added (validated)

Open the writer without try-with-resources; if adding any segment throws, call writer.rollback(), which keeps the original commit, and rethrow; call close() only after every segment was added (+12/-1 in one method). The test then passes, and so do the whole lucene/misc test suite (317 tests) and its static checks.

IndexWriter writer = new IndexWriter(directory, iwc);
try {
  for (LeafReaderContext ctx : reader.leaves()) {
    CodecReader codecReader = (CodecReader) ctx.reader();
    writer.addIndexes(
        SortingCodecReader.wrap(codecReader, computeDocMap(codecReader, null, executor), null));
  }
} catch (Throwable t) {
  try { writer.rollback(); } catch (Throwable t2) { t.addSuppressed(t2); }
  throw t;
}
writer.close();

Roll back on failure; close (commit) only after every segment was added (validated) (recommended)

#

One method, reorderIndexDirectory in BpVectorReorderer.java (+12/-1): open the writer without try-with-resources; if adding any segment throws, call writer.rollback(), which discards the added segments and keeps the original commit, add a rollback failure as suppressed and rethrow; call writer.close() only after the loop. The logic is the finder's fix sketch with the comment reworded.

IndexWriter writer = new IndexWriter(directory, iwc);
try {
  for (LeafReaderContext ctx : reader.leaves()) {
    CodecReader codecReader = (CodecReader) ctx.reader();
    writer.addIndexes(
        SortingCodecReader.wrap(codecReader, computeDocMap(codecReader, null, executor), null));
  }
} catch (Throwable t) {
  try { writer.rollback(); } catch (Throwable t2) { t.addSuppressed(t2); }
  throw t;
}
writer.close();

Trade-offs

  • The success path is unchanged: close() still flushes, waits for merges and commits.
  • On failure the writer is rolled back and closed and the original exception is rethrown. Throwable is caught so an AssertionError (under -ea) is covered too.
  • It does not fix LFV-1023: the tool still refuses 9.x/10.x and soft-deletes indexes, now without deleting them. Indexes already damaged are not restored.
  • Open PR #15430 moves the class to core with this method unchanged; if it merges first, the fix moves with it.
  • Validated for failures inside the segment loop (computeDocMap, addIndexes), where every observed trigger fires. Not tested: the IndexWriter constructor failing, rollback() itself failing, or close() failing after every segment was added (its javadoc: on an exception "changes may have been lost").

What the checks validated

  • Scratch worktree at 645d4fe14a20, gradle, JDK 25: the test fails on stock and passes with the fix, assertions on and off.
  • ./gradlew :lucene:misc:check with the fix: formatting (checkGoogleJavaFormat), ecjLint, forbiddenApis and the whole module's tests (24 suites, 317 tests, 0 failures, 9 skipped), including TestBpVectorReorderer (8 of 8) and TestBPReorderingMergePolicy (its two @Nightly tests were skipped; they do not call the changed method). With assertions off the three reorder test classes pass too.
  • Earlier, the same logic passed the finder's 10-document test, the upstream reorder tests (9 of 9) and the bounded-exhaustive harness with 0 violations of 483 checks (stock: 236).

setCommitOnClose(false) plus an explicit commit() after the loop (not built)

#

Two lines: with commitOnClose off, close() means rollback() (IndexWriter.java:1363-1369), so any failure before the explicit commit keeps the old index.

Trade-offs

On success, merges still running after the explicit commit are aborted by the rollback in close() instead of being waited for and committed (addIndexes(CodecReader...) calls maybeMerge(), IndexWriter.java:3395), so the result may keep more segments than today (inferred, not run).

Write the reordered index to a new directory (not built)

#

Leave the input alone, or swap the new index in only after a successful commit.

Trade-offs

The safest for the input, but it changes the command line's in-place contract and needs twice the disk space.

Javadoc only (not built)

#

Document "back up the index first; a failed run can leave it empty or partial".

Trade-offs

No code risk, but the loss remains, and today's most common failures happen on ordinary indexes.

Downstream note

#

Downstream, this matters for any product or script that runs the tool automatically on indexes it manages: a failed run there deletes the index's documents instead of leaving it unchanged.

How it was found

#

A failure-atomicity review read reorderIndexDirectory and ran probes on main: one injected I/O fault left a partial or empty index at 207 of 225 points, and a small-heap command-line run turned 601,000 documents into 1,000. A bounded-exhaustive single-fault harness then confirmed it (236 violations in 483 checks; 0 with the fix).

Only users of unreleased main (11.0.0-SNAPSHOT) who run the offline lucene/misc BpVectorReorderer command line (or its package-private reorderIndexDirectory) on an index are hit, and only when the run fails, but then the index they asked it to reorder is durably replaced by an empty or partial one and the original commit is deleted (executed: 10 -> 0 documents after the documented NotEnoughRAMException; through main() with default options 601,000 -> 1,000 documents in a small-heap JVM, and 0 documents left for indexes written by 9.12.3 or 10.5.2 or carrying a soft-deletes or parent field); no scale is needed beyond a segment whose vectors need more than the default RAM budget, a tenth of the JVM's initial heap at 8 bytes per vector.
Summary
You run BpVectorReorderer's command line (main(path, field), which calls reorderIndexDirectory) to renumber the documents of an existing index in place, and expect that if the reorder fails you get the exception and the index still holds all its documents. Instead, when computing a doc map or addIndexes throws (for example the documented NotEnoughRAMException), the try-with-resources around the OpenMode.CREATE IndexWriter closes it, close() commits by default, and the new commit holds only the segments rewritten before the failure, while the original commit and its files are deleted. A 10-document index ends with 0 documents, and through main() with default options an index created by Lucene 9.x or 10.x, or one with a soft-deletes or parent field, is wiped to 0 documents.
