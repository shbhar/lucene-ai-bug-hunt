The bug in 30 seconds

#

In romaji the small tsu ッ is written by doubling the next consonant (キット kitto, バッグ baggu). Kuromoji's romaji mode does this for only four kana rows.

  1. You index Japanese text with JapaneseTokenizer and JapaneseReadingFormFilter(tokenizer, true) (romaji mode, useRomaji=true), whose romanizer is documented as "Romanize katakana with modified hepburn".
  2. You expect the small tsu ッ to double the next consonant, as it does for キット → kitto and マッチ → matchi: バッグ (bag) → baggu, ベッド (bed) → beddo.
  3. Instead バッグ → bagu, the same term as バグ (bug), ベッド → bedo, and キッズ (kids) → kizu, the same as キズ (scratch). In the repro 7 of 7 such loanwords lose the ッ; the 4 controls (ッ before the s, t and p rows) pass.
  4. Why: the case 'ッ' branch has inner cases only for the カ, サ, タ and パ rows. Any other next kana falls through to a bare break, so nothing is written for the ッ.
  5. No error: bag and bug match each other, and a query typed baggu stays baggu and matches no document that contains バッグ.

Who is affected

#

Applications that index or query romaji readings with JapaneseReadingFormFilter and useRomaji=true (opt-in; the default katakana mode is not affected), or call ToStringUtil.getRomanization directly, in every release since 3.6.0. Ordinary loanwords trigger it: バッグ, ベッド, ビッグ, キッズ, スタッフ, ブリッジ. A fix changes indexed terms, so romaji fields need reindexing.

Mechanism, terms and numbers489 words

Kuromoji's JapaneseReadingFormFilter can replace each token with its reading in romaji (useRomaji=true, opt-in). Its romanizer, ToStringUtil.getRomanization, is documented as "Romanize katakana with modified hepburn", and Hepburn writes the small tsu ッ by doubling the next consonant. The method does that only before the カ, サ, タ and パ rows (キット kitto, マッチ matchi); before any other kana its case 'ッ' falls through and writes nothing. So common loanwords lose the ッ: バッグ (bag) becomes bagu, the same term as バグ (bug), ベッド becomes bedo, キッズ becomes kizu like キズ. Distinct words then match each other, and a romaji query typed baggu finds no document with バッグ. There is no error and no index damage. It has been so since the method was written in 2012, in every release from 3.6.0 to 10.5.2 and on main; a fix changes indexed romaji terms, so such fields need reindexing.

Terms

#
  • Small tsu (sokuon, ッ): a doubled consonant. キット (kit) is ki-tto, バッグ (bag) is ba-ggu. Hepburn writes it by doubling the consonant that follows, tch before ch (マッチ matchi).
  • JapaneseReadingFormFilter: replaces each token with its reading, in katakana (the default) or, with useRomaji=true, in romaji. For a dictionary word it romanizes the reading, for an unknown word the term text, by calling ToStringUtil.getRomanization (JapaneseReadingFormFilter.java:80-88).
  • ToStringUtil.getRomanization: a public static method, documented "Romanize katakana with modified hepburn" (ToStringUtil.java:240, :251). It walks the string once with a lookahead of two characters and a switch on the current character.

The bug

#
  1. For ッ the method looks at the next character in an inner switch (ToStringUtil.java:264-295). It has cases for カキクケコ (k), サシスセソ (s), タチツテト (t) and パピプペポ (p), each appending the letter and leaving with break main.
  2. Any other next kana matches no case, leaves the inner switch and reaches the outer break, which appends nothing. The next iteration romanizes the following kana as usual.
  3. So バッグ is バ ba + ッ (nothing) + グ gu = bagu, while キット is キ ki + ッ t + ト to = kitto.
  4. The filter writes that string into the term. Positions, offsets and the token count do not change; only the term text does.

The numbers

#

On main: バッグ → bagu (expected baggu), ベッド → bedo, ビッグ → bigu, キッズ → kizu, ブリッジ → buriji, スタッフ → sutafu, バッハ → baha: 7 of 7 wrong, while キット kitto, キップ kippu, ザッシ zasshi and マッチ matchi are right. Through the filter, バッグ and バグ both give the term bagu, and the typed query baggu stays baggu. In the security screen's 3,022-document probe index (random sokuon-heavy text), the term query baggu matched 0 documents on stock main and 116 with the generic fix shadowed in.

Exposure and likelihood215 words
  • Who. Users of JapaneseReadingFormFilter(input, true) or of the SPI factory japaneseReadingForm with useRomaji=true (default false, JapaneseReadingFormFilterFactory.java:44-50; its javadoc shows the Solr schema form, :26-34), and direct callers of ToStringUtil.getRomanization (package ja.dict is exported, module-info.java:25).
  • What triggers it. Ordinary loanwords with ッ before g, z/j, d, b or h/f: バッグ, ベッド, ビッグ, キッズ, グッズ, ブリッジ, スタッフ, ヘッド, ドッグ, バッハ. No special input and no scale. How often such words occur in real text was not measured.
  • Two symptoms. Minimal pairs collide (バッグ/バグ → bagu, キッズ/キズ → kizu), so each matches the other; and romaji queries spelled with the doubled consonant (baggu, beddo) analyze to themselves, so they miss the indexed bagu and bedo (run as an index query for baggu: 0 hits).
  • Inconsistent output. The same method writes kitto and matchi, so users cannot predict when the doubling applies.
  • Silent. No exception, no log line, no index damage (CheckIndex clean in the security probe).
  • How likely. Romaji mode is opt-in and rarely used, and the romanizer is already lossy by design (it drops the long-vowel mark ー, so ビール and ビル share a term); nobody has reported this since 2012.
  • After a fix these words get new romaji terms, so existing romaji fields must be reindexed.

Why it is a bug, not intended

#
  • Both getRomanization overloads say "Romanize katakana with modified hepburn"; Hepburn doubles the consonant after a small tsu, and the method itself does so for k, s, t and p.
  • The other rows are simply missing: no case, test, comment or CHANGES entry covers them.
  • Lucene's own completion table maps ッグ, ッド, ッズ and ッハ to ggu, ddo, zzu and hha.
The full argument287 words
  • The contract. Both overloads say "Romanize katakana with modified hepburn" (ToStringUtil.java:240, :251). Hepburn writes the sokuon by doubling the consonant that follows (tch for ch), with no exception for voiced consonants (the Hepburn page that TestToStringUtil.java:36 points to).
  • The method applies the rule itself for four rows (rokku, zasshi, kitto and matchi, kippu); the other rows get no handling at all, the inner switch just falls through.
  • Lucene's own later romaji table doubles them. The completion filter's romaji_map.txt ("covers romanization systems: modified Hepburn-shiki, Kunrei-shiki (Nihon-shiki), and Wāpuro shiki", line 3) has ッグ,ggu (:178), ッジ,zzi,jji (:193), ッズ,zzu (:194), ッド,ddo (:212), ッハ,hha (:216), ッフ,hhu,ffu (:218), ッバ,bba (:224), ッブ,bbu (:226). It is supporting precedent, not an oracle for this method: lines 4-5 say the table "does not strictly comply with the romanization systems listed above" and covers input-method keystrokes, and some rows differ from what fix B writes (ッヂ,ddi at :209, where fix B gives jji because this method romanizes ヂ as ji).
  • "Used only for debugging" is stale. The class javadoc says so (ToStringUtil.java:24), but the TODO in the same method says "now that this is used by readingsfilter and not just for debugging" (:252-253), and in #5499 (LUCENE-4433, メ romanized as mi) a committer wrote "Now its used by at least a tokenfilter"; that table error was fixed as a bug in 2012.
  • Nothing pins the current output. No upstream test has a ッ input (TestToStringUtil, TestJapaneseReadingFormFilter), and no comment, CHANGES or MIGRATE entry mentions the sokuon.
  • Precedent. Romaji output defects of this filter were filed under "Bug Fixes": GITHUB#12885 (OOV hiragana, 9.10.0) and SOLR-3906 (OOV half-width kana).
The devil's-advocate check209 words

The strongest case for "intended" (the independent reproducer, the intended-behaviour checker and the cross-model lenses rate it moderate): the romanizer is approximate on purpose. It drops the long-vowel mark (マージャン → majan, ロバート → robato, both asserted by upstream tests), so ビール and ビル already share a term; TestToStringUtil says its Hepburn table "isnt even thorough or really probably what we want!"; native and Sino-Japanese words double only k, s, t and p, which may be why only those rows exist; and romaji mode is opt-in.

Why it fails: the approximations cited here are explicit code (case 'ー': break;, ン written m before b/p/m) with tests, while this is an unhandled fall-through with no comment or test; the output is inconsistent (kitto but bagu), so it is not a deliberate "ignore doubling" search key; the native-word pattern explains why the cases were missed, not that dropping was chosen, since the dictionary's readings of common loanwords contain exactly these sequences; and Lucene's own completion table doubles these rows. What remains is a labelling question (bug fix or improvement), not intent. Verdict: not intended, a missing-cases defect. Frame the issue as inconsistent output and missed romaji queries, not as a demand for strict modified Hepburn.

How it was found

#

Semi-formal. A bounded-exhaustive property check ran the stock romanizer on all 761,943 katakana strings of length 1 to 3 and checked the Hepburn rule "ッ doubles the next syllable's first consonant" for every syllable; it flagged the rows other than k, s, t and p. A public-API JUnit then reproduced the common loanword cases end to end.

The method in full135 words
  • Unit. A hunt unit that checked kuromoji and nori token filters against their javadoc, with a bounded-exhaustive harness over the stock kuromoji jar.
  • Section C of the harness. All 761,943 strings of length 1-3 over U+30A1..U+30FA plus ー were romanized twice (determinism: 0 mismatches) and checked for romaji-only output; then, for every one- or two-kana syllable, ッ + syllable was checked against "double the syllable's first consonant, ch → tch". 145 of 200 consonant-initial syllables lost the ッ. That count includes rare sequences (ッ before n, m, r, y, w), so it is not the headline.
  • End to end. The realistic subset, loanwords with ッ before g, z/j, d, b and h/f, was then reproduced through JapaneseTokenizer + JapaneseReadingFormFilter(useRomaji=true) with a public-API JUnit, and checked on releases back to 3.6.0 with a version-independent probe.

Bug record

#

LFV-605, snapshot of 2026-10-28

Registry title
Kuromoji's romaji reading (ToStringUtil.getRomanization, used by JapaneseReadingFormFilter with useRomaji=true) writes the small tsu ッ as a doubled consonant only before the k, s, t and p rows and silently drops it before any other kana, so loanwords with ッ before g, z/j, d, b or h/f lose it: バッグ 'bag' and バグ 'bug' both become 'bagu', ベッド becomes 'bedo'
Area
analysis / kuromoji romanization (ToStringUtil.getRomanization; JapaneseReadingFormFilter romaji mode)
Priority
Low, rank 416: Kuromoji romaji mode silently drops the small tsu before voiced consonants, so loanword pairs such as bag and bug collide, which is deterministic but.
Impact class
silent wrong results
Impact note
Applications that index or query Japanese text through JapaneseReadingFormFilter in romaji mode (useRomaji=true or the factory parameter of that name; the default is katakana) or call ToStringUtil.getRomanization directly, in every release from 3.6.0 to 10.5.2 and main: every occurrence of a common loanword with ッ before g, z/j, d, b or h/f (バッグ, ベッド, ビッグ, キッズ, グッズ, スタッフ, ブリッジ, バッハ) is indexed without the doubled consonant, so it shares a term with a different word (バッグ/バグ -> 'bagu', キッズ/キズ -> 'kizu') and a query typed in Hepburn or keyboard romaji ('baggu', 'beddo') does not match it; no scale is needed, there is no error and no index damage, and a fix changes indexed romaji terms, so such fields would need reindexing.
Summary
You analyze Japanese text with JapaneseTokenizer and JapaneseReadingFormFilter(useRomaji=true), whose romanizer is documented as 'Romanize katakana with modified hepburn', and expect the small tsu ッ to double the next consonant, as the method already does for キット -> 'kitto' and マッチ -> 'matchi'. Instead the 'ッ' case appends a consonant only for the カ, サ, タ and パ rows and appends nothing otherwise, so バッグ 'bag' becomes 'bagu', the same term as バグ 'bug', ベッド becomes 'bedo' and スタッフ becomes 'sutafu'. Distinct words then match each other, and a romaji query 'baggu' finds no document that contains バッグ.
