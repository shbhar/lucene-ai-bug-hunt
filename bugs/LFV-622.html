OpenNLPSentenceBreakIterator.next(n) returns DONE instead of the end of the text when it lands on the last boundary

OpenNLPSentenceBreakIterator.next(n) returns DONE (-1) instead of the end of the text when the n-th boundary is the end, so next(1) disagrees with next(): on a one-sentence text next() returns 27 and next(1) returns -1. It is in every release since 7.3.0; Lucene's own tokenizer never calls next(n).

The bug in 30 seconds

#

OpenNLPSentenceBreakIterator is the OpenNLP module's java.text.BreakIterator over sentences. As for any BreakIterator, next() moves to the next boundary and next(n) jumps n boundaries; both should return DONE (-1) only when no such boundary exists. The last boundary is the end of the text.

  1. You split the 102-character text Sentence number 1 has 6 words. Sentence number 2, 5 words. And finally, sentence number 3 has 8 words. with OpenNLPSentenceBreakIterator and the module's test sentence model. Its boundaries are 0, 31, 59 and 102, the end of the text.
  2. From first() you jump with next(n): next(1) returns 31, next(2) returns 59, and next(4) returns DONE because it steps past the end.
  3. You expect next(3) to return 102, the third boundary, as three calls of next() do. The JDK and ICU4J sentence iterators return 102 on the same text.
  4. Instead next(3) returns -1 (DONE), although the iterator did move to 102. Even with no model at all, on Whole text is one sentence., next() returns 27 but next(1) returns -1.
  5. Why: the class stores only the sentence starts {0, 31, 59}, so the end is boundary number 3. next(n) adds n to its counter and returns DONE when the counter is >= 3: landing exactly on the end is treated like going past it.

Who is affected

#

Only application code that uses this iterator directly and calls next(n) with n > 0, in the opt-in OpenNLP module. A loop that steps with next(n) until DONE loses its last group of sentences; with next(1), the last sentence of every text. Lucene's tokenizer only calls next(): tokens, indexing and search are unchanged.

Mechanism, terms and numbers589 words

OpenNLPSentenceBreakIterator is the OpenNLP module's java.text.BreakIterator over sentences. next(n) should return the n-th boundary from the current one, the same value as n calls of next(). When that boundary is the end of the text it returns DONE (-1) instead, although it does move the iterator there: next(3) from first() on the module's three-sentence test text returns -1 instead of 102, and with no model at all next(1) returns -1 where next() returns 27. A loop that steps with next(n) until DONE loses its last group of sentences (with next(1), the last sentence of every text). No Lucene code calls next(int) on this class, so tokenization, indexing and search are unchanged. Every release from 7.3.0 to 10.5.2 and main is affected; a small fix in next(int) (+4/-1 lines) was validated with the module's tests.

Terms

#
  • Boundary: a position between sentences. For a text of three sentences the boundaries are the three sentence starts and the end of the text: 0, 31, 59 and 102 for the module's test text.
  • next() / next(n): next() moves to the boundary after the current one and returns it, or returns DONE (-1) when the current boundary is already the last one. next(n) jumps n boundaries (BreakIterator#next() is documented as "Equivalent to next(1)"); it returns DONE when there are fewer than n boundaries left.

The bug, step by step (code at 645d4fe14a20)

#
  1. setText() stores only the sentence starts (OpenNLPSentenceBreakIterator.java:195-205): {0, 31, 59}. The end of the text has no entry; counted as a boundary it is number sentenceStarts.length, here 3.
  2. next() (:62-72) returns DONE only when the position is already the end (:64). From the last sentence start it calls last() (:69-70), which moves to the end and returns it (:51-60).
  3. next(int n) (:163-187) adds n to the counter first: currentSentence += n (:165).
  4. Backwards (n < 0, :166-176) it adds one when the position is the end (:167-169), so it counts the end as boundary number 3, and it returns DONE only for a counter below 0: landing on the first boundary returns 0.
  5. Forwards (n > 0, :177-185) it returns DONE when currentSentence >= sentenceStarts.length (:178), after moving to the end (:179-181). >= also matches the end boundary itself, so next(3) from 0 (counter 3, 3 >= 3) moves to 102 and returns -1. By the next() javadoc ("Equivalent to next(1)") and the next(int) javadoc example, only a counter above 3, or a call made at the end, should give DONE; the next(int) javadoc's "has been reached" sentence is the strongest contrary reading (see "Why it is not intended").

Exposure and likelihood277 words
  • Who is exposed. Application code that uses OpenNLPSentenceBreakIterator itself as a java.text.BreakIterator and calls next(int) with n > 0. The class is public final in an exported package of the opt-in lucene-analysis-opennlp module, with no @lucene.internal tag; the public no-argument NLPSentenceDetectorOp is enough (no model file).
  • Deterministic. With n = 1 it fires from the last sentence start of every non-empty text; for larger n whenever the n-th boundary is the end. Assertions on or off. Where there is no distinct end boundary to land on (an empty text, or no sentences), DONE is already right.
  • Effect. One wrong return value, -1 instead of the end offset. A loop that stops at DONE loses its final group whenever the sentence count is a multiple of n; with n = 1 it loses the last sentence of every text. In a probe over 48 layouts, such a loop was wrong in 48 on main and in 23 with the fix or the JDK iterator (the overshoot cases the contract allows). A caller that uses the value as an offset unchecked gets a StringIndexOutOfBoundsException. A caller that reads current() after DONE is unaffected.
  • Not in Lucene's own paths. OpenNLPTokenizer is the only in-tree user, through SegmentingTokenizerBase, which calls only setText, current() and next(); it gives the same 24 tokens and offsets on main, the fixed build and 10.5.2. The only other next(int) call outside tests, in LengthGoalBreakIterator, is marked "Not supported".
  • How likely. Rare: no caller of next(int) on this class was found in Lucene, Solr, Elasticsearch, OpenSearch or the public code-search hits read, and nobody reported it in the eight years since 7.3.0.

Why it is a bug, not intended

#
  • BreakIterator#next() is documented as "Equivalent to next(1)", yet here next() returns the end and next(1) returns DONE from the same position.
  • Backwards the class is right: next(-2) from 59 returns the first boundary, 0, as its own test asserts.
  • The next(int) javadoc example gives DONE only for a jump past the last boundary; nothing documents the forward case.
The full argument255 words
  • The contract. BreakIterator#next(): returns DONE "If the current boundary is the last text boundary", and "Equivalent to next(1)". BreakIterator#next(int): "Returns the nth boundary from the current boundary"; its example, with three more boundaries up to the last one: "the next(2) call will return m + 2" and "A next(4) call would return BreakIterator.DONE", so next(3) returns the last boundary. @return: "The character index of the nth boundary from the current position".
  • The class contradicts itself. Its next() returns the end from the last sentence start (OpenNLPSentenceBreakIterator.java:69-70; the upstream test asserts it at TestOpenNLPSentenceBreakIterator.java:90 and :130), while next(1) from there returns DONE. Its backward branch counts the end as a boundary and returns the edge boundary it lands on (OpenNLPSentenceBreakIterator.java:166-176; the test asserts next(-2) == 0 at :115).
  • Nothing documents the forward exact-landing case. The upstream tests use next(2) and the overshoots next(13) and next(-8) (TestOpenNLPSentenceBreakIterator.java:114, :147-148, :226-227); no code comment, CHANGES or MIGRATE entry, issue or PR states it. The class's deliberate JDK deviations in following() and preceding() carry a JDK-8015110 comment (OpenNLPSentenceBreakIterator.java:82-84, :144-146); next(int) carries none.
  • The other implementations checked return the end. The JDK and ICU4J sentence iterators return 102 for next(3) on the same text. In Lucene, SplittingBreakIterator, WholeBreakIterator and CustomSeparatorBreakIterator implement next(n) as a loop over next() and so return the end.
  • History. The class was added as a "shim class" for OpenNLPTokenizer (LUCENE-2899); none of the issue's 136 comments mentions next(int).
The devil's-advocate check213 words

The strongest case for "works as designed": (1) the next(int) javadoc's first sentence, "If either the first or last text boundary has been reached, it returns BreakIterator.DONE", read as "landing on the last boundary returns DONE"; (2) upstream deliberately keeps non-JDK edge behaviour in this class: following(pos) returns DONE anywhere in the last sentence (asserted at TestOpenNLPSentenceBreakIterator.java:142), and preceding() differs from the JDK (:109-110; #13170 added preceding(25) == 0 "verifying correct behavior" in 2024, where the JDK gives 22). So "the JDK does it" alone does not settle what this class should do.

Why it fails: next() is "Equivalent to next(1)" and this class's own next() returns the end, so reading (1) contradicts the class itself; the javadoc example shows DONE only on overshoot; and the backward branch returns the edge boundary it lands on, which reading (1) would forbid. The following()/preceding() deviations are commented and tested, the next(int) one is neither. A works-as-designed review by a reviewer from another model family rated the case moderate and rejected it; a separate devil's-advocate checker rejected it with "fairly high confidence" (its words). When filing, lead with next() vs next(1) and the asymmetry with next(-n), not with JDK behaviour, and do not report following() or preceding() from this evidence.

#

Recommended A. Return the end when next(n) lands on it

In the n > 0 branch of next(int), return DONE only when the call starts at the end or the counter passes the end; when it lands exactly on the end, move there and return it (+4/-1). Validated: the new test, the upstream test with the additions, all 36 module tests and check pass, assertions on and off.

A. Return the end when next(n) lands on it (validated by the checks) (recommended)

#

In next(int) (OpenNLPSentenceBreakIterator.java:177-185), return DONE only when the call starts at the end of the text or the counter passes sentenceStarts.length; when the counter equals sentenceStarts.length, set the counter to the last sentence, move to the end and fall through to return current(). This is the finder's fix.

Why the position check. At the end the counter is sentenceStarts.length - 1, as last() and next() leave it, so the counter alone cannot tell "at the end" from "at the last sentence start".

Trade-offs

The smallest change at the root cause, still O(1). The returned value changes only where it was -1 for an existing boundary. It leaves the separate leading-whitespace bug of this class and the huge-n overflow as they are. Compatibility (A and B alike): a public method now returns the end offset where it returned DONE; no in-tree or public caller found depends on that, but private callers that treat the terminal DONE as a stop signal cannot be ruled out.

B. Implement next(n) as n steps of next() or previous() (validated by the checks)

#

Replace the body with two loops that call next() (n > 0) or previous() (n < 0) until n steps are done or one returns DONE, the shape of SplittingBreakIterator.next(int) in the highlighter module (+8/-21).

  @Override
  public int next(int n) {
    // n steps of next() or previous(): BreakIterator#next() is "Equivalent to next(1)"
    int result = current();
    for (; n > 0 && result != DONE; --n) {
      result = next();
    }
    for (; n < 0 && result != DONE; ++n) {
      result = previous();
    }
    return result;
  }

Trade-offs

It follows the definition of next(n) as repeated next()/previous() calls (checked on the test texts and the walk oracle's 84 layouts) and adds nothing to a counter, so the tested huge-n case returns DONE instead of overflowing; but it costs O(min(|n|, boundaries left)) per call instead of O(1), and next(-n) then depends on previous(), which throws on text that starts with whitespace (a separate bug in this class): in the walk oracle the crash count goes from 42 to 126 until that bug is fixed. With its fix (setText sets the first sentence start to the begin index), A and B both give 0 everywhere. Prefer B only if both bugs are fixed together.

How it was found

#

A bounded-exhaustive consistency check of the real class: for 84 stub sentence layouts it compared next(k) from first() with k calls of next(). All 84 disagreed, each exactly when the jump landed on the end of the text, and none did with the fix. A public-API test and independent checks followed.

The method in full171 words
  • Method (semi-formal): bounded-exhaustive internal-consistency checking of the stock jar, in the hunt's unit on the OpenNLP filters against the OpenNLP library. A stub sentence detector produced 1 to 14 sentences with start gaps of 1 to 3 characters and a leading offset of 0 or 2 (84 layouts), and three walk rules compared the navigation methods with each other: W1 backward walk = forward walk, W2 next(k) from first() = k calls of next() (and DONE past the end), W3 next(-k) from last() = k calls of previous().
  • Result. W2 failed in all 84 layouts, each exactly at k = the number of sentences (the end boundary), and in none with the fix. W1 and W3 failed only in the 42 layouts with a leading offset: that is the separate leading-whitespace bug of this class, with its own fix.
  • The finder cross-checked the JDK sentence iterator (it returns the end for the same jump), then wrote a public-API JUnit with the module's test model; independent checkers followed (see "Independent checks").

LFV-622, snapshot of 2026-10-29

Registry title
OpenNLPSentenceBreakIterator.next(n) returns DONE instead of the end of the text when the n-th boundary is the last one, so next(1) differs from next() and a caller that steps with next(n) until DONE loses the final sentence group
Area
analysis / opennlp OpenNLPSentenceBreakIterator (java.text.BreakIterator implementation, next(int))
Priority
Low, rank 478: OpenNLPSentenceBreakIterator.next(n) returns DONE instead of the final boundary, and nothing checked in Lucene or downstream projects calls it.
Impact class
minor
Impact note
Hits only applications that use the opt-in analysis-opennlp module's OpenNLPSentenceBreakIterator directly as a java.text.BreakIterator and call next(int) with a positive n: whenever the n-th boundary is the end of the text (with n = 1 from the last sentence start of every text) the call returns DONE (-1) instead of the end offset, deterministically, with -ea and -da, with no model file and no scale needed, in every release from 7.3.0 to 10.5.2 and main; the iterator is still moved to the end, so current() and every later call are correct, a caller that stops at DONE loses the final sentence group (with n = 1 the last sentence) and a caller that uses the value unchecked as an offset gets a StringIndexOutOfBoundsException; no Lucene code calls next(int) on this class (OpenNLPTokenizer, through SegmentingTokenizerBase, uses only setText, current() and next(), and its tokens and offsets are unchanged, executed), and no downstream caller was found.
Summary
You set a text on an OpenNLPSentenceBreakIterator and call next(n) to jump n sentence boundaries, expecting the n-th boundary, as java.text.BreakIterator#next(int) promises ('Returns the nth boundary from the current boundary') and as n calls of next() give. When that boundary is the end of the text, next(n) returns DONE (-1) instead: with the model-free NLPSentenceDetectorOp on 'Whole text is one sentence.', next() from first() returns 27 but next(1) returns -1, and on the module's three-sentence test text (boundaries 0, 31, 59, 102) next(3) from first() returns -1 instead of 102 while next(2) correctly returns 59. The iterator is still moved to the end, so only the returned value is wrong; code that steps with next(n) until DONE loses the final sentence group.
