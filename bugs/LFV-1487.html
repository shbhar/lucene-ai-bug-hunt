JoinUtil score join over a one-segment index loses child scores and hits when the segment is searched in partitions (main only)

On main, a JoinUtil global-ordinals join with scores or a min/max filter can go wrong on a one-segment index that several threads collect in partitions. In the test, a parent with two children scoring 1 each gets 1.0, not 2.0: the one-segment collectors update shared arrays without a lock.

Summary

Medium, rank 264Only on unreleased main (since #16805, not on branch_11x), a scoring or min/max JoinUtil global-ordinals join over a one-segment index silently loses hits and returns wrong or infinite scores when the from-searcher uses opt-in segment partitions, because the single-segment collectors skip the per-block lock. The finding in 30 seconds

#

The join first runs the child query and records, per join value, whether it matched and, where needed, a score and a count. All search threads write into the same arrays. The lock that protects these writes is missing in the collectors used when the index has one segment.

Background: three pieces

#
  1. JoinUtil.createJoinQuery joins at query time. It first runs the from-query (here: the children) and keeps, per join value, a matched bit and, where needed, a score (sum, max or min) and a count. The parents are then matched and scored from these arrays.
  2. Join values are addressed by ordinal, a number per distinct value. With several segments an OrdinalMap translates segment ordinals to global ones. With one segment JoinUtil drops the map.
  3. An IndexSearcher with an executor searches slices in parallel. By default a slice holds whole segments. An application can override slices() to split a segment into doc-id ranges (partitions), so several threads collect the same segment.

The finding, step by step

#
  1. Index two children and one parent with the same join value into one segment. Search with an IndexSearcher that has an executor and whose slices() override splits the segment into partitions (the opt-in for intra-segment concurrency).
  2. Build the join: JoinUtil.createJoinQuery("join", children, parents, searcher, ScoreMode.Total, null). Each child scores 1, so you expect the parent to score 2.0.
  3. On main the parent scores 1.0. Two threads collect one child each. Both read the parent's running total (0), both add 1, both write 1: one child's score is lost.
  4. The join keeps a matched bit per join value and, where it needs them, a score and a count, shared by all threads. With two or more segments every update takes a lock. For one segment JoinUtil picks collectors that do the same updates with no lock.
  5. Without any thread ordering the same race also drops hits and returns scores of Infinity, -Infinity or NaN: Lucene's own randomized join test fails in 88 of 300 replays of a CI seed. Release 10.6.0 and the 11.0 branch collect the children on one thread and pass the same test.

Who is affected

#

Applications on unreleased main whose from-searcher has an executor and a slices() override that allows segment partitions (off by default), running a global-ordinals join with a score mode or a min/max filter over an index with exactly one segment, for example after a force merge. The wrong results are silent. No release and not the 11.0 branch.

Mechanism, terms and numbers1,326 words

JoinUtil.createJoinQuery(joinField, fromQuery, toQuery, searcher, scoreMode, ordinalMap[, min, max]) runs the from-query first and records, per join value, a matched bit and, where the join needs them, a score aggregate (every score mode but None) and a match count (Avg, or a min/max window that can exclude something). Since #16805 (e0a3a951e7ef, merged to main on 2026-11-09) this from-search goes through a CollectorManager with one collector per slice. When the searcher has an executor, the slices run concurrently, on the executor's threads and on the calling thread, and all collectors of one join write the same bit set and the same score and count arrays (GlobalOrdinalsWithScoreCollectorManager.java:44, :52-53).

With two or more segments the collectors make these updates under a per-block lock (:159-171, :254-261). For an index with one segment JoinUtil drops the ordinal map (JoinUtil.java:549-551), and the manager then hands out two other collectors that run the same statements with no lock (:191-202, :271-277). One segment is still collected by several threads when the searcher splits it into partitions, the opt-in intra-segment concurrency of IndexSearcher#slices. Updates are then lost: a parent's score misses children, parents disappear from the result, scores come back as Infinity, -Infinity or NaN, and a min/max filter counts too few children.

Only unreleased main has the defect. Release 10.6.0 and the 11.0 branch (branch_11x, daa54f2e0cd3) run the from-search on one thread and return the right score in the same test. #16805 carries the milestone 11.0.0, so 11.0 would be affected only if the change is applied to that branch before the release.

The code path

#
  1. One segment means no ordinal map. JoinUtil.createJoinQuery sets ordinalMap = null when the reader has one segment ("No need to use the ordinal map, because there is just one segment.", JoinUtil.java:549-551). A map the caller passes is dropped too, so a caller cannot choose the other path.
  2. The from-search can be concurrent. searcher.search(rewrittenFromQuery, manager) (JoinUtil.java:580-583). The searcher takes one collector per slice from the manager (GlobalOrdinalsWithScoreCollectorManager.java:86-94) and hands the slices to its TaskExecutor (IndexSearcher.java:768). When the searcher was built with an executor, the slices run on the executor's threads and on the calling thread (TaskExecutor.java:89-114); without one there is a single slice (IndexSearcher.java:222-231). A partition is searched as a doc-id range of its segment (:794).
  3. Shared state. The collectors are inner classes of the manager and write its collectedOrds bit set (:44), scores and occurrences (:52-53, commented "also written concurrently"). scores has blocks only for a score mode other than None (:69-73), and occurrences exists only for Avg or with a min/max window that can exclude something (:74-78). These are plain arrays and fields, with no volatile and no atomics. The class comment says "we only lock when collecting ... Locks are per-block" (:45-49); one lock covers 4096 ordinals (:79-82, :319).
  4. Two collector families (getLeafCollector, :129-137). With an ordinal map: OrdinalMapCollector, whose collect takes locks[globalOrd / arraySize] around the updates (:156-173), and NoScore's collector likewise (:251-263). Without one: SegmentOrdinalCollector.collect (:191-202) and NoScore's second collector (:271-277) run the same statements with no lock.
// SegmentOrdinalCollector.collect, lines 194-200: no lock
collectedOrds.set(segmentOrd);                        // bits[wordNum] |= bitmask
double existingScore = scores.getScore(segmentOrd);   // read
double newScore = scorer.score();
doScore(segmentOrd, existingScore, newScore);         // write, for Total: existing + new
if (occurrences != null) {
  occurrences.increment(segmentOrd);                  // occurrences[offset]++
}

The numbers (the repro)

#

Three documents, one per partition: child, child, parent, all with the join value k (ordinal 0). Thread 1 collects the first child: it reads the total 0 and calls score(). Thread 2 collects the second child: it reads the total 0 and calls score(). Both get 1 and both write 0 + 1 = 1 (Sum.doScore, :227-229). The parent scores 1.0 instead of 2.0. The test only makes this order certain, with one latch inside the from-query's score(), the one public place between the read and the write.

What else the same statements lose

#

These are examples that were executed or modelled, not a complete list of what the Java memory model allows for unsynchronized fields.

  • A hit. LongBitSet.set is a read-modify-write of one 64-bit word (LongBitSet.java:155-160). Two join values in the same word can lose one bit, and that parent is missing from the result, also without min/max.
  • A whole block. Scores.setScore and Occurrences.increment allocate their 4096-entry block on first use (:336-342, :368-371). Two threads can each allocate it, and setScore publishes the new block before it fills it with the unset value (:338-341), so a score another thread just wrote is overwritten. The unset value is -Infinity for Max and +Infinity for Min (:296-302), and a lost count makes Avg divide by 0 (:116). As the author of #16805 noted on the PR (2026-10-12), an earlier revision had this first-allocation gap in the collectors that lock; it was fixed there before the merge.
  • A count. occurrences[offset]++ (:372) loses increments, so a min/max filter (:102-112) drops a parent or keeps one it should remove, and Avg divides by a count that is too low.

Measured without a latch

#

These runs use a plain TermQuery and no coordination. The counts are statistical and change from run to run.

  • A probe, on one segment of 400,000 documents in 4 partitions (200,000 parents with one child each, 10 joins per case), counting the hits a top-N search returns: 38 of 50 joins wrong. Max was wrong in 10 of 10 joins (188,811 to 198,824 of the 200,000 parents returned), Total in 5, Min in 7, Avg in 7, None with min = max = 1 in 9; Min and Avg returned 399 non-finite scores. With each fix: 50 of 50 exact. Earlier runs of the same probe had every join wrong.
  • A diagnostic on the same index and cases, counting each join three ways (returned by a top-N search, matched at all, and the kind of each match's score): 31 of 50 joins wrong. For Max a top-N search returned 190,287 to 197,823 of the 200,000 parents. Most of the missing parents had matched with a score of -Infinity (215 to 9,475 per join), which a top-N search by score does not return, and 15 to 4,716 per join were not matched at all. For Total, Min, Avg and None with min = max = 1 every missing parent was missing from the match set (up to 502 per join); Total gave up to 10,484 parents per join a wrong finite score, and Min and Avg returned 384 scores of Infinity and one NaN. With the recommended fix: 50 of 50 joins matched all 200,000 parents with the right score.
  • Why Max shows as missing hits. Its unset value is -Infinity, and TopScoreDocCollector skips such a hit (score <= topScore against the queue's -Infinity sentinel, TopScoreDocCollector.java:113; its javadoc, :30-31, says of NaN and NEGATIVE_INFINITY that they "are not valid scores. This collector will not properly collect hits with such scores."). So the 399 non-finite scores of the probe cannot include Max.
  • Lucene's own TestJoinUtil.testRandomOrdinalsJoin, unchanged, with the seed of a CI failure mail, assertions on and tests.multiplier=2 as in the mail's reproduce line: 88 of 300 replays fail (wrong hit sets, wrong top documents, -Infinity, Infinity, "NaN score"). With each fix: 0 of 300.

ScoreMode.None with a window that excludes nothing (min <= 1 and max == Integer.MAX_VALUE, the condition at JoinUtil.java:569) is not on this path: it uses GlobalOrdinalsCollectorManager (JoinUtil.java:569-579), which sets its shared bits with compare-and-set also when there is no ordinal map.

Exposure and likelihood374 words
  • Who. An application that does all three: (a) gives the from-searcher an executor and overrides IndexSearcher#slices to allow segment partitions; (b) runs a JoinUtil global-ordinals join with ScoreMode.Total, Avg, Max or Min, or with None and a min/max window that can exclude something (min > 1 or max < Integer.MAX_VALUE); (c) on an index with exactly one segment. That is the force-merged index partitions are advertised for ("useful to max out available resource usage especially with force merged indices or big segments", CHANGES.txt:2433-2439), or a small index.
  • Opt-in. slices() passes allowSegmentPartitions = false by default (IndexSearcher.java:323-325). Without an executor, or without partitions, one thread collects the one segment and the join is exact.
  • Silent in production. No exception, and no assertion of Lucene's production code fires: the test fails the same way with assertions on and off. The join returns fewer hits, lower sums, or scores of Infinity, -Infinity or NaN, and two identical requests can give different results. Lucene's test framework is stricter: its AssertingScorer rejects NaN and negative scores, which is how part of the replays of Lucene's own test fail.
  • Any size. The test has three documents. An earlier differential on indexes of 2 to 80 documents had 22 to 23 mismatches in 27,000 checks, all on one-segment indexes under partitions. On a 400,000-document segment 38 of 50 joins were wrong in one run and 31 of 50 in another (statistical; see the full explanation above).
  • Not affected. Two or more segments (the locked collectors do not have this race; every check on 2, 3, 4 and 6 segments under every slicing in the earlier differential was exact); ScoreMode.None with a window that excludes nothing (min <= 1, no max); the term and numeric joins; every release; the 11.0 branch as it stands.
  • Workaround. Build the join with a from-searcher that has no executor or does not partition segments. The race is only in the from-search inside createJoinQuery; the returned query only reads the arrays.
  • Likelihood: plausible. An estimate, not usage data: it needs the opt-in, a one-segment index and this kind of join, and only unreleased main has it. Where those meet, most joins tried went wrong.

Minimal repro

#

One JUnit test in lucene/join (no package-private access): three documents in one segment, one partition each, ScoreMode.Total. A latch in the from-query's score() makes both search threads read the parent's total before either writes. It fails on main with assertions on and off, and passes on the 11.0 branch, on 10.6.0 and with the fix.

Expected
The parent scores 2.0, the sum of its two children's scores (1 + 1).
Observed
The parent scores 1.0 (expected:<2.0> but was:<1.0> at line 76): one child's score is lost.

All files of this repro: repro/LFV-1487/

More files, environment, full output524 words

TestGlobalOrdinalsJoinSegmentPartitions (145 lines with the license header, package org.apache.lucene.search.join): one test method, one assertion, no randomness, no loop, no sleep. It uses two search threads because concurrency is the bug. The outcome does not depend on the seed.

  • Which API. The bug is triggered through public API (JoinUtil.createJoinQuery, IndexSearcher), with the test framework around it and no package-private access. The from-query helper, an anonymous FilterWeight, uses the inherited Weight.DefaultScorerSupplier, a protected class marked @lucene.internal (Weight.java:202-207) that Lucene's own queries and tests use the same way. The from-query is a scheduling aid: it ignores the boost and the score mode it is given and always scores 1.
  • Why a latch. The race is a read-modify-write around scorer.score() inside collect(): read the total, score, write total + score. The only public place between the read and the write is the from-query's Scorer.score(). So the from-query is a TermQuery weight wrapped in FilterWeight and FilterScorer, whose score() counts down one CountDownLatch(2) and waits on it for at most 5 seconds. The latch is the only synchronization the test adds.
  • Why three documents. One document per partition is the smallest index with two children in two partitions. Equal child scores make the wrong value the same whichever thread writes last.
  • Which two threads. The executor has one thread. TaskExecutor.invokeAll forks work to the executor and meanwhile runs tasks that have not started on the calling thread (TaskExecutor.java:89-114). The thread that scores the first child waits in the latch, so the other thread takes the second child.
  • It can pass falsely, never fail falsely. If the second thread does not reach score() within the 5 seconds (a sequential from-search, or a machine so loaded that the executor's task starts that late), the wait runs out, the children are collected one after the other and the score is 2.0. That is what happens where the from-search is sequential (the 11.0 branch, 10.6.0) or locked across scoring: the test passes after about 6 seconds. On main it fails in about 1 second.
  • As a regression test. With the recommended fix it passes in under a second, with both threads really scoring at once. :lucene:join:check -x test accepts the file as it is.

Why it looks unintended

#
  • CollectorManager's javadoc: the collection of a segment "may be split across threads", and the manager must handle it.
  • The same class locks these same updates when there are two or more segments. Nothing exempts one segment.
  • Lucene's own randomized join test asserts exact results in this setup. It fails on main and never with the fix.
The full argument347 words
  • The score contract. ScoreMode.Total: "Parent hit's score is the sum of all child scores" (ScoreMode.java:31).
  • The join's javadoc. createJoinQuery puts no condition on the searcher ("The index searcher used to execute the from query") and says "In case of a single segment index, no ordinal map needs to be provided" (JoinUtil.java:484-487, :522-525).
  • The CollectorManager contract. "Multiple LeafCollectors may be requested for the same LeafReaderContext ... across the different Collectors returned by newCollector(). Any computation or logic that needs to happen once per segment requires specific handling in the collector manager implementation, because the collection of an entire segment may be split across threads." (CollectorManager.java:35-39; the same in MIGRATE.md:1771-1779).
  • The migration note of the change itself. "Collectors must be rewritten to be thread safe and provided by a wrapping CollectorManager.newCollector()." (MIGRATE.md:854-856). It is advice to users who migrate their own collectors, so it shows the general expectation and is weaker evidence than the CollectorManager javadoc and the locked sibling collectors.
  • The class locks the same statements on its other path (GlobalOrdinalsWithScoreCollectorManager.java:159-171, :254-261) and says so in its comment (:45-49).
  • Partitions come with a performance caveat only. IndexSearcher#slices: "not enabled by default as there is still a performance penalty for queries that require segment-level computation ahead of time" (IndexSearcher.java:317-321). Where the join module cannot support partitions it throws: ParentsChildrenBlockJoinQuery "does not support intraSegment concurrency" (ParentsChildrenBlockJoinQuery.java:192-197).
  • Lucene's own test. TestJoinUtil.createContext force-merges to one segment at random (TestJoinUtil.java:1783-1788) and searches with newSearcher (:1795), which enables partitions at random (LuceneTestCaseParent.java:1146-1158, :2659-2689). testRandomOrdinalsJoin (:441) compares hits and scores exactly. Two automated CI mails of 2026-11-09 and 2026-11-13 show it failing after the merge (Prior reports); both seeds fail on main and never with the fix.
  • History. A regression. The unlocked collection pattern dates from 2015 and was safe while one thread ran it. #16805 added the lock to the two ordinal-map collectors and not to the two single-segment ones.
The devil's-advocate check149 words

The strongest case for "intended": one segment means one thread. The class comment reasons about "per-segment threads" (GlobalOrdinalsWithScoreCollectorManager.java:47-48) and JoinUtil says "No need to use the ordinal map, because there is just one segment", so the unlocked path could be a deliberate saving. Partitions are off by default behind the Expert slices() hook, and JoinUtil and CollectorManager are marked experimental.

Why it fails: no document permits results that depend on how the searcher slices the index. The CollectorManager javadoc puts exactly this case on the manager. The migration note of the same change asks users for thread-safe collectors. The sibling GlobalOrdinalsCollectorManager (#16091, in 10.6.0) handles the one-segment case atomically. The discussion of #16805 names no exemption for one segment. And Lucene's own randomized test asserts exact results under partitions on one segment and fails on main. Each earlier check that argued the intended reading rated it weak.

Suggested fix

#

Recommended The block lock in the single-segment collectors, taken after scoring (validated)

Take the same per-block lock in the two single-segment collectors and call scorer.score() before taking it, so only the three array updates are locked. Validated: the test passes in under a second, the join module's 106 tests pass, and Lucene's randomized join test no longer fails (0 of 300 replays; 88 of 300 without the fix).

int segmentOrd = docTermOrds.ordValue();
double newScore = scorer.score();
Lock lock = locks[segmentOrd / arraySize];
lock.lock();
try {
  collectedOrds.set(segmentOrd);
  doScore(segmentOrd, scores.getScore(segmentOrd), newScore);
  if (occurrences != null) {
    occurrences.increment(segmentOrd);
  }
} finally {
  lock.unlock();
}
All options and trade-offs5 options · 773 words

Three fixes were built and validated the same way; all change one file, GlobalOrdinalsWithScoreCollectorManager.java. A larger alternative and an application-side workaround were not built. Which shape to take is the maintainers' call.

The block lock in the single-segment collectors, taken after scoring (validated) (recommended)

#

Take locks[segmentOrd / arraySize] in SegmentOrdinalCollector.collect and in NoScore's single-segment collector, as the ordinal-map collectors do, and call scorer.score() before the lock is taken, in both score collectors. Only the updates of the shared arrays are inside the lock. One file, +23/-10.

int segmentOrd = docTermOrds.ordValue();
double newScore = scorer.score();
Lock lock = locks[segmentOrd / arraySize];
lock.lock();
try {
  collectedOrds.set(segmentOrd);
  doScore(segmentOrd, scores.getScore(segmentOrd), newScore);
  if (occurrences != null) {
    occurrences.increment(segmentOrd);
  }
} finally {
  lock.unlock();
}

Trade-offs

  • For: scoring runs in parallel and the critical section is three array updates. That matters most on one segment, where every partition works on the same ordinal blocks. The test passes in under a second and has both threads scoring at once, so it works as a regression test.
  • Against: it also changes three lines in the collector that already locks: scorer.score() moves in front of the lock and the read moves into the doScore call. No benchmark was run.

The same lock exactly as the multi-segment collectors take it (validated)

#

Take locks[segmentOrd / arraySize] in the two single-segment collectors around the unchanged statements, mirroring the ordinal-map collectors line for line. One file, +22/-8.

Trade-offs

  • For: the smallest change; it copies the code beside it.
  • Against: the lock is held across scorer.score(), as in the existing collectors. On one segment scoring is then serialized whenever two threads hit the same block, which is always when there are fewer than 4096 join values. The test needs its bounded 5-second wait with this fix.

One locked collector for both cases (validated)

#

Delete the two single-segment collectors and use the locked ones with LongValues.IDENTITY as the ordinal lookup when there is no ordinal map. One file, +26/-70.

Trade-offs

  • For: one code path, so the two cases cannot drift apart again; about 45 lines fewer.
  • Against: one extra LongValues.get call per collected document on one segment. The lock is held across scoring as in the previous option; it can be combined with the recommended one.

No shared state (not built)

#

Give each collector its own arrays and merge them in reduce(), or use atomic structures as GlobalOrdinalsCollectorManager does for its bit set.

Trade-offs

No lock at all, but a larger rewrite, more memory per slice, and the double-precision sums need care to stay exact when merged. Not built.

Workaround for applications: no partitions on the from-searcher

#

Build the join with a from-searcher that has no executor or does not partition segments. The returned query can then be run by any searcher: it only reads the arrays.

Trade-offs

Not a fix. The from-search of a one-segment index then runs on one thread, as in 10.6.0.

Downstream note

#

No released Lucene contains this code; where it runs, a join used as a filter can drop matching parents, and under a min/max filter it can also keep a parent that the filter should have removed.

How it was found

#

A differential test ran JoinUtil joins against a brute-force join, on main before and after 13 new commits. On the new main the global-ordinals joins gave wrong, run-dependent scores on one segment under partitions; the old main did not. Reading the two collector families explained it, and an exhaustive interleaving model confirmed it.

The method in full198 words

Method: semi-formal (a seeded differential first, then an exhaustive model of the interleavings).

  • Differential. The 13 upstream commits between the previous main f794ff5a505c and 781025d6fe32 were compared with a seeded harness: 8 join kinds, 5 score modes and 4 searcher setups, each against a brute-force join. It showed wrong, run-dependent scores on the global-ordinals lines for one segment under segment partitions on the new main and none on the old one. With two or more segments the global-ordinals lines were exact.
  • Reading the code. The two collector families in GlobalOrdinalsWithScoreCollectorManager differ in one thing: the ordinal-map collectors lock, the single-segment ones do not.
  • Interleaving model. Two threads, one document each, every shared access one step: the unlocked collectors reach a lost bit, a wrong score or a wrong count in 24 of 30 configurations, the per-block lock in none. A deliberately broken lock stripe of 32 ordinals is caught in 12, which shows the model can see a wrong lock.
  • Reduction. First to a four-document test with two latches, then to the three-document, one-latch test of the repro. Lucene's own randomized test was replayed with and without the fix to tie the public CI failures to this defect.

The commit removed IndexSearcher.search(Query, Collector) and moved the join's score path from one sequential Collector to GlobalOrdinalsWithScoreCollectorManager, whose collectors share the bit set and the score and count arrays. Segment partitions exist since 10.0.0 (#13542), but until #16805 the join's score path ran on the calling thread. #16091 (10.6.0) had moved only the ScoreMode.None path without min/max to a manager written for concurrent collection.

LFV-1487, snapshot of 2026-11-23

Registry title
JoinUtil's scoring or min/max global-ordinals join over a one-segment index returns wrong and infinite scores and loses hits when the from-searcher splits the segment into partitions: since #16805 (main only) the single-segment collectors update the shared ordinal, score and count arrays without the per-block lock
Area
join / JoinUtil global-ordinals join with scores or min/max: concurrent collection of one segment in partitions (GlobalOrdinalsWithScoreCollectorManager)
Priority
Medium, rank 264: Only on unreleased main (since #16805, not on branch_11x), a scoring or min/max JoinUtil global-ordinals join over a one-segment index silently loses hits and returns wrong or infinite scores when the from-searcher uses opt-in segment partitions, because the single-segment collectors skip the per-block lock. It is Medium because the results are silently wrong through a public API in a setup that upstream documents and tests, and it is in Medium because partitions are off by default, the index must have exactly one segment and no release has it.
Impact class
silent wrong results
Impact note
Hits only unreleased code (upstream main since #16805; not on branch_11x, in no release) and only an opt-in searcher: an application whose from-searcher has an executor and overrides IndexSearcher#slices to allow segment partitions (off by default) and that runs a JoinUtil global-ordinals join with a score mode (Total, Avg, Max, Min) or with a min/max filter over an index of exactly one segment (a force-merged or a small index) silently gets parent scores that miss children, scores of Infinity, -Infinity, NaN or 0 and missing hits (parents that are not matched at all and, for most of the hits missing under ScoreMode.Max, parents that match with a score of -Infinity, which a top-N search by score does not return; under min/max also hits that the filter should have removed), with -ea and -da and at any index size; with two or more segments the locked ordinal-map collectors are used and results are exact, and a from-searcher without an executor or without partitions is not affected.
Summary
You join parent documents to their children with JoinUtil.createJoinQuery(joinField, fromQuery, toQuery, searcher, ScoreMode.Total, null) on an index with one segment, and your searcher splits that segment into partitions so that two threads collect it (the documented intra-segment concurrency); one parent has two children that score 1 each, so you expect the parent to score 2. Instead, on main since #16805, it scores 1.0: for a one-segment index JoinUtil drops the ordinal map, and the collectors used in that case update the shared ordinal bit set and the score and count arrays without the per-block lock that the multi-segment collectors take, so one thread's update overwrites the other's. Without any scheduling help, most joins tried over a larger one-segment index also go wrong (38 of 50 and 31 of 50 in the two latest runs, every join in the earlier ones): parents drop out of the match set, and others get a score of Infinity, -Infinity, NaN or 0 (a top-N search by score does not return a hit that scores -Infinity, which is most of what goes missing under ScoreMode.Max), while release 10.6.0 and the main before #16805, which collect the from side on one thread, are exact.
