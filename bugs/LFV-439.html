DictionaryCompoundWordTokenFilterFactory on main warns that onlyLongestMatch "has been removed" when the key is not set

On main, the dictionaryCompoundWord filter factory logs "onlyLongestMatch has been removed" for every configuration that never sets that key, the default included, but not for onlyLongestMatch="false". It checks the key's value (default true), not its presence; tokens are unaffected, and no release has this code.

The finding in 30 seconds

#

The factory checks the removed key's value, whose default is true, instead of checking whether you set the key.

Background: the compound-word filter and its two settings

#
  1. DictionaryCompoundWordTokenFilter splits compound words with a word list: with {donau, dampf, dampfschiff, schiff}, the word donaudampfschiff also yields donau and dampfschiff.
  2. Its factory, SPI name dictionaryCompoundWord, builds it from string settings, as CustomAnalyzer, TokenFilterFactory.forName and Solr-style schemas do.
  3. 10.2.0 added onlyLongestMatchIgnoreSubwords (default true) to replace the older onlyLongestMatch. On main the old key does nothing any more; the factory still accepts it and logs a warning that it was removed.

The finding, step by step

#
  1. On main, build the compound-word filter factory with only a dictionary, new DictionaryCompoundWordTokenFilterFactory(new HashMap<>(Map.of("dictionary", "d.txt"))), as Lucene's own factory test does, or add the replacement setting onlyLongestMatchIgnoreSubwords="true".
  2. You expect no message about onlyLongestMatch: you never set it. 10.5.2 and 10.6.0 log nothing, and 10.5.2 gives the same tokens as main: with the dictionary {donau, dampf, dampfschiff, schiff}, donaudampfschiff gives [donaudampfschiff, donau, dampfschiff] on both.
  3. Instead each such construction logs WARNING: onlyLongestMatch has been removed and replaced by onlyLongestMatchIgnoreSubwords. Of 7 configurations tried, 5 are warned; the 2 silent ones set the removed key to false: within the factory settings, only passing the ignored key with a value other than "true" (ignoring case) silences it.
  4. Why: the factory reads the removed key with getBoolean(args, "onlyLongestMatch", true) and warns if (onlyLongestMatch). A missing key returns the default true, so it looks set. The value feeds nothing else, so only the log is wrong.

Who is affected

#

Applications on main (unreleased 11.0) that build this opt-in filter through its factory: CustomAnalyzer, TokenFilterFactory.forName or a Solr-style schema. Every construction without the key logs the warning, so migrated users can silence it, within the factory settings, only by adding the removed key, while a stale onlyLongestMatch="false" goes unflagged. Tokens, indexes and queries are unchanged.

Mechanism, terms and numbers506 words

On main, DictionaryCompoundWordTokenFilterFactory (SPI name dictionaryCompoundWord) still reads the removed onlyLongestMatch key, now only to decide whether to log: boolean onlyLongestMatch = getBoolean(args, "onlyLongestMatch", true); if (onlyLongestMatch) LOG.warning("onlyLongestMatch has been removed and replaced by onlyLongestMatchIgnoreSubwords");. Because getBoolean returns the default true for a missing key, every construction that does not mention the key logs the warning: the plain dictionary=... configuration that Lucene's own factory test uses, and configurations already migrated to onlyLongestMatchIgnoreSubwords. A configuration that names the now-ignored key with false gets no warning, and the class javadoc example still shows onlyLongestMatch="true". Only the log is affected: create() passes only onlyLongestMatchIgnoreSubwords to the filter. The lines came with #14356 (ebc63504bd6, merged 2025-05-10, an 11.0 API removal) and are in no release; 9.12.3 through 10.6.0 log nothing. Warning when the key is present, whatever its value, fixes it.

Terms

#
  • AbstractAnalysisFactory.getBoolean(args, name, defaultVal): removes the setting from the map and returns its value, or defaultVal when it is absent: String s = args.remove(name); return s == null ? defaultVal : Boolean.parseBoolean(s); (lucene/core/src/java/org/apache/lucene/analysis/AbstractAnalysisFactory.java:213-216 at 645d4fe14a20).
  • onlyLongestMatchIgnoreSubwords: the replacement setting, read with default true (DictionaryCompoundWordTokenFilterFactory.java:74). The filter javadoc says it supersedes onlyLongestMatch (DictionaryCompoundWordTokenFilter.java:54-56).

The bug

#
  1. The constructor reads the removed key and warns on its value (DictionaryCompoundWordTokenFilterFactory.java:69-72):
boolean onlyLongestMatch = getBoolean(args, "onlyLongestMatch", true);
if (onlyLongestMatch)
  LOG.warning(
      "onlyLongestMatch has been removed and replaced by onlyLongestMatchIgnoreSubwords");
  1. A missing key and "true" (in any letter case) give true. "false" gives false, and so does any other present value such as "yes" or "", because Boolean.parseBoolean returns true only for "true" (executed: a six-value probe on main). The default true goes back to the first factory version (2008), when the key still had a meaning.
  2. The value is used for nothing else: create() passes only the dictionary, the size limits and onlyLongestMatchIgnoreSubwords to the filter (:97-103), whose 6-argument constructor hands false to the base class (DictionaryCompoundWordTokenFilter.java:58-66).
  3. So the warning fires for every configuration that never set the key, and is silent for the one that set it to false. The class javadoc example still writes onlyLongestMatch="true" (:35-36), so following it also gives the warning.

Why it looks unintended

#
  • The message says the key "has been removed", yet configurations that never used it get it.
  • For deprecated factory keys a warning is the only mechanism (Uwe Schindler, #14311); Uwe Schindler's #15900 sketch warns "if you set" the old key.
  • #14356's author asked on this line "Does this check make sense?"; nobody answered. No doc or test sets it.
The full argument233 words
  • The message. "onlyLongestMatch has been removed and replaced by onlyLongestMatchIgnoreSubwords" is a statement about a key the configuration used. Logging it because a key is missing contradicts its own text.
  • The project's stated mechanism for deprecated factory keys. On #14311, the PR that introduced the replacement setting, Uwe Schindler (uschindler) wrote on 2025-03-05: "We have no mechanism for deprecating those map keys of the factory. We can only log a warning, but have no standard way for this yet." On #15900 (2026-04-03) Uwe Schindler sketched the same pattern for another factory: "if you set prefixLength it uses the old buggy behaviour and logs a warning that it is deprecated". The first names the mechanism without saying when it should fire; the second ties the warning to the user setting the key. Both are context, not a rule for this factory.
  • The author's own question. The only review comment of #14356's author, renatoh, sits on the if (onlyLongestMatch) hunk: "@rmuir Does this check make sense?" (2025-03-14). Nobody answered; the PR merged on 2025-05-10.
  • No documentation or test sets it. No javadoc, CHANGES.txt entry, MIGRATE.md entry or test says when the factory logs. MIGRATE.md:648-668 (GITHUB#14356) covers only the removed filter constructor. TestDictionaryCompoundWordTokenFilterFactory has only testDecompounding and testBogusArguments.
  • Lucene's canonical use is warned. testDecompounding builds the factory with only dictionary, as the minimal test does, so Lucene's own factory test takes the warning path.
The devil's-advocate check184 words

The strongest case for "intended" (a read-only reviewer from another model family, OpenAI GPT-5.6, rated it moderate): the check flags everyone whose legacy onlyLongestMatch is effectively true, including by default, because that is the behaviour that went away, and spares an explicit false, because that configuration lost nothing.

Why it does not hold up (executed): with onlyLongestMatchIgnoreSubwords at its default true, onlyLongestMatch already had no effect on 10.5.2, because the filter ORs the two flags. So the default and the migrated configurations give the same tokens on 10.5.2 and main and never depended on the key, yet they are warned. Against 10.1.0, where onlyLongestMatch=false did change tokens, main does not warn that configuration. On neither upgrade path does the value-based condition pick the configurations whose output changed, the check ignores onlyLongestMatchIgnoreSubwords read on the next line, and nothing records such a policy as a decision. This weakens the intended reading but does not rule it out: the cross-model fact check of the brief (OpenAI GPT-5.6, read-only) again rated it moderate, a plausible migration-warning policy with an inconsistent condition. The maintainers decide.

Suggested fix

#

Recommended A. Warn when the removed key is present, whatever its value; fix the javadoc example

Warn only when the key is present, if (args.remove("onlyLongestMatch") != null) LOG.warning(...), and change the javadoc example to onlyLongestMatchIgnoreSubwords. The repro then passes with assertions on and off, and the compound tests and check pass. Add a MIGRATE line too: onlyLongestMatchIgnoreSubwords="false" alone loses its accidental warning, though its tokens changed in 11.0.

Trade-offs

  • Effect, executed on the 7-configuration matrix: the warning is logged for exactly the 4 configurations that set onlyLongestMatch (true or false) and for none of the 3 that do not; no token changes anywhere.
  • onlyLongestMatchIgnoreSubwords="false" without the old key loses the warning it gets today by accident. Its tokens did change from 10.5.2 to main (dampf is now emitted for donaudampfschiff), because the 10.5.2 factory passed the default onlyLongestMatch=true through the constructor that #14356 removed. That change follows from the intended removal and is not this bug, but MIGRATE.md does not mention it: pair this fix with the MIGRATE line below.
  • Diagnostics for unusual values (executed, six-value probe on main and with this change): today a present value other than "true", such as "yes" or "", is consumed with no message; with the fix it warns like any other use of the key. Probably wanted, but a behaviour change to mention.
