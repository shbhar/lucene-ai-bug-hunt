GraphTokenStreamFiniteStrings.getFiniteStrings: next() after the last path throws NullPointerException instead of NoSuchElementException

The iterator that GraphTokenStreamFiniteStrings.getFiniteStrings() returns ignores the answer of its own hasNext() check: one next() too many throws NullPointerException (AssertionError with assertions on) instead of the NoSuchElementException that java.util.Iterator specifies. Lucene's own query builders never call next() past the end (by reading) and are not affected.

The finding in 30 seconds

#

Background: token graph paths and the Iterator contract

#
  1. A synonym filter can turn a token stream into a graph (for "new york" with the synonym ny, two paths: [new, york] and [ny]). GraphTokenStreamFiniteStrings builds an automaton from it, and getFiniteStrings() returns a java.util.Iterator<TokenStream> with one plain stream per path. Lucene's QueryBuilder uses it to build one clause per path.
  2. A java.util.Iterator signals its end twice: hasNext() returns false, and next() then throws NoSuchElementException. Generic code relies on the second, for example a loop that catches the exception, or Guava's Iterators.getOnlyElement.

The finding, step by step

#
  1. Build new GraphTokenStreamFiniteStrings(new CannedTokenStream(new Token("x", 0, 1))): a token graph with 1 token, so exactly 1 path, [x]. Take its getFiniteStrings() iterator.
  2. Call next(): it returns the stream for [x]. hasNext() now returns false: no paths are left.
  3. Call next() once more. You expect NoSuchElementException, as java.util.Iterator.next() specifies.
  4. Instead you get NullPointerException: Cannot read field "offset" because "ids" is null, or an AssertionError with assertions on. On a graph with 0 tokens the very first next() throws NullPointerException.
  5. Why: next() calls hasNext() when no path is waiting, ignores the false, and wraps the missing path (null) in a new stream, whose constructor then reads it.

Who is affected

#

Only code that calls getFiniteStrings() itself and calls next() without a true hasNext(): a next()-first loop that catches NoSuchElementException, or a generic helper such as Guava's Iterators.getOnlyElement over a graph with no tokens. Lucene's QueryBuilder checks hasNext() first, and IntervalBuilder calls a bare next() only where a path exists. The effect is a loud wrong exception, never a wrong result.

Mechanism, terms and numbers385 words

GraphTokenStreamFiniteStrings.getFiniteStrings() and getFiniteStrings(int, int) return a java.util.Iterator<TokenStream> with one stream per path of a token graph. Its next() calls hasNext() when no path is buffered, so it works without a prior hasNext(), but it ignores the answer (GraphTokenStreamFiniteStrings.java:151-153 at 5adff78bb168) and wraps current even when the iteration has ended and current is null (:154). The inner FiniteStringsTokenStream constructor then fails: assert ids != null (:62) with assertions on, NullPointerException: Cannot read field "offset" because "ids" is null (:64) with assertions off; on a graph with no tokens, tokens[0].cloneAttributes() (:61) throws first. java.util.Iterator.next() specifies NoSuchElementException. hasNext() itself is correct and stays false, so nothing else goes wrong. LUCENE-7638 introduced the lazy iterator in 6.5.0 (2017); every release run since then fails the same way. Lucene's QueryBuilder checks hasNext() first and IntervalBuilder calls a bare next() only where a path exists, so only code that drives the iterator itself, or hands it to a generic helper, sees the wrong exception. A two-line guard fixes it. Priority Low.

The mechanism (main 5adff78bb168, GraphTokenStreamFiniteStrings.java)

#
  1. The adapter. getFiniteStrings(int, int) (:132-158) wraps the inner FiniteStringsIterator, which returns null when no path is left (util/automaton/FiniteStringsIterator.java:97-100). getFiniteStrings() only calls getFiniteStrings(0, -1) (:127-128), so both return this iterator; the repro runs the no-argument one.
  2. hasNext() is right (:139-147): if nothing is buffered it fetches the next path into current, sets finished when that is null, and returns current != null.
  3. next() ignores it (the fix site) (:150-157): if (current == null) { hasNext(); } drops the result, then new FiniteStringsTokenStream(current) (:154) runs with current == null.
  4. The constructor fails (:60-66): super(tokens[0].cloneAttributes()) (:61; NullPointerException when the graph has no tokens), assert ids != null (:62), this.offset = ids.offset (:64, NullPointerException with assertions off).

Exposure and likelihood297 words
  • Who. Application code that calls the public getFiniteStrings() or getFiniteStrings(start, end) itself and calls next() without a true hasNext() first: a next()-first loop that catches NoSuchElementException to detect the end, a "take the first path" step on a graph that may have no tokens, or a generic iterator helper. Executed: Guava's Iterators.getOnlyElement, documented to throw NoSuchElementException on an empty iterator, gets a NullPointerException (:61) over the iterator of a graph with no tokens, with assertions on and off. Lucene's own TestUtil.checkIterator also fails on this iterator, though not with its own message: the NullPointerException (AssertionError with assertions on) escapes from next() before its "broken iterator" check is reached.
  • Also exposed (by reading, not run). A QueryBuilder subclass that overrides newGraphSynonymQuery(Iterator<Query>) gets an iterator whose next() delegates to this one (QueryBuilder.java:520-536).
  • Not affected (by reading). QueryBuilder.analyzeGraphBoolean (:520-536, with the default newGraphSynonymQuery loop at :618-622) and analyzeGraphPhrase (:575-577) call next() only after a true hasNext(). IntervalBuilder.analyzeGraph loops on hasNext() (IntervalBuilder.java:217-219) and calls a bare next() only on a graph segment without side paths, where a path exists (:230-233). So the stock query-builder paths read here never call next() past the end.
  • Effect. A wrong exception type, thrown before any state changes: hasNext() stays false, no result is wrong, nothing hangs.
  • Scale and likelihood. Not tied to the graph's size by the code (next() ignores hasNext() on every graph); run on a one-token graph (the repro) and on a graph with no tokens, where the first next() is itself a past-the-end call (hasNext() is already false). No configuration involved. Rare: it needs next()-first code against this helper, and no public report of it was found since 6.5.0 (2017).

Why it looks unintended

#
  • getFiniteStrings() returns a plain java.util.Iterator, whose next() must throw NoSuchElementException when nothing is left; no javadoc narrows that.
  • next() already calls hasNext() itself; only the false branch is missing. Lucene's TestUtil.checkIterator rejects this iterator.
  • Lucene added the same guard to another iterator "to comply with the Iterator API" (LUCENE-7307, #8361).
The full argument194 words
  • Contract. The class is public final in the exported package org.apache.lucene.util.graph (module-info.java:49) with no @lucene.internal or @lucene.experimental tag (GraphTokenStreamFiniteStrings.java:42-47). Both methods return java.util.Iterator<TokenStream>; their javadoc ("Get all finite strings from the automaton.", :126; :131) and the package javadoc add nothing that narrows Iterator.next()'s @throws NoSuchElementException if the iteration has no more elements.
  • Lucene's own rule. TestUtil.checkIterator defines a well-formed iterator as one that "throws NoSuchElementException if {@code next} is called after {@code hasNext} returns false" (TestUtil.java:221-222). Run on this iterator it fails, with the NullPointerException (AssertionError with assertions on) escaping from next() (:237) before its own "broken iterator (allows next() when hasNext==false)" check (:238) is reached. Other hand-written iterators in core throw it (FilterIterator.java:53, MergedIterator.java:105, PointInSetQuery.java:483); the last guard was added in LUCENE-7307 (#8361) after Adrien Grand asked for it "to comply with the Iterator API".
  • History. LUCENE-7638 (#8689, 2017) introduced the lazy iterator; its discussion never mentions exhaustion. No commit has added NoSuchElementException under util/graph/, and no test covers next() past the end (TestGraphTokenStreamFiniteStrings.testEmpty, :74-80, checks only hasNext()).
The devil's-advocate check141 words

The strongest case for "intended": calling next() after hasNext() returned false is a caller error; it fails loudly and changes nothing; the author's assert ids != null shows the assumption; every in-tree caller iterates in lockstep; and no report of it was found in about 9 years.

Why it fails: the method returns java.util.Iterator, whose contract specifies the outcome of exactly this call, so it is a specified case, not a violated precondition, and nothing narrows it; Lucene's own checkIterator rule and the LUCENE-7307 request treat it as a bug. What the argument does establish: the impact is only a wrong exception type, hence priority Low. The devil's-advocate verifier and the cross-model reviewer both rated the "intended" case weak. A later cross-model fact check of this write-up rated it moderate, and still judged the rebuttal adequate and priority Low proportionate.

Suggested fix

#

Recommended Throw NoSuchElementException when hasNext() is false (fix A)

Honour hasNext()'s answer at the top of next(): if (hasNext() == false) { throw new NoSuchElementException(); } in place of the ignored call. The normal path only adds a hasNext() call that returns at once. The repro passes with assertions on and off, and the 54 tests of the closest suites pass.

        if (hasNext() == false) {
          throw new NoSuchElementException();
        }

Throw NoSuchElementException when hasNext() is false (fix A) (validated by the checks) (recommended)

#

In getFiniteStrings(start, end)'s iterator, replace if (current == null) { hasNext(); } (GraphTokenStreamFiniteStrings.java:151-153) with a guard that throws, and import java.util.NoSuchElementException. This also covers the graph with no tokens, since next() no longer reaches the constructor.

        if (hasNext() == false) {
          throw new NoSuchElementException();
        }

Trade-offs

None worth naming: the normal path now makes one hasNext() call per next(), which returns at once when a path is buffered (two field reads), so the extra cost is negligible; only the exhausted call changes, from NullPointerException/AssertionError to NoSuchElementException.

How it was found

#

A semi-formal proof-obligation audit of GraphTokenStreamFiniteStrings' contract: the java.util.Iterator that getFiniteStrings() returns must honour next()'s NoSuchElementException clause once hasNext() is false. next() ignores that answer; a one-test JUnit on the stock main jars witnessed the wrong exception.

The method in full104 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The obligation: the returned java.util.Iterator follows Iterator.next()'s contract, which specifies NoSuchElementException when the iteration has no more elements.
  • Reading next() (:150-157) showed that it calls hasNext() but drops the answer; a public-API JUnit test on a one-token graph then witnessed AssertionError (assertions on) and NullPointerException (off), and a probe showed hasNext() itself stays correct.
  • An independent reproducer, an executed cross-model review and a devil's-advocate verifier reproduced it with their own tests, and an adjudication re-ran the original test and the reproducer's test ("Prior reports, history and checks").
