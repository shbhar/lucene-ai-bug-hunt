IndexWriter#addBatch accepts a ColumnBatch with a negative numDocs(): the next commit silently drops documents added before it, or, with assertions on, the writer closes

If your ColumnBatch.numDocs() returns a negative number, IndexWriter#addBatch does not reject it. With assertions off, the next commit returns normally but drops documents you added before the batch (1 added, 0 committed); with assertions on, the writer closes.

The finding in 30 seconds

#

addBatch trusts the count your ColumnBatch reports. The only check that it is not negative is an assert, so with assertions off a count of -1 is subtracted from the in-memory segment's document count, and the commit later drops a segment that still holds a document.

Two things to know first

#
  1. IndexWriter#addBatch(ColumnBatch) (experimental, since 10.5.0) indexes documents column by column. You implement ColumnBatch: numDocs() says how many documents the batch has, and columns() gives the field values for documents 0 to numDocs() - 1.
  2. Documents you add are buffered in an in-memory segment that keeps a document count. A commit writes every in-memory segment whose count is above 0 and drops the others.

The finding, step by step

#
  1. Add 1 document with w.addDocument(new Document()). Then call w.addBatch(batch), where your ColumnBatch has no columns and its numDocs() returns -1 (a bug in your batch code).
  2. You expect an IllegalArgumentException, as addBatch throws for a count above IndexWriter.MAX_DOCS or a column doc id outside [0, numDocs()). The writer stays open, and the next commit holds 1 document.
  3. Instead, with assertions off (production), addBatch returns normally. The -1 is added to the in-memory segment's document count: it still holds 1 document but now counts 0.
  4. commit() returns normally, but a segment that counts 0 documents is dropped instead of flushed: the commit holds 0 documents instead of 1.
  5. With assertions on, assert n >= 0 in reserveDocs throws an AssertionError. IndexWriter treats any Error as tragic and closes the writer, so its uncommitted documents are lost.

Who is affected

#

Only applications on the experimental column API whose own ColumnBatch returns a negative numDocs(), a caller bug such as an int overflow; otherwise default configuration. In production (assertions off) the loss is silent: documents the writer already acknowledged are missing from a commit that returned normally. Releases 10.5.0 to 10.6.0 and main.

Mechanism, terms and numbers574 words

ColumnBatch is an abstract class the application implements; its numDocs() "Returns the number of documents in this batch". IndexWriter#addBatch (and both updateDocuments(..., ColumnBatch) overloads) read that count in DocumentsWriterPerThread.updateBatch and pass it to reserveDocs, whose only check that it is not negative is assert n >= 0; its IllegalArgumentException guards only the upper bound, IndexWriter.MAX_DOCS. With assertions off, the production default, a count of -1 is accepted and added to the in-memory segment's document count, so the segment counts one document fewer than it holds. When that count reaches 0, the next commit drops the segment and returns normally, without the documents it held: documents added and acknowledged before the batch (in the single-threaded repro, every uncommitted document). When it stays positive but too small, a later flush fails and closes the writer. With assertions on, the AssertionError is an Error, which IndexWriter treats as a tragic event, so a caller's bad batch closes the writer. Only a bug in the application's own ColumnBatch triggers it, on an experimental API; releases 10.5.0 through 10.6.0 and main are affected. A 4-line IllegalArgumentException check before reserveDocs fixes it.

Other effects of the same unchecked count (assertions off, executed probes on main)

#
  • On a fresh writer, addBatch(-5) leaves getPendingNumDocs() and getDocStats() at -5, and they stay negative after commit(). That count is the writer-wide pendingNumDocs that later reservations test against the document limit (:233-235, IndexWriter.java:6366-6368), so by reading the code those checks would then count too few documents (not exercised).
  • 10 documents, then addBatch(-10), then commit(): the commit returns normally with 0 documents.
  • 10 documents, a batch of -3, then 1 more document: the next flush fails with RuntimeException: Wrote 11 docs, finish called with numDocs=8 from the stored-fields writer and closes the writer.
  • With a column in the bad batch, checkDocID throws a clean-looking IllegalArgumentException (returned batch doc-id 0 which is out of range [0, -1)), but the cleanup deleteLastDocs(numDocsInRAM - docsInRamBefore) (:353) gets -1 and does nothing (:399-405), so the earlier document is still lost at commit.
  • A control batch with a non-negative count commits every document (10 documents, a batch of 2, 1 more: 13 committed).
  • The dropped segment's stored-fields files stay open: the test framework's MockDirectoryWrapper reports 4 of them at close (a side effect, not claimed separately).
Exposure and likelihood260 words
  • Who is hit. Applications that call addBatch or updateDocuments(Term|Query, ColumnBatch) (all @lucene.experimental) with their own ColumnBatch whose numDocs() returns a negative number: a bug in the caller's code, such as an unchecked int overflow or an uninitialised count. Lucene ships no ColumnBatch outside its tests, so the count always comes from application code; a correct caller never hits this.
  • What they see. Assertions off (production): no error; documents added before the bad batch and not yet committed are missing from a commit that returned normally, or a later flush fails and closes the writer. Assertions on (tests): a caller error closes the writer as tragic.
  • Default vs opt-in. No special configuration: a default IndexWriterConfig. The repro runs in LuceneTestCase's randomized test environment (random codec, MockDirectoryWrapper) and failed the same way under every seed tried. The opt-in part is the experimental column API.
  • Scale. One bad batch puts every uncommitted document of its in-memory segment at risk, not just as many as the negative count: they are dropped at the next commit when the count reaches 0 or below (the repro: 1 of 1; a probe: 10 of 10 after addBatch(-10)); in a probe where the count stayed positive (10 documents, a batch of -3, 1 more) the next flush failed and closed the writer, so they were lost with it. Documents already flushed, or held in another thread's in-memory segment, are not dropped: each in-memory segment is checked on its own (DocumentsWriterFlushControl.java:593-614).
  • Likelihood. Contrived: it needs a caller bug that produces a negative count.

Why it looks unintended

#
  • The ColumnBatch javadoc: numDocs() "Returns the number of documents in this batch"; doc ids run from 0 to numDocs() (exclusive).
  • addBatch already rejects the same count above MAX_DOCS, and column doc ids outside [0, numDocs()), with IllegalArgumentException.
  • With assertions off, other valid documents are lost silently; upstream fixed other malformed-batch gaps by rejecting the batch (#16115, #16708).
The full argument239 words
  • Contract. ColumnBatch.java:22: documents in a batch are identified "from 0 (inclusive) to numDocs() (exclusive)"; :28-30: numDocs() "Returns the number of documents in this batch. All column doc-ids must be in the range [0, numDocs())".
  • The sibling checks are real checks. The second half of that javadoc sentence is enforced with IllegalArgumentException on the column paths that call ColumnValidation.checkDocID (ColumnValidation.java:297-308) or checkDenseCount (:311-322) (LFV-098 is a path that does not), and so is the upper bound of the same count (DocumentsWriterPerThread.java:235-237). Upstream tests: testRowColumnOutOfRangeDocIdThrows (TestColumnBatchIndexing.java:535-550) and testAddBatchOverMaxDocsRollsBackReservations (:130), which checks that a rejected count leaves no reservation behind. testEmptyBatch (:924-947) shows that 0 is a valid count.
  • Precedent. #16115 ("Reject duplicate column names in ColumnBatch", 10.5.0) and #16708 ("IndexWriter#addBatch now rejects non-finite float vector values ...", 10.6.0) fixed other malformed-batch gaps with IllegalArgumentException. The per-document path rejects the closest analogue, a negative user-supplied int, the same way: "position increment must be >= 0" (IndexingChain.java:2002-2008).
  • History. The assert-only lower bound arrived with reserveDocs in a 2026-05-07 revision of #15990 (the revisions reviewed on 2026-04-28 and 2026-05-04 had no lower-bound check at all: a per-document reserveOneDoc() loop, then an unchecked numDocsInRAM += numDocs). A 2026-05-11 review suggestion rewrote reserveDocs into the current compare-and-set loop and kept the assert. No review comment, CHANGES entry, javadoc or test says the count is trusted or unchecked.
The devil's-advocate check213 words

The strongest case, argued by an independent reviewer from another model family (OpenAI GPT-5.6, which reproduced the loss and agreed with the root cause): a negative count is outside the documented domain of ColumnBatch.numDocs(); addBatch is @lucene.experimental and documents only IOException (IndexWriter.java:1528-1536); an assert is how Lucene marks an internal invariant, and IndexWriter's own reserveDocs(long) has an assert-only lower bound too (:6366-6367); and nothing in the javadoc promises that a malformed ColumnBatch is rejected, or that the writer recovers from one. So a maintainer may call the check hardening.

Why it fails: the value crosses the API boundary from application code, while the callers of IndexWriter.reserveDocs(long) (:3199, :3356) pass totals Lucene computes itself from segment metadata (:3139, :3344); the same count is already validated at its upper bound, and the doc ids against it; and with assertions off the failure is not loud on the bad input but a silent loss of other, valid documents in a commit that returns normally. A negative count is a caller bug, but addBatch already rejects the other malformed parts it checks (the count's upper bound, out-of-range doc ids, duplicate column names, non-finite vectors), so one comparison per batch brings the lower bound in line.

Suggested fix

#

Recommended Reject a negative count in DocumentsWriterPerThread.updateBatch, before reserveDocs (recommended; validated)

Throw IllegalArgumentException when numDocs < 0 in DocumentsWriterPerThread.updateBatch, before reserveDocs: 4 lines. Nothing is reserved yet, so the writer stays open and keeps its documents. It covers addBatch and both updateDocuments(..., ColumnBatch); the repro and the 167 batch-suite tests pass with it.

final int numDocs = columnBatch.numDocs();
if (numDocs < 0) {
  throw new IllegalArgumentException(
      "ColumnBatch.numDocs() must not be negative, got " + numDocs);
}

Reject a negative count in DocumentsWriterPerThread.updateBatch, before reserveDocs (recommended; validated)

#

Right after final int numDocs = columnBatch.numDocs(); (DocumentsWriterPerThread.java:334). One file, 4 insertions:

final int numDocs = columnBatch.numDocs();
if (numDocs < 0) {
  throw new IllegalArgumentException(
      "ColumnBatch.numDocs() must not be negative, got " + numDocs);
}

Trade-offs

  • One int comparison per batch, not per document.
  • It throws before anything is reserved or counted, on the same path the existing over-MAX_DOCS IllegalArgumentException already takes, so there is nothing to roll back and the writer stays open.
  • It covers addBatch and both updateDocuments(..., ColumnBatch) overloads, which share updateBatch. The message wording is free.
  • It checks the value updateBatch reads; IndexingChain.processBatch calls numDocs() again (IndexingChain.java:718), so a ColumnBatch that returns different values on different calls is not covered (reading the count once and passing it down would cover that).

What the checks validated

  • In a scratch worktree at 5adff78bb168, through gradle, seed DEADBEEF: the repro fails without the fix and passes with it, assertions on and off.
  • With the fix, TestColumnBatchIndexing and org.apache.lucene.document.column.* pass: 7 classes, 167 tests, 0 failures, 0 errors, assertions on and off; :lucene:core:checkGoogleJavaFormat passes.
  • Not run: the full lucene/core suite.

Downstream note

#

Downstream products that build a ColumnBatch from an externally supplied row count should check that the count is not negative before calling addBatch, until a release rejects it.

How it was found

#

Semi-formal: a proof-obligation audit of DocumentsWriterPerThread's contract checked every precondition of updateBatch and found that numDocs >= 0 is only asserted, never checked. An executable one-test repro on main then witnessed the dropped document and the closed writer.

The method in full118 words

Method: semi-formal, a proof-obligation audit witnessed by an executable repro.

  • The audit took the preconditions of DocumentsWriterPerThread.updateBatch as obligations the code must discharge for every input the public API admits. The count comes from the application's ColumnBatch.numDocs(); the upper bound is discharged with an IllegalArgumentException, the lower bound only with assert n >= 0 in reserveDocs.
