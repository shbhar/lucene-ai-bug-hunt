DirectoryTaxonomyReader.getBulkPath overwrites entries of its ordinals argument, although the javadoc says it may only reorder them

Since 10.5.0, DirectoryTaxonomyReader.getBulkPath can overwrite entries of the ordinals array you pass in, not just reorder them as its javadoc says: with ordinal 2 cached, {2, 1} comes back as [1, 1]. The labels it returns are right; only code that reads the array again afterwards is misled.

The finding in 30 seconds

#

getBulkPath first fills in the labels it has cached, then copies the uncached ordinals into the front of your array (DirectoryTaxonomyReader.java:522) and sorts only that prefix (:549). The slots after the prefix keep their old values, so a cached ordinal that comes before an uncached one is overwritten. The javadoc (TaxonomyReader.java:241-242) allows only a reorder.

Background: taxonomy ordinals and getBulkPath

#
  1. A facet taxonomy gives every category an integer ordinal (0 is the root); getPath(ordinal) returns the category's label.
  2. getBulkPath(int... ordinals) returns many labels in one call. Its javadoc says it "may change (reorder elements) its parameter" and that you should avoid reusing the parameter.
  3. DirectoryTaxonomyReader keeps an LRU category cache of recently looked-up labels (up to 4,000 by default): getPath adds a label on a miss, getBulkPath adds its uncached ordinals.

The finding, step by step

#
  1. You build a taxonomy with two categories, a (ordinal 1) and b (ordinal 2), and open a DirectoryTaxonomyReader with default settings. Its category cache keeps the labels it looked up most recently (an LRU cache of up to 4,000 by default).
  2. You call getPath(2), which caches b, and later getBulkPath(new int[] {2, 1}).
  3. You expect the labels [b, a] and, since the javadoc says the method "may change (reorder elements) its parameter", an array that still holds 2 and 1 in some order, as on 9.0.0 to 10.4.0.
  4. You get the right labels [b, a], but the array is now [1, 1]: 2 is gone and 1 is there twice. The method copies the uncached ordinals into the front of your array and never puts the cached ones back.
  5. Only code that reads the array after the call sees this, and the same javadoc sentence advises against that; no in-tree caller does it. Affected: 10.5.0 to 10.6.0 and main (#15711).

Who is affected

#

Application code that calls getBulkPath and reads the array again afterwards, for example to pair labels with counts kept by ordinal, silently works with a lost ordinal and a duplicate. Default reader settings suffice, but the javadoc advises against reusing the array and no in-tree caller does it. Affected: 10.5.0 to 10.6.0 and main.

Mechanism, terms and numbers533 words

TaxonomyReader.getBulkPath(int... ordinals) returns the labels of several taxonomy ordinals in one call, and its javadoc warns: "this method may change (reorder elements) its parameter, you should avoid reusing the parameter after the method is called." From 9.0.0 to 10.4.0 DirectoryTaxonomyReader.getBulkPath sorted the whole array in place, exactly as described.

Since 10.5.0 (#15711, which made the method use the category cache) it looks every ordinal up in the cache first, then copies the uncached ordinals into the front of the caller's array and sorts only that prefix. The slots after the prefix keep their old values, so a cached ordinal that comes before an uncached one is overwritten and the moved value is left twice: with ordinal 2 cached, {2, 1} becomes [1, 1] and {3, 2, 1} becomes [1, 3, 1]. The returned labels are always right.

So this is a documentation/contract defect, priority Low: only a caller that reads the array again after the call, which the javadoc already advises against, gets wrong data, and no in-tree caller does. A two-line swap in the compaction loop makes the javadoc true again without an allocation; a javadoc change is the lowest-risk alternative.

The mechanism (main 645d4fe14a20)

#
  1. The contract. TaxonomyReader.java:241-242: "Note: this method may change (reorder elements) its parameter, you should avoid reusing the parameter after the method is called." The default implementation (:244-250) does not touch the array; the class is @lucene.experimental (:57).
  2. The override's own javadoc (DirectoryTaxonomyReader.java:499-508) says nothing about the parameter, so the note is not inherited there. It still describes a StoredFields fallback (:502-505) that the code no longer has.
  3. Cache first. :515 getPathFromCache(ordinals) fills the labels of the cached ordinals.
  4. Compaction into the caller's array. :519-526: for each ordinal whose label is still missing, ordinals[uncachedLength] = ordinals[i] (:522). The value at uncachedLength is overwritten, not swapped.
  5. All cached: early return at :528-530, the array is untouched.
  6. Prefix sort only. :533-549 sorts ordinals[0..uncachedLength) with their original positions (.sort(0, uncachedLength), :549); the lookup (:558-578) and the cache update (:580-585) read only that prefix. Nothing restores the rest.
  7. What stays right: the returned labels; checkOrdinalBounds still runs first (:512); every write stays inside the caller's array.

Which calls change the array

#
call (ordinals 1 = a, 2 = b, 3 = c)cachedlabelsarray afterwards
getBulkPath(2, 1)2[b, a][1, 1] (2 lost, 1 twice)
getBulkPath(3, 2, 1)2[c, b, a][1, 3, 1] (2 lost, 1 twice)
getBulkPath(3, 2, 1)nothing[c, b, a][1, 2, 3] (a reorder)
getBulkPath(3, 2, 1)all[c, b, a][3, 2, 1] (untouched)

Only "a cached ordinal before an uncached one" breaks the contents: an uncached ordinal before a cached one compacts to the identity. The study's randomized check (300 trials, random cached subsets) saw the contents change in exactly those trials, with the labels right in every trial.

Worked example, {2, 1} with 2 cached: slot 0 (ordinal 2) is cached and skipped; slot 1 (ordinal 1) is uncached and copied into slot 0, giving [1, 1]; the prefix of length 1 is already sorted.

Exposure and likelihood168 words
  • Who. Code that calls DirectoryTaxonomyReader.getBulkPath (directly or through a TaxonomyReader reference) and reads the argument again afterwards.
  • Default vs opt-in. The category cache is on by default (LRU, up to 4,000 labels; setCacheSize changes the limit). getPath adds a label on a miss and getBulkPath adds its uncached ordinals, so the mixed cached/uncached state is normal on a long-lived reader (or one from openIfChanged, which shares the caches unless the taxonomy was recreated). The call pattern that sees it goes against the javadoc's advice, in an @lucene.experimental API.
  • In-tree callers are not affected. TaxonomyFacets.java:320-326 collects the counts before the call at :328 (the 2024 #14008 fix); :406 passes a fresh ordinals.toArray(); ReindexingEnrichedDirectoryTaxonomyWriter.java:72 uses only the labels; the sandbox TaxonomyOrdLabelBiMap.java:44-45 and TestDirectoryTaxonomyReader.java:521 clone first.
  • It has happened before. Until #14008 was fixed in 2024, Lucene's own TaxonomyFacets read the array after getBulkPath (then a pure sort) and reported wrong counts.
  • Silent. No exception; the labels are right, so nothing looks wrong unless the array is read again.

Why it looks unintended

#
  • The javadoc allows only a reorder: "may change (reorder elements) its parameter" (TaxonomyReader.java:241-242). A duplicate is not a reorder.
  • Lucene's own comments agree: getBulkPath "shuffles its input array" and "changes order of param's elements".
  • The overwrite came with a cache speed-up (#15711) that never mentions the argument; a two-line swap keeps the speed-up and the contract.
The full argument128 words
  • The note was exact when written. #12769 (fb5f491643b, 2023-11-09, first in 9.9.0 and 10.0.0) added it when the method sorted the whole array in place; the same PR added the test comment "clone because getBulkPath changes order of param's elements".
  • The change was a side effect. #15711 ("let getBulkPath use cache", fixes #15705) makes the method use the cache result it used to compute and throw away. Its description, reviews and linked issue never mention the argument; it did not touch TaxonomyReader.java; CHANGES.txt:990 lists it under Improvements as "DirectoryTaxonomyReader.getBulkPath() now uses getPathFromCache"; MIGRATE.md says nothing about getBulkPath.
  • The overwrite is not needed for correctness. Swapping instead of copying keeps the array a permutation and the speed-up, with no allocation (Suggested fix); no benchmark was run.
The devil's-advocate check197 words

The strongest case for "leave it": the same sentence says "you should avoid reusing the parameter after the method is called", so a caller that follows it is never affected. In #14008 (2024) a contributor wrote "We're using our API incorrectly by referencing ordinals after getBulkPath", and the fix went into the caller. Both classes are @lucene.experimental, overwriting saves work, and a maintainer can read "(reorder elements)" as an example rather than a limit.

Why it fails: it answers a wrong-results framing, which this report does not make. It does not make "(reorder elements)" accurate, and Lucene's own comments ("shuffles", "changes order") read the note as a permutation; the override's own javadoc says nothing about the parameter at all. Every verifier and reviewer in the study agreed on the mechanism, but the contract question stayed open: the independent reviewer from another model family (OpenAI GPT-5.6), refute lens, rated the "intended" case strong, called the contract question "unresolved" and wrote "A maintainer may still want to clarify that wording even if arbitrary mutation is accepted". Confidence is high that the note is inaccurate, and low to medium that a maintainer will think it worth a change.

Suggested fix

#

Recommended A. Swap instead of overwrite (recommended)

Swap instead of overwrite in the compaction loop of DirectoryTaxonomyReader.getBulkPath (+3 lines): your array stays a reordering of itself, as the javadoc says, with no allocation. Validated with gradle: the minimal test passes with assertions on and off, and the facet module passes (307 tests). Alternative: document that the array's contents are unspecified after the call.

     for (int i = 0; i < ordinalsLength; i++) {
       if (bulkPath[i] == null) {
+        // swap, do not overwrite: the caller's array may only be reordered
+        int x = ordinals[uncachedLength];
         ordinals[uncachedLength] = ordinals[i];
+        ordinals[i] = x;
         originalPosition[uncachedLength] = i;
         uncachedLength++;
       }

A. Swap instead of overwrite (recommended) (validated by the checks)

#

In the compaction loop of DirectoryTaxonomyReader.getBulkPath, swap the uncached ordinal into the prefix instead of copying it. Before step i, the prefix holds the uncached ordinals seen so far, the slots up to i hold cached ones, and slot i still holds the caller's value; the swap keeps that, so the array stays a permutation, and the later code reads only the prefix.

     for (int i = 0; i < ordinalsLength; i++) {
       if (bulkPath[i] == null) {
+        // swap, do not overwrite: the caller's array may only be reordered
+        int x = ordinals[uncachedLength];
         ordinals[uncachedLength] = ordinals[i];
+        ordinals[i] = x;
         originalPosition[uncachedLength] = i;
         uncachedLength++;
       }

Trade-offs

  • Makes the current javadoc true again and keeps #15711's speed-up; no allocation, one extra array read and one extra array write per uncached ordinal (not benchmarked).
  • Callers still get a reordered array, as documented, but not the one 10.5.0 to 10.6.0 leave: {2, 1} comes back [1, 2] (executed); the labels do not change.
  • A suggestion, not a must: the javadoc fix is the lowest-risk change for an @lucene.experimental API, and a maintainer may prefer it.

Summary
You pass an array of taxonomy ordinals to DirectoryTaxonomyReader.getBulkPath, whose inherited TaxonomyReader javadoc says the method 'may change (reorder elements) its parameter', so you expect the array to hold the same ordinals afterwards, perhaps in another order, as it does in 9.0.0 to 10.4.0. Since 10.5.0 (#15711, which made getBulkPath use the category cache) the method packs the uncached ordinals into the front of your array and sorts only that prefix, so a cached ordinal that comes before an uncached one is overwritten and another entry is duplicated. With ordinal 2 cached, getBulkPath(new int[] {3, 2, 1}) returns the right labels [c, b, a] but leaves the array as [1, 3, 1].
