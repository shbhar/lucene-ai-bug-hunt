A segment that ends with child documents and no parent makes each BP reordering merge in which it comes last throw and close the IndexWriter

With BPReorderingMergePolicy, a segment ending in parentless child documents makes each reordering merge in which it comes last throw (with assertions off, at least 64 documents) and close the IndexWriter, again after reopening. A block rejected at a child, after other blocks of its segment and before a commit, suffices.

The bug in 30 seconds

#

BP reordering renumbers the documents of a merged segment so that similar documents sit together. With a parent field it moves each block (children followed by their parent) as a unit, and it assumes the merged documents end with a parent.

  1. You index 20 blocks of 4 children + 1 parent (100 documents) with setParentField("parent") and new BPReorderingMergePolicy(new LogDocMergePolicy(), new BPIndexReorderer()). Every block ends with its parent: docs 4, 9, ..., 99.
  2. A 21st block, the last before the commit, has a 32,767-byte keyword in its third child. addDocuments throws the documented IllegalArgumentException and the writer stays open. After commit() the segment has 103 documents: the rejected block's docs 100-102 are deleted and none carries the parent marker. CheckIndex reports the index clean.
  3. You call forceMerge(1) and expect a merged segment with your 100 documents; a plain LogDocMergePolicy merge of the same segment works.
  4. Instead the reorderer looks for the parent after doc 100, gets NO_MORE_DOCS, and reads past its 103-entry array: ArrayIndexOutOfBoundsException: Index 103 out of bounds for length 103 (an AssertionError with assertions on).
  5. The IndexWriter closes with a tragic exception and loses uncommitted changes, and a new writer fails the same way on its next such merge. Deleting only the parent of the last block fails the same way one merge later (Index 99 of 99).

Who is affected

#

Applications that opt into lucene/misc's BPReorderingMergePolicy with BPIndexReorderer, document blocks and a parent field, and no index sort. It needs a segment ending in parentless documents (a block rejected at a child before a flush, or a parent-only delete or update) that comes last in a reordering merge (with assertions off, of at least 64 documents).

Mechanism, terms and numbers707 words

BPReorderingMergePolicy with BPIndexReorderer (lucene/misc) renumbers merged segments and, since 9.11.0, keeps document blocks together when IndexWriterConfig#setParentField is set. BPIndexReorderer assumes that the merged documents end with a parent and never checks it. A segment can end with documents that have no parent after them through calls IndexWriter accepts: a block rejected at a child as the last block before a flush, in an in-memory segment that also holds accepted blocks (its already-indexed documents stay as deleted documents without a parent marker), or a delete or update term that matches only the parent of the segment's last block (a merge then drops the parent). The next reordering merge in which that segment comes last throws ArrayIndexOutOfBoundsException in shuffle() (with assertions off, once the merged view has at least 64 documents; an AssertionError with assertions on), and the IndexWriter closes with a tragic exception, loses uncommitted changes and fails the same way after every reopen. Committed data stays intact and CheckIndex is clean. Opt-in configuration only; released 9.11.0 through 10.5.2 and on main, introduced by #13125 (2024).

Terms

#
  • Document block: documents added together with IndexWriter#addDocuments; the last one is the parent, the others are its children. With IndexWriterConfig#setParentField, IndexWriter marks every parent with a doc value in that field (IndexingChain.java:604, :644-650).
  • BP reordering: BPReorderingMergePolicy wraps a merge policy and asks BPIndexReorderer (recursive graph bisection) for a new document order for each merged segment. Since 9.11.0 it keeps blocks together when a parent field is set (CHANGES 9.11.0, GITHUB#13125).
  • Merged view: for a reordering merge, IndexWriter wraps all merging segments in one reader, deleted documents included, and hands it to the reorderer (IndexWriter.java:5545-5558); the merge drops deleted documents afterwards.

The bug

#
  1. BPIndexReorderer.computePermutation builds parents = BitSet.of(<parent-field doc values>, maxDoc) (BPIndexReorderer.java:879-882) and reorders all maxDoc documents (:891-893). Nothing checks that document maxDoc - 1 is a parent.
  2. In shuffle(), each block runs from its first document to the next parent: numChildren = parents.nextSetBit(firstChild) - firstChild (:373). For documents after the last parent, nextSetBit returns NO_MORE_DOCS (2147483647), so for the trailing run that starts at doc 100, numChildren is 2147483547.
  3. The loop cumulativeBias += biases[i + j] (:376-377) then runs past the end of biases (one entry per document): ArrayIndexOutOfBoundsException: Index 103 out of bounds for length 103. Once shuffle() runs, this loop comes before any gain comparison, so it needs no qualifying term (no term in the repros reaches the default minDocFreq of 4,096). It only runs when the merged view has at least 64 documents (2 x the default minPartitionSize of 32, :243-246). With assertions on, assert i + numChildren < end in assertParentStructure (:329) fails first, for any size.
  4. IndexWriter treats a failed merge as tragic: tragicEvent(t, "merge") (IndexWriter.java:5109-5113) closes the writer.

How a segment comes to end without a parent

#
  • A block rejected at a child. DocumentsWriterPerThread.updateDocuments gives each document a doc ID before indexing it (DocumentsWriterPerThread.java:291) and, on a non-aborting exception such as a term longer than IndexWriter.MAX_TERM_LENGTH (32,766 bytes), marks the block's documents so far deleted (:302-307). The parent marker is written only for the block's last document, which is never reached. If this block is the last one before a flush, the segment ends with these deleted documents. The segment must also hold accepted documents: a rejected block alone in its in-memory segment is dropped at flush as fully deleted, and the merge works (executed).
  • A parent-only delete or update. A delete or updateDocuments term that matches only the parent of the segment's last block. The first merge still sees the deleted parent's doc value (deleted documents are in the merged view), so it works and drops the parent; the new segment ends with live children that have no parent after them.

The segment must come last in the merged view. When another segment follows it, that segment's first parent ends the trailing run and the merge completes (executed for both triggers: 200 and 199 documents, assertions on and off); the trailing documents are then treated as part of that segment's first block, which for live children is the search-results hazard upstream already knows.

Exposure and likelihood362 words
  • Who. Opt-in only: lucene/misc BPReorderingMergePolicy with BPIndexReorderer, document blocks, IndexWriterConfig#setParentField, and no index sort (an index sort turns merge-time reordering off, IndexWriter.java:5545-5546). BP reordering is not on by default.
  • Trigger. A segment that ends with parentless documents must come last in a reordering merge. Executed: a forced merge of that segment alone, forceMergeDeletes, a natural LogDocMergePolicy merge with an older segment (Index 199 of 199, Index 203 of 203), and a TieredMergePolicy forceMerge(1) with a larger older segment (Index 603 of 603). Forced merges always reorder; natural merges reorder by default (minNaturalMergeNumDocs 1), and with the javadoc's suggested 2^18 small natural merges skip reordering (code reading). With assertions off the merged view needs at least 64 documents.
  • The rejected-block path needs no delete call. IndexWriter rejects a block with a documented IllegalArgumentException (for example a keyword longer than 32,766 bytes in a child), stays open, and itself marks the block's already-indexed documents deleted. An application that checks term lengths before indexing never gets there; otherwise the timing decides: the block must be the last one before a flush in a segment that also holds accepted blocks. One more block in the same in-memory segment defuses it, and a rejected block alone in its segment is dropped at flush (both executed).
  • Effect. Loud: the merge throws, the IndexWriter closes with a tragic exception and changes since the last commit are lost; a reopened writer fails again on its next such merge, so indexing cannot get past that merge until the segment is merged without reordering or not last. Committed documents and deletes stay unchanged, CheckIndex is clean, and the failure is fast (well under a second on about 100,000 documents: 210 ms and 80 ms in two runs).
  • How likely. A judgement, not measured: rare. A randomized merge test with soft deletes hit it in 4 of 5,000 cases with assertions on; with assertions off the same test hit 0 of 5,000, because the four failing merges had 20 to 62 documents, under the 64-document threshold. Once a segment is in this state, every reordering merge in which it comes last fails (with assertions off, from 64 documents).

Why it is a bug, not intended

#
  • IndexWriter accepts every step: it rejects the bad block with the documented IllegalArgumentException and stays open, CheckIndex is clean, and a plain merge works.
  • Short of RAM, BPReorderingMergePolicy "simply skips reordering in order not to fail the merge"; that is the only failure case it documents.
  • With assertions off the failure is an out-of-bounds array read, not a validation error.
The full argument242 words
  • Contracts. BPReorderingMergePolicy: "When reordering doesn't have enough RAM, it simply skips reordering in order not to fail the merge" (BPReorderingMergePolicy.java:35-36). CHANGES 9.11.0: BP "is now supported on indexes that have blocks, as long as they configure a parent field via IndexWriterConfig#setParentField". IndexWriter#addDocument: a term longer than MAX_TERM_LENGTH throws IllegalArgumentException (IndexWriter.java:1480-1481), and after an exception "the index will be consistent, but this document may not have been added" (:1465-1466). IndexWriter#addDocuments limits the effect of deleted block documents to search features: "when these documents are deleted these search features will not work as expected" (:1501-1503). Neither the block docs nor the BP policy docs warn that this reachable state can make a merge fail and close the writer (IndexWriter.merge handles any merge failure as tragic, :5109-5113). The low-RAM promise shows a robustness intent; no general contract says reordering never fails a merge.
  • Behaviour. IndexWriter accepts the rejected block, the delete and the update; core CheckIndex calls the index clean; the same merge without reordering works; deleting the whole block works.
  • Tests. TestBPIndexReorderer.testSingleTermWithBlocks indexes whole blocks and deletes nothing; TestBPReorderingMergePolicy deletes documents but indexes no blocks. No upstream test combines BP reordering, a parent field and deletes or rejected blocks.
  • History. The BP block PRs (#13125, #13128) never discuss deleted parents or segments that end in children; #13128 made IndexWriter reorder only "when it has a chance to preserve the block structure".
The devil's-advocate check352 words

An independent reviewer from another model family (OpenAI GPT-5.6, reading only, could not run Java) built the strongest case for "not a bug": the input is outside the supported block structure. CheckJoinIndex (lucene/join) says "The last document of a segment must always be a parent"; committers have long said that deleting a parent without its children breaks blocks (LUCENE-4068, LUCENE-6660, LUCENE-7674, the #12829 review), and on #14067: "Block-joins require deletes to be consistent across parent and child documents. So I wouldn't call it a bug"; assertParentStructure states the precondition ("Last doc ID must be a parent doc"); the policy promises to skip only when RAM is short; and IndexWriter#addDocuments is marked @lucene.experimental.

Why it fails: on the rejected-block path the application issues no delete call; IndexWriter itself marks the block's already-indexed documents deleted after a documented, non-aborting rejection and leaves the segment ending in them. The application could avoid that only by checking term lengths before indexing, or by the timing of the flush, which it does not normally control. CheckJoinIndex rejects that segment too (executed: "The last document of a segment must always be a parent"), so its invariant is not one IndexWriter maintains; it also rejects a live parent with a deleted child (executed), which addDocuments explicitly supports ("The order of documents within a segment will be preserved, even when child documents within a block are deleted"). Every upstream statement limits the consequence to block-join search results; none says a merge may throw, and @lucene.experimental marks API stability, not a licence for a merge to throw. Lucene asserts check programming errors, not input, and with assertions off the code reads out of bounds. The adjudication (medium confidence), the independent reproducer and the devil's-advocate verifier (moderate-high) rated it a defect; a second cross-model reviewer rated the intended-behaviour case strong for the parent-only path and moderate for the rejected-block path. Verdict: a defect, strongest on the rejected-block path. The parent-only path is much weaker: maintainers can fairly treat CheckJoinIndex's last-parent invariant and the "delete whole blocks" guidance as a precondition of block-aware tooling, so lead with the rejected block.

Suggested fix

#

Recommended Reorder only up to the last parent

Reorder only up to the last parent and leave the parentless documents after it at the end, in their current order (+5/-1 in BPIndexReorderer.computePermutation). The repro passes with assertions on and off; in a 42-block probe every block stays intact and the rest is still reordered; the three closest upstream BP test classes pass (19 tests, nightly tests on).

BitSet parents = null;
int numDocsToReorder = maxDoc;
String parentField = reader.getFieldInfos().getParentField();
if (parentField != null) {
  parents = BitSet.of(DocValues.getNumeric(reader, parentField), maxDoc);
  // Documents after the last parent (e.g. children whose parent was deleted) belong to no
  // block: leave them at the end, in their current order, and reorder the blocks before.
  numDocsToReorder = maxDoc == 0 ? 0 : parents.prevSetBit(maxDoc - 1) + 1;
}

  • After a parent-only delete the merged segment still ends with those children (as a plain merge leaves it); it no longer breaks later merges.
  • "Every block intact" and "the rest still reordered" are shown by one 42-block probe only; deleted children inside blocks, soft deletes, mixed readers, addIndexes and other parent-field layouts were not tested.
  • No change for segments that end with a parent. No compression or query-speed benchmark, CHANGES entry, javadoc build or full check was run.

Skip reordering when the last document is not a parent (the finder's sketch) (validated by the checks)

#

After building parents, if the last document is not a parent, delete the temporary files and return the current order. Patch: optionA-skip-reordering-finder.diff, +6.

Trade-offs

Complementary: delete a parent's children with it

#

An idea from the #12829 review: make a parent delete also delete its children.

Trade-offs

  • Would prevent new parent-only cases, but not the rejected-block path or segments that already end in parentless documents; not a fix on its own.

Downstream note

#

No downstream product was found that reaches it: Solr sets the parent field only together with an index sort, which turns reordering off, and Elasticsearch and OpenSearch do not use BPIndexReorderer (code reading, nothing run).

How it was found

#

A randomized differential test of merges, not a formal method: two writers got the same random operations, one with a no-op reorderer and one with BPIndexReorderer. With soft deletes, 4 of 5,000 cases hit the reorderer's parent-structure assertion. Reading the block handling gave the root cause; a later check found the delete-free rejected-block path.

The method in full160 words

Method: randomized merge-level differential testing (the hunt's non-formal tier; the finder tagged it semi-formal), in a hunt unit on misc reordering and index splitting.

  • Two IndexWriters received the same random sequence of adds, block adds, deletes and merges; one merged through a no-op reorderer, the other through the real BPIndexReorderer. With soft deletes, 4 of 5,000 cases (assertions on) failed in assertParentStructure after a soft-deleted parent.
  • Reading BPIndexReorderer's block handling showed the missing last-document check; a deterministic two-session JUnit reproduced it with assertions on and off, on main and on 9.11.0, 9.12.3 and 10.5.2 (9.10.0 passes).
  • An independent reproducer and a devil's-advocate verifier found single-writer variants (forceMergeDeletes after a parent-only delete; updateDocuments by a term only the parent carries). A later reach check, run after the adjudication, found the path with no delete: a block rejected at a child as the last block before a commit.
  • Found 2026-10-26 on main ea57360912ed; re-checked on a9779ef3c193.

Bug record

LFV-417, snapshot of 2026-10-27

Registry title
BPIndexReorderer assumes every segment ends with a parent document: once a segment ends with child documents that have no parent after them, each BP reordering merge in which that segment comes last throws and closes the IndexWriter
Area
misc / BP merge-time reordering (BPIndexReorderer with document blocks)
Priority
Medium, rank 156: An index state that IndexWriter accepted makes every later BP reordering merge throw and close the writer, the same loud index-unusable profile as LFV-244 behind opt-in BP reordering with blocks.
Impact class
index unusable
Impact note
Applications that opt into the lucene/misc BPReorderingMergePolicy with BPIndexReorderer on an index with document blocks and IndexWriterConfig#setParentField (and no index sort) are hit once a segment ends with child documents that have no parent after them (a delete or update term that matched only the parent of the segment's last block, after a merge has dropped that parent, or a block rejected at a child as the last block before a flush) and that segment comes last in a later reordering merge: the merge throws (AssertionError with -ea; ArrayIndexOutOfBoundsException in shuffle() with -da once the merged view has at least 64 documents), the writer closes with a tragic exception, uncommitted changes are lost and a reopened writer fails again on its next such merge, while committed data stays intact; ordinary scale, released since 9.11.0.
Summary
You index document blocks with IndexWriterConfig#setParentField, merge through BPReorderingMergePolicy with a BPIndexReorderer, and a segment ends up ending with child documents that have no parent after them, for example because you deleted or updated only the parent of its last block and a merge dropped it, or because IndexWriter rejected a block at one of its children (with the documented IllegalArgumentException) just before a flush. You expect later merges to work: IndexWriter accepted every call, CheckIndex calls the index clean and a plain merge of the same segment succeeds. Instead BPIndexReorderer, which assumes the merged view ends with a parent, runs past the end of its arrays in the next reordering merge in which that segment comes last (ArrayIndexOutOfBoundsException with assertions off, AssertionError with them on), and IndexWriter closes with a tragic exception, loses uncommitted changes and fails the same way after every reopen.
