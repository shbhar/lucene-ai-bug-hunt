ConcatenatingTokenStream loses a source's trailing hole (a removed stop word) when the next source produces no tokens

The bug in 30 seconds

#

ConcatenatingTokenStream joins several token streams into one field. Since 7.7.0 it carries the hole a source ends with (for example a stop word removed at its end) over to the first token of the next source. A source that produces no tokens breaks that carry-over.

  1. You build one field from three values with new ConcatenatingTokenStream(...): "alpha the", "" and "beta", each through WhitespaceTokenizer and a StopFilter that removes the. The first value ends in a hole: its end() reports a final position increment of 1.
  2. You expect beta at position 2, two steps after alpha at 0. That is what you get without the empty value, and what the same three values give as a multi-valued field.
  3. You get beta at position 1. The loop that skips finished sources stores each one's final increment with = (line 92), so the empty value's 0 overwrites the pending 1. Offsets in the same loop are added with += and stay right.
  4. So the exact phrase "alpha beta" gets 1 hit instead of 0. If the empty value comes last, end() reports 0 instead of 1. No error, and CheckIndex is clean.
  5. It is the case LUCENE-8650 (7.7.0) missed when it added the carry-over: every release from 7.7.0 to 10.5.2 and main. Run with assertions on at 8 releases and main, and with them off on 9.12.3, 10.5.2 and main.

Who is affected

#

Applications that build a token stream with new ConcatenatingTokenStream(...), usually one field from several values, and can pass an empty or stop-word-only value after a value that ends in a removed word. Phrase, span and interval queries on that field see the later tokens too close. The class has no factory, no in-tree caller and no known downstream use.

Mechanism, terms and numbers734 words

ConcatenatingTokenStream joins several token streams into one field. Since LUCENE-8650 (7.7.0) it carries each source's final position increment, for example the hole left by a stop word that a StopFilter removed at the end of a value, over to the first token of the next source. It stores that increment with an assignment for every finished source (ConcatenatingTokenStream.java:92), while the same loop adds offsets (:94), and end() reads only the last source (:115). So a source that emits no tokens, such as an empty value or one made only of stop words, overwrites the pending hole, and an empty last source makes end() report 0. With the values "alpha the", "" and "beta", beta is indexed at position 1 instead of 2 (the multi-valued field and the concatenation without the empty value give 2), and the exact phrase "alpha beta" gets 1 hit instead of 0. Nothing throws and CheckIndex is clean. Reach is narrow: the class has no factory and no in-tree caller, and no downstream use was found. The fix is to add the increments up in a pending counter (+8/-4 lines), validated with the module's whole test suite.

Terms

#
  • Position increment: how many positions a token moves on from the previous one. A removed stop word leaves a hole: the next token gets increment 2 instead of 1.
  • Final position increment: what a stream reports from end() after its last token, for a hole at its very end ("alpha the" with the removed reports 1).
  • Source: one of the streams ConcatenatingTokenStream joins. A source with no tokens is an empty value, a whitespace-only value, or one made only of removed words.

  1. alpha comes out with increment 1 (position 0). Source 0 ends; its end() reports 1 (the removed the), stored at :92.
  2. Source 1 ("") has no token; its end() reports 0, and :92 replaces the pending 1 with 0. Its offset, 0, is added to the running offset 9.
  3. Source 2 emits beta with 1 + 0 = 1: position 1 instead of 2.

In a run of finished sources, the sum of the final increments of all of them except the last is lost: two empty values in a row lose the same hole, and foo+hole followed by two sources with no tokens and final increments 2 and 1 gives bar 2 instead of 5. If the last source is empty, incrementToken() returns at :90 and end() reads only that source, so end() reports 0. An empty first value ("", final increment 0) is handled correctly; a first value made only of stop words follows the same rule (concat("the", "the", "bar") gives bar increment 2, the single text 3). The assignment and a pending counter that starts at 0 and is cleared once applied agree whenever every source has a token, which is why the LUCENE-8650 test passes.

Exposure and likelihood357 words
  • Who is hit. Code that joins several values into one field with this public analysis-common class (not marked experimental or expert), or uses it in its own analysis or query code (not run), when a value that ends in a removed token is followed by one or more values with no tokens. Such values are ordinary (an empty subtitle, a value made only of stop words), but the class is rarely used.
  • Reach. No analysis factory or SPI name, so CustomAnalyzer and schema-driven setups cannot use it; no caller outside its own file and test; read-only code search of default branches found no use in Elasticsearch, OpenSearch or Solr. No prior report was found in the documented searches.
  • What goes wrong. Every token after the empty value moves closer by the lost hole. An exact phrase across a removed stop word matches ("alpha beta": 1 hit instead of 0), and a phrase that needs the hole stops matching (QueryBuilder turns foo the bar into "foo ? bar", which then misses the document). Only PhraseQuery was run; spans and intervals read the same positions.
  • Empty last value. end() reports 0 instead of the hole. When such a stream is one value of a multi-valued field, the next value starts closer; the position gap between values is kept (a value ending in three removed words, "x the the the", then an empty source, then a second value, with gap 100: 101 instead of 104).
  • Silent and stored. No exception and CheckIndex clean; on main with assertions on and off; the diagram probe indexed with the default codec, the gradle tests with the test framework's randomized codec. The wrong positions are in the index, so documents indexed before a fix keep them until reindexed.
  • Size. The tokens after a run of values with no tokens move closer by the final increments of every finished source in the run except the last: with one such value, the removed trailing tokens of the value before it; with several in a row, more. Positions only move closer and stay in order. No scale needed: one document, three values.

Why it is a bug, not intended

#
  • LUCENE-8650 (7.7.0) fixed the class for "not propagating final position increments from its child streams correctly"; this is the case it missed.
  • The same values as a multi-valued field keep the hole: beta at 2.
  • The same loop adds offsets (+=) but overwrites positions (=).
The full argument293 words
  • CHANGES, Lucene 7.7.0 (CHANGES.txt:6928-6930): "LUCENE-8650: ConcatenatingTokenStream did not correctly clear its state in reset(), and was not propagating final position increments from its child streams correctly." In #9696 the committer wrote that the patch "also handles final position increments (to allow for things like stop words being removed at the end of a tokenstream)". A stop-word-only value is exactly that case.
  • The upstream test testOffsetGaps (TestConcatenatingTokenStream.java:63-83) expects a child's final increment 2 to be added to the next child's first token: posIncs {1, 1, 3, 1} (:76). Both children have tokens, and its end() value 2 (:79) is the last child's own, so neither half of this bug is tested. testBasic has put an EmptyTokenStream between children since the class was added (:44), so empty sources are legal input.
  • The indexing chain (IndexingChain.java:2105-2109) calls end() and adds the final increment for every value, including a value with no tokens, then the position gap (:2122). Executed: the multi-valued field "alpha the", "", "beta" puts beta at 2; the concatenation of the same streams at 1.
  • The analysis docs: TokenStream.end() says skipped positions "(such as those removed by a stopfilter) can be applied to the position increment" (TokenStream.java:152-154); the package docs say the components "must put accurate values into the token attributes to reflect the situation at the end of the field" (analysis/package-info.java:276-281). An empty last source makes end() report 0 although a hole is pending.
  • History: LUCENE-2529 and LUCENE-2668 (2010) fixed, as bugs, empty or stop-word-only values of multi-valued fields that shifted later positions or offsets in the indexing chain; LUCENE-3849 moved trailing holes into end() so that multi-valued fields keep them.
The devil's-advocate check229 words

"Positions across an empty source are unspecified." The class javadoc promises "as if all the inputs were from a single source" only for offsets, end() says "can", not "must", and no test combines an empty source with a pending hole. It fails because LUCENE-8650 made carrying child final increments the stated and tested behaviour, the same loop adds offsets but overwrites positions, and no comment, test or discussion drops the increments of empty sources on purpose.

"Phrases across sources are loose anyway: the class adds no position gap." No gap is a separate, deliberate choice. The defect is that the same tokens get different positions depending on whether an empty value sits between them: concat("alpha the", "beta") puts beta at 2, concat("alpha the", "", "beta") at 1. An empty source should change nothing.

"What a stop-word-only middle value should add is a design question." Possibly; summing its own hole gives the positions of the multi-valued field and of the single text ([1, 3] for foo the + the + bar), which is the natural reading. The case is strongest for an empty value (final increment 0), which should change nothing, and for the empty last value's end(); it is weakest for how several stop-word-only values combine, which no document spells out. Verdict of every verifier and the adjudication: not intended (an opinion; the contracts are above).

Suggested fix

#

Recommended A. Accumulate a pending increment

Keep a pending counter: add (+=) each finished source's final increment, add it to the next token and clear it, add any rest in end(), and clear it in reset() (+8/-4 in one file). Validated: the three repro classes pass, and the module's 1,909 tests and static checks pass. Inputs where every source has a token are unchanged.

A. Accumulate a pending increment (validated by the checks) (recommended)

#

Rename initialPositionIncrement to pendingPositionIncrement (starting at 0), add to it instead of assigning, clear it once it is applied to a token, add what is left in end(), and clear it in reset(). The regression test: the four methods of the repro, added to TestConcatenatingTokenStream.

+      pendingPositionIncrement += sourceIncrements[currentSource].getPositionIncrement();
 ...

+      pendingPositionIncrement = 0;
 ...
-    int finalPosInc = sourceIncrements[currentSource].getPositionIncrement();
+    int finalPosInc =
+        pendingPositionIncrement + sourceIncrements[currentSource].getPositionIncrement();
 ...
+    pendingPositionIncrement = 0;   // in reset()

Trade-offs

  • Positions change only for inputs that hit the bug (a pending hole followed by a source with no tokens, or an empty last source); when every source has a token, the assignment and the pending counter give the same values, and the upstream tests pass unchanged.
  • No extra work per token. Documents indexed before the fix keep their wrong positions until reindexed; the CHANGES entry should say so and reference LUCENE-8650.
  • A stop-word-only middle value adds its own hole too ([1, 3]), matching a multi-valued field; a maintainer may want that spelled out in the javadoc.

What the checks validated

That is the module's 1,909 upstream tests (among them TestConcatenatingTokenStream 4 of 4) plus the 14 repro tests, which fail 10 of 14 on stock main.
  • Static checks: :lucene:analysis:common:check -x test with the fix and the doc's test passes (checkGoogleJavaFormat, ecjLint, forbiddenApis, checkLicenses; error-prone is skipped in this build).
  • Earlier, with the standalone runner: the finder's version of the same fix passes the finder's 4, the independent reproducer's 6 and the security probe's 6 tests; the reproducer wrote the same fix independently.
  • The fact check's probe also ran fix A on two sources with no tokens in a row, an empty first value, a stop-word-only middle value, an empty last value and reuse after reset(): every value matches the multi-valued field. An all-empty stream and early or repeated end() calls were not run.

B. Only change = to += at line 92 (wrong)

#

The one-character change a reviewer may suggest first. The field starts at 1 (line 48) and reset() never clears it, so a bare += also breaks inputs where every source has a token.

Trade-offs

  • Executed (a main() probe on the stock classes with each variant): += alone gives the control concat(foo+hole, bar) [1, 3] instead of [1, 2], the testOffsetGaps input {1, 1, 4, 1} instead of {1, 1, 3, 1} (the upstream test would fail), and three plain one-token sources [1, 2, 2].
  • Adding the clear once applied and the rest in end() still gives the control [1, 3] and testOffsetGaps {1, 1, 4, 1}, gives end() 2 instead of 1 for an empty last source, and leaks state across reset() (the next document's x, y get [1, 3]).
  • Only with all four changes (start at 0, clear once applied, add the rest in end(), clear in reset()) is every case right, and that is option A.

C. Document the limitation instead (not recommended)

#

A javadoc note that positions are not carried across a source with no tokens.

Trade-offs

  • Keeps the silent shift and the mismatch with multi-valued fields, and contradicts what LUCENE-8650 set out to fix.
  • Not run.

D. Workaround without a Lucene change

#

Index the values as a multi-valued field instead: the indexing chain keeps the holes (executed: beta at 2). Dropping empty values before concatenating avoids the empty case, but not a value made only of stop words.

Trade-offs

  • A multi-valued field applies the analyzer's position and offset gaps between values (0 by default for the position gap), which may differ from what the application wanted from one concatenated stream.

History

#

Introduced in 7.7.0 by LUCENE-8650 (7713a4f2458c, 2019), which added the carry-over of final increments with an assignment and a last-source-only end(): an incomplete fix, not a regression. Affected on every release run from 7.7.0 to 10.5.2 and main; the tagged releases in between hold the same file. Before 7.7.0 the same inputs were already wrong, for an older reason.

Only applications that hand-build a field's token stream with ConcatenatingTokenStream (a public analysis-common class with no analysis factory, no in-tree caller and no use found in Elasticsearch, OpenSearch or Solr) are hit, and only when a source that ends in a hole (typically a trailing stop word removed by a StopFilter) is followed by one or more sources that emit no tokens (an empty value, or one made only of removed tokens): the hole is lost, so later tokens of that field are indexed too close, or end() reports 0 instead of the hole, and phrase, span and interval queries on the affected document can over-match or miss, with -ea and -da and the default codec; no scale is needed, nothing throws and CheckIndex stays clean.
Summary
You build one field from several token streams with ConcatenatingTokenStream, for example the values 'alpha the', '' and 'beta', each run through a StopFilter that removes 'the'. You expect the hole left by the removed 'the' to survive, as it does when no empty value sits in between and as IndexWriter keeps it for the same values in a multi-valued field, because LUCENE-8650 (7.7.0) made the class carry each source's final position increment over to the next token. Instead each exhausted source overwrites the pending increment instead of adding to it, and end() reports only the last source's own increment, so a source with no tokens erases the hole: 'beta' is indexed directly after 'alpha', the exact phrase "alpha beta" matches this document but not the single value 'alpha the beta', and with an empty last source end() reports 0 instead of 1.
