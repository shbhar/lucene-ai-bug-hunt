Polygon.fromGeoJSON rejects a GeoJSON Feature whose properties contain a "type" member

Polygon.fromGeoJSON accepts a Polygon inside a GeoJSON Feature, but throws ParseException: ... but got x when the Feature's free-form properties hold a key named "type", such as {"type": "x"}. The parser reads every "type" key as a GeoJSON object type; affected since 6.2.0.

The finding in 30 seconds

#

Background: GeoJSON Features in Lucene

#
  1. A GeoJSON Feature wraps one geometry and free-form data: {"type": "Feature", "geometry": {"type": "Polygon", "coordinates": [...]}, "properties": {...}}. The "type" member names the kind of GeoJSON object; properties is any JSON object the producer chooses.
  2. Polygon.fromGeoJSON(String) in Lucene core turns a Polygon or MultiPolygon, bare, inside a Feature, or inside a one-Feature FeatureCollection, into Polygon[], and throws ParseException for anything else (a Point, several features, a non-CRS84 crs).

The finding, step by step

#
  1. Parse a triangle with Polygon.fromGeoJSON: {"type": "Polygon", "coordinates": [[[0, 0], [1, 0], [1, 1], [0, 0]]]} gives 1 polygon. Wrapped in a Feature with "properties": {"name": "park"}, it gives the same polygon.
  2. Change the property to "properties": {"type": "x"}. GeoJSON lets properties be any JSON object, and the javadoc accepts a Polygon "optionally embedded under a "type: Feature"", so you expect the same 1 polygon.
  3. Instead you get ParseException: can only handle type FeatureCollection (...), Feature, Polygon or MultiPolygon, but got x at character offset 127. The parser checks every "type" key outside crs as a GeoJSON object type (line 186), so x looks like an unsupported geometry.
  4. Its sibling key "coordinates" is read only at geometry positions, so {"coordinates": [...]} in properties is ignored: only "type" is fatal. Data shaped like a geocoder's documented RFC 7946 output (with its full-geometry option), a one-Feature FeatureCollection with properties {"category": "boundary", "type": "administrative"}, fails with ... but got administrative.

Who is affected

#

Applications that pass whole GeoJSON Features, not bare geometries, to Polygon.fromGeoJSON when properties hold a "type" key, such as data shaped like a geocoder's documented output, or copied map tags. No setting and no scale: one key in one document, in every release since 6.2.0. It fails loudly and never returns a wrong polygon; Lucene itself never calls the method.

Mechanism, terms and numbers597 words

Polygon.fromGeoJSON(String) (core, @lucene.experimental) accepts a Polygon or MultiPolygon "optionally embedded under a "type: Feature"", and GeoJSON lets a Feature's properties be any JSON object. The parser behind it, SimpleGeoJSONPolygonParser, tracks where each object sits (geometry, properties, features.[], ...) and reads "coordinates" only at geometry positions, but it reads a member named "type" as a GeoJSON object type at every position except under crs (SimpleGeoJSONPolygonParser.java:186). So a Feature whose properties hold {"type": "x"} is rejected with ParseException: can only handle type FeatureCollection (if it has a single polygon geometry), Feature, Polygon or MultiPolygon, but got x, and {"type": 3} with type should be a string, but got: 3.0. The same Feature without that key parses. Nothing wrong is ever returned: the error is loud and the input is valid. The check came with the parser in LUCENE-7380 (6.2.0, 2016); all 90 releases from 6.2.0 to 10.6.0 and main fail the one-test repro. Reading "type" only where a GeoJSON object can appear fixes it; the recommended fix also keeps the crs checks for a crs on a nested geometry.

Terms

#
  • SimpleGeoJSONPolygonParser: the package-private hand-written parser behind Polygon.fromGeoJSON (Polygon.java:255-257). It "does minimal parsing of a GeoJSON object, to extract either Polygon or MultiPolygon" (SimpleGeoJSONPolygonParser.java:47-51).
  • Path: the parser's address of the object it is reading, built from member names: "" for the top level, geometry, properties, properties.source, features.[], features.[].geometry.
  • Geometry path: isValidGeometryPath (:221-224), the three places a Polygon may sit: "", geometry, features.[].geometry.

The bug

#
  1. parseObject parses a member whose value is an object recursively, with path path + "." + key (:146-153); so the Feature's properties object is read with path properties.
  2. After each member, line 186 asks if (key.equals("type") && path.startsWith("crs") == false): every "type" member outside crs is read as a GeoJSON object type, wherever it sits.
  3. Inside that branch, a non-string value throws type should be a string (:187-190); Polygon and MultiPolygon are accepted only on a geometry path (:192-195); Feature and FeatureCollection only at "" or features.[] (:196-197); anything else throws can only handle type ... but got <value> (:199-204). At path properties no value can pass.
  4. The next check, key.equals("coordinates") && isValidGeometryPath(path) (:205), is scoped by path. That asymmetry is the bug: "coordinates" in properties is ignored, "type" in properties is fatal.

Exposure and likelihood299 words
  • Who is hit. Callers of Polygon.fromGeoJSON (core; Polygon is @lucene.experimental, Polygon.java:41) that pass Features or one-Feature FeatureCollections whose properties (or an object nested in them) hold a key named "type". Default and only behaviour; assertions on or off make no difference.
  • Realistic trigger. "type" is an ordinary data name. The output docs of the OpenStreetMap geocoder Nominatim say its GeoJSON format "follows the RFC7946" and list among the properties fields "category, type - key and value of the main OSM tag". Data shaped like that, a one-Feature FeatureCollection with a polygon geometry and properties {"category": "boundary", "type": "administrative"}, is rejected on main and on 10.6.0; it was built from the docs, not fetched from the service. Caveats: the docs give the centroid (a Point, rejected anyway) unless the caller asks for the full geometry with polygon_geojson, and the parser accepts a FeatureCollection only with a single polygon. In OpenStreetMap a multipolygon relation carries the tag type=multipolygon; data that copies such tags into properties is rejected the same way (... but got multipolygon).
  • Reach. In the Lucene tree the method has no production caller, only TestPolygon and TestTessellator. A read-only code search found a benchmark call in Elasticsearch and none in OpenSearch (Solr not checked). No relevant public report was found in the recorded searches: likelihood "plausible", priority low.
  • What happens. The query area or document cannot be turned into a polygon, and the message is misleading: "but got administrative" names a property value, not a geometry type. Workaround: pass only the geometry object, or drop properties before calling.
  • What does not happen. No wrong or different polygon (a decoy geometry in properties is rejected, never used), no hang, no extra cost beyond a normal parse, nothing written to an index.

Why it looks unintended

#
  • The javadoc accepts a Polygon "optionally embedded under a "type: Feature"" and links the GeoJSON spec, where properties is "any JSON object".
  • The parser already reads "coordinates" only at geometry positions and exempts crs from the "type" check; properties was not exempted.
  • No test asserts this rejection; LUCENE-8964 already fixed this parser for rejecting other legal properties content.
The full argument287 words
  • Contract. Polygon.java:248-254: "Parses a standard GeoJSON polygon string. The type of the incoming GeoJSON object must be a Polygon or MultiPolygon, optionally embedded under a "type: Feature"", with a link to the 2008 GeoJSON specification. Its section 2.2: "The value of the properties member is an object (any JSON object or a JSON null value)"; RFC 7946 section 3.2 says the same. The 6.2.0 CHANGES entry promises parsing of "a standard GeoJSON string" (lucene/CHANGES.txt:8978-8980).
  • The parser's example and tests. The header comment (SimpleGeoJSONPolygonParser.java:23-45) shows an accepted Feature with "properties": {"prop0": "value0", "prop1": {"this": "that"}}; TestPolygon.testGeoJSONPolygonFeature (TestPolygon.java:176-199) parses it.
  • Scoping exists next door. "coordinates" is read only on geometry paths (:205), and crs is exempt from the "type" check (:186) because a crs object has its own "type" (testIllegalGeoJSONLinkedCRS even has "type": "proj4" under crs.properties, TestPolygon.java:283-303). The authors knew "type" occurs outside GeoJSON objects.
  • No test asserts it. The tested rejections concern the geometry, the feature count, the crs or trailing data: testIllegalGeoJSONMultipleFeatures (:305-346, "but got Point" at features.[].geometry), testIllegalGeoJSONLinkedCRS (:283-303), testIllegalGeoJSONExtraCrapAtEnd (:268-281). All 16 pass with the fix.
  • Intent on record. LUCENE-7380 (#8433): "The parser only handles the various ways that a single Polygon or MultiPolygon can appear in a GeoJSON string, and throws an exception otherwise." A Feature with a Polygon geometry is one of those ways; the issue never discusses "type" keys in properties.
  • Precedent. LUCENE-8964 (#10007, 8.3.0, lucene/CHANGES.txt:6239-6240 "Fix geojson shape parsing on string arrays in properties"): the same parser rejected other legal properties content and the project fixed it, in parseArray; this bug reproduces on every release after that fix.
The devil's-advocate check195 words

The strongest case for "intended" (the study's intended-behaviour checker, the cross-model review lenses and the adjudication): the parser calls itself "minimal parsing" (:47-51), Polygon is @lucene.experimental, the parser deliberately rejects Point, LineString, GeometryCollection, several features and linked crs, and RFC 7946 section 6.1 says support for foreign members "can vary across implementations".

Why it fails: "minimal parsing" describes what is extracted, not a restriction on properties, and @lucene.experimental is about API stability. The deliberate rejections cover unsupported geometry types, more than one polygon, crs handling and trailing input; none concerns a "type" key in Feature properties, while the rejected input is exactly the documented shape. properties is a core Feature member, not a foreign member, so section 6.1 does not apply to the main case. For foreign members it cuts both ways: support "can vary", but the same section says "GeoJSON semantics do not apply to foreign members and their descendants, regardless of their names and values". The cross-model lenses rated the intended argument weak; the later cross-model fact check rated it moderate (a deliberately narrow parser), with a strong rebuttal for the properties case. Verdict: a defect, low severity.

Suggested fix

#

Recommended B. Scope "type" to GeoJSON object positions and check every object's crs

Read "type" only where a GeoJSON object can appear (the top level, a geometry, a feature), and run the existing crs checks for a crs on any such object. With it the repro passes with assertions on and off, a nested non-CRS84 crs is still rejected, and TestPolygon, the org.apache.lucene.geo tests and :lucene:core:check pass.

All options and trade-offs3 options · 682 words

Two options were run through gradle in a scratch worktree of 645d4fe14a20; B is recommended. Both leave one residual: a foreign member literally named "geometry" (or "features") is still read as a GeoJSON location, but RFC 7946 section 7.1 forbids such members on a Geometry object, so only non-conforming input hits it. A fix conflicts textually with PR #12295 (open as of the 2026-11-01 scan).

Trade-offs

  • Removes the rejections where "type" is data, and validates a crs on a nested geometry or feature like a top-level one: CRS84 is accepted (main rejects it with the misleading "but got name"), another or a linked crs is rejected with the existing messages.
  • Adds one rejection: a nested crs that lacks its required "type" member and names a non-CRS84 or linked system, or whose name is not a string, which main accepts silently, is rejected, as it already is at the top level.
  • About 15 lines; no API or format change. Not benchmarked: it adds a few string comparisons per parsed member.

A plus an explicit rejection of nested crs (not tried)

Keep A and throw "crs is only supported at the top level" for a crs member below the top level.

Trade-offs

Also closes A's gap and is simple, but rejects a nested CRS84 crs, which the 2008 spec allows (though it says a crs "should not be repeated or overridden on children or grandchildren"). Not tried.

Downstream note

#

No search server is known to pass request or document GeoJSON through this method (a code search found only a benchmark call in Elasticsearch and none in OpenSearch; Solr was not checked), so the exposure is applications that call Polygon.fromGeoJSON directly.

How it was found

#

Non-formal: a differential parsing probe fed the parser accepted GeoJSON shapes with extra members and compared the result with the coordinates as written; a Feature with a "type" key in properties was rejected. Reading the code found the unscoped "type" check, and a public-API JUnit test reproduced it on the stock build.

The method in full108 words

Method: non-formal (differential testing, then code reading and executed tests). On 2026-10-26 the hunt unit for the LatLon geo queries ran a probe over GeoJSON inputs the parser should accept: Polygon, MultiPolygon, Feature and FeatureCollection with holes, extra members, nulls, exponent numbers and whitespace, each compared with its coordinates as written. While probing extra members it saw a valid Feature rejected because its properties held a "type" key. Reading SimpleGeoJSONPolygonParser found the path.startsWith("crs") == false condition next to the path-scoped "coordinates" check. A public-API JUnit test reproduced it on the stock build; independent checkers reproduced it with their own tests, and it was cut to the one-test repro.

LFV-562, snapshot of 2026-11-06

Registry title
Polygon.fromGeoJSON rejects a valid GeoJSON Feature whose properties (or another non-geometry member object) contain a member named "type", throwing ParseException 'can only handle type ... but got <value>' (every release since 6.2.0)
Area
core / geo GeoJSON parsing (Polygon.fromGeoJSON, SimpleGeoJSONPolygonParser)
Priority
Low, rank 1071: Polygon.fromGeoJSON loudly rejects valid Features whose properties contain a 'type' key, reachable by real data but in an experimental method with no production callers.
Impact class
wrong error
Impact note
Hits applications that call Polygon.fromGeoJSON (core; Polygon is @lucene.experimental; the method has no production caller in the Lucene tree, and a read-only code search found only a benchmark call in Elasticsearch and none in OpenSearch) with whole GeoJSON Features rather than bare geometries: a Feature whose properties, or an object nested in them, hold a key "type" (for example a geocoder's 'type' field or a map tag type=multipolygon) is rejected with ParseException, and so is a Polygon carrying a foreign member object with a "type" key; no setting is involved, no wrong polygon is ever returned, nothing hangs and no index is touched, no scale is needed, with -ea and -da, in every release from 6.2.0 to 10.6.0 and main.
Summary
You call Polygon.fromGeoJSON on a standard GeoJSON Feature whose geometry is a single Polygon and whose properties contain an ordinary data member named "type", for example {"type": "Feature", "geometry": {...Polygon...}, "properties": {"type": "multipolygon"}}, and expect the polygon back, because the javadoc accepts a Polygon 'optionally embedded under a "type: Feature"' and GeoJSON allows any JSON object as properties. Instead it throws ParseException 'can only handle type FeatureCollection (if it has a single polygon geometry), Feature, Polygon or MultiPolygon, but got multipolygon' ('type should be a string, but got: 3.0' for {"type": 3}), because the parser reads every "type" member outside crs as a GeoJSON object type, wherever it sits, while it reads "coordinates" only at geometry positions. The same Feature without the "type" property parses, and a "coordinates" key inside properties is ignored.
