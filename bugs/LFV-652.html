Copying a ParallelLeafReader into an index stores a later reader's stored fields under another field's name

Copy a ParallelLeafReader that joins index A (title) and index B (price) into an empty index with addIndexes, and B's price="42" is stored as a second title, with no error and a clean CheckIndex. Every release since 5.0.0 does this.

The bug in 30 seconds

#

ParallelLeafReader joins indexes that hold different fields of the same documents, so they read as one index. Copying that joined view into a real index, with addIndexes over SlowCodecReaderWrapper or from OneMerge.wrapForMerge, should keep every stored field under its own name.

  1. Index A stores title="Lucene in Action" and index B stores price="42" for the same document. Each index numbers its own first field 0, so title and price are both field 0.
  2. Join them with new ParallelLeafReader(false, a, b). Reading works: the document has title and price, and the joined view renumbers price to field 1.
  3. Copy the view into an empty index with addIndexes(SlowCodecReaderWrapper.wrap(parallel)). You expect title="Lucene in Action" and price="42".
  4. You get title="Lucene in Action" and title="42", and no price. B reports its value as field 0; the merge sees that the view's numbers match the new index, skips its by-name check, and writes field 0: title.
  5. No error, and CheckIndex passes; searches still match, because postings, doc values and points copied correctly in every tested case. A merge whose wrapForMerge adds a side index goes wrong the same way.

Who is affected

#

Applications that copy a ParallelLeafReader over two or more indexes, with addIndexes(SlowCodecReaderWrapper.wrap(...)) or a custom wrapForMerge, when a later index stores fields and the target gives the view's fields the view's numbers (an empty target, for one). Default config and codec. Stored values come back under wrong names; query matching is unaffected.

Mechanism, terms and numbers785 words

ParallelLeafReader joins indexes that hold different fields of the same documents; "Each document contains the union of the fields of all documents with the same document number". Reading through it is correct. Copying it into an index, with IndexWriter.addIndexes(SlowCodecReaderWrapper.wrap(parallelReader)) or from a MergePolicy.OneMerge.wrapForMerge that returns one, writes each stored value of a later reader under the name of whichever target field holds that reader's own field number (an earlier reader's field, or another field of the same reader) whenever the target gives the parallel reader's fields the parallel reader's numbers, for example an empty target. With index A storing title="Lucene in Action" and index B storing price="42", the copy holds title="Lucene in Action" and title="42" and no price, with no exception and a clean CheckIndex. storedFields() lets each sub-reader call the visitor with its own FieldInfo (price is number 0 in B), the parallel reader's getFieldInfos() numbers price 1, and StoredFieldsWriter.MergeVisitor skips its by-name remapping because those numbers match the target's, so it writes number 0, which in the target is title. In every tested case postings, doc values, points, vectors, norms and deletions were copied correctly. The merge shortcut came with LUCENE-6133 (5.0.0, 2014), a speed-up; 4.10.x copies correctly, and every release from 5.0.0 to 10.5.2 and main is affected.

Terms

#
  • ParallelLeafReader: a LeafReader over several indexes with the same documents in the same order but different fields: "Each document contains the union of the fields of all documents with the same document number" (index/ParallelLeafReader.java:38-39).
  • Field numbers: every index gives each field name a number, in the order it first sees the names, so independently built indexes all start at 0. A FieldInfo carries a field's name and number; stored fields are written on disk by number.
  • Copying a reader: IndexWriter.addIndexes(CodecReader...) "Merges the provided indexes into this index"; SlowCodecReaderWrapper.wrap turns any LeafReader into the CodecReader it needs. A merge can also wrap each segment with OneMerge.wrapForMerge, "in order to add/remove fields or documents".

The bug

#
  1. The view renumbers. ParallelLeafReader builds its own FieldInfos, first reader wins (ParallelLeafReader.java:154-159); a field keeps its number only if it is still free, else it gets the lowest free one (FieldInfos.java:425-433). B's price, number 0, becomes 1. The javadoc says the numbers "will likely not correspond to the actual field numbers in the underlying readers" (:242-244).
  2. Stored fields are visited with the sub-reader's own numbers. storedFields().document(docID, visitor) hands the caller's visitor unchanged to each sub-reader (:291-296), and SlowCodecReaderWrapper passes it straight through (SlowCodecReaderWrapper.java:332-335). B's reader reports price as number 0.
  3. The merge trusts numbers that look aligned. MergeVisitor turns its by-name remapping on only if a number in the source's getFieldInfos() names a different field in the target (codecs/StoredFieldsWriter.java:182-192, "if field numbers are aligned, we can save hash lookups"). For an empty target the merged numbering adopts the view's (title 0, price 1), so the check passes and remap() returns the visited FieldInfo as is (:237-243).
  4. The codec writes the foreign number. The default stored-fields writer copies a non-codec source field by field through this visitor (Lucene90CompressingStoredFieldsWriter.java:678-685, :637-641) and records number 0, which in the new index is title.

If the target gives even one of the view's fields a different number, the constructor check fails, remapping by name is on and the copy is correct. If only the first reader stores fields, no stored value carries a foreign number; if the earlier readers have no fields at all, a later reader keeps its own numbers and nothing is renamed (read from FieldInfos.java:425-427, not run).

Exposure and likelihood440 words
  • Who. Applications that copy a ParallelLeafReader, or the leaves of a ParallelCompositeReader (same result in one probe), built over two or more indexes: addIndexes(SlowCodecReaderWrapper.wrap(...)) to turn a parallel index into a single one, or a OneMerge.wrapForMerge that folds a side index into segments as they merge (the pattern of upstream's TestDemoParallelLeafReader). A rarely used API combination; everything else is default (IndexWriterConfig, codec, merge scheduler).
  • Trigger. Two conditions. (1) A later sub-reader has a stored field whose own number differs from its number in the view; that is always so in the usual setup, where every index numbers its fields from 0 and an earlier reader has at least one field. (2) The target gives each of the view's fields the view's number: an empty target, or one that already holds the same fields under the same numbers. No special data and no scale; in the usual setup every copied document with a stored value from a later reader is hit.
  • Effect. Silent and permanent. In the copy each stored value of a later reader carries the name of whichever field holds that reader's own number in the target, and the real field is missing: with one field in B that is an earlier reader's field (price becomes title); with several, values move down by as many names as the earlier readers have fields, so some land on other fields of the same reader. Postings, doc values, points, vectors, norms and deletions were copied correctly in every tested case, so queries match the same documents; what breaks is the stored data the application loads: displayed values, highlighting, and any later re-indexing from stored fields, which carries the wrong names on. The stored-only cases are CheckIndex-clean, so nothing reports it; if the source indexes are discarded after the copy, the original values are lost.
  • Not hit when the target's numbering differs (the merge then remaps by name) or when only the first reader stores fields. The wrapForMerge path needs the stored-field side index after the segment reader; upstream's demo puts its side index first and takes the safe path.
  • How often among small cases. A bounded-exhaustive run over 128,625 configurations found stored-field mismatches in 21,993 empty-target copies and none where the target's numbering differs; with fix A, none (8,040-configuration sample).
  • Downstream, by reading only. Elasticsearch and OpenSearch use ParallelLeafReader on a read path only. Solr main (not in a release) has a wrapForMerge that returns SlowCodecReaderWrapper.wrap(new ParallelLeafReader(...)), but its side segments hold only doc values and its padding wrapper exposes no stored fields, so it is not hit as written. Nothing downstream was run.

Why it is a bug, not intended

#
  • Lucene's own composite merge wrapper maps each visited field to its own FieldInfo by name; ParallelLeafReader renumbers but does not remap.
  • addIndexes "Merges the provided indexes into this index", and the view itself returns price; only the copy loses it.
  • Up to 4.10.4 the merge matched fields by name and the copy is correct; the 5.0 change was a speed-up.
The full argument354 words
  • Contracts. ParallelLeafReader: "Each document contains the union of the fields of all documents with the same document number" (ParallelLeafReader.java:38-39). IndexWriter.addIndexes(CodecReader...): "Merges the provided indexes into this index" (IndexWriter.java:3255). SlowCodecReaderWrapper: "Wraps arbitrary readers for merging" (:38). OneMerge.wrapForMerge: "Wrap a reader prior to merging in order to add/remove fields or documents" (MergePolicy.java:302). The addIndexes path uses no experimental or internal API; the merge path does: MergePolicy, MergePolicy.OneMerge (which declares wrapForMerge) and the repro's FilterMergePolicy are @lucene.experimental (MergePolicy.java:69, :189; FilterMergePolicy.java:27).
  • Lucene's own wrappers keep the invariant. SlowCompositeCodecReaderWrapper (#12622, 2023): "Remap FieldInfos to make sure consumers only see field infos from the composite reader, not from individual leaves" (SlowCompositeCodecReaderWrapper.java:118-122, used in every visitor callback at :162-205). The test framework's MismatchedLeafReader, which renumbers fields on purpose, also renumbers the FieldInfo its visitor passes on (MismatchedLeafReader.java:110-135); its issue, LUCENE-6135 (#7197), says merge shortcuts must be off when numbers do not line up, or values get mixed up across fields.
  • History. Before LUCENE-6133 the merge loaded each document and wrote it through fieldInfos.fieldInfo(field.name()), by name; the removed code even had a TODO to "renumber the field number on the fly". LUCENE-6133 (5.0.0) was a speed-up, "Improve default StoredFieldsWriter.merge() to be more efficient" (lucene/CHANGES.txt:11324), and its issue (#7195) discusses only CPU cost. 4.10.4 copies correctly; builds of the commit fail and of its parent pass.
  • Copying parallel readers is a tested path. TestParallelReaderEmptyIndex: "Adding this reader to a new index should not throw any exception", then addIndexes(SlowCodecReaderWrapper.wrap(pr)) (:34-36, :129-134); TestDemoParallelLeafReader returns SlowCodecReaderWrapper.wrap(ParallelLeafReader) from wrapForMerge (:644-650); LUCENE-1918 (2.9.0) fixed exceptions when a ParallelReader was "passed to IndexWriter.addIndexes(IndexReader[])" (lucene/CHANGES.txt:19473-19478); in a 2009 java-user answer a committer (@mikemccand) suggested "use addIndexes(IndexReader[]), passing in your ParallelReader". None of these tests has a stored field in a later reader with an aligned target.
  • Precedent. LUCENE-3575 (#4649, 2011), "Field names can be wrong for stored fields / term vectors after merging", the same symptom in older merge code, was fixed as a bug.
The devil's-advocate check231 words

The intended-behaviour verifier built the strongest case for "not a bug": field numbers are internal; getFieldInfos() warns its numbers "will likely not correspond" to the sub-readers'; StoredFieldVisitor is @lucene.experimental (StoredFieldVisitor.java:35); the class javadoc names searching as the use case (ParallelLeafReader.java:42-44) and warns that indexes not "created and modified the same way" give "undefined behavior" (:46-49); and wrapForMerge is experimental merge-policy API where the application supplies the reader, so maintainers could ask that reader to present consistent FieldInfos.

Why it fails for addIndexes: the NOTE came with LUCENE-4055 (2012, about codec metadata), two and a half years before the merge shortcut, and describes a numbering difference, not renamed persisted data. The addIndexes user calls only public, non-experimental API and never sees a FieldInfo. The "same way" warning's only example concerns documents and their order and it states no field-number requirement, while the same javadoc expects different fields per index, which always number from 0. Upstream tests and CHANGES copy parallel readers. The cross-model reviews and the verifier rated the case weak; a cross-model fact check of this doc rates it moderate for wrapForMerge, the experimental path, which is one more reason to lead with addIndexes. Verdict: a defect. The issue should say up front that copying is supported by tests, CHANGES and a list answer rather than by the class javadoc.

Suggested fix

#

Recommended A: ParallelLeafReader.storedFields() presents its own FieldInfo

Make ParallelLeafReader.storedFields() hand each visitor the view's own FieldInfo, looked up by name, as Lucene's composite merge wrapper already does (+60/-1, one file). Both repros pass, and so do the 191 upstream tests in the 18 closest test classes. It does not cover the expert constructor's stored-only readers.

public void document(int docID, StoredFieldVisitor visitor) throws IOException {
  // Sub-readers report their own FieldInfo (their own field numbers); present this
  // reader's FieldInfo instead, so consumers that trust FieldInfo.number (e.g. the
  // stored fields merge) see numbers consistent with getFieldInfos().
  StoredFieldVisitor remapping = new RemappingStoredFieldVisitor(visitor, fieldInfos);
  for (StoredFields reader : fields) {
    reader.document(docID, remapping);
  }
}
// RemappingStoredFieldVisitor.remap(fi):
//   FieldInfo own = fieldInfos.fieldInfo(fi.name); return own == null ? fi : own;

A: ParallelLeafReader.storedFields() presents its own FieldInfo (validated by the checks) (recommended)

#

Wrap the caller's visitor so that needsField and the seven value callbacks receive the parallel reader's FieldInfo for that field name, falling back to the sub-reader's when the name is unknown. The same pattern as SlowCompositeCodecReaderWrapper. Patch: optionA-parallelleafreader-remap-visitor.diff, the finder's sketch, +60/-1 in ParallelLeafReader.java.

public void document(int docID, StoredFieldVisitor visitor) throws IOException {
  // Sub-readers report their own FieldInfo (their own field numbers); present this
  // reader's FieldInfo instead, so consumers that trust FieldInfo.number (e.g. the
  // stored fields merge) see numbers consistent with getFieldInfos().
  StoredFieldVisitor remapping = new RemappingStoredFieldVisitor(visitor, fieldInfos);
  for (StoredFields reader : fields) {
    reader.document(docID, remapping);
  }
}
// RemappingStoredFieldVisitor.remap(fi):
//   FieldInfo own = fieldInfos.fieldInfo(fi.name); return own == null ? fi : own;

Trade-offs

  • Two hash lookups by name (FieldInfos.fieldInfo(String)) per loaded stored field (one in needsField, one in the value callback; one for a skipped field) and one wrapper-visitor allocation per document() call, on every read through a ParallelLeafReader, at search time too; it could be skipped for sub-readers whose numbering already matches. No benchmark was run.
  • Search-time visitors now see numbers consistent with getFieldInfos(), arguably a fix too.
  • It protects ParallelLeafReader only, not other wrapping readers.

B: MergeVisitor trusts a visited number only if it names the same field (validated by the checks)

#

When the constructor found the numbering aligned, remap() checks that the visited number names the same field in the merged FieldInfos, and otherwise looks the field up by name. Patch: optionB-mergevisitor-check-number.diff, +9/-1 in StoredFieldsWriter.java.

// in MergeVisitor.remap(), after the existing remapper branch:
FieldInfo merged = mergeFieldInfos.fieldInfo(field.number);
if (merged != null && merged.name.equals(field.name)) {
  return field;
}
return mergeFieldInfos.fieldInfo(field.name);

Trade-offs

  • Protects every merge that copies stored fields through StoredFieldsWriter.MergeVisitor (the default merge and the Lucene90 VISITOR strategy) against any wrapping reader that hands it foreign FieldInfo, at the cost of one array lookup and one string comparison per stored field on that path only; the codec's bulk and per-document copy paths are untouched. No benchmark was run.
  • A stored-fields format that overrides merge without MergeVisitor is not covered, and a name the target does not know still yields null (the NullPointerException of the expert aside).
  • Search-time visitors of a ParallelLeafReader still see sub-reader numbers.

What the checks validated

  • With B (A reverted): the finder's test 2/2 and the independent test 3/3 pass.
  • The expert aside now fails with NullPointerException: Cannot read field "number" because "info" is null in the merge thread (Lucene90CompressingStoredFieldsWriter.writeField): B turns that silent rename into an exception, it does not make it copy.
  • The same closest core suites plus TestSimpleTextStoredFieldsFormat (merges through the default StoredFieldsWriter.merge): 21 classes, 215 tests, 11 skipped, 0 failures.

Downstream note

#

Applications that copy a ParallelLeafReader with stored fields should check stored-field names in the copy; Solr main uses the same wrapForMerge pattern without stored fields, so it is not hit (code reading only).

How it was found

#

Bounded-exhaustive metamorphic testing: copies of a ParallelLeafReader were compared with one reference index built from the class javadoc's rules, over 128,625 small configurations. The suspicion came first, while writing an executable model of the javadoc; the run then found stored-field mismatches in 21,993 empty-target copies and none where the target was numbered differently.

The method in full324 words

Method: bounded-exhaustive metamorphic translation validation (a hunt unit, 2026-10-27). No model checker, solver or prover was involved.

  • The relation. A ParallelLeafReader over readers A and B, and its addIndexes copies into an empty target, a reverse-numbered target, an aligned target and through the expert constructor, must equal a reference single index built from the javadoc's union and first-owner rules, compared per live document: live docs, FieldInfos, postings, norms, doc values, points, vectors, stored fields and term vectors.
  • The space. 3 fields; in each of the 2 readers a field is absent or one of {stored, text with term vectors, numeric doc values, 1D int point, 2D float vector}, not absent in both, so 35 combinations per field; 35^3 x 3 deletion modes = 128,625 configurations, 3 documents per reader, 686,000 checks. Run on the stock jars of ea57360912ed, whose stored-field code on this path is identical to a9779ef3c193 (the only differences in the classes involved, in SlowCodecReaderWrapper and the stored-fields reader, are vector-hint and merge-stream code); local samples on a9779ef3c193 agree.
  • The result. Stored-field mismatches in 21,993 empty-target copies, 21,993 aligned-target copies and 7,331 expert-constructor copies; 0 in reverse-numbered targets; 0 with the fix sketch (8,040-configuration sample). The only other mismatch kind was term vectors, a separate registered bug on the same path. Live docs, postings, norms, numeric doc values, 1D points and float vectors never differed; other doc-values types, byte vectors, multi-dimensional points, payloads and fields that are both stored and indexed were not in the model.
  • Order of events. The hypothesis came from reading code while writing the model (the stored-fields visitor is passed through while getFieldInfos() renumbers); a probe confirmed it; the exhaustive run measured it. The finder (an AI tool) then reduced it to a public-API JUnit, ran the release bracket and wrote the fix sketch.
  • Then cross-model reviews, independent verifiers, an adjudication, a history bisect, a prior-report search, a security screen and an audit (see Independent checks).

Introduced in 5.0.0 by LUCENE-6133 (2014-12-29), a stored-fields merge speed-up that skips the by-name lookup when field numbers look aligned; both commits bisected. Executed: 4.10.3 and 4.10.4 correct; the 14 releases run from 5.0.0 to 10.5.2, and main, wrong; tag containment covers the rest of that range. Not fixed upstream.

Introduced by LUCENE-6133 "improve default stored fields merge algorithm" (#7195, by @rmuir, 2014-12-29; a JIRA patch committed through SVN): trunk d249f8bc3378 and the same-day branch_5x backport 52b13f1946b5. It replaced the by-name stored-fields merge with MergeVisitor and its aligned-numbers shortcut. The reader side (renumbering in getFieldInfos(), the visitor passed through) dates from ParallelAtomicReader (LUCENE-3736, 2012) and was harmless while the merge matched by name; the only later edit to the shortcut lines is the behaviour-preserving #12116 (2023).

All 15 5.x release tags contain the backport and all 83 tags from 6.0.0 to 10.5.2 contain the trunk commit, so every release from 5.0.0 to 10.5.2 is affected. Entry points: addIndexes(CodecReader...) with SlowCodecReaderWrapper since 5.0.0 (LUCENE-6165), OneMerge.wrapForMerge since 6.2.0 (LUCENE-6766). Releases before 9.12.3 and the 4.10.x results were run by the finder and the history pass; this doc's fact check re-ran 4.10.4, 5.0.0 and 7.7.3 with the same results. Not fixed upstream: no later commit to the three files on main at search time, and no open PR changes the code.

Bug record

#

LFV-652, snapshot of 2026-10-27

Registry title
Copying a ParallelLeafReader into an index (IndexWriter.addIndexes over SlowCodecReaderWrapper, or a merge whose OneMerge.wrapForMerge returns one) silently stores a later sub-reader's stored fields under another field's name: ParallelLeafReader.storedFields() lets each sub-reader visit with its own FieldInfo numbers while getFieldInfos() renumbers the fields, and StoredFieldsWriter.MergeVisitor skips its remap-by-name step when the numbers look aligned
Area
core / index (ParallelLeafReader stored fields x StoredFieldsWriter.MergeVisitor, on addIndexes and wrapForMerge copies)
Priority
Medium, rank 101: Silent, permanent stored-field corruption that CheckIndex misses, present in every release since 5.0, but it only happens when a ParallelLeafReader is copied, which is rare.
Impact class
data corruption
Impact note
Hits applications that copy a ParallelLeafReader (or the leaves of a ParallelCompositeReader) built over two or more lockstep indexes into an index, with IndexWriter.addIndexes(SlowCodecReaderWrapper.wrap(...)) or from a custom OneMerge.wrapForMerge, when a later sub-reader has stored fields and the target numbers its fields the way the parallel reader does (for example a fresh, empty target); default IndexWriterConfig and codec, any size, with -ea and -da; the later reader's stored values are persisted under an earlier field's name (or the field drops out of the stored document), silently and permanently, CheckIndex passes, and postings, doc values, points, vectors, norms and live docs are copied correctly; a target whose numbering differs takes the remap-by-name path and gets a correct copy.
Summary
You build two indexes in lockstep, as ParallelLeafReader requires (index A stores title='Lucene in Action', index B stores price='42'), wrap them in a ParallelLeafReader, which itself returns both fields correctly, and copy it into a new index with IndexWriter.addIndexes(SlowCodecReaderWrapper.wrap(reader)), expecting the copy to hold title and price. Instead the copy holds title='Lucene in Action' and title='42' and no price field, with no error and a clean CheckIndex: storedFields() lets B report price with B's own field number 0, the parallel reader's getFieldInfos() numbers price 1, and because the target's merged numbers equal the parallel reader's, the stored-fields merge skips its remap-by-name step and writes the value under number 0, which is title. A merge whose OneMerge.wrapForMerge adds a parallel index with stored fields behind each segment goes wrong the same way (a 'summary' value stored as a second 'id').
