Payload-filtered Intervals.term reports Weight#matches for documents it does not match, so a MUST_NOT clause hides its own query's hits from highlighting

Intervals.term("dog", payloadFilter) finds the right documents, but Weight#matches claims a match in every document that contains dog, even where the filter rejected every dog. So MUST_NOT queries lose their hits' highlights and Matches-based matchers report false matches, in every release since 8.1.0.

The finding in 30 seconds

#

Intervals.term(term, payloadFilter) matches a term only where its payload passes your filter. Search results are right, but Weight#matches, the API that says where a query matched, answers "matched" for every document that contains the term at all.

Background in 3 steps

#
  1. A payload is a few bytes stored with one occurrence of a term, for example a part-of-speech tag: dog|noun or dog|verb.
  2. Intervals.term("dog", filter) matches dog only at positions whose payload passes filter. A document whose every dog is rejected does not match.
  3. Weight#matches(leaf, doc) returns where a query matched in one document, or null when the document does not match. Highlighters, the monitor module and named-clause reporting use it, and BooleanQuery builds its answer from its clauses' answers.

The finding, step by step

#
  1. Index two documents whose field f reads "big dog": in doc 0 dog carries payload noun, in doc 1 payload verb. Search IntervalQuery("f", Intervals.term("dog", payload is noun)): 1 hit, doc 0, correctly.
  2. Ask Weight#matches where that query matched in doc 1. You expect null: its javadoc says null "if the document does not match the parent query".
  3. You get a non-null Matches with 0 positions. The source hands out an iterator for every document that contains dog and applies the payload filter only later, when the iterator is read.
  4. Code that trusts it goes wrong. +f:big -<that query> correctly hits doc 1, but BooleanQuery sees its excluded clause "match" and returns no Matches for doc 1, so the default UnifiedHighlighter (offsets indexed) returns it as plain big dog. Monitor's HighlightsMatch.MATCHER reports the stored query as matching doc 1.
  5. Hits, counts, scores and explain() stay correct; only Weight#matches and what is built on it is wrong, silently, on every release from 8.1.0 (2019) to 10.6.0 and on main.

Who is affected

#

Applications that build payload-filtered interval terms in Java and read Weight#matches: the default UnifiedHighlighter (with offsets indexed), the monitor module's HighlightsMatch.MATCHER, NamedMatches, or their own code. Default settings, any index size, deterministic. No Lucene query parser builds these sources, and a public code search found no Elasticsearch, OpenSearch or Solr builder that does.

Mechanism, terms and numbers837 words

Intervals.term(String|BytesRef, Predicate<BytesRef>) builds a source that matches a term only at positions whose payload passes the filter. Searching with it is correct: the scorer applies the filter. But its matches(...) returns an iterator as soon as the document contains the term and applies the filter only inside next(). For a document where the filter rejects every position, IntervalQuery's Weight#matches therefore returns a non-null, empty Matches for a document the query does not match.

Code that reads Weight#matches trusts the non-null value. A BooleanQuery that excludes such a clause with MUST_NOT returns null Matches for its real hits, so the default UnifiedHighlighter returns them unhighlighted; Intervals.or, a required clause and a SHOULD clause with minimumShouldMatch over-report; the monitor module's HighlightsMatch.MATCHER and NamedMatches report matches that do not exist. Hits, counts, scores and explain() are correct. Every release from 8.1.0 (2019) to 10.6.0 and main is affected; only applications that use the payload-filter overload, which no Lucene query parser builds, are hit.

The mechanism (main 645d4fe14a20)

#
  1. The factory. Intervals.term(String, Predicate<BytesRef>) (Intervals.java:82-84) delegates to the BytesRef overload, which returns new PayloadFilteredTermIntervalsSource(term, payloadFilter) (:90-92).
  2. matches hands out an iterator whenever the term is in the document. matches(field, ctx, doc) (PayloadFilteredTermIntervalsSource.java:151-174) seeks the term and calls the private matches(te, doc) (:181), whose only null return is if (pe.advance(doc) != doc) { return null; } (:183-185). The iterator starts with upto = pe.freq() (:198) and applies the filter only in next(): } while (filter.test(pe.getPayload()) == false); (:202-212). If every position is rejected, the first next() returns false, but the iterator is already out.
  3. Non-null means "hit". IntervalQuery's Weight#matches returns null only when the source does (IntervalQuery.java:170-186), and MatchesUtils.forField calls the supplier "eagerly to work out if we have a hit or not", returning a Matches for any non-null iterator (MatchesUtils.java:106-117).
  4. The scorer is right. The scoring iterator applies the filter in nextInterval() (PayloadFilteredTermIntervalsSource.java:117-126) and IntervalScorer's two-phase check rejects a document with no first interval (IntervalScorer.java:80-81), so hits, counts and scores are correct.
  5. Where it spreads. BooleanWeight.matches returns null when a prohibited clause has non-null Matches (BooleanWeight.java:142-146), keeps a required clause's (:147-152) and counts a SHOULD clause's towards minimumShouldMatch (:153-162). DisjunctionIntervalsSource.matches keeps every non-null sub-iterator (DisjunctionIntervalsSource.java:86-97), and two more wrappers hand the child's iterator on unchanged: fixField (FixedFieldIntervalsSource.java:44-47) and the not* sources (notContaining, notContainedBy, nonOverlapping, notWithin) when the subtrahend is absent from the document (DifferenceIntervalsSource.java:58-61); on main, fixField(f, PF(dog)) and notContaining(PF(dog), term(cat)) give non-null Matches for the non-hit. Monitor's HighlightsMatch.MATCHER adds a match whenever Weight#matches is non-null (HighlightsMatch.java:44-62); NamedMatches names a clause whenever its Matches is non-null (NamedMatches.java:105-110). The UnifiedHighlighter uses Weight#matches by default (DEFAULT_ENABLE_WEIGHT_MATCHES = true, UnifiedHighlighter.java:110).
  6. Why conjunctions hide it. Composite sources that can drop their children's intervals check for a first interval before returning: IntervalMatches.asMatches (IntervalMatches.java:34-36; used by maxwidth/maxgaps, extend, OffsetIntervalsSource behind before/after, and the not* sources when the subtrahend is present), ConjunctionIntervalsSource.java:86-88, MinimizingConjunctionIntervalsSource.java:72-74, MinimumShouldMatchIntervalsSource.java:88-89, and core's PhraseWeight (PhraseWeight.java:115-117); on main, maxwidth(1, PF(dog)), extend(PF(dog), 0, 0) and notContaining(PF(dog), term(dog)) give null Matches for the non-hit. This leaf, the only leaf source that filters positions, can drop every position but does not check. The iterator skeleton was copied from TermIntervalsSource.matches (TermIntervalsSource.java:164-194), where laziness is safe because every position of a plain term is an interval.

Exposure and likelihood224 words
  • What goes wrong. For any document whose term occurs only with rejected payloads, the very case a payload filter exists for: false Matches for the lone source, or(), a required clause and SHOULD with minimumShouldMatch; lost Matches, and so lost highlights, for the hits of a query that excludes the source with MUST_NOT; false and missed matches in monitor's HighlightsMatch.MATCHER; a wrong clause name from NamedMatches.
  • Silent, narrow. No exception or warning. Hits, counts, scores and explain() are correct, and nothing is written to the index.
  • No special setup. Default IndexWriterConfig, codec and searcher; the plain-Java probe fails with the production default codec and no test framework.
  • Who is exposed. The payload-filter overload is opt-in and Java-only. LUCENE-8694 describes the source as "the intervals equivalent of SpanPayloadCheckQuery", and open issue #16820 proposes deprecating span queries in favour of intervals, so span-payload users may move to it.
  • Highlighter note. Without offsets in the postings, the UnifiedHighlighter re-analyses the text into a MemoryIndex without payloads, and payload-filtered interval queries then fail with a separate bug's IllegalArgumentException ("no indexed payloads") before this one shows.
  • Likelihood: rare. A visible symptom needs a Matches consumer, and the public searches found no report since the API shipped in 2019. The intervals package "contains experimental classes" (package-info.java:21), and Weight#matches is @lucene.experimental (Weight.java:76).

Why it looks unintended

#
  • Both javadocs reserve null for this case: IntervalsSource#matches when "no intervals exist in the given document", Weight#matches when "the document does not match the parent query".
  • Lucene's own oracles (CheckHits.checkMatches, the TestIntervals null check) fail on it.
  • Composite sources that can drop intervals check for a first one; this leaf, the only leaf that filters positions, does not.
The full argument261 words
  • Two javadoc contracts. IntervalsSource#matches: "Returns null if no intervals exist in the given document and field" (IntervalsSource.java:47-57). Weight#matches: "Returns Matches for a specific document, or null if the document does not match the parent query" (Weight.java:67-78). Matches#getMatches: "or null if there are no matches in that field" (Matches.java:35-37). The factory defines the source's intervals as the term's positions "filtered by the value of the term's payload at each position" (Intervals.java:78-92).
  • Older than the class. Both javadoc sentences were already in place at the introducing commit 5ca25249274.
  • Test oracles. CheckHits.MatchesAsserter asserts "Unexpected non-null Matches object in non-matching doc" (CheckHits.java:640-682), and TestIntervals.checkIntervals asserts "Expected null matches iterator on doc" (TestIntervals.java:180). Both fail on this source.
  • Siblings and scorer. Every composite source that can drop its children's intervals, and core's PhraseWeight, return null when there is no first match; pass-through wrappers (or(), fixField, the not* sources when the subtrahend is absent from the document) cannot drop intervals, hand the child's iterator on unchanged and rely on the leaf's null. This is the only leaf source that filters positions, so the only one that can drop every position, and the source's own scorer rejects the document.
  • Why tests missed it. TestPayloadFilteredInterval, the only upstream test of the class, calls matches() only on a document with accepted positions (TestPayloadFilteredInterval.java:79-87), and no other test in the tree uses the payload-filter overload. The LUCENE-8694 issue never mentions Matches, and no CHANGES entry weakens the contract.
The devil's-advocate check136 words

The strongest case for "intended": IntervalIterator says "it is possible for a document to return NO_MORE_INTERVALS on the first call to nextInterval()" (IntervalIterator.java:35-36), so empty iterators are a known state; Weight#matches and Matches are @lucene.experimental; the document does contain the term; and a lazy iterator avoids reading positions up front.

Why it fails: that note is about the approximation the scorer then filters, while IntervalsSource#matches reserves null for exactly this case; "experimental" warns about API changes, not a waived return value; MatchesUtils.forField and BooleanWeight.matches read non-null as "hit", so the empty iterator changes other queries' answers; and the eager check reads no more positions than the scorer already reads to decide the hit. Verdict: not intended, a defect (the independent reproduction, the cross-model review, the intended-behaviour check, the adjudication and the tie-break).

Suggested fix

#

Recommended Check for a first accepted position with IntervalMatches.asMatches (+6/-1)

In matches(field, ctx, doc), wrap the lazy iterator with the package's own IntervalMatches.asMatches(IntervalMatches.wrapMatches(mi, doc), mi, doc), as FilteredIntervalsSource does: it returns null when no position passes the filter. The repro, every earlier test of this bug and all 513 lucene/queries tests pass.

    IntervalMatchesIterator mi = matches(te, doc);
    if (mi == null) {
      return null;
    }
    // the payload filter is applied lazily in next(): return null if it rejects every position
    return IntervalMatches.asMatches(IntervalMatches.wrapMatches(mi, doc), mi, doc);
All options and trade-offs3 options · 594 words

Two fixes were built and run through gradle in a scratch worktree of 645d4fe14a20. Both return null from matches when the filter rejects every position and stay lazy after the first accepted position. The asMatches fix is smaller and reuses an existing idiom of the package; the look-ahead fix, the hunt's, keeps the check inside the leaf.

Check for a first accepted position with IntervalMatches.asMatches (+6/-1) (validated by the checks) (recommended)

#

In PayloadFilteredTermIntervalsSource.matches(String, LeafReaderContext, int), replace return matches(te, doc); (PayloadFilteredTermIntervalsSource.java:173) with the lines below. IntervalMatches.asMatches advances the wrapped iterator to the first interval and returns null when there is none (IntervalMatches.java:26-36); FilteredIntervalsSource.matches (FilteredIntervalsSource.java:111-125) and OffsetIntervalsSource.matches (OffsetIntervalsSource.java:137-144) use the same pair of helpers.

    IntervalMatchesIterator mi = matches(te, doc);
    if (mi == null) {
      return null;
    }
    // the payload filter is applied lazily in next(): return null if it rejects every position
    return IntervalMatches.asMatches(IntervalMatches.wrapMatches(mi, doc), mi, doc);

Trade-offs

  • Positions are now read eagerly up to the first accepted one: the same work the scorer's two-phase check does to decide the hit. For a document with only rejected positions it reads all of them, as the scorer does.
  • Two small wrapper objects per matches call: the IntervalIterator from wrapMatches and the iterator that asMatches returns (IntervalMatches.java:37, :99-100).
  • The wrapper's getQuery() still delegates to the leaf's iterator, which throws UnsupportedOperationException (a separate issue, LFV-463, that neither fix changes); IntervalQuery overrides getQuery() itself (IntervalQuery.java:179-183).

Look ahead inside the leaf's iterator (the hunt's fix, +24/-1) (validated by the checks)

#

In the private matches(te, doc), read positions until the first one whose payload passes the filter before building the iterator, return null if there is none, and let the iterator report that position first and then continue lazily. Bounded memory: an earlier draft buffered all positions, and the cross-model review's O(freq) note replaced it with this one-position look-ahead.

Trade-offs

No wrapper object and the check stays inside the leaf, but more code to review; the first position is carried in two extra fields. The same eager read as the asMatches fix.

What the checks validated

  • Gradle, the same scratch worktree: the repro passes; org.apache.lucene.queries.intervals.*: 118 tests, 0 failures; checkGoogleJavaFormat and ecjLintMain pass.
  • Earlier: the finder's, the independent reproduction's, the intended-behaviour check's, the adjudication's, the highlight and the monitor/NamedMatches tests pass with it, and so do the 117 upstream intervals tests (main ea57360912ed); the minimal repro and the tie-break tests pass with it on 645d4fe14a20.

Not recommended: make the consumers check for an empty iterator

#

For example in MatchesUtils.forField or DisjunctionIntervalsSource.matches. Not built.

Trade-offs

forField serves many queries and would have to consume the first match and replay it; fixing or() alone leaves the lone source and BooleanQuery wrong. The source is the one place that breaks the contract.

Downstream note

#

Not a Lucene security issue, but code that uses Weight#matches to decide whether a stored query matched, such as the monitor module's HighlightsMatch.MATCHER, treats a payload restriction as satisfied when it is not (executed on main).

How it was found

#

A hunt over the intervals query builders cross-checks Weight#matches against the scorer's hits. Its harnesses do not cover payload filters, so an AI tool applied the check by hand in a small probe, saw Matches for a non-hit and none for a MUST_NOT hit, and wrote a public-API JUnit. Testing, not model checking.

Low, rank 881: The same rarely used overload reports Matches for documents whose payloads are all rejected, so MUST_NOT hits lose their highlights and monitor's HighlightsMatch matcher reports false matches, but hits, counts and scores stay correct.
Impact class
silent wrong results
Impact note
Only applications that call the payload-filter overload Intervals.term(String|BytesRef, Predicate<BytesRef>) (no Lucene query parser and, by public code search, no Elasticsearch, OpenSearch or Solr builder uses it) and that read Weight#matches are hit, with the default IndexWriterConfig, codec and searcher, -ea and -da, at any index size and in every release since 8.1.0: for a document in which the term occurs only with payloads the filter rejects, the source alone or inside Intervals.or reports Matches although the document is not a hit, a BooleanQuery that excludes it with MUST_NOT returns null Matches for such hits (so the UnifiedHighlighter in its default WEIGHT_MATCHES mode returns them unhighlighted when offsets are in the postings; executed on 9.12.3, 10.5.2 and main), a SHOULD clause of this kind counts towards minimumShouldMatch in Weight#matches, and Lucene monitor's HighlightsMatch.MATCHER and NamedMatches report matches the query does not have (executed); search hits, counts, scores and explain() are correct, conjunction-style wrappers (ordered, unordered, maxwidth, containing) hide the defect, and nothing is written to the index.
Summary
You index text with payloads, for example 'big|adj dog|noun' (doc 0) and 'big|adj dog|verb' (doc 1) through DelimitedPayloadTokenFilter, and query IntervalQuery(f, Intervals.term("dog", payload is 'noun')), which correctly hits only doc 0. You expect Weight#matches to be null for doc 1, which the query does not match, and non-null for doc 1 as a hit of +f:big -<that query>. Instead the payload-filtered source returns an empty but non-null MatchesIterator for every document that contains 'dog' at all, so Weight#matches reports a match for the non-hit and the BooleanQuery returns null Matches for its real hit (the default UnifiedHighlighter then leaves that hit unhighlighted, and Lucene monitor's HighlightsMatch matcher reports the non-hit as a match), while hits, counts and scores stay correct.
