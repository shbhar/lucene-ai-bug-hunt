XYPointField.newDistanceQuery and XYDocValuesField.newSlowDistanceQuery document radius 0 as legal, but reject it

The two Cartesian (x/y) point distance-query factories say the radius "must be non-negative and finite", but a radius of 0 throws IllegalArgumentException: radius must be bigger than 0, got 0.0. The rejection is intended; the javadoc is wrong and should say "positive".

The finding in 30 seconds

#

Two public factories document a radius range that includes 0, then build an XYCircle, whose constructor accepts only radius > 0. The lat/lon twins with the same words accept 0.

  1. You index points with XYPointField and want the documents exactly at (1, 2), so you call XYPointField.newDistanceQuery("p", 1f, 2f, 0f). The javadoc says the radius "must be non-negative and finite", and 0 is both.
  2. You expect a query that matches the points at the centre, as LatLonPoint.newDistanceQuery does for a radius of 0 under the same wording.
  3. You get IllegalArgumentException: radius must be bigger than 0, got 0.0 before anything is searched, with assertions on and off. XYDocValuesField.newSlowDistanceQuery("p", 1f, 2f, 0f) does the same.
  4. Both factories hand the radius to new XYCircle(x, y, radius), which accepts only radius > 0. The maintainer who wrote XYCircle calls radius 0 "not allowed", so the code is right and the two javadoc lines are wrong.

Who is affected

#

Applications that build Cartesian distance queries with either factory and can pass exactly 0, such as a tolerance computed as 0 or a user's "within 0". They get an exception instead of a query; no wrong hits, no index change. Default configuration, any index size, every release since 8.5.0. Lucene's own random tests hit it repeatedly.

Mechanism, terms and numbers383 words

XYPointField.newDistanceQuery(field, x, y, radius) and XYDocValuesField.newSlowDistanceQuery(field, x, y, radius) find points within a distance of a centre in flat x/y space. Both document @param radius ...: must be non-negative and finite and promise an IllegalArgumentException only if the radius "is invalid" (XYPointField.java:171-175, XYDocValuesField.java:176-180).

A radius of 0 is non-negative and finite, yet both throw IllegalArgumentException: radius must be bigger than 0, got 0.0 at query construction, because both pass the radius to new XYCircle(x, y, radius) (:178, :183), whose constructor rejects radius <= 0 (XYCircle.java:45-46). The lat/lon twins LatLonPoint.newDistanceQuery and LatLonDocValuesField.newSlowDistanceQuery carry the same wording and accept 0.

The rejection is deliberate: XYCircle has rejected 0 since it was added (LUCENE-8707, 2020), its author calls radius 0 "not allowed" (#10898, #11346), and Lucene's random XY test generators were changed three times to skip it. The factories' javadoc was copied two days later from LatLonPoint, where 0 is legal (LUCENE-9238, first released in 8.5.0). So this is a documentation defect: the fix is "must be positive and finite" in two javadoc lines.

What happens

#

XYPointField.newDistanceQuery("p", 1f, 2f, 0f) throws at XYCircle.<init>(XYCircle.java:46) from XYPointField.newDistanceQuery(XYPointField.java:178); XYDocValuesField.newSlowDistanceQuery("p", 1f, 2f, 0f) throws at the same line from XYDocValuesField.java:183. No query is built, nothing is searched and the index is not touched. A lat/lon query with radius 0 counts the point at the centre.

Exposure and likelihood173 words
  • Who: users of the Cartesian (x/y) point API who pass a radius of exactly 0 to XYPointField.newDistanceQuery or XYDocValuesField.newSlowDistanceQuery, trusting the documented range.
  • What happens: an IllegalArgumentException at query construction instead of a query for the points at the centre. Nothing wrong is returned and nothing changes in the index. Code that treats IllegalArgumentException as "invalid input" reports a valid input as invalid.
  • Reach: default IndexWriterConfig, codec and searcher; any index size, since the throw happens before the index is used. No outside report was found. Elasticsearch builds an XYCircle and queries through newGeometryQuery; OpenSearch's geospatial plugin calls both factories, but only with the radius of an XYCircle it has already built, so a radius of 0 fails there before the factories run (downstream code read).
  • In practice: Lucene's own random XY tests produced radius 0, and their generators were changed three times to skip it (93809ac361c in 2020, #537 in 2021, #15315 in 2025).
  • How long: every release from 8.5.0 to 10.6.0 and main. Not new in 10.6.

Why it looks unintended

#
  • The @param range "must be non-negative and finite" includes 0, on two public classes that are not experimental; nothing narrows it.
  • The words were copied from LatLonPoint, where 0 is legal and still works; XYCircle has always rejected 0.
  • The rejection is intended (radius 0 "is not allowed", #10898, #11346), so the javadoc, not the code, is wrong.
The full argument202 words
  • Contract. XYPointField.java:171-172 and XYDocValuesField.java:176-177: "must be non-negative and finite". The @throws ... radius is invalid line names no other limit, so the @param range is the only stated test of a valid radius. Neither class is @lucene.experimental; no javadoc, package doc, CHANGES or MIGRATE entry narrows the range.
  • Origin. 88dd1c3f3d4 (LUCENE-9238, apache/lucene-solr#1272, iverase, 2020-02-21; its description reads "Adaptation of LatLonPoint to generic cartesian space") added both factories with the @param copied from LatLonPoint.newDistanceQuery, whose LatLonPointDistanceQuery then rejected only radiusMeters < 0. XYCircle with radius <= 0 had come two days earlier in d48bafb2999 (LUCENE-8707, apache/lucene-solr#587).
  • The twins split later. 8bfbed8d4cd (LUCENE-9552, 2020-11-03) moved the lat/lon doc-values factory onto geo.Circle and relaxed Circle from <= 0 to < 0, keeping the lat/lon contract; the XY counterpart 5c027379186 (LUCENE-9553, the same day) left XYCircle unchanged.
  • Intent. The author of XYCircle wrote "It seems we are trying to create distance queries with radius = 0 which is not allowed" (iverase, #10898) and "the test can produce circles with radius 0 which is not allowed" (#11346). Each failure was fixed in the test generator (93809ac361c, #537, #15315); TestXYCircle.java:81 says "radius must be positive". None of these mentions the javadoc.
The devil's-advocate check127 words

The strongest not-a-bug case: the rejection is deliberate, loud, immediate and clearly worded; a radius-0 circle is degenerate; @throws ... radius is invalid leaves room for what "invalid" means; and XYCircle is @lucene.experimental.

Why it fails: all of this defends the behaviour, which nobody disputes, not the text. An explicit @param ... non-negative range includes 0, and the lat/lon twins with identical words accept 0, so a reader cannot learn from the documentation that 0 is refused. The three executed reviews by a model from another family (OpenAI GPT-5.6) rated this argument strong (two) or moderate (one) for the behaviour, found the bug real, and point to the javadoc fix. Verdict: a documentation defect; fix the javadoc. A maintainer may still call it a doc nit.

Downstream note

#

Services that pass a user-entered radius straight to these factories should reject or map 0 themselves; with the current code a "within 0" request surfaces as an IllegalArgumentException.

How it was found

#

Semi-formal: a proof-obligation check of the radius range the two factories document against the argument checks of the XYCircle they build showed that radius 0 meets the documented range but fails the check. A public-API JUnit test on main witnessed it, and independent checks reproduced it with their own tests.

The method in full81 words
  • Obligation: every radius the factories document as legal (non-negative and finite) must pass the checks of the XYCircle they construct.
  • Check: XYCircle's constructor rejects radius <= 0, so the documented value 0 fails the obligation for both factories; the lat/lon twins' checks (< 0) meet the same wording.
  • Witness: a JUnit test on main f794ff5a505c that builds each factory's query with radius 0 fails with assertions on and off.
  • Tier: semi-formal (a proof-obligation check plus executed tests).
