MemoryIndex drops the final position increment between the values of a multi-valued field, so phrase queries disagree with IndexWriter

When a field has several values and one ends in a removed stop word, MemoryIndex forgets the hole, so later values sit one position lower than with IndexWriter and phrases across values match or miss differently. Lucene Monitor inherits it: a document can match alone but not in a batch.

The bug in 30 seconds

#

When a field has several values, IndexWriter starts each value after the hole left by words removed at the end of the previous one. MemoryIndex starts it right after the last kept word, so every later value sits lower.

  1. You index one document whose field body has two values, quick the and fox, with an analyzer that removes the stop word the (the stock EnglishAnalyzer does; default gap 0): once with IndexWriter, once with MemoryIndex.fromDocument.
  2. You expect the same positions. IndexWriter keeps the hole the removed the leaves: quick 0, fox 2, so the phrase "quick fox" gets 0 hits, as for the single value quick the fox.
  3. Instead MemoryIndex puts fox at 1 and "quick fox" gets 1 hit. The analyzer reports the hole when the value ends (TokenStream#end()); MemoryIndex never reads it before starting the next value.
  4. It also misses: on the input of Lucene's own testStopwordsPosIncHole, just a + test of gaps, the phrase "just ? test" gets 1 hit on IndexWriter and 0 on MemoryIndex.
  5. Lucene Monitor matches a single document through MemoryIndex and a batch through IndexWriter: the stored query "quick fox" matches this document alone (1) but not in a batch of two (0).

Who is affected

#

Anyone who matches documents with multi-valued text fields through MemoryIndex, directly or through Lucene Monitor's single-document match, with an analyzer that removes words (any stop filter, for example EnglishAnalyzer), and uses phrase, sloppy-phrase or span queries across value boundaries. Default settings, one document is enough, since 4.5.0. At a large gap such as 100 most exact phrases are unaffected.

Mechanism, terms and numbers770 words

When a document's analyzed text field has several values, IndexWriter starts each value after the previous value's final position increment, the one TokenStream#end() reports; a stop filter puts the positions of the words it removed at the end of a value there. MemoryIndex.storeTerms never reads it: it starts the next value at "last token position + gap". So after a value that ends in a removed word, every later value sits lower than in a one-document IndexWriter index of the same document, and phrase, sloppy-phrase and span queries that cross the value boundary give different answers, in both directions: [quick the | fox] matches "quick fox" only on MemoryIndex, and the input of upstream's testStopwordsPosIncHole matches "just ? test" only on IndexWriter. A second, smaller inconsistency: MemoryIndex skips the position and offset gaps after leading values that produce no tokens. Lucene Monitor matches a single document through MemoryIndex and a batch through IndexWriter, so the same stored phrase query matches a document alone but not in a batch. A divergence since 4.5.0 (the gap part since 4.1.0); default settings, and one document is enough. A fix that carries IndexingChain's accounting into storeTerms passes the repro and the memory, monitor and highlighter suites.

Terms

#
  • Multi-valued field: a document with several fields of the same name, for example two TextField("body", ...). Each value is analyzed on its own; positions and offsets continue from one value to the next.
  • Position hole: a stop filter removes the from quick the fox but keeps its position, so fox is at 2, not 1. A phrase "quick fox" therefore does not match. When the removed word is the last word of a value, the filter reports the hole when the value ends, as the final position increment of TokenStream#end().
  • Gaps: Analyzer#getPositionIncrementGap (default 0) and #getOffsetGap (default 1) are added between values. At gap 0 the values behave like one long value (the analysis package docs: "treat all these sections as one large section").
  • MemoryIndex: a one-document, in-memory index, documented as a substitute for a RAM-resident Directory. Lucene Monitor stores queries and matches incoming documents; it indexes a single document into a MemoryIndex and a batch into an IndexWriter.

The bug

#
  1. A FilteringTokenFilter (StopFilter, LengthFilter, ...) adds the positions of tokens removed after the last kept one to the position increment it reports in end() (FilteringTokenFilter.java:72-75; TokenStream#end javadoc, TokenStream.java:152-154).
  2. IndexWriter uses it: after stream.end() (IndexingChain.java:2105) it adds that increment and the final offset (:2109-2110), then the gaps for every analyzed value, with or without tokens (:2121-2124).
  3. MemoryIndex.storeTerms does not: it starts a value at lastPosition + positionIncrementGap and lastOffset + offsetGap, and only once the field has produced a token (info.numTokens > 0, MemoryIndex.java:994-999); after stream.end() it records the last kept token's position (:1045-1049). The increment end() reported is never read.
  4. After a value that ends in removed words, later values are lower by the size of that hole; after each leading value with no tokens, lower by the gap plus its hole, and their offsets by that value's final offset plus the offset gap. Positions stay in order, so only distances across a boundary and absolute positions change. Term queries and Boolean queries made only of term clauses gave the same hit counts in 108,000 random checks per run (executed); a Boolean query with a phrase clause inherits the phrase difference.
  5. Monitor: DocumentBatch.of sends one document to a MemoryIndex and two or more to an IndexWriter (DocumentBatch.java:55-63, :66-93, :101-114), so its results depend on the batch size.

Exposure and likelihood319 words
  • Who. Users of MemoryIndex.fromDocument, repeated addField calls or Lucene Monitor's single-document match, with multi-valued analyzed text fields and an analyzer that removes tokens: any stop filter (the stock EnglishAnalyzer has one by default; StandardAnalyzer only when given a stop set), a LengthFilter, or a custom FilteringTokenFilter. The gap part needs only an empty or all-stop-word leading value and a positive gap.
  • Effect. Silent wrong match decisions for position-sensitive queries across a value boundary, in both directions (a false positive and a false negative, both executed), plus wrong positions, offsets and term-vector positions read from the MemoryIndex reader. No exception or crash in any run, and nothing is persisted; the effect stays within the document. Default scores are not affected; a custom Similarity that reads FieldInvertState#getPosition() could score differently, because MemoryIndex passes the last kept token's position (MemoryIndex.java:1380-1393) and IndexWriter the position after the last end() and gap (read in the code, not run).
  • Monitor. A document's result depends on whether it is matched alone (MemoryIndex) or in a batch (IndexWriter): 1 match alone, 0 in a batch of two. Monitor documents no such difference.
  • Default vs opt-in. Default MemoryIndex settings, the default Analyzer gaps (0 and 1) and stock analysis components; no opt-in feature.
  • Limits. With a large gap such as 100 most exact-phrase results are unchanged, because the shift is only the size of the hole; sloppy phrases with slop near the gap and absolute-position queries still can differ (executed: "alpha omega"~100 on alpha the + omega). Offsets differ only after leading tokenless values. No report was found in the 13 years since 4.5.0.
  • Scale. Needs no scale: one document triggers it, deterministically, every time the shape occurs.
  • Not affected in-tree: the highlighters build their MemoryIndex from one combined stream per field; the UnifiedHighlighter's MultiValueTokenStream adds end()'s increment and the gap itself (read in the code).

Why it is a bug, not intended

#
  • LUCENE-3849, a 4.5.0 bug fix, made IndexWriter keep this trailing hole between values; its test testStopwordsPosIncHole fails on MemoryIndex.
  • MemoryIndex is documented as a substitute for a RAM-resident directory, and addField as equivalent to adding a field.
  • MemoryIndex disagrees with itself: one value quick the fox puts fox at 2, two values at gap 0 put it at 1.
The full argument348 words
  • The contract. TokenStream#end (TokenStream.java:152-154): "any skipped positions (such as those removed by a stopfilter) can be applied to the position increment". LUCENE-3849 (#4922), a 4.5.0 Bug Fixes entry ("TokenStreams now set the position increment in end(), so we can handle trailing holes", CHANGES.txt:13337), made IndexWriter use it for exactly this multi-valued case; in that issue a committer wrote: “The "bug" is if a field instance ends with a stopword, that accumulated 'hole' is lost.” TestIndexWriter#testStopwordsPosIncHole (TestIndexWriter.java:1899-1927) asserts it, and its input fails on MemoryIndex.
  • MemoryIndex is documented and tested as an IndexWriter substitute. Class javadoc: "a replacement/substitute for RAM-resident Directory implementations" (MemoryIndex.java:106); addField: "Equivalent to adding a tokenized, indexed ... Field" (:683-684, :697-698, :713-714), with gaps "if fields with the same name are added more than once" (:722-724). TestMemoryIndexAgainstDirectory "Verifies that Lucene MemoryIndex and RAM-resident Directory have the same behavior" (:96-97) and already compares a two-valued field's term vectors with IndexWriter (:713-753), for values without holes. With the precedents this sets a strong expectation of equal query results, not a formal promise of identical postings.
  • Precedents. LUCENE-4880 ("Fix MemoryIndex to consume empty terms ... consistent with IndexWriter") and LUCENE-5444 ("offsets were corrupted if multiple fields with the same name were added", the same multi-value code) fixed earlier differences.
  • Self-disagreement. At gap 0, quick the fox as one value puts fox at 2, split into quick the + fox at 1; the quick puts quick at 1, the + quick at 0 (executed). The analysis package docs say values at the default gap are treated "as one large section".
  • History: an omission. Multi-value support came with LUCENE-4515 (4.1.0), nine months before LUCENE-3849, which changed 30 files and not lucene/memory. Executed: both sides agree on 4.1.0-4.4.0 and differ from 4.5.0.
  • Legal trigger. Public API, a stock StopFilter, the default gap; IndexWriter accepts the same document.
  • Monitor swaps MemoryIndex in for IndexWriter purely by batch size, for speed ("MemoryIndex benchmarks as better performing than RAMDirectory for this case", DocumentBatch.java:101-102).
The devil's-advocate check366 words

The strongest case for "intended": Analyzer#getPositionIncrementGap is "Invoked before indexing a IndexableField instance if terms have already been added to that field" and #getOffsetGap "is only called if the field produced at least one token for indexing" (Analyzer.java:297-323). MemoryIndex's numTokens > 0 guard matches that text word for word, so the leading-tokenless part could be called documented; and "replacement/substitute" describes a purpose, not identical postings. Weaker points a reviewer may raise: TokenStream#end says skipped positions "can be applied", not that every consumer must apply them; the addField(String, TokenStream, int, int) overload lets the caller choose the gaps; MemoryIndex already differs from IndexWriter in accepted ways (it keeps freqs and positions and returns term vectors for every indexed field, TestMemoryIndex#testKeywordWithoutTokenStream, #testFieldsOnlyReturnsIndexedFields); positions that have held since 4.5.0 would change; and at a gap of 100 the practical effect is small.

Why it fails: those javadocs say nothing about end()'s increment, so they do not cover the headline at all. For the gap part they are stale: IndexWriter has applied the gaps after empty values since LUCENE-2529 / LUCENE-2668 (3.1.0, CHANGES.txt:17578), and TestIndexWriter#testPositionIncrementGapEmptyField (:768-800) expects position 100 after an empty first value at gap 100. The guard descends from the comment "ensure infos.numTokens > 0 invariant; needed for correct operation of terms()" in MemoryIndex's original 2005 contribution (8f9e2a15e78); LUCENE-4515 left it as unchanged context and only made its new carry branch depend on it, and LUCENE-7091 kept it so that doc-values-only additions add no gap: no change was a decision about gaps. On the weaker points: IndexWriter has applied end()'s increment since LUCENE-3849 and its test asserts it, so "can" is not an opt-out for an index documented as a substitute for it; caller-chosen gaps do not help, because end()'s increment is ignored whatever gap is passed; the accepted differences add information IndexWriter does not keep rather than changing positions it does keep; the behaviour change belongs in a CHANGES entry. Verdict: not intended; high confidence for the headline, medium for the gap part. File the gap part as a secondary consistency fix and correct the two Analyzer javadocs in the same change.

Suggested fix

#

Recommended Carry IndexingChain's position and offset accounting in storeTerms (validated)

Carry IndexingChain's accounting in MemoryIndex.storeTerms: start each value after the previous value's end() position increment and final offset, plus the gaps after every tokenized value (+36/-15). With it the repro passes with assertions on and off and over 10 iterations, and the memory, monitor and highlighter suites and the lint, format and javadoc checks pass.

int pos = info.nextValuePosition;   // was: -1, or lastPosition + gap if numTokens > 0
int offset = info.nextValueOffset;  // was: 0, or lastOffset + offsetGap if numTokens > 0
// ... tokens as before; then, after stream.end():
int next = pos + posIncrAttribute.getPositionIncrement();
int nextOffset = offset + offsetAtt.endOffset();
if (applyGaps) {
  next += positionIncrementGap;
  nextOffset += offsetGap;
}
info.nextValuePosition = next;
info.nextValueOffset = nextOffset;

Trade-offs

  • One more int per field (three instead of two); no extra work per token. No benchmark was run.
  • Behaviour change by design: later values of multi-valued fields move to IndexWriter's positions, so stored Monitor or percolator phrase rules can match differently after an upgrade.
  • The keyword-term path (storeTerm, fake positions from lastPosition++) is untouched, but it does not update the new carry: a token-stream value after a binary-term value (reachable only through a custom IndexableField whose tokenStream() returns null) now starts from the carried value position (or -1), not from lastPosition + gap (read in the code, not tested).
  • Norms still get the last kept token's position (unchanged); only a custom Similarity that reads FieldInvertState#getPosition() would notice.

How it was found

#

A bounded-exhaustive comparison ran the real MemoryIndex against a one-document IndexWriter index on 177,544 small cases (ordered pairs of short canned token streams with modelled holes and gaps, plus 40 single values) through the public reader and query APIs. Position, offset and phrase-match mismatches appeared and vanished with the fix; JUnit tests on the stock jar confirmed it.

The method in full184 words

Method: bounded-exhaustive translation validation on the real jar (semi-formal tier), in a hunt unit on MemoryIndex equivalence.

  • Scope: every pair of canned token streams of up to 2 tokens over {a, b}, with position increments {0, 1, 2} and a final position increment {0, 1}, times 3 index options, norms on or off, offsets on or off, and position gap {0, 3}: 177,504 two-value cases plus 40 single-value cases (177,544), each indexed into a one-document IndexWriter index and a MemoryIndex and compared through the public LeafReader and a fixed query set.
  • Result on main: 56,448 position, 832 offset, 41,664 term-vector position, 19,232 query-match and 26,928 query-score mismatches; 0 of each with the fix shadowed in (two unrelated classes stay unchanged). A random baseline with real analyzers (3,000 documents) found 2,553 position, 1,430 offset and 39 query-match mismatches, 0 with the fix.
  • Then public-API JUnit tests on the stock jar, each asserting the IndexWriter value first. Found 2026-10-26 on main ea57360912ed; then checked by an independent reproducer, an intended-behaviour devil's advocate, reading-only reviews by a model from another family (OpenAI GPT-5.6) and an adjudication.

Bug record

#

LFV-340, snapshot of 2026-10-29

Registry title
MemoryIndex drops the final position increment of each value of a multi-valued field (and the gaps after leading values with no tokens), so phrase and other position queries disagree with IndexWriter, including Lucene Monitor's single-document matching
Area
memory / MemoryIndex term inversion (multi-valued analyzed fields: positions and offsets carried from one value to the next); reached in-tree through monitor single-document batches
Priority
Medium, rank 291: MemoryIndex silently drops the final position increment between values, so phrase results differ from IndexWriter, including in Monitor's single-document path, but it needs a multi-valued field, stop-word removal and a small gap, so it sits with its MemoryIndex sibling LFV-333.
Impact class
silent wrong results
Impact note
Anyone who puts a document with a multi-valued analyzed text field into a MemoryIndex (directly through fromDocument or repeated addField calls, or through Lucene Monitor's single-document matching) with an analyzer that removes tokens (a stop filter, as in the stock EnglishAnalyzer, or a length filter) gets lower positions than IndexWriter gives the same document for every value that follows a value ending in a removed token, and, when the field has a position gap above 0, for the values after leading values with no tokens (offsets differ only in that second case), so phrase, sloppy-phrase and span queries that cross a value boundary or depend on absolute positions match or miss differently (executed: a false positive and a false negative at Lucene's default gap 0, and Monitor matching a document alone but not in a batch); with a large gap such as 100 most exact-phrase results do not change; default MemoryIndex settings and stock analysis components, any scale, every release since 4.5.0 (since 4.1.0 for the leading-tokenless-value part).
Summary
You add a document whose text field has two values, 'quick the' and 'fox', to a MemoryIndex with an analyzer that removes the stop word 'the', and expect the positions of a one-document IndexWriter index: IndexWriter keeps the hole the removed trailing 'the' leaves (TokenStream.end() reports it as a final position increment), so 'fox' is at position 2 and the phrase "quick fox" does not match. MemoryIndex.storeTerms never adds that final increment, puts 'fox' at position 1 and matches the phrase; the reverse also happens (the input of upstream's TestIndexWriter#testStopwordsPosIncHole matches a phrase on IndexWriter but not on MemoryIndex), and values that produce no tokens before the first token skip the position and offset gaps ([the | quick fox] with gap 100: IndexWriter quick at position 101, offsets 4-9; MemoryIndex position 0, offsets 0-5). Lucene Monitor inherits it: a stored phrase query matches the document when it is matched alone (MemoryIndex path) but not when the same document is in a two-document batch (IndexWriter path).
