LeafCollector's javadoc example does not compile: no scoreMode(), and setScorer(Scorer) instead of setScorer(Scorable)

The only code example in the LeafCollector javadoc has not compiled since 5.1.0: javac reports a missing scoreMode() and a setScorer(Scorer) that does not implement setScorer(Scorable). Documentation only; with those two mismatches fixed, it works as described.

The finding in 30 seconds

#

A javadoc example that teaches doc-ID re-basing in a custom Collector cannot compile against the two interfaces it implements.

Background: Collector and LeafCollector

#
  1. A Collector receives the hits of a search. IndexSearcher asks its scoreMode() whether scores are needed, then, for each index segment, asks getLeafCollector(LeafReaderContext) for a LeafCollector.
  2. The LeafCollector is handed the segment's scorer through setScorer(Scorable) and then gets collect(int doc) for every hit. doc is relative to the segment; adding the segment's docBase gives the index-wide doc ID.

The finding, step by step

#
  1. You want to write your own Collector, and you copy the 21-line example from the LeafCollector class javadoc: an anonymous Collector whose LeafCollector calls bits.set(docBase + doc) to turn each segment's local doc IDs into index-wide ones.
  2. You expect it to compile and, on an index of 3 segments with 2, 3 and 1 documents where local docs 0 | 1, 2 | 0 match, to set bits {0, 3, 4, 5}: docBase 0, 2 and 5 plus the local IDs.
  3. Instead javac reports 2 errors, on main, 10.6.0, 10.5.2 and 9.12.3: the anonymous Collector "does not override abstract method scoreMode()", and the anonymous LeafCollector "does not override abstract method setScorer(org.apache.lucene.search.Scorable)".
  4. Why: Collector.scoreMode() is abstract (since 8.0.0; from 5.1.0 to 7.x it was needsScores()), and since 8.0.0 setScorer takes a Scorable, so the example's setScorer(Scorer) is only an overload. Neither change updated the example, which compiled on 5.0.0.
  5. Fix: add scoreMode() returning ScoreMode.COMPLETE_NO_SCORES and take a Scorable. The corrected example compiles and collects exactly {0, 3, 4, 5}.

Who is affected

#

Developers who implement Collector directly (an Expert, @lucene.experimental API) and start from this example, the only one in the LeafCollector javadoc, on any release from 5.1.0 to 10.6.0 or main. Nothing wrong ever runs: javac refuses the code and names the missing pieces. Low impact, but plainly wrong.

Mechanism, terms and numbers469 words

The LeafCollector class javadoc explains that collect(int) receives segment-relative doc IDs and shows "a simple example showing how to collect docIDs into a BitSet" (LeafCollector.java:30-57 on main 645d4fe14a20). Copied into code, it does not compile on any release since 5.1.0: the anonymous Collector lacks the abstract scoreMode() (Collector.java:56; needsScores() from 5.1.0 to 7.x), and the anonymous LeafCollector declares setScorer(Scorer) (:46) where the interface, a few lines below, declares setScorer(Scorable) (:71), so the example's method is only an overload. The example compiled when it was written for 5.0.0; LUCENE-6218 (5.1.0), LUCENE-4100 and LUCENE-6228 (both 8.0.0) changed the API and did not update it. Adding scoreMode() returning ScoreMode.COMPLETE_NO_SCORES and taking a Scorable makes it compile, and the corrected example collects exactly the expected global doc IDs. No runtime code is wrong.

The example (main 645d4fe14a20, LeafCollector.java:36-56)

#
IndexSearcher searcher = new IndexSearcher(indexReader);
final BitSet bits = new BitSet(indexReader.maxDoc());
searcher.search(query, new Collector() {

  public LeafCollector getLeafCollector(LeafReaderContext context)
      throws IOException {
    final int docBase = context.docBase;
    return new LeafCollector() {

      // ignore scorer
      public void setScorer(Scorer scorer) throws IOException {
      }

      public void collect(int doc) throws IOException {
        bits.set(docBase + doc);
      }

    };
  }

});

The two mismatches

#
  1. No scoreMode(). The anonymous Collector implements only getLeafCollector (:40-54). Collector.java:56 declares ScoreMode scoreMode(); with no default (only setWeight has one, :63), so javac reports <anonymous Example$1> is not abstract and does not override abstract method scoreMode() in org.apache.lucene.search.Collector at searcher.search(query, new Collector() { (:38).
  2. setScorer(Scorer) is an overload, not an override. The interface declares void setScorer(Scorable scorer) (:71). Scorer extends Scorable (Scorer.java:28), and a method with a narrower parameter type does not implement it, so javac reports <anonymous Example$1$1> is not abstract and does not override abstract method setScorer(org.apache.lucene.search.Scorable) in org.apache.lucene.search.LeafCollector at return new LeafCollector() { (:43). The other interface methods have defaults, and collect(int) is implemented.

The rest is valid: context.docBase is a public field (LeafReaderContext.java:28), and the deprecated IndexSearcher.search(Query, Collector) (IndexSearcher.java:634-638) still exists and only adds a deprecation note. indexReader and query are illustrative free names and not part of the claim.

Why the build never noticed

#

The build's javadoc checks do not compile the code in this <pre> block. On main, the example's line 46 is the only setScorer(Scorer left in any .java file under lucene/, and the open issue #9534 (LUCENE-8488) asks for such a compile check in general.

Adjacent stale text (same javadoc, not separate bugs)

#
  • :31-32 "recording the docBase from the most recent setNextReader call": that method no longer exists; the example itself correctly reads context.docBase in getLeafCollector.
  • :26 "hold onto the passed {@link Scorer} instance, and call {@link Scorer#score()}" and :68 "save the passed-in Scorer": the parameter is a Scorable.
Exposure and likelihood167 words
  • Who is hit. Anyone who writes a custom Collector from this example. It is the one worked example of doc-ID re-basing in the collector docs. Collector is marked Expert and both interfaces are @lucene.experimental (Collector.java:23, :44; LeafCollector.java:62), and the Collector javadoc steers most users to SimpleCollector or the built-in collectors (Collector.java:26-28).
  • Default vs opt-in. Not a configuration matter: every copy fails. javac fails on each release compiled (5.1.0, 7.7.3, 8.0.0, 9.12.3, 10.5.2, 10.6.0, branch_10x and main), and a class-file scan finds the needed API members missing in all 109 builds from 5.1.0 to main.
  • Scale. One example, 2 compile errors. LUCENE-9129 (#10170) shows a user hitting the same scoreMode() javac error in their own collector after upgrading from 7.x to 8.x, so the API change did trip up at least one user, although that report does not name the example.
  • What it does not do. No wrong results, no runtime path, no index change. MIGRATE.md documents the Scorable change (lucene/MIGRATE.md:1474).

Why it looks unintended

#
  • The same file contradicts it: the example's setScorer(Scorer) sits 25 lines above the interface's setScorer(Scorable), and Collector.scoreMode() is abstract. The javadoc calls it "a simple example".
  • It compiled on 5.0.0, and maintainers updated this example on earlier API changes (2009, 2012, 2015).
  • The API changes were deliberate (the scoreMode() switch was listed only as an optimization); none updated the example.
The full argument168 words
  • Contract text. LeafCollector.java:32-33: "Here's a simple example showing how to collect docIDs into a BitSet:". :71: void setScorer(Scorable scorer) throws IOException;. Collector.java:55-56: "Indicates what features are required from the scorer." ScoreMode scoreMode(); (abstract).
  • History. LUCENE-5527 (85642f59ddf, 2014) moved the example into LeafCollector; it compiles on 5.0.0 (executed). Earlier maintenance of the same example: 5f611724642 (2009, "The example impl in Collector missed the new method acceptsDocsOutOfOrder, added"), 647b5091697 (2012, "fix out of date api usage"), 927827a215a (2015, LUCENE-6179, removed acceptsDocsOutOfOrder()).
  • API changes that skipped it. CHANGES.txt: "LUCENE-6218, LUCENE-6220: Add Collector.needsScores()" (lucene/CHANGES.txt:11080); MIGRATE.md: "LeafCollector.setScorer() now takes a Scorable rather than a Scorer (LUCENE-6228)" (lucene/MIGRATE.md:1474). The switch from needsScores() to scoreMode() (LUCENE-4100) has no MIGRATE entry and was listed only under "Optimizations" in the 8.0.0 CHANGES (as Tomoko Uchida pointed out on #10170). LUCENE-6228 (910a0231f6f) edited this very file and left the example.
  • Tests. No test compiles javadoc examples; #9534 (LUCENE-8488, open) asks for that in general.
The devil's-advocate check146 words

Strongest case for "intended" (verifiers built it): Collector is Expert and @lucene.experimental and points users to SimpleCollector; the snippet is a sketch (the free names indexReader and query); its entry point search(Query, Collector) is deprecated and slated for removal in 11.0 (#12892, listed in #16918; PR #16805 open); the errors are loud, CHANGES.txt lists the needsScores() addition and MIGRATE.md the Scorable change; the build does not compile javadoc <pre> blocks.

Why it fails: experimental status explains why the API changed, not why the same-version docs contradict the interface declared below them. The free names are context, while both errors are about missing API members. The deprecated call still compiles on every release. Maintainers updated this very example on earlier API moves. Every verifier and the adjudication rejected the "intended" reading; an impact audit passed it as a structurally wrong API example, not a typo.

LFV-1018, snapshot of 2026-11-02

Registry title
LeafCollector's class javadoc example ('collect docIDs into a BitSet') does not compile on any release since 5.1.0: its anonymous Collector has no scoreMode() (the abstract needsScores() before 8.0.0) and its setScorer(Scorer) does not implement LeafCollector.setScorer(Scorable) (documentation defect)
Area
core / search (LeafCollector class javadoc example)
Priority
Low, rank 972: The core LeafCollector class javadoc example, the usual starting point for custom Collectors, fails loudly at compile time on every release since 5.1.0 with no runtime effect.
Impact class
minor
Impact note
Documentation only, with no runtime effect: a developer who writes a custom Collector (an extension point the Collector javadoc labels Expert, @lucene.experimental) and starts from the only code example in the LeafCollector class javadoc gets two compile errors on every release since 8.0.0 (one since 5.1.0) and has to find scoreMode() and Scorable in the interfaces or in MIGRATE.md; no configuration, scale or special input is involved.
Summary
The LeafCollector class javadoc explains that collect() receives segment-relative doc IDs and shows 'a simple example showing how to collect docIDs into a BitSet' with an anonymous Collector and LeafCollector. Copied into code on any current release it does not compile: the anonymous Collector does not implement the abstract scoreMode() (needsScores() from 5.1.0 to 7.x), and the anonymous LeafCollector does not implement setScorer(Scorable), because the example's setScorer(Scorer) has only been an overload since 8.0.0. With scoreMode() returning ScoreMode.COMPLETE_NO_SCORES and a Scorable parameter the example compiles and collects exactly the expected global doc IDs, so only the javadoc is wrong.
Introduced
010e352f603 (trunk, svn r1657554; LUCENE-6218 'don't decode freqs or enumerate all positions when scoring is not needed', migrated as #7280, by Robert Muir (rmuir), author date = commit date 2015-02-05; branch_5x backport 8c0dbb90087, svn r1657571, same day, is the one released in 5.1.0): it added the abstract Collector.needsScores() and did not touch LeafCollector.java, so the example's anonymous Collector stopped compiling. Two later API changes kept it broken, neither touching the example: 4fc5a872ded (LUCENE-4100, #5172, Adrien Grand, author date 2017-12-07, 8.0.0) replaced needsScores() by the abstract scoreMode(), and 910a0231f6f (LUCENE-6228, #7290, Alan Woodward, author date 2018-09-03, 8.0.0) changed LeafCollector.setScorer(Scorer) to setScorer(Scorable), editing the declaration further down the same file and leaving the example's setScorer(Scorer) as a mere overload (the second javac error). The example itself was written by 85642f59ddf (LUCENE-5527, #6590, Adrien Grand, 2014-04-04) and was valid in 5.0.0; its code lines are unchanged since 927827a215a (LUCENE-6179, 2015-01-15) [read: git log, git show, git blame and git merge-base --is-ancestor in the full-history clone; exec: release runs, see affected_versions] (2015-02-05 (010e352f603 and its branch_5x backport 8c0dbb90087, author date = commit date, svn import); the second error since 2018-09-03 (910a0231f6f, LUCENE-6228, author date))
