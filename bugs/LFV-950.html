The bug in 30 seconds

#

A Kuromoji or Nori user dictionary file saved with a UTF-8 byte order mark: the mark stays glued to line 1.

Background

#
  1. Kuromoji (Japanese) and Nori (Korean) split text into words with a built-in dictionary. A user dictionary file adds your own words: one entry per line; # starts a comment.
  2. A Nori entry is the word, then optionally its parts: 세종시 세종 시 indexes 세종시 as 세종 + 시. A Kuromoji entry is word,segmentation,readings,part-of-speech.
  3. A byte order mark (BOM) is the 3 bytes EF BB BF that some editors write at the start of a UTF-8 file. Decoded, it is the invisible character U+FEFF.

The bug, step by step

#
  1. You give KoreanTokenizerFactory a user dictionary with one line, 세종시 세종 시: index "Sejong City" as "Sejong" + "city". Your editor saved the file as UTF-8 with a byte order mark (BOM): 3 invisible bytes, EF BB BF, at the start.
  2. You expect the same result as without the BOM: 세종시 gives [세종, 시]. Lucene's loader for stop words and the other analysis resource files skips a leading BOM.
  3. You get [세, 종시], the result with no user dictionary at all, and no error. The factory decodes the BOM to the character U+FEFF and the loader keeps it, so the entry is stored as U+FEFF + 세종시, which ordinary text does not contain.
  4. Kuromoji refuses such a file at setup. The 5-line dictionary of its own factory test, whose line 1 is a # comment, throws ArrayIndexOutOfBoundsException: Index 1 out of bounds for length 1, because the BOM hides the #. An entry on line 1 throws Illegal user dictionary entry, quoting two strings that print the same.

Who is affected

#

Only applications with a Kuromoji or Nori user dictionary (the userDictionary factory argument, or UserDictionary.open on their own reader) whose file starts with a BOM, as editors such as Windows Notepad often write. Nori silently ignores the first entry when line 1 is an entry; Kuromoji fails at setup. Rare: no report found since 2012.

Mechanism, terms and numbers711 words

JapaneseTokenizerFactory and KoreanTokenizerFactory take a userDictionary file. Each factory decodes the file itself with a strict decoder (UTF-8 by default) and passes the reader to UserDictionary.open, whose loop removes # comments and skips blank lines but never removes a leading byte order mark; Java's UTF-8 decoder keeps it as U+FEFF. In Nori the first entry is stored under the key U+FEFF + 세종시, which ordinary text does not contain, so 세종시 is segmented [세, 종시] (the result without any user dictionary) instead of [세종, 시], with no error. Kuromoji fails at analyzer setup: the dictionary of its own testUserDict (line 1 is a comment) throws ArrayIndexOutOfBoundsException: Index 1 out of bounds for length 1, and an entry on line 1 throws Illegal user dictionary entry, whose two quoted strings print the same. Lucene's shared line loader for the other analysis resource files skips the mark (WordlistLoader.getLines, "skip initial bom marker", SOLR-1865), so the stop-tags file of the same module and the new Thai user dictionary accept a BOM. Present since Kuromoji 3.6.0 (2012) and Nori 7.4.0 (2018). Skipping a U+FEFF at the start of line 1 in both loops fixes it; both modules' full test suites pass with that change.

Terms

#
  • User dictionary: the userDictionary argument of JapaneseTokenizerFactory and KoreanTokenizerFactory (a resource path, decoded with userDictionaryEncoding, default UTF-8), or a Reader passed to UserDictionary.open.
  • Byte order mark (BOM): the 3 bytes EF BB BF at the start of a file saved as "UTF-8 with BOM". Java's UTF-8 decoder returns them as the character U+FEFF (JDK-4508058, Won't Fix).

The bug

#
  1. Both factories' inform open the file, build a strict decoder (default UTF-8), wrap it in an InputStreamReader and call UserDictionary.open(reader) (KoreanTokenizerFactory.java:110-124, JapaneseTokenizerFactory.java:142-156). None of the 173 charsets of JDK 25 strips a UTF-8 BOM, so userDictionaryEncoding is no workaround (a UTF-16 file with a BOM works: that decoder consumes its BOM).
  2. Nori (ko/dict/UserDictionary.java:56-65): line.replaceAll("#.*$", ""), skip if line.trim().length() == 0, else keep the line. trim() removes only characters up to U+0020, so U+FEFF stays. An entry on line 1 is stored under U+FEFF + 세종시 (:89-90, :125-131). The lookup starts at every position of the text, so the key could only match where the text itself has U+FEFF before 세종시; ordinary text does not, so for 세종시 the system dictionary decides: [세, 종시]. A comment or blank line 1 leaves a junk entry U+FEFF with no visible effect in the inputs tested.
  3. Kuromoji (ja/dict/UserDictionary.java:59-69): the comment pattern ^#.*$ (:37) does not match U+FEFF + # ..., and the line is not empty, so it is parsed as a one-field entry and the constructor's values[1] (:97) throws ArrayIndexOutOfBoundsException, against the loop's own comment "Skip empty lines or comment lines" (:63). An entry on line 1 keeps U+FEFF in its surface (:96) but not in its segmentation, so the LUCENE-8933 check (:114-123) throws Illegal user dictionary entry.
  4. The other resource files skip it: WordlistLoader.getLines drops a U+FEFF at the start of the first line (WordlistLoader.java:302-304, "skip initial bom marker"). AbstractAnalysisFactory.getWordSet and getLines use it, and with them the stop-tags file of JapanesePartOfSpeechStopFilterFactory and the new ThaiTokenizerFactory user dictionary. The two CJK user dictionaries read lines themselves.

Exposure and likelihood260 words
  • Who is exposed. Applications that opt in to a Kuromoji or Nori user dictionary: the userDictionary argument of JapaneseTokenizerFactory / KoreanTokenizerFactory (directly, through the japanese / korean SPI names, or through a search-server schema, as both factory javadocs show), or code that passes a Reader over such a file to UserDictionary.open. The default configuration, without a user dictionary, is not affected.
  • What it takes. The dictionary file saved as UTF-8 with a BOM. User dictionaries are hand-edited word lists, and editors such as Windows Notepad often write a BOM (the SOLR-1865 change note says so).
  • Nori: silent. When line 1 is an entry, that entry is ignored: documents and queries with that word are segmented as if it were not in the dictionary, with no error. The other entries work. A comment or blank line 1 hides the problem (no visible effect in the inputs tested).
  • Kuromoji 9.0.0 and later: loud. An ordinary BOM-prefixed file fails at analyzer setup, with ArrayIndexOutOfBoundsException (comment or blank line 1, the shape of Lucene's own test dictionary and of the Solr sample) or Illegal user dictionary entry (entry on line 1); neither names the byte order mark. Kuromoji 3.6.0 to 8.11.4 silently ignored an entry on line 1, like Nori.
  • Scale. Deterministic, at setup, independent of index size: one entry (Nori) or the whole dictionary (Kuromoji).
  • How likely. Rare (registry: rare, priority low): opt-in, needs the BOM, Nori loses only an entry on line 1, Kuromoji fails loudly so users re-save the file, and no report was found since Kuromoji shipped in 2012.

Why it is a bug, not intended

#
  • Lucene's loader for other analysis resource files skips a leading BOM (WordlistLoader.getLines), as do the hunspell dictionary and the new Thai user dictionary.
  • On the factory path Lucene decodes the bytes itself, and no JDK charset strips a UTF-8 BOM.
  • Kuromoji's loop says "Skip empty lines or comment lines", yet a BOM makes it crash on one.
The full argument279 words
  • The factory owns the decoding. It turns the file's bytes into characters itself (JapaneseTokenizerFactory.java:142-156, KoreanTokenizerFactory.java:110-124); no factory argument helps: userDictionaryEncoding cannot remove a UTF-8 BOM, because no JDK 25 charset does. The only workarounds are re-saving the file without the BOM or wrapping the ResourceLoader to drop the three bytes, which a workaround probe on main confirmed; a workaround does not make the behaviour intended.
  • Lucene skips the mark elsewhere. WordlistLoader.getLines (SOLR-1865, 2010: it "ignores Byte Order Markers (BOMs) at the beginning of input files, these are often created by editors such as Windows Notepad"), the hunspell dictionary (LUCENE-5505, listed under 4.8.0 "Bug fixes") and the newest tokenizer user dictionary (Thai, GITHUB#16722, 10.6.0, read through getWordSet). Of the three tokenizer user dictionaries, one skips a BOM and two do not.
  • The loader's own intent. Kuromoji's loop says "Skip empty lines or comment lines"; with a BOM it instead crashes on a comment line.
  • Nothing documents or tests the current behaviour. No javadoc, CHANGES or MIGRATE entry says a user dictionary must be BOM-free, UserDictionary.open has no javadoc, no Kuromoji or Nori test uses a BOM, and neither loader ever had BOM handling.
  • Valid input, silent effect. A BOM-prefixed file is valid UTF-8 and Nori accepts it without a word; a silently ignored entry is the kind of leniency a committer objected to in LUCENE-8584 ("Now they can add something to the end of their dictionary and it gets ignored?").
  • Classification is open. No document promises BOM handling, so upstream may call the fix an improvement (SOLR-1865 was typed Improvement). Frame it as an inconsistency with Lucene's own resource loaders, not as a broken documented contract.
The devil's-advocate check264 words

Rated moderate by the cross-model reviews (an independent reviewer from another model family, OpenAI GPT-5.6, reading-only) and by the intended-behaviour checker. (a) UserDictionary.open(Reader) takes characters and promises no BOM handling; Java keeps U+FEFF on purpose; a committer wrote on LUCENE-7785 "if you have a byte order mark in your character input (reader) then your conversion from bytes is screwed up somewhere before". (b) LUCENE-8933 deliberately made Kuromoji require surface = segmentation, and LUCENE-8584 declined to make the loader lenient ("Its not stuff a library should be doing"). (c) KoreanTokenizerFactory is @lucene.experimental. (d) In 2010 a committer answered "No." to "should we consider that a bug?" about a BOM in a stop list, and SOLR-1865 was typed Improvement.

Why it fails: (a) on the factory path the "conversion from bytes" is Lucene's own code, so that remark argues for fixing the factory, not for keeping the behaviour (it was also about a char filter, not file loading); (b) LUCENE-8933 validates entries, it does not intend a comment line to crash, and the LUCENE-8584 objection was to silently ignored entries, which is what Nori does now; (c) experimental does not make a silent loss intended, and the Kuromoji factory is not experimental; (d) the same 2010 reply went on: "Yes, we can ignore them for the first line of the file to be more user-friendly. I'll open an issue" (SOLR-1865 followed), and in 2014 the same slip in hunspell went under "Bug fixes". What survives is the bug-or-improvement classification, not the defect, and maintainers could still reasonably prefer the factory-only fix, which keeps open(Reader) strict.

Suggested fix

#

Recommended Skip a BOM at the start of line 1 in both UserDictionary.open loops (recommended, validated)

In both UserDictionary.open loops, drop a U+FEFF at the start of line 1 before the comment check, the idiom WordlistLoader.getLines already uses (+6 lines each). The 6 new tests pass, and so do all 90 Nori and 198 Kuromoji tests and both modules' static checks.

    // text + optional segmentations
    boolean firstLine = true;
    while ((line = br.readLine()) != null) {
      // skip initial bom marker
      if (firstLine && line.length() > 0 && line.charAt(0) == '\uFEFF') {
        line = line.substring(1);
      }
      firstLine = false;
      // Remove comments
      line = line.replaceAll("#.*$", "");

Skip a BOM at the start of line 1 in both UserDictionary.open loops (recommended, validated) (validated by the checks) (recommended)

#

Before the comment and blank-line checks, remove a U+FEFF at position 0 of the first line; a first comment line is then skipped as intended. The same 6 lines in ja/dict/UserDictionary.java and ko/dict/UserDictionary.java (the Nori loop is shown); the idiom of WordlistLoader.getLines:302-304, with braces (getLines drops U+FEFF until it has kept a line, this drops it from the first line read: the same for a file that starts with a BOM). It reaches every caller of the public open(Reader), including downstream code that reads the file itself.

    // text + optional segmentations
    boolean firstLine = true;
    while ((line = br.readLine()) != null) {
      // skip initial bom marker
      if (firstLine && line.length() > 0 && line.charAt(0) == '\uFEFF') {
        line = line.substring(1);
      }
      firstLine = false;
      // Remove comments
      line = line.replaceAll("#.*$", "");

Trade-offs

Only a U+FEFF at the very start of the input is removed; a later one is untouched. A dictionary whose first surface deliberately began with U+FEFF would change meaning. It changes a public Reader API, which the "a Reader holds characters" view may resist. No CHANGES entry is drafted; open PR #16272 touches both files, so the patch may conflict with it; open PR #14969 edits the Nori constructor, not the loop.

Skip the BOM in the two factories' inform (validated for the factory path) (validated by the checks)

#

Wrap the decoding reader in a PushbackReader, read one character and push it back unless it is U+FEFF, in JapaneseTokenizerFactory.inform and KoreanTokenizerFactory.inform.

        PushbackReader reader = new PushbackReader(new InputStreamReader(stream, decoder));
        // skip initial bom marker
        int first = reader.read();
        if (first != -1 && first != '\uFEFF') {
          reader.unread(first);
        }
        userDictionary = UserDictionary.open(reader);

Trade-offs

Puts the BOM handling where the bytes are decoded and leaves UserDictionary.open(Reader) strict, which answers the "a Reader holds characters" objection; it does not help code that calls open(Reader) on its own reader. Open PR #16272 changes the same KoreanTokenizerFactory.inform line, so this may conflict with it too. A UTF-16 file is unaffected (its decoder already consumed the BOM).

Downstream note

#

Two downstream search servers read the user dictionary with their own UTF-8 reader and hand the text to UserDictionary.open (read, not executed), so only a fix inside open reaches them.

How it was found

#

A bounded-exhaustive metamorphic check loaded every user dictionary of 1 to 3 lines with and without a leading BOM and compared the analysis: 304 of 336 Kuromoji and 126 of 310 Nori checks differed, while three controls that read through WordlistLoader.getLines gave 0. The lead came from the same slip found earlier in a word-list loader.

The method in full190 words

Method (semi-formal): a bounded-exhaustive metamorphic check on the stock main jars.

  • The law: loading a file F and loading BOM + F give the same analysis of every probe text (terms, position increments, position lengths), or the same exception class.
  • The harness enumerated every user dictionary of 1 to 3 lines over a 4-line Kuromoji alphabet (two entries, a comment, a blank line) in search and normal mode, and a 5-line Nori alphabet (a compound entry, a noun entry, c++, a comment, a blank line), with LF and CRLF line ends. Kuromoji: 304 of 336 checks mismatch, all loud (exceptions); Nori: 126 of 310, all silent (different segmentation). Three controls that read through WordlistLoader.getLines (stop words, stemmer overrides, char mappings) give 0, and with the fix sketch every family gives 0, so the check both detects the defect and accepts the fix.
  • The lead came from an earlier hunt unit that found the same BOM slip in the snowball word-set loader and probed the other readers that bypass getLines (first executed 2026-10-27). The finder then reduced it to a public-API JUnit. No model checker, solver or proof was involved.

History

#

Present since each loader's first release: Kuromoji 3.6.0 (LUCENE-3305, 2012) and Nori 7.4.0 (LUCENE-8231, 2018, its loop copied from Kuromoji); never fixed. Executed on 18 Kuromoji and 10 Nori releases up to 10.5.2 and main. Until 8.11.4 Kuromoji also lost a first-line entry silently; from 9.0.0 it throws.

Versions tested6 rows

Introduced by LUCENE-3305, the Kuromoji code donation (Subversion era, no PR): trunk cd372bdc838 (2012-01-12, committed by Robert Muir) and the branch_3x backport 8c9485fb664, released in 3.6.0; and LUCENE-8231 (#9278), the Nori module: e851b89cbeb and branch_7x 8651fbaa8bc (2018-04-13, Jim Ferenczi), released in 7.4.0, whose loop lines git blame traces to the Kuromoji commit. Neither loader ever had BOM handling, so it is an omission, not a regression.

The symptom changed twice, the cause never: LUCENE-8933 (73ba88a50de, 9.0.0) made Kuromoji require surface = segmentation, so a BOM before an entry now throws (the 8.x backport only rejects longer segmentations, so 8.3.0 to 8.11.4 stay silent); LUCENE-8596 (9.0.0) anchored the comment pattern, which keeps the comment-line exception for a different reason. Bug record

LFV-950, snapshot of 2026-10-29

Registry title
Kuromoji and Nori UserDictionary.open keep a leading UTF-8 byte order mark, so Nori silently drops the first user-dictionary entry and Kuromoji refuses to load the file
Area
analysis-kuromoji + analysis-nori / user dictionary loading (UserDictionary.open, reached through the JapaneseTokenizerFactory / KoreanTokenizerFactory userDictionary argument)
Priority
Low, rank 414: It is the same kept-BOM slip in the kuromoji and nori user dictionaries, where nori silently drops the first entry and kuromoji fails loudly, and those are used less than the synonym factories.
Impact class
silent wrong results
Impact note
Applications that load a Kuromoji or Nori user dictionary (the opt-in userDictionary factory argument, or UserDictionary.open on their own Reader) from a file saved as UTF-8 with a byte order mark: Nori silently ignores the first entry whenever line 1 is an entry (every release since 7.4.0), Kuromoji silently ignored it in 3.6.0-8.11.4 and since 9.0.0 refuses such a file with a RuntimeException whose two quoted strings print the same, and in every Kuromoji release a BOM before a comment or blank first line gives ArrayIndexOutOfBoundsException at analyzer setup; no scale is needed.
Summary
You give KoreanTokenizerFactory or JapaneseTokenizerFactory a user dictionary file that an editor saved as UTF-8 with a byte order mark (bytes EF BB BF), and expect the same dictionary as from the file without the mark, because Lucene's shared resource-line loader skips a leading BOM for the other file-based analysis factories (WordlistLoader.getLines, 'skip initial bom marker', SOLR-1865). Instead both factories decode the file themselves and pass it to UserDictionary.open, which keeps the invisible U+FEFF on line 1: in Nori the first entry becomes '\uFEFF세종시', which no text contains, so 세종시 is segmented [세, 종시] instead of the user's [세종, 시] with no error. Kuromoji (9.0.0 and later) rejects the file with 'Illegal user dictionary entry \uFEFF関西国際空港 - the concatenated segmentation (関西国際空港) does not match the surface form (\uFEFF関西国際空港)', and when line 1 is a '#' comment or blank it throws ArrayIndexOutOfBoundsException 'Index 1 out of bounds for length 1', because the BOM hides the comment from its 'skip empty lines or comment lines' check.
