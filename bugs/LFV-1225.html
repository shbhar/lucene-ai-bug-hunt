The finding in 30 seconds

#

Analysis factories read their settings from a Map<String, String>. AbstractAnalysisFactory offers a pair of helpers per type: get* for an optional setting with a default, require* for a mandatory one. For one-char settings the two helpers treat the same wrong value differently.

Factory settings in one minute

#
  1. A factory such as PathHierarchyTokenizerFactory gets its settings as strings, for example {delimiter=/}, from CustomAnalyzer or TokenizerFactory.forName(name, args).
  2. Its constructor reads each setting with a helper that also removes the key from the map, here getChar(args, "delimiter", '/') and getInt(args, "skip", 0). A mandatory setting would use a require* helper such as requireChar(args, name) instead.
  3. At the end it throws IllegalArgumentException("Unknown parameters: ...") if any key is left, which catches a mistyped key name. A mistyped value has to be caught by the helper itself.

The finding, step by step

#
  1. You write a custom TokenFilterFactory whose constructor reads a mandatory one-char setting with requireChar(args, "delimiter"), and configure it with delimiter="ab" by mistake.
  2. You expect IllegalArgumentException: delimiter should be a char. "ab" is invalid. That is what the optional twin getChar(args, "delimiter", '|') throws for the same value.
  3. Instead the factory is built and its delimiter is 'a', with assertions on or off. requireChar is only require(args, name).charAt(0), and require has already removed the key, so the factory's closing "Unknown parameters" check sees nothing wrong either.
  4. The same missing length check turns an empty value into a StringIndexOutOfBoundsException and the emoji U+1F600 into the lone high surrogate U+D83D; getChar rejects both. It has been like this since 4.3.0 (2013).

Who is affected

#

Only custom or third-party factories that read a mandatory one-char setting with requireChar, and only when that setting gets a wrong value. No Lucene factory calls it: Lucene's one-char settings use getChar or, in ConcatenateGraphFilterFactory, its own checked getter. The analyzer is then built and silently uses the wrong char; an empty value gives a bare StringIndexOutOfBoundsException.

Mechanism, terms and numbers499 words

AbstractAnalysisFactory, the base class of every TokenizerFactory, TokenFilterFactory and CharFilterFactory, gives factories a pair of helpers per value type to read their string settings: get* for an optional setting with a default and require* for a mandatory one. For one-char settings the pair disagrees. getChar throws IllegalArgumentException("<name> should be a char. \"<value>\" is invalid") when the value's length is not 1 (AbstractAnalysisFactory.java:231-242), but requireChar is only return require(args, name).charAt(0); (:227-229). So delimiter="ab" silently becomes 'a'; a supplementary character becomes its lone high surrogate; an empty value throws StringIndexOutOfBoundsException. Because require has already removed the key (:119-125), the factory's usual "Unknown parameters" check cannot catch the bad value either. Both methods were added by the same diff for LUCENE-4877 ("Throw exception for invalid arguments in analysis factories", first released in 4.3.0), and every release since, and main, has the gap. No Lucene factory calls requireChar, and no downstream caller is known, so only custom factories with a mistyped mandatory one-char setting are affected: a Low consistency fix. Giving requireChar the check getChar has fixes it.

The code

#
// AbstractAnalysisFactory.java, main 5adff78bb168
public String require(Map<String, String> args, String name) {          // :119
  String s = args.remove(name);                                          // :120  key removed here
  if (s == null) {
    throw new IllegalArgumentException("Configuration Error: missing parameter '" + name + "'");
  }
  return s;
}

public char requireChar(Map<String, String> args, String name) {       // :227
  return require(args, name).charAt(0);                                 // :228  no length check
}

public char getChar(Map<String, String> args, String name, char defaultValue) {  // :231
  String s = args.remove(name);
  if (s == null) {
    return defaultValue;
  } else {
    if (s.length() != 1) {                                               // :236
      throw new IllegalArgumentException(name + " should be a char. \"" + s + "\" is invalid");
    } else {
      return s.charAt(0);
    }
  }
}

The claim is the silent truncation of a longer value. Why the factory's own check does not help

#

By convention (the base class does not enforce it), factories end their constructor with if (!args.isEmpty()) throw new IllegalArgumentException("Unknown parameters: " + args); (for example PathHierarchyTokenizerFactory.java:82-84). require removed the key before charAt(0) ran, so in a factory that follows the convention the map is empty and the factory is built with the wrong char.

Exposure and likelihood206 words
  • Who is hit. Custom or downstream TokenizerFactory, TokenFilterFactory or CharFilterFactory subclasses (or other subclasses of AbstractAnalysisFactory) that call the public helper requireChar. In Lucene, git grep requireChar finds only the definition; the six getChar call sites are in five factories (DelimitedBoostTokenFilterFactory, DelimitedTermFrequencyTokenFilterFactory, FingerprintFilterFactory, PathHierarchyTokenizerFactory (two) and DelimitedPayloadTokenFilterFactory), and the only other one-char setting, ConcatenateGraphFilterFactory's tokenSeparator, is read by that factory's own getter with the same length check (ConcatenateGraphFilterFactory.java:55-56, :81-95). The history shows no caller in Lucene, or in Solr while it shared the repository, and a GitHub code search found no downstream caller (which does not prove there is none).
  • Default vs opt-in. Nothing to configure beyond calling the helper; assertions on or off.
  • Effect. A typo in a mandatory one-char setting goes unnoticed: the analyzer is built and uses the first char (for example \ when \t was typed as two characters for a tab). An empty value fails with a bare StringIndexOutOfBoundsException instead of a configuration error that names the setting. Nothing is corrupted.
  • Scale. None needed: one call.
  • Likelihood: rare. A custom factory that uses requireChar plus a mistyped value; nothing has been reported in the 13 years since 4.3.0.

Why it looks unintended

#
  • LUCENE-4877 added both methods to make factories "Throw exception for invalid arguments" (CHANGES.txt), since a typo gave "no exception and sometimes incorrect behavior" (#5942).
  • The same diff gave getChar a length check and left it out of requireChar.
  • In the Int, Float and Boolean pairs, require* and get* parse a value identically; only Char disagrees.
The full argument194 words
  • The change that added it was about invalid factory arguments. LUCENE-4877 / #5942, "Fix analyzer factories to throw exception when arguments are invalid". Its description (Robert Muir, 2013-03-25): "Currently if someone typos an argument "someParamater=xyz" instead of someParameter=xyz, they get no exception and sometimes incorrect behavior." CHANGES.txt: "LUCENE-4877: Throw exception for invalid arguments in analysis factories. (Steve Rowe, Uwe Schindler, Robert Muir)" (lucene/CHANGES.txt:14172-14173).
  • The check was in the same diff. Commit 6de43dea0af ("LUCENE-4877: more param parsing verbs", Steven Rowe, 2013-04-01) added requireChar without a length check and getChar with one, moved up from a private getChar in PathHierarchyTokenizerFactory that the same commit removed.
  • The family agrees everywhere else. requireInt/getInt both use Integer.parseInt (so "ab" gives NumberFormatException, an IllegalArgumentException), requireFloat/getFloat Float.parseFloat, requireBoolean/getBoolean Boolean.parseBoolean (AbstractAnalysisFactory.java:200-225).
  • Later code followed getChar. For ConcatenateGraphFilterFactory (#10061 / LUCENE-9018, 2019) David Smiley pointed the contributor to getChar, and the contributor wrote an optional Character getter with the same "should be a char" check.
  • No text says otherwise. No javadoc, test, CHANGES entry or issue comment describes truncation as intended, and no upstream test calls requireChar.
The devil's-advocate check164 words

The strongest case for "intended", rated moderate by an executed review from another model family (OpenAI GPT-5.6): requireChar has no javadoc, so it can be read as "require the key, then take its first char"; it was written next to the strict getChar on purpose and has lasted 13 years unreported; and requireBoolean is lenient too.

Why it fails: the boolean pair is lenient in both halves, so it is consistent, while the char pair is the only one whose halves disagree on the same value. An empty value ending in StringIndexOutOfBoundsException is not a designed configuration error. The quiet years are consistent with the absence of known callers; nothing suggests users rely on truncation. The same reviewer still found the bug real, and the adjudication, the independent reproducer and the devil's-advocate verifier agree. What the argument leaves open is the resolution: since nothing in Lucene calls the method, a maintainer may rather deprecate or document it than change its behaviour (see the fixes).

Suggested fix

#

Recommended A: the getChar length check in requireChar

Give requireChar the check getChar already has: if the value's length is not 1, throw IllegalArgumentException(name + " should be a char. ...") (+5/-1 in AbstractAnalysisFactory.java). Validated: the repro passes with assertions on and off, the 169 tests of core's analysis packages pass, and :lucene:core:check -x test is clean.

  public char requireChar(Map<String, String> args, String name) {
-    return require(args, name).charAt(0);
+    String s = require(args, name);
+    if (s.length() != 1) {
+      throw new IllegalArgumentException(name + " should be a char. \"" + s + "\" is invalid");
+    }
+    return s.charAt(0);
   }

A: the getChar length check in requireChar (validated by the checks) (recommended)

#

Read the value with require, reject any length other than 1 with the message getChar uses, then return its char.

  public char requireChar(Map<String, String> args, String name) {
-    return require(args, name).charAt(0);
+    String s = require(args, name);
+    if (s.length() != 1) {
+      throw new IllegalArgumentException(name + " should be a char. \"" + s + "\" is invalid");
+    }
+    return s.charAt(0);
   }

Trade-offs

The smallest change, local to one method; it fixes all three inputs (the empty value then gets IllegalArgumentException too). A custom factory whose configuration relied on truncation would now fail at construction, which is the fail-fast LUCENE-4877 asked for; none is known, which does not rule one out.

Deprecate requireChar (not run)

#

Mark requireChar deprecated and remove it in the next major version. Nothing in Lucene calls it.

Trade-offs

No behaviour change for existing callers, but the truncation stays until removal, and custom factories lose a helper for a mandatory one-char setting.

Downstream note

#

Products that let users write analyzer settings for a custom factory built on requireChar should check one-char values themselves on affected versions; Lucene treats factory arguments as trusted configuration.

How it was found

#

A proof-obligation audit of AbstractAnalysisFactory's contract: each require*/get* pair must parse a value the same way and differ only in how a missing key is handled. The Char pair fails it. A one-test JUnit witnessed it on main, and independent checks reproduced it with their own tests.

The method in full146 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro), on main 5adff78bb168, 2026-11-03.

  • The obligation: for every value, requireX(args, name) and getX(args, name, default) return the same result or throw the same kind of exception when the key is present; they may differ only when it is absent. The Int, Float and Boolean pairs discharge it by calling the same parser in both halves. The Char pair does not: getChar checks s.length() != 1, requireChar does not (AbstractAnalysisFactory.java:200-242).
  • A one-test JUnit witnessed it on main with assertions on and off, and a probe compared the two helpers on "ab", "", U+1F600, "a" and an absent key. An independent reproducer and an executed review by another model family (OpenAI GPT-5.6) wrote their own tests from the claim; a devil's-advocate verifier and an adjudication re-ran the repro.
