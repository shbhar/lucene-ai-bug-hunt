On main (11.0, unreleased), a field-sorted collector asked for Integer.MAX_VALUE hits throws OutOfMemoryError instead of IllegalArgumentException

Asking a field-sorted TopFieldCollectorManager for Integer.MAX_VALUE hits throws OutOfMemoryError on main, where every release from 7.5.0 to 10.6.0 refuses that size with a clear IllegalArgumentException: since #14873 the built-in sort comparators allocate their numHits-sized arrays before the queue's size check runs. Unreleased: main and the 11.0 release branch (branch_11x).

The finding in 30 seconds

#

Background: field-sorted top-N collection

#
  1. A search sorted by fields keeps its best numHits hits in a priority queue, FieldValueHitQueue. Each sort field gets a comparator (for the built-in sort types) that stores one value per queue slot, so it allocates an array of numHits values up front.
  2. A Java array holds at most about 2^31 entries. Since 4.7.0 (SOLR-5661) the PriorityQueue constructor has checked for sizes too big for an array, "to prevent confusing OOME". Its current form, since 7.5.0, refuses a size of ArrayUtil.MAX_ARRAY_LENGTH (2,147,483,631) or more with an IllegalArgumentException.

The finding, step by step

#
  1. Sort by a long field and ask for every hit with Java's usual "no limit": new TopFieldCollectorManager(sort, Integer.MAX_VALUE, null, 1).newCollector(). Core's SortRescorer.rescore(searcher, topDocs, Integer.MAX_VALUE) reaches the same code through new TopFieldCollectorManager(sort, topN, null, Integer.MAX_VALUE) (SortRescorer.java:49).
  2. No queue can hold 2,147,483,647 slots: Java arrays end just below 2^31. You expect the clear refusal that every release from 7.5.0 to 10.6.0 gives, here 10.5.2 and 10.6.0: IllegalArgumentException: maxSize must be >= 0 and < 2147483631; got: 2147483647. Main's score-sorted collector still refuses the size too, with an IllegalArgumentException from its own copy of the guard.
  3. On main you get OutOfMemoryError: Requested array size exceeds VM limit, thrown in LongComparator's constructor, with assertions on and off.
  4. Why: the size check sits in the PriorityQueue constructor. Since #14873 (2025), FieldValueHitQueue.create first builds the sort comparators, each built-in one allocating numHits slots (new long[numHits]), and creates the queue, with its check, only afterwards (FieldValueHitQueue.java:146 runs before :153).
  5. Only the error changes: the call is refused either way, and IndexSearcher.search(query, n, sort) caps n at maxDoc, so it is not affected. But code that catches IllegalArgumentException misses it, and a JVM run with -XX:+ExitOnOutOfMemoryError exits.

Who is affected

#

Code on a main or 11.0 branch build that passes numHits of 2,147,483,631 or more, in practice Integer.MAX_VALUE for "all", to a field-sorted collector without capping it: direct TopFieldCollectorManager use, SortRescorer and the expressions rescorer. Any built-in sort type, default settings. IndexSearcher.search(query, n, sort) caps n and is safe. No release is affected. Rare.

Mechanism, terms and numbers584 words

On main, new TopFieldCollectorManager(sort, Integer.MAX_VALUE, null, 1).newCollector() with a built-in sort (long, string, relevance and index order executed) throws OutOfMemoryError: Requested array size exceeds VM limit. Lucene 9.10.0 to 10.6.0 refuse the same call with IllegalArgumentException: maxSize must be >= 0 and < 2147483631; got: 2147483647, releases from 7.5.0 refuse the equivalent TopFieldCollector.create call the same way, and main's score-sorted TopScoreDocCollectorManager still throws an IllegalArgumentException (with its own message). Since #14873 (39549329509, 2025-07-03), FieldValueHitQueue.create builds the sort comparators, each pre-allocating numHits slots, before it calls the constructor that reaches PriorityQueue's size check, a guard SOLR-5661 added in 4.7.0 "to prevent confusing OOME" and Lucene fixed again for exactly Integer.MAX_VALUE in 2018 (7.5.0). The call never succeeded on any version, so only the error type changes; IndexSearcher.search(query, n, sort) caps n at maxDoc and is not affected, while direct users and SortRescorer are. No release has it; the 11.0 release branch branch_11x has the same code. A small up-front size check in create() restores the old error; it passes the minimal test with assertions on and off, the closest core suites and core's static checks.

Terms

#
  • TopFieldCollectorManager: builds the collectors for a search sorted by Sort fields. Its javadoc says the collectors "pre-allocate a full array of length numHits" (TopFieldCollectorManager.java:44-45, :96-97); its constructor rejects only numHits <= 0 (:62-64).
  • FieldValueHitQueue: the field-sorted hit queue, a PriorityQueue (@lucene.experimental), built by the static create(fields, size).
  • The guard: PriorityQueue's constructor throws IllegalArgumentException for maxSize < 0 || maxSize >= ArrayUtil.MAX_ARRAY_LENGTH, with the comment "Throw exception to prevent confusing OOME" (PriorityQueue.java:121-125). MAX_ARRAY_LENGTH is 2147483631 here, so on main and since 7.5.0 the guard covers the 17 values 2147483631 to 2147483647.

The bug

#
  1. newCollector() calls FieldValueHitQueue.create(sort.getSort(), numHits) (TopFieldCollectorManager.java:112-114), the only production caller of create.
  2. create() (FieldValueHitQueue.java:132-159) first loops over the sort fields and calls field.getComparator(size, ...) for each (:142-151, the call at :146). Each built-in comparator allocates size slots in its constructor: LongComparator.java:38 values = new long[numHits];, and likewise the int, float, double, relevance, string and doc comparators. A CUSTOM sort gets its comparator from user code (SortField.java:511-514); one that does not pre-allocate reaches the guard and gets the normal IllegalArgumentException.
  3. Only then does it call new FieldValueHitQueue<>(fields, size, ...) (:153-158), whose constructor calls super(size, lessThan) (:114-115) and so reaches the guard. For Integer.MAX_VALUE the first comparator's new long[2147483647] has already thrown OutOfMemoryError: Requested array size exceeds VM limit, so the guard never runs.
  4. Up to 10.6.0 the queue's constructor called super(size) first and built the comparators after it (10.5.2 and 10.6.0 FieldValueHitQueue.java:122-123). #14873 moved the comparator loop into create(), ahead of the constructor, because the new LessThan object needs the comparators.

Why it looks unintended

#
  • The guard says why it exists: "Throw exception to prevent confusing OOME" (PriorityQueue.java:122). It was added in 4.7.0 (SOLR-5661) and fixed again in 2018 for exactly Integer.MAX_VALUE.
  • Main keeps the guard elsewhere: its score-sorted collector still throws an IllegalArgumentException, from TernaryLongHeap's copy.
  • #14873 was an API refactor; its CHANGES entry, migration note and review never mention size checks.
The full argument246 words
  • Stated purpose. PriorityQueue.java:121-125: if ((maxSize < 0) || (maxSize >= ArrayUtil.MAX_ARRAY_LENGTH)) { // Throw exception to prevent confusing OOME:. CHANGES.txt:12883-12884, 4.7.0 "Bug fixes": "SOLR-5661: PriorityQueue now refuses to allocate itself if the incoming maxSize is too large (Raintung Li via Mike McCandless)".
  • Fixed again for exactly this value. From 4.9.1 to 7.4.0 the guard let Integer.MAX_VALUE overflow past it (LUCENE-5844, b293b947cb3, moved heapSize = maxSize + 1 ahead of the check), so the call threw NegativeArraySizeException. Michael McCandless fixed that in 2018 (4c646dab3fb, "Fix PriorityQueue constructor to throw IllegalArgumentException if you pass Integer.MAX_VALUE as maxSize (thanks rsaavedraf)", released in 7.5.0), writing today's check and message and adding TestPriorityQueue.testMaxIntSize.
  • Re-applied in newer heaps. LongHeap.java:57-58 and TernaryLongHeap.java:57-58 carry the same check and comment; main's TopScoreDocCollectorManager rejects these sizes with an IllegalArgumentException from that copy ("initialCapacity must be > 0 and < 2147483630"), so the two top-N collector families now disagree.
  • A refactor, not a decision. #14873 ("Change PriorityQueue to take a LessThan interface implementation in its constructor rather than overriding the lessThan abstract method", CHANGES.txt:75-76, 11.0.0 API Changes) moved the comparator loop for a structural reason; its MIGRATE note and review thread discuss the API and performance, not size validation.
  • Tests. TestPriorityQueue.testMaxIntSize (TestPriorityQueue.java:378-382) pins the IllegalArgumentException for the bare queue (added by the 2018 fix); no core search test gives a field-sorted collector a numHits near Integer.MAX_VALUE (those arguments are totalHitsThreshold), so nothing caught the reorder.
The devil's-advocate check190 words

The strongest case for "intended" (put forward by an independent reviewer from another model family, OpenAI GPT-5.6, and argued in full by the intended-behaviour check): no javadoc promises the IllegalArgumentException; FieldValueHitQueue is @lucene.experimental and PriorityQueue @lucene.internal; both javadocs document the numHits pre-allocation, and create() says only "Must be greater than zero"; IndexSearcher caps n, and, as Michael McCandless pointed out on SOLR-5661, callers should bound the size they pass (Adrien Grand described top-k collection as designed for "some reasonable value of k" on LUCENE-8542); and on main and in 10.x the guard covers only 17 values: at 2147483630, main, 10.5.2 and 10.6.0 throw a heap OutOfMemoryError (1 GB heap).

Why it fails: the guard is a deliberate bug fix with a stated purpose, Lucene fixed it again in 2018 for exactly Integer.MAX_VALUE, re-applies it in newer heaps, main's other top-N collector still has it, and the refactor did not mean to drop it; core's own SortRescorer forwards an uncapped topN into this path. The honest residue: the fix restores a clearer error, not a capability, and the contract rests on intent and history, not on a javadoc.

Suggested fix

#

Recommended A. Check the size in FieldValueHitQueue.create before building comparators

Check the size in FieldValueHitQueue.create right after its empty-sort check, before any comparator is built, and throw the same IllegalArgumentException as PriorityQueue. It restores the 10.x error for every built-in field sort. With it the test passes with assertions on and off, and the closest core suites and core's static checks pass.

Trade-offs

  • Restores the 10.x behaviour exactly, with the same message, at the one place every field-sorted collector goes through, including external callers of the public create().
  • Cost: one comparison per newCollector(), not per hit.
  • It duplicates the guard's bound and message; a shared helper could avoid that.
  • It turns the main-only OutOfMemoryError of uncapped callers (the SortRescorer and grouping findings LFV-997 and LFV-964) back into this exception without fixing their own sizing.
  • The diff is against 645d4fe14a20; git apply rejects it on upstream main 2f424fd428da and on branch_11x (#16857 added an import next to its context). The same 7 lines regenerated against 2f424fd428da pass git apply --check there and on branch_11x, but were not compiled or tested on those revisions.
  • Like PriorityQueue, it accepts size == 0, while create()'s javadoc says the size "Must be greater than zero" (FieldValueHitQueue.java:130); TopFieldCollectorManager already rejects numHits <= 0, so only direct create() callers can pass 0.

Downstream note

#

Applications that forward an unbounded size such as Integer.MAX_VALUE to a field-sorted collector and treat OutOfMemoryError as fatal exit on main where 10.x threw a catchable exception; capping numHits at maxDoc, as IndexSearcher does, avoids it.

How it was found

#

Non-formal: an early probe saw SortRescorer with topN = Integer.MAX_VALUE throw OutOfMemoryError on main but IllegalArgumentException on 10.5.2 and the 10.6 release candidate. An AI finder traced that difference by code reading and git history to #14873 and confirmed it with a public-API test across main and releases.

The method in full134 words
  • First signal: an executed probe on the stock jars (2026-10-28) ran SortRescorer and the expressions rescorer with topN = Integer.MAX_VALUE and saw OutOfMemoryError: Requested array size exceeds VM limit on main but the PriorityQueue IllegalArgumentException on 10.5.2 and the 10.6 release candidate.
  • Root cause: the finder, explaining that main-vs-release difference, read FieldValueHitQueue.create and its git history and found the comparator loop that #14873 moved ahead of the queue constructor.
  • Confirmation: a public-API JUnit (long, relevance and string sorts plus a score-sorted control) failed 3 of 4 on main and passed on 10.5.2 and the release candidate. No model or formal tool was involved, so the method is non-formal.
  • Later: independent verifiers, cross-model reviews (reading only), an adjudication, the registration check, a credibility audit, the one-test minimal repro (2026-10-29) and this doc's gradle run (2026-11-01).

History

#

Introduced on main by #14873 (39549329509, 2025-07-03), an API refactor of PriorityQueue; bisected by building the commit and its parent; also on branch_11x, the 11.0 release branch. No release is affected: 7.5.0 to 10.6.0 throw the quoted IllegalArgumentException, older releases fail inside PriorityQueue itself. The guard dates from SOLR-5661 (4.7.0), its current form from 7.5.0.

Versions tested9 rows

Introduced by #14873 "Make PriorityQueue use LessThan interface by default" (commit 39549329509, Simon Cooper, 2025-07-03, milestone 11.0.0; cited as the source of the change, not as blame). It turned FieldValueHitQueue from an abstract PriorityQueue subclass, whose constructor called super(size) before building the comparators, into a class built by the static create(), which builds the comparators first. git blame shows no later change to the order; upstream #16857 and #16947 edited the file without touching it. Releases before 4.7.0 throw an OutOfMemoryError from PriorityQueue itself: the original SOLR-5661 bug, long fixed. The 11.0 release branch branch_11x, cut from main at c5ab3e57b9b on 2026-10-28 (#16929), carries #14873 and the same create() with no size check (read at 603af870375; the fact check read the same on GitHub on 2026-11-01), so a fix needs main and branch_11x. branch_10_6 keeps super(size) first; branch_10x was decommissioned on 2026-10-29 (#16911). What older releases throw for Integer.MAX_VALUE depends on the guard's version: 4.7.0 to 4.9.0 an IllegalArgumentException worded "maxSize must be <= 2147483391" (a guard of Integer.MAX_VALUE - 256), 4.9.1 to 7.4.0 a NegativeArraySizeException (LUCENE-5844 let this one value overflow past the guard), and 7.5.0 on the quoted message, after Michael McCandless's 2018 fix 4c646dab3fb.

LFV-993, snapshot of 2026-11-05

Registry title
On main, a field-sorted TopFieldCollectorManager with numHits >= ArrayUtil.MAX_ARRAY_LENGTH (e.g. Integer.MAX_VALUE) throws OutOfMemoryError instead of the IllegalArgumentException that 10.x throws, because since #14873 FieldValueHitQueue.create allocates the numHits-sized sort comparators before the PriorityQueue size check runs (unreleased regression of the SOLR-5661 guard)
Area
core / search: field-sorted top-N collection (FieldValueHitQueue, TopFieldCollectorManager)
Priority
Low, rank 1129: On unreleased main and branch_11x only, a call that was always refused now throws OOM instead of IAE, and IndexSearcher.search caps n, so it is Low.
Impact class
wrong error
Impact note
Only main and the 11.0 release branch branch_11x (11.0.0-SNAPSHOT, unreleased), since #14873: an application that passes a numHits in [2147483631, 2147483647] (in practice Integer.MAX_VALUE meaning 'all') to TopFieldCollectorManager directly, or through a caller that does not cap it (SortRescorer.rescore, ExpressionRescorer), with any built-in sort and default settings, gets an OutOfMemoryError from newCollector() instead of the IllegalArgumentException that 7.5.0 to 10.6.0 throw; the call is refused either way, IndexSearcher.search(query, n, sort) is not affected because it caps n at maxDoc, and a JVM run with -XX:+ExitOnOutOfMemoryError exits instead of letting the caller catch the error.
Summary
You call new TopFieldCollectorManager(sort, Integer.MAX_VALUE, null, 1).newCollector() with any built-in sort (a long field, a string field, Sort.RELEVANCE), directly or through SortRescorer.rescore(searcher, topDocs, Integer.MAX_VALUE), and expect the IllegalArgumentException 'maxSize must be >= 0 and < 2147483631' that Lucene 7.5.0 to 10.6.0 throw (main's score-ordered TopScoreDocCollectorManager still throws an IllegalArgumentException, with its own message). On main you get OutOfMemoryError 'Requested array size exceeds VM limit' instead ('Java heap space' at 2147483631 with a 1 GB heap). Since #14873, FieldValueHitQueue.create builds the sort comparators, each of which pre-allocates a numHits-sized array, before it calls the PriorityQueue constructor, whose size check exists to prevent exactly this confusing OutOfMemoryError (SOLR-5661).
Introduced
39549329509 (#14873, PR title 'Make PriorityQueue use LessThan interface by default', commit 'Change PriorityQueue to use LessThan interface by default (#14873)', by Simon Cooper (thecoop); base main, milestone 11.0.0): it turned FieldValueHitQueue from an abstract PriorityQueue subclass, whose constructor called super(size) and so reached the SOLR-5661 guard before it built the comparators, into a class built by the static create(), which builds the comparators first and only then calls the constructor [exec: javac core builds of the parent 62e02760321 (3 of 3 field sorts get the IllegalArgumentException) and of 39549329509 (0 of 3, OutOfMemoryError from FieldValueHitQueue.create:146); read: git blame at a9779ef3c193, nothing later changed the order]. #14873 was an API refactor; its CHANGES entry (11.0.0 API Changes), MIGRATE.md and review thread say nothing about size validation.
