Merges through BPReorderingMergePolicy with BpVectorReorderer break document blocks even when a parent field is set

With a parent field set, a merge through BPReorderingMergePolicy with BpVectorReorderer moves children and parents separately: in a 4-block index all 8 children end up before parent b0p, so block joins give 6 of them the wrong parent. No error, CheckIndex passes; main only, unreleased.

The bug in 30 seconds

#

A block is children followed by their parent, and a block join finds a child's parent as the first parent after it. IndexWriter lets a merge reorder documents only when a parent field identifies the blocks, then applies the merge policy's map without checking it.

  1. Set setParentField("_parent"), no index sort, and the merge policy new BPReorderingMergePolicy(new LogDocMergePolicy(), new BpVectorReorderer("vec")) with default settings. Add 4 blocks with addDocuments, each two children with a vector and a parent without one, in two segments: [b0c0 b0c1 b0p b1c0 b1c1 b1p] and [b2c0 b2c1 b2p b3c0 b3c1 b3p].
  2. Run forceMerge(1). You expect every block to stay together, parent last: the parent field exists so that IndexWriter never alters the order of a block, and IndexWriter lets a merge reorder documents only because the parent field lets it keep blocks.
  3. Instead the merged order is b0c0 b0c1 b1c0 b1c1 b2c0 b2c1 b3c0 b3c1 b0p b1p b2p b3p. BpVectorReorderer never looks at the parent field, and it puts every document without a vector after all documents that have one.
  4. So ToParentBlockJoinQuery returns b0p for all 8 children (6 wrong), and a nested kNN query for the best child of 3 parents returns 1 hit instead of 3. With the vectors on the parents instead, all 8 children land after the last parent and have no parent at all.
  5. No exception, with assertions on or off, and CheckIndex passes. The scramble is written into the merged segment; reindexing the affected blocks repairs it.

Who is affected

#

Applications on main that opt into BPReorderingMergePolicy with BpVectorReorderer and index document blocks with a parent field and no index sort. With vectors on the children or the parents, every merge the policy reorders (forced, and at default settings natural too) breaks blocks, from 4 blocks on; with vectors on every document, only merges of 64+ vectors.

Mechanism, terms and numbers818 words

IndexWriter lets a merge renumber documents on an index with document blocks only when a parent field identifies the blocks, because then the reorder can keep each block together; it applies whatever doc map the merge policy returns without checking it. BPReorderingMergePolicy with BpVectorReorderer returns a map that moves every document on its own: the vector bisection never reads the parent field, and documents without a vector are moved after all documents that have one. So a reordered merge silently scrambles the merged segment's blocks: with vectors on the children only or on the parents only, at default settings and at any scale (4 blocks suffice); with vectors on every document, only merges with at least 64 vectors (twice the default minPartitionSize), where the bisection runs, can break them (66 documents: 23 children wrong). Block joins then return another block's parent or none, nested kNN returns fewer hits, and deletes that locate children through a block join miss them; CheckIndex passes, and only reindexing the affected blocks reliably repairs it. The defect came with #14097 (2025-01-07) and exists only on main, so a fix before 11.0.0 keeps it out of every release.

Terms

#
  • Document block: documents added together with IndexWriter#addDocuments, children first, parent last. Block joins (ToParentBlockJoinQuery, DiversifyingChildrenFloatKnnVectorQuery, ...) find a child's parent as the first parent document after it, so the order inside a segment is the only link between them.
  • Parent field (IndexWriterConfig#setParentField): IndexWriter marks every parent with it. Its javadoc: "In order to maintain the API guarantee that the document order of a block is not altered by the IndexWriter a marker for parent documents is required."
  • Merge-time reordering: a merge policy can return a doc map from OneMerge#reorder, and IndexWriter writes the merged segment in that order. BPReorderingMergePolicy does this with an IndexReorderer: BPIndexReorderer (by postings) or BpVectorReorderer (by vector similarity, recursive graph bisection).

The bug

#
  1. IndexWriter.mergeMiddle skips the reorder only if an index sort is set, or if some merging segment has blocks while some merging segment (not necessarily the same one) has no parent field (IndexWriter.java:5544-5555, added by #13128 "Make OneMerge#reorder preserve blocks"). Otherwise it calls merge.reorder(...) (:5558) and applies the map with SortingCodecReader.wrap(mergedView, docMap, null) (:5576). Nothing checks the map against the blocks.
  2. BPReorderingMergePolicy forwards the call to reorderer.computeDocMap(...) (BPReorderingMergePolicy.java:133-145).
  3. BpVectorReorderer.computeDocMap (BpVectorReorderer.java:578-593) permutes the vector ordinals and never reads the parent field; the file contains neither "parent" nor "block". The bisection splits a range only when each half would hold at least minPartitionSize vectors (default 32, :208-211); when it runs it may move any vector document anywhere in the range, so blocks can interleave, depending on the vectors.
  4. valueMapToDocMap (:735-789, "sort docs with no value at the end") gives every document without a vector a new ID after all documents with one. When only the children (or only the parents) carry the vector, all parents end up after all children (or before them), whatever the vector values and even when the bisection does not run. When every document has a vector, nothing is moved to the end, and below 64 vectors (default settings) the bisection does not run either: the map is the identity (:737-738) and the blocks survive.
  5. The sibling BPIndexReorderer reads the parent field and moves whole blocks (BPIndexReorderer.java:376-382, :450-455, :878-882, #13125). BpVectorReorderer came later (#14097) without that.

Exposure and likelihood376 words
  • Who is exposed. Applications that combine BPReorderingMergePolicy with a BpVectorReorderer (lucene/misc, expert), document blocks with IndexWriterConfig#setParentField, and no index sort (with an index sort IndexWriter never reorders). The natural user is a nested-vector index: parents with child "chunk" documents that carry embeddings, searched with DiversifyingChildrenFloatKnnVectorQuery and ToParentBlockJoinQuery. That is the layout that breaks deterministically; the join module's own test notes "only child documents are allowed to have a vector!" for its nested kNN queries.
  • Default or opt-in. Opt-in. Inside that setup, with vectors on the children or on the parents, nothing else is needed: default reorderer settings, no explicit codec (the runs drew randomized test codecs), assertions on or off.
  • Scale. With vectors on the children or on the parents: none, 4 blocks (12 documents) in 2 segments, and the result is deterministic. With vectors on every document and default settings, the merge must hold at least 64 vectors (66 documents broke, 63 did not), and where each child lands depends on the vectors (56 of 60 children wrong in a 30-block run with minPartitionSize 2).
  • Frequency. Whenever the policy applies a doc map to a segment with blocks. Forced merges were executed; by code reading the policy also reorders natural, full-flush and forced-deletes merges that reach minNaturalMergeNumDocs and the biggest-segment ratio (defaults 1 and 0, so every such merge; the javadoc suggests 262,144 documents for natural merges). No map is applied when the reorderer exceeds its RAM budget, when the merge has no float vector field of that name, or when the IndexWriter gate refuses. addIndexes(CodecReader...) passes the same IndexWriter gate but was not executed.
  • What you see. Nothing at write time: no exception, CheckIndex passes (its only parent-aware order check sits in the index-sort test, and reordering never happens with an index sort). At query time block joins return another block's parent or none, nested kNN returns fewer hits, and a delete that finds a root's children through a block join leaves them live. The scramble is persisted; by code reading later merges do not undo it, and reindexing the affected blocks repairs it; documents deleted before the merge stay deleted.
  • Versions. Main only, since #14097 (2025-01-07); CHANGES.txt lists it under 11.0.0. Fixing it before 11.0.0 keeps it out of every release.

Why it is a bug, not intended

#
  • setParentField exists "to maintain the API guarantee that the document order of a block is not altered by the IndexWriter"; addDocuments: "merging will preserve a block".
  • IndexWriter reorders a merge only when the parent field lets the reorder keep blocks (#13128), and the sibling BPIndexReorderer keeps them (#13125).
  • The introducing PR never discusses blocks.
The full argument316 words
  • The contracts. IndexWriterConfig#setParentField (IndexWriterConfig.java:580-588): the parent marker is required "to maintain the API guarantee that the document order of a block is not altered by the IndexWriter". IndexWriter#addDocuments (IndexWriter.java:1499-1500): "the index does not currently record which documents were added as a block. Today this is fine, because merging will preserve a block." Here IndexWriter itself runs the reorder, inside a merge it schedules.
  • The gate. #13128 ("Make OneMerge#reorder preserve blocks", 2024-03-29) changed IndexWriter "to only call OneMerge#reorder when it has a chance to preserve the block structure, ie. either there are no blocks or blocks are identified by a parent field", and made the test framework's MockRandomMergePolicy reverse whole blocks when a parent field is set (MockRandomMergePolicy.java:268-300).
  • The sibling and CHANGES. 9.11.0 CHANGES (lucene/CHANGES.txt:2742-2743): "GITHUB#13125: Recursive graph bisection is now supported on indexes that have blocks, as long as they configure a parent field". BpVectorReorderer's javadoc calls it an "Implementation of recursive graph bisection ... See BPIndexReorderer". TestBPIndexReorderer.testSingleTermWithBlocks asserts complete, parent-last blocks. That entry concerns BPIndexReorderer, the only reorderer at the time, so it shows the design intent rather than a rule for every later reorderer; the setParentField sentence and the #13128 gate are the direct evidence.
  • Intent of #14097. Its PR body: "refactored to make BpVectorReorderer compatible with BPIndexReorderer so that either can plug into BPReorderingMergePolicy". None of its 33 texts (body, reviews, comments) mentions parent, child, nested, join, setParentField or hasBlocks; the 3 hits for "block" are "should not block merging". Upstream's TestBPReorderingMergePolicy picks BpVectorReorderer at random but never uses blocks or a parent field.
  • History repeats. On 9.10.0 the same policy with the postings reorderer broke blocks the same way ("child b4c1 ended up in the block of parent b10p"); 9.11.0 fixed that with #13125 and #13128 (executed). #14097 let a second reorderer into the gated path without the same handling.
The devil's-advocate check386 words

The strongest case for "intended" (an OpenAI GPT-5.6 reviewer with an "intended" lens, and the devil's-advocate verifier): neither the OneMerge#reorder javadoc (@lucene.experimental) nor the IndexReorderer interface (no such tag, like BpVectorReorderer and BPReorderingMergePolicy) says a reorderer must keep blocks; the setParentField javadoc calls the field "optional for all indices that don't use document blocks in combination with index sorting", and MIGRATE says it must be configured "only if index sorting is used together with documents blocks"; addDocuments warns that "in the future Lucene may merge more aggressively re-order documents ... in which case you may need to fully re-index" and that offline re-sorting tools "will likely break them up. Use such tools at your own risk!"; the BPReorderingMergePolicy javadoc still names only BPIndexReorderer; and moving documents without a vector to the end is deliberate and tested (TestBpVectorReorderer.testIndexReorderSparse).

Why it fails: the block duty is stated at the IndexWriter level, and the #13128 gate exists only so that a reorder runs when blocks can be kept; a reorderer that ignores the parent field defeats it. The "future" sentence and the offline-tool NOTE come from LUCENE-3112 (2011, the commit that added addDocuments), long before the parent field (2024). The NOTE is about offline tools; the "future" sentence does foresee merges that reorder documents for compression, which is what this policy does, so the javadoc pulls two ways and the issue should acknowledge it. What settles it: #13128 later made merge-time reordering conditional on the parent field precisely so that blocks are kept. The "optional ... with index sorting" sentence and the MIGRATE note came with #12829 (2024-01-11), before #13128 (2024-03-29) made the same field the condition for reordering an index with blocks at all. (The NOTE does cover BpVectorReorderer's offline reorderIndexDirectory tool, so the issue should say plainly that it is about the merge-policy path.) The policy javadoc is stale, not a restriction: #14097 plugged the vector reorderer into this policy on purpose. Sparse ordering is fine without blocks; with blocks it is exactly what separates parents from children. @lucene.experimental marks an unstable API, not permission to return wrong block-join results. The "intended" lens rated the case moderate in its record and "weak" in its notes; the refute lens, the independent reproducer, the devil's advocate and the adjudication rejected it.

Suggested fix

#

Recommended A: do not reorder segments that have blocks

Stop BpVectorReorderer from reordering segments that have blocks: computeDocMap returns null when the segment has blocks (+8 lines). The test, the closest suites and the whole misc module pass with assertions on and off. The cost: no vector reordering for nested indexes; a block-aware reorderer would keep it, but is untested.

if (vectorScore == null) {
  return null;
}
if (reader.getMetaData().hasBlocks()) {
  // This reorderer moves documents one by one, which would break document blocks (children
  // followed by their parent), so leave segments that have blocks in their current order.
  return null;
}
All options and trade-offs4 options · 800 words

One fix was built and validated in a scratch worktree at ea57360912ed (removed afterwards); the other options come from the adjudication, the verifiers and this doc and were not run.

A: do not reorder segments that have blocks (validated by the checks) (recommended)

#

In BpVectorReorderer.computeDocMap, return null (no reordering) when reader.getMetaData().hasBlocks(), and say so in the class javadoc. +8 lines in BpVectorReorderer.java, no API change.

if (vectorScore == null) {
  return null;
}
if (reader.getMetaData().hasBlocks()) {
  // This reorderer moves documents one by one, which would break document blocks (children
  // followed by their parent), so leave segments that have blocks in their current order.
  return null;
}

Trade-offs

  • Feature loss. Vector reordering is switched off for every segment with blocks, which is the nested-vector layout most likely to want it; those segments keep their merge order, and bp.reordered says false.
  • Offline tool. For indexes without a parent field, reorderIndexDirectory then copies segments with blocks unchanged (SortingCodecReader.wrap accepts a null map) instead of scrambling them (executed). On an index with a parent field the tool already fails before reordering, with and without the fix (IllegalArgumentException: its writer has no parent field), and the run left an empty commit: a possible separate defect, not triaged and not part of this report.
  • Blind spot it inherits. It relies on LeafMetaData#hasBlocks, which segments written before 9.9 do not record. Those indexes cannot have a parent field; that case is a separate bug in the IndexWriter gate (LFV-429) and is not fixed here.

B: make BpVectorReorderer block-aware (untested)

#

Partition whole blocks instead of documents, as BPIndexReorderer does: give all vectors of a block the block's bias (or use one representative per block, such as the centroid of its vectors), sort with blocks as units, and keep documents without a vector inside their block.

Trade-offs

Keeps vector reordering for nested indexes, but it is real work: both the bisection and the "no value at the end" step must change, blocks without any vector need a rule, and ordering quality would need a benchmark.

C: IndexWriter checks the reorder map (untested, defense in depth)

#

In IndexWriter.mergeMiddle and addIndexesReaderMerge, when a parent field is set and the merged view has blocks, verify the returned map against the live documents: every live child must keep the same first live parent after it, and the live documents of a block must stay together and in order; otherwise ignore the map or throw. It also needs a rule for trailing children without a parent, which can occur (LFV-417). The simple predicate "for each non-parent document d, oldToNew(d) + 1 == oldToNew(d + 1)" is enough only for complete blocks without deletions: moving a deleted child breaks it without harm, a block whose parent is deleted can pass it and still leave its live children orphaned, and a trailing child has no d + 1.

Trade-offs

Protects every OneMerge#reorder implementation, custom ones too, for O(maxDoc) per reordered merge. Ignoring the map hides a reorderer's bug; throwing fails the merge. A core change, so it needs core review; combine it with A or B rather than replacing them.

D: document the limitation (not recommended)

#

State in the BpVectorReorderer and BPReorderingMergePolicy javadoc that indexes with blocks are not supported.

Trade-offs

Leaves IndexWriter breaking its own setParentField guarantee without any error. Either way, the BPReorderingMergePolicy javadoc should stop naming only BPIndexReorderer.

Downstream note

#

Once a parent field is set IndexWriter trusts the reorder map, and block joins find a child's root only by position, so children moved by the merge fall under other roots: an application that extends a root's visibility or delete to its children with ToChildBlockJoinQuery then reaches the wrong children. Affected indexes must be reindexed.

How it was found

#

Code reading. While a hunt unit modelled the doc maps that index sorting builds with document blocks, the finder, an AI tool, read every place where IndexWriter applies a doc map and saw that the merge-time reorder path has no block check and that BpVectorReorderer ignores the parent field. A JUnit on the stock jar confirmed it.

LFV-093, snapshot of 2026-10-28

Registry title
Merges through BPReorderingMergePolicy with BpVectorReorderer break document blocks even when a parent field is configured
Area
misc / BP merge-time reordering
Priority
Medium, rank 100: Every merge that BPReorderingMergePolicy with BpVectorReorderer reorders silently scrambles document blocks, so block joins return wrong parents, but it is unreleased (main only) and an expert setup with no known user.0.
Impact class
silent wrong results
Impact note
Applications that opt into the expert lucene/misc BPReorderingMergePolicy with a BpVectorReorderer on an index that has document blocks and IndexWriterConfig#setParentField (and no index sort): every merge the policy reorders silently scrambles the merged segment's blocks, whichever documents carry the vector (children only, parents only or all) and with default reorderer settings, and block-join queries then return the wrong parents and children; ordinary scale (16 blocks suffice); unreleased main (11.0.0) only.
Summary
You index documents in blocks (children followed by their parent) with IndexWriterConfig#setParentField, and use BPReorderingMergePolicy with a BpVectorReorderer over a float vector field. You expect merges to keep every block together with its parent last, because IndexWriter only lets a merge reorder documents when the parent field identifies the blocks, and setParentField promises that IndexWriter does not alter the order of a block. Instead BpVectorReorderer moves each document on its own and puts every document without a vector after all documents with one, so the merged segment's blocks are silently scrambled and ToParentBlockJoinQuery joins children to the wrong parent (59 of 60 children in one run), with no exception and with assertions on or off.
