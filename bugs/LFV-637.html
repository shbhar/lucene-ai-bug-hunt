A Monitor#match that throws leaves ParallelMatcher's worker tasks blocked on the executor forever

ParallelMatcher starts its worker tasks on your executor when a match begins, and only finish() stops them. If the query-index search throws first, for example TooManyClauses for a document with terms in 1,025 query fields, the workers stay blocked until interrupted, and later matches on that pool can hang.

The finding in 30 seconds

#

ParallelMatcher starts its workers when the matcher is created and stops them only in finish(); Monitor#match never calls finish() when the search fails.

Monitor, the presearcher and the matchers

#
  1. A Monitor stores standing queries. Monitor#match(doc, factory) turns the document into a tiny index, asks the presearcher which stored queries could match, and runs those candidates against the document with a CandidateMatcher made by the factory.
  2. The default presearcher's query has one clause per document field whose terms appear in stored queries, so it is subject to the clause limit (IndexSearcher.getMaxClauseCount(), 1,024 by default).
  3. The default matcher runs the candidates on the calling thread. ParallelMatcher.factory(executor, matcher, threads) runs them on threads worker tasks fed through a queue; PartitionMatcher collects all candidates and hands them to the executor at the end.

The finding, step by step

#
  1. Register 1,025 term queries, one per field (f0:x to f1024:x), and match one document that has x in all 1,025 fields with ParallelMatcher.factory(Executors.newFixedThreadPool(1), QueryMatch.SIMPLE_MATCHER, 1).
  2. The presearcher's query needs 1,025 clauses, one over the limit of 1,024, so Monitor#match throws IndexSearcher.TooManyClauses, as the default serial matcher does. You expect that, and an idle pool: awaitTermination(5 s) after shutdown() returns true, as with PartitionMatcher.
  3. Instead the pool is still busy 5 s after shutdown(). The matcher submitted its 1 worker before the search failed; the worker waits in queue.take() for an end marker that only finish() sends, and Monitor#match never calls finish(). Only an interrupt, such as shutdownNow(), frees it.
  4. On a shared pool it sticks: after one failed match on a 2-thread pool with threads = 2, the next valid match on the same pool (still in use) does not return within 10 s. A rejected submit leaks accepted workers the same way; with CallerRunsPolicy on a full pool, Monitor#match itself never returns.

Who is affected

#

Applications that match with the opt-in ParallelMatcher of the optional monitor module. Each match whose query-index search throws strands its threads worker tasks until an interrupt; on a fixed pool sized to threads, one failure hangs every later match on that pool until shutdownNow() or a restart. The serial matcher and PartitionMatcher are unaffected. Rare: unreported since 2019.

Mechanism, terms and numbers672 words

ParallelMatcher's constructor submits threads worker tasks to the caller's ExecutorService before any candidate query exists. Each worker loops on queue.take() until it sees an END marker, and END is put only by finish(). Monitor#match creates the matcher, runs the presearcher and the query-index search, and only then calls finish(); when the search throws, its try-with-resources closes the document batch, but CandidateMatcher has no close or abort method, so nothing releases the workers. They stay parked until something interrupts them, each holding a pool thread; on a fixed pool sized to threads, one failed match makes every later ParallelMatcher match on that pool hang until shutdownNow() (an interrupt) or a restart. The headline trigger is legal input: a document whose terms hit more stored-query fields than the clause limit makes the presearcher throw TooManyClauses, which the serial matcher throws too. Two executor-side triggers hit the same missing release: a rejected submit leaks the workers already accepted, and a worker run on the calling thread (CallerRunsPolicy on a saturated pool, or a direct executor) blocks Monitor#match itself. Monitor#debug has the same shape. The default serial matcher and PartitionMatcher are not affected. Every lucene-monitor release since 8.2.0 and main are affected.

The code

#
  • Workers start in the constructor (ParallelMatcher.java:63-74), before matchQuery has queued anything:
for (int i = 0; i < threads; i++) {
  MatcherWorker mw = new MatcherWorker(matcherFactory);
  futures.add(executor.submit(mw));
}
  • Each worker blocks until END (ParallelMatcher.java:124-138): while ((task = queue.take()) != END) { ... }.
  • Only finish() puts END: doFinish puts one END per worker and waits on each future (ParallelMatcher.java:91-113); CandidateMatcher.finish is its only caller (CandidateMatcher.java:105-106), and CandidateMatcher has no other lifecycle method.
  • Monitor#match has no failure path for the matcher (Monitor.java:218-227):
try (DocumentBatch batch = DocumentBatch.of(analyzer, docs)) {
  LeafReader reader = batch.get();
  CandidateMatcher<T> matcher = factory.createMatcher(new IndexSearcher(batch.get()));
  StandardQueryCollector<T> collector = new StandardQueryCollector<>(matcher);
  long buildTime = queryIndex.search(t -> presearcher.buildQuery(reader, t), collector);
  return matcher.finish(buildTime, collector.queryCount);
}
  • Where the exception comes from: TermFilteredPresearcher adds one TermInSetQuery clause per document field whose terms appear in the query index (TermFilteredPresearcher.java:224-231), and BooleanQuery.Builder.add throws TooManyClauses at the limit (BooleanQuery.java:82-83). A diagnostic stack on main shows it thrown from TermFilteredPresearcher.buildQuery <- WritableQueryIndex.search <- Monitor.java:224: after createMatcher (:222), before finish (:225). With MultipassTermFilteredPresearcher(4) each pass's builder stays under the limit, and the search's clause-count check in IndexSearcher.rewrite throws IndexSearcher.TooManyNestedClauses (a TooManyClauses subclass) instead, from 257 fields on (256 pass); that is also between createMatcher and finish. Any other exception that escapes the query-index search takes the same path, for example the filter-field batch check (TermFilteredPresearcher.java:183-188) or an I/O error from a persistent query index. An exception from a single candidate query does not: StandardQueryCollector.matchQuery catches it and reports it as a match error (Monitor.java:294-303).
  • Monitor#debug (Monitor.java:317-330) has the same create-search-finish shape and leaks the same way (executed for this doc).

Two more triggers of the same missing release

#
  • Rejected submit: if the k-th executor.submit throws RejectedExecutionException (k >= 2), it leaves the constructor with k-1 workers accepted and parked. AbortPolicy is ThreadPoolExecutor's default. Executed: a 1-thread SynchronousQueue pool with threads = 2 still runs the accepted worker 10 s after shutdown().
  • Caller runs: with CallerRunsPolicy on a saturated pool, or a direct executor, submit runs a worker on the calling thread inside the constructor, where it blocks in take() before any task exists. Executed: a pool sized to threads (2 threads, ArrayBlockingQueue(2)) shared by two in-progress matches (built through the public MatcherFactory.createMatcher as stand-ins, not two concurrent Monitor#match calls); a third Monitor#match was still blocked 10 s after the pool went idle. An interrupt ends it with RuntimeException("Interrupted during match").

Not affected

#

The serial matcher (same TooManyClauses, no executor) and PartitionMatcher, which takes the same ExecutorService parameter but submits only in doFinish via invokeAll (PartitionMatcher.java:70-102): after the same failure its pool terminates, and a caller-run task simply runs.

Exposure and likelihood397 words
  • Who. Code that matches with ParallelMatcher.factory(...) from lucene-monitor; the package javadoc offers it "to increase performance in low-concurrency systems" (package-info.java:50-51). The default serial matcher and PartitionMatcher are not affected.
  • Effect. Every Monitor#match or Monitor#debug whose query-index search throws strands the matcher's threads worker tasks until an interrupt; each one that runs holds a pool thread. On a fixed pool of threads threads, the sizing the upstream tests use (a pool of 10 with threads = 10, ConcurrentMatcherTestBase.java:40, :51-52), one failure makes every later ParallelMatcher match on that pool hang, even after the offending document is gone. The caller gets an exception that gives no hint that pool threads are lost; only an interrupt (shutdownNow()) or a restart recovers.
  • Pool shape. On a fixed pool with more threads than threads, later matches keep working until failed matches have taken every thread; on a cached pool parked threads pile up instead (neither executed). A later match on a used-up pool waits in doFinish's future.get() (ParallelMatcher.java:99, executed) or, once its 1,024-slot queue is full, in matchQuery's put (:49, :80, read). The 2-argument factory uses availableProcessors() workers (ParallelMatcher.java:170-184), so one failure can strand that many.
  • Scale. Ordinary: one document and one pool thread in the repro. The headline trigger needs stored queries over more fields than the clause limit (1,024 by default, about 1,024 / passes with MultipassTermFilteredPresearcher) and a document with matching terms in all of them; an I/O error from a persistent query index or a mixed filter-field batch takes the same path. The executor triggers need a rejecting pool or a caller-runs or direct executor.
  • Not executed: an unbounded cached pool (expected: a growing number of parked threads rather than a hang), a pool shared by several Monitors, an end-to-end service scenario.
  • Workaround until fixed. The serial matcher and PartitionMatcher are not affected. An application that keeps ParallelMatcher can wrap its factory, keep the matcher it creates and call its public finish(0, 0) after a failed match; that frees the worker (executed, awaitTermination(5 s) true). Nothing documents this, and finish() also runs any candidates already queued.
  • Likelihood: rare. Each trigger is uncommon among ParallelMatcher users, no downstream user was found and nothing has been reported since 2019; once it happens on a fixed pool, the hang is permanent.

Minimal repro

#

One JUnit class, one method, public API only: register 1,025 one-term queries, match a document that hits all of them with ParallelMatcher on a 1-thread pool, expect TooManyClauses, then assert that the pool terminates within 5 s of shutdown(). It fails with assertions on and off.

Expected
Monitor#match throws TooManyClauses and the pool terminates within 5 s of shutdown(), as with PartitionMatcher.
Observed
TooManyClauses is thrown, but the pool's thread stays parked in ParallelMatcher's queue.take(): expected the pool to terminate after the failed match, but its worker is still running.

Why it looks unintended

#
  • No javadoc puts any requirement on the executor, and Monitor#match itself creates the matcher and drops it on failure; the normal call gives the caller no reference to it.
  • The serial matcher and PartitionMatcher (same executor parameter) throw the same exception and leave nothing behind.
  • The trigger is legal input: the TooManyClauses is expected, only the leaked workers are wrong.
The full argument259 words
  • No documented executor requirement. The javadocs say only "Matcher class that runs matching queries in parallel", "an ExecutorService to use for parallel execution" and "the number of threads to execute on" (ParallelMatcher.java:34-46, :55-62, :157-184); nothing about rejection, caller-thread execution, sizing or cleanup after a failed match. Lucene states such limits where it has them: "The provided Executor must not reject tasks" (BPIndexReorderer.java:834).
  • Lucene's own code drops the matcher. Monitor#match closes its DocumentBatch on failure (Monitor.java:220) but has nothing to call on the matcher. In the normal call, monitor.match(doc, ParallelMatcher.factory(...)), the caller holds no reference to it; releasing the workers needs an undocumented workaround (wrap the public MatcherFactory, keep the matcher, call its public finish() after the failure; executed).
  • The siblings clean up. The serial matcher throws the same TooManyClauses and uses no executor; PartitionMatcher, with the same ExecutorService parameter, throws it and its pool terminates (executed on main and on 8.2.0).
  • The JDK and core Lucene allow caller-runs and rejection. The Executor javadoc lets an executor run a task "immediately in the caller's thread"; ThreadPoolExecutor's default handler is AbortPolicy. Core's TaskExecutor runs a rejected task on the calling thread "to ensure a rejecting executor only reduces parallelism and does not result in failure" (TaskExecutor.java:55-67).
  • Tests. No upstream test makes a ParallelMatcher match fail. The upstream concurrent test runs threads = 10 on a pool of 4 (ConcurrentMatcherTestBase.java:62, :76-77), so "the pool must have threads free threads" is not an upstream assumption.
The devil's-advocate check189 words

The strongest case for "intended" (built by the devil's-advocate verifier; every verifier rated it weak): the class javadoc says the matcher "distributes queries amongst its worker threads using a BlockingQueue" and threads is "the number of threads to execute on" (ParallelMatcher.java:40-42, :61). So the caller must supply an executor that really runs threads long-lived consumer tasks asynchronously; a caller-runs, direct or saturated rejecting pool is a provisioning error, the leaks happen only on exceptional paths where the caller does get an exception, and shutdownNow() frees a dedicated pool.

Why it fails: no text states that precondition, and the upstream test itself runs 10 workers on 4 threads. It does not touch the headline at all: the failed-match leak happens on a correctly sized Executors.newFixedThreadPool with the default policy, because Monitor#match creates the matcher and lets the exception escape without releasing it, and shutdownNow() is not an option for the shared pool the factory invites. The caller-runs part is a separate, more defensible question (which executors are allowed): there a javadoc constraint is a reasonable maintainer answer, which is why the claim leads with the failed-match leak.

Suggested fix

#

Recommended Release the workers when the search fails or a submit is rejected (validated)

Release the workers on failure: a no-op CandidateMatcher#doAbort() hook that Monitor#match and Monitor#debug call when the search throws; ParallelMatcher cancels its worker tasks there, and also when a submit is rejected (+46/-10 lines). It passes the repro and the monitor module's tests. The caller-runs hang needs a separate change or a javadoc note.

// CandidateMatcher: new hook, no-op by default
protected void doAbort() {}

// Monitor#match (the same in Monitor#debug)
long buildTime;
try {
  buildTime = queryIndex.search(t -> presearcher.buildQuery(reader, t), collector);
} catch (Throwable e) {
  matcher.doAbort();
  throw e;
}
return matcher.finish(buildTime, collector.queryCount);

// ParallelMatcher: doAbort() and a failed submit call future.cancel(true) for each worker
All options and trade-offs4 options · 657 words

One fix was built and validated through gradle in a scratch worktree of 645d4fe14a20; it covers the failed-match and rejected-submit triggers and leaves the caller-runs hang. The other options are design sketches, not built.

Release the workers when the search fails or a submit is rejected (validated) (recommended)

#

Add a no-op protected void doAbort() to CandidateMatcher, next to doFinish(). Monitor#match and Monitor#debug call it when the query-index search throws, then rethrow. (A throw from finish() itself needs no hook for ParallelMatcher: doFinish puts every END before it waits.) ParallelMatcher overrides it to call future.cancel(true) on each worker; its constructor does the same for the workers already accepted when a submit throws (for example RejectedExecutionException), and now creates collectorMatcher before the loop.

// CandidateMatcher: new hook, no-op by default
protected void doAbort() {}

// Monitor#match (the same in Monitor#debug)
long buildTime;
try {
  buildTime = queryIndex.search(t -> presearcher.buildQuery(reader, t), collector);
} catch (Throwable e) {
  matcher.doAbort();
  throw e;
}
return matcher.finish(buildTime, collector.queryCount);

// ParallelMatcher: doAbort() and a failed submit call future.cancel(true) for each worker

Trade-offs

  • A running worker is interrupted out of take(), a queued one never starts, and the original exception propagates (ParallelMatcher's doAbort() does not throw; an outside override that throws would replace it, so a PR may add such a failure as suppressed). Successful matches are unchanged; candidate tasks already queued are dropped, which is fine because the match has failed. Cancelled worker tasks still waiting in a bounded executor queue stay there, as no-ops, until a thread takes them.
  • It adds a protected method to a public abstract class. Maintainers may prefer another name, a public abort() (a wrapping CandidateMatcher in another package cannot forward a protected call) or making CandidateMatcher Closeable.
  • cancel(true) interrupts the pool threads that run this matcher's workers, as shutdownNow() does today for the whole pool.
  • It does not fix the caller-runs hang (the worker blocks inside the constructor, before any failure). The study's TLA+ model predicted this: releasing the workers on failure clears the failed-match and rejection deadlocks, not the caller-runs one.

What the checks validated

  • Gradle, scratch worktree of 645d4fe14a20, OpenJDK 25.0.3, seed DEADBEEF (2026-10-31). Stock: the repro fails, and so does a probe that calls Monitor#debug instead. With the fix: both pass with assertions on and off; :lucene:monitor:test runs 183 tests (the module's own 181, the repro and the probe), 1 skipped (@Nightly), 0 failures; checkGoogleJavaFormat, ecjLintMain and forbiddenApisMain pass.
  • The study's other trigger tests on the fixed build: failed match, next match after a failed match, rejected submit, multipass presearcher and filter-field batch now pass; both caller-runs tests still fail, as expected.

Never block a worker that runs on the calling thread (for caller-runs; sketch)

#

Record the constructing thread and let a worker that starts on it return at once; doFinish drains what is left in the queue on the calling thread, and matchQuery runs a task inline when no worker can take it (otherwise its put blocks once the 1,024-slot queue is full). Or submit workers lazily and let the caller help drain the queue.

Trade-offs

Fixes the remaining caller-runs and direct-executor hang, but adds more code to the matching path than the release fix and changes how work is split between threads. Not built or run.

Document the executor requirements (complement)

#

A note on ParallelMatcher.factory that the executor must run the threads workers asynchronously (no caller-runs or direct executor) and that a rejected submit fails the match.

Trade-offs

A plausible maintainer answer for the caller-runs part; alone it leaves the failed-match and rejection leaks in place.

Call finish() on failure instead of adding a hook (considered)

#

No API change: on failure Monitor#match calls matcher.finish(...), which puts END and joins the workers.

Trade-offs

Runs (for PartitionMatcher, starts) every candidate query already collected for a match that has failed, delays the exception until they finish, and can itself throw. Not built.

Downstream note

#

Downstream, a service that matches documents from many sources with ParallelMatcher on a shared pool can lose that pool to a document whose terms span more stored-query fields than the clause limit; the serial matcher and PartitionMatcher avoid it.

How it was found

#

A sweep ran Lucene APIs that take an executor against nine executor behaviours and flagged ParallelMatcher: caller-runs hung, and a rejected submit left the pool running. A TLA+ model of the worker lifecycle then showed the same deadlock for a match that fails after the matcher is created, which became the repro.

The method in full176 words

Method: non-formal first signal (a differential sweep of the real main jar), then a TLA+ model.

  • Sweep. 13 API surfaces that accept an executor, times 9 executor behaviours; oracles: the same result as the executor-less call, a return within 8 s, and an executor that terminates after shutdown(). The ParallelMatcher cells: caller-runs = hang, rejection at the 2nd or 3rd submit = pool never terminates (first run 2026-10-26).
  • Model. ParallelMatcherLifecycle.tla (TLC, deadlock checking on) encodes a failure between createMatcher and finish on purpose; TLC found the failed-match deadlock (12 distinct states) as well as the caller-runs and abort deadlocks, none in the two capacity controls. A fix mutant ("one END per accepted worker on failure") clears the failed-match and abort deadlocks but not the caller-runs one. The verifiers did not re-check the model.
  • Confirmation. A public-API JUnit on stock builds, then an independent reproducer, a devil's-advocate verifier, cross-model reviews (OpenAI GPT-5.6) that ran their own tests, an adjudication and a credibility audit; a follow-up ran the version history, a prior-report search and a security screen.

Finding record

LFV-637, snapshot of 2026-11-08

Registry title
Monitor's ParallelMatcher starts blocking worker tasks in its constructor that only finish() releases: a Monitor#match that fails before finish() (an exception such as TooManyClauses from the presearcher, or a rejected submit) leaves its workers parked on the executor forever, and an executor that runs a worker on the calling thread (CallerRunsPolicy on a saturated pool) makes Monitor#match hang
Area
monitor / ParallelMatcher worker lifecycle (Monitor#match)
Priority
Low, rank 819: One failed match permanently hangs the opt-in ParallelMatcher's pool, which is more reachable than the batch-loss hang LFV-326, so it heads the Monitor hang rows after LFV-207 and above LFV-485 and LFV-326.
Impact class
hang
Impact note
Applications that match with the opt-in ParallelMatcher of the optional monitor module (the default serial matcher and the sibling PartitionMatcher are not affected): once Monitor#match throws after the matcher was created (for example IndexSearcher.TooManyClauses when a document has terms in more fields used by registered queries than the clause limit, 1024 by default or about 1024/passes with MultipassTermFilteredPresearcher), its threads workers stay blocked in queue.take() forever, and on a fixed pool of that size every later ParallelMatcher match hangs until shutdownNow() or a restart; a rejected submit (AbortPolicy, ThreadPoolExecutor's default, on a bounded pool) leaks the workers already accepted; with CallerRunsPolicy on a saturated pool (including a pool sized to threads and shared by concurrent matches) or a direct executor, the calling thread runs a worker inside the constructor and Monitor#match never returns; ordinary scale; every release since 8.2.0 [exec].
Summary
You match documents with Monitor#match using ParallelMatcher.factory(executor, matcher, threads), for example on Executors.newFixedThreadPool(threads), and you expect what the default serial matcher does: Monitor#match returns the matches or throws, and leaves nothing running on your executor. Instead the ParallelMatcher constructor submits threads workers that only finish() can release, so when the match throws before finish() (here IndexSearcher.TooManyClauses from the presearcher for a document with terms in 1,025 fields used by registered queries, the same exception the serial matcher throws) the workers stay parked forever and the next valid match on the same pool never returns. A rejected submit leaks the already-accepted workers the same way, and with CallerRunsPolicy on a saturated pool the calling thread runs a worker itself and Monitor#match never returns.
