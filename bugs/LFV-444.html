The bug in 30 seconds

#

Nori drops punctuation by default, and its opt-in unigram mode splits unknown words into characters. Together, the characters of an unknown word skip the punctuation check.

  1. Build KoreanTokenizer with outputUnknownUnigrams=true, which splits words the dictionary does not know into single characters, and the default discardPunctuation=true, which drops punctuation. Analyze the price 가격: $100 ("price: $100").
  2. You expect [가격, 1, 0, 0]: the :, the space and the $ dropped, 100 split into digits. Lucene 8.1.1 gives exactly that; with unigrams off you get [가격, 100].
  3. You get [가격, $, 1, 0, 0]. $ and 100 are unknown words, so they go through the unigram branch, which adds every character without the punctuation check that the other branch applies. : is a dictionary word and is still dropped.
  4. $ is a real term at position 1, so the digits move one position on: the exact phrase 가격 100 finds 0 documents instead of 1. Line breaks, %, @, tabs and doubled spaces leak the same way, with no error.
  5. It has worked this way since 8.2.0 (2019), when LUCENE-8784 removed the check from this branch while adding the flag. Putting the check back fixes it; kuromoji checks every unigram.

Who is affected

#

Applications that turn on nori's outputUnknownUnigrams (default off) and keep the default discardPunctuation=true, through KoreanTokenizer, the korean factory or KoreanAnalyzer(..., true). Prices, e-mail addresses, line breaks, tabs and doubled spaces then add one-character terms and break exact phrases. Elasticsearch and OpenSearch cannot turn the option on.

Mechanism, terms and numbers742 words

Nori's KoreanTokenizer drops punctuation, symbols and whitespace by default (discardPunctuation=true). Its opt-in outputUnknownUnigrams=true splits each word the dictionary does not know into one-character tokens. With both on, the unigram branch of Viterbi.backtrace adds every character without the shouldFilterToken check that the other branch applies, so the punctuation, symbol and whitespace characters inside an unknown word become terms of their own: 가격: $100 gives [가격, $, 1, 0, 0], 다음\n\n문장 gives [다음, \n, \n, 문장], 50% 할인 gives [5, 0, %, ' ', 할인], and an e-mail address keeps its @ and .. The extra terms carry the SY tag of every unigram, so the default part-of-speech stop filter keeps them, and each one pushes later words one position on, so exact (zero-slop) phrases across them miss (가격 100 finds 0 documents instead of 1). No error. It is opt-in (the korean factory, the constructors and KoreanAnalyzer can turn it on; Elasticsearch and OpenSearch cannot). LUCENE-8784 removed the check in 8.2.0, in the same diff that made shouldFilterToken honour the new flag; 8.1.1 and kuromoji filter each unigram, and putting the check back fixes it.

Terms

#
  • Nori: Lucene's Korean analysis module. KoreanTokenizer finds the cheapest split of the text into dictionary words with a Viterbi search; a stretch the dictionary does not know becomes an unknown word.
  • discardPunctuation (default true): drop tokens that are punctuation, symbols or whitespace. The check is shouldFilterToken: the flag is on and the token's first character is punctuation, a separator, a control or format character, or a math, currency, modifier or other symbol (Viterbi.java:412-445).
  • outputUnknownUnigrams (default false): emit each unknown word as one token per character instead of one token for the word.

The bug

#
  1. Viterbi.backtrace turns the best path into tokens in two branches. The else branch (Viterbi.java:237 on) emits a word as one token; a single-morpheme word, or any word in mode NONE (:248-249), is added only if (shouldFilterToken(token) == false) (:250). Unknown words and dictionary punctuation such as : take this checked path (with unigrams off, : and $ are dropped).
  2. With unigrams on, an unknown word takes the first branch (:214): it loops over the word's characters, builds one token per character from the NGRAM entry of the unknown dictionary, and calls pending.add(token) with no check (:232).
  3. So every punctuation, symbol or whitespace character that is part of an unknown word is emitted, whatever discardPunctuation says.
  4. Every unigram gets the part-of-speech tag SY (dict/UnknownDictionaryBuilder.java:31), which is not in KoreanPartOfSpeechStopFilter.DEFAULT_STOP_TAGS (:36-68). The leaked tokens pass KoreanAnalyzer's stop filter, and no part-of-speech filter can remove only them: letters and digits of unknown words carry the same tag.
  5. Each leaked token takes a position, so every later token moves one position on per leaked token.

Exposure and likelihood432 words
  • Who is exposed. Nori users who turn on unigram mode and keep the default flag: the 4-argument KoreanTokenizer constructor (it always passes discardPunctuation=true, KoreanTokenizer.java:104-110) or the 5-argument one with true, true; the korean factory with outputUnknownUnigrams="true" (discardPunctuation defaults to true, KoreanTokenizerFactory.java:96-97; Solr schemas expose both); KoreanAnalyzer(userDict, mode, stopTags, true), which has no discardPunctuation option and always uses true (KoreanAnalyzer.java:57-74). The classes are @lucene.experimental.
  • Not exposed. The default configuration (unigrams off), and users who set discardPunctuation=false. Elasticsearch and OpenSearch pass a literal false for outputUnknownUnigrams in their nori tokenizer and analyzer, so their settings cannot reach it (read in their source; not executed).
  • What triggers it. Ordinary text with a punctuation, symbol or whitespace character inside an unknown-word run: prices ($100, 50%), e-mail addresses, C++, ab#cd, tabs, line breaks, a space after a symbol, and since 8.10.0 doubled spaces. Deterministic: every such document, every time.
  • Effect on the index. Extra one-code-point terms such as $, @, ., %, a newline or a space, which the default stop filter keeps; and shifted positions, so an exact (zero-slop) phrase across the character misses; slop can absorb the gap. Executed: the phrase 가격 100 misses 가격: $100; the phrase 회의 자료 ("meeting materials") misses documents with $, U+200B, a doubled space, two newlines or U+00AD between the words, and matches them with the fix; the same probe's slop-2 phrase matches the same documents with and without the fix.
  • Effect on queries. Query text with such a character gains a junk term (createBooleanQuery("$") becomes body:$).
  • Not affected. Term queries over punctuation-free words; no term the fixed code emits is lost; offsets are exact and CheckIndex is clean. No hang or amplification: 1M-character punctuation inputs ran at 0.97-1.24x an all-letter control, at most one token per character.
  • No equivalent stock token-filter workaround. A token filter that empties punctuation-only tokens and drops empty ones removes the terms but keeps the position gaps (가격@0, 1@2, ..., executed), so exact phrases would still miss. A patternReplace char filter that turns [\p{P}\p{S}\p{Cc}\p{Cf}\p{Z}]+ into one space in front of the tokenizer gave gap-free output on the 7 inputs tried (가격: $100 -> [가격@0, 1@1, 0@2, 0@3], executed), but it changes the text the tokenizer segments, removes punctuation the dictionary would handle, was tried on 7 inputs only and must be in both the index-time and the query-time analyzer. Otherwise turn unigrams off, or apply the fix and reindex: existing indexes keep the extra terms until then.

Why it is a bug, not intended

#
  • The discardPunctuation javadoc is unconditional: "true if punctuation tokens should be dropped from the output" (KoreanTokenizer.java:119).
  • 8.1.1 drops the $; 8.2.0 keeps it; 8.2.0 with only the removed check restored drops it again.
  • Kuromoji checks every unigram (ViterbiNBest.java:448), and the 8.2.0 CHANGES entry keeps punctuation only when the flag is false.
The full argument371 words
  • The contract. "@param discardPunctuation true if punctuation tokens should be dropped from the output" (KoreanTokenizer.java:119, :150; the factory says the same, KoreanTokenizerFactory.java:61). outputUnknownUnigrams is documented only as "if true outputs unigrams for unknown words" (:102, :118, :149): how unknown words are split, not that punctuation is kept.
  • The introducing change's own words. CHANGES 8.2.0: "LUCENE-8784: The KoreanTokenizer now preserves punctuations if discardPunctuation is set to false (defaults to true)." (lucene/CHANGES.txt:6318-6319).
  • History. Nori's first release (LUCENE-8231, 7.4.0) checked every unigram; the check is in every tag from 7.4.0 to 8.1.1. LUCENE-8784 (a556925eb8a, 8.2.0) made shouldFilterToken return discardPunctuation && isPunctuation(...) and, in the same diff, replaced the checked add in the unigram branch with an unconditional one. The flag-aware check already returns false when the flag is false, so the option did not need the check removed: on 8.2.0 with the check restored, discardPunctuation=false still keeps every character (가격: $10.5 gives [가격, :, ' ', $, 1, 0, ., 5]), and the default drops punctuation again. Removing it changed only the default case.
  • The record. Neither the commit message, the CHANGES entry nor any of the 17 comments of #9828 mentions the punctuation check in the unigram branch or a change to the default output. Two of the comments are the commit notices of db334c792be and its branch_8x copy, which a day later restored the NGRAM part-of-speech tag that the patch had changed "inadvertenly" (sic) on the unigram path; they did not touch the check. That shows one unintended side effect of the patch; it is circumstantial, not evidence about the removed check itself.
  • Maintainers on record. "Punctuations are removed by default" (#10020) and "The tokenizer removes punctuations so it's expected that some characters are filtered" (#9739).
  • The sibling. Kuromoji checks each EXTENDED-mode unigram (ViterbiNBest.java:448); executed (saved run of the verifier), JapaneseTokenizer gives 価格: $100 -> [価格, 1, 0, 0] and ab cd -> [a, b, c, d].
  • Tests. The only deterministic unigram input in TestKoreanTokenizer is 2018 평창 동계올림픽대회, with no punctuation (two assertions on it, :366-372 and :374-405); its punctuation tests use discardPunctuation=false with unigrams off. No test asserts punctuation unigrams.
The devil's-advocate check274 words

The strongest case for "works as designed" (the intended-behaviour checker): read literally, "outputs unigrams for unknown words" covers every character of an unknown word; a committer signed off on the removal; LUCENE-8784 was about keeping the decimal point, and unigram mode does keep the . of 10.1; the classes are @lucene.experimental; no report was found since 2019; the flag still drops separators and dictionary punctuation in unigram mode; users can filter the tokens themselves; and changing it now changes the analysis for anyone who relies on the punctuation unigrams.

Why it fails: the discardPunctuation javadoc is unconditional and the CHANGES entry keeps punctuation only when the flag is false. 7.4.0 to 8.1.1 filtered, and restoring only the check on 8.2.0 brings that back without hurting the new option. Kuromoji filters each unigram, and maintainers said punctuation is removed by default. The record shows no decision to change the default; the next-day NGRAM tag fix is circumstantial only. Keeping the . also when the flag is true goes beyond the issue's stated design, though that does not settle what the patch author intended. Filtering downstream does not work cleanly with token filters: the leaked tokens share the SY tag with every unigram, and a token filter leaves position gaps (a char filter avoids them on the inputs tried but changes the text the tokenizer sees). Few reports fit an opt-in option that two prominent downstream servers cannot turn on. The compatibility point and the explicit patch review are real: the fix changes analysis output for unigram users and needs a CHANGES line and a reindex note. Verdict: on balance not intended, a regression.

Suggested fix

#

Recommended Check each unigram with shouldFilterToken

Check each unigram with shouldFilterToken, as the other branch does and as 7.4.0 to 8.1.1 did: wrap pending.add(token) at Viterbi.java:232 in if (shouldFilterToken(token) == false). Trade-offs

  • Behaviour: unigram mode with the default flag drops punctuation again, including the . of 10.1 ([1, 0, ., 1] becomes [1, 0, 1]). Users who want it set discardPunctuation=false, which keeps it with or without the fix, or follow the keepDecimalPoint proposal #15894.
  • Existing indexes keep the extra terms until reindexed; after the upgrade, exact phrases across punctuation match newly indexed documents but still miss old ones (reasoning). Worth a CHANGES line.
  • Cost: one check per unigram and fewer tokens; no slowdown seen in the follow-up's 1M-character runs (one shared host, so only "no measurable change" is claimed).
  • Backport: on 8.x and 9.x the same block is in KoreanTokenizer.backtrace (the code moved to Viterbi in 10.0.0); only main was built and tested with gradle.
  • Not covered (pre-existing, both branches): shouldFilterToken checks only the first char, so an emoji or other supplementary symbol is still emitted, and a BMP non-spacing mark such as U+FE0F is not in its classes either; with the fix the phrase 회의 자료 still misses 회의😀자료.

Workaround until a fix ships

#

Turn outputUnknownUnigrams off. Or remove the terms with a token filter: a patternReplace filter that empties punctuation-only tokens (^[\p{P}\p{S}\p{Z}\p{Cc}\p{Cf}]+$ to "") followed by length with min=1 (executed). Or rewrite the text first with a patternReplace char filter that turns [\p{P}\p{S}\p{Cc}\p{Cf}\p{Z}]+ into one space in front of the korean tokenizer (executed on 7 inputs).

Trade-offs

The token filter keeps the position gaps (가격@0, 1@2, ..., executed), so exact phrases across the removed characters would still miss (reasoning). The char filter gave gap-free output on the 7 inputs tried, the same as the fixed tokenizer where compared, but it changes the text the tokenizer segments, removes punctuation the dictionary would handle and must be in both the index-time and the query-time analyzer (reasoning). Turning unigrams off changes how every unknown word is indexed.

Downstream note

#

Downstream, an exact-phrase rule on a field analyzed this way, allow or deny, can miss a document whose two words are separated by $, a line break or another leaked character; term-based rules are unaffected.

How it was found

#

Semi-formal. A bounded-exhaustive sweep of 91 SPI-built analysis chains checked, among eight oracles, that a probe's first character appears in the output as often near a buffer edge as far from one. Nori's unigram mode with a space probe was the only hit not explained by design; the finder reduced it to the general punctuation leak and found the cause.

The method in full254 words

Method: bounded-exhaustive buffer-edge sweep with metamorphic oracles (the hunt's "semi-formal" tier), hunt unit "SPI analysis-chain fuzzing", 2026-10-26.

  • The sweep built 91 analysis chains only through SPI names and legal parameters (CustomAnalyzer) and analyzed, for every chain, filler alphabet (13), probe string (13) and insertion position around buffer and refill boundaries (255 to 16384), plus a control position far from any boundary: 900,263 checks per run, two runs.
  • Eight oracles: no exception, offsets in range, start offsets non-decreasing, final offset, position increments and lengths, no unpaired surrogates, probe preservation (W7: the probe's first code point occurs in the emitted terms as often as at the control position), and reuse identity.
  • W7 fired on many chains; the hunt triaged the other hits as by design (filters that multiply, merge or drop tokens, the 255-character token limit, dictionary lemmas and transliterations that contain spaces). The korean tokenizer with outputUnknownUnigrams=true and the space probe was the only W7 hit not explained by design and the only nori configuration with any violation: 71 rows in the first run (5 in the second), where the number of spaces in the emitted terms differed from the control position. That a space shows up in the terms at all is the leak.
  • The finder saw that the leak does not depend on buffer edges, cut it down by hand to the general punctuation leak, found the cause by reading Viterbi.backtrace and the LUCENE-8784 diff, and wrote the public-API JUnit. Independent AI tools then reproduced and judged it (see the checks).

Bug record

LFV-444, snapshot of 2026-10-29

Registry title
KoreanTokenizer with outputUnknownUnigrams=true emits every punctuation, symbol and whitespace character inside an unknown word as its own token ('$', '@', '.', ' ', '\t', '\n') although discardPunctuation=true (the default): LUCENE-8784 (8.2.0) dropped the punctuation check from the unigram branch
Area
analysis / nori KoreanTokenizer (Viterbi.backtrace unigram branch; KoreanTokenizerFactory, KoreanAnalyzer)
Priority
Medium, rank 144: With nori's opt-in outputUnknownUnigrams, ordinary Korean text with prices, e-mails or line breaks deterministically gets extra punctuation tokens that break phrase matching, the same opt-in CJK silent-analysis profile as LFV-360.
Impact class
silent wrong results
Impact note
Applications that analyze Korean text with KoreanTokenizer, the 'korean' tokenizer factory or KoreanAnalyzer with the opt-in outputUnknownUnigrams=true (default false) and the default discardPunctuation=true, in every release from 8.2.0 to 10.5.2 and main, index every punctuation, symbol, format or whitespace character that falls inside an unknown-word run (prices such as '$100', e-mail addresses, line breaks, tabs and, since 8.10.0, doubled spaces) as its own one-character term with part-of-speech tag SY, which the default stop tags do not remove; each such term takes a position, so exact-phrase and other position queries across it miss the document (executed), queries analyzed with the same analyzer gain such terms, and no term the fixed code emits is lost; no exception, no index damage, ordinary text at any size; Elasticsearch and OpenSearch nori settings cannot enable the option (read in source).
Summary
You analyze '가격: $100' or '다음\n\n문장' with KoreanTokenizer(factory, null, DISCARD, outputUnknownUnigrams=true, discardPunctuation=true), or with the 'korean' factory given only outputUnknownUnigrams="true", and expect punctuation and whitespace to be dropped, as the discardPunctuation javadoc says ('true if punctuation tokens should be dropped from the output') and as happens with outputUnknownUnigrams=false ([가격, 100], [다음, 문장]) and in 7.4.0-8.1.1. Instead you get [가격, $, 1, 0, 0] and [다음, \n, \n, 문장], and 'test@example.com' keeps its '@' and '.': the unigram branch of nori's Viterbi.backtrace adds each single-character token of an unknown word without the shouldFilterToken check that the other branch applies. Every such character becomes an index term and pushes the following words one position further, so an exact phrase across it no longer matches.
Introduced
a556925eb8aaea61e55010a6e5c90520139b56c3 (master; first released in 9.0.0) and its branch_8x backport 990f62aca47fc0571c79e80f25ee1d0b7dc4a824 (same Java changes; the commit 8.2.0 ships): LUCENE-8784 'The KoreanTokenizer now preserves punctuations if discardPunctuation is set to false (defaults to true)' (GitHub issue apache/lucene#9828; committed from a JIRA patch attachment, no pull request; author danmuzi, committer jimczi). In KoreanTokenizer.backtrace it replaced 'if (shouldFilterToken(token) == false) { pending.add(token); ... }' in the outputUnknownUnigrams branch with an unconditional pending.add(token), in the same diff that made shouldFilterToken return 'discardPunctuation && isPunctuation(...)' [read: git show; git log -S shouldFilterToken finds no other change to the guard; git blame -C -C -M on today's Viterbi.java:232-234 still attributes the lines to a556925eb8a] [exec: on 8.2.0, restoring only the removed guard turns the probe and the 8.x JUnit from fail to pass, and discardPunctuation=false still keeps punctuation with or without the guard]. The code moved unchanged into nori Viterbi.java with LUCENE-10493 (c89f8a7ea1e, #805, first released in 10.0.0). Regression: the original nori code (LUCENE-8231, e851b89cbeb, 7.4.0) filtered unigrams. LUCENE-10081 (4df8d641ace, #272, released in 8.10.0 and 9.0.0) later widened the inputs that reach the branch (the second of two spaces now lands in an unknown word); it is a correct fix, not a second root cause [exec: reverting only it on 9.0.0 removes the ' ' token and leaves the '$', newline, '@' and '.' leaks] (2019-05-27 (commit date of a556925eb8a; authored 2019-05-24))
