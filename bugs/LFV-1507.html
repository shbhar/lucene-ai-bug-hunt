The finding in 30 seconds

#

Vectors in a segment are numbered 0, 1, 2, ... in document order: the ordinal. If every document has a vector, ordinal and document id are equal. If not, the reader must translate. On 9.8.0 to 9.12.3 the reader of the Lucene 9.1 format returns kNN hits without that translation.

Background: three pieces

#
  1. Lucene 9.1.0 wrote vectors in its own format, Lucene91. Later releases write newer formats and read an old segment through Lucene91HnswVectorsReader (module backward-codecs) until a merge rewrites it.
  2. Inside a segment the vectors are numbered 0, 1, 2, ... in document order. That number is the ordinal. The HNSW graph search works on ordinals.
  3. When some documents have no vector, ordinal and document id differ. The format stores the document id of every ordinal, and the reader translates each hit with it.

The finding, step by step

#
  1. Your index still holds a segment that Lucene 9.1.0 wrote, and only some of its documents have a vector. The test's example: two documents, document 0 has no vector, document 1 has the vector [1, 0].
  2. On Lucene 9.12.3 you run new KnnFloatVectorQuery("v", new float[] {1, 0}, 1), a kNN query without a filter. You expect document 1, the only document with a vector.
  3. You get document 0, which has no vector. No error, with assertions on or off. Lucene 9.7.0, 10.6.0, branch_11x and main return document 1.
  4. A second example, written by the 9.1.0 release itself: five documents d0 to d4, vectors on d0, d1, d3 and d4. The four k = 1 queries for those vectors should return d0, d1, d3, d4. Lucene 9.8.0 and 9.12.3 return d0, d1, d2, d3, each with score 1.0: d2 has no vector, and d3 holds another vector.
  5. Why: the reader finds the right vector but reports its ordinal (its number among the segment's vectors) as the document id. Since 9.8.0 the hit's id is translated by a method that this reader's values class lacks on the 9.x line, so the inherited default runs, and it returns the ordinal unchanged.

Who is affected

#

Applications on Lucene 9.8.0 to 9.12.3 whose index still holds a segment that 9.1.0 wrote and no merge has rewritten since, with a vector field that some documents lack, searched by kNN queries without a filter. Default configuration, silent, CheckIndex reports no problem. Rare: 9.1.0 was current from March to May 2022. IndexUpgrader or a rewriting merge repairs it. Update 2026-11-16: a filter does not prevent it: when its graph search completes, a kNN query with a filter returns the ordinals too, and a hit can then be a document that the filter excludes (detail under Exposure and likelihood, Which queries).

Mechanism, terms and numbers822 words

Lucene 9.1.0 wrote vectors in its own format (Lucene91). Later releases read such a segment through Lucene91HnswVectorsReader in the backward-codecs module until a merge rewrites it. Since the merged #12434 (first released in 9.8.0) the reader's search no longer maps a hit's graph ordinal to its document id itself: it wraps the collector as new OrdinalTranslatedKnnCollector(knnCollector, vectorValues::ordToDoc) (Lucene91HnswVectorsReader.java:260 at the 9.12.3 tag). On the 9.x line the reader's values class declares no ordToDoc(int) (:404-405), so the default of RandomAccessVectorValues runs, which returns its argument (RandomAccessVectorValues.java:62-64). The hit is therefore collected with the ordinal as its document id. The class does hold the right mapping (:428) and uses it for iteration, and the accept check of the same search maps through the field entry (:293).

A hit before the first document without a vector keeps its id, because ordinal and document id are equal there. Every hit behind it is reported under a lower document id of the same segment: a document without a vector, or one that holds a different vector. If that document is deleted, the hit is dropped, so the query returns fewer hits or none. The score is the right vector's score, and nothing is thrown.

This is the reader's graph search. A KnnFloatVectorQuery without a filter always runs it (AbstractKnnVectorQuery.java:127-129 at the 9.12.3 tag), and that is the form the test and the probe run. A query whose filter matches at most k documents is answered by exact search, which goes through the documents by document id, and is right.

On main (781025d6fe32) and branch_11x (daa54f2e0cd3), which have the same reader file, the wrapping line is the same (:262) and the values class declares the method (:485-488, added by the merged #13779 before 10.0.0), so every 10.x release, branch_11x and main are right. This is the sibling of the known defect of the merged #13910 (the Lucene 9.0 reader, Lucene90HnswVectorsReader; LFV-1505): the same change took the mapping out of both old readers' search, as Michael Sokolov found and described there for the Lucene 9.0 reader. The Lucene 9.1 reader is another class with another fix site, other affected releases and other affected indexes.

At the 9.12.3 tag (the defect)

#

Lucene91HnswVectorsReader.java is lucene/backward-codecs/src/java/org/apache/lucene/backward_codecs/lucene91/Lucene91HnswVectorsReader.java.

  1. The field entry reads the mapping from the meta file (:340-356): ordToDoc = null when every document has a vector (:342), else one document id per ordinal (:350-354). FieldEntry.ordToDoc(int) applies it (:398-400).
  2. search (:246-263) wraps the collector at :260: new OrdinalTranslatedKnnCollector(knnCollector, vectorValues::ordToDoc). Each graph ordinal goes through the values object's ordToDoc.
  3. The values class OffHeapFloatVectorValues (:404-405) declares no ordToDoc(int). It holds the right mapping (ordToDocOperator, :428) and uses it for iteration only (:462, :481).
  4. So the interface default runs: "Translates vector ordinal to the correct document ID. By default, this is an identity function.", default int ordToDoc(int ord) { return ord; } (RandomAccessVectorValues.java:56-64 in core).
  5. OrdinalTranslatedKnnCollector.collect passes the result on as the document id: return in.collect(vectorOrdinalToDocId.apply(vectorId), similarity); (OrdinalTranslatedKnnCollector.java:63-64).
  6. In the same search the accept check maps correctly: getAcceptOrds calls acceptDocs.get(fieldEntry.ordToDoc(index)) (:283-301, :293). Only the hit's id takes the identity default.

On main 781025d6fe32 (right; the same file on branch_11x daa54f2e0cd3)

#
  • search (:248-265) has the same wrapping line (:262).
  • The values class (:435) has the same ordToDocOperator (:455) and declares @Override public int ordToDoc(int ord) { return ordToDocOperator.applyAsInt(ord); } (:485-488), added by the merged #13779.

Why it looks unintended

#
  • KnnFloatVectorQuery promises "the k nearest documents", and the format stores "the docids of documents having vectors" for this case.
  • A regression: 9.1.0 to 9.7.0 and every 10.x release are right.
  • The same symptom in the Lucene 9.0 reader was treated as a backwards-compatibility bug: #13910 (Michael Sokolov) fixed it on main, and #13947 (Ben Trent) changed that reader for 9.12.1.
The full argument339 words
  • The contract is a document id. KnnFloatVectorQuery: "Find the k nearest documents to the target vector according to the vectors in the given field" (KnnFloatVectorQuery.java:53-54 at the 9.12.3 tag, :55-56 on main). KnnCollector.collect: "Collect the provided docId and include in the result set." with "@param docId of the vector to collect" (KnnCollector.java:60-62 at the tag, :62-64 on main). OrdinalTranslatedKnnCollector exists for "translating the provided vectorId ordinal to a documentId" (:25).
  • The input is documented. KnnFloatVectorField: "A field that contains a single floating-point numeric vector (or none) for each document" (:29). The Lucene 9.1 format's file layout has a marker for a field with "some documents missing values" and then stores "for sparse case, the docids of documents having vectors, in order" (Lucene91HnswVectorsFormat.java:70-72).
  • Later versions promise to read this format. Lucene91Codec.getKnnVectorsFormatForField in 9.1.0: "future version of Lucene are only guaranteed to be able to read the default implementation" (Lucene91Codec.java:201-202 at the 9.1.0 tag). The probe's index is that default implementation.
  • A regression. 9.7.0 maps the hit through the field entry (:261) and returns the right document, as do 9.1.0 to 9.6.0 and 10.0.0 to 10.6.0.
  • Sibling classes declare the method. At the 9.12.3 tag the values classes of the Lucene 9.2 and 9.4 formats declare ordToDoc(int) for a field that some documents lack (lucene92/OffHeapFloatVectorValues.java:215, lucene94/OffHeapFloatVectorValues.java:223). The classes of the two oldest readers do not.
  • Upstream treated the same symptom as a bug. The description of #13910: "In Lucene90HnswVectorsReader we messed up (removed) ord-to-doc mappings so we were returning vector ords instead of docids in search results" (Michael Sokolov); the user notice drafted on that thread calls it "a backwards compatibility bug". #13910 fixed that reader on main, and #13947 (Ben Trent) changed it for 9.12.1.
  • Why tests did not see it. Upstream's TestLucene91HnswVectorsFormat passes 51 of 51 on the stock 9.12.3 jars, so that suite does not detect it. BaseKnnVectorsFormatTestCase.testRecall, which #13910 added on main, is not in the 9.12.3 test framework.
The devil's-advocate check212 words

The strongest case for "intended": the javadoc of RandomAccessVectorValues.ordToDoc says "By default, this is an identity function", the vector APIs behind the query are marked experimental, and the 9.x line is in maintenance, so a values class that keeps the default could be called documented behaviour for an old format that few indexes still hold.

Why it fails: the sentence before it says the method "Translates vector ordinal to the correct document ID", and the identity is correct only when every document has a vector. This class is built with the real mapping and uses it for iteration, and the accept check of the very same search uses the real mapping too, so one search translates the filter one way and the hit another way. The experimental mark warns about API changes; it does not cover wrong hits from a format that the writing release said later versions would read. The maintainers treated the identical symptom in the neighbouring reader as a backwards-compatibility bug, fixed it on main and released a change for it in a 9.x bug-fix release. What remains is not an argument for "intended" but two limits, both stated on this page: the reach is narrow, and moving to 10.x, which reads these segments right, is a likely answer.

#

Semi-formal: release jars were compared on the same index. During a check of the known sibling defect in the Lucene 9.0 reader, queries on a segment written by 9.1.0 returned other documents on 9.8.0 to 9.12.3 and the right ones on 10.x. It was reduced to one two-document test and separated from the sibling by repairing each reader alone.

The method in full217 words

Method: semi-formal (the real release jars are checked against the answer of the release that wrote the segment and of the releases before the regression; no model checking, SMT solving or proof tool was involved).

  • A side check of the sibling. The history of the known defect of #13910 (the Lucene 9.0 reader) was being traced release by release. As a side check the same kNN queries were run on a segment written by the 9.1.0 release jars: wrong on 9.8.0 to 9.12.3, right on every 10.x release, branch_11x and main.
  • A matrix of builds. The observation was repeated with an eight-document index written by the 9.1.0 release jars on nine builds, and with each old reader repaired alone.
  • Reduction. It was reduced to one JUnit test without a binary index: two documents written with upstream's test-side writer of the Lucene 9.1 format, whose vector files equal those of the 9.1.0 release for the same documents.
  • Separation from the sibling. On the 9.12.3 jars this fix alone leaves a 9.0.0-written segment wrong, and a repair of the Lucene 9.0 reader alone leaves the 9.1.0-written segment wrong. Michael Sokolov found the family and its origin (#12434, first released in 9.8) on #13910 for the Lucene 9.0 reader; this finding is the same loss in the Lucene 9.1 reader.
