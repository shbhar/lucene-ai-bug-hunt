ComplexPhraseQuery.equals ignores the analyzed phrase, so DisjunctionMaxQuery drops one of two differently analyzed phrases

Two ComplexPhraseQueryParsers, one case-sensitive and one with StandardAnalyzer, turn "Foo Bar" on one field into queries that compare equal yet match 0 and 1 documents, so a DisjunctionMaxQuery of both runs only the first and finds 0 hits instead of 1. Affected: 9.0.0 through 10.6.0, and main.

The finding in 30 seconds

#

ComplexPhraseQueryParser turns a quoted phrase into a ComplexPhraseQuery that holds the phrase as analyzed by that parser's analyzer, and searching uses that analyzed form. Two queries that are equals() should match the same documents: core classes such as DisjunctionMaxQuery rely on it to merge duplicates.

  1. Index one document, body: "foo bar", with StandardAnalyzer. Parse "Foo Bar" for body with two ComplexPhraseQueryParsers: exact uses an analyzer that keeps case and matches 0 documents; folded uses StandardAnalyzer and matches 1.
  2. Search new DisjunctionMaxQuery(List.of(exact, folded), 0f). You expect 1 hit: a dis_max matches the union of its subqueries.
  3. Instead you get 0 hits, with no error. Swap the two, [folded, exact], and you get 1.
  4. Why: ComplexPhraseQuery.equals and hashCode compare the field, the raw phrase text, the slop and inOrder, never the phrase as each parser analyzed it, so exact.equals(folded) is true. Since 9.0.0 the dis_max keeps its subqueries in a hash-based multiset: the second "equal" one only raises a count, and the first one runs twice.

Who is affected

#

Applications that use the opt-in ComplexPhraseQueryParser with two differently configured parsers for one field (case-sensitive vs folded, or with vs without query-time synonyms), parse the same phrase with both and combine them in a DisjunctionMaxQuery. The second query's matches silently disappear. Phrases on different fields and BooleanQuery results are not affected.

Mechanism, terms and numbers458 words

ComplexPhraseQueryParser returns a ComplexPhraseQuery for each quoted phrase. A second parse pass fills its contents[0] by parsing the phrase text with the creating parser, so with that parser's analyzer and settings, and rewrite() derives its result from it. equals and hashCode compare only the field, the raw phrase text, the slop and inOrder. So the same phrase parsed by a case-sensitive and by a case-folding parser gives two queries that are equal, with equal hash codes, but match different documents, which breaks the Query#equals contract (equal queries typically have identical document-filtering properties). Since 9.0.0 (LUCENE-9940) DisjunctionMaxQuery keeps its disjuncts in a hash-based Multiset, so it keeps the first-inserted query, runs it twice and never runs the other: the dis_max of [exact, folded] finds 0 documents instead of 1, and [folded, exact] finds 1. Affected: every release from 9.0.0 through 10.6.0, and main. Comparing contents[0] in equals (and leaving hashCode as it is) fixes it.

  • DisjunctionMaxQuery stores its disjuncts in a Multiset<Query> (DisjunctionMaxQuery.java:47, filled at :69). Multiset.add is map.put(e, map.getOrDefault(e, 0) + 1) on a HashMap (Multiset.java:81): an equal second disjunct keeps the first key with count 2, and the iterator returns that key twice (:58).
  • DisjunctionMaxQuery.rewrite() iterates the Multiset (:264-300; loops at :275 and :283), so the first-inserted query runs in both slots, for every tie breaker (at 1.0 it builds a BooleanQuery from the same iteration).
  • Not affected, by reading: phrases on different fields (the field is compared); BooleanQuery search results, because BooleanQuery.rewrite rewrites every clause from its clause list (BooleanQuery.java:299-341) before it removes duplicate FILTER and MUST_NOT clauses (:343); LRUQueryCache, which caches rewritten queries.

Exposure and likelihood176 words
  • Who is hit. Users of the opt-in ComplexPhraseQueryParser (queryparser module) who parse the same user phrase for the same field (same slop and inOrder) with two differently configured parsers and put both queries into one DisjunctionMaxQuery.
  • What happens. Documents that only the second query matches are missing, and scores can differ. The result depends on the order of the disjuncts. No exception, assertions on or off.
  • Also exposed: any consumer that de-duplicates unrewritten queries by equals, such as an application cache keyed on parsed queries (by reading, not run). The monitor module's QueryDecomposer collects the disjuncts of getDisjuncts() into a LinkedHashSet (QueryDecomposer.java:46-51), which also keeps only exact (checked by running decompose on main).
  • Scale. The cause is query equality, which never reads the index, so index size, codec and searcher settings should not matter (by reading); executed on a one-document index, with assertions on and off and several seeds.
  • How likely. Rare: the common multi-analyzer setup uses separate fields (body vs body_exact), which compare unequal and are not affected.

Why it looks unintended

#
  • Query#equals asks that equal queries have identical document-filtering properties; these two match 0 and 1 documents.
  • DisjunctionMaxQuery is documented to match the union of its subqueries.
  • SOLR-6011 fixed this same equals in 2014 for leaving out inOrder, and its test asserts that a parser setting that changes the query makes two parses unequal.
The full argument174 words
  • The contract. Query#equals: "Override and implement query instance equivalence properly in a subclass. This is required so that {@link QueryCache} works properly. Typically a query will be equal to another only if it's an instance of the same class and its document-filtering properties are identical to those of the other instance." (Query.java:95-101).
  • The consumer's contract. DisjunctionMaxQuery "generates the union of documents produced by its subqueries" (DisjunctionMaxQuery.java:30). Its Multiset is sound when equals means equivalence, so the fix belongs in ComplexPhraseQuery.
  • Precedent. SOLR-6011 (fix commit 54cfa922ae3, Yonik Seeley, 2014, "ComplexPhraseQuery hashCode/equals fix for inOrder"). TestComplexPhraseQuery.testHashcodeEquals still asserts that after qp.setInOrder(false); // SOLR-6011 a new parse is unequal (TestComplexPhraseQuery.java:198-223).
  • Siblings compare the configuration that shapes the query. MoreLikeThisQuery.equalsTo compares its analyzer (MoreLikeThisQuery.java:171-177); the surround parser's RewriteQuery.equalsTo compares its query factory (RewriteQuery.java:61-65, after LUCENE-2945).
  • Nothing found that pins the current behaviour. In the source, tests, CHANGES and MIGRATE we found no entry that says the analyzed phrase is left out of equality on purpose.
The devil's-advocate check149 words

The case: a ComplexPhraseQuery is a deferred placeholder whose identity is its source text, like its toString(); contents[0] is mutable state filled in by the second pass, so it cannot be hashed; Lucene's own query cache only sees rewritten queries; and open #16820 proposes deprecating the parser.

Why it is still worth fixing: mutable contents justify leaving contents[0] out of hashCode only, which the recommended fix does. A core consumer, DisjunctionMaxQuery, de-duplicates the unrewritten query. SOLR-6011 and testHashcodeEquals show that unrewritten equality is already expected to follow matching. And #16820 is an open proposal without comments that says nothing about this, while the parser ships in 10.6.0 and main. A maintainer may still prefer source-text identity for a niche parser, for maintenance or compatibility reasons (a second reviewer rated the intended case moderate, not weak); that is a fair call, but it leaves the dis_max result wrong.

Suggested fix

#

Recommended Compare the analyzed phrase in equals, keep hashCode (validated)

In ComplexPhraseQuery.equalsTo, also compare the analyzed phrase, && Objects.equals(contents[0], other.contents[0]), and keep hashCode unchanged: contents[0] is filled in after the query may already sit in a hash-based set. The repro passes, the whole queryparser suite has 0 failures (534 tests, 1 skipped as on stock), and the module's static checks pass.

Compare the analyzed phrase in equals, keep hashCode (validated) (recommended)

#

Two parses of the same text then compare equal only if their analyzed queries are equal; the term, multi-term, synonym and Boolean queries that rewrite() accepts all implement equals. Equal queries keep equal hash codes; unequal ones may share a hash, which the hashCode contract allows.

--- a/lucene/queryparser/src/java/org/apache/lucene/queryparser/complexPhrase/ComplexPhraseQueryParser.java
+++ b/lucene/queryparser/src/java/org/apache/lucene/queryparser/complexPhrase/ComplexPhraseQueryParser.java
@@ -452,7 +452,9 @@
       return field.equals(other.field)
           && phrasedQueryStringContents.equals(other.phrasedQueryStringContents)
           && slopFactor == other.slopFactor
-          && inOrder == other.inOrder;
+          && inOrder == other.inOrder
+          // contents[0] is set after the first parse pass, so it stays out of hashCode()
+          && Objects.equals(contents[0], other.contents[0]);

Trade-offs

  • Why hashCode stays: the parser's first pass already puts the ComplexPhraseQuery into an enclosing BooleanQuery, whose clause sets are hash-based; contents[0] is filled in the second pass. A variant that also hashes contents[0] changes the hash after insertion, and two parses of "foo bar" OR baz by the same parser no longer compare equal (a check test fails with that variant and passes with this fix).
  • Equality depends on state set during parsing: two queries compare equal until the second pass fills them.

Keep the creating configuration in the query and compare it (not run)

#

Store, for example, the analyzer in the ComplexPhraseQuery and compare it, as MoreLikeThisQuery does. This works before the second pass too.

Trade-offs

Analyzers compare by identity, so two parsers built with separate but identical new StandardAnalyzer() give unequal queries: correct, but fewer cache hits and no de-duplication of truly equal queries.

Not recommended: go back to a list in DisjunctionMaxQuery

#

The Multiset is correct when equals means equivalence (LUCENE-9940 made dis_max equality independent of disjunct order), and other consumers that de-duplicate by equals would stay wrong.

Downstream note

#

Products that combine differently analyzed ComplexPhraseQueryParser phrases for one field in a dis_max, or cache results by unrewritten query equality, can silently serve one parse's matches for the other.

How it was found

#

Semi-formal: a static screen of Query equals/hashCode implementations flagged that ComplexPhraseQuery leaves out contents, the state its matching uses. Tracing a consumer that merges queries by equals, DisjunctionMaxQuery, showed where that becomes a wrong result, and a JUnit test on main confirmed it.

The method in full102 words

Method: semi-formal (a static scan of equality implementations, then a traced consumer and an executed test).

  • Screen. A static scan listed Query subclasses whose equals/hashCode leave out a field that their matching reads; ComplexPhraseQuery leaves out contents, the analyzed phrase that rewrite() uses.
  • Trace. An independent reviewer from another model family (OpenAI GPT-5.6) asked whether the omission is observable; tracing the consumers led to DisjunctionMaxQuery, whose Multiset merges equal disjuncts before rewriting.
  • Witness. A one-test JUnit on the stock main jars: the dis_max of the two parses finds 0 documents instead of 1, with assertions on and off.
