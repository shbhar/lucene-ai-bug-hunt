Geo3DPointOutsideSortField.equals casts to the sibling class, so comparing two outside-distance sorts throws ClassCastException

Build the same Geo3D outside-distance sort twice and compare the two (directly, through Sort.equals or as a HashMap key): instead of true, equals throws ClassCastException, because it casts to the sibling inside-distance class. Every release from 6.1.0 to 10.6.0 has it; searching and sorting never reach the broken line.

The finding in 30 seconds

#

equals checks that the other object is its own class, then casts it to a different class: the sibling inside-distance sort it was copied from. That cast can never succeed, so every comparison of two outside sorts on one field throws.

Background: Geo3D distance sorts

#
  1. Geo3DDocValuesField (module spatial3d) builds SortFields that order hits by distance from a shape: newDistanceSort and newPathSort (distance from a point or path), and five newOutside*Sort factories (distance outside a circle, box, polygon, large polygon or path; points inside get 0).
  2. The first kind is a Geo3DPointSortField, the outside kind a Geo3DPointOutsideSortField: two separate final, package-private subclasses of SortField.
  3. Like every SortField, they are meant to compare by value: SortField.equals and Sort.equals "return true if o is equal to this", and code such as a cache keyed by Sort relies on that.

The finding, step by step

#
  1. Build Geo3DDocValuesField.newOutsideDistanceSort("loc", 10, 20, 1000, PlanetModel.WGS84) twice: two sorts by distance outside the same 1,000 m circle, with equal hash codes.
  2. Compare them: a.equals(b), new Sort(a).equals(new Sort(b)), or a HashMap<Sort, ?> lookup. You expect true, as two identical inside-distance sorts give (and false for two different circles).
  3. Instead every one of these calls throws ClassCastException ("Geo3DPointOutsideSortField cannot be cast to class Geo3DPointSortField") at Geo3DPointOutsideSortField.java:68, with assertions on and off. All five newOutside*Sort factories do it.
  4. Why: equals first checks that the argument is its own class (line 67), then casts it to the sibling Geo3DPointSortField (line 68), a line copied from that class in 2016. The two classes are unrelated, so the cast always fails.
  5. Only comparing fails: sorted search and searchAfter never reach the cast (with an index sort, search does call this equals, against the index-sort field, and it returns false first), Lucene itself never compares two such sorts, and equals never returns a wrong true. The fix is one line: cast to Geo3DPointOutsideSortField.

Who is affected

#

Applications that sort with an outside-distance sort and whose own code compares two separately built ones on the same field, for example a result cache keyed by Sort. Opt-in and rare: no upstream test builds one and no use was found in Elasticsearch, OpenSearch or Solr. No wrong results; workaround: reuse one SortField instance.

Mechanism, terms and numbers721 words

Geo3DDocValuesField has five public factories that sort hits by distance outside a shape, newOutside{Distance,Box,Polygon,LargePolygon,Path}Sort, each returning a package-private Geo3DPointOutsideSortField as a plain SortField. Its equals (Geo3DPointOutsideSortField.java:63-70 at 645d4fe14a20) checks getClass() != obj.getClass() (:67) and then casts the argument to the sibling inside-distance class Geo3DPointSortField (:68). The two are unrelated final subclasses of SortField, so the cast can never succeed, and because SortField.equals passes for any two outside sorts on the same field, comparing any two of them throws ClassCastException: directly, through Sort.equals, or in a HashMap keyed by Sort. The line was copied from Geo3DPointSortField.equals, where it names its own class. It dates from LUCENE-7212 (2016) and is in every release from 6.1.0 to 10.6.0 and on main. Searching and sorting never reach the cast, Lucene's own code never compares two such sorts, and equals never returns a wrong true; the fix is one line.

The mechanism (main 645d4fe14a20)

#
  1. Every outside sort on a field looks the same to SortField.equals. The constructor calls super(field, SortField.Type.CUSTOM, false, Double.POSITIVE_INFINITY) (Geo3DPointOutsideSortField.java:32). SortField.equals (SortField.java:451-461) compares only field, type, reverse, comparator source and missing value, and SortField has no setter for them on main. So super.equals is true for any two outside sorts on the same field.
  2. The method then checks the class and casts to the wrong one (Geo3DPointOutsideSortField.java:63-70):
public boolean equals(Object obj) {
  if (this == obj) return true;                                // :65
  if (!super.equals(obj)) return false;                        // :66
  if (getClass() != obj.getClass()) return false;              // :67  obj is a Geo3DPointOutsideSortField
  final Geo3DPointSortField other = (Geo3DPointSortField) obj; // :68  unrelated final class: always throws
  return distanceShape.equals(other.distanceShape);            // :69  never reached
}

Geo3DPointOutsideSortField (:26) and Geo3DPointSortField (Geo3DPointSortField.java:26) are both final class ... extends SortField, so no object is both. The jar's bytecode has checkcast org/apache/lucene/spatial3d/Geo3DPointSortField at line 68.

  1. hashCode is value-based (:53-61, over the shape), so two identical outside sorts land in the same HashMap bucket and the lookup calls equals (a lookup with a different shape normally has a different hash code, so the map does not call equals for it). Sort.equals compares the field arrays with Arrays.equals (Sort.java:119), which calls each SortField.equals.
  2. What does not throw: the same instance (:65; Arrays.equals also short-circuits on identical references), another field name or null (:66), an inside sort (:67).
  3. Lucene's own code never reaches the cast. Its non-sandbox Sort comparisons are the early-termination check of sorted search, TopFieldCollector.canEarlyTerminateOnPrefix (TopFieldCollector.java:160-172, comparison at :168), which on every sorted search over an index-sorted segment compares the search sort fields with the segment's index-sort fields and so does call this equals; IndexWriter.isCongruentSort (IndexWriter.java:1232-1239) and the index-sort check in ParallelLeafReader.java:136, which compare index sorts only; and grouping's comparisons with Sort.RELEVANCE. An outside sort can never be an index sort (IndexWriterConfig.setIndexSort rejects a sort field with no IndexSorter, IndexWriterConfig.java:505-509, and SortField.getIndexSorter returns null for CUSTOM, SortField.java:598-604), so in the early-termination check equals returns false at :66 or :67, before the cast; Sort.RELEVANCE's field is null, so super.equals returns false first. An instrumented copy of the class showed it: a sorted search over an index-sorted index called this equals once (from canEarlyTerminateOnPrefix) and without an index sort not at all. An executed probe ran sorted search (10 hits returned) and searchAfter (does not throw) with outside sorts, alone and with a numeric sort, on a multi-segment index, with and without an index sort and an executor (3 of 3 pass on ea57360912ed and again on 645d4fe14a20). (Whether searchAfter pages correctly with these sorts is a separate bug, LFV-544.)

Exposure and likelihood204 words
  • Who is hit. Applications that sort with one of the five outside-distance sorts and whose own code compares two separately built ones on the same field: a result or request cache keyed by Sort (or by query plus sort), code that de-duplicates or compares requests, or an assertEquals in the application's tests. Every such comparison throws, deterministically; it does not depend on the data, an index or assertions.
  • Default vs opt-in. Opt-in and rare. spatial3d is an optional module, and these sorts look like a niche corner of it, judging by the code inspected (real-world usage volume is unknown): no upstream test builds any Geo3D sort field, and read-only code searches of Elasticsearch, OpenSearch and Solr found no use of Geo3DDocValuesField or of these factories (not exhaustive). Within that, it needs nothing special: the default PlanetModel.WGS84, ordinary arguments, no index.
  • Effect. A loud unchecked exception from equals. No wrong results, no hang, no resource use, no index effect, and never a wrong true, so a Sort-keyed cache cannot hand one request's results to another.
  • Workaround. Reuse one SortField instance per distinct sort (self-comparison returns true before the cast), or key caches on the sort's parameters instead of the Sort object.

Why it looks unintended

#
  • The class compares by value: hashCode and equals both use the shape. A cast that always fails after a same-class check is not a design.
  • The SortField and Sort javadoc promise a boolean, and TestSort.testEquals asserts that separately built equal sorts are equal.
  • Every sibling class casts to its own type; this line was copied from Geo3DPointSortField in 2016.
The full argument318 words
  • The class defines value equality. It overrides hashCode over distanceShape (Geo3DPointOutsideSortField.java:53-61), and its equals ends by comparing distanceShape (:69). A method that can never reach its own last line for two objects of its own class is not a design.
  • The contract promises a boolean. SortField.equals: "Returns true if o is equal to this" (SortField.java:447); Sort.equals: the same (Sort.java:112), comparing the field arrays element by element (:119). The Object#equals general contract describes an equivalence relation; for two instances of this class equals gives no answer at all. Nothing (javadoc, comment, CHANGES.txt, MIGRATE.md, test) documents identity-only equality or an exception for these sorts; the factory javadoc covers only ordering, missing and multiple values and argument checks. Geo3DDocValuesField is public, in an exported package, with no @lucene.experimental or @lucene.internal tag (the PlanetModel that every factory takes as an argument is tagged @lucene.experimental, PlanetModel.java:26).
  • Every sibling uses the matching cast after the same guard: Geo3DPointSortField.java:68, LatLonPointSortField.java:67, XYPointSortField.java:64.
  • Upstream tests treat sort equality as a contract: TestSort.testEquals (TestSort.java:73-92) asserts that separately built equal sorts are equal and different ones unequal, in both directions; TestSortedNumericSortField.testEquals and TestSortedSetSortField.testEquals do the same for single sort fields, in one direction. Sort/SortField value equality itself was added by LUCENE-1481 (#2555).
  • History shows a copy slip. Geo3DPointSortField was added on 2016-05-17 (07af00d8e7bc) with a correct equals; the next day cc263413457c added Geo3DPointOutsideSortField and copied that method, cast included (git blame -C -C traces line 68 to Geo3DPointSortField.java at 07af00d8e7bc). The LUCENE-7212 discussion (#8267, 49 comments) never mentions equals, hashCode or a cast, and no later commit touched the line.
  • Precedent. #12827 (merged 2023-11-21, in 9.9.0) fixed the same kind of slip, an equals that casts to a class it is not a subtype of, in PayloadFilteredTermIntervalsSource, with a one-line change.
The devil's-advocate check128 words

Strongest case (from the intended-behaviour checker and the cross-model reviews): the class is package-private, no Lucene code compares two of these sorts, no test builds one, the factories take an @lucene.experimental PlanetModel, no production user has been shown, and nobody has reported it since 2016, so the method is effectively unused and harmless.

Why it fails: that is about impact, not intent. Users get the object through public, documented, untagged factories (only their PlanetModel argument type is experimental) as a public SortField, and SortField.equals and Sort.equals are public, documented and tested; a cast that cannot succeed right after a same-class guard has no intended reading. The low impact is reflected in the priority (low), not in the verdict. The cross-model lenses rated the intended argument weak.

Suggested fix

#

Recommended Cast to Geo3DPointOutsideSortField

Cast to the class's own type: final Geo3DPointOutsideSortField other = (Geo3DPointOutsideSortField) obj; (one line). With it the minimal test passes with assertions on and off, and the whole lucene/spatial3d suite runs clean (182 tests, 0 failures).

  @Override
  public boolean equals(Object obj) {
    if (this == obj) return true;
    if (!super.equals(obj)) return false;
    if (getClass() != obj.getClass()) return false;
    final Geo3DPointOutsideSortField other = (Geo3DPointOutsideSortField) obj;
    return distanceShape.equals(other.distanceShape);
  }

How it was found

#

Static analysis: SpotBugs flagged that equals checks for an operand type incompatible with its own class, at line 68. A bytecode scan of all 599 equals(Object) methods in core and the non-sandbox modules found exactly this one cast to an unrelated type. A public-API JUnit then reproduced it.

spatial3d / Geo3DDocValuesField outside-distance sort fields (Geo3DPointOutsideSortField equality)

Low, rank 712: Geo3DPointOutsideSortField.equals throws ClassCastException when two outside-distance sorts are compared (for example by a Sort-keyed cache), a loud failure in a barely used API, so it goes with its loud spatial3d sibling LFV-282 in the crash rows.
Impact class
crash
Impact note
Hits only applications that sort with one of the five Geo3DDocValuesField.newOutside{Distance,Box,Polygon,LargePolygon,Path}Sort factories of the opt-in spatial3d module (no upstream test builds one, and a read-only code search found no use in Elasticsearch, OpenSearch or Solr) and whose own code compares, or hashes and then compares, two separately built such sort fields on the same field, for example a result cache keyed by Sort: with the default WGS84 model and no setting or scale needed, that equals call throws ClassCastException with -ea and -da, while Lucene's own sorted search and searchAfter (executed) and its index-sort, grouping and query-cache paths (read) never reach the cast, so there are no wrong results, no hang and no index damage; every release from 6.1.0 to 10.6.0 (10.6.0 by reading) and main is affected.
Summary
You build the same outside-distance sort twice, for example Geo3DDocValuesField.newOutsideDistanceSort("loc", 10, 20, 1000, PlanetModel.WGS84), and compare the two with equals, with Sort.equals, or by looking one up in a HashMap keyed by Sort, and expect true (or false for two different shapes), which is what the inside-distance sort gives. Instead equals throws ClassCastException ('Geo3DPointOutsideSortField cannot be cast to class Geo3DPointSortField'): the method was copied from the sibling class Geo3DPointSortField and still casts to that class right after checking that both objects are Geo3DPointOutsideSortField, so the cast can never succeed. Searching and sorting with these sort fields work; only comparing two of them fails.
