The finding in 30 seconds

#

A documentation defect on main: counting a shared query's RAM once is intended, but both callbacks' javadoc still describes one fixed amount per entry.

Background: cache entries and their RAM

#
  1. LRUQueryCache caches, per segment, the documents a filter matches; each (segment, query) pair is one entry. For per-index statistics its javadoc says to override callbacks, preferably onCacheEntryInserted / onCacheEntryEvicted (main only), which get the segment, the query and ramBytesUsed.
  2. An entry's RAM has three parts. In the repro: the per-entry key, 48 bytes; the cached doc id set and its table slot, 112 bytes; the query object itself, 184 bytes.
  3. Before #16657 every entry counted the query's bytes, although the entries of one search share one query object: one filter on two segments took 688 bytes. #16657 lets all entries of a query share one query object and counts it once: 504 bytes.

The finding, step by step

#
  1. You subclass LRUQueryCache to keep RAM per index, as its javadoc suggests: add ramBytesUsed in onCacheEntryInserted, subtract it in onCacheEntryEvicted. Both javadocs call it "the total RAM cost of this entry".
  2. You cache one filter, color:red, on an index with two segments, then close segment 0 (the next cache cleanup removes its entry). You expect its entry to leave with the 344 bytes it came in with, and its count to return to 0.
  3. It leaves with 160. Both entries share one 184-byte query object, counted once since #16657: its bytes come with the first insertion and go with the last eviction. Events: insert 344, insert 160, evict 160, evict 344.
  4. With two indices sharing one cache, index A keeps +184 bytes after it is closed and index B ends at -184, while the cache itself correctly reports 0. Each shared filter whose first and last entries are in different indices adds its query size.
  5. The count-once accounting is correct; the javadoc, written when every entry's amount included the query's bytes, was never updated. Main only; no release has these callbacks.

Who is affected

#

Only main and branch_11x (the coming 11.0). It takes an application's own LRUQueryCache subclass that keeps per-segment or per-index RAM from the unified callbacks, as the class javadoc suggests; the query cache is off by default on main. One filter on two segments is enough. Results, cache contents and the memory bound stay correct.

Mechanism, terms and numbers660 words

LRUQueryCache invites subclasses to keep "per-index or per-query-class statistics" through its callbacks and to prefer the unified onCacheEntryInserted / onCacheEntryEvicted, "which provide the full context (segment key, query, total RAM)". Both callbacks' javadoc says ramBytesUsed is "the total RAM cost of this entry" (of "the evicted entry"), "including both the query key overhead and the cached DocIdSet value". That matched the code when #15558 wrote it, because every entry's amount then included the query's bytes (double-counting a query shared by several entries, which #16657 fixed).

#16657 made all entries of a query share one canonical query object and count its RAM once. The query's bytes now come with the insertion of its first entry and with the eviction of its last entry, often entries of different segments or indices. So one entry is inserted with 344 bytes and evicted with 160, and with two indices sharing one cache a per-index ledger kept through the callbacks ends at +184 for one index and -184 for the other while the cache reports 0. The count-once accounting is intended and every amount is the exact change of the cache's own ramBytesUsed(); the defect is that the javadoc still describes one fixed amount per entry, and the MIGRATE.md advice added after #16657, which points to these callbacks, says nothing about shared bytes. Search results, cache contents, hit counts, ramBytesUsed(), getCacheSize() and the memory bound are correct.

What the javadoc says

#

onCacheEntryInserted (LRUQueryCache.java:385-386, :390 at 645d4fe14a20): "The ramBytesUsed parameter reflects the total RAM cost of this entry, including both the query key overhead and the cached DocIdSet value." / "@param ramBytesUsed total RAM bytes used by this cache entry". onCacheEntryEvicted (:402-403): "the total RAM cost of the evicted entry, including both the query key overhead and the cached DocIdSet value"; its @param (:407) says "total RAM bytes freed by this eviction". The class javadoc (:91-99) offers the callbacks for "per-index or per-query-class statistics" and says to prefer the unified ones, "which provide the full context (segment key, query, total RAM)". MIGRATE.md:521-522: "Prefer onCacheEntryInserted / onCacheEntryEvicted."

What main does

#
  1. A query goes to partition query.hashCode() & (numberOfPartitions - 1) (:1277-1278), so all its entries share one partition, whose uniqueQueries map holds one canonical instance per distinct query (:954).
  2. putIfAbsent (:1085-1137): the per-entry amount is QueryCacheKey.ramBytesUsed(), "Per-entry overhead only" (:1096, :1346-1350). "Account the query object only on the first entry that references it in this partition": queryBytes = perEntryBytes + (firstReference ? ref.queryBytes : 0) (:1111, :1120-1121), then onCacheEntryInserted(cacheKey, canonical, queryBytes + cachedValueBytesUsed) (:1126-1127).
  3. remove (:1155-1189): "reclaim the query bytes on the last reference" (:1176-1177); releaseQuery returns the query's bytes only when its count drops to 0, else 0 (:1001-1017); then onCacheEntryEvicted(..., queryBytes + docIdSetBytes) (:1183-1184).

344 = 48 (key) + 112 (doc id set with its table slot) + 184 (query); 160 = 48 + 112. With #16657's parent shadowed, every event is 344 and the cache holds 688 with both entries. Two indices A and B sharing one cache, the same filter, readers closed in turn: the unified-callback ledger ends at A = +184, B = -184 with ramBytesUsed() = 0 and getCacheSize() = 0; the deprecated per-core onDocIdSetCache / onDocIdSetEviction ledger ends at A = 0, B = 0. The drift depends on order: with segment 1 cleared before segment 0 (the query's first and last entry in the same segment) the events are 344, 160, 160, 344 and both ledgers end at 0.

Exposure and likelihood304 words
  • Who is hit. Applications on 11.0 (main and branch_11x today) that subclass LRUQueryCache and keep per-segment, per-index or per-shard RAM from onCacheEntryInserted / onCacheEntryEvicted. Their ledgers drift silently: one index stays positive with no entries left, another goes negative, and the error grows with every shared filter whose first and last entries are in different segments or indices (the devil's-advocate verifier ran 50 shared filters: index A ended above its live RAM by the sum of their query sizes and index B below it by the same sum, at a negative value; the fact check's probe, searching A then B and closing A first, got A = +9200 and B = -9200). When a filter's first and last entries are in the same segment, its ledger balances.
  • Default vs opt-in. Opt-in: the query cache is off by default on main (IndexSearcher.java:84, DEFAULT_QUERY_CACHE = null), and only a subclass that overrides these protected @lucene.experimental callbacks is affected. No in-tree subclass outside the tests overrides them, and a GitHub code search (indexed public code) found no implementer outside apache/lucene.
  • Scale. The most ordinary trigger, one cached filter on an index with two segments, already makes the per-segment amounts differ; no concurrency, no clear(), no unusual parameters.
  • Not affected. Search results, cache contents, hit and miss counts, ramBytesUsed(), getCacheSize(), the memory bound (eviction uses the partition's own accounting, LRUQueryCache.java:1128), and every release, 10.6.0 included.
  • Workarounds for subclass authors. Remember each entry's inserted amount and subtract that at eviction: it balances per index, but while a shared query is still held the per-index sum is below ramBytesUsed() by the query's size. Or keep the deprecated per-core onDocIdSetCache / onDocIdSetEviction, which still balance per core on main but "will be removed in a future release" (:361, :373).

Why it looks unintended

#
  • Both javadocs call the amount the entry's total RAM cost; the first entry's 344 also carries the 184-byte shared query.
  • That matched the code when #15558 wrote it (every event 344); #16657 changed the amounts, not the text.
  • The class javadoc offers the callbacks for per-index statistics and, like MIGRATE.md, points to the unified pair; neither mentions shared bytes.
The full argument244 words
  • The contract text names one per-entry quantity with two components, at both events (LRUQueryCache.java:385-386, :390, :402-403). On main the 184-byte query object is neither component: QueryCacheKey.ramBytesUsed() is "Per-entry overhead only" (:1347), 48 bytes, and a structurally identical second entry reports 160.
  • History. #15558 (d50fb36d9af3, 2026-04-14) wrote the text when each entry's key included the query's bytes; all five LRUQueryCache.java versions from #15558 to #16657's parent pass the repro (assertions on). #16657 (fadd63e0eb4e) left the javadoc and the class javadoc byte-identical (the class javadoc's per-index sentence, :91-93, is older, 2d6ad2fee6df, 2020; :94-99 is from #15558); its PR body and 13 comments never discuss what the callbacks report. CHANGES.txt:281-282 says only that a query's RAM is accounted once.
  • The class javadoc offers the callbacks for per-index statistics (:91-93), and it and MIGRATE.md point to the unified pair (:97-99; MIGRATE.md:521-522, #16756), while the deprecated per-core pair, the only one that still balances per index, is marked for removal.
  • Tests. No upstream test checks per-entry or per-segment amounts: testUnifiedCacheEntryCallbacks (TestLRUQueryCache.java:2725) forces one segment, where a query's first and last entry coincide, and checks aggregate balance; testFineGrainedStats (:954) keeps RAM only cache-wide.
  • Precedent (weaker than it reads). #12614 (2023) fixed an earlier, different insert/evict amount mismatch in the predecessor onQueryCache / onQueryEviction pair as a bug; there it also broke the cache's own total, here it does not.
The devil's-advocate check304 words

The strongest case for "works as designed" (the executing refute review by OpenAI GPT-5.6, verdict not real, high confidence, and the devil's-advocate verifier): each amount is the actual cache-wide RAM change of its event, and the eviction @param says exactly that ("total RAM bytes freed by this eviction"); nothing promises that an entry's two amounts are equal; a shared query's RAM cannot be split per index without double counting; upstream tests pin the aggregate balance and the count-once accounting (testQueryRamAccountedOncePerDistinctQuery, testCanonicalQueryInstanceSharedAcrossSegments); in 10.x onQueryCache also reported a query's RAM once per distinct query, so folding it into one insertion is the faithful sum of the pair the unified callback replaces; the hooks are experimental and unreleased.

Why it fails: it defeats a code-bug claim, which is why none is made. It does not make the text right. The insertion javadoc has no "added by this insertion" wording at all, and its two named components do not cover the 184 bytes the first insertion carries. The eviction sentence repeats the per-entry wording, and its "freed by this eviction" @param fits the per-event reading, but was written when that was the same number as the per-entry total, so it does not show that one entry's two amounts were meant to differ. The class javadoc offers the callbacks for per-index statistics, and it and MIGRATE.md point to the unified pair, with no word on shared bytes. The reviewer itself wrote that "a clarification could make the javadoc less susceptible to this interpretation". Verdict (tie-break): a documentation defect, not a code bug. The cache-wide-delta reading is the cross-model reviewer's and the intended-behaviour check's; their correct points belong in the fix text. The second cross-model fact check (OpenAI GPT-5.6) also rates the intended-behaviour case strong and calls "clarify the attribution" the strongest version of the claim.

Suggested fix

#

Recommended A: describe the per-event amounts in the javadoc and MIGRATE.md (recommended, validated)

Documentation only: describe ramBytesUsed as the RAM this insertion added or this eviction freed; a shared query's own RAM comes with its first insertion and last eviction, so one entry's two amounts can differ and per-segment sums need not return to zero; clear() reports only onClear(). Same note for the class javadoc's "total RAM" and MIGRATE.md.

A: describe the per-event amounts in the javadoc and MIGRATE.md (recommended, validated)

#

The finder's wording with the adjudication's corrections: both callbacks, the class javadoc's "total RAM" sentence and one paragraph in the #15558 section of MIGRATE.md (+26/-8 lines). The finder's sentence "the sum of all inserted amounts minus all evicted amounts equals ramBytesUsed()" is dropped, because it fails when an insertion runs concurrently with clear() (LFV-991). Trade-offs

  • Documents the intended accounting instead of changing it: no runtime cost, #16657's count-once design stays.
  • It does not give subclasses balanced per-index numbers; it tells them why they are not balanced. The workarounds (remember each entry's inserted amount, or the deprecated per-core pair) could be added if maintainers want.
  • The class-javadoc sentence is the one LFV-1000's fix also rewrites ("under a lock"), and LFV-1000's fix also inserts a MIGRATE.md paragraph at the same place, so the two edits overlap. The eviction @param ("total RAM bytes freed by this eviction") is accurate and stays.
  • A leaves the class javadoc's other stale sentence, :66-68 (one query's entries "may reside in different partitions"; since #16657 they share one), which is LFV-054's documentation point.

B: report the shared query bytes separately (a question, not run)

#

Give the unified callbacks a stable per-entry amount (key overhead plus doc id set) and report the query object's RAM through a separate per-query notification or an extra parameter.

Trade-offs

Per-entry and per-index sums would balance and a subclass could still rebuild ramBytesUsed(), but it adds API surface to hooks that are new in 11.0. Not built.

C: count the query bytes per entry again (not recommended)

#

Restore the pre-#16657 accounting, so every event of one entry carries the query's bytes.

Trade-offs

Makes the javadoc true again (shadowed parent: every event 344) but counts the query twice, 688 instead of 504 bytes for one filter on two segments, which is the bug #16657 fixed. The devil's-advocate verifier showed that no per-entry split of a shared query's bytes balances both per entry and cache-wide.

Downstream note

Downstream: elastic/elasticsearch#163523 (open) tracks adapting Elasticsearch's per-shard query-cache statistics to the new cache, names these callbacks as the replacement hooks and does not mention how a shared query's RAM is attributed; its Lucene 11 branch still uses the deprecated pairs.

How it was found

#

Bounded-exhaustive checking of the real jar: a probe ran every short sequence of cache operations on the stock main jar and checked that each entry's insertion and eviction amounts balance; 12,819 to 15,089 of 46,650 sequences did not. The finder ran a reference model in lockstep with the cache (0 mismatches) and reduced the failure to one test.

The method in full162 words

Method: semi-formal, bounded-exhaustive checking of the real jar. A probe enumerated every operation sequence up to a small bound against the stock main LRUQueryCache and checked per-entry and per-core callback balance: 12,819 of 46,650 sequences violated on a9779ef3c193 with assertions off; on 645d4fe14a20 15,089 with assertions off and 12,819 with them on (the count varies with identity-hash order in cleanUp()).

The finder (a hunt unit) then ran an independent reference model of the partitioned cache in lockstep with the real one: every sequence of length 1-6 over 8 operations and 9 configurations, 2,696,328 sequences and 16,353,259 event checks, 0 model mismatches; per-entry balance failed in 1,511,830 sequences and per-core balance in 973,900, the other six properties held. It read the root cause off putIfAbsent / remove and wrote a public-API JUnit. It was then reduced to the one test above.

The independent cross-model reviewer (OpenAI GPT-5.6) and the devil's-advocate verifier then framed it as stale documentation rather than a code bug.

LFV-1008, snapshot of 2026-11-05

Registry title
On main, LRUQueryCache's onCacheEntryInserted/onCacheEntryEvicted javadoc still calls ramBytesUsed 'the total RAM cost of this entry', but since #16657 a query's shared RAM is reported only with its first inserted entry and its last removed entry, so one entry is inserted and evicted with different amounts and per-segment or per-index RAM kept through these callbacks drifts (one index stays positive, another goes negative) (documentation defect, main only)
Area
search / query cache (LRUQueryCache unified callback javadoc and MIGRATE.md)
Priority
Low, rank 1214: This main-only stale javadoc in the core LRUQueryCache misleads subclass authors: following the documented per-index use gives silently drifting RAM ledgers in a deterministic, single-threaded case while results, cache contents and the memory bound stay exact.
Impact class
minor
Impact note
Documentation only, on unreleased main (11.0): an application that subclasses LRUQueryCache and keeps per-segment or per-index RAM through the unified callbacks, as the class javadoc and MIGRATE.md recommend, gets ledgers that never return to zero once a query is cached on two or more segments (in the repro one index keeps +184 bytes with no entries left and another ends at -184; the drift grows with every shared filter), while search results, cache contents, hits, the cache's own ramBytesUsed()/getCacheSize() and its memory bound stay exact; the default query cache is off on main, no public subclass uses these callbacks yet, and every release, 10.6.0 (released 2026-10-29) included, lacks the API.
Summary
You subclass LRUQueryCache to keep per-index RAM statistics in onCacheEntryInserted/onCacheEntryEvicted, whose javadoc says ramBytesUsed is 'the total RAM cost of this entry' (and of the evicted entry), so you expect each entry to give back at eviction what it added at insertion and an index's total to return to 0 once its entries are gone. Since #16657 the cache deliberately counts a query's own RAM once per distinct query and reports it only with the query's first inserted entry and with the entry that drops its last reference, usually entries of different segments or indices: in a two-segment index one entry is inserted with 344 bytes and evicted with 160, and with two indices sharing one cache index A keeps +184 bytes after it is closed while index B ends at -184. The dedup and the cache's own accounting are correct; the defect, as the independent cross-model reviewer and the devil's-advocate verifier framed it, is that both callbacks' per-entry javadoc (written in #15558, when it was true) was left unchanged and that the class javadoc and MIGRATE.md recommend these callbacks for per-index statistics without saying how a shared query's bytes are attributed.
