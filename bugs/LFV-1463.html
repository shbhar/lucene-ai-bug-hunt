Sandbox numeric multi-range query drops a half-open clause such as [Long.MIN_VALUE, 10] when the query has another clause

The sandbox SortedNumericStabbingBuilder silently drops a clause such as [Long.MIN_VALUE, 10] (the documented way to write f <= 10) when the query has another clause: its lower - upper test for reversed clauses overflows. Values 5 and 150 with [Long.MIN_VALUE, 10] and [100, 200] count 1, not 2 (since 10.3.0).

The finding in 30 seconds

#

A query for f <= 10 OR 100 <= f <= 200 loses its f <= 10 part: the check that throws away reversed clauses computes lower - upper, which overflows for any clause with upper - lower > 2^63. That hits f <= x for every x >= 1, f >= x for every x <= -2, [MIN, MAX], and any two-sided clause that wide.

Background: the sandbox multi-range builder and open ends

#
  1. DocValuesMultiRangeQuery.SortedNumericStabbingBuilder (lucene/sandbox, @lucene.experimental) builds one query for "the value is in any of these ranges" over a NUMERIC or SORTED_NUMERIC doc-values field. One clause becomes SortedNumericDocValuesField.newSlowRangeQuery; two or more become SortedNumericDocValuesMultiRangeQuery, which first sorts and merges the clauses.
  2. Lucene writes an open end with the extreme long: newSlowRangeQuery documents lowerValue = Long.MIN_VALUE for a <= query and upperValue = Long.MAX_VALUE for >=. A Java long holds -2^63 to 2^63 - 1; an arithmetic result outside that range wraps around without an error.

The finding, step by step

#
  1. You index two documents whose field f holds 5 and 150 and ask for f <= 10 OR 100 <= f <= 200, writing the open end the way newSlowRangeQuery documents it: SortedNumericStabbingBuilder("f").add(Long.MIN_VALUE, 10).add(100, 200).build().
  2. You expect 2 hits: the query is a union of its ranges, 5 is in [Long.MIN_VALUE, 10] and 150 is in [100, 200].
  3. To build the query, Lucene throws away reversed clauses (lower > upper) by testing whether lower - upper is positive. For the first clause that is Long.MIN_VALUE - 10 = -9223372036854775818, which does not fit in a long and wraps to +9223372036854775798, so the clause looks reversed and is dropped.
  4. You get 1 hit and no error; the query keeps only f:[100..200]. The same clause on its own matches 5, so adding a second clause changes the answer.

Who is affected

#

Applications using the sandbox builder with two or more clauses, one with upper - lower > 2^63, in practice an open end written the documented way (most often f <= x, x >= 1). Every hit of that clause is lost silently, on NUMERIC and SORTED_NUMERIC fields, default codec, any index size. No other Lucene module uses the builder.

Mechanism, terms and numbers703 words

DocValuesMultiRangeQuery.SortedNumericStabbingBuilder (lucene/sandbox, @lucene.experimental) builds "the value is in any of these ranges" over a NUMERIC or SORTED_NUMERIC doc-values field. With two or more clauses it builds SortedNumericDocValuesMultiRangeQuery, whose constructor sorts each clause into a point, a range or a reversed clause, which it drops, by the sign of long cmp = r.lower - r.upper; (SortedNumericDocValuesMultiRangeQuery.java:98 on main). When upper - lower > 2^63 the true difference does not fit in a long and wraps to a positive number, so a legal clause is dropped as reversed. Among the documented half-open forms that is exactly [Long.MIN_VALUE, x] for any x >= 1 (f <= x), [x, Long.MAX_VALUE] for any x <= -2, and [Long.MIN_VALUE, Long.MAX_VALUE]; any other clause that wide is dropped too, such as [-6000000000000000000, 6000000000000000000]. Values 5 and 150 with [Long.MIN_VALUE, 10] and [100, 200] count 1 instead of 2, silently; one clause alone takes another code path and is right. The line came with the builder in #14404 and is in every release from 10.3.0 to 10.6.0 and in main. int cmp = Long.compare(r.lower, r.upper); fixes it and was validated with the sandbox module's tests.

An SMT query (z3, 64-bit bit-vectors, 11 queries) confirms the exact set: a clause is misclassified if and only if the true lower - upper does not fit in a long, and Long.compare gives the intended class for every pair.

Where and when

#
  • build() sends a single clause to newSlowRangeQuery (DocValuesMultiRangeQuery.java:178-181), which is right, and two or more to this class (:183, :186-188). So the same clause matches alone and vanishes next to a second clause.
  • The drop happens in the constructor, before any index is read: NUMERIC and SORTED_NUMERIC fields, with or without a doc-values skip index, are hit alike (bounded-exhaustive check over 4 index shapes).

Other effects of the same line (same fix)

#
  • When every clause overflows, e.g. [Long.MIN_VALUE, 10] + [Long.MIN_VALUE, 200], the clause set is empty (the query prints f:[]) and IndexSearcher.count throws NoSuchElementException at sortedClauses.getFirst() (:214) instead of counting 2, on any segment that has the field (for one without it scorerSupplier returns null first, :211-213).
  • A really reversed clause whose lower - upper exceeds Long.MAX_VALUE, e.g. [Long.MAX_VALUE, -2] or [0, Long.MIN_VALUE], wraps the other way, is kept as a "range" whose upper edge sorts before its lower edge, and breaks the overlap merge: [MAX, -2] + [0, 10] throws NoSuchElementException instead of counting 1; [0, 10] + [MIN, 0] + [0, MIN] trips assert strictlyIncreasing (:141) with assertions on, and with them off builds f:[-9223372036854775808..-9223372036854775808, 0..0] and counts 0 instead of 1.

Related bugs in the same class (separate root causes)

  • LFV-1464: when every clause is really reversed (no overflow), search throws NoSuchElementException because nothing guards the empty clause set (:214). This page's fix does not fix it, and its fix does not fix this bug.
Exposure and likelihood195 words
  • Who is hit: an application that maps a user's range filter with an open end onto the sandbox builder, for example "price <= 10 OR price 100-200" as [Long.MIN_VALUE, 10] + [100, 200]. f >= x is hit only for x <= -2, so f >= 0 or f >= 900 are fine; f <= x is hit for every x >= 1.
  • Silent: the hits of that clause are missing; nothing says a clause was dropped.
  • Opt-in: only by using the sandbox builder (@lucene.experimental). Nothing else is needed: default codec and IndexWriterConfig, NUMERIC or SORTED_NUMERIC, with or without a skip index, assertions on or off.
  • Scale: none; two documents and two clauses.
  • Reach: no other Lucene module builds this query. The recorded downstream searches found OpenSearch using only the SortedSet builder (IP ranges) and no use of the numeric builder in Elasticsearch, OpenSearch or Solr; that is a search result, not proof that nobody uses it.
  • Priority Medium: silent missing hits for a common open-end shape, in every release since 10.3.0; not higher because the query is sandbox and @lucene.experimental, with no downstream user found. The adjudication leaned Low-Medium.

Why it looks unintended

#
  • The class is documented as "A union multiple ranges"; one range "behaves like" newSlowRangeQuery, which documents Long.MIN_VALUE / Long.MAX_VALUE as open ends.
  • The code means to drop only reversed ranges (// else drop reverse ranges); [Long.MIN_VALUE, 10] has lower < upper.
  • The same clause matches alone but vanishes next to another; upstream tests use ranges inside [-100, 300] only.
The full argument243 words
  • The contract. Class javadoc: "A union multiple ranges over SortedNumericDocValuesField" (SortedNumericDocValuesMultiRangeQuery.java:45). Builder javadoc: "For the single range it behaves like SortedNumericDocValuesField#newSlowRangeQuery(String, long, long)" (DocValuesMultiRangeQuery.java:156-160); add(long, long) documents no value limit (:169-172). newSlowRangeQuery: "You can have half-open ranges (which are in fact </≤ or >/≥ queries) by setting lowerValue = Long.MIN_VALUE or upperValue = Long.MAX_VALUE" (SortedNumericDocValuesField.java:90-91). The builder promises newSlowRangeQuery behaviour only "for the single range"; that the open-end idiom carries over to several clauses is an inference from it and from the union javadoc, not something the builder says. The argument does not need the idiom, though: [Long.MIN_VALUE, 10] is an ordinary inclusive range with lower < upper, and so is a two-sided clause such as [-6000000000000000000, 6000000000000000000].
  • The code's intent. The comment drops only reversed ranges (:105).
  • Tests. TestSortedDvMultiRangeQuery checks the query against a disjunction, but draws lower in [-100, 200] and upper = lower + [0, 100] (TestSortedDvMultiRangeQuery.java:140-141), so no upstream test uses an extreme bound.
  • History. The line came with the class in #14404 and never changed. The review had no human comment on open ends or value limits. An automated (Copilot) review comment of 2025-04-16 flagged a different subtraction in the same method, the edge comparator a.getValue() - b.getValue() < 0, and suggested Long.compare; that comparator was replaced before any release (#14632, later Comparator.comparingLong in #14761/#14817), and nobody mentioned the classification line.
The devil's-advocate check225 words

Strongest case for "intended": (a) the code drops clauses on purpose, and the sign of lower - upper is its definition of reversed; (b) the class is @lucene.experimental ("This API is experimental and might change in incompatible ways in the next release"); (c) the motivating use was IP-style stabbing, far from the extremes of long, and the builder javadoc does not repeat the half-open idiom.

Why it fails: the comment names reversed ranges and this one is not; @lucene.experimental is an API-stability notice, not leave for wrong results against the class's own union semantics; no value precondition is documented, and the builder has no other way to say "no lower bound" for longs (the SortedSet builder only has // TODO support nulls as min,max boundaries ???); and the same clause is right alone and wrong in company. The intended-behaviour devil's advocate, the cross-model reviews (OpenAI GPT-5.6, refute and intended lenses: each "real, high", intended-behaviour argument weak) and the adjudication (confirmed, high confidence) agree.

A later cross-model fact check of the brief (OpenAI GPT-5.6) rated the case for "intended" moderate rather than weak: a maintainer could prefer a javadoc note, or decline on sandbox priority, since a BooleanQuery of newSlowRangeQuery clauses is a workaround and no report of it since 10.3.0 is known. It still found "won't fix" technically weak, for the reasons above.

Downstream note

#

Downstream products are affected only if they build this sandbox query with a clause where upper - lower > 2^63 (in practice an open-ended one) next to another clause, for example to run a user's "price <= 10 OR 100-200" filter; the effect is silently missing hits.

How it was found

#

Semi-formal analysis. While modelling the doc-values skip index and the queries that use it, the long subtraction in the clause check stood out and a public-API probe showed the dropped clause. An SMT query characterised exactly which clauses are misclassified, a bounded-exhaustive check of the real jar confirmed it, and it was reduced to one JUnit test.

The method in full202 words
  • Model and probe. A component model of the doc-values skip index and the queries that consume it listed the multi-range query's range normalisation as computing r.lower - r.upper in long arithmetic; a public-API probe with an open-ended clause showed the clause dropped.
  • SMT characterisation (z3 4.12, 64-bit bit-vectors, 11 queries, all as expected): a clause is misclassified if and only if the true lower - upper does not fit in a long; no false points; Long.compare gives exactly the intended classification; every replay against Java semantics agrees.
  • Bounded-exhaustive translation validation of the real jar: every 1- and 2-clause list over a 10-value extreme domain plus every 3-clause list over 5 values (25,725 clause lists), on each of 4 index shapes (NUMERIC and SORTED_NUMERIC fields, with and without a skip index): 102,900 checks against a union-of-clauses reference. Stock: all 57,368 mismatching checks fall in the overflow class or the separate all-really-reversed class (LFV-1464), none elsewhere (assertions on and off). With Long.compare: no overflow mismatches. The check is bounded (this value domain, every document with a value); the SMT query covers the classification for every pair of longs, not the rest of query execution.
  • Reduced to the one-test JUnit (found 2026-11-09).

LFV-1463, snapshot of 2026-11-10

Registry title
Sandbox SortedNumericDocValuesMultiRangeQuery classifies each clause by the sign of 'lower - upper', which overflows, so a legal half-open clause such as [Long.MIN_VALUE, 10] or [-5, Long.MAX_VALUE] given together with another clause is silently dropped as if it were reversed (values 5 and 150 with the clauses [Long.MIN_VALUE, 10] and [100, 200] count 1, not 2); since 10.3.0
Area
sandbox / doc-values multi-range query construction (DocValuesMultiRangeQuery.SortedNumericStabbingBuilder -> SortedNumericDocValuesMultiRangeQuery clause classification before the overlap merge)
Priority
Medium, rank 198: The sandbox numeric multi-range query silently loses every hit of a half-open clause that spans more than half the long range, such as the common 'f <= 10' written as [Long.MIN_VALUE, 10], whenever the query has a second clause, on any NUMERIC or SORTED_NUMERIC doc-values field with default settings in every release since 10.3.0. It stays Medium rather than higher because the builder is sandbox and @lucene.experimental, with no known downstream user.
Impact class
silent wrong results
Impact note
Users of the sandbox (@lucene.experimental) builder DocValuesMultiRangeQuery.SortedNumericStabbingBuilder who pass two or more clauses, one of which is wider than 2^63 (in practice the documented half-open forms [Long.MIN_VALUE, x] with x >= 1 and [x, Long.MAX_VALUE] with x <= -2, or [Long.MIN_VALUE, Long.MAX_VALUE]), lose every hit of that clause with no error, on NUMERIC and SORTED_NUMERIC fields, with or without a skip index, with the default codec, with -ea and -da and at any index size; when every clause overflows the query matches nothing and search throws NoSuchElementException; one clause alone is right; released 10.3.0 through 10.6.0.
Summary
You index two documents whose field f (SortedNumericDocValuesField) holds 5 and 150 and count the hits of new DocValuesMultiRangeQuery.SortedNumericStabbingBuilder("f").add(Long.MIN_VALUE, 10).add(100, 200).build(), that is 'f <= 10 OR 100 <= f <= 200' written with the open-end convention that newSlowRangeQuery documents; you expect 2, since the query is documented as the union of its ranges. Instead the count is 1 and the query prints f:[100..200]: building the query sorts out reversed clauses by the sign of 'lower - upper', and Long.MIN_VALUE - 10 overflows to a large positive number, so the legal clause is thrown away as if it were reversed. Every clause wider than 2^63 is lost the same way, while one clause alone takes a different code path and is right.
