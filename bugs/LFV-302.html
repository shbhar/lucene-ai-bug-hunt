ShapeAreaValueSource ignores its multiplier in equals/hashCode, so BooleanQuery merges area clauses with different multipliers

Two ShapeAreaValueSources that differ only in the multiplier compare equal, so BooleanQuery merges them: area x 1 OR area x 3 on a rectangle of area 800 scores 1600 instead of 3200, and two area filters collapse into one. Since 5.0.0; only applications that build this experimental class are hit.

The finding in 30 seconds

#

ShapeAreaValueSource gives each document the area of its shape times a multiplier you choose, for example to change units. Lucene simplifies a BooleanQuery by merging clauses that equals calls the same, and this source's equals ignores the multiplier.

Background in 3 steps

#
  1. A DoubleValuesSource computes one number per document; FunctionScoreQuery(query, source) scores each match with that number.
  2. new ShapeAreaValueSource(shapeSource, ctx, geoArea, multiplier) returns the shape's area times the multiplier: a 20 x 40 rectangle gives 800 with multiplier 1 and 2400 with multiplier 3.
  3. While rewriting, BooleanQuery treats equal clauses as duplicates: equal SHOULD or MUST clauses become one clause with a summed boost, equal FILTER or MUST_NOT clauses are kept once. FunctionScoreQuery is equal when its query and its source are equal.

The finding, step by step

#
  1. Index one 20 x 40 rectangle (planar area 800) with BBoxStrategy. Score all documents with FunctionScoreQuery over new ShapeAreaValueSource(strategy.makeShapeValueSource(), ctx, false, m): with m = 1 the document scores 800, with m = 3 it scores 2400.
  2. Put both as SHOULD clauses into one BooleanQuery. A disjunction scores the sum of its matching clauses, so you expect 800 + 2400 = 3200.
  3. You get 1600, and no error. equals and hashCode compare only the shape source and geoArea, never the multiplier, so the two clauses are "equal" and the rewrite merges them into the first one with boost 2: 2 x 800. Swap the clauses and you get 4800.
  4. Area filters are merged the same way. In a 20,000-document test, FILTER (area x 2 >= 500) plus FILTER (area x 1 >= 500) returns 3800 hits instead of 2550, and FILTER x 2 plus MUST_NOT x 1 becomes MatchNoDocsQuery: 0 hits instead of 1250.

Who is affected

#

Only applications that construct ShapeAreaValueSource themselves (@lucene.experimental; Lucene builds it only in tests, no query parser does) and use two sources that differ only in the multiplier, such as one area in two units, in one BooleanQuery or behind one query cache. Default settings, any index size. Solr's BBoxField fixes the multiplier per field type and cannot build the pair.

Mechanism, terms and numbers763 words

ShapeAreaValueSource returns, per document, the area of its indexed shape times a multiplier passed to its public constructor. Its equals compares only geoArea and the shape source, and its hashCode hashes only those two, so area x 1 and area x 3 over the same field are equal and hash alike, and so are the FunctionScoreQuery objects built on them.

BooleanQuery.rewrite removes "duplicate" clauses by equality. Two equal SHOULD (or MUST) clauses become the first one with boost 2, so a disjunction of area x 1 and area x 3 on a rectangle of area 800 scores 1600 instead of 3200, or 4800 with the clauses swapped. Two equal FILTER or MUST_NOT clauses are kept once, so an area filter or exclusion is silently dropped, and FILTER x 2 with MUST_NOT x 1 rewrites to MatchNoDocsQuery. An equality-keyed query cache serves one multiplier's match set for the other.

The multiplier was added by SOLR-6797 (2015-01-03, first released in 5.0.0) without touching equals, hashCode or the printed form; the wrong scores appear from 7.1.0, when BooleanQuery started merging equal clauses. Affected: 5.0.0 to 10.6.0 and main. Reach is narrow: the class is @lucene.experimental, Lucene builds it only in tests, and the only downstream caller found (Solr) cannot build the colliding pair. Fix: compare and hash the multiplier (2 lines).

The mechanism (main 645d4fe14a20)

#
  1. The multiplier scales the value. The public constructor stores it in a non-final field (ShapeAreaValueSource.java:40, :42-48), and doubleValue() returns shapeValues.value().getArea(geoArea ? ctx : null) * multiplier (:63).
  2. Equality ignores it. equals returns false only for a different geoArea or shape source (:89-100); hashCode combines only those two (:102-107). The field comment exempts only ctx from identity ("not part of identity; should be associated with shapeValueSource indirectly", :37). toString is area(<shape source>,geo=<geoArea>) (:51-53), so the merged query prints as if nothing was lost.
  3. The query takes its equality from the source. FunctionScoreQuery.equals is Objects.equals(in, that.in) && Objects.equals(source, that.source) and hashCode is Objects.hash(in, source) (FunctionScoreQuery.java:143-154).
  4. BooleanQuery merges equal clauses. SHOULD and MUST clauses live in Multisets, FILTER and MUST_NOT clauses in HashSets (BooleanQuery.java:129-142). SHOULD clauses are de-duplicated when minimumNumberShouldMatch <= 1 (:438-447), MUST clauses always (:449-455), in deduplicateClauses (:714-758): boosts.merge(query, boost, Double::sum) (:726) keeps the first equal key; an unboosted pair gets computeQueryTermWeight(2) = 2 from the default BM25Similarity (:743-746; IndexSearcher.java:123; BM25Similarity.java:121-136), a boosted pair the linear sum (10.x releases always sum linearly). So area x 1 + area x 3 becomes (area x 1)^2 = 1600. Duplicate FILTER/MUST_NOT clauses are dropped (:343-362), and a FILTER clause equal to a MUST_NOT clause returns MatchNoDocsQuery("FILTER clause also in MUST_NOT") (:364-369).
  5. Filters and caches inherit the same equality. FunctionRangeQuery compares its value source (FunctionRangeQuery.java:119-125), FunctionMatchQuery its source and predicate (FunctionMatchQuery.java:119-124), and the facet drill-down query that DoubleRange.getQuery builds (DoubleRange.java:335) its range, fast-match query and value source (DoubleRange.java:130-143; the probe passes no fast-match query). A query cache looks entries up by equality; caching is off by default on main (IndexSearcher.java:82-84), on in 10.x releases.

Adding the multiplier to equals/hashCode, and nothing else, makes the repro and every other executed form pass, so the equality is the cause.

Exposure and likelihood298 words
  • Silent. Wrong scores that depend on clause order (1600 or 4800 for 3200), and, for area filters, missing or extra hits, with no exception.
  • Default settings, any size. The score form needs one document, the default IndexWriterConfig, the default similarity and a plain IndexSearcher; the filter forms need no cache. The test extends LuceneTestCase, which still randomizes the default codec, locale and time zone and installs a test query cache; the search needs scores, so the cache is not used (IndexSearcher.java:979-980), and the result is the same under both seeds run. Only the cache form needs a query cache: the default in 10.x releases (it caches segments of at least 10,000 documents after repeated use), opt-in on main. The probe used one 20,000-document segment and ran the warming query 10 times. A cache stores match sets only for searches without scores, so it can change hits only through a filter consumer such as FunctionRangeQuery or FunctionMatchQuery, never for a bare FunctionScoreQuery; and the tenant TermQuery in the same query stayed enforced.
  • Which queries. Two area clauses over the same shape field that differ only in the multiplier, in one BooleanQuery as SHOULD (with minimumNumberShouldMatch <= 1), MUST, FILTER or MUST_NOT clauses, or in two queries behind one query cache.
  • Who is exposed. Applications that call the public constructor directly. Lucene constructs the class only in TestBBoxStrategy, and no query parser builds it. Solr's BBoxField (score=area and area2D), the only downstream caller found, passes a unit factor fixed per field type and uses the source only as a score; a read-only code search (2026-10-26) found no use in Elasticsearch or OpenSearch.
  • Likelihood: rare. No report found since 5.0.0 (search gaps under Prior reports); the class is @lucene.experimental (ShapeAreaValueSource.java:33).

Why it looks unintended

#
  • Lucene's own test requires FunctionScoreQuery over constant(1) and constant(2) to be unequal (TestFunctionScoreQuery.java:91): changing scores must change equality.
  • All three sibling spatial sources with a multiplier compare it in equals; the class comment exempts only ctx from identity.
  • SOLR-6797 added the multiplier in 2015 without touching equals, and a disjunction whose score depends on clause order is no design choice.
The full argument260 words
  • Value-source equality is meant to track values. LUCENE-7723 (#8774, filed by Adrien Grand; committed by Alan Woodward as 1a278ae89be, 2017) made DoubleValuesSource.equals/hashCode abstract (DoubleValuesSource.java:125-129); its description reads: "Given that we embed values sources in queries and sorts, from which we expect that they have working equals/hashCode". In LUCENE-7736 (#8787) Adrien Grand wrote "I think it's important for equals to behave correctly and never return true for values sources that could return different values", and Alan Woodward agreed.
  • Lucene's own tests require it. TestFunctionScoreQuery asserts that FunctionScoreQuery over the same term query with DoubleValuesSource.constant(1) and constant(2) are unequal (QueryUtils.checkUnequal(q2, q3), TestFunctionScoreQuery.java:78-91).
  • The siblings do it. DistanceToShapeValueSource compares and hashes its multiplier (:110, :123), and vector/DistanceValueSource (:110) and ShapeFieldCacheDistanceValueSource (:113) compare it too. LUCENE-5118 (#6182, 2013) added the multipliers of DistanceValueSource and ShapeFieldCacheDistanceValueSource and compared them; DistanceToShapeValueSource compared and hashed its multiplier from its creation (LUCENE-5408, 2014).
  • History points to an oversight. LUCENE-5714 created the class in 2014 with no multiplier, and its equals covered every field except ctx, which the comment exempts. SOLR-6797 (8fd247cc0e5, 2015-01-03) added the field, the constructor argument and * multiplier, and did not touch equals, hashCode or the printed form (description() then, toString today); none of its 25 comments mentions equality. That it was an oversight is an inference; nobody said so.
  • Nothing documents it. No javadoc or test says the multiplier is outside identity; TestBBoxStrategy.testAreaValueSource checks only that multiplier 2 doubles the value (TestBBoxStrategy.java:311-329).
The devil's-advocate check181 words

The strongest case for "intended": Query#equals says "Typically a query will be equal to another only if it's an instance of the same class and its document-filtering properties are identical to those of the other instance" (Query.java:95-107), and a multiplier only scales a score; the class is @lucene.experimental; the "not part of identity" comment shows identity was considered on purpose; and the only real caller, Solr, uses one fixed multiplier per field type.

Why it fails: "typically" hedges, and the javadoc does not say that state which changes scores may be left out of equals, while FunctionScoreQuery's own test requires score-only differences to make queries unequal, and BooleanQuery sums the boosts of equal clauses, which is right only if they score the same; the multiplier does change which documents an area filter matches (executed); the comment predates the multiplier and names only ctx; @lucene.experimental warns about API changes, not wrong results. Verdict: not intended, a defect (the independent reproduction, the cross-model review and the intended-behaviour check returned real; the adjudication confirmed it with high confidence).

Suggested fix

#

Recommended A: compare and hash the multiplier

Compare the multiplier in equals with Double.compare and add Double.hashCode(multiplier) to hashCode, as DistanceToShapeValueSource does: +2 lines. The repro passes, and so do all 118 lucene/spatial-extras tests and the module's lint checks. Optionally also make the field final and print the multiplier in toString (validated too).

    if (geoArea != that.geoArea) return false;
    if (Double.compare(multiplier, that.multiplier) != 0) return false;
    if (!shapeValueSource.equals(that.shapeValueSource)) return false;
    ...
    result = 31 * result + (geoArea ? 1 : 0);
    result = 31 * result + Double.hashCode(multiplier);

Downstream note

#

Not a Lucene security issue, but an application that builds area filters with different multipliers on one field would silently have one area FILTER or MUST_NOT clause replaced by the other (executed); restriction clauses that are not area clauses are unaffected.

How it was found

#

A bytecode scan of query components compared the fields their value code reads with the fields equals/hashCode read, and flagged ShapeAreaValueSource.multiplier. An AI tool then wrote a public-API JUnit, and independent reproducers confirmed it on a real BBoxStrategy index. No model checker or solver was involved.

The method in full158 words

Method: semi-formal (a hunt unit, query object contracts).

  • A bytecode scan of the stock main jars (JDK 25 ClassFile API), over the unit's inventory of 184 query-component classes (value sources, intervals sources, rewrite methods), compared for each class the fields read by its value code with the fields read by equals/hashCode. It reported EQ-MISS ShapeAreaValueSource.multiplier, read by ShapeAreaValueSource$1.doubleValue but not by equals/hashCode (its ctx entry is intended, per the class comment).
