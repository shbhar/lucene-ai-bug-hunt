SortedSetDocValues faceting throws NullPointerException for the root of a hierarchical dimension that no document has, instead of returning null

Ask SortedSetDocValues faceting for the top children of a dimension that FacetsConfig declares hierarchical but that no document in the reader has, and you get a NullPointerException instead of the documented null. A flat dimension in the same state returns null; 9.2.0 returned null too, every release since 9.3.0 throws.

The bug in 30 seconds

#

SSDV faceting builds one ordinal tree per hierarchical dimension, and only for dimensions that occur in the reader. Since 9.3.0 a request for the root of a hierarchical dimension reads that tree without checking that it exists; the flat branch and the path branch of the same method do check and return null.

  1. You call config.setHierarchical("category", true) and index one document that has only a flat facet, author=bob. No document has a category yet.
  2. You ask for the top categories: getTopChildren(10, "category") or getAllChildren("category") on SortedSetDocValuesFacetCounts. You expect null: the Facets javadoc returns null "if this dimension was never seen", and the absent flat dimension publisher does return null.
  3. Instead both throw NullPointerException: Cannot read field "dimStartOrd" because "dimTree" is null, with assertions on and off, also from ConcurrentSortedSetDocValuesFacetCounts and the count-all constructor: 4 of the repro's 5 tests fail, the control passes.
  4. Why: since 9.3.0 a request without a path reads state.getDimTree(dim).dimStartOrd directly, and getDimTree returns null for a dimension with no indexed term, because its trees are built only from indexed terms. A path below it, getTopChildren(10, "category", "books"), still returns null.
  5. The same happens after every document with category is deleted and merged away (the call worked before the delete), and when DrillSideways results read a drill-down on such a dimension through getAllDims.

Who is affected

#

Applications on 9.3.0 or later that use SSDV facets with a dimension set hierarchical (a non-default FacetsConfig setting) and ask for its root on a reader where no document has it: a newly configured dimension, a shard or tenant index without it, or all its documents deleted and merged. Deterministic at any size; no wrong results or index damage.

Mechanism, terms and numbers592 words

Facets#getTopChildren and Facets#getAllChildren return null "if this dimension was never seen", and SortedSetDocValues (SSDV) faceting has done so for flat dimensions since LUCENE-9971 (9.0.0). For a dimension that FacetsConfig declares hierarchical, the same request throws when no document in the reader has the dimension: NullPointerException: Cannot read field "dimStartOrd" because "dimTree" is null, from SortedSetDocValuesFacetCounts and ConcurrentSortedSetDocValuesFacetCounts, with assertions on and off. A shortcut added in 9.3.0 by #915 (LUCENE-10585, a cleanup) reads state.getDimTree(dim).dimStartOrd for a request without a path, and getDimTree returns null for a dimension with no indexed term. The flat branch next to it, a path below the same dimension, getSpecificValue and taxonomy faceting all treat that state as "never seen". In 9.1.0 and 9.2.0 getTopChildren returns null (getAllChildren did not exist yet: LUCENE-10550 added it in 9.3.0, already affected); 9.3.0 to 10.5.2 and main throw. A 4-line null check that mirrors the flat branch restores the documented result.

Terms

#
  • SSDV faceting: facet counting over SortedSetDocValuesFacetField values, without a taxonomy index. DefaultSortedSetDocValuesReaderState reads the facet terms of a reader once; SortedSetDocValuesFacetCounts and ConcurrentSortedSetDocValuesFacetCounts count them for a query and share the base class AbstractSortedSetDocValueFacetCounts.
  • Hierarchical dimension: FacetsConfig#setHierarchical(dim, true) lets a dimension have paths such as category/books/fiction. For each such dimension found in the reader, the state builds a DimTree (its first ordinal dimStartOrd plus child and sibling links); a flat dimension gets an OrdRange instead.
  • Root request: getTopChildren(n, dim) or getAllChildren(dim) with no path asks for the dimension's top-level children.

The bug

#
  1. getTopChildren (AbstractSortedSetDocValueFacetCounts.java:56-63 on main a9779ef3c193) returns null when hasCounts() is false (:58), else calls getTopChildrenForPath, which calls prepareChildIteration (:294). getAllChildren (:66-75) calls prepareChildIteration first (:68) and checks hasCounts() only afterwards (:73).
  2. prepareChildIteration (:247-285), hierarchical branch: DimTree dimTree = state.getDimTree(dim); (:252). With a path it runs dv.lookupTerm(...) (:254) and returns null for pathOrd < 0 ("path was never indexed", :259-262). Without a path it takes the shortcut "If there's no path, this is a little more efficient to just look up the dim:" pathOrd = dimTree.dimStartOrd; (:256-257), with no null check.
  3. DefaultSortedSetDocValuesReaderState#getDimTree returns prefixToDimTree.get(dim) (:381-387). The map gets an entry only while the state walks a dimension's indexed terms (:185), so a dimension with no indexed term has none, getDimTree returns null and :257 throws.
  4. The flat branch handles the same case: if (ordRange == null) { // means dimension was never indexed return null; } (:269-273).
  5. So getAllChildren(dim) throws whenever it is called; getTopChildren(n, dim) throws when hasCounts() is true: in practice when the query had hits (strictly, once a segment with hits and the facet field was counted, SortedSetDocValuesFacetCounts.java:79-83, 173-187), always with the count-all constructor, and always for ConcurrentSortedSetDocValuesFacetCounts, whose hasCounts() returns true (ConcurrentSortedSetDocValuesFacetCounts.java:80-84).
  6. Not affected: requests with a path, getSpecificValue (term lookup, -1), and getAllDims/getTopDims of the plain counts, which iterate the indexed dimensions only.

The numbers

#

One document with only author=bob, category configured hierarchical, default codec and searcher. getTopChildren(10, "category") with hits, getAllChildren("category"), the count-all constructor and the concurrent class: 4 of 4 throw the NPE at AbstractSortedSetDocValueFacetCounts.java:257. Controls on the same state: flat publisher null from both calls; getTopChildren(10, "category", "books") and getAllChildren("category", "books") null; getSpecificValue("category") -1. The independent reproducer adds: getAllChildren after a zero-hit query throws, and getTopChildren returns a result while one document has the dimension, then throws after that document is deleted and forceMerge(1) runs.

Exposure and likelihood347 words
  • Who. Applications that use SortedSetDocValues facets with a dimension declared hierarchical (FacetsConfig#setHierarchical, not the default) and ask for its root, getTopChildren(n, dim) or getAllChildren(dim), on a reader in which no document has that dimension: the dimension is configured before its first document arrives; one shard, tenant, time partition or filtered index of an application-wide FacetsConfig lacks it; or every document with it was deleted and merged away (unmerged deletes still keep it "seen"). The dimension must be absent from the whole reader, because the state is built from the reader's terms: a filtered index means one built from a subset of the documents, and a query or filter that excludes every document with the dimension leaves it "seen" and does not trigger the bug (executed, probe S2).
  • Through Lucene's own code. DrillSideways builds one SortedSetDocValuesFacetCounts per drill-sideways dimension and returns them in a MultiFacets, whose getAllDims calls getTopChildren(topN, dim) on each (MultiFacets.java:81-88). A drill-down on a configured hierarchical dimension that no document has returns its hits (0), then getAllDims(10) on the result throws (executed on ea57360912ed and 10.5.2).
  • Default dimension config. An application whose getDefaultDimConfig (FacetsConfig.java:142-151, for dimensions "not known beforehand") makes hierarchical the default gets the exception for any dimension name that is not indexed (executed).
  • What happens. The facet call throws instead of returning null; a caller without per-facet error handling fails the whole request. After the exception the same Facets object and reader state answer other dimensions correctly (executed). No wrong results, no index change.
  • Default vs opt-in. The only non-default setting is the hierarchical flag of an SSDV dimension: the diagram probe, a plain main() with ByteBuffersDirectory, new IndexWriterConfig() (default codec) and a plain IndexSearcher, throws the same NPE with -ea and -da; the JUnit repro, under LuceneTestCase's randomized directory, codec and IndexWriterConfig, failed with every seed run (executed).
  • Scale. Deterministic, one document is enough, assertions on or off.
  • Workaround. Check state.getDimTree(dim) != null before asking for the root of a hierarchical dimension (the method throws UnsupportedOperationException for flat ones).

Why it is a bug, not intended

#
  • The Facets javadoc: both methods return null "if this dimension was never seen"; LUCENE-9971 (9.0.0) made SSDV faceting do so "as per Javadoc spec".
  • For the same state the flat branch, a path below the dimension, getSpecificValue (-1) and taxonomy faceting all say "never seen".
  • 9.2.0's getTopChildren returned null; #915, a cleanup that "doesn't modify the API", added the throw.
The full argument341 words
  • The contract. Facets.java:33-37 (getAllChildren) and :39-44 (getTopChildren): "Returns null if the specified path doesn't exist or if this dimension was never seen." Nothing restricts this to flat dimensions.
  • The precedent. LUCENE-9971 (#149, 9.0.0), CHANGES.txt:4974-4976: "Requesting facet counts for unseen dimensions in SortedSetDocValueFacetCounts and ConcurrentSortedSetDocValueFacetCounts now returns null / -1 instead of throwing IllegalArgumentException as per Javadoc spec in Facets." In that PR's review (2021-05-25) @gsmiller wrote "I think it's reasonable to return null (it's much like a Java Map)", and in its discussion (2021-05-26) "+1 for making the change you proposed, particularly since it's consistent with the Javadoc".
  • Every sibling returns null for the same state (executed): the flat branch (AbstractSortedSetDocValueFacetCounts.java:269-273), the same hierarchical dimension with a path (lookupTerm < 0), getSpecificValue (-1; Facets.java:46-50 "Returns -1 if this path doesn't exist") and taxonomy faceting (FastTaxonomyFacetCounts) with the same FacetsConfig.
  • History. Up to 9.2.0 the hierarchical code looked the dimension up with dv.lookupTerm(...) first and returned null for pathOrd < 0; it read getDimTree only after that. #915 (LUCENE-10585) replaced the lookup with the dimStartOrd shortcut; its author wrote that the change "is purely meant to remove some code duplication and make some very minor optimizations, and doesn't modify the API", the PR says "No new tests were written", and CHANGES calls it a "Facet module code cleanup" (CHANGES.txt:4067-4068). When hierarchical SSDV facets were added (#509, 9.1.0), a dimTree == null check was removed as unreachable ("If we reach this point, it means the path was indexed. Shouldn't there always be a dim tree then?"), which was right while the lookup ran first.
  • Why tests missed it. TestSortedSetDocValuesFacets#testHierarchicalNonExistentDimension configures fizz as hierarchical but asks for "non-existent dimension", which is flat by default, and asserts null (comment: "make sure the result is null (and no exception was thrown)") (:1779-1815).
  • The trigger is legal. Public API only, and every document is built with the same FacetsConfig the search uses, as FacetsConfig's javadoc asks (FacetsConfig.java:53-55).
The devil's-advocate check237 words

The strongest case for "intended or misuse", built by the intended-behaviour verifier, a review by a model from another family (OpenAI GPT-5.6) and the adjudication: the facet classes are @lucene.experimental, SortedSetDocValuesReaderState#getDimTree is not documented as non-null, a dimension that is configured but has no documents could be called a configuration/index mismatch, and the upstream never-seen tests only use an unconfigured name.

A narrower precedent a committer may raise: in the same #149 review @gsmiller argued for keeping an IllegalArgumentException when a dimension configured in FacetsConfig is looked up in the wrong index field ("hey, we actually know about this dimension but you're looking in the wrong place!"), and taxonomy faceting does that today (TaxonomyFacets#verifyDim, TaxonomyFacets.java:213-235). It does not cover this case: the repro reads the dimension's own (default) index field, the dimension simply has no document, and that review argued for a deliberate, descriptive exception for a misconfiguration, not for an NPE on a legal state.

Why it fails: experimental means the API may change, not that it may throw an NPE against its own javadoc; the javadoc covers exactly the "never seen" case; every document was built with the same config, as required; the flat branch, the path branch, getSpecificValue and taxonomy faceting all treat the state as never seen; 9.2.0 returned null; and #915 was declared API-neutral. Every reviewer rated the intended argument weak or none. Verdict: not intended, a regression.

Suggested fix

#

Recommended Return null when the dimension has no tree

In prepareChildIteration, return null when state.getDimTree(dim) is null, with the flat branch's own comment "means dimension was never indexed" (4 lines). The repro and a new test in TestSortedSetDocValuesFacets then pass with assertions on and off, and so does the whole facet module suite (312 tests).

     if (dimConfig.hierarchical) {
       DimTree dimTree = state.getDimTree(dim);
+      if (dimTree == null) {
+        // means dimension was never indexed
+        return null;
+      }
       if (path.length > 0) {
All options and trade-offs3 options · 630 words

One fix was applied in a scratch worktree at a9779ef3c193 and run through gradle (seed DEADBEEF), together with a new upstream-style test in TestSortedSetDocValuesFacets; option B was run on 9.3.0 by the version-history runs; option C was not run.

Return null when the dimension has no tree (validated by the checks) (recommended)

#

Four lines in AbstractSortedSetDocValueFacetCounts#prepareChildIteration, right after getDimTree. The shortcut stays and the term lookup that #915 removed does not come back (the cost of the added null check was not benchmarked); the root of an unindexed hierarchical dimension returns null, as in 9.2.0, and a path request for it returns the null it already returned, one step earlier. A second diff adds testConfiguredHierarchicalDimensionNeverIndexed to TestSortedSetDocValuesFacets, next to testHierarchicalNonExistentPath: root and path requests return null and getSpecificValue returns -1, through getAllFacets (sequential or concurrent at random).

     if (dimConfig.hierarchical) {
       DimTree dimTree = state.getDimTree(dim);
+      if (dimTree == null) {
+        // means dimension was never indexed
+        return null;
+      }
       if (path.length > 0) {

Trade-offs

  • None for results: it returns what the javadoc, the flat branch and 9.2.0 return.
  • It also turns any other route to a missing tree into null. LFV-324 (the SSDV tree is built from ord order and can drop a dimension that is present) may reach the same line for a dropped dimension (inferred, not executed); this check would turn that crash into null but does not fix LFV-324, which belongs in the tree construction.
  • Placement: the check sits before the path/no-path split. With the default reader state getDimTree is null only when the dimension has no indexed term, where a path request already returned null; but a custom SortedSetDocValuesReaderState that returns no tree for a dimension with indexed terms, or a tree dropped by LFV-324, would now get null for a path request too instead of an NPE at dimTree.iterator(pathOrd) (:263). To keep that loud, put the check only in the empty-path branch, or use option B. Neither variant was run.

What the checks validated

  • Stock main a9779ef3c193: the repro fails 4 of 5 and the new upstream-style test fails (6 tests, 5 failed), with assertions on and off.
  • With the fix (gradle, scratch worktree at a9779ef3c193, seed DEADBEEF): the repro and the new test pass, 6 of 6, with -Ptests.asserts=true and =false.
  • With the fix, the whole lucene/facet test suite, including both new tests: 312 tests in 40 classes, 0 failures, 8 skipped; checkGoogleJavaFormat and ecjLint of the facet module pass.
  • Classpath runner, the fix shadowed onto the stock main jars: the repro passes 5 of 5 and the independent reproducer's test 8 of 8. In the hunt, the finder's fix (the same check) turned the finder harness's 15 NullPointerException entries into 0, and with the hunt unit's fix sketches shadowed together 75 upstream facet tests passed (TestSortedSetDocValuesFacets, TestDrillSideways, TestParallelDrillSideways, TestMultipleIndexFields and three taxonomy suites, seeds DEADBEEF and 1234ABCD).
  • Not run: a benchmark (the change adds one null check per root request).

Restore the term lookup for the root too (run on 9.3.0 only)

#

Drop the shortcut: resolve pathOrd with dv.lookupTerm(pathToString(dim, path)) for every request, return null for pathOrd < 0, then read getDimTree, as 9.2.0 did. The version-history runs's one-hunk revert on 9.3.0 is this option, and both repros pass with it.

Trade-offs

One extra term lookup per root request, the cost #915 wanted to save; not run on main.

Make getDimTree never return null (not run)

#

Return an empty DimTree for a hierarchical dimension with no indexed term.

Trade-offs

Changes a public abstract method of SortedSetDocValuesReaderState that custom implementations override, and an empty tree needs care so that the root is not reported as an existing path; more change than the bug needs.

Downstream note

#

A read-only GitHub code search (default branches only, best effort) found no use of these SSDV facet classes in Elasticsearch, OpenSearch or Solr; nothing was tested downstream. The clearest known audience is custom applications on the facet module; one whose getDefaultDimConfig makes dimensions hierarchical gets the exception for any unindexed dimension name a user asks for.

How it was found

#

Randomized model-based metamorphic testing of the Facets API: a reference written from the javadoc ran against the real classes on random facet schemas and tiny indexes. Its exception bucket held 15 of these NullPointerExceptions in 500 iterations, all where a hierarchical SSDV dimension had no document, and none with the null check added.

The method in full190 words

Method: randomized model-based metamorphic testing (non-formal tier), in a hunt unit on the facet API.

  • A written specification of the five Facets methods, taken from their javadoc (for example: getTopChildren and getAllChildren return null for a dimension that was never seen), served as an executable reference.
  • The harness built random facet schemas (0-3 count dimensions, flat or hierarchical of depth 1-3, single- or multi-valued, plus association dimensions) over indexes of at most 40 documents in 1-4 segments with random deletions, and compared taxonomy, SSDV and string-value faceting, MultiFacets and TaxonomyFacetLabels, sequential and concurrent, against the reference.
  • In 500 iterations with seed 11 its exception buckets for SSDV faceting held 15 NullPointerException entries, all with the dimTree message and all in schemas where a hierarchical SSDV dimension had no document; with the one null check shadowed onto the jar they went to 0. The case was then reduced to a public-API JUnit.
  • Found 2026-10-26 on main ea57360912ed; then checked by an independent reproducer, an intended-behaviour devil's advocate, read-only reviews by a model from another family (OpenAI GPT-5.6), an adjudication, a history, prior-report and security follow-up, and a credibility audit.

History

#

Introduced by #915 (LUCENE-10585, 8db1e41fc07, 2022-05-29), first released in 9.3.0. Executed: getTopChildren returns null in 9.1.0 and 9.2.0 (getAllChildren arrived in 9.3.0); 9.3.0, 9.10.0, 9.11.0, 9.12.3, 10.0.0, 10.5.2 and main throw. A commit-level bracket on branch_9x and a one-hunk revert on 9.3.0 confirm the cause. Not fixed upstream.

Versions tested10 rows

Introduced by 8db1e41fc072 on main, "LUCENE-10585: Scrub copy/paste code in the facets module and attempt to simplify a bit (#915)" (@gsmiller, 2022-05-29), and its branch_9x backport 075f5103e9ac the same day, which shipped first, in 9.3.0. It replaced the null-safe lookupTerm of the hierarchical branch with pathOrd = dimTree.dimStartOrd for a request without a path. #914 (LUCENE-10550, 9.3.0) copied the shortcut into the new getAllChildren, and #983 (9.3.0) moved both copies into prepareChildIteration, which is why git blame on main names #983.

Since 9.11.0 (#12408, backported as #13300) SortedSetDocValuesFacetCounts#getTopChildren with zero hits returns null before it reaches the shortcut; every other entry point still throws. The unguarded line is present at every release tag from 9.3.0 to 10.5.2 (read).

LFV-527, snapshot of 2026-10-30

Registry title
SortedSetDocValues faceting throws NullPointerException from getTopChildren/getAllChildren for a dimension that is configured hierarchical but has no document in the reader, instead of returning null as the Facets javadoc says (regression since 9.3.0)
Area
facet / SortedSetDocValues faceting (AbstractSortedSetDocValueFacetCounts#prepareChildIteration, shared by SortedSetDocValuesFacetCounts and ConcurrentSortedSetDocValuesFacetCounts)
Priority
Medium, rank 207: Hierarchical SortedSetDocValues facets throw NPE for a configured dim absent from the reader, a deterministic loud regression since 9.3 on sharded or fresh indexes, so it follows LFV-526.
Impact class
crash
Impact note
Applications that use SortedSetDocValues facets with a dimension declared hierarchical in FacetsConfig (a non-default setting) and ask for the root of that dimension, getTopChildren(n, dim) or getAllChildren(dim), on a reader in which no document has it (the dimension is configured before its first document, a shard, tenant or filtered index lacks it, or all its documents were deleted and merged away) get a NullPointerException instead of null, also through DrillSideways results whose getAllDims calls getTopChildren per drill-down dim; default codec, IndexWriterConfig and searcher, tiny indexes, -ea and -da, every release from 9.3.0 to 10.5.2 and main; no wrong results, no index damage, and path requests, flat dimensions, getSpecificValue, getAllDims and getTopDims of the plain counts are unaffected.
Summary
You declare a facet dimension as hierarchical (FacetsConfig.setHierarchical("category", true)), index SortedSetDocValues facets in which no document has "category" yet, and call getTopChildren(10, "category") or getAllChildren("category") on SortedSetDocValuesFacetCounts or ConcurrentSortedSetDocValuesFacetCounts, expecting null, because the Facets javadoc says both methods return null 'if this dimension was never seen' and the same call for a flat dimension does. Instead both throw NullPointerException: Cannot read field "dimStartOrd" because "dimTree" is null (getTopChildren when the query has hits, always with the count-all constructor and the concurrent class; getAllChildren always). The cause is a shortcut added in 9.3.0 to AbstractSortedSetDocValueFacetCounts#prepareChildIteration, which reads dimTree.dimStartOrd for an empty path without checking that state.getDimTree(dim) is non-null, while the flat branch and the path branch next to it return null for the same case.
Introduced
8db1e41fc072920dc1c6554f5859d4dd623dace6 (LUCENE-10585, apache/lucene#915 'Scrub copy/paste code in the facets module and attempt to simplify a bit', by @gsmiller; branch_9x backport 075f5103e9ac7f344d11e4b3ad3699a1f2be9f66, the line that shipped first) [exec: the facet module compiled at the backport 075f5103e9a fails the history test 4 of 7 with the same NPE, at its parent eecf8ea63b9 it passes 7 of 7; reverting only the shortcut on 9.3.0 makes both repros pass]. It replaced the null-safe dv.lookupTerm(pathToString(dim, path)) of the hierarchical branch with 'pathOrd = dimTree.dimStartOrd' for an empty path ('a little more efficient to just look up the dim'), ahead of the 'pathOrd < 0 -> null' check. LUCENE-10550 (#914, 9.3.0) copied the shortcut into the new getAllChildren and #983 (9.3.0) moved both copies into prepareChildIteration (git blame on main points at that move). In the review of LUCENE-10250 (#509, 9.1.0) a dimTree == null check had been removed as unreachable, which was correct while the term lookup ran first.
