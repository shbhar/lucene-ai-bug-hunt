IndexWriter#addBatch does not range-check the tuple doc ids of a doc-values-only DictionaryColumn: doc id numDocs() lands on the next document added

IndexWriter#addBatch never range-checks the tuple doc ids of a doc-values-only DictionaryColumn: in a 2-document batch, a tuple for doc 2 is accepted and its value lands on the next document you add. Every other column kind rejects the same off-by-one with IllegalArgumentException.

The finding in 30 seconds

#

The column pass turns each tuple's batch doc id into a segment doc id. It range-checks that id for every column kind except a doc-values-only DictionaryColumn, whose writer only checks that ids increase. So batch doc numDocs becomes the segment number of the next document you add, and that document gets the value.

Background: indexing a batch by columns

#
  1. IndexWriter#addBatch(ColumnBatch) (experimental, since 10.5.0) adds a batch of documents column by column. A batch has numDocs() documents, numbered 0 to numDocs() - 1 inside the batch.
  2. Each column carries one field. A sparse column gives Lucene (doc id, value) pairs through a tuple cursor that the application writes; a DictionaryColumn gives each value as an ordinal into its dictionary, for SORTED or SORTED_SET doc values.
  3. Lucene appends the batch to the in-memory segment: batch doc i becomes segment doc baseDocID + i, and the next document added after the batch gets the next segment number, baseDocID + numDocs.

The finding, step by step

#
  1. Build a ColumnBatch with numDocs() == 2 and one doc-values-only SORTED DictionaryColumn "tag" (dictionary a, b) whose own cursor returns (doc 0, a) and (doc 2, b). Doc 2 is one past the end: an off-by-one in your cursor.
  2. Call writer.addBatch(batch), then writer.addDocument(new Document()) with no "tag" field, and open an NRT reader: 3 documents.
  3. You expect addBatch to throw IllegalArgumentException ("returned batch doc-id 2 which is out of range [0, 2)"), as it does for a LongColumn or BinaryColumn with the same mistake, or at least the new document to have no tag.
  4. Instead addBatch returns normally and the new document, segment doc 2, reads tag = b. The dictionary path skips the range check, and its writer only checks that doc ids increase, so it stores a value for a document that does not exist yet.
  5. The same happens with SORTED_SET columns, and doc id -1 can land on the document added just before the batch, when there is one. No error with assertions on or off, on 10.5.0, 10.6.0 and main.

Who is affected

#

Applications that use the experimental addBatch (10.5.0 and later) with a doc-values-only SORTED or SORTED_SET DictionaryColumn whose own cursor is off by one at either end. Default config, a 2-document batch, assertions on or off. A document added through plain addDocument silently gains a value, and sorting, faceting or doc-values filters on that field see it.

Mechanism, terms and numbers927 words

IndexWriter#addBatch(ColumnBatch) (experimental, since 10.5.0) indexes a batch column by column; the application writes the tuple cursors that say which batch document gets which value, and ColumnBatch#numDocs says "All column doc-ids must be in the range [0, numDocs())". The column pass enforces that rule with ColumnValidation.checkDocID on every LongColumn, BinaryColumn and vector tuple, and the row pass enforces it for stored and indexed columns, but IndexingChain.processDictionaryColumn hands a doc-values-only DictionaryColumn's tuples straight to the SORTED / SORTED_SET writers, which check only that ids increase (SORTED) or only assert it (SORTED_SET). So in a 2-document batch a tuple for doc 2 is accepted, stored for segment doc baseDocID + 2, and the next document added with plain addDocument silently reads that value; doc id -1 can land on the document added just before the batch, if there is one. No error with assertions on or off. Every trigger is a caller cursor that breaks the documented contract of an experimental API, so the priority is low and maintainers will likely call the fix hardening; but the same mistake is rejected on every other column kind, and here a document outside the batch changes. A related gap, fixed by the same patch: on SORTED_NUMERIC and SORTED_SET columns the only check that tuple doc ids never decrease is a Java assert. It is in 10.5.0 to 10.6.0 and main; a cursor wrapper that calls checkDocID fixes it and passes all 8,898 core tests.

  1. Every other tuple loop checks the batch doc id first: ColumnValidation.checkDocID(column, batchDocID, numDocs) (ColumnValidation.java:296-307, "Throws if batchDocID is outside [0, numDocs)") at IndexingChain.java:982, :990, :1017, :1026, :1038 (LongColumn), :1125, :1136, :1149, :1162 (BinaryColumn), :1280, :1293, :1306 (vectors). The row pass rejects out-of-order (:903-909) and out-of-range (:948-958) ids of stored and indexed columns.
  2. processDictionaryColumn does not, for sparse SORTED and for every SORTED_SET column. The writers do not check the range either: the SORTED writer checks only that ids increase (SortedDocValuesWriter.java:133), the SORTED_SET writer only asserts it (SortedSetDocValuesWriter.java:125).
  3. So segment doc baseDocID + numDocs gets a value although that document does not exist yet. The next document added to the in-memory segment takes that number; if it has no value for the field, nothing notices, and the flush writes the value as its own. Doc id -1 gives segment doc baseDocID - 1, the document added just before the batch, if the in-memory segment has one. For SORTED_SET the value is added to that document's set, because the writer keeps its last document open until the next one or the flush; SORTED accepts it only if that document has no value for the field (otherwise the order check at :133 rejects it, as it does when the batch starts the segment). The executed -1 runs (a SORTED_SET test of the study, a SORTED case of the diagram probe) each had one earlier document without a value.
  4. No error with the default codec, assertions on or off, when a later document fills the slot. With no later document, one exploration run (assertions off, default codec; a single observation, not a general result) committed a 2-document segment that read back 0=a 1=b (batch doc 1 had no value) and CheckIndex reported it clean; with the test framework's asserting codec the flush can instead fail an assertion.
  5. Not affected: DENSE SORTED dictionary columns (the dense path counts values, :1236-1239) and stored or indexed dictionary columns (the row pass rejects the id first).

A related gap, fixed by the same patch: order checked only by assert

#

SortedNumericDocValuesWriter.addValue (:63), SortedSetDocValuesWriter.addValue (:85) and SortedSetDocValuesWriter.addOrdinalTuples (:125) check that doc ids never decrease only with assert docID >= currentDoc;. The two addValue asserts were written in 2016 (LUCENE-7474) for the per-document chain, which generates the ids itself, and #15990 routed caller tuple ids into them; #16101 wrote addOrdinalTuples with a copy of the same assert; the cursor javadoc says the ids are "emitted in non-decreasing order". With tuples (1, v) then (0, v') on a SORTED_NUMERIC LongColumn or SORTED_SET column: with assertions on, an AssertionError escapes addBatch and the writer closes as a tragic event (IndexWriter.java:1581-1589); with assertions off (production) the batch is accepted and a later valid addDocument with that field is rejected with Out of order doc ids: last=1, next=0; the study also saw a later document read a batch value ([20] instead of [40]) and, for SORTED_SET, the next commit fail and close the writer. NUMERIC, BINARY/SORTED and SORTED dictionary columns already reject backwards ids, through the single-valued writers' "appears more than once in this document" check. The one-test repro covers the range gap only.

Exposure and likelihood213 words
  • Who is hit. Callers of the experimental IndexWriter#addBatch (also updateDocuments(Term|Query, ColumnBatch)), new in 10.5.0, with a doc-values-only DictionaryColumn (SORTED sparse; SORTED_SET sparse or dense) and a tuple cursor of their own that returns numDocs or -1. Lucene ships only abstract columns and cursors, so every caller writes its own cursor.
  • No special setup. Default IndexWriterConfig, codec and directory; a 2-document batch with one boundary tuple; deterministic; assertions on or off. Far-out ids were not run.
  • What goes wrong. A document outside the batch, which the caller added with plain addDocument, silently gets a SORTED or SORTED_SET value it never had (for SORTED_SET, an extra value in its set), and anything that reads that field's doc values sees it. With no later document, a document inside the batch can get the value instead, and CheckIndex called the result clean (one exploration run, default codec).
  • What does not go wrong. Correct cursors are unaffected; DENSE SORTED, stored and indexed dictionary columns are checked; nothing outside doc values is touched. The one downstream user found (Elasticsearch, by code reading) builds no DictionaryColumn, and its tuple cursors take doc ids from a bounded row counter.
  • Impact class: data corruption, likelihood contrived (it needs a buggy caller cursor on an experimental API); priority low.

Why it looks unintended

#
  • The same addBatch rejects the same out-of-range id with IllegalArgumentException on every other column kind, with upstream tests.
  • The other rule of the same cursor javadoc, ordinals in range, is checked on this very path; the doc-id rule is not.
  • #16101 added the dictionary path without the check #15990 gave the others, and the value lands outside the batch.
The full argument246 words
  • The same boundary rejects the same mistake everywhere else. ColumnValidation.checkDocID runs on every Long, Binary and vector tuple, and the row pass rejects bad ids for stored and indexed columns. Upstream tests assert it: TestColumnBatchIndexing#testRowColumnOutOfRangeDocIdThrows and #testRowColumnOutOfOrderDocIdThrows, TestColumnBatchVectorColumn#testVectorOutOfRangeDocIDFails and #testDecreasingDocIDFails. The study's parity probe: out-of-range ids on BinaryColumn SORTED, LongColumn NUMERIC and a stored DictionaryColumn are rejected with IllegalArgumentException and the writer stays open.
  • The other clause of the same javadoc is enforced. OrdinalsTupleCursor says ids are "batch-local (0 to numDocs - 1)" and each ordinal "must be in [0, dictionary.length)"; the ordinal rule is checked on this path and tested (TestColumnBatchDictionaryColumn#testOutOfRangeOrdSparseThrows, #testOutOfRangeOrdDenseThrows), the doc-id rule is not.
  • History shows an omission, not a decision. checkDocID came with the API (#15990, 2026-05-14). #16101 (2026-05-26) added DictionaryColumn without it, with one approving review and no comments; its tests cover out-of-range ordinals only. The reviewed history (both PRs and their review threads, the 9 mails of the dev@ DISCUSS thread) and the code comments give no sign that the omission was deliberate.
  • Precedents. #16708 (merged 2026-09-28; CHANGES.txt lists it under 10.6.0 "Improvements", not "Bug Fixes") closed another addBatch-vs-addDocument validation gap, vector values; the API author's open #16116 adds doc-id order and upper-bound checks for a new column-pass consumer. Both support consistency; #16708's label also points toward a "hardening" label for this one.
  • The damage leaves the batch: the value lands on a document the caller added separately, through addDocument.
The devil's-advocate check240 words

Strongest case for "intended" (caller misuse, so the fix is hardening): the rule is a caller obligation. ColumnBatch#numDocs says "All column doc-ids must be in the range [0, numDocs())", the cursors say ids are batch-local and non-decreasing, the API is @lucene.experimental, and addBatch declares only IOException, so nothing promises an IllegalArgumentException. Breaking the precondition is undefined behaviour. (Built by the study's intended-behaviour checker and an independent reviewer from another model family, OpenAI GPT-5.6, which rated it moderate.)

Why it fails: (1) Lucene treats the range part of that precondition as something to enforce: every other column-pass tuple loop range-checks its doc ids, since the API's first commit, with tests, and the neighbouring ordinal clause of the same javadoc is enforced on this very path (order is enforced less uniformly: three sibling paths only assert it). (2) The range check is two int comparisons per tuple, which every sibling path already pays; fix A adds one order comparison and one wrapper call per dictionary tuple. (3) The failure is silent and lands outside the caller's batch. (4) #16708 and #16116 show the project fixing exactly this kind of gap. What remains is the label, bug or hardening, which sets the low priority, not the verdict. A maintainer may also cite the dev@ proposal's goal of "less redundant field validation"; the study's intended-behaviour checker read that as schema checks once per column, not per-tuple doc-id checks. Verdict: not intended.

Suggested fix

#

Recommended A. Check the dictionary tuples in processDictionaryColumn, and turn the order asserts into exceptions

In processDictionaryColumn, wrap the tuple cursor so every doc id goes through ColumnValidation.checkDocID (plus an order check), and turn the three assert docID >= currentDoc order checks into IllegalArgumentException. The repro passes, as do 14 closest suites (784 tests, assertions on and off) and all 8,898 core tests.

All options and trade-offs3 options · 641 words

A is validated and recommended; its checkedTuples wrapper is what fixes this bug, and the writer changes close the related order gap. B is the range part alone. A separate finding about a rejected out-of-range ordinal on a SORTED_SET DictionaryColumn has a different root cause, but its fix edits the same addOrdinalTuples loop. Workaround for users today: in your own cursor, check 0 <= doc && doc < numDocs, and that ids never decrease, before returning a doc id from nextDoc().

A. Check the dictionary tuples in processDictionaryColumn, and turn the order asserts into exceptions (validated by the checks) (recommended)

#

The study's fix, formatted with the build's google-java-format, +61/-6 in IndexingChain, SortedNumericDocValuesWriter and SortedSetDocValuesWriter. Shown: the wrapper that both dictionary branches now use (writer.addOrdinalTuples(baseDocID, dict, checkedTuples(column, numDocs))). The writer changes replace assert docID >= currentDoc; with if (docID < currentDoc) throw new IllegalArgumentException("field \"...\": doc ids must be added in non-decreasing order; got " + docID + " after " + currentDoc).

private static OrdinalsTupleCursor checkedTuples(DictionaryColumn column, int numDocs) {
  final OrdinalsTupleCursor in = column.tuples();
  return new OrdinalsTupleCursor() {
    int last = -1;

    @Override
    public int nextDoc() {
      int doc = in.nextDoc();
      if (doc != DocIdSetIterator.NO_MORE_DOCS) {
        ColumnValidation.checkDocID(column, doc, numDocs);
        if (doc < last) {
          throw new IllegalArgumentException(
              "DictionaryColumn \""
                  + column.name()
                  + "\" returned out-of-order batch doc-id "
                  + doc);
        }
        last = doc;
      }
      return doc;
    }

    @Override
    public int ordValue() {
      return in.ordValue();
    }
  };
}

Trade-offs

Callers with a buggy cursor now get an IllegalArgumentException from addBatch, as on the other column kinds. Cost: three int comparisons (two in checkDocID, one for order) and one wrapper call per dictionary tuple (no benchmark run). The writer checks also sit on the per-document path (addValue runs for every SORTED_NUMERIC / SORTED_SET value of addDocument, where ids are always in order); an if replaces an assert there. Not a rollback: the exception comes after updateBatch has reserved the batch's doc ids, and earlier tuples may already be buffered; the batch's documents are then marked deleted (DocumentsWriterPerThread.java:339-354), not erased. In the diagram probe's fix run the rejected batch left 2 deleted documents in RAM and tuple (0, a) buffered; the readers then showed one live document with no tag, and CheckIndex was clean. What was tested is a usable writer and no spill onto the next document.

Downstream note

#

Only the application's own cursor chooses these doc ids; a product that maps client-sent row positions to them without its own check could see a doc-values value land on a neighbouring document.

How it was found

#

Fuzzing the columnar addBatch API: a fuzz target that checks the writer after random batches found a dense SORTED_SET dictionary batch for 7 documents whose last tuple named doc 7, one past the end; it was accepted and changed the next document. A code check showed that only the dictionary path skips the range check.

The method in full181 words
  • Method (non-formal): fuzzing in a hunt unit on the columnar addBatch API. A Jazzer target built random column batches and checked a writer-consistency property after every addBatch. Its smoke run found a dense SORTED_SET DictionaryColumn for numDocs = 7 whose 8 tuples had doc ids 0 to 7 (the target numbers dense tuples 0, 1, 2, ...), so the last was doc id 7 = numDocs, one past the end; addBatch accepted it and it changed the next document's values ("recovery doc lost its SORTED_SET value for field a (batch threw=false)"). The tuple count alone is not the fault: a dense SORTED_SET column needs at least one value per document, and this path counts nothing.
  • Diagnosis. A read-only check showed that every column-pass tuple loop calls checkDocID except the dictionary path. The order gap was found separately, by code reading while modelling the column pass: the 2016 per-document asserts now receive caller tuple ids.
  • Reduction. The finder wrote public-API JUnit tests (6 tests, range and order); a later minimization kept only the 2-document SORTED case as the one-test repro.

LFV-098, snapshot of 2026-11-07

Registry title
IndexWriter#addBatch does not validate tuple doc-ids on some doc-values column paths: a doc-values-only SORTED/SORTED_SET DictionaryColumn accepts a doc-id outside [0, numDocs) and writes the value onto a neighbouring document, and SORTED_NUMERIC/SORTED_SET columns check doc-id order only with a Java assert, so decreasing doc-ids close the writer (-ea) or are accepted and break later documents and commits (-da)
Area
index / columnar addBatch (column pass: DictionaryColumn, SORTED_NUMERIC and SORTED_SET doc-values writers)
Priority
Low, rank 890: AddBatch skips doc-id validation on some doc-values column paths, so an off-by-one in a caller's cursor silently lands a value on a neighbouring document, but only buggy callers of an experimental API hit it.
Impact class
data corruption
Impact note
Hits only applications that call the experimental IndexWriter#addBatch (first released in 10.5.0) with a tuple cursor of their own that breaks the documented doc-id contract, either a doc-id of -1 or >= numDocs on a doc-values-only SORTED or SORTED_SET DictionaryColumn or decreasing doc-ids on a SORTED_NUMERIC LongColumn, SORTED_SET BinaryColumn or SORTED_SET DictionaryColumn, which is input that every sibling column path rejects with IllegalArgumentException; default IndexWriterConfig, codec and directory, ordinary scale (one bad tuple); the damage reaches documents outside the batch (a value silently attached to the previous or next document, surviving commit with a clean CheckIndex, or a writer that closes and loses uncommitted documents), and the one downstream user found (Elasticsearch, code reading) builds no DictionaryColumn and the tuple cursors read there take doc-ids from a bounded row counter, so they are in order by construction.
Summary
You add a batch with IndexWriter#addBatch whose doc-values-only DictionaryColumn (SORTED or SORTED_SET) has a tuple cursor that returns a batch doc-id equal to numDocs or -1, or whose SORTED_NUMERIC or SORTED_SET column returns doc-ids in decreasing order, for example (1, v) then (0, v'). You expect an IllegalArgumentException with the writer still open and no other document touched, which is what the same addBatch call does for LongColumn, BinaryColumn, vector and stored or indexed (row-pass) columns that break the same documented contract. Instead the out-of-range value is silently attached to the document indexed just before or just after the batch (it survives commit, and CheckIndex reports a clean index), and the out-of-order tuples either throw an AssertionError that closes the writer (-ea) or are accepted (-da), after which a later valid addDocument is rejected with 'Out of order doc ids: last=1, next=0', another later document reads a value from the batch, and the next commit can fail and close the writer.
Introduced
Two commits by Tim-Brooks, both first released in 10.5.0. Part (b), order on SORTED_NUMERIC LongColumn and SORTED_SET BinaryColumn: 3d895681557 (#15990 'Add experimental columnar indexing api', main; branch_10x backport 3ec3bff01b1, #16066), which started passing caller tuple doc-ids to SortedNumericDocValuesWriter.addValue and SortedSetDocValuesWriter.addValue, whose only order check is 'assert docID >= currentDoc' from d50cf97617c (LUCENE-7474, 2016, written for the per-document path where the writer assigns the ids), and added only the range check (checkDocID) on those loops. Part (a), range, plus the SORTED_SET DictionaryColumn order case: e79c6780627 (#16101 'Add DictionaryColumn for SORTED / SORTED_SET dvs', main; branch_10x cherry-pick 8a9e55f254d), whose processDictionaryColumn never calls checkDocID and whose SortedSetDocValuesWriter.addOrdinalTuples has only the assert [read: git log -S/-L, git blame and ancestry in the full-history clone; exec: release boundary only, 10.4.0 cannot compile the repro and 10.5.0 fails; builds at the two commits were prepared but not run]; not a regression of any release (2026-05-14 (part b, #15990 merged) / 2026-05-26 (part a, #16101 merged))
