Hunspell FLAG UTF-8 with an 8-bit SET other than ISO8859-1 merges affix classes, so spell() and the stemmer accept forms the dictionary forbids

With FLAG UTF-8 and an 8-bit SET such as ISO8859-2, Lucene's Hunspell Dictionary splits each two-byte flag into two characters and affix rules keep only the first, so the classes á and â merge: kote is accepted and stems to kot, silently. ISO8859-3, -6 and -8 fail to load.

The bug in 30 seconds

#

A Hunspell .aff can say FLAG UTF-8 (each affix class is named by one Unicode character) and SET ISO8859-2 (the words are Latin-2). Lucene decodes the whole line as Latin-2 first, so a two-byte flag turns into two characters, and an affix rule keeps only the first one.

  1. Load a Hunspell dictionary whose .aff says SET ISO8859-2 and FLAG UTF-8 (both standard values) and has two suffix classes: flag á adds "a", flag â adds "e". The .dic lists kot/á and las/â.
  2. You expect kot to take only "a" and las only "e": accept kota and lase, reject kote and lasa. C Hunspell does this for all 18 SET values tried, and so does Lucene with SET ISO8859-1 or UTF-8.
  3. Lucene reads the .aff and .dic through an ISO8859-2 decoder before it parses the flags, so á (bytes C3 A1) becomes the two characters ĂĄ and â (C3 A2) becomes Ă˘. An affix rule keeps only the first character: both rules get the flag Ă (U+0102), and both words carry Ă.
  4. You get spell("kote") and spell("lasa") = true and stem("kote") = [kot], with no error. On main, 12 of the 18 SET values merge this way, ISO8859-3, -6 and -8 throw UnmappableCharacterException at load, and only no SET, ISO8859-1 and UTF-8 are right.

Who is affected

#

Users of the opt-in Hunspell module (Dictionary, Hunspell, HunspellStemFilter and its factory) whose dictionary pairs FLAG UTF-8 with an 8-bit SET other than ISO8859-1 and has non-ASCII flags sharing a lead byte (under ISO8859-14, even with different lead bytes). The dictionary loads, but spell checking and stemming overaccept, silently. No public dictionary with this combination is known.

Mechanism, terms and numbers804 words

After a first pass finds the SET and FLAG lines, Lucene's Hunspell Dictionary reads the whole .aff and the .dic through the SET decoder before it parses flags. For FLAG UTF-8 (flags are UTF-8 characters) it undoes that decoding only when the decoder's charset is ISO-8859-1 (LUCENE-9708); every other 8-bit SET that loads gets one flag per decoded character, except ISO8859-14, whose decoder claims to be ISO-8859-1. A two-byte flag such as á (C3 A1) therefore becomes two characters; an affix rule keeps only the first, the lead byte shared by all of U+00C0-U+00FF, while a word keeps both. Affix classes whose flags share a lead byte merge: spell() accepts and the stemmer stems forms the dictionary forbids, with no error. On main this affects 12 of 18 SET values (ISO8859-2, -4, -5, -7, -9, -13, -14, -15, KOI8-R, KOI8-U, microsoft-cp1251, TIS620-2533); ISO8859-3, -6 and -8 fail to load with UnmappableCharacterException. C Hunspell 1.3.2 and 1.7.2 decode such flags from the raw bytes and are right for all 18. All 13 releases run, from 3.5.0 to 10.5.2, mishandle these files (3.5.0-4.7.2 and 8.9.0-10.5.2 silently, 4.8.0-8.8.2 with a load error), and the source history places the releases in between in the same eras. No public dictionary is known to use the combination. A byte-table decoder fixes all three observed symptoms in the probe and the tests, and the module's 1,917 tests pass with it.

Terms

#
  • .aff / .dic: a Hunspell dictionary is an affix file (rules such as SFX á 0 a .: "class á adds the suffix a") and a word list (kot/á: the word kot may take the classes named by flag á).
  • SET: the encoding of the files' words, for example ISO8859-2 (Latin-2) or KOI8-R. hunspell(5): "Set character encoding of words and morphemes in affix and dictionary files."
  • FLAG UTF-8: each flag is one Unicode character written in UTF-8. hunspell(5): "`UTF-8' parameter sets UTF-8 encoded Unicode character flags." C Hunspell decodes these flags from the raw bytes whatever the SET is.
  • Lead byte: the first byte of a multi-byte UTF-8 character. All of U+00C0-U+00FF start with C3, all of U+0400-U+043F with D0.

The bug

#
  1. A first pass finds the SET and FLAG lines (Dictionary.java:245-260, :837-868); then Dictionary reads the whole .aff and the .dic through a reader that decodes the SET charset (:348, :1015), so flags arrive as SET-decoded characters.
  2. getFlagParsingStrategy (Dictionary.java:922-944) gives FLAG UTF-8 the strategy that turns those characters back into bytes and reads them as UTF-8 (DefaultAsUtf8FlagParsingStrategy) only if the decoder's charset equals ISO-8859-1 (:932). Every other 8-bit SET that loads gets SimpleFlagParsingStrategy (:935): one flag per decoded character, except ISO8859-14 (step 5).
  3. An affix rule takes one flag with parseFlag, which returns the first character and ignores the rest because checkFlags = false (:1356, :1364-1370). A word takes all characters (:1130).
  4. So with SET ISO8859-2, á (C3 A1) reads as ĂĄ and â (C3 A2) as Ă˘: both rules become class Ă, and the words carry [Ă, Ą] and [Ă, ˘]. Each word now takes both suffixes.
  5. ISO8859-14 is read by ISO8859_14Decoder, which reports ISO-8859-1 as its charset (ISO8859_14Decoder.java:45), so it takes the ISO-8859-1 branch; re-encoding turns the bytes its table remaps into ?, and both rules get U+FFFD. Under ISO8859-14 flags merge even when their lead bytes differ: á (C3 A1) and ġ (C4 A1) stay apart under ISO8859-2 and -15 but merge under ISO8859-14 (executed, assertions on and off).
  6. A flag byte that the SET leaves unassigned (C3 in ISO8859-3 and -8, A1 in ISO8859-6 and -8) makes the reader throw UnmappableCharacterException while the line is read (:350), because the decoder replaces only malformed input (:910-912).

ISO8859-15 decodes C3, A1 and A2 exactly like ISO8859-1 and still merges: only the charset's identity picks the strategy. Under ISO8859-2 and the 10 other SETs that take SimpleFlagParsingStrategy, a merge needs two flags with the same lead byte; under ISO8859-14 it needs flags whose bytes its table remaps, whatever their lead bytes. The 18 values are a selection: hunspell(5) also lists ISO8859-10, which Lucene cannot load at all (sibling bug LFV-928), and ISCII-DEVANAGARI, which was not tested.

Exposure and likelihood224 words
  • Who is exposed. Any code that loads such a dictionary through the public Dictionary constructors: Hunspell spell checking, HunspellStemFilter, and HunspellStemFilterFactory, which builds the same Dictionary (by reading; not run). Within the module no setting is needed: the two directives alone trigger it.
  • What the damage looks like. Silent: affix classes merge, so spell() accepts forbidden forms and the stemmer returns extra stems (for example kote → kot), which then become index and query terms. For ISO8859-3, -6 and -8 (with these flags) the dictionary does not load at all, with UnmappableCharacterException: Input length = 1 and no file or line.
  • What it takes. Under ISO8859-2 and the 10 other SETs that read one flag per character: two flags with the same UTF-8 lead byte, which is common for non-ASCII flags (U+00C0-U+00FF share C3, U+0400-U+043F share D0). Under ISO8859-14: flags with bytes its decoder remaps, even with different lead bytes. Deterministic: no scale, randomness or concurrency; assertions on and off behave the same.
  • How likely. Rare. The finder found 0 of 191 public dictionaries with this combination (not re-checked); in a 99-file LibreOffice snapshot FLAG UTF-8 appears only with SET UTF-8 (24 files) or with no SET (pt_BR, the case LUCENE-9708 handled). Mixing an 8-bit encoding with UTF-8 flags is a real pattern, though: pt_BR does it with the default encoding.

Why it is a bug, not intended

#
  • hunspell(5) defines FLAG UTF-8 flags as UTF-8 characters with no SET condition, and C Hunspell decodes them from the raw bytes for every SET.
  • Lucene's LUCENE-9708 is titled "support FLAG UTF-8 in absence of SET UTF-8" but handled only ISO-8859-1.
  • ISO8859-15 decodes the same bytes exactly like ISO8859-1 yet merges; no doc or test excludes other SETs.
The full argument247 words
  • Contract. hunspell(5): SET is the encoding "of words and morphemes in affix and dictionary files"; FLAG UTF-8 "sets UTF-8 encoded Unicode character flags". C Hunspell's decode_flags and decode_flag (case FLAG_UNI) call u8_u16 on the flag bytes with no SET check; C Hunspell 1.3.2 and 1.7.2 give the expected verdicts for all 18 SET values on byte-identical files.
  • Lucene's own intent. LUCENE-9708 (7a7949aed2a, PR apache/lucene-solr#2270): title "Hunspell: support FLAG UTF-8 in absence of SET UTF-8", body "This is a valid situation to be supported". (Its first javadoc said "Used for FLAG UTF-8 on non-UTF-8 encoding", but that code was already ISO-8859-1-only and the wording was narrowed in review to match, so it is weak evidence.) The ISO-8859-1 limit follows from the re-encode trick (getBytes(ISO_8859_1) restores the bytes only for ISO-8859-1).
  • Javadoc. Hunspell "can be used in place of native Hunspell for many languages" and lists what is unsupported (Hungarian, non-BMP characters, PHONE); this combination is not listed. SimpleFlagParsingStrategy says it "Can be used with both the ASCII and UTF-8 flag types", true only for UTF-8 text. Lucene neither rejects nor warns.
  • Tests. TestDictionary.testUtf8Flag covers FLAG UTF-8 only with the default charset, testFlagWithCrazyWhitespace only with UTF-8; flagutf8.aff has no SET line. No test pins the merged behaviour.
  • Behaviour varies by accident. Correct for ISO8859-1, silently wrong for ISO8859-15, which decodes these bytes identically, and a load failure for ISO8859-3.
  • Precedent. LUCENE-5824 (#6886) fixed FLAG long flags collapsing, with the same overgeneration symptom, as a bug.
The devil's-advocate check193 words

The strongest "intended" case (the devil's-advocate verifier; the intended-lens review by another model family rated it moderate): LUCENE-9708 scoped UTF-8 flags to the default encoding on purpose (its private javadoc was narrowed in review to "even if the rest of the file is in the default (8-bit) encoding"), and SET can be read as the encoding of the whole file, flags included.

Why it fails: hunspell(5) restricts SET to words and morphemes and defines UTF-8 flags without a SET condition; C Hunspell decodes them from bytes for every SET; the same PR calls FLAG UTF-8 without SET UTF-8 "a valid situation to be supported"; the ISO-8859-1 limit is a property of the round-trip trick; no javadoc, test, CHANGES or MIGRATE entry excludes other SETs; and the outcome flips between ISO8859-1 and ISO8859-15 for identical bytes. Verdict: a defect (adjudication: confirmed, high). What the counter-case gets right: hunspell(5) and C Hunspell are strong compatibility evidence, not a Lucene API guarantee; the first-commit javadoc ("on non-UTF-8 encoding") sat on code that was already ISO-8859-1-only, so it says little; and no public dictionary is known to use the combination, so this is a low-priority correctness fix.

Suggested fix

#

Recommended Decode FLAG UTF-8 files through a byte table that keeps every byte

When FLAG UTF-8 meets a single-byte SET other than ISO-8859-1, read the files through a byte table built from the SET decoder (unassigned bytes become private-use characters) and turn flag characters back into bytes before decoding them as UTF-8. All 8 repro tests and the module's 1,917 tests pass.

} else if ("UTF-8".equals(flagType)) {
  if (decoder instanceof ByteTableDecoder byteTable) {
    return new EightBitAsUtf8FlagParsingStrategy(byteTable);
  }
  Charset charset = decoder.charset();
  if (DEFAULT_CHARSET.equals(charset) && !(decoder instanceof ISO8859_14Decoder)) {
    return new DefaultAsUtf8FlagParsingStrategy();
  }
  if (isSingleByte(charset)) {
    return new EightBitAsUtf8FlagParsingStrategy(new ByteTableDecoder(decoder));
  }
  return new SimpleFlagParsingStrategy();
}
All options and trade-offs3 options · 752 words

Option A (smaller) fixes the silent merge and the ISO8859-14 case but not the ISO8859-3/-6/-8 load failure; option B fixes all three in the probe and the tests. Both change the same method as open PR #16422 (coordinate with it), which rewrites getFlagParsingStrategy as a switch with the same ISO-8859-1-only test. Whichever is chosen, add the FLAG UTF-8 + 8-bit SET cases to the hunspell tests.

Decode FLAG UTF-8 files through a byte table that keeps every byte (validated by the checks) (recommended)

#

A new package-private ByteTableDecoder (70 lines) decodes each byte through a 256-entry table built once from the SET decoder (a byte the SET leaves unassigned becomes U+F700 + byte instead of an error) and maps decoded text back to its bytes. getFlagParsingStrategy uses it for FLAG UTF-8 with a single-byte SET other than plain ISO-8859-1 (ISO8859-14 included); readConfig then reads the .aff and .dic through it; the new EightBitAsUtf8FlagParsingStrategy decodes the recovered flag bytes as UTF-8. +107/-3 in two files.

} else if ("UTF-8".equals(flagType)) {
  if (decoder instanceof ByteTableDecoder byteTable) {
    return new EightBitAsUtf8FlagParsingStrategy(byteTable);
  }
  Charset charset = decoder.charset();
  if (DEFAULT_CHARSET.equals(charset) && !(decoder instanceof ISO8859_14Decoder)) {
    return new DefaultAsUtf8FlagParsingStrategy();
  }
  if (isSingleByte(charset)) {
    return new EightBitAsUtf8FlagParsingStrategy(new ByteTableDecoder(decoder));
  }
  return new SimpleFlagParsingStrategy();
}

Trade-offs

  • Only dictionaries with FLAG UTF-8 and a single-byte SET other than ISO-8859-1 take the new path; no SET, ISO-8859-1 and UTF-8 dictionaries are untouched. Multi-byte non-UTF-8 charsets (not Hunspell SET values) keep today's behaviour.
  • In that configuration the whole .aff and .dic, words included, are decoded through the new table (built once from the SET decoder) instead of that decoder, so it needs compatibility tests on real dictionaries beyond these synthetic flags and words. A word byte that the SET leaves unassigned now loads as a private-use character instead of failing the load (unassigned bytes inside words were not tested). The table would collide only if a SET charset mapped a byte into U+F700-U+F7FF; none of the 17 single-byte charsets checked in Python's codec tables does, and the 15 of them that the JDK provides were also checked in Java 25 (no byte in that range, no duplicate chars); other Java charsets that pass the single-byte gate were not checked.
  • One map lookup per flag character, at load time only. Larger than option A (a new class plus a decoder swap in readConfig).

Re-encode the flag text with the SET charset, then decode UTF-8 (the finder's sketch) (validated by the checks)

#

For FLAG UTF-8 with any non-UTF-8 SET, a new strategy rebuilds the bytes with rawFlags.getBytes(setCharset) (an inverse table ISO8859_14Decoder.encode for ISO8859-14) and decodes them as UTF-8; the decoder is unchanged. +55/-3 in two files.

if (DEFAULT_CHARSET.equals(charset) && !(decoder instanceof ISO8859_14Decoder)) {
  return new DefaultAsUtf8FlagParsingStrategy();
}
if (!StandardCharsets.UTF_8.equals(charset)) {
  return new EightBitAsUtf8FlagParsingStrategy(decoder); // getBytes(SET charset), then UTF-8
}

Trade-offs

Smaller and does not change how words are decoded. Leaves the ISO8859-3/-6/-8 load failure, because those lines fail to decode before flags are parsed. A one-method variant without the ISO8859_14Decoder change cut the independent reproducer's failures from 7 to 2 (ISO8859-14 and ISO8859-3 remained).

Reject the combination with a clear error

#

Throw a ParseException naming the FLAG and SET lines when FLAG UTF-8 meets a SET the code cannot handle. Not run.

Trade-offs

Turns the silent merge into a loud failure, but refuses files that C Hunspell reads correctly, and is no simpler than option A.

Downstream note

#

Products that load Hunspell dictionaries through HunspellStemFilterFactory or Dictionary inherit the merged classes for such files; the files are configuration that Lucene trusts as given, and query or document text cannot trigger the merge.

How it was found

#

A differential test loaded one FLAG UTF-8 dictionary under 18 SET values through the stock jar and compared spell verdicts with C Hunspell 1.3.2 and 1.7.2 on byte-identical files: 12 values merged the flags and 3 failed to load, while C Hunspell was right for all 18. Code reading then found the ISO-8859-1-only branch.

The method in full127 words

Method: differential testing against a reference implementation (the study's "semi-formal" tier), a side leg of a hunt unit that compared Lucene's handling of Hunspell SET encodings with C Hunspell, 2026-10-28.

  • A probe built one .aff/.dic pair (FLAG UTF-8, classes U+00E1 and U+00E2) and varied only the SET line over 18 values: none, ISO8859-1 to -9, -13, -14, -15, KOI8-R, KOI8-U, microsoft-cp1251, TIS620-2533 and UTF-8. Lucene was right for 3, merged 12 and failed to load 3; C Hunspell 1.3.2 (the command-line tool) and 1.7.2 (the library, raw-byte driver) were right for all 18.
  • Code reading of getFlagParsingStrategy explained the split; an AI finder then wrote a 5-test JUnit (public API plus the package-private Stemmer), and independent AI tools reproduced, reviewed and judged it (see the checks).

The root cause dates from LUCENE-3414 (2011, first released in 3.5.0). LUCENE-5517 (4.8.0) turned it into a load error; LUCENE-9708 fixed only ISO-8859-1 and LUCENE-9724 made it silent again (both 2021, in 8.9.0 and 9.0.0). Bug record

LFV-932, snapshot of 2026-10-29

Registry title
Hunspell Dictionary with FLAG UTF-8 and an 8-bit SET other than ISO8859-1 silently merges UTF-8 flags that share a lead byte, so spell() and the stemmer accept forms the dictionary forbids (some SET values fail to load instead)
Area
analysis / hunspell (Dictionary FLAG UTF-8 parsing under the SET encoding)
Priority
Low, rank 380: The opt-in Hunspell module silently merges UTF-8 flag classes so spell and stem accept forbidden forms, but only for FLAG UTF-8 with an 8-bit SET other than ISO8859-1, which no surveyed public dictionary uses.
Impact class
silent wrong results
Impact note
Only applications that use the opt-in Hunspell module (a Dictionary built directly, through HunspellStemFilterFactory, or for the Hunspell spell-checker) with an affix file that pairs FLAG UTF-8 with an 8-bit SET other than ISO8859-1 are hit: the dictionary loads with no error, but UTF-8 flags that share their first byte (all of U+00C0-U+00FF share 0xC3, all of U+0400-U+043F share 0xD0) become one affix class, so spell() accepts and the stemmer stems word forms the dictionary forbids, deterministically and with no scale needed; for some SET/flag pairs (ISO8859-3, -6, -8 with Latin-1 flags) the dictionary fails to load instead; no public dictionary with this combination is known, and the silent form is in 3.5.0-4.7.2 and 8.9.0-10.5.2.
Summary
You load a Hunspell dictionary whose affix file says FLAG UTF-8 (flags are UTF-8 characters) and SET ISO8859-2, KOI8-R, microsoft-cp1251 or another 8-bit encoding except ISO8859-1, with two suffix classes whose flags are, say, U+00E1 and U+00E2, and expect what C Hunspell 1.3.2 and 1.7.2 do on the same bytes: a word that carries only the first flag takes only the first suffix. Instead Lucene reads the flags from text already decoded with the SET charset, so each 2-byte flag becomes two characters and an affix rule keeps only the first one, the shared lead byte: both classes merge, spell() accepts the forbidden forms (kote, lasa in the repro) and the stemmer returns kot for kote, with no error. Only no SET, SET ISO8859-1 and SET UTF-8 work; ISO8859-14 merges too (its decoder reports ISO-8859-1 as its charset, and the re-encode turns remapped flag bytes into '?'), and with ISO8859-3, -6 or -8 the load throws UnmappableCharacterException because a flag byte is unassigned in that charset.
Introduced
e3172b9239c (trunk) / 1e084f1d08e (branch_3x), LUCENE-3414 'Added Hunspell for Lucene' (apache/lucene#4487, no PR, SVN era), first released in 3.5.0: FLAG UTF-8 mapped to SimpleFlagParsingStrategy (one flag per char of the line already decoded with the SET charset). The symptom then changed twice: a4b6ef84dd0 (branch_4x) / 2c98dd5b320 (trunk), LUCENE-5517 (#6580, 4.8.0) made parseFlag throw 'expected only one flag', so the same dictionaries were rejected at load; then 7a7949aed2a, LUCENE-9708 (#10747, PR apache/lucene-solr#2270) added DefaultAsUtf8FlagParsingStrategy only for the ISO-8859-1 charset, and 1cc26b6bb44, LUCENE-9724 (#10763, PR apache/lucene-solr#2307) set checkFlags = false, which turned the load error back into the silent merge for every other 8-bit SET. Both 2021 commits first shipped in 9.0.0 and, through the LUCENE-9687 bulk backport c6b964a1157 (PR apache/lucene-solr#2499), in 8.9.0. The fix site (getFlagParsingStrategy / the flag strategies) is LUCENE-3414 code patched for ISO-8859-1 only by LUCENE-9708; LUCENE-9724 only changed the symptom.
