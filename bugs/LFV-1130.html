LatLonShapeDocValues / XYShapeDocValues bounding-box getters return a tree node's box after relate()

After relate() walks into a shape's tree, the getters getEncodedMinX/MinY/MaxX/MaxY of the same LatLonShapeDocValues (or XYShapeDocValues) return the box of the last tree node it did not skip: for the line (0,0) -> (10,10) -> (20,20), getEncodedMinX() goes from 0 to 119304647 (longitude 10). Lucene's queries and getBoundingBox() stay correct.

The finding in 30 seconds

#

Code that relates a shape doc value to a query box and then asks it for its bounding box gets the box of a piece of the shape instead.

  1. Build a LatLonShapeDocValues for the line (lat, lon) (0,0) -> (10,10) -> (20,20) with LatLonShape.createLatLonShapeDocValues(...). Its getters give the shape's box, lat 0..20 and lon 0..20: getEncodedMinX() = 0, getEncodedMinY() = 0.
  2. Call relate() with the small box lat [19, 21], lon [19, 21] at the line's far end. It answers CELL_CROSSES_QUERY, which is correct. You expect the four getters, documented as "the shape's bounding box", to be unchanged.
  3. Instead getEncodedMinX() is 119304647 (longitude 10) and getEncodedMinY() is 238609294 (latitude 10): the box of the segment (10,10) -> (20,20), the child node relate() walked into. No error, assertions on or off. getBoundingBox() on the same object still reports lat 0..20, lon 0..20.
  4. Why: the object keeps no copy of its box. The getters read the reader's one reusable scratch box, and relate() overwrites that box at each child node it walks into (a child skipped as disjoint leaves it alone). A later relate() answered at the root (say a far-away box) puts the right values back, so the answer depends on call history.

Who is affected

#

Only code that uses the experimental LatLonShapeDocValues / XYShapeDocValues object directly, calls relate() with a query that crosses the shape's box, and then reads getEncodedMinX/MinY/MaxX/MaxY on the same object. Lucene's own queries, relate() answers and getBoundingBox() are unaffected; no setting or scale is involved. Rare.

Mechanism, terms and numbers493 words

LatLonShapeDocValues and XYShapeDocValues (@lucene.experimental) wrap one shape's doc-value bytes; client code gets one from the public factories LatLonShape.createLatLonShapeDocValues(BytesRef) / XYShape.createXYShapeDocValues(BytesRef) (since 9.5.0) and can call the public relate(Component2D) and the four public getters getEncodedMinX/MinY/MaxX/MaxY, documented as the shape's bounding box. The getters do not keep their own copy: they read the reader's single reusable scratch box, which relate() also uses as working space while it walks down the shape's tree. So after a relate() that walks into child nodes, the getters return the box of the last one it did not skip as disjoint. getBoundingBox(), computed once in the constructor, stays right, so one object reports two different boxes. Lucene's own queries are unaffected (they build a fresh object per document and never read the getters). Present since the feature was added (d7fd48c9502, 2022); the fix is to copy four ints at construction, like the centroid.

The mechanism (main 5adff78bb168, lucene/core/src/java/org/apache/lucene/document/)

#
  1. One scratch box. ShapeDocValues.java:578: the Reader keeps private final BBox bbox; // scratch bbox instance. readBBox() (:599-606) and resetBBox(..) (:609-612) both return bbox.reset(..), which overwrites the four fields and returns this (:663-670).
  2. Kept by reference. The ShapeComparator constructor stores this.boundingBox = dvReader.readBBox(); (:691) in a private final SpatialQuery.EncodedRectangle field (:680): the scratch object itself, not a copy. The public getters (:105-123) read it through getMinX..getMaxY (:702-716).
  3. Overwritten by the walk. relate(Component2D) (:743-802) re-reads the header box into the scratch box (:750). When the shape's box crosses the query and the root component does not decide it, it recurses, and every visited child that is not skipped as disjoint (:826-831) calls dvReader.resetBBox(tMinX, tMaxX, tMinY, tMaxY) (:836). Nothing restores the header box.
  4. The rest is copied. version, numberOfTerms, centroidX/Y and highestDimension are copied into final fields (fields :678-683, assigned at :688-694); only the box (:680, :691) is held by reference.
  5. The other box stays right. getBoundingBox() is computeBoundingBox(), run once in the constructor (:80, :92) from the four getters (LatLonShapeDocValues.java:66-71, XYShapeDocValues.java:67-72), before any relate().

Exposure and likelihood172 words
  • Who is exposed. Client code that gets the object from LatLonShape.createLatLonShapeDocValues(BytesRef) or XYShape.createXYShapeDocValues(BytesRef) (LatLonShape.java:350-352, XYShape.java:280-282, public since 9.5.0), calls the public relate() (ShapeDocValues.java:163-165) and afterwards reads the encoded getters, for example a custom collector that relates per-document shapes and then reports their bounds.
  • Trigger. The query must cross the shape's box, the root component must not decide it, and some child node must be visited (a shape with two or more tessellation components). A relate() answered at the root or by the root component leaves the getters right (executed).
  • Not exposed. Lucene's shape doc-values queries build a fresh object per document (BaseShapeDocValuesQuery.java:78, LatLonShapeDocValuesQuery.java:42-43) and never read the getters; the only in-tree callers of the getters are the two computeBoundingBox() methods, which run before any relate().
  • Silent. No exception and no assertion, with -ea and -da; the value is plausible (a real box inside the shape's box).
  • How likely. Rare: no public report was found since the factories became public in 9.5.0 (2023).

Why it looks unintended

#
  • Each getter's javadoc says it returns a value "for the shape's bounding box"; nothing says relate() changes it.
  • The same object's getBoundingBox() is built from these getters at construction and stays right: one object, two boxes.
  • Every other header value (version, term count, centroid, dimension) is copied into a final field; only the box references the scratch object.
The full argument116 words
  • Contract. ShapeDocValues.java:105, :110, :115, :120: "returns the min x [min y / max x / max y] value for the shape's bounding box". relate() has no javadoc; nothing documents it as changing the getters.
  • Tests. No test in the repository reads the four getters; TestShapeDocValues checks getBoundingBox() only (grep of lucene/ at 5adff78bb168).
  • History. The alias came with the feature (d7fd48c9502, LUCENE-10654, #1017). Issue #11752, "Enable Relate Interface of Shape Doc Values to be used by clients of Lucene", and its PR #11753 added the public factories so that client code can call relate(). None of #1017, #11690, #11752 or #11753 discusses the getters or the scratch box.
The devil's-advocate check131 words

The strongest "intended" case (rated moderate by the cross-model reviews and the devil's-advocate verifier): the scratch reuse is deliberate, so the traversal allocates nothing per visited node; the object is a per-document, query-time view; the classes are @lucene.experimental, the superclass is package-private and Component2D is @lucene.internal; and getBoundingBox() already gives a stable box.

Why it fails: the fix keeps the scratch reuse in the traversal and copies four ints once per object; @lucene.experimental allows API changes, not a getter that contradicts its own javadoc depending on an earlier call; and #11752 / #11753 made relate() reachable from client code by adding the factories (the public LatLonGeometry.create / XYGeometry.create supply the Component2D). A maintainer may still prefer to document or narrow the getters; the fix section lists that option.

Suggested fix

#

Recommended Keep the header box as four final ints (fix A)

Copy the header box into four final int fields in the ShapeComparator constructor, like centroidX/Y, and let the getters read them; the traversal keeps its scratch box. Validated with gradle on 5adff78bb168: the repro fails on stock and passes with the fix; 10 shape suites (68 tests) and :lucene:core:check -x test pass.

Downstream note

#

The one downstream wrapper the search found, OpenSearch's GeoShapeDocValue, calls relate() and getBoundingBox() but not the encoded getters, so it does not see the wrong values (by reading its source).

How it was found

#

A proof-obligation audit of ShapeDocValues' contract checked the getters' promise, "the shape's bounding box", against every state relate() can leave the object in, and found the shared scratch box; a one-test public-API repro witnessed it. An independent reproducer, cross-model reviews, a devil's-advocate verifier and an adjudication confirmed it.

The method in full165 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The obligation: after any sequence of public calls, getEncodedMinX/MinY/MaxX/MaxY equal the box encoded in the doc value's header. The proof step "the comparator's box is never written after construction" fails, because the field aliases the reader's scratch box and relate() writes it per visited node; a public-API JUnit witnessed it on main, 10.6.0 and 9.5.0, and copying the header box at construction made it pass.
  • Then an independent reproducer wrote its own client-package tests (LatLon and XY), cross-model reviews (OpenAI GPT-5.6, refute and intended lenses, executed) wrote and ran their own tests, a devil's-advocate verifier argued the intended-behaviour case with its own XY polygon test, and an adjudication re-ran the tests. An audit and a final repro check followed and reduced the repro to the single test shown here.
  • An earlier hunt pass over the shape doc-values tree had checked the getters only on fresh objects and did not see it.

Registry title
LatLonShapeDocValues and XYShapeDocValues getEncodedMinX/MinY/MaxX/MaxY return a tree node's box instead of the shape's bounding box after a relate() call that descends the shape's tree, because the getters read the reader's reusable scratch box
Area
core / document: shape doc values (ShapeDocValues.ShapeComparator bounding box behind LatLonShapeDocValues / XYShapeDocValues getEncodedMinX, getEncodedMinY, getEncodedMaxX, getEncodedMaxY)
Priority
Low, rank 441: After a relate() call that descends the shape's tree, the experimental shape doc-values bounding-box getters silently return a tree node's box, in every release since 9.5.0. Query results and getBoundingBox() are unaffected and only client code that reads these getters after relate() on the same instance is hit, so it is rare.
Impact class
minor
Impact note
Minor: the wrong values reach only client code reading the experimental getters after relate(). It hits only client code that builds a LatLonShapeDocValues or XYShapeDocValues through the public factories createLatLonShapeDocValues / createXYShapeDocValues(BytesRef) (released since 9.5.0, @lucene.experimental), calls relate(Component2D) with a query that crosses the shape's bounding box and reaches a non-root tree node (any shape with two or more tessellation components), and then reads getEncodedMinX/MinY/MaxX/MaxY on the same instance: the getters then silently return the last visited node's box, identically with -ea and -da [exec], until a later relate() decided at the root puts the header box back; relate() results, getBoundingBox() and every Lucene query are unaffected (BaseShapeDocValuesQuery builds a fresh instance per document and no Lucene code reads the getters after relate()), no setting and no scale are needed, and the one known downstream client (OpenSearch's GeoShapeDocValue) uses getBoundingBox() instead.
Summary
You build a LatLonShapeDocValues (or XYShapeDocValues) from a shape's doc-value bytes, call relate() with a query box, and then read getEncodedMinX/MinY/MaxX/MaxY, which are documented as 'the shape's bounding box'; you expect the same four values as before the relate() call. Instead, when the query box crosses the shape's box so that relate() walks down the shape's tree, the getters afterwards return the box of the last tree node visited: for the points (0,0), (10,10), (20,20) and a small box around (0,0), relate() correctly answers CELL_CROSSES_QUERY but getEncodedMaxX() then returns 0 instead of encodeLongitude(20) = 238609294, with no error.
