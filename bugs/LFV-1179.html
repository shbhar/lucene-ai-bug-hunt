PagedBytesDataInput: clone() and setPosition(getPosition()) at the end of a full last block throw ArrayIndexOutOfBoundsException

A PagedBytes DataInput that has read to the end of data filling its last block cannot be cloned, re-seeked to its own position or skipped onto the end: with 16 full blocks it throws ArrayIndexOutOfBoundsException. Every release since 3.5.0; Lucene's own code never makes these calls.

The finding in 30 seconds

#

Reads and seeks disagree about where the end of a full block is: a read stays on the finished block, a seek jumps to the next one. At the very end of the data, that next block does not exist.

Background in two steps

#
  1. PagedBytes is an internal Lucene buffer that stores bytes in fixed-size blocks (16 bytes for new PagedBytes(4)). After freeze(), getDataInput() returns a PagedBytesDataInput that reads the blocks in order; like other DataInputs it can report its position, seek with setPosition, skip bytes and be cloned.
  2. The input remembers (block, offset). A read moves to the next block only when it needs another byte, so after the last byte of block 15 it sits at (15, 16): position 15 × 16 + 16 = 256. setPosition(256) instead computes (16, 0) and fetches block 16 at once; clone() and skipBytes go through setPosition.

The finding, step by step

#
  1. new PagedBytes(4) stores bytes in blocks of 16. Write 256 bytes (exactly 16 full blocks), freeze(false), and read all 256 from getDataInput(): getPosition() returns 256.
  2. Call clone(), setPosition(256) or skipBytes(0). You expect an input at position 256: setPosition takes "a position previously obtained from getPosition", and a clone is "positioned at the same point".
  3. Instead each throws ArrayIndexOutOfBoundsException: Index 16 out of bounds for length 16, with assertions on and off. The reads stopped at the end of block 15, but setPosition looks up block 256 / 16 = 16, which does not exist.
  4. With 255 bytes, or no data, the same calls work. With 1 or 17 full blocks they return but leave the input with no current block, so a following zero-length read throws NullPointerException.

Who is affected

#

Only code that uses the @lucene.internal PagedBytes.getDataInput() directly and clones, re-seeks or skips it exactly at the end of data whose length is a multiple of the block size. Lucene's one production user, BinaryDocValuesWriter, only reads forward, so no Lucene code path is hit. No wrong data, no index involved; every release since 3.5.0.

Mechanism, terms and numbers502 words

PagedBytes keeps bytes in fixed-size blocks, and PagedBytes.getDataInput() returns a PagedBytesDataInput that reads them in order. The reads move to the next block lazily: after the last byte of a block they stay on it at offset blockSize. setPosition instead looks up the block for the new position straight away.

When the data ends exactly on a block border, the end position is the start of a block that does not exist. So after reading to the end, clone(), setPosition(getPosition()) and a skipBytes that lands exactly on the end look up the block after the last one. With 16 full blocks (256 bytes at blockBits 4, 64 KiB at blockBits 12) that throws ArrayIndexOutOfBoundsException, with and without assertions, and so does any block count that fills the grown block array (20, 24, 28, 32, ... full blocks); when the array has a spare slot (for example 1 or 17 full blocks) it leaves a null current block instead. The same calls work when the data ends inside a block or is empty.

Both classes are public but @lucene.internal, and Lucene's only production user, BinaryDocValuesWriter, only reads forward, so no Lucene code path is hit: the bug is latent, Low priority. It has been there since the class was added (LUCENE-2205, 3.5.0). The fix is a few lines in setPosition.

The mechanism

#
  1. The input keeps (currentBlockIndex, currentBlockUpto, currentBlock) (PagedBytes.java:300-302); getPosition() is currentBlockIndex * blockSize + currentBlockUpto (:316-318).
  2. readByte moves to the next block only when currentBlockUpto == blockSize and another byte is needed (:329-331); readBytes calls nextBlock() only while more bytes are left than the current block holds (:340-351). After the last byte of a full last block the state is (numBlocks - 1, blockSize), (15, 16) in the repro, and getPosition() is numBlocks * blockSize = 256, the data length.
  3. setPosition(pos) sets currentBlockIndex = pos >> blockBits and at once currentBlock = blocks[currentBlockIndex] (:321-325, lookup at :323). For 256 that is blocks[16], one slot past the last block: the fix site.
  4. clone() is getDataInput() then clone.setPosition(getPosition()) (:309-313); skipBytes(n) is setPosition(getPosition() + n) (:356-362).
  5. The block array starts with 16 slots (:35) and grows with ArrayUtil.grow (:165-168). When the block count equals the array length (16 here) blocks[numBlocks] is past the array and throws. Otherwise the slot is null: the call returns with a null currentBlock, and only a following zero-length read throws NullPointerException (executed with 1 and 17 full blocks). That variant is secondary, because at such a block-aligned end a read of one or more bytes past the end fails on the original input too (readByte() throws NullPointerException).

The original input in the failing state still works (a zero-length read on it succeeds), and the same calls work at the end of data that ends inside a block (255 bytes; 4095 and 65535 bytes at blockBits 12) and on empty data.

Exposure and likelihood164 words
  • Who: code that uses the public but @lucene.internal PagedBytes.getDataInput() directly, reads to the end of data whose length is an exact multiple of the block size, and then clones the input, seeks back to the position it reported, or skips exactly onto the end (for example skipping the last record).
  • Not hit: Lucene itself. The only production (non-test) getDataInput() caller is BinaryDocValuesWriter (:124, :141, :155), whose iterator only calls readBytes (:193), and that works at the end; outside PagedBytes itself the only other caller is TestPagedBytes (:139, :165). The one downstream use found, Elasticsearch's legacy-index Lucene54DocValuesConsumer, also only reads forward.
  • Effect: a loud exception from that one call; no wrong data, no index involved, nothing read or written out of range. The sizes are ordinary: 64 KiB at blockBits 12, the block size BinaryDocValuesWriter uses.
  • Likelihood: rare; a search on 2026-11-03 found no public report, although the code has been there since 3.5.0 (2011).

Why it looks unintended

#
  • setPosition's javadoc accepts "a position previously obtained from getPosition", and 256 is what getPosition() returned.
  • The same calls work when the data ends inside a block or is empty; ByteBuffersDataInput.seek accepts the end position.
  • The same boundary in the sibling PagedBytes.Reader.fillSlice was fixed as a bug (LUCENE-5218, #6282).
The full argument248 words
  • Its own contract names the argument. setPosition: "Seek to a position previously obtained from {@link #getPosition}" (PagedBytes.java:320); 256 is what getPosition() returned one call earlier. DataInput.clone: "Clones of a stream access the same data, and are positioned at the same point as the stream they were cloned from" (DataInput.java:236-237). As support only: skipBytes "may skip bytes in whatever way is most optimal, and may not have the same behavior as reading the skipped bytes" (DataInput.java:295-296); that allows skipping without reading but does not say whether a skip onto the end is legal, so the case rests on setPosition and clone.
  • The same calls work everywhere else: at the end of data that ends inside a block and on empty data, and the original input in the failing state still serves a zero-length read; only the calls that go through setPosition fail. Lucene's other paged in-memory input, ByteBuffersDataInput.seek, throws only when the position is beyond length() (ByteBuffersDataInput.java:389-395); IndexInput.seek fails only "beyond the end of the file" (IndexInput.java:69-71).
  • The project fixed this boundary as a bug before. LUCENE-5218 (#6282, d98e92a87cc, 2013): an ArrayIndexOutOfBoundsException in PagedBytes.Reader.fillSlice for a zero-length value whose start sat on the block-aligned end; the fix returns early in fillSlice only, and PagedBytesDataInput was not touched.
  • Untested, not excluded: TestPagedBytes skips only up to numBytes - 1 (TestPagedBytes.java:166); no javadoc, test, CHANGES or MIGRATE entry says the end position is unsupported.
The devil's-advocate check119 words

Both classes are @lucene.internal (PagedBytes.java:28, :297) and no Lucene code path makes these calls. An independent reviewer from another model family (OpenAI GPT-5.6) ruled it "not real" on that ground alone, while reproducing it, agreeing with the root cause and the fix, and calling it "internal hardening" a maintainer could still accept.

Why it fails: the tag means "This API is for internal purposes only and might change in incompatible ways in the next release" (RenderJavadocPlugin.java:506), a stability warning, not a usage precondition. The class and methods are public, the input is ordinary, no assertion is involved, and the class breaks its own javadoc. What remains is reach, which is why this is Low.

Suggested fix

#

Recommended A. Keep the reads' end state at numBlocks << blockBits, the end of a full last block (validated)

In setPosition, when the position is the end of a full last block, keep the state the reads leave there, (numBlocks - 1, blockSize), instead of looking up blocks[numBlocks] (+6/-1, net +5 lines, in PagedBytes.java). The repro passes with assertions on and off; TestPagedBytes, TestBinaryDocValuesUpdates and the core format, lint and forbidden-API checks pass.

public void setPosition(long pos) {
  currentBlockIndex = (int) (pos >> blockBits);
  currentBlockUpto = (int) (pos & blockMask);
  if (currentBlockUpto == 0 && currentBlockIndex > 0 && currentBlockIndex == numBlocks) {
    // end of a full last block: same state as after reading its last byte
    currentBlockIndex--;
    currentBlockUpto = blockSize;
  }
  currentBlock = blocks[currentBlockIndex];
}
All options and trade-offs4 options · 534 words

Four options. A and B were validated with gradle in a scratch worktree of 5adff78bb168; C and D are by reading.

A. Keep the reads' end state at numBlocks << blockBits, the end of a full last block (validated) (recommended)

#

In PagedBytesDataInput.setPosition (PagedBytes.java:321-325):

public void setPosition(long pos) {
  currentBlockIndex = (int) (pos >> blockBits);
  currentBlockUpto = (int) (pos & blockMask);
  if (currentBlockUpto == 0 && currentBlockIndex > 0 && currentBlockIndex == numBlocks) {
    // end of a full last block: same state as after reading its last byte
    currentBlockIndex--;
    currentBlockUpto = blockSize;
  }
  currentBlock = blocks[currentBlockIndex];
}

Trade-offs

  • Changes behaviour only for that one position; every other seek resolves exactly as before.
  • Also fixes the null-block variant, because the lookup becomes blocks[numBlocks - 1].
  • The input keeps no logical length, so when the last block is partial the same position lies past the logical end (no getPosition() returns it): stock throws at the seek, fix A defers the failure to the next read, as stock already does for other past-the-end positions inside the last block. Probe, 255 bytes at blockBits 4, setPosition(256): with fix A a following zero-length read succeeds after freeze(false) and throws ArrayIndexOutOfBoundsException after freeze(true).
  • Cost: one comparison per seek, up to three on block-aligned positions.

What the checks validated

  • Gradle in a scratch worktree of 5adff78bb168, OpenJDK 25.0.3, seed DEADBEEF: stock, the repro fails with assertions on and off; with fix A it passes, on and off.
  • With fix A and the repro: TestPagedBytes (4 tests, 1 skipped by @Ignore, 0 failures), the repro (1 test, 0 failures) and TestBinaryDocValuesUpdates, which drives the one production user (29 tests, 1 nightly-only test skipped, 0 failures).
  • checkGoogleJavaFormat, ecjLint, forbiddenApisMain and forbiddenApisTest of lucene/core: pass with fix A and the test. A first run flagged only the test's longer comment line (google-java-format), which was then shortened; no change to the fix. ecjLintMain ran and passed in that first run and was up to date in the second (the main sources had not changed); a separate re-run ran all four checks fresh with fix A and the test, and they passed.
  • The full lucene/core suite was not run.

B. Treat every block-aligned position the way the reads do (validated)

#

The same change without currentBlockIndex == numBlocks in the condition: any position on a block border is stored as the end of the previous block, and the next read moves on.

Trade-offs

One uniform rule with no numBlocks check, but it changes the stored state of every block-aligned seek (the next read calls nextBlock() first); the reads already handle that state.

What the checks validated

The repro passes with assertions on and off; TestPagedBytes passes (4 tests, 1 skipped, 0 failures, assertions off).

C. Make clone() copy the three fields

#

Copy currentBlockIndex, currentBlockUpto and currentBlock into the clone instead of calling setPosition.

Trade-offs

Fixes clone() only; setPosition(getPosition()) and skipBytes onto the end still fail. By reading, not run.

D. Document the end position as unsupported

#

Say in the javadoc that setPosition must not be given the end of block-aligned data.

Trade-offs

Contradicts setPosition's own javadoc and DataInput.clone. Not recommended.

Downstream note

#

Downstream, only products whose own code clones, re-seeks or skips a PagedBytes DataInput at a block-aligned end see it, as an exception from that call; no document, query or index file reaches it.

How it was found

#

Semi-formal: a proof-obligation audit of PagedBytesDataInput against its javadoc, that setPosition accepts every position getPosition() returns and that a clone starts where the original is. The eager block lookup cannot meet that at a block-aligned end, and a JUnit test on stock main witnessed the failure.

The method in full81 words
  • Obligation: for every state the reads can reach, setPosition(getPosition()) succeeds and leaves the same position (PagedBytes.java:320), and clone() is positioned at the same point (DataInput.java:236-237).
  • Finding: the reads leave (numBlocks - 1, blockSize) at the end of a full last block, and setPosition maps that position to blocks[numBlocks]; clone() and skipBytes inherit it.
  • Witness: a JUnit test on stock main, then an independent reproduction, a cross-model review, an intended-behaviour review and an adjudication (see Independent checks).

Summary
You write data into a PagedBytes whose length is an exact multiple of its block size (here 16 blocks of 4 KiB), freeze it, read a PagedBytesDataInput from getDataInput() to the end, and then clone it, call setPosition(getPosition()), or skip the last bytes so that the position lands exactly on the end. You expect an input positioned at the end, as setPosition's javadoc ('Seek to a position previously obtained from getPosition') and DataInput.clone's ('positioned at the same point as the stream they were cloned from') promise, and as happens when the data ends inside a block or is empty. Instead setPosition looks up the block after the last one, because it resolves the block eagerly while the reads move to the next block only when they need more bytes, and throws ArrayIndexOutOfBoundsException 'Index 16 out of bounds for length 16' (or, for other block counts, leaves a null block that the next zero-length read trips over); no Lucene code makes these calls, so only code that uses the internal class directly is affected.
