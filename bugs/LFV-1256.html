A Tessellator.Monitor on an XYPolygon throws "invalid longitude" for x beyond ±180 ("invalid latitude" for y beyond ±90)

Attaching a debugging Tessellator.Monitor to an XYPolygon with a vertex at x = 500 throws "invalid longitude 500.0" instead of returning its 1 triangle. The callbacks get each Cartesian vertex as a geographic Point(lat = y, lon = x), which rejects values beyond ±90 / ±180.

The finding in 30 seconds

#

The XY overload hands its monitor the same kind of point list as the geographic one: getPoints builds new Point(node.getY(), node.getX()) for every vertex, and Point's constructor rejects a latitude beyond ±90 or a longitude beyond ±180. Cartesian values outside that box throw while the first callback's points are built.

Background: the Tessellator and its Monitor

#
  1. Tessellator cuts a polygon into triangles; LatLonShape (degrees) and XYShape (Cartesian floats) use it to index shapes. The class is marked @lucene.internal.
  2. Since 9.3.0 each tessellate overload has a variant that takes a Monitor: a debugging hook that is told, at each step, the status, the remaining ring as a list of points and the triangles so far.
  3. Those point lists are typed List<Point>, Lucene's latitude/longitude point, which checks its ranges when it is constructed.

The finding, step by step

#
  1. Build the Cartesian triangle (0,0) (500,0) (0,50) as an XYPolygon. Tessellator.tessellate(triangle, false) returns 1 triangle.
  2. Call Tessellator.tessellate(triangle, false, monitor) with a Monitor that does nothing. The Monitor is a debugging observer that "will receive calls with internal data at each step", so you expect the same 1 triangle.
  3. Instead the call throws IllegalArgumentException: invalid longitude 500.0; must be between -180.0 and 180.0 while the first callback's point list is built (the monitor is never called), with assertions on and off.
  4. Why: the two point callbacks take List<Point>, and getPoints wraps each vertex as new Point(y, x), which range-checks latitude (±90) and longitude (±180). So x = 200 alone or y = 100 alone fails too, while a square inside that box works.
  5. Only the debugging path breaks: XYShape and LatLonShape never pass a monitor, so indexing and queries are unaffected. Every release from 9.3.0 to 10.6.0, and main.

Who is affected

#

Developers who attach a Monitor to an XY tessellation, typically to debug a polygon, with a Cartesian value beyond ±180 / ±90: they cannot watch it at all. It is an opt-in debugging overload; indexing and queries never pass a monitor, so no index or query result changes; only the monitored call fails. Priority Low.

Mechanism, terms and numbers415 words

Tessellator.tessellate(XYPolygon, boolean, Monitor) lets a debugging Monitor watch the triangulation of a Cartesian polygon. The Monitor's two point callbacks take List<Point>, and getPoints builds those lists as new Point(node.getY(), node.getX()) for every vertex, XY input included (Tessellator.java:1555-1563). Point(lat, lon) range-checks both values (Point.java:41-43), so an XY vertex with |x| > 180 or |y| > 90 that is still in the ring at the first notification makes the call throw IllegalArgumentException: invalid longitude (or invalid latitude) while the first callback's point list is built, although the same polygon tessellates without a monitor. No indexing or query path attaches a monitor, so no index or query result changes, and the tessellation without a monitor is unchanged: only a developer debugging an XY tessellation is hit. It came with the Monitor (#946, LUCENE-10604) and is in every release from 9.3.0 to 10.6.0 and on main; giving XY input its own callbacks that carry XYPoint fixes it.

The bug

#
  1. The XY overload passes the monitor to earcutLinkedList, which calls notifyMonitor at each step of the ear-cutting loop; splitEarcut calls notifyMonitorSplit (Tessellator.java:1565-1572, :1580-1597).
  2. Both build their point lists with getPoints, which knows nothing of the input type: it labels y as latitude and x as longitude.
  3. Inside the box the values pass through unchanged (still Cartesian, labelled as degrees). Outside it, Point's constructor throws, so the call fails before the first triangle is cut.

Executed on main without assertions: x 0..200, y 0..50 gives "invalid longitude 200.0"; x 0..50, y 0..100 gives "invalid latitude 100.0"; x 0..100, y 0..50 tessellates with and without the monitor (2 triangles).

Exposure and likelihood148 words
  • Who is hit. Developers who call Tessellator.tessellate(XYPolygon, boolean, Monitor), for example to see why a polygon fails to tessellate, on ordinary projected or other Cartesian data with a value beyond ±180 (x) or ±90 (y).
  • Default vs opt-in. Opt-in debugging overload of an @lucene.internal class. XYShape and LatLonShape call the two-argument tessellate, which passes no monitor (XYShape.java:100,112, LatLonShape.java:102,114).
  • Effect. A loud IllegalArgumentException from the observer instead of the triangles. Nothing is corrupted, and the same call without a monitor works.
  • Scale. None needed: one triangle. Deterministic, with assertions on and off.
  • Population. Tiny: the only known Monitor implementations are Lucene's own TestTessellator (a geographic polygon, TestTessellator.java:811-821), copies of it vendored into other repositories (a GitHub code search found 13 implements Tessellator.Monitor files, all this test or copies of it), and the external debugging tool the Monitor was made for (geographic input only).

Why it looks unintended

#
  • The commit that added the Monitor also added the public XY overload taking one; nothing limits it to geographic input.
  • The Monitor javadoc describes a debugging hook receiving "internal data at each step"; it says nothing about making the call fail.
  • XYPolygon puts no range on its coordinates, but the XY monitor path works only inside the latitude/longitude box.
The full argument179 words
  • The overload exists on purpose. 66b65b79e8b (#946, LUCENE-10604) added tessellate(XYPolygon, boolean, Monitor) next to the geographic overload. No javadoc, CHANGES entry, test or review comment limits it to geographic input or a coordinate range (#946's description and all 16 review comments, and both review summaries, read).
  • The contract. Tessellator.java:1534-1540: an implementation "will receive calls with internal data at each step of the triangulation algorithm. This is of use for debugging complex cases". It does not expressly promise that attaching a monitor leaves the result unchanged, but nothing says it may make the call fail.
  • The input. XYPolygon "Represents a polygon in cartesian space" (XYPolygon.java:24) and puts no range on its coordinates: it checks only that each is finite (XYEncodingUtils.java:35-41), besides structural rules such as a closed ring of at least 4 points (XYPolygon.java:48-87). Working only when Cartesian values happen to fit the latitude/longitude box reads as an oversight, not a design.
  • Tests. The only Monitor test, testComplexPolygon50_WithMonitor, uses a geographic GeoJSON polygon; no test covers the XY overload with a monitor.
The devil's-advocate check147 words

The strongest case: Tessellator is @lucene.internal, the Monitor is a debugging aid with no production caller, and its point callbacks are typed List<Point>, which "Represents a point on the earth's surface" with "latitude/longitude values ... in decimal degrees" (Point.java:21,27). So the type itself says the monitor reports geographic points. An executed review by another model family (OpenAI GPT-5.6) voted "not a bug" (high) on these grounds, while reproducing the failure, agreeing on the root cause and writing that "The unrestricted XY monitor overload probably reflects an internal debug-API oversight".

Why it does not settle it: @lucene.internal is an API-stability notice ("might change in incompatible ways"), not a licence to fail; the List<Point> type is the defect, not a documented limit, because the same commit offered the monitor for XY input; and having no production caller bears on impact (hence Low), not on correctness.

Suggested fix

#

Recommended A: XY callbacks on the Monitor, fed with XYPoint lists for XY input

Give the Monitor XY callbacks: default methods currentStateXY and startSplitXY taking List<XYPoint>, called for XYPolygon input; by default they forward to the existing callbacks with null points. Existing monitors compile unchanged. Validated: the repro passes with assertions on and off; 224 geo and shape tests and :lucene:core:check -x test pass.

All options and trade-offs4 options · 543 words

Every fix needs a small API decision, because the public Monitor interface takes List<Point>. Option A is additive; B is cleaner long term but breaks existing implementations; C declares the limit instead of lifting it.

A: XY callbacks on the Monitor, fed with XYPoint lists for XY input (validated by the checks) (recommended)

#

fix.diff (+55/-16, Tessellator.java only): two default methods on Monitor, a getXYPoints helper that builds new XYPoint((float) node.getX(), (float) node.getY()), and the notify helpers take the polygon argument that earcutLinkedList and splitEarcut already carry, to pick the callback.

    default void currentStateXY(String status, List<XYPoint> points, List<Triangle> tessellation) {
      currentState(status, null, tessellation);
    }

    default void startSplitXY(
        String status, List<XYPoint> leftPolygon, List<XYPoint> rightPolygon) {
      startSplit(status, null, null);
    }
  ...
      if (polygon instanceof XYPolygon) {
        monitor.currentStateXY(status, start == null ? null : getXYPoints(start), tessellation);
      } else {
        monitor.currentState(status, start == null ? null : getPoints(start), tessellation);
      }

Trade-offs

Additive and source-compatible: both new methods are defaults, so every existing implementation compiles unchanged, the repro's anonymous class included (Monitor has three abstract methods, so lambdas are not a concern); the geographic path is unchanged. An existing monitor on XY input now gets null point lists by default, where it got in-box values labelled as degrees, or the exception. currentState already gets null points for COMPLETED and FAILED (Tessellator.java:1591-1592), but startSplit never got null before. A separate probe with fix A confirmed the fallback: a monitor that does not override the new methods gets its 2 currentState calls with null points, assertions on and off. A monitor that wants XY coordinates overrides the two new methods. The (float) casts are exact: XY nodes are built from the polygon's floats.

What the checks validated

Gradle in a scratch worktree of 5adff78bb168, seed DEADBEEF: the repro fails stock and passes with the fix, assertions on and off. With the fix, the repro, the 17 other org.apache.lucene.geo test classes, TestXYShape and TestLatLonShape pass (20 classes, 224 tests, 8 skipped, 0 failures); a probe monitor that overrides currentStateXY sees x up to 500 and y up to 50 and gets no geographic callback; :lucene:core:check -x test (google-java-format, ecj lint, forbidden APIs) passes with the fix and the test in place. Targeted runs, not a clean full build.

B: one coordinate-neutral point type for both inputs (not run)

#

Change the callbacks' point lists to a type that carries any coordinates, for example x/y pairs, as Triangle already exposes getX/getY.

Trade-offs

One code path and no null defaults, but every existing Monitor implementation stops compiling, the external debugging tool included. Acceptable on main for an @lucene.internal class, not in a 10.x release; the repro's callback signatures would change with it.

C: declare the limit (not run)

#

Document that the Monitor supports geographic polygons only, and reject a non-null monitor for XYPolygon with a clear message (or drop the XY overload).

Trade-offs

Smallest change, but it removes a capability that works today for XY values inside the box; the repro would then expect that exception.

Not recommended: build the callback Points without the range check

#

An unchecked Point for XY input would make the call pass.

Trade-offs

It breaks Point's own invariant (latitude/longitude in degrees) for whatever the monitor does with the points.

Downstream note

#

How it was found

#

A proof-obligation audit of the Tessellator's Monitor contract asked whether every polygon the public tessellate(..., Monitor) overloads accept can be reported to the callbacks. For XYPolygon it cannot: the callback points are range-checked degrees. A one-test JUnit witnessed it on main.

The method in full114 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro), on main 5adff78bb168, 2026-11-03.

  • The obligation: for every XYPolygon that tessellate(polygon, false) accepts, tessellate(polygon, false, monitor) with a passive monitor returns the same triangles. Discharging it needs getPoints to accept any finite x/y, but it builds range-checked Points.
  • A JUnit test witnessed it on main with assertions on and off, and a probe showed that |x| > 180 alone and |y| > 90 alone suffice while an in-box square works. An independent reproducer and an executed review by another model family (OpenAI GPT-5.6) each wrote their own test, and a devil's-advocate verifier re-ran the finder's; all reproduced it.

Impact note

Summary
You tessellate a Cartesian XYPolygon, for example the square (0,0) (500,0) (500,50) (0,50), with Tessellator.tessellate(polygon, false, monitor) and a no-op Tessellator.Monitor to watch the algorithm, and expect the same 2 triangles that tessellate(polygon, false) returns, since the Monitor is documented as an observer that 'will receive calls with internal data at each step of the triangulation algorithm'. Instead the call throws IllegalArgumentException 'invalid longitude 500.0; must be between -180.0 and 180.0': getPoints, which builds the point lists passed to the callbacks, wraps every node as a geographic new Point(node.getY(), node.getX()), and the Point constructor range-checks latitude and longitude. Any XY vertex with |x| > 180 or |y| > 90 fails this way, so the XY overload with a monitor works only when the Cartesian coordinates happen to lie inside the latitude/longitude ranges.
