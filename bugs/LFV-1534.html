FreeTextSuggester.lookup can offer the empty word as a next-word prediction when a zero-length token followed the key's last word in a text given to build(): AssertionError with assertions on; with assertions off a suggestion that ends in the separator and can take the only place of a one-entry list (an experimental class; every release from 4.6.0 to 10.6.0, branch_11x and main)

Rare and small: the experimental FreeTextSuggester can predict an empty word where an analyzer left a zero-length token (runs: ArabicAnalyzer on a standalone tatweel; a whitespace tokenizer whose pattern filter blanks a punctuation-only token). With assertions lookup throws AssertionError; by default the visible effect is one suggestion that adds nothing.

The finding in 30 seconds

#

It takes three things at once: this opt-in class with a bigram or higher-order model (a unigram model is not affected), an analyzer that turns a whole word into a token of length 0, and a key that ends right behind a word which such a token followed in a built text. A tatweel (U+0640) normally sits inside a word.

Background: three pieces

#
  1. FreeTextSuggester learns from the texts given to build() which word follows which (an n-gram model; bigrams by default) and suggests next words for what a user typed.
  2. A suggestion's key is the n-gram: the context word, a separator byte (U+001E by default) and the predicted word. Its score is the n-gram's count over the context's count.
  3. An analyzer can emit a token of length 0, for example when a filter removes every character of a word. PatternReplaceFilter's javadoc says that it "may produce Tokens whose text is the empty string".

The finding, step by step

#
  1. Build a FreeTextSuggester (default bigram model) with the stock ArabicAnalyzer from one text, foo ـ bar: two words with a standalone tatweel (U+0640) between them. The analyzer removes the tatweel and leaves a token of length 0, so its tokens are foo, an empty token, bar.
  2. Call lookup("foo ", 10). This page expects predictions that are words of length 1 or more: here none, since no other word followed foo. No javadoc sentence says so; an assertion in the class's own result loop does. The same analyzer over foo bar predicts bar (score 1.00).
  3. With assertions on, lookup throws AssertionError from that assertion (FreeTextSuggester.java:669). With assertions off it returns one suggestion with score 1.00: foo, the separator (U+001E) and no word behind it.
  4. Add a second text, foo baz. With assertions off, lookup("foo ", 10) returns the empty-word suggestion and foo baz, 0.50 each. lookup("foo ", 1) returns only the empty-word suggestion: baz is left out (in a tie the empty word sorts first). With foo baz given twice, baz ranks first (0.67) and a list of one is right.
  5. Why: build() stores the n-gram "foo, separator, nothing" like any other. For a key that ends behind a word, lookup allows the empty completion behind foo + separator, and an assertion in the same method says that it cannot occur. Not affected: a unigram model, a key that ends inside a word that the analyzer keeps, a zero-length token elsewhere in the text.

Who is affected

#

Only an application that uses the opt-in, experimental FreeTextSuggester with a bigram or higher-order model and an analyzer that turns a whole word into a zero-length token. Without assertions nothing throws and nothing is stored wrongly: one suggestion adds nothing and can cost a real word its place in a short list. Rare.

Mechanism, terms and numbers2,098 words

Rare and small. It needs three things at once. First, FreeTextSuggester (org.apache.lucene.search.suggest.analyzing), an opt-in class tagged @lucene.experimental whose javadoc says "Likely this suggester would only be used as a fallback", with a bigram or higher-order model (the default is the bigram model; a unigram model is not affected). Second, an analyzer that turns a whole word into a token of length 0: in the runs the stock ArabicAnalyzer for a standalone tatweel (U+0640), which normally sits inside a word, and a whitespace tokenizer with a PatternReplaceFilter that blanks a punctuation-only token (salt & pepper). Third, a key that ends at a word boundary right behind a word which such a token followed in a text given to build(), and a completion search that reaches the empty word. In the default bigram model that means: the empty word is among the first num predictions of that context. In a model of order 3 or more the search can also reach it behind words that a longer context has already predicted (run with a trigram model).

Then the model holds the n-gram "word, separator, nothing", and lookup offers it: the search over the completions is started with the empty completion allowed (FreeTextSuggester.java:642, lines at main 596ef11ddf96), while an assertion in the result loop of the same method says that the word behind the last separator is not empty (:669). With assertions on lookup throws AssertionError. With assertions off, the default of a JVM, nothing throws: lookup returns one suggestion that is the key's context plus the separator with no word behind it, scored as the stored n-gram it is. It adds nothing and takes a place; in a list cut to num entries it can leave a real following word out (run: one text each, 0.50 against 0.50, lookup(key, 1) returns only the empty-word suggestion; a tie goes to the empty word by rule, because it sorts first).

In the default bigram model nothing happens when a real word ranks ahead and num is 1. A trigram model reaches further (run): for a key with two context words lookup threw AssertionError with assertions on where the list without assertions held no empty word, and in another run the empty-word suggestion took the second of two places although two real words ranked before it in its own context.

This page does not call the result without assertions a wrong result: the returned n-gram is one the model holds, with its true count, and the javadoc says "the suggestions are the analyzed forms". No javadoc sentence promises that a prediction is not empty. What makes it a finding is that two lines of one method cannot both hold for such a model, the call that allows the empty completion and the author's own assertion that a predicted word is not empty, on input that public API and stock components produce. An assertion is an internal check, not a public contract: a maintainer may as well decide that the assertion is the line to change, and the result without assertions is then the accepted behaviour.

Every release that has the class does it, 4.6.0 (2013) to 10.6.0, and so do the builds of branch_11x 89e68e0f3a50 and main 596ef11ddf96 that were run: both lines came with the class. One small change was run: offer the empty completion only when part of the last word was typed.

Texts foo - bar, foo aaa, in either order, num 1: <foo|>/0.50. A three-way tie with num 2: <foo|>/0.33 <foo|baz>/0.33, qux is left out.

Why it looks unintended

#
  • The class's own result loop asserts that a predicted word is not empty, in the same method that allows the empty completion.
  • The input is legal: public API and stock components; PatternReplaceFilter documents that it may produce empty tokens.
  • No javadoc promises it, and an assertion is no public contract: without assertions the result is called useless here, not wrong.
The full argument401 words
  • Two lines of one method cannot both hold. The search over the completions is started with the empty completion allowed (FreeTextSuggester.java:642), and the result loop asserts that the word behind the last separator is not empty (:669). Both lines are in the class as first committed (2013). A behaviour cannot be intended while the class asserts that it does not happen: for a model that holds foo plus the separator, the start path and the assertion cannot both hold.
  • No javadoc promise. No sentence of the class javadoc (:82-104) says that a prediction is not empty. What says it is the assertion: the author's internal check, their stated assumption, not a public contract. This is the weak point of the finding, stated plainly.
  • Three ways out, and the choice is the maintainers'. Change the start path, so that the empty completion is offered only where it is a word (the change that was run, below; for a key that ends inside a word the argument true is right and stays). Or delete or relax the assertion at :669: the result without assertions is then the accepted behaviour, by the javadoc at :90-91 and :97, and the test of this page, which requires that no suggestion ends in the separator, would be declined. Or keep the token out of the model (not built). Nothing in the sources rules any of the three out.
  • The input is legal. Public API only: the constructor, Lookup.build(Dictionary) and lookup(CharSequence, int), with stock analysis components. PatternReplaceFilter's javadoc: "this TokenFilter may produce Tokens whose text is the empty string" (PatternReplaceFilter.java:31-32). Lucene's own test asserts the empty output of the Sorani normalizer for a tatweel (TestSoraniNormalizationFilter.java:85). The only token rule the class documents is about the separator byte (:147-150, :176-180).
  • What the class does about empty tokens on the key side. A key whose tokens are all zero-length is rejected with IllegalArgumentException ("no tokens produced by analyzer, or the only tokens were empty strings", :448-451, :476-479). A key with a real token and a zero-length one is accepted.
  • Tests. Lucene's TestFreeTextSuggester has no analyzer that emits a zero-length token; its testEmptyString covers the empty key (TestFreeTextSuggester.java:245-257).
  • History. LUCENE-5214 (#6278, 2013) added the class with both lines. Its thread has no line on empty or zero-length tokens.
The devil's-advocate check392 words

The strongest case for "works as designed": the class javadoc says "the suggestions are the analyzed forms (so your analysis process should normally be very "light")" (FreeTextSuggester.java:90-91) and "the key of each result is the ngram token" (:97). foo plus the separator is an n-gram the model really holds, returned with its true count; with a plain WhitespaceAnalyzer the same lookup returns - as the next word, so the suggester returns the token that followed, as it does for any token. The author accepted odd analyzed forms knowingly (Michael McCandless on LUCENE-5214, 2013-09-17: the suggester "only suggests the analyzed forms, which may be too ... weird?"). The class is experimental and described as a likely fallback. An analyzer that emits empty tokens can have a length filter behind it. And the class already returns a non-word on purpose: the filler _ that ShingleFilter puts where a stop filter removed a word. Lucene's testEndingHole expects wizard _ oz/1.00 for the key wizard of (TestFreeTextSuggester.java:259-282), and in a run for this page a bigram model over wizard of oz with a stop filter for of returns <wizard|_>/1.00 for the key wizard . So a suggestion whose next word is not a word is something this class returns knowingly.

Where it holds, and where it does not: it holds, to a moderate degree, for the result without assertions, which is why this page does not call that result wrong. It does not cover the AssertionError: the author's own check says that the word behind the last separator is never empty, and no documentation covers the exception; a maintainer who takes the works-as-designed view would have to remove that assertion, which is one of the three ways out named above. The filler differs in one point: for it the class has code (:481-491, :535-541) and two tests and no assertion against it, while for the empty word its only statement is an assertion that it does not occur. The advice of a light analysis does not avoid the trigger either: a whitespace tokenizer with one pattern filter has no stemmer and no stop filter. What is left of the argument is about weight, not about correctness, and this page says the weight first. A maintainer may fairly answer that an analyzer which emits empty tokens should filter them.

Suggested fix

Recommended Offer the empty completion only when part of the last word was typed (validated)

Impact note
Hits an application that uses the opt-in, @lucene.experimental FreeTextSuggester with a bigram or higher-order model (run: the default bigram model and a trigram model; a unigram model returned no suggestion and no error) and an analyzer that turns a whole word into a token of length 0 (run: the stock ArabicAnalyzer for a standalone tatweel U+0640, and a WhitespaceTokenizer with a PatternReplaceFilter that blanks a punctuation-only token), for a lookup key that ends at a word boundary right behind a word which such a token followed in a text given to build(), or whose own last token is the zero-length one [exec]. Summary

You expect predictions that are words of length 1 or more (here none, since nothing else followed foo): no javadoc sentence states that; an assertion in the class's own result loop says that the last word of a suggestion is not empty.
