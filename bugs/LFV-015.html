After rolled-back segment names are reused, reopening an old NRT reader throws a misleading IllegalStateException

An NRT reader kept across two rolled-back writer sessions cannot be reopened on a later commit: openIfChanged(reader, commit) throws an IllegalStateException that blames the application for deleting index files, although Lucene's own file deleter removed them and a later writer reused the segment name _0. Default configuration, since 6.2.0.

The finding in 30 seconds

#

A reopen reuses the old reader's per-segment readers by segment name. Here a name comes back for a different segment, because the counter that hands out names is kept only by a completed commit and two writer sessions in a row were rolled back.

Background: segment names, NRT readers and reopen

#
  1. Each new segment gets a name, _0, _1, ..., when the writer starts it (at the first addDocument), from a counter in the writer's memory. Only a completed commit keeps the counter (prepareCommit() writes it to a pending file that rollback removes); rollback() closes the writer without a commit.
  2. When a writer starts, its file deleter moves the counter past any segment files it finds, then deletes the files no commit refers to (leftovers of crashed or rolled-back sessions).
  3. An NRT reader (DirectoryReader.open(writer)) can see segments that were never committed, and it keeps their files alive. openIfChanged(reader, commit) builds a reader on another commit and reuses the old per-segment readers whose segment names match; each segment also carries a random id, and a guard throws when the same name has a different id.

The finding, step by step

#
  1. Writer 1 adds 1 document and you open an NRT reader on it: segment _0, never committed. Roll writer 1 back, then open a second writer and roll it back too.
  2. Writer 3 adds 2 documents and commits. You call DirectoryReader.openIfChanged(reader, commit) and expect a new reader with 2 documents, as its javadoc says. With one rolled-back writer fewer, that is what you get.
  3. Instead it throws IllegalStateException: same segment _0 has invalid doc count change; likely you are re-opening a reader after illegally removing index files yourself ....
  4. Why: writer 2's startup moved its name counter past the leftover _0 files and deleted them; its rollback lost the counter. So writer 3 named its new segment _0 again, with a new id. The reopen matches old segment readers by name, sees the other id and throws a guard meant for applications that ran rm -rf.
  5. No wrong results were observed: the old reader still finds its 1 document and DirectoryReader.open(commit) sees 2. The message's advice, OpenMode.CREATE, does not help.

Who is affected

#

Applications that keep an NRT reader (or an NRT SearcherManager whose RefreshCommitSupplier returns a commit) open while two writer sessions in a row end in rollback() without a commit, then reopen it on a later commit. Default configuration, deterministic, but an unusual sequence. The reopen fails with a false diagnosis; no wrong results were observed.

Mechanism, terms and numbers627 words

DirectoryReader.openIfChanged(DirectoryReader, IndexCommit) promises a new reader when the commit differs, and Lucene has supported it for near-real-time readers since LUCENE-4898. Keep such a reader open while its writer is rolled back without ever committing, then open a second writer and roll it back as well: the second writer's IndexFileDeleter moves the segment counter past the leftover _0 files and deletes them as unreferenced, and its rollback discards the raised counter. A third writer then names its new segment _0 again, with a new segment id, and commits. Reopening the old reader on that commit looks old segment readers up by name, finds a different id and throws the LUCENE-5931 guard's IllegalStateException, whose message says the application illegally removed index files and advises OpenMode.CREATE, which does not help. No wrong result was observed: the old reader keeps working and a fresh DirectoryReader.open(commit) is correct. From 4.3.0 to 6.1.0 the same call silently returned the stale 1-document reader. A 19-line change that opens such segments fresh for NRT readers passes the repro and the whole core test suite.

Without the second writer, w3 itself sees the leftover _0 files, moves its counter to 1 and writes _1: no name collides and the reopen returns the 2-document reader. On a file system that cannot delete open files (the test framework's WindowsFS, a simulation, not a run on Windows), the files stay as pending deletions, which the next writer also counts (IndexFileDeleter.java:211-217), so it does not collide either. With an index that already has a commit, the same sequence collides on the uncommitted _1 instead.

The guard does a real job: before it existed (4.3.0 to 6.1.0), the same call silently reused the stale _0 reader. What is wrong is the decision to throw, with a diagnosis that is false here.

Exposure and likelihood296 words
  • Who is hit. An application that keeps an NRT reader open across writer sessions in one directory, where two consecutive sessions end in rollback() with no commit in between, and then reopens the old reader with openIfChanged(reader, commit). Lucene's SearcherManager makes this call when built on a writer with a RefreshCommitSupplier that returns a commit (SearcherManager.java:199-200, since 10.3.0; the default supplier returns null, which takes the writer path): after the same sequence maybeRefresh() throws the same exception, while without the second writer it refreshes to 2 documents.
  • Configuration. Default IndexWriterConfig, public API, single thread; the plain main() probe (lucene-core only) uses the stock codec. Executed on ByteBuffersDirectory, and on MMapDirectory and NIOFSDirectory on Linux. File systems that refuse to delete open files avoid it (the study's WindowsFS control, a simulation, not a run on Windows).
  • How often. Rare: it needs two rolled-back sessions in a row with no commit, while an old NRT reader stays open. As few as 1 old and 2 new documents trigger it. It also happens on an index that already has a commit (the collision is then on the uncommitted _1).
  • What goes wrong. The reopen fails with an IllegalStateException that says the application illegally removed index files; its advice (IndexWriter.deleteAll or OpenMode.CREATE) does not apply, and OpenMode.CREATE was run: the same exception. No wrong result was observed: the old reader keeps working and DirectoryReader.open(commit) is correct.
  • Why it matters beyond the message. The same name reuse is the trigger for a separate, more serious defect in the same hunt: merge instances re-open segment files by name, so addIndexes of an old leaf can copy another segment's data on main. That one needs its own fix.
  • Impact class: wrong error; priority low.

Why it looks unintended

#
  • The openIfChanged(reader, commit) javadoc says "open and return a new reader"; reopening an NRT reader on a commit is supported since LUCENE-4898 and tested upstream.
  • The guard exists to catch an application that "illegally 'rm -rf' their index"; here Lucene's own file deleter removed the files.
  • The same calls with one rolled-back writer fewer return the 2-document reader.
The full argument309 words
  • Contract. DirectoryReader.java:276-281: "If the IndexCommit differs from what the provided reader is searching, open and return a new reader; else, return null." No NRT or closed-writer exception is stated. CHANGES.txt:14052-14054 (LUCENE-4898): "DirectoryReader.openIfChanged now allows opening a reader on an IndexCommit starting from a near-real-time reader (previously this would throw IllegalArgumentException)."
  • Upstream tests reopen an NRT reader on a commit: TestDirectoryReaderReopen.testOpenIfChangedNRTToCommit (:649-671) and TestIndexWriterReader.testReopenNRTReaderOnCommit (:1179).
  • Old readers keep working across writer sessions. IndexWriter.java:103-108: with OpenMode.CREATE "The old readers will continue to search the "point in time" snapshot they had opened, and won't see the newly created index until they re-open." This documents searching, not reopening an orphaned NRT reader (see the devil's advocate).
  • The guard is for application abuse. StandardDirectoryReader.java:274-275; CHANGES.txt:9027-9029 (LUCENE-5931): "Detect when an application tries to reopen an IndexReader after (illegally) removing the old index and reindexing"; CHANGES.txt:12286-12290 (LUCENE-5684): "when IndexReader is reopened after all files in its index were removed and recreated by the application". The guard's test calls its trigger "Abuse" (TestDirectoryReaderReopen.testDeleteIndexFilesWhileReaderStillOpen, :1043-1090). In #6993 rmuir asked "Can you make a test change to trip it without manually removing files from your index?" and mikemccand answered "I don't think so ... the only way I know of this happening is if an app has a reader open, then removes the index, rebuilds it, then tries to openIfChanged the reader". This sequence trips it with no file removed by the application.
  • Lucene knows names get reused after its own cleanup. util/FileDeleter.java:176-181: "it's very unusual yet possible ... if you open IW on a crashed index, and it removes a bunch of unref'd files, and then you add new docs / do merging, and it reuses that segment name." IndexWriter.java:2173-2177 bumps the change count so a writer does not "close, re-open and re-return the same segment name".
The devil's-advocate check285 words

Strongest case for "works as designed": the NRT note "Once the writer is closed, any outstanding readers may continue to be used. However, if you attempt to reopen any of those readers, you'll hit an AlreadyClosedException" makes reopening an orphaned NRT reader unsupported; the guard is deliberate, results are never wrong and DirectoryReader.open(commit) is an easy workaround; maintainers have said that mixing files from several writers is unsupported (dev@/java-user@ 2022, "customize segment names?"). Two of the study's verifiers and one noise triage leaned this way, and the read-only cross-model reviewer rated this argument "strong".

Why it fails:

  1. The note is written on openIfChanged(DirectoryReader, IndexWriter) and its executor variant (DirectoryReader.java:330-332, :372-374) and on the package-private IndexWriter.getReader (:507-509), whose readers' openIfChanged "will simply forward back to this method" (:493). The commit overload has not gone through the writer since LUCENE-4898 (StandardDirectoryReader.java:456-459) and returns the new reader after a rollback in every control; TestIndexWriterReader.testAfterClose asserts the AlreadyClosedException only for openIfChanged(r).
  2. Even under the broad reading, the outcome is not the documented one: a different exception with a false diagnosis, and only when a name was reused.
  3. A one-file change returns the right reader and keeps the abuse detection the upstream tests assert, so the failure is not a necessary cost of the guard. No files are mixed: the writers run one after another, each holding the write lock.

What stays open: the docs do not say what reopening an NRT reader whose writer was rolled back should do, so this is a gray zone (a later cross-model fact check rated the intended-behaviour case "moderate"). A maintainer could reasonably choose a message or javadoc fix (C) over fix A.

Suggested fix

#

Recommended A. For an NRT reader, reuse an old segment reader only when the segment id matches (+19/-1)

For an NRT reader, reuse an old segment reader on reopen only when its segment id matches the commit's; otherwise open that segment fresh (+19/-1 in StandardDirectoryReader.doOpenIfChanged). Plain readers keep the guard. The repro passes, as do 9 related suites and all 8,898 core tests.

All options and trade-offs3 options · 744 words

Fix A was run and is recommended; B and C were not run. Workaround for users today: after rolling writers back, open a fresh reader with DirectoryReader.open(commit) instead of openIfChanged(oldNrtReader, commit), or close (commit) the middle writer instead of rolling it back, which saves the counter.

A. For an NRT reader, reuse an old segment reader only when the segment id matches (+19/-1) (validated by the checks) (recommended)

#

In StandardDirectoryReader.doOpenIfChanged(SegmentInfos, ExecutorService), the path behind openIfChanged(r, commit), drop old leaves whose segment id differs from the same-named segment of the commit when the reader is NRT (writer != null). Those segments are then opened fresh from the files on disk; leaves with matching ids are reused as before. Plain readers still throw the guard's exception. This is a policy choice, not only a better message: for NRT readers the abuse exception on this path goes away.

Trade-offs

For NRT readers this path no longer reports an application that deleted and rebuilt the index; it returns a correct fresh reader instead (plain readers still throw, as the guard's upstream test asserts). Only openIfChanged(nrtReader, commit) changes; the writer-based reopen and the replicator's direct StandardDirectoryReader.open are untouched. The name reuse itself remains, so the merge-instance defect that it triggers still needs its own fix. Keying on SegmentReader.isNRT instead does not work: a pooled NRT segment reader without deletes has isNRT == false; a variant that passes a flag into getOldSegmentReader was also run green.

B. Keep segment names unique across rolled-back sessions

#

Make a writer never re-issue a name whose files its deleter removed at startup: for example, do not delete unreferenced files newer than the last commit (rmuir's proposal in LUCENE-6171 to "only delete files older than the current commit point", never committed), at least until a commit has saved a counter past them; or skip extra names at writer startup (rmuir on #6965: "gobble up extra generations on IW bootup").

Trade-offs

Attacks the root cause and would also cover the merge-instance defect and #6965, but only a completed commit leaves a saved counter, and rollback() must not write one; keeping leftover files changes cleanup behaviour; a counter jump only makes collisions unlikely. Larger and riskier than A. Not run.

C. Make the exception message truthful

#

Say that a segment name can also be reused after rolled-back writer sessions, and suggest DirectoryReader.open(commit).

Trade-offs

Cheap, but the documented call still fails (the repro test still fails) and the message loses the clear abuse diagnosis it exists for. At most a complement to A. Not run.

Downstream note

#

Lucene's own SearcherManager, built on a writer with a RefreshCommitSupplier that returns a commit (10.3.0+), hits it too: maybeRefresh() throws the same exception after the two rollbacks.

How it was found

#

Model-based randomized testing, the study's non-formal baseline, found it first: random sequences of writer operations, NRT opens, rollbacks, commits and reopens on the stock jars, each reader checked against an executable reference model. TLA+, Alloy, P, Dafny, OpenJML and JBMC experiments re-found it after it was on their task list (hinted).

The method in full109 words
  • Method: model-based randomized testing (the study's non-formal baseline), 2026-10-22, main 7cecf79523: an executable reference model of writer and reader state, random operation sequences, a conformance check at every reader-producing step and automatic shrinking of failing sequences. First hit in the first run after 161 s (sequence 1,809).
  • Re-finds: TLA+ (TLC), Alloy, P, Dafny, OpenJML and JBMC experiments reached the same sequence; all were hinted (the candidate was on their task list), so none is a blind formal discovery.
  • Reduction: the study's two 8-test classes (3 of 8 fail in each) were minimized on 2026-10-29 to the one test above, and a control without the second rollback was run.

LFV-015, snapshot of 2026-11-02

Registry title
After rolled-back segment names are reused, reopening an old NRT reader throws a misleading IllegalStateException
Area
index / IndexWriter NRT
Priority
Low, rank 769: Reopening an old NRT reader after rolled-back segment names are reused throws a misleading IllegalStateException, a wrong error type in an unusual session sequence that matters mainly as LFV-004's enabler.
Impact class
wrong error
Impact note
Default configuration; needs an NRT reader kept open across two consecutive rolled-back, never-committed writer sessions (the second session's startup deletes the first one's leftover files and its rollback discards the raised segment counter), after which a later writer reuses the segment name and commits, and the old reader is reopened on that commit; low severity on its own, but it enables the merge-instance re-open bug.
Summary
You open an NRT reader from a writer that is then rolled back without committing, a second writer is opened and rolled back too, a third writer reuses the same segment names and commits, and you call openIfChanged(oldReader, commit). You expect a new reader or an AlreadyClosedException, as documented. Instead the LUCENE-5931 guard throws an IllegalStateException that blames the application for removing index files, although Lucene's own IndexFileDeleter deleted them, and its OpenMode.CREATE advice also fails.
Introduced
34e56d51f0d (branch_4x; trunk twin c18676ed4fb), LUCENE-4898 'openIfChange now allows targeting an IndexCommit from an NRT reader' (#5963, Michael McCandless): openIfChanged(nrtReader, commit) now reopens through the path that reuses the old reader's segment readers by segment name only, so from 4.3.0 the bug's call sequence silently returns a stale 1-document reader; the misleading IllegalStateException comes from 6b0b119074f (branch_6x, first released in 6.2.0; master twin 664e39292bd, first released in 7.0.0), LUCENE-5931 'detect when segments were (illegally) replaced when re-opening an IndexReader' (#6993, Mike McCandless), which added the segment-id guard in place of the stale reader [read: git show, git blame, tag containment; exec: the history probe on every boundary release from 4.0.0 to 10.6.0 and main] (2013-04-04 (LUCENE-4898, the stale-reader form, first released in 4.3.0); 2016-06-12 (LUCENE-5931, the misleading IllegalStateException, first released in 6.2.0))
