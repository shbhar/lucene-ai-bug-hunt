The finding in 30 seconds

#

Documentation only: two class javadoc sentences name c where AlbanianNormalizer writes q for the precomposed ç. For this finding no code is wrong and no code change is claimed: the q folding is intended, as the normalizer's own javadoc and the package's tests say. No result of the stock analyzer is wrong because of the two sentences. No release has the package.

Background: three pieces

#
  1. Albanian has two letters outside ASCII, ë and ç. The normalizer's javadoc says they are very often typed as plain e and c, and ç also as q, which sounds the same to most speakers.
  2. AlbanianNormalizer folds these spellings to one form so that they index to the same term. Its javadoc: ë becomes e, and ç and c become q; words that really have a c (cili, kec) are listed in a file and keep it.
  3. AlbanianNormalizationFilter applies that normalizer to each token, and AlbanianLightStemmer expects input that went through it. new AlbanianAnalyzer() chains tokenizer, lower-casing, normalization, stop words and stemmer.

The finding, step by step

#
  1. You read the class javadoc of the new AlbanianNormalizationFilter: "ë/ç are folded to e/c and in-word apostrophes are removed." The class javadoc of AlbanianLightStemmer says the same of the input it expects: "normalized by AlbanianNormalizer", with "ç→c".
  2. You run the word çfarë through the filter, with ç and ë as single precomposed letters, and expect the term cfare.
  3. You get qfare. The one test, which asserts the javadoc sentence, fails with term 0 expected:<[c]fare> but was:<[q]fare> on branch_11x 262e019500ec and on main b5a4546a5964 (commits of 2026-11-22), with assertions on and off.
  4. The q is intended, and no code change is claimed. AlbanianNormalizer, the class both sentences link to, documents "ç and c → q" and says why, and the package's own test expects qfare for çfarë. The defect is the two sentences.
  5. Who can be misled: a caller who writes a word set by hand in the folded form the javadoc states. In the run the stop set {cdo} given to AlbanianAnalyzer(CharArraySet) left the stop word çdo in the stream as qdo. The dictionary spelling {çdo} failed the same way. The set {qdo}, or a set made with the public AlbanianNormalizer.normalize, removed the word.

Who is affected

#

A caller who writes a word set by hand in the folded form the javadoc states (c for ç) can be misled. In the run the dictionary spelling failed the same way, while the public AlbanianNormalizer.normalize gave the right form. new AlbanianAnalyzer() is not affected. Low: a documentation point that can still be corrected before a first release has it.

The class they link to

#

The class javadoc of AlbanianNormalizer (AlbanianNormalizer.java:37-39):

 *   <li><code>ë</code> → <code>e</code>, and <code>ç</code> and <code>c</code> → <code>q</code>,
 *       whether precomposed or written as a base letter followed by a combining diaeresis / cedilla
 *       (text copied from PDFs and some web pages comes in that decomposed form)

It says why at :50-56: ç, c and q "become one class because that is how the letter is typed", and "The class is spelled q so that the stemmer's palatal rules (miq / mik) keep working on folded text." The code (:154-158; :165-167 writes Q for the capital):

        case 'ç':
          // ç is typed as c (no cedilla) and as q (the same sound to most speakers): one class,
          // spelled q so the stemmer's palatal rules (miq / mik) still apply after folding
          s[i] = 'q';
          break;

The filter adds nothing of its own: it calls normalizer.normalize for each token that is not marked as a keyword (AlbanianNormalizationFilter.java:49-51). The package's own test pins the letter with the same word: check("çfarë", "qfare") (TestAlbanianNormalizer.java:32), and testKeyboardSpellings (:66-77) expects qdo for çdo, cdo and qdo.

What was run

#

On main b5a4546a5964 and branch_11x 262e019500ec, assertions on and off, the same output each time:

  • çfarë, precomposed, through the filter: qfare. The same word through AlbanianNormalizer.normalize, through the filter's factory by its name albanianNormalization and through Analyzer.normalize: qfare each.
  • The other half of the filter's sentence holds: farë gives fare.
  • Upper case: ÇFARË gives QFARE (the filter does not lower-case).
  • Each token of 1 to 5 letters over nine lower-case letters (ç, c, a, e, i, l, k, d, o), no apostrophe: 66,429 tokens, 28,981 of them with ç. Each of their 35,983 letters ç was written q, 657 of them in the 596 tokens in which a listed word kept its plain c. Each token of 1 to 4 letters over six upper-case letters: 985 of 985 letters Ç were written Q.

Why this page says "precomposed"

#

The statement is about the precomposed letter ç (U+00E7), the form the test uses. Other shapes that were run: a one-letter ç in front of an apostrophe is dropped with the apostrophe, as the normalizer's javadoc says (ç'është gives eshte); the decomposed spelling, c followed by the combining cedilla U+0327, gives q in a token that no listed word matches (qfare) and c behind a listed prefix (cilc, where the precomposed letter gives cilq): the base letter is read as the plain c of a listed word before the combining mark is handled. Decomposed spellings are what a separate finding on this package, LFV-1574, is about. A token marked as keyword before the filter is left alone.

Why it looks unintended

#
  • AlbanianNormalizer, the class both sentences link to, documents "ç and c → q", says why, and writes q for the precomposed ç.
  • The package's own test expects qfare for çfarë.
  • Both sentences name an output letter, and each pairs ë with e, which is what comes out.
The full argument167 words
  • On the letter for the precomposed ç, the linked class's javadoc, its code and the package's tests agree with each other. The normalizer's class javadoc says "ç and c → q" (AlbanianNormalizer.java:37) and why (:50-56), its code writes q (:154-158), and TestAlbanianNormalizer.java:32 expects qfare for çfarë. That is what the word "intended" rests on here. The two sentences are the ones that differ.
  • The sentences name an output. "Are folded to e/c" and the arrow "ç→c" name the letter that comes out. The same sentence pairs ë with e, and e is what comes out: farë gives fare in the run.
  • The thread. #16957 was read whole on 2026-11-20 (description, 6 comments, 2 reviews, 2 inline comments): nobody mentions the two sentences. On 2026-11-22 it had the same 6 comments.
  • No code change follows from this. The q folding stays; what is claimed is that two sentences name another letter than the class they link to writes for the precomposed ç.
The devil's-advocate check195 words

The strongest case that nothing is wrong: the filter's sentence is shorthand. It says that the filter applies AlbanianNormalizer, links that class twice, and the linked javadoc has the full and right mapping; "folded to e/c" can be read loosely, as "ë and ç are treated like their plain letters".

Why it fails. As an equivalence the sentence does not hold either: for a word on the keep-c list the plain c stays and the ç does not join it (cili gives cili, ç followed by ili gives qili in the run). The other filters of this kind do not use such shorthand: of the fourteen *NormalizationFilter classes in the main sources of the analysis-common module at main b5a4546a5964, the eight others whose javadoc says "applies XNormalizer" name no mapping (Arabic, Bengali, Sorani, Persian, Hindi, Indic, Telugu, Thai), and the five that describe a mapping name its output (German, Scandinavian, Norwegian, Romanian, Serbian). The folded form is not internal: two public constructors take a caller's sets in it and getDefaultStopSet() hands it out.

What remains of the argument is the weight: a small documentation point. That is why it is Low.

Suggested fix

#

Two shapes of a javadoc correction, one of them run; neither is a recommendation: the wording is the maintainers' choice. Shape 1, run: name q in the two sentences; the package's 61 tests pass, the module's lint passes and the rendered javadoc says "folded to e/q". Shape 2, not run: take the mapping out. No code change, no test change.

Registry title
Two class javadocs of the new Albanian analysis package name c as the letter that ç is folded to (AlbanianNormalizationFilter: 'ë/ç are folded to e/c'; AlbanianLightStemmer: input 'normalized by AlbanianNormalizer' with 'ç→c'), but AlbanianNormalizer writes q for the precomposed ç: in the test the filter turns çfarë into 'qfare' (documentation defect on branch_11x and main, both unreleased; the q folding is intended and no code change is claimed here)
Area
analysis-common / Albanian (org.apache.lucene.analysis.sq, new on main and branch_11x): the class javadocs of AlbanianNormalizationFilter and AlbanianLightStemmer against AlbanianNormalizer
Priority
Low, rank 1461: Two class javadoc sentences of the new Albanian analysis package, on main and branch_11x (both unreleased), name another output letter for ç (c) than the normalizer writes for the precomposed letter (q). No result of the stock analyzer is wrong because of them; a caller can be misled when writing a word set by hand in the stated folded form, and in the run the dictionary spelling failed the same way while the public AlbanianNormalizer.normalize gave the right form. It is Low because it is a documentation point (no code is wrong) that can still be corrected before the first release that has the package.
Impact class
minor
Impact note
Documentation only, in a package that is new on main and branch_11x (both unreleased; no release has it): no result of new AlbanianAnalyzer() is wrong because of the two sentences, and only a reader of the two class javadocs is told another letter than the normalizer writes for the precomposed ç. Summary
You read the class javadoc of the new AlbanianNormalizationFilter, which says that ë/ç 'are folded to e/c' (the class javadoc of AlbanianLightStemmer says the same of the input it expects: 'ç→c'), and you expect the word çfarë to come out of the filter as 'cfare'. Instead it comes out as 'qfare': AlbanianNormalizer, the class both sentences point to, writes q for ç on purpose, as its own javadoc and the package's tests say (run with the precomposed letter on branch_11x 3221dd4cf3a1 and main 7b8418faa2ff, with and without assertions). The defect is in the two sentences: the q folding is intended, this finding proposes no code change, and no release has the package yet.
