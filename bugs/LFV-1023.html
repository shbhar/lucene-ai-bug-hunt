BpVectorReorderer's command line cannot reorder an index created by Lucene 9.x or 10.x, or one that uses soft deletes

BpVectorReorderer's command line (new in Lucene 11) rewrites the index through a default IndexWriterConfig stamped "created by major 11", so addIndexes refuses every index created by 9.x or 10.x and every index that used soft deletes. Keeping the source's created major and soft-deletes field fixes it.

The finding in 30 seconds

#

reorderIndexDirectory rewrites the index in place: a reader on the current commit, a new CREATE-mode writer on the same directory, then one addIndexes per segment. The writer gets a default config, so the new index is stamped with the running major (11 on Lucene 11) and has no soft-deletes field, while every re-added segment keeps its own.

Three things to know first

#
  1. Every index records the major version that created it, and that never changes, even after upgrades. Lucene 11 opens and writes indexes created by 9.x and 10.x.
  2. IndexWriter.addIndexes accepts only segments created by the same major as the target index, and segments that use soft deletes only if the writer's config names the soft-deletes field.
  3. A writer in OpenMode.CREATE starts a new index whose created major comes from IndexWriterConfig.setIndexCreatedVersionMajor; the default is the running major, 11 on Lucene 11.

The finding, step by step

#
  1. You have an index of 10 documents with a 2-d vector field f, written by Lucene 10.5.2 with default settings. Lucene 11 opens and writes it, and the index stays "created by major 10" for good.
  2. You run the tool on it: java -cp lucene-core.jar:lucene-misc.jar org.apache.lucene.misc.index.BpVectorReorderer $IDX f. You expect the same 10 documents back, renumbered so that similar vectors get nearby doc ids.
  3. The tool opens a second IndexWriter on the same directory with new IndexWriterConfig() and OpenMode.CREATE. That writer starts a fresh index stamped "created by major 11", then re-adds each old segment with addIndexes, which accepts only segments of the index's own major.
  4. You get exit code 1: IllegalArgumentException: Cannot merge a segment that has been created with major version 10 into this index which has been created by major version 11. A 9.12.3 index fails the same way; an index that used soft deletes fails with "soft-deletes field is not configured in IWC".
  5. With the fix (copy the source's created major and soft-deletes field into that config) the same command exits 0: 10 documents, still created by major 10.

Who is affected

#

Anyone who runs this lucene/misc tool on 11.0 on a compatible index carried over from 9.x or 10.x: such an index keeps its creation version for good. Default settings and options are enough, and every attempt fails at the first segment. Unreleased (branch_11x, main) and loud: a clear exception names the cause.

Mechanism, terms and numbers619 words

BpVectorReorderer (lucene/misc, added for 11.0 by #14097) has a command line, main(indexPath, field), that renumbers the documents of an existing index in place so that documents with similar vectors get nearby doc ids. It calls reorderIndexDirectory, which opens a reader on the index, then a new IndexWriter on the same directory with new IndexWriterConfig() and OpenMode.CREATE, and adds each segment back with addIndexes(SortingCodecReader.wrap(...)). A CREATE writer takes the index's created major from its config, by default the running major (11 on Lucene 11), and the default config has no soft-deletes field, while each wrapped segment keeps its own created major. So addIndexes refuses the first segment of every index created by 9.x or 10.x, and of every index that used soft deletes, with an IllegalArgumentException. Lucene 11 documents 9.x and 10.x indexes as fully writable and an index's creation version as permanent, so on 11.0 the tool cannot reorder a compatible index carried over from 9.x or 10.x. On main, now 12.0, it also refuses 11.x indexes. The javadoc of IndexWriterConfig.setIndexCreatedVersionMajor names exactly this addIndexes restriction and its remedy; copying the source's created major and soft-deletes field into the rewrite's config fixes it (+8 lines). Unreleased: the tool is only on the 11.0 release branch branch_11x and on main.

The bug (main 645d4fe14a20)

#
  1. main (BpVectorReorderer.java:653-682) takes the index path, the field and three tuning options (--max-iters, --min-partition-size, --thread-count); it has no option for the writer configuration. It calls reorderIndexDirectory(FSDirectory.open(path), executor) (:679-680).
  2. reorderIndexDirectory (:684-697) opens a DirectoryReader on the directory, then new IndexWriterConfig() with setOpenMode(OpenMode.CREATE) (:686-687) and a writer on the same directory, and for each segment calls writer.addIndexes(SortingCodecReader.wrap(segment, computeDocMap(...), null)) (:689-694).
  3. In CREATE mode the writer starts new SegmentInfos(config.getIndexCreatedVersionMajor()) (IndexWriter.java:1009); the default is the major of Version.LATEST, 11 at this commit (IndexWriterConfig.java:177-179). No soft-deletes field is configured.
  4. SortingCodecReader.wrap keeps the segment's createdVersionMajor (SortingCodecReader.java:454-457).
  5. addIndexes validates each segment first (IndexWriter.java:3290): validateMergeReader throws when the index's created major differs from the segment's (:3228-3236), 11 vs 10 or 9. For segments that carry a soft-deletes field, the field check that follows (verifyFieldInfo, IndexWriter.java:3292 -> FieldInfos.java:401-403) reaches FieldInfos.verifySoftDeletedFieldName, which throws because the writer has none configured (FieldInfos.java:459-465).
  6. All segments of an index share its created major, so the very first addIndexes call fails and nothing is reordered. A soft-deletes field that was configured but never used leaves no trace in the segments and reorders fine.
  7. On main after #16942 (2026-10-29) Version.LATEST is 12, so there the same code also refuses indexes created by 11.x: the test below fails on main 716d6f216f5 with "created with major version 11 into this index which has been created by major version 12".

Exposure and likelihood156 words
  • Who is hit. Users of the 11.0 release branch branch_11x or of main (unreleased) who run BpVectorReorderer's command line, or call reorderIndexDirectory from the same package. BPReorderingMergePolicy and computeDocMap with the caller's own IndexWriter are not affected.
  • Default vs opt-in. The tool is an opt-in expert utility. Once it runs, default index settings and default options are enough, and no option avoids the failure.
  • Scale. No size or timing condition: the first segment fails, every time, with assertions on and off. An index's creation version "never changes" (MIGRATE.md:165), also after IndexUpgrader or forceMerge, so an index created by 9.x or 10.x can never be reordered by the tool. On main (12.0) the same holds for indexes created by 11.x.
  • Effect. A clear IllegalArgumentException naming the cause; nothing is reordered. Today the failure also empties the index (LFV-1022, a separate bug in the same method); with LFV-1022 fixed, the index would be kept.

Why it looks unintended

#
  • main() takes "a path containing an index to reorder"; Lucene 11 keeps 9.x indexes "fully supported (open and write)", and an index's creation version "never changes".
  • setIndexCreatedVersionMajor's javadoc names this exact addIndexes restriction and its remedy; the tool does not apply it.
  • IndexUpgrader and IndexSplitter keep the source's created major; the tool's PRs, tests and CHANGES state no version limit.
The full argument242 words
  • Contract. main: "@param args two args: a path containing an index to reorder" (BpVectorReorderer.java:648-651), with no version restriction; neither the class nor main is marked @lucene.experimental. MIGRATE.md:143: "Set to 9 for Lucene 11.0.0, so indexes created with Lucene 9.x remain fully supported (open and write)"; :165: "The index's creation version is still 9 (this never changes)"; CHANGES 11.0, GITHUB#16741: "Indexes created with 9.x remain fully supported in Lucene 11, no reindexing required".
  • The documented remedy. IndexWriterConfig.setIndexCreatedVersionMajor: "It is sometimes useful to set the previous major version for compatibility due to the fact that IndexWriter#addIndexes only accepts indices that have been written with the same major version as the current index" (IndexWriterConfig.java:174-178), added by LUCENE-8508 (#9554) so that a new index can take an older created major and so accept older segments through addIndexes (the issue's stated motivation is resharding with addIndexes).
  • Other tools. IndexSplitter.split writes new SegmentInfos(infos.getIndexCreatedVersionMajor()) (IndexSplitter.java:112); IndexUpgrader writes into the existing index with the default open mode CREATE_OR_APPEND (IndexUpgrader.java:183), so its created major is kept.
  • Tests and history. TestBpVectorReorderer runs main() as "the index reordering tool" (:353-354, :412-413), only on indexes it just created on main. #13683, the tool's first version, describes renumbering "an existing HNSW graph ... without the need to re-index it" and lists limitations (float vectors only, no index sort), but no index-version or soft-deletes limit; #14097 discusses none either.
The devil's-advocate check226 words

Strongest case (built by the devil's-advocate check and the cross-model reviews, rated moderate): the same-major rule of addIndexes is deliberate and tested (LUCENE-7756; TestBasicBackwardsCompatibility.testAddOldIndexesReader asserts the same message); the command line began as a research tool (in #13565 its author wrote "it would be easier to start with a tool that rewrites the index" if "we want to just get an idea of what the impact of such a change might be"; on #14097 a reviewer accepted open questions "especially for the misc module"); CHANGES describes #14097 as a merge policy and never mentions the command line; and IndexMergeTool and MultiPassIndexSplitter use the same default-config addIndexes pattern without a report.

Why it fails: the guard stops mixing majors in one index, but this tool rewrites one index's own segments into the same directory, which mixes nothing, and the documented setter exists for exactly this case. The command line is public, unmarked and tested upstream, and ships in 11.0, where an index carried over from 9.x or 10.x is a documented, supported index state; failing on it is not a research trade-off. IndexMergeTool and MultiPassIndexSplitter write a new index elsewhere, where stamping the current major is arguable; this tool overwrites the user's index in place, whose creation version main says never changes. Verdict: a defect. Residual risk: a maintainer may prefer to document the limit (option C).

Suggested fix

#

Recommended Keep the source's created major and soft-deletes field in the rewrite's config (validated)

In reorderIndexDirectory, give the rewrite's config the source's created major (from the latest commit) and, if the index has one, its soft-deletes field (+8 lines). The test then passes with assertions on and off, TestBpVectorReorderer passes 8 of 8, all 317 lucene/misc tests pass, and a real 10.5.2 index is reordered keeping created major 10.

// addIndexes only accepts segments of the index's own created major, and checks the
// soft-deletes field: keep both from the index being rewritten
iwc.setIndexCreatedVersionMajor(
    SegmentInfos.readLatestCommit(directory).getIndexCreatedVersionMajor());
String softDeletesField = FieldInfos.getMergedFieldInfos(reader).getSoftDeletesField();
if (softDeletesField != null) {
  iwc.setSoftDeletesField(softDeletesField);
}

Keep the source's created major and soft-deletes field in the rewrite's config (validated) (recommended)

#

In reorderIndexDirectory, after setOpenMode(CREATE), set the config's created major to the one recorded in the index's latest commit, and its soft-deletes field to the one recorded in the index's field infos, if any (+8 lines and two imports in BpVectorReorderer.java; the hunt's fix sketch). It carries over only these two settings: commit user data, a parent field and an index sort are still not carried over (the parent field deliberately, see below; the other two behave as today and are not claimed).

// addIndexes only accepts segments of the index's own created major, and checks the
// soft-deletes field: keep both from the index being rewritten
iwc.setIndexCreatedVersionMajor(
    SegmentInfos.readLatestCommit(directory).getIndexCreatedVersionMajor());
String softDeletesField = FieldInfos.getMergedFieldInfos(reader).getSoftDeletesField();
if (softDeletesField != null) {
  iwc.setSoftDeletesField(softDeletesField);
}

Trade-offs

  • The success path for indexes created by the running major is unchanged.
  • The rewritten index keeps its created major, as IndexUpgrader does, so it stops being openable when MIN_SUPPORTED_MAJOR is later raised, exactly like the original (the note on setIndexCreatedVersionMajor).
  • readLatestCommit re-reads segments_N; it is the commit the reader just opened unless another writer commits in between (the tool assumes none). Reading the reader's own commit, SegmentInfos.readCommit(directory, ((DirectoryReader) reader).getIndexCommit().getSegmentsFileName()), closes even that window (not built).
  • Parent-field indexes are still refused ("this IndexWriter has no parent document field configured"); that is arguably right, because the tool does not keep document blocks (LFV-093), so the fix deliberately does not copy the parent field.
  • It does not fix LFV-1022: a failed run still commits an empty index. Land both; each fix alone leaves the other bug's test failing (LFV-1022's fix alone: this test still fails; this fix alone: LFV-1022's test still fails, 10 documents expected, 0 found).
  • Open PR #15430 moves the class to core with this method unchanged; if it merges first, the fix moves with it.

What the checks validated

Gradle, fresh scratch worktree at 645d4fe14a20, JDK 25, seed 5EED1023: without the fix the test fails (assertions on and off); with it TestBpVectorReorderEarlierMajorIndex + TestBpVectorReorderer pass 9 of 9 with assertions on and again with -Ptests.asserts=false, and :lucene:misc:test passes 24 suites, 317 tests, 0 failures (9 skipped by the test framework). Standalone runner: the test passes with -ea and -da; indexes written by the real 10.5.2 and 9.12.3 jars are reordered keeping created major 10 / 9 and all 10 documents; the soft-deletes index keeps its 11 documents; the default-options command line on a 10.5.2 index exits 0 with 10 documents, created major 10.

Read both values from the opened reader (not built)

#

Take the created major from reader.leaves().get(0).reader().getMetaData().createdVersionMajor() instead of re-reading segments_N.

Trade-offs

Same behaviour, but needs a special case for an empty index (no segments).

Refuse with a clear message before touching the index (not built)

#

Check the created major and the soft-deletes field before opening the writer, and refuse with "reindex with the current major first".

Trade-offs

Documents the limit instead of removing it: still no reorder for any index from an earlier major. It never opens the CREATE writer for these inputs, so it also avoids LFV-1022's wipe for them.

How it was found

#

While testing how the same tool handles a failed run, the hunt read the rewrite's writer config against IndexWriter's addIndexes checks, then ran ordinary indexes through the stock command line: one from an earlier major, one with soft deletes and a control, then indexes written by the real 9.12.3 and 10.5.2 jars. Code reading confirmed by execution.

The method in full117 words

Method: code reading confirmed by execution (non-formal tier: the first signal was code reading, not a model).

  • The hunt unit was testing the failure atomicity of the tool's in-place rewrite (the sibling bug LFV-1022). One leg of its harness ran config-only natural inputs through the stock command line: an index with an earlier created major, a soft-deletes index, a parent-field index and a control. Only users of the lucene/misc BpVectorReorderer command line (BpVectorReorderer.main) on unreleased main and branch_11x are hit, but on its normal input: every run on an index created by 9.x or 10.x, which main opens and writes (MIN_SUPPORTED_MAJOR = 9), even one written with default settings, and every run on an index with a soft-deletes field fails at the first addIndexes with IllegalArgumentException, with -ea and -da and no scale or timing condition, so the tool cannot reorder such an index at all; once 11.0 ships, every existing index was created before 11. Today the exception also wipes the index, which is counted in LFV-1022, not here. The no-noise gate (2026-10-29) reclassified it from crash to minor, consistent with the same bug class at other fix sites (LFV-618 MultiPassIndexSplitter, LFV-695 IndexRearranger, both minor): the tool fails loudly with a clear IllegalArgumentException and the data loss that accompanies it today is counted in LFV-1022.
Summary
You run BpVectorReorderer.main(path, field) on an index written by Lucene 10.x or 9.x, or on any index that has a soft-deletes field, and expect it to reorder the vectors in place: its javadoc takes 'a path containing an index to reorder', and on main indexes created with 9.x and 10.x 'remain fully supported (open and write)'. Instead reorderIndexDirectory opens a new IndexWriter with new IndexWriterConfig() and OpenMode.CREATE, which records created major 11 and no soft-deletes field, so the first addIndexes(SortingCodecReader.wrap(leaf, ...)) throws IllegalArgumentException 'Cannot merge a segment that has been created with major version 10 into this index which has been created by major version 11' (branch_11x; on main, 12.0.0-SNAPSHOT since #16942, the numbers are 11 and 12) (or 'soft-deletes field is not configured in IWC'). The javadoc of IndexWriterConfig.setIndexCreatedVersionMajor names exactly this addIndexes restriction and its remedy (use the source's created major), which the tool does not apply.
