A failed open of a persistent Monitor leaves its query index write-locked until the JVM restarts

If opening a persistent Monitor fails after it built its internal IndexWriter (say, a stored query no longer parses), the writer is never closed. Every later writable open of that index in the same JVM then fails with LockObtainFailedException, in every release checked since 8.2.0.

The finding in 30 seconds

#

The constructor takes the write lock first, then does more work, and has no cleanup if that work fails.

Background: the Monitor's query index and its lock

#
  1. Lucene's monitor module matches documents against many stored queries. A persistent Monitor keeps those queries in a small Lucene index on disk, written by an internal IndexWriter that it creates when it opens and closes in close(). When it opens an existing index, it re-parses every stored query string with your MonitorQuerySerializer.
  2. An IndexWriter holds the directory's write.lock until it is closed. With FSDirectory's default NativeFSLockFactory, the JVM also records held locks in a static set, so a second writer on the same directory in the same JVM fails at once with LockObtainFailedException.
  3. When a Java constructor throws, the caller receives no object. Only the constructor itself can release what it already acquired.

The finding, step by step

#
  1. Open a persistent Monitor (setIndexPath), register 1 query (f:a) and close it. Reopen it with a parser that rejects the stored string, as after a parser change between two versions of your application.
  2. That open throws IllegalStateException: Couldn't parse some queries from the index, as it should. But its constructor had already built an IndexWriter, which holds the index's write.lock.
  3. You switch back to the working parser and retry in the same JVM. You expect the index to open with its 1 query: a constructor that throws must release what it took, as IndexWriter's own constructor does.
  4. Instead the retry, and all 200 retries in a probe, fail with LockObtainFailedException: Lock held by this virtual machine. The lock stays recorded as held in this JVM until it restarts, even after the unreachable writer is garbage-collected.
  5. Nothing is lost: the index on disk is intact and a read-only Monitor on it still matches correctly. An I/O error while opening, a missing serializer or setPurgeFrequency(0, ...) leak the lock the same way.

Who is affected

#

Users of the optional monitor module with a query index on disk (setIndexPath or setDirectoryProvider; the default Monitor is in memory) whose open fails and who retry in the same JVM, for example a service that reloads its configuration. Writable reopens of that index fail until a restart; nothing on disk is lost, and the leak is bounded per path.

Mechanism, terms and numbers697 words

new Monitor(analyzer, config) with a query index on disk (MonitorConfiguration.setIndexPath or setDirectoryProvider) builds a WritableQueryIndex. Its constructor first builds an IndexWriter (WritableQueryIndex.java:77), which takes the index's write.lock, and only then opens a SearcherManager (:79), re-parses every stored query (:83) and schedules the purge task (:85-98). Nothing after :77 is inside a try, so when any of those steps throws, the constructor throws with the writer still open. The caller gets no Monitor, so close(), the only release (:322-325), can never run, and NativeFSLockFactory keeps the lock in a static JVM-wide set until the lock is closed. With that default lock factory, every later writable Monitor on that path in the JVM then fails with LockObtainFailedException ("Lock held by this virtual machine"), even with a correct configuration. Four triggers were executed: stored queries the current parser rejects, a non-empty index opened without a serializer, an I/O error while the index opens, and setPurgeFrequency(0, ...). Nothing on disk is lost, and read-only Monitors and other paths keep working. IndexWriter's own constructor releases its lock on any failure; this one never did. Reproduced on nine releases from 8.2.0 to 10.6.0 and on main; garbage collection frees the writer but not the JVM's record of the lock. Low priority: it needs a failed open of an opt-in persistent Monitor and a retry in the same JVM.

  1. MonitorConfiguration.buildIndexWriter() (MonitorConfiguration.java:93-95) returns new IndexWriter(directoryProvider.get(), ...); setIndexPath opens a fresh FSDirectory for each Monitor (:87-91). IndexWriter obtains write.lock (IndexWriter.java:954). If IndexWriter's own constructor fails, it releases the lock itself (IndexWriter.java:1202-1209, "init: hit exception on init; releasing write lock").
  2. Every exception after :77 escapes with the writer open. Four triggers, each executed:
    • I/O error while the SearcherManager opens the index (:79), with a correct serializer and parseable queries (a FilterDirectory that throws on the doc-values file).
    • setPurgeFrequency(0, ...): MonitorConfiguration.java:130-134 stores any value without validation, and scheduleAtFixedRate throws IllegalArgumentException for a period <= 0, even on an empty index.
    • Stored queries the serializer rejects: populateQueryCache collects every parse error and throws IllegalStateException("Couldn't parse some queries from the index") (:173-180). This is the minimal repro.
    • A non-empty index with no serializer: IllegalStateException("Attempting to open a non-empty monitor query index with no MonitorQuerySerializer") (:139-150; non-empty means at least one live query document).
  3. The exception leaves Monitor's constructor too (Monitor.java:87-99). The only releases, WritableQueryIndex.close() (:322-325: shut the executor down, then close the manager, the writer and the directory) and Monitor.close() (Monitor.java:142-145), belong to objects the caller never received.
  4. NativeFSLockFactory adds the lock path to its static LOCK_HELD set when it obtains the lock (NativeFSLockFactory.java:68, :108) and removes it only when that lock is closed (:145-150); a later attempt throws "Lock held by this virtual machine" (:119). Garbage collection does not help: it frees the unreachable writer and closes its lock file channel, but the path stays in LOCK_HELD, so the retry still fails (an independent verifier's test, five System.gc() rounds; a later probe, ten rounds, with a weak reference showing the writer was collected). One undocumented workaround: subclass MonitorConfiguration, override the public buildIndexWriter() to keep the writer, and close it yourself. Another, also undocumented and executed: a setDirectoryProvider whose FilterDirectory records the Lock from obtainLock; closing that Lock after the failed open lets the retry open with its 1 query, but it releases only the lock, not the writer or its reader.

By reading only, not claimed: the default in-memory Monitor (MonitorConfiguration.java:41, a new ByteBuffersDirectory per open) shows no lock error, because every open gets its own directory.

Exposure and likelihood280 words
  • Who. Applications of the optional lucene-monitor module that keep the query index on disk. This is opt-in: "By default, Monitor instances are ephemeral, storing their query indexes in memory" (package-info.java:99-100).
  • When. An open fails (most realistically an I/O error, or stored queries that a new version of the application's parser no longer accepts) and the application then retries or reopens in the same JVM instead of exiting: a long-running service that reloads its configuration, falls back to a lenient parser, or opens the index writable to delete the bad query; or a test suite. A startup failure followed by a process restart never sees it. Likelihood is rated rare: no report since 8.2.0 (2019).
  • What goes wrong (executed probe on main with assertions on and off, 10.5.2 and 9.12.3): every writable open of that path fails until the JVM restarts; 200 retries all failed and added 0 file descriptors. The message says the lock is held, not why, so it looks like a second writer the application does not have. Each failed open leaves an unreachable IndexWriter with its lock file channel and, except for the I/O-error trigger (where new SearcherManager itself throws), a SearcherManager with its reader. Garbage collection frees the writer and closes the channel, but the path stays recorded as locked in the JVM, and the reader's index-file mapping stays (seen for the parser trigger), until a restart.
  • What it does not do (same probe): nothing on disk is lost or corrupted (a plain DirectoryReader sees all 3 stored queries); a read-only Monitor on the same path loads all 3 and matches exactly the right ones; Monitors on other paths and in-memory Monitors keep working.

Why it looks unintended

#
  • IndexWriter's own constructor releases its write lock on any failure; upstream fixed that same symptom there in 2010 (LUCENE-2476).
  • The package docs describe reloading a persistent index "by a new Monitor instance"; the failing retry does exactly that.
  • Two triggers break no precondition: an I/O error while opening, and setPurgeFrequency(0, ...), which is accepted unchecked.
The full argument193 words
  • The codebase rule. IndexWriter's constructor catches any Throwable, including configuration it rejects, and releases its lock (IndexWriter.java:1202-1209). It was added as a bug fix: LUCENE-2476, "release write lock on any exception during IndexWriter ctor" (2010).
  • Ownership. WritableQueryIndex.close() releases exactly what the constructor acquires (executor, searcher manager, writer, directory; WritableQueryIndex.java:322-325). A caller of a failed constructor has no object to close and no unlock API.
  • The documented use is reopening. package-info.java:104-107: stored queries must "be re-parsed by the associated MonitorQuerySerializer when the index is loaded by a new Monitor instance".
  • Two triggers break no precondition. An I/O error is an ordinary failure the constructor declares; setPurgeFrequency documents only "the frequency value" and accepts 0 (MonitorConfiguration.java:123-134).
  • Nothing says otherwise. No javadoc, test, CHANGES.txt or MIGRATE.md entry says a failed open keeps the lock; the upstream monitor tests never retry after a failed open, and their purge tests use only positive frequencies. The two IllegalStateException messages are code-level validation errors, in no javadoc and no upstream test. The constructor shape came with the module (LUCENE-8766, 2019) and survived the 2022 refactor (LUCENE-10422) without any discussion of failure cleanup.
The devil's-advocate check191 words

The strongest "works as intended" case (built by a devil's-advocate verifier and by cross-model reviews, OpenAI GPT-5.6): the package docs make re-parseability of stored queries the application's job, so the parser and null-serializer triggers start from an application error; scheduleAtFixedRate documents IllegalArgumentException for a non-positive period, so 0 is invalid configuration; no javadoc promises that a failed Monitor construction can be retried; Closeable covers only constructed objects; the lock exists to stop two writers; and a restart clears it.

Why it fails: those points justify the first exception, not keeping a native lock on a writer nobody can reach. IndexWriter releases its lock even for configuration it rejects; the I/O-error trigger breaks no precondition at all (it is the strongest case; the parser and null-serializer triggers do start from an application error); the "second writer" is unreachable garbage, and even once garbage collection frees it the JVM still records the lock as held; and a restart is a workaround. The devil's-advocate verifier rated "not intended" high; the earlier cross-model reviews rated the intended argument moderate; a later cross-model review that ran its own repro rated the bug real with high confidence.

Suggested fix

#

Recommended A. try/catch (Throwable) after buildIndexWriter(): shut the executor down, close the manager, roll back the writer, close the directory, rethrow

Wrap everything after buildIndexWriter() in WritableQueryIndex's constructor in try/catch (Throwable): shut the purge executor down if created, close the searcher manager, roll back the writer, close the directory, rethrow (+14/-3 ignoring whitespace). The repro, the monitor module's 182 tests, lint and all four triggers pass.

this.writer = configuration.buildIndexWriter();
ScheduledExecutorService executor = null;
try {
  // ... SearcherManager, populateQueryCache: unchanged ...
  executor = Executors.newSingleThreadScheduledExecutor(new NamedThreadFactory("cache-purge"));
  executor.scheduleAtFixedRate(/* unchanged arguments */);
  this.purgeExecutor = executor;
} catch (Throwable t) {
  if (executor != null) {
    executor.shutdown();
  }
  IOUtils.closeWhileSuppressingExceptions(t, manager, writer::rollback, writer.getDirectory());
  throw t;
}

Option A was run through gradle in a scratch worktree of 645d4fe14a20, and against the other three triggers' tests. A. try/catch (Throwable) after buildIndexWriter(): shut the executor down, close the manager, roll back the writer, close the directory, rethrow (validated by the checks) (recommended)

#

In WritableQueryIndex.java:77-98: the rest of the constructor moves, unchanged and re-indented, into the try; the executor goes through a local because a blank final field cannot be read in the catch. Ignoring whitespace the change is +14/-3.

this.writer = configuration.buildIndexWriter();
ScheduledExecutorService executor = null;
try {
  // ... SearcherManager, populateQueryCache: unchanged ...
  executor = Executors.newSingleThreadScheduledExecutor(new NamedThreadFactory("cache-purge"));
  executor.scheduleAtFixedRate(/* unchanged arguments */);
  this.purgeExecutor = executor;
} catch (Throwable t) {
  if (executor != null) {
    executor.shutdown();
  }
  IOUtils.closeWhileSuppressingExceptions(t, manager, writer::rollback, writer.getDirectory());
  throw t;
}

Trade-offs

  • Covers all four triggers, because the guarded region includes the executor creation and scheduling.
  • Roll back, not close: IndexWriter.close() commits by default (IndexWriter.java:1363-1369); rollback() commits nothing, so a failed open leaves the index as it was (a failed first open of an empty directory creates no commit).
  • Same resources and order as close() (WritableQueryIndex.java:322-325). Like close(), it closes the directory the provider returned; for a setDirectoryProvider that hands out a shared Directory that is the existing ownership rule, but a caller who retries with that same instance would then find it closed (the provider API does not say who owns the directory when the open fails).
  • The original exception is rethrown, with any cleanup failure suppressed into it, the same idiom as IndexWriter.java:1202-1209; only if a cleanup step throws an Error (and the original is not one) does the helper throw that Error instead, with the original suppressed (IOUtils.java:116-136). The helper exists from 10.4.0 on; a 9.x backport would use IOUtils.closeWhileHandlingException (not run).

What the checks validated

  • Stock 645d4fe14a20: the repro fails with assertions on and off.
  • With the fix: the repro plus TestMonitorPersistence, TestMonitorReadonly and TestCachePurging pass with assertions on and off (4 suites, 15 tests, 0 failures); the whole :lucene:monitor:test passes with assertions on (33 suites, 182 tests, 0 failures, 1 skipped); checkGoogleJavaFormat, ecjLintMain, ecjLintTest, forbiddenApisMain and forbiddenApisTest pass.
  • The other triggers, against the built main jars with the fixed class shadowed: the purge-frequency-0 check (stock fails, fixed passes), the I/O-error and garbage-collection tests (stock 2 fail, control passes; fixed 3 of 3), the null-serializer and rejected-query tests (stock 2 fail; fixed 2 of 2); no leaked-file report with the fix.

B. Validate the purge frequency before acquiring anything (complement, not run)

#

Reject frequency <= 0 in MonitorConfiguration.setPurgeFrequency (or at the start of the constructor) with a clear message.

Trade-offs

  • Covers only the purge-frequency trigger and gives a better error; the other three still need A. Open issue #11710 asks for a way to disable the scheduled purge, so maintainers may prefer 0 to mean "disabled".

C. Guard only the searcher manager and populateQueryCache (the first fix draft; not recommended)

#

try/finally around SearcherManager creation and populateQueryCache, with IOUtils.closeWhileHandlingException(manager, writer, writer.getDirectory()) on failure.

Trade-offs

  • Passes the minimal repro, but stops before the executor, so setPurgeFrequency(0, ...) still leaks the lock with it (executed twice, by reviewers); it also closes the writer, which commits by default (commitOnClose), instead of rolling it back.

Downstream note

#

A read-only code search found no use of the monitor module in Elasticsearch, OpenSearch or Solr (an open Solr PR proposes adding it), so the exposure is mainly applications that embed lucene-monitor directly.

How it was found

#

Found by reading the serializer error path while building model-based tests of the Monitor's persistence lifecycle; those tests never retried after a failed open, so they did not hit it themselves. A JUnit test on the stock jars then confirmed the lock leak.

The method in full109 words

Method: code reading (non-formal), in a hunt unit on the monitor module's lifecycle and persistence whose secondary focus was serializer edge cases, such as a serializer that throws on one query.

  • While modelling the persistence lifecycle for operation-level model-based tests, the finder read the constructor's serializer error path and saw that nothing closes the writer built before it.
  • A public-API JUnit test (null serializer; a parser that rejects the stored string, then a retry) failed 2 of 2 on main with assertions on and off, 10.5.2 and 9.12.3.
  • Independent verifiers added the I/O-error trigger and the purge-frequency trigger; the latter showed the first fix draft was too narrow.

LFV-507, snapshot of 2026-11-06

Registry title
When opening a persistent Monitor fails after its query index has built the IndexWriter (stored queries the serializer cannot parse, no serializer for a non-empty index, an I/O error, or a purge frequency of 0), the writer and its write lock are never released, so the same index cannot be opened for writing again in that JVM
Area
monitor / persistent query index (WritableQueryIndex construction, failure cleanup)
Priority
Low, rank 1082: A failed persistent Monitor open leaks the write lock so same-JVM retries fail until restart, but it needs a failed open of an opt-in persistent Monitor.
Impact class
crash
Impact note
Applications of the optional lucene/monitor module that keep their query index on disk (setIndexPath or setDirectoryProvider, opt-in: the default Monitor is in memory) and retry or reopen in the same JVM after a failed open (stored query strings the current serializer rejects, for example after a parser change between application versions; a null serializer on a non-empty index; an I/O error while the query index opens; or setPurgeFrequency(0, ...)) get LockObtainFailedException 'Lock held by this virtual machine' on every writable open of that path until the JVM restarts, with one IndexWriter, one SearcherManager with its reader and one write.lock file channel leaked per failed path; the index on disk is intact, a read-only Monitor on the same path and Monitors on other paths keep working, 200 further retries leaked nothing more [exec], and no scale is needed.
Summary
You open a persistent Monitor (MonitorConfiguration.setIndexPath) and the open fails after the query index has built its IndexWriter, for example because a stored query no longer parses with the current parser (IllegalStateException 'Couldn't parse some queries from the index'), because no serializer was given for a non-empty index, or because of an I/O error while the index opens. You expect the failed constructor to release what it acquired, as IndexWriter's own constructor does for its write lock, so that you can fix the parser or the configuration and open the index again. Instead the IndexWriter, its SearcherManager and the write lock stay open with no object left to close them, so every later writable Monitor on that path in the same JVM fails with LockObtainFailedException 'Lock held by this virtual machine', even with a correct serializer, until the JVM restarts.
