TermInSetQuery.equals ignores the rewrite method, so set queries that match different documents compare equal and IndexWriter drops one of two such deletes

Two TermInSetQuery objects with the same field and terms compare equal even when their rewrite methods make them match different documents. IndexWriter.deleteDocuments then runs only one of them: deleting a doc-values-only document with a postings set query plus newSlowSetQuery leaves it live (1 document, expected 0).

The finding in 30 seconds

#

A set query can run on postings, on doc values, or keep only its top terms. That choice, its rewrite method, can change which documents match, but equality ignores it.

Set queries and their rewrite method

#
  1. new TermInSetQuery("f", terms) matches documents whose field f has any of the terms. Since 9.6.0 it is a MultiTermQuery, and its rewrite method decides how it runs: on the inverted index (postings, the default), on doc values (DOC_VALUES_REWRITE), or keeping only the top N terms.
  2. SortedSetDocValuesField.newSlowSetQuery("f", terms) is the doc-values variant: a TermInSetQuery with DOC_VALUES_REWRITE. Its javadoc suggests using it next to the postings TermInSetQuery, inside an IndexOrDocValuesQuery.
  3. Lucene compares queries with equals and hashCode wherever it de-duplicates or caches them. IndexWriter keeps buffered delete-by-query calls in a HashMap keyed by the query until they are applied, for example at a flush, an NRT reopen or a commit.

The finding, step by step

#
  1. You index one document whose field f has only a doc value, SortedSetDocValuesField("f", "a"), with the default IndexWriterConfig.
  2. You call deleteDocuments(new TermInSetQuery("f", [a]), SortedSetDocValuesField.newSlowSetQuery("f", [a])). The first query reads postings and matches 0 documents (f has none); the second reads doc values and matches 1.
  3. You expect 0 live documents: deleteDocuments deletes "the document(s) matching any of the provided queries".
  4. You get 1. The two queries compare equal, because TermInSetQuery.equals and hashCode look only at the field and terms, not at the rewrite method that decides how the query runs. IndexWriter buffers deletes in a HashMap keyed by query, so it keeps the first query and runs only that one.
  5. No error, and the result is committed. Two separate calls collide the same way when nothing applies the buffered deletes in between, and so do a top-terms rewrite (2 vs 1 matching documents) and any cache keyed on un-rewritten queries. Lucene's own query cache is not affected.

Who is affected

#

Applications passing two set queries with the same field and terms but different rewrite methods to deleteDocuments before the deletes are applied, or to their own query-keyed cache or the monitor module, when the two select different documents: a doc-values-only field, a field missing postings, or a top-terms rewrite. Default configuration; Lucene's search path is not affected; rare in practice.

Mechanism, terms and numbers724 words

Since 9.6.0 TermInSetQuery is a MultiTermQuery, and its rewrite method decides how it runs: on postings (the default), on doc values (DOC_VALUES_REWRITE, which SortedSetDocValuesField.newSlowSetQuery returns), or keeping only the top N terms. MultiTermQuery#equals and hashCode compare the rewrite method, but TermInSetQuery overrides both with a 2017 version that compares only the packed field and terms. So queries that match different documents compare equal: on a field with only doc values, new TermInSetQuery("f", [a]) and newSlowSetQuery("f", [a]) match 0 and 1 documents; on an ordinary field, new TermInSetQuery("f", [a, b]) and its TopTermsScoringBooleanQueryRewrite(1) variant match 2 and 1. Anything keyed on the un-rewritten query treats each pair as one. The main case inside Lucene is IndexWriter's delete-by-query buffer, a HashMap<Query, Integer> that keeps the first of two equal keys: with the default IndexWriterConfig, deleteDocuments with both doc-values-case queries leaves the document live, and in the other order a document added between two calls is deleted although no call matched it. The monitor module's QueryDecomposer also merges such a pair of disjuncts, so with presearcher filtering off a doc-values-only match is missed. Lucene's search path is not affected, because it compares rewritten queries. Affected: 9.6.0 to 10.6.0 and main; the fix is to delegate to MultiTermQuery#equals/hashCode, as the other core subclasses do.

The bug (main 645d4fe14a20)

#
  1. The rewrite method decides what matches. TermInSetQuery extends MultiTermQuery (TermInSetQuery.java:73) and has a public TermInSetQuery(RewriteMethod, String, Collection<BytesRef>) constructor (:87-92); the class javadoc invites custom rewrite methods "to define different execution behavior, such as relying on doc values ... or if scores are required" (:65-69). MultiTermQuery#rewrite is final: return rewriteMethod.rewrite(indexSearcher, this); (MultiTermQuery.java:325-327).
  2. The parent compares it, the subclass does not. MultiTermQuery#equals/hashCode include rewriteMethod and field (MultiTermQuery.java:336-352). TermInSetQuery overrides both: equals is sameClassAs(other) && equalsTo(...), equalsTo compares termDataHashCode and termData only, and hashCode is 31 * classHash() + termDataHashCode (TermInSetQuery.java:203-217). It never calls the parent. Every other concrete MultiTermQuery outside sandbox (AutomatonQuery, so WildcardQuery and RegexpQuery, PrefixQuery, FuzzyQuery, TermRangeQuery, join TermsQuery) calls super.equals, except MultiFacetQuery (facet module), which extends TermInSetQuery and inherits its override. All of them but join TermsQuery also build hashCode on super.hashCode() (join TermsQuery.java:127-129 uses classHash()).
  3. The doc-values factory is such a query. SortedSetDocValuesField.newSlowSetQuery returns new TermInSetQuery(MultiTermQuery.DOC_VALUES_REWRITE, field, values) (SortedSetDocValuesField.java:130-132; the same in SortedDocValuesField.java:126-128). TermInSetQuery.newIndexOrDocValuesQuery (:104-110), used by KeywordField.newSetQuery, pairs a postings and a doc-values TermInSetQuery that compare equal.
  4. IndexWriter keys buffered deletes on the query. deleteDocuments(Query...) (IndexWriter.java:1883-1898) reaches the delete queue, whose QueryArrayNode.apply calls bufferedUpdates.addQuery(query, docIDUpto) for each query (DocumentsWriterDeleteQueue.java:462-472). BufferedUpdates.deleteQueries is a HashMap<Query, Integer> (BufferedUpdates.java:64); addQuery does deleteQueries.put(query, docIDUpto) (:110-116), which for an equal key keeps the first key object and replaces only its doc-id limit.
  5. Only the first query runs. FrozenBufferedUpdates copies the keys (FrozenBufferedUpdates.java:93-99) and runs each once per segment (:388-420). The postings query matches nothing on a field without postings, so the document stays live. In the other order, the stored doc-values query takes the later limit and also deletes a document added between the two calls.
  6. Search is not affected. BooleanQuery rewrites its clauses before it removes duplicate FILTER and MUST_NOT clauses (BooleanQuery.java:299-362), LRUQueryCache keys on the rewritten query (LRUQueryCache.java:834), and IndexOrDocValuesQuery.rewrite compares rewritten halves (IndexOrDocValuesQuery.java:131). In the executed cases the rewritten forms differ (different wrapper classes), so those keys stay distinct.

Exposure and likelihood373 words
  • What goes wrong. A delete that silently does not take effect, so the document stays searchable; or, in the other order, a document that no call matched is deleted. Both are committed. No error is raised.
  • Configuration. The default IndexWriterConfig, codec and NRT reader suffice. One call with both queries always collides. Two calls collide only if nothing applies the buffered deletes in between: a flush, an NRT reopen or a commit does, and so can IndexWriter itself when buffered deletes use too much heap (DocumentsWriter.java:153-166). A commit between the calls avoids it.
  • What it takes. Two TermInSetQuery objects with the same field and terms whose rewrite methods select different documents. With the documented pairing (postings TermInSetQuery next to newSlowSetQuery) that needs a field that lacks postings or doc values on the documents concerned, for example a doc-values-only field or documents indexed before a schema change. With a top-terms or scoring rewrite an ordinary field is enough.
  • Other consumers. An application cache or set keyed on un-rewritten Query objects serves one query's result for the other (an independent reproducer: a map returned 2 for the top-1 query, whose true count is 1). Wrapper equality inherits it: a BooleanQuery with a FILTER clause of either variant compares equal. The monitor module's QueryDecomposer keeps the un-rewritten clauses of a registered query in sets (QueryDecomposer.java:77-102): a BooleanQuery with both variants as SHOULD clauses decomposes into 1 part, not 2, and with Presearcher.NO_FILTERING a document whose field has only the doc value gets 0 matches where a direct search counts 1 (executed on main; with the fix 2 parts and 1 match). With the default presearcher both builds give 0, because it does not select doc-values-only fields.
  • Not affected, of the consumers checked. Lucene's search path: BooleanQuery de-duplication, LRUQueryCache and IndexOrDocValuesQuery compare rewritten queries, which differ in the executed cases (impact probes on main). MultiFacetQuery inherits the override but always uses the default rewrite method. Other in-tree code that keeps un-rewritten queries in sets or maps was not audited.
  • Likelihood. Contrived for the delete path: no caller doing this is known, and the recorded searches found no report since 9.6.0 (2023). Index size does not matter; the repro has one document.

Why it looks unintended

#
  • deleteDocuments(Query...) promises to delete "the document(s) matching any of the provided queries"; the doc-values query matches, yet the document stays.
  • MultiTermQuery.equals and hashCode include the rewrite method, and every sibling subclass's equals calls the parent's.
  • The terms-only equals predates rewrite methods (2017); the 9.6.0 change that added them left it untouched.
The full argument324 words
  • The delete contract. IndexWriter.deleteDocuments(Query...): "Deletes the document(s) matching any of the provided queries" (IndexWriter.java:1875). The repro asserts exactly this, so it needs no argument about what equals should return.
  • The equality contract. Query#equals is "required so that QueryCache works properly", and "Typically a query will be equal to another only if it's an instance of the same class and its document-filtering properties are identical to those of the other instance" (Query.java:96-107). Here they differ: 0 vs 1 and 2 vs 1 matching documents.
  • The parent and the siblings. MultiTermQuery#equals/hashCode include the rewrite method (MultiTermQuery.java:336-352), and every other concrete subclass outside sandbox calls super.equals, except MultiFacetQuery, which inherits TermInSetQuery's override (the core siblings also call super.hashCode; join TermsQuery does not). For BlendedTermQuery, a test requires two queries that differ only in their rewrite method to be unequal (TestBlendedTermQuery.java:39-49).
  • History. The terms-only equals dates from LUCENE-7624 (2017), when TermInSetQuery extends Query had no rewrite method. #12156 (9.6.0) made it a MultiTermQuery with a public rewrite-method constructor and changed no line of equals/hashCode; its discussion never mentions equality. Before #12175 (9.6.0) the doc-values set query was a separate class that never compared equal.
  • Maintainer statements and precedent. LUCENE-10431 (#11467) kept the rewrite method in MultiTermQuery#equals (9.x left it out of hashCode only, because it was mutable there). In LUCENE-7810 (#8861), a false-positive query equality fixed as a bug, Adrien Grand wrote, about taking the score mode into account in the join query's equals, that "two queries should only be equal if they matche [sic] the same docs and give them the same scores" (2017-05-16). Similar omissions were fixed as bugs: LUCENE-10026 (CombinedFieldQuery), LUCENE-10552 (KnnVectorQuery), #12260 (SynonymQuery).
  • Nothing pins the current behaviour. TestTermInSetQuery's equality tests use only the default rewrite method (TestTermInSetQuery.java:315-376); no CHANGES or MIGRATE entry describes it.
The devil's-advocate check217 words

The strongest case for "intended" (a devil's-advocate verifier and a cross-model review): the rewrite method is an execution strategy. On a field indexed with the same values in postings and doc values, the layout KeywordField and IndexOrDocValuesQuery assume, the default, doc-values and constant-score rewrites match the same documents, so treating them as equal is harmless and lets the two halves of newIndexOrDocValuesQuery compare equal. Query#equals says only "Typically"; Lucene's own consumers compare rewritten queries; and 9.x once took the rewrite method out of MultiTermQuery#hashCode (LUCENE-10431).

Why it fails: TermInSetQuery's own javadoc offers rewrite methods that change matches and scores, not only execution (top-terms(1): 2 vs 1 documents; SCORING_BOOLEAN_REWRITE: top score 1.0 vs 0.315). A doc-values-only field is a legal use of newSlowSetQuery, and there the "same documents" premise fails (1 vs 0). The deleteDocuments contract breaks however one reads "Typically". LUCENE-10431 kept the rewrite method in equals and left it out of the 9.x hashCode only because it was mutable there; on main it is final and in both. The independent reproducer, the devil's-advocate verifier and the intended-lens review returned "real" (the reading-only refute review's "not real" was procedural: it could not run Java); the adjudication confirmed with high confidence. The practical reach is narrow, so a maintainer may still rate it low priority.

Suggested fix

#

Recommended Delegate to MultiTermQuery#equals and hashCode (recommended, validated)

Let TermInSetQuery.equals and hashCode call MultiTermQuery's, as the other core subclasses do, so the rewrite method (and the field) count (+3/-3 lines). Validated: the repro passes, 2,838 core search and document tests, the monitor, facet and join modules and the core lint checks pass. On 9.x the same change keeps the mutable rewrite method out of hashCode.

@Override
public boolean equals(Object other) {
  // super.equals checks the class, the field and the rewrite method
  return super.equals(other) && equalsTo(getClass().cast(other));
}

@Override
public int hashCode() {
  return 31 * super.hashCode() + termDataHashCode;
}
All options and trade-offs3 options · 503 words

Both fixes that make equality include the rewrite method were validated through gradle in a scratch worktree of 645d4fe14a20; the recommended one is the idiomatic form. A change to the delete buffer instead was not built.

Delegate to MultiTermQuery#equals and hashCode (recommended, validated)

#

Call super.equals(other) instead of sameClassAs(other), and build hashCode on super.hashCode() instead of classHash(), as PrefixQuery, AutomatonQuery, FuzzyQuery and TermRangeQuery do. The parent checks the class, the field and the rewrite method.

@Override
public boolean equals(Object other) {
  // super.equals checks the class, the field and the rewrite method
  return super.equals(other) && equalsTo(getClass().cast(other));
}

@Override
public int hashCode() {
  return 31 * super.hashCode() + termDataHashCode;
}

Trade-offs

  • Side effect. The two halves of TermInSetQuery.newIndexOrDocValuesQuery (and so of KeywordField.newSetQuery) stop comparing equal, which restores the pre-9.6 distinction between the doc-values and the postings set query. Nothing in-tree relies on their equality; IndexOrDocValuesQuery.rewrite compares rewritten halves, which already differ.
  • Cost. One extra rewrite-method and field comparison per equals, before the term data. The built-in rewrite methods are singletons or value-equal, so hash codes stay stable. A custom RewriteMethod without equals makes queries built with different instances unequal (cache misses only), as for every other MultiTermQuery today.
  • 9.x. There MultiTermQuery#hashCode deliberately leaves out the then-mutable rewrite method while equals keeps it (LUCENE-10431), so delegating gives the right result on 9.x without a special backport (read, not run on 9.x).

Compare the rewrite method in equalsTo and hashCode (validated, equivalent)

Key the delete buffer by identity instead (not recommended, not built)

#

Make BufferedUpdates keep every delete query object (an identity map or a list).

Trade-offs

Fixes only the delete path, not application caches or wrapper equality, and loses the de-duplication of genuinely equal delete queries.

Downstream note

#

Code outside Lucene that keys caches or de-duplicating sets on un-rewritten Query objects aliases the two variants the same way and can serve one query's hits for the other; Lucene's own query cache keys on rewritten queries and is not affected.

How it was found

#

A scan of the bytecode of every concrete Lucene query class found that TermInSetQuery's equality never reads the rewrite method its rewrite() uses. A bounded-exhaustive equality harness then found equal pairs that match different documents, and a security screen found the delete-by-query consequence.

The method in full149 words

Method: semi-formal (a static field-set scan plus bounded-exhaustive testing, then public-API JUnit tests).

  • A hunt unit on query object contracts scanned the bytecode of all 142 concrete Query classes in the main jars and listed, for each class, the fields that other methods, such as rewrite(), read but equals/hashCode do not. MultiTermQuery.rewriteMethod was read by rewrite() but not by TermInSetQuery.equals/hashCode.
  • The unit's bounded-exhaustive equality-congruence harness ran small queries on small indexes and found equal TermInSetQuery pairs with different matching documents, different scores, and unequal rewritten forms. The finder reduced it to a JUnit on the public API.
  • An independent reproducer, a devil's-advocate verifier (who added the doc-values-only case), cross-model reviews (OpenAI GPT-5.6, reading only) and an adjudication checked it. The security screen then executed the IndexWriter.deleteDocuments consequence, the follow-up re-ran it with the default configuration, and the repro was minimized to one test.

History

#

Introduced by #12156 (3809106602a, 2023-03-01), which made TermInSetQuery a MultiTermQuery with rewrite methods and kept its 2017 terms-only equals; #12175 the same day made newSlowSetQuery return such a query. First released in 9.6.0; 9.6.0 to 10.6.0 and main are affected; not fixed.

Versions tested6 rows

Introduced by apache/lucene#12156, "Remove custom TermInSetQuery implementation in favor of extending MultiTermQuery" (gsmiller, merged 2023-03-01, milestone 9.6.0): main 3809106602a, 9.x fa1d050df1d. The bug is an omission: the PR changed no line of equals/equalsTo/hashCode, whose text comes from LUCENE-7624 (22940f5c492, 2017), a LUCENE-7637 comment (43874fc5b5c) and a 2020 reformat (2d6ad2fee6d).

The doc-values trigger comes from #12175 (main 569533bd76a, 9.x 5ff8ea4952a, also 2023-03-01): newSlowSetQuery became new TermInSetQuery(DOC_VALUES_REWRITE, ...). In 9.5.0 the doc-values set query was the sandbox DocValuesTermsQuery, a different class that never compared equal.

The release tags 9.6.0, 9.12.3, 10.0.0, 10.5.2 and 10.6.0 have the same equalsTo and hashCode text (the follow-up checked every tag from 9.6.0 to 10.5.2). On 9.6.0 to 9.12.3 the deprecated MultiTermQuery#setRewriteMethod is a second way to change the rewrite method. Upstream main 2f424fd428da (2026-10-30) is unchanged.

LFV-321, snapshot of 2026-11-03

Registry title
TermInSetQuery.equals/hashCode ignore the rewrite method, so set queries that match different documents compare equal, and IndexWriter's delete-by-query buffer then applies only one of them
Area
core / search: TermInSetQuery equality (MultiTermQuery rewrite methods); consequence in index / IndexWriter delete-by-query buffering
Priority
Low, rank 790: TermInSetQuery equality ignores the rewrite method and can merge two different delete-by-query calls, but only when differing rewrites select different documents within one flush window, so it heads the narrow equality rows above LFV-216.
Impact class
data corruption
Impact note
Applications that build TermInSetQuery objects for the same field and terms with different rewrite methods (most naturally new TermInSetQuery next to SortedSetDocValuesField.newSlowSetQuery, which is a DOC_VALUES_REWRITE TermInSetQuery, on a field that lacks postings or doc values on some documents, or a top-terms or scoring rewrite) and hand both to something that keys on un-rewritten queries are hit: IndexWriter.deleteDocuments(Query...) keeps only the first of the two within one flush window (executed with the default IndexWriterConfig on main -ea and -da and on 10.5.2: a delete that silently does not take effect, or a later document deleted that no call matched), and an application cache keyed on Query serves one query's result for the other; Lucene's own search-time consumers (BooleanQuery clause de-duplication, LRUQueryCache) compare rewritten queries and are not affected; ordinary scale; released 9.6.0 to 10.6.0.
Summary
Since 9.6.0 TermInSetQuery is a MultiTermQuery whose rewrite method decides which documents it matches and how it scores, but its equals/hashCode still compare only the field and terms: new TermInSetQuery("f", [a]) equals SortedSetDocValuesField.newSlowSetQuery("f", [a]) although on a field with only doc values they match 0 and 1 documents, and on an ordinary field new TermInSetQuery("f", [a, b]) equals its TopTermsScoringBooleanQueryRewrite(1) variant although they match 2 and 1 documents. You expect queries that match different documents to be unequal, as PrefixQuery, AutomatonQuery, FuzzyQuery and TermRangeQuery are when only the rewrite method differs. Instead anything keyed on the un-rewritten query treats the two as one: IndexWriter.deleteDocuments with both queries in one flush window applies only the first, so a doc-values delete silently does not happen, or a document added in between is deleted although no call matched it.
