SolrSynonymParser rejects a whole synonyms file when one line holds only spaces or tabs

A Solr-format synonyms file is rejected as a whole, with ParseException: Invalid synonym rule at line 2, when a "blank" line holds a few spaces or a tab, although the parser's javadoc says blank lines are comments. Only a truly empty line is skipped; every release since 3.4.0 does this.

The finding in 30 seconds

#

Background: the Solr synonyms format

#
  1. A synonyms file holds one rule per line: couch, sofa makes the words equivalent, i-pod => ipod maps one side to the other.
  2. The parser trims each term and runs it through an analyzer. A term that leaves no word is an error, and one bad line rejects the whole file.
  3. The class javadoc lists, as rule 1 of the format: "Blank lines and lines starting with '#' are comments."

The finding, step by step

#
  1. Write a synonyms file of three lines: couch, sofa, a line of three spaces, and big, large. Load it with SolrSynonymParser, or with SynonymGraphFilterFactory, whose default format is this one.
  2. You expect line 2 to be skipped: the javadoc says "Blank lines and lines starting with '#' are comments." With an empty line 2 the file loads and gives 2 rules.
  3. Instead the parser skips a line only when its length is 0. Line 2 has length 3, so it is read as a rule; its single term trims to an empty string, and the analyzer turns that into no word at all.
  4. The whole file is rejected: ParseException: Invalid synonym rule at line 2, caused by term: was completely eliminated by analyzer (the factory reports IOException: Error parsing synonyms file:). The analyzer cannot be built until the spaces are deleted.

Who is affected

#

Anyone who loads Solr-format synonyms, the default format of SynonymGraphFilterFactory and the deprecated SynonymFilterFactory (also through CustomAnalyzer), or calls SolrSynonymParser directly, from a file with a line of only spaces or tabs, for example left by an editor. Through the factories it fails loudly when the analyzer is built and names the line; no wrong results.

Mechanism, terms and numbers484 words

SolrSynonymParser, the default parser of SynonymGraphFilterFactory and SynonymFilterFactory, documents that "Blank lines and lines starting with '#' are comments", but it skips a line only when it has zero length. A line of only spaces or tabs is parsed as a rule whose single term trims to the empty string; the analyzer leaves nothing of it, and the whole file is rejected with ParseException: Invalid synonym rule at line N (the factories wrap it in IOException: Error parsing synonyms file:). Through the factories it fails loudly when the analyzer is built and names the line; nothing goes silently wrong. The pre-3.4 Solr loader of the same format, and Lucene's WordlistLoader today, skip such lines. Every release from 3.4.0 to 10.6.0 and main is affected; the fix is one line.

Terms

#
  • SolrSynonymParser: reads the Solr synonyms format into a SynonymMap for SynonymGraphFilter. SynonymGraphFilterFactory and the deprecated SynonymFilterFactory use it when format is missing or solr (the default), and analyze rule terms with a WhitespaceTokenizer unless a tokenizer or analyzer is configured.
  • Blank line: the javadoc does not define it. Lucene's WordlistLoader uses the word for lines that are empty after trim(), and so did the Solr loader that read this format before 3.4.

The bug

#
  1. addInternal skips a line only if line.length() == 0 || line.charAt(0) == '#' (SolrSynonymParser.java:85-86, comment "ignore empty lines and comments").
  2. For the line " ", split(line, "=>") gives one side, so it takes the equivalent-synonyms branch; split(line, ",") gives [" "], and analyze(unescape(...).trim(), ...) analyzes "" (:90-91, :114-117).
  3. SynonymMap.Parser.analyze throws IllegalArgumentException("term: was completely eliminated by analyzer") when no characters are left (SynonymMap.java:374-377), or "analyzed to a zero-length token" for a tokenizer that emits one empty token (:349-352). In the hunt's security probe the line was rejected in all 48 combinations of WhitespaceAnalyzer, StandardAnalyzer, KeywordAnalyzer, SimpleAnalyzer, expand on/off and six blank forms. Only an analyzer that emits a non-empty token for empty input accepts such a line (executed with a custom one).
  4. parse() turns it into ParseException("Invalid synonym rule at line 2") (:72-76); the factories wrap that in IOException("Error parsing synonyms file:") (SynonymGraphFilterFactory.java:162-163, SynonymFilterFactory.java:165-166). Through the factories no map is built, so every rule in the file is lost. A direct caller that catches the ParseException and calls build() anyway gets only the rules before the line (executed).

  • Who is hit. Callers of SolrSynonymParser.parse, and users of SynonymGraphFilterFactory or SynonymFilterFactory with the default format, directly or through CustomAnalyzer and configurations that name the factories. Such a line is easy to produce: an auto-indented separator line, whitespace left on an otherwise empty line, a last line holding a space (trailing whitespace after a rule is harmless: every term is trimmed).
  • Default vs opt-in. The synonym filter is in no stock Analyzer; within it, the bug needs only defaults (format solr). SolrSynonymParser and SynonymGraphFilterFactory carry @lucene.experimental.
  • Scale. None: one whitespace-only line anywhere in the file.
  • Visibility. Loud and early: through the factories the analyzer is not built, the error names the line, and nothing is indexed or searched with a partial map (only a direct caller that ignores the exception and builds anyway could get one). The message is misleading: an "invalid synonym rule" with an empty term: for a line that holds no rule.
  • Severity. Low: a wrong error; through the factories no wrong results and no index damage; deleting the whitespace works around it.

Why it looks unintended

#
  • Javadoc: "Blank lines ... are comments." Lucene's WordlistLoader also treats a line of spaces as blank: it trims, then skips it.
  • The pre-3.4 Solr loader of this format skipped such lines; the 3.4 rewrite dropped that silently.
  • Such a line holds no rule and fails under every analyzer tried, so skipping it changes no file that parses today with them.
The full argument216 words
  • Javadoc (SolrSynonymParser.java:33): "Blank lines and lines starting with '#' are comments."
  • Lucene's own word for it. WordlistLoader "adds every non-blank line ... (omitting leading and trailing whitespace)" and does word = word.trim(); // skip blank lines (WordlistLoader.java:43-44, :56-58; also :107, :123-124, :294, :307-308). TestWordlistLoader.testGetLines feeds a line holding one space and expects it skipped. GITHUB#12291, "Skip blank lines from stopwords list", is listed under Bug Fixes in 9.7.0.
  • The format's previous loader. Solr's SolrResourceLoader.getLines, which read synonyms files before 3.4, did if (word.startsWith("#")) continue;, then word=word.trim();, then // skip blank lines. LUCENE-3233 created SolrSynonymParser to parse "the existing solr synonyms format"; its thread lists the known differences as "deduping rules, lowercasing" and never mentions blank lines. In the 4.0.0 jar the kept pre-3.4 loader (luceneMatchVersion=LUCENE_33) accepts the file, while LUCENE_34 and LUCENE_40 reject it.
  • No test asserts the rejection: no test in the analysis-common module uses a whitespace-only line either way.
  • No file that parses today with the analyzers tried changes: with them such a line is rejected in every combination tried. Only an analyzer that emits a token for empty input lets it parse (executed with a custom one); for it, the fix would drop a one-term rule.
The devil's-advocate check189 words

The strongest case for "intended" (an intended-behaviour devil's advocate, and a reviewer from another model family, OpenAI GPT-5.6, who rated it "moderate"): the inline comment says "ignore empty lines" (:86); the comment check is literal too, so # x is a rule; the parser is strict on purpose, and upstream tests require a ParseException when the analyzer removes a term (TestSolrSynonymParser.testInvalidAnalyzesToNothingOutput / Input, inputs a => 1 and 1 => a); the class is @lucene.experimental; the behaviour is 15 years old and the error names the line.

Why it fails: those strictness tests use lines that hold a rule whose real term the analyzer removes; a whitespace-only line holds no rule, and the "term" in the error is an empty string the user never wrote. The inline comment is the only support for the narrow reading, while the public javadoc, Lucene's other line loaders and this format's own previous loader all skip trimmed-empty lines, and nothing records a decision to narrow it. These points bear on severity and on the "bug or improvement" label, not on whether the code matches the documented format.

Suggested fix

#

Recommended Skip lines that are empty after trim()

Skip lines that are empty after trim(): change line.length() == 0 to line.trim().isEmpty() in SolrSynonymParser.addInternal, the rule the pre-3.4 loader and WordlistLoader use. One line; the repro passes with assertions on and off, all 121 synonym-package tests pass, and the module's static checks pass.

-      if (line.length() == 0 || line.charAt(0) == '#') {
-        continue; // ignore empty lines and comments
+      if (line.trim().isEmpty() || line.charAt(0) == '#') {
+        continue; // ignore blank lines and comments
       }

Skip lines that are empty after trim() (validated by the checks) (recommended)

#

Matches the pre-3.4 Solr loader and WordlistLoader exactly.

-      if (line.length() == 0 || line.charAt(0) == '#') {
-        continue; // ignore empty lines and comments
+      if (line.trim().isEmpty() || line.charAt(0) == '#') {
+        continue; // ignore blank lines and comments
       }

Trade-offs

Skips exactly the lines whose single term the parser would trim to the empty string (it uses the same trim() on every term, :99, :105, :117); with the analyzers tried every such line fails today, so no file that parses today with them changes meaning (an analyzer that emits a token for empty input is the one exception). No public API signature changes; it is a leniency change: files rejected today are accepted. Indented comment lines ( # x) stay rules, as before, and so do lines of only Unicode spaces that trim() keeps, such as U+3000 (rejected today with WhitespaceAnalyzer, and still rejected). Cost: one trim() per line at load time.

  • With the fix: it passes with assertions on and off (-Ptests.asserts=false).

line.isBlank() (the hunt's fix) (validated by the checks)

#

The same condition with String.isBlank().

-      if (line.length() == 0 || line.charAt(0) == '#') {
+      if (line.isBlank() || line.charAt(0) == '#') {

Trade-offs

A different set of lines, not just a broader one: trim() removes every character up to U+0020, while isBlank() uses Character.isWhitespace. So B also skips lines of Unicode whitespace that trim() keeps (U+2003, U+3000), but still rejects lines of control characters that trim() removes and that are not whitespace (U+0001). Executed on the main jars (couch, sofa / X / big, large): a U+0001 line is rejected today, parses with A and is still rejected with B. A U+3000 or U+2003 line is rejected today with WhitespaceAnalyzer and parses with B; with KeywordAnalyzer it parses today as a one-term rule that adds no mapping with expand on and maps the term to itself with expand off (3 words). B skips it, so with expand off the self-mapping is lost (2 words). B therefore changes how a file that parses today is read, in a small way; A matches the old loader exactly and is the safer choice (the adjudication rated either fix safe before this difference was found).

What the checks validated

Gradle in the same scratch worktree: the repro and TestSolrSynonymParser pass with assertions on (11 tests, 0 failures); the other suites and the static checks were not run through gradle for this option (the fact check later ran the repro with it through gradle with assertions off: pass). Earlier, shadowed into the stock main jars, the four earlier test classes (21 tests) and the 10 upstream TestSolrSynonymParser tests pass, and the minimal repro passes with assertions on and off.

Trim before the '#' check (not recommended)

#

Would also turn indented # x lines into comments.

Trade-offs

A different change: it alters how files that parse today are read (an indented # line is a rule today, and was in the pre-3.4 loader too). Not tried.

Downstream note

#

Elasticsearch's synonym filters parse rules with a subclass of SolrSynonymParser (by code reading), so their users get the same error unless they enable its lenient mode, which drops the failing rule instead.

How it was found

#

Semi-formal: a bounded-exhaustive check compared the parser on 253,130 small synonym files (1,012,520 parse-and-build checks) with a reference written from the javadoc, with 0 mismatches. Writing that reference forced a decision on what "blank line" means, so whitespace-only lines were tested on their own, and they are rejected.

The method in full112 words

Method: semi-formal (bounded-exhaustive translation validation). The harness enumerated synonym files of 1-3 rules, with expand and dedup on and off, parsed and built each with SolrSynonymParser and SynonymMap.Builder, decoded the resulting FST rule set and compared it exactly with a reference implementation of the javadoc's rules: 253,130 files, 1,012,520 checks, 0 mismatches; two deliberately broken reference variants are caught, so the check is not vacuous. The reference had to say what a blank line is, so whitespace-only lines were checked as their own class, and a public-API JUnit test then showed the rejection on the stock main jars (2 of 3 tests fail: spaces-only and tab-only line; the empty-line control passes).
