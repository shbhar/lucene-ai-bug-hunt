FSTCompletionLookup ignores exactMatchFirst=false for by-weight lookups after build() and load(), so an exact match is always ranked first

FSTCompletionLookup built with exactMatchFirst=false still ranks an exact match first in by-weight lookups: for star (weight 1), star wars (100) and start (50), lookup("star", true, 3) returns [star/0, star wars/6, start/3], not [star wars/6, start/3, star/0], with no error. Every release since 3.6.0 is affected.

The bug in 30 seconds

#

FSTCompletionLookup keeps two views of one FST: a by-weight view for lookup(key, true, num) and an alphabetical view for lookup(key, false, num). build() and load() pass exactMatchFirst only to the alphabetical view, where an exact match sorts first anyway. The by-weight view always keeps its "exact first" default.

  1. You create new FSTCompletionLookup(dir, "fst", 10, false) to rank suggestions purely by popularity and build() it from star (weight 1), star wars (weight 100) and start (weight 50). With 10 buckets they land in buckets 0, 6 and 3.
  2. The user types "star" and you ask for the most popular completions: lookup("star", true, 3). The javadoc of exactMatchFirst says that with false exact matches "appear in the order of discretized weight", so you expect [star wars/6, start/3, star/0].
  3. Instead you get [star/0, star wars/6, start/3]: the least popular entry comes first, only because it equals the typed text. With lookup("star", true, 1) the only suggestion is star/0. No error, and exactMatchFirst=true returns the same lists.
  4. Why: the lookup keeps two views of one FST. build() and load() pass the flag only to the alphabetical view; the by-weight view is made with new FSTCompletion(fst), which means "higher weights first and exact first".
  5. It is the same after store() and load() into an instance built with false. The other constructor, which takes a pre-built FSTCompletion, passes the flag to both views and returns [star wars/6, start/3, star/0].

Who is affected

#

Applications that build the experimental FSTCompletionLookup with the non-default exactMatchFirst=false and ask for by-weight suggestions, lookup(key, true, num). Any typed prefix that is itself a less popular entry is ranked first, every time; with a small num it pushes out a correct entry. The default true and alphabetical lookups are unaffected.

Mechanism, terms and numbers598 words

FSTCompletionLookup has a constructor argument exactMatchFirst; its javadoc says that with false exact matches "appear in the order of discretized weight and alphabetical within the bucket". The lookup keeps two FSTCompletion views over one FST: a by-weight view for lookup(key, true, num) and an alphabetical view for lookup(key, false, num). build() and load() pass the flag only to the alphabetical view; the by-weight view is created with the one-argument FSTCompletion(FST), "higher weights first and exact first". So by-weight lookups always put the exact match first, whatever its weight, with no error, and on distinct keys the argument has no visible effect at all. With star (1), star wars (100), start (50) and 10 buckets, lookup("star", true, 3) returns [star/0, star wars/6, start/3] instead of [star wars/6, start/3, star/0]. It came with the class in SOLR-2888 (3.6.0), which replaced FSTLookup, a class that honoured the flag; every release since is affected. Two statements fix it: create the by-weight view with new FSTCompletion(fst, true, exactMatchFirst) in build() and load(), as the pre-built-completion constructor already does.

Terms

#
  • Buckets: build() sorts the entries by weight and splits them into buckets equal ranges, bucket = (int) (line * buckets / inputLineCount) (FSTCompletionLookup.java:222-227). A result shows the bucket, not the weight: star wars/6. With 3 entries and 10 buckets: star (weight 1) gets 0, start (50) gets 3, star wars (100) gets 6.
  • Two views: higherWeightsCompletion (by weight, highest bucket first) and normalCompletion (alphabetical), two FSTCompletion wrappers over the same FST (FSTCompletionLookup.java:96-100). lookup(key, contexts, higherWeightsFirst, num) picks the first when higherWeightsFirst is true (:268-272); Lookup.lookup(key, onlyMorePopular, num) delegates to it (Lookup.java:193-195).
  • Exact first: an FSTCompletion with exactFirst set looks for the key itself, puts it at the head of the results and removes it from the rest (FSTCompletion.java:233-283).

The bug

#
  1. The buckets constructor FSTCompletionLookup(Directory, String, int, boolean) stores exactMatchFirst (FSTCompletionLookup.java:130-136).
  2. build() ends with this.higherWeightsCompletion = builder.build(); (:242) and this.normalCompletion = new FSTCompletion(higherWeightsCompletion.getFST(), false, exactMatchFirst); (:243-244). FSTCompletionBuilder.build() returns new FSTCompletion(automaton) (FSTCompletionBuilder.java:197), and that constructor is "Defaults to higher weights first and exact first", this(automaton, true, true) (FSTCompletion.java:124-131).
  3. load() does the same with new FSTCompletion(new FST<>(readMetadata(...), input)) (FSTCompletionLookup.java:305-306); again only normalCompletion gets the flag (:307-308).
  4. In the alphabetical view the flag cannot show: when more than one bucket is in use the results are sorted before they are cut (FSTCompletion.java:202-206), and an exact match is a prefix of all its completions, so it sorts first anyway; with one bucket the depth-first walk already emits it first. On stock main, instances built with true and with false gave 0 different results over about 300,000 lookups in each mode on random dictionaries of distinct keys; with the fix about 37,000 by-weight lookups differ.
  5. The fourth constructor, FSTCompletionLookup(Directory, String, FSTCompletion, boolean), creates both views with the flag (FSTCompletionLookup.java:152-153) and returns the documented order.

The numbers

#

star (1), star wars (100), start (50), 10 buckets, exactMatchFirst=false: lookup("star", true, 3) = [star/0, star wars/6, start/3], expected [star wars/6, start/3, star/0]; lookup("star", true, 1) = [star/0], expected [star wars/6]. The same after store() + load(). The alphabetical lookup("star", false, 3) = [star/0, star wars/6, start/3], which is correct UTF-8 order. Another dictionary, {foo: 1, bar: 5, fool: 200, food: 500, foobar: 1000}: lookup("foo", true, 1) = [foo/0] instead of [foobar/8]. The smallest case: {a: 0, aa: 1}, lookup("a", true, 1) = [a/0] instead of [aa/5].

Exposure and likelihood287 words
  • Who. Code that calls the buckets constructor (Directory, String, int, boolean) with exactMatchFirst=false, for example to rank suggestions purely by popularity, and then lookup(key, true, num), after build() or after load().
  • When. For distinct keys and num > 0: whenever the typed text is itself an entry and another of its completions is in a higher bucket: ordinary autocomplete input, such as "star" while "star wars" is far more popular. Deterministic; no scale, concurrency or unusual data needed.
  • What goes wrong. Silent ranking error. If num covers all completions only the order is wrong; if num is small the exact match takes a slot and the lowest-ranked correct entry drops out, so the top-1 suggestion can be the least popular entry.
  • Not affected. The default (FSTCompletionLookup(dir, prefix) uses true, FSTCompletionLookup.java:116-118), alphabetical lookups, get(key) (it reads normalCompletion, :287-290), and the pre-built-completion constructor. The class is @lucene.experimental (:71).
  • Size of the check. A bounded-exhaustive differential on the stock jars over every set of 1-3 distinct keys from the 39 strings of length 1-3 over {a, b, c}, with weights {0, 1, 2, 2^31-1} (596,908 dictionaries, about 4.76 billion lookups) found 265,860 order mismatches each for 3 and 10 buckets with false, and none with true or with 1 bucket. That full scope was not re-run with the fix; a smaller exhaustive run with the fix shadowed (keys of length 1-2, sets of 1-4 keys: 141,904 dictionaries, about 1.13 billion lookups) found no FSTCompletionLookup mismatch.
  • Distinct keys only. Every check used dictionaries of distinct keys; a dictionary holding the same key twice, with weights in different buckets, was not covered, so the doc makes no claim about it.

Why it is a bug, not intended

#
  • The javadoc: with false, exact matches "appear in the order of discretized weight and alphabetical within the bucket".
  • The pre-built-completion constructor passes the flag to both views and returns that order; TestFSTCompletion asserts that FSTCompletion(fst, true, false) does not promote.
  • A regression: the replaced FSTLookup honoured false (3.5.0: [star wars, start, star]); 3.6.0 FSTCompletionLookup does not.
The full argument224 words
  • The contract. FSTCompletionLookup.java:126-128: "@param exactMatchFirst If <code>true</code> exact matches are promoted to the top of the suggestions list. Otherwise they appear in the order of discretized weight and alphabetical within the bucket." "Order of discretized weight" only describes the by-weight path, the one that ignores the flag. The same text is on the pre-built-completion constructor (:142-144), which honours it (:152-153).
  • The lower-level switch is documented and tested. FSTCompletion's exactFirst: "Find and push an exact match to the first position of the result list if found" (FSTCompletion.java:109-110). TestFSTCompletion.testRequestedCount asserts that new FSTCompletion(fst, true, false) does not promote the low-weight "one" (TestFSTCompletion.java:136-139). The sibling WFSTCompletionLookup honours exactFirst=false (TestWFSTCompletion.testNonExactFirst). No upstream test builds FSTCompletionLookup with false.
  • History. SOLR-2378 added exact-match promotion "(weighted mode)" to the old FSTLookup, and SOLR-2762 fixed it there, so the flag was a feature of the weighted path. SOLR-2888 replaced FSTLookup with FSTCompletionLookup and switched Solr's FSTLookupFactory from new FSTLookup(buckets, exactMatchFirst) to new FSTCompletionLookup(buckets, exactMatchFirst) as a drop-in; its CHANGES entry announces no change in behaviour. Executed on the same input: 3.5.0 FSTLookup(10, false) returns [star wars, start, star]; 3.6.0 FSTCompletionLookup(10, false) returns [star/0, star wars/6, start/3]. Three days after the class was committed, its author added the "Otherwise ..." javadoc (3408defc8db, "JavaDoc clarifications").
The devil's-advocate check310 words

The strongest works-as-designed case (built by the intended-behaviour verifier, reviews by a model from another family, OpenAI GPT-5.6, and the adjudication): FSTCompletionBuilder's class javadoc says "If there is an exact match in the automaton, it is returned first on the results list (even with by-weight sorting)" (FSTCompletionBuilder.java:77-78), its no-argument constructor makes an FSTCompletion "with default options: 10 buckets, exact match promoted to first position" (:127-131), and FSTCompletion(FST) defaults to exact first; the class is @lucene.experimental; nobody complained in about 15 years; and for load(), the no-argument constructor "should only be used to read a previously saved suggester" (FSTCompletionLookup.java:105), defaults to true, and store() does not record the flag. Nearby javadoc is also loose: FSTCompletion says higherWeightsFirst=false "has no effect" (FSTCompletion.java:106-108), yet lookup then sorts alphabetically when more than one bucket is in use (:202-206), and Lookup documents the by-weight switch as onlyMorePopular, "return only more popular results" (Lookup.java:189).

Why it fails: the builder and one-argument docs describe the default view, which the explicit argument exists to override, and its own javadoc says so; experimental status allows API changes, not a documented argument that does nothing; few users set false, and Solr's modern suggest component uses the unaffected alphabetical path; load() itself applies this.exactMatchFirst to normalCompletion, nothing forbids loading into a configured instance, Solr does exactly that, and the build() path alone proves the bug. The exactMatchFirst text, unlike the loose sentences, is specific to this class and argument, was added by the class's author three days after the class, and is implemented by the pre-built-completion constructor. Every check rated the intended argument weak; the cross-model fact check of this doc rated it weak for build() and moderate for load(). Lead the issue with build() and the 3.5.0 to 3.6.0 regression.

#

Recommended Build the by-weight view with the flag in build() and load()

Create the by-weight view with the flag, new FSTCompletion(fst, true, exactMatchFirst), in build() and load(), as the pre-built-completion constructor already does: two statements. Validated: the repro and a new TestFSTCompletion test fail on stock and pass with it, assertions on and off, and the whole suggest module passes (240 tests).

Trade-offs

  • The default exactMatchFirst=true behaves exactly as before.
  • Behaviour change for users who set false: by-weight lookups now follow the documented order; worth a CHANGES line. Anyone who relied on the old order can pass true, which gives it for distinct keys (duplicate keys were not checked).
  • builder.build() still makes one throwaway FSTCompletion (it caches at most one root arc per bucket), negligible next to building the FST.

How it was found

#

A bounded-exhaustive differential check ran the suggester Lookup implementations (all except FreeTextSuggester) on the real jars against a reference written from each one's javadoc. For FSTCompletionLookup with exactMatchFirst=false it found 265,860 order mismatches each for 3 and 10 buckets and none with true; a smaller exhaustive run with the fix found none. Reading build() and load() gave the cause.

The method in full190 words

Method: bounded-exhaustive differential translation validation on the stock jars (semi-formal tier), in a hunt unit that compared the suggest module's Lookup implementations (all except FreeTextSuggester).

  • The harness builds every implementation from the same dictionary and compares each lookup with an independent reference written from that class's javadoc; for FSTCompletionLookup: bucket descending, then UTF-8 order, the exact match first only when exactMatchFirst is true.
  • Scope: every set of 1-3 distinct keys over the 39 strings of length 1-3 over {a, b, c}, with weights {0, 1, 2, 2^31-1}: 596,908 dictionaries, 7,759,804 builds and 4,763,325,840 lookups, assertions off. The class "exact=false, order" appeared 265,860 times for 3 buckets and as often for 10, never for true or 1 bucket. With the fix shadowed onto the jar (141,904 dictionaries including 4-key sets, about 1.13 billion lookups) it appeared 0 times.
  • The class was reduced to a public-API JUnit (found 2026-10-27 on main ea57360912ed, whose lucene/suggest equals a9779ef3c193), then checked by an independent reproducer, an intended-behaviour devil's advocate, two executed reviews by a model from another family (OpenAI GPT-5.6), an adjudication, a history and prior-report follow-up and a credibility audit.

History

#

Born with the class in SOLR-2888 (92de7e88486, 2011-12-01; branch_3x d3e380f824a, first release 3.6.0), which replaced FSTLookup, a class that honoured the flag. Executed: 3.6.0 to 10.5.2 (23 releases) and main fail; 3.5.0 has no such class. Never fixed.

Versions tested7 rows

Introduced by SOLR-2888, "FSTSuggester refactoring: utf8 storage, external sorts (OOM prevention), code cleanups" (svn era, no PR): trunk 92de7e884868 (svn r1209265, 2011-12-01) and the branch_3x backport d3e380f824a5 (svn r1232289, 2012-01-17), which shipped first, in 3.6.0. The commit created FSTCompletionLookup; both defect sites are in its first version; its 21 JIRA comments never mention exact-match handling. The exactMatchFirst=false javadoc followed three days later in 3408defc8db ("JavaDoc clarifications"), so no release has the code without the contract.

It is a regression of that refactoring: FSTLookup, deprecated in 3.6 and removed in 4.0, applied the flag on the by-weight path. All 126 release tags with the class build the by-weight view the same faulty way (the surrounding lines differ between versions), the 9 untagged 8.x releases 8.8.2 to 8.11.4 were executed instead (135 releases counting the 4.0.0-alpha and 4.0.0-beta prereleases, 133 final releases), and FSTCompletionLookup.java is byte-identical on upstream main a95c754ee003, branch_10x and branch_10_6 (fetched 2026-10-26).

Bug record

LFV-706, snapshot of 2026-10-29

Registry title
FSTCompletionLookup ignores exactMatchFirst=false for by-weight lookups after build() and load(), so an exact match is always ranked first
Area
suggest / FST completion suggester (FSTCompletionLookup build/load exactMatchFirst wiring)
Priority
Low, rank 326: Ranking-only, and it needs the non-default exactMatchFirst=false in the experimental FSTCompletionLookup.
Impact class
silent wrong results
Impact note
Applications that build the opt-in, @lucene.experimental FSTCompletionLookup with the non-default exactMatchFirst=false (for example to rank suggestions purely by popularity) and then call lookup(key, true, num) after build() or after load() get the exact match first whatever its weight bucket, with no error: when num covers all completions only the order is wrong, and when num is small the exact match pushes out the lowest-ranked correct entry (top-1 can be the least popular entry); alphabetical lookups and the default exactMatchFirst=true are unaffected, no scale is needed, and every release from 3.6.0 through 10.5.2 and main is affected (by code reading, Solr's FSTLookupFactory exposes the setting, but its SuggestComponent calls the alphabetical lookup(token, false, count), which the bug does not reach).
Summary
You build an FSTCompletionLookup(dir, "fst", 10, false) from star (weight 1), star wars (100) and start (50) and ask lookup("star", true, 3) for the most popular completions first. You expect [star wars/6, start/3, star/0], because the constructor javadoc says that with exactMatchFirst=false exact matches 'appear in the order of discretized weight and alphabetical within the bucket'. Instead you get [star/0, star wars/6, start/3], with no error, after build() and equally after store() and load(): both paths create the internal by-weight FSTCompletion with its exact-first default, and the flag reaches only the alphabetical completion, where it changes nothing.
Introduced
92de7e884868f91b42689aa344c51b1b8aa8fdbb (trunk, svn r1209265, 2011-12-01) and its branch_3x backport d3e380f824a59857c3cd72e7f789e6f5682e7853 (svn r1232289, 2012-01-17; the backport shipped first, in 3.6.0), SOLR-2888 'FSTSuggester refactoring: utf8 storage, external sorts (OOM prevention), code cleanups' (an svn-era JIRA change, no pull request; its 21 comments never mention exact-match handling). The commit created FSTCompletionLookup with build() keeping higherWeightsCompletion = builder.build() and load() using the one-argument new FSTCompletion(fst), both exact-first by default, while only normalCompletion received exactMatchFirst; the pre-built-completion constructor of the same commit passes the flag to both [read: git log --follow, git log -L on the build() line (only 92de7e88486), git blame -w -M -C; both defect sites are in the class's first version, so no commit-level bisection was needed] [exec: release boundary, the predecessor FSTLookup honours exactMatchFirst=false on 3.5.0, 3.6.0 and 3.6.2, FSTCompletionLookup ignores it on 3.6.0]. The exactMatchFirst=false javadoc followed three days later in 3408defc8db (2011-12-04, 'JavaDoc clarifications'), so no release has the code without the contract (2011-12-01 (trunk); 2012-01-17 (branch_3x backport))
