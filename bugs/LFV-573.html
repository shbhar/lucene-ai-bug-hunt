Lat/lon distance queries can miss a point exactly at the radius, and match one just beyond it

A distance query whose radius equals a point's own Lucene distance can miss that point, and a radius one ulp smaller can match it: the radius becomes the wrong sort-key threshold. Nanometres under 19,000 km, but a hit whose sort distance you reuse as the radius goes missing; since 6.1.0.

The bug in 30 seconds

#

Lucene's distance for a point is SloppyMath.haversinMeters, the number the distance sort and LatLonPoint.nearest report. A distance query should match exactly the points whose distance is at most the radius. Here is a point at exactly the radius that is missed.

  1. You index a point and sort by distance from a center: Lucene reports 8154434.476304402 m, the same as SloppyMath.haversinMeters. You run LatLonPoint.newDistanceQuery with exactly that radius and expect the point back: the query matches points "within the specified distance".
  2. You get 0 hits, with no error. LatLonDocValuesField.newSlowDistanceQuery and a LatLonShape circle query give 0 too. The other way round, a point at 1.6056103066824859E7 m is matched by radius 1.6056103066824857E7, one ulp smaller.
  3. Why: per document the query compares sort keys, not metres, against one threshold key computed from the radius. Adjacent keys share distances: here keys -2, -1 and 0 are all 8154434.476304402 m, and the point sits on key 0.
  4. GeoUtils.distanceQuerySortKey binary-searches for that threshold and returns the first equal-distance key it lands on, key -1, so key 0 fails key <= threshold. When no key has the radius' exact distance, it returns the first key beyond the radius, which can be a point's own key.
  5. It bites when the radius comes from Lucene itself: with radius = the k-th hit's sort distance, that hit was missing in 92 of 400 trials. A wrong match was measured at most about 2e-8 m beyond the radius (radii under 19,000 km). Every release since 6.1.0.

Who is affected

#

Users of LatLonPoint.newDistanceQuery, LatLonDocValuesField.newSlowDistanceQuery or a Circle query; no special settings are needed. Typed radii practically never hit it; a radius reused from a distance sort does, and then lost that hit in 92 of 400 trials (nearest reports the same value). Only points exactly at the radius, or nanometres beyond it (micrometres near the antipode), are affected.

Mechanism, terms and numbers818 words

A lat/lon distance query is documented to match "points within the specified distance", and Lucene's own distance is SloppyMath.haversinMeters, the value a distance sort and LatLonPoint.nearest report. To avoid an asin per document, the query compares each point's sort key with one threshold key that GeoUtils.distanceQuerySortKey(radius) computes per query. Several adjacent sort keys round to the same distance in metres, so the threshold must be the largest key whose distance is <= radius. The binary search instead returns the first key it meets whose distance equals the radius, which can sit below the point's own key (the point is dropped), When no key has exactly that distance it returns lo, the key where the search ends, whose distance is beyond the radius (its assert checks only that; in the repro it is the first key beyond it), and a point on that key matches. Example: the distance sort and haversinMeters both put a point 8154434.476304402 m from the center, and LatLonPoint.newDistanceQuery, LatLonDocValuesField.newSlowDistanceQuery and LatLonShape.newDistanceQuery(Circle) with exactly that radius all return 0 hits. With radius = the distance-sort value of the k-th hit, that very hit is missing in 92 of 400 trials. No special configuration is needed; every release from 6.1.0 (2016, LUCENE-7215) to 10.5.2 and main. Searching on haversinMeters(key) <= radius and returning hi, the last key that passed (+12/-16 in one method), makes the repro pass, and one complete lucene/core test run with it passed (assertions on, seed DEADBEEF).

Terms

#
  • Sort key: SloppyMath.haversinSortKey(lat1, lon1, lat2, lon2), the first half of the haversine formula, a double between 0 and 2 that grows with distance. Its low three bits are cleared "so subsequent rounding does not create ties" (SloppyMath.java:73-74), so only every 8th double can be a point's key.
  • Distance: haversinMeters(key) = TO_METERS * 2 * asin(min(1, sqrt(key * 0.5))) (SloppyMath.java:57-59). haversinMeters(lat1, lon1, lat2, lon2) is exactly haversinMeters(haversinSortKey(...)) (:47-49), so a point's Lucene distance is a function of its key.
  • Threshold: to skip the asin per document, a distance query computes once GeoUtils.distanceQuerySortKey(radius) and matches a point when its key is <= that threshold (LatLonPointDistanceQuery.java:107-108, GeoEncodingUtils.java:176 and :381-383; Circle2D.java:415, :438, :443 for every Circle geometry, including LatLonDocValuesField.newSlowDistanceQuery and LatLonShape).

The bug

#
  1. Consecutive keys often give the same distance value (around the first repro point, runs of 2 or 3 keys; tables below). "key <= threshold" equals "distance <= radius" only if the threshold is the largest key whose distance is <= radius.
  2. distanceQuerySortKey (GeoUtils.java:114-141) binary-searches the bit patterns 0 to Double.MAX_VALUE (about 63 steps). When haversinMeters(mid) == radius it returns mid at once (:127-128), whichever key of the run it hit first: a point on a later key of the run is at exactly the radius but fails.
  3. When no key has exactly the radius' distance, it returns lo (:136-140), the key where the search ends: it tested above the radius and the key just before it tested below, so where distance does not decrease as the key grows it is the smallest key beyond the radius. The assert haversinMeters(ceil) > radius checks only the first part. A point on that key matches although it is beyond the radius.

Exposure and likelihood382 words
  • Which queries. LatLonPoint.newDistanceQuery, LatLonDocValuesField.newSlowDistanceQuery, their IndexOrDocValuesQuery combination, LatLonShape.newDistanceQuery with a Circle (INTERSECTS, WITHIN, and DISJOINT with the errors mirrored) and LatLonPoint.newGeometryQuery / LatLonDocValuesField.newSlowGeometryQuery with a Circle: all nine tested factories share the threshold and show identical counts (400 point documents; CONTAINS and indexed lines or polygons were not run). By reading, the same threshold is used wherever a Circle is evaluated and in the points query's cell relations. The first two are not @lucene.experimental.
  • Default vs opt-in. Nothing to opt into: the error is in the per-query threshold, not in the codec, writer or searcher. The repro runs under the test framework's randomized writer config, codec and searcher, the finder's harness under a default IndexWriterConfig with NoMergePolicy and a plain IndexSearcher; both fail the same way, with assertions on and off.
  • When it bites. Only a radius equal to a point's own Lucene distance, or less than one sort-key step below it (a few ulps of the distance for radii under 19,000 km). Typed or random radii practically never land there, which is why upstream's random tests pass. Reusing a distance Lucene computed does: "everything at least as close as my k-th nearest hit" (radius = the k-th distance-sort value) lost that very hit in 92 of 400 trials (116 of 400 with another seed), once the nearest hit at 683007.9829461674 m, whose own distance as radius returned 0 hits. LatLonPoint.nearest reports the same value as the distance sort (by reading, and equal for the repro point), so a radius taken from it should behave the same; that workflow was not run. "Strictly closer than this document" (radius Math.nextDown of its distance) can still return the document.
  • Scale. A point is dropped only when its distance equals the radius exactly; a wrongly matched point was at most about 2e-8 m beyond the radius for radii under 19,000 km, and 2.6e-5 m in the worst case near the antipodal maximum (1.2 million radii probed; measured, not proven). That is far below the coordinate encoding (about 4.7 mm of latitude) and the documented 40 cm error of haversinMeters. The harm is inconsistency: the query disagrees with the distance the same application shows from Lucene's sort.
  • How likely. Rare; the searches listed under Prior reports found no earlier report.

Why it is a bug, not intended

#
  • The method promises "the exact sortKey needed to match the specified radius".
  • Upstream's test oracle is exactly haversinMeters(center, point) <= radiusMeters; the code is a 2016 speed-up of that exact check (LUCENE-7215).
  • It errs in both directions, so it is no lenient cut; the documented 40 cm error is against the true haversine, not Lucene's own distance.
The full argument248 words
  • The method promises exactness. "binary search to find the exact sortKey needed to match the specified radius any sort key lte this is a query match" (GeoUtils.java:110-113); haversinSortKey "always compares the same" as haversinMeters (SloppyMath.java:61-64), though that reads most naturally as a claim about ordering, not as a promise that a radius maps back to an exact key.
  • The public contract is inclusive. "matching points within the specified distance", radiusMeters the "maximum distance from the center in meters" (LatLonPoint.java:285-292; LatLonDocValuesField.java:196-209 says the same).
  • Upstream's oracle is exact. SloppyMath.haversinMeters(centerLat, centerLon, lats[id], lons[id]) <= radiusMeters, no tolerance (BaseGeoPointTestCase.java:1061). It never draws a radius equal to a point's distance; TestGeoUtils.java:49 carries "TODO: randomly quantize radius too, to provoke exact math errors?".
  • A speed change, not a semantics change. Until 6.0.1 the leaf check was SloppyMath.haversinMeters(h1) <= radiusMeters. LUCENE-7215 (#8270, CHANGES "Optimizations") replaced it with the key comparison; its issue says "we just need to compute the exact sort key needed for comparisons" and never discusses the boundary. The original query (LUCENE-7054, #8110) came with a random test "that doesn't have any leniency/tolerance/deltas ... to keep testing exact".
  • Precedent. LUCENE-7185 (#8240) fixed the same kind of key/metre tie inconsistency for the distance sort, by masking the low bits of the sort key.
  • Wrong in both directions. A deliberately lenient threshold would never drop a point at the radius; this one drops them (equality branch) and admits points beyond it (ceil branch).
The devil's-advocate check229 words

The strongest case for "works as designed" (built by the intended-behaviour checker; the cross-model reviewers raised it too): SloppyMath is "Math functions that trade off accuracy for speed" with up to 40 cm error (SloppyMath.java:31, :38); GeoUtils and Circle are @lucene.experimental (GeoUtils.java:49, Circle.java:47); the ceil comment and assert show the author knew the returned key is beyond the radius; and no test pins the exact boundary.

Why it fails: the 40 cm figure compares haversinMeters with the true haversine, not the query with haversinMeters, the number the distance sort and nearest report; the equality branch causes false negatives, so the cut is not conservative; the method's own javadoc says "exact"; LatLonPoint.newDistanceQuery is not experimental; and the change that introduced it was filed as an optimization of an exact predicate. The ceil comment explains why an exact match may not exist, not that the boundary may move. What the rebuttal does not cover: the public javadocs ("within the specified distance", "maximum distance from the center in meters") name no distance function, do not promise agreement with the distance sort and define no rounding at the boundary, so maintainers can call the exact boundary unspecified, and documenting it as approximate is a legitimate choice. Expect the "sloppy by design" push-back: lead with the k-th-hit workflow, the method's own "exact" javadoc and the false negatives.

Suggested fix

#

Recommended Return the last key whose distance is <= radius (binary search, return hi)

Make GeoUtils.distanceQuerySortKey search on haversinMeters(key) <= radius and return hi, the last key that passed. The repro, a new TestGeoUtils test and one complete lucene/core test run pass. That is the largest key within the radius wherever distance does not fall as the key grows; 2 billion key pairs showed one 1-ulp dip, where no point key was misclassified.

    long lo = 0;
    long hi = Double.doubleToRawLongBits(Double.MAX_VALUE);
    while (lo <= hi) {
      long mid = (lo + hi) >>> 1;
      double midRadius = haversinMeters(Double.longBitsToDouble(mid));
      if (midRadius <= radius) {
        lo = mid + 1;
      } else {
        hi = mid - 1;
      }
    }
    double floor = Double.longBitsToDouble(hi);
    assert haversinMeters(floor) <= radius;
    return floor;

One fix was applied in a scratch worktree at a9779ef3c193 and run through gradle; the alternatives were not run.

Workaround today: to include a point at a known distance d, pass Math.nextUp(d) as the radius (0 misses over 480 such queries for each of the 9 factories in the fact check's run); a point one more ulp beyond can then match by the same bug.

Return the last key whose distance is <= radius (binary search, return hi) (validated by the checks) (recommended)

#

In GeoUtils.distanceQuerySortKey (GeoUtils.java:114-141) drop the equality early return and the ceil return: move lo past every key with haversinMeters(key) <= radius, move hi below every key above it, and return hi. The search ends on a key hi that tested within the radius while hi + 1 tested beyond it; where distance does not decrease as the key grows, that is the largest key within the radius. The javadoc gains "the largest sort key whose distance is less than or equal to the radius", and an assert haversinMeters(floor) <= radius replaces the old ceil assert (it holds for every radius the query constructors accept: hi ends on the last key that passed). The "effectively infinite" branch is unchanged. The finder wrote this fix and the independent reproducer the same one; this version adds the javadoc sentence and the assert. For the PR, qualify the javadoc sentence and the code comment ("assuming the distance does not decrease as the key grows") or limit them to point keys: at the one measured dip they do not hold for raw keys (below).

    long lo = 0;
    long hi = Double.doubleToRawLongBits(Double.MAX_VALUE);
    while (lo <= hi) {
      long mid = (lo + hi) >>> 1;
      double midRadius = haversinMeters(Double.longBitsToDouble(mid));
      if (midRadius <= radius) {
        lo = mid + 1;
      } else {
        hi = mid - 1;
      }
    }
    double floor = Double.longBitsToDouble(hi);
    assert haversinMeters(floor) <= radius;
    return floor;

Trade-offs

  • Cost (not benchmarked): no per-document change; the search stays bounded at about 63 haversinMeters calls per query, and the stock code already runs the full search whenever no key has exactly the radius' distance. Radii that hit an equal-distance key, such as distances reused from a sort, used to stop early and now run the full search; that per-query cost was not measured.
  • Premise: exact if haversinMeters(key) never decreases as the key grows. For arguments up to sin(73 degrees) (keys up to about 1.83) SloppyMath.asin interpolates from one of 8,193 table cells (SloppyMath.java:144-155, :239-243); above that it uses an fdlibm-derived formula (:156-169). So the cell boundaries and the switch are where a dip could hide. A scan of 2,074,872,896 adjacent key pairs (every boundary and the switch +/-65,536 keys, the last 1M keys before 2.0, 1,000 random runs of 1M keys) found exactly one decrease: one ulp (1.86e-9 m) at key 1.4201579892440324 (about 12,770 km), on the boundary between cells 7218 and 7219. There, for radius 1.2770150274362441E7 the fix returns a key 2 below the dip while 2 later keys have exactly that distance; neither has its low 3 bits clear, so no point can sit on them. Over the 4,514 radii equal to a distance of the 8,193 nearest keys, that is the fix's only miss; stock misclassifies a key with its low 3 bits clear (one a point could have; the probe checks only the bit mask) for 232 of those radii. Measured, not proven: say so in the PR.
  • Inputs: the query constructors reject negative and NaN radii (LatLonPointDistanceQuery.java:62-64, Circle.java:63-65), but distanceQuerySortKey is public and does not check its argument. On a direct call with a negative or NaN radius the fixed loop ends at hi = -1: the new assert fails with assertions on, and with them off the method returns NaN, which no key is <= (stock: 0.0 for a negative radius; for NaN its own assert fails, +Infinity with assertions off). A PR may want an explicit argument check.
  • For the PR (not done here): the threshold also drives BKD cell pruning and acceptance and the grid relations (GeoUtils.java:147-180, GeoEncodingUtils.java:176-187, :379-385, LatLonPointDistanceQuery.java:197-218, Circle2D.java:421-424); the tests here use one-document indexes, a 400-document harness and random point pairs, so a PR test should also cover cells fully inside and outside the circle. The regression tests do not pin the dip spot or invalid direct inputs.

Downstream note

#

Downstream relevance: a distance filter used as a geofence or a MUST_NOT exclusion can decide differently from the distance the application shows, but only for points exactly on the circle or nanometres beyond it (micrometres near the antipode).

How it was found

#

A check compared nine distance-query factories with Lucene's own haversinMeters on 400 encoded points and 40 centers, at radii equal to each point's distance and one ulp around it. All nine missed points at radius = distance and matched points one ulp beyond; reading distanceQuerySortKey and a patched copy confirmed the cause, and a public-API JUnit reproduced it.

The method in full192 words

Method: translation validation of the real jar's distance predicates at the radius boundary (semi-formal tier).

  • A hunt unit on lat/lon geo queries planned a check of "a radius at the exact distance of a grid point". Its harness ran the 9 public distance-query factories over 400 encoded points and 40 centers with radius 0, d, nextDown(d) and nextUp(d) (d = SloppyMath.haversinMeters(center, point)), against upstream's own oracle haversinMeters(center, point) <= radius: 154 of 480 radius-d queries missed the point and 147 of 480 radius-nextDown(d) queries matched it, for every factory; nextUp(d) and radius 0 were always right (logged per kind for LatLonPoint.newDistanceQuery; the fact check's own run confirms it for all nine).
  • Reading GeoUtils.distanceQuerySortKey gave the cause; a patched copy (a search for the last key within the radius) removed every mismatch (0 of 13,320 factory queries), and a public-API JUnit on fixed coordinates reproduced it on the stock jar.
  • Then an independent reproducer, reading-only reviews by a model from another family (OpenAI GPT-5.6), an intended-behaviour devil's advocate, an adjudication and a credibility audit; this doc's runs added a targeted probe of the fix's monotonicity premise.

History

#

Introduced by LUCENE-7215 (2335a458d834, backport 87069500fb2e, 2016-04-13), first released in 6.1.0; 6.0.1 is clean. A portable probe fails on 14 releases from 6.1.0 to 10.5.2 and on main with identical counts wherever Circle accepts the radius; the method is unchanged on upstream main, branch_10_6 and branch_10x.

Versions tested7 rows

Introduced by LUCENE-7215 "don't invoke full haversin for LatLonPoint.newDistanceQuery" (#8270, by @rmuir, a JIRA patch, no PR): 2335a458d834 on master and the branch_6x backport 87069500fb2e, both 2016-04-13; first released in 6.1.0 (the 6.0.x branch never got it). It replaced the exact SloppyMath.haversinMeters(h1) <= radiusMeters check with the key comparison. Later commits only moved the method into core GeoUtils (LUCENE-7343: fb3480b8071 on master, the branch_6x backport fc68bd90e6f in 6.2.0) and reformatted its javadoc (LUCENE-9570).

Attribution by execution: the commit itself was not built (2016 ant build); 6.0.1 passes, 6.1.0 fails, and 6.1.0 with only the threshold function replaced by the fix passes, so none of the other geo commits between 6.0.1 and 6.1.0 is needed.

The doc's 2-test, three-factory JUnit ran on main, 10.5.2 and 9.12.3; a reduced LatLonPoint-only version ran on 9.0.0, 8.11.4, 7.7.3, 6.6.6 and 6.1.0 (fail) and on 6.0.1 (pass).

Each API from its first release: the LatLonPoint distance query from 6.1.0, the LatLonDocValuesField one from 6.5.0, LatLonShape circles from 8.5.0 (until 8.8.0 Circle rejected radii above 3,185,504 m). LatLonPoint and LatLonDocValuesField were in lucene-sandbox until 7.4.x, in core since 7.5.0.

Bug record

LFV-573, snapshot of 2026-10-29

Registry title
Lat/lon distance queries can drop a point whose distance equals the radius and match a point one ulp beyond it, because GeoUtils.distanceQuerySortKey does not return the largest sort key within the radius (every release since 6.1.0)
Area
core / geo distance queries (GeoUtils.distanceQuerySortKey, shared by LatLonPoint, LatLonDocValuesField and LatLonShape circle queries)
Priority
Low, rank 349: Core lat/lon distance queries mis-classify a point only when its distance exactly equals the radius, a boundary band that a radius taken from Lucene's own distance does reach.
Impact class
silent wrong results
Impact note
Hits every application that runs LatLonPoint.newDistanceQuery, LatLonDocValuesField.newSlowDistanceQuery, their IndexOrDocValuesQuery combination, LatLonShape.newDistanceQuery with a Circle (INTERSECTS, WITHIN, DISJOINT) or a LatLonPoint/LatLonDocValuesField geometry query with a Circle, with the default codec, IndexWriterConfig and searcher, at any index size, with -ea or -da: a point whose Lucene distance (SloppyMath.haversinMeters, the value the distance sort and LatLonPoint.nearest report) equals the radius can be missing, and a point one ulp of the radius (one masked sort-key step) beyond it can match, with no error; typed or random radii essentially never land in that band, but a radius taken from a distance Lucene computed does (the independent reproduction: the k-th distance-sorted hit is missing from a query that uses its own sort distance as the radius in 116 of 400 trials), and the misclassification is nanometre-scale (measured at most about 2e-8 m beyond the radius below 19,000 km, 2.6e-5 m near the antipodal maximum), so the practical severity is low.
Summary
You index points with LatLonPoint (or LatLonDocValuesField or LatLonShape) and run a distance query whose radius is exactly a point's distance from the center as Lucene computes it (SloppyMath.haversinMeters, the same value a distance sort or LatLonPoint.nearest reports), and expect that point to match, because the query matches 'points within the specified distance' and Lucene's own test oracle is haversinMeters(center, point) <= radius; with the radius one ulp smaller you expect it not to match. Instead the point is often missing in the first case and often still matches in the second (each in roughly a fifth to a third of random cases, depending on the points): for example, two points that both the distance sort and haversinMeters put 8154434.476304402 m apart are not matched by any of the three distance queries with exactly that radius. The cause is GeoUtils.distanceQuerySortKey, which turns the radius into a sort-key threshold by binary search: it returns the first key it meets whose distance equals the radius, not the largest such key, so a point on a larger key of the same distance fails 'key <= threshold', and when no key has exactly that distance it returns the smallest key whose distance exceeds the radius.
