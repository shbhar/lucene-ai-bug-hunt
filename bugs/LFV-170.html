Postings docIDRunEnd() returns Integer.MIN_VALUE near 2^31 doc IDs, so CheckIndex flags a healthy segment as broken

In a segment at Lucene's 2^31-document limit, the default postings reader's docIDRunEnd() returns Integer.MIN_VALUE on the dense blocks after a term's last skip block, so CheckIndex at level 2 or higher reports a valid segment of 2,147,483,519 documents as broken. Search results stay correct; every release since 10.2.0 is affected.

The finding in 30 seconds

#

For a dense block, docIDRunEnd() stretches the run to the end of the enclosing 8,192-doc skip block if that block is full. After a term's last complete skip block there is none: the reader stores the sentinel NO_MORE_DOCS yet counts 8,192 more docs, and the shortcut ignores the sentinel. Near 2^31 its test passes and returns NO_MORE_DOCS + 1.

Background: postings blocks, skip blocks and docIDRunEnd

#
  1. The default postings format stores a term's doc IDs in blocks of 256 (level 0). After every 32 blocks, 8,192 docs, it writes a level-1 skip entry with the last doc ID of that stretch, so advance can jump ahead. A term's last fewer than 8,192 docs have no level-1 entry.
  2. A block whose 256 doc IDs are consecutive is stored as a full bit set: a dense block.
  3. docIDRunEnd() returns one past the last doc of the run of consecutive matching docs that contains the current doc, and must be greater than docID(). CheckIndex (level 2 and up) checks it; query scorers use it to handle a whole run at once.
  4. Doc IDs are Java ints: NO_MORE_DOCS is 2^31 - 1 = 2,147,483,647, and adding 1 wraps to -2,147,483,648. One index holds at most IndexWriter.MAX_DOCS = 2,147,483,519 documents.

The finding, step by step

#
  1. You force-merge an index to one segment at the limit, IndexWriter.MAX_DOCS = 2,147,483,519 documents, each with the term f:x (the shape of Lucene's own testExactlyAtTrueLimit test), and run CheckIndex at -level 2.
  2. You expect "No problems were detected". At doc 2,147,475,456 the postings of f:x are a dense block of 256 docs, so docIDRunEnd() should return 2,147,475,712, the end of that block.
  3. Instead it returns -2,147,483,648 there, and on all 7,936 docs of the 31 dense blocks after the term's last complete 8,192-doc skip block. CheckIndex throws "Run end -2147483648 is <= doc ID 2147475456" and reports 1 broken segment containing 2,147,483,519 documents, which -exorcise would remove.
  4. Why: after the last skip block the reader marks "no next skip block" with NO_MORE_DOCS (2,147,483,647) yet counts 8,192 more docs. The shortcut compares the doc-ID gap to that phantom block's end, 2,147,483,647 - 2,147,475,711 = 7,936, with its remaining docs, 8,192 - 256 = 7,936, finds them equal and returns NO_MORE_DOCS + 1, which overflows.
  5. Smaller segments are fine (a 67,108,864-doc segment is clean), queries return exact results because the bad value only shortens a run, and with a one-condition guard the full segment passes CheckIndex.

Who is affected

#

Holders of one segment within about 8,000 doc IDs of the 2^31 limit, for example a shard force-merged at MAX_DOCS, who run CheckIndex at level 2 or higher (not the default) or Lucene's test framework at that scale. Default codec, every release since 10.2.0. Searches stay exact; the risk is acting on a false corruption report.

Mechanism, terms and numbers872 words

BlockPostingsEnum#docIDRunEnd() in the default postings reader (Lucene104PostingsReader, and the same code in the Lucene101 and Lucene103 readers) extends a fully dense 256-doc block's run to the end of the enclosing 8,192-doc level-1 skip block when the doc-ID gap and the doc-count gap to that block's end are equal. After a term's last complete level-1 block there is no such block: skipLevel1To sets level1LastDocID = NO_MORE_DOCS as a sentinel but still adds 8,192 to level1DocCountUpto, and the shortcut does not exclude the sentinel. For ordinary doc IDs the gaps differ by about two billion and the method is correct; within 8,192 doc IDs of 2^31 they can be equal, and the method returns NO_MORE_DOCS + 1 = Integer.MIN_VALUE, breaking its contract ("The returned doc is greater than docID()").

For a term in every document this happens on every dense block after the term's last complete level-1 block once maxDoc >= 2,147,475,712, up to IndexWriter.MAX_DOCS = 2,147,483,519. On a default-codec segment of exactly MAX_DOCS documents written by IndexWriter, CheckIndex at level 2 reports "Run end -2147483648 is <= doc ID 2147475456" and "1 broken segments (containing 2147483519 documents)", and says -exorcise would remove the segment; with a one-condition guard the same segment is clean. Query results stay exact (the value is below docID(), so consumers only lose a shortcut). Introduced by #14390 in 10.2.0; every release from 10.2.0 to 10.6.0 and main is affected.

The bug, step by step (main 645d4fe14a20)

#

Constants: BLOCK_SIZE = 256, LEVEL1_FACTOR = 32, LEVEL1_NUM_DOCS = 8,192 (Lucene104PostingsFormat.java:343, :348, :351).

  1. Small terms never reach it. With docFreq < LEVEL1_NUM_DOCS the enum starts with level1LastDocID = NO_MORE_DOCS and level1DocCountUpto = 0 (Lucene104PostingsReader.java:559-568); the shortcut's right side is then negative and can never match. A term needs at least one complete level-1 block.
  2. The sentinel state. skipLevel1To (:674 on) computes docCountLeft = docFreq - level1DocCountUpto (:683), then adds LEVEL1_NUM_DOCS to level1DocCountUpto (:684), and only then, if fewer than 8,192 docs are left, sets level1LastDocID = NO_MORE_DOCS and stops (:686-688). In a term's tail the counter therefore includes a full phantom level-1 block.
  3. The unguarded shortcut. docIDRunEnd() (:1099-1129), for a UNARY block whose four 64-bit words are all set (:1101-1115), computes level0DocCountUpto = docFreq - docCountLeft (:1117) and tests level1LastDocID - level0LastDocID == level1DocCountUpto - level0DocCountUpto (:1118-1119); if true it returns level1LastDocID + 1 (:1121), else level0LastDocID + 1 (:1124).
  4. When it misfires. For the j-th full block after the last complete level-1 block (j = 1..31) the right side is 8,192 - 256 x j (at most 7,936) and the left side is NO_MORE_DOCS - level0LastDocID, about two billion for ordinary doc IDs. They are equal exactly when level0LastDocID = NO_MORE_DOCS - (8,192 - 256 x j), so only blocks whose docs are all at or above 2^31 - 8,192 = 2,147,475,456 can trigger it; then :1121 returns NO_MORE_DOCS + 1 = Integer.MIN_VALUE, with assertions on or off.
  5. Worked example (the minimal test). One term of 8,448 consecutive doc IDs, 2,147,467,264 to 2,147,475,711: one complete level-1 block ending at 2,147,475,455, then one dense block 2,147,475,456 to 2,147,475,711. At doc 2,147,475,456: level1LastDocID = 2,147,483,647 (sentinel), level1DocCountUpto = 16,384 (two blocks counted, one exists), level0LastDocID = 2,147,475,711, level0DocCountUpto = 8,448. Left 7,936, right 7,936: it returns -2,147,483,648 instead of 2,147,475,712. Shifted 1,000,000 doc IDs lower, the left side is 1,007,936 and the answer is right.
  6. A term in every document. After k complete level-1 blocks the test reduces to k x 8,192 = 2^31 - 8,192, so k = 262,143: it fires on every dense tail block exactly when maxDoc is in [2,147,475,712, MAX_DOCS]. A Z3 bit-vector model with Java int semantics derived this range (unique k) and proved the bad state unreachable while level0LastDocID < MAX_DOCS - 16,386.
  7. The reader knows the sentinel elsewhere. Impacts.numLevels() returns 1 when level1LastDocID == NO_MORE_DOCS (:1358); docIDRunEnd() does not check it.
  8. Older formats. The backward-codecs readers for indexes written by 10.1.x to 10.3.x (Lucene101 and Lucene103 formats) have the same shortcut with 128-doc blocks and 4,096-doc level-1 blocks (Lucene101PostingsReader.java:1059-1062, Lucene103PostingsReader.java:1105-1108, sentinel at :679 in both); their first failing doc is 2,147,479,552. 10.1.0 code has no postings docIDRunEnd, but 10.1.0 already writes the Lucene101 format, and a term it wrote near 2^31 returns -2,147,483,648 at doc 2,147,479,552 once main reads it (executed).
  9. Who sees the value. CheckIndex testPostings runs only at level >= 2 (CheckIndex.java:1114-1125, :4754) and checks runs of every term with docFreq > 1024, every 1024th term, or all terms at level 3 (:2090-2104); checkDocIDRuns throws "Run end X is <= doc ID Y" (:2549) and the segment is reported FAILED with "exorciseIndex() would remove reference to this segment" (:1208). The CLI default is level 1 (:4742, :4748); new CheckIndex(dir) without setLevel keeps 0 (:499). The test framework's AssertingPostingsEnum asserts endDocID > startDocID (AssertingLeafReader.java:609). DenseConjunctionBulkScorer evaluates a clause with a short run end normally and DisjunctionDISIApproximation discards it with Math.max (DenseConjunctionBulkScorer.java:196-212, DisjunctionDISIApproximation.java:225-233).
Exposure and likelihood302 words
  • Who is hit. A single segment within about 8,000 doc IDs of IndexWriter.MAX_DOCS with a term that is dense near the end of the doc-ID space, for example a term in every document of a shard force-merged to one segment at the hard limit, checked with CheckIndex at level 2 or higher, or Lucene's own tests at that scale with the default postings format (such as testExactlyAtTrueLimit: predicted, not run).
  • Default vs opt-in. The default codec and IndexWriter settings produce the state; nothing is configured. Seeing it needs CheckIndex at level 2 or 3 (the CLI default is 1), the test framework's check-on-close, or a caller of docIDRunEnd() that relies on the contract.
  • Scale. maxDoc >= 2,147,475,712 for a term in every document; in general a dense 256-doc block whose docs are all at or above 2,147,475,456 (2,147,479,552 for indexes written by 10.1.x to 10.3.x) right after the term's last complete level-1 block. A 67,108,864-doc segment is clean.
  • What goes wrong. CheckIndex reports a valid segment as broken ("1 broken segments (containing 2147483519 documents)") and says -exorcise would remove it; an operator who trusts it and runs -exorcise would drop about 2^31 healthy documents (follows from CheckIndex's code and warning; not executed). docIDRunEnd() breaks its contract on up to 7,936 docs per term. Under the test framework, AssertingPostingsEnum fails.
  • Queries are fine. The value is below docID(), so it can only shorten a run. Five FILTER conjunctions, some with nested disjunctions, over a MAX_DOCS segment with holes inside the affected tail returned exact results with assertions on and off while the bad value was consumed 2 to 4 times per query; the same with the fix, with no measurable time difference.
  • Likelihood: contrived. Almost no deployment runs single segments at the 2^31 limit, but Lucene supports and tests that limit.

Why it looks unintended

#
  • docIDRunEnd() promises "The returned doc is greater than docID()", with no exception near 2^31; CheckIndex and AssertingPostingsEnum enforce it.
  • IndexWriter.MAX_DOCS = 2,147,483,519 is the documented hard limit, and Lucene's @Monster test testExactlyAtTrueLimit builds this segment shape.
  • The same reader treats the sentinel as "no level 1" in Impacts.numLevels(); no review of the shortcut ever discussed it.
The full argument200 words
  • Contract. DocIdSetIterator.java:245-263: "1. The returned doc is greater than docID(). 2. All docs in range [docID(), docIDRunEnd()) match this iterator." The only exception: "It is illegal to call this method when the iterator is exhausted or not positioned." The method is public, without @lucene.internal or @lucene.experimental.
  • Lucene enforces it. #14390 added the postings shortcut together with CheckIndex.checkDocIDRuns, which rejects a run end <= doc; AssertingPostingsEnum asserts it too.
  • The limit is supported. IndexWriter.MAX_DOCS = Integer.MAX_VALUE - 128 is the "Hard limit on the maximum number of documents that may be added to the index" (IndexWriter.java:202-208). TestIndexWriterMaxDocs#testExactlyAtTrueLimit (:47-89) adds exactly MAX_DOCS documents with one StringField, calls forceMerge(1) and closes a test directory, which runs CheckIndex.
  • The reader handles the sentinel elsewhere. Impacts.numLevels() (Lucene104PostingsReader.java:1358).
  • History. The bodies, comments and reviews of #14390, #14693 and #15160 never mention the NO_MORE_DOCS level-1 sentinel or doc IDs near 2^31; no comment, test, CHANGES.txt or MIGRATE.md entry allows Integer.MIN_VALUE.
  • Precedent. #16161 "SkipBlockRangeIterator: Don't extend docIdRunEnd into sparse blocks" (merged 2026-06-01) fixed the same class of bug, a run end extended up the skip levels without a density check, in the doc-values skipper iterator.
The devil's-advocate check214 words

The strongest case for "not a bug": (1) nobody runs a single segment within 8,192 docs of 2^31; (2) the first repros wrote postings through @lucene.experimental codec classes and a hand-built SegmentInfo instead of IndexWriter; (3) the sentinel looks meant to make the density test fail, so the author assumed doc IDs stay far from 2^31; (4) no query returns a wrong result. A later reading-only adversary also gave a procedural "not real" because it could not run code; on the merits it agreed with the root cause and the fix.

Why it fails: (1) the limit is documented and has its own test; (2) the same value at the same doc was reproduced on a segment that IndexWriter wrote and DirectoryReader opened, and the codec-level test only feeds the default writer legal doc IDs below MAX_DOCS; (3) that assumption is written nowhere, the contract has no exception, and the reader's own numLevels() handles the sentinel; (4) low impact lowers the priority, it does not make a false corruption report intended. Nor is it a case of an absurd parameter that then fails loudly: the parameter is Lucene's own tested limit, and the loud failure is a false report on a valid segment that recommends removing it. Verdict: a defect, low priority.

Suggested fix

#

Recommended Guard the shortcut against the sentinel, in all three readers

Skip the level-1 shortcut when level1LastDocID is the NO_MORE_DOCS sentinel: level1IsDense = level1LastDocID != NO_MORE_DOCS && (the existing equality), in the Lucene104 reader and in the Lucene101 and Lucene103 readers of backward-codecs. Reader-only, no format change; the test passes and the closest suites, including the nightly testDocIDRunEnd, stay green.

int level0DocCountUpto = docFreq - docCountLeft;
// After the last complete level-1 block, level1LastDocID is the NO_MORE_DOCS sentinel:
// there is no level-1 block to extend the run into.
boolean level1IsDense =
    level1LastDocID != NO_MORE_DOCS
        && level1LastDocID - level0LastDocID == level1DocCountUpto - level0DocCountUpto;
if (level1IsDense) {
  return level1LastDocID + 1;
}
return level0LastDocID + 1;

Guard the shortcut against the sentinel, in all three readers (validated by the checks) (recommended)

#

+12/-3 in Lucene104PostingsReader, backward_codecs/lucene101/Lucene101PostingsReader and backward_codecs/lucene103/Lucene103PostingsReader (the last two with two spaces less indentation). In a term's tail the method falls back to level0LastDocID + 1, the end of the current dense block; wherever a real level-1 block exists the shortcut is unchanged.

int level0DocCountUpto = docFreq - docCountLeft;
// After the last complete level-1 block, level1LastDocID is the NO_MORE_DOCS sentinel:
// there is no level-1 block to extend the run into.
boolean level1IsDense =
    level1LastDocID != NO_MORE_DOCS
        && level1LastDocID - level0LastDocID == level1DocCountUpto - level0DocCountUpto;
if (level1IsDense) {
  return level1LastDocID + 1;
}
return level0LastDocID + 1;

Trade-offs

  • One extra int comparison per call on a dense block. No result changes outside the bug window: for terms below 8,192 docs, and for tails far from 2^31, the equality is already false.
  • Reader-only: no format change; existing indexes written by 10.1.x to 10.6.x are read correctly without reindexing (the data on disk is valid).
  • Mirrors how Impacts.numLevels() already treats the sentinel.

Do not count the phantom level-1 block (validated by the checks)

#

In skipLevel1To, move level1DocCountUpto += LEVEL1_NUM_DOCS; below the if (docCountLeft < LEVEL1_NUM_DOCS) { level1LastDocID = NO_MORE_DOCS; break; } block, so the counter only counts level-1 blocks that exist. In the tail the shortcut's right side is then negative and never matches.

docCountLeft = docFreq - level1DocCountUpto;

if (docCountLeft < LEVEL1_NUM_DOCS) {
  level1LastDocID = NO_MORE_DOCS;
  break;
}
level1DocCountUpto += LEVEL1_NUM_DOCS;

Trade-offs

Fixes the state where it is created and also stops level1DocCountUpto from wrapping to Integer.MIN_VALUE for an all-docs term at MAX_DOCS (262,144 x 8,192 = 2^31 with the phantom block). The field is read only in skipLevel1To and docIDRunEnd, and the method is not entered again after the sentinel, but it touches the advance path and changes a field's meaning, so it needs a closer review; the two backward-codecs readers need the same change.

What the checks validated

The minimal test passes with only this change shadowed into the stock main jar, assertions on and off. No suites were run.

Downstream note

#

Tools that run CheckIndex at level 2 or higher on segments near 2^31 documents and act on the verdict automatically, for example with -exorcise, would drop a healthy segment.

How it was found

#

While modelling the Lucene104 postings reader's skip state, the finder noticed that the level-1 shortcut does not exclude the NO_MORE_DOCS sentinel. A Z3 bit-vector model with Java int semantics then gave a witness, proved the state unreachable below about 2^31 - 2^14 doc IDs, and the exact all-docs range, which a codec-level test and an all-docs run confirmed.

The method in full245 words

Method: semi-formal (the hypothesis came from code reading; the SMT model then produced the witness, the unreachability bound and the exact trigger range).

  • The finder's hunt unit modelled the Lucene104 reader's skip state. Reading docIDRunEnd next to skipLevel1To, it noticed that the level-1 shortcut compares a doc-ID gap measured from the NO_MORE_DOCS sentinel with a doc count that includes a phantom level-1 block.
  • A Z3 bit-vector model of the skip arithmetic with 32-bit Java int semantics: Q4a found a witness (level0LastDocID = 2,147,477,503, returning NO_MORE_DOCS + 1); Q4b showed the state unreachable while level0LastDocID < MAX_DOCS - 16,386; Q4c gave the all-docs trigger range, maxDoc in [2,147,475,712, MAX_DOCS] with the unique count k = 262,143 of complete level-1 blocks.
  • A codec-level JUnit on the stock jar failed on main (assertions on and off) and on 10.4.0 and 10.5.2 (assertions on). A run on a separate test host wrote 2,147,475,712 postings of an all-docs term in 10.7 s and failed a CheckIndex-style loop at doc 2,147,475,456, the first doc of the predicted tail block.
  • The unit's postings differential (191 million checks, 0 mismatches) never reached doc IDs near 2^31; its mutant "level-1 density always true" was killed, so the shortcut is exercised at ordinary scale.
  • Cross-model reviews, an independent reproducer, a devil's advocate and an adjudication then confirmed it; the repro was later cut to the one test above, and a tie-break on current main reproduced it on an IndexWriter-built segment.

LFV-170, snapshot of 2026-11-03

Registry title
Postings docIDRunEnd() returns Integer.MIN_VALUE for dense blocks after a term's last level-1 skip block when doc IDs are within 8,192 (4,096 before 10.4) of 2^31, so CheckIndex at level 2 or higher reports a healthy segment of about 2^31 documents as corrupt
Area
codecs / postings reader (Lucene104 BlockPostingsEnum#docIDRunEnd, also the Lucene101 and Lucene103 readers); index / CheckIndex
Priority
Low, rank 910: The postings docIDRunEnd() returns Integer.MIN_VALUE near 2^31 docs, so CheckIndex flags a healthy segment as corrupt while query results stay exact.
Impact class
wrong error
Impact note
Hits only holders of a single segment within about 8,000 doc IDs of IndexWriter.MAX_DOCS (maxDoc >= 2,147,475,712 for a term in every document, for example a shard force-merged to one segment at the hard limit) who run CheckIndex at level 2 or higher (or the test framework's check-on-close): they get a false 'Run end -2147483648 is <= doc ID ...' corruption report on a healthy segment, which -exorcise would turn into a dropped segment; default codec, every release since 10.2.0; query results stay exact (executed), only a dense-run shortcut is lost on at most 31 tail blocks per term.
Summary
You have one segment of about 2^31 documents (within about 8,000 docs of IndexWriter.MAX_DOCS) with a term whose postings are dense near the end of the doc-ID space, for example a term that every document has, and you call docIDRunEnd() on its postings or run CheckIndex at level 2 or higher. You expect docIDRunEnd() to return a doc ID greater than the current one, as its javadoc promises, and CheckIndex to pass. Instead, in the dense blocks after the term's last full 8,192-doc level-1 skip block (4,096 docs in 10.2-10.3), the default postings reader returns Integer.MIN_VALUE and CheckIndex reports the healthy segment as corrupt ('Run end -2147483648 is <= doc ID 2147475456'); query results stay correct, and the repro writes the postings through the public codec API rather than indexing 2^31 documents with IndexWriter.
