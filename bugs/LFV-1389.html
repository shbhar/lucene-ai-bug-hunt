The synonym factories do not trim names in a comma-separated synonyms file list: synonyms="a.txt, b.txt" fails to load b.txt

List two synonym files with a blank after the comma, synonyms="a.txt, b.txt", and the analyzer fails to build with IOException: Resource not found ...: b.txt: the synonym factories ask for the file " b.txt", blank included. The eight other callers of the shared splitter splitFileNames trim each name; every release since 4.0.0 is affected.

The finding in 30 seconds

#

The shared splitter splitFileNames documents that it does not trim list items. Its eight other callers trim each name (stop words, types, mappings, ICU rule files, ...). The two synonym factories pass each name unchanged to openResource, at SynonymGraphFilterFactory.java:191 and SynonymFilterFactory.java:194.

Background

#
  1. Analysis factories that read word or rule files (stop words, keep words, mappings, synonyms, ...) take a file name argument that may list several files separated by commas; a comma inside a name is escaped as \,.
  2. The factory asks its ResourceLoader for each name. FilesystemResourceLoader (what CustomAnalyzer.builder(dir) uses) looks the exact string up in dir, then hands it to its delegate loader (for CustomAnalyzer.builder(dir), a classpath loader), which throws Resource not found if it has no such resource either.

The finding, step by step

#
  1. Write two synonym files, a.txt (foo => baz) and b.txt (qux => quux), and build CustomAnalyzer.builder(dir).withTokenizer("whitespace").addTokenFilter("synonymGraph", "synonyms", "a.txt, b.txt").
  2. You expect both files to load, so foo qux analyzes to [baz, quux]. The same list form loads both files for the stop, keepWord and mapping factories, and Lucene's own tests use it ("stop-1.txt, stop-2.txt").
  3. Instead addTokenFilter throws java.io.IOException: Resource not found (...): b.txt (note the two blanks). The factory splits the list at the comma into "a.txt" and " b.txt" and asks the resource loader for " b.txt" as is, which does not exist.
  4. Without the blank, "a.txt,b.txt", both factories give [baz, quux]: deleting the blank is the workaround. The deprecated synonym factory fails the same way.

Who is affected

#

Anyone who lists two or more synonym files for synonymGraph (or the deprecated synonym) with a blank after the comma. Opt-in: no stock analyzer uses the filter. The failure is loud, at build time, and the message shows the blank; only if a file literally named " b.txt" exists does that file load instead.

Mechanism, terms and numbers495 words

SynonymGraphFilterFactory (and the deprecated SynonymFilterFactory) accept several synonym files as a comma-separated list in the synonyms argument. They split the list with the shared helper splitFileNames, which documents that it does not trim list items, and pass each item unchanged to ResourceLoader.openResource. So "a.txt, b.txt" asks for " b.txt", which does not exist, and building the analyzer fails with IOException: Resource not found ...: b.txt.

The eight other callers of splitFileNames trim each name, so the same list works for the stop, keep-word, type, mapping, stemmer-override and word-delimiter factories, and Lucene's own tests use that form for the stop, keep-word and type factories (and for CommonGrams, CommonGramsQuery, ProtectedTerm and SuggestStop). The synonym factory itself trimmed these names from 2008 (SOLR-663) until the 2011 rewrite LUCENE-3233 dropped the trim without comment. The failure is loud, happens once when the analyzer is built, and the message shows the blank; deleting it works around the bug. The fix is one word per factory: loader.openResource(file.trim()). Its one compatibility cost: a file whose name really starts with a blank, which stock main loads from such a list, could no longer be named there.

Mechanism (Lucene main 5adff78bb168)

#
  1. SynonymGraphFilterFactory.inform calls loadSynonyms (SynonymGraphFilterFactory.java:161).
  2. List<String> files = splitFileNames(synonyms); (:188). splitFileNames is splitAt(',', fileNames) (AbstractAnalysisFactory.java:337-339), whose javadoc says: "List items can contain comma characters escaped by backslash '\'. Whitespace is NOT trimmed from the returned list items." (:341-344). So "a.txt, b.txt" becomes ["a.txt", " b.txt"].
  3. Each item goes to the loader unchanged: parser.parse(new InputStreamReader(loader.openResource(file), decoder)); (:191). This is the fix site. The deprecated SynonymFilterFactory has the same loop (SynonymFilterFactory.java:191-194).
  4. FilesystemResourceLoader.openResource resolves " b.txt" literally, finds nothing and hands the name to its delegate loader, here the classpath loader that CustomAnalyzer.builder(Path) passes (CustomAnalyzer.java:114-115), which throws IOException: Resource not found ...: b.txt (FilesystemResourceLoader.java:84-89).

The other splitFileNames callers trim

#

AbstractAnalysisFactory.getWordSet (:292, getLines(loader, file.trim())) and getSnowballWordSet (:322, openResource(file.trim())), TypeTokenFilterFactory.java:74, MappingCharFilterFactory.java:73, StemmerOverrideFilterFactory.java:74, WordDelimiterFilterFactory.java:140, WordDelimiterGraphFilterFactory.java:143 (each getLines(loader, file.trim())) and ICUTokenizerFactory.java:92 (the rulefiles path, .trim()). That is 8 trimming callers of splitFileNames against the 2 synonym factories. ProtectedTermFilterFactory calls splitAt directly: its comma-list call (wrappedFilters, :118-121) trims each item; its second call (:135-136) splits a filterName.argKey parameter key at the dot, not a file list, and does not trim.

One list-taking factory does not use splitFileNames: HunspellStemFilterFactory (@lucene.experimental) splits its dictionary list with dictionaryFiles.split(",") (:97) and opens each item untrimmed (:105), so on main dictionary="a.dic, b.dic" fails with Resource not found (...): b.dic while "a.dic,b.dic" builds. It is a separate fix site, not part of this patch.

Controls (executed on main)

#
  • "a.txt,b.txt": [baz, quux] for both synonym factories; "a.txt" alone: [baz, qux].
  • "a.txt, b.txt" for stop, keepWord and mapping: both files load, the same result as without the blank.
Exposure and likelihood143 words
  • Who: users of the synonym filter who give it several files and type the list the way Lucene's own sibling-factory tests do, with a blank after the comma. One configuration string, no scale, the same with assertions on and off.
  • Opt-in: no stock Lucene analyzer uses the synonym filter. SynonymGraphFilterFactory is tagged @lucene.experimental (SynonymGraphFilterFactory.java:72), but it is the non-deprecated replacement the deprecated factory points users to (SynonymFilterFactory.java:73-74).
  • Effect: the analyzer, and any field type or schema that uses it, fails to build with IOException: Resource not found ...: b.txt. No index or query is affected; deleting the blank works around it.
  • Downstream: Solr's reference guide documents the synonyms argument as "a comma-separated list of paths", and Solr's resource loader does not trim either (by reading; no Solr report was found). Elasticsearch and OpenSearch use their own synonym factories.

Why it looks unintended

#
  • splitAt keeps whitespace ("Whitespace is NOT trimmed from the returned list items"); of the ten callers of splitFileNames, only the two synonym factories do not trim.
  • Lucene's own tests pass lists like "stop-1.txt, stop-2.txt" to seven sibling factories.
  • The synonym factory trimmed these names from 2008 (SOLR-663) until the 2011 rewrite (LUCENE-3233) dropped the trim without comment.
The full argument202 words
  • The helper keeps whitespace; its other callers trim: the "Whitespace is NOT trimmed" sentence came with LUCENE-8273 (d91273ddf0b, 2018), when splitAt was pulled out of splitFileNames; the comma-list call added in that commit, ProtectedTermFilterFactory's wrappedFilters split, trims each item (:118-121), and so do the eight other splitFileNames callers.
  • Lucene's tests use the blank form for the siblings: TestStopFilterFactory.java:39 ("stop-1.txt, stop-2.txt"), TestKeepFilterFactory.java:38 ("keep-1.txt, keep-2.txt"), TestTypeTokenFilterFactory.java:37, TestCommonGramsFilterFactory.java:56, TestCommonGramsQueryFilterFactory.java:60, TestProtectedTermFilterFactory.java:48, and in lucene/suggest TestSuggestStopFilterFactory.java:43. No synonym test uses a list at all.
  • History: SOLR-663 (4ac6ce3190d, 2008-07-30, "Allow multiple files for stopwords, keepwords, protwords and synonyms") added the lists with loader.getLines(file.trim()) in the synonym factory as in the word-list factories. LUCENE-3233 (015ecfa0a02, 2011-07-11) added FSTSynonymFilterFactory with loader.openResource(file), no trim, while the SlowSynonymFilterFactory kept in the same commit still called loader.getLines(file.trim()). Neither the commit nor its issue (#4306) mentions whitespace.
  • No synonym javadoc defines a list grammar either way: the class javadoc shows a single file (SynonymGraphFilterFactory.java:43-52). The expectation is therefore implied, by the helper's division of labour, the uniform convention, the tests and the history, which is why the adjudication rated confidence medium.
The devil's-advocate check152 words

The strongest case, made by one executed cross-model review (OpenAI GPT-5.6, refute lens): resource names are literal. splitAt documents that it keeps whitespace, ResourceLoader.openResource only says "Opens a named resource", no synonym javadoc defines a list grammar, and a file literally named " second.rules" is legal on POSIX: the reviewer loaded one from "first.rules, second.rules" on stock main and showed the trim fix breaks that.

Why it fails: no other factory that uses splitFileNames can name that file in a list today, the synonym factory itself did not allow it before 2011, and no synonym test or javadoc uses a list at all; splitAt's sentence describes what the helper returns, and its other callers trim. The reviewer agreed with every fact (reproduced, same root cause, legal input) and disagreed only on the contract. The case is real, though unlikely: it is a compatibility note, not a reason to keep the behaviour.

Suggested fix

#

Recommended Trim each name where the synonym factories open it (recommended)

Trim each name where the synonym factories open it: loader.openResource(file.trim()) in SynonymGraphFilterFactory and the deprecated SynonymFilterFactory, one word each, as the eight other splitFileNames callers do. Validated on 5adff78bb168: the repro passes, and so do the module's 1,910 tests and its format, lint and forbidden-API checks.

    List<String> files = splitFileNames(synonyms);
    for (String file : files) {
      decoder.reset();
      parser.parse(new InputStreamReader(loader.openResource(file.trim()), decoder));
    }

      try (final Reader isr = new InputStreamReader(loader.openResource(file.trim()), decoder)) {

How it was found

#

Semi-formal: a bounded differential comparison of how 19 list-taking analysis factory cases split a two-file list, each given 3 whitespace forms (a, b, a ,b, a,b) and compared with a,b: 57 checks per assertion mode, 6 mismatches in each, all six in the two synonym factories. A reading of the history came second.

The method in full138 words
  • Comparison: each of 19 list-taking factory cases was built through CustomAnalyzer with a FilesystemResourceLoader and given the same two files as a,b and in three whitespace forms: a blank after the comma, before it, and before the first name. Each form's output was compared with that of a,b. Only synonymGraph and synonym disagreed, in all three forms each (IOException: Resource not found), with assertions on and off (57 checks in each mode). The 19 cases did not include the Hunspell dictionary list, the ICU rule files, commonGramsQuery or the deprecated wordDelimiter factory.
  • History: reading SOLR-663 (4ac6ce3190d) and LUCENE-3233 (015ecfa0a02) showed that the trim existed and was dropped in 2011.
  • Reduction: one public-API JUnit test (Minimal repro), then an independent reproduction, cross-model reviews, an intended-behaviour review and an adjudication (see Independent checks).

History

#

Introduced by LUCENE-3233 (015ecfa0a02, 2011-07-11), which dropped the file.trim() SOLR-663 had added in 2008; LUCENE-6664 copied the loop into SynonymGraphFilterFactory (6.4.0). Every Lucene release from 4.0.0 to 10.6.0 and main is affected; Solr 3.3.0 passes, 3.4.0 fails. Not fixed upstream.

Versions tested8 rows

Introduced by LUCENE-3233 "improve ram/perf of SynonymFilter, add wordnet parsing, nuke contrib/wordnet" (Robert Muir; 015ecfa0a02 on trunk, a52015db05f on branch_3x; author date 2011-07-11; SVN era, no PR; issue #4306). Its new FSTSynonymFilterFactory opened each name with loader.openResource(file); the factory it replaced had called loader.getLines(file.trim()) since SOLR-663 (4ac6ce3190d, 2008-07-30).

The factories moved from Solr into Lucene's analysis module with LUCENE-2510 / LUCENE-4044 (677846e6a0f, 2012-07-25), so 4.0.0 is the first affected Lucene release. In 4.x a luceneMatchVersion below 3.4 still went through the trimming slow factory (removed for 5.0.0); every 3.4+ match version took the untrimmed path. LUCENE-6664 (c0467bb9291, Mike McCandless, 2016-12-22) copied the untrimmed loop into the new SynonymGraphFilterFactory (first release 6.4.0). Upstream main still has it (re-checked read-only on 2026-11-05 at d060c053bd8).

Summary
You build an analyzer with the synonymGraph filter and synonyms="a.txt, b.txt" (two synonym files, a blank after the comma) and expect both files to load, as the same list form does for the stop, keep-word, type and mapping factories. Instead the build throws IOException 'Resource not found ...: b.txt': the factory splits the list but asks the resource loader for ' b.txt' with its leading blank, while every other caller of the shared file-list splitter trims each name. The same list without the blank works, and the deprecated SynonymFilterFactory fails the same way.
Introduced
015ecfa0a02 (LUCENE-3233 'improve ram/perf of SynonymFilter, add wordnet parsing, nuke contrib/wordnet', by Robert Muir, on trunk; the same change on branch_3x is a52015db05f; SVN era, no pull request; JIRA LUCENE-3233, apache/lucene#4306 after the migration) [read; before/after executed: Solr 3.3.0 passes, Solr 3.4.0 fails]: its new FSTSynonymFilterFactory opened each listed file with loader.openResource(file), without the file.trim() that SOLR-663 (4ac6ce3190d, 2008) had given the synonym factory, while the SlowSynonymFilterFactory kept in the same commit still called loader.getLines(file.trim()); LUCENE-6664 (c0467bb9291 on trunk, 68db0334089 on branch_6x, 2016-12-22, by Mike McCandless) copied the untrimmed loop into the new SynonymGraphFilterFactory (2011-07-11 (author date 2011-07-11T12:58:52Z on trunk, 13:59:45Z on branch_3x); SynonymGraphFilterFactory 2016-12-22)
