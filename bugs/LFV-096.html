An addBatch that declares a new term-vector field but indexes no row leaves a commit that cannot be opened

In the experimental column API, a batch that declares a new term-vector field but indexes no row leaves a segment that promises term vectors it never wrote. After one addDocument, one empty batch and commit(), DirectoryReader.open throws CorruptIndexException (10.5.0 to main).

The bug in 30 seconds

#

Lucene creates a segment's term-vector writer only when a document finishes indexing. The column API registers a batch's fields before it indexes any row, so a batch without rows can register a term-vector field and never create the writer.

  1. Add 1 document with addDocument, then call addBatch with a batch of numDocs() == 0 whose only column, body, is a text field with term vectors that this segment has not seen yet.
  2. You expect the empty batch to change nothing: after commit(), DirectoryReader.open returns 1 document, as it does when the same new field arrives through addDocument.
  3. Instead commit() succeeds and DirectoryReader.open throws CorruptIndexException, caused by "No sub-file with id .tvd found in compound file _0.cfs". The segment's FieldInfos say body has term vectors; its compound file holds 12 entries, norms for body among them, but no term-vector file.
  4. Why: addBatch registers body ("has term vectors") before it indexes any row. The term-vector writer is created only when a document finishes, and flush writes term-vector files only if that writer exists. No row, no writer, no files.
  5. The same happens when the batch is rejected (a later column conflicts with the schema: IllegalArgumentException) or its cursor throws on the first value. With the default config, commit() and then close() throw instead.

Who is affected

#

Users of the experimental column API (addBatch, updateDocuments with a ColumnBatch; 10.5.0 to main), with the default config and codec. It takes a batch that declares a term-vector field new to the in-memory segment and indexes no row, another document already in that segment, and no later document indexed there before the flush.

Mechanism, terms and numbers635 words

IndexWriter#addBatch (the experimental column API, 10.5.0 and later) registers the field of every column in the segment's FieldInfos before it indexes any row. For a field with term vectors that only sets a flag; the term-vectors writer is created when the first document finishes, and flush writes term-vector files only if that writer exists. A batch that indexes no row (numDocs() == 0, a later column rejected by the schema check, or a cursor that throws on its first nextDoc()) therefore leaves FieldInfos that declare term vectors and no .tvd/.tvx/.tvm files. A document already in the same in-memory segment is flushed into that segment, and the commit cannot be opened: DirectoryReader.open throws CorruptIndexException, or, with the default config and the two failure triggers, commit() and close() throw. The per-document path is safe because it always finishes the document it started.

Terms

#
  • FieldInfos: the per-segment list of fields and what each one stores (postings, norms, term vectors, doc values, points, vectors). A reader opens one file set per feature that FieldInfos declare.
  • Term vectors: an optional per-document copy of a field's terms (FieldType#setStoreTermVectors), stored in .tvd, .tvx and .tvm files.
  • addBatch / ColumnBatch: the experimental column-oriented indexing API (10.5.0). A batch has numDocs() documents and a list of columns, one per field feature; each column hands out a cursor over (doc, value) pairs.
  • In-memory segment: the documents an IndexWriter thread has buffered since its last flush; a flush or commit writes them as one segment.

The bug, step by step (main a9779ef3c193)

#
  1. IndexingChain.processBatch (IndexingChain.java:717) first loops over the columns (:726-780), then calls initAndValidateFields (:782-785). In column order, that creates the FieldInfo of each new field (:692-693) or checks an existing field's schema (assertSameSchema, :695, which throws IllegalArgumentException on a conflict).
  2. Creating an indexed field calls PerField.setInvertState() (:1415-1416). For a field with term vectors it calls termVectorsWriter.setHasVectors() (:1916-1918), which only sets a flag (TermVectorsConsumer.java:112-114).
  3. The term-vectors writer is created only in TermVectorsConsumer.finishDocument (:117-128), when a document finishes. flush writes term vectors only if (writer != null) (:78-89).
  4. The batch path finishes documents only in its row loop (IndexingChain.java:889, termsHash.finishDocument at :937), and asks each row column for its first document before that loop (:875). No document is finished when (a) numDocs() is 0, (b) step 1 threw for a later column, after body was created, or (c) the cursor throws at :875.
  5. For (a) reserveDocs returns at once (DocumentsWriterPerThread.java:226-230); for (b) and (c) updateBatch treats the exception as non-aborting and marks the batch's reserved documents deleted (:349-354). The writer keeps going, and the earlier document is flushed into the same segment.
  6. SegmentCoreReaders opens the term-vectors reader whenever FieldInfos declare term vectors (SegmentCoreReaders.java:120-128) and turns the missing file into CorruptIndexException (:141-144).

The per-document path is safe: processDocument calls termsHash.startDocument() (IndexingChain.java:598) before it creates any FieldInfo and termsHash.finishDocument in its finally block (:662-681), so even a rejected document creates the writer, and flush fills empty entries.

The numbers

#

Default codec, NoMergePolicy, one document (id = "0"), then the batch. Right after the batch the in-memory state is body(tv=true), hasVectors=true, writer=null. The committed segment _0 has maxDoc 1 (empty batch), 2 (rejected batch, 1 deleted) or 4 (cursor fails, 3 deleted), 1 live document, and 12 or 16 compound sub-files: postings, norms (also for body), stored fields, FieldInfos and, for (b), doc values, but no term vectors. DirectoryReader.open throws. The same rejection through addDocument creates the writer, writes .tvd, .tvm and .tvx, and opens with 1 document.

Exposure and likelihood441 words
  • Who. Applications on IndexWriter#addBatch (@lucene.experimental, IndexWriter.java:1535) or updateDocuments(Term|Query, ColumnBatch), which reaches the same code (IndexWriter.java:1554, :1570; by code reading, not executed). Released in 10.5.0, 10.5.1 and 10.5.2; branch_10_6 has the same code.
  • What it needs. A batch that declares a term-vector field new to the in-memory segment and indexes no row: empty, rejected by a later column's schema check, or a cursor that fails on its first value. At least one other live document in that segment. For a rejected batch, the term-vector column must be checked before the failing one. Default IndexWriterConfig and codec (also SimpleText, run with the empty batch only); deterministic; any scale. That another live document is needed was run for the empty batch; for the other two triggers it is read from the code. The three triggers are examples: any exception after the batch's FieldInfos are created and before its first row is finished does the same (code reading).
  • What masks it. A later document indexed in the same segment before it flushes creates the writer and repairs the segment: an addDocument (run) or, by code reading, a batch with an inverted column and a row. A later doc-values-only batch does not, and an index sort does not either (run with the empty batch).
  • What it does.
    • NoMergePolicy, or the default config with an empty batch: commit() succeeds and writes a commit no reader can open; with the default deletion policy it replaces the previous good commit.
    • Default config, rejected or failing-cursor batch: commit() throws CorruptIndexException (merge-on-commit opens the new segment); the writer stays open and not tragic; one more addDocument plus commit() fails again, and close() throws; on a new index nothing is ever committed. Only these two fail inside commit() because they leave the segment 50% and 75% deleted, so the default merge policy merges it at commit, which opens it (code reading). After an earlier good commit, rollback() closes the writer; a new writer opens the previous commit, without the document added since.
    • NRT: DirectoryReader.open(writer) throws the same exception.
    • CheckIndex reports the segment broken (numBadSegments=1, totLoseDocCount=1); -exorcise would drop it with its documents.
  • Loud, not silent. No wrong results; every failure is an exception (CorruptIndexException, or IndexNotFoundException when a new index never got a commit). Postings, stored fields and doc values of the documents are written; only the term-vector files are missing.
  • How likely. Rare in steady state: a pipeline whose batches always carry the term-vector column with rows heals itself. It sits on the error path, where one bad batch becomes an unopenable commit instead of one rejected batch.

Why it is a bug, not intended

#
  • Empty batches are legal and tested upstream (testEmptyBatch), and batch failures are designed to leave a usable writer (test*ThrowMidBatchRecovers).
  • The per-document path writes term-vector files even for a rejected document, and the same code writes norms "even if no documents actually succeed".
  • #13369 fixed the same FieldInfo-without-file state for points as a bug.
The full argument255 words
  • Commit contract. IndexWriter#commit: "Commits all pending changes ... such that a reader will see the changes" (IndexWriter.java:4189-4190).
  • Empty batches are legal. ColumnBatch#numDocs only requires doc ids "in the range [0, numDocs())" (ColumnBatch.java:28-31); reserveDocs returns at once for n == 0 (DocumentsWriterPerThread.java:228-230); upstream TestColumnBatchIndexing#testEmptyBatch (:924) adds an empty batch and checks that the "Writer still functions for follow-up work" (its batch has no columns).
  • Batch failures are non-aborting by design. updateBatch: "the iterator threw an exception that is not aborting / go and mark all docs from this block as deleted" (DocumentsWriterPerThread.java:350-353); #16270 aligned it with updateDocuments; upstream test*ThrowMidBatchRecovers (TestColumnBatchIndexing.java:682, :740, :794, :841) throw from cursors and assert the writer recovers. addDocument's javadoc: after an exception "the index will be consistent" (IndexWriter.java:1465).
  • The rule in the same code. setInvertState: "Even if no documents actually succeed in setting a norm, we still write norms for this segment" (IndexingChain.java:1912-1913). The broken segment does have norms for body; only term vectors lack the guarantee, and only on the batch path.
  • Precedent. #13369 (9.11.0, closing #13353): "Fix NRT opening failure when soft deletes are enabled and the document fails to index before a point field is written", the same FieldInfo-without-file state for points, fixed as a bug.
  • Untested corner. No upstream test combines term vectors with column batches (none of the 8 test files that use ColumnBatch). The #15990 review never mentions term vectors.
The devil's-advocate check208 words

The strongest case for "intended" (a cross-model reviewer rated it moderate): Lucene deliberately avoids term-vector files until a document uses them. LUCENE-2776 (2010) stopped creating the term-vector writer at flush when no document had used it, and at first let the reader tolerate exactly this state: "If all documents flushed in a segment had hit non-aborting exceptions, it's possible that FieldInfos.hasVectors returns true yet the term vector files don't exist." The API is @lucene.experimental, an empty batch with columns is odd, and a failing cursor is the caller's code.

Why it fails: LUCENE-2811 removed that reader tolerance 17 days later ("it should only be opened if they exist"), and today a missing term-vector file is corruption. Since then the per-document path has kept the invariant by finishing every document it starts, including rejected ones. Empty batches and non-aborting batch failures are accepted and tested upstream. @lucene.experimental allows API changes, not a commit that cannot be opened. Before LUCENE-2776, flush created the writer for exactly this case ("all documents seen in this segment hit non-aborting exceptions"); fix option A restores that guard, keyed on hasVectors. Verdict: a defect (the independent reproducer, cross-model reviews, the devil's advocate and the adjudication agree). Cite LUCENE-2776 and LUCENE-2811 in the issue.

Suggested fix

#

Recommended A. TermVectorsConsumer.flush creates the writer when term vectors are declared (validated)

Recommended and validated: in TermVectorsConsumer.flush, create the term-vector writer when FieldInfos declare term vectors but no document created it, so flush writes an empty entry per document (5 lines). It fixes all three triggers; the repro and 305 tests in 18 related classes pass with assertions on and off.

// TermVectorsConsumer.flush, before "if (writer != null) {"
if (writer == null && hasVectors) {
  // A field with term vectors was registered (e.g. by an empty or rejected column batch) but no
  // document finished afterwards: still write (empty) term vectors, FieldInfos declare them.
  initTermVectorsWriter();
}

A. TermVectorsConsumer.flush creates the writer when term vectors are declared (validated) (validated by the checks) (recommended)

#

If hasVectors is set and no document created the writer, create it in flush; the existing fill(numDocs) then writes an empty entry for every document. This is what the per-document path already writes after a rejected document. With an index sort, SortingTermVectorsConsumer.flush calls super.flush and overrides initTermVectorsWriter, so the same lines create its temporary writer.

// TermVectorsConsumer.flush, before "if (writer != null) {"
if (writer == null && hasVectors) {
  // A field with term vectors was registered (e.g. by an empty or rejected column batch) but no
  // document finished afterwards: still write (empty) term vectors, FieldInfos declare them.
  initTermVectorsWriter();
}

Trade-offs

  • A segment that registered a term-vector field but has no document with term vectors now gets small term-vector files with empty entries, instead of none. Format and reader are unchanged.
  • flush's assert numDocs > 0 still holds: a thread state with no documents is never flushed (guards at DocumentsWriterFlushControl.java:367, :584; asserts at DocumentsWriterPerThread.java:428, :444).
  • Open draft PR #16269 refactors TermVectorsConsumer and keeps the writer != null guard; a patch may need a rebase if it lands first.

B. Create the writer when the flag is set (not run)

#

Call initTermVectorsWriter() from setHasVectors(), or from processBatch right after initAndValidateFields when a term-vector field was registered.

Trade-offs

setInvertState() does not throw IOException today, so it needs plumbing; the batch-only variant fixes this caller and leaves the invariant implicit for the next one; term-vector outputs open at field registration instead of at flush.

C. Return early from processBatch when numDocs() == 0 (not sufficient)

#

Skips the empty batch before any field is registered.

Trade-offs

Fixes trigger (a) only: the rejected-batch and failing-cursor triggers stay broken. Only useful combined with A or B.

D. Do not leave FieldInfos behind from a batch that indexes no row (not run)

#

Create FieldInfos only once the row pass starts, or roll them back when the batch fails.

Trade-offs

A much larger change to processBatch, whose column pass needs the per-field state; field numbers are shared index-wide; and it would differ from the per-document path, which keeps the FieldInfo of a rejected document.

Rejected: let the reader tolerate missing term-vector files

#

What LUCENE-2776 did in 2010.

Trade-offs

LUCENE-2811 removed that tolerance; it would hide real corruption.

Downstream note

#

Not a security issue (the application builds the batch), but a service that forwards client-supplied batches to addBatch can turn one empty or malformed batch into a commit that no reader can open.

How it was found

#

A bounded-exhaustive harness indexed every small single-column batch shape both through addBatch and row by row and compared the two indexes: 29,408 scenarios, 32 of which left an index that could not be opened, all with a term-vector column, zero rows and one document before the batch. The other two triggers came from reading the code.

The method in full185 words

Method: bounded-exhaustive translation validation (the hunt's semi-formal tier) on the real jar, a hunt unit (columnar addBatch).

  • Scope A: one column, 26 column specs (long, binary, dictionary, float and byte vector and token-stream columns; stored, inverted with every index option and term vectors with positions, offsets and payloads, every doc-values type, skip index, 1-D and 2-D points), dense and every sparse pattern for numDocs 0 to 3, a document before and/or after the batch, 4 writer configurations (default, index sort, parent field, soft deletes). Each scenario was indexed through addBatch and through the row-by-row reference, and the indexes were compared; with assertions on and off.
  • Result: 29,408 scenarios; 32 corrupt indexes on the batch side, exactly the term-vector specs with numDocs = 0 and one document before the batch. A mutant (a +1 on one value) was caught (256 mismatches), so the comparison is not vacuous.
  • The finder minimised it by hand into a JUnit; the rejected-batch and failing-cursor triggers came from reading processBatch afterwards. An independent reproducer, cross-model reviews (OpenAI GPT-5.6) and an intended-behaviour devil's advocate checked it before the adjudication confirmed it.

Versions tested6 rows

Introduced by #15990, "Add experimental columnar indexing api" (author @Tim-Brooks, merged by @ChrisHegarty on 2026-05-14 as 3d89568155799 on main), backported the same day by #16066 (3ec3bff01b15, branch_10x), which ships in 10.5.0. Bug record

#

LFV-096, snapshot of 2026-10-29

Registry title
An addBatch that registers a new term-vector field but frames no rows leaves a segment whose FieldInfos declare term vectors with no term-vector files, so the committed index cannot be opened
Area
index / columnar addBatch (term vectors)
Priority
Medium, rank 125: An empty, rejected or failing addBatch that declares a new term-vector field can leave a commit that DirectoryReader.open rejects, catastrophic but loud and an unusual edge sequence on an experimental API.
Impact class
index unusable
Impact note
Applications on the experimental column API (IndexWriter#addBatch, 10.5.0 and later) that send a batch which declares a term-vector field new to the in-memory segment but frames no row (numDocs()==0, a batch rejected by the schema check of a later column, or a column cursor that throws before the first row) while that segment holds another live document and no later document is framed in it before the flush; default IndexWriterConfig and codec, ordinary scale, deterministic; then DirectoryReader.open fails for the whole index, or (default config, rejected-batch and failing-cursor triggers) commit() and close() keep throwing CorruptIndexException; released 10.5.0-10.5.2.
Summary
You add a document, then call IndexWriter#addBatch with a column batch that declares a new text field with term vectors but adds no row: the batch is empty, or it is rejected with IllegalArgumentException because a later column conflicts with the existing schema, or its column cursor throws before the first row. You expect the earlier document to commit and the index to open, as it does when the same rejection happens through addDocument.
