The document suggester checks its reserved end byte U+0000 only in the raw value, so an analyzer that emits U+0000 hides suggestions

SuggestField rejects U+0000, the end byte of every entry in the suggester's FST, only in the raw value, not in the analyzed form. So with HTMLStripCharFilter, a (weight 1) next to a&#0; (weight 2) silently vanishes from a prefix query for a, and other inputs fail the commit under assertions.

The bug in 30 seconds

#

The document suggester stores each suggestion in an FST as its analyzed bytes, then the end byte 0x00, then one or more dedup bytes. SuggestField refuses U+0000 in the value you pass, but the analyzed form, which is what reaches the FST, is never checked.

  1. You index suggestions with an analyzer HTMLStripCharFilter + KeywordTokenizer: doc 0 a (weight 1), doc 1 a&#0; (weight 2). Both values are accepted: SuggestField rejects a raw U+0000, and a&#0; contains none.
  2. You expect PrefixCompletionQuery("a") with n = 100 to return both documents. With a&#1; (U+0001) instead of a&#0;, it does.
  3. Instead it returns only doc 1, with assertions on or off. The analyzer turned &#0; into U+0000, the end byte of every FST entry: a is stored as 61 00 00, a+U+0000 as 61 00 00 00. One entry is a prefix of the other, and the lookup drops the lower-weight one.
  4. With a&#0;&#0;, a, a, b, the second a entry (61 00 01) sorts after 61 00 00 00 00. With assertions on, commit() throws "inputs are added out of order" and closes the IndexWriter: 4 buffered documents lost. With them off, a query for a&#0;&#0; returns nothing, although a query for a still lists it.
  5. It has been there since the document suggester arrived in 5.1.0 (2015): 16 releases up to 10.5.2 and main fail the same way. A MappingCharFilter rule that outputs U+0000 triggers it too.

Who is affected

#

Users of the opt-in document suggester whose analyzer can turn accepted text into U+0000: the stock HTMLStripCharFilter on &#0; or &#x0;, or a char-filter mapping rule. In production, suggestions silently go missing, and a query ending in U+0000 can return extra ones; with assertions on, commit or merge closes the writer. Rare: misses need x and x+U+0000 in one segment.

Mechanism, terms and numbers1,138 words

The document (NRT) suggester stores every suggestion in an FST whose input is the analyzed form, then the end byte 0x00 (NRTSuggesterBuilder.END_BYTE), then one or more dedup bytes. Because 0x00 ends every entry, SuggestField reserves U+0000 and throws IllegalArgumentException for a value that contains it. It checks only the raw value, though; the analyzed form, which is what goes into the FST, is never checked, and the class javadoc invites "the usual Analyzers".

A stock char filter turns an accepted value into a reserved one: HTMLStripCharFilter decodes &#0; to U+0000, and a MappingCharFilter rule can do the same. Then the input of a (61 00 00) is a prefix of the input of a+U+0000 (61 00 00 00), and a second entry for a (61 00 01) sorts after a+U+0000+U+0000 (61 00 00 00 00). In production (assertions off) suggestions silently disappear: with a (weight 1) and a&#0; (weight 2) in one segment, a prefix query for a with n = 100 returns only the second document, and with a&#0;&#0;, a, a, b a prefix query for a&#0;&#0; misses the first document (a query for a still lists it). With assertions on, the second case fails the commit with FSTCompiler's "inputs are added out of order" AssertionError, which closes the IndexWriter. The same analyzer with &#1; (U+0001) indexes and finds everything. The bug came with the document suggester itself (5.1.0, 2015) and is in every release since; checking the analyzed form in CompletionTokenStream and throwing the same non-aborting IllegalArgumentException fixes these symptoms. The same in-band byte also gives a wrong extra hit on the query side, which that check does not remove: on main, a prefix query for a&#0; also returns a.

Terms

#
  • Document suggester: SuggestField (or ContextSuggestField) indexed with a completion postings format such as Completion104PostingsFormat, queried with SuggestIndexSearcher and a CompletionQuery such as PrefixCompletionQuery. It is @lucene.experimental and opt-in.
  • Analyzed form: the suggestion after the field's analyzer, concatenated by ConcatenateGraphFilter inside CompletionTokenStream. The FST is built from these bytes (UTF-8; U+0000 is the byte 0x00).
  • FST input: analyzed bytes + END_BYTE 0x00 ("Marks end of the analyzed input and start of dedup byte", NRTSuggesterBuilder.java:42-43) + a dedup byte 0, 1, 2, ... per entry with that analyzed form (:66-69, :81-97). FST inputs must be added in increasing byte order.

The bug

#
  1. Only the raw value is checked. The constructor loops over the value (SuggestField.java:86-96) and rejects isReserved characters: U+001F, U+001E and NRTSuggesterBuilder.END_BYTE U+0000 (:140-149), as its javadoc promises (:75-76).
  2. The analyzed form passes unchecked. SuggestField.tokenStream wraps the analyzer's stream in CompletionTokenStream (:103-120), whose incrementToken passes the ConcatenateGraphFilter output on unchanged (CompletionTokenStream.java:74-81). HTMLStripCharFilter has already decoded &#0; (or &#x0;) to U+0000: any code point up to 0x10FFFF except surrogates goes through Character.toChars (HTMLStripCharFilter.jflex:494-514, :528-547).
  3. 0x00 is the terminator, unescaped. At flush CompletionFieldsConsumer calls startTerm once per analyzed term, in byte order, then one entry per document and finishTerm (CompletionFieldsConsumer.java:195-227). So a with one entry is 61 00 00, with two entries 61 00 00 and 61 00 01; a+U+0000 is 61 00 00 00; a+U+0000+U+0000 is 61 00 00 00 00. Without a 0x00 inside an analyzed form the inputs are prefix-free and increasing; with it, both properties break.
  4. Out of order at flush. a's second input 61 00 01 comes before 61 00 00 00 00 although it is larger. FSTCompiler.add asserts increasing order (FSTCompiler.java:854-855). With assertions on, the AssertionError escapes flush (NRTSuggesterBuilder.finishTerm:96 <- CompletionFieldsConsumer:226 <- IndexWriter.commit), a tragic event that closes the writer. With assertions off the FST is compiled from out-of-order inputs and a query for a&#0;&#0; no longer returns that document.
  5. A hidden suggestion at lookup. 61 00 00 is now both the end of a and a step on the way to a+U+0000. NRTSuggester collects only in its acceptResult override of Util.TopNSearcher (NRTSuggester.java:189-227; "we do not use it, instead collect at acceptResult", :254-255). When the higher-weight a+U+0000 wins at that node (weights are stored as Integer.MAX_VALUE - weight, lower is better, :329-334), a's final path is queued; when it is popped, TopNSearcher adds it to its own result list without calling acceptResult (Util.java:333-337). That branch is a separate weakness, reachable here only because the inputs stopped being prefix-free.
  6. When it triggers. Some analyzed form in a segment must start with another analyzed form of the same segment followed by U+0000, such as a and a+U+0000 (from the encoding). A lone x&#0; with no plain x in the segment is indexed and found normally. Merges rebuild the FST from the merged terms, so a pair in two segments meets again at merge. The extra hit below needs only a query whose analyzed form ends in U+0000 and a suggestion equal to the text before it.

Exposure and likelihood494 words
  • Who is hit. Users of the document suggester (SuggestField or ContextSuggestField with a completion postings format; opt-in, @lucene.experimental) whose analysis chain can turn an accepted value into a form with U+0000. Stock components and plain document text suffice: HTMLStripCharFilter decodes &#0; and &#x0;; a MappingCharFilter or PatternReplaceCharFilter rule can output U+0000. Common text analyzers such as StandardAnalyzer add no U+0000. Binary-term analyzers such as CollationKeyAnalyzer write raw collation-key bytes, which contain 0x00 by design (a JDK root-locale collation key for a is 00 53 00 00 00 01 00 00 00 01); how they behave in a suggest field today was not tested.
  • Silent in production. With assertions off nothing throws: a suggestion accepted at addDocument is just missing from the results of a query for its own value. The lost one can be the U+0000 document or an ordinary neighbour with a lower weight. A query whose analyzed form ends in U+0000 can also return suggestions that do not start with that form.
  • Loud with assertions. With -ea (tests, development) the commit throws and closes the IndexWriter; every document added since the last commit is lost. A merge that brings such a pair together trips the same assertion, and IndexWriter.merge handles any merge failure as a tragic event that closes the writer (IndexWriter.java:5109-5113); in the probe's four such merges, forceMerge three times reported the writer's unrecoverable error and once reported the merge exception while isOpen() still returned true. Segments committed before are not lost.
  • Scale. Deterministic at any index size, given the colliding pair in one segment. In the hunt's bounded-exhaustive run over every list of 1-3 documents whose analyzed forms are 1-3 characters over {a, U+0000} starting with a (399 lists): with assertions on, 12 flush failures (each closes the writer) and 68 lists with a missed suggestion; with them off, 0 and 71; 52 of the missed queries are for documents without U+0000; the U+0001 control has 0 and 0. An independent re-implementation in the fact check got the same counts and found the 12 failing flushes to be exactly the 12 lists predicted out of order. In a larger probe (2 to 600 copies of a with weights 1..n, plus U+0000 forms with the highest weights, single and merged segments, assertions off) 76 of 78 runs lost U+0000 documents and none lost an a document. These are counts over the probe's constructed cases, not a frequency estimate; in other layouts a plain document is the one hidden (the single a above, the 52 missed queries). No run threw, ran out of memory or took longer than the probe's 20 s limit per operation; allocation was not measured.
  • Likelihood. Rare: text with &#0; (or a mapping rule to U+0000) next to a suggestion equal to the text before it, plus a weight order or duplicate count that exposes it. No prior report was found in the recorded searches (2026-10-27; see Prior reports).

Why it is a bug, not intended

#
  • U+0000 is reserved because it ends every analyzed form in the FST; only analyzed bytes reach the FST, yet only the raw value is checked.
  • The javadoc invites "the usual Analyzers" and nothing restricts their output; ConcatenateGraphFilter already escapes its own in-band separator.
  • With &#1; everything works; #5600 fixed a 0-byte collision in AnalyzingSuggester as a bug.
The full argument203 words
  • The reservation exists for the FST. U+0000 is in SuggestField.isReserved (SuggestField.java:140-149) because it is NRTSuggesterBuilder.END_BYTE, which "Marks end of the analyzed input" (NRTSuggesterBuilder.java:42-43). Only the analyzed bytes reach the FST, so a check on the raw value alone cannot keep the byte out.
  • Any analyzer is invited. "Besides the usual Analyzers, CompletionAnalyzer can be used" (SuggestField.java:35-37). No javadoc, CHANGES or MIGRATE entry restricts analyzer output.
  • In-band markers are escaped elsewhere. ConcatenateGraphFilter escapes its own SEP_LABEL inside tokens; nothing handles END_BYTE.
  • Tests cover the raw value only. TestSuggestField#testReservedChars (TestSuggestField.java:101-124) builds SuggestFields with raw reserved characters. No document-suggester test (suggest/document) uses an analyzer that emits U+0000; the only 0-byte analyzer test in lucene/suggest is TestAnalyzingSuggester#test0ByteKeys (TestAnalyzingSuggester.java:1204-1223), added by LUCENE-4534 (#5600) for the AnalyzingSuggester.
  • Precedent. #5600 / LUCENE-4534 (2012) fixed 0 bytes in AnalyzingSuggester/WFST keys as a bug ("0 bytes are rare, they are 'allowed' but will cause exceptions"), with test0ByteKeys as its regression test.
  • History. LUCENE-6339 (#7400) introduced the encoding; LUCENE-6459 (#7518) added the raw-value reservation of U+0000. Neither review discusses analyzer output.
  • The control. The same analyzer and documents with &#1; (U+0001) index and find every suggestion.
The devil's-advocate check221 words

The strongest case for "intended": the API is @lucene.experimental; the javadoc promises the IllegalArgumentException for the raw value only; the writer close needs assertions; HTML5 maps &#0; to U+FFFD, so one could blame HTMLStripCharFilter; and NRTSuggester says "search admissibility is not guaranteed" (NRTSuggester.java:257).

Why it fails: experimental allows API changes, not a silent loss of other documents' suggestions; the production (assertions off) loss is the main symptom, not the writer close; a MappingCharFilter rule triggers the same defect, so the missing check is the bug whatever HTMLStripCharFilter should decode &#0; to; and the admissibility notes tie misses to many deletions or a restrictive filter (:55-64, :280-290), while the repro has neither and asks for 100 hits out of 2-4 documents. Binary-term analyzers (collation keys) emit 0x00 by design; whether a suggest field should accept them is a decision for the fix, not an argument that the silent loss is intended. Two reading-only reviews by one model from another family (OpenAI GPT-5.6; neither ran code) rated the intended argument weak; a later fact check by the same family rated the strongest case moderate for the U+0000 suggestion's own miss and for the assertions-on writer close, and weak for the hidden neighbour. The devil's advocate found no intended or misuse argument that survives. Verdict: a defect.

Suggested fix

#

Recommended Reject an analyzed form that contains END_BYTE, in CompletionTokenStream

Check the analyzed form in CompletionTokenStream.incrementToken and throw the same non-aborting IllegalArgumentException as for a raw U+0000 (+14 lines, one file). In a scratch worktree the repro then passes 3 of 3 with assertions on and off, the whole lucene/suggest module passes (240 tests), and a new TestSuggestField test fails before and passes after.

BytesRef analyzed = termAttr.getBytesRef(); // TermToBytesRefAttribute
for (int i = 0; i < analyzed.length; i++) {
  if (analyzed.bytes[analyzed.offset + i] == NRTSuggesterBuilder.END_BYTE) {
    throw new IllegalArgumentException(
        "analyzed form contains the reserved byte 0x"
            + Integer.toHexString(NRTSuggesterBuilder.END_BYTE)
            + " at position "
            + i);
  }
}
payloadAttr.setPayload(payload);

Reject an analyzed form that contains END_BYTE, in CompletionTokenStream (validated by the checks) (recommended)

#

In CompletionTokenStream.incrementToken, scan the term bytes of each concatenated form and throw IllegalArgumentException if one is NRTSuggesterBuilder.END_BYTE, as SuggestField does for the raw value. The exception is thrown during addDocument, so it is non-aborting: the document is rejected and the writer stays open. It covers ContextSuggestField too, whose contexts are part of the same bytes. It checks the index side only (see the trade-offs).

BytesRef analyzed = termAttr.getBytesRef(); // TermToBytesRefAttribute
for (int i = 0; i < analyzed.length; i++) {
  if (analyzed.bytes[analyzed.offset + i] == NRTSuggesterBuilder.END_BYTE) {
    throw new IllegalArgumentException(
        "analyzed form contains the reserved byte 0x"
            + Integer.toHexString(NRTSuggesterBuilder.END_BYTE)
            + " at position "
            + i);
  }
}
payloadAttr.setPayload(payload);

Trade-offs

  • Behaviour change. It rejects every analyzed form with a 0x00, also a lone x&#0; that works today, and any analyzer that emits 0x00 on purpose (for example binary or collation-key terms) can no longer feed a suggest field. It also rejects a raw context that contains U+0000, which ContextSuggestField accepts today (its own check, ContextSuggestField.java:166-179, rejects only U+001D; not tested). Say so in a CHANGES entry; the javadoc of SuggestField could mention that the analyzed form is checked too.
  • Cost. One pass over the bytes of each suggestion at index time; nothing at search time. Not benchmarked.
  • Existing indexes. The check runs only when a document is added. Merges copy the stored terms through CompletionFieldsConsumer (CompletionFieldsConsumer.java:85-102, :195-226) without the token stream, so a segment written before the fix keeps its entries: suggestions stay missing, and with -ea a later merge can still trip the assertion. Only reindexing the affected documents removes them.
  • Query side not covered. A prefix query whose analyzed form ends in U+0000 still matches suggestions whose analyzed form is the query's without that last U+0000: with the fix, an index holding only a returns a for a query for a&#0; (diagram probe, assertions on and off). Rejecting or escaping 0x00 in query analysis as well would close that; not run. The repro does not test it. LFV-691 needs a query-side fix for RegexCompletionQuery too; a shared change to the query automaton may cover both (not explored).
  • Message. It could also name the field, and the value as the raw-value message does.
  • Add a regression test: fix-with-test.diff adds TestSuggestField#testReservedCharInAnalyzedForm.

Escape 0x00 inside analyzed forms, on the index and the query side

#

Like ConcatenateGraphFilter escapes SEP_LABEL: index an in-band 0x00 as an escape sequence and build every completion query's automaton the same way.

Trade-offs

Keeps such values indexable and findable and also covers the query-side extra hit, but touches the FST content and every CompletionQuery (prefix, regex, fuzzy, context), so it is a larger change with format implications. Not run.

Make HTMLStripCharFilter decode &#0; to U+FFFD

#

HTML5 maps the character reference for code point 0 to U+FFFD.

Trade-offs

Removes one trigger only: a MappingCharFilter or PatternReplaceCharFilter rule still produces U+0000. It also changes the filter's output for every user. A possible separate hardening, not a fix of this bug. Not run.

Call acceptResult for a queued final path in Util.TopNSearcher

#

TopNSearcher adds a queued END_LABEL path to its results without acceptResult (Util.java:333-337), which is how the lower-weight suggestion is lost.

Trade-offs

Partial: the hunt shadowed such a change alone, and the hidden-suggestion test passed but the out-of-order flush still failed (3 run, 1 failed). Worth its own issue; it does not stop 0x00 from reaching the FST.

Document that suggest-field analyzers must not emit U+0000

#

A javadoc note on SuggestField and CompletionAnalyzer.

Trade-offs

Leaves the silent loss and the writer close in place for anyone who misses the note. Not recommended.

Downstream note

#

Not a Lucene security issue under its SECURITY.md, but downstream, where untrusted document text feeds a completion field through an HTML-decoding analyzer, one document containing &#0; can lose its own suggestion and, in small segments, hide another document's.

How it was found

#

A bounded-exhaustive differential check of the stock document suggester: every list of 1-3 suggestions whose analyzed forms mix a and U+0000, against "every accepted suggestion is found and commit succeeds" and an independent model of the FST input order, which predicted exactly the 12 failing flushes. It was then reduced to a public-API JUnit with HTMLStripCharFilter.

The method in full202 words

Method: bounded-exhaustive differential checking on the stock main jar (the hunt's "semi-formal" tier; no model checker, solver or prover).

  • An earlier hunt over the completion suggester had seen the mechanism with a custom MappingCharFilter rule, found no stock trigger and did not report it. A later unit that turns such stranded leads into public-API repros picked it up.
  • The harness indexed every list of 1-3 documents whose suggestion analyzes to a 1-3 character string over {a, U+0000} starting with a (399 lists), with U+0001 as the control, and compared the jar with two oracles: an independent reference (every accepted document is found by a prefix query for its own value; commit succeeds) and an independent model of NRTSuggesterBuilder's FST input order, which predicts exactly the 12 lists whose flush fails with assertions on (a count match in the hunt; the fact check's independent re-implementation confirmed the same set).
  • The finder then searched for a stock trigger, found HTMLStripCharFilter decoding &#0;, and wrote the JUnit (2026-10-27). An independent reproducer, reading-only reviews by a model from another family (OpenAI GPT-5.6), an intended-behaviour devil's advocate, an adjudication, a history sweep, a prior-report search, a security screen and a credibility audit followed.

History

#

Introduced with the document suggester itself, LUCENE-6339 (b7adb6ac770, 2015-03-27), first released in 5.1.0. One portable probe fails on 16 releases from 5.1.0 to 10.5.2 and on main; 5.0.0 has no document suggester. Not a regression, and not fixed upstream.

Versions tested6 rows

Introduced by b7adb6ac770 (trunk, 2015-03-27, "LUCENE-6339: Added Near-real time Document Suggester via custom postings format", Areek Zillur; JIRA LUCENE-6339 = #7400; svn era, no PR) and its branch_5x backport 40e94c39ad3 (2015-03-28), first released in 5.1.0. It built each FST input as analyzed bytes + 0x00 + dedup byte(s) and escaped only the separator U+001F; git log -L on startTerm lists only this commit.

The contract came later. LUCENE-6459 (#7518, be4d58c7740, 2015-05-28, first in 5.3.0) added isReserved with U+0000 and the javadoc promise, for the raw value only. In 5.1.0-5.2.1 even a raw U+0000 is accepted and hides suggestions. LUCENE-8332 (7.4.0) moved the concatenation to ConcatenateGraphFilter, which still escapes only SEP_LABEL. CompletionTokenStream.java and NRTSuggesterBuilder.java on branch_10_6 are byte-identical to main (read).

Bug record

LFV-798, snapshot of 2026-10-30

Registry title
The document suggester checks its reserved end byte U+0000 only in the raw SuggestField value, not in the analyzed form, so an analyzer that emits U+0000 (for example HTMLStripCharFilter decoding '&#0;') hides another document's suggestion or its own and adds FST inputs out of order at flush (with assertions enabled the IndexWriter closes)
Area
suggest / document (NRT) suggester (SuggestField's raw-value reserved-character check vs. the analyzed form that CompletionTokenStream passes to NRTSuggesterBuilder's FST encoding)
Priority
Low, rank 242: Needs an analyzed U+0000 that collides with another suggestion's prefix form in the opt-in document suggester.
Impact class
silent wrong results
Impact note
Hits applications that use the opt-in document suggester (SuggestField with a completion postings format) whose analysis chain can turn an accepted value into a form that contains U+0000 (the stock HTMLStripCharFilter decodes '&#0;' or '&#x0;' in document text; a MappingCharFilter or PatternReplaceCharFilter rule can do it too), and only in a segment that also holds a suggestion whose analyzed form equals the text before that U+0000 (for example 'a' next to 'a&#0;'): in production (-da) the lower-weighted plain suggestion, or the U+0000 suggestion itself, is silently not returned for its own prefix, and with assertions enabled (-ea), once the shorter form has two or more entries, commit throws an AssertionError that closes the IndexWriter and loses the buffered documents; deterministic at any scale, in every release from 5.1.0 to 10.5.2 and on main.
Summary
You index suggestions with SuggestField through an analyzer that decodes HTML character references (HTMLStripCharFilter + KeywordTokenizer), for example 'a' (weight 1) and 'a&#0;' (weight 2), and expect a PrefixCompletionQuery 'a' with n=100 to return both documents, as it does with '&#1;'. Instead only the second document comes back; and with 'a&#0;&#0;', 'a', 'a', 'b' the commit fails with an 'inputs are added out of order' AssertionError that closes the IndexWriter when assertions are enabled, while without assertions 'a&#0;&#0;' is never found for its own value. SuggestField rejects U+0000, the byte that ends every entry in the suggester's FST, only in the raw value, so the analyzed form can still carry it and collide with that terminator.
Introduced
b7adb6ac7704a7e6364ee0d831bf77cf849f2090 (trunk, 'LUCENE-6339: Added Near-real time Document Suggester via custom postings format', by Areek Zillur; JIRA LUCENE-6339 = apache/lucene#7400; svn era, no pull request) and its branch_5x backport 40e94c39ad3b0f018ae9647b7d30bd0cfe341d86 (the commit in the 5.1.0 release): the commit that created the document suggester already built each FST input as analyzed bytes + END_BYTE 0x00 + dedup byte(s) (NRTSuggesterBuilder.startTerm/finishTerm) and passed the analyzed form on unchecked; the only in-band escaping it added was for the separator label U+001F [read: full-history clone, git log -L on NRTSuggesterBuilder.startTerm lists only this commit; exec: 5.0.0 has no document suggester, 5.1.0 fails]. The raw-value reservation of U+0000 came later with LUCENE-6459 (be4d58c7740 trunk / 380bb29f395 branch_5x, 2015-05-28, first in 5.3.0, apache/lucene#7518): it states the contract the bug breaks and narrowed it (a raw U+0000 is rejected from 5.3.0 on), but did not introduce the defect [exec: in 5.1.0-5.2.1 a raw U+0000 is accepted too and hides suggestions]. Not a regression. (2015-03-27 (trunk b7adb6ac770); 2015-03-28 (branch_5x 40e94c39ad3))
