galician.rslp repeats the Noun rule {"ido",3}, so its exception list never applies and "marido" (husband) is stemmed to "mar" (sea)

The stock GalicianAnalyzer indexes "marido" (husband) as mar, the same term as "mar" (sea), although the Noun step's "-ido" rule lists "marido" as an exception: a later copy of that rule without the list, where the cited rules have "-ído", strips it anyway. Seven words are hit, since 3.1.0.

The finding in 30 seconds

#

A stemmer cuts word endings so that the forms of a word share one index term. Lucene's Galician stemmer reads ordered rules from galician.rslp; a rule may list exceptions, words it must leave alone. Within a step the first matching rule wins, and an exception only stops its own rule.

  1. Index one document, "marido" (husband), with the stock new GalicianAnalyzer(), then search for the analyzed "mar" (sea).
  2. You expect 0 hits: galician.rslp:219 removes "-ido" except from seven listed words, "marido" among them, as in the rules page that GalicianStemmer cites. So "marido" keeps "-ido", only the final "o" goes, and the term is marid.
  3. But line 224, under the comment # mantído -> mant, is {"ido",3}: the same rule without the list, where the page has "ído". A step applies the first rule that matches, and an exception only stops its own rule, so line 224 removes "-ido": mar.
  4. The search for "mar" finds 1 of 1 documents, with no error; with line 224 as "ído" it finds 0 of 1. maridos, consolido ("I consolidate"), duvido ("I doubt"), cándido ("candid"), rápido ("fast") and decidido ("decided") lose "-ido" the same way: the list applies to no word.

Who is affected

#

Applications that index or search Galician text containing these words with GalicianAnalyzer (default constructor), GalicianStemFilter or the galicianStem factory; no setting is needed to hit it. Only seven words and their plurals are hit: marido, consolido, duvido, cándido, cândido, rápido, decidido. The worst case: marido/maridos (husband) share the term of mar/mares (sea). How often they occur was not measured.

Mechanism, terms and numbers615 words

GalicianStemmer says it implements "Regras do lematizador para o galego" and links that rules page (GalicianStemmer.java:22-27). Its rule file galician.rslp has, in the Noun step, {"ido",3,"",{"cándido","cândido","consolido","decidido","duvido","marido","rápido"}} at line 219: remove "-ido", except from these seven words. Five lines later, under the comment # mantído -> mant, line 224 is {"ido",3}, the same rule without the list; the rules page has "ído" (with an accent) in that row. RSLPStemmerBase.Step.apply returns at the first rule that matches (RSLPStemmerBase.java:229-231) and an exception declines only its own rule (:173), so every listed word falls through to line 224 and loses "-ido" anyway: the list has no effect on any word (a Z3 string-theory query over unbounded words is UNSAT).

Through the stock new GalicianAnalyzer(), "marido" (husband) and "maridos" are indexed as mar, the same term as "mar" (sea) and "mares", so a one-document search for "mar" finds 1 of 1 documents that only say "marido"; following the rules page, "marido" gives marid and the search finds 0 of 1. No error, every release from 3.1.0 to 10.6.0 and main.

The fix is a trade-off, said plainly: today's output matches the reference Java implementation that the rules page links (it has the same duplicate), and Lucene's vocabulary test data gl.txt, generated from that implementation, pins 3 of the affected stems (decidido, rápido, rápidos). The one-character fix (line 224 "ido" -> "ído") therefore needs 3 regenerated test pairs and a reindex note. No native-speaker check was done: the expected stems follow the cited rules page and the file's own exception list and comment.

GalicianStemFilter (used by GalicianAnalyzer and the galicianStem factory) runs GalicianStemmer.stem on every token (GalicianStemFilter.java:45-49). The stemmer runs the steps of galician.rslp in order: Plural, Unification, Adverb, Augmentative, Noun, then Verb only if the Noun step removed nothing, then Vowel (GalicianStemmer.java:47-67).

The Noun step (galician.rslp:197, exception flag 0: exceptions are ends-with patterns) contains, in this order:

218  # xemido -> xem
219  {"ido",3,"",{"cándido","cândido","consolido","decidido","duvido","marido","rápido"}},
220  # mantida -> mant
221  {"ida",3,"",{"bastida","dúbida","dubida","duvida","ermida","éxida","guarida","lapicida","medida","morida"}},
222  {"ída",3},
223  # mantído -> mant
224  {"ido",3},

For "marido": line 219 matches the suffix but declines the word (it ends with the exception "marido", RSLPStemmerBase.java:173); lines 221-222 cannot match a word ending in "ido"; line 224, the same suffix and minimum with no list, matches and removes "ido" (:229-231): mar. The Noun step changed the word, so the Verb step is skipped (GalicianStemmer.java:62-65), and the Vowel step finds no final vowel. With line 224 as {"ído",3}, "marido" passes the Noun and Verb steps unchanged and the Vowel rule {"o",3,...} (galician.rslp:638) gives marid. Last, stem turns á, é, ê, í, ó and ú into plain vowels (GalicianStemmer.java:69-89), which is why cándido gives cand today and candid with the fix.

Example words, with approximate glosses (Galician is written in the Latin alphabet, so no transliteration is needed; no native speaker checked the glosses, the expected stems or whether the rules page's example words, such as mantído, are standard Galician today): marido, maridos "husband(s)"; mar, mares "sea(s)"; consolido "I consolidate", consolidar "to consolidate", consolar "to console"; duvido "I doubt", duvidar "to doubt"; cándido "candid, innocent" (cândido: the Portuguese spelling), candidato "candidate"; rápido, rápidos, rápida "fast", rapidez "speed", rapidamente "quickly"; rapaciños "little boys, kids" (diminutive plural of rapaz "boy"; unrelated to rápido); decidido, decidida "decided, determined", decidir "to decide", and its forms decidan "(that) they decide", decidi "I decided", decidindo "deciding", decidirá "will decide", decidirán "they will decide", decidirao "will decide it", with decididamente "decidedly"; xemido "groan" and mantído, mantida "kept" (the rules page's examples); partido "party; split" (a control word).

Exposure and likelihood191 words
  • Who. Applications that index or query Galician text containing these words through GalicianAnalyzer (default constructor included), GalicianStemFilter or the galicianStem factory (GalicianStemFilterFactory.java:41), at index and query time. GalicianMinimalStemFilter uses only the Plural step (GalicianMinimalStemmer.java:32) and is not affected.
  • What triggers it. The seven listed words, their plurals and any longer word ending in one of them; deterministic, the same with assertions on and off.
  • Damage. Wrong terms with no error: marido/maridos become mar, the term of mar/mares, so a query for "mar" also finds documents about a husband (1 of 1 in the probe); consolido joins consolar (consol) instead of consolidar; duvido, cándido, rápido and decidido lose "-ido" (duv, cand, rap, decid).
  • Scale, honestly. Seven words and their plurals; likelihood "rare" and priority Low are judgements, not measurements. Two of the seven (decidido, rápido) get the stems Lucene's vocabulary test expects today.
  • Reindex. A fix changes the indexed terms of these words. A workaround without a Lucene change (not run): put the words in GalicianAnalyzer's stem-exclusion set (they are then indexed unstemmed) or map them with StemmerOverrideFilter.

Why it looks unintended

#
  • GalicianStemmer implements the rules page it links, which has "ído" 3 (mantído → mant) in the row Lucene writes as {"ido",3}; Lucene's comment above it is that example.
  • Exceptions are "patterns that should not be stemmed"; this list can never apply (Z3: UNSAT).
  • Against: the linked reference implementation has the same duplicate; Lucene's vocabulary test pins 3 affected stems.
The full argument262 words
  • The cited rules. GalicianStemmer.java:22-27: "Galician stemmer implementing "Regras do lematizador para o galego"", with @see the rules page "Description of rules" (http://bvg.udc.es/recursos_lingua/stemming.jsp, read from a web-archive capture of 2014-01-16). Its Noun table: "ido" 2 xemido -> xem with the seven exceptions, then "ida" 3 mantida -> mant with its list, "ída" 3, then "ído" 3 mantído -> mant in exactly the row Lucene writes as {"ido",3}.
  • Lucene's own comment. Line 223 is the page's example # mantído -> mant, which a rule spelled "ido" can never produce: "mantído" does not end in "ido" (the Verb step's {"ído",3} at galician.rslp:497 stems it).
  • The format. RSLPStemmerBase.java:60-62: exceptions are "patterns that should not be stemmed". The rule constructors already reject one kind of dead exception while the file is parsed, an entry that does not end with the rule's suffix (RuleWithSuffixExceptions, "warning: useless exception", :153-164; RuleWithSetExceptions, :132-138; both called from parseRules, :302, :309), but nothing checks for a list made dead by a later copy of the rule.
  • History. The file came with LUCENE-2842 (#3916, 2011), which says the analyzer is "based upon" the rules page; nobody discussed the rules there or later.
  • Not claimed. The page gives minimum 2 for the first "ido" row where the file has 3; that does not affect the seven words. Here the file follows the reference implementation, as it does for "ada" (file 3, page 2) and "ación" (file 2, page 3), so the page is not a row-by-row specification of the file.
The devil's-advocate check292 words

The strongest case for "intended": Lucene copies the reference Java implementation that the rules page links, and that implementation has the same duplicate (its Noun array: the "ido" rule with the seven exceptions, "ida", "ída", then an "ido" rule with an empty list). TestGalicianStemFilter.testVocabulary ("Test against a vocabulary from the reference impl", TestGalicianStemFilter.java:51-53) checks gl.txt, which pins decidido -> decid and rápido, rápidos -> rap. GalicianStemmer is package-private, RSLPStemmerBase is @lucene.internal, and no public API promises exact stems. An independent reviewer from another model family (OpenAI GPT-5.6) reproduced the bug and agreed on the root cause, but voted "not real" (medium confidence) on exactly this ground, in two executed runs.

Why the evidence still favours an inherited typo over a decision: gl.txt is generated golden data ("vocabulary test data for the reference galician implementation from a small corpus", #3916), not a decision about this rule. Lucene's file is not a byte-for-byte copy: in the same Noun step the commit that added it changed three reference entries whose exceptions do not end with the rule's suffix (aira -> aria at :209, aria -> aría at :282, the udo exception escuso -> escudo at :226). The rule constructors reject such entries, so these changes were needed for the file to load at all; two of them (aria, aría) also match the cited page, while escudo matches neither. They show that the file was adapted where the reference could not load, not by themselves that every list was meant to stay live. And the file's own comment and the cited page both say "ído". What remains is a maintainer's judgement call: they may prefer reference compatibility, a change to the docs only, or fix B (no output change).

Trade-offs

  • Changes indexed terms of the listed words (a reindex note is needed) and departs from the reference implementation's output.
  • Measured as same-stem pairs on gl.txt (9,416 words): 2 gained (rápido, rápidos "fast" join rapidez "speed") and 15 lost: 9 because decidido "decided" no longer joins the forms of decidir "to decide" (decidan "(that) they decide", decidi "I decided", decidida "decided" (feminine), decididamente "decidedly", decidindo "deciding", decidir, decidirao "will decide it", decidirá "will decide", decidirán "they will decide"; the rule authors listed decidido as an exception), 6 because rápido and rápidos split from rápida "fast" (feminine), rapidamente "quickly" and rapaciños "little boys, kids". rapaciños (from rapaz "boy") is unrelated to rápido, so 2 of the 15 lost pairs only undo a conflation that is wrong today. The glosses are approximate and were not checked by a speaker of Galician.
  • Outside gl.txt: ends the marido/maridos vs mar/mares collision, moves consolido from consolar to consolidar, joins duvido with duvidar and cándido with candidato.

Downstream note

#

Search products that build Galician analysis on GalicianAnalyzer, GalicianStemFilter or the galicianStem factory get the same terms, and a fix changes their indexed terms too.

How it was found

#

A scan of Lucene's rule-based stemmers for rules that another rule in the same step shadows flagged the exception-free {"ido",3} at line 224. An exact Z3 string-theory model of one rule step proved that line 219's exception list changes no word's result, and the stock analyzer stemmed "marido" to mar.

The method in full145 words
  • Scan. The rule-based stemmers' rule files were scanned for rules that a rule elsewhere in the same step shadows. It flagged the exception-free duplicate {"ido",3} in galician.rslp's Noun step, and a probe on the stock jar gave marido -> mar.
  • Proof. An exact Z3 string-theory model of one RSLP step (unbounded word length; recorded as checked against the stock jar on 524 rule witnesses, 282 Galician and 242 Portuguese, with 0 mismatches) decided for the rule at line 219 whether deleting its exception list changes the step's result on any word: UNSAT (it never does). With line 224 read as the page's "ído", the same query is satisfiable, with witness "marido" (a mutation check against vacuity).
  • Execution. Reduced to the one-assertion public-API JUnit above and run on main and release jars.
  • Method class: semi-formal (a rule-shadowing scan plus an SMT proof, confirmed by execution).

galician.rslp repeats the Noun rule {"ido",3} where the rules page GalicianStemmer cites has "ído", so the first 'ido' rule's exception list (cándido, cândido, consolido, decidido, duvido, marido, rápido) never applies and GalicianAnalyzer stems 'marido' (husband) to 'mar', the same term as 'mar' (sea)
Area
analysis-common / Galician stemmer rule file (galician.rslp Noun step, run by RSLPStemmerBase; GalicianStemFilter, GalicianAnalyzer and the 'galicianStem' factory)
Priority
Low, rank 304: In every release since 3.1.0 the stock GalicianAnalyzer stems the seven words that its first Noun-step 'ido' rule lists as exceptions, and their plurals, as if the list were not there, so 'marido' (husband) is indexed as 'mar' and a query for 'mar' (sea) also finds documents that only say 'marido', with no error. It is Low because only those few words are hit, today's output matches the reference implementation linked from the cited rules page, and a fix trades off other same-stem pairs and changes indexed terms.
Impact class
minor
Impact note
Wrong terms with no error: every application that indexes or queries Galician text through GalicianAnalyzer (default constructor included), GalicianStemFilter or the 'galicianStem' factory, on every release from 3.1.0 through 10.6.0 and on main, stems the seven words that the Noun step's first 'ido' rule lists as exceptions, and their plurals, as if the list were not there: marido and maridos become 'mar', the term of mar and mares (sea), so a query for 'mar' also matches documents that only say 'marido'; consolido becomes 'consol', the stem of consolar; duvido, cándido, rápido and decidido lose 'ido' as well. No scale or setting is needed, -ea and -da behave the same, and because a fix changes indexed terms, affected fields need reindexing after it. Impact class minor (real but narrow: seven listed words and their plurals; current output matches the reference Java implementation linked from the cited rules page, Lucene's reference vocabulary gl.txt pins 3 of the affected outputs, and the fix is a stemming trade-off, gaining 2 and losing 15 same-stem pairs on gl.txt).
Summary
You index Galician text with the stock GalicianAnalyzer; one document says 'marido' (husband) and a query says 'mar' (sea). You expect no match: galician.rslp's Noun step lists 'marido' (with cándido, cândido, consolido, decidido, duvido and rápido) as an exception of its 'ido' rule at line 219, so, as in the rules page that GalicianStemmer says it implements, the word keeps 'ido' and only the final vowel is removed ('marid'). Instead line 224, under the comment '# mantído -> mant', is an exact copy of that rule without the exception list where the cited page has 'ído', and because the first matching rule wins it removes 'ido' anyway: 'marido' is indexed as 'mar' and the query for 'mar' finds the document, with no error.
