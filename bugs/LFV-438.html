UnifiedHighlighter with maxPassages = Integer.MAX_VALUE throws a message-less IllegalArgumentException for every document that has a match

Pass Integer.MAX_VALUE, a conventional "no limit" value, as maxPassages to the UnifiedHighlighter, and every document with a match throws an IllegalArgumentException with no message instead of returning its snippet. The passage queue's starting size is Math.min(64, maxPassages + 1), and that + 1 wraps around to a negative number.

The finding in 30 seconds

#

The highlighter keeps the best passages in a java.util.PriorityQueue whose starting size is Math.min(64, maxPassages + 1). The 64 keeps big limits cheap; the + 1 matches the one extra passage it holds for a moment. For Integer.MAX_VALUE the + 1 overflows to a negative size, and the JDK refuses it.

Background: passages and maxPassages

#
  1. The UnifiedHighlighter cuts a field's text into passages (by default, sentences), scores each passage that contains a query match, and joins the best ones into the snippet.
  2. maxPassages is how many of those top-scoring passages a snippet may use. highlight(field, query, topDocs, maxPassages), highlightFields(fields, query, topDocs, int[] maxPassages) and highlightWithoutSearcher(field, query, content, maxPassages) take it as a plain int with no documented range.

The finding, step by step

#
  1. You highlight the text a test for the query body:test with highlightWithoutSearcher("body", query, "a test", 1000) and get a <b>test</b>.
  2. You pass Integer.MAX_VALUE (2,147,483,647) instead, to mean "no limit". You expect the same a <b>test</b>: the javadoc sets no upper bound, and 1, 3, 64, 1000 and 2,147,483,646 all give it.
  3. You get an IllegalArgumentException with no message, thrown by the java.util.PriorityQueue constructor. With highlightFields and per-field limits {1, Integer.MAX_VALUE} the whole call fails, so the field that asked for one passage loses its snippet too.
  4. Why: the queue's starting size is Math.min(64, maxPassages + 1). 2,147,483,647 + 1 wraps to -2,147,483,648, Math.min picks it, and the JDK rejects a size below 1. A document without a match never builds the queue (since 7.3.0), so it still gets its summary.

Who is affected

#

Anyone who passes Integer.MAX_VALUE as "no limit", directly or by forwarding a client's snippet count. Every document with a match fails, and a multi-field call loses all its snippets. The error has no message and is not the documented one. It fails loudly on the first matching document; no wrong results, hang or index damage was observed.

Mechanism, terms and numbers605 words

The UnifiedHighlighter keeps a field's best maxPassages passages in a java.util.PriorityQueue, created in FieldHighlighter.highlightOffsetsEnums with the initial capacity Math.min(64, maxPassages + 1) (FieldHighlighter.java:141-143 on main 645d4fe14a20). The 64 cap keeps the eagerly allocated initial array small for large limits; the + 1 matches the queue briefly holding one passage more than the limit (why it was written this way is not recorded). For maxPassages = Integer.MAX_VALUE, a conventional "no limit" value (Lucene's own javadocs use it that way, in this module too: MatchRegionRetriever, FastVectorHighlighter), the + 1 wraps to Integer.MIN_VALUE, Math.min returns it, and the JDK constructor throws IllegalArgumentException with no message.

With the stock highlighter that happens for every document whose field has a match; it was executed through highlight, highlightFields and highlightWithoutSearcher, with offsets in postings and with re-analysis, with assertions on and off; in a multi-field call the other fields lose their snippets too. Every limit from 1 to Integer.MAX_VALUE - 1 gives a valid capacity and every one tested works; since 7.3.0, documents without a match are summarized normally. The expression has been there since the UnifiedHighlighter was added (LUCENE-7438, 2016); every release from 6.3.0 to 10.6.0 and main is affected. A one-line overflow-safe clamp fixes it.

The code (main 645d4fe14a20, lucene/highlighter/.../uhighlight/)

#
  • Entry points. highlight(field, query, topDocs, maxPassages) wraps the value in an array and calls highlightFields (UnifiedHighlighter.java:766-770), which ends in highlightFieldsAsObjects (:858). That method checks only "fieldsIn must not be empty" and "invalid number of maxPassagesIn" (:892-897), plus that a searcher is set (:898-902), never the values, and builds one FieldHighlighter per field with its own count (:922-924). highlightWithoutSearcher does the same for one string (:1096-1107).
  • No match, no queue. highlightFieldForDoc calls highlightOffsetsEnums (FieldHighlighter.java:86), which returns new Passage[0] when there is no term occurrence (:137-139); the summary path then sizes its list with Math.min(maxPassages, 10) (:112). So Integer.MAX_VALUE works for documents without a match.
  • The wrap. With a match, :141-143 builds new PriorityQueue<>(Math.min(64, maxPassages + 1), comparator). 2147483647 + 1 = -2147483648 and Math.min(64, -2147483648) = -2147483648; for 2147483646 the expression is Math.min(64, 2147483647) = 64.
  • The throw. JDK 25 PriorityQueue(int, Comparator): if (initialCapacity < 1) throw new IllegalArgumentException();, then new Object[initialCapacity] (PriorityQueue.java:173-175). The queue grows on demand, so 64 is only a starting size.
  • The + 1. maybeAddPassage (FieldHighlighter.java:201-224) offers the new passage and polls the lowest when size() > maxPassages (:215-217), so the queue briefly holds maxPassages + 1 entries, which the + 1 matches (the original rationale is not recorded).

Why it looks unintended

#
  • The javadoc sets no upper bound on maxPassages; the only documented IllegalArgumentException is for fields without offsets.
  • The 64 cap keeps big limits cheap: every value from 1 to 2,147,483,646 gets a valid size, and Integer.MAX_VALUE already works for documents without a match.
  • Intended rejection looks different: in the same class, withMaxLength rejects Integer.MAX_VALUE up front, with a message.
The full argument229 words
  • Contract. Every overload documents maxPassages only as "The maximum number of top-N ranked passages [per-field] used to form the highlighted snippets" (UnifiedHighlighter.java:757-758, :819-820, :845-846, :881-882, :1089-1090), with no range, and nothing validates the values (:892-897). The only documented IllegalArgumentException is for fields indexed without offsets (:744-745, :763-764, :793-794, :825-826, :851-852, :887-888).
  • Built for large limits. The cap of 64 keeps a large count from allocating a large queue; every value from 64 to MAX_VALUE - 1 gets capacity 64. The predecessor PostingsHighlighter sized its queue from the raw count and threw OutOfMemoryError ("Requested array size exceeds VM limit") for both MAX_VALUE and MAX_VALUE - 1 (executed on 6.2.1); the cap avoids that for every value except the one where + 1 wraps.
  • Intended rejection looks different. setMaxLength and Builder.withMaxLength reject Integer.MAX_VALUE up front with "maxLength must be < Integer.MAX_VALUE" (:192-196, :355-360); their comment names a different + 1 hazard (BreakIterator.preceding(offset+1) and the offsets-queue sentinel). maxPassages never had such a guard.
  • Tests. No upstream test passes maxPassages = Integer.MAX_VALUE; the uhighlight tests use withMaxLength(Integer.MAX_VALUE - 1) only.
  • History and precedent. LUCENE-7438 (#8490) and its 28 comments never discuss the queue capacity or Integer.MAX_VALUE. LUCENE-10135 (#11172, PR #334, 9.0.0) fixed a similar MAX_VALUE overflow of maxPassageWindow in MatchHighlighter's PassageSelector.
The devil's-advocate check201 words

The strongest case for "works as designed": no contract promises Integer.MAX_VALUE; UnifiedHighlighter is @lucene.experimental and FieldHighlighter @lucene.internal; 2^31 - 1 passages is unattainable (by default a stored value is truncated to maxLength, 10,000 characters, when it is loaded, so a field read from the index has at most 10,000 passages); the classic Highlighter in the same module also rejects maxNumFragments MAX_VALUE and MAX_VALUE - 1 ("maxSize must be >= 0 and < 2147483631", executed); and Elasticsearch and OpenSearch pass MAX_VALUE - 1 as their "all fragments" value.

Why it fails: the classic Highlighter has no bounds check of its own (only Math.max(1, maxNumFragments)); its rejection comes from the range check of Lucene's generic org.apache.lucene.util.PriorityQueue (commented "Throw exception to prevent confusing OOME"), a stable limit with a message that names it. Here every value but one works, and that one fails inside a JDK collection, without a message and only for documents with a match. The experimental tag allows API changes, not an undocumented error from an accepted argument, and the downstream MAX_VALUE - 1 is an unexplained value choice, not a documented limit. Verdict: a defect, low severity; clamping or rejecting with a message both fix it.

Suggested fix

#

Recommended Overflow-safe cap on the initial queue capacity (one line)

Make the cap overflow-safe: maxPassages >= 64 ? 64 : maxPassages + 1 at FieldHighlighter.java:143, one line. Every value below Integer.MAX_VALUE keeps today's starting size, and Integer.MAX_VALUE gets 64. With it, the minimal test and all 723 highlighter tests pass.

    PriorityQueue<Passage> passageQueue =
        new PriorityQueue<>(
            maxPassages >= 64 ? 64 : maxPassages + 1, // no int overflow for Integer.MAX_VALUE

All options and trade-offs2 options · 504 words

Two options; the clamp is preferred here for compatibility, and rejecting is also defensible. The clamp was validated on 645d4fe14a20; rejecting the value with a message was not executed. Either way, do not size the queue from maxPassages itself (for example new PriorityQueue<>(maxPassages + 1) or long arithmetic without the cap): java.util.PriorityQueue allocates its initial array eagerly, the predecessor PostingsHighlighter threw OutOfMemoryError that way for both MAX_VALUE and MAX_VALUE - 1, and a downstream engine capped huge fragment counts after the classic Highlighter allocated gigabytes (elastic/elasticsearch#155507). A natural combination: the clamp for this bug, plus a maxPassages < 1 check for the maxPassages = 0 failure (a separate bug, a NullPointerException at FieldHighlighter.java:212).

Trade-offs

  • The same initial capacity as today for every value below Integer.MAX_VALUE: maxPassages + 1 up to 63, 64 from 64 to Integer.MAX_VALUE - 1; Integer.MAX_VALUE now gets 64 as well. The initial allocation stays bounded.
  • It does not change maxPassages = 0 (a separate NullPointerException at FieldHighlighter.java:212) or negative values, which stay invalid and are not claimed: the new expression gives n + 1 for them, like the old one. On main (executed, -1, -5 and Integer.MIN_VALUE), a document with a match gets the same message-less exception at line 143, and a document without a match fails earlier in the summary path (new ArrayList<>(Math.min(maxPassages, 10)), line 112) with "Illegal Capacity: <n>".
  • What the validation covers: the positive boundary (Integer.MAX_VALUE) and the existing highlighter suites; no negative input was run with the fix, and below Integer.MAX_VALUE the new expression equals the old one.

Reject the value up front with a clear message

#

Check the counts in highlightFieldsAsObjects and highlightWithoutSearcher, as withMaxLength does for maxLength: == Integer.MAX_VALUE covers this bug; < 1 would also turn the maxPassages = 0 failure into a clear error. Not executed.

Trade-offs

Clear error instead of a JDK one, consistent with withMaxLength. But the conventional "no limit" value becomes an error that callers must work around with Integer.MAX_VALUE - 1, while every other large value stays legal.

Downstream note

#

By code reading only (nothing run downstream): Solr passes hl.snippets to maxPassages unchecked, so hl.snippets=2147483647 should fail the same way. Elasticsearch rejects counts above 10,000 by default and maps "all fragments" to 2,147,483,646, which works. OpenSearch maps it the same way, passes other counts through (no upper bound found, not fully traced) and keeps its own copy of the line.

How it was found

#

A static scan listed, for every public method in the core and module jars, which argument checks it makes: highlightFields checks the field list and the array length but never the maxPassages values. A search of such unchecked parameters for + 1 arithmetic found the wrap, and a public-API test confirmed it.

The method in full133 words

Method: a static guard inventory, then a guided search (the finder labelled it semi-formal; the last step was a text search, so it sits at the boundary with non-formal), in a hunt unit on accepted-parameter boundaries, run on the stock main jars at ea57360912ed.

  • A bytecode pass (the JDK ClassFile API) over 27 core and non-sandbox module jars listed 1,231 public or protected entry points whose code reaches an IllegalArgumentException, with each guard's parameters and constants.
  • For UnifiedHighlighter.highlightFields / highlightFieldsAsObjects the only guards are "fieldsIn must not be empty" and "invalid number of maxPassagesIn": the counts themselves are accepted unbounded.
  • Searching the accepted-unbounded parameters for + 1 and * 2 arithmetic found Math.min(64, maxPassages + 1); a hand-written public-API JUnit witnessed the failure, later reduced to the single test shown here.

Impact note
Applications on any release from 6.3.0 through 10.5.2 or on main that call UnifiedHighlighter (highlight, highlightFields, highlightWithoutSearcher; offsets in postings and re-analysis were run; default settings) with maxPassages = Integer.MAX_VALUE, the usual Java 'no limit' value, get a message-less IllegalArgumentException from inside java.util.PriorityQueue for every document that matches (the javadoc documents an IllegalArgumentException only for fields without offsets), and in a multi-field call such as {1, MAX_VALUE} the whole call fails, so the other fields lose their snippets too; every value up to Integer.MAX_VALUE - 1 works, documents without a match are summarized normally, there are no wrong results, no corruption and no hang, no index size is needed, and by code reading (not executed) Solr's hl.method=unified with hl.snippets=2147483647 reaches it, while default Elasticsearch caps number_of_fragments at 10000 and both Elasticsearch and OpenSearch map 0 ('all') to Integer.MAX_VALUE - 1.
Summary
You ask the UnifiedHighlighter for at most Integer.MAX_VALUE passages, meaning 'no limit', and expect the same snippet that 1000 or Integer.MAX_VALUE - 1 gives (or, if the value is not allowed, an IllegalArgumentException that says so). Instead, for every document that has a match, FieldHighlighter.highlightOffsetsEnums sizes its passage queue with Math.min(64, maxPassages + 1); the + 1 wraps to Integer.MIN_VALUE, Math.min returns it, and the java.util.PriorityQueue constructor throws an IllegalArgumentException with no message. With per-field counts such as {1, MAX_VALUE} the field that asked for one passage loses its snippet too, because the whole call throws.
