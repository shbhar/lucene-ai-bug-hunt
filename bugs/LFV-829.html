The classic Highlighter counts the empty positions before a MultiPhraseQuery as gaps and marks pairs that do not match

With a stop-word and synonym analyzer, the phrase "the dogs bark" becomes a MultiPhraseQuery starting at position 1, and the classic Highlighter marks dogs often bark as well as the real match dogs bark. It counts the empty position before the phrase as a gap, in every release since 2.4.0.

The bug in 30 seconds

#

To find a phrase in the text, the classic Highlighter turns it into a span query whose slop is the phrase's slop plus its gaps. For a MultiPhraseQuery it counts the gaps from position 0, so empty positions before the phrase's first word count too.

  1. You parse the quoted phrase "the dogs bark" with QueryParser or QueryBuilder and an analyzer that removes stop words and adds dog as a synonym of dogs. The dropped the keeps position 0, so you get a MultiPhraseQuery: [dogs|dog] at position 1, bark at 2, slop 0.
  2. You index dogs often bark but my dogs bark (words at positions 0 to 6). The phrase matches once: dogs bark at positions 5-6, as Weight#matches reports.
  3. You highlight it with Highlighter and QueryScorer and expect dogs often bark but my <B>dogs</B> <B>bark</B>. The same query moved to positions 0 and 1, and a PhraseQuery at positions 1 and 2, give exactly that.
  4. Instead you get <B>dogs</B> often <B>bark</B> but my <B>dogs</B> <B>bark</B>, with no error. The highlighter turns the phrase into a span query and counts every empty position from 0 as a gap between the words, so the empty position 0 becomes slop 1 and dogs often bark qualifies.
  5. Each further leading position adds one more: "the dogs bark" (positions 2 and 3) marks a pair with two words between them. Sloppy phrases get the extra unit too.

Who is affected

#

Applications that highlight with the classic Highlighter and QueryScorer, or with the UnifiedHighlighter with weight matches off (its default in 6.3 to 8.11), when a quoted phrase starts with a removed stop word and contains a synonym. Near-miss pairs get extra marks; hits and scores are correct. The default UnifiedHighlighter since 9.0 is exact.

Mechanism, terms and numbers769 words

The classic Highlighter with QueryScorer converts a MultiPhraseQuery into a SpanNearQuery. WeightedSpanTermExtractor walks the position slots from 0 to the last position and counts every empty slot as a gap, including the slots before the phrase's first position, and adds that count to the slop. A MultiPhraseQuery that starts at position k > 0 therefore gets k extra units of slop. QueryBuilder, and so the classic QueryParser, build such a query for a quoted phrase that starts with a removed stop word and contains a same-position synonym: "the dogs bark" becomes [dogs|dog]@1 bark@2, and on dogs often bark but my dogs bark the highlighter also marks dogs often bark, although Weight#matches reports only positions 5-6. The PhraseQuery branch of the same method measures gaps from the first position and is correct. Search hits, counts and scores are not affected. The UnifiedHighlighter shows the same marks with weight matches off (its default in 6.3.0 to 8.11.x); its default since 9.0 is exact. Every release from 2.4.0 to 10.5.2 and main is affected (17 releases and main run, the rest by code history). A one-condition fix passes all 732 tests of the highlighter module, the repro tests included.

Terms

#
  • Classic Highlighter: org.apache.lucene.search.highlight.Highlighter with a QueryScorer. The scorer asks WeightedSpanTermExtractor which words of the text belong to a match of the query; for phrases it converts the query to a SpanQuery and runs it on a one-document index of the text.
  • Positions: each word of a phrase query has a position. A removed stop word keeps its position, so "the dogs bark" gives dogs position 1 and bark position 2. MultiPhraseQuery documents its positions as relative: shifting them all by the same amount does not change what matches.
  • MultiPhraseQuery: a phrase with several alternatives at one position, here [dogs|dog]. QueryBuilder builds one when the analyzer stacks a token at the same position, for example a single-word synonym. Without a stacked token the same input becomes a PhraseQuery.
  • Slop of a SpanNearQuery: "the maximum number of intervening unmatched positions" between its clauses (SpanNearQuery.java:38-40).

  1. For [dogs|dog]@1 bark@2 the array has 3 slots. Slot 0 is empty (the dropped the); slots 1 and 2 hold the clauses.
  2. The loop counts slot 0 as a gap: positionGaps = 1, although nothing lies between the two clauses.
  3. The span query is spanNear([spanOr([dogs, dog]), spanOr([bark])], 1, true): ordered, slop 1. A trace prints slop 0, 1 and 2 for the same query starting at position 0, 1 and 2.
  4. On dogs often bark but my dogs bark that span query also matches dogs(0) ... bark(2), so the extractor records bark at positions [0,2] and [5,6] instead of [5,6] only, and QueryScorer marks the first pair too.

Where the input comes from: QueryBuilder.analyzeMultiPhrase starts at position = -1 and adds each token's increment (QueryBuilder.java:464-497), and position increments are on by default (QueryBuilder.java:198-206), so a removed leading stop word makes the first position 1. The classic QueryParser builds the same query from "the dogs bark".

Exposure and likelihood430 words
  • Who. Users of the classic Highlighter with QueryScorer (position-aware by default since 2.9.0), on re-analysed text and on term-vector token streams; and users of the UnifiedHighlighter with withWeightMatches(false) (a builder option since 9.1.0), whose PhraseHelper reuses the same extractor. From 6.3.0 to 8.11.x that was the UnifiedHighlighter's default path. By reading, any configuration that keeps strict phrase highlighting but loses weight matches gets there too: weight matches are set only when multi-term handling, strict phrases and passage relevancy are all on (UnifiedHighlighter.java:518-527), so withHandleMultiTermQuery(false) or withPassageRelevancyOverSpeed(false) also use PhraseHelper (:1219-1235). The default UnifiedHighlighter of 9.0 and later uses Weight#matches and is exact.
  • Trigger. A MultiPhraseQuery whose smallest position is above 0. In practice: a query analyzer that removes stop words and stacks same-position tokens (single-word synonyms, or any filter that emits a token with position increment 0 and position length 1; a longer token sends QueryBuilder to its graph path, which builds phrase queries per path instead), and a quoted phrase that starts with a stop word and contains such a token. With Lucene's SynonymGraphFilter the filter order matters: synonyms before stop words trigger it for this example, stop words first gave positions 0 and 1 and an exact highlight (traced, this example only). Hand-built queries that start above 0 do the same. Plain stop-word phrases become a PhraseQuery and are not affected.
  • Effect. Extra marks: pairs of the phrase's words that are up to k positions further apart than the query allows, where k is the first position (one per leading removed word); sloppy phrases too. A text without a match can get marks. Hits, counts and scores do not change, and there is no error with assertions on or off. By reading, not run: QueryScorer scores fragments by the query terms they contain, so the extra marks can also change which fragment is picked.
  • Scale. A bounded-exhaustive harness (152 documents of 1-3 words, 2,139 queries, 153,082 checks, one per query hit, against an exact phrase reference cross-checked with Weight#matches) found this class in 92 cases in each of the two token-stream modes, and none for a PhraseQuery with the same positions.
  • How likely. Rare: each ingredient is ordinary, but the combination plus a near-miss pair in the text is uncommon, and nobody has reported it in 18 years. The classic Highlighter is the older highlighter; #16820 (open) proposes deprecating it, nothing is deprecated yet.
  • Workaround. Use the UnifiedHighlighter with weight matches (its default since 9.0), or shift the MultiPhraseQuery so its positions start at 0 before highlighting; the controls show both highlight exactly.

Why it is a bug, not intended

#
  • MultiPhraseQuery documents its positions as relative; the same query at positions 0 and 1 is highlighted exactly.
  • The PhraseQuery branch of the same method measures gaps from the first position, so identical positions give different highlights.
  • The accepted approximation covers holes between positions; no test or decision covers empty positions before the first.
The full argument210 words
  • Positions are relative by contract. MultiPhraseQuery.Builder.add(Term[], int): "Allows to specify the relative position of terms within the phrase" (MultiPhraseQuery.java:122); getPositions(): "Returns the relative positions of terms in this phrase" (:176). Weight#matches gives the same positions for the query at 0,1 and at 1,2, and PhraseQuery.rewrite subtracts positions[0] (PhraseQuery.java:309-314).
  • The same method already does it right for PhraseQuery. Since LUCENE-5503 (5.4.0) that branch uses positions[last] - positions[0] - n + 1 (:154-155). Its CHANGES entry says the extractor "converts a PhraseQuery to an equivalent SpanQuery" (CHANGES.txt:10042-10045), and PhraseHelper.java:107 says "WSTE will convert to an equivalent SpanQuery" (a code comment; PhraseHelper is @lucene.internal).
  • The scorer's stated goal. QueryScorer "attempts to score only those terms that participated in generating the 'hit' on the document" (QueryScorer.java:33-37).
  • No test covers it. The upstream highlighter tests that use a MultiPhraseQuery all start at position 0: TestHighlighter.java:820-849 (two tests) and :1732-1740 (a one-term query), and TestUnifiedHighlighterStrictPhrases.testSynonyms (:261-279, positions 0 and 1). The contributed patch that introduced the loop (LUCENE-794, 2008) tested only positions starting at 0. No CHANGES, MIGRATE or won't-fix entry mentions it.
  • History. LUCENE-7417 (2016) edited this loop for a one-clause crash and kept the leading-slot count.
The devil's-advocate check195 words

Strongest case (an intended-behaviour checker and a reviewer from another model family, OpenAI GPT-5.6): the classic phrase-to-span conversion is a known approximation. On LUCENE-2003 markrmiller called adding holes to the slop "one - uh - sloppy fix ... I think that keeps a fairly good approximation"; QueryScorer only "attempts" to score participating terms; the sandbox PayloadSpanUtil copies the same loop, so it looks like a convention; and #16820 proposes deprecating the classic Highlighter.

Why it fails: the accepted approximation is about holes between positions (the sibling bug LFV-827). A slot before the first position is not a hole, and every formula committers discussed gives 0 for it: "maxPos-minPos+1-numTokens" (yonik, LUCENE-2003) and LUCENE-5503's positions[last] - positions[0] - n + 1. Shifting the query by a constant, which the API defines as meaningless, changes the highlight. A copied loop (in a sandbox class marked @lucene.experimental) is not a decision, a proposed deprecation is not a decision, and the UnifiedHighlighter's weight-matches-off path is not part of that proposal. The reviewer rated the argument moderate and outweighed; the checker and the adjudication: not intended. When filing, base the contract on the relative-position javadoc and PhraseQuery's normalisation.

How it was found

#

Semi-formal: a bounded-exhaustive comparison of the classic Highlighter's marks with an exact phrase reference, cross-checked against Weight#matches (153,082 checks of query hits), flagged multi-phrase queries that start at position 1. Code reading traced it to the gap loop, and it was reduced to a public-API JUnit with a QueryBuilder query.

The method in full150 words
  • Harness (bounded-exhaustive translation validation of the stock jars). All single-valued documents of 1-3 words over a small alphabet (152 documents, including position holes and stacked tokens) against 2,139 queries: term, synonym, phrase and multi-phrase queries with holes, slop 0-2 and start position 0 or 1, and Boolean combinations; 153,082 checks, one per query hit. Each highlight was compared with an independent exact phrase reference, itself cross-checked against Weight#matches on every hit (0 calibration mismatches), for re-analysed text and for term-vector token streams.
  • Signal. The class classic EXTRA mpq+start: 92 cases per mode, for example [a]@1 [b]@2 on a a b marks the first a. The PhraseQuery with the same positions had no such class, which pointed at the MultiPhraseQuery branch.
  • Reduction. Code reading found the slot loop; the finder wrote the public-API JUnit with a QueryBuilder-built query and ran it on main and on 10.5.2 and 9.12.3.

Never changed in substance: git log -L lists 13 later commits on the branch (a whole-file rewrite, generics, the builder, LUCENE-7417's one-clause case, reformatting); none changes the gap count. Bug record

LFV-829, snapshot of 2026-10-29

Registry title
Classic Highlighter counts the unused positions before a MultiPhraseQuery's first position as gaps, so a phrase that starts at position 1 or later (a leading stop word plus a synonym) is highlighted with extra slop and non-matching pairs get marked
Area
highlighter / original Highlighter, QueryScorer and WeightedSpanTermExtractor (MultiPhraseQuery-to-span conversion)
Priority
Medium, rank 251: A new silent over-highlighting bug in the classic Highlighter with QueryScorer since 2.4/2.9 that leaves hits correct and needs a stop-word-plus-synonym analyzer, a phrase starting with a stop word and a near-miss in the text.
Impact class
silent wrong results
Impact note
Applications on any release from 2.4.0 through 10.5.2 or main that highlight with the original Highlighter and the default QueryScorer (or with the UnifiedHighlighter with weight matches turned off, through PhraseHelper, which was the UnifiedHighlighter default from 6.3.0 through 8.11.x) a MultiPhraseQuery whose first position is above 0, which QueryParser and QueryBuilder build for a quoted phrase that starts with a removed stop word and contains a same-position synonym, get extra highlights on texts where the phrase's terms also occur in order with up to one extra word between them per leading removed word: that pair is marked although it does not match; search hits, counts and scores are correct, there is no error with -ea or -da, no setting or scale is needed beyond such an analyzer, and the default UnifiedHighlighter of 9.0 and later (weight matches on) highlights correctly.
Summary
You search for the quoted phrase "the dogs bark" with an analyzer that removes the stop word 'the' and adds the synonym dog for dogs (QueryParser and QueryBuilder build a MultiPhraseQuery [dogs|dog] at position 1, bark at position 2, slop 0), and highlight the text 'dogs often bark but my dogs bark' with Highlighter and QueryScorer, expecting 'dogs often bark but my <B>dogs</B> <B>bark</B>' (Weight#matches reports only positions 5-6, and the same query starting at position 0, or a PhraseQuery at positions 1 and 2, is highlighted that way). Instead you get '<B>dogs</B> often <B>bark</B> but my <B>dogs</B> <B>bark</B>', with no error. WeightedSpanTermExtractor counts every empty slot from index 0 up to the last position as a position gap, including the unused slot 0 below the first position, so the phrase becomes an ordered SpanNearQuery with slop 1 instead of 0 (one extra unit per leading slot, also for sloppy phrases), while its PhraseQuery branch measures gaps from the first position.
Introduced
35c7eb36dfb07ff919147d7570158433e48cd092 (svn trunk r652164, 'Commit of LUCENE-794 patch - adding phrase/span query support to highlighter', committed by Mark Harwood; JIRA LUCENE-794 is now apache/lucene#1869) wrote the first MultiPhraseQuery-to-SpanNearQuery conversion, already with the slot loop that counts every null slot of disjunctLists[0..maxPosition] as a gap and 'new SpanNearQuery(clauses, slop + positionGaps, slop == 0)' [read: git blame -w -M -C of main :215-224 and :229-232 in the full-history clone]; the MultiPhraseQuery code came from 'MultiPhraseQueryExtraction.patch', attached to LUCENE-794 by others (Benjamin Keil) on 2008-03-09 and folded into the main patch by Mark Miller on 2008-03-10, whose tests use only positions starting at 0. Later commits did not change the counted text: f32b5a56986 (LUCENE-1285, whole-file rewrite) and 3966f998214 (LUCENE-7417, 2016, one-clause special case) kept the loop [read: git log -L]. The PhraseQuery branch never had this defect (relative since LUCENE-2003 in 2.9.1 and LUCENE-5503 in 5.4.0) and the MultiPhraseQuery branch was never aligned with it. Present since the code was written, not a regression; svn era, so no pull request (2008-04-29 (author and commit date of 35c7eb36dfb; the contributed MultiPhraseQuery patch is from 2008-03-09))
