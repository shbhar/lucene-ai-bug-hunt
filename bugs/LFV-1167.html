Operations.complement and minus return a wrong, non-deterministic automaton when an arc ends at Integer.MAX_VALUE

The complement of makeCharRange('a', Integer.MAX_VALUE) accepts "a" and is not deterministic, with no error, because Operations.totalize computes t.max + 1 in int and the wrap adds a dead-state arc on top of the real one. minus is hit the same way; automata built from regex strings are not.

The finding in 30 seconds

#

Background: automaton arcs and how complement works

#
  1. A Lucene Automaton is a set of states joined by arcs. Each arc carries a label range [min, max] of code points (stored as int), so one arc can stand for many characters. Automata.makeCharRange(min, max) builds one arc from a start state to an accepting state.
  2. Operations.complement accepts exactly the words its input rejects. It first makes the automaton deterministic and total: totalize adds an arc into one extra dead state for every label range a state does not handle. Then it flips every state's accept bit, so the dead state, which input words never reach, now accepts.
  3. To find the uncovered ranges, totalize walks a state's arcs in order and remembers the first label not yet covered, t.max + 1. Whatever is left after the last arc, up to Character.MAX_CODE_POINT (1114111), goes to the dead state.

The finding, step by step

#
  1. Build Automata.makeCharRange('a', Integer.MAX_VALUE): it accepts every one-character word from "a" (code point 97) upward, with Integer.MAX_VALUE as an open upper end, the value Lucene's own TestRegExpParsing uses in the expected automaton of [^c].
  2. Call Operations.complement on it. You expect a deterministic automaton that rejects "a". With the upper end Character.MAX_CODE_POINT (1114111) that is exactly what you get.
  3. Instead the complement accepts "a" and isDeterministic() is false, with assertions on or off and no error. Operations.minus(makeString("a"), thatRange) keeps "a" instead of returning the empty language.
  4. Why: complement sends every label a state does not cover to a dead state, tracking the first uncovered label as t.max + 1. For 2147483647 that int sum wraps to -2147483648, so it also adds an arc 0 to 1114111 into the dead state, on top of the real arc. Flipping the accept bits makes the dead state accepting, and "a" reaches it.

Who is affected

#

Only application code that builds its own automaton with an arc ending at exactly Integer.MAX_VALUE (for example makeCharRange(min, Integer.MAX_VALUE) as an open upper end) and passes it to complement or minus. No configuration or scale needed. Regex queries are not hit: RegExp keeps every range within code points. Every release from 4.0.0-alpha to 10.6.0.

Mechanism, terms and numbers536 words

Operations.complement(a, limit) "Returns a (deterministic) automaton that accepts the complement of the language of the given automaton" (Operations.java:338-339 at 5adff78bb168). It determinizes, calls totalize (:351), which adds an arc to one dead state for every label a state does not handle, and flips every accept bit (:352-355). totalize keeps int maxi, the first label not yet covered (:1325), and updates it with if (t.max + 1 > maxi) maxi = t.max + 1; (:1333-1335). For an arc ending at Integer.MAX_VALUE, t.max + 1 wraps to Integer.MIN_VALUE, maxi stays behind, and the tail arc [maxi, 0x10FFFF] to the dead state (:1338-1340) is added on top of the real arc. After the flip the dead state accepts. So complement(makeCharRange('a', Integer.MAX_VALUE)) accepts "a", a word of its input, and reports isDeterministic() false, with assertions on and off; minus(a1, a2), which is intersection(a1, complement(a2)) (:383), keeps words it should remove. Upper ends 0x10FFFF, 0x110000 and Integer.MAX_VALUE - 1 give a deterministic complement that rejects "a". The wrap dates from 2010, when automaton labels went from char to int (LUCENE-2265); every release from 4.0.0-alpha to 10.6.0 has it. RegExp, the only caller of complement in Lucene's runtime code (outside the test framework), cannot create the label, and both methods are deprecated for removal in Lucene 12 on main and branch_11x (public and not deprecated in 10.6.0; the Operations class is tagged @lucene.experimental). The wrong result is demonstrated; whether a label above 0x10FFFF is inside the documented contract is disputed ("Why it looks unintended"), so the fix reads best as a robustness fix.

The mechanism (main 5adff78bb168, lucene/core/src/java/org/apache/lucene/util/automaton/Operations.java)

#
  1. :351: complement runs totalize(determinize(a, limit)). For makeCharRange('a', Integer.MAX_VALUE), state 0 has one arc [97, 2147483647] -> 1; state 1 accepts.
  2. :1325: int maxi = 0. :1330-1332: t.min = 97 > maxi, so the gap arc [0, 96] -> dead is added (correct).
  3. :1333-1335 (the fix site): t.max + 1 is 2147483647 + 1, which wraps to -2147483648; t.max + 1 > maxi is false and maxi stays 0.
  4. :1338-1340: maxi (0) <= 0x10FFFF, so the tail arc [0, 1114111] -> dead is added on top of [97, 2147483647] -> 1. When the result finishes state 0 (Automaton.finishCurrentState, called from addTransition once the arcs of state 1 start, Automaton.java:162-165), it finds the overlap and clears its deterministic flag (:300-305).
  5. :352-355: the accept bits are flipped; the dead state loops on every code point (:1320-1321) and now accepts, so "a" can follow the tail arc into it.

The numbers

#
  • The complement's arcs, as the hunt's probe prints them: s0*: [0,1114111]->2 [97,2147483647]->1, s1: [0,1114111]->2, s2*: [0,1114111]->2 (* = accepting; state 2 is the former dead state); isDeterministic=false.
  • Upper end 0x10FFFF, 0x110000 or 2147483646: deterministic and rejects "b" for makeCharRange('b', hi); 2147483647: not deterministic, accepts "b".
  • minus(makeString("a"), makeCharRange('a', Integer.MAX_VALUE)) is not empty; with Character.MAX_CODE_POINT it is.
  • With char labels (before 2010) t.max + 1 was at most 65536 and could not wrap.
Exposure and likelihood209 words
  • Who. Application code that calls Operations.complement or Operations.minus (or the test framework's AutomatonTestUtil.minus, AutomatonTestUtil.java:74) on an automaton it built itself with an arc ending at exactly Integer.MAX_VALUE, via makeCharRange or addTransition. One arc is enough.
  • Not affected. RegExp's REGEXP_COMPLEMENT (RegExp.java:676-681), the only caller of complement in Lucene's runtime code (outside the test framework), complements negated character classes whose ranges are code points, so regex strings cannot reach it. determinize, CompiledAutomaton and complement with an upper end of Integer.MAX_VALUE - 1 handle such labels correctly.
  • Effect. A silently wrong language: the complement accepts words it must reject, and minus keeps words it must remove. The result also breaks the javadoc's "(deterministic)" promise, so new CharacterRunAutomaton(result) throws IllegalArgumentException "Automaton must be deterministic" (RunAutomaton.java:63-64; executed, assertions on and off).
  • API status. Both methods are @Deprecated ("will be removed in Lucene 12") on main (Operations.java:346-349, :372-375) and branch_11x (#15763, #15755); in 10.6.0 and earlier they are public and not deprecated (the Operations class is tagged @lucene.experimental, Operations.java:56, as on main).
  • Likelihood: rare. No matching public report was found in the recorded searches and no Lucene component builds the label, but whoever does gets the wrong language every time.

Why it looks unintended

#
  • complement promises "a (deterministic) automaton that accepts the complement"; no javadoc states or checks an upper label bound.
  • Only Integer.MAX_VALUE fails, the wrong answer is on a valid code point ("a"), and Lucene's own TestRegExpParsing uses that value as an open upper end.
  • Disputed: the package describes a Unicode alphabet, so labels above 0x10FFFF may be outside the contract.
The full argument299 words
  • What is shown and what is disputed. The implementation defect is demonstrated: for the stored int intervals, totalize builds overlapping arcs and complement accepts words of its input. Whether an arc ending above 0x10FFFF is inside the documented contract is disputed (the devil's advocate below; the cross-model reviewer rated that defence strong). The points below are a judgement, not a settled fact.
  • Contract. complement: "Returns a (deterministic) automaton that accepts the complement of the language of the given automaton" (Operations.java:338-339); minus promises the same for intersection(a1, complement(a2)) (:360-362); totalize: "added transitions to a dead state so that from every state and every label there is a transition" (:1309-1310). Neither these nor makeCharRange ("accepts a single codepoint whose value is in the given interval", Automata.java:136-151) or addTransition state or validate an upper label bound.
  • Tests. TestRegExpParsing.testNegatedChar and testNegatedCharRange build the expected automata of [^c] and [^b-d] as unions whose upper part is makeCharRange('d', Integer.MAX_VALUE) and makeCharRange('e', Integer.MAX_VALUE) (TestRegExpParsing.java:190-194, :240-244). Caveat: those tests never complement these automata, and they compare languages through AutomatonTestUtil.sameLanguage / subsetOf (TestRegExpParsing.java:832-840), which ignores labels above Character.MAX_CODE_POINT; so they show the idiom in Lucene's own code, not a promise about what complement does above 0x10FFFF. Complementing the [^c] one accepts "e", a word in the Unicode range, and is not deterministic; complement(new RegExp("[^c]").toAutomaton()) rejects "e" (main and 10.6.0).
  • Neighbouring code guards the same overflow. AutomatonTestUtil.subsetOf caps at Character.MAX_CODE_POINT before computing max + 1 (AutomatonTestUtil.java:681-686); totalize has no such guard.
  • History. The line comes from the char-label code, where t.max + 1 could not wrap, and was kept unchanged when labels became int (LUCENE-2265, 2010). No commit, issue or PR found in the recorded searches discusses the wrap.
The devil's-advocate check191 words

The strongest case for "intended": the package documents a "DFA/NFA implementation with Unicode alphabet" (package-info.java:33) and makeCharRange speaks of code points, so an arc ending at Integer.MAX_VALUE is outside complement's domain; a maintainer once said a special label must be a valid Unicode character for UTF32ToUTF8 (#6094, LUCENE-5030). makeAnyChar, totalize and RegExp all bound labels by Character.MAX_CODE_POINT. The cross-model reviewer refuted the bug on exactly these grounds (medium confidence, and it rated this defence strong), while reproducing it and agreeing with the root cause and the fix.

Our answer (a judgement): no javadoc states the precondition and nothing enforces it; Lucene's own tests use Integer.MAX_VALUE as an open upper end (although only in expected automata, compared up to Character.MAX_CODE_POINT); other operations handle the label; and the wrong answer is on an in-alphabet word ("a"). That makes it a fair argument for Low priority and for framing the fix as hardening (or for clarifying the contract, fix C), rather than evidence that the behaviour is intended. The independent reproducer, the devil's-advocate verifier and the adjudication did not accept it as making the behaviour intended.

Suggested fix

#

Recommended Keep maxi as a long (fix A)

Keep maxi in totalize as a long (t.max + 1L, two (int) casts where it is passed on), so the sum cannot wrap. Nothing changes for arcs that do not end at Integer.MAX_VALUE. The repro passes with assertions on and off, and core's util.automaton test package runs 239 tests with 0 failures (2 skipped).

        }
        if (t.max + 1L > maxi) {
          maxi = t.max + 1L;

      ...

Downstream note

#

Downstream code that builds its own automata with Integer.MAX_VALUE as an open upper end and subtracts them with complement or minus gets silently wrong languages; automata built from regex strings are not affected.

How it was found

#

A proof-obligation audit of Operations.complement's contract: for every legal input the result must be deterministic and accept exactly the words the input rejects. The obligation fails at t.max + 1 in totalize for an arc ending at Integer.MAX_VALUE; a public-API JUnit test then witnessed the wrong language.

The method in full108 words

Method: semi-formal (a proof-obligation audit of a class's contract, witnessed by an executable repro).

  • The finder checked complement against its javadoc promise and totalize against its own ("from every state and every label there is a transition", with no overlap), over the full int label range that makeCharRange and addTransition accept, and found that t.max + 1 can wrap.
  • The finder then wrote a public-API JUnit test, a probe that prints the complement's arcs, and the long-maxi fix that makes them pass.
  • An independent reproducer, an executed cross-model review, a devil's-advocate verifier and an adjudication reproduced it with their own tests ("Prior reports, history and checks").

#

Summary
