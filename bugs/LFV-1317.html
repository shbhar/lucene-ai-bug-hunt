FixedBitSet.xor with a longer set sets bits past length(): an empty 10-bit set reports bit 15

FixedBitSet.xor with a longer set that fits in the same 64-bit words copies the longer set's bits past length(): an empty 10-bit set XORed with a 20-bit set holding bit 15 reports cardinality() 1 and nextSetBit(0) 15. No Lucene production code calls xor; only its direct callers are hit.

The finding in 30 seconds

#

xor XORs whole 64-bit words and never clears the unused top bits of the last word. A longer set that fits in the same number of words passes its only check, so its bits past this set's length() stay set, and every method that reads whole words counts them.

Background in three steps

#
  1. A FixedBitSet of length n stores its bits in 64-bit long words. A 10-bit set has one word, and bits 10-63 of it are unused: the class calls them ghost bits.
  2. The class keeps the ghost bits 0. cardinality(), nextSetBit(), intersects(), equals(), hashCode() and several more read whole words without masking; each is marked "Depends on the ghost bits being clear!".
  3. So every method that writes bits must leave the ghost bits 0, for every input it accepts.

The finding, step by step

#
  1. Make an empty FixedBitSet a of length 10 and a FixedBitSet b of length 20 with only bit 15 set. Both fit in one 64-bit word; bits 10-63 of a's word are unused "ghost bits" that must stay 0.
  2. Call a.xor(b). You expect a to stay empty: b has no bit in 0-9, the only bits a can hold.
  3. xor XORs whole words and only asserts that b has no more words than a. Both have one, so b's bit 15 is copied into a's ghost bits.
  4. Now a.cardinality() is 1, a.nextSetBit(0) is 15 and a.equals(new FixedBitSet(10)) is false, while a.get(0) to a.get(9) are all false. No assertion fires in these calls, with assertions on or off.
  5. a.xor(new BitSetIterator(b, 1)) does the same. The same doc through an iterator that is not backed by a FixedBitSet is dropped, and a stays empty.

Who is affected

#

Only code that calls FixedBitSet.xor itself (an @lucene.internal class) with a longer set, directly or through a BitSetIterator over a FixedBitSet. No Lucene production code calls xor, so Lucene's own indexing, queries and search are not affected. For such a caller the result is silently wrong, with assertions on or off, in every release since 4.7.0.

Mechanism, terms and numbers604 words

A FixedBitSet stores its bits in 64-bit words, and the unused high bits of the last word (the class calls them ghost bits) must stay 0, because cardinality, nextSetBit, intersects, equals, hashCode and several other methods read whole words without masking. xor(FixedBitSet other) XORs whole words and only asserts that other has no more words than this set. When other is longer but fits in the same number of words, its bits at or above this set's length() land in the ghost bits.

An empty 10-bit set XORed with a 20-bit set holding only bit 15 then reports cardinality() 1 and nextSetBit(0) 15, with assertions on and off, while get(0) to get(9) are all false. xor(DocIdSetIterator) does the same for a BitSetIterator over a FixedBitSet, while its generic loop drops docs at or above length(). No Lucene production code calls xor, so only code that uses this @lucene.internal class directly is hit. Every release since 4.7.0 has it (eight releases and main were run; the others follow from the source history).

The mechanism (main 5adff78bb168)

#
  1. The invariant. The FixedBitSet(long[], int) javadoc: the "'extra' or 'ghost' bits must be clear (or they may provoke spurious side-effects)" (FixedBitSet.java:152-159). verifyGhostBitsClear: "Some methods rely on this implicit assumption" (:177-193). The marker "Depends on the ghost bits being clear!" is on cardinality (:216), nextSetBitInRange (:412), intersects (:638), equals (:844) and hashCode (:850), and also on ensureCapacityInternal (:70), intersectionCount, unionCount, andNotCount (:97, :108, :128), nextClearBitInRange (:384) and scanIsEmpty (:706). This wording and the markers came with LUCENE-6427 (#7486) and first shipped in 5.2.0; from 4.7.0 to 5.1.0 cardinality() already counted whole words (BitUtil.pop_array(bits, 0, bits.length)), so the symptom is the same there.
  2. Entry points. xor(FixedBitSet other), javadoc "this = this XOR other", calls xor(other.bits, other.numWords) (:608-611). xor(DocIdSetIterator) sends a BitSetIterator over a FixedBitSet to the same method (:616-618); any other iterator runs while ((doc = iter.nextDoc()) < numBits) flip(doc); (:620-623), which drops docs at or above length().
  3. The fix site. The private xor(long[], int) (:627-634) asserts otherNumWords <= numWords (:628), then XORs words [0, min(numWords, otherNumWords)) and never masks the last word above numBits. A 10-bit and a 20-bit set both have one word, so the check passes (also with -ea), and bit 15 of b is written into bit 15 of a's word, a ghost bit.
  4. The symptoms. cardinality() counts whole words: 1. nextSetBit(0) calls nextSetBitInRange(0, numBits), which returns the first set bit of the word, 15, with no check against numBits (:351-356, :411-432); the base class defines nextSetBit(index) as nextSetBit(index, length()) (BitSet.java:93-97), which would give NO_MORE_DOCS. equals compares the arrays: false against an empty 10-bit set. The other readers are wrong too: after the XOR, a.intersects(b) is true, a.scanIsEmpty() false and FixedBitSet.intersectionCount(a, b) 1; FixedBitSet.ensureCapacity(a, 30) returns a larger set in which get(15) is true, so the ghost bit becomes a real member; and a.clone() (:827-831) fails the constructor's ghost-bit assert (:169) with assertions on and copies the bit with assertions off.
  5. Multi-word variant. With assertions off, a longer other with more words corrupts the shared last word the same way (a 10-bit set reported nextSetBit(0) 40); with assertions on that case trips the assert.

Related row: LFV-1318 is the same shape in LongBitSet.or and LongBitSet.xor (its own methods and fix site in LongBitSet.java).

Exposure and likelihood130 words
  • Who: code that calls FixedBitSet.xor(FixedBitSet), or xor(DocIdSetIterator) with a BitSetIterator over a FixedBitSet, passing a set with a larger length() that has a bit at or above this set's length() in this set's last word. FixedBitSet and BitSet are @lucene.internal (FixedBitSet.java:29, BitSet.java:25).
  • Not hit: Lucene itself. A grep of lucene/*/src/java on main finds no .xor( call; the callers of FixedBitSet.xor are tests only (TestFixedBitSet and three tests in org.apache.lucene.search). In 2015 a maintainer (jpountz) remarked on #7486 that flip "is only used by xor which is not used".
  • Effect: silent wrong counts, iteration and equality on the caller's own bit set; no exception. Code outside Lucene that calls xor directly can be hit.
  • Since: 4.7.0 for xor(FixedBitSet), 5.0.0 for the BitSetIterator path.

Why it looks unintended

#
  • The class says ghost bits "must be clear (or they may provoke spurious side-effects)"; xor's javadoc is only "this = this XOR other": no length rule.
  • xor(DocIdSetIterator)'s generic loop drops docs >= length(): the same call clips or corrupts, by iterator class.
  • With assertions on, the tested siblings clip or fail on this input; only xor still corrupts silently.
The full argument345 words
  • The contract. The ghost-bit invariant is documented in the class, and the methods that depend on it are marked ("Depends on the ghost bits being clear!"). xor's javadoc is only "this = this XOR other"; no javadoc, CHANGES or MIGRATE entry or test states a length rule for xor.
  • The same class clips this input. The generic xor(DocIdSetIterator) loop accepts docs at or above length() and drops them (FixedBitSet.java:620-623). On the 10-bit set, doc 15 through a BitSetIterator over a FixedBitSet gives cardinality 1 and through a range iterator 0; on a 3-bit set, doc 5 through a BitSetIterator over a FixedBitSet gives 1 and over a SparseFixedBitSet 0 (assertions on and off).
  • With assertions on, every sibling tested clips or fails; only xor accepts the input silently even then. On the same input and(FixedBitSet) and andNot(FixedBitSet) leave the 10-bit set empty; or(FixedBitSet) throws IndexOutOfBoundsException: Range [0, 0 + 20) out of bounds for length 10 (it goes through orRange, whose Objects.checkFromIndexSize rejects it, :477-481, :603-606, since #14083/#14134 in 10.2.0), and or(BitSetIterator) over a FixedBitSet throws, with assertions on and off. or(DocIdSetIterator) with doc 15 from an iterator not backed by a FixedBitSet (a range iterator, or a BitSetIterator over a SparseFixedBitSet), and andNot with a range iterator, fail the range assert of set or clear with assertions on. With assertions off that or writes the same ghost bit (cardinality 1, nextSetBit(0) 15), because it hands the docs to iter.intoBitSet (:455-460), which calls set(int, int) for a range iterator and set(int) in the default loop (DocIdSetIterator.java:92-96, :205-209), and their range checks are asserts only (:296, :774-776). That case breaks an asserted precondition of set; xor's case passes xor's own assert.
  • History. LUCENE-5440 (#6503) added xor. Its author, Shai Erera, wrote on 2014-02-11 that they "added an assert to FBS.or/xor if the given set.length() was bigger than current – we silently discarded bits!"; the assert that was committed (87f987082b5) compares word counts, not lengths.
The devil's-advocate check183 words

"other must never be longer: this is caller misuse." FixedBitSet is @lucene.internal, the util package says its APIs "are primarily internal" (package-info.java:35), and the word-count assert, the 2014 comment and the upstream random test, which XORs only when b0.length() <= b.length() (TestFixedBitSet.java:213), all point that way. An independent reviewer from another model family (OpenAI GPT-5.6) returned not real on exactly this scope argument, after reproducing the bug and agreeing on the cause and the fix.

Our answer (a judgment; the maintainers decide): the precondition is not documented; it is enforced only per word and only with -ea, so the violating input passes silently even with assertions on; the same class's generic xor(DocIdSetIterator) path accepts the input and clips; and where Lucene treats a longer operand as illegal (or(FixedBitSet)) it fails loudly. The package note says these APIs "may change between releases" (package-info.java:35), which is about stability rather than results. A maintainer may still call it caller misuse; then the bug is that the precondition is unenforced, and the fix is option B.

Suggested fix

#

Recommended A. Mask the last word after the XOR

Suggested: mask the last word after the XOR when other has as many words: thisBits[numWords - 1] &= -1L >>> -numBits; (+4 lines). It drops other's bits past length(), like the generic iterator loop; the repro and 171 tests of the closest suites pass. Rejecting a longer set (B, like or()) is as defensible; maintainers choose.

    while (--pos >= 0) {
      thisBits[pos] ^= otherBits[pos];
    }
    if (otherNumWords >= numWords && numWords > 0) {
      // other may be longer than this set: clear the ghost bits it set in the last word
      thisBits[numWords - 1] &= -1L >>> -numBits;
    }
All options and trade-offs3 options · 433 words

Three options. A was tested with gradle in a scratch worktree of 5adff78bb168 (the repro and the closest suites, not the full core suite); B and C are by reading. A or B is a maintainer choice: A keeps xor lenient like the generic xor(DocIdSetIterator) loop; B matches or(FixedBitSet) and the 2014 author's stated intent. The related row LFV-1318 suggests rejecting the longer set (this doc's B) for LongBitSet, which has no iterator overload of or or xor that clips; a fix for both rows would use one rule for both classes.

A. Mask the last word after the XOR (validated by the checks) (recommended)

#

In the private xor(long[], int) (FixedBitSet.java:627-634), after the XOR loop, +4 lines:

    while (--pos >= 0) {
      thisBits[pos] ^= otherBits[pos];
    }
    if (otherNumWords >= numWords && numWords > 0) {
      // other may be longer than this set: clear the ghost bits it set in the last word
      thisBits[numWords - 1] &= -1L >>> -numBits;
    }

Trade-offs

  • Gives what the generic xor(DocIdSetIterator) loop gives (other's bits past numBits dropped), so both iterator paths agree; covers xor(FixedBitSet) and the BitSetIterator path (same private method). One AND per call, with the class's existing -1L >>> -n mask idiom.
  • Keeps the word-count assert: a longer set with more words still fails with -ea and is now clipped with -da. Dropping the assert would make it clip always.

What the checks validated

  • Gradle in a scratch worktree of 5adff78bb168, OpenJDK 25.0.3, seed DEADBEEF: stock, the repro fails with assertions on and off; with fix A it passes, on and off.
  • With fix A: TestFixedBitSet (34), TestBitSetIterator (11), TestFixedBitDocIdSet (7), TestDocValuesOrdinalRangeIterator (23), TestSkipBlockRangeIteratorBitSetOperations (56) and TestDocValuesRangeIteratorIntoBitSet (40): 171 tests, 0 failures, 10 skipped (@Nightly); TestFixedBitSet with assertions off: 34, 0 failures.
  • checkGoogleJavaFormat, ecjLintMain, ecjLintTest, forbiddenApisMain and forbiddenApisTest (core): pass. Not run: the full lucene/core suite.

B. Reject a longer set, as or(FixedBitSet) does (by reading)

#

In xor(FixedBitSet), throw when other.length() > length() (as orRange's Objects.checkFromIndexSize does for or), and let xor(DocIdSetIterator) take its fast path only when the bit set is not longer, else the clipping loop.

Trade-offs

  • Matches the 2014 assert's intent and or(); at least as defensible as A.
  • Turns a silent return into an exception for existing callers; the regression test becomes an expectThrows test.

C. Remove the unused xor methods (by reading)

#

No Lucene production code calls xor(FixedBitSet) or xor(DocIdSetIterator).

Trade-offs

  • An API removal on an internal class, which maintainers may prefer for a major version; the tests that use xor would need rewriting.

Downstream note

#

How it was found

#

Semi-formal: a proof-obligation audit of FixedBitSet's contract, where every mutating method must leave the ghost bits clear for any input it accepts. xor accepts a longer set with the same word count and leaves that set's high bits in place; a one-test JUnit repro on stock main witnessed it.

The method in full84 words
  • Obligation: after every mutating method, the bits at or above length() are 0, for every input the method accepts (FixedBitSet.java:152-159, :177-193).
  • Finding: xor's only guard compares word counts and is an assert (:628), so a longer set within the same word count is accepted, and the whole-word XOR (:630-633) keeps its high bits.
  • Witness: a JUnit test on stock main, then an independent reproduction, a cross-model review, an intended-behaviour review and an adjudication (see Independent checks).
