Grouped faceting with a facetPrefix drops binary facet values that have ten 0xFF bytes after the prefix, and an exact match empties the segment's result

TermGroupFacetCollectorManager ends the facetPrefix range at the prefix plus ten 0xFF bytes, a bound that holds only for text. Binary facet values with ten or more 0xFF bytes after the prefix are silently dropped, and one equal to that bound empties the segment's result: 0 entries instead of 2.

The finding in 30 seconds

#

The collector counts only facet ordinals in [lookup(prefix), lookup(prefix + BIG_TERM)). BIG_TERM is ten 0xFF bytes and is only guaranteed to be bigger than UTF-8 terms. A binary value at or above that end key is cut off; a value equal to it turns the single-valued end ordinal negative, so nothing in the segment is counted.

  1. Index two documents in one group, with the single-valued facet values pa (2 bytes) and p followed by ten 0xFF bytes (11 bytes). Both start with p.
  2. Count grouped facets with TermGroupFacetCollectorManager and facetPrefix p. You expect 2 entries, count 1 each: the javadoc says "only include facet entries with this prefix".
  3. To find where the prefix range ends, the collector looks up p + ten 0xFF bytes (UnicodeUtil.BIG_TERM), assuming nothing with the prefix sorts that high. True for UTF-8 text, where 0xFF never occurs; here it is exactly the second value.
  4. The lookup finds that value (ordinal 1), so the end ordinal becomes -1 - 1 = -2 and every document of the segment is skipped: 0 entries, pa included. With assertions on, assert ef < 0 throws an AssertionError from IndexSearcher.search instead.
  5. With eleven 0xFF bytes only that value is lost (1 entry instead of 2), single- or multi-valued; nine 0xFF bytes are counted. Text facets are never affected. Every release since 4.0.0 has this code.

Who is affected

#

Only applications that run grouped faceting (TermGroupFacetCollectorManager, experimental; TermGroupFacetCollector before 10.6) with a facetPrefix over binary facet values, such as packed numbers or composite keys, with ten or more 0xFF bytes right after the prefix. Text facets cannot hit it. Default config, no scale needed; silent with assertions off.

Mechanism, terms and numbers500 words

TermGroupFacetCollectorManager limits facetPrefix to the facet ordinals from lookupTerm(prefix) up to lookupTerm(prefix + UnicodeUtil.BIG_TERM), where BIG_TERM is ten 0xFF bytes. That end key is above every value with the prefix only when the bytes after the prefix are UTF-8; BIG_TERM's own javadoc promises no more. A binary facet value that starts with the prefix and continues with ten or more 0xFF bytes sorts at or above the end key and is silently left out. When a single-valued value equals the end key, the lookup finds it, ef = -ef - 1 turns the end ordinal negative, and collect() skips every document of the segment: in the repro the facet values pa and p + ten 0xFF bytes with prefix p give 0 entries instead of 2 (with assertions on, assert ef < 0 throws an AssertionError out of IndexSearcher.search). Text facet values can never hit it. The code came with grouped faceting in 4.0.0 (LUCENE-3802, 2012) and fails on every release run up to 10.6.0 and on main.

Terms

#
  • Grouped faceting: for each facet value, count the distinct groups that have at least one document with that value (TermGroupFacetCollectorManager class javadoc, :44-45). facetPrefix keeps only facet values that start with the prefix.
  • Ordinals: per segment, the distinct values of a SortedDocValuesField (or SortedSetDocValuesField) are sorted as unsigned bytes and numbered 0..n-1. All values with a given prefix form one contiguous ordinal range, so the collector only needs its start and end.

Exposure and likelihood178 words
  • Who is exposed. Users of TermGroupFacetCollectorManager (10.6.0 and main) or of TermGroupFacetCollector (4.0.0 to 10.6.0) who pass a non-null facetPrefix and index binary facet values in SortedDocValuesField or SortedSetDocValuesField.
  • What it takes. A facet value with ten or more consecutive 0xFF bytes right after the prefix. An independent check built a plausible shape: a type byte 0x01 followed by NumericUtils.longToSortableBytes(Long.MAX_VALUE) twice (sixteen 0xFF), prefix {0x01}; the max key was dropped, 1 entry instead of 2, on main and 10.6.0. No real collation-key trigger was shown, and none is claimed.
  • Opt-in. Grouped faceting with a prefix must be asked for, and the class is @lucene.experimental (:54); the codec and IndexWriterConfig are the defaults.
  • Effect. With assertions off, matching entries are silently missing. The exact-match case empties the facet result of the whole segment that holds the value, also values without any 0xFF; with assertions off, other segments are unaffected (each computes its own range). With assertions on, that segment's AssertionError aborts the whole search.
  • Not affected. Text (UTF-8) facet values, and facetPrefix == null.

Why it looks unintended

#
  • The javadoc promises prefix semantics, "only include facet entries with this prefix"; nothing on the grouping API limits facet values to UTF-8.
  • The code's own assert ef < 0 says the end key is never a value; legal input breaks it, and pa, with no 0xFF, is lost too.
  • The upstream test's oracle is startsWith(facetPrefix); it only generates text.
The full argument163 words
  • Contract. @param facetPrefix only include facet entries with this prefix; may be null (TermGroupFacetCollectorManager.java:73); the 2012 API said "The facet prefix a facet entry should start with to be included" (4.0.0 TermGroupFacetCollector.java:52). SortedDocValuesField takes any value "at most 32766 bytes long" (SortedDocValuesField.java:38), and facetPrefix is any BytesRef. No grouping javadoc, package doc (package-info.java:180-193), CHANGES or MIGRATE entry limits facet values to UTF-8.
  • Invariant. assert ef < 0 (written in 2012 in aed1b577a83 on the doc-values branch, first released in 4.2.0 through the LUCENE-4547 merge 5cbaddcbc7ff) states that the end key cannot exist in the field. Legal input breaks it, and the in-range value pa is lost too: a broken invariant, not an approximation at the edge.
  • Tests. TestTermGroupFacetCollectorManager.java:738 uses facetValue.startsWith(facetPrefix) as the oracle; its values are random Unicode strings, so they never contain 0xFF bytes.
  • History. No issue, PR, review comment or list thread records a by-design decision about binary values and this bound.
The devil's-advocate check203 words

The strongest case for "intended": BIG_TERM was always a heuristic for character data. When the ten-0xFF sentinel was chosen (#3578, LUCENE-2504, 2010), a comment there called it "like a NaN sentinel, if someone is doing something very wierd, maybe it wont work"; its javadoc says only "likely" for terms that are not UTF-8; in 2012 the postings highlighter replaced a one-byte 0xFF ceiling, commented "this looks bogus, but its not. we are dealing with characters :)", with BIG_TERM (9dd7d2ecf64); the grouping API is experimental, FacetEntry.toString() prints values with utf8ToString() (GroupedFacetResult.java:131), and its tests use text only.

Why it fails: that caveat lives only on the @lucene.internal UnicodeUtil and in code comments, never on the public facetPrefix contract, and toString() is a debug string that plays no part in the counting; #3578 is about a sort comparator's null proxy, in 2010, about a year and a half before grouped faceting (2012); and the exact-match case does not just mishandle the odd value, it drops every value of the segment. The executed review by another model family (OpenAI GPT-5.6) rated the "intended" case moderate, and the devil's-advocate check concluded it does not hold. It does make the trigger contrived, hence Low.

Suggested fix

#

Recommended End the range at the prefix's byte successor (validated)

End the prefix range at the prefix's byte successor: increment its last byte that is not 0xFF and cut after it; no end bound if the prefix is empty or all 0xFF. Use it in both paths and drop the assert (+29/-13). The repro, TestTermGroupFacetCollectorManager, the whole grouping module and check pass with it.

// Smallest term greater than every term that starts with prefix, or null if there is none.
private static BytesRef prefixUpperBound(BytesRef prefix) {
  for (int i = prefix.length - 1; i >= 0; i--) {
    if (prefix.bytes[prefix.offset + i] != (byte) 0xFF) {
      byte[] bound = new byte[i + 1];
      System.arraycopy(prefix.bytes, prefix.offset, bound, 0, i + 1);
      bound[i]++;
      return new BytesRef(bound);
    }
  }
  return null;
}

End the range at the prefix's byte successor (validated) (recommended)

#

Add the helper below. Single-valued: end == null gives ef = facetDV.getValueCount(), else ef = facetDV.lookupTerm(end) and, if negative, ef = -ef - 1. Multi-valued: end == null gives ef = facetFieldNumTerms, else seekCeil(end) as today. The end key may now exist as a value; it is exclusive either way, so the assert goes. The BytesRefBuilder and UnicodeUtil imports go too.

// Smallest term greater than every term that starts with prefix, or null if there is none.
private static BytesRef prefixUpperBound(BytesRef prefix) {
  for (int i = prefix.length - 1; i >= 0; i--) {
    if (prefix.bytes[prefix.offset + i] != (byte) 0xFF) {
      byte[] bound = new byte[i + 1];
      System.arraycopy(prefix.bytes, prefix.offset, bound, 0, i + 1);
      bound[i]++;
      return new BytesRef(bound);
    }
  }
  return null;
}

Trade-offs

  • Exact for any bytes, at the same cost (one lookup per segment).
  • bound[i]++ wraps a signed Java byte (0x7F becomes 0x80), which is still the successor, because BytesRef compares bytes unsigned.
  • Afterwards nothing in lucene/ on main uses BIG_TERM any more (these two lines are its last users).

How it was found

#

A semi-formal proof-obligation audit of UnicodeUtil.BIG_TERM's contract: its users may rely on it as an upper bound only for UTF-8 terms. The audit first judged that lead harmless; an independent reviewer from another model family (OpenAI GPT-5.6), asked to refute the verdict, pointed at this collector, and a public-API test confirmed it.

The method in full102 words
  • The obligation. Every user of BIG_TERM as an upper bound must only compare it with UTF-8 terms, or must otherwise make sure no real term reaches it.
  • The audit. The first pass over the users judged the lead harmless. An independent reviewer from another model family (OpenAI GPT-5.6), asked to refute that negative verdict, named TermGroupFacetCollectorManager's prefix range end as a user that takes arbitrary binary doc values.
  • The witness. Code reading confirmed both paths, and the one-test public-API repro above failed on main with assertions on and off; further variants mapped nine, ten and eleven 0xFF bytes in both paths.
