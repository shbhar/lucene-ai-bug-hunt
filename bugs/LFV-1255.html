FieldType.equals and hashCode ignore the vector dimension, encoding and similarity

FieldType.equals and hashCode never look at the vector settings: a 3-dimensional FLOAT32 EUCLIDEAN type equals a 768-dimensional BYTE DOT_PRODUCT type, and both hash alike. No production code in Lucene calls these methods, so only applications that compare field types or use them as map keys are affected, in every release since 9.0.0.

The finding in 30 seconds

#

A FieldType describes how a field is indexed. Since 9.0.0 it also holds vector settings: dimension, encoding (FLOAT32 or BYTE) and similarity function, set with setVectorAttributes. equals and hashCode exist so code can tell whether two field types are the same.

  1. Make two vector field types: a.setVectorAttributes(3, FLOAT32, EUCLIDEAN) and b.setVectorAttributes(768, BYTE, DOT_PRODUCT). The stock factories KnnFloatVectorField.createFieldType(3, EUCLIDEAN) and KnnByteVectorField.createFieldType(768, DOT_PRODUCT) behave the same.
  2. You expect a.equals(b) to be false: dimension, encoding and similarity are part of a field's schema, and IndexWriter refuses to mix them in one field.
  3. Instead a.equals(b) is true and both have the same hashCode. A HashSet holding a, b and a plain new FieldType() has size 1.
  4. Why: equals and hashCode compare 13 properties (stored, tokenized, index options, norms, four term-vector flags, doc values, skip index, point dimensions) but none of the three vector settings, although the copy constructor copies them.

Who is affected

#

Only application code that compares FieldTypes with equals, or keys a map or set by them, and has vector types that differ only in vector settings: such types collapse into one. Lucene's own indexing and search never call these methods and are unaffected. Default configuration, every release since 9.0.0; rare, so priority Low.

Mechanism, terms and numbers394 words

FieldType.hashCode (FieldType.java:536-554) and equals (:556-576) compare 13 properties: the point dimensions, doc values type, skip index, index options, norms, the four term-vector flags, stored and tokenized. They never read vectorDimension, vectorEncoding or vectorSimilarityFunction (:49-51), although the copy constructor copies them (:69-71) and setVectorAttributes sets them (:386-396). So two types that differ only in their vector settings, or a vector type and a plain new FieldType(), compare equal and hash alike. No production code in Lucene was found to call these methods (IndexingChain compares field types by identity), so indexing and search are unaffected; the wrong answer reaches only applications that compare field types or key maps and sets by them, and Lucene's own TestFieldType.testCopyConstructor, which uses equals as its oracle. The methods were added "so one can easily check if they are the same" (LUCENE-5793), the same gap for the point dimensions was fixed in LUCENE-7073, and of the properties added since, the index dimension count (LUCENE-8496) and the doc-values skip index (#13449) went into both methods, while the vector settings and the experimental attribute map (LUCENE-8601) did not. Present since 9.0.0 (encoding since 9.4.0) and on main; adding the three fields fixes it.

The code (main 5adff78bb168)

#
  • State. vectorDimension, vectorEncoding and vectorSimilarityFunction are fields of FieldType (FieldType.java:49-51), set by setVectorAttributes (:386-396) and copied by the copy constructor (:69-71).
  • The comparison. hashCode (:536-554) mixes in 13 properties and equals (:556-576) compares the same 13. Neither reads a vector field.
  • Schema identity elsewhere. FieldInfo.verifySameVectorOptions (FieldInfo.java:401-425) rejects a field whose vector dimension, encoding or similarity differs from the one already recorded.

The numbers

#

A 3-dim FLOAT32 EUCLIDEAN type and a 768-dim BYTE DOT_PRODUCT type: equals true, same hashCode. Changing only the dimension (3 against 4), only the encoding or only the similarity: each still equal with the same hash. A plain new FieldType() against a 3-dim vector type: equal. new HashSet<>(List.of(f3, b768, plain)).size() is 1 (the 3-dim, the 768-dim and the plain type). Controls: types that differ in stored or in point dimensions compare unequal.

toString (:439-490) prints no vector setting either, so the repro's failure message shows an empty value. That is consistent with the same oversight and is not part of the claim.

Exposure and likelihood237 words
  • Who is hit. Code that de-duplicates field types in a registry, caches by FieldType, or compares two types to decide whether they match. Two vector types that differ only in dimension, encoding or similarity, and a vector type and a plain type, are treated as one.
  • Not hit. Lucene's indexing chain compares field types by identity (IndexingChain.java:1879, :1889), and no production code under lucene/*/src/java was found to call FieldType.equals/hashCode or to key a map or set by FieldType; Lucene's own TestFieldType does call them. IndexWriter still rejects a document whose vector settings differ from the field's.
  • Inside Lucene's tests. TestFieldType.testCopyConstructor checks assertEquals(ft, new FieldType(ft)) on a random type that has vector settings (TestFieldType.java:102-140), so it cannot catch a copy constructor that drops them, the failure LUCENE-7073 was about.
  • Consequence in an application (by reading, not executed). If a 768-dim type is replaced by an "equal" 3-dim type, the vector field constructor later fails loudly on the dimension or encoding (KnnFloatVectorField.java:134-145); a type that differs only in similarity passes that constructor and could go unnoticed, unless the index already holds the field with the other similarity, which IndexWriter rejects (IndexingChain.java:2351-2354).
  • Default vs opt-in, scale. Default configuration, public API, assertions on or off; two objects are enough.
  • Likelihood: rare. No prior report was found (searches of 2026-11-03), although the gap has been there since 9.0.0 (2021).

Why it looks unintended

#
  • LUCENE-5793 added the methods "so one can easily check if they are the same"; they compared every schema property then present.
  • Robert Muir called the same gap for point dimensions broken and fixed it (LUCENE-7073); #13449 added the skip index to both.
  • IndexWriter treats the vector settings as schema: it rejects a field whose dimension, encoding or similarity differs.
The full argument177 words
  • Purpose. #6855 (LUCENE-5793, bb081414094, 2014): "would be nice to have equals and hashCode to FieldType, so one can easily check if they are the same". The first version compared every schema property; only the mutability flag frozen is left out ("// Do not copy frozen!", FieldType.java:75).
  • Precedent. #8129 (LUCENE-7073): Robert Muir wrote "There is a test for this copy constructor stuff, but it relies on hashcode/equals working, which is also broken", and 4df4cb07ac6 added the point dimensions to equals, hashCode and the test.
  • Maintenance pattern. LUCENE-8496 (1118299c338) and GITHUB#13449 (048770205cb) added their new properties to both methods. The two vector commits (c02f07f2d5d, a693fe819b0) added field, getter, setter and copy-constructor line, but not equals/hashCode. LUCENE-8601 (63dfba4c7d8, 2019) likewise left the experimental attribute map out of both methods (not claimed). No review comment, javadoc, test, CHANGES or MIGRATE entry says this was deliberate.
  • Tests. TestFieldType.testEquals (TestFieldType.java:30-66) has no vector case; no test anywhere asserts that types with different vector settings are equal.
The devil's-advocate check113 words

The strongest case: the methods have no javadoc, Object.equals need not compare every field, frozen is already left out, and no production code in Lucene uses them.

Why it is weaker than it looks: frozen is a mutability flag, not a schema property. The methods exist to tell whether two types are the same; the project fixed the same gap for the point dimensions and later added the index dimension count and the skip index to both methods. The argument lowers the impact, not the defect, though a maintainer could still judge the change too minor. An executed review by another model family (OpenAI GPT-5.6) rated the defence moderate and the bug real.

Trade-offs

The smallest change, in the style of the existing comparisons; Objects.hashCode stays null-safe for a copy of a custom IndexableFieldType. It changes the result of equals only for types that differ in vector settings, which is the point. It also changes the hash value of every FieldType, since the new terms are mixed in for all of them; no production code in Lucene depends on the old values.

Impact note
Hits only application code that compares FieldType objects with equals or keeps them in hash-based structures (a registry that de-duplicates field types, a cache keyed by them) and has vector field types that differ only in dimension, encoding or similarity: such types, and a vector type and a plain type, are silently treated as one; no production code in Lucene calls FieldType.equals or hashCode (IndexingChain compares field types by identity, and IndexWriter still rejects a document whose vector settings differ from the field's), so indexing and search are unaffected; default configuration, -ea and -da, any size, every release since 9.0.0 (vectorEncoding since 9.4.0) and main. Summary
You build two FieldTypes with setVectorAttributes, one 3-dimensional FLOAT32 with EUCLIDEAN similarity and one 768-dimensional BYTE with DOT_PRODUCT, and expect them to be different field types, since Lucene treats these settings as part of a field's schema (IndexWriter rejects a document whose vector dimension, encoding or similarity differs from the field's). Earlier properties missing from these methods were treated as bugs and added (the point dimensions in LUCENE-7073, the doc-values skip index in GITHUB#13449); the vector settings, added in 9.0.0 and 9.4.0, never were.
