addIndexes(CodecReader...) counts deleted documents against the doc limit since 9.9.0, rejecting inputs whose live documents fit

Since 9.9.0, by default addIndexes(CodecReader...) builds a temporary combined reader of its inputs for an optional reorder step, and that reader counts deleted documents against the 2,147,483,519 limit. Two indexes of 1,073,741,824 doc IDs with 1,024 live documents each fail in one call, though only 2,048 documents would be added.

The finding in 30 seconds

#

addIndexes admits its inputs by live documents, but since 9.9.0 it first builds a combined view of them for an optional reorder step, and that view counts deleted documents against the limit.

Background: live documents, doc IDs and the reorder step

#
  1. IndexWriter.addIndexes(CodecReader...) copies documents from readers you pass, such as the segments of other indexes, possibly filtered, into this index. Deleted documents are dropped; only live documents are copied.
  2. An index holds at most IndexWriter.MAX_DOCS = 2,147,483,519 documents. A reader's maxDoc() counts every doc ID, deleted ones included; numDocs() counts only the live ones.
  3. Since 9.9.0 a merge may renumber documents first through OneMerge#reorder, which BPReorderingMergePolicy uses. To offer that, Lucene glues the merge's inputs into one temporary combined reader. By default reorder() does nothing and returns null.

The finding, step by step

#
  1. Two indexes, A and B, have 1,073,741,824 doc IDs each but only 1,024 live documents each (the rest deleted). You pass all their segments to one addIndexes(CodecReader...) call on a writer with the default IndexWriterConfig.
  2. You expect 2,048 documents added: far below the limit of 2,147,483,519 (MAX_DOCS), and every document-limit check addIndexes makes counts live documents. 9.8.0 adds them.
  3. Instead it first glues the inputs into one temporary reader for OneMerge#reorder. That reader counts all 2,147,483,648 doc IDs, deleted ones included, and refuses: IllegalArgumentException: Too many documents: composite IndexReaders cannot exceed 2147483519 but readers have total maxDoc=2147483648. Nothing is added.
  4. The temporary reader was not needed: the default reorder() returns null. Two calls (A, then B) add the 2,048 documents.

Who is affected

#

Applications that add several very large inputs in one addIndexes(CodecReader...) call with the default config, when their doc IDs, deleted or filtered-out ones included, pass 2,147,483,519 while their live documents fit: for example consolidating heavily deleted views of two billion-document indexes. The call fails cleanly and writes nothing; splitting the inputs over several calls works around it. Rare.

Mechanism, terms and numbers798 words

IndexWriter.addIndexes(CodecReader...) copies only the live documents of its inputs and checks the doc limit (MAX_DOCS, 2,147,483,519) against live documents only. Since 9.9.0, when no index sort is configured, addIndexesReaderMerge first wraps all inputs of the merge in a SlowCompositeCodecReaderWrapper so that OneMerge#reorder can renumber documents. The wrapper builds a MultiReader, which counts every doc ID, deleted ones included, and throws IllegalArgumentException: Too many documents: composite IndexReaders cannot exceed ... when they add up to more than the limit. The default reorder() returns null, so the view is built and thrown away.

So a call whose inputs fit by live documents but not by maxDoc() fails cleanly and adds nothing: at full scale with no test hook, two indexes of 1,073,741,824 doc IDs with 1,024 live documents each fail in one call on main and 10.5.2, succeed in two calls, and succeed in one call on 9.8.0. It needs more than 2^31 doc IDs across the inputs of one call, so it is rare. Introduced by #12622 (9.9.0); every release from 9.9.0 to 10.6.0 and main is affected. Building the view only when the inputs' maxDoc() sum fits fixes it; that fix passes the reduced-scale repro, the closest core suites, TestBPReorderingMergePolicy and core lint (not run at full scale), but it silently skips a custom reorder() for such an oversized merge.

The bug, step by step (main 645d4fe14a20, under lucene/core/src/java/org/apache/lucene/index/)

#
  1. Admission counts live documents. addIndexes(CodecReader...) (IndexWriter.java:3275) sums leaf.numDocs() (:3294) and calls testReserveDocs(numDocs) (:3296). The default MergePolicy.findMerges(CodecReader...) puts all readers into one OneMerge (MergePolicy.java:627-631), whose totalMaxDoc is the sum of numDocs() (MergePolicy.java:245-254); after success addIndexes reserves that sum (IndexWriter.java:3344, :3356). addIndexesReaderMerge checks live documents once more (:3504, :3518).
  2. The eager view. With no index sort and no input that has blocks without a parent field (:3548-3556), addIndexesReaderMerge runs CodecReader mergedReader = SlowCompositeCodecReaderWrapper.wrap(readers); (:3561) and only then merge.reorder(mergedReader, directory, intraMergeExecutor) (:3562). If reorder returns null, the input readers are merged as they are (after OneMerge#wrapForMerge, :3542-3546, which by default returns each reader unchanged).
  3. The view counts deleted documents. wrap returns a single reader as is (SlowCompositeCodecReaderWrapper.java:54); for two or more it builds the wrapper, which adds up reader.maxDoc() into int doc starts (:73) and creates new MultiReader(...) over the inputs (:95). BaseCompositeReader sums maxDoc() as a long (BaseCompositeReader.java:86) and above IndexWriter.getActualMaxDocs() (:89) throws IllegalArgumentException("Too many documents: composite IndexReaders cannot exceed ...") for a reader that is not a DirectoryReader (:99-107).
  4. The view was not needed. The default OneMerge#reorder returns null (MergePolicy.java:325-328; javadoc "will be called when index sorting is disabled on a merged view of the OneMerge", :311-324). SegmentMerger (IndexWriter.java:3569) gets those input readers and drops deleted documents: without the view, 9.8.0 writes the merged segment at full scale, and the proposed fix passes the reduced-scale tests (it was not run at full scale).
  5. How it fails. The exception is thrown before SegmentMerger exists, so nothing is written; with the default ConcurrentMergeScheduler the merge fails on the merge thread, which also reports it as an uncaught MergeException, and addIndexes rethrows the merge's exception (:3382); with SerialMergeScheduler (the minimal test) it comes straight out of handleMergeException (:5056). Either way only an Error is treated as tragic (:3390). Each failed call leaves its merge in the writer's merge-exception list (:5040-5041, :5819-5824) until the next forceMerge clears it (:2250) or the writer is closed: a probe counted 20 retained entries after 20 failing calls.
  6. Who reaches it. One index's own maxDoc is capped at MAX_DOCS (a DirectoryReader above it is rejected as corrupt, BaseCompositeReader.java:90-98), and a single input never builds a MultiReader, so at real scale one merge needs two or more input readers whose maxDoc() sum exceeds the limit: for example the leaves of two indexes (the executed runs), or the leaves of one index passed twice, as TestIndexWriterMaxDocs.testAddTooManyIndexesCodecReader repeats one reader (read, not run). The ordinary merge path builds the same view (IndexWriter.java:5557), but there the writer has reserved every input document, so its maxDoc sum stays within the limit.

Exposure and likelihood242 words
  • Who is hit. Callers of addIndexes(CodecReader...) with the default configuration (no index sort) that pass two or more inputs (for example the segments of two indexes) holding more than 2,147,483,519 doc IDs in total, deleted or filtered-out ones included, while their live documents fit: for example heavily deleted, or FilterCodecReader-filtered, views of two indexes of about a billion documents each.
  • What goes wrong. The call is refused with a misleading message (the result would hold a fraction of the limit) and adds nothing. It fails cleanly: in a probe of 20 failing calls in a row (assertions on and off) no file was written, no document reservation leaked, the inputs were untouched, the writer stayed open and not tragic, and CheckIndex was clean afterwards. Each failed call does leave one entry in the writer's merge-exception list until the next forceMerge or close.
  • Workarounds. Split the inputs so that each merge's maxDoc() sum fits: one addIndexes call per input index (executed at full scale), or a findMerges(CodecReader...) override that splits them into groups (executed at small scale). An index sort on the destination is not a general workaround: it skips the view, but a sorted destination accepts only inputs that already have a congruent index sort and rejects unsorted ones with cannot change index sort (IndexWriter.java:3245-3251).
  • Likelihood: rare. Few deployments combine more than 2^31 doc IDs in one call, and the recorded searches found no public report since 9.9.0 (2023).

Minimal repro

#

One JUnit test in lucene/core: a source index with two segments, maxDoc 2 with one deleted document and maxDoc 1, so 2 live documents and a maxDoc sum of 3. The test framework's setIndexWriterMaxDocs(2) lowers the limit for the destination, as TestIndexWriterMaxDocs does. One addIndexes call with both segments should add 2 documents; it throws.

Why it looks unintended

#
  • Every document-limit check and reservation on this path counts live documents; the javadoc throws only "if addIndexes would cause the index to exceed MAX_DOCS".
  • The combined reader only feeds OneMerge#reorder, whose default returns null; the same inputs split over two calls succeed.
  • 9.8.0 accepted the call; the 9.9.0 change never discussed doc limits, and nothing announces the restriction.
The full argument260 words
  • Live documents everywhere. The up-front check (IndexWriter.java:3294-3296), OneMerge(CodecReader...)'s totalMaxDoc (MergePolicy.java:245-254), the merge's own check (:3504, :3518) and the final reservation (:3344, :3356) all count live documents. The javadoc's only doc-limit failure is "if addIndexes would cause the index to exceed MAX_DOCS" (:3272-3273), and MAX_DOCS is the limit on documents "added to the index" (:201-203). The view is the one place that counts deleted documents.
  • Unused by default. The default reorder() returns null and the view is discarded; the same inputs succeed in two calls or with one merge per reader. For inputs that are already index-sorted, the destination's index sort alone decides: two sorted inputs fail into an unsorted destination and succeed into one with the same sort, which skips the view (executed at small scale). Unsorted inputs cannot take that route, since a sorted destination rejects them.
  • A regression. 9.8.0 accepts the identical full-scale call. #12622, which added the view, never discusses doc limits, addIndexes or MAX_DOCS in its 45 comments and reviews; its author describes the view as "the reordering logic that works on a merged view of the input segments and doesn't care about deletes". No CHANGES.txt, MIGRATE.md, javadoc or test entry announces a limit on the inputs' maxDoc() sum.
  • Deleted and filtered inputs are normal here. TestAddIndexes.testFakeAllDeleted adds an all-deleted filtered reader; MultiPassIndexSplitter ("the input data comes from the input index with artificially applied deletes") and PKIndexSplitter pass filtered leaves. TestIndexWriterMaxDocs tests the addIndexes limit only with all-live inputs.
The devil's-advocate check212 words

The strongest case for "works as designed", rated moderate by the independent reproducer and cross-model reviews (root-cause and intended lenses); the refute lens rated it weak and the intended-behaviour devil's advocate found it does not survive: a composite reader has one int doc-ID space, OneMerge#reorder is documented to receive a merged view whenever index sorting is off, so a merge whose inputs cannot be addressed as one reader is arguably unrepresentable; findMerges(CodecReader...) (whose javadoc mentions one merge per reader) or separate calls are the documented knobs. It also needs more than about 2.1 billion input doc IDs and fails loudly before anything is written, with an easy workaround, so maintainers may see a surprising limitation rather than a contract violation.

Why it fails: with the default configuration nothing uses the view, every document-limit check counts live documents, for already index-sorted inputs the destination's index sort alone decides whether the limit applies, and the call worked in 9.8.0 with no announcement of the change. Where it does hold: a merge policy that really overrides reorder(), such as BPReorderingMergePolicy, needs the view, so a fix must decide what that policy gets for an oversized group. Maintainers may also prefer a javadoc change, since the @throws clause does not literally say "only if".

Trade-offs

  • For an oversized group a merge policy that overrides reorder() is not called, so that group is merged without reordering, silently (a probe counted reorderCalls=0). BPReorderingMergePolicy already treats reordering as best-effort: it skips it on NotEnoughRAMException and records reordered=false in the segment diagnostics when reorder() was not called. An infoStream message for the skipped case would make it visible (not run).
  • Cost: one pass over the inputs' maxDoc() per merge.

Build the view only when reorder() is meant to run

#

For example a OneMerge method that says whether it reorders, or a view built lazily; give a clear error only when a reordering policy meets an oversized group (the adjudication's preference).

Trade-offs

Keeps the default configuration free of the view and makes the oversized case explicit, but needs a small API change or an override check; not run.

Split the inputs in the default findMerges(CodecReader...)

#

Group the readers so that each OneMerge's maxDoc() sum fits.

Trade-offs

Reordering still runs per group, but one call then produces several segments, unlike the documented default of one, and custom findMerges overrides still hit the limit; not run.

Document the limit

#

State that, without an index sort, the inputs of one merge must fit MAX_DOCS by maxDoc(), deleted documents included.

Trade-offs

No code change, but keeps the 9.9.0 regression and makes the limit depend on index sorting; not run.

Downstream note

#

Solr's MERGEINDEXES core-admin action passes the segments of several source indexes to one addIndexes(CodecReader...) call, so merging very large, heavily deleted cores there can hit it (read, not tested). Solr's shard split adds one filtered segment per call, so it never builds the view and is not affected.

How it was found

#

Semi-formal. While modelling the doc-ID arithmetic of the merged view in Z3 with exact Java int semantics, the AI-assisted hunt asked whether inputs can fit the limit by live documents but not by maxDoc(): satisfiable for addIndexes, impossible on the ordinary merge path. A JUnit on the stock jar then hit the exception.

The method in full166 words

Method: semi-formal (an SMT query encoding a hypothesis formed while modelling, then executed tests).

  • In a hunt unit (CodecReader wrappers) the finder modelled SlowCompositeCodecReaderWrapper's doc-ID arithmetic in Z3 (quantifier-free bit-vectors, exact Java int semantics).
  • Query Q5a, with the ordinary merge path's precondition (the inputs' maxDoc() sum within MAX_DOCS, which the writer guarantees for its own segments), showed that the view's doc starts never wrap (unsat).
  • Query Q5b encoded addIndexes(CodecReader...)'s actual precondition (live documents within MAX_DOCS) and asked for a maxDoc() sum above it: sat, with a concrete witness. So the view's MultiReader check is reachable from a legal call.
  • The finder bridged that to the stock jar with a JUnit at reduced scale and a full-scale run with no test hook; independent checks reproduced it (see the checks below).
  • Recorded as semi-formal rather than formal: the query encodes a hypothesis and its sat answer is plain arithmetic; the exception path itself was found by reading the code and confirmed by execution.

LFV-285, snapshot of 2026-11-09

Registry title
addIndexes(CodecReader...) with the default config rejects inputs whose maxDoc() sum, deleted documents included, exceeds MAX_DOCS although only their live documents are added, because it always builds a merged view of the inputs for OneMerge#reorder (regression since 9.9.0)
Area
index / IndexWriter addIndexes(CodecReader...) (addIndexesReaderMerge merged view: SlowCompositeCodecReaderWrapper over a MultiReader, BaseCompositeReader doc limit)
Priority
Low, rank 1000: IndexWriter.addIndexes() rejects inputs whose doc IDs, deleted ones included, add up to more than 2^31; the failure is clean, the writer stays usable and splitting the call works around it.
Impact class
wrong error
Impact note
Hits an application that adds several very large inputs in one addIndexes(CodecReader...) call with the default IndexWriterConfig (no index sort) when the inputs' maxDoc() sum, deleted or filtered-out documents included, exceeds 2^31-129 while their live documents fit (for example consolidating heavily deleted or filtered views of two indexes of about a billion documents each): the call fails cleanly with IllegalArgumentException and adds nothing, the writer stays open and usable and nothing is written, the default ConcurrentMergeScheduler also reports the exception as an uncaught MergeException, and one call per input (or a findMerges(CodecReader...) override that splits the inputs) works around it.
Summary
You call IndexWriter.addIndexes(CodecReader...) with readers that have many deleted or filtered-out documents, so their live documents fit under IndexWriter.MAX_DOCS but their maxDoc() values (deleted documents included) add up to more. You expect the call to succeed, since addIndexes counts and reserves only live documents, its javadoc throws IllegalArgumentException only if the index would exceed MAX_DOCS, and 9.8.0 accepted the same call. Instead, with the default configuration it throws IllegalArgumentException 'Too many documents: composite IndexReaders cannot exceed ...' and adds nothing, because since 9.9.0 addIndexesReaderMerge always wraps the inputs in a SlowCompositeCodecReaderWrapper (a MultiReader over the uncompacted inputs) for OneMerge#reorder, whose default returns null and discards the view.
