FuzzyCompletionQuery with unicodeAware=true compares the query's code points with the suggestion's UTF-8 bytes, so its prefix boost stops at the first non-ASCII letter

With unicodeAware=true, FuzzyCompletionQuery counts shared prefix letters by comparing the query's code points with the suggestion's UTF-8 bytes, so the count stops at the first non-ASCII letter. The query aéc then ranks the typo axcd (4.0) above aécd (3.0); in ASCII, abc ranks abcd (6.0) first.

The bug in 30 seconds

#

A fuzzy completion's boost is the number of letters the suggestion's matched prefix shares with the query. In unicode-aware mode the query side holds code points and the suggestion side UTF-8 bytes, and the count compares them as if they were the same unit.

  1. You index two suggestions, aécd (weight 3) and the typo axcd (weight 4), and run FuzzyCompletionQuery for aéc with the default fuzzy settings and unicodeAware=true, the option that measures the query in letters (code points) instead of bytes.
  2. You expect what the same data gives in ASCII. The score is weight x boost (the weight alone when the boost is 0), and the boost counts the letters the suggestion's matched prefix shares with the query: for abc, abcd gets 3 x 2 = 6.0 and axcd 4 x 1 = 4.0.
  3. You get axcd 4.0 above aécd 3.0: the exact prefix gets boost 1, the same as the typo. With no ASCII letter at all every boost is 0: кот ranks the typo киты (4.0) above коты (3.0).
  4. Why: the query is kept as code points (é = E9) but the matched suggestion arrives as UTF-8 bytes (é = C3 A9). The count matches a, then compares E9 with C3 and stops.
  5. Which suggestions match stays right; their scores and order change, so a top-n cut can drop the exact prefix (with n = 1 the query returns only axcd). The default byte mode and ASCII-only text are not affected. Since 5.3.0 (2015).

Who is affected

#

Users of FuzzyCompletionQuery, plain or in ContextQuery, with unicodeAware=true (default false) on non-ASCII text. The boost is capped at the ASCII letters before the first non-ASCII query letter (0 if there is none); every lookup whose matched prefix reaches such a letter is affected. A heavier typo can then rank first, and a top-n limit can drop the exact prefix.

Mechanism, terms and numbers818 words

FuzzyCompletionQuery, the document suggester's fuzzy prefix query, boosts each suggestion by the number of leading letters its matched prefix shares with the typed text, so an exact prefix normally gets a larger boost than a typo (a typo in the last letter ties with it, the minimal-prefix NOTE). With unicodeAware=true, documented as measuring the query "in Unicode code points (actual letters) instead of bytes", that count compares two units: the query is kept as code points, the matched suggestion arrives as UTF-8 byte labels (FuzzyCompletionWeight.setNextMatch, FuzzyCompletionQuery.java:266-286). ASCII letters have the same value in both, so the count runs through ASCII letters and, when the comparison reaches the first non-ASCII query letter, stops there; an all-non-ASCII query gets boost 0, and a code point can accidentally equal an unrelated byte (U+00C3 and the first byte of é), which can even give a typo a larger boost than the exact prefix. With the default fuzzy settings, aéc over aécd/3 and the typo axcd/4 gives [axcd/4.0, aécd/3.0] instead of the ASCII twin's [abcd/6.0, axcd/4.0], and кот over коты/3 and киты/4 gives [киты/4.0, коты/3.0]. Which suggestions match is right; their scores and order change, and with them which matches make a top-n list, in the plain query and inside ContextQuery. It has been this way since the class was added (LUCENE-6459, first release 5.3.0). Decoding the matched path to code points before comparing (+15/-2, one file) fixes it, and the whole suggest module still passes.

Terms

#
  • Document suggester: suggestions indexed as SuggestField (or ContextSuggestField) values, each with an integer weight, searched with SuggestIndexSearcher. Internally an FST whose labels are UTF-8 bytes.
  • FuzzyCompletionQuery (@lucene.experimental): returns suggestions whose prefix is within maxEdits of the typed text (defaults: maxEdits 1, transpositions on, nonFuzzyPrefix 1, minFuzzyLength 3). Score = weight x boost; a boost of 0 gives the weight (CompletionScorer.java:98-106).
  • Boost: for each matched prefix path, the longest run of leading letters it shares with the query (FuzzyCompletionWeight.setNextMatch, FuzzyCompletionQuery.java:266-286). The path is the shortest prefix the fuzzy automaton accepts, so for the query abc the exact suggestion abcd is scored on ab (the NOTE at :268-271): that is why the expected boosts are 2 and 1, not 3 and 1.
  • unicodeAware (default false, :61): "Measure maxEdits, minFuzzyLength, transpositions and nonFuzzyPrefix parameters in Unicode code points (actual letters) instead of bytes" (:57-59).

The bug

#
  1. createWeight analyzes the query with stream.toAutomaton(unicodeAware) (:150-153); in unicode-aware mode its labels are code points. toLevenshteinAutomata keeps every string of it as a boost reference, refs.add(IntsRef.deepCopyOf(string)) (:166-170).
  2. Because the FST has byte labels, only the match automaton is converted to UTF-8 with UTF32ToUTF8 (:156-160); the refs are passed on unchanged (:163).
  3. NRTSuggester calls setNextMatch(path.input().get()) with the matched path in UTF-8 bytes (NRTSuggester.java:230-231); ContextQuery forwards the bytes after the context (ContextQuery.java:308-328). (A separate registered bug, LFV-254, can also change ContextQuery's context boost when a longer indexed context is matched through a prefix context or addAllContexts(); the ContextQuery cases cited here index every suggestion under one context, so there is no longer context for that bug to act on.)
  4. setNextMatch compares ref.ints[i] with pathPrefix.ints[i] position by position (:277) and keeps the longest run as the boost. No side is converted.

Worked example: query aéc over aécd (weight 3)

#
positionquery (code points)matched prefix aé (UTF-8 bytes)equal?
061 (a)61yes: count 1
1E9 (é)C3 (first byte of é)no: stop

Boost 1, score 3 x 1 = 3.0; counting letters gives 2 and 6.0. The typo axcd (matched prefix axc) gets boost 1 either way, 4.0. So the typo ranks first.

The result is neither a code-point count nor a byte count. Every ASCII letter (0-127) has the same value in both units; the first non-ASCII query letter is compared with a single byte of the suggestion and differs, except by accident when the code point has the same value as that byte: Ã is U+00C3 and é starts with the byte C3, so for the query aÃc the typo aécd is credited with 2 letters. After such an accident the next query code point meets a continuation byte (80-BF), so a code point U+0080-U+00BF can extend the run: for the query aÃ© (61 C3 A9) the typo aé©d (bytes 61 C3 A9 C2 A9) gets boost 3 and the exact aÃ©d (matched prefix aÃ = 61 C3 83) only 2, so with equal weights the typo ranks first, [aé©d/3.0, aÃ©d/2.0].

A matched path is scored right when it ends, or its comparison stops at an ASCII mismatch, before the first non-ASCII query letter: abé over abéd/3 and axéd/4 gives the correct [abéd/6.0, axéd/4.0] (the exact suggestion is scored on ab).

Exposure and likelihood429 words
  • Who. Applications that build FuzzyCompletionQuery with the 9-argument constructor and unicodeAware=true (the class is @lucene.experimental; the flag defaults to false), directly or wrapped in ContextQuery, over SuggestField or ContextSuggestField values.
  • When. A matched path is scored wrong when its comparison with the query reaches a non-ASCII query letter: the boost is then capped at the ASCII letters before it, and is 0 when there is none (unless a code point accidentally equals a byte). A path that ends, or stops at an ASCII mismatch, before that letter is scored right (abé over abéd/3 and axéd/4: [abéd/6.0, axéd/4.0]). With the default settings the exact prefix of a query of 3 or more letters is scored on all letters but the last, so its boost is wrong whenever a non-ASCII letter comes before the last letter. In the examples, without the bug the exact prefix wins whenever its weight x 2 beats the typo's weight; with it the weights alone decide: the order changes when the typo is heavier, and with equal weights they tie.
  • How bad. The accidental byte equality can give a typo the exact prefix's boost (aÃc: [aécd/8.0, aÃcd/6.0]) or a larger one: aÃ© over aÃ©d/1 and aé©d/1 ranks the typo first with equal weights, [aé©d/3.0, aÃ©d/2.0].
  • What stays right. Which suggestions match the query: the match automaton does not use the boost. Scores and order change, and so, under a top-n limit, does which matches are returned (aéc over aécd/3 and axcd/4 with n = 1: [axcd/4.0]; with the fix [aécd/6.0]). Nothing throws or logs. Default byte mode and ASCII-only text are unaffected. In the hunt's bounded-exhaustive comparison (ranked top-n lists for n = 1, 3 and 200) every mismatch of this bug's class was explained by the boost units alone.
  • Scale and settings. Deterministic (20 iterations, always the same two failures). Executed on two-suggestion indexes and on the hunt's bounded indexes (39 suggestions; one, two or three segments, or index-sorted); nothing in the mechanism depends on index size (read). The repros use the default base codec with the completion postings format on the suggest field, as the upstream tests do; assertions on or off.
  • Downstream (read, not tested). Elasticsearch's completion suggester exposes unicode_aware as a fuzzy option (elastic/elasticsearch#10746, #107707), and OpenSearch's feeds its fuzzy options into FuzzyCompletionQuery (opensearch-project/OpenSearch#22924).
  • How likely. Rated plausible: deterministic for every affected lookup, but only a ranking change, easy to mistake for the known minimal-prefix limitation, and no prior report was found (searches of 2026-10-27).

Why it is a bug, not intended

#
  • The javadoc: unicodeAware measures the query "in Unicode code points (actual letters) instead of bytes".
  • The change that added the class defines "boost = # of prefix characters matched"; the upstream test pins that count.
  • The same data ranks correctly in ASCII and in byte mode; renaming one letter to another single code point changes the score.
The full argument270 words
  • Contract. Class javadoc (FuzzyCompletionQuery.java:43-44): "This query boost documents relative to how similar the indexed terms are to the provided prefix." DEFAULT_UNICODE_AWARE (:57-59): "Measure maxEdits, minFuzzyLength, transpositions and nonFuzzyPrefix parameters in Unicode code points (actual letters) instead of bytes." Constructor (:123): "@param unicodeAware treat prefix as unicode rather than bytes". isUnicodeAware (:227): "lengths are measured in unicode code-points rather than bytes".
  • Intent on record. LUCENE-6459 (#7518), which added the class: "Documents are 'boosted' by the number of matching prefix letters of the suggestion with respect to the original term text" and "boost = # of prefix characters matched". Its patch author, in the comments: FuzzyCompletionWeight "would count the number of prefix characters a matched input has w.r.t. the analyzed query prefix and set the boost for it to the number of common prefix length". A Lucene committer in elastic/elasticsearch#24903 (2019): "a boost per path that is equal to the length of the shared prefix". None of them mentions unicode, code points or bytes.
  • Tests. TestFuzzyCompletionQuery.testFuzzyQuery pins the boost as the shared-prefix count (suaggestion 4 x 2, suggestion 2 x 3, sugfoo 1 x 3, ssuggestion 1 x 1). No upstream test builds FuzzyCompletionQuery with unicodeAware=true.
  • History. The comparison loop is unchanged since the class was added (git blame -w -M -C); no commit, CHANGES or MIGRATE entry or discussion calls the mixed units a choice.
  • Controls. On the same Cyrillic data the default byte mode ranks the exact prefix first ([коты/15.0, киты/12.0]), and the Latin twin does too; only the documented unicode option breaks it.
The devil's-advocate check195 words

The strongest case for "works as designed": the class is @lucene.experimental; no document gives the boost as a number or names its unit; the unicodeAware javadoc lists only the edit parameters; CompletionWeight.setNextMatch documents pathPrefix only as "the prefix of a matched path"; and fuzzy completion scoring already has an accepted weak spot, the minimal-prefix NOTE in setNextMatch, which a committer defended in elastic/elasticsearch#24903 ("I agree that it can be misleading but this limitation is needed"), with the same symptom: exact matches tie with typos.

Why it fails: #24903 is ASCII and comes from which path is scored; it cannot cut the count at the first non-ASCII letter, give 0 to an all-Cyrillic query, or match a code point with an unrelated byte. The Latin control and byte mode on the same Cyrillic data pass, and fixing either problem leaves the other. Cross-model reviews (OpenAI GPT-5.6) rated the intended-behaviour argument moderate and still concluded real; the devil's advocate and the adjudication found no argument that survives. Verdict: a defect. When filing, lead with "query code points are compared with UTF-8 byte labels", and cite the NOTE and #24903 with the reason this is different.

Suggested fix

#

Recommended Decode the matched path to code points when unicodeAware (reused buffers)

Pass unicodeAware to FuzzyCompletionWeight and, in setNextMatch, decode the matched UTF-8 path to code points with two reused buffers before comparing (+15/-2, one file). The repro passes, and so do the whole suggest module (242 tests, 0 failures) and the format and lint checks. Add a CHANGES entry: scores change for unicode-aware users.

@Override
protected void setNextMatch(IntsRef pathPrefix) {
  if (unicodeAware) {
    // refs hold code points, but the matched path holds UTF-8 byte labels: compare letters
    codePointScratch.copyUTF8Bytes(Util.toBytesRef(pathPrefix, utf8Scratch));
    pathPrefix = codePointScratch.get();
  }
  // ... the existing comparison loop, unchanged
}

Decode the matched path to code points when unicodeAware (reused buffers) (validated by the checks) (recommended)

#

Give FuzzyCompletionWeight the unicodeAware flag (from createWeight) and, at the top of setNextMatch, turn the UTF-8 byte labels into code points with Util.toBytesRef and IntsRefBuilder.copyUTF8Bytes into two reused buffers; the comparison loop stays as it is. Units then match the javadoc's "code points (actual letters)". Byte mode is untouched. The accepted path is valid UTF-8 by construction, because the match automaton is the UTF32ToUTF8 conversion, so decoding is well defined.

@Override
protected void setNextMatch(IntsRef pathPrefix) {
  if (unicodeAware) {
    // refs hold code points, but the matched path holds UTF-8 byte labels: compare letters
    codePointScratch.copyUTF8Bytes(Util.toBytesRef(pathPrefix, utf8Scratch));
    pathPrefix = codePointScratch.get();
  }
  // ... the existing comparison loop, unchanged
}

Trade-offs

  • One decode per matched prefix path. The byte and int buffers are reused once grown, but IntsRefBuilder.copyUTF8Bytes calls UnicodeUtil.UTF8toUTF32, which creates one small UTF8CodePoint object per non-empty decode (the JIT may remove it); performance was not measured.
  • The weight already keeps per-match state (currentBoost), so the buffers add no new thread-safety concern.
  • Behaviour change: scores rise for unicode-aware users with non-ASCII text; say so in a CHANGES entry (Bug Fixes) and add the repro as a test (no upstream test covers unicodeAware=true today).

Encode the refs to UTF-8 once and count whole code points (not run)

#

In createWeight, keep the refs as UTF-8 bytes; in setNextMatch compare bytes but add 1 to the count only when a whole code point has matched.

Trade-offs

Compare and count bytes (not recommended)

#

Encode the refs to UTF-8 and count matching bytes.

Trade-offs

Consistent, but the boost becomes a byte count: a shared first byte earns partial credit and a non-Latin letter counts 2-4 times. By hand, коты and киты would tie at 12. Not run.

Workaround today (no Lucene change)

#

Leave unicodeAware at its default (false). Byte mode ranks the exact prefix first on the Cyrillic example ([коты/15.0, киты/12.0]).

Trade-offs

Then maxEdits, nonFuzzyPrefix and minFuzzyLength count UTF-8 bytes, so a typo on a multi-byte letter can cost more than one edit (read, not tested): the problem unicodeAware exists to solve.

Downstream note

#

Not a Lucene security issue (it only changes the scores and order of the suggestions the query matches, and so the top-n cut among them); Elasticsearch's completion suggester exposes this flag as its fuzzy unicode_aware option, so its users with non-ASCII suggestions would see the same ranking (read from its issue tracker, not tested).

Bug record

LFV-689, snapshot of 2026-10-29

Registry title
FuzzyCompletionQuery with unicodeAware=true compares the query's code points with the UTF-8 bytes of the matched suggestion, so its prefix-similarity boost stops at the first non-ASCII letter and exact prefixes lose their boost advantage over typos
Area
suggest / document (NRT) suggester (FuzzyCompletionQuery: FuzzyCompletionWeight.setNextMatch prefix-similarity boost in unicodeAware mode, also inside ContextQuery)
Priority
Medium, rank 312: Like LFV-479 it gets ranking wrong while the result set.
Impact class
silent wrong results
Impact note
Hits applications that use the document suggester's FuzzyCompletionQuery (directly or wrapped in a ContextQuery) with the opt-in unicodeAware=true on suggestions with non-ASCII letters, in every release from 5.3.0 to 10.5.2 and on main, with the default codec and with -ea or -da: on every such lookup the prefix-similarity boost counts only the ASCII letters before the first non-ASCII one (0 for an all-non-ASCII query) and can count an unrelated code point and UTF-8 byte of the same value as equal, so an exact prefix gets the same boost as a typo and ties with it or ranks below a heavier typo, depending on the index weights; the set of suggestions is right, nothing throws, any scale; the default byte mode and ASCII-only text are unaffected.
Summary
You build a FuzzyCompletionQuery with unicodeAware=true, the documented option that measures the query 'in Unicode code points (actual letters) instead of bytes', and expect a suggestion that shares more leading letters with the typed prefix to get a larger boost, exactly as for ASCII text. Instead FuzzyCompletionWeight.setNextMatch compares the query's code points with the UTF-8 byte labels of the matched suggestion, so the count stops at the first non-ASCII letter: for the query 'aéc' over aécd (weight 3) and the typo axcd (weight 4) both get boost 1 and the exact prefix ranks second, [axcd/4.0, aécd/3.0], while the same data in ASCII ('abc' over abcd and axcd) gives [abcd/6.0, axcd/4.0]; for an all-CJK or all-Cyrillic query every suggestion gets boost 0, so the exact prefix only ties with typos and the weight alone decides. Only scores and ranking are wrong (the suggestions found are right), for the plain query and inside a ContextQuery.
