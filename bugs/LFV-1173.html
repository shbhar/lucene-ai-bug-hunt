A throwing reader-closed listener leaves IndexWriter holding a closed segment reader, so every later NRT open fails

If a reader-closed listener on an NRT segment reader throws while IndexWriter swaps in a fresh copy of that reader, the writer throws the fresh copy away and keeps the closed one. Every later DirectoryReader.open(writer) then fails with AlreadyClosedException, and close() and rollback() throw too.

The finding in 30 seconds

#

Background: the writer's pooled readers

#
  1. IndexWriter keeps one SegmentReader per segment, its pooled reader. An NRT reader opened from the writer uses that same object as its leaf while the segment has no deletes.
  2. Readers are reference-counted. When decRef() drops the count to 0, the reader is closed and then its closed listeners run. If a listener throws, the reader stays closed (by design since LUCENE-5553).
  3. After a delete, when something asks for the segment's latest reader (in the repro, the merge policy), the writer builds a fresh pooled reader that shares the segment's files (the core) and releases the old one.

The finding, step by step

#
  1. Index 2 documents (one segment) and open an NRT reader. With no deletes, its only leaf is the writer's own pooled reader of the segment (refCount 2: the pool and the NRT reader). Add a closed listener that throws to that leaf, then close the NRT reader (refCount 1).
  2. Delete id:a and open an NRT reader again. The merge policy asks for the segment's latest reader, so the writer builds a fresh one and releases the old one: refCount 0, the old reader closes, its listener throws. This open fails with the listener's IOException, as expected.
  3. You expect the next DirectoryReader.open(writer) to work and show numDocs 1: the writer is still open, and the fresh reader was already built.
  4. Instead it throws AlreadyClosedException: SegmentCoreReaders is already closed. The release sat inside the try whose error handler drops only the fresh reader, so the pool still holds the closed one. close() and rollback() throw this IndexReader is closed, and the next delete plus flush closes the writer as tragic.

Who is affected

#

Applications that hang reader-closed listeners on NRT segment readers (for example per-reader caches) and whose merge policy reads segments: a custom policy using the reader supplier in numDeletesToMerge, or soft deletes with SoftDeletesRetentionMergePolicy once a segment is fully deleted. Default hard-delete setups skip this path (a doc-values update reaches the same swap; not claimed). No scale needed; 7.4.0 to 10.6.0.

Mechanism, terms and numbers496 words

IndexWriter keeps one pooled SegmentReader per segment. When its live docs are stale, ReadersAndUpdates builds a fresh reader and releases the old one. The release (reader.decRef()) sits inside the try whose failure handler releases only the new reader, and the pooled field is assigned only on a normal return. IndexReader.decRef() closes a reader before it runs its closed listeners, so when a listener throws, the old reader is already closed, the new one is thrown away, and the pool keeps the closed one.

From then on every DirectoryReader.open(writer) throws AlreadyClosedException (with the repro's merge policy SegmentCoreReaders is already closed; through SoftDeletesRetentionMergePolicy this IndexReader is closed), close() and rollback() throw AlreadyClosedException: this IndexReader is closed, and the next delete plus flush closes the writer as tragic, dropping uncommitted changes. The last commit stays intact. It needs a listener that throws and a merge policy that reads the segment (a custom one using the reader supplier, or soft deletes with SoftDeletesRetentionMergePolicy); every release from 7.4.0 to 10.6.0 and main is affected.

Where it goes wrong (main 5adff78bb168)

#
  1. The merge policy's reader supplier reaches ReadersAndUpdates.getLatestReader (numDeletesToMerge :249-251, isFullyDeleted :1117-1119, keepFullyDeletedSegment :1121-1123). When the pooled reader's live docs are stale (needsRefresh, :258), it calls swapNewReaderWithLatestLiveDocs() (:261).
  2. createNewReaderWithLatestLiveDocs (:1067-1086) builds the new reader, then runs try { pendingDeletes.onNewReader(newReader, info); reader.decRef(); } catch (Throwable t) { newReader.decRef(); throw t; }. The old reader's release is the decRef at :1080.
  3. IndexReader.decRef (:215-232) sets closed = true and runs doClose() and then the closed listeners (:223-227). A listener that throws leaves the old reader closed.
  4. The catch releases the new reader, and swapNewReaderWithLatestLiveDocs (:1088-1090, reader = createNewReaderWithLatestLiveDocs(reader);) never assigns: the pool keeps the closed old reader. getReader treats the IOException as non-tragic and closes its half-built NRT reader (IndexWriter.java:711-720), which releases the shared core's last reference.
  5. In the repro, every later NRT open builds its leaf on the pooled reader's core (getReadOnlyClone, :239-240) and fails at SegmentCoreReaders.incRef. Through SoftDeletesRetentionMergePolicy the open fails earlier, when getLatestReader checks the closed reader (:258, this IndexReader is closed; an executed probe). close() and rollback() reach dropReaders (:213-225), whose decRef of the closed reader throws this IndexReader is closed.

The catch is right for a failure in onNewReader (keep the old reader) and wrong for a failure in the old reader's own release, which has already closed it. The same file's dropReaders handles that case: try { reader.decRef(); } finally { reader = null; } (:216-221).

In the repro the refresh runs inside DirectoryReader.open(writer): IndexWriter.getReader -> preparePointInTimeMerge -> TieredMergePolicy.findMerges -> the test's numDeletesToMerge, which calls readerSupplier.get(). At the listener call the old reader's refCount is 0 and the core's is 2 (the new reader and the NRT clone); after the failed open both are 0.

Exposure and likelihood306 words
  • The trigger. A reader-level closed listener (getReaderCacheHelper().addClosedListener, an @lucene.experimental API) on an NRT leaf that is the writer's pooled reader (a segment with no deletes when the NRT reader opened), which throws when the writer releases that reader during a refresh. An unchecked exception has the same effect. A core-level listener does not trigger it: the fresh reader shares the core, so the core outlives the old reader [read].
  • The refresh path. getLatestReader, reached from the merge policy's reader supplier: a merge policy that calls readerSupplier.get() in numDeletesToMerge (the repro; MergePolicy.java:760-778 documents the supplier), or the in-tree SoftDeletesRetentionMergePolicy through keepFullyDeletedSegment (SoftDeletesRetentionMergePolicy.java:80-82) on a plain DirectoryReader.open(writer) once a segment is fully deleted (an executed probe on main and 10.6.0); these are the two executed routes. With hard deletes and the default policies the path is not taken: MergePolicy.numDeletesToMerge returns delCount (:774-778), keepFullyDeletedSegment returns false (:754-757), and PendingDeletes.isFullyDeleted ignores the supplier (:219-221). The default configuration does reach the same release order through a doc-values update (the writeFieldUpdates call, an executed probe); that call is not claimed (below).
  • What follows (executed probes): the writer is open and not tragic, but every NRT open fails; with the repro's merge policy commit() fails too; the next delete plus flush closes the writer as tragic, dropping uncommitted changes; rollback() throws but still closes the writer and releases the lock; the last commit reopens with its documents.
  • Scale and likelihood. 2 documents and one delete; no load or concurrency. Rare in practice: no report since 7.4.0 (2018).
  • Not claimed: the listener's own exception surfacing once (expected), and the writeFieldUpdates call of the same swap (ReadersAndUpdates.java:1027-1030, after a doc-values update), which fails the same way but is entangled with a separate defect there (LFV-110). The suggested fix changes that call too.

Why it looks unintended

#
  • ClosedListener.onClose may throw IOException, and since LUCENE-5553 a throwing listener still leaves the reader closed (TestIndexReaderClose asserts it).
  • The same file's dropReaders clears the pooled field when the release throws; the swap keeps it.
  • One listener IOException later becomes a tragic close: the next delete hits the closed pooled reader, where failures are tragic by design.
The full argument182 words
  • IndexReader.ClosedListener.onClose(CacheKey) throws IOException (IndexReader.java:140-146): a throwing listener is an anticipated outcome.
  • LUCENE-5553 (#6615, 2014) made decRef close the reader and call every listener even when one throws (lucene/CHANGES.txt). TestIndexReaderClose registers a FaultyListener, expects close() to throw and then expects AlreadyClosedException from the reader (:76-97). So after a thrown final release the reader is closed, and a caller has to treat it that way.
  • ReadersAndUpdates.dropReaders does (:216-221): try { reader.decRef(); } finally { reader = null; }.
  • The later tragic close comes from the poisoned pool, not from the listener: the next delete is applied to the writer's own closed pooled reader (ReadersAndUpdates.getReader, its incRef at :196), and IndexWriter treats any failure while applying a delete packet as tragic by design (IndexWriter.java:2934-2943). So one listener IOException becomes a tragic close later, which drops uncommitted changes (an executed probe).
  • The code dates from LUCENE-8246 (#9293); its discussion is about merge-policy delete accounting and does not mention a failing release of the old reader. No test asserts the current behaviour.
The devil's-advocate check202 words

Strongest argument for "intended": on #9738 (LUCENE-8692, open) a maintainer wrote that exceptions from getReader() and other writer methods are not treated as tragic "since a user could always call rollback()", and that continuing after a failed reopen can leave inconsistency.

Why it fails here: it is a comment on a different question (which writer exceptions should be tragic), not documentation; the writer had already built a good reader and threw it away; and the stated remedy, rollback(), itself throws AlreadyClosedException in this state (it still closes the writer). The other argument, that the listener API is @lucene.experimental, marks API instability, not undefined behaviour.

Second argument: the decRef javadoc says "If an exception is hit, the refCount is unchanged" (IndexReader.java:209), and the swap's catch, which keeps the old reader, follows that sentence.

Why it fails here: the sentence is stale. The code decrements the count and sets closed = true before doClose() and the listeners run (:222-227), LUCENE-5553 made that deliberate, and TestIndexReaderClose (:76-97) requires the reader to be closed afterwards. The stale sentence is tracked separately as a documentation defect with a javadoc-only fix (LFV-497). Fixing the javadoc would not unpoison the pool.

Suggested fix

#

Recommended Pool the new reader first, then release the old one (validated)

Pool the new reader first, then release the old one (+8/-3 lines in ReadersAndUpdates), the guarantee dropReaders already gives (the pooled field never keeps a released reader). The listener's exception still surfaces once, but the writer keeps working. Validated: the repro passes, and so do the 1,398 org.apache.lucene.index tests and :lucene:core:check.

private void swapNewReaderWithLatestLiveDocs() throws IOException {
  SegmentReader oldReader = reader;
  reader = createNewReaderWithLatestLiveDocs(oldReader);
  // release the old reader only once the new one is pooled: decRef() closes the old reader even
  // if it throws (e.g. from a closed listener), so the pool must not keep it
  oldReader.decRef();
}

Pool the new reader first, then release the old one (validated) (recommended)

#

createNewReaderWithLatestLiveDocs drops its reader.decRef(). swapNewReaderWithLatestLiveDocs assigns the new reader to the pooled field and then releases the old one; getReaderForMerge releases its own reference after the call. +8/-3 lines in ReadersAndUpdates.java.

private void swapNewReaderWithLatestLiveDocs() throws IOException {
  SegmentReader oldReader = reader;
  reader = createNewReaderWithLatestLiveDocs(oldReader);
  // release the old reader only once the new one is pooled: decRef() closes the old reader even
  // if it throws (e.g. from a closed listener), so the pool must not keep it
  oldReader.decRef();
}

Trade-offs

  • The listener's exception still surfaces once, as LUCENE-5553 intends; only the pool's state changes.
  • The same order now also applies to the writeFieldUpdates call of the swap (:1029).
  • In getReaderForMerge the released reference is the caller's own, which cannot drop the pooled reader's refCount to 0 while the pool holds its reference, so no listener runs there [read]. LFV-446 (a leak in getReaderForMerge) touches the same lines; coordinate the two fixes.

The same order in the dropReaders style

#

Inside the swap: build the new reader without releasing, then try { oldReader.decRef(); } finally { reader = newReader; }.

Trade-offs

Same behaviour as the recommended option; a style choice. Not run separately.

Treat a failed release as tragic

#

Close the writer at once when the old reader's release throws.

Trade-offs

Loud and simple, but turns an application callback failure into lost uncommitted changes at once, while the writer already holds a good new reader. Not recommended.

Documentation only

#

Document that closed listeners must not throw.

Trade-offs

In tension with onClose(...) throws IOException and LUCENE-5553, and it leaves the pool poisoned and rollback() throwing when a listener throws anyway. Not recommended.

Downstream note

#

Services that keep per-reader caches with closed listeners on NRT readers should make those listeners non-throwing until this is fixed: one failure leaves the writer unable to open NRT readers until it is replaced.

How it was found

#

Code reading of ReadersAndUpdates: the release of the old pooled reader sits inside the error scope of the swap, which only expects the new reader's setup to fail. A single-threaded JUnit test on main then showed the closed reader kept in the pool.

The method in full67 words

Method: non-formal code reading, witnessed by an executable test. Reading the pooled-reader refresh showed that reader.decRef() of the old reader is inside the try whose catch only undoes the new reader, while IndexReader.decRef closes the reader before its listeners can throw. A JUnit test with a throwing reader-closed listener and a merge policy that reads the segment then failed on main 5adff78bb168 with assertions on and off.

Low, rank 603: When an application's reader-closed listener throws as IndexWriter swaps out its pooled reader of a segment, the writer keeps the closed reader, so every later NRT open fails and the next delete plus flush closes the writer and drops uncommitted changes, in every release since 7.4.0. It needs a throwing listener plus an opt-in or custom merge policy that triggers the swap, every failure is loud and the last commit stays intact, so it is Low.
Impact class
minor
Impact note
Applications that register a reader-closed listener (IndexReader.CacheHelper.addClosedListener, @lucene.experimental) on a leaf of a writer-opened NRT reader whose segment had no deletes (so the leaf is the writer's pooled reader), and whose listener throws when the writer later refreshes that pooled reader through getLatestReader (in-tree through SoftDeletesRetentionMergePolicy.keepFullyDeletedSegment on a plain DirectoryReader.open(writer), or through any merge policy that uses the documented readerSupplier in numDeletesToMerge), see the listener's exception once, as expected, and are then left with a writer that is open and not tragic but holds a closed reader: every later DirectoryReader.open(writer) throws AlreadyClosedException, the next delete plus flush makes the writer close itself as tragic (its uncommitted changes are lost), and rollback() throws AlreadyClosedException although it still closes the writer and releases the lock; the last commit stays intact, every failure is loud, it needs an application callback that throws plus an opt-in or custom merge policy, no scale is needed, and every release since 7.4.0 is affected.
Summary
You register a reader-closed listener on a segment of an NRT reader opened from an IndexWriter, close that reader, and later the writer refreshes its own pooled reader of that segment (for example after a delete, when the merge policy asks for the segment's latest reader); the listener throws while the writer releases the old reader. You expect that exception once and a writer that keeps working, because the old reader is closed either way and the new reader is already built. Instead the writer throws the new reader away and keeps the now closed old one in its pool, so every later DirectoryReader.open(writer) throws AlreadyClosedException ('SegmentCoreReaders is already closed') and the next delete plus flush closes the writer as tragic.
