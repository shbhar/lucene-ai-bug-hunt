addIndexes of a SortingCodecReader fails when the writer reorders merges with BpVectorReorderer

addIndexes of a SortingCodecReader, such as the reader BPIndexReorderer.reorder returns, into a writer whose merge policy reorders with BpVectorReorderer throws UnsupportedOperationException and adds nothing once the input has 64 vectors. Main and branch_11x only, unreleased; the writer and the index stay healthy.

The finding in 30 seconds

#

Background in three lines

#
  1. SortingCodecReader.wrap(reader, docMap, null) presents a segment's documents in a new order; addIndexes then writes them in that order. The reader is meant only for merging.
  2. BPReorderingMergePolicy reorders the segments its merges write, addIndexes included, with a pluggable reorderer: the postings BPIndexReorderer or the vector BpVectorReorderer.
  3. A field's vector values number their vectors with ordinals; copy() returns an independent view of them, which BpVectorReorderer needs once per thread.

The finding, step by step

#
  1. Index 64 documents with a 2-dimensional vector field v, then wrap the segment with SortingCodecReader.wrap(leaf, docMap, null), using a doc map that reverses it (doc 0 becomes doc 63). BPIndexReorderer.reorder returns a reader of this kind and says to pass it to addIndexes.
  2. Call addIndexes on a writer with new BPReorderingMergePolicy(new TieredMergePolicy(), new BpVectorReorderer("v")) and no index sort. You expect the 64 documents to be added and reordered by their vectors, as happens for a plain segment reader, and for this reader with the postings BPIndexReorderer.
  3. Instead addIndexes throws UnsupportedOperationException and adds 0 documents. The policy reorders addIndexes like a forced merge; from 64 vectors on (twice the default minimum partition size of 32) BpVectorReorderer asks the vectors for a copy(), and SortingCodecReader's vector views throw from copy().
  4. The writer stays open and the index is unchanged. A copy()-only fix is a trap: the reorderer then reads the view's vector ordinals as doc order and moves the wrong documents (0 of 512 positions right in a probe).

Who is affected

#

Only code on main or branch_11x (unreleased 11.0.0) that uses the opt-in BPReorderingMergePolicy with BpVectorReorderer on a writer without an index sort, and passes a SortingCodecReader with 64 or more vectors to addIndexes. Then every such call fails. A destination with an index sort is not affected.

Mechanism, terms and numbers567 words

IndexWriter#addIndexes(CodecReader...) of a SortingCodecReader into a writer whose merge policy is BPReorderingMergePolicy with a BpVectorReorderer, and that has no index sort, throws UnsupportedOperationException and adds nothing. The policy reorders addIndexes as a forced merge; BpVectorReorderer copies the input's float vector values for its per-thread state on the first split (from 64 FLOAT32 vectors with default settings); SortingCodecReader's vector views throw from copy(). The reader from the documented BPIndexReorderer.reorder -> addIndexes recipe hits it when added to such a writer, while the postings BPIndexReorderer accepts the same input under the same policy. The failure is clean (writer open, not tragic, index unchanged). Making copy() work is not enough: BpVectorReorderer.valueMapToDocMap then reads the view's ordinals as doc order, so the reorder is applied to the wrong documents. Main and branch_11x only, since #14097 (2025-01-07); no release is affected.

The bug, step by step (Lucene main 645d4fe14a20)

#
  1. BPReorderingMergePolicy.findMerges(CodecReader...): "addIndexes is considered a forced merge" (BPReorderingMergePolicy.java:199-203), with no minimum size (:103-105).
  2. IndexWriter.addIndexesReaderMerge skips reordering only if the destination has an index sort (or blocks without a parent field), and otherwise calls merge.reorder(SlowCompositeCodecReaderWrapper.wrap(readers), ...) (IndexWriter.java:3548-3562). With one input, wrap returns the input itself (SlowCompositeCodecReaderWrapper.java:49-58).
  3. BpVectorReorderer.computeDocMap takes reader.getFloatVectorValues(field) (BpVectorReorderer.java:590) and bisects the ordinal range. A range is split only if each half holds at least minPartitionSize vectors (:208-211, default 32), so with the default from 64 vectors on (a missing or non-FLOAT32 field returns null first, :586-589, :699-724). The first split creates the thread's state (:217, :619-624), and its constructor calls vectors.copy() (:108-111).
  4. SortingCodecReader's SortingFloatVectorValues.copy() is throw new UnsupportedOperationException() (SortingCodecReader.java:346-347; byte :393-394 and float16 :436-437 likewise, latent because BpVectorReorderer handles FLOAT32 only). With several inputs the merged view's copy() copies each input (SlowCompositeCodecReaderWrapper.java:306-307, :903-909) and reaches the same throw.
  5. The policy catches only NotEnoughRAMException (BPReorderingMergePolicy.java:136-141); addIndexes rethrows the merge's exception (IndexWriter.java:3380-3382), and only an Error would be tragic (:3390-3392). The reorder (:3562) runs before the SegmentMerger is created (:3568), so nothing is written.

The hidden second half

#

BpVectorReorderer.valueMapToDocMap (BpVectorReorderer.java:735-789) returns the ordinal permutation itself as the doc map when every document has a vector (:737-739), and otherwise numbers ordinals by position in doc order (:744-764). A SortingCodecReader view keeps the wrapped reader's ordinals: its iterator's index() "may skip around, not increasing monotonically as iteration proceeds" (SortingCodecReader.java:264-266), and vectorValue(ord) reads in the delegate's ordinal space (:323-327). So once copy() works, the permutation computed over the vectors is applied to other documents.

The numbers

#
  • 64 documents, 2-dimensional vectors {i, 1}, one reversing SortingCodecReader: addIndexes throws, 0 documents added, with assertions on and off, 20 of 20 random seeds. With 63 documents nothing is split and nothing throws.
  • The same failure for the reader BPIndexReorderer.reorder(leaf, dir, null) returns, for SortingCodecReader.wrap(leaf, Sort) into a writer without an index sort, with the default ConcurrentMergeScheduler, and for two 32-document sorting readers in one call.
  • With only copy() fixed, a 512-vector index wrapped by a reversing view gets a doc map equal to the plain reader's at 512 of 512 positions and to the correctly re-based map at 0 of 512; cluster changes in doc order after BP: 383 (plain reader with BP: 35; no BP: 404).
Exposure and likelihood245 words
  • Who is exposed. Applications that combine BPReorderingMergePolicy(..., new BpVectorReorderer(field)) (lucene/misc, opt-in), a destination without an index sort (and not the document-blocks case IndexWriter also skips, IndexWriter.java:3550-3556), and addIndexes with a SortingCodecReader input: SortingCodecReader.wrap(reader, Sort), wrap(reader, docMap, null), or the output of BPIndexReorderer.reorder (its documented recipe). For example, an offline postings-BP pass whose output is added to a writer that also reorders by vectors, or a re-sort or rewrite job feeding such a writer.
  • What it takes. At least 64 FLOAT32 vectors in the reordered field across the call's inputs (two times the default minPartitionSize of 32). Default settings, ordinary data, SerialMergeScheduler or ConcurrentMergeScheduler. No scale is needed. With several inputs, one without vectors for the field may hit a NullPointerException in the merged view's copy() instead (LFV-269).
  • Not affected. A destination with an index sort (IndexWriter then skips the reorder); plain segment readers; the postings BPIndexReorderer; every release (the class is on main and branch_11x only).
  • What the user sees. A clean, unchecked UnsupportedOperationException (no message) from addIndexes, within milliseconds. Nothing is added, nothing is lost; the writer stays open and is not tragic.
  • Workarounds. Give the destination an index sort, write the sorted index first and add plain segment readers, or do not use the vector reorderer on that writer.
  • How likely. Rare: the combination reorders the data twice, because the vector reorder discards the order the SortingCodecReader provides. Once on that path, it fails on every call.

Why it looks unintended

#
  • Both SortingCodecReader and BPIndexReorderer.reorder document passing such a reader to addIndexes; the failure is inside that merge.
  • The postings BPIndexReorderer accepts the same input under the same policy, which #14097 opened to either reorderer.
  • copy() throws on purpose (#13779), for views read only by iteration; #16705 fixed the same throw in another wrapper.
The full argument259 words
  • Contracts. SortingCodecReader (SortingCodecReader.java:47-52): re-sort an index "by wrapping all readers of the index with this reader and adding it to a fresh IndexWriter via IndexWriter#addIndexes(CodecReader...). NOTE: This reader should only be used for merging." BPIndexReorderer.reorder (BPIndexReorderer.java:825-842): the returned reader "should typically be used in a call to IndexWriter#addIndexes(CodecReader...)"; its class example ends in w.addIndexes(reorderedReaderView) (:73-89). IndexReorderer.computeDocMap takes any CodecReader (IndexReorderer.java:25-35). The policy "simply skips reordering in order not to fail the merge" when RAM is short (BPReorderingMergePolicy.java:34-37).
  • Tests. TestBPReorderingMergePolicy randomly plugs BpVectorReorderer into the policy, including testReorderOnAddIndexes (:49-57, :147-148), but only with SlowCodecReaderWrapper inputs (:189). No test, javadoc, CHANGES or MIGRATE entry excludes SortingCodecReader inputs.
  • History. #13779 (6053e1e3137, 2024-09-28, by msokolov) made the sorting views' copy() throw on purpose; its body relies "on testing to catch missing required methods", because "some of these readers would only ever be used iteratively", and a review comment by benwtrent asked that sub-classes "purposefully indicate that this is unsupported" (on createIterator(), about the pattern in general, not on copy()). #14097 (02a09f6ab12, 2025-01-07, same author) added the copying BpVectorReorderer and "refactored to make BpVectorReorderer compatible with BPIndexReorderer so that either can plug into BPReorderingMergePolicy"; none of its comments mention copy(), SortingCodecReader or addIndexes.
  • Precedent. #16705 (by goankur, merged 2026-10-01) replaced the throwing copy() of ExitableDirectoryReader's vector views with a delegating copy because a new consumer needed one; the same commit edited SortingCodecReader.java and left its copy() throwing.
  • Framing.
The devil's-advocate check169 words

Strongest case for "intended or harmless": the throw is deliberate (#13779); SortingCodecReader is @lucene.experimental and "should only be used for merging"; and the combination is pointless, because the vector reorder throws away the order the caller just built, so a user who wants vector BP should pass plain readers.

Why it fails: this is merging, the documented use, with the documented output of BPIndexReorderer.reorder. #13779's own rationale expects a method that a real consumer needs to be caught and filled in, and #14097, by the same author, says either reorderer should plug into the policy; the postings reorderer accepts the same input. For a reorder it cannot afford (not enough RAM) the policy skips the reorder rather than fail the merge; that rule is about RAM only, and nothing documents what should happen when the reorderer cannot read an input. Redundancy lowers the likelihood (rare), but it does not make an exception from an accepted call correct. Verdict: a defect. Expect the "why reorder twice?" question in review.

Suggested fix

#

Recommended A: make copy() work and map ordinals through the iterator

Make the sorting views' copy() return a view over delegate.copy() that shares the immutable doc mapping, and have BpVectorReorderer take each document's ordinal from the iterator (it.index()) instead of counting positions. The test, the closest suites and the misc module pass, and the reorder lands on the right documents. Land it with the fix for LFV-278.

// SortingCodecReader: each Sorting*VectorValues (float shown)
@Override
public FloatVectorValues copy() throws IOException {
  return new SortingFloatVectorValues(delegate.copy(), iteratorSupplier);
}

// BpVectorReorderer.valueMapToDocMap: no dense shortcut; ordinals from the iterator
KnnVectorValues.DocIndexIterator it = values.iterator();
for (int nextDoc = it.nextDoc(); nextDoc != NO_MORE_DOCS; nextDoc = it.nextDoc()) {

  int newOrd = valueMap.oldToNew(it.index()); // was: valueMap.oldToNew(ord++)

A: make copy() work and map ordinals through the iterator (validated by the checks) (recommended)

#

Two halves, +31/-15 lines in two files, no API change. (1) In SortingCodecReader, each sorting vector view gets a private constructor taking a delegate and the existing SortingIteratorSupplier, and copy() returns new Sorting*VectorValues(delegate.copy(), iteratorSupplier); the supplier's arrays are never modified after construction, so copies can share them, as iterator() already does. (2) In BpVectorReorderer.valueMapToDocMap, drop the "every document has a vector" shortcut and look up each document's new position by its own ordinal, it.index(). For a plain reader the result is identical, because its ordinals follow doc order.

Trade-offs

  • Land with LFV-278. With two SortingCodecReader inputs in one call, this fix makes addIndexes succeed, and then the merged view's iterator puts the wrong vector on 64 of 64 documents (LFV-278). With both fixes, all 5 failing shapes and 5 controls of the tie-break probe pass.
  • Below 64 vectors nothing is split, and the doc map now follows the wrapped reader's ordinals instead of being the identity: in a 63-document control the output follows the underlying reader's order, not the reversed view's. No contract fixes the output order of a reorder that found nothing to split; mention the change in the PR and leave it to the maintainers whether it is acceptable. Starting the bisection from the view's doc order instead is an untested alternative.
  • The dense case builds two int[maxDoc] arrays instead of reusing the permutation; small next to the bisection.
  • copy() now delegates, so a sorting view is only as copyable as the vector values it wraps.
  • The regression test checks only that addIndexes succeeds; the doc-space half is covered by the probes, not by the test; an upstream PR should add a test of the doc map.

B: give each thread a fresh view instead of a copy (untested)

#

Build each per-thread state from reader.getFloatVectorValues(field) instead of vectors.copy().

Trade-offs

Works for any reader without copy(), but costs a new doc mapping (an int[maxDoc] plus a bit set) per thread for sorting views, and still needs the ordinal half of option A.

C: skip reordering on UnsupportedOperationException (untested, not recommended)

#

BPReorderingMergePolicy catches it like NotEnoughRAMException and leaves the merge unreordered.

Trade-offs

Hides the incompatibility; the input silently stays unreordered (bp.reordered=false); the catch is broad.

D: document the limitation (not recommended)

#

Say that SortingCodecReader inputs are unsupported with BpVectorReorderer.

Trade-offs

Leaves the documented BPIndexReorderer.reorder -> addIndexes recipe broken for this policy.

E: fix copy() only (not enough)

#

Only half (1) of option A, the first fix the hunt wrote.

Trade-offs

Downstream note

#

For a downstream service this is a failed import or re-sort job, not data damage: only the application's own addIndexes call with this configuration reaches the throw, and it fails before anything is written.

How it was found

#

A hand-written end-to-end JUnit from a hunt unit on vector doc/ordinal mappings re-sorts a segment with SortingCodecReader, adds it with addIndexes to a vector-reordering writer and checks that every document keeps its vector; it failed earlier, with this exception. A second unit then inventoried every copy() implementation and caller and found this the only unreported throwing pair.

LFV-404, snapshot of 2026-11-08

Registry title
addIndexes of a SortingCodecReader (including the reader that BPIndexReorderer.reorder returns) into a writer that uses BPReorderingMergePolicy with BpVectorReorderer throws UnsupportedOperationException, because SortingCodecReader's vector views do not support copy()
Area
misc / index: BpVectorReorderer merge-time reordering (BPReorderingMergePolicy) over core / index: SortingCodecReader vector views
Priority
Low, rank 675: AddIndexes of a SortingCodecReader into a writer that reorders with BpVectorReorderer fails loudly and adds nothing, but it is unreleased and needs a rare double-reorder combination, so it follows the opt-in crash rows LFV-296, LFV-438 and LFV-265.
Impact class
crash
Impact note
Only applications on unreleased main (11.0.0-SNAPSHOT) that opt into the expert lucene/misc BPReorderingMergePolicy with a BpVectorReorderer on a writer without an index sort and pass a SortingCodecReader to IndexWriter#addIndexes(CodecReader...) (re-sorted by a Sort or a DocMap, or the reader that BPIndexReorderer.reorder returns, which its javadoc says to pass to addIndexes) with at least 64 FLOAT32 vectors in the reordered field are hit, on every such call: addIndexes throws a clean unchecked UnsupportedOperationException within milliseconds and adds nothing, while the writer stays open and non-tragic and the index is unchanged (executed with both merge schedulers); a destination that carries the index sort (the usual re-sort recipe) skips reordering and is not affected, no released version contains BpVectorReorderer, and no scale is needed.
Summary
You pass a SortingCodecReader, for example the reader that BPIndexReorderer.reorder returns or SortingCodecReader.wrap(reader, docMap, null), to IndexWriter#addIndexes on a writer whose merge policy is BPReorderingMergePolicy with a BpVectorReorderer, and expect the documents to be added and reordered, as they are for plain segment readers and as the same policy does with the postings BPIndexReorderer. Instead addIndexes throws UnsupportedOperationException and adds nothing: the policy reorders addIndexes as a forced merge, BpVectorReorderer's per-thread state calls copy() on the input's float vector values, and SortingCodecReader's vector views throw from copy() (with several such readers in one call the throw comes through SlowCompositeCodecReaderWrapper's merged copy()). Making copy() work is not enough on its own: BpVectorReorderer then treats the sorting view's ordinals as doc order, so the reordering is silently applied in the wrong doc space.
