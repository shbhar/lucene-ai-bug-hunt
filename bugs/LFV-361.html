XML query parser rejects a <Clause> without occurs instead of treating it as SHOULD

The XML query parser's DTD says a <Clause> without occurs is optional (should), but since 5.1.0 CoreParser.parse rejects it with ParserException: Invalid value for "occurs" attribute of clause:. The code checks the attribute for null, while the XML DOM returns "" for a missing attribute.

The finding in 30 seconds

#

One dead check: the builder's own "missing occurs means SHOULD" branch tests for null, but a missing XML attribute reads as the empty string.

Background: how the XML query parser builds a BooleanQuery

#
  1. CoreParser.parse(InputStream) turns an XML document into a Lucene Query: a <BooleanQuery> element becomes a BooleanQuery, and each <Clause> child becomes one of its clauses.
  2. A clause's occurs attribute picks its role: should (optional), must (required), mustNot (excluded) or filter.
  3. The shipped LuceneCoreQuery.dtd documents this syntax and makes occurs optional with the default should. The parser does not validate against the DTD, so the builder has to apply that default itself.

The finding, step by step

#
  1. Parse <BooleanQuery fieldName='f'><Clause><TermQuery>a</TermQuery></Clause></BooleanQuery> with new CoreParser("f", analyzer).parse(...). The <Clause> has no occurs attribute.
  2. You expect a BooleanQuery with one optional (SHOULD) clause f:a: the DTD gives occurs the default "should", the same document with occurs='should' parses to exactly that, and 5.0.0 treats a missing occurs as SHOULD.
  3. Instead the whole parse fails with ParserException: Invalid value for "occurs" attribute of clause:, with nothing after the colon. An explicit occurs="" fails the same way.
  4. Why: getOccursValue reads getAttribute("occurs"), which returns "" for a missing attribute, never null. Its occs == null branch, meant to return SHOULD, never runs, so "" reaches the throw.
  5. It fails closed: no query is built and the parser stays usable; occurs="should" works around it. Every release from 5.1.0 to 10.6.0 rejects the clause; 5.0.0 accepts it.

Who is affected

#

Users of the opt-in XML query parser who leave occurs out of a <Clause>, as the DTD allows, or write occurs="". The whole query is refused with a checked ParserException: no wrong results, no setting involved. Published examples write occurs out, so hits are rare; occurs="should" is the workaround.

Mechanism, terms and numbers586 words

In the XML query parser (CoreParser, CorePlusQueriesParser, CorePlusExtensionsParser), the occurs attribute of a <Clause> says whether the clause is optional (should), required (must), excluded (mustNot) or a filter. The shipped LuceneCoreQuery.dtd declares <!ATTLIST Clause occurs (should | must | mustnot) "should">, its generated docs say "Default value: should", and BooleanQueryBuilder.getOccursValue has its own branch for a missing attribute. Yet CoreParser.parse of <BooleanQuery fieldName='f'><Clause><TermQuery>a</TermQuery></Clause></BooleanQuery> throws ParserException: Invalid value for "occurs" attribute of clause:. org.w3c.dom.Element.getAttribute returns "" for an absent attribute, so the occs == null branch is dead and "" falls through to the throw; occurs="" fails the same way. LUCENE-6270 introduced it in 5.1.0 while adding occurs="filter": the rewrite replaced the original "".equals(occs) test with occs == null. The parse fails cleanly, with no wrong results; also treating an empty value as SHOULD fixes it.

Terms

#
  • XML query parser: org.apache.lucene.queryparser.xml in lucene-queryparser. CoreParser registers a BooleanQueryBuilder for <BooleanQuery> (CoreParser.java:93 at 645d4fe14a20); CorePlusQueriesParser and CorePlusExtensionsParser inherit it.
  • Element.getAttribute: the DOM call the builders use. Its JDK javadoc: "The Attr value as a string, or the empty string if that attribute does not have a specified or default value."
  • DTD default: <!ATTLIST Clause occurs (should | must | mustnot) "should"> (LuceneCoreQuery.dtd:124). An XML parser fills such a default in only when it reads the DTD; CoreParser parses without validation (CoreParser.java:184) and its default entity resolver refuses external entities (:169-171, :218-226), so a document cannot pull the shipped DTD in.

The bug

#
static BooleanClause.Occur getOccursValue(Element clauseElem) throws ParserException {
  String occs = clauseElem.getAttribute("occurs");                      // :71, "" when absent
  if (occs == null || "should".equalsIgnoreCase(occs)) {                // :72, null never happens
    return BooleanClause.Occur.SHOULD;
  } else if ("must".equalsIgnoreCase(occs)) {
    return BooleanClause.Occur.MUST;
  } else if ("mustNot".equalsIgnoreCase(occs)) {
    return BooleanClause.Occur.MUST_NOT;
  } else if ("filter".equals(occs)) {
    return BooleanClause.Occur.FILTER;
  }
  throw new ParserException("Invalid value for \"occurs\" attribute of clause:" + occs);  // :81
}
  1. BooleanQueryBuilder.getQuery calls getOccursValue for each <Clause> (BooleanQueryBuilder.java:54).
  2. With no occurs, getAttribute returns "" (:71); a DOM built like CoreParser's gives hasAttribute("occurs") == false and getAttribute("occurs") == "".
  3. occs == null (:72) is false and "" matches none of the four names, so :81 throws, with the empty value after the colon. The exception leaves CoreParser.parse (CoreParser.java:141-142), which declares ParserException; the caller gets no query.

The same builder reads its other two attributes correctly, through DOMUtils.getAttribute(e, name, default), which treats null or empty as "use the default" (DOMUtils.java:119-137): minimumNumberShouldMatch (:46, default 0) and boost (:63, default 1.0), the defaults the DTD declares (LuceneCoreQuery.dtd:115, :109). Only occurs is read raw and tested for null.

Exposure and likelihood170 words
  • Who is hit. Applications that use CoreParser, CorePlusQueriesParser or CorePlusExtensionsParser (public, in the exported packages org.apache.lucene.queryparser.xml and .builders) and send a <Clause> without occurs, or with occurs="": hand-written queries, query templates (the DTD names XSLT query templates as a motivation) or generators that rely on the documented default. Solr's xmlparser query parser reaches the same builder (code reading, not run).
  • Default vs opt-in. The XML query parser is opt-in; inside it no setting is needed, the default CoreParser(String, Analyzer) constructor is enough. Assertions on or off make no difference.
  • What happens. The whole query fails with a checked ParserException; nothing is built or searched, so there are no wrong results, and the same parser instance keeps working.
  • Scale. None: one clause triggers it.
  • Likelihood: rare. All 28 <Clause> elements in the upstream test fixtures and the DTD's own example write occurs out; a hit fails loudly during development; no public report of it since 5.1.0 (2015) was found.
  • Workaround. Write occurs="should" on every optional clause.

Why it looks unintended

#
  • The builder's own code maps a missing occurs to SHOULD (occs == null, line 72), but that branch can never run.
  • The DTD declares occurs with the default "should"; nothing documents it as required.
  • 5.0.0 and earlier parse it as SHOULD; the 5.1 rewrite that added filter dropped the empty-string test, with no CHANGES note.
The full argument286 words
  • The builder's own default. BooleanQueryBuilder.java:72 returns SHOULD for occs == null. That branch maps an attribute read as missing to SHOULD, and with the JDK DOM it cannot run.
  • The rewrite kept the old null case and lost the empty case. Before LUCENE-6270 the method started from SHOULD, mapped "should" or "" to SHOULD (("should".equalsIgnoreCase(occs)) || ("".equals(occs))) and threw only for an unknown value that was not null (if (occs != null)). bed131f1808 (2015-02-21) rewrote the method to add occurs="filter", one part of LUCENE-6270's replacement of TermsFilter with TermsQuery, and turned that into occs == null || "should".equalsIgnoreCase(occs).
  • Documentation. LuceneCoreQuery.dtd:123-124: "Controls if the clause is optional (should), mandatory (must) or unacceptable (mustNot)" and <!ATTLIST Clause occurs (should | must | mustnot) "should">; the DTD says it "describes the XML syntax" and that "CoreParser.java is the Java class that encapsulates this parser behaviour" (:20, :66). The generated docs (lucene/queryparser/docs/xml/LuceneCoreQuery.dtd.html:136, :142) say "Default value: should". No javadoc, CHANGES.txt or MIGRATE.md entry makes occurs required.
  • History. From the parser's first commit (2006; the 1.9 release has the identical file) a missing or empty occurs meant SHOULD; 4.10.4 and 5.0.0 parse the hunt's probe to f:a +f:b. The LUCENE-6270 CHANGES entry (lucene/CHANGES.txt:11095-11096) says only "Replaced TermsFilter with TermsQuery, use a QueryWrapperFilter(TermsQuery) instead."; the 5.1.0 MIGRATE.txt and the issue's 12 comments never mention occurs. No upstream test asserts the rejection.
  • Precedent. LUCENE-7219 (#8274, 6.0.1 "Bug Fixes", lucene/CHANGES.txt:9296-9298) made the range builders' lowerTerm/upperTerm optional, matching the underlying queries: they had been read with getAttributeOrFail, and the fix reads them through DOMUtils.getAttribute(e, name, null), which treats "" as absent.
The devil's-advocate check192 words

Strongest case for intended (the reviewers rated it moderate): CoreParser parses without validation and refuses to load the DTD, so DTD defaults have no runtime force; the DTD is stale elsewhere (it documents FilteredQuery, RangeFilter, NumericRangeQuery, BooleanFilter and disableCoord, which core no longer builds, and omits occurs="filter"); every upstream test, stylesheet and DTD example writes occurs out; and the failure is loud. So occurs is effectively required and the DTD is documentation debt.

Why it fails: the non-validating parser is exactly why the builder must apply the default itself, and it tries to: the occs == null branch reads as "missing means SHOULD", and the same builder applies the DTD's defaults for boost and minimumNumberShouldMatch. The stale DTD entries describe removed elements; Clause and occurs are live. A deliberate tightening in a minor release would have come with a CHANGES or MIGRATE note and a "missing attribute" message, not Invalid value ... : with an empty value. Fixtures that always write occurs pin nothing about the absent case. In our reading the argument limits severity, not validity; this is evidence about intent, not proof of it.

Suggested fix

#

Recommended A. Also treat an empty value as SHOULD (one line)

Treat an empty occurs like a missing one: if (occs == null || occs.isEmpty() || "should".equalsIgnoreCase(occs)). With it the repro passes with assertions on and off, the whole lucene/queryparser suite passes (534 tests, 0 failures) and check is clean. Reading the attribute through DOMUtils.getAttribute(e, "occurs", "should") is an equivalent alternative.

   static BooleanClause.Occur getOccursValue(Element clauseElem) throws ParserException {
     String occs = clauseElem.getAttribute("occurs");
-    if (occs == null || "should".equalsIgnoreCase(occs)) {
+    if (occs == null || occs.isEmpty() || "should".equalsIgnoreCase(occs)) {
       return BooleanClause.Occur.SHOULD;
All options and trade-offs2 options · 473 words

Both options were run through gradle in a scratch worktree of 645d4fe14a20 and restore the pre-5.1 behaviour: a missing or empty occurs means SHOULD; explicit values, invalid values and the error message are unchanged.

  • Not recommended: declare occurs required (DTD #REQUIRED, regenerated docs, a "missing occurs" message). It would document today's behaviour but contradicts the builder's own default, the docs since 2007 and the 1.9-5.0 behaviour. Not run.
  • A design choice, not run: to keep occurs="" an error (it is not one of the DTD's values), test !clauseElem.hasAttribute("occurs") instead of isEmpty(); that differs from pre-5.1 behaviour and from how DOMUtils treats empty attributes.
  • CHANGES entry: say plainly that a missing occurs means SHOULD (optional), as the DTD documents, not MUST or FILTER, so nobody who builds restriction clauses from templates reads the restored default as restrictive.

A. Also treat an empty value as SHOULD (one line) (validated by the checks) (recommended)

#

In BooleanQueryBuilder.getOccursValue (BooleanQueryBuilder.java:72), add occs.isEmpty() to the SHOULD test.

Trade-offs

  • Restores the 1.9-5.0 behaviour for a missing or empty occurs and matches the DTD default; occurs="filter", added in 5.1, keeps working.
  • Keeps the null guard, which is dead with the JDK DOM; option B drops it.
  • An explicit occurs="" becomes SHOULD, as before 5.1 and as DOMUtils treats empty attributes.

B. Read occurs like the builder's other attributes (validated by the checks)

#

Read the attribute through DOMUtils.getAttribute(clauseElem, "occurs", "should"), which maps null or "" to the default, and drop the dead null test.

   static BooleanClause.Occur getOccursValue(Element clauseElem) throws ParserException {
-    String occs = clauseElem.getAttribute("occurs");
-    if (occs == null || "should".equalsIgnoreCase(occs)) {
+    // a missing (or empty) occurs attribute means SHOULD, the default in LuceneCoreQuery.dtd

+    if ("should".equalsIgnoreCase(occs)) {

Trade-offs

  • Same behaviour as A, written the way getQuery already reads minimumNumberShouldMatch and boost and the way LUCENE-7219 fixed the range builders.
  • States the default in one place; DOMUtils is already imported.

The method in full92 words

Method: non-formal (code reading, then executed tests). On 2026-10-26 the hunt unit for the flexible, simple and XML query parsers set up, as its secondary method, a comparison of each XML builder's output with the syntax LuceneCoreQuery.dtd documents. Reading getOccursValue against the DTD's occurs default showed the null test that the DOM never satisfies. A public-API JUnit test reproduced the rejection on main, a main() probe on release jars found the boundary (5.0.0 accepts, 5.1.0 rejects), independent checkers reproduced it with their own tests, and it was cut to the one-test repro.

Registry title

Area
queryparser / xml (BooleanQueryBuilder)
Priority
Low, rank 919: The niche XML query parser loudly rejects a clause that leaves out occurs (the DTD default) and the workaround is obvious.
Impact class
wrong error
Impact note
Applications that use the opt-in XML query parser (CoreParser and its subclasses CorePlusQueriesParser and CorePlusExtensionsParser, with default settings; downstream wrappers such as Solr's xmlparser query parser reach the same code [read]) and send a <Clause> without occurs, or with occurs="", relying on the documented SHOULD default, get a ParserException for the whole query on every such input; it fails closed (no Query is built, no wrong results, the parser stays usable), needs no scale, is in every release since 5.1.0, and writing occurs="should" avoids it.
Summary
You give the XML query parser (CoreParser.parse) a <BooleanQuery> whose <Clause> has no occurs attribute and expect an optional (SHOULD) clause, because LuceneCoreQuery.dtd declares occurs with the default "should", BooleanQueryBuilder.getOccursValue has its own 'attribute absent -> SHOULD' branch, and 5.0.0 and earlier parsed it that way. Instead the whole parse fails with ParserException 'Invalid value for "occurs" attribute of clause:' (nothing after the colon): org.w3c.dom.Element.getAttribute returns an empty string, never null, for an absent attribute, so the 'occs == null' default branch never runs; an explicit occurs="" is rejected the same way. Explicit should, must, mustNot and filter values work as before, and writing occurs="should" is a workaround.
