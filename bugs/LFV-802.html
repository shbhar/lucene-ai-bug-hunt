IndexWriter#tryUpdateDocValue accepts a doc id outside [0, maxDoc), returns success and updates a different (or a nonexistent) document

The finding in 30 seconds

#

tryUpdateDocValue(reader, docID, fields) updates one document by its number in an NRT reader, but never checks that the number lies in [0, maxDoc). The update buffer stores each doc id in a few bits sized for the segment, so an out-of-range id can wrap onto another document, or survive as an entry for a document that does not exist.

Background: updating a document by its number

#
  1. Inside a segment, documents are numbered 0 to maxDoc - 1. A DirectoryReader is a composite reader that numbers documents across its segments; each of its leaf readers is one segment.
  2. IndexWriter#tryUpdateDocValue(reader, docID, fields) (Expert) changes the doc values of the one document that has number docID in an NRT reader of this writer. Writing the soft-deletes field this way soft-deletes that document.
  3. The writer buffers the change as (doc id, value) entries per segment, packed into a few bits sized for that segment's maxDoc (at least as many as its largest doc id needs, sometimes rounded up to 8, 16, 32 or 64), and returns a sequence number > 0 to say the update succeeded.

The finding, step by step

#
  1. Index 4 documents with a numeric doc-values field v = 0, 1, 2, 3 (default config, one segment) and open an NRT reader with DirectoryReader.open(writer).
  2. Call writer.tryUpdateDocValue(leaf, -1, new NumericDocValuesField("v", 777)) on its only leaf reader, as if a "not found" value of -1 had slipped through your code.
  3. You expect the call to reject -1, as the same reader's stored fields do (IndexOutOfBoundsException), or at least to change nothing: -1 names no document.
  4. Instead the call returns 7, a value > 0 that the javadoc defines as "the update succeeds", and doc 3 now has v = 777. The update buffer of a 4-document segment keeps only 2 bits of each doc id, and the low bits of -1 read as 3.
  5. With assertions off (the production default) a composite reader does the same: on 8 documents, id 8 overwrites doc 0 and a soft-delete of id 9 hides doc 1; on 10 documents, id 12 commits an entry for a document that does not exist, CheckIndex calls it clean, and forceMerge(1) shifts the next segment's 10 values by one.

Who is affected

#

Applications that call the Expert tryUpdateDocValue (also used to soft-delete or un-delete one document) and, through their own bug, pass an id outside the reader: a -1 or NO_MORE_DOCS sentinel, an off-by-one, an id from another reader, a top-level id with a leaf reader. Default config; the call reports success at any segment size tried, so nothing warns them.

Mechanism, terms and numbers938 words

IndexWriter#tryUpdateDocValue(reader, docID, fields) (Expert) updates doc values of one document named by its number in an NRT reader, and is also the documented way to soft-delete or un-delete one document. Its helper tryModifyDocument, shared with tryDeleteDocument, never checks that the number lies in [0, reader.maxDoc()): the leaf-reader branch uses it as is, and the composite branch only asserts. The id goes into a per-segment update buffer that packs each doc id plus a flag bit into an entry of at least bitsRequired(maxDoc - 1) + 1 bits (the packed array may round the width up to 8, 16, 32 or 64 bits) and keeps only the entry's low bits; its only guard is assert doc < maxDoc. So on a 4-document segment, id -1 is stored as doc 3: the call returns 7 (a value > 0, "the update succeeds") and doc 3 gets the new value, with assertions on or off. On other segment sizes the same call still returns success but leaves an entry for a nonexistent document (doc 15 on 10 documents, doc 127 on 40, 64 or 100). With assertions off, the production default, ids at or past maxDoc on a composite reader wrap onto other documents (8 -> doc 0, 9 -> doc 1, NO_MORE_DOCS -> doc 7), or are kept as an entry for a nonexistent document, which the commit persists, CheckIndex calls clean and forceMerge(1) shifts onto the next segment's documents. Every trigger is a caller bug, so the priority is low; but the call reports success while it changes a different, valid document (or adds an entry for a nonexistent one). It is in every release since 7.4.0 and on main; a 7-line range check at the top of tryModifyDocument fixes it and passes the whole core test suite.

Step by step, on the repro

#
  1. The buffer. tryUpdateDocValue creates a NumericDocValuesFieldUpdates sized for the segment's maxDoc (IndexWriter.java:1740-1744) and adds the caller's leaf id unchanged (:1756-1757).
  2. The width. Each entry has at least bitsRequired(maxDoc - 1) + 1 bits: PackedInts.DEFAULT lets the packed array round the width up to 8, 16, 32 or 64 bits when that costs at most 25% more (PackedInts.java:186-213, since LUCENE-8598 in 7.7.0), and Packed64.set does not mask, so only the low bits of that width survive. For maxDoc 4 the width is exactly bitsRequired(3) + 1 = 2 + 1 = 3 bits. -1 << 1 | 1 is all ones; its low 3 bits are 0b111; shifted back, that is doc 3.
  3. The guards. The leaf branch has none; the buffer's assert doc < maxDoc holds for -1. So the update is applied with assertions on or off, and the call returns docWriter.getNextSequenceNumber() (IndexWriter.java:1824): 7.
  4. Same arithmetic, other ids (assertions off, composite reader, where only the asserts at :1803-1804 stand in the way): maxDoc 8 gives 4 bits, so 8 -> doc 0, 9 -> doc 1 and NO_MORE_DOCS (2^31 - 1) -> doc 7. maxDoc 10 gives 5 bits, so 12 fits and is kept: an entry for a document that does not exist, written to the new doc-values generation at commit.
  5. Other segment sizes (leaf reader, id -1, assertions on and off): -1 lands on the last document only when the width is exact and maxDoc is a power of two (4, 8 or 16 documents). On 10 documents it becomes an entry for nonexistent doc 15, and on 40, 64 or 100 documents for nonexistent doc 127 (8-bit entries: 7 bits rounded up for 40 and 64, exactly 8 for 100). Every one of these calls returns success.
  6. After the commit the doc-12 entry is an extra FieldExistsQuery hit, and stored fields reject doc 12; CheckIndex does not flag that commit on any version tested, and forceMerge(1) shifts the next segment's values by one document.

Exposure and likelihood272 words
  • Who is hit. Callers of the Expert IndexWriter#tryUpdateDocValue, including its documented uses to soft-delete and un-delete single documents (IndexWriter.java:1712-1715; CHANGES.txt:7417-7421), that pass an id outside the reader they pass. Plausible caller bugs: a -1 or NO_MORE_DOCS "not found" value, an off-by-one, an id from another or newer reader, or a top-level id together with a leaf reader (the study's probe, assertions off: two 10-document segments, the second segment's leaf with top-level id 17, meant for its doc 7, returns 26 and writes into its doc 1, because only the low 4 bits of 17 are kept).
  • No special setup. Default IndexWriterConfig and codec, a 4-document segment, one thread, deterministic. The leaf-reader -1 call returns success at every segment size tried (4 to 100 documents), with assertions on or off, so Lucene-style -ea test runs do not catch it; which document it hits depends on the size. The composite cases need assertions off, the production default.
  • What goes wrong. A different, valid document gets the value, or is soft-deleted and so disappears from search, while the call returns its success value; or the commit holds an entry for a document that does not exist, CheckIndex calls it clean, and the next merge shifts values across ten other documents and drops one.
  • What does not go wrong. Correct callers, with ids from the same NRT reader, are unaffected. No Lucene main code calls tryUpdateDocValue; IndexRearranger (lucene/misc) calls tryDeleteDocument with ids from a loop over maxDoc. No memory corruption: the wrong data goes through ordinary Java arrays.
  • Impact class: data corruption, likelihood contrived (needs a caller bug); priority low.

Why it looks unintended

#
  • The javadoc says a return value > 0 means "the update succeeds"; it states no doc-id precondition.
  • Asserts on the composite path and in the buffer show such ids are not meant to get through; production runs without assertions, and the leaf path has none.
  • The same reader rejects -1 with an exception; here a different, valid document changes silently.
The full argument287 words
  • Contract. IndexWriter.java:1707-1712: "If the provided reader is an NRT reader obtained from this writer, and its segment has not been merged away, then the update succeeds and this method returns a valid (> 0) sequence number; else, it returns -1 ...". No doc-id precondition and no "undefined" clause. CHANGES.txt:7417-7421 (LUCENE-8297): "With tryUpdateDocValues users can update doc-values fields for individual documents. This allows for instance to soft-delete individual documents."
  • The asserts show such ids are not meant to get through (an inference from the code; no comment says so). The composite branch has asserted docID >= 0 and docID < reader.maxDoc() since LUCENE-4203 (2012), and the buffer doc < maxDoc since LUCENE-7868 (2017). When tryDeleteDocument was added (4.0), its delete path also asserted the range (ReadersAndLiveDocs.delete), on the leaf branch too; with assertions off, the 4.0 BitVector threw ArrayIndexOutOfBoundsException for most bad ids, though ids between maxDoc and the next multiple of 8 returned true and deleted nothing (executed on the 4.0.0 jars). LUCENE-8297 (2018) then sent the same unchecked id into a packed buffer that truncates it; its discussion (#9344) never mentions validation.
  • Lucene rejects out-of-range ids elsewhere on the same reader. BaseCompositeReader.java:261-266 throws IllegalArgumentException "docID must be >= 0 and < maxDoc"; CodecReader.java:93-101 checks with Objects.checkIndex under the comment "Don't trust the codec to do proper checks"; TestDirectoryReader.testOOBDocID (:1090-1097) expects the exception. IndexWriter#addBatch checks its doc ids too (ColumnValidation.java:297-307).
  • The same call rejects other bad input with IllegalArgumentException, for example a field without doc values ("can only update NUMERIC or BINARY fields! field=id", IndexWriter.java:2090-2093), executed in the tie-break probe.
  • No cost argument. The method is synchronized and already does a linear search over segments (IndexWriter.java:1814-1819).
The devil's-advocate check276 words

Strongest case for "intended" (caller misuse, so the fix is hardening): a doc id is by definition in [0, maxDoc) (IndexReader.java:51-52: "non-negative integers which each name a unique document"); these methods are Expert; Lucene often documents out-of-range ids as the caller's problem (Bits.get: "The result of passing negative or out of bounds values is undefined by this interface, just don't do it!", Bits.java:30-31; DocValuesIterator.advanceExact: the target "must be a valid doc ID") and guards internal invariants with asserts; in LUCENE-4203 (#5275) the issue's reporter and committer, Michael McCandless, wrote that "you should use an NRT reader from IW anyway to even find the docID to delete"; and open PR #16847 keeps the range check assert-only. All read-only cross-model reviews made this point.

Why it fails:

  1. Those "undefined" clauses are stated in the javadoc of read APIs; tryUpdateDocValue's javadoc has none, and it is a write API that persists the damage.
  2. The damage is not confined to the caller's bad input: a different, valid document changes, under a success return value.
  3. The writer commits an internally inconsistent index (a doc-values entry beyond maxDoc) that CheckIndex accepts and a merge spreads onto other documents.
  4. The leaf branch has not even an assert, so Lucene's own -ea test runs cannot catch the negative-id case.
  5. The same reader, the same call and addBatch reject bad input with exceptions; the merged #16919 (2026-10-28) turned more explicit AssertionErrors into proper exceptions in other files, the same direction.

What remains is framing (bug or hardening), which sets the low priority, not the verdict. A "hardening" label is likely; the trigger is a caller error.

Suggested fix

#

Recommended A. Range-check the id at the top of tryModifyDocument (7 lines)

At the top of tryModifyDocument, which both try* methods share, throw IllegalArgumentException("docID must be >= 0 and < maxDoc=...") when docID < 0 || docID >= readerIn.maxDoc(), as BaseCompositeReader does (7 lines). The repro passes, as do the 10 closest suites (246 tests in 11 classes with the repro, assertions on and off) and all 8,898 core tests.

Trade-offs

Callers that pass out-of-range ids get an exception instead of silent success. For tryDeleteDocument that replaces today's "> 0 but nothing deleted" (maxDoc 10, id 10) or ArrayIndexOutOfBoundsException (maxDoc 64, id 64); a composite -1 changes from IndexOutOfBoundsException to IllegalArgumentException; an out-of-range id on a reader that is not a SegmentReader now gets the range message instead of "the reader must be a SegmentReader ...", since the check runs first. How it was found

#

Code reading during a hunt unit that stress-tested tryDeleteDocument and tryUpdateDocValue against flush, merge and commit. While writing a "returns success but changed a different document" check, the finder saw that the doc id is only asserted. Stock-jar probes with assertions off confirmed the effect; the concurrency testing itself did not find it.

LFV-802, snapshot of 2026-11-03

Registry title
IndexWriter#tryUpdateDocValue does not validate the doc id: an id outside [0, maxDoc) returns success and silently updates or soft-deletes a different document, or commits a doc-values entry for a nonexistent document that a merge shifts onto other documents
Area
index / IndexWriter tryUpdateDocValue (tryModifyDocument doc-id validation, doc-values update buffer)
Priority
Low, rank 824: Silent corruption of another document happens only when a caller passes an out-of-range id to the Expert tryUpdateDocValue, a contrived caller bug, but it has shipped since 7.4.0, a merge spreads the ghost entry, and the negative id gets past -ea.
Impact class
data corruption
Impact note
Only applications that call the Expert tryUpdateDocValue (including its soft-delete and un-delete uses) with a doc id outside [0, reader.maxDoc()) because of their own bug (an id from another reader, an off-by-one, a -1 or NO_MORE_DOCS sentinel, or a top-level id passed with a leaf reader) are hit; with the default IndexWriterConfig and codec and assertions disabled (the production default) the call returns its success value while it changes or soft-deletes a different document of the same segment, or commits an entry for a nonexistent document that the next merge shifts onto the next segment's documents; a negative id on a leaf reader does this with assertions enabled too; no scale is needed (an 8-document segment), CheckIndex on 10.x and main does not notice, and it is in every release from 7.4.0 through 10.6.0 and main.
Summary
You call IndexWriter#tryUpdateDocValue with an NRT reader and a doc id outside [0, reader.maxDoc()), for example 8 or 9 on an 8-document reader, 12 on a 10-document reader, or -1 on a 4-document leaf reader. You expect the call to be rejected, as the same reader rejects such an id ('docID must be >= 0 and < maxDoc', IllegalArgumentException), or at least to leave every other document alone. Instead, with assertions disabled (and for the negative leaf-reader id even with them enabled) it returns a sequence number > 0, which the javadoc says means the update succeeded, and writes the value to or soft-deletes a different live document (8 -> doc 0, 9 -> doc 1, -1 -> doc 3), or commits a doc-values entry for nonexistent doc 12 that CheckIndex accepts and that forceMerge turns into every document of the next segment carrying its predecessor's value (b0=777, b1=1000, ..., b9=1008; 1009 is lost).
