ICUTokenizerFactory leaves a custom rule file open when reading or decoding it fails

If a custom ICU rule file (rulefiles) is not valid UTF-8, or reading it fails, ICUTokenizerFactory.inform() throws as it should but never closes the stream it opened: the file handle stays open until garbage collection. Every release since 4.1.0 has it; a try-with-resources fixes it.

The finding in 30 seconds

#

Background: custom ICU rule files

#
  1. ICUTokenizer splits text into words with ICU break rules, one rule set per script (Latin, Cyrillic, Thai, ...). Its factory, SPI name icu, can replace the rules of a script with your own file: rulefiles="Latn:latin.rbbi".
  2. The factory reads each rule file once, when the analyzer is set up (inform(ResourceLoader)). The ResourceLoader opens the file (from disk with FilesystemResourceLoader, from the classpath with ClasspathResourceLoader) and hands the stream to the factory.

The finding, step by step

#
  1. You configure ICUTokenizerFactory with rulefiles="Latn:latin.rbbi". The rule file is 17 bytes, # café and the rule .+ {200};, saved as ISO-8859-1, so é is the single byte 0xE9: not valid UTF-8.
  2. You expect inform() to fail, because Lucene reads rule files with a strict UTF-8 decoder, and to close the file it opened, as it does for a valid file and as Lucene's stopword loader does with the same decoder.
  3. You get MalformedInputException: Input length = 1, but the stream's close() is never called. parseRules closes the reader only after its read loop ends normally, and the exception jumps past that line.
  4. With a real file on disk, five failed inform() calls leave 5 file descriptors open (1, 2, 3, 4, 5 after each try) until System.gc() brings the count back to 0; Lucene's test filesystem reports file handle leaks. An I/O error during the read leaks the same way.

Who is affected

#

Only applications that set rulefiles (custom per-script ICU rules), directly, through CustomAnalyzer or a search-server schema, and whose rule file cannot be read to the end: a file saved in a legacy encoding such as ISO-8859-1 with a non-ASCII character, or an I/O error. Each failed load leaves one stream open until GC. Tokens and the index are unaffected.

Mechanism, terms and numbers562 words

ICUTokenizerFactory can load custom ICU break rules per script from files (rulefiles="Latn:latin.rbbi"). In inform(), parseRules opens each file through the ResourceLoader, reads it line by line through Lucene's strict UTF-8 decoding reader, and calls reader.close() only after the read loop has finished normally. When the file is not valid UTF-8 (for example saved as ISO-8859-1 with é in a comment) or the stream throws an IOException mid-read, inform() fails with that exception, as it should, but the close is skipped and the stream stays open until it is garbage-collected. With FilesystemResourceLoader that is an open file handle, which Lucene's own LeakFS test filesystem reports as a leak. The default configuration (no rulefiles) opens no rule file through the ResourceLoader, a rule file that decodes but does not compile is closed before compiling, and tokens and the index are unaffected. It has been there since rulefiles arrived in 4.1.0; a try-with-resources around the stream and the reader fixes it.

Terms

#
  • rulefiles: a comma-separated list of code:rulefile pairs, a four-letter ISO 15924 script code and a resource path, each compiled by ICU's RuleBasedBreakIterator (class javadoc, ICUTokenizerFactory.java:49-66 at 645d4fe14a20).
  • Decoding reader: IOUtils.getDecodingReader(stream, UTF_8) reports malformed input instead of replacing it (CodingErrorAction.REPORT, IOUtils.java:192-199); its javadoc says it is "useful to load configuration files, stopword lists or synonym files to detect character set problems".

The bug

#
  1. inform() calls parseRules(resourcePath, loader) once per pair (ICUTokenizerFactory.java:116-120, call at :119); without rulefiles it opens nothing through the ResourceLoader (:111-112; the bundled Default.brk and MyanmarSyllable.brk come from the jar, read once by DefaultICUTokenizerConfig's static initializer, DefaultICUTokenizerConfig.java:81-84, :144-153).
  2. parseRules opens the stream (loader.openResource(filename), :139), wraps it in a BufferedReader over the decoding reader (:140-141), reads line by line (:143-148) and calls reader.close() at :149, with no try/finally. It then compiles the rules (:150).
  3. A byte that is not valid UTF-8 makes readLine() throw MalformedInputException; a failing stream makes it throw IOException. Either leaves the method before :149.
  4. Within Lucene, parseRules is the only holder of the stream and inform() returns nothing, so no Lucene code can close it later (the stock FilesystemResourceLoader and ClasspathResourceLoader keep no reference either). What it holds is released only if the stream's own cleanup runs when the garbage collector reclaims it: for a real file, the probe saw the descriptor released after a forced System.gc(). With several pairs, the files read before the failing one were already closed at :149; only the failing stream stays open.

Exposure and likelihood253 words
  • Who is hit. Users of the analysis-icu module who opt in to rulefiles: on the factory directly, through CustomAnalyzer with the SPI name icu, or through a search-server schema (the class javadoc's examples are such schemas). The default factory, without rulefiles, opens no rule file through the ResourceLoader.
  • What it takes. A rule file that cannot be read to the end: not valid UTF-8 (a file saved in a legacy encoding such as ISO-8859-1, where one non-ASCII character anywhere, even in a comment, becomes a byte that is not valid UTF-8) or an I/O error while reading. No scale, no unusual parameters; the same with assertions on and off.
  • What happens. inform() fails loudly, as it should, and one InputStream per failed load stays open until it is garbage-collected: one file handle with FilesystemResourceLoader, one resource stream with ClasspathResourceLoader. An application that keeps retrying a bad configuration leaks one more each time until the next GC: five failed calls on a real file left 1, 2, 3, 4, 5 descriptors open, and 0 only after System.gc() (0 after every call with the fix). Lucene's LeakFS test filesystem fails a test that does this.
  • What does not happen. No wrong tokens, no index change, no data exposure. Not measured and not claimed: running out of file descriptors, or an open handle blocking replacement of the file on platforms that lock open files.
  • How likely. Rare: no report since 4.1.0, and the leak hides behind the loud setup failure.

Why it looks unintended

#
  • parseRules opens the stream and closes it on success; after a failure no Lucene code can close it.
  • Lucene's stopword loader (the same strict decoder) and the other factory loaders close on failure; OpenNLP's lemma dictionary never closes (a separate bug, LFV-461).
  • Upstream fixed the same leak class as bugs: GITHUB#14727 (10.3.0, the same close-only-on-success pattern), LUCENE-7547 and LUCENE-8188.
The full argument318 words
  • Ownership. parseRules opens the stream (ICUTokenizerFactory.java:139), is the only Lucene code that holds it and closes it after a successful read (:149). As Uwe Schindler put it on LUCENE-4165 (#5237): "of course we close streams, but only if we open them". Here Lucene opens it.
  • A designed failure path. IOUtils.getDecodingReader reports charset problems on purpose: "Decoding readers are useful to load configuration files, stopword lists or synonym files to detect character set problems" (IOUtils.java:185-186). A rule file in the wrong charset is an expected outcome of the reader parseRules chose.
  • The sibling loaders close on failure, with one known exception. WordlistLoader.getLines (the stopword loader, the same decoding reader, try-with-resources at WordlistLoader.java:297-299), AbstractAnalysisFactory.getSnowballWordSet (:322), JapaneseTokenizerFactory (:144), the Korean, Morfologik, Word2Vec, Hunspell and hyphenation factories, and the six OpenNLP model loaders. The exception is OpenNLP's lemma dictionary: OpenNLPOpsFactory.getLemmatizerDictionary hands the stream to OpenNLP's DictionaryLemmatizer (OpenNLPOpsFactory.java:162), which never closes it, on success or failure; that is a separate leak, LFV-461 (LUCENE-10171 undid the LUCENE-8188 fix there). An executed probe with injected read failures over 18 analysis-factory configurations (OpenNLP not among them) found leaks only in the ICU rulefiles runs (5 of 54 runs).
  • Accepted bug fixes of the same class (lucene/CHANGES.txt, Bug Fixes): LUCENE-7547 "JapaneseTokenizerFactory was failing to close the dictionary file it opened" (6.4.0, 5.5.4); LUCENE-8188, OpenNLPOpsFactory "InputStreams fetched from the ResourceLoader to be leaked" (7.3.0); GITHUB#14727 "Fix several resource leaks" (10.3.0), which replaced a close() at the end of the success path with try-with-resources in smartcn's BigramDictionary and WordDictionary.
  • Tests and history. Upstream TestICUTokenizerFactory has 5 tests; the three that load rule files use valid ones, and none covers a failing one. parseRules is unchanged in behaviour since SOLR-4123 (2012), whose 21-comment thread covers the rulefiles syntax, resource paths and rule syntax errors but never mentions closing the stream or a failed read.
The devil's-advocate check137 words

The strongest case for "intended" (built by reviewers): no javadoc says who closes the stream after a failed inform() (ResourceLoader.openResource says only "Opens a named resource"); invalid UTF-8 is a configuration error that already fails loudly; the JDK reclaims the handle at GC; and DefaultICUTokenizerConfig.readBreakIterator closes Lucene's bundled .brk files the same close-on-success way (DefaultICUTokenizerConfig.java:144-153).

Why it fails. The contract's silence is answered by ownership: Lucene opened the stream and no Lucene code can reach it after the failure. GC timing is unbounded, which is why Lucene's own test framework fails tests that leave handles open. The sibling loaders and three accepted bug fixes show the project's intent. The bundled-resource reader handles known-good resources inside Lucene's own jar, so it is a side note (optional hygiene, not part of this claim), not a counter-example.

Suggested fix

#

Recommended A. Open the stream and the reader in a try-with-resources in parseRules

Open the stream and the reader in a try-with-resources in parseRules (9 lines added, 9 removed); the rules are still compiled after the close. With it the repro passes with assertions on and off, and the analysis-icu module's 159 tests and static checks pass.

-    InputStream rulesStream = loader.openResource(filename);
-    BufferedReader reader =
-        new BufferedReader(IOUtils.getDecodingReader(rulesStream, StandardCharsets.UTF_8));
+    try (InputStream rulesStream = loader.openResource(filename);
+        BufferedReader reader =
+            new BufferedReader(IOUtils.getDecodingReader(rulesStream, StandardCharsets.UTF_8))) {
       // read loop unchanged, indented one level
     }
-    reader.close();
     return new RuleBasedBreakIterator(rules.toString());

A. Open the stream and the reader in a try-with-resources in parseRules (validated by the checks) (recommended)

#

Move the read loop into try (InputStream rulesStream = loader.openResource(filename); BufferedReader reader = ...) { ... } and drop the explicit reader.close(); the rules are compiled after the block, as before. 9 lines added, 9 removed, ICUTokenizerFactory.java only.

-    InputStream rulesStream = loader.openResource(filename);
-    BufferedReader reader =
-        new BufferedReader(IOUtils.getDecodingReader(rulesStream, StandardCharsets.UTF_8));
+    try (InputStream rulesStream = loader.openResource(filename);
+        BufferedReader reader =
+            new BufferedReader(IOUtils.getDecodingReader(rulesStream, StandardCharsets.UTF_8))) {
       // read loop unchanged, indented one level
     }
-    reader.close();
     return new RuleBasedBreakIterator(rules.toString());

Trade-offs

  • Success path unchanged: the stream is still closed before ICU compiles the rules, so a rule file that does not compile still leaves nothing open.
  • On failure the caller sees the same exception, with any exception from close() attached as suppressed; on success a failing close() propagates, as the explicit close() at :149 does today. The stream is its own resource, so it is also closed if wrapping it in the decoding reader fails. Closing the stream after the reader is a harmless second close.
  • The same idiom as WordlistLoader.getLines and GITHUB#14727. LFV-719 (a byte order mark kept as rule text) changes the same loop; the two fixes do not conflict.

What the checks validated

  • Gradle in a scratch worktree of 645d4fe14a20 (2026-11-01): the repro fails on stock and passes with the fix, with assertions on and off.
  • The whole :lucene:analysis:icu:test task with the repro in place: 17 test classes, 159 tests (10 skipped), 0 failures, including the 5 TestICUTokenizerFactory tests.
  • :lucene:analysis:icu:check -x test (google-java-format, ecj lint, forbidden APIs) passes with the fix and the test in place.
  • Earlier checks: the finder's 4 tests pass, fault injection finds 0 leaks in 157 checks (156 fault points and a fault-free baseline), and five failed tries on a real file leave 0 descriptors open.

B. try/finally with IOUtils.closeWhileHandlingException

#

Keep the code as is and close the reader (or the stream) in a finally block, for example with IOUtils.closeWhileHandlingException.

Trade-offs

Same effect in older style, with more lines; no reason to prefer it. Care is needed: a plain finally with IOUtils.close lets a failing close replace the read exception, so closeWhileHandlingException belongs on the failure path only (the usual success flag idiom). Not run.

Downstream note

#

OpenSearch's ICU plugin and Lucene.NET read rule files with their own code, which closes the file on failure (source read), so the leak is specific to Lucene's ICUTokenizerFactory and the applications that configure it.

How it was found

#

Non-formal first signal: an executed probe injected read failures into 18 analysis-factory configurations, and only the ICU rulefiles runs left a stream open. A TLA+ model of the load and fault injection at every byte of a real rule file then confirmed it, and it was cut to one public-API test.

The method in full131 words

Method: non-formal first signal, then formal characterization. On 2026-10-28 an exception-safety probe (FactoryInformLeakProbe) gave 18 analysis-factory configurations a close-tracking ResourceLoader with a read failure injected at byte 0 or 3 and a malformed file: 54 runs, 5 leaking, all on ICUTokenizerFactory rulefiles read or decode failures; the other configurations and an ICU rule file that does not compile closed every stream. The hunt unit then wrote a TLA+ model of the load's resource lifecycle (TLC: 14 traces break the release invariant, all at the read step; the fixed variant holds) and ran model-based fault injection on the real jar (157 checks, 156 fault points and a fault-free baseline: 154 leak, 0 mismatches with the model, 0 leaks with the fix), and reduced it to a public-API JUnit test.

Area
analysis / ICU (ICUTokenizerFactory per-script rule files: rulefiles, parseRules)
Priority

Impact class
minor
Impact note
Only applications that opt in to custom per-script ICU rule files (the rulefiles argument of ICUTokenizerFactory, analysis-icu module, directly or through CustomAnalyzer 'icu') are hit, and only when a rule file cannot be read to the end at analyzer setup, because it is not valid UTF-8 (for example saved as ISO-8859-1 with a non-ASCII character in a comment) or because its stream throws an IOException; inform() then fails loudly with that exception and one InputStream (with FilesystemResourceLoader, one file descriptor) stays open until it is garbage collected, so an application that keeps retrying a bad configuration accumulates them; tokens and index contents are unaffected, a rule file that decodes but does not compile is not affected, no scale is needed, and it is the same with -ea and -da in every release from 4.1.0 to 10.6.0 [exec].
Summary
You configure ICUTokenizerFactory with rulefiles="Latn:latin-rules.rbbi" and the rule file cannot be read to the end, because it is not valid UTF-8 (for example saved as ISO-8859-1 with an accented letter in a comment) or because reading it throws an IOException; you expect inform() to fail with that exception and to close the stream it opened, as it does after a successful read and as the other Lucene analysis factories do. Instead parseRules calls reader.close() only after its read loop has finished normally, so the exception skips the close and the InputStream returned by the ResourceLoader stays open: a tracking loader still holds it after inform() threw, and with a real file read through FilesystemResourceLoader the test framework's LeakFS reports 'file handle leaks: [InputStream(.../latin-rules.rbbi)]'. The descriptor is released only when the stream is garbage collected; a rule file that decodes but does not compile is closed before compiling and does not leak.
