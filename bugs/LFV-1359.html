QueryTimeListener.timingMatcher never finishes the matcher it wraps, so around ParallelMatcher or PartitionMatcher every Monitor.match returns no matches

Wrapping PartitionMatcher or ParallelMatcher in QueryTimeListener.timingMatcher makes every Monitor.match return 0 matches, with no exception and none of the errors from running the queries: the wrapper never calls the inner matcher's finish(), the only place those two collect their matches. Every lucene-monitor release since 8.2.0; the reverse order works.

The finding in 30 seconds

#

Two matchers collect their matches only in the finish step, and the timing wrapper skips that step for the matcher it wraps.

Background: matchers in the monitor module

#
  1. Monitor.match creates one CandidateMatcher from the MatcherFactory you pass, hands it every registered query that may match (matchQuery), then calls its finish() to collect the matches and errors.
  2. finish() first runs the matcher's doFinish() hook, "called when all monitoring of a batch of documents is complete", then returns the matcher's own match lists and errors.
  3. PartitionMatcher and ParallelMatcher wrap another factory to match on several threads: their matchQuery only buffers or queues the query for worker threads, and the matches and errors reach them only in their doFinish().
  4. QueryTimeListener.timingMatcher(factory, listener) wraps a factory and reports how long each matchQuery call took.

The finding, step by step

#
  1. Register one query, q = f:a, in a Monitor. Match a document whose field f is "a" with timingMatcher(PartitionMatcher.factory(executor, SIMPLE_MATCHER, 1), listener), to log how long each query takes.
  2. You expect 1 match, as PartitionMatcher.factory(...) alone returns, plus a timing for q.
  3. Instead getMatchCount() is 0, with no errors and no exception; the listener is still called. With ParallelMatcher in place of PartitionMatcher it is 0 too.
  4. Why: these two matchers only buffer or queue each query in matchQuery and collect the matches in their finish step. The timing wrapper forwards matchQuery, but at the end it only copies the inner matcher's match list, still empty, and never calls the inner finish().
  5. The reverse order, PartitionMatcher.factory(executor, timingMatcher(SIMPLE_MATCHER, listener), 1), returns the match, and so does timingMatcher around a plain matcher.

Who is affected

#

lucene-monitor applications that time queries by wrapping ParallelMatcher.factory(...) or PartitionMatcher.factory(...) in timingMatcher, or a custom matcher that works in doFinish. Every call silently returns no matches and none of the errors from running the queries; with ParallelMatcher, the workers are never told to stop. Opt-in and rare; the reverse order works.

Mechanism, terms and numbers651 words

QueryTimeListener.timingMatcher(factory, listener) wraps a matcher factory to log how long each query takes. The matcher it returns forwards every matchQuery call to the wrapped matcher and times it, but its finish step only copies the wrapped matcher's match lists: it never calls the wrapped matcher's finish(), so that matcher's doFinish() never runs. PartitionMatcher and ParallelMatcher only buffer or queue each query in matchQuery and gather matches and errors only in doFinish() (PartitionMatcher also runs the queries there). So timingMatcher(PartitionMatcher.factory(...)) and timingMatcher(ParallelMatcher.factory(...)) make every Monitor.match return 0 matches, with no exception and none of the errors from running the queries, whatever the documents and queries; the listener is still called for each query the presearcher selects. With ParallelMatcher the workers also never get their stop marker: each either stays parked on the caller's executor until shutdownNow or later dies with AlreadyClosedException, depending on timing. It needs an opt-in, rare composition (the reverse order works and gives the meaningful timings), it is in every lucene-monitor release since 8.2.0, and the fix is a few lines: finish the wrapped matcher and carry over its matches and errors.

The code (main 5adff78bb168, lucene/monitor/src/java/org/apache/lucene/monitor/)

#
  • Monitor.java:218-226: match creates one matcher from the factory (:222), feeds each query the presearcher selects to its matchQuery and records an exception thrown there with reportError (StandardQueryCollector, :294-303), then returns matcher.finish(buildTime, queryCount) (:225). The in-memory document batch is closed when match returns (:220).
  • CandidateMatcher.java:105-115: finish calls doFinish(), then builds the result from this matcher's own match lists and error map. :117-118: doFinish() is "Called when all monitoring of a batch of documents is complete". :120-124: copyMatches(other) replaces this matcher's match lists with the other's and copies no errors.
  • QueryTimeListener.java:38-60, the wrapper: it creates the inner matcher from the wrapped factory (:39); matchQuery times and forwards (:42-48); resolve forwards (:50-53); doFinish is copyMatches(matcher) only (:55-58). Nothing calls matcher.finish(...).
  • PartitionMatcher.java:71-73: matchQuery only adds the query to a task list. :81-102: doFinish partitions the tasks, runs them on the executor and adds the matches; worker errors go to the PartitionMatcher's own reportError while it runs (:120).
  • ParallelMatcher.java:69-72: worker tasks are submitted in the constructor. :77-84: matchQuery only puts the query on a queue. :92-113: doFinish puts one END marker per worker and gathers the workers' matches and errors. :127: each worker loops on queue.take() until END.

Under the wrapper the inner match lists are still empty when they are copied, and the inner errors are never gathered. For a leaf matcher such as SIMPLE_MATCHER the work happens in matchQuery, so copying the lists is enough; that is the only case the upstream tests cover.

Side effect with ParallelMatcher

#

The workers never receive END, which only the skipped doFinish() sends (ParallelMatcher.java:94-96). So each worker either stays parked on queue.take(), holding a thread of the caller's executor until shutdownNow, or later takes a query still on the queue, runs it against the batch Monitor.match has already closed (Monitor.java:220) and dies with AlreadyClosedException. Which one happens depends on timing: in probes on main, with SIMPLE_MATCHER the workers stayed parked after a one-document match (10 of 10 runs) and died after a 7-document match, while with the scoring, explaining and highlighting matchers a worker died even after a one-document match (10 of 10 runs each).

Exposure and likelihood176 words
  • Who. lucene-monitor applications that time queries with QueryTimeListener.timingMatcher and put it around ParallelMatcher.factory(...) or PartitionMatcher.factory(...). The same applies to any user-written composite matcher that defers its work to doFinish(), a pattern the module's author supported by making finish() public for composite matchers (#13109, #13632).
  • Default vs opt-in. Opt-in: the monitor module and two optional wrappers. The wrong order compiles without a warning: both factories return a plain MatcherFactory<T> (ParallelMatcher.java:165-168, PartitionMatcher.java:145-148), which timingMatcher accepts.
  • Scale. None: one query, one one-term document.
  • Effect. Total and silent for that composition: every Monitor.match returns 0 matches, no exception and none of the errors from running the queries, assertions on and off. The listener still gets timings, so the application sees "queries ran, nothing matched". With ParallelMatcher, the workers are never told to stop: each stays parked on the caller's executor until shutdownNow, or later dies with AlreadyClosedException.
  • Likelihood. Rare: no caller of timingMatcher outside Lucene's own tests and copies of them was found, and losing every match shows at the first test.

Why it looks unintended

#
  • timingMatcher takes "a matcher factory to use for the actual matching", with no restriction; both factories compile into it.
  • It skips the documented doFinish() step of the matcher it owns; ParallelMatcher itself finishes its sub-matchers and re-adds their results.
  • The module's author wrote on #13109 that composite matchers need to call matchQuery(), reportError() and finish().
The full argument202 words
  • The contract has no restriction. QueryTimeListener.java:30-35: "A wrapping matcher factory to log query times to a QueryTimeListener", @param factory "a matcher factory to use for the actual matching". Nothing in MatcherFactory, Monitor.match or the package docs limits it to leaf factories.
  • The documented lifecycle. doFinish() is "Called when all monitoring of a batch of documents is complete" (CandidateMatcher.java:117-118), and both built-in concurrent matchers rely on it. ParallelMatcher.doFinish calls finish(0, 0) on each worker matcher and re-adds its matches and errors (ParallelMatcher.java:98-108).
  • The author's statement. On #13109 (2024-07-29) Alan Woodward (romseygeek) wrote: "Given that composite matchers need to call those methods for CandidateMatcher to be useful, I think the simplest way forward here is to make matchQuery(), reportError() and finish() public." That led to #13632, which made finish() public.
  • No test pins the current behaviour. The only upstream use of timingMatcher is TestTermPresearcher.java:60, around SIMPLE_MATCHER, whose doFinish is empty; it passes with the fix. No CHANGES or MIGRATE entry or review comment discusses composition order.
  • History. The wrapper came with the module (LUCENE-8766, 2019) with doFinish() { copyMatches(matcher); }, and ParallelMatcher and PartitionMatcher already gathered their results in doFinish() in the same commit.
The devil's-advocate check171 words

The strongest case for "intended", made by an intended-behaviour check and by an independent reviewer from another model family (OpenAI GPT-5.6), all rating it weak (the same reviewer family rated it moderate in a later fact check of this doc): the package docs present the concurrent matchers as the outer wrappers ("Matchers can be wrapped in PartitionMatcher or ParallelMatcher to increase performance in low-concurrency systems", package-info.java:50-51); Partition/Parallel(timing(leaf)) works; and timing taken outside an asynchronous matcher only measures enqueue or buffering time, so the failing order is not useful anyway.

Why it fails: that is about usefulness, not a documented precondition. The package docs do not forbid the other order, the API accepts it, and less useful timings do not justify silently dropping every match and error. A maintainer may prefer to document the order, or to reject it with an exception; the wrapper should still not lose results silently. Not claimed: that the outer timings become meaningful with the fix (they still measure enqueue time). Verdict: a real Low bug.

Suggested fix

#

Recommended A. Finish the wrapped matcher and carry over its matches and errors (validated)

In the wrapper's doFinish(), call the inner matcher's finish(0, 0) and re-add its matches and errors, as ParallelMatcher does for its workers. The repro passes with assertions on and off, the whole lucene/monitor module passes (182 tests, 0 failures, 1 skipped), and the formatter check is clean.

         @Override
         protected void doFinish() {
-          copyMatches(matcher);
+          MultiMatchingQueries<T> results = matcher.finish(0, 0);
+          for (int doc = 0; doc < results.getBatchSize(); doc++) {
+            for (T match : results.getMatches(doc)) {
+              addMatch(match, doc);
+            }
+          }
+          for (Map.Entry<String, Exception> error : results.getErrors().entrySet()) {
+            reportError(error.getKey(), error.getValue());
+          }
         }

Trade-offs

The same pattern ParallelMatcher.doFinish uses for its workers (ParallelMatcher.java:98-108). For the built-in leaf matchers the result is the same (empty doFinish, the same matches re-added); a wrapped matcher whose finish() throws now makes the outer finish() throw, where today the call is skipped; for the concurrent matchers it restores matches and errors and also sends END to the ParallelMatcher workers. Around an asynchronous matcher the timings still measure only enqueue time; a javadoc sentence recommending Partition/ParallelMatcher.factory(executor, timingMatcher(leaf, listener), n) for per-query times would complement it.

One seed, no nightly tests; not the full test matrix.
  • :lucene:monitor:checkGoogleJavaFormat passes with the fix and the repro test in place.

B. Document the order only

#

Say in the timingMatcher javadoc that it must wrap a leaf factory, and that ParallelMatcher / PartitionMatcher should wrap it.

Trade-offs

No code change, but the wrong order still compiles and silently returns nothing, and user-written composite matchers stay exposed. Not run.

C. Workaround for users (no Lucene change)

#

Use the reverse order, PartitionMatcher.factory(executor, timingMatcher(leaf, listener), n) or the ParallelMatcher equivalent.

Trade-offs

Returned the same matches as the leaf alone in every tested composition and times each query where it actually runs, but every user has to know about it. Checked in the differential check (Partition(timing(F)), Parallel(timing(F)): no mismatch) and by a cross-model reviewer's Partition(timing(SIMPLE)) test (passes).

Downstream note

#

A product that raises alerts from monitor matches would get none with this composition, but the trigger is the application's own code, never a document or query.

How it was found

#

A semi-formal proof-obligation audit of the monitor's matcher-composition contracts: timingMatcher must report what the factory it wraps reports, plus timings. Reading the wrapper's doFinish() showed it never finishes its delegate; a public-API probe and a differential check of 7 compositions over 4 leaf matchers witnessed it.

The method in full139 words

The obligation: for any factory F, timingMatcher(F, listener) returns the same matches and errors as F alone and calls the listener once per query run. The wrapper meets it only if F's matcher has recorded its matches by the end of matchQuery. A public-API probe on main showed the loss for both concurrent matchers; a bounded differential check then compared 7 compositions (timing(F), Partition(F), Parallel(F), the two reverse orders and the two outer-timing orders) with F alone over 4 leaf matchers and 8 document batches (the 7 non-empty subsets of the terms {a, b, c} one at a time, and one 7-document batch), plus an error leg: (4 x 8 + 1) x 7 = 231 comparisons, 66 mismatches, all and only the two outer-timing orders, 0 with the fix. The one-method JUnit test is the reduced witness.
