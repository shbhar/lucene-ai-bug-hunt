An OutOfMemoryError while an NRT open or commit freezes buffered deletes is replaced by IllegalStateException: IndexWriter stays open and its next commit drops those deletes and updates

If an OutOfMemoryError strikes while an NRT open or commit() packs the buffered deletes and doc-values updates, a cleanup step replaces it with an ordinary IllegalStateException: IndexWriter stays open instead of closing itself, and its next commit silently leaves those acknowledged changes out. Every release since 8.2.0 has it.

The finding in 30 seconds

#

During an NRT open or commit with no buffered documents, IndexWriter packs the buffered deletes and doc-values updates of the old delete queue into a frozen packet. If building that packet throws, a finally block's close() of the old queue throws a different exception, hides the Error and leaves the writer open without those changes.

How a commit or NRT open handles buffered deletes, in one minute

#
  1. deleteDocuments and update*DocValue calls do not touch the index at once: they go into the writer's current delete queue and return a sequence number.
  2. A commit or NRT open runs a full flush. It swaps in a fresh delete queue for new calls and flushes the buffered documents. When there are none, it packs the old queue's buffered changes into a frozen packet ("naked" deletes) that is then applied to the index.
  3. After that the old queue must be empty, and the flush closes it. close() refuses to close a queue that still has changes.

The finding, step by step

#
  1. Commit id:1 (dv=1) and id:2 (dv=2). Then call deleteDocuments(id:1) and updateNumericDocValue(id:2, "dv", 22): both return sequence numbers and wait in the writer's delete buffer.
  2. Open an NRT reader with DirectoryReader.open(writer). No documents are buffered, so the open only packs those two changes into a frozen packet, and an OutOfMemoryError strikes while it builds that packet.
  3. You expect what the IndexWriter javadoc promises: "if you hit an Error ... IndexWriter will close itself". The caller sees the Error, the writer is closed, and the last commit stands.
  4. Instead a finally block closes the old delete queue, finds the two changes still in it and throws IllegalStateException: Can't close queue unless all changes are applied, which replaces the Error. That exception is not tragic, so the writer stays open.
  5. Nothing applies the old queue's changes afterwards: the next commit() returns -1 ("no pending changes") and the index still has id:1 and dv(id:2)=2, with no error. With assertions on, an AssertionError replaces the Error instead and closes the writer.

Who is affected

#

Default configuration, assertions off: applications that open NRT readers or commit while only deletes or doc-values updates are buffered, and hit an OutOfMemoryError while those are packed. They get a plain IllegalStateException, the writer stays open with no tragic exception, and if they carry on, the next commit silently drops the acknowledged changes. Rare.

Mechanism, terms and numbers707 words

A commit, an NRT open or flush() runs DocumentsWriter.flushAllThreads. It swaps in a fresh delete queue (DocumentsWriter.java:680) and, when no documents were flushed but the old queue holds buffered deletes or doc-values updates, freezes them into a packet (:691-698). The freeze builds new FrozenBufferedUpdates(...) before it clears the buffer (DocumentsWriterDeleteQueue.java:270-272), so an OutOfMemoryError in that constructor, which allocates in proportion to the buffered changes, leaves the old queue with its changes. The finally then calls flushingDeleteQueue.close() unconditionally (DocumentsWriter.java:704-709), and close() throws IllegalStateException("Can't close queue unless all changes are applied") (DocumentsWriterDeleteQueue.java:320-321), which replaces the Error with no cause and nothing suppressed. IndexWriter.getReader and prepareCommitInternal treat only an Error as tragic (IndexWriter.java:711-713, :3879-3881), so with assertions off (production) the writer stays open, nothing applies the old queue's changes afterwards, and the next commit() returns -1 while the acknowledged delete and update are missing. With assertions on, finishFullFlush's assertion (DocumentsWriter.java:733) throws an AssertionError instead, which since 10.0.0 closes the writer. The class javadoc promises that an Error closes the writer (IndexWriter.java:162-165). Introduced in 8.2.0 by LUCENE-8813; present through 10.6.0 and on main. Reporting the original failure as tragic and closing the old queue without the check fixes it.

Step by step

#
  1. The packet's constructor allocates in proportion to the buffered changes: it encodes the delete terms into a PrefixCodedTerms, finishes each doc-values update buffer and copies the updates map (FrozenBufferedUpdates.java:89-106). An OutOfMemoryError there skips globalBufferedUpdates.clear() (DocumentsWriterDeleteQueue.java:272); DocumentsWriterFlushQueue.addTicket undoes its ticket count and rethrows the original (:38-52).
  2. The finally of flushAllThreads closes the old queue unconditionally (DocumentsWriter.java:704-709). It runs after any throwable from the try body (:687-703), not only from the constructor; by reading, a failure just before it, in globalSlice.apply (DocumentsWriterDeleteQueue.java:264-267), would also leave the changes in the old queue and end the same way. Only the constructor was exercised.
  3. close() finds the unfrozen changes and throws IllegalStateException (DocumentsWriterDeleteQueue.java:320-321). A finally that throws replaces the in-flight Error: the caller's exception has no cause and 0 suppressed.
  4. Assertions off: getReader (IndexWriter.java:669-677, :711-722) and prepareCommitInternal (:3867-3884) call the tragic-event handler only for an Error, so the writer stays open and getTragicException() is null. The old queue was swapped out at DocumentsWriter.java:680; later flushes and applyAllDeletes work on the new queue (this.deleteQueue, :169-180), and in the runs nothing applies the old queue's changes afterwards. The next commit() finds no pending change and returns -1.
  5. Assertions on: getReader's inner catch calls finishFullFlush(false) (IndexWriter.java:671), whose assert setFlushingDeleteQueue(null) (DocumentsWriter.java:733) fails because the old queue is still open ("Can not replace a full flush queue if the queue is not closed", :647-649). That AssertionError replaces the exception again; since #13277 (10.0.0) every Error is tragic, so the writer closes. On 8.2.0-9.12.3 it stayed open and every later full flush failed with the same AssertionError.

The numbers

#

Two committed documents, id:1 (dv=1) and id:2 (dv=2). Buffered: deleteDocuments(id:1) and updateNumericDocValue(id:2, "dv", 22). The NRT open's packet constructor throws one OutOfMemoryError. Assertions off: the caller gets the IllegalStateException, isOpen() is true, the next commit() returns -1, and the committed index has 1 hit for id:1 and dv(id:2)=2. Assertions on: the caller gets the AssertionError and isOpen() is false.

Exposure and likelihood405 words
  • Who is hit. Applications on the default configuration (assertions off in production) that open NRT readers from the writer (DirectoryReader.open(writer), openIfChanged(reader, writer)) or call commit() or flush() while only deletes or doc-values updates are buffered, for example a refresh after a burst of deleteDocuments or updateNumericDocValue calls with no new documents, and that hit an OutOfMemoryError while those changes are frozen.
  • What they see. An ordinary IllegalStateException with no cause, isOpen() true and getTragicException() null: nothing tells the application that an Error happened. An application that logs a failed refresh or commit and carries on gets a next commit() that returns -1 and leaves out the acknowledged delete and update: deleted documents come back, updates are reverted, with no error.
  • Default vs opt-in. No opt-in setting is needed. The JUnit repro uses new IndexWriterConfig() and sets only an InfoStream to place the Error (the test framework randomizes the codec, Asserting(Lucene104) in the logged run; the code involved does not depend on it). A supporting main() needs no custom InfoStream: the default IndexWriterConfig (16 MB buffer), codec and InfoStream, 60,000 buffered delete terms (6.7 MB, below the buffer), heap ballast and -Xmx128m fail 3 of 3 launches on main with assertions off (writer open, tragic=null, later commit -1, id:1 live, dv(id:2)=2). That main() is a controlled setup, not a natural workload: just before the NRT open it calls System.gc(), fills the heap with ballast (catching the OutOfMemoryErrors that raises) and frees about 2 MB of it again. A devil's-advocate probe with the default configuration and about 7 MB of buffered deletes under application heap pressure masked the Error and lost the delete in 4 of 8 launches (the other 4 had no OutOfMemoryError during the open).
  • Assertions on (Lucene's own test runs): the writer closes with an AssertionError, so nothing beyond the uncommitted state is lost, but the caller still never sees the OutOfMemoryError. That may be why the data-loss path has not shown up in Lucene's own test runs (a guess: we did not check whether any CI job runs with assertions off).
  • Scale. None: two documents, two buffered changes; only heap pressure while the frozen packet is built.
  • Likelihood: rare. It needs an OutOfMemoryError while the packet is built and, for the data loss, an application that catches the IllegalStateException and keeps the writer. No public report was found in the sources searched.

Why it looks unintended

#
  • The javadoc: "if you hit an Error ... IndexWriter will close itself"; it stays open. commit() returns -1 ("no pending changes") with two acknowledged changes pending.
  • The throwing close() came with a race fix (LUCENE-8813), not for a failed freeze.
  • #9259: "Never swallow Exceptions in IndexWriter and DocumentsWriter"; #13277: every Error is tragic.
The full argument234 words
  • The contract. IndexWriter class javadoc: "if you hit an Error, or disaster strikes during a checkpoint then IndexWriter will close itself. This is a defensive measure in case any internal state (buffered documents, deletions, reference counts) were corrupted. Any subsequent calls will throw an AlreadyClosedException" (IndexWriter.java:162-165). commit(): "If nothing was committed, because there were no pending changes, this returns -1" and "All sequence numbers <= this value will be reflected in the commit" (:4202-4209; the same for prepareCommit, :3730-3732).
  • The guard was not meant for this path. The throwing close() and its call in the finally came with LUCENE-8813 (#9857, "testIndexTooManyDocs fails"; PR apache/lucene-solr#688 by Simon Willnauer), which fixed a race in which deletes were applied from an already flushed queue. TestDocumentsWriterDeleteQueue.testClose (TestDocumentsWriterDeleteQueue.java:206) tests the guard on its own. Neither the PR nor the issue discusses a try block that has already failed, and no test asserts this IllegalStateException or AssertionError from this path.
  • Upstream's stated stance. #9259 (LUCENE-8212, 2018): "the original exception is rethrown and all other exceptions are added as suppressed". #13277 (2024, 10.0.0): every Error is tragic. #14731 (2025): a VirtualMachineError hidden because cleanup in a finally threw, at another site, was treated as a bug; thecoop's closing comment there (2025-07-10): "The pattern of using finally blocks to handle cleanup is one which we are slowly removing, and replacing with suppressed exceptions".
The devil's-advocate check237 words

The argument: after an OutOfMemoryError "nothing is guaranteed"; the repro injects it through InfoStream, which is @lucene.internal ("Debugging API", InfoStream.java:24-28), and the real-OutOfMemoryError main() is a controlled setup with heap ballast; the caller does get an exception; and the open issue #9738 (LUCENE-8692) records the view that after a non-tragic exception from getReader or commit the user can call rollback().

Why it fails: the class javadoc promises that an Error closes the writer, and #13277 made that hold for every Error. Lucene's own TestIndexWriterExceptions.testOutOfMemoryErrorCausesCloseToFail and testOutOfMemoryErrorRollback (TestIndexWriterExceptions.java:1111, :1150) inject OutOfMemoryError through InfoStream.message the same way, and a real OutOfMemoryError with the default InfoStream reproduces it. The rollback stance covers the data-loss half on its own: in #9738 Simon Willnauer wrote that getReader(), prepareCommitInternal(), doFlush() and similar methods "might cause documents go missing etc. but we treated them not as fatal or tragic events since a user could always call rollback()" (2019-03-06) and that "if somebody continues after a failed commit / prepareCommit / reopen they will end up with inconsistency and / or dataloss" (2019-03-11). It does not cover this bug: the original failure is an Error, which the javadoc says closes the writer, and Lucene's own finally replaces it with an IllegalStateException with no cause, so the application cannot tell that an Error happened. Maintainers may still prefer another fix shape (B or C) to A.

Suggested fix

#

Recommended A: a failed full flush that leaves unfrozen changes in the old queue is tragic; close that queue without the check

In flushAllThreads, remember a failure; in the finally, if the old queue still has unfrozen changes, report the original failure as tragic and close that queue without the check, so the Error propagates and the writer closes itself. Validated: the repro passes with assertions on and off; the org.apache.lucene.index tests (1398) and :lucene:core:check -x test pass.

} catch (Throwable t) {
  failure = t;
  throw t;
} finally {
  if (failure != null && flushingDeleteQueue.anyChanges()) {
    flushNotifications.onTragicEvent(failure, "flushAllThreads");
    flushingDeleteQueue.closeDiscardingChanges();
  } else {
    flushingDeleteQueue.close();

All options and trade-offs3 options · 604 words

Validated with gradle in a clean scratch worktree of 5adff78bb168 (OpenJDK 25.0.3, seed DEADBEEF, 2026-11-03): the repro fails stock with assertions on and off and passes with fix A, on and off. With fix A and the repro in place, :lucene:core:test --tests 'org.apache.lucene.index.*' passes (1398 tests, 0 failures, 56 skipped) and so does :lucene:core:check -x test. A real OutOfMemoryError with the default configuration, fix A in place: 3 of 3 launches pass (the NRT open throws java.lang.OutOfMemoryError: Java heap space and the writer is closed with it as the tragic exception).

Why fix A works: the original Throwable remains the thrown exception (onTragicEvent can at most add a suppressed exception to it if its own logging fails, IndexWriter.java:6074-6082); onTragicEvent only records it (:6067-6083, callable "from any location without respecting any lock order"), and the existing maybeCloseOnTragicEvent calls in getReader (:719) and prepareCommitInternal (:3883) then close the writer, so the last commit stands. The old queue is marked closed, so finishFullFlush's assertion (DocumentsWriter.java:733) no longer fires. It also closes the writer for a RuntimeException in the same window, which today leaves the writer open and drops the changes, for example the IllegalStateException("buffer was finished already") that FieldUpdatesBuffer.finish() throws (FieldUpdatesBuffer.java:219-223) when an earlier freeze failed after finishing a buffer (the message in the related downstream report, which came from another flush path that A does not change). No stress or performance run was made.

A: a failed full flush that leaves unfrozen changes in the old queue is tragic; close that queue without the check (validated by the checks) (recommended)

#

In DocumentsWriter.flushAllThreads, catch and remember the failure (failure = t; throw t;). In the finally, when failure != null && flushingDeleteQueue.anyChanges(), call flushNotifications.onTragicEvent(failure, "flushAllThreads") and the new package-private DocumentsWriterDeleteQueue.closeDiscardingChanges() (marks the queue closed and bumps nextSeqNo like close(), without the anyChanges() check); otherwise call close() as today. 26 lines added and 3 removed, in DocumentsWriter.java and DocumentsWriterDeleteQueue.java.

Trade-offs

A failure in this window now closes the writer instead of letting it continue without the changes; those changes were already lost, the close makes the loss visible. One more method on the delete queue. Reasoning from the source plus the test runs; no stress or performance run.

What the checks validated

Gradle, scratch worktree of 5adff78bb168: the repro passes with assertions on and off; org.apache.lucene.index.* (1398 tests, 0 failures) and :lucene:core:check -x test pass; the real-OutOfMemoryError main() passes 3 of 3 launches.

B: keep the original failure and add close()'s exception as suppressed

#

The #9259 pattern: with assertions off the Error then reaches IndexWriter and closes the writer.

Trade-offs

Not sufficient (by reading, not run): the old queue stays open, so with assertions on finishFullFlush's assertion (DocumentsWriter.java:647-649, :733) still replaces the Error with an AssertionError; and a RuntimeException in the window still leaves the writer open without the changes.

C: make the freeze failure-atomic and keep the unfrozen changes

#

Carry the changes to the new queue or re-buffer them, so that a non-Error failure could leave the writer open with nothing lost.

Trade-offs

Largest change; needs care with sequence-number order (the new queue hands out higher numbers); not run. It is also what the related downstream report would need (later flushes failing with "buffer was finished already" after a failed freeze on another flush path), which A does not change.

Downstream note

#

Products that catch a failed refresh or commit and keep the same IndexWriter can silently lose acknowledged deletes and updates after an OutOfMemoryError; getTragicException() stays null, so they cannot tell.

How it was found

#

A bounded-exhaustive sweep threw one OutOfMemoryError at each of 850 points (106 code sites) reached through the writer's InfoStream and checked the final index against a model of ids and doc values. Two points in an NRT open left the writer open, the Error replaced and the delete and update missing. A one-test JUnit and a real OutOfMemoryError witnessed it.

The method in full245 words

Method: semi-formal (a bounded-exhaustive single-Error injection sweep on the real jar, checked against an independent model, then witnessed by JUnit and real-OutOfMemoryError repros), on main a9779ef3c193, 2026-10-28.

  • The sweep ran a fixed indexing script (SerialMergeScheduler) and, in each run, threw one OutOfMemoryError at one of 850 points (InfoStream message calls; 106 distinct code sites in IndexWriter and the classes it uses) reached through the writer's InfoStream callback. Each run was classified by the writer's state after the failure (closed with a tragic exception, or open) and by comparing the final index with an independent model of ids and doc values.
  • The injections at DocumentsWriter.flushAllThreads (the "flush naked frozen global deletes" message) and inside FrozenBufferedUpdates.<init> during the NRT open came out as "writer open, no tragedy", with the thrown exception replaced by the IllegalStateException and the acknowledged delete and doc-values update missing from the final index; with assertions on, an AssertionError replaced the Error and closed the writer.
  • A static scan of error handlers had listed this finally as a rethrowing site and not flagged it: the masking comes from a throw inside the finally, which only the dynamic sweep exposed.
  • The finding was reduced to a JUnit test (public API plus the InfoStream hook) and witnessed with a real OutOfMemoryError and the default InfoStream; a JVM exception log showed the OutOfMemoryError raised under FrozenBufferedUpdates.<init>. This doc's one-test repro was written from that JUnit on main 5adff78bb168.

LFV-843, snapshot of 2026-11-08

Registry title
An Error (in practice an OutOfMemoryError) while an NRT reopen or commit that has no buffered documents freezes the buffered deletes and doc-values updates is replaced by IllegalStateException("Can't close queue unless all changes are applied") from the finally of DocumentsWriter.flushAllThreads, so IndexWriter stays open instead of closing itself and its next commit silently drops those acknowledged deletes and updates (with -ea an AssertionError replaces the Error; every release since 8.2.0)
Area
index / IndexWriter full flush (DocumentsWriter.flushAllThreads naked-delete freeze, DocumentsWriterDeleteQueue.close)
Priority
Medium, rank 27: An OutOfMemoryError while freezing buffered deletes turns into a plain IllegalStateException, so the default IndexWriter stays open and silently drops acknowledged deletes and doc-values updates at the next commit in every release since 8.2.0, but it needs heap exhaustion at one allocation.
Impact class
data corruption
Impact note
Hits applications on the default configuration (production runs without -ea) whose NRT reopen or commit() has buffered deletes or doc-values updates but no buffered documents, when an OutOfMemoryError is raised while those changes are frozen into a packet: the caller gets an ordinary IllegalStateException with no cause and nothing suppressed, the writer stays open with no tragic exception, and if the application catches the exception and keeps using the writer, the next commit() returns -1 ('no pending changes') while the acknowledged deletes are undone and the updates reverted, with no error [exec]; with -ea an AssertionError replaces the Error and, since 10.0.0, closes the writer, so only the uncommitted state is lost there [exec]; no scale is needed, only heap pressure at that one allocation.
Summary
You commit documents id:1 and id:2, call deleteDocuments(id:1) and updateNumericDocValue(id:2, dv, 22) (both return sequence numbers), and then open an NRT reader from the writer or call commit() with no documents buffered, and an OutOfMemoryError strikes while the writer freezes those two buffered changes; the IndexWriter javadoc says the writer closes itself after an Error, so you expect to see the Error and a closed writer (or, if the writer stays usable, a later commit that contains both changes). Instead the finally of DocumentsWriter.flushAllThreads closes the delete queue that the flush has already swapped out, and its close() throws IllegalStateException("Can't close queue unless all changes are applied"), which replaces the Error; IndexWriter does not treat that as tragic and stays open, the old queue with both changes is abandoned, and the next commit() returns -1 with id:1 still live and dv(id:2) still 2. With -ea an AssertionError ('Can not replace a full flush queue if the queue is not closed') replaces the Error instead, and since 10.0.0 it closes the writer.
