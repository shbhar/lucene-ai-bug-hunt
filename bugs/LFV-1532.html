The finding in 30 seconds

#

Lucene damages nothing: it misses existing damage. Three opt-ins must meet: your own merge policy with the experimental partitioned merge, a wrapper that hands out, through getters marked internal, files of another index or segment, and damage already in such a file. The limits and the two readings, one by one

#
  1. Lucene damages nothing. The file is damaged before the merge (in the test, by the test: one flipped bit). What is missing is the detection of that damage: the merge copies the wrong value it reads into new segments, whose own checksums are valid. A partitioned merge of ordinary readers does checksum its inputs.
  2. Three opt-ins must come together. First, a merge policy of your own whose OneMerge returns isPartitioned() true: the partitioned merge is tagged @lucene.experimental, and no merge policy in Lucene's main sources uses it (the tests of the feature bring their own). Second, a wrapForMerge reader that is a hand-written FilterCodecReader and hands out, from a producer getter, a producer over files that are not the wrapped segment's own (in the runs of this page: the doc values of another index): these getters are tagged "Expert" and @lucene.internal. Third, damage that is already there in the data bytes of one of those files.
  3. No release has the code. It came with #16571 on 2026-11-12, to main (12.0.0-SNAPSHOT) and to branch_11x (11.0.0-SNAPSHOT), both unreleased. 10.6.0 does not have the partitioned merge.
  4. One reading: not a bug. One executed second opinion reproduced the behaviour with a test of its own and still called it not a bug: the getters are internal, the feature is experimental, wrapForMerge promises nothing about another index's files, FilterCodecReader's class javadoc calls the wrapped reader "its basic source of data", and its public checkIntegrity() has forwarded to the wrapped reader since 2017. These premises are true.
  5. The other reading: a small defect. The javadoc of the new verified flag says it "can never suppress a check that has not happened", and on this path it does. The finding, step by step

#
  1. Index A holds 256 documents with one numeric doc-values field: document i holds i. Index B is a copy of A in which one bit of the doc-values data is flipped (bit 0 of byte 164 of the 329-byte .dvd file), as a storage fault would do.
  2. Your merge policy merges A's segment with a OneMerge that is partitioned (isPartitioned() true, two outputs) and whose wrapForMerge returns a FilterCodecReader that hands out B's doc values from getDocValuesReader(). You call forceMerge(1).
  3. You expect CorruptIndexException. The ordinary merge of the same readers throws it, on these builds and on 10.6.0: the writer closes itself and the index stays as it was.
  4. You get a merge that completes: 2 new segments, 256 documents, 1 wrong value (document 107 holds 106), and CheckIndex reports the merged index clean.
  5. Why: a partitioned merge checksums its inputs once, up front, by asking each wrapped reader. FilterCodecReader passes that question to the segment it wraps, so A's files are read end to end and the data of B's file is not. The merge is then marked verified, and from then on the check of each format of the default codec reads only a file's footer.

Who is affected

#

Only an application that combines a partitioned-merge policy of its own (experimental; no merge policy in Lucene's main sources uses it), a hand-written FilterCodecReader over files of another index or segment, and damage already in such a file. Not the default, in no release. In the run 1 of 256 merged values was wrong. A check inside wrapForMerge protects today.

Mechanism, terms and numbers1,699 words

Small and disputed. Lucene damages nothing here. The file is damaged before the merge, and what is missing is the detection of that damage. It takes three opt-ins at once: a merge policy of the application's own whose OneMerge returns isPartitioned() true (the partitioned merge is tagged @lucene.experimental, came with #16571, and no merge policy in Lucene's main sources uses it); a wrapForMerge reader that is a hand-written FilterCodecReader and hands out, from a producer getter, a producer over files that are not the wrapped segment's own, in the runs of this page the doc values of another index (the getters are tagged "Expert" and @lucene.internal); and damage that is already there in the data bytes of one of those files. No release has the code: only main (12.0.0-SNAPSHOT) and branch_11x (11.0.0-SNAPSHOT), both unreleased.

The dispute. One executed second opinion reproduced the behaviour with a test of its own, agreed with the cause and with the repair shape, and still called it not a bug: the getters are internal, the feature is experimental, wrapForMerge promises nothing about another index's files, FilterCodecReader's class javadoc calls the wrapped reader "its basic source of data", and its public checkIntegrity() has forwarded to the wrapped reader since 2017. Those premises are true. The other checks called it a real, small defect. Whether such a wrapper is supported use is a maintainer's call that nobody has made in public.

What happens. A partitioned merge verifies its inputs once, before any output is written: IndexWriter.multiOutputMergeMiddle calls checkIntegrity(merge) on each reader that wrapForMerge returned and then marks the merge's inputs verified (IndexWriter.java:5858, :5862, lines at main 596ef11ddf96). FilterCodecReader overrides that package-private method and forwards to the reader it wraps (FilterCodecReader.java:133-136), so the files that are read end to end are those of the wrapped segment. A producer that a subclass hands out from its own getter is not asked by this up-front check. It is asked later, when its format's merge begins, and by then the flag is set: the check of each format of the default codec then reads only the footer of a file (CodecUtil.java:633-641). In the run with 256 documents and one flipped bit in the doc-values data of the second index, the partitioned merge completed, 1 of 256 values in the merged index was wrong (document 107 holds 106) and CheckIndex reported the merged index clean. The ordinary merge of the same readers throws CorruptIndexException ("checksum failed (hardware problem?)"), which closes the writer and leaves the index as it was, on the same builds and on 10.6.0.

Why it is a finding all the same. The javadoc of the new verified flag says it is set "only after verifying all of them, so it can never suppress a check that has not happened" (MergePolicy.java:238-244; the javadoc of a package-private method, so the design's own rule and not a promise to users). On this path it suppresses the full read of a file whose data no check has read end to end. The same producer handed out by a direct CodecReader subclass is checksummed and refused: the two runs differ only in the wrapper's base class, which fits an oversight and does not prove one. And the cause is one forwarding override with a one-line repair shape (the override calls super.checkIntegrity(merge)): a shape that confirms the root, not a reviewed patch.

Runs. The one test fails 1 of 1 on main 596ef11ddf96 and on branch_11x 89e68e0f3a50 (commits of 2026-11-17), with assertions on and off, and passes with the one-line change. On the 10.6.0 release jars the test does not compile, because the partitioned merge does not exist there; the same test as an ordinary merge passes there. Only doc values were run for this page, with one flipped bit in the data bytes of the file.

Terms

#
  • Ordinary merge: when a format's merge begins, it calls checkIntegrity(merge) on each producer it was handed, which in the default codec reads the whole file and compares its checksum (DocValuesConsumer.java:136 for doc values; the other formats make the same call).
  • Partitioned merge: one merge that writes several segments, new with #16571 and tagged @lucene.experimental. A merge takes this path when its OneMerge.isPartitioned() returns true (IndexWriter.java:5983-5984). Each format's merge then runs once per output, so the full read of the inputs would repeat per output.
  • The verified flag: to avoid that, the partitioned merge checks its inputs once, up front, and sets OneMerge.inputsVerified (MergePolicy.java:220-244). CodecUtil.checksumEntireFile then reads only a file's footer for this merge (CodecUtil.java:633-641).
  • wrapForMerge: a hook of OneMerge, "Wrap a reader prior to merging in order to add/remove fields or documents." (MergePolicy.java:331-339). A wrapper is usually a FilterCodecReader: it leaves documents out by overriding getLiveDocs() and numDocs(), and it changes or adds field data by overriding the producer getters of CodecReader.
  • What opening an index reads: of a doc-values data file (.dvd) only the header and the footer; its small meta file (.dvm) is checksummed whole (Lucene90DocValuesProducer.java:103-151). The data between header and footer is read end to end only by a check.

The code (main 596ef11ddf96)

#

Step 1. multiOutputMergeMiddle wraps each input once, CodecReader wrapped = merge.wrapForMerge(reader); (IndexWriter.java:5826), under a comment that ends: "Verifying here instead leaves one check per input per merge, and does it before any output has written anything." (:5816-5821).

Step 2. It calls wrapped.checkIntegrity(merge); (:5858) and, after the loop, merge.markInputsVerified(); (:5862), under the comment "Only now, so that the checks just above are the ones that read the files."

Step 3. CodecReader.checkIntegrity(MergePolicy.OneMerge) (CodecReader.java:335-377, package-private) walks the seven getters of the reader it is called on and asks each producer; for doc values getDocValuesReader().checkIntegrity(merge) (:354-356).

Step 4. FilterCodecReader overrides it and forwards (FilterCodecReader.java:133-136):

@Override
void checkIntegrity(MergePolicy.OneMerge merge) throws IOException {
  in.checkIntegrity(merge);
}

So the walk of step 3 runs on the wrapped segment reader, over the segment's own producers. The producer that the subclass returns from getDocValuesReader() is not asked.

Step 5. When the doc-values merge begins, DocValuesConsumer.merge calls docValuesProducer.checkIntegrity(mergeState.oneMerge); (DocValuesConsumer.java:136) on the producer it was handed: in a partitioned merge the output's range view of the wrapper's producer, which forwards the call (DocRangeDocValuesProducer.java:252-255). That reaches CodecUtil.checksumEntireFile (CodecUtil.java:633-641):

if (merge != null && merge.areInputsVerified()) {
  // This merge read this file end to end once already, and a second pass over the same bytes
  // cannot find anything the first one missed. Reading the footer still catches a truncated
  // file. [...]
  return retrieveChecksum(input.clone());
}

The flag is set, so only the footer is read (in the run, bytes 313 to 328 of the 329-byte file, once per output). The flipped bit is in the data and the footer is intact, so the merge goes on.

Step 6. In an ordinary merge the flag is never set: it has one writer (IndexWriter.java:5862) and one reader (CodecUtil.java:635). The same call at DocValuesConsumer.java:136 reads the whole file and throws. A merge's exception is a tragic event of the writer (IndexWriter.java:5170-5175): the writer closes itself and the index stays at its last commit.

Why it looks unintended

#
  • The flag's javadoc: set "only after verifying all of them, so it can never suppress a check that has not happened". Here it does.
  • The same producer through a direct CodecReader subclass is checksummed and refused: the two runs differ only in the wrapper's base class.

The full argument602 words
  • The new code's own statements. They are the design's own rule (the javadoc of package-private methods and a code comment), not a guarantee given to users. markInputsVerified() (MergePolicy.java:238-244): "Records that every input of this merge has been verified. Only {@link IndexWriter} sets this, and only after verifying all of them, so it can never suppress a check that has not happened." The comment at CodecUtil.java:636: "This merge read this file end to end once already". CodecReader.checkIntegrity(OneMerge) (CodecReader.java:335-339): "Covers exactly what the formats verify for themselves when their merges begin"; what a format verifies is the producer of the reader that wrapForMerge returned, and FilterCodecReader's override asks the wrapped reader's producers instead.
  • Caller-facing texts. getDocRangePartitions (MergePolicy.java:370-372): "The inputs are verified once for the whole merge rather than once per output". The public javadoc of CodecUtil.checksumEntireFile(IndexInput, OneMerge) (CodecUtil.java:618-627) and of DocValuesProducer.checkIntegrity(OneMerge) (DocValuesProducer.java:86-95) name aborting as the effect of the merge argument; neither says that the check reads only the footer once the merge's flag is set.
  • Only the base class differs. The same second-index producer handed out by a direct CodecReader subclass is checksummed up front and refused (run on both builds). That difference fits an oversight in one override. It does not prove one: a rule that holds for FilterCodecReader alone would give the same two results.
  • The ordinary merge needs nothing from the wrapper's author. It refuses the file on main 596ef11ddf96, on branch_11x 89e68e0f3a50 and on the 10.6.0 release jars (run).
  • No hook on the reader. The reader-level method that the merge calls up front is package-private, and a wrapper's public checkIntegrity() is called 0 times by the partitioned and by the ordinary merge (run). What the author of a wrapper can do lies outside the reader: a check inside wrapForMerge, or a producer that reads its file in full whatever the merge says (run: the merge then throws). Both need the author to know that the up-front check does not reach the producers the wrapper hands out.
  • The override is forced, not chosen. Lucene's TestFilterCodecReader.testDeclaredMethodsOverridden requires FilterCodecReader to override every method that CodecReader declares, unless it is private, final or static. With the override deleted that test fails (run through Lucene's own build). A forwarding body is the usual choice for such an override.
  • What wrappers are for. FilterCodecReader's class javadoc: "A FilterCodecReader contains another CodecReader, which it uses as its basic source of data, possibly transforming the data along the way or providing additional functionality." (FilterCodecReader.java:31-32). The second half is what a wrapper over other files rests on; the first half is a point of the other reading. SlowCodecReaderWrapper's class javadoc sends merge wrappers to it: "Consider using {@link FilterCodecReader} instead." (SlowCodecReaderWrapper.java:37-40).
  • Nothing documents it. By the earlier reading of the thread of #16571 (12 conversation comments, 23 review comments, 17 reviews, 21 commit messages), it does not mention the flag, the override or the producers of a wrapForMerge reader. Its one sentence on verification is in the first commit's message: "Merge inputs are verified once for the whole merge rather than once per output, which otherwise repeats a full read of them per output." No test source at 596ef11ddf96 names the flag.

The first sentence of areInputsVerified() ("verified the checksums of every file of every input", MergePolicy.java:222-236) is not contradicted: "input" can be read as the input segment, whose own files were read whole. The devil's-advocate check404 words

The strongest case for "not a bug" is the reading of the second opinion that reproduced the behaviour and still rejected it:

  • the wrapper overrides and calls CodecReader.getDocValuesReader(), which is tagged "Expert" and @lucene.internal, as all seven producer getters are (CodecReader.java:38-85);
  • the partitioned merge is tagged @lucene.experimental (MergePolicy.java:399-413);
  • wrapForMerge promises nothing about files of another index;
  • FilterCodecReader's class javadoc calls the wrapped reader "its basic source of data" (FilterCodecReader.java:31-32), and forwarding checksums every file of the wrapped segment, also of a kind of data that a wrapper replaces or hides;
  • FilterCodecReader's public checkIntegrity() has forwarded to the wrapped reader since 2017 (LUCENE-7676, #8727; FilterCodecReader.java:128-131), and the new method is its analogue;
  • no merge policy in Lucene's main sources is affected, and an application can verify its own files;
  • Lucene's SECURITY.md says that the content of index files is "not defensively validated when read", and calls a change that "replaces a low-level failure with a clean CorruptIndexException on a broken index" welcome as long as it costs no performance. Read with that, a missed detection of a file that is already damaged is a matter of hardening.

Every one of these premises is true.

Why they do not settle it:

  1. The tags speak about stability. Overriding these getters is the only way a FilterCodecReader, a public class without a tag, changes or adds the data of a field that a merge reads (leaving documents out goes through getLiveDocs() and numDocs(), as Lucene's own wrapLiveDocs does).
  2. "The wrapper must verify its own files" is written nowhere. As a rule for wrappers in general one run speaks against it: the same producer through a direct CodecReader subclass is checksummed and refused. That run does not rule out a rule for FilterCodecReader alone.
