The bug in 30 seconds

#

XYShape stores a polygon as triangles, and a point query asks each stored triangle whether it contains the point. That test has a blind spot: the second corner of a clockwise triangle counts as outside. Lucene means to store only counter-clockwise triangles, but for XY it checks the winding on an integer encoding that can flip it, so its own corrective swap can leave a triangle clockwise as floats.

  1. You index the triangle (0,1) (1,2) (3,3) as an XYPolygon with XYShape.createIndexableFields (default codec) and run XYShape.newPointQuery with INTERSECTS at each of its three corners.
  2. You expect 1 hit at every corner, as at the other two corners and at every corner of the same triangle moved by (8, 8), which gives 1, 1, 1; LUCENE-8736 made shape relations include boundary points.
  3. You get 1, 0, 1: the corner (1,2) misses its own polygon, and DISJOINT at (1,2) returns it. A metre-like hexagon misses its corner (518885, 4395432) the same way.
  4. Why it is stored clockwise: Lucene makes triangles counter-clockwise but checks this on its integer encoding of the floats, where 0, 1, 2, 3 sit at 0, 254, 256, 257 (times 2^22). The tessellator hands over the triangle counter-clockwise as floats, but on that ruler it looks clockwise (-248), so Lucene swaps two corners: the stored triangle is counter-clockwise as ints (+248) and clockwise as floats (-1).
  5. Why the corner is lost: at the second corner two of the test's three orientation checks are 0, so the answer falls back to the triangle's own winding, and clockwise means outside. The first and third corners and every edge point still match.

Who is affected

#

Applications that index polygons with XYShape (projected or cartesian coordinates) using the default codec and run point queries at exact vertex coordinates, such as corners shared by neighbouring shapes. INTERSECTS silently misses the shape and DISJOINT returns it. In one synthetic random-polygon test, 0.07-0.3% of metre-like polygons and about 3% near the origin had such a corner.

Mechanism, terms and numbers1,005 words

An XYShape point query placed exactly on a polygon's corner can miss the polygon. Index the triangle (0,1) (1,2) (3,3) with XYShape.createIndexableFields and query each corner with XYShape.newPointQuery: INTERSECTS gives 1, 0, 1 hits and DISJOINT gives 0, 1, 0, while the same triangle moved by (8, 8) matches at all three corners. Two pieces combine. ShapeField.encodeTriangle makes stored triangles counter-clockwise, but it checks the winding on the encoded ints, and the XY encoding (floatToSortableInt) keeps the order of floats but not their spacing. So the tessellator's counter-clockwise triangle can look clockwise on the ints, and the swap meant to fix it leaves the stored triangle counter-clockwise as ints and clockwise as floats. The query tests the decoded floats with Component2D.pointInTriangle, which rejects the second corner of a clockwise triangle and accepts everything else. Every release from 8.5.0 to 10.5.2 and main is affected, with the default codec and no error. A one-function fix in pointInTriangle (accept when all three orientations are >= 0 or all <= 0) fixes it without reindexing.

Terms

#
  • Triangles: XYShape.createIndexableFields tessellates a polygon into triangles and stores each one with its three corners, called a, b and c in the code.
  • Winding: a triangle is counter-clockwise (CCW) when its signed area (the determinant) is positive, clockwise (CW) when it is negative. GeoUtils.orient(a, b, c) returns +1, -1 or 0.
  • The XY encoding: XY coordinates are floats and are stored as NumericUtils.floatToSortableInt(x). This keeps the order of floats and is exact, but it is not linear: within one power-of-two range it is a plain scaling, and from one power-of-two range to the next the scale halves or doubles.

Step 1: indexing checks the winding on the encoding, and its swap breaks the float winding

#

ShapeField.encodeTriangle takes the corners in the tessellator's order, rotates them so that the smallest x comes first (ShapeField.java:157-182 at a9779ef3c193), and then ("change orientation if CW", :214-228) swaps b and c when GeoUtils.orient of the encoded ints is -1. On the encoded ruler the values 0, 1, 2 and 3 sit at 0, 254, 256 and 257 (in units of 2^22): the encodings of 0 and 1 are 254 x 2^22 apart, those of 1 and 2 are 2^23 apart, and those of 2 and 3 are 2^22 apart. The tessellator hands over the triangle as (1,2) (0,1) (3,3); after the rotation it is a = (0,1), b = (3,3), c = (1,2).

corners a, b, cdeterminantwinding
handed over, after the rotation: floats(0,1) (3,3) (1,2)(3-0)(2-1) - (1-0)(3-1) = +1counter-clockwise
the same on the encoded ints (units of 2^22)(0,254) (257,257) (254,256)257 x 2 - 254 x 3 = -248clockwise: the swap fires
stored after the swap: encoded ints(0,254) (254,256) (257,257)254 x 3 - 257 x 2 = +248counter-clockwise
stored after the swap: floats, as the query decodes them(0,1) (1,2) (3,3)(1-0)(3-1) - (3-0)(2-1) = -1clockwise

The swap meant to normalise the winding is what makes the float triangle clockwise. On the lattice {0..5}^2 every one of the 6,768 tessellated triangles reaches encodeTriangle counter-clockwise as floats, and the 240 that end up stored clockwise as floats all got there through this swap. In metre-like data the same happens at 2^19 = 524,288 or 2^22 = 4,194,304: below 524,288 one unit holds 32 float steps, above it 16. The repro's hexagon has x from 517,494 to 539,509, and its triangle at the missed corner goes through the same swap.

Step 2: the query tests the decoded floats

#

XYShapeQuery decodes each stored triangle to floats and calls intersectsTriangle (XYShapeQuery.java:93-99); for a point this is Component2D.pointInTriangle (Point2D.java:83-95).

Step 3: the blind spot (Component2D.java:250-278)

#
int a = orient(x, y, aX, aY, bX, bY);
int b = orient(x, y, bX, bY, cX, cY);
if (a == 0 || b == 0 || a < 0 == b < 0) {
  int c = orient(x, y, cX, cY, aX, aY);
  return c == 0 || (c < 0 == (b < 0 || a < 0));
}
return false;

At p = corner b the point lies on both edges that meet there, so a == 0 and b == 0, and the method returns c >= 0, where c = orient(b, c, a) is the triangle's own winding: true for a counter-clockwise triangle, false for a clockwise one. At corners a and c two orientations are 0 as well and the method returns true for either winding; edge and interior points are accepted for either winding too. An exhaustive comparison on the stock jar over every triangle and point of the integer grid {-4..4}^2 (43,046,721 cases) found that the stock method and the winding-independent fix disagree in exactly the 247,824 cases where p is corner b of a clockwise triangle. At the level of signs the two differ only for (a, b, c) = (0, 0, -1) of the 27 sign triples; reading that as "corner b of a clockwise triangle" assumes exact orientations, which holds here (every product is a small exact integer) but not for GeoUtils.orient in general.

What the user sees

#
  • A polygon's corner is missed only if every stored triangle that touches it misses it: always for a lone triangle, and in the repro's hexagon too, where only one of its four stored triangles touches the missed corner.
  • INTERSECTS misses the document; DISJOINT (no triangle intersects) returns it. CONTAINS (Point2D.withinTriangle, same test) also answers differently per corner, but its correct boundary answer is debatable.
  • The experimental XYShapeDocValues.relate(Component2D) also decodes XY triangles to floats and calls intersectsTriangle (ShapeDocValues.java:919-934), so with a point component it likely misses the same corner (not executed); the fix covers it too.
  • LatLonShape is not affected in the scope checked: its decoding is a positive linear scaling of the encoded ints, so stored triangles decode with their encoded, counter-clockwise winding (0 of 281,203 grid triangles stored clockwise as decoded doubles).
Exposure and likelihood326 words
  • Who. Applications that index polygons with XYShape (building and floor plans, CAD drawings, game maps, projected GIS data in metres) and run XYShape.newPointQuery, or newGeometryQuery with an XYPoint, with INTERSECTS or DISJOINT at a coordinate that equals a polygon vertex exactly: corners shared by neighbouring shapes, a click snapped to a vertex, or a re-query with stored vertex coordinates.
  • Default configuration. Public, non-experimental API, no special setting. The codec does not matter (the triangle encoding is in the field's bytes, the test runs at query time): the repro (Lucene's randomized test configuration) fails under every randomized test codec it met, and the independent reproducer's JUnit and the diagram probe, both with a plain new IndexWriterConfig(), fail with the default codec (Lucene104 in the adjudication's run).
  • Silent. No exception and no assertion; the same with assertions off.
  • How often (the finder's random-polygon probe; not re-run by the verifiers): polygons with a missed corner were 0.30% (60 of 20,000 triangles) and 0.16% (32 of 19,562 hexagons) in projected-metre ranges, 0.07% (13 of 18,933) in a narrower metre window, 0.15% (29 of 18,937) around 1,000-1,900, and about 3% (590 of 19,878; 650 of 19,533) around the origin. With the fix, 0 (re-run for the hexagon range and the lattice triangles only). On the lattice {-2..2}^2, 8 of 2,148 triangles miss a corner. These rates come from one synthetic generator (random star-shaped polygons, fixed seed, checked on their stored triangles), not from real data: they show that the miss is not confined to toy coordinates, not how often real queries hit it.
  • Blast radius. A miss affects only the documents that hold a polygon with such a corner, and only point queries at exactly that corner; the index itself is not changed.
  • Not affected. LatLonShape (scope check); points indexed with XYPointField, which stores no triangles.
  • Rare in practice. Nobody has reported it since 8.5.0 (2020); the registry rates the likelihood "rare" and the priority low.

Why it is a bug, not intended

#
  • The point-query javadoc promises every complying shape, and LUCENE-8736 made the box and polygon relations with triangles "correctly include boundary points".
  • The test handles both windings everywhere else: the interior, every edge and the first and third corners of a clockwise triangle match.
  • Moving the same triangle by exactly (8, 8) makes the miss disappear.
The full argument245 words
  • Contract. XYShape.newPointQuery: "create a query to find all indexed shapes that comply the QueryRelation with the provided point" (XYShape.java:236-239). CHANGES for LUCENE-8736: "Point in Polygon now correctly includes boundary points. Box and Polygon relations with triangles have also been improved to correctly include boundary points."
  • Written for both windings. The method compares signs (a < 0 == b < 0, c < 0 == (b < 0 || a < 0)) instead of testing all three >= 0, and its javadoc states no precondition: "Compute whether the given x, y point is in a triangle; uses the winding order method".
  • Upstream tests pass clockwise triangles to Component2D. TestLatLonShape.testTriangleCrossingPolygonVertices calls Component2D.intersectsTriangle on (-5,0) (10,0) (-5,-15), which is clockwise, and expects true.
  • Position should not matter. The exact translation by (8, 8) makes the miss disappear; the independent reproduction's metre-like triangle is fixed by a (+10000, +10000) move.
  • Precedent. LUCENE-8973 (#10016, fixed 2019): "XYShape encoding is not lineal and shapes loose their spatial relationship. XYRectangle2D should work then on the float space." A review comment on #1017 (2022): "XY queries should work on the float space."
  • Why tests missed it. The random point-query check draws random points, which rarely land exactly on a stored vertex, and validates them with the same Component2D code; and the TRIANGLE branch of BaseShapeEncodingTestCase computes its "original" and "encoded" predicates from the same original coordinates, so it cannot see a change caused by the encoding.
The devil's-advocate check210 words

The strongest case for "works as designed": Component2D is @lucene.internal, and ShapeField documents that triangles are stored counter-clockwise (since LUCENE-8581, 2018; LUCENE-9642 moved the check after the corner rotation), so a clockwise triangle would be a broken precondition, not a predicate bug.

Why it fails: the counter-clockwise guarantee holds only for the encoded ints, not for the floats the query actually tests; Lucene's own winding swap turns a triangle the tessellator emitted counter-clockwise into a clockwise float triangle, for a valid public XYPolygon (the reversed ring stores the same triangle); no precondition is documented; and the public result changes under an exact translation. The fallback argument, that boundary answers are best effort because GeoUtils.orient "does not yet have the floating point tricks to be exact", fails too: every product here is a small exact integer, so the miss is branch logic, not rounding. The XYShape precision WARNING covers double to float only; these coordinates are already floats, which the XY encoding keeps exactly. Maintainers may still see a decoded clockwise triangle as an encoding-side precondition violation and prefer to fix it there or with the narrowest predicate change; the fixes section lists both. Verdict: not intended (the intended-behaviour check, high confidence; the cross-model reviews rated the intended-behaviour argument weak).

Suggested fix

#

Recommended Make pointInTriangle independent of the winding (one function, no reindexing)

Make Component2D.pointInTriangle independent of the winding: accept the point when its three orientation tests are all >= 0 or all <= 0. This changes exactly one answer, the second corner of a clockwise triangle, and needs no reindexing. The repro and the whole lucene/core test suite (8,892 tests) pass with it.

Trade-offs

  • Exactly one answer changes: the two return statements differ only for the sign triple (0, 0, -1) of the 27, which in exact arithmetic means the point is the second corner of a clockwise triangle (stock false, fix true); on every grid triangle and point that is the only difference. Counter-clockwise triangles get the same answers as before.
  • Other callers. pointInTriangle is also called from Line2D, Rectangle2D, Circle2D, Polygon2D and SpatialQuery. SpatialQuery's two calls test encoded triangles, which are counter-clockwise or degenerate in encoded space (asserted by decodeTriangle), so in exact arithmetic their answers cannot change (GeoUtils.orient rounds when encoded ints are far apart, so a near-degenerate encoded triangle was not ruled out; not audited). For the float-space callers the change can only turn "outside" into "inside" when the tested point is exactly the second corner of a clockwise decoded triangle, the answer they already give at the other two corners; their user-visible effects were not audited separately.
  • No reindexing and no format change: the stored triangles stay as they are.
  • Cost: the fix computes the third orientation on every call inside the bounding box, where the stock code can reject after two; no benchmark was run. pointInTriangle is shared by several geometries, so measure it, or take the narrower variant below.

Narrower variant that keeps the early reject (checked at the sign level only) (validated by the checks)

#

Keep the stock code and also accept when a == 0 && b == 0 in the inner return: return c == 0 || (a == 0 && b == 0) || (c < 0 == (b < 0 || a < 0));.

Trade-offs

Same answers as the recommended fix at the sign level, without computing the third orientation where the stock code rejects early; harder for a reader to see that it is winding-independent.

What the checks validated

Over all 27 sign triples it gives the same answers as the recommended fix (sign-enum.txt). Not run in Lucene.

Orient XY triangles in float space when encoding (not run)

#

Make ShapeField.encodeTriangle choose the winding of XY triangles from the float coordinates, so stored triangles decode counter-clockwise.

Trade-offs

encodeTriangle is shared with LatLon and works on ints; decodeTriangle asserts the encoded-space invariant, and the 3-bit reconstruction code relies on it ("Triangles are encoded with CCW orientation and might be rotated to limit the number of possible reconstructions to 2^3"), and a triangle that is counter-clockwise as floats can be clockwise as ints, so this is an encoding change. Existing indexes keep their clockwise triangles until reindexed. It touches the same swap block as LFV-204 (edge flags); test both together.

Re-orient decoded XY triangles before calling Component2D (not run)

#

In XYShapeQuery (and other XY decoders), swap b and c, and the edge flags, when the decoded float triangle is clockwise.

Trade-offs

No reindexing, but it fixes only the call sites that decode, costs one orientation test per visited triangle, and the edge-flag swap must be right for withinTriangle (CONTAINS).

Workaround for users today: a zero-size box query at the point (not a fix) (validated by the checks)

#

Query XYShape.newBoxQuery(field, relation, x, x, y, y) instead of newPointQuery at an exact vertex.

Trade-offs

Checked on two shapes only; a box query goes through a different relation code path.

Downstream note

#

Downstream engines and applications that index cartesian shapes with XYShape and use its point queries inherit this; it would matter for access or geofencing decisions only where those rest on point queries at exact polygon vertices.

How it was found

#

A metamorphic test indexed every triangle of a small integer lattice, plus random samples of larger lattice shapes, as-is and under 22 exact transforms, and compared the hits of all four query relations. With registered geo fixes applied, most remaining mismatches were point queries at polygon corners; a probe showed that exactly the triangles stored clockwise miss their second corner.

The method in full217 words

Method: metamorphic bounded-exhaustive translation validation of the stock main jar (semi-formal tier), in a hunt unit on orientation-preserving transforms of geo shapes.

  • Every document and query of a 6 x 6 integer-lattice family (9,156 documents, including all 6,768 non-degenerate lattice triangles, and 1,631 queries) was indexed and queried as-is and under 22 exact transforms: quarter-turn rotations, reflections with vertex reversal, cyclic vertex rotation, translations by +-2^k and reversal. All four relations were run on the BKD, doc-values, point and point doc-values paths, and the correct side of each mismatch was decided by an exact DE-9IM reference plus the closed-set convention.
  • With the fixes of the registered geo bugs shadowed in, most of the remaining mismatches, 80,128, were point or multi-point queries at polygon vertices; with this bug's fix also shadowed in, none of those remained, and the rest came from separate findings, mainly circle queries after ±2^23 translations. A component-level probe then showed that exactly the 240 lattice triangles stored clockwise in float space miss their second corner (0 with the fix).
  • The finding was reduced to a public-API JUnit and checked by an independent reproducer, an intended-behaviour devil's advocate, reading-only reviews by a model from another family (OpenAI GPT-5.6), an adjudication, a history, prior-report and security follow-up, and an audit. Found 2026-10-27 on main a9779ef3c193.

Bug record

LFV-764, snapshot of 2026-10-28

Registry title
XYShape point queries can miss a polygon at one of its own vertices: Component2D.pointInTriangle rejects the second vertex (b) of a clockwise triangle, and ShapeField.encodeTriangle makes XY triangles counter-clockwise only on their sortable-int encodings, so a stored triangle can decode clockwise; an INTERSECTS point query at that vertex misses the polygon and DISJOINT returns it (since 8.5.0)
Area
geo / XYShape point queries (Component2D.pointInTriangle; ShapeField.encodeTriangle orientation for XY)
Priority
Low, rank 333: Default XYShape INTERSECTS/DISJOINT point queries give silent wrong answers only for a query placed exactly on a clockwise-decoded polygon vertex, an exact-geometry boundary case that belongs below the two silent Tessellator rows and above the loud Tessellator crash rows LFV-762 and LFV-755.
Impact class
silent wrong results
Impact note
Hits applications on 8.5.0 through 10.5.2 or main that index polygons with the default XYShape.createIndexableFields (default codec and IndexWriterConfig, no scale needed) and run XYShape point or multi-point queries whose coordinate equals a polygon vertex exactly, when every stored triangle at that vertex holds it in position b and decodes clockwise, which can happen when a triangle's x or y range crosses zero or a power-of-two boundary: INTERSECTS silently misses the polygon and DISJOINT silently returns it (CONTAINS also answers differently per vertex, but its correct boundary answer is debatable); the finder measured such a vertex in about 0.07-0.3% of random polygons in metre-like and 1000-1900 coordinate ranges and about 3% of random polygons around the origin (not re-run by the verifiers); LatLonShape is not affected in the scope checked (its decoding is linear) [exec on main and all 52 releases 8.5.0-10.5.2].
Summary
You index the clockwise triangle (0,1) (1,2) (3,3) as an XYPolygon with XYShape.createIndexableFields and run XYShape.newPointQuery at each of its corners; you expect every corner to match the polygon (INTERSECTS) and none to be DISJOINT from it, as happens for the same triangle moved by (8,8) and for every point of its edges. Instead the INTERSECTS query at (1,2) finds nothing and the DISJOINT query at (1,2) returns the document: ShapeField.encodeTriangle checks the winding on the sortable-int encodings of the floats, which are ordered like the floats but not evenly spaced, so the stored triangle decodes clockwise, and Component2D.pointInTriangle reports the second vertex of a clockwise triangle as outside. The same happens with projected metre-like coordinates, for example at vertex (518885,4395432) of a hexagon whose x range crosses 2^19.
