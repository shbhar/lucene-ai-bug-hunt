The finding in 30 seconds

#

One rescored hit: first-pass score 1.0, popularity 7, expression _score * 100 + popularity. The rescore sorts it by 107.0; its explanation says 7.0.

Background: expression rescoring and explain

#
  1. A rescorer re-sorts the top hits of a first search. Expression.getRescorer does it with a formula over the hit's first-pass score (_score) and document values, for example _score * 100 + popularity.
  2. explain returns a tree of numbers that says how a hit got its value. ExpressionRescorer's javadoc says its tree shows the value of each variable.
  3. SortRescorer, which ExpressionRescorer extends, explains a re-sort with a placeholder value of 0.0 and puts the real sort value in the text.

The finding, step by step

#
  1. Rescore first-pass hits with Expression.getRescorer for _score * 100 + popularity. A hit with first-pass score 1.0 and popularity 7 is sorted by 1.0 x 100 + 7 = 107.0.
  2. Ask rescorer.explain(searcher, firstPassExplanation, doc) how that hit got its value. You expect _score = 1.0 and the value 107.0: the javadoc says explain shows "the value of each variable", and up to 6.6.6 the _score line was right.
  3. Instead you get 7.0 = _score * 100 + popularity, and the _score line reads 0.0 = sort field values for sort=.... The javadoc's own example sqrt(_score) + ln(popularity) is explained as just ln(popularity).
  4. Why: explain first asks SortRescorer for its explanation, whose value is always a 0.0 placeholder, and hands that node to the expression as the score. So the expression is evaluated with _score = 0.
  5. Only the explanation is wrong: the rescored order, sort values and scores are right. Passing the real first-pass explanation instead, labelled "first pass score", fixes it; all 171 tests of the expressions module pass.

Who is affected

#

Code that explains a rescorer from Expression.getRescorer whose expression reads _score: for hits with a nonzero first-pass score, the explanation shows the wrong _score and, where it depends on _score, the wrong value. Ranking, sort values and scores are correct. The API is experimental and rarely used: no Lucene code outside tests calls it; no report in nine years.

Mechanism, terms and numbers486 words

Expression.getRescorer re-sorts first-pass hits by an expression, and its explain is documented to give "more detail by showing the value of each variable". Since 7.0.0 (LUCENE-7741) ExpressionRescorer.explain hands SortRescorer's explanation, whose value is always 0.0, to the expression as the score explanation, so the expression is evaluated with _score = 0 and the _score detail is that 0.0 node. For _score * 100 + popularity, a hit with first-pass score 1.0 and popularity 7 is sorted by 107.0 but explained as 7.0 = _score * 100 + popularity; the Expression javadoc's example sqrt(_score) + ln(popularity) is explained as ln(popularity), and popularity / _score as +Infinity. The rescored order, sort values and scores are correct. 6.5.1-6.6.6 show _score correctly; 7.0.0 to 10.5.2 and main do not, and putting back only the old ExpressionRescorer.java on 7.0.0 removes the failure. Passing the first-pass explanation, labelled "first pass score", fixes the repro and passes all 171 expressions tests. Low priority: an explain-only defect in an experimental, rarely used API.

Mechanism (Lucene main 645d4fe14a20)

#
  1. rescore() (SortRescorer.java:38-93) sets the scorer's score to each hit's first-pass score (:77, score.score = hit.score), so the sort value is 1.0 * 100 + 7 = 107.0, and it keeps ScoreDoc.score at 1.0 (:89-91).
  2. ExpressionRescorer.explain (ExpressionRescorer.java:49-62) first calls SortRescorer.explain (:52). That re-runs the rescore for the one hit and returns Explanation.match(0.0f, "sort field values for sort=...", subs) (SortRescorer.java:125), whose details are the first-pass explanation and a 0.0 node with the sort value in its text (:118-120).
  3. It passes that 0.0 node to ExpressionValueSource.explain as the score explanation (ExpressionRescorer.java:59-61).
  4. ExpressionValueSource.explain evaluates the expression with the scores bound to DoubleValuesSource.constant(scoreExplanation.getValue()) = 0.0 (ExpressionValueSource.java:191-195): 0 * 100 + 7 = 7.0. For _score, DoubleValuesSource.SCORES.explain returns the score explanation itself (DoubleValuesSource.java:376-377), so the _score detail is the 0.0 node.

What you see on main, with assertions on and off:

7.0 = _score * 100 + popularity, computed from:
  0.0 = sort field values for sort=<expr(_score * 100 + popularity)>!     <- the _score detail
    1.0 = first pass score
      1.0 = *:*
    0.0 = sort field <expr(_score * 100 + popularity)>! value=107.0
  7.0 = double(popularity)

(The arrow is ours.) The right value, 107.0, appears only as text inside a node whose value is 0.0.

More effects

#
  • sqrt(_score) + ln(popularity), the Expression javadoc's example, is explained as ln(popularity) (1.9459 for popularity 7, against a sort value of 2.9459).
  • popularity / _score is explained as +Infinity, and ln(_score) + popularity as -Infinity; the rescored values stay finite and nothing throws.
  • The explained values can order hits differently from the rescore: on 7.0.0 the rescore ranks three hits 25.13, 25.11, 24.43, and their explanations say 6.0, 5.0, 7.0.
  • Expressions that do not read _score explain correctly, and the expression's own DoubleValuesSource.explain, given the real first-pass explanation, returns the sort value.
Exposure and likelihood239 words
  • Who. Applications that call explain on a rescorer from Expression.getRescorer whose expression reads _score, directly or through a binding. For every explained hit the _score detail is SortRescorer's 0.0 node instead of the first-pass explanation; when the first-pass score is not 0 (true of every hit in our runs), the _score value shown is wrong, and so is the expression value wherever it depends on _score. It reproduced with a plain IndexSearcher, the default BM25 similarity and the default codec (the release probe, 3 documents) and in randomized test fixtures of 1 and 6 documents, on main with assertions on and off; by reading, nothing on the explain path depends on the codec or the index size.
  • What is wrong. Only the Explanation: the _score value shown, and the expression value computed from it.
  • What is right. The rescored order, the FieldDoc sort values, the ScoreDoc scores and isMatch() (checked by a probe on main with assertions on and off).
  • Opt-in, rarely used API. Expression and ExpressionRescorer are @lucene.experimental; ExpressionRescorer is package-private and reached only through the public getRescorer. No Lucene code outside tests calls getRescorer.
  • Likelihood: plausible. Anyone who explains a _score-based expression rescore sees it at once, but rescorer explanations are a rare diagnostic, and nobody has reported it since 7.0.0 (2017).
  • Workaround. Explain the expression directly: expression.getDoubleValuesSource(bindings).explain(leaf, docInLeaf, firstPassExplanation) returns the sort value (an independent reproducer's control test).

Why it looks unintended

#
  • The class javadoc says explain shows "the value of each variable"; it shows _score as 0, not the score the rescore used.
  • A regression: 6.6.6 showed _score correctly; LUCENE-7741 (7.0.0) swapped in the 0.0 node without a stated reason.
  • The explained 7.0 = _score * 100 + popularity is wrong arithmetic, not a placeholder.
The full argument227 words
  • The class javadoc (ExpressionRescorer.java:29-33): functionally the same as SortRescorer "except for the explain method which gives more detail by showing the value of each variable".
  • The Rescorer contract (Rescorer.java:45): "Explains how the score for the specified document was computed." In the #14776 review (2025), vigyasharma wrote that "Rescorer#explain API is meant to explain how the _Rescorer_ would score this docId for given searcher, when rescore() is called".
  • The original design (LUCENE-5545, #6608, mikemccand, 2014): "explain() includes the values of each of the bindings ... so you can see the values that led to the overall expression".
  • A regression. Up to 6.6.6 the code bound the scores to firstPassExplanation.getValue() and printed variable "_score" with the first-pass score. LUCENE-7741 (fb24d451cc98) replaced that loop with the call that passes SortRescorer's node. Its issue thread (#8792) never mentions rescorers, and the commit message gives no reason for this change.
  • The code defines the parameter as the score's explanation. SCORES.explain returns it, and the default DoubleValuesSource.explain evaluates with scoreExplanation.getValue() as the score (DoubleValuesSource.java:80-89).
  • Why nobody noticed. The same commit changed the upstream test from expl.contains("= variable \"popularity\"") to expl.contains("= double(popularity)"); TestExpressionRescorer.testBasic checks only substrings, never a value.
  • Precedent. Wrong values in an explanation are fixed as bugs, for example "GITHUB#13691: Fix incorrect exponent value in explain of SigmoidFunction" under 9.12.0 Bug Fixes.
The devil's-advocate check221 words

The strongest case for "works as intended" (rated moderate by the cross-model reviews, weak by the devil's-advocate verifier): SortRescorer's 0.0 root is a deliberate placeholder, since a re-sort keeps ScoreDoc.score and puts the keys in FieldDoc.fields; ExpressionRescorer is documented as functionally the same as SortRescorer; the APIs are @lucene.experimental; nothing promises that the root equals FieldDoc.fields[0]; DoubleValuesSource.explain has no @param for scoreExplanation; and LUCENE-7741 may have passed SortRescorer's node on purpose to keep the "first pass score" text that testBasic asserts.

Why it fails: that explains a 0.0 root, not binding the documented _score variable to 0. Since 7.0 the root is not the placeholder either: it claims 7.0 = _score * 100 + popularity, computed from:, false arithmetic for the real _score, so it follows no convention. Keeping the "first pass score" text does not need the 0 value: the recommended fix keeps it and testBasic passes. The rest (experimental, explain-only) argues for Low priority, which is how it is classed, not for intent. The root never equalled the sort value, 6.6.6 included. This is evidence that the behaviour conflicts with the javadoc and the 6.x code, not proof of what LUCENE-7741 intended; the fix shape is the maintainers' choice (the recommended fix gives an expression-valued root, the 6.x restore keeps SortRescorer's 0.0 root).

Suggested fix

#

Recommended Pass the first-pass explanation, labelled "first pass score"

In ExpressionRescorer.explain, pass the first-pass explanation, wrapped as "first pass score", to the expression instead of SortRescorer's 0.0 node (+5/-3 lines). The hit then explains as 107.0 = _score * 100 + popularity with 1.0 = first pass score. The repro and all 171 expressions tests pass.

// rescore() computes the expression with _score = the first-pass score, so explain it that way
Explanation firstPassScore =
    Explanation.match(
        firstPassExplanation.getValue(), "first pass score", firstPassExplanation);
return expression
    .getDoubleValuesSource(bindings)
    .explain(readerContext, docIDInSegment, firstPassScore);
