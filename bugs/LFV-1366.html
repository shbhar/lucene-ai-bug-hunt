CopyOneFile.close() throws IllegalStateException after visit() has finished the copy

In the NRT replicator, CopyOneFile.visit() closes the copy itself when it finishes, so the caller's own close() of the finished copy throws IllegalStateException: file f was not actually being copied?, although the file was copied and verified. Present since 6.0.0; only application-written copy jobs hit it.

The finding in 30 seconds

#

CopyOneFile.visit() closes the copy itself when it finishes. close() has no closed flag, so a second close() repeats its work: it tells the replica a second time that the file is done, and the replica's bug-catcher throws.

Background: how an NRT replica copies a file

#
  1. In NRT replication (the opt-in lucene-replicator module) a replica pulls new index files from the primary. The application supplies the transport by subclassing the abstract ReplicaNode and CopyJob.
  2. A CopyJob copies each file with a CopyOneFile: create it, then call visit() until it returns true. Meanwhile ReplicaNode keeps the name in a map of files being copied, to catch two jobs copying the same file.

The finding, step by step

#
  1. Copy a 46-byte index file f to a replica: new CopyOneFile(input, replica, "f", metaData, new byte[1024]). The constructor registers f with the replica as "being copied".
  2. Call visit() once. It copies 38 bytes, verifies the checksum, writes the last 8 bytes, closes the copy itself (which unregisters f) and returns true.
  3. Now close the copy, as any owner of a Closeable may (try-with-resources, a finally). You expect no effect: Closeable says closing an already closed stream has no effect.
  4. Instead close() runs again, tries to unregister f a second time and throws IllegalStateException: file f was not actually being copied?, with assertions on and off. The copied file is complete and correct.

Who is affected

#

Only applications that use the opt-in NRT replicator, write their own CopyJob (Lucene ships only a test one) and close a CopyOneFile after visit() returned true, for example with try-with-resources. They hit it deterministically, for every file whose copy completes. The file is copied and verified first. Lucene's own code never closes a finished copy.

Mechanism, terms and numbers338 words

In NRT replication a replica copies each new index file with a CopyOneFile, calling visit() until it returns true. On the call that finishes the copy, visit() writes the checksum and calls close() itself. close() is out.close(); dest.finishCopyFile(name); with no closed state, and CopyOneFile is a public Closeable.

So a caller that also closes the finished copy, as try-with-resources or a finally does, runs finishCopyFile a second time, and the replica's bookkeeping throws IllegalStateException: file <name> was not actually being copied?. The file is already complete and checksum-verified, but the exception escapes from a successful copy, and a job that treats it as a failure would cancel a good copy. Lucene's own code never closes a finished copy; applications that write their own CopyJob can. It is there since 6.0.0 (2016) and fails on every release we ran.

Exposure and likelihood234 words
  • Who is hit. A replica subclasses the abstract ReplicaNode, whose abstract newCopyJob returns a CopyJob (ReplicaNode.java:508); CopyJob is abstract too and its only in-tree implementation, SimpleCopyJob, is test code, so a replicating application writes its own. Only a job that closes a finished CopyOneFile is hit, for example try (CopyOneFile copy = ...) { while (copy.visit() == false) {} }.
  • What happens to them. The exception escapes from a copy that succeeded. A job that cancels on any exception from its visit step, as the in-tree test runner does (Jobs.java:76-85, test sources), would cancel a good copy.
  • What does not happen. No wrong data from Lucene: the temp file is complete and checksum-verified before the throw. What follows is up to the application's job: one that aborts or retries on the exception discards or repeats a good copy (not executed; the repro stops at the throw). SimpleCopyJob sets current = null once visit() returns true (SimpleCopyJob.java:212-219), and CopyJob.cancel / _transferAndCancel close current only while it is non-null, through IOUtils.closeWhileHandlingException (CopyJob.java:204-211, :250-257).
  • Scale and config. No scale needed: one file of any size, default settings, assertions on or off.
  • Why it likely went unnoticed (an inference). The failure is loud and deterministic, so an implementer who hits it probably sees it at once and drops the close. We found no report since 6.0.0.

Why it looks unintended

#
  • CopyOneFile is a public Closeable, and Closeable.close() says closing an already closed stream "has no effect". No javadoc says that visit() closes the copy.
  • The check that throws is "Used only to catch bugs": one file copied by two jobs, not one copy closed twice.
  • Precedent: LUCENE-6124 (#7186) fixed throwing double closes in codec and store APIs.
The full argument257 words
  • The contract. public class CopyOneFile implements Closeable (CopyOneFile.java:30); java.io.Closeable.close(): "If the stream is already closed then invoking this method has no effect." close() has no javadoc of its own.
  • Nothing documents the restriction. The class javadoc ("Copies one file from an incoming DataInput to a dest filename in a local Directory", :29) and visit()'s ("Copy another chunk of bytes, returning true once the copy is done", :93) say nothing about visit() closing the copy. No test, CHANGES or MIGRATE entry states a close-once rule.
  • Not tagged experimental, though its framework is. CopyJob, ReplicaNode and Node carry @lucene.experimental; CopyOneFile does not, although the LUCENE-5438 thread says "I've marked the new APIs experimental or internal", and the package javadoc says only "Near-real-time replication framework". The surrounding API is experimental, so the missing tag is not decisive; it does show that CopyOneFile was not marked internal. It is part of the API every CopyJob implementer uses: protected CopyOneFile current (CopyJob.java:61) and protected abstract CopyOneFile newCopyOneFile(CopyOneFile current) (:214).
  • Project precedent. LUCENE-6124 (#7186), a Bug Fixes entry of 5.0.0: "Fix double-close() problems in codec and store APIs" (lucene/CHANGES.txt:11625). BaseLockFactoryTestCase.testDoubleClose ("close again, should be no exception"), BaseDirectoryTestCase.testDoubleCloseOutput / testDoubleCloseInput and TestSearcherManager.testCloseTwice ("per Closeable's contract") test it for those APIs; a precedent, not a written project-wide rule. The JDK draws the same line: AutoCloseable.close() "is not required to be idempotent ... unlike Closeable.close which is required to have no effect if called more than once", and CopyOneFile implements Closeable.
The devil's-advocate check165 words

The strongest case for "intended": the replicator follows a consistent one-owner lifecycle. On success visit() finishes the copy itself, and the owner closes only an unfinished copy (SimpleCopyJob drops a finished copy; CopyJob.cancel and _transferAndCancel close only a non-null current). The copying map is a deliberate bug-catcher, the framework is experimental, and no complaint about it was found since 2016.

Why we think it fails (a maintainer may weigh it differently): the rule is written nowhere, CopyOneFile itself is public and declares Closeable, whose contract says the opposite; the bug-catcher's own comment aims it at two jobs copying one name; and LUCENE-6124 and the double-close tests are precedent for idempotent close(). Ten years without a report shows how narrow the reach is, not that the behaviour was chosen. Verdict: a small defect. A maintainer may reasonably call it working as intended for an experimental framework, or accept the fix only as hardening; fix B (document the lifecycle) is the fallback then.

Suggested fix

#

Recommended A. A closed flag in CopyOneFile.close() (recommended; validated)

Give close() a closed flag: a second call returns at once, and finishCopyFile runs in a finally after out.close(), so the name is unregistered exactly once on every path. With it the repro, TestNRTReplication (13 nightly tests) and TestStressNRTReplication pass.

  private boolean closed;

  @Override
  public void close() throws IOException {
    if (closed) {
      return;
    }
    closed = true;
    try {
      out.close();
    } finally {
      dest.finishCopyFile(name);
    }
  }
All options and trade-offs2 options · 475 words

Option B is the smallest change if maintainers prefer no code change. Rejected: dropping the self-close from visit() would leave the name registered for every finished copy, because SimpleCopyJob and jobs written on its model never close a finished copy; making finishCopyFile lenient (ignore a name that is not registered) would also stop the throw, but would silence that bookkeeping check for every caller of the public finishCopyFile, not only for a repeated close of one copy; the two-jobs check itself is in startCopyFile (ReplicaNode.java:878-882) and is unaffected either way. One seed; not the full test matrix.

A. A closed flag in CopyOneFile.close() (recommended; validated)

#

Add private boolean closed; and guard close() (CopyOneFile.java:87-91).

  private boolean closed;

  @Override
  public void close() throws IOException {
    if (closed) {
      return;
    }
    closed = true;
    try {
      out.close();
    } finally {
      dest.finishCopyFile(name);
    }
  }

Trade-offs

The finally matters: without it, an out.close() that throws inside visit() would set the flag but leave the name registered, the owner's later cancel would no longer unregister it, and the next copy of that name would throw "is being copied in two places!" (ReplicaNode.java:880). With it the name is unregistered once on every path. Today's code gets there only through cancel's second close, and only if that retried out.close() succeeds: if it throws again, IOUtils.closeWhileHandlingException swallows it before finishCopyFile runs (CopyJob.java:250-256). This path is reasoned from source, not tested.

A second close() no longer retries out.close(); cancel deletes the partial file anyway (CopyJob.java:255). A plain field matches how the class is used: a CopyOneFile is driven by one thread at a time (SimpleCopyJob's visit, cancel and transferAndCancel are synchronized), and the IndexOutput it wraps is not thread-safe anyway; concurrent close was not tested. The transfer constructor (:74-85) starts with the flag false, which is right, because _transferAndCancel drops the old instance without closing it (CopyJob.java:188).

B. Document the lifecycle (not validated; the smallest change)

#

Say on the class and on visit() that visit() closes the copy when it returns true and that the owner must close only an unfinished copy.

Trade-offs

No code change, but it documents a Closeable that breaks Closeable's contract, and the trap stays.

Downstream note

#

Downstream, Yelp's nrtsearch has its own CopyOneFile classes with the same pattern (visit() closes the copy, close() keeps no closed state), so a fix in Lucene does not reach them.

How it was found

#

A semi-formal proof-obligation check of CopyOneFile's Closeable contract: a close() of an already closed copy must have no effect. visit()'s self-close breaks that obligation for every completed copy; an executable public-API probe confirmed it, and the minimal JUnit test followed.

The method in full88 words

The obligation comes from java.io.Closeable.close() ("If the stream is already closed then invoking this method has no effect"), which CopyOneFile declares. close() is reached from visit() when a copy completes (CopyOneFile.java:129) and from CopyJob.cancel and _transferAndCancel for an unfinished copy (CopyJob.java:204-211, :250-257). After the first, the owner still holds a copy that is already closed, and a close by the owner runs finishCopyFile a second time. An executable probe through public API confirmed it on main 5adff78bb168; the minimal JUnit test followed.
