A failed addIndexes(CodecReader...) leaves its unstarted merges queued, so the next addIndexes call runs them on the earlier call's closed readers

With SerialMergeScheduler and one merge per reader, a failed addIndexes(CodecReader...) call (say, disk full) leaves its unstarted merges in the writer's shared queue. The next call runs them first and, if their readers are closed, throws AlreadyClosedException, as can every later call until rollback(), deleteAll() or close().

The finding in 30 seconds

#

addIndexes(CodecReader...) puts its merges on one to-do list that the whole writer shares. A call that fails partway leaves its unstarted merges on that list, and the next call runs them first.

How addIndexes(CodecReader...) runs its merges

#
  1. The merge policy turns the incoming readers into a plan of merges: by default one merge for all readers; a policy that overrides findMerges(CodecReader...) can make, for example, one merge per reader.
  2. Every merge of the plan goes into one queue that the whole writer shares. Then the merge scheduler takes merges from the head of that queue and runs them.
  3. Only when every merge of its plan succeeded does the call add the new segments to the index. Otherwise it throws and adds nothing.

The finding, step by step

#
  1. Configure the writer with SerialMergeScheduler and a merge policy whose findMerges(CodecReader...) returns one merge per reader, the javadoc's way to get the most concurrency.
  2. Call 1: addIndexes with the 2 segments of index A. Both merges go into the writer's shared queue; the first hits a disk-full IOException. The call throws and adds 0 documents; the writer stays open, not tragic. You close reader A.
  3. Call 2: addIndexes with the 1 segment of index B, no fault. You expect it to add 1 document.
  4. Instead the scheduler first runs A's second merge, still queued from call 1, on the closed reader: AlreadyClosedException: this IndexReader is closed. B's merge is left queued in turn, so, with each call's readers closed when it returns, 4 of 4 later calls failed the same way; only rollback(), deleteAll() or close() clears the queue.
  5. If reader A stays open instead, call 2 silently runs 2 merges instead of 1 and writes a segment that is never added. The index itself is never damaged.

Who is affected

#

Applications that add indexes with addIndexes(CodecReader...) using a multi-merge findMerges(CodecReader...) with SerialMergeScheduler, or a custom scheduler that can throw early, and keep the writer after a failed call. With the default plan and scheduler the only path found is an interrupt while a saturated ConcurrentMergeScheduler stalls the call, and then only a background merge fails. Every release since 9.4.0.

Mechanism, terms and numbers582 words

addIndexes(CodecReader...) asks the merge policy for a plan of merges, puts every merge of the plan into one queue that the whole writer shares, and then lets the merge scheduler run the queue. If the call fails before the scheduler took every merge, it throws and adds nothing, as promised, but it never takes its unstarted merges back out of the queue. After that a queued merge leaves the queue only when a later scheduler run takes it, or when rollback(), deleteAll() or close() drops the whole queue. SerialMergeScheduler stops at the first exception, so a plan of several merges whose first merge fails (for example on disk full) leaves the rest behind.

In a single-threaded application the next addIndexes(CodecReader...) call queues its own merge behind the old ones, and the scheduler runs the old ones first, on the earlier call's readers. If the caller closed them, the valid call throws AlreadyClosedException: this IndexReader is closed and leaves its own merge behind, so, when each call's readers are closed after it, every later call fails the same way. If the readers are still open, the old merge runs for nothing: its segment is never added (in the executed probe its files stayed on disk, unreferenced, until close). Every release from 9.4.0 to 10.6.0 and main.

The bug, step by step

#
  1. One shared queue. AddIndexesMergeSource holds one pendingAddIndexesMerges queue for the writer (IndexWriter.java:3399-3401); getNextMerge() takes the oldest merge (:3420-3429).
  2. Register all, then run. addIndexes(CodecReader...) registers every merge of the plan (:3311), calls mergeScheduler.merge(addIndexesMergeSource, MergeTrigger.ADD_INDEXES) (:3312), then spec.await() (:3313).
  3. The failure path forgets the queue. When the scheduler throws, the finally (:3316-3324) only deletes the files of merges that have merge info. Nothing takes this plan's still-queued merges out. abortPendingMerges() (:3443-3457) is called only from abortMerges() (:2837), that is from rollback/close (:2621) and deleteAll() (:2771).
  4. The serial scheduler stops at the first exception. SerialMergeScheduler.merge loops getNextMerge() / mergeSource.merge(merge) with no catch (SerialMergeScheduler.java:32-40), so the first merge's exception leaves the later ones queued.
  5. The next call runs them first (single thread; with concurrent addIndexes calls, whichever call's scheduler run comes next takes them). It queues its own merge at the tail. The scheduler takes the old merge, whose reader is closed, and reader.codecReader.leaves() throws AlreadyClosedException (:3505). That exception propagates the same way, so the new call's merge is left behind in turn.
  6. A leftover merge is never useful. Only the call that owns a plan adds its segments, after spec.await() and only on success (:3340-3367). Once that call has returned, nobody adds the leftover's output.

Other ways in

#
  • Any MergeScheduler whose merge() throws before taking every merge, even with the default one-merge plan (seen first by the enumeration that found the bug).
  • The default one-merge plan and the default scheduler class, ConcurrentMergeScheduler: a Thread.interrupt() of the addIndexes thread while CMS stalls it in maybeStall because it already runs its maximum number of merges (ConcurrentMergeScheduler.java:566, before getNextMerge at :570) leaves the single merge queued. Then the later call succeeds and a background merge thread fails with AlreadyClosedException instead. Executed with setMaxMergesAndThreads(1, 1) and one regular merge held running to force the stall; with the stock limits (maxMergeCount is maxThreadCount + 5, :60-66) the stall needs that many merge threads running at once (:611), and it was not run that way.
Exposure and likelihood215 words
  • Effect. Loud, not silent: a later valid addIndexes throws an exception naming a reader the caller already closed, which points away from the real cause, and, while each call's readers are closed when it returns, it keeps throwing until rollback() (which discards every uncommitted change and closes the writer), deleteAll() (which also deletes every document) or close().
  • With the readers kept open. One wasted merge per leftover, an unreferenced segment (in the probe, on disk until close), and the failed input's field names registered in the writer's in-memory field map until the writer is reopened: a later document that uses such a name with a conflicting doc-values type is rejected with IllegalArgumentException.
  • Not affected. No document of the failed call ever becomes visible (NRT reader, commit, reopen), CheckIndex is clean, and no file outside the commit survives close. The other operations the probe checked work (adding documents, NRT readers, commit, reopen).
  • What it takes. A non-default merge plan or scheduler, a failure during addIndexes (disk full, an I/O error, an interrupt), and a caller that keeps using the writer. The javadoc itself suggests one merge per reader for concurrency (MergePolicy.java:610-612), and the open #11512 proposes it as the default.
  • Scale. One failed call is enough; assertions on or off; tiny input.

Why it looks unintended

#
  • Not tragic: the writer stays open and getTragicException() is null, so by our reading it should keep working.
  • The readers are the caller's ("The provided IndexReaders are not closed"); no javadoc asks to keep them open or to roll back.
  • A leftover merge is never useful: only the call that owns it adds its segment, and that call has returned.
The full argument254 words
  • Lucene treats this failure as non-tragic. The class javadoc says the writer closes itself "if you hit an Error, or disaster strikes during a checkpoint" (IndexWriter.java:162-165), and the code treats some other failures as tragic too, for example a failed regular merge (:5111). This one is not: isOpen() is true and getTragicException() is null. By our reading that means the writer is expected to keep working; no javadoc says so in as many words, and none says otherwise.
  • The readers belong to the caller. "The provided IndexReaders are not closed." (:3257).
  • The transactional promise is about content, and it holds. "either no indexes will have been added or they all will have been" (:3084-3086, referenced from :3259-3260). The failed call adds nothing; the bug is the work it leaves behind for other calls.
  • Precedent. LUCENE-702 made addIndexes transactional and, in the same change, fixed IndexWriter.mergeSegments and IndexReader.commit() to "clean up and keep the instance state consistent" after exceptions (lucene/CHANGES.txt:21400-21407); LUCENE-846 fixed, as a bug, an addIndexes exception that "could corrupt the instance of IndexWriter (but, not the index itself)" (lucene/CHANGES.txt:20905-20910).
  • The design covered rollback and close only. In PR #633, which added the queue, the author wrote that pending merges "are aborted when IndexWriter is rolled back or closed". The upstream partial-failure test (TestAddIndexes.java:796) uses a scheduler that takes every merge and closes the ones it skips (:759-794, :783), so the serial path is never tested.
The devil's-advocate check171 words

The strongest case. In #9738 (LUCENE-8692, 2019) Simon Willnauer lists addIndexes() among IndexWriter methods whose exceptions "might cause documents go missing etc." and says they are not treated as tragic "since a user could always call rollback()". Read that way, a caller who keeps using the writer after a failed call accepts that its state may be inconsistent. MergeScheduler and MergeSource are experimental, and the defaults avoid the main trigger.

Why it fails. That comment is about which exceptions should count as tragic, and it predates the 2022 queue. It accepts that a failed call may lose that call's documents; it does not say that a later, unrelated call on the open writer should fail. "Could always call rollback()" offers a way back to the last commit. No javadoc requires a rollback, and rollback() throws away all other uncommitted work and closes the writer. A leftover merge can never produce anything that is used, so running it later is never the intended outcome. This is an argument, not a documented contract.

Suggested fix

#

Recommended A. Dequeue this call's unstarted merges on failure (validated)

In the failure path of addIndexes(CodecReader...), take this call's merges that are still queued out of the queue, mark them aborted and close them, as abortPendingMerges() does for the whole queue. Validated: the repro passes with assertions on and off, and with the fix 70 tests (the repro, two reach checks, TestAddIndexes, TestIndexWriterOnDiskFull, TestIndexWriterReader) pass.

All options and trade-offs4 options · 491 words

Option A was applied in a scratch worktree at 5adff78bb168 and run through gradle (seed DEADBEEF); one seed, no nightly tests, not the full test matrix.

A. Dequeue this call's unstarted merges on failure (validated) (recommended)

#

IndexWriter.java: one call in the finally (:3316-3324) and a helper in AddIndexesMergeSource, 18 added lines.

         } finally {
           if (mergeSuccess == false) {
+            // merges of this call that the scheduler never started must not stay queued for the
+            // next addIndexes call
+            addIndexesMergeSource.abortPendingMerges(spec.merges);
             for (MergePolicy.OneMerge merge : spec.merges) {

+    /** Aborts those of the given merges that are still queued. */
+    void abortPendingMerges(Collection<MergePolicy.OneMerge> merges) throws IOException {
+      synchronized (IndexWriter.this) {
+        IOUtils.applyToAll(
+            merges,
+            merge -> {
+              if (pendingAddIndexesMerges.remove(merge)) {
+                merge.setAborted();
+                merge.close(false, false, _ -> {});
+                onMergeFinished(merge);
+              }
+            });
+      }
+    }

Trade-offs

It cleans up this call's merges that are still queued when the failure path's finally runs, whichever way the scheduler call threw (the serial scheduler, a custom scheduler that throws, the CMS interrupt; both reach checks pass with it). It does not help a custom scheduler that takes a merge and then neither runs nor closes it. Concurrent addIndexes calls share the queue, so another call's scheduler run can still take a failing call's merge before this cleanup runs. Like the existing deleteNewFiles in the same finally, an exception from closing a merge would replace the original one; an upstream patch may prefer a catch that adds it as suppressed.

What the checks validated

  • The repro fails without the fix (gradle, assertions on and off) and passes with it (assertions off).
  • With the fix and assertions on: the repro, the two reach checks, TestAddIndexes (39), TestIndexWriterOnDiskFull (4) and TestIndexWriterReader (24, 1 skipped) pass: 70 tests, 1 skipped, 0 failed.
  • The reach checks fail without the fix: with the default policy and ConcurrentMergeScheduler, an interrupt during the stall makes a background merge fail with AlreadyClosedException; with SerialMergeScheduler, 4 of 4 later fault-free calls throw. Both pass with the fix.
  • A fresh :lucene:core:checkGoogleJavaFormat run passes with the fix and the repro in place.

B. One queue per call

#

Give each addIndexes(CodecReader...) call its own merge source, so a scheduler run sees only that call's merges.

Trade-offs

Removes the cross-call leak at the root, including between concurrent calls, but changes the shared AddIndexesMergeSource design that ConcurrentMergeScheduler threads pull from; a larger change. Not validated.

C. Make SerialMergeScheduler close what it does not run after a failure

#

Catch in SerialMergeScheduler.merge, close the remaining merges, rethrow.

Trade-offs

Fixes the main trigger only: custom schedulers and the CMS interrupt path stay broken, and it changes SerialMergeScheduler for regular merges too. Not recommended.

D. Document that a failed call needs rollback()

#

Javadoc only.

Trade-offs

No code change, but it turns a recoverable failure into "throw away all uncommitted changes and reopen", against the non-tragic contract.

Downstream note

#

Services that add pre-built indexes with addIndexes(CodecReader...) and a multi-merge plan, and keep the writer after a failed call, should roll the writer back (or reopen it) before the next such call until this is fixed.

How it was found

#

A semi-formal, bounded-exhaustive enumeration: each index-level IndexWriter operation was run against an executable reference of its documented outcome, with an exception injected at the first and last point of every distinct I/O code path and at every user-callback invocation, then repeated without faults. The fault-free repeat of addIndexes(CodecReader...) threw AlreadyClosedException; the case was then reduced to one JUnit test.

The method in full107 words

The hypothesis came from reading addIndexes(CodecReader...) while modelling it for the enumeration, which then witnessed it on the stock jars: one-shot and sticky I/O failures at the first and last point of every distinct I/O code path (an equivalence-class reduction), and a throwing callback at every merge-policy and merge-scheduler invocation. The fault-free repeat failed in 1,190 runs (1,188 of the 341,800 counted runs, plus 2 in a configuration that was only partly counted), first with a merge scheduler that throws on the ADD_INDEXES trigger and the default one-merge plan. A second JUnit test with one merge per reader, SerialMergeScheduler and a disk-full error showed the realistic trigger.

Registry title

Area
index / IndexWriter addIndexes(CodecReader...) failure path (AddIndexesMergeSource queue, SerialMergeScheduler)
Priority
Low, rank 843: A failed addIndexes(CodecReader...) leaves its queued merges behind so later calls fail loudly, which needs a non-default multi-merge setup plus an I/O failure, the same failed-call-leaves-state class as LFV-124 and LFV-134.
Impact class
crash
Impact note
Hits only applications that call addIndexes(CodecReader...) with a non-default merge setup (a MergePolicy whose findMerges(CodecReader...) returns more than one merge, the documented way to parallelise addIndexes, together with the stock SerialMergeScheduler, or a custom MergeScheduler that throws before taking every merge) when that call fails, for example on disk full, and the writer is kept open: if the caller closed the failed call's readers, later addIndexes(CodecReader...) calls with valid readers throw AlreadyClosedException until the writer is rolled back or closed; if the readers are still open, the next call runs a useless extra merge whose segment is never added and is deleted at close; with the default policy and ConcurrentMergeScheduler the only path found is a Thread.interrupt while CMS stalls the addIndexes thread, and then the later call succeeds and only a background merge thread fails; tiny scale, every release 9.4.0-10.6.0 and main, -ea and -da alike; no index damage and no document of the failed call becomes visible.
Summary
You call addIndexes(CodecReader...) with a merge policy that turns the readers into several merges and with SerialMergeScheduler, and the first merge fails (for example disk full); the call throws, adds nothing, and the writer stays open and not tragic. You expect that failed call to be over, so you close its readers and later call addIndexes with other, valid readers, which should merge exactly those readers. Instead the failed call's unstarted merges are still in the writer's shared addIndexes queue, so the next call runs them first and throws AlreadyClosedException 'this IndexReader is closed', leaving its own merge queued in turn, so later calls keep failing this way until rollback() or close(); if you kept the old readers open, the next call silently runs the stale merge and writes a segment that is never used.
