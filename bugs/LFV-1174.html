An Error while IndexWriter aborts the queued segments of a failed flush hangs its self-close forever

If an Error, in practice an OutOfMemoryError, hits IndexWriter while it throws away the queued in-memory segments of a failed flush, the clean-up loop stops halfway and the rest stay marked as flushing. The writer's own self-close then waits for them forever: DirectoryReader.open(writer) never returns, in every release since 7.4.0.

The finding in 30 seconds

#

Background: how IndexWriter flushes

#
  1. Each indexing thread fills its own in-memory segment (inside Lucene: a DWPT). Three threads indexing at once give three of them.
  2. A full flush (DirectoryReader.open(writer), commit(), flush()) checks them all out, registers each in a set of flushing segments and queues them. A segment leaves that set only through one method, doAfterFlush.
  3. After any Error, IndexWriter closes itself. Part of that close waits until the set of flushing segments is empty.

The finding, step by step

#
  1. Three threads call addDocument at the same time on one IndexWriter with the default config, so the writer holds 3 in-memory segments of 1 document each.
  2. DirectoryReader.open(writer) flushes all 3. Writing segment 1 fails with an OutOfMemoryError (the repro simulates it in IndexOutput.close()), so the writer throws away segments 2 and 3.
  3. You expect what the IndexWriter javadoc promises: the open throws the Error and the writer closes itself. On 7.3.1 an earlier, longer version of this test passes: the open throws and the writer is closed.
  4. Instead, a second Error while throwing away segment 2 ends the clean-up loop, which catches only Exception. Segment 3 is never released and stays registered as flushing.
  5. The self-close waits until no segment is flushing, so DirectoryReader.open(writer) never returns: the repro times out after 20 s, with assertions on and off.

Who is affected

#

Applications that index from several threads and open NRT readers on the default configuration (commit and flush reach the same code), and keep the JVM running after an OutOfMemoryError. The thread hangs silently and the writer's self-close never finishes. It needs a failed full flush with 3 or more in-memory segments, then an Error at that step: rare.

Mechanism, terms and numbers433 words

When several threads index into one IndexWriter, each holds its own in-memory segment. A full flush (DirectoryReader.open(writer), commit(), flush()) queues them all. If flushing the first one fails, DocumentsWriterFlushControl.abortPendingFlushes aborts the rest, but it wraps each abort in catch (Exception _). An Error thrown while aborting one of them (in practice an OutOfMemoryError) ends the loop: the segments it has not reached stay registered in flushingWriters, and nothing ever removes them. IndexWriter then closes itself, as it documents for any Error, and that close waits in waitForFlush for those segments forever, so DirectoryReader.open(writer) never returns. Until LUCENE-8215 (2018, first release 7.4.0) the loop caught Throwable to "keep on aborting the flush queue". Every release since is affected. It is realistically OutOfMemoryError-only, so it is Low priority.

The bug, step by step (main 5adff78bb168)

#
  1. Three segments queued. DirectoryReader.open(writer) -> IndexWriter.getReader -> flushAllThreads() (IndexWriter.java:586). markForFullFlush checks out every segment with documents; checkOutForFlush adds each to flushingWriters (DocumentsWriterFlushControl.java:427, :437-441) and all go into flushQueue (:626).
  2. The first flush fails. maybeFlush takes segment 1 from the queue (DocumentsWriter.java:494) and flushes it; IndexOutput.close() throws, and doFlush's finally releases segment 1 with doAfterFlush (DocumentsWriter.java:577). Segments 2 and 3 are still queued and registered. Any throwable in a segment's flush is an aborting exception, so the writer is already tragic here (DocumentsWriterPerThread.java:585-603); an IOException would do as well.
  3. The abort loop meets an Error. getReader calls finishFullFlush(false) (IndexWriter.java:669-671) -> abortFullFlushes (DocumentsWriter.java:738) -> abortPendingFlushes (DocumentsWriterFlushControl.java:694-723). Aborting segment 2 closes its open stored-fields writer through IOUtils.closeWhileHandlingException (StoredFieldsConsumer.java:112-113), which rethrows Errors on purpose ("we ensure that we bubble up any errors", util/IOUtils.java:155-178).
  4. Segment 3 is stranded. catch (Exception _) (:700, and :712 for blocked flushes) does not take the Error. The per-entry finally releases segment 2 only, the Error leaves the loop, and the outer finally clears the queue (:718-722) while segment 3 is still in flushingWriters. Only doAfterFlush (:298-301) removes it, and nothing will call it.
  5. The self-close waits forever. getReader's catch (Throwable) marks the Error as tragic and runs maybeCloseOnTragicEvent (IndexWriter.java:711-722) -> rollbackInternalNoCommit -> docWriter.abort() (:2635) -> waitForFlush() (DocumentsWriter.java:226), an untimed wait() while flushingWriters is not empty (DocumentsWriterFlushControl.java:361-369).

A RuntimeException thrown at the same point is caught and the open returns promptly, with no hang (the controls of the cross-model reviewers; 1.3 s in one), so the catch (Exception) boundary is the defect.

Exposure and likelihood210 words
  • Who. Multi-threaded indexing (IndexWriter is documented as "completely thread safe", IndexWriter.java:167) with NRT reopen, commit or flush, on the default configuration; the injected Error is a fault, not a setting.
  • Effect. A silent hang, not an exception: the thread that opened the reader blocks forever [exec]. By reading only: commit() (IndexWriter.java:3875, :3879) and flush() (:4411, :4427-4434) reach the same loop. Executed by the fact check's probe: any later rollback() or close() of that writer never returns either, because the hung self-close has already set closing (:6102, :1379), so they wait in shouldClose(true) -> doWait() (:1387, :5867).
  • Data. The hang comes before the write.lock release (:2635 runs before :2684), so the last commit on disk is untouched, write.lock stays held in that JVM until the process exits, and buffered documents are lost, as in any tragic close [read].
  • Scale. Three in-memory segments and one Error; no size threshold; it does not depend on assertions.
  • How rare. Contrived: a full flush must fail, then an Error must hit the abort of a queued segment that is not the last one. Many servers exit the JVM on OutOfMemoryError. No report of this hang was found since 7.4.0.

Minimal repro

#

One JUnit test method, public classes only, default config (default codec pinned). Three threads each add one document at the same time (a latch holds them, so there are 3 in-memory segments); then every IndexOutput.close() throws a simulated OutOfMemoryError and the test calls DirectoryReader.open(writer). @Timeout(20 s) is the hang oracle. Deterministic; fails with assertions on and off.

The same method is the regression test (it fits next to TestIndexWriterOnError). With a fix it passes in under 1.5 s. Older releases need more than package renames: FilterIndexOutput first shipped in 9.6.0 (GITHUB-11868, #11958), so before 9.6.0 wrap IndexOutput by hand, as the hunt's earlier, longer test for 7.x/8.x does; on 7.x/8.x the test framework package is org.apache.lucene.util, and on 7.x RAMDirectory replaces ByteBuffersDirectory.

The fault is harsher than a natural one-off OutOfMemoryError: once fail is set, every IndexOutput.close() throws. By reading, the hang needs only a failed flush of the first segment (any exception) and then one Error while a queued segment that is not the last is aborted. During the hang writer.isOpen() already returns false (IndexWriter.java:6117-6118), so it does not show that the close finished.

The timeout report also lists a leaked thread (the test thread still parked in waitForFlush) and a stdout-limit failure (the timeout's thread dump); both are consequences of the hang.

Why it looks unintended

#
  • The IndexWriter javadoc promises that after an Error the writer "will close itself"; here that close never finishes.
  • abortPendingFlushes was created (LUCENE-4277, 2012) to stop exactly this kind of rollback hang, catching Throwable to "keep on aborting the flush queue".
  • LUCENE-8215 (2018) narrowed it to Exception without discussing this loop; the fix still lets the Error propagate.
The full argument243 words
  • Contract. "if you hit an Error, or disaster strikes during a checkpoint then IndexWriter will close itself. ... Any subsequent calls will throw an AlreadyClosedException." (IndexWriter.java:162-165). getReader implements this for every Error (:711-722).
  • Purpose of the loop. LUCENE-4277 (#5345, b26dd733f77, 2012; CHANGES: "Fix IndexWriter deadlock during rollback if flushable DWPT instance are already checked out and queued up but not yet flushed") created abortPendingFlushes with catch (Throwable ex) { // ignore - keep on aborting the flush queue }. LUCENE-4989 (#6053) and LUCENE-5002 (c0e7a50ab8e, 2013) moved doAfterFlush into a per-entry finally so a failing abort could not skip the release.
  • The narrowing. LUCENE-8215 (#9262, 2e35ef2b3da, 2018, "Fix several fragile exception handling places in o.a.l.index") changed both catches to catch (Exception ex). Its discussion is about the new IOUtils helpers and never mentions this loop. The same commit added IOUtils.applyToAll ("even if an exception is thrown. The first exception ... is re-thrown"), the shape of the recommended fix.
  • Precedent. Upstream fixed Error-induced writer hangs as bugs: #12654 (fixed by #12751, 2023, an Error during the tragic close left rollback() waiting forever) and LUCENE-7570, whose test TestTragicIndexWriterDeadlock throws an OutOfMemoryError from mergeSuccess and expects commit() to fail fast and close() to return.
  • Tests. TestIndexWriterOnError injects fake Errors from I/O but runs "just one thread" (:59 of the test), so it never queues three segments in one full flush; no upstream test pins the hang.
The devil's-advocate check133 words

The strongest case for "not a bug": LUCENE-8215 narrowed the catch on purpose so that Errors are not swallowed, and after an OutOfMemoryError the JVM state is undefined, so Lucene owes nothing. Also, it needs two faults in one flush.

Why it fails: the narrowing meant that Errors should propagate, and the fix keeps that (it rethrows the first Error after every segment is released); nothing in #9262 says cleanup may stop halfway. IndexWriter itself documents a self-close after any Error and treats every Error as tragic; a hang breaks that promise and leaves the writer unclosable. The repro uses no InfoStream and no writer-internal hook: the Error comes from IndexOutput.close(), the kind of directory-I/O Error that Lucene's own TestIndexWriterOnError injects. Needing two faults lowers the likelihood (hence Low), not the validity.

Suggested fix

#

Recommended Catch Error per entry, finish both loops, rethrow the first Error (fix A)

In abortPendingFlushes, also catch Error per segment, keep the first (later ones suppressed), finish both loops so every queued and blocked segment reaches doAfterFlush, then rethrow it (+11 lines with the import). The repro then passes with assertions on and off, and so do nine IndexWriter suites (77 tests, 4 @Nightly skipped).

+    Error firstError = null;
     ... for each queued DWPT, then each blocked DWPT:
         } catch (Exception _) {
           // that's fine we just abort everything here this is best effort
+        } catch (Error e) {
+          // keep aborting so every DWPT reaches doAfterFlush, rethrow below
+          firstError = IOUtils.useOrSuppress(firstError, e);
         } finally {
           doAfterFlush(dwpt);
     ... the outer finally clears flushQueue and blockedFlushes ...
+    if (firstError != null) {
+      throw firstError;
+    }
All options and trade-offs2 options · 470 words

Option A was built and checked through gradle on 5adff78bb168; option B is the pre-7.4.0 code, which the hunt ran on 7.4.0. IOUtils.applyToAll is not a drop-in: it rethrows the first throwable of any type (util/IOUtils.java:566-577), so it would turn today's ignored abort exceptions into failures.

Catch Error per entry, finish both loops, rethrow the first Error (fix A) (validated by the checks) (recommended)

Exceptions stay ignored as today. The hunt's variant with explicit addSuppressed is the same idea and passed the repro too.

If the full flush failed with an exception and the abort then hits an Error, finishFullFlush(false) now throws that Error in place of the flush's exception, as any throw from it does today.

Trade-offs

It swallows the abort's Error. The writer still closes itself, because the failed flush already made it tragic (DocumentsWriterPerThread.java:585-603), but if the flush failed with an IOException and the abort then hit an OutOfMemoryError, the OOM would be neither thrown nor recorded (the tragedy and the thrown exception stay the IOException; by reading), against LUCENE-8215's aim of not swallowing Errors.

Downstream note

#

Downstream, a service that catches OutOfMemoryError and keeps serving, instead of exiting, can be left with a hung indexing thread and a writer that never finishes closing, until the process restarts.

How it was found

#

Code reading of DocumentsWriterFlushControl: the exception handling of abortPendingFlushes was checked against the flushingWriters accounting that waitForFlush depends on. A JUnit test on public classes then witnessed the hang on main.

The method in full105 words

Method: non-formal (code reading, witnessed by an executable repro).

  • The finder asked which throwables can leave abortPendingFlushes and what each leaves behind in flushingWriters, the set waitForFlush waits on. catch (Exception _) lets an Error out, the outer finally clears the queue, and only doAfterFlush removes entries, so every segment after the one that threw stays registered.
  • DWPT.abort can throw an Error because IOUtils.closeWhileHandlingException rethrows Errors by design, and the tragic self-close after an Error runs waitForFlush.
  • The finder's first test threw the Error from an InfoStream; an independent reproducer then wrote the Directory-based test this repro is reduced from, with no InfoStream.

Hits applications on the default configuration that index from several threads and open NRT readers when a full flush fails and an Error, realistically an OutOfMemoryError, is then thrown while the writer aborts a still-queued in-memory segment that is not the last one: DirectoryReader.open(writer) and the tragic self-close it starts never return [exec, -ea and -da], and by reading the same happens through commit() and flush(); any later rollback() or close() of that writer never returns either, because it waits in shouldClose -> doWait for the hung self-close [exec: the fact check's probe, -da]; no scale is needed (three in-memory segments), and every release from 7.4.0 through 10.6.0 and main is affected.
Summary
Several threads index into one IndexWriter, so it holds three or more in-memory segments, and you open an NRT reader; the full flush fails, and while the writer aborts the segments still queued behind the failed one an Error (realistically an OutOfMemoryError) is thrown. You expect what the IndexWriter javadoc promises: after an Error the writer closes itself, DirectoryReader.open(writer) throws, and later calls throw AlreadyClosedException. Instead abortPendingFlushes catches only Exception, so the Error leaves its loop after releasing just the current segment, the segments it has not visited yet stay registered as flushing with nothing left to release them, and the writer's self-close waits for them forever, so DirectoryReader.open(writer) never returns.

The rest of the mechanism is older and was harmless while the catch took Throwable: the outer finally that clears the queues (LUCENE-4277, b26dd733f77, 2012) and the per-entry finally doAfterFlush (LUCENE-5002, c0e7a50ab8e, 2013).
